# 02 · 双实现对账一致会不会是同谋的假独立（Q2）

> 任务疑问：583 的 N1（prop_asof）、N3（与 metrics_collector 对账）、未来 N2（Python 闭包 vs SQLite 递归 CTE）都用"两个实现结果一致"当正确性证据。当两个实现共享同一解析器、同一 git 时间源、同一套字段语义假设时，对账一致提供的是独立性还是"同一错误犯两遍"？

---

## 1. common-mode failure：已被实锤，不是猜测

- **[ES6] Knight & Leveson 1986（IEEE TSE）**：对 N-version programming 做了实验评估，结论原文摘要即 "N-version programming must be used with care"——多版本**失败高度相关**，并不独立。
- **[ES7] Hatton 1997《Safety in Numbers?》**（二手/一方称）：同样指出相似程序在相似输入上倾向于一起失败。
- **关键判据**：独立性的来源**不是"两个实现"这个数量**，而是"不同的错误假设"。若两个实现共享解析器、时间源、字段语义假设，它们会**系统性地在同一类输入上犯同一个错**——这就是 common-mode，对账一致恰好把"同一错误"伪装成"互相印证"。

---

## 2. 独立第二实现判据清单（criteria）

判定"两个实现对账一致"是否算独立证据，逐条打分：

- **C1 异解析器**：是否用不同的 YAML/JSON/数据解析实现？（同用 `parse_frontmatter`+PyYAML 则违）
- **C2 异时间源**：是否来自不同的 git 引用 / 不同的时钟 / 不同的提交视角？（同用 `git log -1 %cI` 则违）
- **C3 异字段语义假设**：对"同一事实"的定义是否不同？（例如一个认 `verified_by_oracle` 版本号、另一个认 frontmatter 哈希）
- **C4 异进程/异语言**：故障域是否隔离？（同进程 `import` 调用则违）
- **C5 异数据源**：是否不共享同一个文件/数据库？（同读 `propositions.db` 则违）
- **C6 异人/异模型产出**：产出方故障是否不相关？（同一个人/同模型生成则违）

**判等**：满足 C1+C2+C3 且 **C5 不违** → "弱独立"（可当交叉校验，但仍同源风险）；满足 C4/C5/C6 任一条 → "强独立"。否则**不算独立**，只是一致性自检。

---

## 3. N1 / N2 / N3 逐条判定（代码实测）

### N1 · `prop_asof.py` 四轴视图 vs `prop_graph.py`
- 两者都读 `data/propositions.db`（`prop_asof._props` L85–101；`prop_graph` 同源 sqlite `mode=ro`）→ **违 C5（同数据源）**。
- 都用 `git log -1 --format=%cI` 取断言时间（`prop_asof._git_commit_iso` L48–57）→ **违 C2（同时间源）**。
- 都从卡的 frontmatter 解析 `verified_by_oracle` / `anchor_source` → **部分违 C3（同语义）**。
- **判定：连弱独立都不算，只算"同一视图查两遍"。** N 档：在文档里明确降格为"只读视图"，**不得宣称"独立校验"**。

### N2 · Python 闭包 vs SQLite 递归 CTE（规划中）
- 异语言/异进程 → **满足 C4**。
- 但同读 `propositions.db` → **违 C5**；同字段语义假设 → **部分违 C3**。
- **判定：中弱独立**，比 N1 好（故障域隔离），但**仍是同数据源**，common-mode 未根除。
- N 档：可保留作"实现层冗余"，但报告措辞须写"同数据源冗余，非独立证据"。

### N3 · `metrics_collector.py` 与 gate/poison/replay 对账
- `collect_quality` **进程内** `import gate_engine as ge; ge.run()`（L130–137）→ 与 gate **同一进程、同一份代码**。
- `pd.drill()`（L148）/ `replay` 子进程（L157）→ 还是**同一批工具自己**。
- **连 C4 都不满足（同进程/同源）**，common-mode 满分。
- **判定：只算"自描述度量 / 趋势采集"，绝对不算"跨实现正确性核对"。**
- N 档：在 `metrics_collector` 文档与 `DELEGATION_SWITCHES`（L337，已全 OFF）旁明确：**采集器永远不进判决路径**，对账一致仅用于"趋势"，不用于"证明正确"。

---

## 4. 结论

> N1/N2/N3 **当前都不构成"独立第二实现"**。N2 最接近（异语言/异进程）但仍是同数据源；N1 是同视图查两遍；N3 是对自己对账。要拿到真独立，必须引入**异数据源**（人持清单 / 异仓库 / 异模型重算）——这恰是 Q1 第 3 节"真正异质第二锚"的同一条路。

**最小加固（N 档，不引入密码学/服务器）**：在每一处"双实现对账"的文档与报告里，用上面的 C1–C6 清单标注它满足哪几条、不满足哪几条，并据此选用措辞（"只读视图" / "同数据源冗余" / "自描述度量"），**禁止**统一写成"独立校验 / 互相印证"。
