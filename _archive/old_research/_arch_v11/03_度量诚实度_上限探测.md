## 二、行为级 covered 还能被怎么伪造（逐类核验）

当前 covered 取自 drill 运行时 who 集合。可能的伪造路径：

1. **进程内 monkeypatch who**：在 drill 收集循环里把目标规则 ID 塞进每条 payload 的
   who —— 与 564 PoC#1（进程内把 check 置空）同属"进程内自篡改"类。该类攻击
   【已查证】可行且已有 PoC 范式（_arch_v7/probes/poc1_rule_supply_chain.py，
   文件存在本轮 LS 已证）。**模型内无法结构性消灭进程内攻击**：Python 进程内一切
   皆可改。缓解边界：tool_integrity 在三入口 enforce（gate_engine.py:3647），
   篡改代码不重签即拒绝运行——但 monkeypatch 不改磁盘文件，checksum 查不到，
   这是解释型语言的结构性盲区。
2. **篡改 gate 返回值（in-memory）**：同上，属 PoC#1 同族，不构成新攻击面。
3. **跨进程/盘上伪造**：本轮核验 who 数据不持久化（drill 内存收集，surface_map
   只写 name/pass/type），故没有"改盘上 coverage 文件"这条路径。
   （surface_map 手工 --write-surface-map 才落盘，poison_drill.py:2365-2368。）
4. **豁免台账伪造**：新豁免缺签名 fail-closed 已实现；但**台账文件本身可直接编辑**
   ——攻击者加一条 date≤2026-09-18 的 legacy 行即获豁免（legacy 无签名要求）。
   这是【已查证】的残余口子：legacy 截止日是硬编码的，任何回溯日期行都归 legacy。
   实践中只能靠 git diff 审查（台账改动必现），无机器闸。

## 三、模型上限态

1. **"谁来度量度量者"——模型能建元层，但元层仍在同一信任根内**：
   - 可建的元度量：① coverage 自身的可伪造性自检（已有幽灵自检雏形，可扩成
     "covered 规则在 drill 全 run 中必须出现≥1 次真 block/warn 命中"的强校验）；
     ② 度量新鲜度闸（575 已恢复采集，投喂词）；③ 豁免台账改动的机器报警
     （git diff 新行规则化检查）。
   - 不能突破的：元层工具自身仍可被 monkeypatch/重签（585 Q1"第二锚不独立"，
     【一方称】，本轮读到机制同意该判断：所有工具同仓同进程，enforce 在
     tool_integrity.py:104，而 tool_integrity.py 自己不在 CORE_TOOLS 里——
     【已查证】CORE_TOOLS 列表 gate...：CORE_TOOLS（tool_integrity.py:40-46）不含
     tool_integrity.py 自身。即"校验者不自校"是设计声明的递归边界，靠 git 兜底。
2. **阴阳载荷完备性可做到按规则枚举**：当前 83 阳/41 阴，阴性不是每规则配对
   （41 条阴性多为"声明完整须放行"的形态类对照，surface_map negative_controls
   结构为 name/pass/type）。模型能写脚本输出"每规则：阳性数/阴性数/缺阴性清单"，
   但"阴性对照设计完备"无理论上限——对一条 block 规则，阴性至少需要"同形良性
   变体"，当前部分规则（如 EV-ZERO-DIAG-WERROR 等零命中规则）连阳性都是合成
   pytest 而非端到端载荷。
3. **覆盖率定义争议——我的判断**：
   - 对**自查/回归**场景：诚实覆盖率（行为命中 ∪ 机器核验背书）最诚实，表观率
     只适合暴露虚高，应禁止单独展示。
   - 对**攻击面**场景：按规则严重度加权会引入主观权重（block/warn 严重度本身是
     人定），单用户下加权率不如直接报分子分母。
   - 系统当前做法（两个率都报、分母强制、n=0 拒答，stat_bounds.py:34-49）
     已到模型可设计的诚实机制上限；再往上是"独立第三方核验"，单用户结构性缺失。

2. **"度量驱动行为"的风险（当前未讨论）**：一旦覆盖率/逃逸率成为考核信号，就有

   核心可信度指标保持"不可优化"——逃逸清单逐条定性而非只报率。当前系统事实上
   就是这么做的（escaped_list 全列），这是好的设计本能。
