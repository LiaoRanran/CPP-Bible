# 06 方向 6：落地路线图与分阶段实施方案

> 基于 01-05。每阶段给：目标 / 交付物 / 工具 / 验收 / 依赖 / 风险 / 成本-收益。标注【已查证】/【一方称】。

---

## 6.1 阶段划分

### 阶段 0：基线与评估（无代码改动）
- **目标**：确认 replay 现状、编译可复现性、TLA+ 工具链可行性。
- **交付物**：读码报告（状态机/锁/重编译不变量）+ 编译可复现基线（见 05 §5.2 探针）+ TLA+ 工具链可行性（Windows 装 tlc 需 Java）。
- **工具**：只读 `--check`、git status、probe 脚本（临时目录）。
- **验收**：状态机建模完成（01）、探针实证完成（05）。
- **依赖**：无。
- **风险**：低（全程只读）。
- **成本-收益**：成本低（已做），收益高（纠偏：轻量 TV 已存在）。

### 阶段 1：编译可复现性审计（纯标准库，最小落地，性价比最高）★ 若只做一件选它
- **目标**：把"编译可复现"从隐含假设变显式可证属性；升级 `_recompile_invariant` 为"跨时间窗口 + 符号表/段一致"。
- **交付物**：`tools/build_reproducibility.py`（或集成进 replay） + 跨时间窗口探针 + "编译可复现率"指标 + 不可复现卡待修复清单。
- **工具**：纯标准库 + g++/nm/readelf/diffoscope（可选）。**零新语言、零 SMT**。
- **验收**：N 张卡中 M 张可复现；不可复现卡有明确差异报告（diffoscope 段级）。
- **依赖**：无（独立）。
- **风险**：低。唯一难点是 3 个时间宏夹具 + 多 TU 链接顺序（05 §5.3），需补 `SOURCE_DATE_EPOCH`/`-ffile-prefix-map`。
- **成本-收益**：成本小，收益高。

### 阶段 2：replay 状态机 TLA+ 建模与模型检查（需学 TLA+，中成本）
- **目标**：把隐式状态机变显式规格，TLC 检查关键不变量（I1/I4/I5/I7）。
- **交付物**：`docs/formal/replay_state_machine.tla`（PlusCal 写主流程 + 纯 TLA+ 补锁/公平性）+ TLC 检查报告。
- **工具**：TLA+ Toolbox / tlc（Java 运行时）。
- **验收**：TLC 通过（不变量成立）或发现并修复 bug（如 04 §4.3 单卡异常中断整批）。
- **依赖**：无（独立）。
- **风险**：中（TLA+ 学习曲线；Windows 装 tlc 需 Java）。
- **成本-收益**：成本中，收益中-高（防回归 + 活文档）。

### 阶段 3：轻量级翻译验证（纯标准库，基于阶段 1）
- **目标**：replay 判定增加"翻译验证"维度（重编译不变量 + 符号表 + 关键段一致）。
- **交付物**：replay inspection 点 + 失败 → `infra_error` 分支 + 报告。
- **工具**：纯标准库 + nm/readelf。
- **验收**：replay 的 confirm/refute 增加 TV 维度；TV 失败卡有报告。
- **依赖**：阶段 1（符号表/段比对基础）。
- **风险**：低。
- **成本-收益**：成本中，收益高。

### 阶段 4：中量级翻译验证（需 GIMPLE IR，中-高成本）
- **目标**：g++ `-fdump-tree-all` 导出 GIMPLE，比对不同优化级别差异，验证"优化未改可观察行为"。
- **交付物**：GIMPLE 比对报告 + 改变可观察行为的卡入待审查。
- **工具**：g++ `-fdump-tree-all`（自带）+ 自写 GIMPLE diff（纯标准库难，需投入）。
- **验收**：N 张卡 GIMPLE 比对报告。
- **依赖**：阶段 3。
- **风险**：高（GIMPLE 解析/diff 复杂）。
- **成本-收益**：成本大，收益中 → 优先级靠后。

### 阶段 5：重量级翻译验证（需 SMT，高成本，远期/不做）
- **目标**：Alive2/Souper 验证具体编译优化。
- **工具**：LLVM + Z3。**本项目 g++/MinGW 非 LLVM + 纯标准库无 Z3 → 结构性不可行**。
- **验收**：不适用。
- **依赖**：换用 clang/LLVM（重大决策）。
- **风险**：极高（技术栈不兼容）。
- **成本-收益**：收益极低 → **建议不做**。

## 6.2 阶段依赖图
```
阶段0 ──┬─→ 阶段1 ──→ 阶段3 ──→ 阶段4
        └─→ 阶段2 (独立) ──→ (可选) 阶段5[不建议]
```
- 阶段 1 是阶段 3 的前提（TV 需要可复现基础）。
- 阶段 2 独立（状态机建模不依赖可复现性）。
- 阶段 4 依赖阶段 3。
- 阶段 5 结构性不可行，留远期。

---

## 6.3 关键决策点（需用户裁决）
1. **是否引入 TLA+ 工具链**（阶段 2）：需装 Java + tlc，学习 1-2 天。建议先做阶段 1（零成本）再评估。
2. **是否做中量级 TV（阶段 4）**：GIMPLE diff 投入大，收益中，建议暂缓。
3. **是否换 clang/LLVM 以启用 Alive2（阶段 5）**：重大技术栈决策，与本项目 g++/MinGW 基调冲突，**不建议**。

## 6.4 与 601 供应链溯源层集成
- 翻译验证结果作为 in-toto `replay_verify` step 的 **inspection**（参考 600 的 in-toto layout 设计）。
- 编译可复现率作为 **SLSA 溯源元数据** 的一部分（build definition 的确定性证明）。

## 6.5 与现有 replay/metrics/gate 集成
- **replay**：阶段 1/3 直接改 `atom_evidence_replay.py` 的 `_recompile_invariant` 与 verdict 分流（仍 fail-closed）。
- **metrics**：新增"编译可复现率""TV 通过率"；写入现有 metrics 流水线。
- **gate**：将"编译可复现率 < 阈值"作为 gate 的 warn/block 规则（参考 gate_engine 63 条规则机制）。

---

## 6.6 测试策略（每阶段怎么验证有效）
- 阶段 1：对 3 个时间宏夹具 + 多 TU 夹具做"跨时间窗口 + 真实命令"复跑，确认可复现或给出差异。
- 阶段 2：TLC 模型检查报告 + 制造已知 bug（如删一处 `finally` 还原）验证 TLC 能抓到。
- 阶段 3：注入"工件被篡改"场景，验证 TV 维度能判 `infra_error` 而非误 `confirm`。
- 阶段 4：选 1-2 优化敏感夹具，比对 -O0/-O2 GIMPLE，确认差异仅在不可观察部分。
