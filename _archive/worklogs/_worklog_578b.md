## 5 · 复现性对照（全量 ×2，跑前各清空 manifest）

见 `_rep578.log`（后台脚本 → `data/mutation/_578_repA.json` / `_578_repB.json`）。
判读口径：**两次逐算子一致 ⇒ 清态跑是确定的**；**不一致 ⇒ 还有别的源**。

**结果：两次逐算子完全一致，且与已提交的 v5 逐字一致。**

```
run A（manifest 已清空）: blocked=989（严格 619） escaped=9 n_a=185
run B（manifest 再次清空）: blocked=989（严格 619） escaped=9 n_a=185
逐算子对照: M1 64/1/27 | M2 168/0/27 | M3 65/0/42 | M4 200/0/33
            M5 29/0/56 | M6 324/8/0 | M7 139/0/0      ← 两次完全相同
两次全量逐算子一致: True
```

⇒ **三条结论**：
1. **清态（manifest 空）跑是可复现的**，且**已提交的 `full_baseline_v5.json`（989/9/185、M5 29/0/56）正是这个值**
   ⇒ 578 的交付**站得住**，不需要改数。
2. 那次 991/7 的离群跑，**唯一差别是它继承了上一次跑残留的 `build/replay_manifest.json`**
   ⇒ **跨跑携带的 replay 增量状态是运行间方差的来源**（§4-1 从假设升为**强证据**）。
3. 由此，M5 strict 3/0、M6 8/6、strict 212/211 这三次抖动应同源（都只在"继承状态"的跑里出现）。

> 备注：`build/` 在 `.gitignore:9`（manifest 是构建产物、不受版本控制）⇒ 对照中"跑前清空"是安全的，
> 不影响任何受控文件；跑完工作树 `git diff --quiet -- data/mutation/ atoms/ evidence/` 仍 exit 0。

## 6 · 建议（交给监工裁决，不在本批动手）

* **给跑批工具加"确定性自检"**：`mutation_fuzz.py` 增 `--selfcheck-determinism`（或跑完对关键子集
  立即重跑一次逐变体比对），不一致就 **fail-loud** 打印"哪张卡的哪条 finding 抖了"。
  理由：这类非确定性**只能靠自证发现**——本批若不是"重跑一次核对提交产物"就完全看不见。

  若要彻底免疫亚毫秒改盘，可给写入方加 O(1) 的 `invalidate(path)` 并规定"进程内改盘必须调它"。

  不覆盖这种**运行间方差**（当前实测方差 ≥ 2/998）——这句话建议写进 `metrics_collector` 的 tag。

## 7 · 拟改法（**规格，未落码**——本批只出规格，改动留给下一批任务书）

> 纪律：判定核心（`tools/`）的改动需要监工任务书；本节只写"改哪个文件哪个函数 + 正反例测试长什么样"。

**M1（首件，直击 §5 结论）：让跑批工具不继承 replay 增量状态**
* 点：`tools/mutation_fuzz.py` 的 `sandbox()`（62 行）与 `classify()` 调 replay 的入口。
* 改法：跑批期间把 `atom_evidence_replay.MANIFEST` 指向**本次跑的临时副本**（`tmp/replay_manifest.json`），
  跑完丢弃；**不读、不写**仓库的 `build/replay_manifest.json`。
  理由：manifest 是"真卡未变 ⇒ 复用上次真编译结论"的**跨进程缓存**；跑批输入是**变异体**，
  复用语义对它无意义（变异体指纹每次不同 ⇒ 永远不会被合法复用，只会受**别人留下的条目**影响）。
* 正例测试（应绿）：`test_578b_manifest_is_isolated`——先在真 manifest 里塞一条**伪造/异源条目**
  （或用一次小跑把 manifest 填脏），再跑同一个变体，断言判定与"manifest 清空"时**逐字段相同**。
* 反例测试（应红，锁住旧病）：同一输入在"manifest 脏"与"manifest 空"下各跑一次，断言两者**必须一致**；
  在旧代码上这条会红 ⇒ 本机制可证伪。
* 存量误伤预估：**0**（manifest 是 gitignore 的构建产物；不动任何规则、不改判定口径）。

**M2（可选，便宜）：`_meta` 注释收紧 + `invalidate(path)` 口子**
* 点：`tools/gate_engine.py:198`（注释）、`_meta`（217）、`_fm_hardening_hits`（1301）。
* 改法：注释改成"窗口为亚毫秒级（实测同尺寸改写 0ms 间隔 9/12 相撞、≥0.5ms 0/12），工具内写入间隔远大于它"；
  另加 `invalidate(path) -> int`（O(1) 摘该路径条目）供进程内改盘的写入方显式调用。
* 测试：写同尺寸变异体 → `invalidate` → 断言 `_meta` 读到**新**内容；不 `invalidate` 的对照用例锁"旧注释过强"这一事实。
* 影响：gate 属 CORE_TOOLS ⇒ 需同 commit 重钉 `.tool_checksums` + 重跑 gate/poison/replay/fast/slow。
