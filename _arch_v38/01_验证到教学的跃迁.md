> 所属：`_arch_v38_brief.md` 方向 1。检索日期：2026-09-28，来源编号见 `99_来源清单.md`（本篇引 D1-S1–S14）。

## 1. 一句话结论

**验证与教学的差别不在界面，而在判决信息被如何使用：只给四态结果就是"验证"（assessment of learning，终结判定）；把结果转成"为什么错+例外点+补救路径+再练机会"才是"教学"（assessment for/as learning，形成性回路）。阙疑不需要新建一个课程平台，需要给现有每张卡加一条"判决→反馈→补救→复测"的信息回路。**

---

## 2. 本质区别：目标函数不同

| 维度 | 验证系统（阙疑现状） | 教学平台（阙疑目标） |
|---|---|---|
| 目的 | 判定命题真伪 / 对 LLM 回答定级 | 促成学习者持久的能力变化 |
| 时机 | 学习终点、抽样审计 | 学习全程、高频嵌入 |
| 输出 | 四态 + 规则命中 | 反馈（任务/过程层）+ 下一步 + 再练 |
| 对 fail 的处理 | 记录、拦截、fail-closed | 诊断归因、补救、间隔复测 |
| 对 unknown 的处理 | 不猜测、升级人审 | 再采证：请求学生更多表现证据 |
| 成功指标 | 逃逸率、误判率 | 无辅助复测通过率、同错误不再犯率 |

- 形成性评估促进学习为【强】证据：Black & Wiliam《Inside the Black Box》综述约 250 项研究，典型效应 0.4–0.7 SD，低分学生收益最集中 [D1-S1]；但独立再检验（Kingston & Nash 2011）中位效应仅 0.25，本篇方向 06 详述。
- **关键操作结论**：同一张验证卡可以同时服务两种用途，差别只在结果信息被如何使用 [D1-S2]。这意味着教学化改造的最小单元不是"做课程"，而是"改造卡的结果页"。

## 3. 三个参照平台的真实模式（2024–2026）

| 平台 | 核心循环 | 对"卡住"的解法 | AI 立场 |
|---|---|---|---|
| Exercism | 做题 → 自动分析器 → **真人志愿者导师 code review** → 社区解法对比 | 靠人；刻意无排行榜/无分数 | 平台不内建 AI（2025 维护者："当目的是学习时，Copilot 会拿走问题解决这个环节本身"）[D1-S6] |
| LeetCode | 刷题 → 讨论区题解 → 面试 | 靠 AI 降摩擦：2025 年上线 Ask Leet（思路/优化/测试/调试，多模型可选）[D1-S7] | 全面拥抱，应试效率导向 |
| Codecademy | 浏览器内写真实代码 → 即时反馈 → Skill/Career Path | 结构化路径 + AI Learning Assistant（2024 起：Explain code、错误根因、渐进提示）[D1-S9] | AI 助教 + AI 原生课程（2025–26 含 Vibe Coding 系列）[D1-S10] |

- Exercism：82+ 语言轨道、约 200 万用户（第三方口径）[D1-S4]；2024 年试水 Teams（师生进度追踪）[D1-S5]。
- 三家共同趋势是**把"学习者卡住的时间"视为首要优化对象**，分歧在靠人还是靠 AI、AI 给答案还是给支架。三家教学成效没有头对头 RCT【盲区】。
- 对阙疑的直接含义：Exercism 路线（真人、非竞争、刻意练习）最贴合"验证严肃感"，但单人项目无法供给真人导师；可借鉴其"非竞争 + 反馈聚焦"，把导师角色交给**被验证的规则与真机**而非无护栏 AI。

## 4. 教学产品的最小件：教学可行性 + 反向设计

- **EdTech MVP ≠ 功能最小集**：最小版本必须具备"教学可行性（instructional viability）"——能证明自己促成了某一具体学习结果。方法：从一个具体的"核心学习转变"（具体学习者 + 具体能力变化）出发，锁定微人群，保证"讲解→支架练习→及时反馈→有意义评估"闭环；可用 Wizard-of-Oz 人工交付验证需求；用学习结果而非 DAU 衡量 [D1-S12]。
- **反向设计（Backward Design, Wiggins & McTighe）三阶段** [D1-S13][D1-S14]：
  1. 确定预期结果（区分"持久理解的大概念 / 需掌握的知识技能 / 值得了解"三层）；
  2. **先于教学活动**确定可接受的掌握证据（评估设计）；
  3. 再规划学习体验。
  - 核心收益是目标—评估—活动三者的"一致性"；避开"活动导向"（动手但无目的）与"覆盖导向"（灌输—测验—凭运气）两宗罪。

## 5. 阙疑现有资产的教学化盘点

| 资产 | 教学用途 | 改造需求 |
|---|---|---|
| 37 张验证卡 | 天然的"正反例 + 真机证据"教学单元骨架 | 补概念最小讲解与再练题；结果页从"判决"改为"反馈+出路" |
| 67 条规则 | 领域知识的权威判据 | 需翻译层：规则术语→学习者语言（feed back 具体化） |
| 452 条改判账本 | "LLM 判错→人纠正"的真实错误案例库（方向 07 主菜） | 案例叙事化 + 错误分类标签（概念误解/slip/知识缺失） |
| 42 误解节点 | 反例与反驳文本的锚点（仓库 `Index/MISCONCEPTIONS.md` 已实读，现 55 条且持续扩充） | 命中误解后接入差异反馈，而非一律重讲 |
| fail-closed / unknown | 教学纪律：证据不足不猜测 | unknown → 触发"再测一题"，不判学生 fail |
| 真机编译 / 现场验哈希 | 可亲手复算的可信演示 | 增加"换编译器/优化级别对比"（方向 08） |

## 6. 阙疑应该怎么做（3 条）

1. **先改造一张卡的结果页，而不是做一门课**：四态结果改为 comment-only 反馈——指出具体违反的规则（过程层）、例外点（pass_with_exception）、对应的误解节点、一道再练题；这是 Backward Design 第 2 阶段"先定掌握证据"的最小落地，也是成本最低的教学化动作。
2. **MVP 定义为"一张卡的完整掌握闭环"**（概念最小讲解 → 正反例真机对照 → 主动回忆测试 → 四态反馈不给分 → 间隔复测），用 7 日后无辅助复测通过率验收，而非注册量；选一张高频误解对应的卡（建议从内存/指针类中选，见方向 02 的盲区处理）。
3. **产品定位保持"验证器长出教学层"，不做"课程平台"**：课程、社区、游戏化全部后置；所有教学内容必须能被阙疑自己的门禁复算——教学化是给判决加回路，不是给系统换身份。
