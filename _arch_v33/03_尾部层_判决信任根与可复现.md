## 0. 阙疑尾部层现状（本仓库实读）

- 判决：gate_engine 四态（pass/fail/unknown/abstain）+ 带例外；DAL A–E 失效后果分级决定人审。
- 保护器：B1 冲突（唯一改判）/B2 anti-windup/B3 盲审/B4 校准/B5 MDL；真实触发≈0、B4 饱和（647 自登记）。
- 信任根：tool_integrity（CORE_TOOLS=5，缺文件曾只 warning）、verifier_closure=23 文件（不含 67 规则/PCK schema/账本锚/证据索引）、Merkle/in-toto/OTS（外部锚缺失，独立性 L2 未达 L3）、decision ledger 452 事件、authority log v2。
- 数据：37 卡 PCK（sha256 + M1–M7 变异 + cs_upper_bound）。
- 微内核：813 行纯逻辑核心（brief 口径），queyi-core 拆分有"两份并列"债。

**总判断**【推断】：2024–2026 工业界在尾部层做的全部主要动作，可归纳为一句话——**把"相信我"换成"给你一个可独立重算的东西"**：判决在加粒度（条件化/有界化），保护器在加位置（工具门/shadow/熔断），信任根在缩小并下移到硬件（CVM），透明账本在换后端（tile/checkpoint），复现从口号变成 L4 准入项（SLSA），而知识内容的 provenance 标准（C2PA/W3C VC/RATS/in-toto）已经成熟到阙疑只需对齐词表。

## 1. 判决模型：四态之后，业界加的是"条件"和"粒度"，不是第五态

### 1.1 证据

- **Belnap 四值逻辑**（T/F/Both/Neither）是多源冲突信息系统的经典底座：冲突（Both）与未知（Neither）都是一等值。阙疑事实上把 Both 折叠成 fail（B1）、把 Neither 折叠成 unknown/abstain——工程上省事，但丢失了"两源都支持且互相矛盾"的显式态。
- 工程界 2025–2026 的判决枚举普遍是**四态或更多的条件态**：质量治理词汇表 assessed / partially_assessed / not_assessed / blocked，finding basis 用 verified / plausible / not_assessed / not_applicable，置信度独立成轴（high/medium/low/none）【一手 schema 实证】[S40]；测试执行工业标准（JUnit 五态）把 **aborted/skipped 独立出来**，skipped 再带 suppressed/assumption-violated 等子因——"跳过"不等于"失败"，假设不成立是放弃而非否定。
- 学术引文核查（SemanticCite）用 supported / **partially supported** / unsupported / uncertain 四档，partial 是独立判项而非折中 [S13]；自动核查（CAAFC）同构使用 supported/contradicted/unverifiable 并按多数证据聚合但允许标"时间外"[S8]。
- 形式化工具早给了第三类：Kani（Rust/CBMC 系）输出 **可证伪 / 给反例 / 资源耗尽（undetermined）** 三态 [v31-S26]；ESBMC 同构（successful / violation witness / 超时，bounded K 语义）[S23]。

### 1.2 对阙疑的硬映射【推断】

> **T1（落地动作）**：四态不动，补两个**正交轴**而非新态——
> 1. **条件轴（带例外的结构化）**：`pass` 可挂 `conditions[]`（编译器集合/标准版本/unwind K/平台），任何条件不满足时该证据不可用于本案判决（JUnit assumption 语义）；消灭"带例外"散文，例外必须是机器可判的谓词；
> 2. **粒度轴（partial 回滚）**：卡级 verdict 从原子 verdict 聚合——全 pass→pass；任一 fail→fail；mixed→`partial` 并强制附 failing atom ids（SemanticCite 式），卡判决从 partial 原子集上卷，不允许整体 pass 盖住局部 fail；
> 3. **冲突显式态**：B1 改判时账本记录原态为 `conflicting`（Belnap Both），不再是两个 pass 静默改一个 fail——改判可审计性立刻提高；
> 4. bounded/unverifiable 严格写作 `unknown(reason=bounded_K|resource|tool_absent)`，unknown 的原因枚举化（对齐 Kani 第三态），看板上 unknown 率与原因分布并列展示（v31 已定"挂起率不是失败"）。

## 2. 保护器：LLM agent 安全工业在 2025 年给出了完整谱系，阙疑 B1–B5 是其子集

### 2.1 三个边界 + 五种架构位置（2025–2026 收敛形态）

- agent 的攻击面与聊天机器人本质不同：从"说错话"变成"做错事"，防护必须独立覆盖**输入 / 工具 / 输出**三边界；OWASP LLM Top 10（2025 版）已把 prompt injection 列为第一风险，agent 化后风险高一个量级【二手汇编】[S42 区]。
- 防护层的五个标准位置：①pre/post 中间件（最简单）；②**工具级门**（每次工具调用前过三查：风险分级 read/write/destroy + 权限 + 参数白名单，拒野指针/负数/越界）；③人工中断-评审点（高风险动作）；④**shadow 模式**（异步旁路只记账不阻断）；⑤元规则"Rule of Two"（不可信输入/敏感数据/外部写出三类资源，单动作至多触及两类）[S41 区]。
- 开源参考实现：**LlamaFirewall**（PromptGuard 2 通用越狱检测 + **AlignmentCheck 实时审计 CoT 是否被目标劫持，首个开源此类防护** + CodeShield 代码风险）[S38]；商业参考：NeMo Guardrails（NemoGuard-8B 内容/主题/越狱三 NIM，3.5 万标注 42 类）[S42]。
- 工业纪律：纵深防御 = 堆叠互相独立的防护，不押单一防护；红队化常态化（攻击成功率 ASR 是规范指标），工具链 PyRIT/Garak/PromptFoo [S41 区]。

### 1.2 阙疑 B1–B5 在该谱系中的位置与缺口

| 阙疑保护器 | 工业对应物 | 状态 |
|---|---|---|
| B1 冲突检测 | 输出校验器 / policy enforcer（OPA 式） | 唯一改判，保留 |
| B2 anti-windup | 速率限制 / 预算闸门 / bulkhead | 保留，预算维度扩展（见下） |
| B3 盲审 | 输入消毒（间接注入防护的子集） | 保留，扩到品牌/年份（v31 已定） |
| B4 校准 | 漂移监控 + 自动降级 | 数学化（见 02 篇 §3） |
| B5 MDL | 准入控制器（admission gate） | 保留，候选规则走同一模式 |

> **T2（落地动作）**：补四个 B 系列保护器，全部有 2025 工业先例、全部是确定性组件（不许 LLM 自判）——
> - **B7 工具门**：白名单工具 + 参数 schema 校验 + 危险工具（写文件/执行命令/发请求）人审或双签；对应 647 A1 supply_chain 缺口从 warning 升级 fail-closed 的同款纪律；
> - **B8 shadow 轮转**：新规则/新模型/新变异器上线先 shadow N 批（只记账不生效），对比 incumbent 判定后才转执行——LlamaFirewall 的标准上线法，正好治"保护器真实触发≈0"（shadow 期间积累的是触发率分母与 FP 台账，不需要真实拦截先发生）；
> - **B9 熔断器**：连续异常（LLM 超时率/非法输出率/外部检索失败率）超窗即自动断开该通道并 fail-closed 到规则/人审，恢复需人确认（circuit breaker 模式）；
> - **B10 预算执行器**：LLM 调用预算与变异/取证轮次预算硬封顶（B2 从队列预算扩到 token/轮次预算），超限即 B9。
> 五新保护器与 B1–B5 同样遵守"确定性、可记账、可人审关停"三条件；B6（Sage 自审）按 v31 A2 排期。

## 3. 信任根：最小 TCB 的工业答案是"把 TCB 移出运营商、移进硬件，并持续测量它"

### 3.1 RATS 角色模型（阙疑信任根缺的词汇表）

RFC 9334 定义三角色与三类对象【官方，已实读 rfc-editor】[S43]：

- **Attester** 出 Evidence；**Verifier** 用 Reference Values + Endorsements + Appraisal Policy 对 Evidence 做 appraisal；**Relying Party** 按 Attestation Results 决定放行；
- 关键分离：**判决逻辑在 Appraisal Policy（RP 侧），Verifier 只产出结构化结果**——这正是"验证器闭包只含可复核机制、政策外置"的标准形态。阙疑当前 gate_engine 同时演两个角色，拆分时的目标架构已在 RFC 里。
- 信任传递靠 reference values（期望度量）+ endorsements（部件可信凭证），不是靠声明。

### 3.2 机密 VM（CVM）：2024–2026 已规模化，信任根从云运营商下移到 CPU 厂商

- 三大件：AMD SEV-SNP / Intel TDX / Arm CCA；机密 VM 无需改应用即获得内存与 CPU 态机密性/完整性，硬件签名报告替代 enclave 改造【实测综述，PACMMET 2024-12，42 页含 CVE/TCB 分析】[S44]。
- 远程证明三件套已工程化：报告由 vTPM / AMD Secure Processor / **TDX module（MRTD 度量固件、RTMR 运行时度量寄存器，用户态可扩展）**签名；nonce 防重放；可自验证或委托 Google Cloud Attestation / Intel Trust Authority；报告含启动链/内核/配置度量与事件日志【官方】[S45]。
- 边界诚实记录：TCB **缩小但非零**——CVM 自身有 CVE 史，host 被移出 TCB 后，CPU 固件/证明服务成为新 TCB；经验论文的方法学就是逐项列 CVE + 测性能代价 [S44]。
- 社区要点：可信不是单一实体，是**从硬件根开始逐环节验证的信任链**，靠签名报告 + nonce 新鲜性 + 平台度量比对建立 [S45 区]。

### 3.3 对阙疑的硬映射【推断】

1. 647 A3 闭包 23 文件太胖：按 RATS 词汇重分为三类库存——**reference values（67 规则库、PCK schema、M1–M7 定义、模板）/ endorsements（人审身份公钥、OTS 凭证）/ verifier code（813 行纯核心）**；闭包目标是"核心 + 引用值清单"，规则数据作为外部 reference value 被哈希引用而不是 import 进闭包。
2. 外部锚独立性 L2→L3 的现实路径分两档：
   - **低工程档（现在就能做）**：账本周期根哈希/证书发布到**公开透明日志**（Rekor 或自建，见 §4），第三方只看日志即可验证发布存在性——独立性来自"你无法控制日志"，不需要自建 TEE；
   - **高工程档（触发条件：真实外部用户/对抗模型）**：判决/复现跑进 CVM，MRTD/RTMR 度量 queyi-core，报告作为 RP 放行证据——单人项目明确缓建。
3. tool_integrity 升级原则照抄 CVM 纪律：缺 reference value 不是 warning 是 fail（647 A1 只改了 exit code，还要把"值本身"从静态文件升级为度量比对）。

> **T3（落地动作）**：按 RATS 三角色重写闭包清单文档（Verifier/RP 边界、政策外置）；647 A3 的扩闭包不动代码先扩"引用值清单"；外部锚采用低工程档（公开日志周锚）；CVM 写入"queyi-core Rust 重写/真实外部对抗出现"的触发条件，不提前投入。

## 4. 透明账本：append-only 哈希链之后，2024–2026 的新构造是 tile、checkpoint 与"日志即证书"

| 方案 | 状态（2026-09 实测） | 对阙疑的用法 |
|---|---|---|
| Certificate Transparency 二代：**static CT API / tile 后端** | Let's Encrypt Sunlight 与 Cloudflare Azul（Rust 开源）落地；tile 化让缓存/服务成本大降、监控可只拉增量 [S47] | 账本存储格式的直接参照：checkpoint + tile |
| **Merkle Tree Certificates**（IETF draft-06，2025-07） | 把公开日志**折进证书自身**，更短证书生命周期 + 后量子签名下减负，含无签名优化档【官方草案】[S46] | 思想可借：判决证书可内嵌最新账本头/包含证明，减少外部依赖 |
| **Key Transparency**（IETF WG，draft-05，2025-07） | prefix tree + 透明日志组合，给 label-version→commitment，带一致性/包含证明的标准化协议【官方草案】[S48] | 账本的"多版本值映射"同构：卡 id→当前证书哈希+历史版本，协议构造可直接缩形 |
| Rekor v2 | 2025-10 GA（tile 后端），但**公共 good 实例 2026-06 宣布继续默认 v1**（客户端行为破坏性变更）；Cosign v3 支持离线验签+attestation 打包，sigstore-c 已移植到 C89 [S49] | 迁移教训：**日志后端更换会伤客户端**——阙疑自建账本从第一天就用 checkpoint/tile 的稳定 API 面 |
| 监控方 | rekor-monitor（GH Actions）/omniwitness 常态化第三方目击 | 多目击者（gossip）是防日志方作恶的要件，阙疑无此组件 |

**透明日志的三个数学不变量**（任何新方案都必答）：append-only 一致性证明 + 包含证明 +（对外发布的）checkpoint 目击/gossip。阙疑本地哈希链只有追加哈希，三样都没有。

> **T4（落地动作）**：账本 API v1 直接对齐 static CT API 最小集——`/checkpoint`（EDSF 签名头：树大小+根哈希+时间戳）+ `/tile` + `/proof/inclusion` + `/proof/consistency`；这是把"透明"从声明变成可独立验证的关键一跃（v32 证书展厅的"检索台"有了真后端）；**一致性证明是必选项**（append-only 全靠它证明，哈希链只防改写不防回滚）；上线即接第三方周目击（GH Actions cron 签名 checkpoint），否则日志仍只是自述。OTS 维持但定位写清：它是时间戳锚（防事后补造），不是发布锚（不证明存在性），两者互补不可互替。

## 5. 可复现性：SLSA 把"可复现"列成 L4 准入项；Nix 给出构造级答案；2024–2026 供应链攻击给出了反面教材

- **SLSA v0.1（已批准）**：Build L4 要求 hermetic + parameterless，**Reproducible 仅 L4 且为 ○（best-effort，需书面理由，消费者可拒绝）**；L1–L3 不要求位级可复现，要求脚本化构建/托管构建/生成式签名 provenance【官方规范实读】[S50]。
- **Nix 的答案是构造级的**：每个构建产物是全部输入（含传递依赖）的哈希寻址函数，同 lockfile 任意机器任意日期同字节；无需先信任构建机【二手但与官方文档一致】[S51]。
- 反面教材（为什么必须做）：SolarWinds（构建期注入，源码干净）、**XZ Utils（2024，维护者耗时数年的后门，过了多人 review，靠异常提交后才被发现）**——非可复现构建无法让审计者区分"官方构建"与"注入构建"；SLSA provenance 是检测面，可复现是检测原理 [S52]。
- 现实分层：Dockerfile 通常不可复现（apt 拉当日最新版）；pinned 工具链 + `SOURCE_DATE_EPOCH` 是零成本起点；reproducible-builds 项目维护工具链补丁清单。
- 阙疑 648 已有部分基建：真机探针 + sha256 + run_match + 命令记录 + golden 并行化（项目记忆：编译临时物入 gitignored build/）；缺的是**环境清单与"一键复现"入口**。

> **T5（落地动作）**：每条 L1 证据附 **reproduce manifest**（不引入 Nix，Windows/单人务实档）：编译器全版本字符串（`gcc --version` 原文）+ 完整命令 + 输入文件 sha256 + 期望 stdout/退出码/asm 关键符号的 sha256 + `SOURCE_DATE_EPOCH` 式时间归一说明；仓库提供一条 `python tools/replay_probe.py <EV-ID>` 复现入口（大部分件已存在，组装即可）；对外叙事对齐 SLSA Build L1–L2（脚本化构建 + provenance 可用 in-toto link 格式落盘），但**位级可复现只作为长期目标不做假承诺**（SLSA 自己也把它放在 L4 best-effort）。

## 6. 813 行小核心的形式化：性价比数据在 2025–2026 更清楚了——答案分三层，不是"做/不做"

1. **定理证明助手（Lean/Coq/F\*/Verus）**：v31 数据维持——VeruSAGE 849 任务最佳 agent 组合完成 80%+、人类专家未完成集 90%+；VeriStruct 128/129 函数全验证；工业案例 94h 换 1 个新 bug [v31-S23-S25]。2025–2026 无改变结论的新证据：证明助手在**有规范语言支撑的系统代码**上成立，Python 不在其列。
2. **有界/符号工具（CBMC/ESBMC/Kani）**：C/Python 小核心没有成熟低成本工具链；对 Python 纯函数，工业界的实际答案是**性质测试**。
3. **性质测试（PBT）2025–2026 的地位**：Hypothesis 式 stateful 测试（`RuleBasedStateMachine`）把系统建模为状态机、自动搜索违例操作**序列**——生产事故实证：多数严重故障是"单次都对、序列才错"（OSDI'14：简单测试可防大多数关键事故，多数故障需要动作序列诱发），stateful PBT 正是为此设计；Anthropic 2026-01 公开报道用其在 NumPy/Pandas/SciPy 发现多个真实 bug【实测汇编】[S53]；Teralizer（2025-12）显示 PBT 泛化能把变异分数提升 1–4pp，开发者测试几乎不动 [S54]。

**对 813 行 queyi-core 的三层结论**【推断】：

- gate_engine 判决合成、账本追加/哈希链校验、保护器改判条件、四态状态机——全是**无 IO 纯函数 + 状态置换序列**，恰好是 stateful PBT 的标准靶心，且在 Python 工具链内（项目已重度使用 pytest）。
- BMC/证明助手不上（Python 无低成本后端、94h/bug 性价比在已被 sanitizer+真机覆盖的域更差）；Lean/Coq 继续仅列为 **Rust 重写验收条件**（v31 已立，不变）。
- 头部探针的 ESBMC falsification（01 篇 §6）与核心 PBT 共用 witness/反例文化但工具不同，勿混。

## 7. "知识验证"没有行业标准，但 2026 的内容 provenance 标准已经齐到可以直接借词表

- **C2PA 2.2（2026 现行）**：Content Credentials = Manifest（claim 绑定）+ Assertions（有标签的结构化声明，含 actions v2、AI 披露、成分 ingredients）+ 硬绑定/软绑定；Manifest Store；内置/外置 assertion 存储；断言红action（redaction）；W3C Verifiable Credentials 可内嵌进 manifest【官方规范实读】[S55]。
- 2026-07 增补指南：**生成式 AI 内容的 provenance 配方化**——prompt/参考图可作为 ingredients 断言记录，c2pa.ai-disclosure 标 AI 修改区，数字训练数据引用 [S55 邻]。
- 信任模型分 hard/soft bindings：硬绑定（签名清单随文件走）与软绑定（分离元数据）是两档场景，不是二选一。
- 周边生态：SLSA（构建 provenance）、in-toto（供应链 attestation，CNCF graduated）、RFC 9334 RATS（远程证明角色模型）、Sigstore（签名/透明日志）——软件制品的四件套已闭环；**媒体/知识内容由 C2PA 接管**。
- 空白带：没有任何主流标准管"**断言-证据-判决**"这一层（C2PA 管资产来源，不管事实真假；Sigstore 管谁签的，不管内容对不对）。

**对阙疑的硬映射**【推断】：PCK 证书在结构上已经是 C2PA Manifest 的知识域同构物——claim ↔ assertion、boundary ↔ claim_boundary、fingerprint ↔ hard binding、chain[] ↔ ingredients/链路、mutation_tests ↔ 行动断言的否定验证、cs_upper_bound ↔ 置信断言。差距只剩三件：

> **T7（落地动作）**：①词表对齐（降低未来生态摩擦）：证书字段映射 in-toto attestation / C2PA assertion（statement→claim，predicate→evidence pack，materials/products 已有）；②软/硬绑定概念引入（签名清单与分离元数据两档，区分"文件自证"与"页面元数据"）；③**生态位判断**：软件制品签名走 Sigstore（v32 路线已定），**知识卡 manifest 是 C2PA 空白生态位的候选事实标准**——把 PCK jsonl 按 C2PA 断言词表导出 + M1–M7 命名为标准否定断言类型，单人项目可先成为该格式的参照实现，不需要等委员会；AI 起草/生成动作以 `c2pa.actions` 同构方式留痕（哪段文字由谁起草），透明账本同时服务"谁改的"与"怎么验的"。
