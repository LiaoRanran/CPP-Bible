# C6 结构体与内存布局：对齐、填充与重排

> 参考：《C 语言极致详解手册》。编译器 GCC 15.3.0（`gcc -std=c11`），所有输出为本机真实运行产物（MinGW x64，LLP64）。汇编视角见 A5。
> 示例源：`c/_demo/c06_struct.c`

## ① 我们真正要回答的问题 <span class="badge badge-std">标准</span>

1. 我写 `struct { char a; int b; }`，`sizeof` 为什么是 **8** 而不是 5？那 3 个字节去哪了？
2. 字段在内存里隔多远？偏移是谁定的，是我还是编译器？
3. 为什么同样的 `struct`，在 Windows 上 `sizeof` 和 Linux 上不一样？

> 判决先行：**你写下的成员顺序 ≠ 内存里的字节顺序；`sizeof(T)` 几乎永远大于各字段字节之和；每个字段的偏移是编译器按「对齐规则」算出来的编译期常数。** 结构体不是把字段平铺进内存，而是先经过一套对齐规则「拍平」，中间塞进你没要的 padding。

> 历史注脚：`ritchie:chist` 记载，结构体是 C 在 B/BCPL 之后逐步补进来的特性之一（与 `typedef`、枚举并列）。动机是给系统编程一种「把异质字段钉成一条记录」的类型——BCPL 的世界里一切都是无类型字，根本没有「记录」概念。换句话说，**`struct` 是 C 为了描述真实数据而主动向高级语言借来的东西**，代价就是必须面对机器对「对齐」的要求。

## ② 对齐规则：先给直觉，再给数字

对齐（alignment）的含义只有一句话：**一个类型为 `T` 的对象，其地址最好是 `alignof(T)` 的整数倍**。原因在 A5 已经埋好：CPU 按「字 / 缓存行」取数，地址不对齐的访问要么更慢，要么在部分架构（典型如 ARM、或 x86 上的 SSE 载荷）直接 `SIGBUS`。

先看本机各基础类型的对齐值（真机，别背）：

```text
alignof  char=1 short=2 int=4 long=4 double=8 void*=8
```

注意 `long` 的对齐是 **4**——因为本机是 LLP64（A5 §⑤、C3 类型章），`long` 只有 4 字节，它的对齐自然也是 4，不是 8。

结构体整体的对齐值 = **其成员里最大的那个对齐值**（再叠加 `_Alignas` 的上拉）。

## ③ 证据：六个结构体，同一套规则

下面全是 GCC 15.3 真机 `sizeof` + `offsetof`（`-O2` 不改变布局，布局由 ABI 定）：

```text
S1{char a; int b;}              sizeof= 8  a@0 b@4
S2{int a; char b;}              sizeof= 8  a@0 b@4
S3{char a; char b; int c;}      sizeof= 8  a@0 b@1 c@4
S4{char a; int b; char c;}      sizeof=12  a@0 b@4 c@8
S5{int b; char a; char c;} 重排 sizeof= 8  b@0 a@4 c@5
S6{double a; char b;}           sizeof=16  a@0 b@8  align=8
Aligned{_Alignas(16) char; int} sizeof=16  tag@0 x@4  align=16
```

把它们归到同一条规则上：

1. **成员偏移** = 从「已用字节数」向上取整到该成员的对齐值。
   - `S1`：`a`(char,对齐1)放 @0；`b`(int,对齐4)从 1 向上取整到 4 → @4；中间 **@1,@2,@3 是 padding**。
   - `S3`：两个 char 连续（`a`@0,`b`@1），`c`(int)从 2 取整到 4 → @4，只填 @2,@3 两字节。
2. **整体对齐** = 最大成员对齐（`S1` 是 int 的 4）→ `sizeof` 向上取整到 4 的倍数。`S1` 用到 @8，已是 4 的倍数 → 8。
3. **`S4` 为什么是 12**：`a`@0、`b`@4、`c`@8（char,对齐1，紧接 b 后），用到 @9；整体对齐 4 → 向上取整到 12（@9,@10,@11 三字节尾填充）。
4. **重排省内存**：`S5` 把 `int` 放最前，`a`@4,`c`@5，用到 @6，取整到 8。**和 `S4` 装一样的字段，少占 4 字节。** 这是「把大对齐成员往前排」的金律。
5. **`_Alignas(16)`** 把整体对齐从 4 拉到 16：`tag`@0,`x`@4，尾填到 16。

> 立场：[标准] C 标准（N1570 6.2.8）只规定「每个完整类型有一个对齐值、且是 2 的幂、指针转换要保持对齐」，但**具体对齐多少由实现/ABI 决定**。`char` 对齐必为 1、`int` 至少 2 这类是底线；x86-64 System V / Microsoft x64 的「int=4、double=8」是 ABI 约定，不是 C 语法。
> 立场：[实现·GCC15.3] padding 本质是用空间换对齐访问速度。它能让你 `p->b` 一次取 4 字节，而不是拆两次再拼。性能与体积的取舍，从结构体布局就开始了。

## ④ 位域：当你真的想省那几比特

```text
BF{三个 1-bit 位域}            sizeof= 4   （等价于只占 1 个 unsigned int）
ThreeInt{三个 unsigned int}    sizeof=12
```

位域（bit-field）把多个小整数塞进同一个字的相邻比特，常用于标志位、协议头。`BF` 三个 1-bit 字段共享一个 `unsigned int`，所以 `sizeof` 只有 4；而 `ThreeInt` 是三个完整 `unsigned int`，12 字节。

> 立场：[经验] 位域跨平台**不可移植**——C 标准不规定位从哪端排起、是否跨字、padding 位是否参与。同一份位域结构体在两种编译器上可能字节布局不同。**需要线格式稳定时别用裸位域**，改用显式移位/`stdint.h` 的位掩码（主书 ch52 位运算详述）。

## ⑤ 事故现场：padding 不是「零」，跨平台不兼容

### 事故 1：padding 字节是不确定的

只给字段赋值，然后把整块按字节打印（真机）：

```text
Header sizeof=16 原始字节: 50 f0 90 90 07 00 00 00 01 00 90 90 2a 00 00 00
```

`50`='P' 是 `magic`；其后 `f0 90 90` 是 3 字节 **padding**——它们是栈上残留的垃圾（`0x90` 是 x86 的 NOP 机器码，常作为栈填充）。`flags` 之后 `90 90` 又是一段 padding。

> 立场：[标准] 填充字节的内容是**未指定的**（N1570 6.2.6.1 / 6.7.2.1）。以为 `memset` 整块或 `memcmp` 整块比较结构体就安全，是经典错误——你拿 padding 里的垃圾去和网络对端 `memcmp`，永远对不上；把整块 `memcpy` 到缓冲区再发出去，对端收到的是带噪点的记录。**逐字段序列化，永远别 memcpy 裸结构体。**

### 事故 2：同一个 `struct`，两个平台两种尺寸

`Header` 含一个 `long id`。本机 LLP64：

```text
本机(LLP64)  Header sizeof=16  id@12
LP64(Linux)   long=8 字节 -> id 需 8 对齐 -> id@16, sizeof=24
```

只因 `long` 在 Linux 上是 8 字节、`id` 需要 8 对齐，结构体的布局和尺寸整个变了。把本机 `sizeof=16` 的 `Header` 按 `char raw[sizeof(int)+sizeof(char)+sizeof(short)+sizeof(long)]`（本机=11）当缓冲去 `memcpy`，**直接越界**；更隐蔽的是把 `Header` 原始字节写文件/发网络，Linux 端按 `id@16` 解，解出一坨错值。

> 立场：[平台·x86-64] 结构体布局是 ABI 的一部分。**不要在不同数据模型的程序间直接 `memcpy`/`fwrite` 裸结构体**。跨平台线格式一律：固定宽度整型（`uint32_t`/`int64_t`）+ 显式打包（`#pragma pack` 或手算偏移）+ 按字节序收口（主书 ch52）。这条坑贯穿 C9 互操作、ch158 序列化。

## ⑥ `#pragma pack`：能关 padding，但代价是 ABI

`#pragma pack(1)` 把对齐上限压到 1，上面 `Header` 会变成 9 字节紧密排列。代价：

- 字段不再自然对齐，在 ARM 或 x86 的未对齐 SIMD 载荷上触发 `SIGBUS`；x86 上普通标量虽能跑，但每次访问变慢。
- 破坏 ABI：你 `pack` 的结构体，和没 `pack` 的同一声明在链接期「同名不同构」，传参/返回直接错位。

> 立场：[经验] `#pragma pack` 只该用在「必须和外界既有线格式逐字节对齐」的场合（读老协议头、和 C#/其他语言约定死的结构）。正常数据结构**用重排而不是 pack 来省内存**——重排零代价，pack 有 UB 风险。

## ⑦ 为什么偏移是常数：回到 A5

A5 §③ 看过 `Point` 的反汇编：字段名在编译后彻底消失，只剩 `结构体基址 + 常数偏移`。本章程算出的 `@0/@4/@8` 正是写进那些 `[rcx+0x4]` 指令里的常数。**你以为在「访问字段」，机器只在「按偏移取一块内存」**。理解布局，是理解 C/C++ 对象模型（主书 ch19 变量、ch33 类布局、ch34 虚表指针在哪）的第一块砖。

规则速记（记住就够用）：

| 步骤 | 做法 |
|------|------|
| 成员偏移 | 从「已用字节数」向上取整到成员对齐值 |
| 整体对齐 | 取成员最大对齐（再叠加 `_Alignas`） |
| `sizeof` | 已用字节数向上取整到整体对齐值 |
| 省内存 | 大对齐成员往前排；或位域（仅限非跨平台场景） |

## ⑧ 小结与路线图

对齐让 `sizeof` 常大于字段字节和；偏移是编译期常数、由 ABI 定；重排成员零代价省内存；padding 字节不确定、裸结构体禁止跨平台 memcpy；`#pragma pack` 有 ABI 代价。
