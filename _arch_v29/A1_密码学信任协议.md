# 方向 A1：密码学信任协议

> 核心问题：**在没有可信第三方的情况下，如何建立可验证的信任？** 直接对应阙疑的"信任根独立"。
> 检索：15 次（zk-SNARK/STARK、可信设置仪式、MPC、门限签名、TUF、SLSA、in-toto、区块链共识、可验证计算、Bulletproofs、递归 SNARK、算术化、HE vs ZK、TUF 委托、透明日志）。
> 边界：v21 已封棺 zkML/TEE，本轮只做**增量深化**；与 v28 攻防理论不重复。

## 一、核心概念清单（≥10 条）

- **零知识证明（ZKP）**：证明者在不泄露任何额外信息的前提下，使验证者确信某陈述为真。Goldwasser, Micali, Rackoff (1985) 在 IP 系统中首次提出，对 NP 全类问题均存在这样的证明。
- **zk-SNARK（简洁非交互知识论证）**：证明极短、验证极快、非交互；代价是多数构造需要一个"可信设置"（trusted setup）生成公共参数，其"有毒废物"（toxic waste）若被保留可伪造证明。
- **zk-STARK**：不依赖可信设置、抗量子（基于哈希）；代价是证明尺寸比 SNARK 大。Ben-Sasson 等 (2018, STARKware)。
- **可信设置仪式（Setup Ceremony / Powers-of-Tau）**：多方计算仪式生成 SNARK 公共参数，只要有一方诚实删除其秘密份额，整体即安全——"1-of-N 诚实"假设把信任从单点分散到多方。
- **安全多方计算（MPC）**：n 个互不信任的参与方联合计算协商函数 f(x1…xn)，各方输入不被他人获取。姚期智 (Yao, 1982) 百万富翁问题开宗，GMW 协议推广到多方，基于混淆电路（garbled circuits）或秘密分享。
- **门限签名（Threshold Signature）**：n 个密钥分片中任意 t 个（t-of-n）可联合生成有效签名，少于 t 个无法伪造。BLS 签名支持密钥聚合与门限；Stinson & Strobl (2001) 给出可证明安全的分布式 Schnorr 门限方案。
- **The Update Framework (TUF)**：软件更新安全框架（Cappos 等, NYU）。核心=**角色分离**（root/targets/snapshot/timestamp/delegated targets）+ **签名阈值** + **元数据过期与冻结**。即使 targets 密钥被泄露，root 仍可撤销；委托角色限制单点权限。
- **SLSA（Supply-chain Levels for Software Artifacts）**：OpenSSF 的软件供应链安全框架，分级（L0–L3）强制制品完整性与可溯源；核心产物是 **provenance**（可验证的"在哪、何时、如何生产"）。
- **in-toto**：将软件构建的每一步（谁、用什么工具、输入输出）做成带签名的 attestation（证明），与一条"layout"策略比对，验证整条供应链未被篡改。Witness 项目是其工程化实现。
- **可验证计算（Verifiable Computation）**：云返回计算结果并附"计算正确"的证明，验证成本远低于重算。源自 PCP/IP 理论（Walfish & Blum 综述）。
- **Bulletproofs**：无需可信设置的非交互 ZK 证明，区间证明（range proof）尺寸对数级（Bünz, Bootle, Poelstra 等, 2017），基于内积论证 + Fiat-Shamir。
- **递归 SNARK / 折叠方案（Nova, IVC）**：Kothapalli, Setty, Tzialla (2022)。证明者递归证明"上一步证明本身正确"，验证者工作量不随计算步数增长——增量可验证计算（IVC）的工程化。
- **算术化（Arithmetization）**：把程序执行转成 R1CS / PLONK / AIR 多项式约束，再经多项式承诺（polynomial commitment）证明。任何计算都可被约束化，这是 ZK 能"证明任意程序"的数学基础。
- **透明日志（Transparency Log / Certificate Transparency）**：Google Trillian 提供可验证 append-only 日志，Merkle 树提供"包含证明"与"一致性证明"，任何人可审计。对应"公开、可审计账本"。

## 二、对阙疑的映射（全标【类比推断】）

- **ZK → 验证者无需看到证据原文即可验证卡片断言【类比推断】**：阙疑的 VerificationRun 本质上是"验证者要确认一张卡片（命题/误解图）成立，但不必把全部源码/实验原始数据塞给验证者"。ZK 的机制——证明者持私有见证 w，公开陈述 x，输出 π 使验证者以极高 soundness 接受——恰好是"验证与证据暴露解耦"的密码学形态。相关点：阙疑当前是"人审读原文"，若引入 ZK 化 attestation，可在不泄露被测对象细节的前提下证明"已按某规则核查"，减轻人审负担与信息过载。
- **可信设置仪式的 1-of-N 诚实假设 → 信任根独立的多方化【类比推断】**：阙疑要求"信任根独立于被验证对象"。ZK 仪式的"只要一人诚实删除 toxic waste 就安全"是一种把单点信任分散到 N 方的工程范式，启发阙疑的 root-of-trust 不应是单一组件/单一人，而应是"N 方中至少 k 方独立签署"的阈值结构。
- **门限签名 t-of-n → 多独立验证者的数学阈值【类比推断】**：v22 已证 BFT 3f+1 与 v26 审计阈值同源。门限签名提供"任意 t 个验证者签名即有效、t-1 个无法伪造"的密码学实现，可直接作为阙疑"多验证者聚合判决"的签名层：硬开火率需 k 方签名，单点无法独断。
- **TUF 角色分离 + 签名阈值 → VerificationRun 的信任链与权限最小化【类比推断】**：TUF 把"能签署元数据"拆成多个角色，单角色被攻破不致全盘崩溃。阙疑的"攻击-验证"对抗中，应把"生成规则""运行验证""签发判决""归档账本"拆成互相独立的角色/密钥，任一角色失陷可被 root 撤销（对应 v21 信任根独立的工程化）。
- **SLSA provenance / in-toto attestation → VerificationRun 的过程可验证绑定【类比推断】**：阙疑每条 VerificationRun 应像 in-toto 的 layout 一样，记录"哪条规则、用哪个工具、在哪个 commit、由谁（人或机）触发、产出什么证明"，形成不被篡改的 provenance。这是 v21 Assurance 2.0 的供应链化延伸。
- **透明日志 → 阙疑 Ledger 的公开可审计形态【类比推断】**：v25 的 Ledger 若改为 Merkle 化透明日志，任何第三方可独立验证"某判决确实被记入、未被回改"，是对"append-only 不可抵赖"的密码学强化，对抗内部篡改与事后抵赖。
- **递归 SNARK/IVC → 验证链自身的可递归验证【类比推断】**：阙疑的"自我进化"要求"验证器能验证新规则的验证器"。IVC 的"递归证明证明本身"机制，是"验证器自举/自证"的理论近亲——可设想每层验证器升级都附一层证明，证明"本层验证逻辑正确编译自规格"。
- **Bulletproofs 无需可信设置 → 轻量 ZK 的落地窗口【类比推断】**：阙疑若要给某些凭据加零知识证明，优先选无需可信设置的方案（Bulletproofs/STARK），避免"可信设置"引入新的中心化信任点——与"信任根独立"原则一致。

## 三、净新增（v21-v28 没有的洞察，≥3 条）

1. **"1-of-N 诚实"比"N-of-N 全部诚实"更适合分布式信任根**：可信设置仪式揭示了一个被 v21/v22 忽视的工程事实——我们不需要所有方诚实，只要至少一方删除了 secret 即可。这直接松动了"必须完全独立无共谋"的苛刻假设，对阙疑多验证者架构是可行性的关键放宽。
2. **供应链 provenance 是"验证过程"而非"验证结果"的可验证化**：in-toto 把"过程"做成可审计证明，提示阙疑的信任对象不应只是最终判决，而是"判决是如何被生产出来的"——把 v21 的 Assurance Case 推进到机器可校验的 attestation 层。
3. **Merkle 透明日志让"账本不可篡改"可第三方独立证伪**：比单写本地 Ledger 更强的，是任何一方都能出具一致性证明揭穿篡改，这是对 v25 Ledger 的去中心审计升级。
4. **算术化是"任意程序可证明"的数学桥梁**：明确"计算 → 多项式约束 → 承诺证明"的链路，说明 ZK 能覆盖阙疑规则引擎的任意逻辑，而非仅特定断言。

## 四、设计原则（1-2 条，可操作）

- **D-A1-1：信任根按角色拆分并设签名阈值**——把"规格/工具/验证/签发/归档"拆成独立密钥角色，硬判决需 ≥k 方签名；单角色失陷可由 root 撤销，避免 v21 单点信任根风险。
- **D-A1-2：过程 provenance 不可省略**——每条 VerificationRun 强制记录 layout（规则·工具·commit·触发者·产物证明），采用 in-toto 式签名 attestation，使"怎么验的"与"验成什么"同等可审计。

## 五、失败教训与死路（≥5 条）

- **zkML / TEE 被 v21 封棺**：在"验证器自身可信"问题上，zkML 证明神经网络推理、TEE 把信任交予厂商，均无法解决"谁证验证器"的回归。本轮不重述——仅作增量提醒：任何把信任交给单一黑盒的方案都违背信任根独立。
- **可信设置的中心化风险**：若仪式参与方共谋或少于 1 方诚实，toxic waste 可被重用以伪造任意证明——证明"分布式仪式"也需警惕参与方同质化（与阙疑多验证者需异质同源）。
- **MPC 通信与轮复杂度爆炸**：安全多方计算在参与方多、电路深时通信轮次与带宽极高，难以用于实时验证；提醒阙疑的"多验证者"若真跑 MPC 会拖垮闭环节奏。
- **门限签名依赖 DKG 安全**：分布式密钥生成（DKG）若实现有缺陷，门限结构形同虚设；纯密码学方案需配套安全的密钥生命周期管理。
- **SLSA/in-toto 依赖签名基础设施完备**：若构建步骤未全链路签名（手工步骤、不可签名的物理过程），provenance 出现断点，验证链被绕过——阙疑的 provenance 必须覆盖全部环节，否则制造虚假安全感。
- **透明日志需活跃审计者**：CT 日志若无人实际监测（monitor），伪造证书仍可被长期忽略——阙疑 Ledger 的"可审计"必须配套主动 monitor，否则只是摆设。
