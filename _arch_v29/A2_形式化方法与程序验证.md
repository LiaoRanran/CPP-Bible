# 方向 A2：形式化方法与程序验证

> 核心问题：**用什么数学工具能把"程序正确"变成可机械检验的事实？** 对应阙疑"验证器自身也要被验证"。
> 检索：15 次（CompCert、CakeML、Lean/mathlib、seL4、模型检测、抽象解释、分离逻辑、Curry-Howard、Coq、Isabelle、Hoare 逻辑、形式化成本、依赖类型、可用性障碍、规格错误）。
> 边界：v21 已确认"全量形式化不可行"，本轮只做**增量深化**；与 v24 数学地板、v28 复杂系统不重复。

## 一、核心概念清单（≥10 条）

- **CompCert**：Leroy 等用 Coq 形式化验证的优化 C 编译器（CACM 2009；JAR 2009 后端）。证明"源码语义 → 汇编语义"的逐层精化正确，是工业级已验证编译器的标杆。
- **CakeML**：用 HOL4 证明的 Standard ML 实现，端到端从解析到机器码全程证明；支持 bootstrap（编译器用自身语言写、再被自身编译）。含"证明生成的检查器"。
- **Lean 4 / mathlib**：de Moura 主导的交互式定理证明器；mathlib 是社区驱动的统一形式化数学库。Lean 4 把证明助手与编程语言融合。
- **seL4**：Klein 等 (SOSP 2009, NICTA) 用 Isabelle/HOL 对完整通用微内核做功能正确性证明——首个完整 OS 内核的机器证明，基于 Hoare 三元组逐语句推理。
- **模型检测（Model Checking）**：对有限状态系统穷举搜索是否满足时态性质（LTL/CTL）。SPIN（Promela 建模）、NuSMV 是主流工具；核心难题是**状态空间爆炸**。
- **抽象解释（Abstract Interpretation）**：Cousot & Cousot (1977) 框架。不运行程序而静态计算其性质的上/下近似，保证**可靠性（soundness）**——任何真实行为都被抽象域覆盖。是静态分析（如 Astrée）的数学基础。
- **分离逻辑（Separation Logic）**：Reynolds、O'Hearn 等扩展 Hoare 逻辑以推理指针/堆。关键发明是 **frame rule（框规则）**，支持"局部推理"——只描述关心的那块内存，其余用分离合取 `*` 推到旁边。
- **Curry-Howard 同构**：命题即类型、证明即程序（propositions-as-types, proofs-as-programs）。直觉主义逻辑的证明项就是 λ 项；程序正确性可被"类型"编码。
- **依赖类型（Dependent Types）**：类型可依赖于值（如 `Vec A n` 表示长度为 n 的向量）。Agda、Idris、Coq/Gallina 支持；可在类型层强制前置条件。
- **演绎验证（Deductive Verification）与 Hoare 逻辑**：用 `{P} C {Q}` 三元组 + 最弱前置条件（wp）生成验证条件（VC），交给 SMT 求解器（如 Z3）证明。Viper 是典型工具。
- **Isabelle/HOL**：Paulson、Nipkow 开发的高阶逻辑证明助手，seL4 即在其上完成。
- **规格-实现鸿沟（spec gap）**：形式化只证明"程序满足所写规格"，规格本身若错/漏，证明毫无意义——近年智能合约形式化翻车多源于此。

## 二、对阙疑的映射（全标【类比推断】）

- **CompCert → "验证器自身也需要被验证"的终极形态【类比推断】**：阙疑要求信任根独立，但验证器（规则引擎、攻击生成器）本身是一段程序。CompCert 证明"编译器没悄悄改变语义"——阙疑可设想对核心验证逻辑做精化证明，确保"验证器按规格运行"，把 v21 的"谁证验证器"推进到机器可查。
- **seL4 微内核正确性 → 最小可信基（TCB）的可验证性【类比推断】**：v21 信任根独立要求 TCB 尽量小且可证。seL4 表明"一个完整内核可被全程证明"在现实可行，启发阙疑把可验证核心（规则匹配、账本写）缩到最小并形式化。
- **抽象解释 → 规则覆盖的"上界近似"【类比推断】**：阙疑要回答"规则集覆盖了多少可能攻击"。抽象解释把不可判定问题变成 sound 的近似——阙疑的 coverage 度量应是 sound 的上界（绝不漏报近似方向），而非精确但不可算的覆盖。
- **分离逻辑 frame rule → 规则间干扰推理【类比推断】**：v25 的 Rule/ProofObject 推理若涉及共享状态（如同一段代码被多条规则审查），frame rule 的"局部推理"范式提示：每条规则应只声明它关心的状态，其余用分离合取隔离，避免规则互相踩踏——这正是 v21 规则间副作用隔离的形式化来源。
- **模型检测 → 规则引擎的穷举性质检查【类比推断】**：阙疑的"攻击-验证共同进化"可把有限状态子集（如规则状态机、判决状态机）交给模型检测器，穷举证明"不会进入非法状态"——对应 v26 用模型检测补强人工审计。
- **Curry-Howard → "规则即类型、判决即证明项"【类比推断】**：可把每条阙疑规则的"前置条件→结论"编码为类型，一次通过验证的 VerificationRun 即一个证明项；类型检查器天然拒绝不满足前置条件的判决，把 v25 的 ConflictDetector/Lifecycle 推到编译期。
- **依赖类型 → "规则前置条件在类型中声明"【类比推断】**：v25 规则的前置（如"只在 L 层匹配 object 语义"）可写成依赖类型，非法调用在类型层被拒，减少运行时冲突检测负担。
- **规格错误（spec gap）→ 阙疑"规格反思"的死穴警示【类比推断】**：形式化最大的坑是"证明了错误的东西"。阙疑若形式化规则，必须配套"规格审计"——谁来证明规则集本身是对的？这恰恰回到 v24 数学地板与 v25 七对象里 CalibrationTracker 的角色。

## 三、净新增（v21-v28 没有的洞察，≥3 条）

1. **"可验证核心"可以很小且现实可行**：seL4/CompCert 证明不必全系统形式化，只要把 TCB 缩到最小并精化证明即可。对阙疑是重大松动——不必形式化整个 Agent 外骨骼，只需形式化"信任根那几百行"。
2. **抽象解释的 sound 近似是 coverage 的正确数学定义**：之前 v23 的 coverage 缺乏数学底座；抽象解释给出"上界覆盖"范式，阙疑的逃逸率上界应建立在 sound 抽象域上，而非经验统计。
3. **frame rule 提供规则隔离的可形式化方案**：多规则共享被测对象时的干扰问题，分离逻辑已有成熟局部推理工具，可直接借鉴做 v21 规则间干扰的精确刻画。
4. **bootstrap 验证器**：CakeML 的自我编译证明显示"验证工具链可自举并自证"，给阙疑"验证器验证自己"提供了一条可操作的工程路径。

## 四、设计原则（1-2 条，可操作）

- **D-A2-1：只对 TCB 做精化证明，不全量形式化**——把可验证核心（规则匹配、判决签发、账本写入）缩到最小，用 Coq/Lean 做精化证明；其余用测试+审计覆盖，规避"全量形式化不可行"的死路。
- **D-A2-2：规则前置条件进类型/规格层**——用依赖类型或 Hoare 式前置条件声明每条规则的适用域，非法 VerificationRun 在编译/静态期被拒，降低运行时冲突。

## 五、失败教训与死路（≥5 条）

- **全量形式化成本极高、不可行（v21 已确认）**：CompCert 花了数十年人年；阙疑若想形式化整个系统必死——必须把范围砍到 TCB。
- **规格本身可能错（spec gap）**：形式化证明"满足规格"但规格漏写关键性质，等于没验证。智能合约多起"已验证却被盗"皆因此——阙疑形式化前必须先有可靠的规则规格审计。
- **模型检测状态爆炸**：系统状态稍大即不可穷举；阙疑若对大状态空间跑模型检测需抽象+剪枝，否则超时。
- **证明助手学习曲线极陡**：Lean/Coq 门槛高，团队难以普及——阙疑若依赖人工写证明，人力成本会爆炸；须靠 LLM 辅助证明（如 DeepSeek-Prover）或 DSL 降低负担。
- **SMT 求解器不完全**：演绎验证的 VC 交给 Z3 等，可能存在超时不决或误判；不可把验证结论当绝对真理。
- **证明维护负担**：代码一改，证明需重证，与敏捷迭代冲突——阙疑规则频繁进化时，证明维护会成为瓶颈，需自动化证明再生。
