# 方向 A4：操作系统安全与可信计算基

> 核心问题：**如何把"必须被信任"的代码缩到最小，并让它在被攻陷时尽量少崩？** 对应阙疑"最小可信内核是什么"。
> 检索：15 次（能力安全、微内核 TCB、SGX 侧信道、TrustZone、seccomp/Landlock、安全启动、攻击面缩减、TEE 局限、EROS/KeyKOS、容器隔离、信息流控制、SGX 证明、微内核性能、硬件信任根、最小特权）。
> 边界：v21 已提 TEE 死路，本轮**深挖为何死**；与 v28 攻防不重复。

## 一、核心概念清单（≥10 条）

- **能力安全（Capability Security）**：权限以"不可伪造的令牌（capability）"持有，持有即有权。seL4、Capsicum、EROS/KeyKOS 为代表；支持**选择性撤销**（revocation）。
- **微内核与最小 TCB**：把 OS 仅保留地址空间、线程、IPC 等极少量机制在内核，其余（驱动、文件系统）移出。seL4 因此能把 TCB 缩到可全验证（见 A2）。
- **可信执行环境（TEE）**：Intel SGX（enclave 加密内存）、ARM TrustZone（Secure World/Normal World 硬件隔离）。目标是"即便 OS 被攻破，enclave 内仍机密完整"。
- **SGX 侧信道攻击**：Foreshadow（L1TF 跨 enclave 泄露）、Plundervolt（降电压在写入内存前翻转 enclave 内 bit）、缓存侧信道——**Intel 官方承认 SGX 不防侧信道**。
- **ARM TrustZone 信任边界**：安全世界靠 NS 位硬件隔离，但 TrustZone 自身代码量大、安全世界 bug 即全盘失守；Arm CCA 引入 Realm 反向保护高权限。
- **seccomp / Landlock**：Linux 非特权沙箱——seccomp-bpf 过滤系统调用，Landlock LSM 做文件系统作用域访问控制；把进程能做的系统调用/文件访问最小化。
- **安全启动与信任链（Chain of Trust）**：UEFI Secure Boot（PK/KEK/db 四级签名库）逐级验签；Measured Boot 把执行过的代码哈希记录供远程核验。根信任在固件不可变密钥。
- **攻击面缩减（ASR）**：系统性减少暴露的端口/API/系统调用/代码复杂度；对 Agent 而言即限制工具权限与可达资源。
- **容器隔离的脆弱性**：namespace/cgroup/seccomp 共享内核，内核 bug（如 CVE-2024-21626 runc）可逃逸；gVisor 等用用户态内核补强。
- **信息流控制（IFC / DIFC）**：不只控制"谁能访问"，更控制"数据能流向哪"；去中心化标签（DIFC）允许各主体自定标签，防机密泄露与隐通道。
- **SGX 远程证明（Remote Attestation）**：enclave 生成 QUOTE（含度量+CPU SVN），由 Quoting Enclave 签名，依赖 Intel 根证书——**信任根仍在 Intel**。
- **硬件信任根（Hardware RoT）**：TPM 提供不可克隆、不可变身份与密钥，做平台度量与证明；是 Secure Boot 的锚点。
- **最小特权原则（Saltzer & Schroeder, 1975）**：每个主体只拿恰好够用的权限；经典 8 条安全设计原则之一。

## 二、对阙疑的映射（全标【类比推断】）

- **TCB（最小可信基）→ 阙疑的最小可信内核【类比推断】**：v21 信任根独立问"谁必须被信任"。TCB 范式回答：把可被信任的代码缩到最小（规则匹配+判决签发+账本写），其余（UI、报告生成、学习）都可外移且不可污染内核。阙疑的"通用验证内核"应是一个 seL4 式微内核，而非把一切塞进 Trusted Verifier。
- **能力安全 → 规则/工具的权限最小化【类比推断】**：v21 强调"验证器不能既当运动员又当裁判"。能力模型让每条规则、每个工具只持有所需 capability（如"只能读某目录下源码""只能写 Ledger 追加"），规则越权操作在机制层被拒，比 RBAC 更细、更防越权。
- **安全启动信任链 → VerificationRun 的信任链【类比推断】**：阙疑每次 VerificationRun 都应有"逐级度量+签名"的信任链——从内核→规则引擎版本→具体规则→工具→结果，任何一层被篡改都能被 Measured Boot 式记录揭穿，对应 v21 Assurance Case 的硬件化落地。
- **SGX 死路 → "信任根交厂商"的教训【类比推断】**：v21 已封 TEE，本轮补其死因——SGX 远程证明的信任根在 Intel，侧信道频发，且"不防侧信道"是官方承认的局限。阙疑若要隔离，**绝不能把信任交给单一厂商硬件**，必须回到 v21"信任根独立"。
- **seccomp/Landlock → 验证器运行沙箱【类比推断】**：阙疑的攻击生成器（mutation）是潜在危险代码，应用 seccomp 限制其系统调用、Landlock 限制文件访问，使其无法越界读取被测对象之外数据——对应 v21 攻击面缩减。
- **信息流控制 → 人审/机验间的隐通道封堵【类比推断】**：v21 关注"验证者与被测对象共谋"。DIFC 提供"数据不能从被测对象流回攻击生成器"的标签机制，从信息流层面阻断共谋隐通道，比单纯权限隔离更强。
- **攻击面缩减 → Agent 外骨骼的工具最小化【类比推断】**：阙疑 642+ 的 Agent 外骨骼给工具权限，应按 ASR 原则只暴露必要工具，砍掉可达敏感资源的路径，降低被劫持后的爆炸半径。
- **最小特权 → 人审账号的最小权限【类比推断】**：v23 人审队列中的人审账号应只持判决所需最小权限，避免单个人审账号被攻陷即全局沦陷。

## 三、净新增（v21-v28 没有的洞察，≥3 条）

1. **TCB 可缩到"可全验证"规模**：seL4 证明微内核级 TCB 能形式化验证（呼应 A2），给阙疑"最小可信内核"一个现实可达的尺度参照——不是抽象口号，而是几千行可证代码。
2. **TEE 死因具体化**：不只是"不可信厂商"，更包括"侧信道不可避免 + 证明链信任根外置"。这比 v21 的笼统封棺更精确，反向确认阙疑必须自持信任根。
3. **能力安全提供比 RBAC 更细的越权防护**：选择性撤销 + 持有即有权，恰好对应阙疑"每条规则/工具按需授权、可随时吊销"的运行模型。
4. **信息流控制补权限隔离之不足**：权限对了但数据仍可偷偷流走（隐通道），DIFC 是防共谋的更深一层。

## 四、设计原则（1-2 条，可操作）

- **D-A4-1：阙疑核心按微内核 TCB 重构**——把"规则匹配、判决签发、Ledger 追加"作为唯一可信内核（目标可形式化验证），其余模块（报告、学习、UI）全部外移且默认无内核权限。
- **D-A4-2：每条规则/工具授予 capability 并默认沙箱**——用 seccomp/Landlock 式机制限制系统调用与文件作用域，攻击生成器强制沙箱，越权在机制层拒绝。

## 五、失败教训与死路（≥5 条）

- **TEE 信任根在厂商（SGX/TrustZone 死路）**：证明链依赖 Intel/ARM 根证书，厂商可被妥协或断供；且侧信道（Foreshadow/Plundervolt/缓存）频发——阙疑若依赖 TEE 即背叛信任根独立。
- **SGX 不防侧信道（官方承认）**：任何把机密交给 enclave 却忽略侧信道的部署都形同虚设；提醒阙疑隔离方案必须显式评估侧信道。
- **容器共享内核易逃逸**：namespace/cgroup 非真正隔离，内核 CVE 可跨容器逃逸；阙疑多层验证若同居一内核仍需额外沙箱（gVisor 类）。
- **安全启动根信任单一**：UEFI PK 是单点，私钥泄露则全盘伪造；阙疑信任链根也须多方/硬件不可变，避免单密钥崩盘。
- **微内核性能代价**：IPC/上下文切换开销高于单体内核；阙疑若把核心拆成微内核，高频 VerificationRun 需评估 IPC 成本，必要时用 fastpath 优化（seL4 已有）。
- **能力系统撤销复杂**：纯 capability 难做全局吊销，需 hybrid（capability+ACL）；阙疑权限管理需兼顾细粒度与可撤销性。
