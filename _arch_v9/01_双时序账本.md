**唱反调（先找不适用）**：
- **Graphiti/Zep 的"双时序"我是【未一手核实】的**：摘要里**没有出现** `bi-temporal` / `valid time` / `invalid time` / `episode` 这些词（我为此专门抓了 arXiv 摘要页核实）；正文我未读。**二手描述**（多篇 2026 中文技术对比）称其"双时序"，我**不采信为事实**，只记作【一方称】。且其评测数字（DMR 94.8% vs MemGPT 93.4%、LongMemEval +18.5%）来自**厂商自评论文**，不构成独立证据。
- **XTDB/Datomic/TerminusDB 三家都是"外部服务/引擎"**：引入即扩大信任面（谁编译它、谁签它、换版本要不要重验）——这正是 Lens 3 的问题。本仓当前连"自己的 g++ 换了版本"都没有影响面报告，谈外部引擎的版本治理是**跳级**。
- **SQL:2011 时态表**：本仓存储是 **sqlite**；sqlite **没有**系统时态表（我没有找到官方支持声明；其 `lang_with` 系列也没有 temporal 语法）⇒ 这条只能作为**设计参考**（"两个时间轴分开存"），不能作为实现路径。

## 二、本仓现状（读代码/只读统计到的事实）

**命题表没有任何时间列**（`tools/prop_graph.py:90` 的 `SCHEMA`，`PROPS_COLUMNS` 见 `:51`）：
`props(prop_key, card, card_path, card_kind, prop_id, claim_type, subject, predicate, object, statement, extracted_by, signed_by, evidence, machine_verified, anchor_source, signoff_state)` —— 全部是**当前态**；没有 `asserted_at`/`valid_at`/`verified_by_oracle`/`overturned_at`。库本身是**派生视图**（`:11` 注释："可随时 build 重建"，进 `.gitignore`）⇒ **加列的成本极低**（重建即可，无迁移）。

**四个"时间"事实分散在四处，且没有共同的连接键**：

| 时间事实 | 现在存在哪 | 证据 |
|---|---|---|
| 卡文本何时变成现在这样 | **git 历史**（`git log -1 --format=%cI -- <card_path>`；也是"人签"判据的来源） | `gate_engine._git_author_for()`（verified_by 规则用它） |
| 命题何时被断言 | **不存在**（只能近似取卡的提交时间） | 命题无字段 |
| 被哪个验证者版本判过 | 卡面**可选**字段 `verified_by_oracle` + `data/oracle_registry.json`（3 个 oracle：gcc 15.3.0 / gate_engine M4-2026.09.17 / atom_evidence_replay 2026.09.17，各带 `scope` 散文） | `metrics_collector.py:335 ORACLE_REGISTRY`、`:340 oracle_report()` |
| 何时/被谁推翻 | 代码齐备、**数据 0 条**：`OVERTURNED_FILE = ROOT/"data"/"overturned_events.jsonl"`（`metrics_collector.py:374`），`log_overturned()`（`:406`，schema `{ts,target,card,old_verdict,new_verdict,by,reason}`，human 须过 git 作者绑定、**fail-closed**），`read_overturned_events()`（`:377`，缺文件返回 `[]`）。**只读实测：该文件不存在**（`rglob` 0 命中） | `probes/recon1.py` |

**只读统计（2026-09-18 实测）**：原子卡 27 / 证据卡 56；**带 `verified_by_oracle` 的卡 = 0**（83 张全缺）；命题 79（obs 50 / inf 29）、**带命题级 `liveness` 锚 = 0**；`metrics.jsonl` **4 条**，其中**1 条**含 `curves`（键：`timepoints / monotone_convergence / mutation_escape_rate / overturned_by_stronger_verifier / escape_survival_batches`）；`data/knowledge_graph.db` 325 节点 / 291 边（含 **1 条 `CONTRADICTS`**）。

**已有的一半设计**（先读再评，不重复造）：
- 574 任务的"**只写不读**"硬不变量：`verified_by_oracle` 只进报告层、**判决路径一律不读**（`metrics_collector.py:343` 注释 + pytest 锁）——这条**极其正确**，任何"换代重验"设计都**不许**破坏它。
- `metrics_collector` 已声明：无数据 ⇒ `None`，**不许填 0**（"被推翻数""生存时间"当前就是 `None`）—— 这与我看到的 `curves` 里 `overturned_*`/`escape_survival_*` 的 `note`/`None` 一致 ✓。
- `prop_graph.py:4` 明确"**命题 ≠ 概念**"，故不与 `knowledge_graph.db` 的 concepts 混表 —— 资产层演进**必须尊重**这条边界（详见 `02`）。

## 三、差距与风险

1. **缺口 1：没有"某验证者版本下的命题快照"**。今天要回答"gcc 升到 16 之后，哪些结论必须重验"，只能人工翻卡。**这不是缺引擎，是缺视图。**
2. **缺口 2：`asserted_at` 与 `valid_at` 分不开**。"这条断言什么时候开始被系统知道" vs "它声称在什么时间范围内有效"（例：C++20 之后的语言行为 vs C++17）在本仓**完全没有表达**；`status_history` 之类字段最多表达"卡的状态变化"。
3. **缺口 3：推翻通道 0 数据 ⇒ 三条曲线里的两条永远说不了话**。这是**设计上的诚实**（`None` 而非 0），但意味着"可累积不丢真"目前**无法被任何数字证伪**。
4. **风险 A：把 git 当唯一时间轴**。git 历史可以被 rebase/amend 重写（本批我刻意不碰 git 写），因此"何时被知道"若只依赖 `%cI`，其可信度等于"仓库的 git 纪律"，属于**B 级证据**，必须在报告里标注。
5. **风险 B：引入外部时序库 = 把判决可信链外包**。见 Lens 3：换验证者必须 fail-closed 重验，而外部引擎的"版本/构建来源/许可"都不可在本仓复算。

## 四、N / D / W

**N（现在借，1 件，先做这件）——`tools/prop_asof.py`：只读的四轴快照视图**

- 输入：`data/propositions.db`（`prop_graph.query()` 只读）、`data/oracle_registry.json`、`data/overturned_events.jsonl`（可缺）、`git log -1 --format=%cI -- <card_path>`（每卡一次）。
- 输出（stdout/JSON）：每条命题一行 `{prop_key, asserted_at≈卡提交时间, oracle: {name,version}|missing, overturned: 0|1, anchor_source}` + 三张清单：`缺 oracle 字段`、`被 registry 判 stale`、`无 liveness 锚（50 条）`。
- 关键设计：**只读、无写、无 schema 变更**；把"git 时间是近似"写进字段名（如 `asserted_at_approx_from_card_commit`），**不许**叫 `asserted_at`（避免把近似当真值）。
- 机器验收：① 两次跑 stdout 逐字相同；② 断言脚本内无 `open(...,'w')`/`write_text`/`mkdir`；③ 命题总行数 == `prop_graph.stats()["propositions"]`（79）；④ 时间字段为空时**fail-loud**（`git` 不可用 ⇒ exit 非 0，不返回空表）。
- 零误伤证据：新文件；不 import 判决路径的任何可变状态；`git diff --quiet -- tools/atoms/evidence/gate_engine...` 中除新增文件外零差异。

**D（攒数据，2 件）**

- D1：**把 `verified_by_oracle` 填起来**（83 张卡全缺 ⇒ 先机器出清单，人/强模型填；机器**不代填**）。填了之后 `oracle_report()` 的 `stale` 才有意义，N3 的影响面才不是"全体"。
- D2：**推翻通道产生真实事件**（人等显式动作；`log_overturned` 已 fail-closed 且有 git 作者绑定）。**至少 1 条**才能验证 schema/读路径端到端；`escape_survival_batches` 才有分母。
- 攒的门槛（机器可判）：`metrics.jsonl` 连续 ≥6 批 + 推翻事件 ≥1 条。

**W（等条件，3 件）**

- W1：**引入 bitemporal 引擎**（XTDB/Datomic/TerminusDB）—— 解冻信号：① 需要"任意历史时点"**在线**查询（不是离线重建）；② 命题 ≥1 万；③ 本仓已完成 D1/D2 且 N1 的视图成为瓶颈。三条同时满足才评估；评估时必须先回答"该引擎自身的 TCB 边界怎么声明"（Lens 3）。
- W2：**SQL:2011 式系统时态表语义**—— 解冻信号：换到支持 temporal 的存储，或 sqlite 生态出现该能力。（**现在无路可走**，只能手工两轴。）
- W3：**PROV-O 形式的溯源导出**—— 解冻信号：需要对外交付/跨系统审计时。映射是直接的（命题=Entity、判定=Activity、oracle=Agent），但**现在导出没有消费者**，属过度工程。
