# 560-C · 前沿调研与批判吸收（检索日期 2026-09-17）

> 每条给：来源（可访问）→ 对本仓哪个真问题 → 现在做/攒数据/等模型 → 不采纳什么。
> 总原则先行：业界方案默认"可信执行环境里的构建结果可以复用"；本仓的信任轴是**外部 Oracle（真编译器/真测试）独立判决**，凡把"复用结果"升级为"替代判决"的用法一律拒绝。

## C1. 测试影响分析 / 回归测试选择（直接支撑 B3）

- **Microsoft Test Impact Analysis（Azure DevOps，产品化多年）**：按提交自动选择相关测试，机制包含"受影响测试 + 上次失败测试 + 新增测试"三集合，**无法理解的提交（如 HTML/CSS 变更）自动回退全量**，并支持定期强制全量。[learn.microsoft.com TIA 文档](https://learn.microsoft.com/ja-jp/previous-versions/azure/devops/pipelines/test/test-impact-analysis?view=tfs-2018)
  → 采纳：选择三集合 + safe-fallback + 周期全量，正是 B3 的骨架。本仓对应物：impact_analysis 多跳闭包（558 Part C 已落地，纯 Python frontmatter 图，**不用 CTE**——数据源不是 SQLite）。
- **TestPrune（FSE 2026，arXiv:2510.18270v2）**：把回归套件最小化到高相关子集喂给调试 agent，SWE-Bench 上问题复现率相对 +6.2–9.0%、解决率 +8.0–12.9%，单实例检索成本 $0.02–0.05。
  → 部分采纳：其"最小化是为了上下文预算"的动机与本仓 fast 套件同构；但它的最小化依赖 LLM 相关性判断，**本仓选择规则只用机械的依赖闭包**，可解释、可审计、零误判自由裁量。
- **风险型回归策略（企业实践综述，2026-07）**：TIA 典型削减 60–80% 执行量；三层执行（每提交冒烟/合并核心/发版全量）是行业共识；flaky 率 >15% 会摧毁套件可信度。[totalshiftleft 指南](https://totalshiftleft.com/blog/regression-testing-strategy-enterprise-guide)
  → 采纳三层套与"选择集-全量周比对"；数字（60-80%）只作预期量级，本仓以实测为准（B3 目标 fast 98s→15-25s）。
- **ReCatcher（arXiv:2507.19390，2025-07）**：模型换代的回归测试框架，实测 GPT-4o-mini 相对 GPT-4o 执行时间退化达 80%。
  → 直接对接本仓 reverify_model/W 批次 canary（534 §7.3）：换模型时结构性 canary 任务集的做法有学界同款背书。
- **不采纳**：ML 预测型测试优先级（随机森林/RL 排序）——56 卡规模用机械闭包足够，引入学习型选择器等于引入不可解释漏判面。

## C2. 内容寻址构建 / 远程缓存（支撑 B2 不可变工件目录；大部分不采纳）

- **Bazel Remote Cache（ACM Queue 实战文）**：action = 命令+环境+输入文件 Merkle 摘要；命中则从 CAS 下载产物不执行；构建与测试动作同构；缓存可独立淘汰，miss 自动回退本地执行。[dl.acm.org/doi/pdf/10.1145/3267120](https://dl.acm.org/doi/pdf/10.1145/3267120)
  → 只借"action 指纹 + miss 回退"思想到 B2 的 replay_resultset 指纹（工作树不符即弃清单）。**不引入 Bazel**：108 个工具的小仓、夹具是自由 cpp 不做 hermetic BUILD 图，迁移成本大于收益。
- **Nix CA derivations 现状（2026 技术参考）**：内容寻址派生 2.4 起实验，到 2026-03 稳定化里程碑仅 ~65%，Lix 分叉在删它；输入寻址保证"输入逐字节一致"但不保证产物逐字节（编译器本身需确定性）。[gist 技术参考](https://gist.github.com/wyattgill9/990529c04d4b62e11a1f63fb789c30e4)；HN 讨论（2025-02）明确"Nix 保证可复现环境，不保证 bit-exact 产物"。
  → 支撑本仓既有口径：sha 锚定同编译器同 TU，跨编译器走结构断言（533 已定），不追求跨环境字节复现；**CA 缓存不能当判决**——它回答"这些输入曾产生过这个输出"，本仓 replay 要回答"此刻此编译器确实产生它"。
- **构建系统选型综述（2026）**：CMake+Ninja 事实标准；Bazel 强在 hermetic/远程/超大 monorepo，弱在第三方异构依赖与采用成本。[gist 选型](https://gist.github.com/MangaD/26ef92a1e1efd967c3e0188dc0591e83)
  → 维持现状（无构建系统、单 TU 直调 g++）是合理的；不上 Meson/Ninja。
- **确定性并行测试隔离**：业界共识做法与 508 失败教训一致——hermetic 沙箱（每测试独立临时根/临时 HOME）是并行正确性的前提，而非调度器参数。本仓 B2 给的就是这个：每 worker 独立工作根+按卡加锁+输入冻结，不用 xdist 的隐式共享。

## C4. coding agent 长期记忆 / 经验回放（支撑 E2）

- **Letta Code（2025-12-16 发布，memory-first 编码 agent）**：长生命周期 agent 跨会话持久；`/init` 深读代码库形成 memory blocks；`/remember` 显式反思；skill 学习沉淀为 .md 并可 git 版本化；TerminalBench 上模型无关 OSS harness 第一。[letta.com/blog/letta-code](https://www.letta.com/blog/letta-code)
- **Context Repositories（Letta，2026-02-12）**：记忆即**本地文件系统上的 git 仓库**，agent 用 shell/脚本程序化管理（progressive disclosure），frontmatter 描述控制是否常驻 system prompt（`system/` 目录）；多 subagent 用隔离 worktree 并发写记忆再 git 合并。[letta.com/blog/context-repositories](https://www.letta.com/blog/context-repositories/)
  → 这是 E2 最直接的形态依据：本仓记忆资产也应是**带 frontmatter 的版本化文件 + 一个机器查询入口**，而不是更多散文 .md；"system/ 常驻 vs 按需检索"对应本仓"铁律/判据常驻投喂词、案例库按需 grep"。
- **Anthropic Memory tool（Claude 4+，2025-08）**：just-in-time 检索（用时读文件而非全量入 context），client-side 文件操作，路径遍历保护；官方语境工程文强调渐进披露。[platform.claude.com memory-tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
  → 采纳 JIT 原则：失败案例库按结构化条目检索，不进每次上下文。
- **Letta Memory Models（2026-06）**：指认"LLM 会用 context 但不会可靠地为未来造 durable context，memory rot 真实存在"，未来需专门的 memory model；token-space 学习（sleep-time/self-study/skill）是当前主流但昂贵且过泛化。[letta.com/blog/towards-agents-that-learn](https://www.letta.com/blog/towards-agents-that-learn/)
  → 边界依据：本仓不指望模型自动沉淀记忆，**记忆入库走结构化模板+人/红队确认**（与自动 KG 入库冻结同口径）。
- **MemGPT 三层（core/archival/recall）**：[chatforest 综述（2026-05）](https://chatforest.com/reviews/letta-memgpt-stateful-agent-framework/)。→ 本仓映射：core=投喂词铁律/三分类（常驻），archival=`data/` 结构化案例库（检索），recall=worklog/对抗报告（全文留证，不入判决）。

## C5. RAG 用于高保证验证：正确姿势与红线（支撑 E1）

- **VeriCite（SIGIR-AP 2025，arXiv:2510.11394）**：三阶段——初答→NLI 模型逐 claim 验证→支持证据选择→最终精炼；在 5 个开源模型/4 数据集上提升引文质量且不伤正确率。
  → 借"逐 claim 挂证据 + 独立验证器"形态；但本仓验证器不是 NLI 模型，是**编译器/gate/引用闭包**——RAG 检索到的条文是 claim 候选，必须被本仓 Oracle 复算或人签，与 526 铁律一致。
- **CATS 冲突感知 RAG（arXiv:2512.16795，2025-12）**：文档级裁决→冲突分析→接地综合三段，冲突时给"有据拒绝"而非硬答；539 查询集上评估接地性/事实正确性/拒答准确性。
  → 采纳"冲突即拒答/挂起"：外部来源互相矛盾（如标准草案 vs cppreference 实现差异）时进 open_questions，不入卡。
- **Consultative AI 量化（arXiv:2601.15476，2026-01）**：提出 false citation rate(FCR)/fabricated fact rate(FFR) 两指标，双盲专家评测 12 模型 2700 答，结论是 RAG 把模型从"创意神谕"变"档案员"但仍需验证管线。
  → 指标形态可借：E1 的检索通道也应统计"引文失效率"（检索条目不复现/被 Oracle 驳回比例）。
- **Faithful RAG 验证（arXiv:2603.10143，2026-03）**：rationale verifier 把陈述分八类（显式支持/隐式/无证据/错误信息…）。→ 借"无证据"是独立类别：检索不到不等于证伪。
- **红线（本仓明确拒绝的 2025-2026 流行做法）**：LLM-as-judge 替代编译/测试判决；把检索片段直接写入 verified_facts；同质模型辩论提高置信；在线改权重；用 RAG 召回的"答案"跳过外部复算。这些在高保证域被多篇文献自己标注为"减少但不消除幻觉"，本仓零容忍。

## C6. 三档归属（并入 00 路线图）

- **现在做**：TIA 式机械测试选择+周比对（B3）；记忆资产文件化+结构化+JIT 查询（E2）；检索双通道之"线索通道"与引文可追溯模板（E1）。

- **等模型变强**：memory model 自动沉淀（Letta 2026-06 自陈尚不可靠）；NLI 式 claim 验证辅助（只能进 advice 通道）；语义检索/embedding 入 KG（自动入库冻结项不解禁）。
