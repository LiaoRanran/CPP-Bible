# 04 · 证据时效性与漂移调研（644 阶段 A · A4）

> 任务：调研标准版本管理 / 编译器版本差异 / 学术撤稿更正 / 证据过期检测，≥5 个案例，含漂移检测建议。

## 一、五个案例

### 1. 标准版本管理（C++ 标准演进）
- C++ 每 3 年一版（C++17/20/23/26）。同一条款可能在新版改写（如 `std::allocator` C++17 移除 construct）。
- **案例**：EV-MEM-026 锚定 c++23；若未来 c++26 改 allocator 语义，该证据需重新判定。
- **检测**：记录 `matrix.std`，跨标准版本复测。

### 2. 编译器版本差异
- 同代码 GCC 13 vs 15 行为可能不同（bug 修复、警告升级为错误）。
- **案例**：`-Werror` 下某警告在 15 变错误，导致旧证据「编译通过」失效。
- **检测**：D2 记录 `compiler_version`；C3 重取比对。

### 3. 学术撤稿 / 更正（retraction / correction）
- 论文被撤稿后，引用它的「证据」应降级或作废。
- **映射**：阙疑若引用的外部博客/文章被作者更正，证据需标记过期（对应 L5 或 `expired`）。

### 4. 网页内容漂移（链接腐烂 link rot）
- 网页改版、URL 失效；cppreference 页面会随标准更新改写。
- **映射**：D1 存原始内容 hash；C3 周期性重取比对 hash，漂移则标记。

### 5. 证据文件自身漂移（627 已发现）
- 627 发现 56 张 PCK `evidence.hash` 与文件不匹配（内容行尾/编码/真实变更）。
- **映射**：C3 直接复用「hash 比对」思想；头部层存储的证据也需自校验。

## 二、漂移检测建议（落到 C3）

1. **静态 hash 校验**：`EvidenceID == SHA256(content)` 每次读取都验（已实现 `is_valid`）。
2. **来源重取比对**：对 `source_url` 可访问的证据，定期重取并比 hash，差异记入漂移清单。
3. **版本维度标记**：每条证据存 `matrix`（std/compiler/opt/arch），跨版本变化时触发重测。
4. **过期时间**：网络证据建议设 `freshness_ttl`（如 180 天），到期标 `stale` 需人审。
5. **处置建议**：重取 / 标记过期 / 人审——与 §十一.7（是否定期重取）呼应。

## 三、落到 644 阶段 C/E 的设计输入

- **C3 `evidence_integrity_644.py`**：hash 一致性 + 来源重取对比 + 引用但已删。
- **E1 `evidence_gap_scanner_644.py`**：把「过期」作为不足项之一。
- **E2 求索触发器**：过期证据触发重新获取（D5），获取后重判充分性。

> 漂移是诚实红线（§十二.8）：「获取失败」≠「证据不存在」，只标记不编造。
