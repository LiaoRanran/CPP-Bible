# 00 · 综合与头部层架构设计建议（644 阶段 A · A5）

> 把 A1（等级）· A2（寻址）· A3（获取）· A4（时效）收敛成 644 阶段 B–E 的具体设计输入。
> 本文件是 A1–A4 的结论落地清单，不是又一份调研。

## 一、A1–A4 收敛结论

| 维度 | 调研结论 | 644 采纳 |
|---|---|---|
| 等级 | 等级应是**可移动量表**（GRADE），分离「可采性」与「分量」 | L1–L5 + credibility 可修正；grade 表分量、source_url 表溯源 |
| 寻址 | 内容寻址天生不可变（Git/IPFS）；溯源三元组必存 | SHA256(content) + `<hh>/<hash>` + url/time/method 必填 |
| 获取 | 本地实测最可靠、网络抓取需降级与合规、反例只搜不判 | D1 降级、D2 沙箱、D3 不判定 |
| 时效 | 标准/编译器/网页都会漂移；需 hash + 重取 + TTL | C3 漂移检测 + 过期标记 |

## 二、对 B–E 的 5 条可直接执行的设计输入

1. **等级映射修订（B1）**：cppreference 从「L2 权威」降为「L3 共识」（二手）；AI 生成默认 L5。实现见 `evidence_base_644.grade_from_source`。
2. **充分性判据（B2）**：`充分` = ≥1 条 L1/L2 且 ≥3 条独立 且 反例已处理 且 未过期 且 hash 一致；否则 `不足` 或 `需人审`（边界：有反例未处理→需人审）。输出缺失项清单。
3. **冲突检测（B3）**：同卡多条证据矛盾（L1 vs L2、不同编译器结果不同）→ 严重度分级 + 建议（人审/重测/标记争议）。无冲突不误报。
4. **内容寻址与索引解耦（C1–C2）**：store 只存证据 blob（不可变）；`evidence_index.json` 存多对多关联（support/refute/background），绝不写卡片 YAML。
5. **获取器统一契约（D1–D5）**：所有获取工具返回 `{ok, evidence_records, error}`；网络不通 → `ok=False, error="获取失败"`（降级）；沙箱隔离；编排器 D5 用 B2 判充分性 + N 轮上限 + 只获取不修改卡片。

## 三、头部层与尾端的关系（铁律 §九）

- 头尾**解耦**：头部层只「向外求索 + 保存候选」，尾端 `evidence/` 仍是生产判决证据。
- **只读联动（E3）**：头部新证据喂给尾端验证器做「是否支持卡片结论」的只读校验，不修改任何生产数据。
- **人审后才关联（§九.6）**：自动获取的证据默认不写 `evidence_index.json` 的生产关联，需人审后才建立。

## 四、诚实边界（落到 §十二）

- D1–D4 是**原型级**，不是生产爬虫（§十二.1）。
- 等级是**启发式**（§十二.2），阈值需人审。
- 反例搜索**可能漏**（§十二.3），只搜不判。
- 编译器实测**只有 g++**（§十二.4）。
- 范围以「头部层点火 + 调研 + 原型」为限（§十二.9），不扩展到实时答案验证/跨领域/信任根独立。

> 以上 5 条设计输入已逐条落到 B1–B3、C1–C2、D1–D5、E3 的具体工具实现。
