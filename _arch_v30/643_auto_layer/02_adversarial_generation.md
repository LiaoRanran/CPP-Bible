# A2 · 自适应攻击生成调研（对阙疑怎么用）

> 643 阶段 A。检索 7 次（覆盖引导变异 / LLM 引导模糊 / 针对验证器的对抗样本）。
> 检索日期：2026-09-26。

## 一、现有做法盘点（≥5）

| # | 名称 | 机制 | 对阙疑的可借点 | 关键失败模式 |
|---|---|---|---|---|
| 1 | **AFL / AFL++**（灰盒覆盖引导） | 位翻转/算术/字典/拼接等**通用变异算子** + 覆盖反馈选种子（power schedule） | 阙疑已有 M1–M7 算子族与 622/623 沙箱跑批 ⇒ **算子库现成** | 通用变异**盲目**：对"语义级缺陷"命中率低；覆盖反馈需要**可测的覆盖**（阙疑的"覆盖"是规则命中，非代码行） |
| 2 | **libFuzzer**（in-process 覆盖引导） | 与被测库链接，最大化覆盖语料 | **in-process** 思路：阙疑可在**同进程**内对多卡批量跑（省掉子进程开销） | 需要"测试入口点"；阙疑的入口是 gate 判决，**无 oracle**（逃逸=没报，不等于"错"） |
| 3 | **FuzzGPT / TitanFuzz**（LLM 合成/变异程序） | 用 LLM 生成**罕见程序**当种子/变异源 | **用 LLM 生成"看起来合法但语义越界"的卡**正是阙疑的"对抗样本"来源 | **成本**：每次 LLM 调用远贵于位翻转；**有效性难证**（"LLM 更会找 bug"多为按次迭代的演示，非等价预算对比） |
| 4 | **Token-level fuzzing**（UCSB，AFL 之上） | 在 **token 层**而非字节层变异（对解析器/语言类目标更对味） | 阙疑的输入是 **Markdown 卡（结构化文本）** ⇒ **字段级/模板级变异**天然优于字节级 | token 边界识别错则变异"无效"（生成物连格式校验都过不了，等于**空跑**） |
| 5 | **LLM-guided 种子重加权**（把 LLM 当"种子生成器/打分器"接在覆盖 fuzzer 上） | LLM 只负责**生成高质量种子**，覆盖引导负责**淘汰** | **分工**是阙疑该抄的：LLM（或规则）只做"**生成计划**"，**淘汰交给机械 oracle**（gate 判决） | 若让 LLM 兼做淘汰判断 ⇒ 引入不可审计的偏差 |
| 6 | **针对检测器的对抗样本**（日志分析器规避、二进制检测器"合法性注入"） | 在**保持功能等价**的前提下让检测器失灵 | 阙疑的"语义等价改写"变异（C2 的 5 类之一）就是这一族 | **不是所有检测器都该被规避**：把"防御本身失效"当成功，会掩盖**真缺陷**（须人审确认） |
| 7 | **Prompt injection / 提示注入**（对 LLM 判定环节） | 在**被审内容**里埋指令影响 LLM 判定 | 阙疑有 `quadrant=llm|hybrid` 的规则与 LLM 环节 ⇒ **提示注入是真实攻击面**（L1.x 层） | 阙疑当前是"机器判决为主"，LLM 参与度低 ⇒ 优先级低于结构性攻击 |

## 二、失败教训（归纳 5 条）

1. **"找到逃逸"≠"找到缺陷"**：fuzzer 报的 crash 要**去重 + 根因归类**，否则报一堆同因不同形的样本。
   ⇒ 阙疑须按 **归因**（D1）而非按**条数**汇报。
2. **等价预算对比**：LLM 引导的收益常来自"每次迭代更贵"，不做**等算力**对比就是自欺。
   ⇒ C4 必须做**针对性 vs 随机**的同预算对比（否则质量报告无意义）。
3. **变异必须"过得了格式门"**：大多数随机变异连 卡 的 frontmatter 校验都过不了 ⇒ **无效样本占绝大多数**。
   ⇒ 阙疑要有**有效性口径**（C4 的"有效攻击率"= 真的进入规则评估的比例），否则逃逸率被稀释成噪声。
4. **oracle 缺失是根本困难**：模糊测试靠"程序崩了"当 oracle；阙疑的 oracle 是"**该报没报**"，需要**预期规则**（`expected_oracle`）显式声明。
   ⇒ 阙疑的 mutation **必须自带 `expected_oracle`**（C2），且要登记"预期可能猜错"（§十二.7）。
5. **覆盖反馈不可移植**：AFL 的 power schedule 依赖**行覆盖**；阙疑需要自造"**规则命中 + 规则新增**"的覆盖代理（622/623 已有 `new_block_rules / lost_rules`）。

## 三、对阙疑的设计结论（落 C 阶段）

| 结论 | 落到哪 | 具体做法 |
|---|---|---|
| K1 **从规则 precondition 反向生成** | C1→C2 | 目标导向：`target_rule → precondition → artifact carrier → mutation operator → expected_oracle`（v29 收敛建议） |
| K2 **字段级/模板级变异，不做字节级** | C2 | 5 类：字段删除 / 值篡改 / 跨卡引用断裂 / 格式微扰 / 语义等价改写（都保持"能被解析"） |
| K3 **每个 mutation 自带 `expected_oracle`** | C2 | 并登记"预期命中率可能猜错"，由 C3 实测修正（预期错 ⇒ 记 `oracle_mismatch`，不改预期） |
| K4 **生成与淘汰分工** | C2/C3 | 生成侧（规则驱动，本批**不引入 LLM**）只出计划；淘汰侧用**机械 gate 判决** |
| K5 **等预算对比** | C4 | 同预算下"针对性 vs 随机"的逃逸率/有效攻击率对比，样本量小则**明确说无统计意义** |
| K6 **沙箱隔离 + 零生产副作用** | C3 | 复制卡到临时目录再跑 gate（复用 `mutation_fuzz.sandbox()` 思路），生产 `atoms/` 零触碰 |

> **诚实登记**：本批**不引入 LLM 生成攻击**（成本/可审计性），只做**规则驱动的针对性变异**；
> 因此"A2 的 LLM 路线"在 643 只到"设计结论"层，未实现。FuzzGPT/TitanFuzz 的具体数字本次未逐篇核对，
> 只借其**形态**（LLM 生成罕见输入）与**教训**（等价预算、去重、oracle）。
