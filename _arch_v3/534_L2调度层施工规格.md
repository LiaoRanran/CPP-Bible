### 2.4 并发 claim 与接管的 SQL（单事务，已双进程实测）

```sql
BEGIN IMMEDIATE;
-- ① 自动 stale 回收（落地版 _sweep_stale 原样复用，只在非 takeover 路径）
-- ② 人工接管（人知道旧会话已死；机器不知道，故必须显式）
UPDATE tasks SET status='queued',claimed_by=NULL,claimed_token=NULL,
       lease_expires=NULL,heartbeat_at=NULL
WHERE id=:tid;                       -- 前置：心跳<grace 必须 --force+--reason，否则回滚
-- ③ 候选：落地版 ORDER BY 不动，循环内 deps 门 + touch 过滤
--    跳过者写入返回体 blocked_by_touch:[{id,blocked_by:[{task,files}]}]
-- ④ 认领（与落地版同一句 WHERE，双保险）
UPDATE tasks SET status='claimed',claimed_by=:w,claimed_token=:secret,
       claimed_at=:now,heartbeat_at=:now,attempts=attempts+1
WHERE id=:id AND status='queued';
COMMIT;
```

**租约语义（上一沙箱会话现场发现、本轮实测继承的关键设计）**：任务已被 claim 且心跳在 grace（默认 120s）内时，裸 claim **拿不到**、无 force 的 takeover 也被拒——否则新会话一进来就顶掉别人正在干的活。接管只有两条路：心跳过期走 stale（机器判定死亡），或人显式 `--takeover T --force --reason "旧会话到顶/kill"`（人担责留痕，events 表记 manual_takeover）。

**deps 环检测的诚实结论**：在"deps 仅在 enqueue 时声明 + 缺依赖即拒 + id 幂等"三重约束下，插入新节点在图论上构不成环（新边只从新节点指出），唯一例外是自引用 `id∈deps`——实测它被"缺依赖"检查先行拦截（S8 self_cycle_msg=`deps 引用不存在任务：['LOOP']`）。DFS 环检测仍写入（`_has_cycle`），价值在防未来开放"加边/改 deps"命令与自引用笔误；不夸口它挡得住当前构造不出的环。

### 3.1 字段模板（v1，block 写法；文件存 `data/tasks/<id>.handoff.json`，路径入 handoff_path 列）

```json
{
  "schema": "tq-handoff/v1",
  "task_id": "TMAIN",
  "goal": "一句话可验证目标（完成判据写在这，不是愿景）",
  "steps_done": [{"n": 3, "title": "…",
    "outputs": [{"path": "work/step3.txt", "sha256": "<64hex>"}]}],
  "steps_remaining": [{"n": 4, "title": "…", "action": "具体命令",
    "touch": ["work/step4.txt"]}],
  "verified_facts": [{"fact": "…", "trust": "L1|L2|L3",
    "anchor": "path:line | cmd:<可重跑命令> | git:<sha>"}],
  "tried_and_failed": [{"attempt": "…", "why_dead": "…", "evidence": "锚点"}],
  "next_action": "继续 step 4（claim 后逐步 checkpoint）",
  "touched_files": ["work/step1.txt"],
  "budget_used": 380,
  "open_questions": []
}
```

| 字段 | 必填 | 机器校验（不过即拒，yield/checkpoint 共用 `validate_handoff`） |
|---|---|---|
| goal | 是 | 非空 |
| steps_done[] | 是 | 每项有 title；outputs.path 必须**在盘**，有 sha256 必须**逐字相等**（防产物被偷换/半成品冒认） |
| steps_remaining[] | yield 时必填非空 | 空 remaining 应走 complete 而非 yield |
| verified_facts[] | 是（≥1） | trust∈{L1,L2,L3}；anchor 必填且可解析：文件锚点必须存在，`cmd:` 长度合法；**L2 必须用 cmd: 锚点** |
| next_action | 是 | 长度≥4 且像具体动作 |
| tried_and_failed / open_questions | 否 | 队列只展示不判决（open_questions 非空时 doctor 提示等人裁决） |
| budget_used | 是 | 非负整数 |

校验函数是纯函数，gate 可原样复用（同 EV-FALSIFICATION 的 gate/replay 双侧复用模式）。

### 3.2 checkpoint 频率与"关键步骤"判据

落盘点 = 每个**产生了可命名产物或外部状态变化的步骤**完成时：写完文件/跑完验证/提交入队之后立即 checkpoint，而不是任务结束。判据给苦力一句话：**"这一步若丢了，新会话需要重跑一条命令才能恢复——就值得 checkpoint"**。读取/思考类动作不落盘。实测每步事务中位 11.5ms【实测 S6】，频率成本可忽略。

指纹 `cp_fingerprint = sha256(各 done 步的 n+产物 path/sha256 … + remaining 数量)[:16]`，用于假活检测（§6.3）。

### 3.3 端到端续跑时序（主场景，实测全绿）

```
会话A：claim TMAIN(attempt1) → step1→cp step2→cp step3→cp → 【kill -9，3.72s 时】
人  ：只做一个动作——开新会话
会话B（新进程，除 db 路径/worker id 外零上下文）：
  1) claim（裸）           → claimed=null  【心跳 120s 内，不顶活人】
  2) claim --takeover TMAIN（无 force）→ exit2 "疑似仍在跑"
  3) claim --takeover TMAIN --force --reason "A 到顶被 kill"
     → 成功；输出 handoff 全文；attempt=2；events 记 manual_takeover
  4) 对 steps_done 逐条做盘上哈希核对：
       step1-3 哈希全中 → TRUST（不重做）；发现盘上有未被枚举的 step4.txt 半成品
       → 不承认、直接覆盖重写（只信 handoff 枚举）
  5) step4→cp step5→cp → complete（verify_cmd 自动跑）→ done
结果【实测】：A_did=[1,2,3] B_trust=[1,2,3] B_did=[4,5] redo_overlap=[] status=done
```

B 判断"前 3 步不用重做"的唯一依据是**独立核对**（新进程自己读盘算哈希，不是读 A 的声明）；判断"从第 4 步开始"的唯一依据是 handoff.steps_remaining 的绝对步骤号（子任务场景同构）。

### 3.4 yield 切子任务算法（S4 实测：A 1-2→子任务→B 3-4-5→父子双 done）

1. handoff 全量校验（remaining 非空）；预算剩余 <100 或 `--force` 才让出（预算还足不允许逃）。
2. 默认切 **1 个**续跑子任务 `<id>.c1`（携带全部 remaining、继承 touch_set/verify_cmd/budget，预算按剩余比例且 ≥80）；handoff 显式给 `step_groups` 时最多切 `MAX_CHILDREN=4` 个，组间自动串 deps；空子任务拒绝（防碎片）。
3. 父→`yielded`、释放所有权；子→queued。普通 claim 即可领到（父已非 claimed，touch 不互锁）。
4. 最后一个子任务 complete 时，检查 `parent` 的所有子任务全 done → 父自动 done（回卷）。

## 4. 任务 3 · 写冲突锁 + 完成验证闭环

### 4.1 touch_set 文件锁（派发时 + 完成后两道）

**派发时（预防）**：enqueue 声明 `--touch`（posix 相对路径逗号分隔）；claim 候选循环里，候选 touch_set 与任一 claimed 任务的 touch_set 相交即跳过，返回体点名：

```json
{"claimed": {…"id":"TC"…},
 "blocked_by_touch": [{"id":"TB","blocked_by":[{"task":"TA","files":["work/shared.txt"]}]}]}
```

实测 S2：A 领 TA（touch shared）后，B 的 claim 跳过 TB、领走不冲突的 TC，同时拿到"TB 在等 TA"。这把 55b53ae/527 类事故（两人同改工作树互不知）从事后清理变成派发时可见。

**完成后（审计）**：complete 时跑 `git status --porcelain -uall`，真实改动减去声明集再减去系统豁免（queue.db*、workers/*.token、handoff_path 登记文件）= `undeclared_touch`，写入 done 事件。
**实测教训（写进施工版，探针已按此实现）**：①必须 `-uall`，否则整个未跟踪目录只显示成 `work/`，逐文件声明永远匹配不上；②主场景实测审计真抓到一个漏报——`work/journal.log`（worker 运行日志未声明），证明审计有效；施工时约定 worker 日志固定到 `data/tasks/logs/`（自动豁免）或在 touch 用 glob 声明。

### 4.2 complete 验证闭环（worker 不自证）

`complete <id> --worker w`：所有权校验 → 取 verify_cmd（行内或参数）→ 在锚根跑（超时沿用 900s）→

- rc=0：置 done，`verify_hash=sha256(out+err)[:16]@<耗时>s rc=0`，触发父回卷；
- rc≠0：attempts+1、error 记尾部 300 字，>MAX(3) → blocked，否则回 queued 释放所有权；
- 无 verify_cmd：必须 `--result-ref`，verify_hash=`HUMAN_REVIEW_REQUIRED`（研究/文档类转人审，不允许裸 done）。

实测 S5（MAX=2 加速复现）：A verify 失败→queued(attempts=2)；B 再失败→**blocked(attempts=4)**，事件链 verify_failed/requeue/blocked 齐全。

### Windows + SQLite 诚实坑单

1. **【本轮挖出的最深坑】冷启动双进程建库竞争，实测 6/8→修复后 0/12**：两个进程同时对**不存在的库**跑首个连接时，①落地版 `_connect` 的 `PRAGMA journal_mode=WAL` 排在 `PRAGMA busy_timeout` **之前**——切 WAL 要排它锁而此刻还没有锁等待预算，直接 OperationalError；②增量迁移若把多个 ALTER 逐条自动提交，第二个进程会读到"加列中途"的中间态，两进程补同一列 → `duplicate column name`（实测 6/8 命中）；③`init 连接关闭→迁移连接开启`之间还有缝隙（单事务迁移后仍 1/10 复现）。**修法（已在 tq_ext 实测）**：迁移用独立单连接，先 `busy_timeout` 后 `journal_mode`，建表（引用 `tq.DDL`）+全部 ALTER+events 放进**一个 BEGIN IMMEDIATE**，用 `PRAGMA user_version` 做版本门，第二个进程等锁后见版本已升整段跳过。修复后 12/12 双进程冷启动零失败。稳态（库已存在）再无此问题，所以 d976170 的 8 测试（线程+已建库）没暴露它。
2. **journal_mode 是数据库头持久属性，但裸连接在建库前 PRAGMA 读到默认 delete**（S7 首跑误报）：查询模式必须在首个迁移连接之后；进程全退出后 wal/shm sidecar 被 checkpoint 合并是正常 clean shutdown。
3. **库建好后 WAL + busy_timeout 下并发写零 locked**【实测：稳态 40 次双进程写 ×多轮、4×25 共 100 次均 0 错误】：落地版稳态选型正确；不要加 `?nolock=` 网络盘 hack。网络盘/杀软目录是已知 WAL 风险，队列库放本地 `data/tasks/`。
4. **taskkill /F 不执行 atexit**：靠 WAL 已提交事务存活（checkpoint 每步独立提交），不靠进程清理——"被杀最多丢一步"的物理基础。
5. **文件句柄延迟释放 + git 只读位**：进程退出后 q.db 句柄可能残留数百毫秒、`.git/objects` 只读，测试沙箱 rmtree 要 chmod 清位 + 一次短重试（onExc）。
6. **控制台编码**：子进程统一 `encoding="utf-8", errors="replace"`；taskkill 输出是 gbk，单独按 gbk 解。
7. **时间戳比较**：heartbeat 用落地版同款本地 ISO 秒级字符串，stale/grace 统一走 `time.mktime(strptime(...))`，别混 offset-aware。

## 6. 任务 5 · 对设计的自攻（5 条，含机器判据）

### 6.1 冒名（E12）：claimed_by 字符串不够，叠加 token possession

落地版只比 `claimed_by` 字符串，知道名字就能冒充。增量：claim 时在 `data/tasks/workers/<worker>.token` 落 128-bit 随机 secret（文件含 host/user/pid/创建时间），行里存 `claimed_token`；heartbeat/checkpoint/yield/complete 同时校验 worker 名 + **磁盘 token 与行内一致**。实测 S8：bob 无 token 文件，heartbeat 与 complete 均 exit2。边界（诚实）：同一 Windows 用户能读 token 文件就能冒充——本机单人场景文件系统权限即信任边界；跨用户/CI 场景再升级为 OS keyring/签名。

### 6.2 deps 环：enqueue 即检（结论见 §2.4）

DFS 沿 deps 链找回边，自引用/未来加边命令成环在入队事务内拒绝；当前"仅入队声明+缺依赖即拒"约束下新任务无法成环，自引用被缺依赖检查先行拦死——如实记录，不夸大。

### 6.3 假活/僵尸：心跳在但不推进

新增 `last_hb_fp/hb_same_count`：心跳携带当前 handoff 指纹，与上次心跳指纹相同则计数+1，≥1 报 `heartbeat_zombie`，doctor 列入 zombie_suspect；指纹推进即清零。实测 false→true→（checkpoint 推进后）false。**关键区分**：checkpoint 推进指纹不算心跳重复（正常工作）；必须是两次心跳之间没有新 checkpoint。施工版叠加"间隔须达一个完整心跳周期"，避免长步骤误报。stale（心跳停了）与 zombie（心跳活着但没进度）是两类假活，doctor 分开报。

### 6.4 handoff 投毒（最关键）：可继承/必复核的机器判据

信任不是整体开关，按 verified_facts 的 **trust 三级 + 锚点形态**判：

| 级 | 形态 | 机器判据 | 新会话动作 |
|---|---|---|---|
| **L1 物证** | 文件锚点 `path[:line]` | 新会话**独立重算**该文件 sha256，与 steps_done 记录一致 | 可继承（只防损坏/偷换；**不证明内容正确**） |
| **L2 判决** | `cmd:<命令>` | 必须是可重跑命令；**claim 后由新会话独立执行一遍**，结果与 fact 描述一致才采信 | 必复核（自动重跑，成本=一次 verify 量级） |
| **L3 裁决** | 人签/外部事实/标准条文 | 无机器锚点（git sha 仅证明出处） | **永不自动继承**：进 open_questions，人/红队重判；不得作为跳过步骤的理由 |
| 无锚点/锚点不存在/L2 用文件锚 | — | checkpoint/yield 直接拒收 | — |

**残余攻击（诚实承认）**：上一个会话"认真做错"并配了真哈希——L1 会通过。机器层封死的是传输/篡改类错误；语义正确性靠 ① complete 的 verify_cmd（最终闸门重跑）② L2 关键判决强制重跑 ③ L3 不继承 ④ 产物未被 handoff 枚举一律重做（挡半成品，主场景已含一例 step4 残留）。即：**新会话被允许"偷懒"的只有 L1 的字节级一致；任何判决性结论要么可重跑、要么走人**。

### 6.5 预算误判与碎片：三道量化闸门

① yield 预算门槛（剩余 ≥100 不许让）；② 单次切分 ≤4 个子任务、空子任务拒绝、每子预算下限 80 calls；③ 父回卷依赖全部子任务完成。施工期把"预算实际/估计比"与"单任务平均子任务数"进 doctor/周报：连续 2 批中位误差 >2× 就回头修预算指引（改估计方法，不放松闸门）。

## 7. 任务 6 · 架构质变调研（批判吸收）

### 7.1 长流程断点恢复（直接支撑 handoff/checkpoint）

- **Temporal**：核心是 append-only Event History + 确定性 replay——崩溃后新 worker 重放历史重建内存状态，重放到"未决定点"继续；工作流代码必须确定，与历史不一致报 non-determinism 错误；事件历史 **10240 条告警**，靠 Continue-As-New 续接（[Temporal Events 文档](https://docs.temporal.io/workflow-execution/event)、[Event History walkthrough](https://docs.temporal.io/encyclopedia/event-history/event-history-python)、[2026 三引擎综述](https://iotdigitaltwinplm.com/durable-execution-architecture-temporal-restate-dbos-2026/)）。
  **可迁**：append-only 事件表（=events）、状态只靠重放重建（=claim 后读 handoff）、副作用必须可重放（=verify_cmd/锚点）。**不迁**：Temporal Service、独立 worker 进程池、定时器/Signal 全套——对单人仓库是纯负担；我们的"重放"粒度是步骤不是指令级，确定性靠 L1/L2 锚点而非全函数确定性。
- **Airflow**：Task Instance 有完整状态机（queued/running/up_for_retry/deferred/awaiting_input…），clear 不删记录只重置状态并保留 max_tries（[Airflow 3.0 Tasks](https://airflow.apache.org/docs/apache-airflow/3.0.6/core-concepts/tasks.html)）。
  **可迁**：`up_for_retry`=我们 verify 失败回 queued 且 attempts+1；clear 保留历史=stale/takeover 保留 attempts。**不迁**：调度器常驻进程（G-supervisor 边界）。
- **LangGraph**：每个 super-step 末把 checkpoint 写库（不写内存）；pending writes 保证崩溃时同 super-step 已完成节点不重放；**resume 时传 None 不传新输入**否则从入口重跑；官方明确建议"每个节点开头自查持久状态、已完成则跳过"（[Checkpointers 文档](https://docs.langchain.com/oss/javascript/langgraph/checkpointers)、[Building LangGraph 2025-09](https://blog.langchain.com/building-langgraph/)、[resume 论坛 2025-08](https://forum.langchain.com/t/can-we-resume-from-the-checkpoint-and-continue-running-at-the-interruption-point-instead-of-starting-from-the-first-node/1240)）。
  **可迁且被本轮实测逐条印证**：每步骤落库=checkpoint；"传 None"=新会话只发 claim 不带任务内容；"节点自查"=worker 盘上哈希核对（我们纠正了它的坑：自查必须以 handoff 枚举为准，不能"文件在就算"，否则认半成品）。**不迁**：thread/time-travel/fork、Postgres checkpointer 平台。
- **业界流行但对本系统是错的**：上一套持久工作流引擎（Temporal/Cadence/Restate）或 Agent Server。我们的失败域是"会话 500 次调用到顶"，停机是计划内的、频率一天数次，11ms 的 SQLite 事务 + 文件 handoff 已实测够用；引擎引入的运维面比问题本身大。

### 7.2 预注册/可重复性（防事后编故事）

- OSF 预注册要求在数据分析前（实操 ≥24h）冻结假设与判据（[Transparency in Methods, 2026-04 verified](https://theneuralbase.com/ai-for-research/learn/beginner/transparency-in-methods/)）；ML 领域 2025 的主张是把评审对象从"结果大小"换成"实验设计"，并有论文指出自报清单/可选代码/作者自控日志无法回答"代码是否真产生了这些数字"，提出非否认性（nonrepudiation）签名报告（[arXiv:2605.08586, 2026-05](https://arxiv.org/html/2605.08586v1)；大样本软件工程实践调查 [arXiv:2502.00902v2](https://arxiv.org/html/2502.00902v2/)）。
