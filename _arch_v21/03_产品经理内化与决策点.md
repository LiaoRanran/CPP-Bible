## 一、产品经理对两波评审的总体判断

### 1.1 评审质量评估

**高。** 理由：
1. 评审者独立复算了关键统计数字（Clopper-Pearson 1/1406 C-P95=0.40%、56张卡0假阳性上界5.21%），全部对上——说明评审者真的读了数据，不是泛泛而谈
2. 评审者发现了项目作者自己没发现的问题（统计对象定义问题、镜像边隐藏delegation、打包缺陷、数字漂移）——说明有独立视角价值
3. 评审者的建议具体可执行（estimand三层拆分、四元组legacy、release manifest格式、SNAPSHOT_MANIFEST结构）——不是空话
4. 评审者明确区分了"已查证"和"一方称"，对拿不到一手数据的内容明确标待验证——诚实性与项目自身标准一致

### 1.2 评审中最有价值的三个发现

按产品经理判断的价值排序：

1. **统计对象定义问题**（第一波第1项）：这是比 peeking 更深的问题。CS 修复了"连续偷看"，但没有解决"1406个mutation到底对应什么随机总体"。如果不修复，0.9062% 这个数字对外宣传时会被内行质疑。**修复成本低（加estimand字段+品牌级说明），价值高（堵住统计口径的根本质疑）。**

2. **388条人审名不副实 + 镜像边隐藏delegation**（第一波第2/5项）：项目最大的"诚信品牌支柱"（388全量人审）被拆穿成批量授权。这不是小问题——任何怀疑者10行脚本即可复现。**修复成本中等（30条逐条复核+镜像边安全性证明），价值极高（修复诚信品牌的核心支柱）。**

3. **从verification correctness到verification independence的结构性判断**（第一波额外发现+第二波整体）：评审者准确指出了项目的演进方向和当前位置——"已经进入验证系统本身成为研究对象的阶段，但尚未进入外部第三方可独立复核的阶段"。这个定位比项目自己的六维度评分更精准。**价值：为后续所有架构决策提供了坐标系。**

### 1.3 评审中产品经理不完全同意的点

1. **"工具合并低优先级"**：评审者说工具合并低优先级，产品经理部分同意——确实不应该为了合并而合并，但当前204个工具中确实存在语义完全重复的（比如多个metrics收集器、多个审计工具），这些可以在不破坏证据链的前提下做轻量合并。**处理：列入P3，不紧急。**

2. **"data目录整理暂缓"**：评审者说暂缓，产品经理同意——历史可追溯性确实比目录整洁更重要。但"逻辑索引"应该做（37号路线图的导航层已经在做）。**处理：只做逻辑索引，不做物理移动。**

3. **"保形预测先不做生产实现"**：评审者说作为研究原型保留，产品经理同意——mutation stream确实破坏exchangeability，1/1406只有一个escape不适合支撑复杂conditional prediction。但ABSTAIN三态（雷6）是另一个问题，不是保形预测，应该单独推进。**处理：保形预测留研究轨，ABSTAIN三态留620。**

## 二、9 个决策点（产品经理建议）

基于两波评审，产品经理梳理出9个需要人审裁决的决策点：

### 决策点 1：CS 对外口径是否正式启用？

- **背景**：616 已实现 CS（anytime 上界 0.9062%），但未决定是否对外正式启用
- **评审建议**：有条件启用，作为 continuous-monitoring 主口径，cp_* 保留为 fixed-endpoint reference
- **产品经理建议**：**启用**，但必须同时加 estimand 字段（617 A1），禁止单独使用"逃逸率≤0.9062%"而不标注"在当前mutation流程的概率模型下的anytime上界"
- **影响**：品牌级说明更新、README数字更新（留交人）、对外宣传口径统一
- **风险**：0.9062% 比旧的 0.3370% 大 2.69 倍，对外宣传时"数字变大"可能被误解为"系统变差"——需要主动解释这是"更诚实的口径"而非"系统退化"

### 决策点 2：30 条逐条复核是否执行？

- **背景**：615 已出 30 条逐条复核决策清单（17 modify + 13 approve），但未实际执行
- **评审建议**：当前最值得做的一项，优先级高于绝大多数新功能
- **产品经理建议**：**执行**，但必须使用新人审 schema（加 review_seconds、review_method=item_by_item、confidence、evidence_refs），每条预计 3-5 分钟，总计 90-150 分钟
- **影响**：388 条人审中 30 条从 batch_authorization 升级为 item_by_item，人审记录可信度提升
- **风险**：耗时较长（用户时间成本），可能发现某些边的判决需要改变（如果复核后发现原 approve 有误，需要 reject——这会改变 W2 判决）
- **注意**：617 E1 只做可执行化和模拟，不实际执行——实际执行需要人审授权

### 决策点 3：镜像边安全性结论如何处理？

- **背景**：388 条人审中 194 条是 mirror edge（审一个方向，另一个方向免审）
- **评审建议**：镜像边是隐藏 delegation 通道，必须证明语义同构/权重同构/判决同构才能安全镜像
- **产品经理建议**：**先做 W2 判决对比实验**（617 E2），如果单向边和双向边的 W2 判决无差异，则镜像边在当前 W2 模型下是"判决安全"的，但仍需标注"mirror，未独立语义审查"；如果有差异，则 194 条镜像边需要逐条审查
- **影响**：如果判决无差异，镜像边可以保留（但标注）；如果有差异，需要追加 194 条人审（工作量翻倍）
- **风险**：W2 判决无差异不代表语义同构——可能只是当前权重下（全 low）恰好不影响判决，未来如果权重变化（modify→medium/high），镜像边可能变得不安全

### 决策点 4：他验架构是否进入实施（从 L1 升级到 L2）？

- **背景**：616 已建他验三件套原型（HMAC + 透明日志），独立性等级 L1（分离实现，同一信任主体）
- **评审建议**：应进入试点，但不要把 HMAC prototype 当成"独立验证已经实现"；最终需要非对称签名+独立公钥+独立runtime+外部透明日志
- **产品经理建议**：**L1 保持，L2 暂缓**。L2（分离执行）需要不同执行环境和不同密钥，单用户阶段不可达（用户只有一台电脑、一个身份）。可以先做 L1 的诚实化标注（617 B1），等有外部第三方（比如另一个模型/另一个人）时再升级到 L2
- **影响**：他验停留在 L1，对外宣传时必须明确标注"分离实现，非独立验证权威"
- **风险**：长期停留在 L1，"他验"的品牌价值有限——但这是结构性上限（单用户），不是工程问题

### 决策点 5：warn 不增锁是否正式启用？

- **背景**：615/616 已建 warn_governance（五桶分类）和 Goodhart 监控（危险分 80.1/100），但未正式启用"不自动采纳 legacy"
- **评审建议**：应该实施，但 Goodhart 80.1 是 dashboard heuristic 不是统计测量，建议改成制度条件"任何自动采纳 legacy 的路径必须关闭"
- **产品经理建议**：**启用**，但按评审建议改成制度条件（不设阈值 60，直接关闭自动采纳路径）。Goodhart 80.1 保留为 dashboard 监控指标，不作为启用/停用的阈值
- **影响**：golden baseline 不再自动膨胀，warn 从"自动采纳为 legacy"改为"人工 governance review 后才能采纳"
- **风险**：warn 积压可能增多（不自动采纳了），需要定期人工 review——但这正是"不增锁"的目的

### 决策点 6：27 条 legacy 豁免是否逐条重审？

- **背景**：616 已处置 27 条豁免（27/27 continue exemption），但评审认为证据密度不够高
- **评审建议**：不能直接全部续期，应该逐条重审，每条需要四元组（exemption→reason→compensating test→expiry condition）
- **产品经理建议**：**分批重审**，先重审 P0 级（涉及核心规则/核心验证路径的豁免），再重审 P1/P2。每条补全四元组。预计 27 条 × 10 分钟 = 4.5 小时，可以分 2-3 次完成
- **影响**：部分豁免可能被取消（如果重审后发现补偿测试不足），这会导致 gate warn 增多——但这是"更严格"的表现
- **风险**：耗时较长，且可能发现某些豁免的补偿测试确实不足——需要补测试或接受 warn

### 决策点 7：EV-MATRIX 是否从 regex heuristic 向 typed provenance 发展？

- **背景**：615/616 已修复 EV-MATRIX 隐性预处理（artifact_sha256 行剥离），双实现一致率 68.4%→100%
- **评审建议**：100% 一致不证明规则可靠（common-mode failure），建议从 regex heuristic 过渡到 typed evidence schema（检测"带类型的 CI provenance"而非"像 run number 的数字"）
- **产品经理建议**：**中期推进**（619+，作为 PCK 的一部分）。当前 regex heuristic 已经够用（隐性预处理已修复），typed evidence schema 是更根本的方向但工作量大（需要重新设计 evidence schema 和 parser），可以等 PCK（雷4）推进时一起做
- **影响**：当前保持 regex heuristic，未来 PCK 时升级为 typed evidence schema
- **风险**：regex heuristic 可能还有其他 collision source（时间戳、序列号、版本号等）——但这些可以在发现时逐个修复，不需要立刻重构

### 决策点 8：QueYi Core 剥离是否启动设计？

- **背景**：评审建议把阙疑从 C++ Bible 里剥离出来，CPP-Bible 靶场化
- **产品经理建议**：**621+ 启动设计，不早于 620**。当前机制层（雷2/3）和对象层（雷4/5/6）还没稳定，过早剥离 Core 会导致接口频繁变更。等 617-620 把攻击面、攻击者、PCK、Authority、未知检测都做了一轮之后，Core 的接口才能稳定下来，那时再剥离
- **影响**：617-620 继续在 CPP-Bible 内建设，621 启动 Core 剥离设计
- **风险**：推迟剥离可能导致 CPP-Bible 和 QueYi 的耦合加深——但 617-620 的建设本身就在做解耦（攻击面分类、Authority 接口、PCK 结构都是与 C++ 无关的）

### 决策点 9：Verification Failure Discovery Rate 是否作为核心指标？

- **背景**：评审建议加一个核心指标"Verification Failure Discovery Rate"——不是问"测了多少"，而是问"在相同预算下还能主动发现多少此前未知的验证漏洞"
- **产品经理建议**：**作为研究指标，暂不作为对外核心指标**。VFDR 需要攻击者目标函数（雷2）才能度量——当前 mutation 是固定的，没有"主动发现未知漏洞"的能力。等 618 攻击者目标函数做了之后，VFDR 才能有意义地度量。在此之前，对外核心指标仍是逃逸率（1/1406）和 CS 上界（0.9062%）
- **影响**：VFDR 列入研究指标，等 618 后开始度量
- **风险**：VFDR 的度量本身可能有争议（"未知漏洞"的定义、"相同预算"的口径）——需要在 618 时明确定义

## 四、产品经理的最终判断

### 4.1 两波评审对项目的价值

**极高。** 这是项目第一次获得真正的外部独立视角，价值不亚于 10 个批次的内部建设。具体体现在：
1. 发现了项目自己没发现的根本问题（统计对象定义、镜像边 delegation）
2. 给出了可执行的修复方案（estimand三层拆分、四元组legacy、release manifest）
3. 指出了项目的结构性位置和演进方向（verification correctness → verification independence）
4. 提出了能让项目"换一个物种"的八条雷霆方向

### 4.2 产品经理的核心策略

**"先止血，再质变"**：
- **止血（617）**：修复评审指出的最紧急问题——统计口径诚实化、人审诚实化、打包缺陷修复、数字漂移修复、攻击面分类。这些是"诚信品牌"的支柱，必须先修。
- **质变（618-620）**：推进最可能带来质变的方向——攻击者目标函数（雷2）、PCK（雷4）、未知检测（雷6）、Verification Horizon（雷7）。这些是"换物种"的核心。
- **架构（621+）**：等机制层和对象层稳定后，启动 QueYi Core 剥离（雷1）和 Protocol 标准化（雷8）。

### 4.3 对用户的建议

1. **617 投喂后，优先做决策点 2（30条逐条复核）**——这是评审认为优先级最高的一项，也是修复诚信品牌的关键。用户时间成本约 90-150 分钟，可以分 2-3 次完成。
2. **不要急于对外宣传**——在统计口径（决策点1）和人审诚实化（决策点2/3）修复之前，对外宣传"逃逸率≤0.9062%"和"388条全量人审"会被内行质疑。等 617 完成后再更新对外口径。
3. **他验的结构性上限要接受**——单用户阶段他验只能到 L1（分离实现），L2/L3 需要外部第三方。这不是工程问题，是结构性上限。可以等有外部合作者时再升级。
4. **八条雷不要全做**——产品经理建议只押雷2（攻击者目标函数）作为 618 的核心，其他雷按路线图逐步推进。全做会导致资源分散，每个都做不深。
