## 审查总结

我认为目前最重要的三个发现是：

**第一**，616 对 CP→confidence sequence 的修正方向是成立的，但项目现在最大的统计问题已经不再是"有没有连续偷看"，而是"1406 个 mutation outcome 到底对应什么随机总体"。Confidence sequence 确实用于 anytime-valid inference，核心就是用 e-process + Ville 不等式获得随时查看/任意停止仍有效的覆盖保证。但这并不自动把一个人为构造的、确定性的 mutation suite 变成可推广到"未来所有错误"的随机样本。现在的 0.9062% 最多可以在明确统计模型下成立，不能直接解释成"项目未来知识逃逸率 ≤0.9062%"。

**第二**，所谓"388 条全量人审"已经被你们自己诚实化，这一步是对的，但它也暴露了目前论证层最大的结构性问题：388 条全部被标成 batch_authorization，194 条还是 mirror edge，真正逐条人工判断实际上没有发生。20/20 的抽样只能说明那 20 条抽样结果，没有证据支持把整个 194 条外推成真实逐条审查。更关键的是，"对称边"能否安全镜像，本身就是需要证明的语义命题，而不能仅因为图结构上存在反向边就天然视为等价。

**第三**，"他验"才是这个系统下一阶段真正的分水岭。现在已经开始设计 independent verifier + VSA + transparency log，这是正确的问题。但 HMAC 本身并不能制造独立性——如果生成者、验证者和持钥者还是同一信任主体，HMAC 只能证明"持有这个密钥的主体生成了凭证"，不能证明"一个独立主体认可了这个结果"。真正的独立性需要不同代码、不同执行环境、不同信任根，最好再有外部可审计的透明日志。Sigstore/Rekor 的思路本质上也是签名 + 身份绑定 + append-only transparency log + 第三方可验证，而不是单纯"加一个 HMAC"。

## 1. 置信序列正式启用

**判断：有条件启用，而且应该把它作为连续监控的正式口径。**

616 的数学方向是合理的。项目文档给出的核心形式：

```
log E_n(p0) = log B(x+a,n-x+b)/B(a,b) - x log p0 - (n-x)log(1-p0)
```

本质上是 Beta-mixture likelihood-ratio e-process；再通过 Ville 型界把 e-process 反演成 confidence sequence。这个思路与现代 anytime-valid inference 的标准框架一致。

因此：
```
1/1406 -> CP 0.3370% -> CS 0.9062%
```
这种"连续查看会明显变宽"的现象是合理的，而且项目主动把旧数字降格为固定终点口径，这一点非常重要。

但是这里有一个比 peeking 更深的问题：你们现在并没有在文档里把"逃逸事件"的生成模型讲清楚。

假设：
1. 1406 个 mutation 是人为构造的固定全集；
2. 每个 mutation 是故意针对规则系统设计的攻击；
3. v1→v7 又存在版本演化和选择性修改；
4. 未来 mutation 还会继续由人/Agent 根据已有结果生成。

那么它并不是典型的 iid Bernoulli sampling process。

所以：
- "在当前 mutation 流程的某个概率模型下，逃逸率上界是 0.9062%"
- "系统未来任意知识的真实逃逸率不超过 0.9062%"

是两个完全不同的命题。这是目前统计层最需要补的一刀。

更严谨的做法是把指标拆成三层：
1. **"测试集经验逃逸率"**：1/1406
2. **"对某个预先定义的随机抽样机制而言的统计上界"**：CS
3. **"对未来未见攻击分布的泛化保证"**：另建 holdout / 随机生成机制 / fresh mutation distribution

否则 CS 虽然解决了 optional stopping，却可能把"统计技术正确"与"测量对象定义正确"混在一起。

所以我支持 cs_* 成为 continuous-monitoring 主口径，cp_* 保留为 fixed-endpoint reference，但建议在输出里再增加：
```
estimand = finite_suite_escape_rate
```
或者明确：
```
target_population = mutation_stream_under_protocol_X
```
这样才能避免 0.9062% 被外行理解成泛化错误率。

另外，20/20、300/3000 Monte Carlo 这些结果只能验证实现/模拟覆盖性质，不能替代真实业务过程的假设验证。这个区分应写进品牌级说明。

## 2. EV-MATRIX 隐性预处理

**判断：应该采纳"规则显式化"这个原则，但不建议简单粗暴地把某一份 Markdown 定成唯一权威；应该把规则变成机器可执行规范。**

这里你们发现的问题相当漂亮。615 的独立实现只有 68.4% 一致，最后发现官方实现实际上还有一个没有写在规则说明里的：`artifact_sha256:` 行剥离。而这个 64 位 hex 里的长数字片段又会碰到 `\d{10,}`，所以形成"证据伪锚 → 双编译器卡被放行"的结构性问题。

这个案例的价值非常高，因为它不是"代码写错了一行"，而是证明了："代码中的规范"与"人理解的规范"不是同一个东西。这恰好是你这个系统非常核心的研究点。

但这里我不会直接接受"100% 一致 = 规则可靠"。100% 一致只证明：官方实现 == 第二实现，不证明：官方实现 == 正确语义，也不证明：第二实现 != 同源认知。这就是典型 common-mode failure。

更进一步，裸 10+ 位数字 = CI run 这个规则本身就偏危险。你们只是消除了一个已知 collision source，未来还可能存在：时间戳、序列号、版本号、随机 ID、artifact ID、hash 中的数字片段……继续撞到这个正则。

所以我更建议最终演进为：不要检测"像 run number 的数字"，而检测"带类型的 CI provenance"。例如明确接受：
- GitHub Actions run URL
- run #123456
- provider=github + run_id=...

甚至直接机器解析 provenance JSON。也就是说，从 regex heuristic 逐渐过渡到 typed evidence schema。这是比继续补 P3/P4 更根本的方向。

## 3. warn 不增锁

**判断：应该实施，但不能把 80.1 当成一个客观阈值系统。**

这一项的机制设计本身是合理的：
```
new → observation → considerable → adopted_legacy → expired_reassess
```
最关键的是"不自动采纳"。这实际上是在给 golden baseline 建立一种"单向膨胀阻断"。这是必须的，因为从你给的序列看：31 → 136 → 186 → 186...，而 block 一直是 0，人审 reject 又是 0。如果这个过程允许系统自己不断把 warning 吞进 legacy，那么最终会出现典型的 specification drift：系统越来越"绿"，但不是越来越严格，而是越来越不愿意报错。

但是 Goodhart 80.1/100 更适合作为 dashboard heuristic，不应该被包装成统计测量。现在这个分数实际上是：若干手工设计的子指标 + 人工权重 + 人工解释。尤其"达到 60 才启用"目前看不到足够的经验依据。

所以应该把它描述成：governance risk score，而不是一个具有外部可解释性的 80.1/100 "真实风险"。

我的建议是直接把"threshold 60"改成制度条件："任何自动采纳 legacy 的路径必须关闭；开启前必须完成一次人工 governance review。"这样反而更硬。

## 4. 27 条 legacy 豁免

**判断：不能直接全部续期；应该逐条重审。**

这里我比较警惕。因为 27 条最终处置结果是：27/27 continue exemption，而且大量理由完全模板化："字段/枚举/结构类：pytest 正反例已兜底、端到端毒样例不经济"。

这在工程上完全可能合理，但在独立审查视角下，它的证据密度不够高。尤其是：豁免存在本身，就是验证系统的 blind spot。所以"为什么删掉它成本太高"不能单独构成足够理由。

每条 legacy 最少应该有四元组：
```
exemption -> reason -> compensating test -> expiry condition
```
例如：
- "为什么豁免"
- "代替它的 pytest 正反例是什么"
- "哪个毒样例仍覆盖该语义"
- "什么条件满足后必须取消豁免"

否则 legacy 很容易变成："曾经有理由不测 → 后来有理由继续不测 → 最终永久不测"。你们已经意识到这一点，所以才搞 expiry；但目前 expiry 主要还是提醒机制，还没真正成为"去豁免压力"。

## 5. 30 条真正逐条人审

**判断：这是当前最值得真正做的一项，而且优先级应该高于绝大多数新功能。**

这个包最大的一个价值，就是没有掩饰 388 条人审的真实情况。从 human_review_honesty_labels.jsonl 可以直接看出：388/388 都是 review_method = batch_authorization，其中 mirror = 194，非 mirror 194，template 也是高度模板化：T1 177 / T2 176 / T3 17 / T4 17 / T5 1。

这和报告里的"全量人审完成"在字面上确实容易产生误导。更准确的定义应该是："388 条均完成授权标注"，而不是："388 条均被逐条人工语义审核"。这是当前整个项目我认为最关键的诚信修复之一。

还有一个统计问题：20/20 = 100%，然后写"合理估计 90–95%"。这个 90–95% 并不是从这 20/20 直接推出来的一个正规点估计。20/20 的严格点估计仍然是 100%，只是区间很宽。你可以说"样本不足以排除真实准确率明显低于 100%"，但最好不要人为给一个 90–95% 的"合理估计"。

更大的问题是镜像。假设 MIS -> proposition 和 proposition -> MIS 在数据库结构上成对存在，并不意味着"人审一个方向，另一个方向可以免审"。你必须证明这个关系本身是语义同构、权重同构、判决同构的。否则 mirror 是一条隐藏 delegation 通道。这恰恰违反你们自己的第一原则："AI 不能自己决定自己对。"

所以我认为 30 条逐条复核不是"小优化"，而是目前论证层的关键补洞。

而且这个包有个明显限制：你们在报告中引用的 data/human_review_item_by_item_30_615.md 并不在这个审查包里。真正的 annotation 文件 human_attack_edge_annotations.jsonl 也不在包里。grounded_labels_w2.json 也不在。所以第三方目前无法真的审那 30 条，只能审"关于那 30 条的二手描述"。这是一个很重要的 packaging flaw。

## 6. 他验架构

**判断：应进入试点，但不要把 HMAC prototype 当成"独立验证已经实现"。**

这里你的方向是对的，而且已经碰到了真正的系统问题。现在的结构仍然主要是：生成者 → 本项目工具 → 本项目自己判断。你现在开始引入：独立 verifier → VSA → Merkle / transparency。这才真正开始切断 self-certification。

工业供应链里的 SLSA / Sigstore 也采用类似思路：构建产物产生 provenance/attestation，再通过签名与透明日志让其他方可以独立验证；Rekor 本身提供 append-only、可验证的透明日志结构。

但一定要区分："独立代码"和"独立信任主体"这两个概念。如果 A 写 verifier、A 持有 HMAC secret、A 跑 verifier、A 保存 log，那么这是 separated implementation，不是 independent verification authority。HMAC 最终只是共享秘密证明。

试点阶段可以使用 HMAC，因为它简单。但最终阶段应该考虑：非对称签名、独立公钥、独立 verifier runtime、独立密钥托管、外部透明日志。最终最好能做到：生成者改结果 ≠ 可以自己伪造验证凭证。这才是真正"他验"。

## 7. 保形预测 / 弃权三态

**判断：先不做生产实现，作为研究原型保留。**

保形预测本身并不是噱头。它的核心优势就是在适当条件下提供有限样本、分布自由的 coverage guarantee；但关键前提通常是 exchangeability。

而你这个 mutation stream 本身就存在明显的：版本迭代、攻击者自适应、规则变化、人为定向构造、历史反馈。这些都可能破坏简单 exchangeability。所以目前做"每张知识卡自己的可靠度区间"会很诱人，但数据量和数据生成机制都还不够成熟。

尤其当前 1/1406 只有一个 escape。这种极低事件率数据非常适合证明机械系统"目前没有发现很多逃逸"，却不太适合立刻支撑复杂的 conditional prediction system。

我会把它放在："统计框架 v2 research track"，而不是核心生产轨。

## 8. 工具合并

**判断：低优先级。**

你现在已经有 196 个工具，但从这个包暴露出来的问题看，真正的风险不是"工具多"，而是：规则语义分散、测试与规范分离、不同 verifier 之间存在 common-mode、人审数据与真正审查记录分离。这些问题比"25 个工具能不能合成 15 个"严重得多。

过早重构工具，很可能反而破坏现在已经建立的证据链。所以我会保持"暂不合并"，除非出现：语义完全重复、维护成本显著、两个工具无法独立演化。否则宁可多工具、少耦合。

## 9. data 目录整理

**判断：暂缓。**

理由很直接：现在最大的价值在于历史可追溯性。大量 _arch_*、615/616 批次工件、baseline、recalc、proposal、acceptance，这些文件从普通工程目录角度看很乱，但从实验档案角度看正是 provenance。

此时大规模移动目录有很高的引用风险，而且你们自己已经发现 4+ 工具和测试引用它。所以现在应该优先做："逻辑索引"，而不是："物理整理"。最终甚至可以保留 append-only archive，而只增加稳定的 manifest / index。

## 10. CI 四 job 实跑

**判断：必须完成，但是它属于"基础设施事实确认"，不是当前研究核心。**

目前包里实际上已经自己写得很诚实：616 验收报告明确说监工门禁没有重新跑，很多数字只是 baseline 对照。这是对的。

但同时 quickref 又写：#619 running，而 guide 中则描述："614+615+616 共 58 commit 刚 push，CI 正在实跑。"因此当前预审包没有给第三方一个明确的：HEAD -> CI run -> job result -> commit 映射。

这种东西最容易解决，做一个 release manifest：
```
HEAD=e5ceeba
gate=#619 PASS
pytest=#619 PASS
quality=#619 PASS
replay=#619 PASS
timestamp=...
```
就够了。

真正值得警惕的反而是 package 内部数字已经出现漂移：00_README 写的是 1469+ commits / 204 tools / 183 tests，而 project_key_numbers_quickref_v5 写的是 1446 commits / 196 tools / 175 tests。这不是小误差。这是当前审查包自身的 provenance/versioning 问题。

如果两个数字来自不同 HEAD，就应该显式写 source_commit=...，而不是把两组数字同时放在一个"真实文件、未过滤"的审查包里。

另外 MIS 数量也出现不同口径：README 写 79 个 MIS，而 quickref 写的是 80 个 MIS，其中 42 个带 related_atoms。这些都说明你现在真正缺的是一个 SNAPSHOT_MANIFEST.json，把所有指标绑定到一个 commit/hash。

## 额外发现

有一个比 10 项更值得你关注的结构性问题：现在你的系统正在从"verification correctness"转向"verification independence"。

早期系统的主要问题是："模型写错了怎么办？"
后来变成："gate 会不会漏？"
再后来："统计口径会不会骗人？"
现在又变成："谁来证明 gate 没骗人？"

这个演进非常明显。616 最有价值的地方其实正是在这里：
- CP peeking correction → 解决 measurement validity
- EV dual implementation → 解决 implementation/spec divergence
- warn governance → 解决 baseline drift
- honesty labels → 解决 human-review provenance
- independent verifier → 开始解决 trust-root independence

这五个东西已经开始形成一个相当清晰的系统论结构了。

但下一阶段不能继续只靠"再增加一个工具"。应该开始建立四个明确概念：
```
Specification / Evidence / Verifier / Authority
```
然后强制要求每个关键结论都能沿着：
```
Claim → Evidence → Verifier → Independent witness → Decision
```
一路反向追踪。如果做到了，这个项目的性质会发生一次明显变化。

## 对项目整体的评价

从这份 2026-09-21 预审包来看，我不会把它评价成"已经完成的可靠知识系统"，但也绝对不会把它看作普通的 Agent 工具堆。

目前最大的优势是：你开始主动攻击自己的验证系统，而不是只展示它的成功率。1/1406 被重新改成 0.9062% anytime upper bound，388 条所谓"全量人审"被拆穿成 batch authorization，EV-MATRIX 的隐性预处理被从代码里挖出来，Goodhart 漂移被单独量化，这些行为本身比某个漂亮的最终数字更有价值。

最大的弱点则非常明确：目前仍然存在"同一主体生产、定义、验证、打包和解释证据"的闭环。你正在削弱它，但还没有真正切断它。

所以我对现在这个版本的定性是：**已经进入"验证系统本身成为研究对象"的阶段，但尚未进入"外部第三方可以不信任作者也能复核结论"的阶段。** 这是一个很关键的分界线。

另外，这个"预审查包"本身最好尽快修一次。它现在缺少多份自己在 README 中称为关键依据的原始工件，包括 human_review_item_by_item_30_615.md、实际 annotation、W2 结果、EV-MATRIX 第二实现、他验三件套等。因此目前它更像"审查导航包"，还不是"可复算审计包"。把这些证据补齐，再加一个绑定单一 HEAD 的 manifest，你的"他验"体系会立刻比现在扎实很多。

从系统设计角度说，这一轮最值得继续深挖的已经不是"还能再加多少规则"，而是：**能不能让一个不信任你的外部模型，在拿到同一份 evidence 后，独立重建你的结论，而且它没有权限继承你的判断。** 这个问题一旦真正解决，阙疑才算跨过一个很实质的门槛。
