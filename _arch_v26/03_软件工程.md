## 一、核心实践清单（8 条，含数字与流程）

### P1. 测试金字塔：按成本/速度分层，但 70/20/10 是"良好初猜"不是教条

- Mike Cohn《Succeeding with Agile》(2009) 提出形状：**大量快速单元测试（ms 级）→ 较少集成测试（s）→ 少量 E2E（min）**；原则是"把每个测试尽量往下压"。**70/20/10 在 Google 原始博客中并无出处**，常被误传；Fowler 的权威表述只有两句："多粒度测试；越高层越少"。【已查证】https://google.github.io/eng-practices/ ；realpython 词条考证
- **反模式：冰淇淋蛋筒**——测试堆在慢而脆的 UI/人工层。实测 E2E flaky 率 **15–21%**，flaky 测试消耗开发者约 **2.5%** 工作时间。
- 变体：前端用 testing trophy（集成层最宽），微服务用 honeycomb（Spotify，弱化实现细节单测）。

### P2. 代码评审：Google 标准——小变更、连续改进、设计优先

- **小 CL 原则**：自包含、一件事；**~100 行合理、1000 行通常过大**（200 行 spread 到 50 个文件也算大）；审查者**有权仅因"太大"直接拒绝**。
- **评审标准（最高原则）**："只要 CL 确实改善了整体代码健康度就应批准，即使它不完美"——追求**连续改进而非完美**；非阻塞意见加 **"Nit:"** 前缀；技术事实与数据压过个人偏好。
- 三重批准位：**LGTM 同行正确性 + CODEOWNERS 所有者 + 可读性/语言专家**；Google 每个变更都评审，结对编程算已评审。
- 评审检查序：**设计 > 功能 > 复杂度（警惕过度工程/"未来可能需要"）> 测试 > 命名 > 注释 > 风格**；测试必须与生产代码同 CL（紧急除外）。
- **经验现实（Microsoft/Google 挖掘研究）**：评审评论中只有 **14–25% 指向功能缺陷**，约 **75% 是可维护性/可读性/知识传递**——"评审主要用来找 bug"是行业级错觉，但仍是最划算的缺陷防线之一（SmartBear/Cisco 称轻量同行评审发现 60–90% 缺陷，为营销性综述，谨慎引用）；Microsoft 2017：评审使发布后缺陷密度降 **40–60%**；成本约占开发时间 **10–15%**。

### P3. 形式化验证：只在"内核级"组件上用，成本约 1 个数量级

- **seL4**：约 10KLoC C 微内核，功能正确性+安全属性证明到二进制，累计约 **200+ 人年**；证明排除整类缺陷（溢出/空指针/未定义行为），但假设规格本身正确。
- **CompCert**：机器检验的编译器正确性证明，生成代码性能约 GCC -O1 的 90%；2026 年首次以 DO-178C/DO-333 取证信用用于 ATR 航电。
- **AWS s2n**：约 0.7KLoC，3 人年——**组件越小越规则，形式化越划算**。
- 行业结论：形式化验证是"证明缺陷缺席"的唯一手段，但价格决定它只用于**信任根（trust anchor）**，不用于全系统（v25-A 结论的工业实证）。

### P4. FMEA：S×O×D 已被淘汰，严重度主导的 AP 取代 RPN

- 经典 RPN = **严重度×发生度×探测度**（各 1–10，1–1000）；MIL-P-1629（1949）起源、AIAG 汽车业普及。
- **2019 AIAG-VDA 七步法改用 Action Priority（H/M/L）**：**严重度为主、发生度次之、探测度只作修正**——因为不同 S/O/D 组合可得到同一 RPN 却风险完全不同（S=10,O=2,D=5 的安全问题 ≠ S=4,O=5,D=5）。
- 关键设计洞见：**严重度不能靠加强检验降低，只能改设计**；FMEA 在变更时重估，FRACAS 用现场数据回灌发生度。

### P5. 混沌工程：五原则，故障注入必须"小爆炸半径 + 连续自动"

2014《Principles of Chaos》五原则：①围绕**稳态指标**建假设（如"播放成功率不下降"，不是"系统没问题"）②引入**真实世界事件**③**在生产**实验（staging 给不出真实态）④**自动化持续运行**⑤**最小化爆炸半径**。
- 起源：Netflix 2008 数据库损坏停摆 3 天 → 2010 Chaos Monkey **工作时间随机杀生产实例**，强制每个服务天生容忍实例失效；升级阶梯：实例（Monkey）→ 可用区（Gorilla）→ 区域（Kong）。
- 本质：消防演习——"知道东西迟早会坏，不如挑工程师都在岗的时候让它坏"。

### P6. 可观测性三支柱 + SLI/SLO/错误预算

- **三支柱**：logs（带时间戳的离散事件）、metrics（聚合数值）、traces（跨服务请求全路径，span/因果 ID 关联）；目标是回答"未知的未知"，OpenTelemetry 为厂商中立标准。
- **SLI**（测量）→ **SLO**（目标）→ **错误预算 = 1−SLO**。99.9% SLO = 0.1% 预算 ≈ 30 天里 **43 分钟**。
- 错误预算是**跨职能决策规则**：预算内可快迭代；**预算烧穿即冻结发布、转做可靠性**；"100% 可靠不是目标"——过度可靠牺牲迭代速度且用户无感。

### P7. DORA 四（五）指标：速度与稳定不是取舍

| 指标 | Elite | Low |
|---|---|---|
| 部署频率 | 每天多次 | 月-半年 1 次 |
| 变更前置时间 | <1 小时 | 1-6 月 |
| 变更失败率 | 0–5% | 46–60% |
| 失败恢复时间 | <1 小时 | 1 周-1 月 |

2024 增第五指标**部署返工率**；核心发现：精英团队**又快又稳**。反直觉警示：**变更失败率 0% 是红旗**（说明检测不到、发布太稀疏、或在掩盖回滚）；常见测量错误：不含 hotfix、把"宣告恢复"当"用户影响结束"。

### P8. 无追责复盘（blameless postmortem）与部署安全

- 触发：耗尽错误预算/用户可见故障/需要升级；文档固定字段：摘要、**定量影响**（禁"部分用户受影响"）、UTC 精确时间线（从日志不从记忆）、促成因素、**行动项（具体描述+实名 owner+期限+工单链接）**、教训（含"哪些做对了"）；5 Whys 追到可改的系统因素。
- **>50% 复盘行动项从未完成**——没有 owner 与跟踪的复盘等于没做；AWS 制度：COE（Correction of Errors），周会跟踪预防措施落地。
- **渐进发布**：canary **5%→25%→50%→100%**，每阶段质量门（对比基线，超阈自动回滚）+ bake time；蓝绿秒级切换；feature flag 按租户开；**"不存在低风险的生产部署"**（Azure WAF 原文）。
- **bus factor**：133 个热门 GitHub 项目中 **46% 为 1、28% 为 2**；3.6 万项目研究：89% 经历过核心团队流失、仅 27% 能吸引到新核心开发者；OpenSSF 金级认证硬性要求 bus factor ≥2。

## 二、踩过的坑（4 个真实事故）

### F1. Knight Capital（2012，45 分钟，4.4 亿美元）——手动部署漏掉 1/8 服务器
8 台服务器手工部署新代码漏了 1 台；该台残留 2003 年测试程序 Power Peg（被同一配置 flag 意外激活，且其成交回报在 2005 重构中失效→无限下单）；45 分钟 400 万笔交易、154 只股票、66 亿美元错位持仓。**告警响了无人响应**；无应急 runbook，"回滚"反而把缺陷扩散到全部 8 台。SEC 处罚依据：缺乏市场接入风控（无仓位上限/熔断/kill switch）。【已查证】SEC 34-70694
**教训链**：手工部署 + 休眠代码 + 无硬熔断 + 无回滚预案 + 诊断 20 分钟。
### F2. AWS S3 us-east-1（2017，3 小时 57 分）——一个 playbook 参数错误
按既定 playbook 下线少量计费服务器，参数错误扩大为大批服务器，**误删同机的 index + placement 两个关键子系统**（后者依赖前者）；工具**无最小容量保护**；两子系统多年未完整重启，元数据完整性校验从未在此规模演练→恢复极慢；**状态看板依赖 S3 本身，事故头两小时显示全绿**（控制面与数据面共命运）。事后：容量移除工具分区化+最小容量保护+分阶段移除+看板跨区。【已查证】https://aws.amazon.com/message/41926/
### F3. 737 MAX（2018-19，346 死）——评审/测试样本代表性失败
见 02 航空安全：委托 48% 试飞、用王牌试飞员反应代表普通飞行员。软件工程侧对应：**用作者自测/专家验收替代代表性用户测试**。
### F4. "100% 覆盖但故障照发"——覆盖率的系统性误导
100% 行覆盖的测试可以无一条断言；覆盖度量"执行"不度量"检错能力"。变异测试（mutation testing）是金标准反制：自动植入缺陷（如 `<`→`<=`、`+`→`−`），看测试能否杀死；**Google 将存活变异体抽样嵌入代码评审流程，报告称约 70% 的 bug 本可由针对变异体补的测试阻止**；pitest 作者的实践警告：不要设夜间阈值门（没人看结果），要在代码"还湿"时对变更子集运行。

## 三、对阙疑的映射【类比推断】

| 软件工程实践 | 阙疑组件/机制对应 |
|---|---|
| P1 测试分层 + flaky 成本 | 1593 mutation 是"E2E 层"，贵且脆；规则单元检查（结构/模式）应是宽基底；flaky 治理（隔离/重试/删除）直接适用，flake 率应作测试资产健康指标 |
| P2 小 CL 100 行/单一目的 | 规则改动必须小而自包含；v25-D 的 MDL 边际判据可配"改动规模上限"：大改动强制拆分审查；评审拒绝权可仅因"太大" |
| 连续改进而非完美 | 卡片判定不追求 0 逃逸的"完美 PR"，只要整体指标改善即放行——与 v25-E 可错主义、错误预算合流 |
| 评审 14-25% 才是功能缺陷 | 人审的主要价值不在"再判一次对错"，而在可维护性/接地/知识传递；人审流程应设计为**过程审查**（Safer Dx 同证），不应按"抓到几个错"考核人审 |
| Nit 前缀/技术事实优先 | 评审意见分级（阻塞/nit）；争议以数据与既定原则裁决，压制品味之争——直接对应评审界面设计 |
| P3 seL4/CompCert/s2n 成本曲线 | kernel_checker 做形式化小内核（v25-A）在此得到成本锚：信任根组件值得，全规则库不值得；组件规模决定方法选择 |
| P4 AP 取代 RPN | v26-E/F 的风险打分应**严重度主导**：高危错误类型不因罕见而被乘法稀释——直接修正"RPN 同值不同险"的设计陷阱 |
| P5 混沌五原则 | 对验证流水线做受控故障注入：故意让单条证据源/单个验证器失效，观察降级行为；爆炸半径从小子集开始；稳态假设必须可量化（如"人审队列 SLO 不破"） |
| P6 三支柱 | 阙疑可观测性：事件日志（DecisionEvent）、聚合指标（逃逸率/校准/ECE）、追踪（一张卡跨 gate/replay/人审的 trace_id）——v25 黑匣子设计的软件版实现 |
| 错误预算=发布政策 | 给规则系统设错误预算（逃逸/误报预算）：预算内允许快速迭代规则，烧穿则冻结新规则、只做修复——把 v25-E 控制论 γ 约束变成组织规则 |
| P7 DORA + 0% 失败率红旗 | 阙疑应报告"规则变更失败率/回滚率/恢复时间"；长期 0 回滚的规则体系是红旗（说明不敢改或检测不到） |
| P8 行动项 owner+期限 | 复盘/逃逸 RCA 的 action items 实名+工单+到期，周会跟踪；没有闭环的 RCA 不计完成 |
| canary 5% 阶梯 | 新规则/新检查器上线阶梯（影子→5% 卡→25%→全量），每阶段与基线统计比较，超阈自动回滚——v25-B 阶段解锁的工业细化参数 |
| 控制面不与数据面共命运 | 安全告警/状态看板必须独立于被监控系统：阙疑自身的故障报告通道不能依赖阙疑主流程（S3 看板两小时全绿之鉴） |
| bus factor ≥2 | 每条关键规则/每个 kernel 组件必须 ≥2 人能独立维护；核心知识独占应作为组织级风险登记；他验同时是知识冗余投资 |
| 变异测试 | 对"测试的测试"：对 mutation 测试集本身做变异演练（杀死率=mutation 集检错力）；124 毒样例应定期变异扩充并在"湿"时反馈 |

## 四、可直接搬的设计（5 条）

1. **变更规模上限 + 拆分拒绝权**：规则/工具变更以"自包含单一目的"为默认单位，评审者可仅因规模拒绝。
2. **错误预算政策**：设定逃逸/误报预算，烧穿自动冻结非必要规则变更，优先级切换到可靠性；预算与 v23 三阈值挂钩。
3. **复盘行动项闭环表**：owner（人，非团队）+ 期限 + 工单 + 周会跟踪；无闭环不复盘。
4. **新规则 canary 阶梯参数**：5/25/50/100% 流量（卡片比例），每阶段质量门对照基线（逃逸率、误报率、人审推翻率），自动回滚。
5. **关键组件 bus factor 登记**：kernel/规则库关键域强制 ≥2 名独立维护者，纳入阶段评审。

## 五、不能直接搬的（4 条及原因）

1. **70/20/10 固定比例**：原始来源即不支持该数字；阙疑按风险分布选形（高危卡需要更高比例的"端到端"复核），不按虚假教条分配。
2. **全系统形式化验证**：200 人年/10KLoC 的成本在规则规模上不可行；只做信任根。
3. **生产环境随机故障注入（Chaos Monkey 原样）**：阙疑处理的是知识而非在线用户流量，错误注入只能在影子库/历史卡片副本上做，不能在真实放行链路随机杀组件。
4. **把评审当缺陷计数指标**：评审主要产出是可维护性而非 bug 计数；用"每人抓到几个错"考核会催生表演性审查（rubber stamp <2 分钟、零评论=负价值）。
