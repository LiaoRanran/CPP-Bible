# 方向 11：论文版本管理（v0.1 → camera-ready）

## 核心结论
1. 论文版本管理的本质是**给"思考的演进"打时间戳**：v0.1（idea+基线）→ v0.5（实验）→ v1.0（投稿）→ v1.x（rebuttal）→ camera-ready（最终）。每个版本对应一个可回溯的 git tag + arXiv 版本，避免"改崩了找不回"。
2. 对单人作者，最大风险是**没有版本纪律导致越改越乱**；QueYi 应把"论文版本"和"代码/corpus 版本"绑定（每升一版 corpus，论文同步升版）。
3. camera-ready 不是"定稿"，是"在录用意见上做最小必要修改 + 补 acknowledgment + 更正 typo"；严禁在 camera-ready 偷偷加大实验（会被查）。

## 精确数字与案例
- **语义版本约定**：v0.x=pre-submission（x 每加一次实验/重写）；v1.0=首次投稿；v1.1=rebuttal 后；v2.0=camera-ready。QueYi 当前 48 卡，可设 v0.1=26 verified+19 draft 基线稿，v0.2=补完 3 red-team 后。
- **git 实践**：论文源（LaTeX）与代码同仓或子模块；每次"投出"前 `git tag paper-v0.3`；arXiv replace 与 tag 一一对应，写 `CHANGELOG.md` 记录"v0.2→v0.3: 新增 15 条真实缺陷夹具重注入实验"。
- **案例**：顶会投稿系统（OpenReview）要求提交 PDF + 声明版本；rebuttal 阶段可更新补充材料但不能换主文核心；camera-ready 有页数上限（NeurIPS 主会 ~9 页 + 附录）。
- **双非作者的特殊价值**：版本历史 = 工作持续性的证据，rebuttal 时可直接说"自 v0.1 起我们持续扩展 corpus，见 arXiv 演进"，对抗"一次性水稿"质疑。

## 对阙疑的 3 条具体行动
1. **建 paper 仓库**：`_arch_v45/../queyi-paper/` 放 LaTeX，配 `CHANGELOG.md` + git tag；每升一版 corpus 同步升 paper 版本并记变更。
2. **arXiv 版本对齐**：v0.1(2026-10) → v0.3(2027-03, 补实验) → v0.4(2027-05 投稿锁版)，每次 replace 留注"what changed"。
3. **camera-ready 守纪律**：录用后只做"最小修改 + 补数据来源声明 + 致谢算力/合作者"，不夹带新核心实验；保留 v1.0 投稿稿备查。

## 盲区（诚实标注）
- NeurIPS 2027 camera-ready 页数/格式未发布，以 2027 CFP 为准。
- "版本绑定 corpus"是我的建议，非会议要求；若 corpus 在审稿中增长，需在 rebuttal 透明说明（方向 04）。
- git tag 与 arXiv 版本一一对应需手动维护，易漏。
