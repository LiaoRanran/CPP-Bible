# 方向 59：项目烂尾了怎么办

## 核心结论
1. 单人项目"烂尾"是**高概率正常事件**（时间/动力/优先级变化），关键是**优雅收尾而非烂尾**：归档、写清状态、放出可用部分——这对未来求职/读研仍是资产，而非污点。
2. 三种处理：**① 暂停冻结（可能重启）：按方向 44 的冻结协议归档；② 缩小范围（保核心）：只维护 813 行内核 + demo，弃扩张；③ 彻底归档（公开墓地）：写"archived，why, what's done"**。
3. 对 QueYi：即使不投 NeurIPS，**一个诚实的 archived 项目 + 明确 README 仍能证明"你会做系统工程"**——比一个空简历强。所以别删仓库。

## 精确数字与案例
- **烂尾诱因**：无外部 deadline（方向 34）、被拒后动力崩（方向 58）、考研/工作挤压（方向 44）、scope 膨胀。
- **优雅收尾清单**：① README 顶部加 `[archived]` + 一句话状态；② 标注"已完成 X（48 卡/80% 检出），未完成 Y"；③ 放出可跑 demo；④ 关 issue/PR 模板。
- **案例**：大量知名项目进入 archived 仍被引用/使用（如早期工具）；GitHub archive（只读）是体面终局。
- **反模式**：删仓库（抹掉你的工作痕迹）、假装还活跃（失信）。
- **重启成本**：方向 44 的"重启手册"就是为"可能烂尾后重启"设计的。

## 对阙疑的 3 条具体行动
1. **写"重启手册"作为保险**：即使现在活跃，也先写好（编译/demo/corpus/下一步 TODO），任何时刻烂尾都能体面归档。
2. **设"最小可维护版"**：若动力下降，只保 813 行内核 + demo 可跑，弃扩张——保有资产而非全弃。
3. **归档而非删除**：真决定停时，README 写清状态 + 已达成数字，GitHub 设为 archived；未来求职仍可展示。

## 盲区（诚实标注）
- "烂尾高概率"是通用观察，非 QueYi 预测；你可能坚持到底。
- archived 项目对求职的正面作用无量化，但有胜于无。
- 若项目被他人 fork 续做，需明确许可（方向 30 的 license）以允许延续。
