# 方向 49：现在有谁在做类似的事（列 10 个）

## 核心结论
1. "代码评测/验证"赛道 2025–2026 **明显变热**（多篇 ICLR 2026），但**没有人做 QueYi 的精确组合**（C++ 知识 + 四态判决 + append-only 哈希链 + 灾难污染控制 + 三编译器）。QueYi 的细分位仍相对空白，但"宽泛的代码验证"竞争加剧。
2. 最直接的邻居是 **TC-Bench（抗分数膨胀）** 与 **Code2Bench（动态代码评测）**——它们解决"benchmark 被刷分"，QueYi 解决"知识正确性 + 可审计"，互补但可被 reviewer 拿来对比。
3. 战略含义：QueYi 必须在 related work 明确与这 10 个的差异；否则 reviewer 会问"这跟 TC-Bench 有何不同"。差异 = **可审计性（哈希链）+ C++ 知识语义 + 污染控制**。

## 精确数字与案例（10 个同类/邻接工作）
1. **TC-Bench**（ICLR 2026，哈工大）：精选最少测试样例消除代码 benchmark 分数膨胀；实证 LCB 上 HackRate 近 100%→TC-Bench 仅 ~50%。
2. **Code2Bench**（ICLR 2026，北航）：双扩展动态评测，从 GitHub 2025-05~09 最新提交构建实战基准（Python/Java）。
3. **TrustJudge**（ICLR 2026，北大/清华等八校）：用概率分布改进 LLM-as-a-judge，降低评估不一致。
4. **Do LLMs Trust the Code They Write?**（arXiv 2512.07404）：研究模型对自己生成代码的置信度/校准——直指"模型自评不可靠"。
5. **LLM-Vectorizer**（Taneja et al., 2025）：LLM 生成向量化代码，报"52% 时间生成正确代码"——验证是瓶颈。
6. **Trusted LLM-based Code Optimization and Verification**（arXiv 2608.14953, 2026-08）：面向可信代码优化/验证的流程。
7. **LiveCodeBench**：抗污染的持续更新代码评测基准。
8. **CrashJS**（MSR 2024）：从崩溃提取的 JS 基准，SE 侧"真实缺陷基准"范例。
9. **DataComp / Dolma**（NeurIPS D&B）：数据策展透明化——QueYi 的哈希链可对标其"可审计数据"。
10. **Mull / muCPP**：C++ 变异测试工具——QueYi 变异 97.3% 的方法论来源与对比对象。

## 对阙疑的 3 条具体行动
1. **related work 逐条对比**：为上述 10 个各写一句"它做 X，QueYi 补 Y（可审计/C++ 知识/四态）"，做成一张对比表进正文。
2. **主动引用 TC-Bench/Code2Bench**：在 intro 承认"代码评测变热"，再指出"它们不解决 C++ 知识正确性与可审计信任"——把邻居变垫脚石。
3. **做差异化实验**：证明 QueYi 的哈希链能被第三方独立校验（`verify-chain`），而上述工作无等价机制——这是不可替代性证据。
