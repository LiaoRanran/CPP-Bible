# 方向 30：安全（不要泄漏密钥 / 凭证管理）

## 核心结论
1. 单人开源项目最常见的灾难是**把 API key / token 提交进 Git 历史**——QueYi 若调用 LLM API（跑模型验证）极可能踩坑。规则：密钥永不进仓库，只用环境变量 / GitHub Secrets / `.env`（gitignore）。
2. 凭证管理三件套：**`.gitignore` 排除 `.env` + `git-secrets`/预提交钩子扫描 + CI 用 GitHub Secrets**；一旦泄露立即轮换（revoke），因为历史里永远在。
3. 对 QueYi 额外风险：账本（452 条）若含**模型原始输出/用户输入代码片段**，可能含隐私或版权内容——需脱敏 + 明确许可（方向 03 的"数据来源/许可"项）。

## 精确数字与案例
- **泄露渠道**：`.env`、`config.json`、`硬编码 token in source`、`CI 日志打印密钥`。GitHub 公开库一旦推送，机器人数分钟内爬走并利用（如挖矿/盗刷 LLM 额度）。
- **工具**：`git-secrets`（AWS）、`gitleaks`（扫描历史）、`trufflehog`（查泄露）、pre-commit 钩子自动拦。
- **GitHub Secrets**：CI 用 `${{ secrets.API_KEY }}`，不进日志（GitHub 默认对 secrets 打码，但你自己 `echo` 会泄露）。
- **案例**：2023–2025 多起开源项目因 `.env` 提交致 LLM key 被盗刷数万美元；这是单人作者高概率雷。
- **凭证轮换**：OpenAI/Anthropic 等支持一键 revoke + 重发；发现泄露先 revoke 再修仓库（用 `git filter-repo` 清历史）。

## 对阙疑的 3 条具体行动
1. **立即审计仓库**：跑 `gitleaks detect` / `trufflehog` 扫 QueYi 历史，确认 813 行内核与配置无硬编码 key；有则 revoke + `git filter-repo` 清除。
2. **加 .gitignore + pre-commit**：排除 `.env`、`*.key`、`credentials.json`；装 `pre-commit` + `gitleaks` 钩子，未来提交自动拦密钥。
3. **账本脱敏**：确认 452 账本不含明文 API key 或敏感用户代码；若含，落盘前脱敏（哈希/截断），并在数据许可声明中写清（方向 03/54）。
