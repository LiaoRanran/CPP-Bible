## 3. 发现：`compile` job 缺 `fetch-depth: 0` ⇒ **T1-1 门禁静默失效**（未擅自修）

### 3.1 事实

`compile` job 的 checkout 是裸的 `- uses: actions/checkout@v7`（`ci.yml:708`），**没有 `with: fetch-depth: 0`** ⇒ 默认**浅克隆（depth 1）**。
该 job 里有两条依赖 git 历史的命令：

```yaml
- Compile Audit (隔离块语法检查 · T2 增量优先)
  run: python3 tools/cppbible.py compile --changed --parallel || python3 tools/cppbible.py compile --full --parallel
- Compile + Link + Run + Sanitizer (T1-1 运行期门禁)
  run: python3 tools/compile_run_sanitize_pipeline.py --changed --chapter-context
```

- 第 1 条**有兜底**：`compile_all.py:408` 在 `--changed` 找不到变更时打印"无章节变更，回退全量编译" ⇒ **不受影响**。
- 第 2 条**无兜底**：`compile_run_sanitize_pipeline.py:488-508` 依次尝试 `origin/master...HEAD`、`HEAD~1..HEAD`，
  两者都取不到时只打印 `[*] --changed: 无变更章节，跳过。` 并**正常退出**。

⇒ 浅克隆下 **T1-1（编译+链接+运行+Sanitizer）在 CI 上从未真正执行**，且**不报错、不留红**。

### 3.2 为什么算"配置缺口"（仓库自己的文档已把它列为通用要求）

| 出处 | 原文 |
|---|---|
| `data/673q_CI验证准备.md:74` | \| git 历史 \| `fetch-depth: 0` \| checkout 参数 \| 增量门禁（`--changed`）拿不到 HEAD~1 \| |
| `data/673s_环境依赖清单.md:66` | replay / 增量门禁要完整历史（`fetch-depth: 0`） |
| `_arch_v46/37_CI_CD最小配置.md:291-292` | `actions/checkout` 默认做**浅克隆**（`fetch-depth: 1`）…**阙疑必须显式写 `fetch-depth: 0`**，否则"用 tag 钉住版本"的整个方案在 CI 里会**静默失效** |

`quality / pytest / replay / gate / discipline-670c` 都显式写了 `fetch-depth: 0` —— `compile` 是**唯一**用了 `--changed` 却没写的 job。

### 3.3 处置：**只登记，不启用**（理由）

| 为什么不在本批加 | 说明 |
|---|---|
| 1. 不是"会导致 CI 变红"的问题 | 它的表现是**静默跳过**，不是红。本批目标是"修复会导致 CI 变红/失效的配置"——它属"失效"，但修法会**启用一个此前从未在 CI 跑过的门禁**。 |
| 2. 结果**无法在本批验证** | T1-1 依赖 Linux 的 ASan/UBSan/TSan；本机 MinGW 缺完整 sanitizer 运行时（673q §2.2 已列"必须 CI"）⇒ 本地无法预演"启用后会不会红"。 |
| 3. 与既有处置纪律一致 | 673s 对同类"加了会引入新红源"的项（`tool_integrity`、`adversarial_regression`）**明确选择不补并登记**；本批沿用。 |
| 4. 属策略决策 | "T1-1 是否应在每次 push 都真跑"是 owner 的取舍（成本 vs 覆盖）。 |

**建议的最小补丁（交 owner 拍板后一行即可）**：

```yaml
    - uses: actions/checkout@v7
      with:
        fetch-depth: 0        # 673u：compile job 的 T1-1 用 --changed，浅克隆会静默跳过
```
