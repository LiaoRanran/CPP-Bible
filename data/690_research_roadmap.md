# 690 · E · 研究路线图（690 之后的 6–12 个月）

- 批次：690｜依据：`690_critical_assessment.md`（43 条甄别结论）、`690_tensions_and_blindspots.md`（7 矛盾 / 8 盲点）
- 评审给出的四步路线（independent labels → environment causality → independent evaluator → cross-domain transfer）**被采纳为骨架**，但按本批的依赖分析做了次序与范围修正。

## 0. 总纲

### 0.1 第一篇上限≠ 方向上限（采纳 R3-01）

评审第三轮判断"第一篇论文的上限不等于这个方向的上限"。**这个判断被采纳为长期投入的依据**，但必须给出可操作的区分，否则它只是一句安慰话：

| 层面 | 由什么决定 | 本项目的位置 |
|---|---|---|
| **第一篇上限** | 现有证据能支撑的最大 claim 强度 | 受**标注效度**（无人类 IAA）与**等价检验未通过**双重限制 |
| **方向上限** | 这个研究问题本身的天花板 | 由"评估装置的效度问题在代码领域有多普遍"决定，**不受第一篇的证据缺口限制** |

**操作含义**：短期（E1）的工作目标是**把第一篇推到它自己的上限**；长期（E3）的工作目标是**不受第一篇的短板约束**。**混淆这两个层面会导致两种典型错误**：要么因为第一篇的缺陷而放弃方向（过度悲观），要么因为方向的潜力而放松第一篇的要求（过度乐观）。

### 0.2 五档排序的修正：三维而非一列（修正 R3-02/R3-03）

评审把五个方向排成一列高低。**我们接受操作序，但不接受这个维度**，因为这五项不在同一维度上，硬排会掩盖依赖关系：

| 维度 | 项目 | 性质 | 依赖 |
|---|---|---|---|
| **A. 效度前提** | 人类独立标注（labels） | **前提**——不解决则其他实验的结论都不可信 | 无（可立即开始，且**工期最长**） |
| **B. 方法贡献** | 环境感知协议（environment） | **独立贡献**——可操纵、低成本、产出普适命题 | 依赖 A 的部分（类型标签需可信） |
| **C. 外部效度** | 真实外部系统对比 / 原始项目 CVE | **补短板**——把内部结论接到外部 | 依赖 A（否则比较的是两个不可信标签） |
| **D. 证伪工具** | 信息论 / 子模 | 已完成，降为装置 | 无 |
| **E. 跨域** | 跨语言 / 跨领域 | 规模化验证 | 依赖 A+B+C |

**修正后的操作序**：**A 与 B 并行启动**（A 是工期瓶颈，越早开始越好；B 成本低、可以立刻出结果），C 在 A 有初步结果后进入，E 在三者之后。

> **为什么把 A 提到与 B 并列**（评审把人类标注排第 1，环境排第 2，我们同意次序，但不同意"串行"）：人类标注工期 40–60 小时且依赖外部人力，**是全项目唯一的长周期资源**。若按"做完 A 再做 B"的串行安排，A 的工期会成为整个 E1 的关键路径。**正确做法是让 A 的数据采集与 B 的因子实验并行**，因为二者使用不同的样本与不同的执行环境，不冲突。

| **预期结果** | 人类 IAA 的 `defect_type` κ，以及**人类 vs AI** 的 κ（后者才是真正的效度检验） |

### E1-E · 环境感知因子设计（Agent 可做，2–3 周）

| 项 | 内容 |
|---|---|
| **目标** | 把"measured environmental loss"从工程观察升级为**可做因果陈述的实验** |
| **方法** | 正交因子分解（编译器身份 × sanitizer 可用性 × 优化级别 × OS 内核），**≥2×2 设计** + 因子内随机化（预声明 seed）。详见 `690_experiment_designs.md` §2 |
| **预期结果** | 各因子的主效应与交互项；把现有 −35.45pp 总差距**分解**到具体因子上 |
| **成功标准** | 至少能把差距分解为"可操纵因子贡献 X pp / 不可操纵残余 Y pp" |
| **失败应对** | 若因子间强混杂无法分离（预期风险：MinGW 无 sanitizer 是**捆绑**的），**降级为"可分离子集上的因子设计"**并诚实报告哪部分不可分离。**绝不**用整体换环境的旧数据冒充因果证据 |

### E1-F · LLM audit transfer study（Agent 可做，2–3 周）

| 项 | 内容 |
|---|---|
| **目标** | 测**协议的可迁移性**（不是 judge 的准确率） |
| **方法** | n=100；对照臂=直接信 LLM 判定（二值），协议臂=LLM 只提证据候选 + 程序裁决（四态）；载体 = 一个可执行的代码 judge 任务。详见 `690_experiment_designs.md` §4 |
| **预期结果** | 协议相对载体默认实践的增量；以及**协议在非 C++/非断言载体上的失效模式清单** |
| **成功标准** | 给出"协议在何种载体上失效"的可描述结论（哪怕是负面的） |
| **失败应对** | 若协议在任何载体上都无增益 ⇒ **这是一个诚实的负结果**，说明协议的价值绑定在"证据可执行重算"这一前提上——那反而**加强**了我们的差异化主张。**不得**改设计去凑出正面结果 |

## 2. 中期（E2，3–6 个月，第一篇投稿后 / 审稿中）

### E2-A · 论文 revision 准备

**触发**：收到审稿意见后 48 小时内做逐条处置表（格式复用 `690_review_opinion_inventory.md`）。
**准备物**：E1 的全部实验产物 + 修订后的 claim audit（复用 `686_claim_audit.json` 的格式）。
**纪律**：revision 阶段最容易犯的错是"逐条答应评审"导致 claim 通胀——用 `690_rebuttal_redlines.md` §1.2 的反向清单自查。

### E2-B · 真实外部系统对比（扩展）

E1-G 的 3–5 个系统扩展到 8–10 个；加入**至少一个 LLM judge**（呼应 E1-F），使对比覆盖"确定性工具 / 统计工具 / 模型 judge"三类。
**成功标准**：对比表能支撑"我们的能力不在准确率轴上，而在可审计轴上"这一非平凡结论。

### E2-C · 原始项目 CVE 验证（15–30 个）——**排序第四但必做**

**为什么排第四仍要做**：R3-10 把排序理由隐含为"单文件重构已经够了"，**这个理由我们不接受**（见 `690_tensions_and_blindspots.md` T-01）。外部效度是当前最薄环节。

**现实成本警告（基于 683 的经验）**：为每个原始项目重建可用的 sanitizer 构建环境是**不可忽略的成本**（WSL 硬依赖、缺 `libclang_rt.asan_dynamic`、TSan 在高熵 ASLR 下间歇不可用）。**务实路径**：先做 **5 个**能成功构建的项目（必须含 ≥1 个能触发 tsan 的并发缺陷）证明方法可迁移，再谈规模。

**命名纪律**：若仍用重构，必须继续叫 "source-derived reconstruction"，**不得**改称"原始项目验证"。

### E2-D · 跨语言初步验证（Python 小样本）

**最小设计**：n=60–80 个 Python 缺陷，单资产子集（`log_error` + 跨编译检查），预声明口径。
**成功的最低标准**：不是"检出率与 C++ 可比"（不可比），而是"**协议在新语言上仍然可执行且不需修改**"——这是关于**协议可移植性**的陈述，不是关于检出率的陈述。

### E2-E · 投稿策略（arXiv / TMLR 并行）

沿用 688 的策略文件；本批新增一条判断依据：**E1-D（人类标注）若在投稿前未完成，则必须按三态原则把 T17 写成"未见证据未闭合"而非"安全"**（这与「行远」项目第 15 条约束同源）。

## 3. 长期（E3，6–12 个月，第二篇方向）

### 3.1 框架定位（采纳 R3-08 "Evaluation as a Measurement System"）

**采纳为组织语言，不作为题目。** 理由：框架是组织方式，不是研究问题；用框架当题目会在审稿时被读作"没有具体问题"。评审把它当框架是对的，当题目是错的。

### 3.2 三个候选方向

---

**方向 A（推荐）：Auditing LLM Judges: A Measurement-Centric Framework**

| 项 | 内容 |
|---|---|
| **核心研究问题** | 当判定者从"确定性工具"变为"模型"时，**可执行重算的证据要求**应如何调整？调整后，哪些失效模式消失、哪些新增、哪些变得更严重？ |
| **与第一篇的关系** | 直接承接：E1-F 是它的最小版本（n=100，单载体）。第二篇把它做成**框架**：多载体 × 多失效模式 × 证据要求的形式化 |
| **可行性** | **高**。E1-F 已跑通全流程；CodeJudgeBench（26 judge 模型）提供了现成的载体清单；BabelJudge 的四类失效模式提供了因变量分类 |
| **预期贡献** | ①证据要求的形式化（什么样的证据对一个模型 judge 是充分的）；②失效模式在"证据可重算"约束下的**重分类**；③协议迁移的**边界条件** |
| **风险** | BabelJudge 已占"可靠性审计框架"的名词位 → **必须靠"证据要求"这个支点差异化**，不能靠框架名 |
| **与评审的对应** | 直接实现 R3-04 与 R3-07 第三步（independent evaluator） |

---

**方向 B：Environment as a First-Class Citizen in Evaluation**

| 项 | 内容 |
|---|---|
| **核心研究问题** | 评估结论的可信度，在多大程度上由**未声明的环境上下文**决定？能否给出一个可移植的"环境指纹"协议，使跨环境比较成为默认动作而非事后补救？ |
| **与第一篇的关系** | 承接 E1-E 的因子设计，把它从 C++ 推广到"任意可执行断言的评估" |
| **可行性** | **中**。E1-E 只在 C++/单平台上做过；跨语言必须先做 E2-D。**工作量大于方向 A** |
| **预期贡献** | ①环境因子的**通用分解**；②环境指纹协议；③"静默退化"现象的跨语言复现（这是最有价值的一类复现——若在 Python 上也观察到"unknown 率不上升而 recall 下降"，它就接近一个普适定律） |
| **风险** | 方向 B 与方向 A 争夺同一批执行资源（都需要多载体实验）。**必须串行，不能并行** |

---

**方向 C：When Benchmarks Drift: A Caliber-Audit Protocol**

| 项 | 内容 |
|---|---|
| **核心研究问题** | 基准的"口径"（分母、unknown 记账、工具义务）随时间漂移时，如何**审计**一个已发表的 benchmark 数字是否仍可比？ |
| **与第一篇的关系** | 最远，但**最快能写**：数据大部分已在（多批次、多口径的历史数字） |
| **可行性** | **最高**（主要是回溯已有产物） |
| **预期贡献** | 一个 caliber 漂移的**实证目录** + 审计规程 |
| **风险** | **最容易显得 incremental**——它像第一篇的附录而非新论文。若选它，必须找到第一篇没有的**新数据源**（例如他人已发表的 benchmark 数字的口径回溯） |

---

### 3.3 三方向的排序与建议

**推荐 A，理由三条**：
1. **依赖已就位**：E1-F 会在投稿前跑完最小版本，第二篇的**基础设施和预注册口径都是现成的**；
2. **评审已指认方向**：R3-04 与 R3-07 第三步都指向它，这是评审唯一主动推荐的方向；
3. **差异化支点最硬**："证据可重算"是一个结构性的、能被证伪的差异，不是措辞差异。

**B 是最有科学潜力的，但必须等 A 的最小版本发表后再决定**（避免两篇同质化）。**C 是备选**——若 A 的实验结果不理想，C 的成功率最高。

## 4. 不做清单（明确放弃）

> 本节采纳 R3-06 与 R3-11，但**每条都给出"放弃的理由"与"重议条件"**，否则"不做清单"会变成惰性。

### 4.1 放弃：信息论 Goodhart 大统一理论

- **理由**：确实会变成 busywork——我们从未做过，也不打算做。**但注意**：放弃的是**理论**，不是**测量**（684 的两个数保留，见 `690_critical_assessment.md` §3.7）。
- **重议条件**：若某天出现一个**能量化预测**的理论框架，且其预测在我们数据上可检验，则重议。

### 4.2 放弃：真正的多轮演化性能提升

- **理由**：**证据显示空间极小且已被我们自己否证**。E 的 failure 分量 14/14 块 ≡ set-cover greedy；贪心 = 穷举最优（ratio 1.000）；自适应天花板仅 +2.29pp 且真实自适应策略**低于**静态贪心。**三条独立证据都指向"没有提升空间"**。
- **重议条件**：需出现一个**非覆盖型**的目标函数（例如引入"证据多样性"或"判定延迟"作为第二目标）。那是新问题，不是本问题的延伸。

### 4.3 放弃：再增加内部规则 / metric

- **理由**：R3-06 的"做过头"警告在这一点上完全正确。现状：67 规则、8 资产、VC/EE 两个内部指标，**已经足够支撑全部四个贡献**。第 68 条规则不会让任何 claim 更可信。
- **重议条件**：仅当某个**现有 claim** 因缺少某个具体数字而无法成立（且该数字不能从已有数据算出）。**不接受"再加一个更全面的指标"作为理由。**

### 4.4 放弃：与成熟 verifier 比性能

- **理由**：**错误战场**。我们不是编译器也不是 sanitizer；在一个我们不优化的轴上比较，赢不了也不该赢。
- **重要限定（修订 R3-04 的表述）**：这与 E1-G/E2-B 的"公平外部对比"**不矛盾**——**对比是为了定位（positioning），不是为了取胜**。两者的区别在预声明与报告口径：定位性对比允许我们落后，条件是**如实报告并据此缩小 claim**。
- **重议条件**：若某天我们的方法确实在某类缺陷上成为 SOTA，则重议（那时比性能才有意义）。

### 4.5 放弃：补做 A1–A4 消融

- **理由**：A1（去失败驱动规则）需要回溯重跑规则集，A4（去 mutation）需要 mutation 算子——属新实验，会引入新的一致性风险；而**本工作的主张不依赖它们**（主张是"可审计的治理纪律 + 精度化的能力边界"，不是"每个组件都贡献增益"）。
- **处置**：**删除**这五行，而不是留着 TODO。**删除一个我们没做的实验，比留一个占位符诚实得多。**

### 4.6 放弃：多语种 / 多框架的全面横扫

- **理由**：与 4.4 同源。E2-D 的 Python 小样本是**协议可移植性**测试，不是**语言覆盖**扩张。

## 5. 路线图的诚实边界

1. **E1-D（人类标注）不在 Agent 的能力范围内**。它是本路线图**唯一的外部依赖**，也是整个 E1 的关键路径。**如果找不到第二标注者，E1 的 A/E2/F 三项全部落空**，只剩稿件清理类工作。这一点必须诚实承认，不能用"AI 自一致 κ=0.727"替代。
2. **E1-G（公平对比）有真实的资源约束**：本机缺 MSVC、MinGW clang ASan 不可用。可选的外部系统可能比预期的少，**必须在设计阶段先核实可获得性**，而不是先承诺再发现做不了。
3. **E2-C（原始项目）的成本被系统性低估**。按 683 的经验，每个项目的构建环境适配成本可能超过其样本本身的价值。若时间窗不足，应先做 5 个而非 15–30 个，**并诚实报告是 5 个**。
4. **本路线图的所有时间估计都是估计**。48 周、40–60 小时、2–3 周这些数字**没有历史基准支撑**——它们是本项目的**第一次**尝试做这类计划。第一个真实交付后必须回头修订。
5. **E3 的三个方向都有"novelty 被更早的工作覆盖"的风险**（DeepFact 已做 co-evolving benchmark + audit；BabelJudge 已做 reliability audit framework）。**方向选择的实质是在"别人占了什么位置"上赌博**，不是"我们想做什么"。
