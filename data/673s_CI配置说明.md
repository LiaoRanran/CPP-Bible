## 3. 本批（673s）对 ci.yml 的改动

**只加了 1 个步骤**，位置在 **`discipline-670c` job** 的「Master gate 670c」之后
（该 job 是 658+669d+D2/D3+671a 守卫的汇聚点，补漏门禁放这里语义最贴）：

```yaml
- name: Quality gates 补漏（book_atom_sync / writer_selfcheck · 只读）
  continue-on-error: true
  run: |
    python3 tools/book_atom_sync.py --check
    python3 tools/writer_selfcheck.py --all
```

### 3.1 为什么补这两个（审计发现）

`pyproject.toml [tool.cppbible].quality_gates` 声明了 **31 项**核心门禁。
逐项核对 ci.yml 后发现 **4 项一次都没出现**：

| 缺失门禁 | 干净检出实测 | 是否补 | 理由 |
|---|---|---|---|
| `book_atom_sync.py --check` | **exit=0**，且**只读**（跑完 `git status` 零改动） | ✅ 补 | 安全且是真覆盖缺口 |
| `writer_selfcheck.py --all` | **exit=0**，且只读 | ✅ 补 | 同上 |
| `tool_integrity.py` | **exit=1**（**在最新 HEAD `189adf04` 的干净检出上复验**） | ❌ 不补 | 干净检出上 `evidence/` 与 `data/mutation` 的 merkle 根与台账不匹配 ⇒ 加进来必红。**注意**：673q D 报告里写的 "tool_integrity → exit 0" 是**主仓脏树**口径——其绿依赖**未提交的** `tools/.tool_checksums`；CI 拿到的是提交版 ⇒ 必红。属**真实治理债**（670c 信任锚漂移） |
| `adversarial_regression.py` | exit=0 **但改写 33 个受跟踪文件**（`_adv_v80/probes/*.md`） | ❌ 不补 | 会弄脏工作树，撞 quality job 的 Worktree Cleanliness ⇒ 引入新的红源 |

两项补漏都标 `continue-on-error: true`（与相邻步骤同口径）：补漏不该成为新的红源。

### 3.2 为什么不把 `tools/fast_gate.py` 整个塞进 CI

任务书建议 CI 跑 `fast_gate`。实测结论：**它的内容已被 CI 覆盖**，而且直接跑有副作用。

- 覆盖关系：`fast_gate` 的三道门禁（658 / 669d / 671a guard）⊆ CI 的
  `tools/run_master_gate_670c.py --check`（该工具内部 import `guard_rerun_671a` / `drift_watch_671a`，
  并以子进程调 658）⇒ **已在 `discipline-670c` job 覆盖**。
- 副作用：`fast_gate` 会**直接子进程调用 `run_658_gate.py`**，而后者会写
  `data/658_gate_status.json` / `data/669d_gate_status.json` / `docs/669d_gate_report.md`
  （**冻结件**）。CI 用 `run_master_gate_670c.py --check` 而不用 `fast_gate` 正是为了**不写**这些冻结件。
  ⇒ 把 `fast_gate` 塞进 CI 会污染工作树、可能与 Worktree Cleanliness 冲突。

## 4. CI 跑什么 / 不跑什么

### 4.1 跑

- **快档**：`pytest -m "not slow" -n 16`（pytest job）+ 同一子集在 gate job 里再跑一次（同屏可读性）。
- **慢档**：`pytest -m slow -n0`（串行，WSL 编译类 / 全量变异 / 全量重跑）。
- **门禁**：见 §2 表。
- **重活**：全量 compile（`compile` job）、PDF/EPUB（`pdf`/`epub` job）、站点（`site` job）。

> ⚠ 任务书写"不跑慢校验（全量 compile、全量 mutation），只跑快档"。**现有 CI 与这条不同**：
> 它跑 `-m slow -n0`，另有独立 `compile` job。本批**没有**删它们——删掉会直接降低覆盖，
> 属**策略决策**（需 owner 拍板），不是清理杂活。此处只登记差异。

### 4.2 不跑

- 本地安全删除拦截层（`SAFE_DELETE_BULK_CONFIRM_REQUIRED`）—— CI 无此层。
- `fast_gate.py` 本体（理由见 §3.2）。
- `tool_integrity.py` / `adversarial_regression.py`（理由见 §3.1）。

## 6. 阻塞登记：CI 在干净检出上不会绿（必须如实报告）

**方法**：`git worktree add --detach <clean> HEAD` 造一个**干净检出**（= CI 所见），
在其中跑 CI 同口径命令。同时发现**本机 `PYTHONPATH` 注入了 WorkBuddy 的安全删除拦截层**
（`sitecustomize.py` → `SAFE_DELETE_BULK_CONFIRM_REQUIRED`），它会把大量删除类测试伪造成
`SystemExit: 1` ⇒ 必须用 `CODEBUDDY_SAFE_DELETE_ENABLED=0` 关掉才看得到真信号。

```
cd <clean-worktree>
CI=true CODEBUDDY_SAFE_DELETE_ENABLED=0 python -m pytest tests/ -q -m "not slow" -n 16 --tb=line -rf
→ exit=1，42 failed
```

### 6.1 42 条失败的分类

| 类别 | 条数 | 例子 | CI 会不会红 |
|---|---|---|---|
| A · 缺**未跟踪的派生/构建产物** | ~20 | `data/metrics.jsonl`、`data/propositions.db`、`build/replay_manifest.json`、`dist/`（多数被 `.gitignore` 排除 ⇒ 任何干净检出都没有） | **会** |
| B · 平台 / 本机环境特有 | ~8 | `test_split_670c`（本机存在 `C:/CodeLearnling/queyi-verifier`）、`test_numbers_env_671g`（真实机器环境）、`test_quality_gate_613`（ruff 版本差异） | **多数不会**（CI 是 ubuntu） |
| C · 真实治理债 / 漂移 | ~14 | `tool_integrity`（信任根）、`pck_hash_renewal`、`ots_anchor`、`governance_supply_chain`、`guard_rerun_671a`（12 个 block）、`grounded_audit`、`human_review_honesty`、`ruler_coverage`、`c_target_648` | **会** |

### 6.2 已实测的缓解：给 pytest job 加"准备派生产物"

在干净检出里先跑：

```
python tools/prop_graph.py build        # → data/propositions.db
python tools/metrics_collector.py --no-heavy   # → data/metrics.jsonl
```

再把 A 类文件重跑一次：**42 → 24 条**（prop_* / metrics_* / learner_twin / debt_replay 等转绿）。

**但没有采用为 CI 步骤**，因为实测发现一个**冲突**：
`prop_graph build` 会让 `test_sqlite_version_671e::test_current_db_user_version_is_zero_documents_gap`
由绿转红（该用例断言"活库 `user_version` 仍为 0，用于**记录未同步缺口**"，建库后变成 2）。
⇒ 这些用例是**对着开发机的产物状态**写的，不是对着干净检出写的。
在 owner 决定"哪些产物该在 CI 里生成"之前，加 prepare 步骤会按下葫芦浮起瓢。

### 6.3 建议的处置顺序（不在本批范围，交 owner）

1. **C 类（~14）**：属治理动作（重钉信任根 / 重跑 pck / 重跑 671a 守卫源头批次）。
   按既有惯例由对应批次 owner 处置，本批不擅自动（红线 4：不擅自清 debt 票）。
2. **B 类（~8）**：给平台相关用例加**条件守卫**（`skipif(os.environ.get("CI")=="true")` 或按
   平台探测）——注意这类改动会碰测试文件，建议独立批次。
3. **A 类（~20）**：先决定"哪些产物由 CI 生成、哪些由用例改成条件 skip"，
   再给 `pytest` job 加 prepare 步骤；同时处理 §6.2 的冲突。
