## 博客 1：同一个 C++ 检测器，在 WSL 和 Windows 原生下差了 35 个百分点：我用 1147 个样本量化了"环境漂移"

### 导语

你有没有过这种经历：论文里报的检测率是 60%，换台机器、换个 shell、换个 libc，数字突然变成 25%，而你甚至不知道该怀疑什么。我把这件事拆成了 1147 个样本、两个环境、一次严格的配对实验，结论有点吓人——**这个漂移是静默的，你的指标根本不会报错**。

### 正文

#### 0. 先说结论

同一个 C/C++ 软件验证检测器，同一份冻结样本库，只换运行环境：

- **E1（WSL 子系统）：检出率 60.07%**
- **E2（Windows 原生）：检出率 24.74%**

差了 **35.33 个百分点**。

更扎心的是统计检验：McNemar 配对检验 **p = 1.24×10⁻⁶⁰**。这个 p 值什么概念？通常 p<0.05 就显著了，10⁻⁶⁰ 这个量级意味着"这俩结果来自同一个测量过程"这个假设，在数学上已经死得不能再死。

但你的检测器自己**一个 warning 都没报**。它只是默默把"正确"这个词的定义换了。

#### 1. 什么叫"静默退化"

做评测的人都熟悉一个词：regression。新版本跑挂了，CI 红了，你知道要修。

但我这次遇到的是另一种病：**Δunknown = 0**。

翻译成人话：在 E1 和 E2 两个环境下，检测器"看不出来、归到 unknown 桶"的样本数，**一模一样**。也就是说，从外部观察，这个检测器没有变得更犹豫、没有变得更爱拍脑袋、没有 throw 任何异常。它只是把"我认为是 bug"的那一栏，从 60% 的位置搬到了 25% 的位置。

这就是我说的**静默退化（silent degradation）**：
- 你不会看到 crash。
- 你不会看到 unknown 比例上升。
- 你不会看到任何一条日志说"我环境不对"。
- 你只是……数字变了。

如果你是一个跑评测的博士生，你会觉得这是你自己模型没调好，然后继续调参。如果你是一个 reviewer，你会觉得这个数字"还行"。

#### 2. 为什么差了 35 个点

我把 F1 分数的变化做了一次因果分解。表面上一次"改进实验"带来了 **+24.03** 的 F1 提升，听起来很美好。但拆开看：

| 因子 | 贡献 |
|---|---|
| 口径变化（caiber / 定义改了） | **−9.55** |
| 两个零产出组件（加了等于没加） | **−8.27** |
| linker 行为差异 | **−4.65** |
| k 档位扫描（真正的改进） | **+10.74** |
| **净结果** | **+12.30** |

看出来了吗？那个 +24.03 的"改进"，**有一半以上是测量漂移，不是真进步**。

WSL 和原生 Windows 的差异，本质上就是这个分解里 "linker 行为" + "口径" 的叠加：同一份 C++ 代码，在 WSL 下链接出来的二进制和原生 Windows 下链接出来的，符号表、异常处理、RTTI、栈展开都不完全一样。检测器基于 AST / 基于二进制的判定路径，就这么悄悄换了一条。

#### 3. 这件事为什么重要

如果你只做一次实验，你永远不知道自己站在 60% 还是 25% 那一侧。

更可怕的是：**这种漂移不需要任何人故意优化指标**。它没有 Goodhart 定律那种"有人盯着指标刷分"的主动性。它就是环境自己变了，测量口径自己跟着变了，你的数字自己动了。

我把这一类叫做**结构性（被动）Goodhart**——下一篇博客会展开讲它的四种亚型，以及为什么其中两种亚型**用配对实验永远测不出来**。

#### 4. 我做了什么

- 冻结了一份 1147 样本的检测矩阵，不让检测器重跑，保证两个环境读到的是同一份"标准答案"。
- 在两个环境下分别复跑，做严格配对。
- 用 McNemar 检验量化差异。
- 把整个流程写成可复现工具：你 clone 仓库，跑一行 `python tools/verify_paper_numbers.py`，就能在自己机器上复现 60.07 / 24.74 / 1.24e-60 这三个数。

这套东西不是只给 C++ 检测器用的。任何"在一个环境跑出一个数、换个环境数字就变了"的评测场景——ML 模型 benchmark、SAST 工具跑分、编译器 fuzzing 统计——理论上都吃同一个病。

#### 结尾

我把所有冻结矩阵、分析脚本、两篇配套论文的 LaTeX 源码，都放在了一个匿名 GitHub 仓库里，双盲、无作者信息、Apache-2.0。你可以自己跑一遍，看看你机器上能不能复现这 35 个百分点的差距。

仓库链接见评论区 / 个人简介。如果你的领域也有"换台机器数字就变了"的问题，欢迎来 issue 区聊——不用客气，我不回私信，但会读 issue。

## 博客 2：你的评估指标可能在骗你：结构性 Goodhart 的四种类型和一个 R²=0.9997 的公式

### 导语

Goodhart 定律说"指标一旦成为目标就失效"。但我们做评测的人经常发现一个更诡异的现象：**没人在刷分，指标自己就变了**。我把这种"被动 Goodhart"拆成了四种类型，然后发现它们在一个 40 个真实 CVE 的案例库上，几乎完美地落在一条二次曲线上——R² = 0.9997。

### 正文

#### 1. 传统 Goodhart vs 结构性 Goodhart

Goodhart 定律有一个常见版本："当一个度量变成目标，它就不再是好的度量。"

这个版本隐含一个前提：**有人在优化它**。ML 里刷 validation acc、公司里刷 KPI、学术圈刷引用数——都是有人盯着指标在发力，指标被"刷坏"。

但我在做软件验证评测审计的时候，看到的是另一类问题：**没有人优化指标，指标自己动了**。

同一个检测器，同一份样本，WSL 下 60.07%，Windows 原生下 24.74%。没有人故意改模型、没有人刷分、没有 adversarial pressure。只是环境变了，测量口径跟着变了。

我把这种现象叫**结构性 Goodhart（structural / passive Goodhart）**。它的病根不在"有人在优化"，而在"测量系统本身有自由度"。

#### 2. 四种类型

我把结构性 Goodhart 分成四型，对应测量链条上四个可能出问题的位置：

- **Type I — Acquisition drift（采集层漂移）**：输入到检测器的东西变了。比如编译器版本、libc 版本、链接器行为。输入分布悄悄移了。
- **Type II — Caliber drift（口径漂移）**：判定"什么算检出"的那条线动了。比如"报告了一个 warning 就算检出" vs "必须报出文件+行号+函数名才算检出"。
- **Type III — Label drift（标签漂移）**：金标准答案本身变了。比如某个 CVE 在 2024 年被判为"真实漏洞"，2025 年 NVD 更新后降级为"不是漏洞"。
- **Type IV — Aggregation drift（聚合漂移）**：单个样本的判定没变，但聚合方式变了。比如从 macro-F1 换成 micro-F1，或者按项目加权 vs 等权。

这四型不是我拍脑袋分的——它们对应后面要讲的 8 公理代数里，不同公理独立失效的位置。

#### 3. 那条 R² = 0.9997 的曲线

我在一个 40 个真实 NVD CVE 的案例库上（其中 14 个能在我的环境里实际编译成 PoC），扫了不同程度的"表观增益" d。所谓 d，可以理解为"在多大程度上动了测量口径"。

结果发现，**表观增益 g_app(d)** 几乎完美地符合一个二次函数：

```
g_app(d) = 5.47 + 5.28·d − 0.26·d²
R² = 0.9997
```

怎么读这个公式？

- **截距 5.47**：就算 d=0（完全不动口径），基线还有 5.47 的"水分"。这部分来自检测器本身的噪声、样本选择偏差。
- **线性项 +5.28·d**：一开始，你动一点口径，表观增益线性上涨。这是大多数人刷指标的区间。
- **二次项 −0.26·d²**：但动得太狠，曲线开始下弯。因为口径动到一定程度，你会把明显不是 bug 的东西也算进来，方差爆炸，反而拖低表观分。

R²=0.9997 这个数字，在真实世界数据里是很罕见的。它说明：**在这个测量系统里，"表观增益"几乎是被一个低维解析形状决定的，不是随机的**。

这其实是个坏消息。因为它意味着——你看到的 +10、+20 的"改进"，很大概率只是你无意中把 d 调到了曲线上升沿的某个位置。

#### 4. 用我自己的 F1 分解举例

之前提过一次，我这次研究里有一个表面 +24.03 的 F1 提升，分解后：

- −9.55 来自口径变化（Type II）
- −8.27 来自加了两个零产出组件（相当于聚合方式变了，Type IV）
- −4.65 来自 linker 行为（Type I）
- +10.74 来自 k 档位扫描（这才是真改进）
- 净 +12.30

换句话说，+24.03 里有 **接近 60% 是结构性 Goodhart**。如果我不做这次审计，我会以为自己搞出了一个大改进，发一篇论文，然后 reviewer 在他的机器上复现不出来，game over。

#### 5. 那 Type III 呢？

标签漂移（Type III）是最阴险的。因为金标准答案在你手里，你以为它是固定的。但 NVD 会更新、CVE 的严重性评级会改、项目维护者会给历史 issue 打新标签。

更麻烦的是：**Type III 和 Type IV 在配对设计下，检测功效恒等于 0**。

这句话是什么意思？意思是：不管你采多少样本——100 个、1000 个、10⁹ 个——只要你用的是"同一个样本跑两次"这种配对实验，你就**数学上不可能**区分"是金标变了"还是"是聚合方式变了"。这是信息论给的硬边界，下一篇博客会展开。

#### 结尾

Goodhart 定律真正可怕的版本，不是"有人在刷分"，而是"测量系统本身有自由度，而你以为它是刚性的"。

那个 R²=0.9997 的公式、四型分类、F1 因果分解的脚本，我都放在匿名 GitHub 仓库里。你可以拿自己领域的评测数据套一下 g_app(d)，看看你的"改进"落在曲线哪个位置。

不接广告、不接咨询，issue 区见。

## 博客 3：为什么有些 bug 永远测不出来：测量漂移的信息论下界和 8 条公理

### 导语

做实验测漂移，需要多少样本？直觉是"多多益善"。但信息论给了个冷酷答案：Type I 漂移至少要 849 个样本，Type II 只要 17 个，而 Type III 和 Type IV——**多少个都不够**。这不是工程问题，是数学问题。

### 正文

#### 1. 一个朴素问题

假设你怀疑评测系统有漂移。你打算做一个配对实验：拿同一批样本，在两个"版本"的评测流程下各跑一次，看结果差多少。

要跑多少个样本才够？

大多数人的答案是"尽可能多"。统计学家会说"算一下 power analysis"。但没有人问过一个更前置的问题：**在最理想的情况下，这个问题到底可不可识别（identifiable）？**

如果问题本身不可识别，你跑 10⁹ 个样本也没用。

#### 2. 8 条公理和 3 条独立公理

我把"测量"这件事公理化。一个测量系统要谈"漂移"，至少要满足 8 条基本性质（A1–A8）。这套公理的作用，是把"什么叫测量变了"这件事变成代数。

我原本以为 8 条公理都是独立的。结果在 4096 种覆盖结构 × 7 种聚合方式下跑了一遍，发现：

- A1（幂等性）→ 是定理 T1
- A3（交换性）→ 是定理 T2
- A4（不可逆性）→ 是定理 T3
- A6 / A7（可观测分层）→ 是定理 T4–T5
- **真正独立的公理只有 3 条：A2（移除单调性）、A5（超加性）、A8**

而且系统是**不完备**的：标签漂移（Type III）在现有公理体系里**根本表达不出来**，必须补一条 A8。

换句话说：过去大家讨论"评测可不可信"，很多争论其实是在重复推定理。真正需要当作"假设"来信的，只有 3 条。剩下的，你接受了这 3 条，其他都自动成立。

#### 3. 信息论下界

在这个公理体系下，我推了 6 个定理（T1–T6），其中最硬核的是样本复杂度下界。

| 漂移类型 | 配对设计所需样本下界 | 解读 |
|---|---|---|
| **Type I（采集层）** | **849 个样本** | 你得采近千个配对样本，才有足够功效检测出输入分布漂移 |
| **Type II（口径）** | **17 个样本** | 口径漂移很容易测，十几对就够 |
| **Type III（标签）** | **功效恒为 0** | 配对设计下，n→∞ 也测不出来 |
| **Type IV（聚合）** | **功效恒为 0** | 同上 |

Type I 需要 849、Type II 只要 17——差了 50 倍。这告诉我们：**不是所有漂移都一样贵**。口径漂移便宜，采集层漂移贵。

但真正让人绝望的是 Type III / Type IV：**配对设计在数学上就无法识别它们**。

#### 4. 为什么 Type III / IV 测不出来

直觉上，标签漂移和聚合漂移都是"评测变了"。但你手里的观测是什么？是两个环境下的 (检测器输出, 金标) 对。

问题来了：
- 如果金标本身在两个环境间悄悄换了（Type III），同时聚合公式也换了（Type IV），你看到的最终差异，**无法分解**。

这就像你看到两个传感器读数不一样，但你不知道是传感器漂了，还是参考真值漂了，还是两个都漂了——而且没有第三个传感器做三角测量。

信息论给的答案是：**在配对设计这种观测结构下，这两种漂移是不可识别参数（non-identifiable）**。你必须换观测结构——比如引入第三方标注、引入时间序列、引入嵌套设计——才能打破这个 degeneracy。

只有在"嵌套假设"（nesting）成立时，才能做点估计。但嵌套假设本身是个强假设，你没法证。

#### 5. 那审计还有什么意义？

看到这里你可能会问：既然 Type III/IV 测不出来，那审计是不是没用？

不是。我推了一个**能力边界预测模型**，在留出集上 **AUC = 0.7551**。意思是：在你花成本做审计之前，你可以先预测"这个评测系统大概在哪个位置最容易漂移"，然后把 849 个样本的预算花在刀刃上。

这是一种"元审计"思路：不是所有系统都需要做全量审计。先用一个便宜的模型告诉你"哪一类漂移最可能发生"，再决定投入多少样本。

#### 6. 三个边界

整套理论最后收敛到三句话：

1. **可识别性边界**：结构性漂移和真实能力漂移，单凭配对数据不可分（嵌套下才可点识别）。
2. **可纠正性边界**：事后补救只能修测量之后的层；采集层漂移必须重测，残余误差最高 30%。
3. **样本复杂度边界**：审计成本由"不一致率"决定，不由效应量决定。Type III/IV 在配对设计下 n=∞ 也无效。

#### 结尾

这三条边界合起来，其实是在说一件事：**评测不是一次性的事，是一个需要持续审计的测量系统**。而审计本身有它自己的数学极限——你不能假装它不存在。

8 条公理、6 个定理、4 型漂移、样本下界的推导过程，我都放在匿名 GitHub 仓库的论文 2 LaTeX 源码里。你可以自己推一遍，看看哪里不同意——我特别欢迎有人来证伪 T1–T6，因为这才是这套东西能往前走的方式。

我不接合作邀约、不接演讲邀请，issue 区慢聊。
