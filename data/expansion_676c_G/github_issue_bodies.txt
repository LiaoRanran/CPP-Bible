===== nlohmann/json#5647 [closed] operator[](size_type) with SIZE_MAX empties the array and writes out of bounds
### Description

The non-const `operator[](size_type idx)` clears the array and then writes before the start of its buffer when `idx` is the largest `size_type` value. This index is easy to produce by accident, for example `j[v.size() - 1]` with an empty `v`.

[`include/nlohmann/json.hpp#L2838`](https://github.com/nlohmann/json/blob/633de8e44bbbc29383d72f8c920343ea5d1eaa21/include/nlohmann/json.hpp#L2838):

```cpp
if (idx >= m_data.m_value.array->size())
{
    ...
    m_data.m_value.array->resize(idx + 1);   // idx + 1 wraps to 0 for idx == SIZE_MAX
    ...
}
return m_data.m_value.array->operator[](idx);   // out of bounds on the now empty vector
```

For `idx == SIZE_MAX`, `idx + 1` is `0`, so `resize(0)` erases all elements, and `operator[](SIZE_MAX)` then addresses `begin() + SIZE_MAX`, which is one element *before* the buffer. The assignment writes there. In an optimized build without sanitizers this silently empties the array and corrupts the heap. For every other too-large index (for example `SIZE_MAX - 1`), `resize()` throws `std::length_error` and the array stays unchanged.

The [`operator[]` documentation](https://json.nlohmann.me/api/basic_json/operator%5B%5D/) promises: "Strong exception safety: if an exception occurs, the original value stays intact." It also says that a missing index is created and the gap filled with `null`, which is impossible for `SIZE_MAX`; the documented exceptions list only `type_error.305`. With `JSON_DIAGNOSTICS`, the same branch also computes `idx + 1 - old_size`.

**Since when:** reproduces with the v3.12.0 headers (same output as below); the `resize(idx + 1)` line is there in v3.12.0 as well.

Related but different: #3973 (buffer overflow in *const* `operator[]` on out-of-range access, documented as undefined behavior).

===== leethomason/tinyxml2#1065 [open] Security: Integer Overflow and Heap Buffer Overflow in DynArray::EnsureCapacity
Description:
I am developing a static analysis engine called Lumos, based on the Z3 theorem prover. It flagged a potential security vulnerability in tinyxml2.h.
Location:
In DynArray<T, INITIAL_SIZE>::EnsureCapacity(size_t cap) (around line 450-470).
The Problem:
The code calculates new allocation size as follows:
cpp
const size_t newAllocated = cap * 2;

The safety of this operation is only guarded by:
cpp
TIXMLASSERT( cap <= SIZE_MAX / 2 / sizeof(T));

Since TIXMLASSERT is removed in Release builds, there is no runtime protection. If cap is large enough (e.g., via a specially crafted XML), newAllocated will overflow, leading to:
A very small memory allocation.
A large memcpy operation into that small buffer:
memcpy( newMem, _mem, sizeof(T) * _size );
This results in a Heap Buffer Overflow.
Suggested Fix:
Add a runtime check that persists in release builds:
cpp
if (cap > SIZE_MAX / 2 / sizeof(T)) {
    // Return error or handle gracefully
}
