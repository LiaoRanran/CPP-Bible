## 任务 B：ci.yml compile job 加 `fetch-depth: 0`（E4）

### 根因（已定位到代码行）

`ci.yml` 的 `compile` job 在 `actions/checkout@v7` 后**没有** `with:` 块 ⇒ 用默认 `fetch-depth: 1`（浅克隆）。而同 job 的 T1-1 步跑：

```
python3 tools/compile_run_sanitize_pipeline.py --changed --chapter-context
```

`tools/compile_run_sanitize_pipeline.py:488-508` 的基线策略：

```python
for spec in ("origin/master...HEAD", "HEAD~1..HEAD"):   # 策略1 PR / 策略2 push
    out = _sp.run(["git", "diff", "--name-only", spec], ...).stdout
    ...
if not changed:
    print("[*] --changed: 无变更章节，跳过。")   # ← 静默跳过，exit 0
```

浅克隆下 `HEAD~1` 不存在 ⇒ `git diff` 报错 ⇒ `changed` 为空 ⇒ 打印「跳过」并 **exit 0**。叠加该步的 `continue-on-error: true`，结果就是：**T1-1（compile+link+run+ASan/UBSan/TSan）自迁入以来在 CI 上从未真跑过**，而日志呈现为绿。

讽刺点：同文件 `ci.yml:843-845` 的注释**已经写着**「CI 在 fetch-depth:0 下有完整历史」——注释与配置脱节，正是这个 bug 能长期存活的原因。

### 改动

`.github/workflows/ci.yml` 的 `compile` job checkout 步新增 `with: fetch-depth: 0`，并把上述根因写进注释（防止后人再次误删）。改动后 YAML 解析验证通过，`fetch-depth: 0` 出现 7 处，与已用该配置的 quality/pytest/replay/gate/discipline 对齐。**未改** `concurrency-safety` / `publish-check` / `site` / `pdf` / `epub` 的 checkout（不属本批范围，登记为可选对齐项）。

### 风险提示（任务卡要求的诚实声明）

1. **无法本地预演**。T1-1 需要 Linux 完整 sanitizer 运行时（ASan/UBSan/TSan）。本机 MinGW 15.3.0 存在 `std::print` 链接缺口与 winpthreads 线程崩溃缺陷，工具自身会做 toolchain-skip 降级 ⇒ **本批未能本地验证该步真跑**，只验证了配置与代码路径。
2. **CI 上可能暴露新的编译/运行失败——这是预期的**。此前是「静默跳过」，现在变「真跑」。首次真跑大概率出现 T1-1 自身的基线失败（此前观察期从未积累过数据）。**但该步 `continue-on-error: true`，失败不会让 CI 红**，只会体现为日志/step summary 里的显式失败——这正是设计意图（观察全书基线），但也意味着**别把「CI 绿」误读为「T1-1 过了」**。
3. **本批提交本身仍不会触发 T1-1**：即使基线可取，`--changed` 只处理 `ch*.md`。本次 diff 是 `ci.yml` + `data/**` + `docs/669d_gate_report.md`，**零章节变更** ⇒ 仍会打印「无变更章节，跳过」。要让 T1-1 首次真跑，需满足二者之一：① 一次改动 `Book/**/ch*.md` 的提交；② 手动 `workflow_dispatch` 并把该步改走 `--all-run`。**换言之本批修的是「能力缺失」，不是「立刻见效」**——这一点必须写明，否则会误以为已验证。

### 历史 event 的 ruleset_hash 能否从 git 历史回溯？——**能取到值，但不能用**

`tools/decision_event_v2_626.py:11` 写死了哈希链语义：

> **哈希链**：`self_hash = SHA256(除 self_hash 外所有字段的 JSON 序列化 + prev_hash)`

且 `:112-121`：

```python
def compute_self_hash(self) -> str:
    return hashlib.sha256(f"{self.prev_hash}|{self._payload()}".encode("utf-8")).hexdigest()
def finalize(self, prev_hash, seq):
    self.prev_hash = prev_hash
    self.self_hash = self.compute_self_hash()
    self.event_id = f"AE-{seq:06d}-{self.self_hash[:8]}"   # ← event_id 由 self_hash 派生
```

`:257-261` 的 verify 逐步重算并断言串联：

```python
if e.prev_hash != prev: ...          # 链式校验
if e.compute_self_hash() != e.self_hash: ...   # 逐条重算
```

因此给历史 452 条补一个 `ruleset_hash` 字段会引发**五重连锁破坏**：

1. 每条的 `self_hash` 改变（`_payload()` 覆盖除 self_hash 外全部字段）；
2. 每条的 `event_id` 改变（后 8 位是 self_hash 前缀）⇒ `AE-000001-bf00447a` 这类主键全部失效；
3. 后续所有条的 `prev_hash` 全部失效 ⇒ **全链重算**；
4. `data/646_authority_rule_annotation.jsonl`（452 行，按 `event_id` 关联 67 条规则）**全部失联**；`data/646_authority_rule_annotation.md` 里「原账本 sha256 `ec8cbf5cca2def3d…` 一字未改」的断言当场失效；
5. `_payload()` 的排除清单（`:105`）改动本身即改核心工具 ⇒ 触发 `tool_integrity` 信任根失效、`replay` 全量、merkle/PCK 重锚。

「从 git 历史回溯当时规则集、算出 ruleset_hash、再重算全链」技术上可行，但结果就是**重写一段 append-only 账本的历史**——直接违反任务卡「不得为了补字段而篡改历史数据」与 append-only 铁律。**故不实现。**

### 可行的替代方案（供下一批决策，本批未做）

- **新 event 加字段**（推荐方向）：在 `DecisionEvent` 上新增可选字段并纳入 `_payload()`，只对**今后追加**的 event 生效，历史 452 条原样保留。若 schema 允许缺省，可在报告口径上把历史标注为 `pre-ruleset-hash`——但**不得**回写历史行。
- **旁挂映射表**（更低风险，零账本改动）：新建 `data/authority/ledger_ruleset_hashes.json`，`event_id → {commit, ruleset_sha256}`，历史段用 git 历史回溯**只读标注**，账本本身一字不改。这条路不碰哈希链、不触发 tool_integrity 重锚，是本评估给出的**首选落地形态**。
- 无论选哪条，改 `tools/` 都要按既有流程同 commit 重锚哈希面（`pck_hash_renewal_628 --apply` / `merkle_integrity build-all` / `tool_integrity --update`），否则 `tool_integrity` fail-closed 拒绝运行。属独立批次工作量。

**优先级**：P2，**不与 P0 抢跑**。

## 任务 E：单标注者一致性自检 / Cohen's κ（P4 · 只做评估，**未实现**）

### 结论：**有数据基础，但不能由本批代做，且对现有数据算 κ 会失真**

### 候选标注数据盘点

| 文件 | 条数 | 是不是人工标签 | 适用性 |
|------|------|---------------|--------|
| `data/646_authority_rule_annotation.jsonl` | 452 | **否**。由 `tools/authority_rule_annotator_646.py` 脚本生成，`rule_ids` 是规则引擎的**自动触发结果** | 重标 = 脚本幂等性检查，**不是标注者信度**，κ 无意义 |
| `data/human_attack_edge_annotations.jsonl` | 388 | **是**。`reviewer=LiaoRanran`，含 `action` / `reason` / `timestamp` / `new_confidence` | 唯一可用的人工标签集 |

`human_attack_edge_annotations.jsonl` 的类别分布：**approve 354 / modify 34**（无 reject）。

### 为什么仍不实现

1. **κ 的前提是两次相互独立的判断**。而这 388 条的真实形态是「**AI 预标注 → 抽样 20 条验证准确率 100%(20/20) → 用户确认通过率 90% 以上即授权批量通过**」（首条 `reason` 原文）。即 354 条 approve **并非逐条独立判断**，而是同一判断的批量外推。标注者若两周后重标，κ 会**高得离谱却毫无信息量**——它度量的是「同一授权决定的重复性」，不是「标签效度」。用它替代第二标注者，会制造一个**看起来漂亮、方法上无效**的数字，这在论文语境下是负债不是资产。
2. **极端不平衡**：354:34。κ 在单类占 91% 时对本就偏低，且不可靠。
3. **κ 计算器可写，但数据得由人产生**。真正可做的是：两周后（**2026-10-17** 起）对随机 78 条（20%）**逐条重新独立判断**（屏蔽原标注、隐藏原 reason），再与原标注比。这要求用户本人实际重标，本 Agent 无法代替。
4. **时间窗尚未到**：任务卡设想「隔两周」⇒ 最早 2026-10-17 才可启动。

### 建议的落地形态（下一批，本批不建）

- 现在只做**抽样与协议**：确定 78 条随机样本（带固定种子，脚本化以保证可复现）、写盲化重标模板（隐藏 `action`/`reason`，只暴露 `edge_id` + 命题/证据原文）。
- 到 10-17 由用户重标后，用一个纯函数脚本算 κ（20 行、无依赖，标注者间/标注者内两种 κ 都可算）。
- **诚实口径**：单标注者 κ 度量的是 **intraclass consistency（标注者内一致性）**，论文里必须这样写，**不得**表述为 inter-rater reliability（那需要第二个人）。这是方法学上的硬边界，写错等于给了审稿人一个致命抓手。

**优先级**：P4 替代方案，**不强制实现**。
