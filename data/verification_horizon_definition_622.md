## 一、定义

> **Verification Horizon（验证地平线）**：
> **验证器能够*可靠*处理的最大攻击复杂度**。
> 超过这条线的变异，验证器可能**漏判**（既不拦、也不察觉）。

**与 METR 的类比**（提示词指定）：

| 维度 | METR task-completion time horizon | Verification Horizon（本定义） |
|---|---|---|
| 被测量 | AI 能完成任务的**最长时间尺度** | 验证器能可靠处理的**最大攻击复杂度** |
| 横轴 | 任务时长（分钟/小时） | 攻击复杂度分数（0–100） |
| 纵轴 | 完成率 | **检出率**（blocked / 可施加） |
| 交点 | 完成率降至 50% 处 | **检出率跌破阈值处的复杂度** |
| 用途 | 预测 AI 能力边界 | 预测验证器的**盲区边界** |

**核心直觉**：验证器不是"万能的"，它在**低复杂度**变异上可靠，在**高复杂度**变异上会漏。
Horizon 就是那条**分界线**。

## 二、复杂度的四个维度

| 维度 | 含义 | 取值依据（本实现的代理） |
|---|---|---|
| **语法复杂度** | 变异在语法/表示层做了多少变换 | 算子类型：字段级编辑 < 结构级编辑 < 跨字段注入 |
| **语义复杂度** | 变异是否改变 C++/命题语义 | M3 断言弱化 / M4 恒真注入 / M9 引用破坏 语义影响最高 |
| **证据复杂度** | 是否涉及多证据卡/跨卡交叉 | 证据卡 0.7 / 原子卡 0.3 / M9 跨卡引用 1.0 |
| **规则复杂度** | 是否绕过多条规则的组合 | 命中/触发规则数：1 条 0.3 / 2 条 0.6 / ≥3 条 1.0 |

**加权**：语法 0.25 / 语义 0.30 / 证据 0.20 / 规则 0.25（和为 1.0）

```
complexity_score = 100 × (0.25·syntax + 0.30·semantic + 0.20·evidence + 0.25·rule)
```

## 三、测量方法

1. 对每条 mutation 计算 `complexity_score ∈ [0,100]`；
2. 按分值分桶（20 分一档，共 5 档）；
3. 每桶统计**检出率** = `blocked / 可施加数`（`infra_error` 不计入分母）；
4. **Horizon = 检出率仍 ≥ 阈值（默认 0.5）的最高桶**；
5. 超过 Horizon 的变异 = **验证器的可疑盲区**。

**与 METR 的数值类比**：METR 取"完成率 50%"为界；本定义同样取**检出率 50%** 为界
（阈值可配置，但**改阈值即改结论**，须显式声明）。

## 四、为什么要这个指标

1. **把"漏判"从离散事件变成连续刻度**：过去只能说"这条逃逸了"，
   现在能说"验证器在复杂度 ≥ X 的变异上检出率跌破 50%"。
2. **让"验证器变强"可度量**：每次规则/证据改造后重算 Horizon，
   横轴右移即能力提升（E2 用它画 v1–v7 曲线）。
3. **指导投资方向**：若 Horizon 卡在某桶，说明该复杂度带的规则覆盖不足。

## 五、局限性（诚实登记）

1. **复杂度是启发式代理**：`syntax/semantic` 由**算子类型**映射而来，
   **不是**对实际 AST/语义差异的计算 ⇒ 是**序数近似**，不是精确度量。
2. **检出率依赖判决口径**：本仓 `escaped` 采用严格口径（须"检测消失"），
   ⇒ Horizon 可能**偏乐观**（漏判被低估）。
3. **样本量小**：622 两轮共 80 条（可施加 52 条），分 5 桶后**每桶样本很少**。
4. **阈值 0.5 是拍的**（照搬 METR 类比），无数据支撑。
5. **只度量 gate（规则层）**：未含 replay 复算层 ⇒ Horizon 是**规则层的**地平线。
6. **未做重复性验证**（gate 判定确定性，风险低）。
