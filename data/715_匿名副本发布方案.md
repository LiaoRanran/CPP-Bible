## 1. 任务 2.1：三条路线对比

先纠正一个常见误解（712 已核实）：**GitHub 没有"匿名提交"功能**——提交必然带 author/committer 邮箱；
唯一合规做法是用**与身份无关的账号/组织**，或干脆不发布 git 仓库。

### 1.1 对比表

| 维度 | A. 中立 GitHub 账号 | B. Zenodo | C. OSF（Open Science Framework） |
|---|---|---|---|
| 匿名性 | ⚠️ 需要新邮箱+新账号，且**不复用**头像/用户名/bio；账号本身可被关联（提交时间、内容指纹） | ⚠️ `Creators` 字段**必填**；选 **Organisation** 时只有一个**自由文本名称**字段，可用集体名（如 `Anonymous`）——**✅已核实**（Zenodo 帮助文档 Creators 页）；**是否允许 Person 化名：⚠️未核实**，官方帮助页未涉及，需查 Policies 或问支持 | ⚠️ 可选择不公开真实姓名；**view-only link 机制**（只读、可撤销）被第三方明确用于匿名评审——**⚠️未核实（未在 OSF 官方页确认）** |
| 审稿人可访问性 | ✅ 最好：`git clone` + 逐条跑命令 | ⚠️ 只能下载归档（文件/tarball），不能 clone；（git 仓库可打包上传） | ⚠️ 同 Zenodo（下载/预览），取决于是否上传 tarball |
| 持久性 | ⚠️ 删除即失效；fork/镜像不可控 | ✅ 长期归档（CERN 运营） | ✅ 长期归档（COS 运营） |
| DOI | ❌ 无 | ✅ **每份上传都分配 DOI**——**✅已核实**（Zenodo 官方站点："Every upload is assigned a Digital Object Identifier (DOI)"） | ⚠️ 注册（registration）可获 DOI，**是否所有项目都分配：未核实** |
| 审核周期 | 无 | ✅ 官方站点写 **"No waiting time"**——**✅已核实** | ⚠️ 未核实 |
| 费用 | 免费（公开仓库） | 免费 | 免费 |
| 双盲合规风险 | 🔴 **高**：GitHub 页面/账号本身是可检索的身份线索 | 🟢 低 | 🟢 低 |
| 额外风险 | 若账号被关联到 `LiaoRanran` 的其它仓库，等于没匿名 | 上传者账号本身仍是一个句柄 | 同 Zenodo |

### 1.2 推荐（任务卡允许默认推荐 OSF，但本批给出**不同的**推荐并说明理由）

**推荐路线：`C（OSF 禁运/私有 + view-only link）` 作为双盲期主通道，`B（Zenodo）` 作为投稿后的 DOI 归档。**

理由（三条，均基于已核实的部分）：

1. **双盲期真正需要的是"只读、可撤销、不暴露账号"的通道**，而不是"公开可 clone"。
   OSF 的 view-only link 正好是"私有项目 + 只读链接"，且可随时撤销（⚠️ 机制存在性由第三方说明支持，
   官方细节需用户自查）。GitHub 无论怎么开账号，**页面本身就是身份线索**（这一点在 712 已经被实测验证：
   即使文件内容 0 命中真名，提交元数据与 URL 仍然暴露）。
2. **DOI 是在投稿之后才需要的**（审稿人不引 DOI；录用后的 camera-ready 才引）。
   Zenodo 的 DOI 是 ✅已核实的免费+即时，适合作为**发表后**的永久归档。
   把"双盲审稿"与"永久引用"分成两个阶段，就不必在双盲期承担任何身份暴露风险。
3. **不建议在双盲期用中立 GitHub 账号**：收益（可 clone）与风险（账号关联）不成比例；
   而 OSF/Zenodo 的下载包同样能满足"陌生研究者能重算数字"的要求——
   包内 `REPRODUCTION.md` 与 `REPRODUCTION_LOG.md` 的全部命令都是**本地命令**，
   不依赖 `git clone`（唯一用到 git 的是 README 的 `git clone <this-repo>` 占位符，见 §4）。

**如果必须让审稿人 clone**（某些评审系统偏好链接）：退而求其次的顺序是
`A（中立账号，且只用它托管这一个仓库）` ➜ `B（Zenodo 的 git-兼容 tarball）`。
**任何情况下都不要**用 `LiaoRanran` 名下的 `queyi-audit` 作为审稿链接。

### 2.3 清除的代价（实测，不是估算）

清除 = 改写冻结产物字节 ⇒ 该文件的 sha256 变化 ⇒ 需要：

1. 重新生成 `data/693_data_manifest.sha256`（**这一步本批已经做过，可复现**）；

   审稿人无法用源仓库的锚定去校验匿名包。

## 3. 任务 2.3：原仓库投稿期是否设 private

### 3.1 三个仓库的关系

| 仓库 | 现在 | 建议 |
|---|---|---|
| `LiaoRanran/CPP-Bible`（源） | 有 remote，可见性未知 | **投稿期设 private**（若已 public） |
| `LiaoRanran/queyi-audit`（过渡匿名包） | 有 remote，**含真名账号** | **投稿期设 private**；或**删除**（见 §3.3） |
| `LiaoRanran` 账号本身 | — | 无需变动 |

### 3.2 为什么设 private 而不是删除

1. **删除不能保证消失**：fork、镜像、GitHub API 缓存、Software Heritage 归档都可能保留旧对象
   （712 已在报告中写明）。删除会给用户一种"已经处理了"的错觉，**private 至少停止继续暴露**。
2. private 不破坏本地历史与后续 push 的可行性（随时可再公开）。
3. 投稿期结束后，如果论文被接收，可以再决定是否公开（届时身份已经公开，不再是问题）。

### 3.3 `queyi-audit` 的特别说明（诚实登记一处不一致）

`LiaoRanran/queyi-audit` 是 712 之前那版"匿名包"，**它的提交历史里带真名与 QQ 邮箱**（713 报告已核实），
而它的名字又是 `queyi-audit`——与我们将要发布的匿名包**同名**。
**风险**：审稿人若搜到它，会得到与匿名包相同的文件名 + 作者真名 ⇒ **等于直接关联**。

⇒ **建议：投稿期把 `LiaoRanran/queyi-audit` 设为 private（或删除）**，并把匿名副本改用
一个**不同的仓库名**（例如不叫 `queyi-audit`），避免"同名 + 旧身份版本"的检索关联。

### 3.4 操作步骤（只出方案，不执行）

```
Private 化（源仓库与过渡包各做一次）：
  1. 打开 https://github.com/LiaoRanran/<repo>/settings
  2. 页面拉到最底 "Danger Zone"
  3. 点 "Change repository visibility" → "Make private"
  4. 按提示输入仓库名确认
  5. 确认后：Settings 顶部应显示 "Private"；未登录状态下访问该 URL 应返回 404

投稿结束后（可选）：
  6. 同一入口 → "Change visibility" → "Make public"
  （注意：private 期间新增的提交在其间不可被外部引用）
```
