## 4. 与 673t / 673s 修复结果的对齐（任务 C 的"内容冲突以实际状态为准"）

### 4.1 `tool_integrity` 的"脏树绿 / 干净检出红"

673s 的判断（§3.1、§6.1）：`tool_integrity` 在**干净检出**上 exit=1，根因是 `evidence/`、`data/mutation` 的 Merkle 根与台账不匹配。
673q 的判断（§2.1）：`tool_integrity → exit 0`（**主仓脏树**口径）。

**673t 的修复结果**：commit `1072c605`（"让 Merkle 根与 tool_integrity 摆脱检出环境（CRLF 归一）"）。
根因是**与治理清单同一类**的口径 bug —— `leaf_hash` / `sha256_of` 哈希**工作区原始字节**，
而本机工作树有 659 个 CRLF 文件、CI/干净检出是 LF ⇒ 同一份提交内容在两处算出不同根，**两边都是真实机器，红得修不掉**。
修法：按 git 的文本/二进制分类，把文本文件 CRLF→LF 后再哈希。

**673u 复验**（干净检出 `git worktree add --detach 1072c605`）：

```
[tool_integrity] OK：5 个核心工具与基准一致
[tool_integrity] OK：信任根数据文件与基准一致（6 个已存在，警告 0 条）
[tool_integrity] OK：目录级 Merkle 根与当前内容一致（警告 0 条）
[tool_integrity] OK：判决尺子与基准一致（22 个）      # exit 0
```

⇒ **"脏树绿 / 干净检出红"的分裂不再成立**。两份文档的相关段落已按此更新（673q §2.1 加校订注；673s §3.1 加校订注 + §6.4 新增进展表）。

### 4.2 治理清单漂移 634 处

673s §6 未单列此项（当时只知"4 处 skip 无法解除"）。**673u 任务 A 修掉了它**（扫描面按 git 在册过滤 + 哈希按 `.gitattributes` 归一换行 + 重签 + 重钉），
漂移 **634 → 0**，且 manifest 逐条 == git blob（CI 必绿）。**4 处 `residue_present` 型 skip 全部解除**（第 4 处依赖 673t 的 Merkle 修复）。
