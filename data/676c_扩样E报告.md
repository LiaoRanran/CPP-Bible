## 3. 淘汰原因分析（含 TSan 不稳定影响）

**本轮淘汰 0 个，但开发期淘汰并修复了 16 个候选**，逐条记录（这是本批最有价值的部分）：

| 类别 | 样本 | 问题 | 处置 |
|---|---|---|---|
| **编排 bug（门闸变量写反/ 无人置位）** | E067 | `while(g_go.load())` 取反写反，worker 永久自旋 → 挂起是**假象** | 改为 `while(!g_go.load())`，重跑后 miss（真盲区） |
| | E138 | `main` 等 `step==1`，但没有任何线程置位 → 挂在 main 里，与 ABA 无关 | 补上 `step.store(1)`，重跑后 miss |
| **缺陷不成立（我写错了，不是检测器的问题）** | E088, E102 | 以为「持锁等条件变量」会死锁，但 `cv.wait` **本来就会释放那把锁** ⇒ 程序其实能正常收敛 | 改为「持第二把锁跨 wait」（锁泄漏型），死锁确定性成立 |
| | E104 | `unique_lock` unlock 后再 lock 只是活锁风险，不构成死锁 | 换为「`std::lock` 参数里漏掉已持有的锁」，确定性死锁 |
| | E109 | 异常展开会正常释放两把 RAII 锁 ⇒ 不死锁 | 改为「手动 `lock()` 无 RAII 兜底 ⇒ 异常路径永久泄漏锁」 |
| | E175, E178 | **谓词在锁内写时，notify 的先后顺序其实无关紧要**（等待者持锁检查谓词，通知方拿不到锁就发不出通知）⇒ 这两个程序本来是正确的 | 改为「谓词在**锁外**写」——这才是丢失唤醒的真正根因；重跑后 TSan catch |
| **缺陷存在但不可观测（结构性）** | E021, E037, E040 | 消费者把非原子载荷的读放在 `if(flag.load())` 分支里，标志通常为 false ⇒ 读根本没发生 | 改为无谓词自旋后再读，竞争真实成立 |
| | E035 | 同上，判据分支恒假 | 改为按完成计数自旋后读 |
| | E152 | `tail` 的 300000 次读在 `flush` 写之前就跑完了 | 让持锁线程持续写、读线程全程跨越；**并去掉 `(void)arr[i]`**——见下 |
| | E190, E196 | 读侧解锁后读非原子变量，但**写侧在同一把锁内**⇒ 通过 mutex 有 happens-before，不构成竞争 | 改为写侧确实在锁外 / 读侧在锁外跨越写者窗口 |
| | E115 | `delete dead` 写在 `a.join()` **之后**⇒ A 访问时对象还活着 | 把 delete 移进 ABA 窗口内，UAF 真实成立 |
| | E101–E110 系列中的 E110/E103 | 实测不是挂起，而是 glibc 抛 `std::system_error("Resource deadlock avoided")` 后 abort | 保留样本，改标 miss 并写明实测形态（见 §5） |
| **标注错误（机械性）** | 约 100 个 | 手写的 `defect_location.function` 与源码里的实际函数名漂移（写了 `shift_ptr`、代码里叫 `shifter`）；`thread_count` 与实际 `std::thread` 构造数不符（`std::thread a(f), b(g);` 只数出 1） | **改为从落盘后的源码自动推导** `function` 与 `thread_count`，不再采信手写值 |

**两个值得单独记下的「工具性教训」**：

1. **`(void)shared_array[i]` 会被编译器整体优化掉**，TSan/ASan 什么都看不到（E152 首版就是这么写的，
   读侧循环被 DCE 消除 ⇒ 报告 miss）。凡是「只读不存」的观测循环，必须把结果**累积到变量里**。
2. **release/acquire 会保护它之前的一切**。E011/E020 首版把「acquire 只约束原子载荷、不约束非原子镜像」
   当成缺陷，实测 TSan 正确地不报——因为 release 之前的非原子写确实被 acquire 覆盖了。
   真实的缺陷必须写成「release **之后**又改了非原子字段」。这两次是**我的标注错了，不是 TSan 漏报**。

**TSan 不稳定性的实际影响**：本轮 `detect()` 的 TSan 分支**没有出现一次 `unknown`**
（无 `FATAL: ThreadSanitizer`，`-O0`/`-O2` 两档全部编译成功），也没有出现「同一样本两档结论相反」。
复跑层面的非确定性只有 4 个样本（§6），全部是**缺陷本身的时序窗口**造成的，不是 TSan 抖动。
因此卡片「不要因为 TSan 漏报就淘汰样本」这条在本批**没有被触发**。

## 4. 盲区清单（哪些类型完全没有检测器）

按「现有三个 sanitizer 资产（tsan/asan/ubsan）+ 挂起观测」的实测覆盖：

| 缺陷类型 | 盲区率 | 盲区成因 |
|---|---|---|
| **lock_priority_inversion** | **76.7%（23/30）** | **完全没有检测器**。sanitizer 不看调度、不看优先级；「中优先级抢占低优先级持锁者」这一步在通用调度器上根本不会发生。7 个 catch 全部来自样本里**额外植入的真实数据竞争**（无锁快路径写共享缓冲），不是反转本身被检出 |
| **aba_problem** | **66.7%（20/30）** | **纯逻辑 ABA 完全不可见**。静态 arena 复用（地址必然回到原值、无 UAF）只表现为「可达节点数 ≠ 存活节点数」这种计数错误，sanitizer 无从判断。10 个 catch 全部是「ABA 恰好伴随 use-after-free」——即**ABA 只有在退化成 UAF 时才可见** |
| **atomic_ub** | **57.1%（20/35）** | 分三类：① UBSan **不插桩 atomic RMW** ⇒ E048/E049/E050/E066 有符号原子溢出（C++17 是 UB）全部无报告；② 原子变量**未初始化**是 UB 但没有任何 sanitizer 为「原子的不确定初值」设陷阱（E041/E042/E043）；③ 逻辑类误用（CAS 失败不检查 expected、load+store 丢更新、exchange 返回值被忽略）根本没有运行时表现 |
| **memory_order** | **55.0%（22/40）** | TSan **只检查竞争、不建模内存序**。全 atomic 的内存序错误（relaxed 轮询标志、seq_cst 写配 relaxed 读、consume 误用、fence 位置错误、发布链被 relaxed 打断）在 C++ 内存模型下是 UB，但**没有竞争就没有报告**。x86-TSO 上这些缺陷通常也不显现 |
| **condition_variable** | **50.0%（15/30）** | 虚假唤醒、边沿谓词被当电平、wait_for 超时未检查谓词——这些是**语义错误**，程序正常结束、状态错了，sanitizer 无从下手。3 例通知丢失表现为**永久挂起**，靠超时才观测到 |
| **deadlock** | **5.7%（2/35）** | 唯一「几乎全覆盖」的类型，但覆盖形态很特殊，见 §5 |

**一条额外发现的盲区（新类别，卡片未列）**：
**E110 / E103 这类「让进程直接崩溃的并发缺陷」对三个 sanitizer 完全隐形。**
`condition_variable_any` 配 `recursive_mutex`、以及已持有 `unique_lock` 时再 `lock()`，
在 WSL glibc 2.39 上都由 libstdc++ 抛 `std::system_error("Resource deadlock avoided")`（EDEADLK）并
`abort()`（rc=6）——**它们既不挂起也不产生任何 sanitizer 报告**。
这类缺陷比 miss 更值得警惕：程序当场崩掉，而整个检测器流水线给出的标签是「干净」。

## 5. 死锁样本的触发率统计

死锁类 35 个样本，**每个复跑 3 轮**（共 105 轮次）：

| 指标 | 数值 |
|---|---|
| 每轮触发率（catch 轮次 / 总轮次） | **99/105 = 94.3%** |
| 3/3 全部触发的样本 | **33/35（94.3%）** |
| 3 轮都稳定触发（无抖动）的样本 | 33 |
| 未触发：E103、E110 | 0/3，**确定性失败**（EDEADLK abort，非挂起）——已单列为盲区 |
| 触发形态：运行超时（rc=124，两档都挂） | **31/35** |
| 触发形态：TSan 自己报 `lock-order-inversion` | **2/35（E087、E107）** |

**这里有一个必须写清的事实**：TSan **确实带死锁检测器**（`lock-order-inversion (potential deadlock)`，
本轮实测命中 2 例，rc=66），但它**只在自己观察到了完整的锁序环时才报**。
35 个确定性死锁样本里它只报了 2 个（5.7%），其余 29 个是靠**「程序挂起 + 6 秒超时」**判定的。
换句话说：**死锁检测能力在 TSan 上存在，但触发条件苛刻；工程上更可靠的做法仍是超时/心跳检测。**

设计上，全部 35 个死锁样本都用**原子门闸**（`held` / `first_held` / `producer_ready` 计数）
保证两线程各自先拿到第一把锁后才去抢第二把，把「概率性死锁」变成「确定性死锁」。
这也是触发率能到 94.3% 的原因——不是运气好，是编排出来的。

条件变量类另有 3 例（E176、E191、E198）因通知丢失而永久挂起，占该类 10%。

## 7. 质量抽检结果

卡片要求「固定种子抽 20%」。本批做了**两层**：

**(a) 机械化标注一致性审计 —— 覆盖 100%（比 20% 更严）**

| 检查项 | 说明 |
|---|---|
| 必填字段齐全 | 11 个必填字段全部存在 |
| `defect_location.line` 真的指向 `/*DEFECT` 行 | 逐行回读比对 |
| `defect_location.function` 出现在源码中 | 见下方说明 |
| `thread_count` == 实际 `std::thread` 构造数 | 按语句切分后数顶层逗号分隔的声明器 |
| `severity ∈ {low, medium, high}` | — |
| `planted == true` | — |
| `timeout_seconds > 0` | — |
| 编译 rc == 0 | — |
| `expected_detectors` 非空 | — |
| 死锁类可触发 | 挂起 / lock-order-inversion / 异常终止（rc=6/11）三者之一 |

**结果：200/200 全部通过，不合格率 0.0%。**

> 首轮审计曾报出 **103 个不合格（51.5%）**，全部是标注机械性问题——手写的 `function` 名与源码漂移、
> `thread_count` 与实际线程数不符。**没有靠人工逐个去改**，而是把生成器改成**从落盘后的源码自动推导**
> 这两个字段（`_defect_function()` 从 DEFECT 行向上找最近的外层函数定义；`_thread_count()` 按语句数声明器），
> 一次性根除。理由：手写标注在 200 个样本上必然漂移，标注必须从**最终文本**里读出来，而不是从人的记忆里。

**(b) 人工级抽检 —— seed=6761，20% = 40 个**

逐条核对四项：并发缺陷是否真实存在 / 线程同步是否正确（或故意错误）/ 死锁是否能稳定触发 / 标注是否准确。

**结果：40 个抽检样本中，复跑判定不确定的 1 个（E022，2.5%）**，远低于卡片 10% 的阈值，
因此**不需要把抽检比例提高到 50%**。

需要说明的是，「缺陷是否真实存在」这一项在本次执行中**不是靠抽检保证的，而是靠 100% 审计 + §3 的
16 例修复**：开发期对全部 200 个样本逐条读过源码，编排 bug 与「缺陷不成立」是在这个过程中被发现的
（典型如 E175/E178——我以为「notify 早于置位」会丢失唤醒，实测发现谓词在锁内写时 notify 顺序无关紧要，
这两个程序本来是对的）。抽检在这个阶段起的作用是**复核判定稳定性**，而不是第一次发现缺陷。

## 8. 入池样本清单

- 目录：`data/holdout_expansion/expE/`，共 **401 个文件** = 200 × `.cpp` + 200 × `.json` + `INDEX.json`
- 逐样本清单见 `data/holdout_expansion/expE/INDEX.json` 的 `samples` 数组（含每例的
  `defect_type` / `defect_location` / `severity` / `planted` / `expected_verdict` /
  `original_expected_verdict` / `expected_detectors` / `pooled_verdict` / `hung` / `reconcile`）

**入池 JSON 的口径**：`expected_verdict` 一律写**实测判定**，原预测保留在
`verification.original_expected_verdict`，调和过程保留在 `verification.reconcile`，
检测器原始输出保留在 `verification.detector_note`，逐轮复跑结果保留在
`verification.stability` / `verification.flakiness`，`raw_rc` 保留原始退出码
（124 = 超时挂起，66 = TSan 报告，6 = SIGABRT，11 = SIGSEGV）。
这样「标注」与「检测器输出」永远自洽，且完整可追溯——不会出现「标注说 catch、实测是 miss」这种
读者无法判断谁对的记录。

**调和结果**（`reconcile` 分布）：

| 调和类型 | 数量 | 含义 |
|---|---|---|
| `consistent` | 79 | 标注与实测一致（catch） |
| `consistent_blindspot` | 98 | 标注与实测一致（miss，真实盲区） |
| `updated_to_catch` | 19 | 原预期 miss，实测被捕获 → 按卡片更新标注为 catch |
| `downgraded_to_miss_real_blindspot` | 4 | 原预期 catch，实测未报告 → 按卡片「真实盲区：改标 miss」处理 |

**标注与实测总一致率 88.5%**（177/200）。19 例升级里有 12 例是 atomic_ub——
它们的标注只考虑了「原子误用」这一层缺陷，漏掉了源码里**同时存在**的非原子共享状态竞争
（例如 E053/E054/E056/E064/E070 的计数字段是普通 int，TSan 抓的是这个竞争）。
4 例降级全部在 `notes` 里写明了「这是检测器盲区，不代表缺陷不成立」。

## 9. 环境偏差（WSL / TSan 限制）

**关于运行超时这一处 harness 适配，需要明确交代**（因为它触及卡片「检测器零修改」的红线）：

`tools/holdout_reveal_661.py` **文件本身一个字节都没有改**。适配全部发生在**运行时**，
包在 `verify_E.py` 里的 `hr._wsl` 包装函数中，只有两处，且都**不改变判定语义**：

1. **exe 名去冲突**：检测器固定用 `/tmp/rv_bin_O0` / `/tmp/rv_bin_O2`，并发跑多个样本会互相覆盖二进制。
   按 worker 把 `/tmp/rv_bin_` 重写为 `/tmp/rv_bin_<tag>_`——**只改文件名，不改编译参数、不改命中判据**。
   （若不重写就只能串行跑，验证时间从 ~2 分钟涨到 ~2 小时。）
2. **运行超时**：给**运行命令**（以 `setarch` 或 `/tmp/rv_bin_` 开头）加 `timeout 6`，
   编译命令不加。`rc=124` 被单独识别为「程序挂起」，按卡片「死锁样本超时挂起：视为 catch」处理。
   这是卡片**自己要求**的（§环境注意事项 5），不改的话验证流程会永久卡死。

`hr.ATOMS` 指向 `data/expansion_676c_E` 是卡片 §任务C 步骤 1 明确授权的 monkeypatch。
`detect()` 内部的命中判据（TSan 看 `WARNING: ThreadSanitizer` / `data race` / `rc==66`；
ASan 看 `AddressSanitizer` / `LeakSanitizer`；UBSan 看 `runtime error`）**一字未动**。

## 10. 局限性

1. **x86-TSO 掩盖了大部分内存序缺陷**。本批 40 个 memory_order 样本在 x86 上即使编译成
   `-march=native` 也基本不会真的读到脏数据（22 个 miss 里绝大多数属于这一类）。
   这些样本能测的是「**检测器能不能发现内存序错误**」（答案：不能），不能测「内存序错误会不会出事」
   （在 ARM/POWER 上答案会不一样）。要真正复现需要异构硬件或 litmus-test 工具（如 herd7），本次不具备。
2. **优先级反转无法在通用调度器上复现**。30 个 lock_priority_inversion 样本建模的是**代码形态**
   （低优先级持锁做耗时/阻塞操作 + 高优先级等锁 + 中优先级抢占），
   「中优先级抢占低优先级持锁者」这一步在 Linux CFS 下不会真的发生。
   这批样本的 23/30 miss 反映的是**工具缺口**，不是「反转不严重」。
3. **ABA 样本一半靠 allocator 行为**。用 `new/delete` 的 10 例依赖 glibc malloc 复用同一地址；
   若换成不立即复用的分配器，这些会从「ABA（miss）」变成「UAF（ASan catch）」。本次已用
   静态 arena 路线把 20 例做成与分配器无关的确定性 ABA。
4. **死锁判定依赖超时**。6 秒阈值对「本应很快返回」的程序足够，但对真实工程里
   「卡了 6 秒 vs 卡了 60 秒」无法区分；本批靠门闸编排让死锁变成确定性的，规避了阈值敏感性。
5. **单平台单编译器**。全部在 WSL g++ 13.3 / libstdc++ 上测。
   `condition_variable_any` 配 `recursive_mutex` 的行为（EDEADLK abort）是 **glibc 特有**的，
   在 MSVC 上可能是挂起。E103/E110 的实测形态不可跨平台移植。
6. **卡片列出的部分变体未能覆盖**：C++20 的 `atomic::wait/notify_one`（编译标准是 `-std=c++17`，
   无法编译）、`memory_order_consume` 的完整语义（只做了误用形态）、
   无锁队列的 Michael-Scott 正确实现对照（未加对照组）。
7. **severity 分布偏斜**：188/200 为 high。因为并发高级缺陷本身多为「静默错误或永久挂起」，
   按「是否可被察觉」分级时几乎都落在 high/low 两端。medium/low 样本偏少，
   若后续要做严重度分层实验，这一层的样本量不足。
8. **`resource_leak` 类未纳入**：卡片未要求，且与扩样-A 的 `resource_leak` 池重叠。

## 附：给后续批次的可复用结论

1. **并发缺陷的检测器缺口与内存错误完全不同**。内存错误（越界/UAF/泄漏）已被 asan/ubsan 覆盖得相当好；
   而内存序、ABA、优先级反转、原子 RMW 溢出这四类，**现有 sanitizer 资产基本为零**。
   论文若要讲「验证器的边界」，这批数据比再加内存错误样本更有说服力。
2. **「程序挂起」是一个真实可用的判定信号**，但它必须由 harness 显式实现（超时 + 归一化 rc）。
   TSan 自带的 lock-order-inversion 在本批 35 个确定性死锁里只报了 2 个。
3. **三态→四态框架在这里有了一个具体用例**：E110/E103 这种「进程崩溃但所有 sanitizer 都干净」的情况，
   既不是 pass 也不是 fail 的传统二分，而应该进 `contradict` 或独立的 `unknown`——
   「检测器无能力」与「检测器说没问题」是两件不同的事，混淆它们会让检出率虚高。
4. **样本生成必须让标注从最终文本推导**。200 个样本里手写标注漂了 100 个；
   改成 `_defect_function()` / `_thread_count()` 自动推导后，不合格率从 51.5% 降到 0%。
