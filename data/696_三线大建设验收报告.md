**两处 harness 层面的真实障碍（均已定位并修复，判据一字未改）**：

**① 终端注入的 `PYTHONPATH` shim 让两个有状态门禁假红。** 本机 WorkBuddy 终端把
`PYTHONPATH` 指向其沙箱 shim 目录（`…\cli\vendor\shim`），该 shim 的 `sitecustomize.py`
在 `Path.unlink()` 上装了 bulk-delete 守卫，累积到阈值即 `raise SystemExit(1)`：

```
sitecustomize.py … _safe_path_unlink → _try_trash → _check_bulk_delete_guard
    → _exit_bulk_guard_control → raise SystemExit(1)
```

表现为 `Evidence Replay` / `Poison Drill` 两个**有状态**门禁随机红（同一份代码同一时刻，
直跑 27/27 全绿、再跑 25/2）。**这是终端环境副作用，不是仓库缺陷**（CI/Ubuntu 与普通
shell 无此 shim）。验证与处置：

```bash
env -u PYTHONPATH .venv/Scripts/python.exe tools/poison_drill.py            # exit 0
env -u PYTHONPATH .venv/Scripts/python.exe tools/atom_evidence_replay.py --check   # exit 0
```

⇒ 本批正式门禁与 push **在剥离该 shim 的干净环境下执行**。

**② `prepush_check.py` 的单检查超时 600 s 小于 `quality` 阶段的真实耗时。** 实测
`tools/cppbible.py check --stage quality`（27 个门禁）在本机需 **484–798 s**（随并发负载
波动），原硬编码 `timeout=600` ⇒ 机器稍忙即**恒因超时失败**，且失败与门禁是否达标无关。
这与本文件 648 记录的 `timeout=15 ⇒ pre-push 恒假失败` 是**同一类 harness 缺陷**。处置：
把单检查超时提到 **1800 s**（可用 `PREPUSH_TIMEOUT_S` 覆盖），**没有放宽任何一条判据**：

```python
CHECK_TIMEOUT_S = int(os.environ.get("PREPUSH_TIMEOUT_S", "1800"))
...
subprocess.run(exe, ..., timeout=CHECK_TIMEOUT_S)   # 原：timeout=600
```

> 该改动落在 `tools/prepush_check.py`，**不在** `tools/tool_integrity.py` 的哈希面
> （CORE_TOOLS = gate_engine / atom_evidence_replay / poison_drill / toolchain / cppbible），
> 故不会连带触发 Tool Integrity 红。
