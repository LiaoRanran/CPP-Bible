## 1. 缺陷确认（修复前实测）

### 1.1 缺陷位置

`tools/verify_paper_numbers.py::check_dependencies()`（修复前第 330–346 行）：

```python
res = {}
for name, files in DEPENDENCY_FILES.items():
    entry = {}
    ready = False
    for rel, need in files:
        ...
        ok = n is not None and n >= need
        ready = ready or ok          # ← 缺陷：组内任一文件满足即整组 ready
        entry[rel] = {"n": n, "need": need, "ready": ok}
    res[name] = {"files": entry, "ready": ready}
```

### 1.2 缺陷后果（实测数据，2026-10-10）

声明的依赖（`DEPENDENCY_FILES`）：

| 组 | 文件 | 需要 | 实测 | 单文件 ready |
|---|---|---|---|---|
| 676f | `data/a5_676f_results.json` | ≥1 | 1 | True |
| 676f | `data/a5_676f_matrix_local.jsonl` | ≥1147 | **673** | False |
| 676f | `data/a5_676f_matrix_san.jsonl` | ≥1147 | **1054** | False |
| 676g | `data/blindspot_676g_stats.json` | ≥1 | 1 | True |
| 676g | `data/blindspot_676g_ckpt_san.jsonl` | ≥3126 | **文件不存在（None）** | False |

修复前 `data/676h_number_audit.json` 的组级输出：

```json
"676f": { "files": {...}, "ready": true },   // 3 个里只满足 1 个，却 ready=true
"676g": { "files": {...}, "ready": true }    // 2 个里只满足 1 个（另一个文件不存在），却 ready=true
```

**与评审描述完全一致**：676f 组矩阵文件分别只有 673/1147、1054/1147 仍标记就绪；676g 组检查点矩阵根本不存在仍标记就绪。

### 1.3 为什么这是元验证问题

审计器是「判断材料是否可信」的工具。它自己的就绪判定用 `or`，意味着：

- 一个都不缺 → ready
- 缺 1 个 → ready
- 缺 2 个只留 1 个 → **仍然 ready**
- 只有全部缺失（0/3）才会是 False

即该字段的实际语义是「组内**存在**一个已满足的文件」，而报告里把它渲染成「依赖就绪状态」。任何读这份报告的人（包括作者自己）都会被误导。**验证工具自身的逻辑漏洞会让不完整材料通过检查**，这正是评审点名的元验证风险。

## 2. 修复方案

### 2.1 严格合取 + 三态表示

新增纯函数 `aggregate_dep_state(entry)`，与磁盘 I/O 解耦，便于单元测试：

```python
def aggregate_dep_state(entry: dict) -> dict:
    # 逐文件判定，统计满足数
    ready = n_total > 0 and n_ready == n_total       # 严格 AND
    state = "ready" if ready else ("partial" if n_ready > 0 else "not_ready")
    return {"ready": ..., "state": state, "n_ready": ..., "n_total": ...,
            "missing": [...], "short": [(rel, n, need), ...]}
```

三态语义（**部分就绪不再与完全就绪混为一谈**）：

| state | 含义 | ready |
|---|---|---|
| `ready` | 全部必需文件均满足 | True |
| `partial` | 至少 1 个满足，但存在缺失/不足项 | False |
| `not_ready` | 一个都没满足（含全缺） | False |

边界：`n == need` 视为满足（`>=` 语义，与修复前一致）；`n = need - 1` 不视为满足；**空声明组不得为 ready**（避免 0 个文件"全部满足"的伪真）。

### 2.2 报告渲染同步改造

`data/676h_number_audit_report.md` §3 由「一个布尔」改为：

1. 组状态表：`state` + `ready` + `n_ready/n_total`
2. 逐文件表（保留，未放宽）
3. 缺失清单 / 数量不足清单（自动列出具体文件与 `(实测<需求)`）

### 2.3 新增：权威重算源（不顶绿）

修复后两组都诚实显示 `partial`。但这里必须区分两件事：

- 「声明依赖未达成」——这两个 `.jsonl` 是检测过程中的**流式导出**，历史上就从未达到声明规模（676g 的 `ckpt_san` 根本没生成过）。
- 「关键数字不可重算」——**这两件事不是一回事**。真正供陌生研究者重算的完整产物是：

| 组 | 权威重算源 | 样本数 | 论文对应 |
|---|---|---|---|
| 676f | `data/a5_676f_detection_matrix.json` | **1137** | 论文中 1137/1147 脚注的来处 |
| 676g | `data/blindspot_676g_detection_matrix.json` | **1147** | 能力边界地图全量 |

**处理原则（关键）**：没有把这两个 JSON 塞进 `DEPENDENCY_FILES` 去"顶绿"——那正是最容易被做的手脚，会把缺失的 `.jsonl` 换成完整的 `.json`，让 `partial` 变回 `ready`。做法是**另立一张表**（`RECOMPUTE_SOURCES` + `check_recompute_sources()` + 报告 §3b），与声明依赖**并列、不互相替代**，并在测试里钉死"重算源不得出现在声明依赖里"。
