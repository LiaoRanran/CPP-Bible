# 639 D8 · data/638 文件丢失根因分析

> 生成：2026-09-25。结论：**已复现、已定位、非数据损坏**。

## 一、现象（638 诚实登记）

638 批次期间，`data/638_rr_conflict_analysis.md/.json` 等刚生成的产物在随后的
pytest 运行后**消失**（`Get-ChildItem data -Filter 638*` 为空），当时归因不明。

## 二、根因（代码级 + 实证复现）

**机制**：根级 `conftest.py`（634 A1「生产 data/ 写隔离」）注册了
**session 级 autouse fixture**：

1. pytest 会话**开始**：快照 `data/` 全部文件字节（`_snapshot()`）；
2. 会话**结束**：`_restore()` 两步——
   - **删除所有「快照里没有」的文件**（= 会话期间新建的，含未跟踪）；
   - 还原「快照里有但被改动」的文件。

⇒ 任何**在 pytest 会话存活期间新建**的 `data/` 文件，会话结束时被无差别删除。

**639 实证复现**（2026-09-25）：

```
探针 tests/test_639_probe_loss.py：会话期间写 data/639_probe_loss_canary.txt
pytest 输出：[634 A1] 生产 data/ 写隔离：还原被改 0 个、删除新建 1 个
探针文件 after：False（已被删除）
```

**638 事故还原**：638 批次中「生成报告」与「pytest」交错执行——产物在某个
**已开跑的 pytest 会话期间**落盘（或由测试内调用 `write_report()` 落盘），
会话结束即被清理器删除。638 当时记录的「文件被删」与该机制完全吻合。

## 三、定性

- **不是**磁盘/数据损坏，不是 git 操作，是**设计行为的副作用**：
  634 A1 的目标是「pytest 对 data/ 净 0 改动」，其代价是把
  「会话期间人为/工具落盘的新文件」也视为测试残留。
- 634 A1 的**隔离目标本身是对的**（防测试污染生产 data/）。

## 四、防复发建议（交人/留 640）

1. **流程**：生成 data/ 报告前确认无 pytest 会话在跑（或先跑完再生成）；
2. **机制**：conftest 清理器加**豁免名单**（如 `639_*`/`*_report.md` 的
   会话期新建不删）——需改 conftest 并重钉相关哈希，留 640；
3. **提示**：会话删除 >0 个文件时在 pytest 输出**列明文件名**（现只报数量，
   638 正因只见数量未见名单而难排查）；
4. **测试侧**：测试不得调用生产 `write_report()`（634 A1 已登记的根因之一），
   一律写 `tmp_path`。
