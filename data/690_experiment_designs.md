## 1. 人类独立标注（E1-D）· 优先级最高，**今天就启动**

> **这是唯一一个 Agent 无法完成、且是全项目唯一致命意见（T17）的实验。** 它放在第一位不是因为它最容易，而是因为它**工期最长且依赖外部人力**——晚一天启动，就晚一天解除对所有其他结论的封锁。

### 1.1 689 已有的部分

`data/689_human_annotation_protocol.md` + `data/annotation_package/`（方案 + 材料包 + 统计预案，状态 = 待执行）。

### 1.2 690 必须补强的三点

| # | 补强要求 | 理由 |
|---|---|---|
| **S1** | **抽样必须按类分层，且长尾类明确登记为"未取得人类验证"** | 35 类中 `logic_error` n=3、`data_race` n=4、`interrupt_safety` n=4、`atomics/bit_operation/cross_tu_ub/endianness/register_ub` n=5 —— **每类 >=5 在多数类上不可行**，不能假装能做 |
| **S2** | **必须同时算"人类 vs AI"的 kappa，而不只是"人类 vs 人类"的 kappa** | 后者只说明人类之间一致；**前者才是 AI 标注的效度检验**，也才是评审 R1-05 真正问的东西 |
| **S3** | **必须报告 kappa_expected_verdict（现 0.437）与 kappa_severity（现 0.157）的人类对照值** | 这两个是 AI 自一致的值。**若人类的 kappa 也低**，说明是该维度本身难（如 severity 主观性高），不是 AI 的问题——**这个区分只有拿到人类数据才做得出来** |

### 1.3 完整设计

**假设**

- **H1（信度）**：在 top-8 缺陷类型上，人类第二标注者与第一标注者的 Cohen's kappa >= 0.6。
- **H2（效度）**：人类标注与 682 的 AI 流水线的 kappa >= 0.5（即 AI 标注在语义类型上**大体**可用）。
- **H3（severity 反直觉预测）**：人类在 `severity` 上的 kappa 也**低**（<0.4）——若成立，则 kappa=0.157 应归因于**该维度的主观性**，而非 AI 流水线的能力上限。

> H3 是本设计的一个**真正有价值的判别性预测**：它把"AI 标注差"与"severity 本身难"两种解释分开。若不做这个实验，我们只能承认 kappa=0.157 而无法解释它。

**方法**

1. **抽样**：从 `data/blindspot_676g_detection_matrix.json` 对应的 1137 条中分层抽取——
   - **top-8 类各 20-25 条**：`memory_safety`、`out_of_bounds`、`memory_leak`、`string_ub`、`other_ub`、`integer_overflow`、`data_race`、`move_semantics`；
   - **逻辑/并发类全量**：`logic_error`(n=3) + `data_race`(n=10) + `deadlock`(n=4) + `memory_order`(n=15) 全部纳入（这类是"检测范式边界"的核心，n 小但意义大）；
   - **severity 专项**：额外抽 60 条做 severity 三分类（high/medium/low），因为这是 n=262 上 kappa=0.157 的维度；
   - 合计 **n ~ 250-290**（主层）+ 60（severity 层，可重叠）。
2. **标注规程**：
   - 标注者拿到**去标识**样本（不含 AI 判定、不含第一标注结果）；
   - 提供**类型定义表**（681 归一化后的 34 类词表）+ 边界案例集；
   - 标注者独立完成，**不与 AI 流水线交互**（避免锚定）；
   - 每条附**必填的置信度**（1-5）与**不确定时的理由**（据此可算弃权率）。
3. **第三裁决**：kappa<0.6 的类进入第三裁决（第三标注者或作者本人仲裁），并记录裁决理由。
4. **统计**：Cohen's kappa（主层两两）+ Krippendorff's alpha（三类及以上，severity 层）+ 弃权率 + **人类 vs AI 的 kappa**（H2）。

**数据**

- 输入：`data/blindspot_676g_detection_matrix.json`（冻结矩阵，只读）、`data/681_type_stats_normalized.json`（34 类词表权威口径）、`data/682_kappa.json`（AI 侧对照）
- 产出：`data/691_human_iaa.json` + `data/691_human_iaa_report.md` + **去标识标注包**（可公开发布，供第三方复核）

**预期结果**

- top-8 类人类 kappa 落在 [0.6, 0.85]（文献经验区间）；
- 人类 vs AI kappa 低于人类 vs 人类 kappa，**但不低于 0.5**；
- severity 人类 kappa < 0.4（支持 H3）；
- `expected_verdict` 的人类 kappa **高**（因为它可由编译/运行裁决，不依赖人判断直觉）。

**判定标准**

| 结果 | 判定 | 后续动作 |
|---|---|---|
| top-8 人类 kappa >=0.6 **且** 人类 vs AI kappa >=0.5 | T17 可闭合 | 标签轴升级为"人类验证的分类学"，全部结论解锁 |
| 人类 kappa >=0.6 **但** 人类 vs AI kappa <0.5 | 部分闭合 | 结论方向保留（686 已证 15% 标签翻转不致方向反转），但**绝对率需下调置信**；AI 标注降级为"索引" |
| top-8 人类 kappa <0.6 | 未闭合 | **把缺陷类型轴从"效度标签"彻底降级为"分类学索引"**，所有按类型的分解（F2 的家族/类型结构）标注为"探索性" |
| H3 不成立（人类 severity kappa >=0.6） | 反面结果 | **AI 在 severity 上确实失效**（kappa=0.157 是 AI 的问题）→ 688 的 by-severity 分析必须撤回 |

**失败应对**

- **找不到第二标注者**（最可能的失败）：**降级方案**——用"两名不同 prompt 策略的独立 AI 标注者 + 强制引用源码证据"替代人类，但这**只能测 AI 内部一致性，不能测效度**，因此 T17 **仍视为开放**，并在 Limitations 明确写"我们无法在本轮提供人类 IAA"。**绝不用 kappa=0.727 冒充 IAA。**
- **样本量不足**：优先保 top-8 类，长尾类明确登记为未验证（不做全类覆盖的虚假宣称）。

## 2. 环境感知协议实验（E1-E）· 从观察升级为因果实验

### 2.1 689 已有的部分

`data/689_environment_experiment_design.md`（Part 1 实测复算 + Part 2 aware vs unaware 方案，标"待执行"）；`689_environment_metrics.json/_report.md`（三组件指标已算）。

### 2.2 现有证据为什么**不能**支撑因果主张

`689_environment_metrics_report.md` 第 2 节已自陈：native 一档是**架构/口径推断，非本机实测**。且整体换环境（WSL -> Windows native）时，以下因子**同时改变**：

1. 编译器身份（g++ 13.3 -> MinGW g++ 13.1）
2. **sanitizer 可用性**（asan/ubsan/tsan 全部不可用）——注意这是**捆绑**的
3. OS 内核与路径语义
4. ASLR / 熵设置（TSan 敏感）
5. 可执行文件加载路径与 DLL 解析

**因此 R2-11 的追问（"怎么排除混淆变量"）完全正确，且当前证据无法回答。**

### 2.3 690 补强的核心：把"环境"拆成**可独立操纵的正交因子**

### 2.4 完整设计

**假设**

- **H1（因子可分离）**：跨环境的 -35.45pp 差距中，可归因于 **sanitizer 可用性**的份额 >=50%（因为该因子一次性移除了 3 个主力资产）。
- **H2（编译身份效应小）**：在 sanitizer 可用的条件下，换编译器身份（g++ <-> clang）的效应 <=2pp（**683 已实测 93.5% 一致、Delta<=2pp，此处为复现性检验**）。
- **H3（静默退化是普遍的）**：`unknown` 率不上升而 recall 下降这一现象，在**至少两个独立环境对照**中都能复现（而不仅是 WSL->native 一例）。

**方法：>=2x2 因子设计 + 因子内随机化**

| 因子 | 水平 | 操纵方式 | 可行性 |
|---|---|---|---|
| **F1 sanitizer 可用性** | {on, off} | `-fsanitize=address` 开/关 | 完全可操纵 |
| **F2 编译器身份** | {g++ 13.3, clang 18.1.3} | 同一 flag 集合（两者共同支持） | 已验证可跑（683） |
| **F3 优化级别** | {-O0, -O2} | 已有的双档口径 | 已验证 |
| **F4 编译警告集** | {默认, +Wunsequenced 等} | MinGW **不支持** `-Wunsequenced`（已登记） | 部分不可分离 |

**设计骨架**（最小可执行版）：

```
                F2=g++13.3        F2=clang18
F1=on, F3=-O0      A                  B
F1=on, F3=-O2      C                  D
F1=off, F3=-O0     E                  F
F1=off, F3=-O2     G                  H
```

- **样本**：从 110 真实靶场中取**可被两编译器共同编译**的子集（预计 n=85-95，剔除依赖特定扩展的样本），**固定子集后不再变动**；
- **随机化**：每个样本在每个 cell 内的**编译顺序随机化**（预声明 seed 6891，与 689 保持一致），防止顺序效应（缓存升温、磁盘状态）；
- **预声明**：8 个 cell 的主效应与交互项的估计量、检验方法、多重比较校正（Holm）**在跑之前写死**；
- **重复**：每 cell 3 次重复（探测器的偶然性），报 cell 内方差。

**关键设计点：F1 = off 时必须记录 unknown 还是 miss。**

这是**整个实验的核心**：现有口径规定"检测器不可用 = unknown，绝不 = miss"（`683_algorithm_positioning.md`）。因此 F1=off 时的正确记法是**该样本在该资产上 unknown**，OR 聚合后样本级 unknown 应上升——**而 689 报告的 Windows native 档恰恰出现了 unknown Delta=0.00pp**（"静默退化"）。

**这构成一个必须解决的不一致**：要么 (a) 那档 native 数据本身记错了（把不可用记成了 miss），要么 (b) "静默退化"是真实的记账现象。**691 的第一件事就是查清这一点**，因为它决定 F3 的结论是否存在。

**数据**

- 输入：`data/683_real_world_benchmark.json`（110 条 PoC，`poc_sha256` 可锚定）
- 产出：`data/691_environment_factorial.json` + `_report.md` + 环境指纹规范草案

**预期结果**

| 因子 | 预期主效应 | 依据 |
|---|---|---|
| F1 sanitizer | **-30pp 以上**（主导） | 一次移除 3 个资产；native 档实测 -35.45pp |
| F2 编译器 | <=2pp | 683 实测 Delta<=2pp |
| F3 -O0/-O2 | 小但非零（-2~-5pp） | 已有双档口径 |
| F1xF3 交互 | 可能显著（-O2 下 sanitizer 收益更大） | 未测，属新知识 |
| F4 | **不可分离**（MinGW 缺 flag） | 已登记 |

**判定标准**

- **H1 成立**（sanitizer 份额 >=50%）=> 可以写"环境作为一等公民"是一个**因果性**主张，而不只是观察；
- **H1 不成立**（各因子份额均 <30%）=> 降级为"环境是多因素复合体，任一单因子都不足以解释"，**不得**写因果语言；
- **F1/F4 因 MinGW 限制不可分离** => 用"可分离子集设计"，并**明确报告哪部分不可分离及原因**。

**失败应对**

- **若 native 一侧无法实测**（本机无 native sanitizer 环境）：**缩小设计为 F2xF3 的 2x2**（全在 WSL 内，全部可测），牺牲 H1 但保住可执行性。**这是推荐的默认方案**——因为 F1 的操纵实际等价于"换 OS"，成本极高。
- **若样本子集不足 n=60**：报 n 与功效，不放宽"不可分离"的判定。

## 3. 公平外部对比（E1-G）· 风险最高的一项

### 3.1 689 已有的部分

`data/689_fair_comparison_protocol.md`（公平性 8 条）+ `data/689_svcomp_positioning.md`。

### 3.2 690 补强：SV-COMP 口径必须写清三点差异

评审 R1-11 指出 SV-COMP 定位不清。**差异必须落到三个可核对的维度**，否则"59.09%"会被误读为与 SV-COMP 的 verified/confirmed 分数同量纲：

| 维度 | 我们 | SV-COMP |
|---|---|---|
| **分母** | 8 资产 **OR 聚合**的样本级检出 | **每 benchmark 单一工具义务**（每个工具对自己的义务负责） |
| **代码来源** | source-derived 单文件重构 | **原始项目版本 + 官方修复 commit** |
| **成功判据** | 编译/运行时是否产生 sanitizer 报告 | 形式化验证工具的证明义务（correct / incorrect / unknown 三分） |

**并在正文写明"我们的 59.09% 不可与 SV-COMP 分数比较"**，而不是只说"我们与 SV-COMP 不同"。

### 3.3 完整设计

**假设**

- **H1（诚实预期）**：在**可获得**的外部工具中，至少存在一个在我们的矩阵上检出率**高于**我们的 OR 组合（因为组合 8 个资产通常强于单工具——**我们预期这一条不成立，即我们更强**）。
- **H2（真实价值轴）**：即使在检出率轴上我们不占优，我们在**可审计性轴**上占优——即对"某条判定是在什么环境下、由哪些证据产生的"的**可追溯率**显著高于外部工具。

> **H2 才是这个实验真正要测的东西。** 若只测检出率，我们很可能赢得一个没意义的比较（因为我们有 8 个资产的 OR），而输掉一个重要的比较（因为别人是单一成熟工具）。**把主问题设为 H2，是这个实验不变成"自我表扬"的关键。**

**方法**

1. **候选外部系统（须先核实可获得性）**：
   - `cppcheck`（静态分析）；
   - `clang-tidy`（**注意：它已在 683 作为 cross-compile 臂出现，因此不算"外部"**，只能算既有资产）；
   - `scan-build` / `clang --analyze`（同源，需声明）；
   - **一个 LLM judge**（呼应 E1-F 与 E2-B）；
   - **一个真正的动态分析工具**（若可获得）。
   > **可获得性风险**：MSVC 缺失、MinGW clang **缺 `libclang_rt.asan_dynamic`** => sanitizer 类外部工具在本机基本不可用。**因此候选清单必须在设计阶段先跑一遍"能不能装、能不能跑"的核实**，不能先写名单后才发现做不了。
2. **统一环境**：同一编译器、同一 flag 集、同一 `-O` 双档、同一 110 条（真实）+ 1137（合成）矩阵，**全部 8 资产臂与外部工具在同一批次跑**。
3. **预声明配置**：每个外部工具的**命令行参数、启用检查集、版本号**在跑之前写死并提交（`data/691_fair_comparison_prereg.json`）。**理由**：外部工具默认配置通常调优到最好用；事后调参再比较是不公平的。
4. **计分口径统一**：
   - 三态判定（catch / miss / unknown）**逐样本**给出；
   - **unknown 一律不计 catch**（与我们的口径一致）；
   - 报OR 与逐工具两套数。
5. **可追溯性审计（测 H2）**：对每个工具，统计"**给定一个判定，第三方能否独立复现它**"——
   - 我们的系统：`evidence tuple` 完整（编译器版本+命令+-O+输出+内容哈希）=> 期望 100%；
   - 外部工具：记录其输出是否包含等价的可执行记录；
   - **这是一个可以客观计数的指标**，且是本文的核心差异点。

**数据**

- 输入：`data/683_real_world_detection_matrix.json`、`data/a5_676f_detection_matrix.json`（1137x8 冻结矩阵）
- 产出：`data/691_fair_comparison.json` + `_report.md` + `_prereg.json`

**预期结果**

| 指标 | 预期 | 备注 |
|---|---|---|
| 外部单工具 OR 检出率 | **低于我们的 8 资产 OR** | 组合优势，几乎确定；**这个结果没有信息量，不应作为主结果** |
| 与最强外部工具的差 | 不确定 | 这是唯一有信息量的检出率比较 |
| **可追溯率（traceability rate）** | **我们 100% vs 外部大概率显著更低** | **这是主结果** |
| 配置敏感性 | 外部工具对配置**高度敏感**（启发式检查集） | 可作为次要发现：**"工具输出不是证据"** |

**判定标准**

- **H2 成立**（可追溯率差异显著）=> 主结论写成"**在检出率轴上我们与成熟工具相当/更优，在可审计轴上我们显著更优，且后者是外部工具的结构性缺口**"；
- **H1 被证伪**（某外部工具检出率显著高于我们）=> **缩小 claim**：从"我们提供了更好的检测"退到"我们提供了**可审计的**检测，且外部工具的可追溯性缺口是其结构性问题"；
- **两者都不成立**（外部工具既更强又更可追溯）=> **这是最坏但最有价值的结果**：说明我们的差异化主张被证伪，应老实写进 Limitations，并考虑改做方向 B（环境协议）。

**失败应对**

- **可获得性失败**（装不上/跑不了）：如实报告"在本文的声明环境内无法获得可运行的外部工具"，并说明这本身是复现性信息。**绝不**用"我们测了一个玩具配置"来凑数。
- **结果不利**：**预先接受**。**这个实验的价值恰恰在于它可能让我们缩小 claim**——若我们只做能赢的比较，这个实验就没有信息量。
- **一个反向风险**：如果外部工具是**单一工具义务**而我们是 **8 资产 OR**，则我们本不该比——**必须同时报单资产最好成绩（asan 在真实 110 上 49.09%）作为"同等约束下的比较"**，否则是不公平比较（**评审 R1-16 批评过我们犯同类错误，不能自己再犯**）。

## 4. LLM audit transfer study（E1-F）

> 评审 R3-04 的意见是：**不要做"加 LLM 发现幻觉"，要做 audit transfer study。**

### 4.1 设计目标的关键澄清

| | 无价值的版本（R3-04 明确反对） | 有价值的版本（本设计） |
|---|---|---|
| 被测对象 | LLM judge 的**准确率** | **审计协议的可迁移性** |
| 对照 | 无对照，只报一个数 | **协议臂 vs 载体默认实践** |
| 结论形态 | "LLM 能抓到 73% 的问题"（已知） | "在什么样的载体上，证据可重算的要求是必要的 / 不必要的" |
| 失败也有价值吗 | 否 | **是**（若协议无增益，说明它绑定在"可执行重算"前提上，反而加强差异化） |

**若不做对照臂，这个实验会退化成 R3-04 反对的那种实验。** 这是设计的第一个要点。

### 4.2 完整设计

**假设**

- **H1（协议有增量）**：在同一个 LLM judge 载体上，**协议臂**（LLM 只提证据候选 + 程序裁决四态）比**默认臂**（直接信 LLM 的 pass/fail）产生更少的**不可追溯判定**，且总体准确率不劣。
- **H2（协议有边界条件）**：协议在**输出天然可执行**的载体上边际收益小，在**输出为自然语言**的载体上边际收益大——即协议的收益**绑定在"证据能否被重算"这一前提上**。

> **H2 是这个实验真正的科学产出**：它不是"协议有效"，而是"**协议何时有效**"。若 H2 成立，它直接支撑第二篇论文（方向 A）的核心命题。

**方法**

1. **样本**：n=100，从 `CodeJudgeBench`（arXiv 2507.10535，26 judge 模型）或自建代码任务中取**有客观 ground truth** 的任务（编译/测试可判定），避免用"人的偏好"作 ground truth。
2. **两臂**：
   - **默认臂**：LLM 输出 `pass`/`fail` 二值，直接采信（多数系统的默认做法）；
   - **协议臂**：LLM 只输出**结构化证据候选**（文件、行号、编译命令、预期诊断），程序裁决器执行该命令并据输出判定，四态输出（catch/miss/unknown/contradict）。
3. **跨载体（至少 2 类）**：一类是**输出天然可执行**的（如"这段代码能否编译"），一类是**输出为自然语言判断**的（如"这段代码的命名是否清晰"）。**这是 H2 的关键对照。**
4. **指标**（借用 BabelJudge 的四类失效模式作为因变量，这合法且省一轮争议）：
   - **可追溯率**：判定能否被第三方独立复现（主指标）；
   - **四态分布**：尤其 `unknown` 率（默认臂通常没有 unknown，只会 pass/fail——**这正是协议的核心增量**）；
   - BabelJudge 四类失效：**位置偏置**（同一答案换顺序，判定是否改变）、**冗长偏置**（更长答案是否更容易被判 pass）、**自偏好**（同族模型是否偏好自己的输出）、**低资源语言/格式偏置**；
   - **准确率**（次要，用于检查协议是否以准确率换可追溯性）。
5. **模型**：>=2 个 judge（1 个开源本地可跑 + 1 个 API），避免单模型结论。

**数据**

- 产出：`data/691_audit_transfer.json` + `_report.md`；建议同时发布**协议提示词与裁决器代码**（可复现性资产）。

**预期结果**

| 载体 | 预期 | 说明 |
|---|---|---|
| 输出可执行的载体 | 协议臂可追溯率显著高于默认臂；准确率**可能略降**（因为 unknown 被诚实记为 unknown） | 这是协议的成本，要如实报 |
| 输出自然语言的载体 | 协议臂可追溯率**大幅**高于默认臂；但裁决器可能大量 unknown（无法执行自然语言证据） | **这正是 H2 的边界条件** |
| 位置偏置 / 冗长偏置 | 默认臂**显著**存在；协议臂因证据锚定而**减弱** | 最可能出现的"协议有效"证据 |

**判定标准**

- **H1+H2 成立** => 这是第二篇论文（方向 A）的最小版本，路线图 3.2 方向 A 成立；
- **H1 成立但 H2 不成立**（协议在两类载体上收益相同）=> 说明协议的收益来自"程序化裁决"而非"证据可重算"，**机制解释被推翻，必须如实报告**；
- **H1 不成立**（协议臂无增量甚至更差）=> **诚实的负结果**：协议的价值绑定在"证据天然可执行"的 C++ 断言场景，不能迁移。**这是路线图第 4 节放弃跨域的又一证据**，但它同时**加强**了我们的差异化主张（因为它把边界划清楚了）。

**失败应对**

- **若协议臂大量 unknown 导致无法比较**：这是**预期的**，处置是**改用"条件召回"口径**（只在证据可执行的子集上比较），并**明确报告可执行率**——这个数字本身有价值（它是"载体适配度"的一个度量）。
- **若 API 不可用**：用本地开源模型，n 降到 60，并诚实报告 power 下降。

## 6. 本设计的诚实边界

1. **本批未执行任何实验**。四个设计里，第 1 节（人类标注）是唯一**必须今天启动**的，而它**不在 Agent 能力范围内**。如果找不到第二标注者，第 1 节的降级方案**不能**满足评审 R1-05，其余三项实验的结论可信度也会受"标签未验证"的连带影响。
2. **第 3 节（公平对比）的可获得性风险最高**。本机缺 MSVC、MinGW clang 缺 `libclang_rt.asan_dynamic`——**外部工具的可运行性必须先核实再承诺**。本设计给出的候选清单是"待核实"，不是"已确认可用"。
3. **第 2 节的 F1 因子在默认方案（2x2 全 WSL）下不可操纵**——因为 sanitizer 可用性与 OS 绑定。推荐的默认设计牺牲 H1 换取可执行性，**这是诚实但较弱的方案**；若能解决 native sanitizer 环境，可上全因子。
4. **第 4 节借用 BabelJudge 的四类失效模式作为因变量**，这在方法上合法（复用他人分类），但**等于承认我们的失效模式分类没有独立贡献**——因此第二篇论文必须把贡献放在"证据要求"而非"失效模式分类"上。
5. **所有时间与 n 的数字都是估计**，且没有任何历史基准（本项目是第一次做这类实验设计）。第一个真实交付后必须回头修订。
