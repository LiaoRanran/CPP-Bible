## 4. 与 692 的关系

692 是**环境感知 + 公平外部对比 + LLM 第四臂 + 投稿材料**；
693 在其上做了**三件 692 明确登记为缺口的事**：

| 692 登记的缺口 | 693 的处理 |
|---|---|
| H1「**人类 IAA 仍为 0**，是唯一能定性 LLM 独有命中的手段」 | 材料包从"designed and packaged"推进到 **packaged + AI 双标跑通 + 31 条分歧已收敛 + 招募材料齐备**；人类标注仍待执行，但**真人回来后 0 成本可算 κ** |
| 692 报告"**本机无 Docker**，compose/Dockerfile 未实测构建" | 693 给出**面向全链复现的独立镜像**（`docker/reproduce/`，多阶段）+ 一键脚本 + 环境锁定文档 + 14 项 sha256 清单；**仍无 Docker，仍未实测** |
| 692 的「环境是测量的坐标」 | 693-E4 的 D 臂把它做成**反事实臂**（E1/E2 配对 Δ=35.3357pp，与 692 逐位一致，构成**交叉验证**） |

**693 相对 692 的新增发现（3 条最重的）**：

1. **`data/676l_单检测器性能报告.md` 是陈旧指标**——676m 修了标签但没重算它，
   导致单资产 recall 系统性偏低 0.07–3.15pp、并集 recall 从 94.21% 变成 99.22%。
   这是**跨批次一致性缺口**，692 没发现。
2. **去标识化失败 13 条**——689 的净化正则没覆盖 `// expected_verdict:` 这一行。
3. **`linker` 的 AUC = 0.506（≈随机）**——把论文"低边际但不可替代"从定性论断
   变成可量化的边界值。

## 9. 第二次操作事故与修正（`scripts/` vs `Scripts/` 路径大小写）

**发生了什么**：693-B 把两个复现脚本写到 `scripts/reproduce_all.sh` 与
`scripts/verify_environment.sh`，并在 `git add scripts/...` 后提交。
但仓库**已存在的目录是 `Scripts/`（大写 S）**；Windows 文件系统大小写不敏感，
所以文件**实际落在 `Scripts/` 里**，而 `git add scripts/...` 在索引层**什么都没加**
（索引是大小写敏感的）——**两个交付物从未进入任何提交**，
且 693-B 的提交信息谎称包含它们。

**更严重的影响**：容器与 CI 会**真的失败**——

- `docker/reproduce/Dockerfile` 的 `CMD ["scripts/reproduce_all.sh"]` 在 Linux 容器里
  路径不存在 ⇒ 镜像默认入口直接报错；
- `.github/workflows/ci.yml::research-gate` 的 `bash scripts/verify_environment.sh` ⇒ CI 红。

**怎么发现的**：`git status --short | grep '^??'` 时看到
`?? Scripts/reproduce_all.sh` / `?? Scripts/verify_environment.sh` 两条未跟踪项。

**怎么修的**（693-G 提交）：
1. 把 **16 个文件**里的 `scripts/` 全部改成 `Scripts/`（含 Dockerfile、compose、
   两个 workflow、4 篇 docs、README、`tools/README.md`、`tools/utils/errors.py`、
   `tools/gen_693_manifest.py`、两个脚本自身、两份报告）；
2. `git add Scripts/reproduce_all.sh Scripts/verify_environment.sh`（用**正确大小写**）；
3. 重跑两个脚本验证可用：
   - `bash Scripts/verify_environment.sh --report` → **OK=3 FAIL=0 WARN=11**
   - `bash Scripts/reproduce_all.sh --out out/693_fix --skip-env` → **S0–S4 全跑通**

**教训（写给自己）**：`git add <path>` **不报错 ≠ 加进去了**。
在本仓库这种「已有大写目录 + Windows 大小写不敏感」的组合下，
新增脚本后必须用 `git status --short` 复核是否真的进了索引。
本批新增的 `tests/test_693_research.py` 已包含
`test_e7_paper_tex_unmodified_by_this_batch` 这类红线断言，但**没有**覆盖"文件是否真的入库"——
这是可以补的一类门禁（建议后续批次加：`git status --porcelain` 必须为空才允许写验收报告）。
