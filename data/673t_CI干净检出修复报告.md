## 1. C：Merkle 根与 tool_integrity 为什么在干净检出上必红

**根因不是"忘了重钉"，是锚本身取决于检出环境。**

`merkle_integrity.leaf_hash` 与 `tool_integrity.sha256_of` 都直接哈希**工作树的原始字节**，
而工作树行尾取决于检出环境。干净检出实测（a412b8ff）：

```
[merkle] Book     台账 0a36f80b / 实际 584ff780   （文件数 183 -> 183）
[merkle] Examples 台账 265147a0 / 实际 a82dc1b1   （文件数 1586 -> 1586）
[merkle] atoms    台账 8f77fb41 / 实际 178cc4ed   （文件数 54 -> 54）
[merkle] evidence 台账 14e0d74d / 实际 305fa8d2   （文件数 72 -> 72）
[merkle] mutation 台账 42829d78 / 实际 df83b789   （文件数 7 -> 7）
[supply_chain] data/governance_docs_manifest.json 期望 ff213a11 / 实际 b4b708ee
```

**文件数完全一致 ⇒ 不是漏文件，是字节不同。** 计数佐证：本机主仓受控树里
659 个文件是 CRLF（DEBT-002 的漂移面），干净检出是 97 个（且那些是 `.gitattributes`
显式声明的）。

这个红**修不掉**：重算成本机（CRLF）⇒ CI 红；重算成干净检出（LF）⇒ 本机红。
两边都是真实机器，谁也不该被判假。673q 的绿正是依赖本机 CRLF 树 + 一份**未提交**的
`tools/.tool_checksums`（实测主仓有 2 行未提交重钉），一进干净检出就露馅。

**修法**：哈希前对**文本文件**做 CRLF→LF 归一，二进制字节一字不动。
文本的行尾不是内容——git 自己也这么判（`core.autocrlf` / `eol` 只影响检出形态，
索引里是 LF）。分类用 git 自己的判定（`git ls-files --eol` 的 `attr/-text` 即二进制），
整仓只问一次并缓存；git 不可用时退回"无 NUL 即文本"。

**刻意不改**用 `git cat-file blob`（哈希索引内容）：那样本地未暂存的改动会被忽略，
篡改工作树而根不变——对完整性锚是安全性倒退。

**ALGO v1 -> v2**：哈希口径变了，`ALGO` 就是为这种换代准备的标记。已升 v2 并重算
全部 5 个根、重钉 `.tool_checksums`。（`.ots` 未变——它本就是"占位登记，不是时间戳证明"。）

**验证（核心判据）**：CRLF 主仓与 LF 干净检出各算一次，**5 个根逐字节相同**
（Book a83ef1bb / Examples 16c27b56 / atoms 178cc4ed / evidence 305fa8d2 / mutation df83b789）。

### test_sqlite_version_671e：673s 点名的那个

生成后失败形态从 `no such table: meta` 变成 `assert 2 == 0`，测试名是
`test_current_db_user_version_is_zero_documents_gap`。判定：

- `prop_graph.py` 有 `sync_user_version()`，`build` 执行 `PRAGMA user_version = int(SCHEMA_VERSION)`
  ⇒ **建库后 user_version 的合理值是 2**（实测 `user_version=2`、`meta.schema_version=('2',)`，
  与代码 `SCHEMA_VERSION = "2"` 一致）。
- 也就是说：673e 当时记录的 gap（"`schema_version` 记了但标准机制没用"）**后来被关掉了**。
- 原断言 `uv == 0` 钉的是**一次性历史状态**，只在"库由更老的版本构建"时成立 ⇒ **断言过期**。

修法：`uv == int(meta.schema_version) == int(SCHEMA_VERSION)`——锁**镜像关系**而不是锁常量 2
（否则将来 SCHEMA_VERSION 升 3 又假红）。这正是 673e 任务 D 真正要保证的不变量。
干净检出验证：**7 passed / exit 0**。
