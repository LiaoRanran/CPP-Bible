# 641 任务 0.2 · 偶发项 `test_poison_coverage_581` **定位与处置**

## 一、现象

| 全量轮次 | 结果 |
|---|---|
| 640c 第 1 次 | 该用例 **绿**（当次 3 红全是 UTF-16 产物导致的控制字符误伤，与本用例无关） |
| 640c 第 2 次 | 该用例 **红**（唯一红） |
| 641 任务 0.1（第 3 次） | 该用例 **绿**（当次 8 红全是我方新工具未过 ruff/mypy 所致） |

⇒ 单跑 ✅、`-k poison` 组 ✅、`-k test_p` 组 ✅，只在**全量**里偶发 ⇒ 顺序/状态敏感，非随机。

## 二、根因（**已定位，非猜测**）

`poison_drill` 是**整个 pytest 会话共享的模块单例**，`behavioral_covered()` 用模块级
`_LAST_BEHAVIORAL_COVERED` 缓存：

```python
def behavioral_covered() -> set:
    global _LAST_BEHAVIORAL_COVERED, _LAST_DRILL
    if _LAST_BEHAVIORAL_COVERED is None:
        _LAST_DRILL = drill()          # 只有缓存为空才真跑
    return _LAST_BEHAVIORAL_COVERED
```

而用例里：

```python
real_cov  = pd.behavioral_covered()      # pd：会话内**可能已被更早测试填充** ⇒ 返回陈旧缓存
ghost_cov = mod.behavioral_covered()     # mod：源码副本，**本次必然新跑**完整 drill
assert ghost_cov == real_cov
```

⇒ 断言比较的是"**陈旧基线** vs **新跑结果**"。只要两次 drill 之间 `build/` 状态（或任何
影响 drill 的东西）有变化，就红。多个测试文件都会触发该缓存
（`test_poison_exemptions_581`、`test_s1_s6`、`test_high_complexity_rules_regression_624`…），
所以是否红取决于 pytest 的**文件顺序与当时状态**——这正是"单跑绿、全量偶发红"的解释。

## 三、确定性复现（实证，非口头）

脚本（`%TEMP%\probe_581_flake.py`）人为灌入陈旧缓存后跑**同一段断言逻辑**：

```
[1] 陈旧基线 = ['STALE-FROM-EARLIER-TEST']…（n=1）
[1] 新跑结果 n=39
[1] 旧写法断言 ghost==real ⇒ FAIL（复现偶发红）      ← 失败模式 100% 复现
[2] 新鲜基线 n=39；ghost n=39
[2] 新写法断言 ghost==real ⇒ PASS                    ← 修复后
[3] 'FAKE-GHOST-581' in ghost_cov ⇒ False            ← 断言仍有力度
```

## 四、处置

`tests/test_poison_coverage_581.py`：取基线前先 `pd._LAST_BEHAVIORAL_COVERED = None`
（让基线也是**本次现算**），并把这个机制写进注释。

**力度未削弱**：① 仍要求"注入死文本后两侧覆盖集合完全相同"；② 仍断言
`FAKE-GHOST-581` 不得进入覆盖分子（上表 [3] 实证）。
修的是"拿陈旧缓存当基线"这一**测试自身的顺序依赖**，不是把断言放松。
