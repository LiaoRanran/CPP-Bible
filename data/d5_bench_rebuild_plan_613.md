| 项 | 任务书假设 | **实测** | 判定 |

**根因（实测）**：基准源并非丢失，而是**历史上整体迁到了 `_archive/benchmarks/`**
（未被 .gitignore 忽略，`git ls-files` 显示 135 个文件已跟踪）。而两个 D5 门禁的契约都是
"**仓库根**必须存在且 git 跟踪的 `_bench_d5_X.cpp`"，于是全部声明被判"缺失/未跟踪"。

门禁实测（修复前）：
- `tools/d5_appendix_audit.py`：**ERROR=119**（全部 `BENCH_MISSING`，"引用的基准源文件不存在于库根"）→ **CI quality job 首个红步**。
- `tools/d5_source_integrity.py --check`：声明 99 / 磁盘 0 / git 0 → exit 1。

## 二、决策：**不重建、不删引用 —— 改为门禁解析扩展（库根优先 + 归档兜底）**

| 候选方案 | 评估 | 结论 |
|---|---|---|
| ① 重建缺失基准文件（内容从章节推断） | **无内容可重建**：126 个文件真实存在，重建=凭空造一份可能与原文不同的副本，反而污染可复现承诺 | ❌ 不适用 |
| ② 移除 Book 中的 D5 引用 | 直接削弱"可复现 demo 有源码"的承诺，且需改受控目录 Book/ | ❌ 不采纳 |
| ③ **门禁解析扩展：库根优先、`_archive/benchmarks/` 兜底** | 文件真实存在 + git 跟踪 ⇒ 契约的两条实质要求（存在性、可追溯）**都满足**；不改受控目录；零内容伪造 | ✅ **采纳** |
| ④ 物理迁回库根（126 个文件） | 最贴合"库根"字面承诺，但改动面大、与 `_archive` 归档意图冲突 | ⚠️ 交人（见下） |

**采纳 ③ 的理由**：门禁的实质是防"可复现性承诺回归"（声明了却拿不出源码）。
文件在 `_archive/benchmarks/` 且被 git 跟踪，读者 `git clone` 后同样能拿到并复现，
承诺并未落空；真正落空的是"库根"这个**路径字面**描述。

## 四、残留与交人项

## 五、风险与回滚

- 风险：若未来有人把基准源移到第三处，门禁会重新变红（**这是期望行为**，不会静默放行）。
- 回滚：两处改动均为独立小函数/两行 pathspec，`git revert` 即可，无数据迁移、无副作用。
