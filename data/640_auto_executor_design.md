# 640 B1 · 闭环自动执行层设计（auto_executor_640.py）

## 一、定位

闭环（637 观测 → 637 检测 → 637 候选 → 638 调参/重跑）一直是影子模式。本工具补上
**执行层**：只做白名单内的机械修复，其余建议照旧走"交人清单"。

## 二、白名单（允许自动执行）

| 类别 | 操作 | 改后验证 |
|---|---|---|
| `control_chars` | 清 0x00-0x08/0x0B/0x0C/0x0E-0x1F | 复扫 = 0 |
| `final_newline` | 补文件末尾换行 | 复查 = 有 |
| `trailing_ws` | 去行尾空白 | 复扫 = 0 |
| `ruff_fix` | `ruff check --fix`（仅限指定路径） | ruff 复查通过 |
| `snapshot_update` | pytest --snapshot-update | 快照测试复跑绿 |

**明确禁止**（攻击面见 B3）：改 gate 规则 / CORE_TOOLS 判决逻辑 / ledger 内容 /
atoms-evidence 知识卡 / 人审操作 / push / 删除文件。

**git 防线（640 B2 实测新增）**：tracked-and-modified 文件跳过——它们可能含
未提交的无关改动，自动修复会把漂移卷进格式 diff。

## 三、六重护栏

1. **白名单**：类别不在 `WHITELIST` ⇒ 拒绝（记日志）；
2. **改前备份**：字节级备份到 `%TEMP%/auto_executor_640_backup/`；
3. **改后验证**：按类别复检清零；
4. **失败回滚**：验证失败 ⇒ 从备份字节还原（单测锁"字节一致"）；
5. **批量上限**：单次 ≤10（`--max N`）；
6. **日志留痕**：每项写 `data/640_auto_executor_log.jsonl`（ts/action/status/detail）。

## 四、模式

| 模式 | 行为 |
|---|---|
| `--dry-run`（默认） | 只列出将执行项，零改动 |
| `--apply` | 真执行（全护栏） |
| `--max N` | 批量上限 |
| `--check` | 自检（零改动） |
| `--selftest-fixture` | 临时目录夹具：3 个真实小修 + 2 个攻击，验证全流程 |

## 五、实测（640 B2/B3）

- 夹具试运行：**3 项修复成功**（控制字符/末尾换行/行尾空白，文件状态逐一验证）；
  2 项攻击被拒（非白名单类别 `gate_rule_edit` + 保护路径 `tools/gate_engine.py`）；
- 真实仓库：检出 376 项行尾空白候选；首批 10 项 apply 成功，但实测为 **CRLF 归一**
  （git 内容零 diff，无信息量）⇒ 已还原；**真实仓库当前没有带内容量的可自动修项**
  （A1 清算后系统干净）——这正是闭环该有的"无事可做"状态；
- 安全审计：9 例攻击/护栏测试全过（见 `tests/test_auto_executor_640.py`）。

## 六、诚实边界

1. 文本类修复是字节级机械操作，不做语义判断；
2. `ruff_fix` / `snapshot_update` 两类已定义未在本批触发（仓库当前无对应待修项）；
3. 权重/建议来自 637+640A2 覆盖层，执行层不判断"该不该修"，只判断"能不能安全修"。
