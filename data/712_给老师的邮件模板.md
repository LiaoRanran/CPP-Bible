# 712 批次 — 给老师的邮件模板（三个版本）

> 使用说明：
> 1. 三个版本分别对应三种不同请求。根据你要找的老师身份选一个。
> 2. 你只需要替换两个占位符：`<老师称呼>`（例如 "张老师"、"李教授"）和 `<你的姓名>`。
> 3. 邮件里**不要提 GitHub 匿名仓库的真实 URL**，只说"一个匿名双盲仓库"，避免老师不小心在邮件里回复破盲。
> 4. 附件：两篇论文 PDF 各一份（老师回邮件后再发，第一封先不要带大附件）。
> 5. 语气原则：**陈述事实 + 明确请求 + 给出老师的成本估算**。不卑不亢。

---

## 版本 A — 请求用学校邮箱注册 OpenReview / arXiv 账号

> 适用场景：你要找的老师是**认识你、愿意帮你走个行政流程**的专业课老师 / 班主任 / 毕设指导老师。请求很轻，只需要老师用学校邮箱帮你收一封验证邮件，或者指导你怎么用学校邮箱注册。

### 主题行

```
请教：关于用学校邮箱注册 OpenReview / arXiv 的一点流程问题
```

### 正文

```
<老师称呼>，您好：

冒昧打扰。我是<你的姓名>，本学期修过您的〈课程名〉。最近在课余时间独立完成了一项关于 C/C++ 软件验证评测审计的研究，整理成了两篇论文，想在 OpenReview 和 arXiv 上公开挂出来，供同行评议和引用。

简单汇报一下研究内容：这项工作提出了一套"审计评测器本身"的协议。在实证侧，我在 1147 个样本上对比了同一检测器在 WSL 与 Windows 原生环境下的表现，检出率从 60.07% 漂移到 24.74%（McNemar p=1.24e-60），并且这种漂移是静默的——未知桶计数为零，评测系统自身不会报警；同时把表观增益分解到结构性 Goodhart 的四种类型，拟合出 g_app(d)=5.47+5.28d−0.26d²（R²=0.9997）。在理论侧，我建立了测量漂移的 8 公理代数（其中仅 A2/A5/A8 独立），并给出信息论样本复杂度下界：Type I 漂移需 ≥849 样本，Type II 需 ≥17，Type III/IV 在配对设计下功效恒为 0。另在一个 40 个真实 CVE 的案例库上验证，其中 14 个实测可编译。

现在遇到一个流程上的小卡点：OpenReview 和 arXiv 在注册时都倾向于识别机构邮箱，我个人邮箱注册会被标记为非机构账号，后续投稿和 endorsement 都会受限。学校邮箱我目前没有自行注册的权限（学生邮箱一般需要通过学院或图书馆渠道开通）。

想请您帮个忙，具体是其中一件即可：

1. 指导我通过哪个官方渠道（图书馆？信息中心？教务系统？）申请一个学生机构邮箱；或者
2. 如果方便，用您的学校邮箱帮我代收一次 OpenReview / arXiv 的注册验证邮件（我会把验证链接发给您，您只需要点一下转发给我即可，全程预计 2 分钟）。

这件事只占用您很少时间，不涉及对论文内容的评审或背书。论文目前是双盲匿名投稿状态，我不会在邮件附件里放作者信息，也请您暂时不要对外扩散，等我论文有了正式结果再公开。

如果您近期忙，回复"稍后联系"即可，我不着急。

谢谢老师！

<你的姓名>
```

## 版本 B — 请求 arXiv endorsement

> 适用场景：你要找的老师是**在 CS / 软件工程 / 系统方向有 arXiv 发文记录**的副教授以上老师。请求比 A 重一些——老师要花 5 分钟登录 arXiv endorsement 页面点一下。选老师时先确认他/她过去 endorsing 过别人（arXiv 账号要满 3 个月、有一定发文记录才能 endorsing）。

### 主题行

```
请教：关于 arXiv cs.SE endorsement 的一点请求
```

### 正文

```
<老师称呼>，您好：

冒昧打扰。我是<你的姓名>，本学期修过您的〈课程名〉。最近在课余时间独立完成了一项关于 C/C++ 软件验证评测审计的研究，整理成两篇论文，计划投往相关会议，同时希望先在 arXiv 上挂出预印本，供同行早期反馈。

研究内容简要汇报：
- 实证侧：在 1147 个样本上测量了同一 C/C++ 验证检测器的环境漂移，检出率从 WSL 下的 60.07% 下降到 Windows 原生下的 24.74%，McNemar 配对检验 p=1.24×10⁻⁶⁰，且漂移是静默的（未知桶计数 Δ=0）。同时把一次表面 +24.03 的 F1 提升做了因果分解：口径变化 −9.55、两个零产出组件 −8.27、linker 差异 −4.65、k 档位扫描 +10.74，净 +12.30，识别出结构性 Goodhart 四型，并拟合表观增益曲线 g_app(d)=5.47+5.28d−0.26d²，R²=0.9997。
- 理论侧：建立测量漂移的 8 公理代数（仅 A2/A5/A8 独立，其余为定理 T1–T6），给出信息论样本复杂度下界——Type I 漂移 ≥849 样本，Type II ≥17，Type III/IV 在配对设计下功效恒为 0；能力边界预测模型 AUC=0.7551。
- 实证锚点：40 个 NVD 真实 CVE 案例库，14 个实测编译通过。

现在的卡点是：arXiv 的 cs.SE / cs.PL 类目需要已有作者的 endorsement。我查了一下您过去在 arXiv 上的发文记录，方向上和我的工作（软件工程评测 / 测量方法论）比较接近，因此冒昧写信。

想请您帮忙做一件事：在 arXiv 上给我的账号 endorsing 一下。具体流程是——
1. 我会把我的 arXiv 账号 ID 和拟投稿的类目（cs.SE，可能兼挂 cs.PL）发给您；
2. 您登录 arXiv，进入 "Endorse Someone" 页面，输入我的 ID，确认 endorsing；
3. 全程预计 3–5 分钟。

endorsement 只是 arXiv 的资格门槛，**不代表您对论文内容背书**。论文目前是双盲匿名投稿状态，我会先把匿名版 PDF 发给您过目（您可以选择不读，直接 endorsing 也完全没问题），等正式接收后我再补致谢。

如果您觉得方向不对、或者近期不方便，直接回复一句即可，我完全理解，不会再打扰。

谢谢老师。

<你的姓名>
```

## 版本 C — 请求指导人类 IAA（inter-annotator agreement）的招募

> 适用场景：你要找的老师是**做软件工程实证研究 / 有自己的研究生团队 / 认识其他学校同行**的老师。这个请求最重——需要老师帮你指一条路，或者介绍 2–3 个标注员。论文里 "Human IAA = 0" 是个硬伤，必须补上。

### 主题行

```
请教：关于实证研究中人类标注一致性（IAA）招募的一点建议
```

### 正文

```
<老师称呼>，您好：

冒昧打扰。我是<你的姓名>，本学期修过您的〈课程名〉。最近在课余时间独立完成了一项关于 C/C++ 软件验证评测审计的研究，两篇论文的核心结果已经跑通，但在一个方法论环节上卡住了，想请您指点一下。

先汇报研究内容：这项工作提出审计评测器本身的协议。实证上，在 1147 个样本上测得同一检测器环境漂移 60.07%（WSL）→ 24.74%（原生），McNemar p=1.24e-60；拟合结构性 Goodhart 四型的表观增益曲线 g_app(d)=5.47+5.28d−0.26d²（R²=0.9997）；F1 表面 +24.03 分解后净 +12.30。理论上，8 公理测量漂移代数（A2/A5/A8 独立），样本复杂度下界 Type I=849、Type II=17、Type III/IV 配对功效恒 0；能力边界 AUC=0.7551。锚点是 40 个真实 CVE 案例，14 个实测编译。

**现在的硬伤是：人类标注一致性（Human IAA）= 0。**

具体说，论文里所有的 κ 值目前都是 AI 自一致性，不是真正的人类间一致性。我已经把 145 条待标注样本整理成了去标识化的 annotation package，冻结在仓库里，但我一个人既当作者又当标注员，算不出有意义的 inter-annotator agreement。审稿人如果认真查，这一条会直接拒稿。

我需要 2–3 位**独立的人类标注者**，对这 145 条样本做二次标注，然后我来算 Cohen's κ / Fleiss' κ。

想请您在以下三件事里指点任意一件：

1. **招募渠道建议**：以我目前的身份（本科生、双盲投稿、不能公开学校），通过什么渠道能找到愿意花 1–2 小时做标注的同行？是否有专门的实证软件工程标注众酬社区？
2. **lab 介绍**：如果您实验室或您认识的老师实验室里，有研究生愿意花 1–2 小时帮标注（可以付少量报酬，或论文里明确致谢——但双盲期致谢要脱敏），能否帮忙牵个线？
3. **方法论兜底**：如果实在招不到人，在论文里把 Human IAA=0 作为局限声明、改用 AI self-consistency 并附完整敏感性分析，这种处理在 cs.SE 顶会里能过审吗？还是说必须补人类标注？

这件事对我比较关键，因为它直接决定论文能不能从"有明显硬伤"变成"可投"。您不需要帮我做具体标注，只要指个方向或者泼盆冷水告诉我哪条路走不通就行。预计回复成本不超过 5 分钟。

如果您近期忙，回复"过两周再说"即可。

谢谢老师。

<你的姓名>
```

## 通用发送前检查清单

- [ ] 主题行里没有出现"跪求"、"恳请"、"打扰了"这类过度谦卑的词。
- [ ] 正文里所有数字（60.07 / 24.74 / 1.24e-60 / 0.9997 / 849 / 17 / 0 / 0.7551 / +24.03 / +12.30 / 40 / 14 / 145）和仓库里冻结的一致，没有手误。
- [ ] 没有出现"我很菜"、"我只是个本科生"、"希望您不要嫌弃"这类自贬表述。
- [ ] 明确给了老师一个"成本估算"（2 分钟 / 3–5 分钟 / 5 分钟），降低老师的决策成本。
- [ ] 每封信末尾都给了老师一个"体面拒绝"的台阶（"回复稍后联系即可"、"直接回复一句即可"）。
- [ ] 第一封邮件**不要带论文 PDF 附件**，等老师回复后再发；附件会触发学校邮箱的反垃圾系统。
- [ ] 不要在邮件里贴 GitHub 仓库 URL（双盲期）。
- [ ] 发送前用 Word / 邮件客户端检查一遍错别字，特别是数字。
- [ ] 发送时间建议：工作日上午 9:30–10:30，或下午 14:30–15:30，老师看邮件概率最高。**不要周末晚上发**。

## 三个版本的选择决策树

```
老师是谁？
├─ 只需要行政流程 / 你不太熟
│   └─→ 版本 A（请求学校邮箱）
├─ 方向接近、有 arXiv 发文记录、你上过他的课
│   └─→ 版本 B（请求 endorsement）
└─ 做实证软件工程、有 lab / 研究生资源
    └─→ 版本 C（请求 IAA 招募指导）
```

如果同一位老师既适合 B 又适合 C，**先发 B**（请求更具体、成本更低、老师更容易答应），等 B 落地后再单独发 C。不要一封邮件塞两个请求。
