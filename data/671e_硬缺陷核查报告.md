## 1. 任务 A · 反事实算子 zero_division

### 核查过程
1. 读 `tools/counterfactual_citation_658.py`：仅返回布尔 `dependent`，**无任何 sklearn 调用**。
2. 读 `data/counterfactual_cases_665.json`：10 条样本，`confusion={tp:2,fp:0,tn:8,fn:0}`，`scores={precision:1.0,recall:1.0,f1:1.0}`。
3. 读 `tools/counterfactual_extend_665.py` 第 142–144 行：P/R/F1 为**纯算术**，且已显式 `else 0.0` 防除零：
   ```python
   prec = tp/(tp+fp) if (tp+fp) else 0.0
   rec  = tp/(tp+fn) if (tp+fn) else 0.0
   f1   = 2*prec*rec/(prec+rec) if (prec+rec) else 0.0
   ```
4. 全 `tools/` 递归 grep `sklearn` / `zero_division` / `precision` / `recall` / `f1` / `confusion` / `metrics` = **0 命中**。
5. 手动复现：用 658 算子重跑 10 条样本，预测与产物一致；手工算混淆矩阵 = `{2,0,8,0}` → `P=R=F1=1.0`。

### 结论：**不是缺陷（false positive）**
- 根本不依赖 sklearn，`zero_division` 机制在本项目无从触发。
- 当前数据 `tp=2`（分子分母均 > 0），即便用 sklearn，两个分母都非零 ⇒ `zero_division` 不可能是 F1=1.0 的成因。
- F1=0→1.0 的**真实成因**：666 新增第 3 判据 `machine_marker`，抓住了两条平台测量类 dependent 样本（tp 由 0→2），是算子能力真实提升，非伪影。

### 严重程度：无（误报）
### 修复状态：未修复（无需修复）—— 改用测试锁定真实行为
### 对论文影响
论文 §6.5 的 **F1=1.0 声明成立且真实**，无需修正。但应保留既有诚实注记：F1 是**上界**（判据 3 与真值同源），n=10 为点估计（Clopper–Pearson 95% CI ±约 30pp）。
### 测试
`tests/test_counterfactual_zero_division_671e.py`（13 条）：含"tools/ 无 sklearn/zero_division"、"extend 公式防除零返回 0.0 非 NaN"、"手动混淆矩阵=2/0/8/0"、"端到端复现算子预测"、"判据3与真值同源一致性"等。

## 2. 任务 B · Merkle 树域分隔（第二原像攻击）

### 核查过程
1. grep `merkle` 定位到 `tools/merkle_integrity.py`（`tool_integrity.py` 委派 `mi.build_all/check_all`）。
2. 读实现：`_LEAF_PREFIX = b"\x00"`（第 56 行）、`_NODE_PREFIX = b"\x01"`（第 57 行）。
   - 叶：`leaf_hash = sha256(0x00 || rel_path || 0x00 || content)`（路径绑定）
   - 内节点：`_node_hash = sha256(0x01 || u64(左叶数) || u64(右叶数) || 左 || 右)`（子树规模绑定）
3. 另有：奇数节点**提升**（非复制，防 CVE-2012-2459）、空目录根 = `sha256(b"")`。
4. **PoC 复现（B3）**：构造一个内部节点值（0x01 前缀），试图 (a) 让其等于某叶子 hash → 因 0x00≠0x01 输入空间不相交，穷举候选均失败；(b) 伪造"某文件在树中"的成员证明（把内部节点值塞进 `leaf.hash`）→ `verify()` 用 0x00 前缀重算叶 hash，与伪造值不符，拒绝。

### 结论：**不是缺陷（false positive）**
域分隔（0x00 叶 / 0x01 内）**已实现**，第二原像 / 伪造证明在 `verify()` 复核阶段即被拒。

### 严重程度：无（误报）
### 修复状态：未修复（无需修复）—— 测试锁定（18 条）
### 对论文影响
供应链安全声明成立，无需修正。

## 3. 任务 C · JSON 哈希规范化（JCS）

### 核查过程
1. 全 `tools/` 扫描 `json.dumps`/`json.dump`/`sort_keys`/`sha256`/`canonical`/`JCS`：**唯一 3 处**对内存 dict 做 `sha256(json.dumps(...))` 的代码——`authority_projection_compiler_626._digest`、`e2e_attestation_629`（pub 哈希）、`lifecycle_fsm_638._entry_hash`——**全部已 `sort_keys=True`**。
2. 其余大量 `json.dumps` 为**写文件序列化**（`.encode()` 落盘），其验证哈希在别处对**文件字节**计算，与字典键序无关。
3. 关键信任产物：
   - `data/dataset_hashes_670c.json`：`hash_datasets_670c.sha256_file` 哈希**原始文件字节**（明确不做换行归一）。
   - `data/supply_chain/merkle_roots.json`：落盘 JSON，其哈希在 `tool_integrity.compute_supply_chain` 经 `sha256_of`（读字节）。
   - `tools/.tool_checksums`：`sha256_of` 读字节。
4. **键序问题复现（C3）**：构造两文件内容相同、键序不同 → `sha256_file` 给出**不同**哈希（**设计预期**，正是抓字节级漂移/键序改写的用途），而所有 dict 验证哈希因 `sort_keys=True` 对键序不敏感。

### 结论：**不是缺陷（false positive）**
JCS 风险只存在于"对内存 dict 做 `json.dumps` 哈希且漏 `sort_keys`"；本项目该路径已全部 `sort_keys=True`，信任产物哈希对象为文件字节。

### 严重程度：无（误报）
### 修复状态：未修复（无需修复）—— 未新增 `tools/json_canonical_671e.py`（非缺陷则无需统一规范化工具）；改用测试锁定（14 条）。
### 对论文影响
可复现性声明成立，无需修正。
### 测试
`tests/test_json_canonical_671e.py`（14 条）：含"canonical 哈希键序无关"、"无 sort_keys 会键序敏感（机理演示）"、3 个真实 dict-哈希函数键序无关 + 源码级 `sort_keys=True` 锁定、数据集哈希字节级漂移检测、版本化函数 `_entry_hash` 忽略 `self_hash`、`merkle_roots` 经文件字节哈希等。
