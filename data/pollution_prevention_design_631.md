不依赖每个用例自觉清理，而是让"残留"**必然被抓到**。

## 二、现在的防护为什么不够

| 已有机制 | 覆盖 | 缺口 |
|---|---|---|
| 622 沙箱 6 重护栏（字节备份 / `finally` 还原 / 还原后 sha256 校验 / 并发锁 / 超时 / 路径白名单） | **走 `Sandbox.apply_and_run` 的路径** | ①不覆盖**直接写文件**的用例；②不覆盖 **subprocess 调变异工具**的用例；③还原失败时只记 `infra_error`，**不会让整轮测试红** |
| 收工门禁的 `git diff --quiet -- atoms evidence Examples Book` | 批次收工时点 | 在 CI 与日常开发中**没人跑**；污染可以悄悄存在很久 |
| CI `replay` job | manifest 一致性 | 只查哈希登记，**不查工作区是否残留未提交改动**（CI 工作区用完即弃，残留永远不会被发现） |

⇒ **污染在本地是"静默"的，在 CI 是"不可见"的**，这正是它活到 630 才被发现的原因。

## 三、三层防护设计（建议，按性价比排序）

### L1 · 会话级「受控目录快照守卫」（推荐先做，**零侵入**）

在 `tests/conftest.py` 里加一个 `autouse` 的 **session 级** fixture：

```python
# 伪代码（本批不落地）
@pytest.fixture(scope="session", autouse=True)
def controlled_dir_guard():
    before = snapshot(("atoms", "evidence", "Examples", "Book"))   # 路径→sha256
    yield
    after = snapshot(...)
    changed = diff(before, after)
    if changed:
        pytest.fail(f"受控目录在测试会话中被改动：{changed}", pytrace=False)
```

- **成本**：约 30 行代码，遍历一次目录做哈希（2000+ 文件 ⇒ 秒级）；
- **收益**：任何残留**当场变成一次显式失败**（列出文件），不再静默；
- **风险**：会把"正常的测试内写操作"也判红 ⇒ 需配合白名单
  （例如允许 `sandbox_apply_622` 在 `finally` 内还原的文件），
  或对"最终状态与初始状态一致"判定（**还原过的文件不算污染**）——
  推荐后者：只比**会话结束时的最终状态**，与初始不一致才算污染。

### L2 · 沙箱侧加固（改 622 工具 ⇒ §零.11 越界，需授权）

1. `apply_and_run` 的 `restore` 已在 `finally`——**保留**；补两点：
   - 还原**失败**时改为**重试 + 抛异常**（当前只返回 `infra_error`，调用方可能忽略）；
   - 注册 `atexit` 钩子：进程异常退出前再兜底还原一次。
2. 增加**进程级互斥**：同一时刻只允许一个沙箱会话（已有 `data/.622_apply.lock`），
   并把"锁存在"视为异常（防止上次崩溃留下的脏状态被继承）。

### L3 · 工具侧默认只读（改他批工具 ⇒ 越界，需授权）

任何会写受控目录的工具（`*_mutator_*`、`round3_*`、沙箱等）默认 `--dry-run`，
必须显式 `--apply` 才落盘，并在写前落备份、写后校验 sha256。

### CI 侧（改 ci.yml ⇒ 授权）

在 `pytest` job 末尾加一步：

```yaml
- name: Controlled dirs clean
  run: git diff --quiet -- atoms evidence Examples Book
```

⇒ 让污染在 **CI 也红灯**，而不是随工作区丢弃。

## 四、优先级与成本

| 层 | 侵入性 | 成本 | 收益 | 建议 |
|---|---|---|---|---|
| L1 会话守卫 | 仅 `tests/conftest.py` | 低（~30 行） | 高（污染必现形） | **先做**（631 未做，交 632） |
| CI 侧校验 | `.github/workflows/ci.yml` | 低（1 步） | 中（CI 可见） | 与 L1 同批 |
| L2 沙箱加固 | 改 622 工具 | 中 | 中（降低根因发生概率） | 需授权 |
| L3 工具默认只读 | 改多个他批工具 | 高 | 中 | 需授权、分批改 |

## 五、诚实登记

1. **本批不实施任何一层**（§七 C2.2）；文档只交付设计与参考代码；
2. C1 的根因假设**未证实**——若 L1 落地后污染再次出现，日志会直接指出是哪个文件，
   届时再验证/推翻该假设；
3. L1 的"最终状态一致"判定会放过「写脏又还原」的用例——这是**有意的**：
   我们要抓的是"残留"，不是"临时写"；若将来要更严（禁止任何写），需另设白名单机制。
