# 04 · 人签威胁模型（Q4）

> 任务疑问：T3 拟新增只追加 `data/human_sign_events.jsonl`，`principal_ok` 升级为"文本 + git 作者一致 + 事件可对账"，复用 git 作者绑定 fail-closed。这相对 PoC-3（键入 `human:<名字>` 即过）**净增了哪些真实保证**？哪些只是"多了个文件让人以为签过"？`git user.name/email` 可任意配置、本地 jsonl 可直接改写、无第三方时间戳——逐条拆解。

---

## 1. 现状锚点（代码实测，看清楚"已修到哪"）

- **PoC-3 已部分修复**：旧版 `by: human:随便谁` 即可过；现 `principal_ok`（`gate_engine.py` L128–）要求"前缀 + **实名非空** + 人级署名**在册**"（`HUMAN_PRINCIPALS = ("liaoranran",)` L116；L142 `name.lower() not in HUMAN_PRINCIPALS` → 非在册名被拒）。→ 空名/非在册名已挡住。
- **但 `principal_ok` 不绑 git 作者**：它只查名册，**不查 git 作者**。git 作者绑定只在 `check_git_author_binding`（L2949）里，且是 **warn 级、不 block**（L2958–2962 三条硬理由：协作合法、存量会被改写、观察期）。
- `_author_matches`（L2934–2946）：**子串宽松匹配**（包含即通过），且**空名直接返回 True**（L2945）——这是观察期提示，不是认证。
- `metrics_collector.log_overturned`（L406–442）：human 推翻者须过 `ge._git_author_for` + `ge._author_matches` 的 fail-closed 校验（L424–432，不匹配即 `raise ValueError` 拒绝写入）。→ **这是 T3 想复用的"git 作者绑定 fail-closed"的原型**。

---

## 2. T3 相对 PoC-3 的净增保证（逐条）

| 新增机制 | 真实保证？ | 说明 |
|---|---|---|
| 事件流只追加 `human_sign_events.jsonl` | **部分真实** | 多了一份"谁在何时做了什么签署/推翻"的不可改追加记录 → 可追溯。**但**本地 jsonl 有写权限即可直接改写（见下）。 |
| `principal_ok` 升级"文本+git 作者一致" | **弱真实** | 在 `log_overturned` 路径上，human 推翻者须与该卡最后 git 提交作者一致（fail-closed）。但 git 作者=自设身份（见下），单用户下=自绑。 |
| 事件可对账 | **真实但有限** | 事件流与卡 frontmatter 的 `status_history`/`verified_by` 可交叉核对，发现"卡说已签、事件流无记录"的不一致。 |
| 本地 hash-chaining（每条含前条哈希） | **真实但只防意外** | 文件内篡改（改历史行/乱插）会断链。**但**攻击者重算全链即可（无第三方锚，哈希链本身不抗"拥有全文件写权"的人）。 |

**诚实结论**：T3 相对 PoC-3 **净增了"可追溯 + 防误签 + 防弱模型静默伪造"**，这些是**真实且有价值**的——尤其对"手滑误签 / 弱模型苦力无意改坏署名"这两类（见 Q1 分级）。但它**没有**把威胁模型从"自断言"升级为"抗抵赖"。

---

## 3. 防不住的（诚实威胁模型边界）

1. **git 作者自设**：`git config user.name/email` 任意设 → "git 作者一致"只是与"自设身份"一致；单用户下同一人持所有身份，绑定 = 自绑。
2. **本地 jsonl 直改**：有写权限即可改/删事件流；hash-chaining 只防"不知链结构"的乱改，攻击者重算全链绕过。
3. **无第三方时间戳**：事件里的 `ts` 是本地 `time.strftime`（L435），自断言，可回拨。
4. **单人无法真四眼**：见下，单人阶段的"人签"本质是"人对自己（或模型生成）建议的复核"。

→ **相对"有写权限的蓄意攻击者"，T3 不增加实质抵抗**（与 Q1 同根：本地仓库写权即根）。

---

## 4. 单人场景如何模拟四眼（诚实替代，N 档）

- **异步自我复核**：签署与复核分两次会话/隔段时间，降低"边写边签"的手滑。
- **强制冷静期**：签署事件与推翻事件之间设最小间隔阈值（机器可查），抑制冲动操作。
- **带外确认**：在另一个介质/设备做二次确认（仍是同一人，但提高"无意误签"成本）。
- **异模型复核**：用**异族模型**做 second opinion（非同谋，呼应本任务"异族"设定）——这是单人场景下**唯一接近"独立第二意见"的机制。

> 这些降低"accidental / weak-model"风险，**不降低"malicious-with-write-access"风险**。

---

## 5. 外部实证：人对自动化建议的过度依赖（直接支撑威胁模型）

- **[ES10] NEJM AI 2026 RCT**（*Automation Bias in LLM-Assisted Diagnostic Reasoning…*，AIoa2501001，2026-04-23，一手随机对照试验）：44 名医生、单盲 RCT（2025-06-20 至 08-15），即便完成 20 小时 AI 素养培训，接触 LLM **错误**诊断建议仍使诊断准确率下降约 **14 个百分点**。→ 直接证明"人对自动化/模型建议会橡皮图章式过度依赖（automation bias / rubber-stamp）"。
- **对本仓的含义**：单人阶段的"人签"常常是在复核**模型生成的建议/署名**，NEJM 实证说明这会系统性地 rubber-stamp。因此"人签机制"的诚实边界必须写明：**它防 accidental/weak-model，不防 malicious，且在单人下易受 automation bias 影响而流于形式**。

---

## 6. 结论与档位

- **N 档（现在可做）**：落地 T3 的事件流 + hash-chaining + 冷静期 + 异模型复核；在文档显式标注"单用户下为自绑增强，非抗抵赖"。
- **W 档（该等）**：真正的"四眼 / 抗抵赖 / 第三方时间戳"必须等多主体场景（多人署名、异模型独立签署、第三方时间戳服务）。单用户无密钥下**不该假装拥有**这些保证。

> 否掉方向也算交付：不要把 T3 包装成"解决了人签可信问题"。它解决的是"可追溯 + 防误签"，**不是**"身份可信 + 抗抵赖"——后者是 W 档。
