# 647 E2 · 阙疑用于**嵌入式 C/C++** 的适配调研（**只调研，不建卡**）

> 承接 `docs/c_domain_adaptation_647.md`：那篇讲"语言的 C 化"，本篇讲"**跑在裸机/RTOS 上的 C/C++**"。
> 本文件**不产出任何卡片/规则**。

---

## 一、嵌入式比"普通 C"多出来的四类问题（实测口径）

| 维度 | 桌面 C 的做法 | 嵌入式的现实 | 对阙疑的影响 |
|---|---|---|---|
| **编译器** | `gcc/clang` 本地可跑 | **交叉编译** `arm-none-eabi-gcc`（主机 ≠ 目标） | 探针要区分"**编译通过**"与"**在目标上可运行**"——后者通常**测不到** |
| **资源** | 内存/栈无限 | RAM 几十 KB、栈 1–4 KB、Flash 有限 | 卡片必须能表达"**这个写法在小栈上会炸**"这类论断 |
| **实时性** | 无时序约束 | ISR / 优先级反转 / 抢占 | "正确性"里要含 **时序正确性**（普通 C 不需要） |
| **编译器扩展** | 标准 C 足够 | `__attribute__((...))` / `#pragma` / 内联汇编 | 卡片里会出现**不可移植**的写法 ⇒ 需要"可移植性"分档 |

## 二、适配点（对现有 67 规则 / 工具的影响）

### 2.1 规则层：**零改动仍是结论，但要新增"嵌入式卡级规则"**

复用结论同 E1（67 条审的是卡+证据，与语言无关）。新增建议（前缀 `EMB-*`）：

| 主题 | 论断形态（要能被证据支撑） | 建议新规则 |
|---|---|---|
| ISR 里禁止阻塞 | 中断上下文不得调用阻塞 API（`malloc`/`printf`/互斥量） | `EMB-ISR-NO-BLOCK` |
| volatile 与 MMIO | 寄存器访问**必须** `volatile`，缺了就是 UB | `EMB-VOLATILE-MMIO` |
| 栈用量可证 | 大数组/递归要有**栈用量证据**（`-fstack-usage` 或静态估算） | `EMB-STACK-BUDGET` |
| 浮点/除法代价 | 无 FPU 的 MCU 上浮点是软件模拟 | `EMB-FPU-COST` |
| 位域/打包 | 与硬件寄存器布局绑定时必须 `static_assert` 校验 | `EMB-REG-LAYOUT` |
| 中断与共享数据 | 主循环/ISR 共享变量的原子性（`volatile` **不**等于原子） | `EMB-SHARED-ATOMIC` |
| 启动/链接脚本 | 段布局（`.data` 拷贝、`.bss` 清零）依赖启动代码 | `EMB-STARTUP-SECTIONS` |
| 编译器扩展卫生 | `__attribute__` 用法与可移植性分档（GCC/Clang 差异） | `EMB-ATTR-PORTABILITY` |

### 2.2 编译器与证据源

| 项 | 需要做什么 | 难点（诚实） |
|---|---|---|
| 交叉编译器 | 探针加 `arm-none-eabi-gcc`（`-mcpu=cortex-m4 -mthumb -nostdlib` 之类） | **需要本机装工具链**；且"编译通过"≠"能在板子上跑" |
| 目标实跑 | `qemu-system-arm` / 真板 | 647 环境**没有**这些 ⇒ 真实"目标实测"**留 648+ 且需人提供环境** |
| 反例 | `-fsanitize=undefined` 在**交叉编译**下多数不可用 | 反例只能退化为"**桌面复现 + 标准条款**"（诚实降级） |
| 标准 | C 标准 + 各家 ARM 文档（ARM ARM / CMSIS） | **ARM 文档授权**需人核（同 E1 的标准源问题） |

### 2.3 证据等级（L1–L5）的**口径要扩**

现有分级（`evidence_base_644.grade_from_source`）：L1 = **多编译器实测**（≥2 编译器）。
嵌入式的问题：**双编译器都可能"编过"却都在真机上炸** ⇒ 建议**扩一档**：

```
L0  真机实测（板上跑通 + 观测输出）      ← 嵌入式的新最高档（647 未实现）
L1  多编译器实测（含交叉编译器）
L2  标准/官方文档条款
L3  社区共识
L4  单点来源
L5  未验证
```

**这是 E 线最重要的结论**：**"能编译"在嵌入式里不是"对"的证据**。
⇒ 648+ 若要真做嵌入式卡，**必须先决定 L0 的获取方式**（真板/仿真器/CI 硬件），否则卡片只能停在 L1。

## 三、工作量与风险

| 项 | 估计 | 前置条件 |
|---|---|---|
| 交叉编译器探针（arm-none-eabi-gcc） | 1 人日 | **本机装工具链**（未验证是否可装） |
| 目标实跑（QEMU/真板） | 2–4 人日 | **环境**（真板/仿真器）与 CI 硬件 |
| 嵌入式卡级规则 8 条 | 4 人日 | 需要"栈用量/ISR"这类**可测量**的证据来源 |
| 证据分级扩 L0 | 1 人日 | 先定 L0 获取方式 |
| 嵌入式卡 10 张 | 5 人日 | 同上 |
| **合计** | **≈13–15 人日** | — |

**诚实登记**：
1. **本机未验证 `arm-none-eabi-gcc` 是否可装**，也未跑过任何交叉编译 —— 本文的一切都是**调研推断**；
2. **"真机实测"（L0）在本环境完全不可得** ⇒ 这是嵌入式路线**最大的硬约束**，比写规则难得多；
3. **ARM/CMSIS 文档授权**未核（同 E1）；
4. 嵌入式"正确性"含**时序正确性**，而现有阙疑模型**只有功能性判决**（pass/fail/unknown）⇒
   要不要引入"时序维度"是**模型级决策**，属交人项，本批**不做**。
