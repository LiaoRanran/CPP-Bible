# UVK 纲领 · 持续进化的最小可信内核

> **Universal Verification Kernel（通用验证内核）设计纲领**
> 立此文档的批次：**642**（阶段 B1）。依据：v29 究极大规模调研（`_arch_v29/`，20 方向 / 27 文件）。
> **本文是设计纲领，不是代码**；它约束 643+ 的实现取舍，本身不产生任何判决行为。

---

## 序 · 为什么不能"通用"

v41 的原始愿景是「**通用内容验证器**」：不限领域、自动判定任意卡片/规则/误解图的正确性。v29 的
跨域调研把这一愿景**在数学上钉死**为不可达：

| 钉子 | 内容 | 它否证了什么 |
|---|---|---|
| **Rice 定理**（B1） | 程序的任意**非平凡语义性质**不可判定 | "判定任意内容的语义正确性"无算法 |
| **哥德尔第二不完备**（D4） | 足够强的形式系统不能内部证明自身一致 | "验证器证明自己正确"不可能 |
| **NFL / 无免费午餐**（B1/B2/C2） | 无普适最优归纳器；必须绑定领域先验 | "一个策略/规则集通吃所有领域"不可达 |

三角合围的结论是：**"全能验证器"不存在**。因此本纲领把目标从**判定的内容**改为**架构**：

> **UVK 不是"知道一切的验证器"，而是"一个永不自证、永不全信、永不 fail-open、持续进化的
> 最小可信内核 + 由独立验证者与领域插件补齐的能力"。**

---

## 一、永不自证（No Self-Justification）

**规则**：验证器**不验证自己的正确性**。内核、规则、保护器、账本写入路径的一致性证明，
必须来自**内核之外**的主体（独立验证者 / 外部签名 / 第三方重算）。

**为什么**（数学依据）

- **D4 哥德尔第二不完备**：一个足够强的系统无法在内部构造自身一致性的证明。让验证器
  "自证自己没错"在原则上就不可能，它不是工程懒惰，是**数学禁令**；
- **D4/A2 自指闭包死路**：任何"验证器验证验证器"的自指结构最终都需要一个**循环外**的锚点，
  否则只是把不可判定的问题搬了个家（v29 总览 §五）。

**本仓库的落地形态（截至 642 的实证）**

| 机制 | 位置 | 状态 |
|---|---|---|
| 内核零领域依赖的 **AST 机械证明** | `tools/queyi_core_v10_641.py::verify_no_domain_imports` | ✅ 已在 641 门禁与 642 门禁中作为检查项 |
| **信任根传递闭包**：任一文件缺失即 FAIL | `tools/verifier_closure_641.py`（23 文件） | ✅ 631/641 落地 |
| **独立验证者**（零 import 本项目工具、纯标准库朴素重算） | 628 B1 | ✅ 落地（独立性等级 **L2**，见 §六） |
| **外部可验证签名**（HMAC 凭证 → RSA-2048 双签） | 628 B2 / 629 C1 | ✅ 落地；**公私钥同主体 ⇒ 算法独立 ≠ 信任根独立**（已登记缺口） |
| **透明日志**（append-only 哈希链 + inclusion） | 628 B3 | ✅ 落地（含生产日志隔离开关） |

**禁止**：把"自检通过"当作"验证器正确"的证据。**自检只能证明不变量没被违反，不能证明不变量选对了。**

---

## 二、永不全信（No Single-Source Trust）

**规则**：**任何单一验证结果都需交叉确认**。单一验证者、单一报告、单一数字，都不构成结论；
必须由**来源独立**的第二方复算或签名背书。

**为什么**

- **A3 分布式共识 / BFT**：容错需要 `3f+1` 个**异质**节点才能容忍 `f` 个拜占庭节点；
  单节点（f=0）无法构成真 BFT —— 这是 v22 已证、v29 深挖的结论；
- **A1 门限签名**：`t-of-n` 的意义在于**降低单点**，而不是提高单点强度；
- **E2 验证器是被攻击面**：用 LLM 做语义验证时，验证器本身就是首要攻击目标，
  把它当可信黑盒必然失守。

**本仓库的落地形态**

| 机制 | 位置 | 状态 |
|---|---|---|
| 双路交叉校验（现算 vs 读产物，输出 `consistent`） | `tools/w2_authority_640b.py`、`w2_derived_640c.py` | ✅ 落地 |
| 独立验证者 vs 系统自带验证的一致性比对 | 628 B1 | ✅ 落地 |
| 「算法独立 ≠ 信任根独立」显式登记 | 629 C1 / 631 E2 | ⚠️ **缺口**：公钥托管与外锚仍交人 |
| 验证器攻击面 8 层 × 35 向量 + 探针覆盖 24/35 | 629 B1–B3 / 631 D2 | 🟡 部分覆盖 |

**禁止**：用"同一份实现跑两遍"冒充交叉确认（同源耦合不是独立性）。
**当前诚实边界**：本仓库的独立性等级为 **L2**（零 import + 朴素重算），**未达 L1/L3/L4**（见 §六）。

## 三、永不 fail-open（Never Fail Open）

**规则**：**信任根缺失 / 验证器异常 / 数据不可读 ⇒ FAIL（或降级为"未知"，绝不降级为"通过"）**。
默认值是**不通过**；任何"跳过检查即视为通过"的路径都是缺陷。

**为什么**

- **E4 安全架构**：fail-open 是经典反模式（v29 死路总汇明列）；
- **E1 工程安全**：故障默认应转人审、不开火，而不是放行；
- **C3 决策理论**：本项目的损失是**不对称**的 —— 漏报代价 >> 误报代价
  （逃逸率 0.0711% × 自身免疫率口径的不对称倍数曾实测达 1406.5×，629 D3），
  因此任何不确定都应偏向"拦住"而非"放过"。

**本仓库的落地形态**

| 机制 | 位置 | 状态 |
|---|---|---|
| 信任根闭包**缺失即 FAIL**（不是 warning） | `tools/verifier_closure_641.py::simulate_missing` | ✅ 641 D2 落地 |
| 内核未注册投影 ⇒ **`KeyError`（fail-loud，不静默兜底）** | `tools/queyi_core_v10_641.py::project` | ✅ 641 落地（642 修正了它的自检断言） |
| 禁止"静默删除"（会话清理器：tracked 不删、名单外保守保留 + 留痕） | 根级 `conftest.py`（640 A5） | ✅ 落地 |
| 工具完整性：`tools/.tool_checksums` + Merkle + 尺子 | `tools/tool_integrity.py` | ✅ 落地 |

**已知 fail-open 残留**（642 B3 全量审计的输入，见 `data/642_fail_open_audit.md`）：

1. `tool_integrity` 的 `SUPPLY_CHAIN_FILES` 缺失时**只警告不失败**（GPT 审核指出）；
2. `DecisionEvent.from_dict` 对**缺字段使用默认值**（GPT 审核指出）⇒ 缺失被静默补全。

> **本批只审计不修复**（铁律 §七.5）：修复留 643。

## 四、最小可信内核（Minimal Trusted Core）

**规则**：内核**只做协议 / 账本 / 闭包**；一切领域知识、规则内容、能力扩展都通过**插件/适配器**
注入。内核越小，可被形式化验证的面越小，TCB（Trusted Computing Base）越可信（v29 A4）。
内核能力与插件能力的边界一旦含糊，TCB 就会膨胀。

**本仓库的落地形态（641 内核的实测构成）**

| 层 | 内容 | 归属 |
|---|---|---|
| **内核必须** | 内容寻址（`Artifact`）、证据原语（`Evidence`）、四态判决（`Decision`）、运行协议（`VerificationRun` 构建/封存/只读/自哈希）、**投影派生**、依赖方向的 AST 机械证明 | `queyi_core_v10_641.py` |
| **必须是插件** | C++ 解析与规范化、67 条规则的具体判定、W2/PCK/dashboard/textbook 投影、证据复验实现、沙箱攻击器、Authority 账本实现 | `queyi_core_cpp_641.py` / `queyi_core_toy_641.py` + CORE_TOOLS 适配 |

**内核硬约束**（641 已建，642 与 643+ 不得破坏）

- **零领域 import**：由 `FORBIDDEN_DOMAIN_MODULES` 黑名单 + AST 扫描**机械证明**，非口头声称；
- **适配器不反向依赖**：内核不认识 `gate_engine` / `poison_drill` / `authority_v2_*`；
- **无占位抽象**：端口/原语必须被真实使用，无人实现的抽象应**回退**而非保留（641 §五.8）。

`data/642_kernel_minimality_audit.md` 给出逐项最小性审计与**建议移出清单**（只出报告，**不实际移**）。

## 五、持续进化（Continuous Evolution）

**规则**：**内核稳定，外围可替换**。规则、保护器、验证者、投影都必须是可插拔、可回滚、
可版本化的；进化遵循"显式偏置 + 抗遗忘 + 不可判定残留交人"，而**不是**"越学越强"的线性迷信。

**为什么**

- **C1/C2**：可学习性有边界；NFL 意味着必须**显式声明归纳偏置**，偏置错配的负迁移比无偏置更糟；
- **C4**：灾难性遗忘 ⇒ 进化必须带**回放**与**双记忆**；
- **D2 库恩/拉卡托斯**：真实的进化是"硬核不变 + 保护带调整 + 偶发范式革命"，不是平滑累积；
- **B1/D4**：不可判定残留无法被"学掉"，只能被**显式路由**到人审 oracle + 超时兜底。

**本仓库的落地形态**

| 机制 | 位置 | 状态 |
|---|---|---|
| 规则**外置加载**（内核只做确定性遍历/汇总，判定由 evaluator 注入） | 641 `RuleEngine` / `queyi_core_cpp_641.py` | ✅ 落地 |
| 投影**可注册**（内核只内置 3 个领域无关投影） | 641 `register_projector` | ✅ 落地 |
| 保护器**灰度上岗 + 可回滚**（flag 只标记、block 未实现、标记可叠加与按件摘除） | 642 A1–A6 | ✅ 落地（有效性待 643+ 实证） |
| 规则准入**门槛**（MDL 长度 + 豁免率；被拒规则保留可人工改判） | 642 A5 | ✅ 落地 |
| 规则/工具的**版本台账**与完整性重钉 | `tool_integrity` + Merkle + 尺子 | ✅ 落地 |
| 闭环**校准度**追踪（采纳率的事后验证） | 637/638 → 642 C2 | 🟡 起点（样本 2→3 点，不足以判趋势） |

**禁止**：把"内核也一起改掉"当作扩展手段。**能力扩展必须发生在插件侧；内核改动必须独立成批、
独立证明、独立重钉。**

## 六、独立性等级（本纲领的诚实刻度）

"独立"不是布尔值。为避免自欺，本纲领固定四级刻度，任何"我们做到了独立验证"的说法必须**标级**：

| 等级 | 定义 | 本仓库现状 |
|---|---|---|
| **L1** | 信任根独立：不同主体持有密钥 / 外锚 | ⛔ **未达**（公私钥同主体；外部锚交人） |
| **L2** | 实现独立：零 import 被测工具、朴素重算 | ✅ **已达**（628 B1 / 629 C3 AST 证明） |
| **L3** | 方法独立：不同算法/不同理论路径 | 🟡 部分（RSA/HMAC 属不同原语，但同主体签发） |
| **L4** | 主体独立：人类评审者与机器分离 | ⛔ **未达**（独立人类确认强度仍为 0；真实 Blind Review 待授权） |

> **642 新增的读法**：本批把 A3 盲评协议**工具化**了（`blind_protocol_642`），但**没有**产生任何
> 真实盲评数据 ⇒ **L4 仍未达**。工具存在 ≠ 独立性存在。

## 七、与 v25 七对象 / 641 Core 的衔接

| v25 对象 | UVK 归属 | 说明 |
|---|---|---|
| `Rule` | **插件** | 规则内容外置；内核只提供 `RuleEngine`（确定性遍历/汇总） |
| `ProofObject` / 证据 | **内核原语 + 插件实现** | 内核定义 `Evidence`/`EvidenceResult` 结构；复验实现属插件（`EvidencePort`） |
| `ErrorFlow` / 校准 | **插件（保护器）** | 642 A4 校准追踪器；内核不认识"错误率"概念 |
| `Lifecycle` | **插件** | 卡片生命周期是领域语义；内核只记 `Decision` 四态 |
| `ConflictDetector` 等保护器 | **插件（保护器层）** | 642 A1–A6；**内核不得 import 保护器** |
| `CalibrationTracker` | **插件（保护器层）** | 同上 |
| `Ledger` | **内核协议 + 插件实现** | 内核定义 `AuthorityPort`；append-only 实现由领域插件/账本工具提供 |

**一句话**：**内核 = 协议 + 原语 + 运行记录 + 机械不变量；其余一切都是插件。**

## 八、死路清单（引 v29，供 643+ 避坑）

1. **通用验证器**（Rice/停机/D4 不完备）——目标本身不可达；
2. **全量形式化**（A2 成本 / D4 希尔伯特失败）；
3. **单点信任 / 单用户真 BFT**（A3 需 3f+1）；
4. **TEE/机密计算当信任根**（信任根仍在厂商）；
5. **验证器当可信黑盒**（E2）；**数据投毒静默学坏**（E2/C4）；
6. **fail-open 反模式 / 隐式单点信任**（E4）；
7. **自然语言规则无形式语义**（D3）⇒ 必歧义；
8. **纸面合规 ≠ 真安全**（E1）；**红蓝不复盘 = 演戏**（E1）；
9. **偏置错配的负迁移**比无偏置更糟（C2）；
10. **Kolmogorov 复杂度不可计算**（B2）⇒ MDL 编码选择必然带主观性，只能**声明口径**。

## 十、诚实登记

1. **本纲领是设计原则，不是已实现的能力清单**：上表中标 🟡/⛔ 的项都是**缺口**，
   不是"已达成"；把纲领当成绩汇报即是自欺；
2. **落地需要多批次**：642（纲领化）→ 643（审计与首批修复）→ 644+（信任根独立、真实盲评、
   跨领域）；
3. **UVK 的"通用"是架构通用，不是判定内容通用** —— 后者已被数学否证（§序）；
4. **L1/L4 不在本仓库单方面可达**：需要外部主体（第三方托管公钥、真实人类盲评者），
   机器不代签、不冒充（铁律 §零.4）；
5. **本文件不改变任何判决、规则、账本**；它只约束后续实现的取舍。
