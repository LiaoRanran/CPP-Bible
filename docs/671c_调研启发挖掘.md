## 2. Top 10 启发点（按价值排序）

### 2.1 启发点 1 · e-process / e-value：为"边扩样边看"的账本提供 anytime-valid 统计地基

- **来源**：`_arch_v47/44_序贯检验e-process.md` §核心结论 1–3、§三（peeking 危害）、§四（CELEUS 竞品表）、§五（betting 算法 + 门槛 20）。
- **内容**：e-process 在**任意停时**保持 Type-I 保证（Ville 不等式，α=0.05 拒绝门槛 e-value≥20）；holdout 从 16→30→100 扩样时**不需要重新校正 α**；e-value **可乘、可跨批合并**，每新增一批判决 append 一个 e-value、乘积仍有效——与 452 条 append-only 账本天然同构。文件同时给出硬约束：同水平一次性检验门槛约 3.14，anytime-valid 代价是约 6.4 倍似然比门槛（功效损失，必须明说）；且 CELEUS（arXiv:2606.20820）已把 e-process 用于 LLM 评测，**禁止声称"首次用于评测"**，差异化只能是"对知识断言（而非模型分数）做 anytime-valid 判决 + 第三方离线复算"。
- **反哺论文**：§8 Statistical 层新增一条威胁"**非 anytime-valid 的扩样报告（peeking）**"——文件 §三引 John/Loewenstein/Prelec 2012：56% 心理学家承认看结果后决定是否补数据；power posing 的"25→10→7→5"分块可直接作引文。§7.3 扩样讨论改用置信序列口径。未来工作（现 §10/§7.3）：账本 e-value 累积曲线是"自动演化"故事的统计骨架。
- **反哺系统**：数据层账本条目新增 `e_value_cum`、`wager_lambda` 字段；新建与内核解耦的 `eprocess.py`（文件 §五给出可直接实现的 betting 更新式），验收标准是零假设下 10,000 条×100 长度仿真的越界经验频率 ≤0.05。
- **可行性：中**（算法约 1 天，但仿真校准 + 决定是否进论文主文需 1 周量级）。
- **具体建议**：论文不把 e-value 当主结果（n=16/32 下功效损失扛不住），而作为"扩样协议的预先承诺"写进评估协议与 §8；Related Work 必须引用并差异化 CELEUS。

### 2.2 启发点 2 · "P=R=F1=0"不是结果而是 bug：分母为零必须报"未定义"

- **来源**：`_arch_v47/45_缺失数据处理方法.md` §核心结论 3、§五（"全无命中"的正确处置）、行动 2。
- **内容**：sklearn `precision_score` 在 `TP+FP=0` 时**默认返回 0 并发 UndefinedMetricWarning**；`zero_division` 取值 {warn,0,1,nan}，`nan` 在 1.3 版才加入。反事实算子 P=R=F1=0 极可能是踩了默认值——"系统零命中"被伪装成"性能为零"，与"该层无真错样本"（R 未定义）是**含义完全相反的两件事**。文件给出处置优先级：① 报原始计数 (TP,FP,FN,TN)；② 显式写 undefined 并注明原因；③ 禁止 `zero_division=1` 刷成 1；④ compile_fail/nondeterministic/inconclusive 与 label_missing 分列。
- **反哺论文**：§6.5/§7.1 反事实结果重述；§8 Construct 层新增"**未定义指标被静默填 0**"；Evaluation 增加"缺失与未定义"小段（文件行动 3 的三句固定写法可直接用）。
- **反哺系统**：验证器反事实算子：`zero_division=np.nan`，改用 `precision_recall_fscore_support` 取 support 分母，输出三元组 (计数, 比率或 undefined, 分母)；验收："零命中"与"无真错"输出必须是不同字符串。
- **可行性：中**（定位调用点 + 改 + 回归约 2–3 天；但红线禁止本批改，建议交 671a 排期）。
- **具体建议**：这是 669 Top30 未覆盖的新缺陷类别，与 31（算术不自洽）同级别，建议提为新的 P0/P1 核查项。

### 2.3 启发点 3 · Merkle 叶子/内部节点域分隔（0x00/0x01）是必须立即核查的硬缺陷候选

- **来源**：`_arch_v47/56_数论在哈希密码中的应用.md` §核心结论 2、§一（RFC 6962 §2.1 逐字规范）；`65_Merkle树在数据库中的应用.md` §核心结论 3。
- **内容**：RFC 6962 规定叶子哈希必须是 `SHA-256(0x00‖leaf)`、内部节点 `SHA-256(0x01‖L‖R)`，原文逐字："This domain separation is required to give second preimage resistance." 若实现把叶子直接喂 `SHA-256(leaf)`，33 字节的内部节点哈希可被当作"叶子"重放，攻击者**不破坏任何哈希**即可伪造包含证明。同文给出 452 条规模的证明尺寸：单条包含证明 ≤9 个节点 ≈ **288 字节**——选 Merkle 的理由是证明可贴进论文附录/可离线搬运，不是性能。65 同时警告：**一致性证明只证明"账本未被篡改"，不证明"判决正确"**，论文必须把 integrity 与 validity 拆成两条独立主张（防 §8 overclaim）。
- **反哺论文**：§8 T10 残余风险"OTS 是占位"之外，补"完整性≠正确性"显式声明；§4.5/附录可放 288 字节证明样例。
- **反哺系统**：数据层/独立对账器：核查 `merkle_checkpoint` 等价模块是否带 0x00/0x01 前缀（预计 30 分钟代码审计）；非 2 的幂分割点 k 是否按 RFC（小于 n 的最大 2 的幂）。
- **可行性：高**（半天内可完成核查；若实现正确则零成本获得一条"已对照 RFC 6962 审计"的复现卖点）。
- **具体建议**：核查结果无论对错都写进论文复现附录；实现语言应直接引用 RFC 6962 而非自造描述。

### 2.4 启发点 4 · 哈希必须基于 JCS 规范化字节 + 逻辑全序，不能基于 JSON 文本/.db 文件

- **来源**：`_arch_v47/75_存储格式选型JSON_Parquet_Arrow.md` §核心结论 2（JSONL）、§核心结论 3（RFC 8785 JCS）；`73_数据库索引设计.md` §核心结论 3。
- **内容**：① `{"a":1,"b":2}` 与 `{"b":2,"a":1}` 语义相同但 SHA-256 不同——任何换 JSON 库重序列化都会让账本哈希变化，直接摧毁"判决可复算"；解法是哈希前做 RFC 8785（JCS，2020-08）规范化。② JSONL 一行一事件使新增判决在 `git diff` 中恰为一行 `+`，JSON 数组会产生 3 处噪声改动。③ 索引/VACUUM 影响 .db 字节布局，**不能拿数据库文件哈希当账本哈希**；对账器必须强制按 `seq` 全序扫描（不走索引），哈希输入是 canonical 序列化后的逻辑条目序列。
- **反哺论文**：§4.4 provenance/§8 T5 口径漂移补上规范化协议；附录 D 复现命令加"规范化哈希"说明。
- **反哺系统**：数据层（账本当前是 JSON 行）：引入 JCS 规范化函数并冻结版本号；对账器全序扫描；人读美化版与哈希字节版分离存储。
- **可行性：高**（规范化 + 一个全序读取约定，1–2 天；需要存量 452 条一次性重锚，注意与 671a 排期协调）。

### 2.5 启发点 5 · 规则版本钉扎：每条账本事件必须带 `rules_manifest_sha256`

- **来源**：`_arch_v47/74_数据迁移方案.md` §核心结论 3（rule-version pinning）；`54_模型论与形式语义.md` §核心结论 3（模型 A 必须显式登记）；`64_append-only存储设计.md` §三 映射 1（事件字段建议）。
- **内容**：67 条规则必然演进；账本若只记判决结果不记"哪版规则判的"，第三方拿今天的规则**无法复算一年前的判决**。做法仿 Confluent Schema Registry：每条事件新增 `rules_manifest_sha256`；schema 迁移只追加新字段、永不改写旧条目。54 从模型论角度给出同构要求：Löwenheim–Skolem 决定了有限断言无法唯一锁定"C++ 语义"这个模型，因此被判定模型 A（编译器版本、标准版本、执行轨迹、规则快照）必须作为账本一等公民字段，而不能靠断言集合反推。64 给出完整字段清单（seq/ts_utc/card_id/rule_id+版本/protector_id/verdict/evidence_ref/input_content_hash/crc32c/prev_event_hash）。
- **反哺论文**：§4.4 semantic scope 强制拆分的自然延伸；§8 Temporal 层"样本老化/环境漂移"缓解项增加规则快照哈希。
- **反哺系统**：数据层账本 schema 增字段；门禁可加一条 P0：无规则快照哈希的事件不得入链。
- **可行性：高**（加字段 + 写入侧改动约 1–2 天；存量回填另计）。

### 2.6 启发点 6 · SQLite WAL-reset bug（<3.51.3）与单写者纪律：不做就可能损坏账本

- **来源**：`_arch_v47/62_SQLite在验证系统中的应用.md` §核心结论 1（WAL+FULL）、§核心结论 2（WAL-reset bug）；`69_数据库事务与一致性.md` §核心结论 2（macOS 系统 SQLite 默认 NORMAL）；选型支撑见 `61_关系型vs文档型vs图数据库.md` §核心结论 1–2、`71_嵌入式数据库选型.md` §核心结论 3。
- **内容**：① SQLite 3.7.0–3.51.2 存在 WAL-reset 竞态（两个连接同时写/checkpoint 可损坏库文件），3.51.3（2026-03-13）修复——**内核与独立对账器若同时以写方式打开同一库，正好命中触发条件**；行动：查版本，或保证对账器只读。② 账本应用 `journal_mode=WAL` + `synchronous=FULL`（WAL 下 COMMIT 时 fsync 失败只损失持久性不损坏库）。③ macOS 自带 SQLite 3.43.2 默认 NORMAL，官方承认断电会回滚已提交事务——"452 条已落盘"在该环境不成立，是可写进 §8 的真实威胁。④ 选型结论明确：566 个节点/2–3 跳遍历规模下 SQLite 递归 CTE 10K 节点才 0.8–18ms，图数据库/时序库/DuckDB/Lakehouse 全部不需要（61/67/68/71/72 一致结论）。
- **反哺论文**：§8 Temporal/Internal 层补"环境默认配置可静默弱化持久性"；复现包声明 SQLite 版本下限。
- **反哺系统**：数据层：一条命令查版本；对账器连接串强制 `mode=ro`；若账本未来从 JSON 行迁 SQLite，按 64/71 的"SQLite WAL + 应用层哈希链"双层结构。
- **可行性：高**（版本核查 + 只读连接，半天）。

### 2.9 启发点 9 · t-way 组合覆盖：67 条规则两两交互全覆盖只需 12 次内核运行，三三交互 39 次

## 7. 对未来调研的建议

1. **先有判决再调研：每篇调研产出必须强制三格落位**——"进论文哪一节 / 进系统哪个模块 / 淘汰"，落不进任一格的选题不立项。本批 57 篇淘汰篇的共同特征就是写作时没有这三格。
2. **冻结一切泛化方向**：仿生、分布式、DB 换型、DL 方法（NAS/FL/RL）在系统规模发生量级变化前不再开题；669 终评已证明规模与价值强负相关（v37 综合 8.7 vs v45/v46 2.3），本批再次验证：154 篇里新挖出的硬点全部来自"带着项目具体缺口查的具体问题"（WAL bug、RFC 前缀、zero_division 默认值），没有一个来自宏大叙事。
3. **保留 v47 gems 的写作模板**：带项目锚点数字 + 逐字引文 + 可运行代码/数字表 + 三条带时间点的行动 + 诚实盲区。32/33/43/44/45 之所以高密度，正是这套纪律的产物；泛泛综述（148/149/150 类）零行动。
4. **同主题跨轮重述设上限为 1 篇**：v42→v44→v45→v46 的统计/ablation/threats 四重讲述是最大浪费；新调研必须先引用并 diff 已有篇目，新增信息量不足即不写。
5. **调研-落地间隔设 24–72 小时对账**：669 诊断的核心病根是"结论停在规划里没执行"。以后每篇调研写完立即在任务系统建对应行动卡或显式标"冻结/淘汰"，不允许"先存着以后看"——本报告 §5/§6 两张表就是对存量 154 篇的一次性补对账。
6. **威胁类调研按"当前攻击面是否存在"过滤**：97/98/100 一类以 ML/多中心为前提的攻击，在系统是纯规则+编译器时不立项；每 3 个月随架构变更重估一次即可（147 的季度复审机制）。
