## 0. 阙疑尾部层现状（本仓库实读口径）

- 813 行纯逻辑核心（brief 口径）：四态判决合成、冲突改判（B1）、MDL 准入（B5）、校准（B4）、账本追加与锚定；queyi-core 拆分有"两份并列"债（v33 T3/T6）。
- 已有轻量验证：M1–M7 变异阴性测试、Hypothesis stateful PBT 已登记（v33 T6）、golden 重放、452 事件账本；无任何机器检查证明。
- L0 是真机编译器与标准条款，核心本身的错误模式 = 错判（把 fail 判 pass 或反之）、账本分歧、保护器失效。

**总判断**【推断】：2024–2026 形式化工业的账单已经很清楚——**全证明是 10 人年量级的奢侈品，关键模块证明在 LLM 辅助下正在跌到 1 人年量级，而 stateful PBT+变异+模糊测试仍是性价比最高的第一层**。对 813 行核心，正确策略不是"要不要形式化"的二选一，而是按模块分三档：**证明 / 有界验证 / 密集性质测试**，边界划在"这个模块错一次的代价"上。

## 1. 三个标杆的真实账单：seL4、CompCert、Everest（问题 2）

### 1.1 seL4：从 20 人年到"综合验证"，账单随证明目标翻倍

- **功能正确性单点**【论文/官方】[S15]：约 8,700–10,000 行 C，约 **20 万人年**……准确口径：约 **20 人年**、200,000 行 Isabelle/HOL 证明；其中**第一个精化步骤（抽象规范→可执行规范）单独花了约 8 人年、117,000 行证明脚本**——概念上最难的部分集中在此。
- 早期 CACM 综述口径：33k Isabelle 行 + 14k Haskell/C，20 人年总投入；HACMS 论文（DARPA，Phil. Trans. R. Soc. A 2017）表格口径：10K LoC、480K LoP、13 人年开发期、性能 206 vs 227 cycles（验证版约 9% 开销）【论文】[S15]。
- brief 所引"94 人年"是 **seL4 综合验证**（功能正确性 + 二进制精化 + 完整性/机密性信息流 + 完备性 + 汇编衔接）多年累计口径，不是首证明成本——二者相差约 4–5 倍，引用时必须区分。
- **反面诚实记录**：IEEE Access 2023 综述指出 seL4 验证范围仍有限（配置、部分驱动、DMA、硬件不在证明内），TCB 仍含编译器（后接 CompCert）、汇编器、硬件 [S16]——**"已验证内核"不等于"验证了的系统"**。
- 关键工程经验（HACMS 总结）：可行的革命来自"**代码与证明共同设计**，而非事后验证既有产物"[S15]。

### 1.2 CompCert：账单最透明的样板——76% 的工作量是证明本身

- Leroy, CACM 2009（POPL 2006 初稿起约 5 年工作）：**42,000 行 Coq、约 3 人年**；构成分解：14% 编译算法、10% 语义、**76% 正确性证明**；每个编译遍 1,500 行以上证明【论文】[S17]。
- ERTS² 2016/2018 工业口径：证明增长到 **100,000 行 Coq、约 6 人年**；2015 起由 AbsInt 商业化；工业案例 MTU Friedrichshafen 核电站柴油发动机控制系统（IEC 60880 认证），用形式化证明换取 DO-178C/ISO 26262 类认证中的工具鉴定置信度——**证明的买家是认证体系，不是普通用户** [S17]。
- 账单含义【推断】：CompCert 的"每行产品代码对应证明行数"约 8–10:1（42k Coq 对应约 5k 编译器核心 OCaml/抽取代码），人年比约 3 人年 / 一个编译器。阙疑 813 行若按同密度粗估：纯证明工作量 6–10 人年——但 Verus/F* 的自动化程度已把这个比率压低（见 §2）。

### 1.3 Project Everest：工业级高保障软件的 5 年战役与"没证完"的部分

- 2016–2021，MSR+INRIA+CMU，F* 语言；目标是 verified HTTPS 的 drop-in 替换【官方】[S18]：
  - **HACL\***：每个原语证明内存安全、功能正确、secret independence（侧信道），提取为可读独立 C，部署进 **Mozilla NSS/Firefox、Linux kernel、mbedTLS、Python、WireGuard、Tezos、ElectionGuard**；
  - **ValeCrypt**：验证汇编（性能关键路径）；**EverCrypt**：统一 provider（agility/multiplexing）；部分性能追平或超过非验证库。
- **诚实记录**：TLS 握手（miTLS-fstar）的证明**始终未完成**，完成的是 record layer 与 key schedule（后者后在 Bert13/Rust 项目中机械化）；2025 年项目总结《Project Everest: Perspectives…》专门讲工业级高保障软件的取舍 [S18]。
- 遗产转向 Rust 验证：Hax、Verus、Aeneas 都是 Everest 系的后继——**F*→C 路线正在被 Verus→Rust 路线接替**，这是行业级风向标 [S18]。

### 1.4 标杆账单对照表

| 项目 | 产品代码 | 证明规模 | 人力（关键里程碑） | 产出 |
|---|---|---|---|---|
| seL4 首证明 | ~8.7k–10k 行 C | 200k 行 Isabelle | ~20 人年（首精化 8 人年） | 功能正确性；综合验证累计 ~94 人年 |
| CompCert | ~5k 行核心 | 42k→100k 行 Coq | 3→6 人年 | 商用验证编译器，认证抵扣 |
| Everest/HACL* | 数万行 F*/C/ASM | 与代码同构开发 | 5 年、多机构数十人团队 | 十亿用户部署；握手证明未完成 |

## 2. Verus+Rust 的 2025–2026 新账单：LLM 把证明成本压到了哪里（问题 1）

### 2.1 Verus 生态位与工业落地

- Verus 由 MSR 的 Chris Hawblitzel 与 MPI-SWS/ETH 系的 Andrea Lattuada 共同发起，社区含 MSR/VMware/CMU/ETH/UW/UMich/Wisconsin；**SOSP'24 Distinguished Artifact Award**【官方/论文】[S21]。
- 真实系统清单（2026 在研）：Utah 大学全特性微内核；Microsoft verified-storage（持久内存 durable logs）；**Anvil：Kubernetes controller 的 liveness 证明，OSDI'24 Jay Lepreau Best Paper Award**；Vest 等 [S21][v31]。
- 相对 seL4 栈的代差：Rust 本体给内存安全（消除一整类义务），SMT 自动化承担大量琐碎义务，线性类型（Linear Dafny/Verus ghost 机制）处理资源状态——规格仍要人写，但"证明义务"密度下降。

### 2.2 LLM 辅助证明的两个硬数据

- **VeruSAGE**（UIUC/CMU/MSR/UChicago，2025-12）【实测】[S19]：从 **8 个开源 Verus 验证 Rust 系统**抽出 **849 个证明任务**；最佳 LLM-agent 组合完成 **>80%** 任务；对一批人类专家尚未完成的证明任务完成率 **>90%**。成本以 token/轮次计（论文 §5.5），最强组合需要 hands-on 的 agent 编排而非单次提示。
- **VeriStruct**（Stanford/MSR/北大，2025-11）【实测】[S20]：11 个 Rust 数据结构模块，自动生成规格+修复，**10/11 模块、128/129 函数（99.2%）通过验证**。
- 边界（两篇共同的诚实声明）：数据结构与系统修补任务表现强；**规格本身是否表达了正确意图仍靠人**——LLM 帮你证明"代码符合规格"，不证明"规格符合世界"。

### 2.3 813 行 Python → Rust +（部分）Verus 的粗估【推断，非报价】

参照系：CompCert 人/行密度不适用（Coq 手动时代）；当代 Verus 项目无公开人年账单，但可锚两个点：
- 单纯**语言移植**（不加证明）：pydantic v2 核心 pydantic-core 是 Python→Rust 重写，团队规模小，官方口径性能 4–50×、中位 17×，无纯 Python 回退实现 [S24]；2026 年 agent 辅助移植已有极端案例（Bun Zig→Rust 约 50 万行、11 天、64 并发 Claude、100% 既有测试通过，由作者自述，经 Pydantic 官方文章转述，属【第三方/厂商】证据，仅示上限不可当预算）[S24]。
- 加证明：VeruSAGE 的 80% 任务自动完成意味着**人力主要花在规格建模与剩下 20% 难义务上**。

> 估算口径（明确标注【推断】，误差可能 ±2x）：
> - **只移植到 Rust（无证明）**：1 名熟 Rust 开发者 2–4 人月，前提是测试/黄金集冻结先行；
> - **移植 + 判决合成表/账本追加的 Verus 功能正确性证明**：4–8 人月（规格撰写占一半），LLM agent 可压掉 30–50% 证明编写劳动但压不掉规格评审；
> - **全核心证明到 seL4 式完整精化**：不建议，2–4 人年且学术价值大于工程价值。
> 性能收益对阙疑近零（判决不是 CPU bound，LLM 调用才是）——**重写的收益只在内存安全+可证明性+供应链可信，不在速度**。

## 3. 轻量形式化的置信度：stateful PBT + 变异 + fuzzing 能给什么、不能给什么（问题 3）

### 3.1 能给的：规模化找错能力有百万级运行实证

- OSS-Fuzz 百万会话研究（878 项目、约 112 万 fuzzing sessions，2025）【实测】[S23]：大量 bug 在接入持续 fuzzing **之前**就存在（早期检测率高）；覆盖率随持续运行继续增长，覆盖变化驱动新 bug 发现——持续 fuzzing 的价值曲线是"开头陡、长期不降到零"。
- OSS-Fuzz 早期大样本实证（316 项目、**23,907 个 fuzzer 发现的 bug**）【实测】[S23]：发现与修复都快，但 flaky bug、超时、OOM 问题突出；发现呈"间断均衡"（长期平静偶发尖峰）；多数 bug 损害可用性而非直接的机密性/完整性——**fuzzing 的甜区是崩溃/内存类，不是语义错判**。
- Lemieux（Berkeley 博士论文）的边界结论：现代 fuzzer 自动发现的大部分仍是 C/C++ 内存错且集中在浅层 parser；深路径需要结构化变异 [S23]。
- PBT/stateful PBT 的工业证据（v33 已立）：OSDI'14 多数生产故障可被测试复现、多数故障需动作序列诱发——这正是 stateful PBT 的靶心 [v33-S53]；Hypothesis RuleBasedStateMachine 是该层的现成工具。
- 变异测试（mutation testing）在阙疑已落地为 M1–M7；学术侧 Teralizer 显示变异引导可把单测泛化到 PBT（+1–4pp），但开发者手写测试 80% 基线不动——**变异更像校验测试集充分性的尺子，不直接产正确性** [v33-S54]。

### 3.2 不能给的：三条硬边界

1. **无缺席保证**：测试/fuzzing 只能显示 bug 在场（Dijkstra），永远不能给出"无错判"声明；对判决核心，"我跑了一亿次没出错"不能写进证书。
2. **规格盲区**：PBT 的性质写错时，测试忠实通过；这与 Verus 共有同一残余风险（规格意图），但证明至少保证代码符合规格，PBT 连这层也没有。
3. **状态空间稀疏**：452 个改判事件的组合空间（模型序列×证据集×保护器状态）远超随机构造成都，fuzzer 擅长沙盒崩溃，不擅长 7 步以上的合法业务序列——必须用**从真实账本回放+在回放轨迹上变异**（这正是阙疑 golden 体系的独特资产）。

### 3.3 与证明的置信度差，诚实表述

【推断】阙疑对外的置信度声明应分三层措辞，禁止混用：
- L1（PBT/变异/fuzzing 覆盖）："未发现反例，测试集对 M1–M7 变异体的上界 cs_upper_bound = X"——给频率上界，不给无错承诺；
- L2（有界验证/Kani/ESBMC 式）："在展开界 K 内无违例，超出界报 undetermined"——给有界承诺，bounded 必须显式 [v31-S26][v33-S23]；
- L3（机器检查证明）："模块符合所附规格"——承诺的是代码↔规格一致，规格本身另行背书。
三层对应 v33 T1 的 unknown(reason=bounded_K) 枚举，本就是为诚实表达这套差距准备的。

## 4. 部分形式化的边界：判决合成表、账本追加、保护器改判（问题 4）

### 4.1 划界原则（从标杆反推）

seL4/CompCert/Everest 的共同经验：证明预算永远不够覆盖全部，**先证"错一次不可逆且外部无法复核"的部分**。按此原则给阙疑三模块定级【推断】：

| 模块 | 错一次的代价 | 可外部复核性 | 建议档位 | 工具 |
|---|---|---|---|---|
| **账本追加（append/哈希链/锚定）** | 不可逆、污染全部后续证书 | 弱（外部只见锚） | **L3 证明（首选 Verus，次选 Dafny/Kani 组合）** | Verus；先移植为 Rust |
| **判决合成表（四态+条件轴+冲突改判 B1）** | 直接产出错误 pass/fail | 中（可 replay，但规则集在变） | **L3 证明规格一致性 + L1 密集回放** | Verus + 账本回放；规格即 v33 T1 词表 |
| **保护器改判条件（B1–B5、未来 B7–B10）** | 该拦没拦=错误放行 | 中（shadow 台账可对照） | **L2 有界验证 + L1 stateful PBT**，先不追求证明 | Hypothesis 状态机 + Kani 有界 |
| MDL 准入/校准数学 | 错误规则上线 | 强（有 shadow 期与回滚） | L1 为主，保形数学部分可引用已发表证明 [v33-S31-S35] | PBT |
| LLM 交互/取证/检索 | 错误但被下游拦 | 强（本就要求他验） | **不形式化**，靠 v33 头部层工程 | 工程护栏 |

### 4.2 三个目标模块各自的规格草稿方向【推断】

1. **账本追加**：性质 = ①append-only：任何历史事件哈希在追加后不变（Merkle 包含证明可机检）；②单调性：序列号/时间戳严格递增；③幂等重放：从 genesis 重放得到同一根哈希。这三条都是 Verus 里相对常规的序列/哈希性质，是"849 任务"中高自动完成率的那类 [S19]。
2. **判决合成表**：性质 = ①全 pass→pass、任一原子 fail→fail（v33 T1.2 的粒度轴）；②冲突输入必产生显式 conflicting 态而非静默选择；③conditions[] 不满足时证据不可用于本案（assumption 语义，JUnit 已有工业先例 [v33-S40]）；④改判事件的前置/后置态满足 B1 谓词。难点是规则库是外部引用值（RATS reference values 模式 [v33-S43]）——证明应只覆盖"给定规则集下的合成"，规则库本身哈希引用不进闭包。
3. **保护器改判条件**：B1–B5 的谓词用确定性纯函数表达是前提（现状若有任何 LLM/随机性介入则无法上 L2）；shadow 模式（v33 B8）的对照一致性（同一输入 incumbent/shadow 的判定差分被完整记录）是可测性质。

### 4.3 规格即资产：比证明更重要的是把"判决宪法"写下来

【推断】Everest 没证完握手、seL4 范围受限都说明：**证明项目最大的长期产出是可执行的形式规格本身**。阙疑即使一行证明都不写，也应先把上述性质写成机检无关的形式化规格文档（前置/后置/不变量，数学符号+自然语言双语），理由有三：①它是未来任何工具（Verus/Kani/人工评审）的共同输入；②它是论文的核心贡献物（06 篇 §3）；③规格评审可以让社区参与，而证明编写不能。

## 5. Rust 重写时机：现在、卡到 100 张、还是等有人用？（问题 5）

### 5.1 三个选项的触发条件

【推断】三个候选时点与触发条件：

- **现在做（2026–2027）**：❌ 理由——核心仍在形变（v33 T1 判决两轴、T3 闭包重分都还没落地），在形变的代码上做移植+证明是双重返工；HACMS 的教训"代码与证明共同设计"的前提是**设计已冻结** [S15]；且当前无外部用户，Rust 带来的供应链可信没有消费方。
- **卡到 100 张/规则 200+ 时做**：⚠️ 部分有理但指标选错——规模不是触发条件，**稳定性与外部依赖才是**。
- **等有人用再做**：✅ 方向对但需细化。真实触发条件见下。

> **重写触发条件（全部满足才启动）：**
> 1. **规格冻结**：判决合成/账本的形式规格连续 ≥6 个月无破坏性变更（v33 T1/T4 落地后算起）；
> 2. **黄金集闭环**：replay 覆盖率能在旧 Python 实现上一键跑出（重写的验收 oracle 必须先存在——CompCert/seL4 都是先有规范再写实现）；
> 3. **外部消费方出现**：至少一个外部项目把 queyi-core 当依赖（此时内存安全/供应链可信开始有人付费），或学术投稿需要"可验证参考实现"（06 篇 §4）；
> 4. **queyi-core"两份并列"债先清**：先在 Python 内完成单一化，移植一个有内部争议的实现是把债务搬家。
>
> 满足后，范围严格限定：**先只移植账本追加模块（最小、最独立、性质最清晰），验证流程跑通后再推判决合成表**。不搞大爆炸重写（pydantic 也是先抽 pydantic-core 独立 crate [S24]）。

### 5.2 行业风向的额外权重

- Rust 在微软 2026-09 RustConf 成为内部 Tier-1 语言（与 C++/C#/TS 同级），Windows App SDK Rust 行已超过 C++（152k vs 96k），Azure 对处理不可信输入的新组件事实上强制 Rust；MSRC 2019 起"70% Windows CVE 是内存安全"是政策起点【第三方报道+厂商演讲转述】[S22]。
- Everest 系（Hax/Aeneas/Verus）集体转向 Rust 验证 [S18]。
- 含义【推断】：Rust 是 2026–2030 形式化系统语言的安全选择，不会赌错赛道；但行业风向解决的是"选什么语言"，不改变"什么时候动"——触发条件仍以 §5.1 为准。
