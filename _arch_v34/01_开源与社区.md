## 0. 阙疑现状（本仓库实读口径）

- 单人项目，25 个批次搓出：813 行纯逻辑核心、37 张 PCK 知识卡、67 条规则、452 个改判账本事件、M1–M7 阴性测试、四态 gate、B1–B5 保护器、Merkle/in-toto/OTS 账本骨架。
- 工程文化已具备开源基础设施雏形：`CONTRIBUTING.md`、`GOVERNANCE.md`、`SECURITY.md`、`RELEASE.md`、`LICENSE`、`HANDOVER.md`、`CONVENTIONS.md` 均存在；但全部围绕"单人+批次"运转，无外部贡献者通道的真实流量验证。
- 定位叙事目前三个候选互相打架："AI 验证框架"/"知识证明基础设施"/"Agent 外骨骼"。

**总判断**【推断】：Sigstore、in-toto、C2PA、TUF 四个与阙疑最近的样板，没有一个是"先发代码再找社区"成功的——它们的共同路径是**先有一个被需要的公共缺口 + 一篇/几篇定调论文或一个参照实现 + 一个中立法律载体 + 2–4 个不等的创始背书方，然后才是代码**。阙疑手里最稀缺的不是代码（代码已经跑了 25 批），是前三样里的"中立载体"和"创始背书方"。

## 1. 四个样板的 0→1：时间线、治理结构、版本节奏（问题 1）

### 1.1 Sigstore：工业研究员原型 → LF/OpenSSF 中立托管，1 年内完成

- **起源**：Rekor 由 Luke Hinds（Red Hat）2020 年中发起；Bob Callaway、Dan Lorenc 随后作为联合创始人加入；2021-03 项目正式发布（Rekor/Fulcio/Cosign 三件套），**发布同日成为 Linux Foundation 项目**，创始成员 Red Hat、Google、Purdue University【官方】[S1]。
- **学术渊源不是装饰**：官方 history 页把 *Software Distribution Transparency and Auditability*（arXiv:1711.07278）、*Contour: A Practical System for Binary Transparency*（arXiv:1712.08427）列为直接前置研究【官方】[S1]——透明日志的工业实现有 3 年以上的论文先行期。
- **节奏**：2021-03 入 LF → 2022-10-25 Rekor/Fulcio GA（约 19 个月）；2025-10 Rekor v2 GA、研究数据集（BigQuery 公共镜像）发布；项目归 OpenSSF 治理，自我总结为"neutral governance 让我们能与更大生态协调"【官方】[S1][S2]。
- **关键动作**：公共 good 实例免费运营 + 语言生态逐个绑定（Go/Python/Ruby/Java/Rust 官方客户端）+ npm provenance 等大平台集成。

**对阙疑的映射**【推断】：Sigstore 模式 = "论文先行 1–3 年 → 大厂研究员业余原型 → 携 2–3 个背书方进中立基金会 → 免费公共服务建立事实标准"。阙疑可复刻的是**前两步和最后一步的一半**（论文/技术报告先行、免费工具），不可复刻的是大厂研究员身份——替代方案见 §6 建议 2。

### 1.2 in-toto 与 TUF：学术实验室的十年长征，CNCF 唯二由学者领导毕业的项目

- **in-toto 时间线**【官方】[S3][S4]：
  - 2015：NYU Tandon Secure Systems Lab 创建，导师 Justin Cappos，当时的博士生 Santiago Torres-Arias（后赴 Purdue）+ NJIT 合作者；资助方 NSF、DARPA、AFRL；
  - 2019-08 CNCF Sandbox；2022-03 Incubation（入 sandbox 三年积累 132+ 贡献者、16+ 组织、8 maintainer/5 组织；**是第一个通过 CNCF TAG Security 安全评估的项目**）；
  - 2023-06 spec 1.0；2025-02-10 毕业（04-23 公告）——从论文到 CNCF 最高成熟度**整 10 年**。
- **生产采用拉动毕业**：Datadog（2019 起）、SolarWinds（SUNBURST 后用 in-toto 重建管道）、Autodesk（FedRAMP）；被 SLSA、OpenVEX、Sigstore Cosign 内嵌为 attestation 底层格式——in-toto 是 Rekor 中第二常用机制 [S4]。
- **降低摩擦的子工具决定扩散**：Witness（CI 步骤自动收集证据）+ Archivista（证据存储）被 Autodesk 明确点名为"默认安全而不给开发团队添坎"的关键 [S3]。
- **TUF 是同实验室前传**【官方】[S5]：2010 学术论文 → 2013 PEP 458/480（PyPI 集成）→ 2015 Docker Notary 商业化 → 2017 入 CNCF → 2019 毕业，是 CNCF **第一个安全项目、第一个学术研究者领导毕业的项目**。

**对阙疑的映射**【推断】：in-toto/TUF 是四个样板里与阙疑结构最像的（大学起源、安全供应链语义、attestation/账本）。其路径有三个可直接抄的要点：①**先定标准格式（spec）再堆实现**，in-toto 真正赢下生态的是 statement/predicate 轻格式而非完整 layout 端到端验证；②**借助一次历史性事故完成采用跃迁**（SolarWinds/SUNBURST），阙疑要预先准备好"事故发生时证据链能立刻拿出来"的叙事与工件；③**嵌入更大的既有标准**（SLSA、Sigstore）比自建生态快。

### 1.3 C2PA：双轨制——社区运动（CAI）+ 标准联盟（C2PA）

- **双轨结构**【官方】[S6][S7]：
  - CAI（Content Authenticity Initiative）：Adobe 2019 年发起的**社区/运动层**，免费成员制，2026 年 6000+ 成员，负责布道、开源工具、教育；
  - C2PA：2021-02-22 正式成立的**标准开发组织**，Linux Foundation Joint Development Foundation 下的 mutually governed consortium，创始六家 Adobe/Arm/BBC/Intel/Microsoft/Truepic；它合并了 Adobe 的 CAI 与 Microsoft/BBC 的 Project Origin 两条线。
- **节奏**：2021-09 草案 → 2022-01-26 v1.0（11 个月）→ 2024 年 Google/Meta/Amazon/OpenAI 相继进 Steering Committee → 2026-07 TikTok 进入、spec 2.3 [S8]。
- TWG（技术工作组）主席长期是 Adobe 的 Leonard Rosenthol：**发起方保留技术领导权，但治理在联盟里**。

**对阙疑的映射**【推断】：C2PA 证明"一个免费开放的社区运动 + 一个有正式知识产权安排的标准载体"可以并行且互补。阙疑的 PCK/证书词表工作（v33 T7）未来如果走向标准化，CAI 式社区层可以由作者自己扛，C2PA 式联盟层必须等有 2 个以上对等组织愿意共同署名时才建——单人提前注册"联盟"是空壳。

### 1.4 四个样板的共同骨架（合并观察）

| 要素 | Sigstore | in-toto/TUF | C2PA |
|---|---|---|---|
| 学术先行 | arXiv 2017 两篇 | 2010/2015 论文，NSF/DARPA 资助 | Project Origin/CAI 研究 |
| 创始背书 | Red Hat+Google+Purdue | NYU→Datadog/SolarWinds 拉动 | Adobe+MS+BBC+Intel+Arm |
| 中立载体 | LF/OpenSSF（发布同日） | CNCF（成熟后第 4/9 年） | LF JDF（成立即入） |
| 免费公共品 | good 实例 | 开源参考实现 | 开源 SDK+工具 |
| 嵌入策略 | 各语言客户端 | SLSA/Sigstore 内嵌 | 硬件相机/芯片/平台 |
| 到关键里程碑 | 19 个月 GA | 10 年毕业 | 11 个月 v1.0 |

【推断】进基金会的时机呈现双峰：**Sigstore/C2PA 在出生即刻进**（有大厂护送），**in-toto/TUF 在证明独立社区后才进**（学术项目先自证）。没有大厂护送的学术项目早进基金会不会加速，反而可能暴露在"无人背书的 sandbox 项目"的可见性尴尬里。

## 2. 学术原型转开源的典型死法（问题 2）

### 2.1 维护者倦怠是头号死因，且在 2024 年后有了安全后果

- Tidelift 2023/2024 两轮调查口径【第三方汇编，数字取同源调查】[S9]：60% 维护者自称无酬爱好者；60% 已退出或考虑退出（44% 归因 burnout、54% 生活冲突、51% 兴趣丧失）；61% 单人维护；Harvard/LF 研究 top 500 依赖包维护者中位数 2 人、top 100 中位数 1 人；约 22% 关键项目仅 1 个活跃维护者。
- **XZ Utils（CVE-2024-3094）**：唯一维护者 Lasse Collin 长期单人无酬、2022 年公开承认精神健康问题；攻击者"Jia Tan"用约两年时间、配合傀儡账号施压建立信任后取得提交权；后门因 Andres Freund 注意到 500ms SSH 延迟而意外暴露。CISA 事后定性为"不可持续维护模式的人为漏洞"；OpenSSF Alpha-Omega 事后排查出 50+ 结构相似的关键项目 [S9]。
- **Ingress NGINX**：K8s 生态最广泛部署的组件之一，2025-11 公告、2026-03 后不再有安全补丁，官方原因即一两个夜间周末维护的维护者被"无尽的 bug/功能请求洪水"耗尽 [S9]。
- Nadia Eghbal《Working in Public》的经典诊断：现代流行项目是**被动用户群**（百万下载、极小比例贡献），维护者从社区组织者退化为无偿客服 [S9]。
- **付费改变安全质量**（同调查）：付酬维护者实施关键安全实践的比例 +55%、漏洞修复快 45%、总漏洞数少 50% [S9]——这是"找赞助"最硬的论据。

### 2.2 其余四种死法（样板反推 + 治理文献）

1. **Scope creep（范围蠕变）**：Dawn Foster（IEEE Computer 2026-06）的治理建议首条是"从最简单的治理模型开始，仅在演化需要时升级；过度工程化的治理本身就是新增工作量"【论文/行业期刊】[S13]——对应到功能侧，学术原型最常见的死法是来一个用户加一个选项，核心被稀释。Michlmayr（前 Debian DPL）的 FOSS 基金会指南把"稳定性与机构记忆""冲突解决"单列为项目生命周期的必过关卡 [S13]。
2. **企业 fork 抽干**：Permissive 许可证下云厂商托管化是 2015–2023 的标准剧情（Elasticsearch→OpenSearch、Redis→ElastiCache、MongoDB→DocumentDB），这是 2024–2026 relicensing wave（HashiCorp BSL、Redis RSAL）的直接动因【第三方】[S10]。
3. **安全审计缺位**：学术代码默认"研究质量"，无威胁模型、无签名发布；OpenSSF Scorecard 2025 口径：top 1000 npm 包仅 11% 评分 >7/10，仅 8% 签名发布 [S9]。阙疑作为"安全验证工具"，自身供应链评分低于 7 会直接摧毁叙事。
4. **治理真空导致的夺权事故**：XZ 是社工夺权；商业项目里还有 CLA/版权归属不清导致日后无法 relicense 的陷阱（双重许可必须先有 CLA 或版权转让，因为 relicense 需要每个版权持有者同意）[S10]。

### 2.3 对阙疑的风险自评【推断】

| 死因 | 阙疑当前暴露度 | 依据 |
|---|---|---|
| 维护者倦怠 | **高**（单人、无酬、bus factor=1，且是自己的头号基础设施） | 本仓库实读 |
| Scope creep | 中高（v31–v34 四份调研已积累 60+ 候选项） | 调研目录实读 |
| 企业 fork | **低**（当前零商业价值），但许可证要为"可能变高"留门 | — |
| 安全审计缺位 | 中（有 tool_integrity/闭包，但 647 自登记缺文件曾只 warning） | v33 03 §0 |
| 治理真空 | 低（单人暂无夺权面），开源瞬间升为高 | — |

## 3. 定位三选一："AI 验证框架" / "知识证明基础设施" / "Agent 外骨骼"（问题 3）

### 3.1 三个候选位的生态位实测

- **"AI 验证框架"位**：2026 年已拥挤——LLM 裁判可靠性（CodeJudgeBench，26 个裁判模型横评 [v34-S60]）、行为测试（Openlayer 类商业平台 175+ 测试项 [S48]）、agent 防护（LlamaFirewall [v33-S38]）都在占位；此位讲"我们也能评 LLM"无差异化。
- **"Agent 外骨骼"位**：LangGraph/CrewAI/AutoGen/Dify 总星标数十万，但它们**全部停在编排层，治理层是公开空白**（详见 05 篇 §2）；此位讲"模型可替换、能力沉淀在框架"有空间，但外骨骼是手段不是客户价值。
- **"知识证明基础设施"位**：软件有 Sigstore、媒体有 C2PA、构建有 SLSA/in-toto，**"知识断言真假"无人管**——v33 已定此结论 [v33-S55][v33-S43]；C2PA 2.x 自己明确不做训练数据挖掘（TDM）断言 [v33-S55]。

### 3.2 结论【推断】

> **主定位锁"知识证明基础设施"（Knowledge Provenance / Verifiable Knowledge Claims），"AI 验证框架"是其当前引擎，"Agent 外骨骼"是其交付形态。**

- 理由一：生态位空白是客观的，且有现成标准词表可借（C2PA assertion、in-toto predicate、RATS attestation result），阙疑是**填空者**而非"第 N 个 eval 框架"。
- 理由二：主定位决定项目被谁引用——安全/供应链社区引用"知识 provenance"会顺藤摸到 C2PA/SLSA 群；定位成 eval 框架则淹没在每月数十篇 arXiv 里。
- 理由三：与学术叙事一致（06 篇 §3）：novelty 点"元验证（攻击验证器本身）+ 真机 L0 + 知识证书"只有挂在知识基础设施位才成立。
- 风险与对冲："知识基础设施"太大太早会显空——对冲方式是叙事收口为**"可执行知识（代码/标准行为类断言）的验证基础设施"**，先不宣称覆盖事实性知识（历史/医学），后者作为跨域愿景（05 篇 §5）。

## 4. 许可证：MIT / Apache 2.0 / AGPL 的实测后果（问题 4）

### 4.1 三许可证的 2026 年实测格局【第三方法律/行业汇编 + 官方基金会事实】

- **MIT**：约占 GitHub 已许可仓库三分之一；最大采用、零义务、无专利授权条款；React/Node.js 口径 [S10]。
- **Apache 2.0**：相对 MIT 多三样——明确专利授权与专利报复终止、商标保护、修改声明；**CNCF/ASF/LF 项目的事实标准**（in-toto、F*、Dify 均是）；企业法务的"安全宽松基线"；进入任何软件基金会事实上都要转到 Apache-2.0 类许可 [S10][S47]。
- **AGPL-3.0**：网络使用触发开源；Grafana/Mattermost/Bitwarden/Nextcloud 采用；企业法务普遍要求额外审查，多份企业政策直接禁用依赖；"Google ban AGPL"被广泛误传——实际是 Google 禁止在其基础设施上**运行**需要修改并作为服务提供的 AGPL 代码，不是全球禁用 [S10]。AGPL 未经修改自用/API 连接不触发义务。
- **双重许可需要 CLA**：未来想从宽松转 copyleft 或商业双许可，必须在第一个外部贡献者之前建好 CLA/DCO，否则 relicense 需全体版权人同意 [S10]。
- 2024–2026 的 BSL/SSPL 浪潮是"宽松许可撑不起 SaaS 商业化"的教训，但 BSL/SSPL **非 OSI 开源许可**，会被开源社区和部分基金会拒绝 [S10]。

### 4.2 对阙疑的结论【推断】

> **选 Apache-2.0，第一天就加 DCO（Developer Certificate of Origin，Signed-off-by），不选 MIT、不选 AGPL、不用 CLA。**

1. 不选 MIT 的唯一理由：专利条款。阙疑的核心叙事是供应链/信任，专利授权缺失会被企业法务在选型表上直接扣分，而 Apache-2.0 的成本为零。
2. 不选 AGPL：阙疑的目标采用方是**别的验证/教育/agent 项目内嵌**（in-toto/SLSA 式扩散），AGPL 的网络传染会吓跑所有潜在嵌入者；Grafana 们卖托管服务才需要 AGPL，阙疑不卖托管。
3. DCO 而非 CLA：CLA 要求贡献者向单一法人转让/授权，单人项目无基金会法人时收 CLA 是社区负信号；DCO（Linux Kernel/Kubernetes 模式）只要求签署"有权提交此代码"，保留版权，轻且足够；若未来捐赠基金会，基金会会统一换 CLA，DCO 历史不构成障碍。
4. 商标前置：名字"阙疑/Queyi"在开源时同步注册文字商标（个人持有→未来转基金会），C2PA/Sigstore 都把商标放在中立载体——这是唯一一旦丢失成本极高的资产。

## 5. 第一批贡献者：实证证据与冷启动动作（问题 5）

### 5.1 好的第一任务到底有什么用——纵向实证

- 最新纵向研究（37 个流行仓库、406,826 issues、1,117 个新人 GFI PR，2021-07～2025-06）【论文，EASE 2026】[S11]：
  - GFI（good first issue）标签占比 2024-01 起统计显著下降（项目方供给收缩）；
  - 新人对 GFI 的参与率四年稳定在约 **27%**——标签吸引力没有衰减；
  - 但新人 GFI PR 的**合并率从 61.9% 跌到 42.2%**——接得住的项目在变少；
  - PR 描述长度、代码体量与合并成功**无显著相关**：成败不取决于首提交的"卖相"，取决于维护者的评审支持。
- 经典事实：只有约 **30%** 尝试 onboard 的新人最终完成首次贡献，首要障碍是"找不到入口"和"项目特有知识"；Steinmacher 等的系列研究指出**社交沟通障碍**往往比技术障碍更致命【论文综述转引】[S12]。
- 反直觉证据：Labuschagne & Holmes 发现首个贡献落在 good-first-bug 上的开发者长期留存反而更低——**太人工的新手任务与项目核心脱节，练完即走** [S12]。
- 项目方侧机制：Mozilla 的 good-first-bug 起源；OSS-Doorway（NSF 资助，Steinmacher 团队，2026）用任务化/游戏化 onboarding 教学，证明结构化通道有效 [S12]。

### 5.2 基金会与治理文献给的冷启动清单

- Michlmayr primer：基金会对早期项目提供的价值顺序是**法律载体（许可/商标/责任隔离）→ 冲突解决与机构记忆 → 孵化/导师计划 → 营销**；CNCF Sandbox 四目标是"早期工作公开可见、与既有项目对齐、培育、消除采用与贡献的法律/治理障碍"[S13][S14]。
- llm-d 案例（2026-03 IBM/Red Hat/Google 捐 CNCF sandbox，创始贡献者含 NVIDIA/HF/Mistral + Berkeley/Chicago）：捐赠时同步拉入多个对等方和高校，避免"单厂商仓库"印象【官方】[S14]。
- Foster（IEEE Computer 2026）：在项目健康时尽早写治理；至少文档化"谁决策、谁提供输入、新人如何进入、晋升路径"；Jaeger 式 maintainer council 是推荐的最简起点 [S13]。

### 5.3 对阙疑的冷启动动作【推断】

1. **第一批 issue 不贴"good first issue"标签，贴"verification-bounty"**：候选任务从真实台账长出来——M1 候选规则挖掘器（v33）产出的规则草案复核、648 风格探针的编译器移植、知识卡的标准条款锚点回填。这些任务天然接触项目核心（规避 Labuschagne-Homes 留存陷阱），且每个任务都有客观对错（真机/标准可判），不依赖维护者主观口味——正好打在 GFI 研究"评审支持决定合并率"的痛点上：判决由 L0 做，维护者只做欢迎和合并。
2. **文档分两层**：`CONTRIBUTING.md` 已有，需补"30 分钟跑通一次完整判决"的 quickstart（贡献者复现一次 pass/fail/unknown）和"项目特有概念最小词表"（L0–L3、四态、PCK、保护器，每个 ≤3 行 + 一个例子）。30% 成功率瓶颈主要在项目知识获取 [S12]。
3. **治理文件先写 maintainer 路径**：贡献者→评审者→maintainer 的显式晋升标准（参考 in-toto 多组织 maintainer 结构 [S4]），单人期也写——它在没有空位时的作用是"让外人看到空位存在"。
4. **第一批人不从泛开源社区捞，从三个相邻池捞**：①国内编译器/系统方向实验室本科生（06 篇 §5 给渠道）；②MkDocs/技术书作者群体（知识卡是他们的直接需求）；③Sigstore/in-toto 中国社区活动参与者。冷邮件证据：STEM 领域给教授发简短、读过其论文的邮件是被鼓励的，通常要发 6–10 个才找到一个位置 [S61]。
5. **演讲先于代码宣传**：in-toto/Sigstore 都在 GA 前做了大量 meetup/KubeCon/defcon 曝光；阙疑第一场公开演讲的最小可用内容是"现场对一张卡跑出可重放判决 + 展示改判账本"，demo 即叙事。

## 6. 给阙疑的 3 条具体建议（brief 硬要求）

> **建议 O1：定位收口 + 许可证/DCO/商标一包搞定（2 周内，零代码风险）。**
> 对外定位统一为"可执行知识的验证基础设施：AI 是引擎，L0 真机与账本是信任根"；LICENSE 换 Apache-2.0、全仓库启用 DCO 签名、提交商标注册查询；写一页"项目十年"（对标 in-toto 2015→2025：spec→参考实现→嵌入标准），明确**不追求多快 GA，追求十年后还在**。

> **建议 O2：走 in-toto/TUF 的双峰第二峰——先自证社区，再谈基金会，顺序是"论文/技术报告 → 开源 → 1–2 个真实采用方 → CNCF/OpenSSF sandbox 申请"。**
> 不模仿 Sigstore 出生即入 LF（无大厂护送不可复制）。触发条件量化：≥3 个外部组织在真实项目里调用判决或证书格式、≥2 个非作者 maintainer、一次 TAG Security 式安全评估——in-toto 是在 132 贡献者/16 组织时进的 incubation [S4]。基金会首选 OpenSSF（知识 provenance 与供应链安全同构）而非 CNCF（云原生叙事不对口）。

> **建议 O3：按"单人 bus-factor=1"做反倦怠工程，把项目设计成失去自己 6 个月也不死。**
> 三件事：①所有关键操作（发版、账本周锚、黄金重放）写成可被他人执行的 runbook（Michlmayr 的机构记忆 [S13]）；②尽早引入 Open Source Collective / GitHub Sponsors 接受小额赞助并公开收支——付酬证据（安全实践 +55%）是最硬的募资话术 [S9]；③对贡献请求设置边界（明确不接受的范围、响应 SLA），把"客服洪水"挡在结构外而非靠意志力——这是 Eghbal 诊断的直接对策。

## 7. 盲区与诚实记录

1. **四个样板均为"有组织"项目**：Sigstore 有大厂、in-toto 有大学实验室、C2PA 有六家公司；"纯单人项目走通同一条路"的成功样板本次检索**没有找到**，§6 建议 2 本质是把单人期尽量缩短的赌法，不是已被验证的单人路径。
2. **Tidelift/Harvard 数字经多手转述**：本报告只采用多源重复出现的比例（60% 无酬、44% burnout、bus factor 中位数），精确到小数点的衍生数字一律未采信；原始 Tidelift 报告未逐页实读。
3. **中国语境的开源治理差异未覆盖**：许可证在国内的司法可执行性、国内基金会（开放原子）路径、Gitee 生态均未检索；若首批用户在国内，这是下一轮调研的必补项。
4. **"知识 provenance"位是否会被 C2PA/OpenSSF 自己扩展占掉**——无法排除；对冲只能靠速度与论文优先权（06 篇）。
5. 各项目的星标数、成员数为 2026-09-27 当日快照，开源数字变动快，引用时应标注日期。
