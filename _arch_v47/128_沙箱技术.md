# 方向128：沙箱技术——从seccomp到微虚拟机：让不可信代码"只能做对的事"

## 核心结论

1. **沙箱的技术主线是"逐层削减内核攻击面"，三十年没有变过**。原始 seccomp（Linux 2.6.12，2005-03-08，Andrea Arcangeli）把进程锁死到只剩 `read/write/exit/sigreturn` 四个系统调用[1]；seccomp-bpf（Linux 3.5，2012，Google Chrome 团队的 Will Drewry 推动）让进程可以用 BPF 程序按系统调用号和参数做细粒度过滤[1][2]；Linux namespaces（mount ns 自 2.4.19，2002；user ns 自 3.8，2013）改变进程"看到什么"，cgroups（Google 2006/2007 年"process containers"，2.6.24，2008-01 合入）限制进程"能用多少"[3]。三件套组合就是现代一切 Linux 沙箱的底座。必须分清三者不可互相替代：只加 namespace，进程仍能吃光内存与进程表；只加 cgroups，进程仍能访问全部文件与系统调用；只加 seccomp，进程仍能在已允许的调用下横向移动。沙箱设计因此永远是组合题，不存在单点开关。

2. **没有任何沙箱是"不可逃逸"的，必须按纵深防御设计**。Chromium 的渲染器沙箱（Linux 上两层：Layer-1 用 setuid/user namespace 沙箱挡资源，Layer-2 用 seccomp-bpf 削减系统调用面）[2]仍年年补沙箱逃逸 CVE：2019 年在野利用的 CVE-2019-13720（WebAudio 竞争 UAF，Operation WizardOpium）配合后续漏洞链，攻击者在载荷中大量使用 WASM 模块布置内存[4]；CVE-2019-5786（FileReader UAF，Google TAG 发现）同年在野利用[5]。沙箱不是边界墙而是减速带——价值在于把"一次漏洞得天下"变成"需要多漏洞链"。

3. **安全隔离的光谱上有三档，选型即取舍**：同内核纯过滤（seccomp/namespaces，最快、隔离最弱）→ 用户态内核（gVisor，2018-05 开源，Sentry 用 Go 实现系统调用、Gofer 代理文件访问，隔离较强、有系统调用开销）[6] → 微虚拟机（AWS Firecracker，2018-11 re:Invent 发布、12 月开源，KVM 之上 <125ms 启动到用户态、<5 MiB 内存开销、单机每秒最多 150 个 microVM，NSDI 2020）[7]。另有 FreeBSD jail（4.0，2000-03）、Capsicum（FreeBSD 9.0，2012-01；USENIX Security 2010 论文）、OpenBSD pledge（5.9，2016-03）/unveil（6.4，2018-10）等能力派方案[8][9]。

## 技术全景与关键数字

### 一、seccomp 与 seccomp-bpf：系统调用入口的闸门

原始 seccomp 为网格计算场景设计：进入 SECCOMP_MODE_STRICT 后只允许四个系统调用，违例即 SIGKILL——安全但无法实用[1]。seccomp-bpf 的突破是在每次系统调用入口执行用户装入的经典 BPF 过滤器，动作包括 ALLOW、ERRNO（返回错误但内核不处理）、KILL_PROCESS、TRAP（SIGSYS，可被处理器捕获）、LOG，以及 4.18 加入的 USER_NOTIF（用户态监督进程代为处理，可用于拦截未实现策略）[1][2]。Chromium 的关键经验是：**只过滤系统调用号不够，还必须过滤参数**，且必须保证策略 A 下的进程无法影响策略 B 下的进程（要堵 `ptrace`、`process_vm_writev`、`/proc` 条目等暗路）[2]。

### 二、Chromium 渲染器沙箱：多进程 + 纵深两层

Chromium 多进程模型把解析不可信输入的渲染器、GPU、插件、工具进程分别降权，资源访问经 IPC 向浏览器进程请求[2]。Linux 上两层结构：Layer-1（语义层，setuid 沙箱或现代内核上的 user namespace 沙箱，kernel ≥3.8）挡住对绝大多数资源的直接访问；Layer-2（攻击面削减层，seccomp-bpf，kernel ≥3.5）只放行渲染器实际需要的少量系统调用[2]。历史节点：Chrome 20 起 seccomp-bpf 用于隔离 Flash，Chrome 23 起用于渲染器[1]。2018 年 Chrome 67 起默认开启 Site Isolation，把不同站点放进不同渲染进程，即使渲染器被攻破，同源策略仍由进程边界兜底——这是 Spectre 公开后浏览器隔离模型的一次结构性升级，代价是内存占用上升约一到两成。多进程 + 站点隔离 + 两层沙箱因此构成三重纵深，任何一层被突破都不直接得天下。

### 三、FreeBSD/OpenBSD：能力模式与承诺模式

FreeBSD jail（4.0，2000-03，Poul-Henning Kamp）在 chroot 之上加独立主机名、IP 绑定约束、进程可见性限制与降级的 jailed-root 权限模型[3]。Capsicum 把进程能力化：进入 capability mode 后全局名字空间不可用，只能操作事先持有的**能力文件描述符**（带操作权限的 fd），论文发表于 USENIX Security 2010（Watson、Anderson、Laurie、Kennaway），FreeBSD 9.0（2012-01）合入[8]。OpenBSD pledge（5.9，2016-03，前身是 5.8 的实验性 tame）让进程以命名字符串承诺所需能力子集（如 `stdio inet rpath`），越界操作直接 SIGABRT、不返回错误；unveil（6.4，2018-10-18）在路径查找层做文件系统白名单，未 unveil 的路径返回 ENOENT，两者通常联用[9]。Bob Beck 在 BSDCan 2018 给出的工程标准是"能给 Chrome 各进程分别 pledge 才算设计成立"[9]。

### 四、gVisor：用户态内核的中间道路

gVisor 的 Sentry 是一个用户态内核，用 Go 实现绝大部分 Linux 系统调用语义，应用通过普通系统调用进入 Sentry 而非直接进入宿主内核；文件等资源经 Gofer 代理进程访问[6]。攻击模型上，即使 Sentry 被攻破，攻击者面对的仍是受限的宿主进程和 Gofer 白名单。代价是系统调用路径更长、部分系统调用未实现导致兼容性问题。独立学术测量（多组大学研究）报告其 CPU 密集型工作负载性能接近原生，而系统调用密集型场景开销显著——具体百分数本文不摘录，见盲区。工程细节上，gVisor 支持两种平台后端：ptrace（早期默认，利用断点拦截系统调用，开销较大）与 KVM（利用硬件虚拟化在客户态/宿主态间切换，性能更好、隔离更强）；网络可用其自带的用户态 netstack（Sentry 内部实现协议栈，不经宿主网络命名空间），文件经 Gofer 以 9P 协议逐个路径代理。这些设计共同把"被信任的宿主内核调用面"压缩到几十个调用以内。

### 五、Firecracker：为多租户无服务器重造 VMM

Firecracker 用 Rust 编写（约 5 万行），每个进程只运行一个 microVM；只暴露 5 个模拟设备（virtio-net、virtio-block、virtio-vsock、串口、仅用于关机的极简键盘控制器），无 BIOS、无 PCI、不支持 Windows、不支持实时迁移[7]。论文给出的硬指标：**<125 ms 启动到客户机用户态、<5 MiB 每 VM 内存开销、单机每秒创建至多 150 个 microVM**；已在 AWS Lambda 与 Fargate 支撑每月万亿级请求[7]。配套 jailer 建立 cgroup、chroot 后丢权，并用 seccomp 白名单（约 24 个系统调用）做第二道防线[7]。快照恢复可把重启降到约 5 ms。极简设备模型的安全意义常被低估：QEMU 这类通用 VMM 需要模拟整机历史设备，攻击面以数十万行计；Firecracker 只保留运行现代服务必需的 virtio 与最小控制台，模糊测试与代码审计的成本随之大幅下降——攻击面削减本身就是一种可量化的安全收益。

### 六、沙箱逃逸与 WASM 沙箱

在野攻击持续验证威胁真实存在：WizardOpium（2019-10 水坑攻击，朝鲜语新闻站）的 CVE-2019-13720 是渲染与音频线程间竞争导致的 UAF，修复于 Chrome 78.0.3904.87，攻击链用 WASM 模块承载后续阶段代码以获得可执行内存与稳定布局[4]；GitHub Security Lab 的 Man Yue Mo 报告 CVE-2020-6449 等同类 WebAudio UAF[5]。WASM 本身也是沙箱选项：线性内存 + 校验 + 无默认系统能力，但研究界已指出侧信道（Spectre 类）与运行时自身缺陷——Patrick Ventuzelo 在 Black Hat USA 2022 演示对 wasmtime 等 VM 的模糊测试，仅 `validate` 一项就发现约 6 个缺陷[10]；北大的 WASM 运行时综述（arXiv:2404.12621，覆盖 98 篇论文）系统讨论了沙箱边界[11]。

## 对阙疑的映射

### 一、编译运行不可信 C++ 探针：阙疑风险最高的执行路径

阙疑的 37 张实卡中有相当数量需要**实际编译并运行被检 C++ 代码**来验证"编译期恶意外代码"（编译器按标准应拒而未拒）与 UB 探针。这里存在双重不可信输入：被检源码不可信（可含 `#include </dev/tty>`、编译期 `system()`、模板炸弹、预处理器恶意外构造），未来第三方贡献的规则同样不可信。直接在开发机裸跑等于把宿主内核暴露给任意被检代码。沙箱设计应分层落地：

- **编译器进程最小权限**：编译在独立进程中进行，mount/pid namespace + 只读挂载源码、临时输出目录可写、`--network=none`、seccomp 白名单（编译器只需 `execve/read/write/openat/close/mmap` 等少量调用）、cgroups 限内存（如 1 GiB）限 CPU 时间（如 30s），封堵模板炸弹与 fork 炸弹。
- **生成的二进制二次隔离**：编译产物运行时再降一层——user namespace 内非 root、无网络、文件系统只挂临时目录、严格超时（如 10s）与内存上限；段错误/超时按四态判决中的 UNKNOWN 记账。
- **不信任编译器本身**：编译器版本固定（对齐方向 21/22 的 Docker 真复现），禁止编译器经插件机制加载第三方 .so。

### 二、CI 中执行外部代码：默认零信任

阙疑若在 GitHub Actions 中对 452 条账本做全量重放、对变异集（core 97.3%、all 81.5%）做回归，CI runner 就在循环执行来自被检语料与规则的代码。CI 恰恰是凭据最密集的环境（Shai-Hulud 等蠕虫的主战场）。最小化原则：评测 job 与任何发布 job 物理分离；评测 workflow 顶置 `permissions: contents: read`、不挂任何 secret；job 级别加超时；能用容器内非 root + seccomp 就不在 runner 宿主直接执行。这样即使被检代码是恶意的，能触及的也只是一个一次性容器。

### 三、论文可复现包的"安全开放"问题

NeurIPS 2027 E&D 赛道要求 documented and executable，阙疑要公开 holdout 30 条（17 真错、检出 66.7%）与 corpus 40 条（检出 43.8%）的完整复现路径。复现者的顾虑与我们的顾虑是对称的：他们会担心复现包在自己机器上编译运行恶意代码。把沙箱脚本（`sandbox/run_probe.sh`，基于 bubblewrap 或 Docker `--security-opt no-new-privileges --network none --memory`）作为复现包一等公民交付，README 写明"所有被检代码均在隔离环境执行、无网络、非 root、有资源上限"，既保护复现者，也是论文系统贡献的组成部分。脚本要同时支持"干跑审计"模式：只打印将对每个探针施加的隔离参数而不真正执行，让复现者先审后跑——对一个 0 影响力作者发布的工具，这种可审计性本身就是信任的来源。双非本科、0 影响力的作者要建立的正是这种"陌生人敢运行你的代码"的信任。

### 四、能力最小化：把"规则需要什么"写成清单

借 pledge/Capsicum 的思想，阙疑的 67 条规则与 9 个保护器按能力分三类：纯 AST 分析（零外部能力，占大多数）、需要编译（经内核编译代理）、需要运行产物（经隔离运行代理）。规则自己永远不直接 fork/exec，全部经内核的能力代理，代理按规则清单声明的能力授权并把每次调用记入账本。452 条账本因此附带完整的"能力使用轨迹"，复算者可审计每条判决触发了哪些敏感操作。沙箱信号与四态判决之间还需要一张显式映射表，避免隔离层故障污染判决语义：正常结束按规则输出入四态；超时、内存超限、被 seccomp 拒绝（SIGSYS）、子进程段错误一律记为 UNKNOWN 而非默认阴性——**"没跑成"绝不等于"没有错"**，否则资源限制越严、漏检越多，检出率会被沙箱配置暗中操纵。这张映射表本身要版本化并随账本冻结，复算者用同一规则解释全部 452 条记录。

### 五、沙箱选型：不上 Firecracker，但保留升级路径

在合肥单机、嵌入式背景与有限资源预算下，阙疑的现实组合是 **namespace + seccomp + cgroups（经 Docker/bubblewrap）**：零额外开销、可写进复现包、审稿人机器可得。gVisor/Firecracker 作为论文 related work 与未来工作呈现——例如在威胁模型中论证"若规则生态公开征集且出现逃逸事件，可整体迁移到 microVM 边界，每个规则一个 Firecracker（125ms 启动、5MiB 开销对单机也可承受小批量）"。反事实 P=R=F1=0 的结果提示：评测结论对环境极敏感，因此沙箱配置本身也要版本化、随账本固化。每次升级沙箱运行时或调整过滤策略，都应重跑全部 holdout 与变异集并留下对照记录，确保配置变更不以"安全加固"的名义悄悄改变检出率。

## 对阙疑的三条具体行动

1. **交付 `sandbox/run_probe.sh` 并纳入复现包（2026-12 前）**：优先用 bubblewrap（`bwrap --unshare-all --ro-bind 工具链 --bind 临时目录 --die-with-parent --seccomp 白名单`，显式不共享网络），不可得时回退 Docker 非 root + `--network none --memory=1g --pids-limit 64 --cpus 1`；holdout 30 条全量在沙箱内重放，核对检出仍为 66.7%（即 17 个真错中检出约三分之二的既有口径，逐条与账本核对）。
2. **加固 CI 评测 job（2027-01 前）**：评测与发布拆分为独立 workflow，评测 job 无任何 secret、`permissions: contents: read`、`timeout-minutes: 20`；变异 core 集在沙箱内回归确认 97.3% 不回退；增加一条"被检代码尝试联网即失败"的自建探针作为沙箱自检。
3. **在论文 threat model 中写入沙箱架构与威胁分级（2027-04 前）**：明确三类不可信输入（被检源码、第三方规则、复现包使用者视角）、各层隔离手段与"沙箱逃逸后"的残余风险（jailer 式纵深、最小权限），并把 gVisor/Firecracker 作为可升级边界列入 future work。

## 盲区

- gVisor 的具体性能数字未引用——多组独立研究结论随版本与负载差异大，投稿前需选定一篇近三年测量论文原文核对，不凭印象写百分数。
- Firecracker "约 24 个白名单系统调用"来自社区幻灯片，非官方文档逐字数字；jailer 白名单随版本变化，引用前需回官方仓库核对。
- seccomp-bpf 合入的精确 commit 时间线依据社区教程与 LWN 摘要，未直接阅读当时内核邮件列表原文。
- Chrome 2019–2020 年各 CVE 的修复版本号依据厂商博客与 GitHub Security Lab 文章，NVD 页面未逐条打开；CVE-2019-13720 是否严格构成"沙箱逃逸"还是"渲染器 RCE"需精确区分（后者配合 Windows 提权完成全链）。
- WASM 侧信道（Spectre）对本机隔离的实际影响随内核 mitigations 状态变化，未在双非机器上实测。
- Windows 下无 bubblewrap 等价物，复现包目前只保证 Linux/macOS Docker 路径，Windows 复现者体验未验证。
