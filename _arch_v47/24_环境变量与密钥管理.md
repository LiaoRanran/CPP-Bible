# 方向 24：环境变量与密钥管理

## 核心结论

1. **泄露是常态而非意外：2025 年公开 GitHub 新增 2865 万个硬编码密钥，同比 +34%，是史上单年最大增幅。** GitGuardian《State of Secrets Sprawl 2026》给出的五年曲线是 **11M（2021）→ 14M → 18M → 21M → 29M（2025）**，并逐字写道密钥泄露速度 *"Secrets are leaking 1.6× faster than the developer population is growing since 2021."* 更关键的是修复率：**2022 年泄露的密钥到 2026 年仍有 64% 有效可用**，且该比例逐年恶化（2022: 64% 有效 → 2023: 66% → 2024: 70% → 2025: 77%）。报告原话：*"The problem isn't detection. It's remediation."*

2. **轮换是第一动作，清历史是第二动作——这是 GitHub 官方文档的明确排序。** 逐字：*"if the sensitive data you need to remove is a secret (e.g. password/token/credential)… then as a **first step** you need to revoke and/or rotate that secret. Once the secret is revoked or rotated, it can no longer be used for access, and that may be sufficient to solve your problem. **Going through the extra steps to rewrite the history and remove the secret may not be warranted.**"* 更硬的一条：**GitHub Support 只在"轮换无法缓解风险"时才协助清理**（*"GitHub Support won't remove non-sensitive data, and will only assist in the removal of sensitive data in cases where we determine that the risk can't be mitigated by rotating affected credentials."*）。**顺序错了（先清历史后轮换）等于白做**：密钥在清历史期间仍然有效。

3. **AI 辅助开发使风险翻倍，而阙疑正好在这个高风险区。** 报告实测：*"Claude Code co-authored commits leak secrets at ~2× the baseline across all Public GitHub commits"*；AI 辅助提交的泄露率为 **3.2%，约为基线的 2 倍**；AI 服务凭证同比 **+81%**，是增长最快的类别（OpenRouter 48×、DeepSeek 23×、Perplexity 7.6×、Mistral AI 6.8×、OpenAI Project 6.5×、xAI 6.4×）。**并且 MCP 配置文件已成为重灾区**：在公开 GitHub 上发现 **24,008 个唯一密钥**，其中 **2,117 个仍然有效**；Top 5 类型为 Google API Key（19.2%）、PostgreSQL 连接串（14%）、Firecrawl（11.9%）、Perplexity（11.2%）、Brave Search（11%）。**阙疑项目大量使用 LLM 辅助（75+ 份 AI 生成文档、595 个 .py 工具），且工作环境使用 MCP——这是论文里必须写进 Threats to Validity 的真实风险。**

### 二、扫描工具选型与实测性能（SecretBench，NC State）

**SecretBench**（arXiv:2303.06729，2023-03，NC State 等）：*"a labeled dataset of source codes containing **97,479 secrets (of which 15,084 are true secrets)** of various secret types"*，来自 **818 个仓库**。基于该数据集的工具对比（经 Snyk 转引）：

| 工具 | Recall | Precision |
|---|---|---|
| **Gitleaks** | **88%**（最高） | 46% |
| **GitHub Secret Scanner** | 较低 | **75%**（最高） |
| **TruffleHog** | 52% | 中等 |

**关键结论：没有任何单工具可用。** 高 recall 的工具 precision 低（Gitleaks 46%），高 precision 的工具 recall 低。**推荐组合**：Gitleaks 做 pre-commit 快筛（低延迟、广覆盖）→ TruffleHog 做 CI/历史全量扫描（**800+（官网称 901+）credential 类型支持"live verification"**，即实际登录验证密钥是否还有效，把 46% precision 的噪声压掉）。

**Gitleaks 使用要点（官方仓库逐字）**：
- v8.19.0 起 **`detect` 与 `protect` 已废弃**（*"Those commands are still available but are hidden in the `--help` menu."*），现行三种模式是 **`git` / `dir` / `stdin`**。
- 历史扫描：`gitleaks git -v --log-opts="--all commitA..commitB" path_to_repo`（底层用 `git log -p`）
- 目录扫描：`gitleaks dir -v path_to_directory_or_file`
- 管道：`cat some_file | gitleaks -v stdin`
- **基线机制**（对已有历史仓库最实用）：`gitleaks git --report-path gitleaks-report.json` 生成基线，再 `gitleaks git --baseline-path gitleaks-report.json --report-path findings.json`，*"report output (findings.json) will only contain new issues."*
- pre-commit 配置（逐字）：
  ```yaml
  repos:
    - repo: https://github.com/gitleaks/gitleaks
      rev: v8.24.2
      hooks:
        - id: gitleaks
  ```
  安装：`pre-commit autoupdate && pre-commit install`。跳过：`SKIP=gitleaks git commit -m "..."`（**不建议在团队中允许，但单人项目可作为应急**）。
- 误报压制：`[[rules.allowlists]]`，*"A finding will be ignored if _ANY_ `[[rules.allowlists]]` matches."*
- ⚠️ **重大维护风险**：仓库顶部有官方 Warning——*"**Gitleaks is feature complete. I'm not merging new features into Gitleaks. Future releases will be security patches only. I'm shifting my focus to Betterleaks.**"* 意味着 Gitleaks 进入仅安全补丁模式，长期应关注继任者（本组未核实 Betterleaks 的成熟度）。

**detect-secrets**（Yelp 出品）的差异化在于 **baseline 文件 + 熵检测 + 可审计的审计流程**，适合"历史已有大量疑似项、需要逐条标注真/假"的场景；对单人项目而言维护成本高于 Gitleaks。

### 三、`.env` 的正确用法与 GitHub Actions secrets 的真实约束

**`.env` 的定位**：本地开发期的变量载体，**必须进 `.gitignore`**，仓库里只提交 `.env.example`（含键名、不含值）。这是 12-Factor App 的 Config 原则（配置与代码分离）的落地形式。**常见错误**：把 `.env` 提交后又删除——**git 历史里仍在**，必须走轮换 + 清历史（见第四节）。**另一个错误**：把 `.env` 打进 Docker 镜像（`COPY . .` 会带上）——必须用 `.dockerignore` 排除（方向 22）。

**GitHub Actions secrets 的硬约束（官方 *Secure use reference* 逐字）**：
- *"Any user with write access to your repository has read access to all secrets configured in your repository. Therefore, you should ensure that the credentials being used within workflows have the least privileges required."*
- 第三方 action 风险：*"a compromise of a single action within a workflow can be very significant, as that compromised action would have access to all secrets configured on your repository, and may be able to use the `GITHUB_TOKEN` to write to the repository."*
- `GITHUB_TOKEN` 最小权限：*"It's good security practice to set the default permission for the `GITHUB_TOKEN` to read access only for repository contents."*（工作流里加 `permissions: contents: read`）
- 脱敏不是万能的：*"Because there are multiple ways a secret value can be transformed, automatic redaction is not guaranteed."* 且**绝不要用结构化数据当 secret**：*"do not use a blob of JSON, XML, or YAML (or similar) to encapsulate a secret value, as this significantly reduces the probability the secrets will be properly redacted. Instead, create individual secrets for each sensitive value."*
- 派生值也要登记：*"if using a private key to generate a signed JWT to access a web API, be sure to register that JWT as a secret… Registering secrets applies to any sort of transformation/encoding as well. If your secret is transformed in some way (such as Base64 or URL-encoded), be sure to register the new value as a secret too."*
- 手动掩码：`::add-mask::VALUE`
- 泄露后处置：*"If an unredacted secret is sent to a workflow run log, you should delete the log and rotate the secret."*
- 轮换周期：*"Rotate secrets periodically to reduce the window of time during which a compromised secret is valid."*（第三方建议 30–90 天，非官方）
- **OIDC 是根治方案**：*"you can configure your workflows to authenticate directly to the cloud provider. This will let you stop storing these credentials as long-lived secrets"*；推荐 *"OpenID Connect to create short-lived, well-scoped access tokens for your workflow runs."* **对阙疑的含义**：如果未来需要访问云服务，用 OIDC 而非长期密钥；如果只是跑测试，**根本不需要任何 secret**（这是最安全的方案）。

### 四、已泄露密钥的完整处置流程（GitHub 官方步骤）

**顺序固定为：轮换/撤销 → 评估是否值得清历史 → 清历史 → 联系 Support → 通知协作者。**

重写历史的**七类副作用**（官方逐字列举，节选）：*"**High risk of recontamination**: It is unfortunately easy to re-push the sensitive data… If a fellow developer has a clone from before your rewrite, and after your rewrite simply runs `git pull` followed by `git push`, the sensitive data will return."*；*"**Risk of losing other developers' work**"*；*"**Changed commit hashes**: Rewriting history will change the hashes of the commits that introduced the sensitive data *and* all commits that came after."*；*"**Branch protection challenges**: If you have any branch protections that prevent force pushes, those protections will have to be turned off"*；*"**Broken diff view for closed pull requests**"*；*"**Poor interaction with open pull requests**"*；*"**Lost signatures on commits and tags**… `git-filter-repo` will remove commit signatures and tag signatures for commits that pre-date the sensitive data removal as well."*；以及最微妙的一条：*"when you do modify history, clueful users with an existing clone will notice the history divergence and can use it to quickly and easily find the sensitive data still in their clone that you removed from the central repository."*

**命令**（需 **git-filter-repo ≥ 2.47**，因为要 `--sensitive-data-removal` 标志）：
```bash
# 删除特定文件（所有分支/标签/引用）
git-filter-repo --sensitive-data-removal --invert-paths --path src/module/secrets.env
# 替换文本内容
git-filter-repo --sensitive-data-removal --replace-text ../passwords.txt
# 检查受影响的 PR 数（Support 会要这个数）
grep -c '^refs/pull/.*/head$' .git/filter-repo/changed-refs
# 强制推送
git push --force --mirror origin
```
注意：*"If the file with sensitive data used to exist at any other paths (because it was moved or renamed), you must either add an extra `--path` argument for that file, or run this command a second time naming the alternative path."*

**推送后仍需做的四件事**（官方）：联系 GitHub Support 并提供（仓库名、受影响 PR 数、`First Changed Commit(s)`、LFS 孤立对象信息）；Support 会 *"Dereference or delete any affected PRs on GitHub"*、*"Run a garbage collection on the server to expunge the sensitive data from storage"*、*"Remove cached views"*、*"delete and/or purge the orphaned LFS objects"*。

**三个无法通过清历史解决的残留**：*"In any clones or forks of your repository"*、*"Directly via their SHA-1 hashes in cached views on GitHub"*、*"Through any pull requests that reference them"*。其中 **fork 完全无解**：*"If the commit that introduced the sensitive data exists in any forks, it will continue to be accessible there. You will need to coordinate with the owners of the forks… GitHub cannot provide contact information for these owners."*

**协作者纪律**：*"Collaborators must rebase, *not* merge, any branches they created off of your old (tainted) repository history. One merge commit could reintroduce some or all of the tainted history."* **对单人项目**：没有协作者反而使清历史成本极低——这是单人项目的结构性优势，应充分利用。

## 对阙疑的 3 条具体行动

1. **2026-11 前完成一次"密钥体检"并留下记录**：在 CPP-Bible 与 queyi-verifier 两个仓库分别执行 `gitleaks git -v --log-opts="--all" . > /tmp/leak-scan-$(date +%F).json`，以及 `gitleaks dir -v . `（扫工作树，覆盖未提交文件）。把结果文件归档到 `research/security/leak-scan-<date>.json`（**若命中真实密钥，先轮换再归档，归档里只留脱敏后的规则 ID 与文件路径**）。同时建立基线：`gitleaks git --report-path research/security/gitleaks-baseline.json`，之后 CI 用 `--baseline-path` 只报新增问题。**理由**：Gitleaks 官方明确进入 "feature complete / security patches only" 模式，先把一次性全量扫描做掉，比依赖工具持续更新更可靠。

2. **2026-11 前落地三层防线，并把配置提交进仓库**：(i) **本地**——`pip install pre-commit`，在仓库根建 `.pre-commit-config.yaml`（`rev: v8.24.2`，`hooks: - id: gitleaks`），跑 `pre-commit install`；(ii) **CI**——`.github/workflows/secret-scan.yml` 用 `gitleaks/gitleaks-action`，并在 workflow 顶部写 `permissions: contents: read`（GitHub 官方推荐的最小权限）；(iii) **仓库侧**——在 GitHub 设置里开启 **Secret Scanning** 与 **Push Protection**。**同时立刻做两件低成本事**：建 `.env.example`（只含键名）、把 `.env` 与 `*.json` 的 MCP 配置文件加入 `.gitignore` 与 `.dockerignore`。**论文写作期特别提醒**：不要在 `_arch_v47/` 或其他文档里粘贴任何真实 API key 示例；若需展示格式，用 `sk-XXXX...` 这类明显占位符。

3. **在 `research/` 下新增 `24_secrets_management.md`，写清"我们没有密钥"这一正面声明（2027-01 前）**：内容包含 (i) 一张表列出项目需要的全部环境变量（如 `QUYI_LEDGER_PATH`、`PYTHONHASHSEED`），标注"**非敏感**"或"敏感，仅本地"；(ii) 明确声明 **CI 不持有任何长期凭证**（若需云资源，改用 OIDC 短期令牌，引 GitHub 官方 OIDC 建议）；(iii) 引用 GitGuardian 2026 的 AI 辅助提交 2× 泄露率与 MCP 24,008 个密钥的数据，**在 Threats to Validity 里加一条 T-Sec**："本项目在开发过程中大量使用 LLM 辅助与 MCP 工具，而 2026 年实测显示 AI 辅助提交的密钥泄露率约为基线 2 倍、MCP 配置文件是密钥泄露重灾区；我们通过 pre-commit + CI 双层扫描与基线机制控制该风险，扫描结果见 `research/security/`。" 若确实发生过泄露，**必须按"轮换 → 清历史 → 联系 Support"顺序处理并在文档中记录时间线**，不要隐去。

## 盲区（诚实标注）

- **GitGuardian 报告中的部分关键百分比被图表遮挡**。例如 Shai-Hulud 2 一节"有多少比例的机器持有 >10 个密钥、5% 持有 >100 个"的前一个数字抓取到的是 "0%"，**明显是图表渲染缺失而非真实值**，本组未取到正确数值。
- **"AI 辅助提交泄露率 3.2%、约 2× 基线"的 3.2% 来自 Snyk 转述 GitGuardian 报告**，本组未在 GitGuardian 原始报告页逐字看到 "3.2%" 这个数字（原始页只写 "~2×"）。引用时应写"约 2 倍"或标注转引。
- **GitHub 官方"39 million secret leaks in 2024"与 IEEE S&P 2025 的"80M 文件 / 30% 项目"均为经 Snyk 转引**，本组未打开 GitHub 官方安全报告或 IEEE S&P 论文原文核对。
- **SecretBench 的 recall/precision 数字（Gitleaks 88%/46%、GitHub Secret Scanner 75%、TruffleHog 52%）来自 Snyk 文章的转引**，本组未逐字打开 arXiv:2303.06729 的结果表；且 **SecretBench 是 2023 年数据，工具版本已大幅迭代，数字可能过时**。
- **Gitleaks 的具体许可证类型未核实**（仓库页只显示 LICENSE 徽章，未在抓取内容中写出 MIT/Apache）。**Betterleaks 的成熟度、维护者、是否已被社区采纳完全未核实**——这是一个重要未知，因为 Gitleaks 官方已宣布停止加新功能。
- **detect-secrets 的具体功能与 baseline 机制未逐字核实**（本组仅检索到对比文章，未打开 Yelp 官方仓库）。
- **"轮换周期 30–90 天"来自第三方博客（blacksmith.sh），非 GitHub 官方要求**。GitHub 官方只说 "Rotate secrets periodically"。
- **未核实阙疑当前是否真的存在任何泄露**。本组未读取任何仓库内容（按调研纪律只写 `_arch_v47/`），因此第五节的风险清单是**基于项目特征的推断，不是已确认事实**。
