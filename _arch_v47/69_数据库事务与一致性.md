# 方向 69：数据库事务与一致性（ACID、隔离级别与异常、SSI、线性一致性 vs 可串行化、单人单机场景真正需要什么）

> 调研时间：2026-09-29｜调研员：方向 68–79 组｜真实检索 **22 次**（16 次 WebSearch + 6 次 WebFetch 逐字取数）
> 本文要回答一个对阙疑很关键但容易被忽略的问题：**一个单人、单机、单写者的 append-only 判决账本，到底需不需要"事务"？如果需要，需要哪一部分？**

---

## 核心结论

1. **阙疑需要的不是"隔离"，而是"原子性 + 持久性"，且持久性比想象中难得多。** 隔离性（isolation）解决的是"多个事务并发时彼此看到什么"，而阙疑的 `gate_engine.py`（3826 行）是**单进程、单写者**：不存在并发事务，因此**脏读、不可重复读、幻读、写偏斜、丢失更新这五类经典异常全部不可能发生**。但"追加一条账本条目 + 更新哈希链头 + 写 Merkle checkpoint"这三步必须**原子**，否则崩溃后哈希链断裂——**这是阙疑唯一真实的事务需求**。Hermitage 测试套件（Martin Kleppmann，2014）把这一点说得最直白：*"it's a game of trade-offs... More check marks doesn't necessarily mean better."*
2. **SQLite 的默认持久性设置比你想象的弱，这是一个可以写进论文的威胁。** 官方文档逐字：`FULL (2)` *"ensures that an operating system crash or power failure will not corrupt the database"*——**注意它只保证"不损坏"，不保证"最后一次提交还在"**；只有 `EXTRA (3)` *"provides additional durability if the commit is followed closely by a power loss"*。而在 WAL 模式下 `synchronous=NORMAL` 官方逐字写 *"WAL mode does lose durability. A transaction committed in WAL mode with synchronous=NORMAL might roll back following a power loss or system crash."* 更糟的是：**macOS 自带的 SQLite 3.43.2 默认 `synchronous=1`（NORMAL）且 `fullfsync=0`**（avi.im, 2025-08-24 实测）。**如果阙疑在 macOS 上用系统自带 SQLite 存账本，"452 条判决已落盘"这句话在断电场景下是不成立的。**
3. **可串行化快照隔离（SSI）是数据库史上"用工程换正确性"的教科书案例，值得作为论文的引文，但不值得作为实现。** Cahill/Röhm/Fekete 在 SIGMOD 2008 提出 SSI（*"Serializable isolation for snapshot databases"*, DOI 10.1145/1376616.1376690），Ports & Grittner 在 VLDB 2012 落地到 PostgreSQL 9.1（PVLDB 5(12):1850–1861，摘要逐字：*"the first implementation of SSI in a production database release"*，且 *"achieves performance only slightly below that of snapshot isolation"*）。**但 SSI 的代价是"误杀"**：PostgreSQL wiki 明确承认序列化失败的位置**不确定**（*"there is a random factor used in inserting index entries which have equal keys"*），因此应用必须实现重试循环。**在一个要求"判决可复算"的系统里，"同一个输入可能因为时序不同而给出不同的中止结果"是不可接受的**——这恰好是阙疑应当**主动拒绝** SSI 的理由，而不是"用不起"。

### 三、SSI 的"误杀"问题：PostgreSQL 官方承认的不确定性

PostgreSQL wiki 的 SSI 页面（对应 **PostgreSQL 9.1 起**）逐字：

- 对应关系：*"These correspond to the SERIALIZABLE and REPEATABLE READ transaction isolation levels, respectively, in PostgreSQL beginning with version 9.1."*（SSI ↔ SERIALIZABLE；SI ↔ REPEATABLE READ）
- write skew 定义：*"When two concurrent transactions each determine what they are writing based on reading a data set which overlaps what the other is writing, you can get a state which could not occur if either had run before the other. This is known as write skew, and is the simplest form of serialization anomaly against which SSI protects you."*
- 解决策略：*"The first committer wins and the other transaction is rolled back. The 'first committer wins' rule ensures that there is progress and that the transaction which is rolled back can immediately be retried."*
- **不确定性的官方承认**：*"the predicate locking used as part of conflict detection works based on pages and tuples actually accessed, and there is a random factor used in inserting index entries which have equal keys, in order to minimize contention; so even with identical run sequences it is possible to see differences in where serialization failures occur."*
- 以及：*"An interesting point is that if session 2 attempted to commit after session 1 and before session 3, it would still have failed, and a retry would still have succeeded, but **the fate of the transaction on session 3 is not deterministic**."*
- 观测也会触发失败：*"The act of observing a recently modified database state can cause serialization failures."*
- 应用必须重试：*"it is important, when relying on serializable transactions for managing concurrency, to have some generalized technique for identifying serialization failures and retrying transactions from the beginning."*

**这一节是阙疑拒绝 SSI 的核心论据**：SSI 的**中止集合本身是非确定性的**（同一份输入、同一份操作序列，中止可能落在不同事务上）。阙疑的核心卖点是"**判决可复算**"——第三方拿到相同的账本应当算出**逐位相同**的判决。**引入 SSI 就等于在系统里埋了一个"同一个输入可能得到不同中止结果"的随机源，这与卖点直接冲突。**

**盲区**：PostgreSQL SSI wiki 页面**没有给出任何误报率 / abort 率的具体百分数**（我逐字确认：*"页面中未出现任何关于误报率或 abort 率的具体百分数"*）。

### 四、线性一致性 vs 可串行化：两个正交的概念

- **可串行化（Serializability）** 出自数据库领域：要求**多对象事务**的并发执行结果等价于某种**串行顺序**。它**不约束实时（real-time）顺序**——一个事务即使"早就返回了"，在串行化序里也可以排在"之后才开始"的事务后面。
- **线性一致性（Linearizability）** 出自分布式系统/并发对象领域（Herlihy & Wing, 1990）：要求**单个对象**上的操作看起来是**在某个实时时刻原子生效**的，且该时刻落在操作的调用与返回之间。它**不涉及多对象事务**。
- **严格可串行化（Strict Serializability）** = 可串行化 + 实时顺序约束。这是"看起来像单机单线程顺序执行"的最强保证。

**对本项目的意义（一个必须说清的区分）**：阙疑的"第三方可不信任内核地复算判决"要求的**既不是**可串行化（因为账本是 append-only，没有多事务并发），**也不是**线性一致性（因为没有分布式副本）。它要求的是**账本内容的确定性与可验证完整性**——即"给定账本字节流，任何人都能算出同一个判决，并能验证账本未被篡改"。**这是一个"内容寻址 + 哈希链"的性质，不是事务隔离级别的性质。** 论文中若把这一点与"一致性"混谈，会被数据库方向的审稿人直接质疑。

**一个正面的对照**：CockroachDB 官方文档逐字——*"In contrast to most databases, CockroachDB offers SERIALIZABLE isolation by default, which is the strongest of the four transaction [isolation levels]"*。CockroachDB / FoundationDB / YugabyteDB 选择"默认最强隔离 + 冲突重试"路线，代价是**必须实现重试循环**。**阙疑选择的是完全相反的路线：不做并发，从而不需要隔离。** 这是一条合法的工程路线，但必须在论文里写明"我们假设单写者"，并给出违反该假设时的行为（例如：多进程同时追加账本时应报错而非静默交错）。

### 五、SQLite 的持久性实测与坑（对阙疑账本存储的直接威胁）

**avi.im, "SQLite commits are not durable under default settings"（2025-08-24，后经修订）的逐字要点**：

1. 默认配置实测（SQLite 3.50.4, 2025-07-30）：
   ```
   sqlite> PRAGMA journal_mode;
   delete
   sqlite> PRAGMA synchronous;
   2
   ```
   即默认 `journal_mode=DELETE`、`synchronous=FULL(2)`。

2. 但 `FULL` 在 rollback journal 模式下**不足以保证最后一次提交持久**。官方文档逐字：
   > *"FULL (2) When synchronous is FULL (2), the SQLite database engine will use the xSync method of the VFS to ensure that all content is safely written to the disk surface prior to continuing. This ensures that an operating system crash or power failure will not corrupt the database."*
   > *"EXTRA (3) EXTRA synchronous is like FULL with the addition that the directory containing a rollback journal is synced after that journal is unlinked to commit a transaction in DELETE mode. EXTRA provides additional durability if the commit is followed closely by a power loss."*

   博客的解读逐字：*"Notice that it says `FULL` ensures that the database isn't corrupted, but NOT that the last transaction is durable. The highlighted part in `EXTRA` provides that durability."*

3. WAL 模式下 `NORMAL` 丢持久性。官方文档逐字：
   > *"WAL mode does lose durability. A transaction committed in WAL mode with `synchronous=NORMAL` might roll back following a power loss or system crash."*
   > *"With `synchronous=FULL` in WAL mode, an additional sync operation of the WAL file happens after each transaction commit. The extra WAL sync following each transaction helps ensure that transactions are durable across a power loss."*
   > *"If durability is not a concern, then synchronous=NORMAL is normally all one needs in WAL mode."*

4. **SQLite 作者 DRH 的说法与文档存在冲突**（博客逐字转引 HN 评论）：
   > *"If you switch to WAL mode, the default behavior is that transactions are durable across application crashes (or SIGKILL or similar) but are not necessarily durable across OS crashes or power failures. Transactions are atomic across OS crashes and power failures. But if you commit a transaction in WAL mode and take a power loss shortly thereafter, the transaction might be rolled back after power is restored."*

   **注意这里的关键区分**：**atomic（原子）与 durable（持久）不是一回事**——WAL 保证"要么全在要么全不在"，但不保证"一定在"。**对 append-only 哈希链账本而言，atomic 恰恰是最关键的**：如果一条账本条目写了一半，哈希链就断了；如果它整条消失，链仍然是完整的（只是短了一条）。**这个区分是阙疑应当写进论文的核心工程洞察。**

5. **macOS 是最坏情况**：博客实测 macOS 自带 SQLite **3.43.2（2023-10-10）**：
   ```
   sqlite> PRAGMA journal_mode=wal;
   wal
   sqlite> PRAGMA synchronous;
   1
   sqlite> PRAGMA fullfsync;
   0
   ```
   即 **macOS 默认 `synchronous=NORMAL` 且 `fullfsync=0`**。博客逐字：*"That is, the default is `NORMAL`. So, commits are not durable. But even if you use `FULL`, it's not enough. You'll want to set `fullfsync` to true. This is false by default."* 并给出推荐配置表：

   | journal_mode | synchronous | fullfsync |
   |---|---|---|
   | `DELETE`（rollback） | `EXTRA` | 1 |
   | `WAL` | `FULL` | 1 |

6. 编译期默认：`SQLITE_DEFAULT_SYNCHRONOUS=<0-3>` 默认 **2（FULL）**；`SQLITE_DEFAULT_WAL_SYNCHRONOUS` 若未覆盖则与前者相同；**`fullfsync` 没有编译期选项，默认恒为 false**。

### 六、SQLite 的事务与锁语义（逐字，官方 `sqlite.org/lang_transaction.html`，页面最后更新 2026-02-18）

- **读事务 vs 写事务**：*"SQLite supports multiple simultaneous read transactions coming from separate database connections... but only one simultaneous write transaction."*
- **读事务看到的是历史快照**：*"While a read transaction is active, any changes to the database that are implemented by separate database connections will not be seen by the database connection that started the read transaction... X will continue to see an historic snapshot of the database prior to the changes implemented by Y."*
  → **这意味着 SQLite 的读事务实际上提供了快照隔离（snapshot isolation）语义**（第三方 SQLite 内核解读文章 quant67.com 逐字：*"In WAL mode, SQLite exhibits 'snapshot isolation'."*）
- **读升级为写可能失败**：*"If a write statement occurs while a read transaction is active, then the read transaction is upgraded to a write transaction if possible. If some other database connection has already modified the database or is already in the process of modifying the database, then upgrading to a write transaction is not possible and the write statement will fail with SQLITE_BUSY."*
- **三种 BEGIN**：默认 **DEFERRED**；*"DEFERRED means that the transaction does not actually start until the database is first accessed."*；`IMMEDIATE` *"causes the database connection to start a new write immediately"*，可能在另一写事务活跃时直接返回 `SQLITE_BUSY`；`EXCLUSIVE` 在 WAL 模式下与 IMMEDIATE **等价**。
- **COMMIT 也可能 BUSY**：*"An attempt to execute COMMIT might also result in an SQLITE_BUSY return code if another thread or process has an open read connection. When COMMIT fails in this way, the transaction remains active and the COMMIT can be retried later."*
- **`journal_mode=OFF` 时 ROLLBACK 行为未定义**：*"If PRAGMA journal_mode is set to OFF (thus disabling the rollback journal file) then the behavior of the ROLLBACK command is undefined."*

**工程结论（可直接落地）**：**阙疑的账本写入应当用 `BEGIN IMMEDIATE`**，而不是默认的 `BEGIN`（= DEFERRED）。理由是 DEFERRED 先拿读锁、再升级写锁，两步之间会撞上 `SQLITE_BUSY`；IMMEDIATE 一步到位拿写锁，避免"读→写升级失败"。这一条在多处中文技术资料中反复出现（博客园 maxiongying 逐字：*"如果两个连接都以 BEGIN IMMEDIATE开始事务，那么死锁就不会发生"*），**但我未在 SQLite 官方文档中找到对"IMMEDIATE 避免死锁"的明确表述**——官方只说 IMMEDIATE 会立即拿写锁并可能返回 BUSY。**引用时应引官方那句，而不是引博客的结论。**

**自动回滚的错误码（官方逐字）**：`SQLITE_FULL`（磁盘满）、`SQLITE_IOERR`（I/O 错误）、`SQLITE_INTERRUPT`、`SQLITE_NOMEM`。且：*"An application might want to respond to the errors listed above by explicitly issuing a ROLLBACK command. In that way, the transaction state will always be the same after one of the errors above."* —— **对阙疑的启示：账本写入路径必须显式处理这四类错误并显式 ROLLBACK，否则"事务状态是否已回滚"本身就是不确定的**。

## 对阙疑的 3 条具体行动

1. **【2026-11 前】在 `docs/storage_invariants.md` 里写死三条不变量，并把它们变成可执行断言（不是文档口号）。** 三条不变量：
   - **I1（原子性）**：账本条目的"追加 + 链头更新 + checkpoint 写入"必须在**同一个 SQLite 事务**内完成；进程崩溃后重启时必须能检测到"链头与最后一条条目不一致"并报错退出（而不是静默修复）。
   - **I2（持久性显式声明）**：在代码中显式执行 `PRAGMA journal_mode=WAL; PRAGMA synchronous=FULL; PRAGMA fullfsync=1;`（`fullfsync` 仅 macOS 生效，其他平台无副作用），并在启动日志里打印这三个 PRAGMA 的实际返回值。**验收方式**：在 `tests/test_durability.py` 中断言 `PRAGMA synchronous` 返回 2 且 `PRAGMA journal_mode` 返回 `wal`。**理由引用**：avi.im 2025-08-24 实测 macOS 自带 SQLite 默认 `synchronous=1, fullfsync=0`。
   - **I3（单写者假设显式化）**：所有写操作使用 `BEGIN IMMEDIATE`；并在账本目录放一个 `ledger.lock`（flock），第二个写者立即失败退出。**论文中必须写明"我们假设单写者，多写者行为为未定义"**——这是诚实，也是把"为什么不需要隔离级别"讲清楚的前提。

2. **【2027-01 前】写一节 `research/13_why_not_serializable.md`，主动解释"为什么阙疑不用可串行化隔离"，并把它变成论文的正面贡献而不是省略。** 论据链（每条都要带引文）：
   - 引用 Hermitage 的表说明"**serializable 是唯一能阻止 G2（写偏斜）的级别**"，而阙疑因单写者天然满足；
   - 引用 PostgreSQL SSI wiki 那句 *"the fate of the transaction on session 3 is not deterministic"*，说明**SSI 的中止集合非确定，与"判决可复算"冲突**；
   - 引用 Ports & Grittner VLDB 2012 摘要，说明**引入 SSI 的代价是"应用必须实现重试循环"**，而重试循环会引入一个"判决可能被执行两次"的语义，**与 append-only 账本"一条判决只追加一次"直接冲突**；
   - 结论句建议写法：*"Queyi deliberately does not implement serializable isolation. Its ledger is single-writer and append-only; the only transactional requirement is atomicity of the (append, chain-head, checkpoint) triple. This is a weaker requirement than serializability and is satisfiable by a single SQLite transaction, whereas adopting SSI would introduce non-deterministic aborts that conflict with our recomputability guarantee."*

## 盲区（诚实标注）

- **Ports & Grittner VLDB 2012 论文正文中的具体性能数字我未核实。** 摘要只说 *"performance only slightly below that of snapshot isolation"* 和 *"significantly outperforms the traditional two-phase locking approach on read-intensive workloads"*，**没有任何百分数**。PVLDB 5(12):1850–1861 的 PDF（`vldb.org/pvldb/vol5/p1850_danrkports_vldb2012.pdf`）我没有逐页打开。**论文里若要引用具体吞吐/中止率，必须先读 PDF 原文。**
- **SSI 的误报率（false positive abort rate）我没有找到任何权威数字。** PostgreSQL SSI wiki 页面明确不含此类数字。第三方博客（如 jayicez.github.io 的 VLDB'12 读书笔记、知乎文章）可能有，但我未核实，因此**本文不给出任何误报率数字**。这是一个显著的空白：如果阙疑要在论文里论证"SSI 代价太高"，**缺少量化依据，只能论证"非确定性"这一质性缺陷**（这也足够，但要在论文中说明是质性论证）。
- **"BEGIN IMMEDIATE 可避免死锁"这一说法我未在 SQLite 官方文档中找到。** 官方只说明 IMMEDIATE 立即获取写锁并可能返回 `SQLITE_BUSY`。**该结论目前只有中文技术博客来源，属未核实。**
- **SQLite 的 `EXTRA` 模式我未做实测。** 本文关于 `FULL` 不足以保证持久性的结论，完全依赖 avi.im 博客（2025-08-24）对官方文档的解读，**我没有在真实机器上做过"提交后立即断电"实验**。这是本项目应当自己做的实验（见行动 1 的 I2），但**目前是引文而非实测**。
- **macOS 的 fsync 行为争议未解决。** 博客称 *"Apparently, Apple has purposely fucked up fsync"* 并引用 bonsaidb.io 的文章；**这是有争议的技术主张**，且随 macOS 版本变化。我未核实当前 macOS（2026 年版本）的行为。
- **`journal_mode=OFF` 下 ROLLBACK 未定义**这一条是官方原文，但**阙疑显然不该用 OFF**；此处仅作记录。
- **DRH 的 HN 评论与 SQLite 官方文档存在直接冲突**（关于 WAL+NORMAL 下"应用崩溃是否丢失"）。我**没有打开 HN 原帖核实上下文**（博客给出的链接为 `news.ycombinator.com/item?id=45014296`）。博客自己说 *"I'll leave it up to you to decide which is correct"*。**这属于"权威之间互相矛盾"的情形，论文中应如实呈现两方说法而非选边。**
- **样本偏差 / 结论外推风险**：本文所有数据库证据都来自多用户 OLTP 场景的 benchmark 与测试套件。**没有任何公开研究覆盖"单人单机 append-only 账本"这一场景**，因此"阙疑不需要隔离级别"这句话是我基于定义（无并发 → 无并发异常）的**推理**，不是引用。这个推理本身很稳（隔离性就是为并发而定义的），但**论文中应写成推理并说明前提**，而不是伪装成引用结论。
- **MySQL 8.4 官方文档中我未找到"四种隔离级别 × 三种异常"的汇总表**（该表在文档中不存在，只在教科书和博客里有）。因此 Hermitage 那张表**不能**声称与 MySQL 官方文档一致——Hermitage 是**实测**，MySQL 官方是**机制描述**，两者口径不同。这个差异本身值得在论文里作为"Hermitage 类工作必要性"的证据。
