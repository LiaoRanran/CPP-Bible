# 方向 16：Git 工作树 227 项漂移怎么安全清理

> 调研时间：2026-09-29。**本方向与其它方向不同：我实际登录了 `C:\CodeLearnling\note\note\C++\CPP-Bible` 做了只读实测**（`git status` / `git check-ignore` 类命令全部只读，未做任何修改），因此下面的数字是**本机实测值**，不是文献值。核心发现：**"227 项"这个数字本身是一个会漂移的度量——它取决于你用哪一种 `--ignored` 模式、以及测量时刻是否有其他进程在写仓库。**

## 核心结论

1. **实测：`227` 是一个口径问题，不是状态问题。** 我在 2026-09-29 实测该仓库（分支 `master`，HEAD `edbedbf1`，`2026-09-29` "666 批次：究极收尾大包"，`.git` 目录 **92 MB**，`.gitignore` **132 行 / 4,217 字节**，最后修改 `2026-09-28`）：**`git status --porcelain -uall --ignored=matching` 共 263 行 = 33 条被跟踪改动 + 10 条未跟踪 + 220 条被忽略**。而**同样的仓库换成 `git status --porcelain --ignored`（默认 `traditional` 模式）只得到 214 条被忽略项**——**同一时刻、同一仓库，仅因 `--ignored` 模式不同就差 6 条**。更关键的是：**在两次相邻的测量之间，被跟踪改动从 5 条变成 33 条**（因为同一批次的其他调研进程正在并发写入 `_arch_v47/` 与 `data/`）。**所以"227 项"应被理解为"某个时刻某个口径下的快照"，而清理方案必须对"口径"和"并发"两件事都免疫。**
2. **真正的风险不在那 220 条被忽略项，而在 33 条被跟踪改动里那 1 条 `D`。** 实测的 33 条被跟踪改动中：**32 条是 `M`（modified），1 条是 `D`（deleted）**，即 **`Examples/atoms/_atom_perf_move.asm` 在工作树中被删除了但未 staged**。**这是本仓库当前唯一"内容已经离开工作树"的条目**——其它 32 条修改与被忽略项都还在磁盘上，随时可恢复；唯独这条删除，若直接 `git checkout -- .` 会被静默还原、若直接 `git add -A && commit` 会被永久固化。**分类统计的第一要务就是把 `D` 挑出来单独审。**
3. **安全清理的正确顺序是"先固化再清理"，而不是"先清理再后悔"——因为 `git clean` 删掉的未跟踪文件不在任何 Git 对象库里。** Git 官方文档对 `git clean` 的定性是 **"Remove untracked files from the working tree"**，而 `-f` 的存在意义是 **`clean.requireForce` 默认为 `true`**（即**默认拒绝删除**）。官方对 `-x` 的说明是 **"Don't use the standard ignore rules ... This allows removing all untracked files, including build products. This can be used (possibly in conjunction with *git restore* or *git reset*) to create a pristine working directory to test a clean build."** —— 注意 `-x` 会**连被忽略的文件一起删**，而本仓库有 **220 条被忽略项**（其中 `_auto/` **106 条**、`Part0_Prerequisites/` **29 条**、`Examples/` **23 条**、`data/` **19 条**、`_adv_v80/` **13 条**）。**在这 220 条里，`data/` 那 19 条与研究产物高度相关，一旦被 `git clean -xdf` 扫掉，是不可回滚的。** 因此本方向的第一条硬规则是：**`git clean` 在本仓库默认禁用，只允许在 `git bundle` 备份成功之后、且带 `-n` 预演的前提下、逐目录执行。**

### 二、`git status --porcelain` 的分类语法（官方规范）

`<xy> <path>`，`X` = 索引状态、`Y` = 工作树状态（合并冲突时含义不同）。

| 字符 | 含义 |
|---|---|
| `' '`（空格） | unmodified |
| `M` | modified |
| `T` | file type changed（普通文件 / 符号链接 / 子模块） |
| `A` | added |
| `D` | **deleted** |
| `R` | renamed |
| `C` | copied（需 `status.renames=copies`） |
| `U` | updated but unmerged |
| `??` | untracked（`X` 与 `Y` 恒相同） |
| `!!` | ignored（**仅在 `--ignored` 时出现**） |

**两种 `--ignored` 模式（逐字要点）**：

> `traditional`：Show ignored files and directories, unless `--untracked-files=all` is specified, in which case individual files in ignored directories are displayed.
>
> `matching`：Paths that explicitly match an ignored pattern are shown. If a directory matches an ignore pattern, then it is shown, but not paths contained in the ignored directory. If a directory does not match an ignore pattern, but all contents are ignored, then the directory is not shown, but all contents are shown.

**`-u` 的三个取值**：`no`（不显示未跟踪）、`normal`（显示未跟踪文件与目录，**默认**）、`all`（连未跟踪目录内的单个文件也显示）。

**机器解析建议**：用 **`--porcelain=v1 -z`**（NUL 分隔，文件名不转义、不做引号处理），或用 **`--porcelain=v2`**（有 `# branch.oid` / `# branch.head` / `# branch.ab` 头行与 `1`/`2`/`u`/`?`/`!` 行类型）。**关键**：本机实测输出里中文文件名是**八进制转义**（如 `"_arch_v47/15_AI\350\276\205..."`），**用 `-z` 或 `core.quotePath=false` 才能避免脚本解析踩坑**。

### 三、备份手段：`git bundle`（官方定性为备份工具）

Git 官方对 `git bundle` 的说明是 **"They can be used to create both incremental and full backups of a repository"**，并且可以 **`git clone` 一个 bundle**、**`git fetch` from a bundle**。

| 手段 | 覆盖范围 | 是否含未跟踪/被忽略文件 | 适用场景 |
|---|---|---|---|
| `git bundle create` | **仅提交历史与引用** | ❌ 不含工作树未提交内容 | 备份"已提交的部分"，体积小 |
| `git stash push -u` / `create` | 被跟踪改动 + 未跟踪（`-u`）/ 含被忽略（`-a`） | ✅（`-u`/`-a`） | **把漂移固化成可恢复对象** |
| `git archive` | 某个 tree 的快照 | ❌ 不含工作树 | 交付/发布 |
| 整目录 `tar` / 复制 `.git` + 工作树 | **全部** | ✅ | **最保守**：清理前的一键全量保险 |
| 临时分支 + `commit` | 被跟踪改动 | ❌ 未跟踪需先 `add` | **推荐**：把漂移变成一次可回滚的提交 |

**`git stash` 的官方定位（Git Book「贮藏与清理」）**：`git stash save` 已于 **2017 年 10 月**在 Git 邮件列表讨论后弃用，改用 **`git stash push`**。**注意**：stash 是一个"没有分支、没有安全网"的 commit 栈——**如果 `git stash drop` 之后再 `git gc`，内容可能不可恢复**。

### 四、被删除条目的可恢复性（本仓库的实际关键点）

| 情形 | 能否恢复 | 手段 |
|---|---|---|
| **`D`（工作树删除，未 staged）** | ✅ 一定能 | `git restore <path>` 或 `git checkout -- <path>` |
| `M`（工作树修改，未 staged） | ✅ 一定能 | `git restore <path>`（**会丢弃修改，先确认**） |
| 已 `git add` 后 `git reset` 丢掉的内容 | ✅ 通常能 | `git fsck --lost-found` 找 dangling blob；或 `git reflog` |
| 已 `commit` 后被 `reset --hard` 丢掉的 commit | ✅ 通常能 | `git reflog` 找 SHA → `git reset --hard <SHA>`（**在 `gc.reflogExpire` 未过期前**） |
| **未跟踪文件被 `git clean` 删除** | ❌ **不能** | **无任何 Git 对象库记录** |
| 被忽略文件被 `git clean -x` 删除 | ❌ **不能** | 同上 |

**官方对 `git reflog expire` 的说明**：`expire` 子命令删除旧的引用日志条目；**超过 expire 时间的条目、或超过 `expire-unreachable` 时间且当前 tip 不可达的条目会被清理**。**含义：`git gc` 之后，未跟踪文件的最后希望就彻底消失了。**

### 五、`.gitignore` 治理：本仓库的两条已写明的"脚枪"

本仓库 `.gitignore` 里已经有两段注释值得逐字引用（说明作者已经踩过坑）：

> `# 注意：.gitignore 不支持行内注释，注释必须独占一行，否则整条规则失效`
>
> `# 例外：库根 D5 基准源码须跟踪（覆盖上面 /*.cpp，修复新建 bench 被静默忽略的脚枪）`

**这是本仓库最危险的一类风险**：`/*.cpp` 这类规则**只作用于根目录**，但如果某条规则写得过宽（如 `data/` 或 `*.json`），**新建的研究产物会被"静默忽略"——你不会在 `git status` 里看到它，直到你需要它时才发现它从未入库。** 本仓库 **`data/` 有 19 条被忽略项**、**`tools/` 有 4 条**，正是这类高风险区。

**调试手段（官方）**：`git check-ignore -v <path>` 会**打印是哪一行 `.gitignore` 规则命中了该路径**（`--stdin` 可批量）。**这是唯一能"看见"静默忽略的诊断工具。**

## 对阙疑的 3 条具体行动

1. **先固化，再清理：在 2027-01 前把"漂移清账"做成一条可重复执行的脚本 `tools/drift_triage.sh`，第一条命令永远是全量备份。** 执行顺序（**严格按序，不可跳步**）：
   ```
   cd "C:/CodeLearnling/note/note/C++/CPP-Bible"
   # 0) 全量保险：bundle（含所有 ref）+ 工作树整目录 tar
   git bundle create ../backup_$(date +%Y%m%d).bundle --all
   tar -czf ../worktree_$(date +%Y%m%d).tgz --exclude=.git .
   # 1) 分类统计（先只看，不动）
   git status --porcelain -uall --ignored=matching > /tmp/drift_all.txt
   grep -c '^??' /tmp/drift_all.txt   # 未跟踪
   grep -c '^!!' /tmp/drift_all.txt   # 被忽略
   git status --porcelain -uno        # 被跟踪改动（重点看 ' D ' 和 ' M '）
   # 2) 单独审每一条 D
   git status --porcelain -uno | grep '^ D'
   git diff --stat -- Examples/atoms/_atom_perf_move.asm
   # 3) 用临时分支固化，而不是 stash
   git switch -c drift/2026-09-snapshot
   git add -A && git commit -m "chore(drift): snapshot 2026-09 工作树漂移（清理前固化）"
   git switch master
   ```
   **判据**：`grep '^ D'` 的输出必须逐条人工确认——**本仓库当前有且仅有 1 条 `D`（`Examples/atoms/_atom_perf_move.asm`），它是唯一"内容已离开工作树"的条目**。**禁止在没有 bundle + tar 双备份的情况下执行任何 `git clean`。**
2. **在 2027-01 前把 `.gitignore` 的"静默忽略"风险清掉：对 `data/`、`tools/`、`Part0_Prerequisites/`、`Examples/` 四个目录逐条跑 `git check-ignore -v`，并产出白名单。** 具体命令：
   ```
   git status --porcelain -uall --ignored=matching | grep '^!!' | sed 's/^!! //' \
     | xargs -d '\n' git check-ignore -v > /tmp/ignore_explain.txt
   grep -E '^(data|tools|Part0_Prerequisites|Examples)/' /tmp/ignore_explain.txt
   ```
   **依据**：本仓库已有先例——`.gitignore` 里明确记录了"新建 bench 被静默忽略的脚枪"，并为此加了 `!_bench_d5_*.cpp` 例外。**现在 `data/` 有 19 条、`tools/` 有 4 条被忽略项，其中极可能包含研究产物。** 行动：把**必须入库的研究产物**（`data/*_baseline.json`、`data/counterfactual_cases_*.json`、`tools/*.py`）用 `!` 例外规则显式纳管，**并把这条规则写进 `.gitignore` 的注释里说明理由**（沿用仓库现有风格）。**时间点：2027-01 前完成；此后每次新增数据目录都必须先跑一次 `check-ignore`。**
3. **把"漂移度量"写进论文的 Reproducibility Statement，并明确口径——这是把工程债转化为 E&D 卖点的机会。** 具体写法：`Repository state at submission: N tracked modifications, M untracked files, K ignored entries, measured with \`git status --porcelain -uall --ignored=matching\` on <date> at commit <sha>. Full worktree snapshot archived as a git bundle (git bundle create --all) and deposited with the artifact.` **理由**：① 本方向实测已经证明**同一仓库换 `--ignored` 模式会差 6 条、并发写入会让数字从 5 变 33**——**把口径写清楚，是 E&D track "documentation methodologies" 与 "reproduction/auditing" 明文欢迎的内容**；② 这与阙疑"证据可追"的主卖点同构：**可复算的前提是可复现的度量口径**；③ **零额外成本**——你本来就要为投稿冻结仓库，顺手把口径写进论文即可。

## 盲区（诚实标注）

- **"227 项"未能复现。** 我实测得到 **263**（`-uall --ignored=matching`）与 **257**（`traditional` 口径下 214+33+10）。**227 这个数字本次未能通过任何我试过的口径复现**，可能是 ctx 撰写时刻的快照，也可能包含我未试到的选项组合（如 `--ignored=no` + 子模块、或按目录折叠计数）。**本文件不主张 227 有误，但主张它必须连口径一起给出才能复现。**
- **测量期间仓库在被并发写入，因此我的快照本身可能已被污染。** 证据：第一次测 `git status --porcelain` 得 **5 行**，几分钟后测 `-uno` 得 **33 行**。**因此上表的 33/10/220 是"某一瞬间"的值，不是稳定值。** 若要做正式审计，**必须先在仓库上冻结写入**（或至少记录测量时刻）。
- **我没有执行任何写操作。** 全程只用 `git status` / `git rev-parse` / `git log` / `ls` / `head` / `wc` / `du` 等只读命令。**上表里的 33/10/220 是只读观测值；行动 1 里的 `git bundle` / `tar` / `git add` / `git commit` 都是"建议执行、本次未执行"。**
- **`git clean` 的官方文档本次只取到 `git-clean` 页（last updated in 2.45.0）。** 本机 Git 版本未核实；**`-X` 与 `--ignored=matching` 的交互在不同版本间可能有差异**，落地前请先 `git --version` 并在一个副本仓库上试跑。
- **`git stash` 的"2017-10 弃用 `save`"这一条来自 Git Book 中文版（`git-scm.com/book/zh/v2`）**，本次**未逐字打开原始邮件列表讨论**。表述为"官方文档记录了这次讨论"是安全的，但不要写成"Git 官方废弃了 stash save"。
- **`git fsck --lost-found` 与 `git reflog` 的恢复成功率本次未实测。** 这两条是通行做法，但**对"未跟踪文件"无效**（未跟踪文件从未生成 blob 对象，reflog 与 fsck 都看不到）——这一点是 Git 的对象模型决定的，**不是经验之谈**。
- **`Part0_Prerequisites/`（29 条）、`_adv_v80/`（13 条）、`Examples/`（23 条）为何被忽略，本次未逐条核查。** 这三个目录的忽略规则来源可能是仓库根 `.gitignore`、子目录 `.gitignore`、`.git/info/exclude` 或全局 `core.excludesFile` 四者之一。**行动 2 的 `git check-ignore -v` 会直接打印来源，这是唯一权威答案。**
- **本文件不覆盖 `git filter-repo` / `git filter-branch` 类历史改写。** 那属于"匿名化"范畴，见方向 19。本方向只处理**工作树漂移**，不改写历史——**这是刻意的边界，因为改写历史会破坏方向 08/14 所依赖的"三段式版本证据链"。**
