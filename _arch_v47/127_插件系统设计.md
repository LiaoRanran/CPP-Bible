# 方向127：插件系统设计——从OSGi到extern "C"：边界即契约

## 核心结论

1. **插件系统的本质不是"动态加载代码"，而是"在不可信边界上签订契约"**。三十年的工业经验高度一致：Eclipse OSGi（1999年启动、R1规范2000年5月发布）用 Bundle 清单声明导入导出包与版本区间[1]；VS Code 扩展模型（2015年随产品发布）用 `package.json` 清单声明激活事件与能力点[3]；Java SPI（`ServiceLoader` 自 Java 6，2006年12月）用 `META-INF/services` 文件做无代码耦合的发现[4]。三者形式不同，内核都是同一句话：**宿主与插件之间只交换"清单+稳定函数签名"，不交换实现细节**。对阙疑而言，这正是 3826 行内核与 67 条规则、9 个保护器之间应有的关系——规则可以增删，内核不许改。

2. **C/C++ 做插件的最大坑是 ABI，而不是 API**。`dlopen/dlsym` 本身简单（源自 SunOS 4.0，1988年；POSIX.1-2001 标准化）[5]，但 C++ 符号经 name mangling 后，不同编译器、同一编译器不同版本、甚至同一版本不同编译选项下符号名都不同[6]；GCC 5.1（2015-04）引入的双 ABI（`_GLIBCXX_USE_CXX11_ABI`）让 `std::string` 跨模块传递至今仍是经典事故[7]。工业界的标准答案是微软 COM 在 1993 年就给出的：**跨模块边界一律走 C 二进制约定**——`extern "C"`、固定调用约定、不透明句柄、`IUnknown` 式引用计数（`AddRef/Release/QueryInterface`）[8]。

3. **插件市场已是供应链攻击的主战场，"市场审核过"不等于安全**。RMIT 大学与 ICSI 伯克利对 VS Code 生态的实测研究（arXiv:2411.07479，2024-11）分析 52,880 个扩展，发现 2,969 个（5.61%）存在可疑行为，累计安装量 6.13 亿次[10]；2026 年 Open VSX 的 GlassWorm 行动用 `extensionDependencies` 传递依赖投毒，单次波次识别出 72 个恶意扩展[11]。结论对阙疑直接成立：**任何第三方贡献的规则都必须按不可信代码处理**——沙箱化、能力最小化、崩溃隔离。

## 技术全景与关键数字

### 一、OSGi：版本协商与生命周期管理的天花板

OSGi（Open Services Gateway initiative，1999年由 Ericsson、IBM、Sun 等组建）定义了一套 Java 模块化规范：每个 JAR 即一个 Bundle，清单 `MANIFEST.MF` 中用 `Export-Package`/`Import-Package` 声明对外暴露与需要的包，且**导入可带版本区间**（如 `version="[1.2,2.0)"`），由框架在解析阶段做协商；Bundle 有完整生命周期（installed→resolved→starting→active→stopping→uninstalled），支持运行时热插拔[1]。Eclipse 3.0（2004-06）放弃自研插件模型、全面采用 OSGi R3 实现 Equinox[2]，证明该模型能支撑数万插件的大型生态。OSGi 给出的两个关键设计原语——**版本区间协商**与**服务注册表（Service Registry，接口与实现分离，插件只注册接口实例）**——是后续一切插件系统的共同祖先。

### 二、VS Code 扩展模型：清单驱动 + 激活事件 + 能力点

VS Code 扩展是一个含 `package.json` 的目录/包：`activationEvents` 声明何时加载（懒加载，启动时不执行任何扩展代码），`contributes` 声明向哪些**扩展点（extension point）**注册贡献（命令、语言、调试器等），宿主通过稳定的 Extension API 暴露能力[3]。模型优点是宿主可在独立宿主进程中运行扩展、并限制 API 面；缺陷同样明显——API 没有细粒度沙箱，扩展拿到 `workspace` 权限即可读全部工作区文件、可执行任意 Node 代码。前述 arXiv:2411.07479 实测的五类问题（恶意、脆弱、隐私侵犯等）正是建立在此结构上[10]。

### 三、Java SPI：零编译耦合的发现机制

SPI（Service Provider Interface）约定：接口定义在核心，实现在 classpath 上用 `META-INF/services/<全限定接口名>` 文件逐行列出实现类名，`ServiceLoader.load(接口.class)` 在运行时发现并实例化[4]。JDBC `Driver`、SLF4J 绑定、日志实现都是此模式。它的智慧在于**发现靠配置文件而非代码符号**——宿主与插件之间不存在任何编译期符号依赖。代价是能力极弱：无版本协商、无生命周期管理、无隔离。

### 四、C/C++ 的 dlopen 与 ABI 地狱

`dlopen("x.so", RTLD_NOW)` + `dlsym(handle, "sym")` 是 POSIX 动态加载原语[5]。三个层次的兼容性问题必须分清：

| 层次 | 问题 | 机制/案例 |
|---|---|---|
| 符号名 | C++ name mangling | GCC/Clang 在 x86-64 上遵循 Itanium C++ ABI（2001年），`std::string foo(int)` 被编码为 `_Z3fooi`；MSVC 使用完全不同的方案，两者互不兼容[6] |
| 标准库 | STL 实现与 ABI | GCC 5.1 起双 ABI 并存，新旧 `std::string` 布局不同，跨模块按值传递导致内存破坏[7]；MSVC 各主版本 STL 同样不保证 ABI |
| 编译器/运行时 | 异常、调用约定、RTTI | libc++ 与 libstdc++ 的异常对象不能互投；`-fno-exceptions`/不同异常模型混用崩溃 |

### 五、COM 与 GIMP：两种隔离哲学

微软 COM（1993 年随 OLE 2.0 推出）以 `IUnknown` 三方法（`QueryInterface` 做能力发现、`AddRef/Release` 做生命周期）、`HRESULT` 返回码、接口指针表为核心，达成跨语言、跨版本二进制兼容，并演进为 DCOM（1996）与 WinRT[8]。它的铁律是**接口一经发布永不改变，要变就定义新接口**。GIMP（1995 年由 Kimball 与 Mattis 创建）走另一条路：插件经 libgimp 与宿主的 PDB（Procedural Database）通信，**每个插件是独立进程**，通过 shm/socket 上的线协议交换数据，Script-Fu（TinyScheme 方言）同样注册为 PDB 调用[9]。独立进程带来天然的崩溃隔离——插件崩溃只杀自己。

### 六、沙箱、能力授权与市场供应链

现代插件系统（Figma、Shopify、Envoy、VS Code Web 版）普遍转向 **WASM + capability** 方案：插件无默认权限，文件/网络/时间能力由宿主显式注入。而传统原生插件市场（VS Code Marketplace、Open VSX、JetBrains Marketplace）的供给端事故已常态化：GlassWorm 利用传递依赖让"审核时干净"的扩展日后拉入恶意载荷[11]；2026 年 Aikido 披露 15 个恶意 JetBrains 插件约 7 万次安装、专窃 AI API Key。防御共识：清单签名、发布者验证、安装量异常监控、权限最小化、可选的进程/WASM 隔离。

版本协商在实践中的三个反模式也值得记录：其一，**只比较主版本号**——OSGi 的经验是区间必须细到 minor/patch，因为接口语义可能在 minor 版本中收紧；其二，**协商成功后缓存协商结果但不监听插件卸载**，热插拔场景会出现指向已卸载实现的悬空引用，OSGi 用服务的动态性（服务引用失效即重新绑定）正面处理；其三，**允许插件在运行时反向查询宿主内部对象**，这等于把 ABI 边界打穿，COM 的对策是除 `IUnknown` 外一律不暴露未经版本化的接口。一句话总结三十年经验：**契约窄、版本显式、能力按需，三者缺一个插件系统都会随生态膨胀而失控**。

## 对阙疑的映射

### 一、9 保护器与 67 规则的插件化：把"规则即代码"降级为"规则即清单+合约"

阙疑当前结构是 37 实卡、67 规则、9 保护器、452 条账本、3826 行内核。规则与保护器如果以 Python/C++ 符号直接耦合，每次新增规则都触碰内核——这既违背"内核冻结"的论文承诺，也让 holdout 30 条（17 真错、检出 66.7%）与 corpus 40 条（检出 43.8%）的盲态评测面临"评测后内核随规则漂移"的合理性质疑。应直接借用 OSGi/VS Code 的设计：**每条规则是一个自描述包**——规则 ID、适用 AST 节点类型、所需保护器编号、版本号、能力声明（是否需要编译、是否需要网络——默认都不需要）写在清单里；内核只实现一个注册器与执行器，规则以稳定的 `extern "C"` 函数表注册。规则从 67 条增到 100 条，内核一行不改、3826 行的数字在论文全周期保持有效。

### 二、C 接口边界：extern "C" 是阙疑跨编译器复现的唯一硬保证

阙疑的变异测试成绩（core 97.3%、all 81.5%）依赖大量编译/执行循环，未来评测者可能用 GCC 11/13、Clang 15/17 不同工具链重放。如果规则插件导出 C++ 符号，name mangling 与 STL ABI 差异会让"别人机器上加载失败"——这在 NeurIPS 2027 E&D 赛道"documented and executable"口径下是 desk-reject 级风险。落地做法照搬 COM：

```c
extern "C" {
  typedef struct queyi_rule queyi_rule;
  // 每个插件只导出这一个符号；ABI 一旦冻结永不改，要变就出 v2
  const queyi_rule* queyi_rule_v1(void);
}
```

规则需要的 AST 上下文由内核按不透明句柄 + C 访问器传入；**禁止跨边界传 `std::string`/STL 容器、禁止跨边界抛异常**；字符串用显式长度指针。这样 GCC 编译的内核能加载 Clang 编译的规则，反之亦然。函数表还应显式版本化：表首放结构体大小与版本号字段，内核按版本决定可调用项，新增能力只能在表尾追加——这与 COM"新接口不改旧接口"是同一条生存法则。

### 三、第三方规则不可信：沙箱与能力最小授权

阙疑若公开规则征集（对拿社区反馈与 NeurIPS E&D 曝光必要），收到的规则就是不可信代码：可以在执行时读账本、改判决、外泄 452 条账本数据。能力模型必须是**默认零能力、显式授予**：规则只拿到"读取本条 AST 片段、写判决对象"两个函数表；没有文件系统、没有进程、没有网络、没有编译器调用——需要编译的少数规则（如编译期恶意外代码探针）由内核代行，规则只提交源码片段并接收结构化结果。能力设计上每条规则的清单就是其能力申请，超出声明的调用在内核侧直接拒绝并记入账本。这同时是论文里"系统对恶意贡献者鲁棒"的直接证据。

### 四、崩溃隔离：插件崩溃不能拖垮内核

67 条规则里未来可能有除零、栈溢出、UBSan 已报的未定义行为。Python 层的异常隔离不够——C++ 规则段错误会杀掉整个内核进程。GIMP 的独立进程模型给出了廉价答案：**进程级隔离**——每个（或每批）不可信规则在子进程执行，父子之间用长度前缀的二进制消息通信，子进程超时/段错误/非零退出时内核按"该规则无法判决（UNKNOWN，四态之一）"记账并继续。内核 3826 行的稳定性因此与规则质量解耦。反事实测试 P=R=F1=0 的结论越刺眼，这套"失败可记账、流程不中断"的工程纪律就越重要——它保证最坏情况下系统输出 UNKNOWN 而不是崩溃或伪造判决。对账器重放账本时若发现历史上的 UNKNOWN 如今变成了确定判决，也应作为差异报出——系统行为随规则版本的任何变化都必须显式可见。

### 五、版本协商：让 452 条账本可永久重放

OSGi 版本区间的价值对阙疑是账本可复算性：每条账本记录所用规则 ID 与版本，规则仓库允许同一规则多版本并存，旧账本永远能解析到对应版本执行。NeurIPS 审稿人两年后重放 452 条账本时，拿到的判决必须与今天逐位一致。版本协商规则简单写死：内核支持 ABI v1 区间 `[1.0,2.0)`，插件声明 `abi=1`，不匹配则拒绝加载而非尝试兼容。

### 六、9 保护器的定位与工程克制

9 保护器目前与内核同生共死，一旦保护器逻辑需要调整（例如新增 sanitizer 调用方式），就被迫改动内核。插件化后保护器应作为一类特殊插件存在：它不产生判决，只向规则提供"编译、执行、取证"三类受保护操作；保护器之间显式声明先后顺序（如先静态后动态），由内核编排。这样保护器未来扩到 15 个时，系统结构与论文叙述都不必返工。同时必须清醒：插件框架本身有成本，加载层、版本协商、IPC 序列化都会写进内核，3826 行的数字不可能在加入框架后完全不变。诚实做法是区分"判决内核"与"插件运行时"两个规模数字，重构完成立即冻结、全评测周期不再漂移。插件化只解决规则与内核的耦合，不解决规则判得准不准——holdout 66.7% 与 corpus 43.8% 的差距主要来自语料难度与规则覆盖，不会因架构升级而改善。架构改造与评测推进必须分成两条时间线，这是单人项目避免互相拖累的关键纪律。

## 对阙疑的三条具体行动

1. **冻结插件 ABI v1 并改造规则加载层（2026-11 前）**：在仓库内定义 `plugin/queyi_plugin.h`（仅 C  linkage、不透明句柄、固定函数表），把现有 67 条规则重构为自描述插件包（含 `rule.yaml` 清单：ID/版本/AST 匹配模式/能力声明），3826 行内核只保留注册器与执行器；完成后内核行数重新核对并在论文中冻结该数字。
2. **上线进程级隔离执行器（2027-01 前）**：规则在子进程执行，加超时（建议单规则 10s）、段错误兜底，失败一律记四态中的 UNKNOWN；用现有 holdout 30 条全量回归，确认隔离前后判决一致（仅允许 UNKNOWN 不增加假阳性），并跑一次变异 core 集确认 97.3% 不回退。
3. **在公开规则征集前落地能力白名单与签名（2027-03 前）**：规则调用经能力代理，文件/网络/进程能力默认拒绝；第三方提交的规则包要求签名，内核侧校验；同步在论文 threat model 一节写明"恶意规则贡献者"威胁与对应缓解，作为 E&D 赛道的系统贡献点。

## 盲区

- OSGi 早期版本号与 Eclipse 3.0 采用时点依据社区资料与官方文档核对，**未逐页阅读 OSGi R1 原始规范文本（2000年）**；R3 版本号引用可能有偏差。
- COM 推出时间存在"1993 年 OLE 2.0"与 COM 作为独立架构对外公布时点的细微差异，本文采用 1993 口径；WinRT 与 COM 的继承关系未展开。
- GIMP PDB 的过程总数（随版本变化大）未引用具体数字，仅描述机制；GIMP 3.0 插件架构变化未覆盖。
- 2026 年 GlassWorm、Nx Console、JetBrains 插件事件主要来自安全厂商博客（Snyk/CSA/Aikido），**非 CVE 官方一手文本**，投稿前需逐条回 NVD 核对。
- 子进程隔离的具体性能损耗（阙疑 452 条账本重放总耗时变化）未实测，10s 超时阈值是经验起点。
- 未评估 Windows 侧等价方案（named pipe + 作业对象），当前设计默认 Linux 评测环境。
