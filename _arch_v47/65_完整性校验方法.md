# 方向 65：数据/账本完整性校验的通用方法（integrity verification beyond Merkle）

> 项目锚点（来自 `_v47_ctx.md`）：阙疑 / queyi 是判定 C++ 知识断言是否成立的验证系统，机制为四态判决 + append-only 哈希链账本 + Merkle checkpoint + 不依赖内核的独立对账器；实测规模（2026-09）为 452 条判决账本、67 规则（block 44 / warn 16 / advice 7）、9 保护器、内核 `gate_engine.py` 3826 行。本文聚焦"除 Merkle 外还有哪些完整性保障手段"，并给出端到端不可篡改证据链与独立对账器的可行设计。

---

## 核心结论

1. **Merkle 只是七类手段之一，且对"对抗性内容注入"存在结构性盲区。** SHA-1 已于 2017-02-23 被 SHAttered 攻破（CWI Amsterdam + Google Research，两份不同 PDF 共享同一摘要 `38762cf7f55934b34d179ae6a4c80cadccbb7f0a`，实际计算量约 2^63.1 ≈ 9.2×10^18 次哈希，比通用生日攻击的 2^80 快约 10^5 倍）；Git 因此自 2018 年底选定 SHA-256 作为继任哈希（文档在 Git v2.52.0 / 2025-11-17、v2.55.0 / 2026-06-29 仍在迭代）。阙疑应直接采用 **SHA-256 + 向量承诺（Verkle 单叶证明可由 ~1KB 缩到 <150 字节，Vitalik Buterin 2021）**，而非裸 SHA-1 Merkle，避免重蹈内容寻址崩溃的覆辙。

2. **端到端证据链必须"分层堆叠"而非单点依赖：内容寻址（CAS）＋ 追加哈希链 ＋ 周期检查点 ＋ 数字签名 ＋ 可信时间戳 ＋ WORM。** 其中数字签名（Ed25519 / ECDSA，非对称）提供公钥可验证的**不可否认性**，而 HMAC（对称）只能做"共享密钥方之间的完整性"，无法向第三方证明来源；RFC 3161（2001）可信时间戳由 TSA 作为可信第三方把"哈希 + 时间"强绑定，提供"某时某刻已存在"的证据；WORM 在存储层强制不可变，满足 SEC 17a-4(f) / FINRA 4511 / HIPAA 等合规。Trillian 与证书透明（RFC 6962, 2013）已证明独立 auditor / monitor 可在**不信任服务端**的前提下用 inclusion / consistency proof 验证 append-only。

3. **独立对账器的工程核心是"不信任内核复算"。** 参考 GLASSDB（arXiv:2207.00944，Cong Yue 等，VLDB 2023）的透明日志抽象与 Microsoft Signing Transparency Ledger 的开源 ledger explorer，对账器必须是与 `gate_engine.py`（3826 行）**完全解耦的独立进程**，仅消费 published fixtures（内容寻址）+ rules（67 条）+ ledger 原始记录，逐条复算四态判决并比对，使第三方可在不读内核代码的情况下验证全 452 条账本——这正是阙疑"判决可复算、证据可追、盲态协议不可回盲"三大卖点的技术落点。

## 精确数字与案例

### 一、数字签名 vs HMAC：完整性之外还要"谁能证明"

二者都基于哈希做消息认证，但信任模型迥异。HMAC 用**对称共享密钥**，计算快（测过 HMAC-SHA256 在普通 CPU 上可达 GB/s 级），但任何持有密钥的一方都能生成，无法向第三方证明"究竟是谁签的"，即**无不可否认性**。数字签名基于**非对称密钥**（ECDSA / Ed25519 / RSA），签名者用私钥签哈希摘要，验证者用公钥验证，提供来源认证与不可否认性，但需要公钥基础设施（PKI）或可信密钥分发。

| 维度 | HMAC（如 HMAC-SHA256） | 数字签名（如 Ed25519 / ECDSA） |
|---|---|---|
| 密钥类型 | 对称（共享密钥） | 非对称（私钥签 / 公钥验） |
| 不可否认性 | 无（双方都能生成） | 有（仅私钥持有者可生成） |
| 第三方可验证 | 否（需共享密钥） | 是（公钥可公开） |
| 典型性能 | 快（对称运算） | 较慢（非对称，但 Ed25519 已很快） |
| 适用场景 | 内部系统 / API 调用 / 服务间 | 对外凭证 / 审计 / 合规 / 不可篡改证据链 |

对阙疑的启示：账本条目（452 条）若只用 HMAC 签名，则任何能接触密钥的进程都能"自己证明自己"，无法向审稿人/第三方证明判决由可信内核产生；**检查点必须用非对称签名（Ed25519）做签名树头（Signed Tree Head）**，公钥随论文公开，任何人可验。

### 二、内容寻址存储（CAS）与 SHA-1 的崩塌：地址即哈希是一把双刃剑

内容寻址的核心思想是"数据内容的哈希即其地址"，Git blob、IPFS CID 均如此——任何篡改都会改变地址，天然防篡改。但前提是**底层哈希抗碰撞**。SHAttered 直接击穿了这一前提：

> "On 23 February 2017, researchers at the Cryptology Group at CWI Amsterdam and Google Research published two different PDF files that share the same SHA-1 hash. The digest is `38762cf7f55934b34d179ae6a4c80cadccbb7f0a` for both." — shattered.io

计算代价与对照：

| 项目 | 数值 | 说明 |
|---|---|---|
| 通用生日攻击（暴力基线） | 约 2^80 | 160-bit 哈希的理论基线 |
| SHAttered 实际攻击 | 约 2^63.1（≈ 9.2 quintillion） | 相同前缀碰撞（identical-prefix） |
| 相对暴力加速 | 约 100,000× | 使攻击从"世纪级"降到"月级" |
| 第一阶段算力 | 约 6,500 CPU-years | Google 公布 |
| 第二阶段算力 | 约 110 GPU-years | Google 公布 |

Git 的反应是启动 SHA-1→SHA-256 迁移：官方 `hash-function-transition` 文档明确 *"Migrate Git from SHA-1 to a stronger hash function"*，且 *"In late 2018 the project picked SHA-256 as its successor hash"*；版本记录显示 v2.52.0（2025-11-17）、v2.55.0（2026-06-29）仍在更新该迁移。IPFS 目前已采用更现代的哈希（CIDv1 可携带 `sha2-256` / `sha3-256` / `blake3` 等多算法）。**阙疑 fixtures 的内容寻址必须直接用 SHA-256（或 blake3），绝不能用 SHA-1 做 CID。**

### 三、可信时间戳（RFC 3161）与 WORM：把"存在性"和"不可变性"钉死

RFC 3161（2001 年 8 月，*Internet X.509 Public Key Infrastructure Time-Stamp Protocol*）定义 TSA 的请求/响应格式。其本质是：

> "The TSA is a TTP that creates time-stamp tokens in order to indicate that a datum existed at a particular point in time." — RFC 3161

且 TSA **只对哈希签名**：*"to only time-stamp a hash representation of the datum, i.e., a data imprint associated with a one-way collision resistant hash-function uniquely identified by an OID."* 这给了阙疑一个关键能力：**把每个周期检查点的 Merkle/Verkle 根哈希提交给 RFC 3161 TSA，得到带可信时间的可验证令牌**——任何人在未来都能证明"该判决根在时刻 T 之前已存在且内容未变"，这对学术论文的"证据可追"与防事后篡改至关重要（且可用国密 SM2/SM3 的 RFC 3161 实现替代 RSA/SHA 以符合国内合规）。

WORM（Write Once Read Many）则在存储层兜底不可变。Veeam 的定义指出 WORM 用于满足合规：

> "viable for a host of industry regulations, including SEC 17a-4(f), FINRA Rule 4511, and HIPAA." — Veeam

| 手段 | 防谁 | 关键保证 | 阙疑可用点 |
|---|---|---|---|
| RFC 3161 时间戳 | 事后否认 / 倒填 | 哈希与可信时间绑定 | 检查点根哈希上链前先盖 TSA 章 |
| WORM 存储 | 运维误删 / 恶意改写 | 写入后不可改不可删 | ledger 目录设为 immutable / 只读提交 |
| 软件强制 WORM | 应用层越权 | immutable 标志锁文件 | Git 仓库 + 只读 tag 充当轻量 WORM |

注意：WORM 防的是"存储被改"，**不防"写入时就是错的"**——它必须叠加在正确性的对账之上，这正是独立对账器的价值。

### 四、透明日志、Verkle 与 GLASSDB：让第三方"不信任服务端"地验证

证书透明（RFC 6962, 2013）与 Trillian 给出了可验证 append-only 日志的成熟范式。Trillian 文档说明验证者可在本地重建根哈希：

> "the entry's hash and the proof hashes can be combined to recreate the root hash of the tree." — Trillian Transparent Logging Guide

其默认叶子哈希为 `SHA-256(0x00 | leaf.LeafValue)`（前缀 0x00 抗第二原像攻击），并提供 **inclusion proof（包含证明）** 与 **consistency proof（一致性证明）**，配合 **Signed Tree Head** 让外部 auditor/monitor 不信任服务端即可发现篡改。这正是阙疑独立对账器可借鉴的协议骨架。

Verkle 树是 Merkle 的直接升级，用**向量承诺**替代内部节点的哈希拼接：

> "a tree holding a billion pieces of data needs about 1 kilobyte for a proof under a traditional binary Merkle tree, but a Verkle tree can produce the same proof in under 150 bytes" — shattered.io（引 Vitalik Buterin 2021）

| 方案 | 单叶证明大小（~10 亿叶子树） | 备注 |
|---|---|---|
| 传统二进制 Merkle | ~1 KB | 需路径上所有兄弟哈希 |
| Verkle（KZG 向量承诺） | <150 字节 | 需可信设置、非后量子 |
| 二进制树 + STARK（ETH 2026 新路线） | <25 KB | 无需可信设置、后量子 |

需诚实标注：截至 2026-09-29，**无主要生产区块链在主状态运行 Verkle**（shattered.io 文章称，以太坊 2026-03 已 pivot 到"二进制树 + STARK"）。对阙疑而言，Verkle 的意义在于"证明更小"，但对 452 条账本这种小规模，普通 Merkle + SHA-256 已足够，Verkle 可作未来论文的"可扩展性讨论"而非必需。

GLASSDB（arXiv:2207.00944，Cong Yue、Tien Tuan Anh Dinh、Zhongle Xie、Meihui Zhang、Gang Chen、Beng Chin Ooi、Xiaokui Xiao，提交 2022-07-03，终版 2023-02-20，VLDB）把透明日志抽象成可事务的账本数据库：

> "we explore the design space of verifiable ledger databases along three dimensions: abstraction, threat model, and performance." — GLASSDB 摘要

它为阙疑提供两个借鉴：(a) 明确区分**威胁模型**（不可信服务端 vs 不可信客户端），独立对账器应定位为"不可信服务端"视角；(b) 提出专用 benchmark（扩展 YCSB/TPC-C）——阙疑可借鉴其方法论设计自己的复算基准。

### 五、纠删码（Reed-Solomon）：完整性之外的"可恢复性"保障

纠删码（erasure code）严格说保障的是**可用性与可恢复性**而非单纯完整性，但它能检测并纠正存储损坏，是完整性栈的补层。Reed-Solomon 是最大距离可分码（MDS Code）：把 k 个数据块编码为 n = k + m 个分片，任意 k 个即可重建。Google Colossus、Azure Storage（LRC）等均有部署（具体参数未核实）。对阙疑：452 条账本 + fixtures 体量极小，纠删码意义不大，但**跨地理副本 + 校验分片**可作为 WORM 之外的"灾难恢复兜底"，防止单点丢失。具体参数（如 k=6, m=3）属未核实区间，论文中不宜给死数字。

## 对阙疑的 3 条具体行动

1. **为 452 条账本引入"双层哈希链 + 周期检查点 + Ed25519 签名树头 + RFC 3161 时间戳锚定"的 schema。** 在账本写入 API（如 `ledger.py` 的 `append()`）每条记录增加字段：`prev_hash`（指向上一条 SHA-256 哈希）、`checkpoint_root`（每 N 条做的 Merkle 根）、`sig`（Ed25519 对 `checkpoint_root` 的签名）、`tsa_token`（RFC 3161 时间戳响应，可用 GlobalSign / 联合信任 v.tsa.cn 或国密 SM2/SM3 TSA 获取）。**时间点：2027-03 前完成 schema 与写入器改造**，并在 `_arch_v47/` 新增 `66_账本证据链schema.md` 记录字段定义。

2. **实现完全解耦的独立对账器 `reconciler.py`（绝不 `import gate_engine` 任何符号）。** 该进程只读三类 published 产物：fixtures（内容寻址、SHA-256 CID）、rules（67 条，明文或版本化快照）、ledger 原始记录（不含内核计算结果）。它用一份**独立的极简参考解释器**复算每条四态判决，与账本中 kernel 记录的 `verdict` 比对，输出 `diff_report.json`（含每条 `entry_id / recomputed / recorded / match`）。命令示例：`python reconciler.py --ledger ledger.jsonl --fixtures ./fixtures --rules rules.yml --out diff_report.json`。**时间点：2027-04 前跑通对 452 条的全量复算，并作为论文"可复算性"的实证**。

3. **把 fixtures 改为内容寻址并对账本目录施加软件 WORM + Transparency-Log 风格单条验证。** 每个 fixture 文件以 `sha256:` 前缀的 CID 存入账本条目的 `fixture_cid` 字段（杜绝哈希碰撞用 SHA-256，不用 SHA-1）；账本目录以只读 tag / immutable 标志充当轻量 WORM；同时为每个检查点签发 inclusion proof，使第三方可用 `verify_entry.py --id <n> --root <signed_root>` 不下载全量即验证单条判决。结合行动 1 的 `tsa_token`，形成"内容寻址→哈希链→检查点签名→时间戳→WORM→独立复算"的端到端证据链。**时间点：2027-05 前完成并在论文方法节画出证据链图**。

## 盲区（诚实标注）

- **阙疑内部规模数字（452 条账本、3826 行 `gate_engine.py`、67 规则、变异率 97.3%/81.5% 等）来自共享上下文 `_v47_ctx.md` 的给定锚点**，本文按给定使用，未做独立一手核验；若这些锚点本身漂移（上下文提到工作树 227 项漂移、README 口径滞后），需以实际仓库为准。
- **纠删码在 Google Colossus / Azure LRC 的具体参数（k、m、编码矩阵）未核实**，本文未给出死数字，仅作"可恢复性补层"的方向性引用；具体内容建议引用原始论文（如 Sathiamoorthy et al., "XORing Elephants", SoCC 2013）而非二手博客。
- **WORM 抵御勒索软件/数据丢失的具体百分比未核实**——Veeam 文章只列出合规法规（SEC 17a-4(f)、FINRA 4511、HIPAA），未给出量化防护率；如需量化数字须另查一手报告，本文不编造。
- **Verkle 的"主网未运行"结论来自 shattered.io 2026-09-29 文章（二手）**，非以太坊官方一手公告；以太坊 2026-03 转向"二进制树+STARK"亦为该文转述，存疑，论文引用前需查以太坊官网/EF 博客原始声明。
- **RFC 3161 的实际采用率、国密 SM2/SM3 TSA 的合规认定细节未核实**；国内司法对 RFC 3161 时间戳的可采性需引用《电子签名法》与具体判例，本文仅做方向性提示。
- **部分搜索结果来自 SEO 性质博客**（如 ai-governance-standard.com、certifieddata.io、aegistraces.com 等关于"AI 审计日志"的文章），内容质量与可复核性存疑，本文未将其作为硬证据，仅用于印证"签名追加日志"这一工程趋势。
- **样本偏差**：本文英文来源以 Google / Microsoft / 学术界（VLDB、arXiv、RFC）为主，对国内标准（GB/T、GM/T 国密）覆盖不足；若论文面向国内合规，需补充 GM/T 0033-2023 等一手文档。
