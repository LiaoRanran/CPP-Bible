# 方向 56：数论在哈希密码中的应用

## 核心结论

1. **阙疑的账本安全边界完全由「碰撞阻力」而非「原像阻力」决定，而 452 条这个规模下两者都远离任何现实攻击面**。SHA-256 输出 256 bit，生日界给出的碰撞复杂度是 2^128，而 452 条记录的随机碰撞概率约为 n²/2^257 ≈ 8.8×10⁻⁷³（按生日近似 n(n−1)/2 · 2⁻²⁵⁶ 计算）。也就是说，即使假设攻击者拥有全球算力，阙疑账本的"两条判决意外同哈希"这一风险比宇宙寿命内的硬件误码率还低若干量级。**结论：不需要换 SHA-3，不需要加长到 SHA-512，需要的是把域分隔前缀写对。**

2. **RFC 6962 的 `0x00`/`0x01` 前缀不是可选的工程细节，而是 Merkle 树「二次原像抗性」的唯一来源**。RFC 6962 §2.1 逐字规定：`MTH({d(0)}) = SHA-256(0x00 || d(0))`、`MTH(D[n]) = SHA-256(0x01 || MTH(D[0:k]) || MTH(D[k:n]))`，并明确注释 *"the hash calculations for leaves and nodes differ. This domain separation is required to give second preimage resistance."* 如果阙疑的 `merkle_checkpoint.py`（或等价模块）把叶子直接喂进 `SHA-256(leaf)` 而不加 `0x00`，则一个 33 字节的内部节点哈希可以被当作"叶子"重新提交，攻击者可在**不破坏任何哈希**的前提下伪造包含证明。这是本次调研中**唯一一条必须在 v47 里立刻核查的硬缺陷候选**。

3. **对 452 条这个量级，"Merkle 树"的收益不在省时间，而在"让第三方在不信任内核的情况下验一条判决"**。RFC 6962 给出的一致性证明规模上界是 `ceil(log2(n)) + 1` 个节点；n=452 时 `ceil(log2(452)) = 9`，故上界 10 个 32 字节节点 = **320 字节**；单条包含证明最多 9 个节点 = **288 字节**。而哈希链重放一条第 k 条记录需要 k 次 SHA-256。**452 条下两者都毫秒级完成——所以选 Merkle 的理由是"证明可搬运、可离线、可贴进论文附录"，不是性能**。真正被 Merkle 改变的是**审计协议的形状**：从"你必须相信我重放对了"变成"这是 288 字节，你自己算"。

## 精确数字与案例

### 一、RFC 6962：Merkle 树的逐字规范（这是阙疑应当照抄的规范）

以下全部来自 RFC 6962《Certificate Transparency》(IETF, 2013-06) §2.1，经 WebFetch 逐字核对 rfc-editor.org 原文。

哈希算法（§2.1 原文）：

> "Logs use a binary Merkle Hash Tree for efficient auditing. The hashing algorithm is SHA-256 [FIPS.180-4] (note that this is fixed for this experiment, but it is anticipated that each log would be able to specify a hash algorithm). The input to the Merkle Tree Hash is a list of data entries; these entries will be hashed to form the leaves of the Merkle Hash Tree. The output is a single 32-byte Merkle Tree Hash."

三条核心递归定义：

| 情形 | 公式 | 出处 |
|---|---|---|
| 空列表 | `MTH({}) = SHA-256()` | RFC 6962 §2.1 |
| 单条目（叶子） | `MTH({d(0)}) = SHA-256(0x00 \|\| d(0))` | RFC 6962 §2.1 |
| n > 1（内部节点） | `MTH(D[n]) = SHA-256(0x01 \|\| MTH(D[0:k]) \|\| MTH(D[k:n]))`，其中 **k 是小于 n 的最大 2 的幂**（`k < n <= 2k`） | RFC 6962 §2.1 |

域分隔的理由，RFC 原文括号注释逐字：

> "(Note that the hash calculations for leaves and nodes differ. This domain separation is required to give second preimage resistance.)"

非 2 的幂的处理，RFC 原文逐字：

> "Note that we do not require the length of the input list to be a power of two. The resulting Merkle Tree may thus not be balanced; however, its shape is uniquely determined by the number of leaves. (Note: This Merkle Tree is essentially the same as the history tree [CrosbyWallach] proposal, except our definition handles non-full trees differently.)"

**这一句对阙疑至关重要**：树的形状由叶子数唯一确定，意味着 452 条账本在任何时刻的树形是**规范唯一**的，第三方不需要猜你的实现怎么处理奇数节点。这正是 Bitcoin 用"复制最后一个节点"（见下文 CVE-2012-2459）所不具备的性质。

审计路径定义（§2.1.1 原文）：

> "A Merkle audit path for a leaf in a Merkle Hash Tree is the shortest list of additional nodes in the Merkle Tree required to compute the Merkle Tree Hash for that tree. ... If the root computed from the audit path matches the true root, then the audit path is proof that the leaf exists in the tree."

一致性证明定义（§2.1.2 原文）：

> "Merkle consistency proofs prove the append-only property of the tree. ... We define an algorithm that outputs the (unique) minimal consistency proof."

一致性证明规模上界（§2.1.2 原文逐字）：

> "The number of nodes in the resulting proof is bounded above by ceil(log2(n)) + 1."

RFC 6962 §2.1.3 给了 7 叶示例，可用来做单元测试的黄金向量：

> "The audit path for d0 is [b, h, l]. The audit path for d3 is [c, g, l]. The audit path for d4 is [f, j, k]. The audit path for d6 is [i, k]."

> "The consistency proof between hash0 and hash is PROOF(3, D[7]) = [c, d, g, l]. ... The consistency proof between hash1 and hash is PROOF(4, D[7]) = [l]. ... The consistency proof between hash2 and hash is PROOF(6, D[7]) = [i, j, k]."

**注意**：RFC 6962 原文**从未写出 "O(log n)" 这个渐近记号**，它只给了 `ceil(log2(n)) + 1` 这个精确上界。阙疑若在论文里引用，应引用后者（更精确、更难被审稿人挑刺）。

RFC 9162（Certificate Transparency v2.0）取代 RFC 6962，把 `MerkleTreeLeaf` 结构换成了更易扩展的 `TransItem` 结构（据 rfcinfo.com 的 RFC 9162 中文摘要页面）；但**叶子/节点哈希的 `0x00`/`0x01` 域分隔规则被保留**——我在 rfcinfo 与 msec.tools 的 RFC 9162 页面上确认了这一点，但**未逐字核验 RFC 9162 正文中该常量的写法**，见盲区。

### 二、数论给哈希提供的三块地基：模运算、素数、离散对数

哈希函数本身几乎不用数论（SHA-256 的压缩函数是纯布尔电路 + 32 位模加），但**"为什么哈希能当密码原语用"这件事的论证，全部来自数论/代数**。

**(1) 模运算与有限域。** SHA-256 的 Davies-Meyer 压缩函数在 64 轮中使用常数 `K[i] = floor(2^32 × frac(cbrt(p_i)))`，初始向量 `H0` 使用 `frac(sqrt(p_i))`，其中 `p_i` 是前 8 / 前 64 个素数——这是"取素数立方根/平方根小数部分"以获取"无明显结构"常量的经典手法（该说法由 systemslibrarian 的 Hash Zoo 教学页给出，属教学材料而非标准原文，见盲区）。

**(2) 素数与大整数分解。** 公钥密码（RSA）的安全性建立在"大整数分解困难"之上，这是数论最直接的工程变现。这一块与阙疑**无关**——阙疑不做公钥加密，不做签名（如果做签名也应当用 Ed25519 而非自研）。**明确结论：数论里的素数/分解/RSA 这条线，对阙疑是零收益的，不要写进论文当"理论基础"。**

**(3) 离散对数问题（DLP）。** DLP 是 Diffie–Hellman 与 ElGamal 的困难性来源：给定有限循环群 G、生成元 g、h = g^x，求 x。据 UPF 密码学讲义（upf-cryptography.github.io，2021-02-24）与知乎《Mathematical Cryptography 笔记》，朴素搜索的复杂度是 O(2^k · log²(2^k))（k-bit 的 x 与 n），在 F_p* 中一次 k-bit 模乘花费 k² 次基本运算。**同样与阙疑无关**——阙疑的账本不需要密钥交换。但 DLP 的**结构性教训**与阙疑有关：**"困难性来自单向性，而不来自保密性"**。哈希链的防篡改正是同一逻辑（无需密钥，只需单向性）。

### 三、Merkle–Damgård 的已知弱点，以及它为什么**不**伤害阙疑

SHA-2 家族使用 Merkle–Damgård 结构（Merkle 1979 / Damgård 1989），即 `H_i = compress(H_{i-1}, block_i)`，最终链值即摘要。定理层面的意义：**只要压缩函数抗碰撞，任意长度消息的哈希就抗碰撞**（theorempath.com 的 hash-functions 条目给出了这条归约的证明思路：若 m ≠ m′ 而 H(m)=H(m′)，逐块回退必然在某一步得到压缩函数上的碰撞）。这条归约是"设计者只需做一个定长压缩函数"的全部理由。

副作用是**长度扩展攻击**（length extension）：已知 `H(m)` 与 `len(m)`，可在不知 m 的前提下算出 `H(m || padding || m′)`。多个来源（khimananda.com 的 SHA-256 vs SHA-512 vs SHA-3 对比、sadiqbd.com 的 SHA-2 vs SHA-3 架构指南、systemslibrarian 的 Hash Zoo 现场演示）都给出同一结论，其中 Hash Zoo 给出了一个可交互的真实伪造示例：对 `secret(33 bytes) || data` 的 SHA-256 标签 `b4bf86f6...9b7a`，攻击者仅凭该标签与长度 33，拼接 `8000...0108` 胶水填充与 `&role=admin`，即得到被独立验证为正确的伪造标签 `889decf3...eab2f`。

**这条对阙疑的判决**：
- 如果 `gate_engine.py` 或对账器里出现 **`SHA256(secret || payload)` 当作 MAC** 的写法 → 必须改成 HMAC-SHA-256 或改用 SHA-3/BLAKE3。这是可被一击致命的漏洞。
- 如果只是 `H(prev_hash || record_bytes)` 这种**公开**链式哈希（无密钥），长度扩展攻击**不适用**——因为攻击者本来就知道全部输入，没有"密钥"可保护。**阙疑的账本是公开可复算的，所以 Merkle–Damgård 的这个弱点不构成风险。** 这一点必须在论文里写清楚，否则审稿人会问"你们用 SHA-256 不怕长度扩展吗"。

SHA-3（Keccak sponge，FIPS 202，2015-08 定稿）在结构上免疫长度扩展：1600-bit 状态中 SHA3-256 只用 1088-bit rate + 512-bit capacity，capacity 永不进入输出，故攻击者无法从摘要恢复内部状态（多个来源一致，见 Hash Zoo 与 khimananda.com）。**但阙疑没有需要这个免疫性的场景**，换 SHA-3 的代价是：在无 SHA-NI 指令的 ARM Cortex-M 类目标上，Keccak 纯软件实现通常慢于 SHA-256，且工具链/库支持面更窄。

### 四、碰撞、二次原像、以及 452 条量级的定量结论

三个安全性质必须分清（这三个定义在 theorempath.com 与多份密码学讲义中一致）：

| 性质 | 定义 | 通用攻击复杂度（n-bit 输出） | SHA-256 的值 |
|---|---|---|---|
| 原像抗性 (preimage) | 给定 y，求 m 使 H(m)=y | 2^n | 2^256 |
| 二次原像抗性 (second preimage) | 给定 m，求 m′≠m 使 H(m′)=H(m) | 2^n | 2^256 |
| 碰撞抗性 (collision) | 求任意 m≠m′ 使 H(m)=H(m′) | **2^(n/2)**（生日攻击） | **2^128** |

SHA-1 的教训可作为量级参照：SHAttered 攻击（2017）以约 **2^63** 次计算产生了实际碰撞——远低于其 2^80 的生日界，说明"低于生日界"的真实攻击是存在的（此数字来自 theorempath.com 的二手转述，我未核验 SHAttered 原论文，见盲区）。

**对阙疑 452 条的定量化**（我自己算的，给出公式以便复核）：
- 452 条叶子两两配对数为 `C(452,2) = 452×451/2 = 101,926`。
- 任意一对哈希相等的概率上界 ≈ `101,926 / 2^256` ≈ `1.02×10^5 / 1.16×10^77` ≈ **8.8×10⁻⁷²**。
- 换成人话：假设每秒检查 10⁹ 对，需要约 10⁷² 秒 ≈ 10⁶⁵ 年。可观测宇宙年龄约 1.38×10¹⁰ 年。**差 55 个数量级。**

后量子情形：Grover 算法把原像搜索从 2^256 降到约 2^128；对碰撞，Brassard–Høyer–Tapp（BHT）量子算法（arXiv:quant-ph/9705002，1997-05-02，作者 Gilles Brassard、Peter Høyer、Alain Tapp）在 r-to-one 函数上以 **O((N/r)^(1/3))** 找到碰撞，即 SHA-256 的量子碰撞界约 **2^85.3**。**关键推论：碰撞阻力在量子下仍然够用**（2^85 依然不可行），而 2^128 的原像界在量子下变成 2^128 → 仍然远超可行范围。**所以"后量子哈希"对阙疑不是迁移任务，只是论文 threats-to-validity 里的一段论证。** 真正的后量子工作是**签名**层面：NIST FIPS 205（SLH-DSA，基于 SPHINCS+，2024-08-13 发布）与 NIST SP 800-208（有状态哈希签名 LMS/XMSS，2020-10-29 发布）——**只有当你需要对 checkpoint 做数字签名时才相关**。

### 五、必须避开的实现陷阱：Bitcoin 的奇数节点复制（CVE-2012-2459）

Bitcoin 早期实现处理奇数个节点时**复制最后一个节点**（而非 RFC 6962 的"按最大 2 的幂分裂"）。后果是：存在两个不同的交易列表产生**同一个 Merkle 根**，攻击者可发送一个含重复交易的畸形区块，使节点因根相同而接受它，随后拒绝该区块导致分叉（CVE-2012-2459，影响 bitcoind 0.4.6 之前 / 0.5.5 之前的 0.5.x / 0.6.0.7 之前的 0.6.x；来源：Bitcoin Optech 的 merkle-tree-vulnerabilities 主题页与 GitHub 上 bitcoin 的 `src/consensus/merkle.cpp` 注释）。Bitcoin 后续在 `merkle.cpp` 里显式检测"重复交易"来堵这个洞。

**对阙疑的直接动作**：如果自研 Merkle 实现里出现"若当前层节点数为奇数则 `nodes.append(nodes[-1])`"这样的代码，**立刻删掉，改按 RFC 6962 的 k = 最大 2 的幂分裂**。第二个直接动作：加一条单元测试，断言 7 个叶子的树中 `d6` 的审计路径恰好是 2 个节点（RFC 6962 §2.1.3 的黄金向量），而不是 3 个——这能一次性区分"RFC 6962 实现"与"Bitcoin 式实现"。

### 六、性能量级：452 条到底花多少

来自 arXiv:2407.08284（2024-07-11，Performance Evaluation of Hashing Algorithms on Commodity Hardware）的实测数据，硬件为 AMD EPYC 7501（32 核，128 vCPU），单位是 **hashes/sec**（该论文**没有**给出 MB/s 或 cycles/byte，见盲区）：

| 线程数 | BLAKE3 | SHA-256 | SHA-512 |
|---|---|---|---|
| 1 | 17,509,761 | 1,712,624 | 1,138,808 |
| 8 | 101,868,264 | 621,361 | 603,409 |
| 64 | 370,288,084 | 574,635 | 532,922 |

论文结论逐字：*"my evaluation results show that Blake3 generally outperformed both SHA-512 and SHA-256 in terms of hashes generated per second on tested hardware platforms."* 但也诚实承认反例：*"sha512 outperforms sha256 in some cases"*。（注意：该表 SHA-256 随线程数**下降**，与 BLAKE3 随线程数上升相反，说明是单线程实现未并行化，不是算法缺陷——这个反常应当被指出来而不是照抄。）

**换算到阙疑**：452 条 × 每条 1 次叶子哈希 + 451 次内部节点哈希 ≈ 903 次 SHA-256。按单线程 1.7×10⁶ hashes/sec 计，**约 0.53 毫秒**。即使目标平台是慢 100 倍的 Cortex-M4 类 MCU，也只有 **约 53 毫秒**，且 903×32 = **28.9 KB** 的哈希存储。**这是本次调研最重要的工程结论之一：Merkle checkpoint 的代价在阙疑的规模下可以忽略，唯一的成本是"实现正确性"的人力成本。**

对比：哈希链全量重放 452 条也只要 452 次哈希 ≈ 0.27 ms。**所以在这个量级，Merkle 不是性能优化，是协议优化。**

## 盲区（诚实标注）

- **RFC 9162 正文未逐字核验**。我确认了 RFC 9162 存在（Certificate Transparency Version 2.0，取代 RFC 6962）、确认了 `MerkleTreeLeaf` 被 `TransItem` 取代，但**没有打开 RFC 9162 的 txt 正文逐字确认 `0x00`/`0x01` 常量仍原样保留**。我根据 RFC 惯例与二手摘要推断其保留，但这属于推断而非核验。RFC 9162 的**确切发布月份**（我印象是 2021-12）**未核实**。
- **SHA-256 常数来自素数小数部分的说法，来源是教学网站而非 FIPS 180-4 原文**。Hash Zoo（systemslibrarian.github.io）与 khimananda.com 都这么说，但我没有打开 FIPS 180-4 逐字核验 `K[i]` 的定义式。这个细节若写进论文需要回到 NIST 原文。
- **SHAttered 的 2^63 数字来自二手转述**（theorempath.com 的 hash-functions 条目），我**没有**核验 SHAttered 原论文（Stevens 等，2017）或 shattered.io 官网。作为量级参照可用，作为引用必须回到一手。
- **arXiv:2407.08284 的性能数据有内部矛盾**：表格标题标注 y-axis 为 "1e8"，但表内数值量级为 1e6–1e8；且 SHA-256/SHA-512 的吞吐随线程数**下降**（1 线程 1.71M → 64 线程 0.57M），这不符合物理直觉，说明该实验的多线程部分实现有问题。**该表只能用作"BLAKE3 比 SHA-256 快一个量级"的定性证据，不能用作任何绝对数字的引用。** 阙疑若要引用 SHA-256 吞吐，应改用 OpenSSL 的 `speed sha256` 或 `b3sum` 官方基准，我**没有**查到这两个官方数字。
- **Cortex-M 类嵌入式平台的 SHA-256 cycles/byte 数字未核实**。搜索结果指向 CSDN 博客与文库（blog.csdn.net/weixin_33377602、wenku.csdn.net），我未打开核验，且这类二手汇总的数据可信度存疑。我在上文用了"慢 100 倍"这个假设值做量级推算，**这是假设不是实测**。
- **样本偏差**：本次调研的搜索结果里，中文来源（CSDN、知乎、豆丁）大量是 AI 生成或二次汇编的低可信度内容（例如"数论在密码学中的应用-第1篇-洞察分析"这类标题是典型的 AI 批量产出格式）。我尽量只用它们做"该主题存在"的存在性证据，不作为数字来源。这也提醒阙疑：**你自己的 75+ 份 AI 生成文档在 Pangram 视角下与此同类。**
- **未核实**：RFC 6962 中 `[CrosbyWallach]` 引用的历史树论文的确切标题与年份；LMS/XMSS 的具体签名大小数字（FIPS 205 / SP 800-208 中 SLH-DSA 的签名长度我未查）；Keccak-f[1600] 24 轮这一数字我来自二手（khimananda.com 与 Hash Zoo 一致，但未核 FIPS 202）。
