# 方向 102：刷榜攻击方法——当排行榜分数替代真实性

> 研究对象：leaderboard gaming、Goodhart's law、metric manipulation、cherry-picking、multiple comparisons、hidden test overfitting、submission limit。
>
> 写作边界：本文只讨论评测系统的防御、审计与授权红队建模，不把刷榜写成可直接用于欺骗第三方的操作手册。所有攻击模式都服务于一个问题：阙疑怎样证明自己优化的是 C++ 知识验证的真实性，而不是某个容易被操纵的数字。
>
> 共享上下文锚点：阙疑当前有 37 张实卡、67 条规则、9 个保护器、452 条账本记录和约 3826 行内核；盲 holdout 为 30 条、其中“真错”17 条、检出率 66.7%；外部 corpus 为 40 条，内部锚点记作检出率 43.8%，但方向 31 已指出按 A/B/C 分层的 13/24、1/8、0/8 合计应为 14/40 = 35.0%，43.8% 更像 14/32 的口径，原因尚待账本核实；变异结果为 core 97.3%、all 81.5%；反事实结果为 P=R=F1=0，且存在不自洽。本文不把这些数字自动解释成系统能力，而把它们当作评测协议需要被审计的观测。

## 一、刷榜不是“作弊技巧清单”，而是评价目标被反向优化

刷榜攻击（leaderboard gaming）首先不是某个具体脚本，而是一种激励结构：系统公开一个可观察分数，参与者可以反复提交候选方案，平台返回分数或排名，于是参与者逐步把方案适配到“榜单的反馈函数”。如果反馈函数与真实目标完全一致，这种优化可能有益；但现实中指标往往只是真实性的代理变量。一旦排名、论文标题、宣传口径或项目决策只奖励一个代理变量，参与者就会自然地把资源投入到“提升代理变量”上，哪怕这意味着忽略未测量的错误、缩窄样本分布、隐藏失败案例或破坏可复现性。

这正是 Goodhart's law 的核心。剑桥大学页面记录了 Goodhart 自己在 *Monetary Theory and Practice* 中的表述：任何被施加控制压力的统计规律，都倾向于崩溃；Marilyn Strathern 的更简洁表述是：“When a measure becomes a target, it ceases to be a good measure。”在阙疑语境中，“目标”可以是 66.7% 的检出率、43.8% 的 corpus 数字、97.3% 的 core 变异率，也可以是“在排行榜上高于上一版本”。一旦工程工作围绕这些数字进行，而不是围绕“对未见过的 C++ 断言给出正确、可解释、可追溯的判决”进行，系统就可能出现指标上升、真实性下降的现实漂移。

需要区分三类行为。第一类是正常优化：修复真实规则漏洞、扩大覆盖面、减少误报，并在独立数据上同步改善。第二类是脆弱优化：反复查看反馈，把测试分布、规则边界和评分盲点记熟，最后只在相似样本上表现好。第三类是欺骗性操纵：选择性披露最好结果、删除失败提交、利用答案泄露、针对评测器写特殊分支、改变分母或统计口径。前两类可能没有主观恶意，却同样会让榜单失去外推意义；第三类则直接损害评测公正。防御设计不能只问“有没有人恶意作弊”，还要问“一个理性参与者在现有激励下，是否会被系统性地推向脆弱优化”。

阙疑的首要防线是把“真实性”拆成不可互相替代的证据维度：盲态未见样本上的检出能力、外部 corpus 的分层结果、误报与漏报、不同 C++ 主题和难度的覆盖、规则触发的证据链、反事实测试、变异测试、独立对账器的一致性、运行环境稳定性以及所有失败案例。任何一个单一分数都只能是摘要，不能成为唯一的验收条件。特别是 66.7% 不能覆盖 43.8% 的口径疑点，97.3% 不能覆盖 sanitizer 缺失或变异算子偏差，P=R=F1=0 也不能直接证明系统无用；它们分别回答不同问题，必须在同一张审计表中并列，而不能挑一个最漂亮的数字当 headline。

## 二、刷榜攻击的七个机制：指标操纵、挑选、比较、泄露与自适应过拟合

第一种机制是 metric manipulation，即直接改变指标的分子、分母、阈值或汇总方式。对阙疑而言，最危险的不是把 66.7% 改成 70%，而是悄悄改变“检出”的定义：只把 block 算作阳性，还是把 warn 也算作阳性；把 draft 放入分母还是排除；把三层 A/B/C 按样本数微平均，还是按层等权宏平均；把反事实的零注入结果当成失败，还是承认指标在 prevalence=0 时结构性塌缩。方向 31 的核算说明，按 13/24、1/8、0/8 汇总是 14/40=35.0%，而 43.8% 与 14/32 接近。这里不能凭“哪个数字更合理”修正，必须回到 40 条逐项账本、item_id、stratum、detected 和 rule_id；否则看似只是算术错误，实质上是评测对象发生了漂移。

第二种机制是 cherry-picking，即只挑选有利的样本、版本、随机种子、主题层或结果呈现。典型表现包括：只展示最容易的 C++ 语法题；只报告规则命中最多的子集；只放最好一次运行；把未通过的卡放入“草稿”而不计入总体；把 C 层 0/8 写成“该层没有问题”；把变异 core 97.3% 放在标题，却不同时说明 all=81.5%、工具链缺失和分母构成。Cherry-picking 的危险在于每个局部选择都可以有一个听起来合理的解释，但所有选择叠加后，读者看到的已不是系统在目标分布上的表现，而是作者从许多可见结果中筛出的展示子集。

第三种机制是 multiple comparisons。若阙疑有 67 条规则、多个数据集、多个层级、多个阈值、多个变异算子和多个随机种子，就存在大量潜在的比较路径。方向 36 已给出直观数字：在每次检验 α=0.05 时，67 个独立检验至少出现一个假阳性的概率为 1-(1-0.05)^67，约 96.78%；10 个假设也可能达到约 40%。因此“我们试了很多规则，最后有三条显著”不具有自动说服力。若先看结果再决定检验族、只对显著的三条做校正，或者在 Bonferroni、Holm、BH 之间选择最能产生 headline 的方法，就是把探索性搜索伪装成事前确认性结论。Circulation Research 的统计指南要求报告实际检验数量、纳入校正的假设数量、校正方法和效应量及置信区间；这比只写一个 P 值更能阻止刷榜式叙事。

第四种机制是 hidden-test overfitting。参与者并不需要看到完整测试集，只要每次提交后能得到足够精细的分数、排名、分层分数或错误提示，就可以把隐藏集当作一个有噪声的查询接口，逐步拟合评测器。CapBencher 的摘要明确指出，公开答案会造成污染和评测操纵；即便测试集保持私有，持续的反馈回路仍允许 test-set overfitting。Schmidt 的 *Testing for Overfitting* 也提醒，训练数据上的经验风险与真实分布风险不能简单等同，评估过程本身需要考虑过拟合和分布漂移。对阙疑而言，若每次提交都返回“命中 17/30”“A 层 54.2%”甚至逐卡反馈，攻击者可以不必理解 C++ 语义，只需把规则改造成对反馈函数的拟合器。

第五种机制是 submission-limit gaming 与 best-of-N。限制提交次数本身有价值，因为它降低了查询预算；但如果平台允许撤回失败提交、只保留最好分数，或者组织可以私下测试很多版本后只公开一个，那么“最终分数”会带有选择偏差。NeurIPS 2025 的 *The Leaderboard Illusion* 对 Chatbot Arena 的分析给出了极端案例：一个提供方在公开一个模型前测试了 27 个私有变体，再选择性披露最好的结果；论文认为这种做法会让榜单分数偏向能够进行大量私下测试和结果选择的提供方，并造成对 Arena 特定动态的过拟合。这个案例说明，提交次数不只是运营参数，也是统计实验设计的一部分：必须记录所有尝试、失败、撤回和最终选择，不能只把最好的一次当作独立证据。

第六种机制是 benchmark contamination 与答案泄露。公开的知识卡、标准答案、规则解释和历史失败样例可能被模型或开发者直接记忆；此时高分反映的是复现训练材料，不是面对新断言的推理能力。Kaggle 官方文档将 Public Leaderboard 和 Private Leaderboard 分开，并明确把隐藏私人榜与“防止过拟合”联系起来；MLPerf 规则则强调结果必须符合规则文字和精神、结果必须可复现、不得检测 benchmark 或编码输入数据集信息。对阙疑而言，公开部分可以用于开发，但真正决定论文结论的 holdout 必须保持不可回盲，并且不能通过错误详情、答案摘要、排序信息和过细的 API 返回值间接泄露。

第七种机制是“系统和指标一起被优化”。如果规则引擎知道自己在跑变异测试，就可能针对变异生成器；如果它能识别某个公开 benchmark 的卡片格式，就可能只对 benchmark 输入启用特判；如果评价只奖励命中率，系统就可能扩大 block 范围来提高检出，却牺牲精确率和解释质量。MLPerf 的规则明确禁止 benchmark detection、缓存查询或响应、合并相同查询以及利用输入数据集内容进行编码优化。阙疑应把这些原则迁移为内部测试：同一规则必须在公开开发集、隐藏 holdout、外部 corpus 和扰动格式上使用同一实现；不能为“评测模式”单独保留一套逻辑。

## 三、为什么阙疑当前数字已经显示出刷榜风险，而不是证明成功

66.7% 的盲 holdout 检出率首先是 17/30 这一组有限计数的描述，不是一个可以脱离分母、标注过程和区间的能力常数。30 条样本中，单条判决就能改变约 3.3 个百分点；“真错 17”如果由单一作者定义，还存在 ground truth 偏差；如果某些卡由同一规则模板生成，样本之间还可能相关。正确的报告应至少带上 `n=30`、真错数 17、检出数、漏检数、误报数、按主题和难度分层的结果、精确置信区间以及标注协议。66.7% 可以作为当前观察值，但不能写成“阙疑对 C++ 知识错误的真实检出能力为 66.7%”。

43.8% 的问题更直接地暴露了口径操纵的可能性，即便它最后被证明只是无意的分母遗漏。共享资料已经指出：A 层 13/24=54.2%，B 层 1/8=12.5%，C 层 0/8=0%，按全部 40 条合计是 14/40=35.0%；若去掉 C 层则 14/32=43.75%，四舍五入为 43.8%。这不是“差一点”的四舍五入，而是统计对象发生变化。不能用更高的 43.8% 作为系统 headline，再在附录里把 C 层单独列出；也不能因为 35.0% 更低就反向认定账本一定正确。应以逐条可复算账本为准，修正所有派生表，保留更正记录，并同时公布微平均、宏平均和分层区间，让读者能够自行重新汇总。

变异 core 97.3% 与 all 81.5% 是另一个典型的 metric manipulation 预警。两个数字的差距为 15.8 个百分点，说明“core”与“all”不是同一个总体；若 core 是规则核心子集，97.3% 只能说明在该子集、该变异算子和该运行环境下的通过比例。它不能替代真实错误检出率，更不能掩盖 sanitizer 缺失、变异样本是否独立、算子是否覆盖语义错误以及“变异存活”究竟代表漏检还是编译/运行失败。若评测器对某一变异器特别熟悉，变异分数还会成为可以被针对的游戏目标。因此阙疑应把变异测试定位为压力测试证据，报告 core/all 的完整分母、算子分布、失败原因和环境状态，而不是把 97.3% 当作“真实性 97.3%”。

反事实 P=R=F1=0 则提醒我们：指标可以因定义而塌缩。若反事实操作没有注入任何已知错误，真实阳性 prevalence 为零，精确率、召回率和 F1 不能按普通二分类结果解释。把这个结果直接写成“系统在反事实下完全失效”，会把度量缺陷误当成能力缺陷；但把它静默删除，同样是选择性报告。正确做法是显式标为“零注入下指标不可解释/结构性为零”，补充已知数量、已知类型的合成错误，分别测量注入错误的检出与误报，再把零注入结果作为 specificity/稳健性的一部分报告。

这些不自洽并不等于阙疑已经刷榜，也不能据此指控任何人恶意操纵。它们说明的是：当前协议允许一个善于挑选分母、层级、变异子集和最好运行的作者，得到比真实泛化能力更漂亮的故事。最重要的研究问题不是“如何把榜单分数做高”，而是“如果有人试图把榜单分数做高，哪些独立证据会让这种做法无法伪装成真实改进”。这就是从攻击视角转向防御视角的关键。

## 四、把防刷榜变成评测协议：预注册、隐藏评测、提交预算与完整分布报告

第一道防线是预注册（preregistration）与预分析计划（pre-analysis plan, PAP）。在任何新规则、新数据、新阈值、新聚合方式开始计算前，冻结以下字段：主问题、主数据集、holdout 身份、样本分层、阳性定义、主要指标、分母、置信区间方法、变异测试方案、随机种子、提交预算、停止规则、异常处理、缺失数据处理、主比较和多重比较校正。预注册不是说注册后永远不能改；可以有探索性分析和协议修订，但必须保留时间戳、版本号、变更原因，并把“预先确认”与“事后探索”分开命名。Stanford SIEPR 对 2018—2021 年 15 本经济学期刊 RCT、共 15,992 个检验统计量的研究摘要给出一个重要的限定结论：单纯预注册未必降低所有 p-hacking，但有完整 PAP 的预注册研究显著更少 p-hacked。对阙疑的启示是，不能只创建一个空的 `registered=true` 文件，而要注册具体分析路径。

第二道防线是隐藏评测与双层榜单。公开开发集只能返回低分辨率反馈，例如总分区间、有限频率的分层汇总或延迟发布的版本级报告；不能返回逐卡标签、逐规则错误、精确排名波动和可以反推隐藏答案的反馈。内部应至少划分开发集、锁定 holdout、外部 corpus 和最终审计集；锁定 holdout 在分析完成前不回盲，最终审计集由独立人员或未来版本生成。Kaggle 的公共榜/私人榜拆分是工程上易懂的先例：公共榜用于反馈，私人榜在截止前隐藏并决定最终排名。CapBencher 进一步提醒，单纯把答案藏在服务器后面仍可能被反复查询过拟合，所以还需要提交预算、反馈降精度、查询审计和独立新集。

第三道防线是 submission limit，但不能只写一个“每天 5 次”。应记录 `submission_id`、提交时间、代码版本、配置哈希、数据版本、随机种子、返回的所有反馈、是否撤回、撤回原因和最终纳入哪一张表。限制应作用于一个明确的统计单元：例如每个候选版本对锁定评测集最多一次正式查询；开发阶段可以有更多本地运行，但不得访问锁定标签。若允许撤回，应把撤回也作为结果记录，不能让失败尝试从历史中消失。若组织方有内部私测权，也必须公布私测次数、候选变体数量和选择规则；否则 best-of-N 会使一个看似单一的榜单分数携带未知的选择偏差。正式结论应使用预注册的候选版本或固定选择规则，而不是“所有版本中最好的一次”。

第四道防线是完整分布报告，而不是单点榜单。每次报告至少包括：总样本数 n；每层样本数和检出数；均值、中央値、四分位数或分位数；按主题、难度、错误类型和规则族的完整表；每一层的 prevalence；TP、FP、FN、TN；精确置信区间；随机种子或重复运行分布；失败运行数；版本和环境；变异 core/all；反事实零注入与非零注入；以及所有预先声明但结果不理想的分析。Circulation Research 指南要求每项检验报告效应量和 SE/CI、确切样本量、实际检验数量与多重校正方法，这一原则可以直接迁移到阙疑。对于 66.7%、35.0%/43.8%、97.3%/81.5%，应把它们放在同一份机器可读结果中，禁止只输出一个“最佳指标”。

第五道防线是把多重比较从事后补丁改为协议字段。阙疑可以把 67 条规则定义为一个预先声明的探索性检验族；若只做描述性率，就不假装拥有显著性结论；若确实检验规则差异，则固定 m、原始 P 值、校正方法和 Q/α，并同时给出效应量与区间。Holm 适合在任意依赖下控制 FWER，BH 适合事先声明的探索性 FDR，但不能先看哪种方法更“出结果”再选择。所有被尝试但未入正文的规则和分析也要放在附录或结果清单中。这样做不是为了让报告变长，而是为了让读者知道榜单分数是否来自一个被隐藏的搜索过程。

第六道防线是隐藏测试的抗过拟合设计。可以采用语义等价但表面不同的 C++ 断言、不同命名风格、不同编译器版本、不同错误位置、组合错误、反事实扰动和由独立作者新写的卡片；对规则系统则使用格式变换、同义改写、题目顺序随机化和未公开主题。CapBencher 的思路是通过多个逻辑上正确的答案和受控随机性降低“背答案”能够达到的理论上限，并以超过上限作为泄露/游戏信号；阙疑不必照搬其复杂实现，但可以借鉴“评测器内置报警器”：例如预先构造多个等价解释、隐藏一部分证据链、监测同一提交在语义等价改写上的异常大幅波动。所有抗过拟合措施都必须保证评分语义仍可解释，不能用随机噪声掩盖标注错误。

第七道防线是独立对账与审计日志。内核 `gate_engine.py`、独立对账器、规则快照、卡片来源、评测集哈希和结果表必须分离；对账器不能只复制内核同一段代码。每次正式评测生成不可变的 `evaluation_id`，记录代码提交哈希、配置、规则版本、输入清单、环境、输出摘要和审计时间；所有失败、重跑、撤回和更正追加写入 452 条账本式记录，不允许覆盖。若公开榜只显示一个分数，审计者仍应能够在权限范围内验证完整分布和所有提交历史。这样才是“可复算”而不是“同一套错误逻辑复算出同一个漂亮数字”。

## 五、对阙疑的三条具体行动、验收标准与诚实盲区

**行动一：在锁定数据前完成评测预注册与分母冻结。** 在 `_arch_v47/` 新增的评测协议中固定 holdout 30、外部 corpus 40、A/B/C 分层定义、阳性判定、`core/all` 变异分母、反事实注入方案、主指标、CI 方法、67 条规则的检验族、submission limit 和撤回规则。对 43.8% 做逐条账本审计：列出 40 个 `item_id / stratum / ground_truth / detected / rule_id / timestamp / source_hash`，证明究竟是 14/40、14/32 还是其他分母。验收标准是：任何总率都能由明细表一键复算；修改协议后必须留下版本差异；正文不得使用未能与明细表对账的 headline 数字。

**行动二：建立隐藏评测、提交预算和 best-of-N 防护。** 公开开发集只返回预先规定的聚合反馈；锁定 holdout 和最终审计集由独立人员保管，接口不返回逐卡标签，不允许通过撤回删除历史。每个正式版本绑定代码哈希、规则哈希、数据哈希和随机种子；每次查询进入 append-only 日志；榜单同时展示当前版本和全部尝试的审计摘要，而不是只展示最好分数。至少做一次授权红队：模拟参与者拥有 20 次低分辨率反馈，比较其在开发集、锁定 holdout、外部 corpus 和语义等价改写集上的差距。验收标准是：任何只对反馈函数过拟合的版本，在隐藏集或改写集上会显著暴露；正式报告能显示尝试次数、撤回次数和选择规则。

**行动三：把完整分布、独立复算和不自洽检查接入 CI。** 结果表必须同时输出 `n/k/rate/CI/prevalence/TP/FP/FN/TN/seed/environment`，并分别报告 66.7%、corpus 的真实汇总、变异 core 97.3%/all 81.5% 和反事实 P=R=F1=0 的可解释性状态。CI 中加入整数约束、可加性约束、分层总数约束、`pooled_rate == sum(k)/sum(n)`、规则版本与结果版本一致性、零 prevalence 时禁止把 P/R/F1 解释为普通性能、以及 sanitizer 缺失时禁止发布变异 headline。独立对账器必须在不导入内核判决函数的前提下复算，差异进入审计账本。验收标准是：任何分母遗漏、偷偷删除失败提交、改变汇总口径或环境缺失都在发布前失败，而不是等审稿人发现。

**判断原则：不要用一个更漂亮的数替代真实改进。** 如果修复了规则后 66.7% 上升，但外部 corpus、语义改写集、误报率和隐藏审计集没有同步改善，就只能称为“开发集改进”，不能称为真实性提升；如果 97.3% 变成 98.5%，但 all 仍低、sanitizer 仍缺失，也不能称为鲁棒性提升；如果 43.8% 被保留下来，必须明确它对应哪一个分母，不能让高数字借由标题获得超出证据的含义。阙疑要追求的是跨分布、跨口径、跨版本的一致改善，以及失败结果能够被完整看见。

**诚实盲区。** 第一，现有材料只能证明 43.8% 与 14/32 在算术上吻合，不能证明项目历史上确实漏掉 C 层，必须查 452 条账本和原始 corpus。第二，66.7% 的“真错 17”标注者一致性、主题构成和独立复核尚未给出，因此不能把它当成无偏真值。第三，core 97.3%/all 81.5% 的变异差距是否由 sanitizer 缺失、算子分布或规则覆盖造成，尚无前后对照实验。第四，submission limit 能降低查询预算，但不能单独消除私下测试、团队协作、数据泄露或训练污染；隐藏测试也不能替代正确标注。第五，预注册不能阻止所有探索性分析，完整 PAP 的价值在于标记哪些分析是事前确认、哪些是事后发现。第六，来源中关于 2025/2026 年榜单研究、CapBencher 和部分平台规则的版本会变化，正式投稿前应保存 PDF、版本号、访问日期和本地校验哈希。
