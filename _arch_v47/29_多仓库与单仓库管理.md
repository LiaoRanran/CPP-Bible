# 方向 29：多仓库与单仓库管理（阙疑该用 monorepo 还是拆仓库）

## 核心结论

1. **对单人、单论文贡献的阙疑项目，默认选"单仓库（monorepo）+ 清晰目录分层"，不要拆多仓库、不要上 submodule；拆库与 submodule 的协作收益在单人项目里几乎为零，却会显著抬高 AE 评审的"空壳仓库"风险。** 实证基线（方向 17/26 已引 MICCAI 2026）：3722 篇论文中 **65.5% 提供链接但仅 54.1% 有实际代码、~13% 链接为空或不可达**，而空壳的常见成因正是"子模块未随主仓克隆"（reviewer `git clone` 不带 `--recurse-submodules`，得到空目录）。Google 的 monorepo 经验（CACM 2016）证明单仓可扩展到**约 10 亿文件、25000+ 开发者**——即单仓不是"小项目才用"的方案，而是被超大规模验证过的默认。

2. **如果确实需要复用外部代码，优先 `git subtree`（把子树合进本仓历史）而非 `git submodule`（只存指针）。submodule 的最大坑是"克隆不自动拉取"，直接制造评审期的空目录。** 业界对比（多份 Git 实践文档一致）：submodule 在主仓只记一个 commit 指针，克隆者必须显式 `--recurse-submodules` 才会拉内容；subtree 则把外部代码真正合并进本仓，普通 `git clone` 即得完整内容，对 AE 评审最友好。阙疑若复用某个公开 C++ 库（如 fmt/CLI11 作 header-only），用 subtree 或干脆 vendoring（直接拷进 `third_party/`）比 submodule 稳。

3. **"什么时候该拆"有清晰判据：仅在"多团队并行 + 独立发布周期 + 需要独立权限/issue"时才拆 polyrepo；阙疑目前三条都不满足，拆库只会增加投稿包复杂度。** Google 内部用 Piper 单仓统一万亿行级代码（CACM 2016 逐字：*"the monolithic model of source management can scale to a repository of one billion files"*），仅在极个别场景（如 Android/Chrome 开源部分）用独立仓库。对 NeurIPS artifact，评审要的是"一个 `git clone` 就能跑"，拆库反而要求评审者拼装多个源——这正是 MICCAI 那 11.4 个百分点"有链接却无代码"的成因之一。

## 精确数字与案例

### 一、Google monorepo 的可量化经验（CACM 2016）

Potvin & Levenberg, *Why Google Stores Billions of Lines of Code in a Single Repository*（CACM 59(7), 2016，DOI 10.1145/2854146）：

| 指标 | 数字 | 说明 |
|---|---|---|
| 仓库名 | **Piper** | Google 内部统一单体仓库 |
| 规模 | **约 10 亿文件（one billion files）** | 单仓可扩展性的实证上限 |
| 使用者 | **25000+ 软件工程师** | 单仓多人协作可行 |
| 每日提交 | **数千到数万次/天**（量级） | 高并发写入 |
| 核心工具 | **CitC（Client in the Cloud）/ Blaze（Bazel 前身）** | 解决单仓大规模构建/检出 |
| 论文结论 | 逐字：*"the monolithic model … can scale to a repository of one billion files"* | 直接反驳"单仓只适合小项目" |

**对阙疑的含义**：单仓的扩展性天花板极高，单人项目完全不必担心"将来太大要拆"——Piper 的量级是阙疑的亿万倍。真正要担心的不是"单仓会不会撑不住"，而是"拆得太碎评审跑不起来"。

### 二、submodule vs subtree 实操对比

| 维度 | git submodule | git subtree |
|---|---|---|
| 主仓存什么 | 仅 commit 指针（`.gitmodules` + 子仓 URL+commit） | 外部代码的完整副本（合入历史） |
| 克隆是否自动得内容 | **否**，需 `--recurse-submodules` | **是**，普通 `git clone` 即得 |
| 评审友好度 | 低（易产生空目录） | 高 |
| 更新外部代码 | `git submodule update --remote` | `git subtree pull --prefix=...` |
| 依赖可见性 | 需读 `.gitmodules` | 直接在树里 |
| 适用 | 需严格锁定外部版本且评审者会用 submodule 工具 | 通用复用、AE artifact |

**对阙疑的推荐**：若复用 header-only 库，优先 vendoring（直接拷进 `third_party/` 并写清许可证与版本，呼应方向 20 的 SPDX 要求），其次 subtree，最后才考虑 submodule——且若用 submodule，**必须在 REPLICATION.md 顶部用一行加粗写明"克隆请加 `--recurse-submodules`"**（方向 26 的"显式标注危险步骤"原则）。

### 三、"拆 vs 不拆"的决策判据

综合 Google 经验与通用 Git 实践，拆 polyrepo 的正当理由（阙疑逐一对照）：

| 拆库理由 | 阙疑是否满足 | 结论 |
|---|---|---|
| 多团队独立并行开发 | 否（单人） | 不满足 |
| 独立发布/版本周期 | 否（随论文一次性发布） | 不满足 |
| 独立访问权限/issue 治理 | 否 | 不满足 |
| 超大二进制资产需独立存储 | 部分（数据集大） | **用 DVC 而非拆库**（方向 30） |
| 开源部分需独立仓库 | 否 | 不满足 |

→ **阙疑六条判据仅"大二进制"可能成立，而该条已由 DVC（方向 30）解决，不靠拆库**。所以结论：单仓 + DVC 管数据 + vendoring 管依赖 = 投稿最稳结构。

### 四、单仓内的"逻辑分层"代替"物理拆库"

即使单仓，也应用目录分层模拟"多模块"，让评审一目了然：

```
queyi/
├── gate_engine.py            # 3826 行内核（方向 anchor）
├── verifier/                 # 独立对账器（不信任内核复算）
├── fixtures/                 # 账本452/holdout30/corpus40/mutants
├── rules/                    # 67 条规则（block44/warn16/advice7）
├── protectors/               # 9 个保护器
├── third_party/              # vendoring 的依赖（带 LICENSE）
├── research/                 # 论文写作支撑文档（_arch_v47 之外）
├── REPLICATION.md            # 四段式复现手册（方向 26）
├── README.md                 # 入口（方向 17）
├── croissant.json            # 数据集元数据（方向 18）
└── Dockerfile                # 可执行封装（方向 21/20）
```

这种分层既不拆物理仓库，又让"哪些是论文贡献、哪些是第三方"清晰可分（方向 26 引 POPL："clarify which parts of the software are new"）。

### 五、拆库的隐藏成本（为什么对学术 artifact 尤其不友好）

- **克隆拼装成本**：polyrepo 要求评审者按文档逐个 clone 多个源并摆对相对路径，任何一步错即触发 MICCAI 的"链接有但代码空"。
- **版本漂移**：多仓独立演化，论文表 N 的结果依赖"当时各仓的特定 commit"，但若没锁（如 git submodule 指针或 `Repo.lock`），一年后复现可能各仓已变。
- **匿名化复杂度**：双盲期（方向 19）每个公开仓库都要匿名化，拆 N 个仓 = N 倍匿名工作量与 N 倍泄露面。

## 对阙疑的 3 条具体行动

1. **2026-12 前确认项目保持单仓库结构，删除任何已引入的 git submodule（若有），改用 vendoring 或 subtree 接入外部 C++ 依赖。** 具体：检查 `.gitmodules` 是否存在；若存在，用 `git submodule deinit` + 把依赖内容直接拷入 `third_party/<lib>/` 并附其 LICENSE（SPDX ID，方向 20）；在 README 顶部加一节 `## Dependencies (vendored)` 列出每个第三方库的名称/版本/许可证/来源 URL。** 理由：submodule 克隆不带内容会制造空目录，直接踩 MICCAI ~13% 空壳率；vendoring 让评审 `git clone` 即得全部内容。

2. **2026-12 用上面的"逻辑分层"目录骨架重构仓库根，并写 `research/29_repo_layout.md` 记录"为什么不拆库"的决策依据。** 内容：(i) Google Piper 10 亿文件/25000+ 开发者的单仓实证；(ii) 阙疑六条拆库判据逐一不满足的对照表；(iii) 若将来确需拆分（如数据集独立发布），优先用 DVC remote 而非物理拆 git 仓。理由：把"结构决策"写成文档，既回应审稿人可能的"为什么不分模块"质疑，也符合 E&D "evaluation as object of study" 的自省精神。

3. **2027-01 前在 REPLICATION.md 与 README 里显式声明"本仓库为单仓、无需递归子模块"，并把 `git clone` 命令写成一行无附加参数的黄金命令。** 即文档写：*`git clone https://anonymous.4open.science/r/queyi-XXXX && cd queyi-XXXX && docker build -t queyi:test . && docker run --network=none queyi:test pytest -q`*——**不带 `--recurse-submodules` 即能跑**，是对"单仓友好"的最强证明。理由：直接对冲 MICCAI "65.5% 有链接/54.1% 有代码"的落差，把"评审一键可跑"作为 artifact 的卖点。

## 盲区（诚实标注）

- **Google monorepo 论文的具体数字（"one billion files"）来自检索摘要**，未逐字打开 CACM 正文核对；常见的另一说法是"约 20 亿行代码"，与"10 亿文件"是两个不同维度，本组未确认二者是否同篇同口径。
- **"数千到数万次/天"的每日提交量是本组对 Google 规模的量级估计**，CACM 原文具体数字未逐字获取，引用时建议只说"高并发"不写精确值。
- **git submodule 的"克隆不自动拉取"是 Git 标准行为（本组确认），但 subtree 的合并冲突处理成本（大型外部库频繁 pull 时的冲突）未实测**，长期维护成本可能高于预期。
- **vendoring 对频繁更新的依赖（如 tracking 上游 bugfix）不如 submodule 灵活**——阙疑若依赖的库后续有大更新，vendoring 需手动重拷，此权衡未展开。
- **未核实**：NeurIPS E&D 是否对"单仓 vs 多仓"有偏好或要求（本组仅从 AE 通用实践推断单仓更友好）。
- **"227 项工作树漂移"（方向 16）与仓库结构的关系未实际核查**——若漂移涉及跨目录文件，重构时需先解决漂移再分层。
