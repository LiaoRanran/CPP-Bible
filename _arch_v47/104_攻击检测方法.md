# 方向104：攻击检测方法（Intrusion / Anomaly Detection）

## 一、问题边界：攻击检测不是“猜攻击者”，而是把异常证据变成可复核判决

攻击检测方法首先要区分三个容易混淆的对象：**入侵检测（intrusion detection）**关注是否出现了违反安全目标、越权或恶意行为；**异常检测（anomaly detection）**关注观测序列是否偏离正常分布、正常流程或正常行为基线；**日志检测（log-based detection）**关注如何从事件记录中重建上下文、识别模式并支持后续调查。三者有交集但不等价：一个异常可能只是版本发布、批量导入或维护窗口造成的正常变化；一个真正的攻击也可能伪装成低频但合法的操作，因此不能把“模型分数高”直接当成“攻击成立”。NIST SP 800-94 将 IDPS 的工程对象分为网络型、无线型、网络行为分析软件和主机型，并指出 SIEM 等互补技术也能发现入侵；这说明检测系统应覆盖多个遥测层，而不是把所有希望压在一个分类器上（来源[1]）。NIST 对 behavioral anomaly detection 的定义同样是“提供多方面方法来检测网络安全攻击”，强调的是多源、多维度，而非单一阈值（来源[2]）。CISA 的日志建议把“设置日志、定期监控、建立政策和流程”作为连续闭环，要求记录谁在何时从哪里访问了什么，并为失败登录、权限提升等高风险事件设置告警（来源[3]）。

对阙疑而言，检测对象不是网络数据包，而是 C++ 知识验证系统中的**判决流程与证据流**：知识卡输入、规则命中、保护器状态、编译/运行验证、四态判决、账本追加、checkpoint 发布以及独立对账器复算都应产生结构化事件。当前项目锚点是 37 张实卡、67 条规则、9 个保护器、452 条判决账本和约 3826 行内核；上下文还记录 holdout 30 条真错17、检出率66.7%，corpus 40 的43.8%口径存在算术不自洽，反事实 P=R=F1=0。这里的攻击检测应回答至少四个防御性问题：第一，是否有输入或规则在异常地改变判决分布；第二，是否有日志缺失、乱序、重复、回写或分视图；第三，某条规则或保护器是否长期不触发、恒触发或与其应保护的主判决冲突；第四，检测器自己的误报、漏报和告警积压是否已经使响应链失效。需要明确：本文只讨论检测、审计、复算和评价，不提供绕过检测、投放恶意载荷、横向移动或未授权入侵的操作步骤。攻击检测的输出也不应只有“攻击/非攻击”二元标签，而应至少包含事件时间、主体、对象、证据引用、触发方法、置信度、风险等级、是否需要人工复核和对应账本 entry_id；在证据不足时保留 Unverified 或 Error，避免将统计异常过度解释为事实。

## 二、检测信号与方法组合：规则、统计、变点和机器学习各自负责不同的盲区

第一层是**确定性规则检测**。它最适合检查明确的不变量和高置信事件，例如 `prev_hash` 不等于上一条 `entry_hash`、entry_index 回退、checkpoint 的 tree_size 与账本条数不符、同一 entry_id 出现互相冲突的内容、盲态答案在评测前被读取、保护器配置在一次运行中突然减少，以及规则版本与账本记录的版本不一致。当前67条规则可作为检测骨架：44条 block 代表不可继续的结构性失败，16条 warn 代表需升级人工复核的可疑状态，7条 advice 代表低风险改进建议；但不能把“规则数量多”当成覆盖率。每条规则必须有唯一 rule_id、版本、输入字段、严重性、触发原因、已知盲区和测试夹具。规则检测的优点是可解释、延迟低、容易回归；缺点是只能发现已编码的模式，遇到新型行为、跨事件组合或规则本身被静默修改时容易漏报。MITRE ATT&CK 的数据源页面曾把 Application Log、Command、File、Process、Network Traffic、Sensor Health 等作为检测所需的遥测主题，并在 ATT&CK v18（2025年10月）后提示 data sources 已弃用、转向新的检测策略表达方式；对阙疑的启示是：不要只登记“用了哪条规则”，还应登记规则依赖的日志字段、传感器健康状态和可观测性缺口（来源[4]）。

第二层是**稳健统计与行为基线**。对每个实体分别建立基线，而不是把不同角色、不同卡型、不同运行模式混在一起。可以对“每小时判决数、单卡规则命中数、block/warn/advice 比例、保护器触发次数、复算耗时、日志延迟、失败率、重复 entry 比例、证据哈希变化数”等指标做滑动窗口统计。均值和标准差容易被少量极端值污染，MAD（median absolute deviation，绝对中位差）更适合小样本、偏态和含异常点的场景。对观测值 x，先求窗口中位数 m，再求 `MAD = median(|x_i-m|)`，用 `z_MAD = 0.6745(x-m)/MAD` 形成稳健分数；MAD为0时应使用离散等级、IQR或预先规定的最小尺度，而不是任意除以一个极小数。MAD只能说明“偏离基线”，不能独立证明“攻击成立”，因此应把它作为升级信号。

第三层是**change-point（变点）和 CUSUM**。异常点是单个或少量观测离群，变点则是生成机制在某个未知时刻发生了持续改变。例如规则更新后 block 比例持续下降、某保护器从正常的间歇触发变成长期不触发、同一来源的日志延迟突然抬升，可能不是一个离群点，而是状态切换。Page 在1954年提出 CUSUM 控制图，其核心优势是利用完整历史，而不是只看最近一个观测；Oxford 对该领域70年综述指出，CUSUM适合连续监控随机过程的分布变化，并与只看最近观测的 Shewhart 图形成区别（来源[5]）。工程上可对标准化后的残差 `y_t` 累积 `S_t^+ = max(0, S_{t-1}^+ + y_t-k)`、`S_t^- = min(0, S_{t-1}^- + y_t+k)`，当超过阈值 h 时产生变点候选；k是容忍的小漂移，h控制检测延迟与误报。阙疑不应直接照搬某篇论文的阈值，而应在干净历史窗口上用目标平均无报警长度、允许的日告警量和人工容量共同校准。已有工作也将 adaptive CUSUM 用于 CAN 场景的异常型入侵检测（来源[6]），但这只是方法可迁移性的参考，不是阙疑系统的实测效果。

第四层是**机器学习和序列模型**。日志先要模板化，将动态参数与稳定事件模板分离，再形成事件序列、时间间隔、主体—对象关系和上下文特征。DeepLog 以 LSTM 建模系统日志序列，在日志模式偏离正常序列时进行异常检测和诊断（来源[7]）；日志异常检测综述则显示，深度学习方法通常依赖日志解析、序列建模、无监督或半监督训练，跨数据集和概念漂移时存在泛化问题（来源[8]）。阙疑不宜一开始就使用复杂模型：样本仅有37张实卡、452条判决账本，远不足以支撑高维黑盒模型。更稳妥的路线是先用规则和统计特征建立可解释基线，再把轻量模型用于排序、聚合和人工复核优先级；模型输出只作为证据之一，不能覆盖 block 规则，也不能自动改写账本。若未来扩展到更多运行日志，可以比较 One-Class 方法、Isolation Forest、序列预测、图异常检测和半监督分类，但每次模型更新必须记录训练窗口、特征版本、阈值、随机种子和模型摘要，避免“模型变了但账本仍说同一套检测器”。

## 三、推荐的混合检测架构：把可解释性、实时性与可追溯性连接成一条证据链

建议阙疑采用“**采集—规范化—多路检测—融合—告警治理—完整性记录—独立复算**”七层架构。第一层采集层只收集防御所需的最小遥测：`card_id`、输入快照哈希、rule_id、protector_id、verdict、actor、运行模式、UTC时间、耗时、日志来源、错误码、证据引用和版本信息；对外部来源保存 `source_url`、抓取时间与内容 SHA-256，避免后来网页变化导致复盘时拿不到原始证据。第二层规范化层把不同组件日志转换为固定 schema，统一时区、序列号、字段类型和事件名称，拒绝静默丢弃无法解析的日志；解析失败本身要生成低置信度的 telemetry-gap 事件。第三层是并行检测层：规则通道检查结构不变量和已知危险状态；统计通道计算 MAD、IQR、比例、滑动窗口和分位数；变点通道运行 CUSUM 或其他在线 change-point 检验；ML通道只输出异常分数、相似事件簇和排序建议。四路结果必须保留原始证据，不能只保留一个融合后的分数。

第四层是**风险融合**。可以定义一个透明的风险向量而不是不可解释的单分数，例如 `R=(rule_severity, robust_score, change_score, ml_score, evidence_completeness, asset_criticality)`。只有当多个相互独立的信号一致时，才把普通 anomaly 升级为高优先级 intrusion candidate；单个 MAD 超阈值但没有规则、变点或证据链异常时，先标记为“观察”；规则直接发现哈希链断裂时，即使 ML 分数低，也应提升为完整性事件。融合层应做去重、时间邻近聚合、因果关联和抑制重复告警，但“抑制”必须可审计：记录被合并的原始 alert_id、合并规则、窗口和保留的代表事件。告警状态可使用 `new → triaged → confirmed/refuted → closed`，而不是让模型直接写“攻击成功”。对四态判决系统，检测层的异常结论应与知识真值分离：攻击候选可以进入 `Unverified`，只有人工或独立证据确认后才改变业务判决。

第五层是**日志完整性与独立复算**。每条检测事件追加到 append-only 哈希链，至少包含 `seq、event_id、event_type、event_bytes、prev_hash、entry_hash、rule_ids、evidence_hash、actor、utc_timestamp、detector_version`。`entry_hash = SHA-256(canonical_bytes)`，规范序列化必须固定字段顺序、编码、换行和空值表示，不能依赖 Python `set` 或未排序字典的迭代顺序。每个 checkpoint 对截至某一 `tree_size` 的事件计算 Merkle root，并发布 `{tree_size, root, timestamp, detector_version}`；RFC 6962 说明公开可审计、append-only、untrusted 的日志以及 inclusion proof、consistency proof 可以让第三方发现篡改和分视图，但日志本身不保证写入内容正确（来源[9]）。因此，452条现有账本的根哈希只能证明“记录未被改写”，不能证明“判决事实正确”。9个保护器应进入同一证据链：记录每个保护器是否启用、输入、输出、版本和健康状态；检测器要专门监控保护器恒过、恒阻、长期沉默、互相冲突和版本漂移。

独立对账器只读取公开的规则快照、证据快照、账本和 checkpoint，不导入内核内部状态；它至少执行三类检查：重放哈希链、重建 Merkle root、对每条事件比较 recorded 与 recomputed 的结构结果。对452条账本，单条 inclusion proof 的路径大约是 `ceil(log2(452))=9` 个节点，证明体积约为9×32字节，完整性验证的成本很低；但这一成本估计只适用于完整性，不代表语义正确性已经解决。CISA强调日志需要集中管理、保护访问权限、防止删除篡改并配套保留和响应流程（来源[3]），NIST SP 800-61 Rev.3 则把检测、响应、恢复放入统一的网络安全风险管理活动，并以减少事件影响、提高检测和响应效率为目标（来源[10]）。所以架构的终点不是“生成更多告警”，而是形成可查询、可解释、可复算、可追责的闭环。

## 四、评价指标与失败模式：同时衡量检出能力、成本、延迟、稳定性和账本可信度

评价必须先定义 ground truth 和样本单位。对阙疑至少要分开报告：事件级（一次日志事件是否为异常）、攻击场景级（一个完整异常序列是否被发现）、卡级（一个知识卡是否被正确处理）、账本级（是否完整可复算）和时间窗口级（一个窗口内是否发生变点）。TP、FP、TN、FN仍是基础，但只报 accuracy 会被大量正常事件掩盖。应报告 `precision=TP/(TP+FP)`、`recall/TPR=TP/(TP+FN)`、`FPR=FP/(FP+TN)`、`FNR=FN/(TP+FN)`、`F1=2PR/(P+R)`，并在极度不平衡时优先报告 PR-AUC、每千条事件的告警数和固定告警预算下的 recall，而不是只报 ROC-AUC。误报是把正常维护、版本升级、合法批量运行标成攻击；漏报是异常发生但检测器没有告警，二者代价不对称：完整性断裂、盲态泄露和保护器被关闭的漏报通常比一次可解释的低风险误报更严重，但如果一味降低阈值，也会制造告警疲劳。

第二组指标是时间和人工成本：记录 detection latency、MTTD、从事件发生到首次高优先级告警的时间、从告警到人工确认的时间、每小时告警数、每个事件产生的重复告警数、聚合压缩率、平均调查步骤数和人工复核分钟数。2025年的 SOC alert fatigue 综述将告警疲劳视为研究挑战，说明告警数量、优先级、上下文不足和误报处理会共同消耗分析人员注意力（来源[11]）；低发生率场景下，即使 FPR 很低，也可能因为正常事件基数巨大而产生大量错误告警。阙疑应因此设置告警预算，例如按日限制每类低优先级告警数量，超出后只聚合不丢原始证据；必须保留“被抑制数量、抑制原因、抽样复核结果”，否则降噪会变成隐性漏报。告警 fatigue 的修复顺序应是：先修复事件去重和上下文缺失，再校准阈值，最后才考虑模型筛选；不能用静默规则掩盖长期不稳定的检测器。

第三组指标评价**检测器稳定性与漂移**。对 MAD、CUSUM 和基线模型，应在正常窗口、版本发布窗口、数据源短暂缺失窗口、真实缺陷夹具、已确认异常夹具和未知异常窗口上分别测试。报告报警率随时间的变化、阈值触发后的平均恢复时间、变点 detection delay、平均无报警长度、同一事件在不同随机种子下的一致率、跨版本的分数漂移和校准误差。若模型给出概率，还要报告 reliability diagram、Brier score 或 expected calibration error；如果只是无监督分数，则应明确分数不等于概率。对规则和保护器做消融：移除某条规则、某个保护器、统计层或 ML 层后，分别观察 recall、FPR、告警量和漏报类型，而不能把“67条规则全部启用”的单一结果当成组合贡献。上下文已有变异 core 97.3% / all 81.5%，但这类变异分数不能自动等价于攻击检出率，尤其在 P=R=F1=0 的反事实能力尚未修复时，应把它作为测试健康信号而不是主要安全结论。

第四组指标评价**完整性和可复现性**：452条账本的链校验通过率应为100%，每条 `prev_hash`、`entry_hash`、entry_index 和规范序列化都应可重建；checkpoint 的 Merkle root 必须精确匹配，旧 checkpoint 到新 checkpoint 的 consistency proof 必须通过；独立对账器与内核的结构判决差异数、缺失证据数、重复事件数、乱序事件数、分视图检测数应逐项报告。这里要把“正确性”和“完整性”分栏：root mismatch 是完整性失败，recorded≠recomputed 是复算不一致，ground truth 不同则是语义判定争议，三者不能混成一个 error rate。对于 30 条 holdout，不能只沿用“17条真错、66.7%检出”这一共享上下文数字而不列出整数分母、置信区间和标签来源；对于 corpus 40 的43.8%，必须先对账修复算术口径，否则任何攻击检测曲线都会被不一致的分母污染。最终建议主表至少包含：`dataset/window、n、TP、FP、TN、FN、precision、recall、F1、FPR、FNR、PR-AUC、告警数、MTTD、平均调查成本、ledger_integrity、replay_match`。

## 五、对阙疑的三条具体行动、盲区与来源

**行动一：先建立可冻结的检测事件 schema 和基线。** 在不改变既有业务判决的前提下，为67条规则、9个保护器和所有判决事件补齐 `event_id、seq、actor、utc_timestamp、source、card_id、rule_id、protector_id、severity、evidence_hash、detector_version、prev_hash、entry_hash`；把37张实卡、452条账本、holdout 30和corpus 40分别标记数据集版本。对每个运行模式计算每小时事件量、规则命中比例、保护器触发率、复算耗时和日志缺失率，先用MAD作稳健基线，再以人工审核的窗口校准CUSUM。所有阈值、窗口、k、h、随机种子都写入版本化配置，不能藏在代码默认值中。这样可先得到“检测器健康度”和“证据链健康度”，再谈新模型的提升。

**行动二：实现规则—统计—变点—轻量模型的混合评测，并专门测误报漏报和告警疲劳。** 用已确认的真实缺陷、合法维护、规则版本变更、日志缺失、重复追加、哈希篡改和未知异常构造防御性测试集；不编写任何真实攻击载荷或未授权操作步骤。按事件级、场景级和账本级分别计算 precision、recall、F1、FPR、FNR、PR-AUC、MTTD、告警压缩率和人工复核成本，报告至少五个阈值点和置信区间。做消融实验：规则单独、统计单独、CUSUM单独、规则+统计、规则+统计+CUSUM、完整融合；若增加 ML 只降低告警量而损害关键漏报率，就不能把它称为改进。特别修正 holdout 与 corpus 的算术口径，并把“反事实 P=R=F1=0”作为当前检测能力的明确限制，而不是用高变异分数掩盖。

**行动三：把452条账本正式升级为可审计的攻击检测证据链。** 每次检测事件采用规范化字节追加到哈希链；按固定周期发布带 `tree_size、root、timestamp、detector_version` 的 Merkle checkpoint；提供 inclusion proof、consistency proof、全量 replay 和独立 diff 报告。对账器禁止导入 `gate_engine.py` 内部符号，至少用独立实现校验链、root、规则版本和四态结构结果；9个保护器要有健康事件，长期不触发、恒触发、被禁用或与主判决冲突都要进入告警治理。论文中应明确写出：append-only/Merkle 只能证明“事件被忠实记录且历史未被改写”，不能证明“该事件或判决在事实语义上正确”；这与 RFC 6962 对透明日志“便于发现错误、并非自动阻止错误”的边界一致。优先把每日告警摘要、原始告警、抑制关系和人工处置结果一起入账，才能在告警疲劳发生后追查“哪些告警被隐藏、为何隐藏、是否导致漏报”。

**盲区与适用范围。** 第一，NIST SP 800-94 发布于2007年，NIST页面明确说明2012年的 Rev.1 草案从未成为最终出版物，因此不能把它当成覆盖现代云、容器和模型检测的完整标准；本文只借用其分类和工程框架。第二，DeepLog和许多日志异常检测论文来自大规模系统日志，阙疑目前只有小规模知识卡、账本和验证运行记录，不能把论文中的模型效果移植为本项目实测结论。第三，CUSUM理论适合序列分布变化，但在强烈季节性、版本切换和日志缺失时需要重新建模；MAD在窗口过短、全体值相同或异常占比过高时也会失效。第四，告警疲劳的公开研究多面向 SOC，阙疑是知识验证系统，人员容量、事件语义和损失函数不同；本文的告警预算与指标是工程建议，不是已验证的最优参数。第五，共享上下文中的 holdout、corpus、变异率和账本数字必须以真实文件、独立对账器和可重放命令复核；尤其43.8%与40条样本的算术矛盾未修复前，任何 F1、漏报率或攻击曲线都应标为暂定。最后，检测本身不能保证不存在未知异常，独立对账器也不能消除共同规则、共同证据源或共同实现假设造成的相关错误；论文应诚实报告这些盲区。
