# 方向 72：数据仓库 vs 数据湖 vs Lakehouse（Delta / Iceberg / Hudi），以及对"实验记录 + 判决账本"的必要性批判

> 调研时间：2026-09-29｜调研员：第 8 组（方向 71–80）｜搜索次数：14 次（含 4 次 WebFetch 逐字取数）

## 核心结论

1. **Lakehouse 这个概念是被一篇有明确"利益方"的论文定义的，读它必须先读出处**：*Lakehouse: A New Generation of Open Platforms that Unify Data Warehousing and Advanced Analytics*，作者 **Michael Armbrust, Ali Ghodsi, Reynold Xin, Matei Zaharia**，**CIDR 2021**——四人全部来自 **Databricks**（分别是 Spark 核心作者、CEO、首席架构师、CTO）。摘要逐字：*"This paper argues that the data warehouse architecture as we know it today will wither in the coming years and be replaced by a new architectural pattern, the Lakehouse"*，其成立前提是 (i) 开放格式 Parquet/ORC、(ii) ML/DS 一等公民、(iii) **在 TPC-DS 上与云数仓竞争**。**阙疑的 452 条账本三条前提一条都不满足。**
2. **切换阈值是"数十 TB"，阙疑比它小约 6 个数量级**：Apache Hudi 官方博客（2026-07-23）给出的决策口径逐字为——数据仓库适用于 *"A small team running dashboards over a few terabytes"*；湖仓适用于 *"data volumes are growing into the tens of terabytes and beyond and warehouse bills sting"*；并明确 *"At small volumes the difference narrows, and a managed warehouse can be cheaper in engineering time"*。按 452 条判决 × 平均数百字节估算，账本总量约 **10^5 – 10^6 字节（< 1 MB）**，与 "a few terabytes"（≈10^12 B）差 **6 个数量级**。
3. **三种表格式的机制差异才是真正可借用的东西，而不是"选一个用"**：Delta Lake 用 `_delta_log` JSON 事务日志、**每 10 次 commit 重写为 Parquet checkpoint**、compaction 目标 *"optimally ~1GB, but at least 128MB"*；Iceberg 用分层 manifest 元数据、靠 **CAS 原子换 snapshot ID** 提交；Hudi 用 timeline + COW/MOR，**MVCC 下写并发被限制为 1**（*"write concurrency to 1"*）。**这三条"日志 + checkpoint / 快照指针 / 单写者"的设计，恰好与阙疑的 append-only 哈希链 + Merkle checkpoint + 单写内核同构——可借鉴的是机制，不是产品。**

## 精确数字与案例

### 一、概念谱系与权威出处

| 概念 | 定义 / 出处 | 关键特征 |
|---|---|---|
| 数据仓库 (Data Warehouse) | Inmon / Kimball 传统体系；面向主题、集成、相对稳定、反映历史变化 | **Schema-on-Write**：写入前必须有 schema，强一致性 |
| 数据湖 (Data Lake) | 对象存储（S3/OSS/GCS）+ 原始文件 | **Schema-on-Read**：写入时不校验，读取时解释；廉价着陆区 |
| Lakehouse | **Armbrust, Ghodsi, Xin, Zaharia, CIDR 2021, Databricks** | 开放格式（Parquet/ORC）+ 事务元数据层 + ML 一等公民 |

CIDR 2021 摘要逐字（来自 vldb.org 官方收录页）：
> "Lakehouses can help address several major challenges with data warehouses, including **data staleness, reliability, total cost of ownership, data lock-in, and limited use-case support**. We discuss how the industry is already moving toward Lakehouses… We also report results from a Lakehouse system using Parquet that is **competitive with popular cloud data warehouses on TPC-DS**."

**读法提醒**：这篇论文的"竞争对象"是 Snowflake / Redshift / BigQuery 这类云数仓，"竞争基准"是 TPC-DS（TB 级）。把它的结论搬到一个 1 MB 的判决账本上是**典型的概念误用**——论文解决的问题（数据陈旧、TCO、厂商锁定、ML 取数）在单人科研项目中全部不存在。

### 二、三大表格式的机制硬差异（来源：lakeFS 官方博客，2021-04-12，含逐字引文）

| 维度 | **Delta Lake** | **Apache Iceberg** | **Apache Hudi** |
|---|---|---|---|
| 起源 | Databricks 维护（*"creators of Apache Spark"*） | **Netflix** 最初发布 | **Uber** 最初开源 |
| 事务日志 | `_delta_log` 顺序 JSON 日志 + **每 10 commits** 重写为 Parquet checkpoint | 元数据 JSON + manifest list，**CAS 原子换 snapshot ID** | `.hoodie` timeline，LSM-like，commit instant 为事务单位 |
| 并发控制 | **仅 OCC（乐观并发）** | **仅 OCC** | **MVCC + OCC 双支持**；MVCC 下 *"write concurrency to 1"* |
| Upsert | `MERGE INTO`，copy-on-write | `MERGE INTO`，直接重写文件（COW） | **COW / MOR 双表类型**，专为高频 upsert 设计 |
| 托管摄入 | 无 | 无 | **有（DeltaStreamer）**，可直读 Kafka |
| 引擎 | Spark 深度绑定 | **最广**：Spark/Flink/Trino/Hive/Dremio/Impala | Spark + Flink 为主 |
| 适用规模提示 | *"primarily a Spark shop and expect relatively low write throughput"* | 适合 **超过 10k 分区** 的元数据负担 | *"minute-level analytics"*；AWS Athena/Glue/EMR 预装 |

**Delta Lake 运维成本逐字**：
> "Delta tables need to undergo periodic compaction processes that take many small parquet files and combine them into fewer, larger files (**optimally ~1GB, but at least 128MB in size**)."

> "Read support is available for Presto, AWS Athena, AWS Redshift Spectrum, and Snowflake using Hive's SymlinkTextInputFormat… this requires exporting **a symlink.txt file for every Delta table partition**, and as you might suspect, becomes expensive to maintain for larger tables."

**Hudi 单写者限制逐字**：
> "all writes must be totally ordered in its central log. To offer this guarantee, Hudi **limits write concurrency to 1**, meaning there can only be a single writer to a table at a given point in time"

**Iceberg 提交机制逐字**：
> "Writers then attempt a **Compare-And-swap (CAS) operation** on a special value holding the current snapshot ID. If no other writer replaces the snapshot during a commit, the operation succeeds."

### 三、版本与治理现状（2025–2026）

- **Delta Lake 4.0** 于 **2025-09-25** 发布（delta.io 官方博客，作者 Carly Akerly / Robert Pack），**超过 70 位贡献者**。新特性：catalog-managed tables（Preview）、Delta Connect、**Variant 数据类型（schema-on-read，无需预定义 schema，配合 Shredded Variants 做统计与 file skipping）**、Drop Feature（保留表历史地删除特性）、**Version Checksums（"mini-checkpoints for your Delta logs"）**、Log Compaction、**Row Tracking**、Clustered Tables。
- **Apache Iceberg**：最新文档版 **1.11.0**（iceberg.apache.org 文档导航标注 "Latest (1.11.0)"）；历史版本序列可回溯至 1.4.x。Iceberg **v3 规范**引入 Binary Deletion Vectors、Row Lineage、Variant 等（Atlan 称 deletion vectors "up to 10x faster"——**该 10× 数字来自厂商博客，未独立核实**）。DuckDB 的 Iceberg 扩展自 **1.4.0（2025 年 9 月）** 起支持读写（来源：Grokipedia，二次来源，**需核实**）。
- **Apache Hudi**：官方博客仍在 2026-07 更新架构对比文章，项目活跃。
- **互操作**：**Apache XTable**（原名 OneTable）等新兴项目试图桥接三种格式，降低迁移成本。

### 四、Schema-on-Read vs Schema-on-Write：对账本的判读

| | Schema-on-Write（数仓） | Schema-on-Read（数据湖） |
|---|---|---|
| 写入时 | 校验 schema，不合格拒绝写入 | 不校验，先落盘 |
| 读取时 | 直接读，无解释成本 | 需解析，schema 漂移会产生**静默错误** |
| 一致性 | 强（*"天然支持强一致性，数据质量高，适合金融交易等场景"*） | 弱 |
| 适合 | 结构化、稳定、需强一致 | 原始归档、ML 语料、冷留存 |

**对阙疑的判读**：判决账本恰恰**必须**用 **Schema-on-Write**。理由不是性能，而是**可复算性**：如果账本条目允许 schema-on-read 式漂移，那么第三方对账器在重算时可能对同一条记录做出不同解释，直接摧毁"判决可复算"这一核心卖点。**Lakehouse 派最引以为傲的 schema 演进能力（Iceberg 的 field-id 重命名、Delta 的 mergeSchema、Hudi 的 Avro 兼容），在账本场景是负资产。**

### 五、批判性结论：对"实验记录 + 判决账本"要不要上 Lakehouse

**结论：完全不需要。三条硬理由 + 一条可借鉴点。**

理由一（规模）：452 条账本 ≈ 1 MB 以下；Hudi 官方给出的湖仓启动阈值是 **tens of terabytes and beyond**，差 6 个数量级。在这个规模上，任何表格式带来的收益都被其引入的组件复杂度淹没（Delta 要 Spark，Iceberg 要 catalog，Hudi 要 timeline 服务）。

理由二（可复算性冲突）：三大格式的**核心价值是"可变"**——upsert、delete、compaction、time travel 回滚。而账本的核心价值是**"不可变"**。Delta 的 compaction 会**重写底层 Parquet 文件**（目标 ~1GB/至少 128MB），RocksDB/LSM 同理——**文件字节布局随时间变化 = 无法做字节级可复算 = 与 Merkle checkpoint 直接冲突**。这是架构级的不兼容，不是调优问题。

理由三（依赖树）：Delta 需要 Spark（JVM，数百 MB 起），Iceberg 需要 catalog（Hive Metastore / REST catalog），Hudi 需要 Spark/Flink。而阙疑的卖点是**第三方可不信任内核地复算**——每多一个组件，复算门槛上升一档，可复算性下降一档。

**唯一值得借鉴的三条机制**：
1. **Delta 的"日志 + 每 10 commit 一次 checkpoint"** → 直接映射为阙疑的"append-only 哈希链 + 周期性 Merkle checkpoint"。Delta 官方管 checksum 叫 *"mini-checkpoints for your Delta logs"*，与 Merkle checkpoint 是同一思想的工程实现，可作为论文的**同行佐证引用**。
2. **Hudi 的"单写者"约束** → 阙疑内核 `gate_engine.py` 天然是单写者，这个约束在 Hudi 里是被显式承认并写进文档的（*"write concurrency to 1"*），可以拿来论证"单写者 + append-only"是工业界认可的正确取舍，而不是本项目的简化妥协。
3. **Delta 4.0 的 Row Tracking / Iceberg v3 的 Row Lineage** → 与阙疑"证据可追"卖点同构，可在 related work 中作为"工业界也在往行级血缘走"的证据。

## 对阙疑的 3 条具体行动

1. **在论文 related work 中明确写一段"为什么不采用 Lakehouse 表格式"**（时间点：**2027-02 前**，写入 `research/related_work.md` 新增小节 R7「Why not a lakehouse table format」）。三条逐字可用的论据：(a) Apache Hudi 官方给出的湖仓适用阈值是 *"tens of terabytes and beyond"*，本项目账本 < 1 MB；(b) Delta Lake 官方要求周期性 compaction 到 *"at least 128MB"* 的文件，会重写字节布局，与 Merkle checkpoint 的字节级可复算冲突；(c) Hudi 在 MVCC 下显式 *"limits write concurrency to 1"*，说明"单写者 append-only"是工业界认可的正确取舍。**这段要写成"我们评估后排除"，而不是"我们没考虑"。**
2. **把 Merkle checkpoint 与 Delta 的 "version checksums / mini-checkpoints" 做一次显式类比并给出对照表**（时间点：**2027-04 前**，产物 `_arch_v47/72_ledger_vs_tableformat_mapping.md`）。表头固定为：`mechanism / delta_lake_name / iceberg_name / queyi_name / 是否可字节级复算`。用于回应审稿人"你的哈希链和现有表格式的 time travel 有什么区别"——答案是：**它们的目标是回滚可变表，我们的目标是证明不可变账本未被篡改。**
3. **给账本加一条硬性的 Schema-on-Write 校验并在 CI 中强制**（时间点：**2026-12 前**）。具体：新增 `_arch_v47/tools/ledger_schema.py`（或挂在现有 595 个 .py 工具之一），用 JSON Schema 严格校验每条 verdict 的字段集合与类型，**禁止未知字段**（`additionalProperties: false`），并在 `pre-commit` / CI 中跑 `python ledger_schema.py --strict ledger.jsonl`。理由写进注释：账本走 schema-on-read 会让第三方对账器对同一记录产生不同解释，直接摧毁可复算性。
