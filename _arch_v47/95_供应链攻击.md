# 方向 89：软件供应链攻击（software supply-chain attack）

## 核心结论

1. 软件供应链攻击已从个案变成"常态化的工业化威胁"：Sonatype《2024 年软件供应链状况报告》（第 10 版，2024-10-10 发布）实测 **2019 年以来累计识别恶意开源包 704,102 个，同比（YoY）增长 156%**；国内悬镜安全《2025 年度软件供应链投毒风险研究报告》（2026-02）称 2025 年全年识别投毒包**突破 59,000 个、较 2024 年增幅超 50%**。对依赖数百个第三方包的任何系统（包括依赖众多 Python 库的阙疑）而言，"被投毒"不再是罕见事件而是基线风险。
2. 攻击面不止"包管理器"一条路，而是**四条并行路径**：(a) 包注册表投毒（typosquatting / 依赖混淆，Alex Birsan 2021 年依赖混淆研究拿下 **超 13 万美元** 赏金）；(b) 维护者社会工程（XZ Utils "Jia Tan" 后门 CVE-2024-3094，**CVSS 10.0**，潜伏约 2.5 年）；(c) CI/CD 管道投毒（Ultralytics 2024-12 经 GitHub Actions 脚本注入发布 8.3.41 挖矿版本；Megalodon 大规模 GitHub Actions 投毒行动）；(d) 账户/token 劫持自传播（Shai-Hulud 蠕虫 2.0 于 2025-11-24 **感染 796 个独立 npm 包、1,092 个版本、合计周下载超 2,000 万**）。防线因此必须是分层的：锁定依赖哈希 + SBOM + 最小化依赖 + 可复现构建，任何单点都不够。
3. 对阙疑而言，供应链攻击直接威胁其**核心卖点"判决可复算 + 证据可追"**：如果 `gate_engine.py` 的依赖被投毒，账本上的每一条判决都可被攻击者系统性伪造，且复算者用的同一套依赖同样被污染——污染会"自证清白"。这正是阙疑"独立对账器不依赖内核"机制的价值所在：第三方复算环境必须能脱离内核依赖集重放判决。防御上可落地三件事：依赖锁定 + 哈希校验（对齐方向 23）、git 提交签名与历史可追责（方向 28）、仓库与发布管道最小权限 + 可复现构建（方向 29）。

## 精确数字与案例

### 一、SolarWinds SUNBURST：构建链投毒的"国家级上限"（2020）

SolarWinds Orion 平台构建环境被入侵，攻击者通过名为 SUNSPOT 的注入工具在构建阶段植入 SUNBURST 后门。官方调查博客（2021-01-11，CEO Sudhakar Ramakrishna 署名）给出官方时间线（逐字引文）：

> "Our current timeline for this incident begins in September 2019, which is the earliest suspicious activity on our internal systems identified by our forensic teams in the course of their current investigations."

> "An updated version of the malicious code injection source that inserted the SUNBURST malicious code into Orion Platform releases starting on February 20, 2020."

> "The perpetrators remained undetected and removed the SUNBURST malicious code from our environment in June 2020."

| 指标 | 数字 | 来源 |
|---|---|---|
| 攻击者潜伏起点 | 2019-09（最早可疑活动） | SolarWinds 官方博客 2021-01-11 |
| 后门开始进入正式发布 | 2020-02-20 起 | 同上 |
| 攻击者从环境中清除痕迹 | 2020-06 | 同上 |
| 公开披露 | 2020-12-12 知情 → 当日通报 | 同上 |
| 安装了被污染更新的客户 | **约 18,000 家**（通知了 33,000 家） | SEC 文件，经 ZDNet 2020-12-15 报道 |
| 被攻击者实际深入利用的目标 | 约 100 家（美国财政部、DoD 等二手来源称约 100 家高价值目标，**未从官方一手文件核实具体清单**） | databreachcost.com 等二手汇总 |

教训：构建服务器是一次性信任的汇聚点——源码仓库干净，产物却有毒。SolarWinds 官方博客承认："We recognize the software development and build process used by SolarWinds is common throughout the software industry."（我们使用的软件开发与构建流程在整个行业都很常见。）——这正是"可复现构建 + 构建日志审计"成为监管要求（美国 EO 14028）的直接动因。

### 二、XZ Utils 后门（CVE-2024-3094）：社会工程 + 构建期注入的教科书案例（2024）

| 指标 | 数字/事实 | 来源 |
|---|---|---|
| CVSS 评分 | **10.0**（`AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H`） | CVEReports 分析页；Red Hat 评定 10.0 |
| EPSS 概率 | 85.80%（Top 1% most exploited） | 同上 |
| "Jia Tan" 开始渗透 | 2021-10-01 创建账号开始贡献 | 同上（时间线） |
| 恶意二进制测试文件提交进仓库 | 2024-02-23 | 同上 |
| 带后门的 5.6.1 发布 | 2024-03-09 | 同上 |
| 被发现 | 2024-03-29，PostgreSQL 开发者 Andres Freund 因 **sshd 认证多耗约 500ms** 而起疑并向 oss-security 披露 | 同上 |
| 潜伏总时长 | 约 2.5 年 | 据上表推算 |

技术要点（CVEReports 逐字）：

> "The attacker, operating under the handle 'Jia Tan,' introduced the backdoor in the **release tarballs**—the packaged source code files that package managers download to build the software."

> "If you looked at the GitHub repository for XZ Utils, everything looked clean."

后门藏在 `tests/files/bad-3-corrupt_lzma2.xz` 等二进制"测试文件"里，经 M4 宏在 `./configure` 阶段拼装，通过 glibc IFUNC 机制劫持 `RSA_public_decrypt`，持有特定 Ed448 私钥的攻击者可绕过 SSH 认证获得 root。CVEReports 明确点出防御结论：

> "This is a textbook example of why 'reproducible builds' are critical. If the artifact generated from the source code doesn't match the distributed binary, you have a problem."

注意稳定发行版躲过一劫的原因恰恰是"滞后"：受影响的只有 Fedora Rawhide、Debian Sid、Kali、Arch 等滚动发行版——这从反面说明"跟进上游太快的依赖策略"（如阙疑 CI 里 `pip install` 不锁版本）会放大供应链风险。

### 三、注册表投毒的量化：Sonatype 年报与"依赖混淆/typosquatting"

**Sonatype 第 10 版《State of the Software Supply Chain》（2024-10-10，官方新闻稿逐字数字）**：

> "Sonatype observed a 156% increase in the number of malicious packages year-over-year, reaching more than 704,102 identified since 2019."

> "Python (PyPI) saw an 80% increase in consumption compared to last year, reaching more than 530 trillion package requests, while JavaScript (npm) downloads increased by 70%, with 4.5 trillion package requests."

> "Despite more than 99% of packages having updated versions available, 80% of application dependencies remain un-upgraded for over a year."

**依赖混淆（dependency confusion）**：研究员 Alex Birsan 于 2021-02 披露，向公共 npm/PyPI 上传与各公司内部私有包同名的包，利用包管理器"优先取高版本公共包"的默认行为，成功打入苹果、微软、PayPal 等 35+ 公司内部构建；Simon Willison 博客（2021-02-10）记载其因此获得**超过 130,000 美元**漏洞赏金。防御共识（后续多家供应商指南一致）：私有包在注册表中**占位（reserved namespace）+ lockfile 精确锁定 + 哈希校验**。

**typosquatting 学术研究**：TypoSmart（arXiv:2502.20528，2025-02，Purdue 等机构）针对包注册表 typosquatting 检测；同组（Davis 实验室，davisjam）2025 技术报告对 typosquatting 数据做了攻防模式分析。具体检测率数字见原文（本文未逐条核实其数字，见盲区）。

**国内报告口径**：悬镜安全《2025 年度软件供应链投毒风险研究报告》（2026-02-28，搜狐转载稿）称"全年识别到的投毒包总量突破 59,000 个，相较 2024 年增幅超过 50%"；数字取自转载摘要，**原报告 PDF 未逐页核对**（见盲区）。

### 四、蠕虫化与 CI/CD 投毒：2024–2025 的新形态

**Shai-Hulud npm 蠕虫**（Datadog Security Labs，2025-11-25 分析文，逐字）：

> "Shai-Hulud 2.0 has successfully taken over and backdoored 796 unique npm packages. These packages total over 20 million weekly downloads."

> "we estimate that the data of over 500 unique GitHub users was successfully exfiltrated, belonging to over 150 unique GitHub organizations. This should be interpreted as a lower bound."

| 指标 | Shai-Hulud 1.0（2025-09） | Shai-Hulud 2.0（2025-11-24 起） |
|---|---|---|
| 感染包数 | "数百个"合法包（hundreds） | **796 包 / 1,092 版本** |
| 官方警报 | CISA 2025-09-23 发布供应链警报 | 社区 2025-11-24 发现 |
| 外泄渠道 | 创建公共 GitHub 仓库存窃取凭据 | 同上，另建 14,000+ 外泄仓库 |
| 额外破坏 | — | 无法外泄时删除用户主目录（`shred -uvz` / `cipher /W`） |
| 零号感染 | — | `asyncapi/cli` 仓库恶意提交窃取 npm token（Aikode 分析；PostHog 2025-12-04 复盘确认其 token 由此泄露） |
| 波及公司 | — | PostHog、Postman、Zapier 等 |

关键机制：蠕虫用 `preinstall` 脚本 + Bun 运行时规避 Node.js 监控，用 Trufflehog 扫描密钥，并调用 AWS/Azure/GCP 元数据服务取临时凭据——**CI 环境恰恰是凭据最密集的地方**。

**Ultralytics（YOLO）PyPI 事件（2024-12）**：攻击者利用 GitHub Actions 工作流的脚本注入缺陷（PR 分支名注入），窃取 PyPI token 并发布 8.3.41 版本，内含 XMRig 挖矿程序；Snyk（2024-12-11）与 Schneier on Security（2024-12-13）均有记录。这证明"仓库→CI→PyPI 发布"整条链上任一环被攻破即可向全部下游用户投毒。

**Megalodon（2026-05 披露，CSA 实验室研究笔记）**：大规模自动化 GitHub Actions 投毒行动，`@tiledesk/tiledesk-server` 为确认案例之一——攻击面是 fork 后的 workflow 与 secrets 泄露的连锁反应。

**防御侧数据**：Sigstore/`npm provenance` 生态采用率仍低——Zenn（2026-03）统计"**连 Sigstore 项目自己的 npm 依赖也只有 7.2% 带 provenance**"；Sonatype 报告称去年发布 SBOM 超 60,000 份，但相对 6.6 万亿年下载量仍是九牛一毛。

### 五、监管基线：EO 14028 → NTIA SBOM 最小要素（防御的制度化）

- 2021-05-12 美国行政令 EO 14028《Improving the Nation's Cybersecurity》要求向联邦政府销售软件者提供 SBOM；
- 2021-07 NTIA 发布《The Minimum Elements For a Software Bill of Materials (SBOM)》，定义最小字段：供应商、组件名、版本、唯一标识符、依赖关系、SBOM 作者、时间戳等；
- 2022-05 NIST 发布对应 guidance，要求"Confirm that SBOMs received from third-party suppliers meet the NTIA's Recommended Minimum Elements"（NIST 官网逐字）；
- CISA 于 2026 年更新《SBOM Minimum Elements》（FOSSA 博客 2026-07-30 记载）。

对单人开源科研项目的启示：SBOM 不是大企业专属，`pip freeze` + `requirements.txt` 锁定 + CycloneDX 生成器一行命令即可产出合规 SBOM——这既是防御也是论文"可复现性声明"的现成素材。

## 对阙疑的 3 条具体行动

1. **依赖锁定 + 哈希固定（对齐方向 23）**：为阙疑的 595 个 .py 工具与内核 `gate_engine.py` 生成并提交 `requirements.lock`（`pip-compile --generate-hashes`，或 `uv pip compile --generate-hashes`），CI 一律 `pip install --require-hashes -r requirements.lock`，禁止任何 `pip install <pkg>` 裸调用；同时在 `research/12_threats_to_validity.md` 新增小节 **T7：供应链污染对判决有效性的威胁**，明确"若第三方依赖被投毒，四态判决与账本的可信性如何降级"的论证。时间点：2027-01 前（早于投稿冻结）。
2. **独立对账器与内核依赖隔离（对齐方向 29）**：把独立对账器（不依赖内核的第三方复算器）的依赖集显式最小化到 ≤10 个纯标准库/少依赖包，并在论文附录给出对账器自身的 SBOM（CycloneDX JSON，`cyclonedx-py requirements -o sbom.json`）+ 每次构建的哈希清单，写明"复算环境与生产环境依赖集分离"，防止污染在内核与对账器间共因失效。时间点：2027-03 前。
3. **git 历史可追责 + 发布管道加固（对齐方向 28）**：全仓库启用提交签名（`git commit -S`）与 tag 签名（`git tag -s`），GitHub 仓库开启 branch protection（禁 force-push、要求签名提交）与 Actions 最小权限（`permissions: contents: read` 顶置，PyPI 发布用 Trusted Publishing / OIDC 而非长效 token）；在 `research/14_protocol.md` 增加"账本种子哈希"一节——Merkle checkpoint 的初始种子由签名提交的 git commit hash 派生，使任何构建期注入在 checkpoint 验证时留下可追痕迹。时间点：2027-04 前，随盲态协议冻结一起落。

## 盲区（诚实标注）

- **Sonatype"704,102 / 156%"为厂商自报口径**，其数据来源与判定标准（如何区分恶意包与误报）未公开可复算，存在厂商利益相关（卖安全产品）的样本偏差；悬镜"59,000"取自中文转载摘要，**原报告未逐页核对**。
- **SolarWinds"约 100 家深度渗透目标"** 来自二手汇总（databreachcost 等），未在 SEC/SolarWinds 一手文件中找到精确名单与数字；"18,000"有 ZDNet 报道的 SEC 文件背书，但**原始 8-K 文本未直接打开核对**。
- **typosquatting 学术论文（arXiv:2502.20528 TypoSmart 等）的具体检测率/数据集规模数字未逐条核实**——本文只引用了其存在、机构与主题，未摘录其百分数；引用进论文前必须 WebFetch 原文核对。
- **Shai-Hulud 1.0 的精确感染包数**：Datadog 文中仅写"hundreds"，各二手来源给出 180+/500+ 等不同数字，互相矛盾，本文采用保守的"hundreds"；精确值未核实。
- **npm provenance 7.2%（Sigstore 自身依赖）** 来自 Zenn 个人技术博客，统计方法（top N？全量？时间窗？）未核实，不宜直接进论文。
- **搜索时间偏差**：部分检索结果（如 safeguard.sh、insom.ai）为 2026 年的 SEO 性安全博客，时效性尚可但权威性低于厂商一手报告与 SEC/NTIA 官方文件，引用时应优先后者。
