# 方向 74：数据迁移方案（schema 演进、向前/向后兼容、在线迁移、回滚、数据校验、真实事故）

> 调研时间：2026-09-29｜调研员：方向 68–79 组｜真实搜索 13 次（含 2 次 WebFetch 逐字取数）
> 核心命题：**迁移事故的杀伤力不来自"迁移写错了"，而来自"回滚路径从未被走过"。** 本文用两起公开事故（Resend 2024、GitHub 2018）证明这一点，并给出阙疑在 append-only 账本上的迁移方案。

---

## 核心结论

1. **Resend 2024-02-21 事故是"迁移 + 恢复双重失败"的极端案例，其数字值得逐字记住。** 一次**本地执行的迁移命令误指向生产环境**，直接 **drop 了生产库全部表**；宕机 **05:01–17:05 UTC（约 12 小时）**；**第一次从备份恢复耗时 6 小时但失败**——官方逐字原因：*"the first backup failed and started to investigate"* → *"Found that the backup failed due to a wrong selection of the backup timestamp"*；第二次换用更早的备份又花了 **5 小时**才成功；最终仍丢失 **5 分钟**数据（04:50:00–04:56:27 UTC）。为加速恢复，官方临时把数据库内存从 **128GB 提到 256GB**、CPU 从 **32 核 ARM 提到 64 核 ARM**。**最刺眼的整改第一条是**：*"No accessible user role should have write privileges on the production database."*——**权限隔离的缺失，是这次事故的真正根因。**
2. **对 append-only 哈希链账本，正确的迁移策略不是"改历史"，而是"永不改历史"。** 通用系统的 schema 迁移之所以危险，是因为它**原地改写已有数据**（`ALTER TABLE` + 回填），一旦中途失败就处于"新旧混杂"的中间态。阙疑的账本是 append-only 的——**只要坚持"迁移只以追加新条目实现、旧条目字节永不改动"，整个迁移问题就从"在线 DDL"退化为"给新条目加字段"**。这与 Confluent Schema Registry 的核心思路一致：官方文档逐字 *"The **default compatibility mode** is BACKWARD. Each schema version gets a unique ID and incremented version number. When schemas are updated, Schema Registry checks compatibility before accepting the new version."*——**"每个版本有唯一 ID + 只增不改"就是可复算系统的迁移范式。**
3. **阙疑必须显式引入"规则版本钉扎"（rule-version pinning），否则"判决可复算"这句话在规则演进后就会失效。** 当前状态是 **67 规则（block 44 / warn 16 / advice 7）**，这些规则**必然会随研究推进而修改**。如果账本条目只记录"判决结果"而不记录"用哪一版规则得出的"，那么第三方拿到今天的规则集**无法复算一年前的判决**。**做法**：每条账本条目增加 `rules_manifest_sha256` 字段，指向该次判决所使用的规则集快照的哈希。**这不是我的发明**——它就是 Confluent Schema Registry 的 schema ID 机制在规则集上的同构应用。

## 精确数字与案例

### 一、Resend 2024-02-21：逐字时间线与数字

来源：Resend 官方事故报告（2024-02-22 发布）。

**TL;DR 逐字**：
> *"On February 21st, 2024, Resend experienced an outage that affected all users due to a database migration that went wrong. This prevented users from using the API (including sending emails) and accessing the dashboard from **05:01 to 17:05 UTC (about 12 hours)**."*
> *"The database migration accidentally deleted data from production servers. We immediately began the restoration process from a backup, which completed **6 hours later**. Unfortunately, once it finished, we found that **it failed to restore the data**, so we had to start the restoration process a **second time with a different backup**."*
> *"For data created prior to the migration, there were **5 minutes of data loss** from when the migration started and the database went offline from **04:50:00 to 04:56:27 UTC**."*

**逐字时间线**：

| 时刻（UTC, 2024-02-21） | 事件 |
|---|---|
| 04:56 | 数据库迁移开始 |
| **04:57** | **发现生产库的表正在被删除**（1 分钟内发现） |
| 05:01 | 开始从备份恢复 |
| 05:02 | 发布状态页公告（此后每 30–60 分钟更新） |
| **11:02** | **第一次恢复流程完成**（耗时 6 小时） |
| 11:03 | 意识到第一次备份恢复**失败**，开始排查 |
| 11:33 | **查明失败原因：备份时间戳选错了**（*"wrong selection of the backup timestamp"*） |
| 11:48 | 扩容加速恢复：数据库内存 **128GB → 256GB**，CPU **32 核 ARM → 64 核 ARM** |
| 12:05 | 开始用**更早**的备份恢复 |
| **17:01** | **第二次恢复完成**（又花 5 小时） |
| 17:02 | API 开始接受请求 |
| 17:05 | Dashboard 恢复可访问，事故结束 |

**根因逐字**：
> *"While building a feature, we performed a database migration command locally, but it **incorrectly pointed to the production environment** instead, which **dropped all tables in production**."*

**整改清单（逐字，前三条与本文最相关）**：
1. *"Re-populate data from the 5-minute window of data loss."*
2. *"**No accessible user role should have write privileges on the production database.**"*
3. *"Improve local development to reduce risks related to database migrations."*
4. *"Create redundancy to preserve sending function even during a database outage."*
5. *"**Increase cadence for disaster recovery tests.**"*
6. *"Implement incident banner on Resend dashboard to inform users quickly."*

**三条可直接搬到阙疑的教训**：
- **教训 A（权限）**：*"迁移命令误指向生产"* 这类事故**不能靠"小心"避免**，只能靠**"生产凭据不出现在本地开发环境"**。阙疑的对应风险是：**`gate_engine.py` 的写入模式与"只读复算模式"如果不加区分，一次误运行就可能改写账本**。**行动**：账本写入必须要求显式参数（如 `--append`）+ 目录内 `ledger.lock`，默认运行是只读复算。
- **教训 B（备份时间戳选错）**：恢复失败的原因**不是备份坏了，而是"选错了备份"**。这说明**恢复流程本身必须有校验步骤**——否则"恢复成功"只是"命令跑完了"。阙疑的对应做法就是方向 70 里的 `verify_restore.py`（恢复后必须通过哈希链 + 判决复算 + Merkle root 三重校验）。
- **教训 C（恢复扩容）**：Resend 在 11:48 扩容来加速恢复。**这说明恢复时间是可以用钱买到的，但"选错备份"买不到。** 对阙疑而言，**恢复速度不是瓶颈（账本只有几百 KB 到几 MB），"恢复正确性"才是。**

### 二、GitHub 2018-10-21：43 秒网络分区导致 24 小时 11 分钟降级

来源：GitHub 官方 *October 21 post-incident analysis*（2018-10-30 发布）。

**核心数字（逐字）**：

| 项目 | 数字 |
|---|---|
| 触发原因 | 更换故障的 **100G 光模块**，美国东海岸网络枢纽与主数据中心之间连接中断 |
| 中断时长 | **43 秒** |
| 服务降级总时长 | **24 小时 11 分钟** |
| 事故起点 | 2018-10-21 **22:52 UTC** |
| 服务恢复 | 2018-10-22 **23:03 UTC** |
| 单集群未复制写入（最繁忙集群之一） | **954 条** |
| 积压 webhook 事件 | **500 万+** |
| 积压 Pages 构建 | **8 万** |
| 因超过内部 TTL 被丢弃的 webhook 负载 | 约 **20 万** 条 |
| MySQL 备份频率 | 每 **4 小时**一次 |

**数据不一致的精确描述（逐字要点）**：
- 22:52 网络分区后，东海岸的 Orchestrator 依据 **Raft 共识取消领导权**；西海岸与东海岸公有云的节点达成法定人数，**把集群故障转移到西海岸**。
- 连接恢复后，应用层**立即把写流量导向西海岸新主库**。
- **关键问题**：东海岸数据库含有**少量未复制到西海岸的写入**（原文：*"several seconds"* 的写入）。此时两个数据中心**各自都有对方没有的写入** → **无法安全切回东海岸**。
- 到 23:13，西海岸已接收应用写入**近 40 分钟**。
- 示例条数：*"the busiest cluster had **954 writes** in the affected window"*。
- **决策**：GitHub 明确**优先保数据完整性而非缩短故障窗口**，选择 **fail-forward**（向前故障转移）而非切回。
- 结果是应用在东海岸、数据库在西海岸，**跨洲往返延迟**导致服务对多数用户不可用。

**恢复时间线的两个关键难点（逐字）**：
1. **备份恢复耗时**：备份存于远程公有云 blob 存储，传输 + 解压 + 校验 + 准备 + 加载数 TB 数据耗时数小时。**该流程每日测试，但此前从未需要完整从备份重建整个集群。**
2. **恢复估算严重失准**：原按**线性**估算（2 小时），实际复制追赶呈**幂衰减（power decay）**特性，且欧洲/美国用户醒来后写入负载上升，**恢复时间远超预期**。

**四条技术整改（逐字要点）**：
1. 调整 Orchestrator 配置，**防止跨区域提升数据库主库**；
2. 加速迁移到新的状态报告机制（按组件分别展示状态，而非只有绿/黄/红）；
3. 推进**多数据中心 active/active/active** 工程（目标设施级 **N+1 冗余**）；
4. **"更主动地测试假设"** + 投资**故障注入（fault injection）与混沌工程（chaos engineering）**。

**组织整改（逐字）**：*"转变站点可靠性思维：仅靠更严格的运维控制或更快响应不足以保障可靠性。"*

**对阙疑的价值**：这条事故说明**"每日测试的备份流程"也可能在真正需要时失败**（因为测的是"流程能跑"，不是"整集群能重建"）。**阙疑的 `verify_restore.py` 必须测"完整重建"，而不是"文件能拷回来"。**

### 三、Schema 演进的兼容性规则（Confluent 官方逐字）

**四种兼容性类型（逐字）**：
- **BACKWARD**：*"consumers using the new schema can read data written with old schema (add optional fields, remove fields)"*
- **FORWARD**：*"consumers using old schema can read data written with new schema (remove optional fields, add fields)"*
- **FULL**：*"both backward and forward compatible (add/remove optional fields only)"*
- **TRANSITIVE**：*"compatibility checked against all previous versions, not just the last one"*

**默认设置（逐字）**：
> *"The Confluent Schema Registry **default compatibility type is BACKWARD**, not BACKWARD_TRANSITIVE."*
> *"The main reason that BACKWARD compatibility mode is the default, and preferred for Kafka, is so that you can **rewind consumers to the beginning of the topic**. With FORWARD compatibility mode, you aren't guaranteed the ability to read old messages."*

**"rewind to the beginning" 这句话对阙疑是决定性的**：阙疑的独立对账器**必须能从账本第一条开始复算**（否则"第三方可不信任内核地复算判决"就只对最近几条成立）。**因此阙疑需要的兼容性类型是 `BACKWARD_TRANSITIVE` 的等价物——不是"能读上一条"，而是"能读全部历史"。**

**Avro vs Protobuf 的兼容性规则差异（官方表格逐字）**：

| 允许的变更 | Avro BW | Avro FW | Avro Full | Protobuf BW | Protobuf FW | Protobuf Full |
|---|---|---|---|---|---|---|
| 新增可选字段 | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ |
| 删除可选字段 | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ |
| **新增必填字段** | — | — | — | **✔** | — | — |
| **删除必填字段** | — | **✔** | — | — | — | — |
| 新增 union/oneof 变体 | ✔ | ✔ | — | — | — | — |
| 删除 union/oneof 变体 | ✔ | ✔ | — | — | — | — |
| 放宽标量类型 | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ |
| 收窄标量类型 | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ |

（✔ = 兼容；空白 = 不兼容；BW = backward；FW = forward）

**默认值的决定性作用（逐字）**：
> *"In **Avro** and **Protobuf**, you can define fields with default values. In that case, **adding or removing a field with a default value is a fully compatible change**."*
> *"Note that the new field `favorite_color` has the default value 'green'. This allows data encoded with the old schema to be read with the new one... **Had the default value been omitted in the new field, the new schema would not be backward compatible with the old one since it's not clear what value should be assigned to the new field, which is missing in the old data.**"*

**Protobuf 最佳实践（逐字）**：
> *"Note that **best practice for Protobuf is to use BACKWARD_TRANSITIVE**, as adding new message types is not forward compatible."*

**改字段名（重要盲区）**：Confluent 该页**没有给出字段重命名的独立规则条目**。从规则表推断，重命名等价于"删旧字段 + 加新字段"，**在 FULL 兼容下不成立**。**这一点对阙疑很关键**：如果账本条目里的 JSON 字段名要改（例如把 `verdict` 改成 `judgment`），**必须保留旧字段名的读取路径**，或者干脆不改名。

### 四、迁移的工程模式与回滚边界

**Expand-Contract（扩展-收缩）四阶段**（多篇工程博客一致描述，含 appscale.blog 2026-06-26、palakorn.com 2026-03-25、appropri8.com 2025-11-17）：

| 阶段 | 动作 | 回滚难度 |
|---|---|---|
| **1. Expand（扩展）** | 新增列 / 新表，**不动旧结构**；旧代码忽略新列 | **易**（旧列还在，新列只是冗余） |
| **2. Dual-write（双写）** | 新代码同时写新旧两处 | **中**（需确认旧代码能忽略新列） |
| **3. Backfill（回填）** | 批量把旧数据搬到新结构 | **中**（回填可重跑，但需幂等） |
| **4. Contract（收缩）** | 删除旧列 / 旧表 | **不可逆（point of no return）** |

**关键洞察**：**"不可逆"只发生在第 4 阶段。** 因此工程上的纪律是：**把第 4 阶段尽可能往后拖**，让系统在"新旧并存"状态下多跑一段时间，观察是否有遗漏的读取路径。**这条纪律对阙疑的映射非常直接：阙疑的"Contract"阶段就是"删除旧的规则版本"——而这是绝对不该做的**，因为删除旧规则版本会让旧账本条目无法复算。

**数据校验的三个层次（阿里云 LHM 文档逐字，2025-12-15）**：*"It defines three core validation modes: **row count, aggregate metric, and content consistency**."*

**pt-table-checksum 的机制（Percona 官方）**：*"performs an online replication consistency check by executing checksum queries on the master"*，通过**分块计算校验和 → 通过复制同步到从库 → 对比**，在不影响线上负载的前提下发现主从不一致。**这套机制的启发**：**校验要分块、要能在不打断服务的情况下做、要对比的是"聚合值"而不是"逐行内容"**（逐行对比在规模上不可行）。

**对阙疑的映射**：
- **row count** → 账本条目数（452 条）+ 知识卡数（37 实卡 + 10 草稿）；
- **aggregate metric** → **Merkle root**（这是最强的聚合指标，任何一条改动都会改变它）；
- **content consistency** → **逐条判决复算**（n=452，完全可承受）。
- **阙疑的优势**：因为 n 小，**三个层次可以全部做，而且是精确的而非抽样的**。这与"抽样比对"的企业实践形成鲜明对比。

### 五、Knight Capital 2012：与"迁移"相邻的一类事故

虽然 Knight Capital 严格说是**部署事故**而非数据库迁移事故，但其教训高度相关。多方来源一致记载：**2012-08-01**，因部署错误，**一份 2003 年的休眠代码在一台服务器上被激活**，系统在**约 45 分钟内**向市场发送了**数百万笔非预期订单**，造成**约 4.4 亿美元**损失。SEC 于 **2013-10-16** 发布行政处罚令（`sec.gov/files/litigation/admin/2013/34-70694.pdf`），其中描述 Knight 的失误导致其在**约 45 分钟内**累积了"**非预期的数十亿美元证券组合**"。

**对阙疑的映射**：Knight 事故的本质是**"同一份代码在不同服务器上处于不同版本"**——这正是阙疑已存在的硬伤：**工作树 227 项漂移**。**227 项漂移意味着"本机跑出来的判决"与"仓库里的代码"不一定是同一件事**，这在性质上与 Knight 的"八台服务器中七台已更新、一台还是旧版"完全相同。**这是一个必须在论文 Threats to Validity 里主动披露的问题**，而不是等审稿人发现。

## 对阙疑的 3 条具体行动

1. **【2026-11 前】给账本条目加 `rules_manifest_sha256` 与 `schema_version` 两个字段，并写一个"只增不改"的迁移框架。** 具体要求：
   - **字段设计**：每条账本条目（现有 452 条 + 未来新增）必须包含：
     - `schema_version`: 整数，当前为 `1`；
     - `rules_manifest_sha256`: 该次判决所用规则集快照（67 条规则的序列化 + 排序后）的 SHA-256；
     - `engine_commit`: `gate_engine.py` 所在 git commit 的短哈希。
   - **迁移框架 `tools/migrate_ledger.py`**：只允许两种操作——(a) 为**新**条目写新 schema 版本；(b) 为**旧**条目生成"迁移注解"（写成**新的、独立的** sidecar 文件 `ledger/migrations/annotations.jsonl`），**绝不改写旧条目字节**。
   - **验收断言**：在 `tests/test_ledger_immutability.py` 中断言——对任意 `N`，`sha256(ledger[0:N])` 在迁移前后**必须完全相同**。这条断言就是"append-only"的可执行定义。
   - **理由引用**：Confluent 官方 *"Each schema version gets a unique ID and incremented version number. When schemas are updated, Schema Registry checks compatibility before accepting the new version."*

2. **【2026-12 前】实现三层次迁移校验脚本 `tools/verify_migration.py`，并把输出写进 `migration_report.json`。** 三个层次严格对应阿里云 LHM 的官方分类（row count / aggregate metric / content consistency）：
   - **L1 行数**：账本条目数、实卡数、规则数、保护器数四项计数，与迁移前快照逐一比对，**任何差异必须为 0**；
   - **L2 聚合指标**：重算 **Merkle root**，与迁移前 checkpoint 记录值比对；**这是最强的单值校验**（对应 pt-table-checksum 的"分块校验和"思想，但阙疑可以做到全量而非分块）；
   - **L3 内容一致性**：用**独立对账器**逐条复算全部 452 条判决，输出"逐条一致"的计数与不一致条目的完整清单；
   - **输出格式**：`{"l1": {"ledger_entries": 452, "cards_verified": 23, "cards_redteam": 3, "cards_draft": 11, "rules": 67, "protectors": 9}, "l2": {"merkle_root_before": "...", "merkle_root_after": "...", "match": true}, "l3": {"recomputed": 452, "matched": 452, "mismatched": 0}}`。
   - **理由引用**：Resend 事故的第一次恢复失败原因是 *"a wrong selection of the backup timestamp"*——**恢复"跑完了"不等于"恢复对了"，必须有独立校验**。

3. **【2027-01 前】把"227 项工作树漂移"处理成论文的一个显式小节，并在提交前清零。** 具体做法：
   - 在 `research/12_threats_to_validity.md` 增加小节 **`T4_engine_version_drift`**，内容：
     - **陈述事实**：工作树存在 227 项漂移，即"仓库记录的代码状态"与"本机实际运行的代码状态"不一致；
     - **陈述风险**：这与 Knight Capital 2012-08-01 事故的机制同类（*"a deployment error left dormant 2003 code running on a single Knight Capital server"*，SEC 令 `34-70694`，2013-10-16）；
     - **缓解措施**：每条账本条目记录 `engine_commit`（见行动 1），使**任何判决都能追溯到确切的代码版本**；
     - **残余风险**：`engine_commit` 只能证明"声称用了哪个版本"，不能证明"实际用了哪个版本"；**除非在 CI 里从干净 clone 重跑全部 452 条判决并与账本比对**——这条正是行动 2 的 L3。
   - **时间点**：2027-01 前把漂移清零（`git status` 干净）；2027-03 前把 T4 小节写完。**主动披露 227 项漂移比隐瞒更安全**：审稿人一旦自己发现，论文的可信度会整体崩塌。

## 盲区（诚实标注）

- **Resend 事故中"迁移命令为什么误指向生产"的具体机制我没有核实。** 官方只说 *"we performed a database migration command locally, but it incorrectly pointed to the production environment instead"*，**没有说明是环境变量、连接串还是 profile 配置出错**。因此我给出的"教训 A（权限）"是**基于官方整改条款的推断**，不是官方根因分析。
- **Resend 的具体数据量（表数、行数、库大小）我没有核实**，官方报告未给出。
- **GitHub 事故中"954 条未复制写入"的具体集群名与完整统计我没有核实。** 该数字是官方博客举的"最繁忙集群之一"的示例，**不能代表全部集群**。官方原文提到"仍在进行手动对账"，但**没有给出最终对账完成的确切时间或发现的完整不一致条目总数**。
- **GitHub 官方博客说"no user data was lost"，但同一段落说"几秒的数据库写入需手动对账"。** 这两句话的关系我未完全厘清——**"几秒的写入"是否最终全部保留、是否有条目被丢弃，官方未明确**。论文中引用时必须保留这个模糊性。
- **Confluent 官方文档该页没有给出"改字段名"的兼容性规则**（我逐字确认）。我给出的"重命名等价于删+加"是**从规则表推断的，不是官方原文**。
- **Knight Capital 的 4.4 亿美元损失数字来自二手来源**（markethistories.com、regulayer.com、知乎）。我确认了 SEC 处罚令存在（`sec.gov/files/litigation/admin/2013/34-70694.pdf`，2013-10-16），**但未打开 SEC 原文核对具体金额与时间描述**。SEC 摘要提到"multi-billion dollar portfolio"与"approximately [45 minutes]"，与二手来源一致，但**精确数字必须回溯 SEC 令原文**。
- **`pt-table-checksum` 的机制描述来自 Percona 官方文档摘要与中文技术博客**，我**未核实其具体的分块算法、`--chunk-size` 默认值、以及在超大表上的实际耗时**。
- **Expand-Contract 四阶段与"point of no return"的表述来自多篇工程博客**（appscale.blog、palakorn.com、appropri8.com、yihuaxiang.github.io），**均为二手，不是学术文献或数据库厂商官方文档**。该模式在业界是共识，但**没有找到权威的原始出处**（通常追溯到 2010 年代的若干工程演讲）。论文中引用时应写"the widely used expand-contract pattern"，不要伪造学术引用。
- **样本偏差**：本文三起事故全部来自**有专职 SRE 团队的互联网公司**。**没有任何公开事故报告覆盖"单人科研项目"**。因此对阙疑的建议是**类比推理**，不是实测。论文中必须写明这一点。
- **阙疑"227 项漂移"的具体内容我未核实**（是未提交改动、未跟踪文件，还是换行符差异？），只从项目上下文知道这个数字。**不同类型的漂移风险差异很大**（例如换行符差异风险很低，而未提交的规则改动风险很高）。行动 3 要求写 T4 小节时**必须先把 227 项按类型分类**。
