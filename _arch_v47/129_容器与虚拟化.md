# 方向129：容器与虚拟化——从chroot到Kubernetes：四十年隔离演化

## 核心结论

1. **容器不是 Docker 发明的，Docker 做对的是"开发者体验+标准化分发"**。隔离原语的历史链条清晰可考：`chroot(2)` 随 Unix V7 在 1979 年出现；FreeBSD jail 随 4.0 在 2000-03 发布；Linux mount namespace 自 2.4.19（2002）出现，Google 工程师 2006/2007 年发起的 "process containers" 于 2008-01 合入 Linux 2.6.24 并改名 cgroups（初始仅 3 个 CPU 相关控制器）[1][2]。Solomon Hykes 在 PyCon 2013（2013-03-15 演示、03-20 首个版本）发布 Docker[3][4]，把 namespace + cgroups + 分层镜像 + git 式镜像语义打包成"集装箱"，容器才从运维技术变成全民工具。

2. **虚拟机与容器是两种不同的隔离赌注，硬件虚拟化回归后两者正在合流**。KVM 由 Avi Kivity 在 Qumranet 开发，2006-10 合入、随 Linux 2.6.20 在 2007-02 发布，把 Linux 内核本身变成 hypervisor[5]；Xen 出自剑桥，SOSP 2003 论文《Xen and the Art of Virtualization》开创半虚拟化路线[6]。按 Popek–Goldberg（1974）的经典分类，hypervisor 分 I 型（直接运行于硬件，如 Xen/ESXi）与 II 型（运行于宿主 OS 之上，如 KVM 架构定位、VMware Workstation）[7]。容器共享内核、开销毫秒级但隔离弱；VM 隔离强但重。gVisor（2018）与 AWS Firecracker（2018，<125ms 启动、<5MiB 开销）正是填补中间地带的工业答案。

3. **容器逃逸反复证明"容器不是安全边界"，编排与标准化才是生态主战场**。CVE-2019-5736（runc，容器内 root 可借 `/proc/self/exe` 覆盖宿主 runc 二进制获得宿主 root，2019-02-11 披露）[8]与 CVE-2024-21626（runc ≤1.1.11，文件描述符泄漏经 `/proc/self/fd` 逃逸，CVSS 8.6，2024-02 披露）[9]是两个教科书案例。标准与编排侧：Kubernetes 2014-06 开源、1.0 于 2015-07-21 发布[10]；OCI 于 2015-06-22 成立，Docker 捐出镜像规范与 runc[11][4]；分层镜像（layered image）与 OCI 镜像规范成为行业格式[11]。

## 技术全景与关键数字

### 一、cgroups 与 namespaces：容器的两块内核基石

cgroups 决定进程"能用多少"：层级化进程组 + 资源控制器（CPU、内存、I/O、pids 等），经伪文件系统操作；v1 多树设计（每个控制器一棵树）导致归属不一致、委托不安全等问题，cgroup v2 随 Linux 4.5（2016-03）发布，以单一树、自顶向下启用控制器、一致记账重构，Fedora 31（2019）首个默认 v2，Kubernetes 1.25（2022）切换默认[2]。namespaces 决定进程"能看到什么"，内核特性逐个长出来[1][2]：

| 特性 | 内核版本 | 年份 |
|---|---|---|
| Mount namespace | 2.4.19 | 2002 |
| UTS / IPC namespace | 2.6.19 | 2006 |
| PID namespace / cgroups | 2.6.24 | 2008 |
| Network namespace | 2.6.24 起 | 2008–2009 |
| User namespace | 3.8 | 2013 |
| OverlayFS | 3.18 | 2014 |
| cgroup v2 / cgroup namespace | 4.5 / 4.6 | 2016 |
| Time namespace | 5.6 | 2020 |

### 二、Docker：分层镜像、写时复制与启动开销

Docker 镜像由只读层叠加而成，每层对应 Dockerfile 一条指令的文件系统差异，容器启动时在最上加一个可写层（写时复制），因此镜像可复用基础层、构建可缓存[3][11]。Docker 官方口径：容器镜像通常数十 MB，VM 通常数十 GB；容器共享宿主内核故无每应用 OS 开销，启动以秒甚至毫秒计[3]。容器运行时开销接近原生（多组基准约 0–5% 损耗），真正的成本在镜像拉取、解压与首次构建，而非运行时。构建缓存的失效规则必须吃透：一条指令变更会使该层及其后所有层缓存失效，因此 Dockerfile 要按"稳定性排序"——先放工具链安装这类几乎不变的指令，把源码 COPY 放到最后；`COPY` 的缓存键含被复制文件的内容校验和，源码改一行只失效其后的编译层。存储驱动上 overlay2（基于 OverlayFS）是当前默认，aufs/device-mapper 等旧方案已淘汰。容器启动本身主要耗时在镜像解压、层挂载与初始化，而非进程创建——这也是"镜像预热/懒拉取"成为云厂商优化重点的原因。镜像分发侧还有一层工程现实：镜像以层为单位并行拉取、按需解压，热门基础层在节点上可去重共享；合理利用多阶段构建把最终层数压到最少，比换更快的磁盘更能改善冷启动。对评测场景而言，这意味着复现包体积与首次运行耗时都可以通过精简层数主动控制，而不是听任构建工具自由膨胀。

### 三、KVM/Xen 与 I/II 型 hypervisor

Xen 的半虚拟化要求客户机内核配合修改，早期在 x86 无硬件虚拟化扩展时即可接近原生性能；Intel VT-x（2005）、AMD-V 之后全虚拟化成为主流，Xen 3.0（2005）支持 HVM[6]。KVM 借硬件扩展把虚拟化变成 Linux 内核的一组 ioctl，用户态用 QEMU 模拟设备，架构极简、随内核主线进化[5]。I 型与 II 型之分在 KVM 时代已趋于模糊——内核即 hypervisor，VM 只是宿主上的普通进程[7]。VM 级隔离的安全含义：客户机攻击面是 hypervisor 暴露的虚拟硬件，与宿主内核系统调用面物理隔离，因此逃逸通常需要 hypervisor 漏洞（如历年 QEMU/KVM CVE），门槛显著高于容器。

### 四、Kubernetes、OCI 与编排生态

Kubernetes（源自 Google Borg，Borg 论文发表于 EuroSys 2015）以声明式 API 管理容器编排：Pod、Service、声明式 reconcile[10]。声明式模型与脚本式运维的根本区别在于：用户只提交"期望状态"，控制循环持续观测实际状态并向期望状态收敛，节点故障、容器崩溃都由循环自动修复。这套思想对阙疑的间接启发是账本重放也应声明式化——提交"账本+规则版本→期望判决集"，对账器自动找出任何不一致，而不是手工逐条比对。对单机评测而言不需要部署 Kubernetes，但可借用其声明式校验思路写一个轻量对账脚本。OCI 维护两个规范——Image Spec（镜像格式：manifest、layer、digest）与 Runtime Spec（bundle 格式与容器生命周期），runc 是参考实现[11]；containerd 于 2017 年由 Docker 捐给 CNCF，成为事实上的核心容器运行时[4]。标准化的直接收益是镜像跨云可移植，间接收益是复现者可用同一 OCI 镜像在任何机器重建相同环境。

### 五、容器逃逸：两个必须写进教案的案例

CVE-2019-5736：runc init 阶段 `/proc/self/exe` 指向宿主 runc 二进制且该路径在容器命名空间内可见；容器内 root 可在 runc 下次执行时写入其二进制，获宿主 root。缓解：非 root 运行、SELinux、镜像哈希钉死、升级 runc/Docker 18.09.2[8]。CVE-2024-21626（Leaky Vessels）：runc 内部文件描述符（指向宿主 `/sys/fs/cgroup`）泄漏进 init，恶意镜像把工作目录设为 `/proc/self/fd/<n>` 即可进入宿主挂载命名空间，还可覆盖宿主二进制完成完全逃逸；runc 1.1.12 修复，CVSS 8.6（AV:L/AC:L/PR:N/UI:R/S:C/C:H/I:H/A:H），发现者为 Snyk 的 Rory McNamara 等[9]。两者都利用 `/proc` 伪文件系统，教训一致：**容器边界的细节在 init 路径，不在运行路径**。

### 六、安全容器：gVisor 与 Firecracker

gVisor 用用户态 Sentry 拦截系统调用、Gofer 代理文件访问，在容器与宿主内核之间加一层实现内核；Firecracker 在 KVM 上为每个容器/函数提供一个极简 microVM，jailer + seccomp 白名单做纵深，指标 <125 ms 启动、<5 MiB 开销、单机 150 microVM/s，已支撑 AWS Lambda/Fargate[12]。Kata Containers 等项目走类似路线。隔离光谱因此完整：裸容器（快、弱）→ gVisor（中、中）→ microVM（接近 VM 强、毫秒级）。值得记的量化参照还有密度：Firecracker 官方材料称单台 EC2 裸金属主机可承载数千个 microVM，而传统 VM 单机密度通常以个位到两位数计；容器单机密度则可达数百上千。密度差两个数量级的直接后果，就是多租户单位成本与冷启动弹性的本质差异。

## 对阙疑的映射

### 一、承接方向21/22：Docker 真复现是阙疑可执行开放的主干

阙疑目标 NeurIPS 2027 E&D，赛道评审明确按"documented and executable"检验。方向 21 已引用的实测研究表明 Docker 不等于可复现：5298 个曾成功构建的 GitHub Actions 构建两年后仅 72% 可重建，且无一镜像输出哈希相同[方向21]。阙疑的复现策略因此必须是**单镜像、少外部输入、钉 digest**：一个 Dockerfile 固定编译器（GCC/Clang 具体补丁版本）、Python 版本、sanitizer 运行时，复现者 `docker run --network none` 即可重放 452 条账本并核对 Merkle 根。容器在这里不是部署工具，而是**论文的可执行附件**。对外只需要发布 Dockerfile 与锁定文件，镜像 digest 作为"本文所用环境"的唯一指纹写进附录，任何复现偏差都可据此定位。

### 二、评测环境固定：编译器版本与 sanitizer 是实验效度的一部分

阙疑的核心数字（holdout 30 条 17 真错检出 66.7%、corpus 40 条检出 43.8%、变异 core 97.3%/all 81.5%、反事实 P=R=F1=0）全部是特定工具链下的测量。编译器版本变化会直接改变判决：新版本可能修复一个"编译器应拒未拒"的实卡（假阳性消失、检出率下降），也可能引入新警告（假阳性增加）；sanitizer 缺失或版本不同会让 UB 探针漏报（方向 42 已分析）。因此镜像必须把 `gcc/g++`、`clang`、`libasan/libubsan`、`cmake` 全部钉到精确版本，评测日志记录镜像 digest 并写入论文附录。**每一个百分数都要能回答"在哪个镜像里测的"**。还应固定一组容器运行参数：时区与 locale 写死（避免警告文本因 locale 变化而影响基于输出的判决）、`PYTHONHASHSEED=0`、运行期禁网络。这些细节单看琐碎，合起来才是"同一镜像在不同机器产出同一判决"的完整条件。论文附录建议给一张完整的环境清单：发行版快照、内核最低要求、全部工具链补丁版本、镜像 digest 与构建日期，让复现者逐行核对，而不是只看到一个含糊的 "tested on Linux"。

### 三、镜像体积与构建时间：单人项目的真实工程预算

合肥单机、嵌入式方向背景意味着没有 CI 农场。镜像设计要直接控制成本：多阶段构建（builder 阶段装工具链，运行阶段只 COPY 内核与规则），优先 slim 基础镜像；利用分层缓存，规则/账本变更不触发工具链层重建；镜像构建一次、本地复用。粗估预算：含 C++ 工具链的 builder 层数百 MB（属一次性下载），运行镜像可压到百 MB 级；全量 452 条账本重放含编译探针，以分钟计，须在普通笔记本可完成——这是"陌生人愿意复现"的硬门槛。CI 上还需配置缓存避免每次冷构建。更细的时间预算应实测并拆成四段公开：镜像首次拉取、镜像构建、账本重放（其中编译探针占大头）、Merkle 核对；本地开发时后三段是日常成本，投稿前必须把它们压到一顿午饭的时间以内。还可以用编译结果缓存进一步提速——同一探针源码与编译器版本的编译产物可缓存复用，452 条账本中重复模式不少，这一步对反复回归尤其值钱，但要保证缓存键含编译器版本，避免拿旧产物污染新评测。

### 四、双非机器上的资源预算：cgroups 即护栏

编译探针含模板炸弹、fork 炸弹风险（方向128），容器运行时直接用 cgroups v2 参数兜底：`--memory`、`--cpus`、`--pids-limit`、`--timeout`。在个人机器上这些限制同时保护宿主——失控的被检代码不会吃掉写论文的内存。user namespace + 非 root + `--security-opt no-new-privileges` 让 CVE-2019-5736 类攻击面默认关闭。容器逃逸史提示：**永远不在评测容器里挂 `~/.ssh`、仓库凭据或 Docker socket**——挂 socket 等于直接放弃容器边界。

### 五、未来工作：microVM 作为规则生态的隔离升级

若阙疑公开规则征集，可在论文 future work 论证升级路径：每个不可信规则在 Firecracker microVM 中执行（125ms 启动、5MiB 开销对单机小批量可行），或整体跑在 gVisor 容器中。这把"沙箱被突破"从宿主级灾难降为 VM 逃逸问题。对 0 影响力起点的作者，更现实的价值是：**容器化让系统证据与个人身份脱钩**——审稿人评估的是自包含镜像里的 452 条账本与判决逻辑，而不是作者的头衔。还应补充一条长期纪律：镜像与账本一样需要归档冗余。方向 21 引用的实测显示，3620 个历史镜像中 2079 个在分析时已无法从注册表取回，因此钉死 digest 之外，还要把镜像 tar 包随论文附件或 Zenodo 长期保存并取 DOI；只依赖 Docker Hub 的默认保留策略，等于把复现命门交给第三方。容器层数据（层哈希、构建时间戳）同样建议设置 SOURCE_DATE_EPOCH 以缩小逐位差异。

## 对阙疑的三条具体行动

1. **固化评测镜像并写入复现命令（2026-11 前，对齐方向21/22行动）**：完成多阶段 Dockerfile，工具链版本全部 `=` 钉死并 `--network none` 验证运行段；在 README 提供一键命令重放 452 账本并比对 Merkle 根；记录 digest 至论文附录。
2. **镜像内回归核心指标（2027-02 前）**：在固定镜像中重跑 holdout 30 条（核对 66.7%）、corpus 40 条（核对 43.8%）、变异 core/all（核对 97.3%/81.5%）、反事实集（核对 P=R=F1=0），任何指标与历史值不一致即排查工具链漂移，结果以表格进论文。
3. **建立资源限制与逃逸面基线（2027-03 前）**：评测容器统一非 root、内存/CPU/pids 限制、不挂敏感目录与 socket；增加一个"容器内试图取 Docker socket/SSH key 即失败"的自检探针，并在 threat model 中引用 CVE-2019-5736 与 CVE-2024-21626 论证配置合理性。

## 盲区

- 容器运行时"0–5% 开销"为多组基准的大致共识，未指定单一来源精确数字；系统调用密集型与网络密集型负载差异大，论文引用需选原文。
- cgroups 初始"3 个 CPU 控制器"依据 Kerrisk 幻灯片，具体控制器名未在本文展开；内核版本年份按发布月推算。
- I/II 型分类在 KVM 语境下学界已有争议（有人称其本质 I 型），本文沿用经典教科书表述并指出模糊化趋势。
- 镜像体积"数百 MB/百 MB 级"为量级估计，未实测阙疑镜像；真实值取决于所选基础镜像与工具链。
- Kubernetes 版本演进、PodSecurityPolicy 废弃（1.25）等细节未覆盖，本文只取与评测环境相关的最小集。
- gVisor 性能与 Firecracker 在 Windows/macOS 桌面端的可用性未验证（Firecracker 仅 Linux/KVM），桌面复现者仍依赖 Docker。
