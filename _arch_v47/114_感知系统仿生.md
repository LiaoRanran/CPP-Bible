# 方向114：感知系统仿生——从感知、融合、注意到反馈的可审计 C++ 验证回路

## 一、核心命题：仿生感知不是“多接几个传感器”，而是把感知变成有目标、有记忆、可反馈的闭环

感知系统仿生最容易被误写成“模仿眼睛、耳朵和皮肤”，然后堆叠视觉模型、音频模型和触觉模型；这会把仿生学降格为传感器清单。更有用的抽象是：生物感知系统持续接收不完整、有噪声、时延不一致的输入，先在局部通道形成候选表征，再依据任务和注意资源选择信息，随后融合多源证据，产生带不确定性的内部状态，最后通过行动改变下一轮输入。也就是“感知—融合—注意—反馈”的循环，而非一次性分类器。主动视觉研究将主动感知定义为系统为了特定目标或不确定性，通过 sensing and action 动态改变行为；它可以改变注意区域、移动传感器、交互物体，以取得更有信息量的数据。[1] 这个定义很适合阙疑：系统不应假装从一条文档片段直接得到确定结论，而应回答“当前证据足够吗”“冲突在哪里”“下一步应读取哪一个 C++ 标准条款、头文件、示例或测试”。

视觉、听觉、触觉三个通道可以对应三种不同的证据性质。视觉适合捕捉代码文本、API 名称、控制流结构和文档中的显式条件，但容易受到版本、平台和上下文遮挡影响；听觉仿生在这里可抽象成时间节律和事件流，关注编译器输出、测试失败、运行时日志、警告序列的时间关系，而不是把文本机械地当作另一种视觉输入；触觉仿生则对应“接触式验证”，例如真正编译一个最小程序、运行一个单元测试、改变编译选项、观察 `std::variant` 是否进入 `valueless_by_exception`，或验证 ROS 2 的 QoS 不兼容是否导致消息根本不传递。视觉是远距观察，听觉是时间事件，触觉是行动后的反作用；三者不能简单平均，否则会把高质量的可执行证据稀释成普通文本相似度。

阙疑当前的真实锚点是 37 张实卡、67 条规则、9 个保护器、452 条账本和 3826 行内核；盲 holdout 30 条中真错 17 条、检出率 66.7%，外部 corpus 40 条的检出率为 43.8%，变异测试 core 为 97.3%、all 为 81.5%，反事实 P=R=F1=0。这些数字不应被包装成“系统已经理解 C++”，而应被当作感知闭环的初始校准：内核的规则输出是一个候选感知，账本是带来源的感觉痕迹，独立对账器和实际编译/测试是触觉反馈，holdout 与 corpus 的差异是分布变化，反事实失败则说明系统还没有把“如果证据改变，判决是否随之改变”变成稳定的反馈通道。方向 114 的主张因此限定为：仿生感知可以帮助阙疑把“看到一个说法”改造成“发现证据、评估证据质量、主动补证、融合冲突、延迟或升级判决”，但不能声称它解决了 C++ 真值的不可判定部分。

## 二、从 C++ 文档和代码提取证据：把每次“看见”变成带位置、时间、版本和可复算动作的感知事件

阙疑的输入不应只是 `claim: string` 和 `verdict: string`。应把 C++ 文档/代码的观察结果规范化为 `Observation`，最小字段包括：`observation_id`、`claim_id`、`modality`（`text`、`code`、`build`、`test`、`runtime`）、`source_url_or_path`、`source_revision`、`language_version`、`compiler_id`、`file_span`、`symbol`、`timestamp`、`extractor_version`、`raw_hash`、`normalized_hash`、`support`、`refute`、`unknown`、`quality`、`dependencies` 和 `action_taken`。其中 `file_span` 至少含文件、起止行和抽取器；若是网页文档，记录 URL、页面标题、访问时间和段落定位；若是代码运行，记录编译命令、退出码、标准输出/错误输出摘要、测试名称和环境哈希。这样“cppreference 说 `std::variant` 是类型安全联合体”与“本地最小程序确实能按类型访问并在错误访问时抛出 `std::bad_variant_access`”不会被混成同一强度的证据。

已有 C++ 文档可提供很清晰的感知接口。`std::variant` 的官方参考说明它在正常情况下持有一个备选类型，同时存在 `valueless_by_exception()` 这一实现层无值状态；`std::visit` 根据当前状态分派访问器。[6] 因此四态证据不能直接写成一个模糊整数，而可用 `enum class EvidenceState { neither, supported, refuted, both };`，或者在不同状态带有不同载荷时使用 `std::variant<Neither, Supported, Refuted, Both>`。必须把业务上的 `neither` 与运行时 `valueless_by_exception` 分开，否则“对象损坏”会被错误解释成“没有证据”。C++23 的 `std::expected<T,E>` 又给出另一种重要接口语义：成功值 `T` 与明确错误 `E` 二选一，调用者可以通过 `has_value()`、`error()`、`and_then` 和 `transform` 显式传播失败。[7] 在阙疑中，解析文档失败、编译环境缺失、超时、版本不匹配都不应被静默降级为 `draft`；它们应成为带错误码的 `expected` 结果，并进入证据账本。

代码证据还应包含并发和时间语义。C++ 内存模型以字节和内存位置描述对象存储，连续位域可能共享同一内存位置；这意味着多传感器式的并发采集若把多个标志压进位域，不能仅凭字段名推断它们可以独立更新。[8] 对阙疑而言，抽取器、编译器、测试器和账本写入器可能并发运行，必须记录 `event_id`、单调时间戳、输入哈希和提交顺序，并用明确的队列或同步协议生成快照。ROS 2 官方文档对 sensor data profile 的设计取向是及时拿到最新样本，通常采用 best effort 和较小队列；同时 QoS 的 reliability、history、depth、deadline、lifespan、liveliness 等策略可能导致连接不兼容或消息过期。[4] 这正好对应证据流的“听觉/时间通道”：一条证据缺失可能不是反驳，而是传输质量、截止时间或版本不兼容导致的观测缺失。任何提取器都应把“未观察到”与“观察到不成立”分开编码。

可执行的证据结构可以写成如下伪 C++：

```cpp
struct EvidenceEvent {
    std::string claim_id;
    std::string modality;          // text, code, build, test, runtime
    std::string source_ref;        // URL or repository path
    std::string revision;
    std::string span;
    std::string raw_hash;
    std::string extractor_version;
    std::chrono::steady_clock::time_point observed_at;
    EvidenceState state;
    double reliability;             // 仅作融合权重，不直接等于概率
    std::vector<std::string> causes;
};

std::expected<EvidenceEvent, ExtractError>
extract_cpp_evidence(const Claim& claim, const Source& source);
```

这里 `reliability` 不能伪装成校准概率；它只是证据质量或传感器可信度的工程权重。每个事件还要能反向指向原始文档片段、代码行、命令和产物哈希，确保“为什么判成 warn”可以被另一段程序重放。

## 三、证据融合与不确定性：用一致的状态代数承认冲突，而不是用平均数掩盖冲突

感知融合至少有三层。第一层是时间和空间对齐：不同来源必须先检查版本、时间戳、标准模式、编译器和上下文是否兼容；ROS 2 `ApproximateTimeSynchronizer` 的官方 C++ 教程说明，多条消息可以在允许的时间窗口内近似同步。[5] 这给阙疑一个直接启发：同一断言的文档解释、头文件声明、示例代码和编译结果，不能因“差不多同时出现”就自动绑定，必须有 `sync_window`、`context_key` 和 `revision`。第二层是通道内聚合，例如同一 C++ API 的多个文档段落、同一符号的多个实现和多个测试结果先各自汇总。第三层才是跨通道融合，把文本、代码、构建、运行时和外部规范的证据组合成对断言的支持、反驳、未知或冲突。

概率滤波可以作为连续状态估计的参考，但不能被直接当成阙疑四态判决。OpenCV 的 `cv::KalmanFilter` 文档把流程明确分成 `predict()` 和 `correct(measurement)`，并公开 `statePre`、`statePost`、`errorCovPre`、`errorCovPost`、`measurementNoiseCov` 和 `processNoiseCov` 等状态与协方差字段。[3] 对阙疑而言，`predict` 对应在尚无新文档/代码证据时依据已有规则维持一个候选判决，`correct` 对应新证据到达后的更新；`errorCovPre/post` 的类比是当前不确定性，而不是“正确率”。若文本证据与编译实验相冲突，不能用一个高斯平均把冲突抹平；应把冲突提升为可审计状态，并要求主动感知补充证据。

Dempster–Shafer 类证据理论提供了另一个有用但必须谨慎的视角：证据可以分配给单个假设，也可以保留给一个假设集合，从而区分“我不知道”与“我认为两者同样可能”。但高冲突证据下，朴素 Dempster 组合会出现归一化敏感性，因此本项目不应直接宣称某个融合公式天然正确。工程上可先采用透明的四态计数与冲突字段：`support_sources`、`refute_sources`、`unknown_sources`、`conflict_mass`、`independence_group`、`fusion_rule_version`。只有在独立性、来源相关性和冲突处理策略都写入实验协议后，才可比较加权计数、Dempster-Shafer、贝叶斯更新或规则优先级。融合输出至少应是 `(state, reasons, uncertainty, missing_evidence)`，而不是单个分数。

四态判决可借用 Belnap FOUR 的双序思想，但不要把现有业务命名强行改成理论术语。信息序表达“证据多少”：`draft` 或 `neither` 是没有支持/反驳信息，`verified` 是支持，`block` 是反驳，`both` 是两边都支持；真值序表达“倾向成立还是不成立”。方向 52 已经指出，`Both` 不是装饰，而是多个可能互相矛盾来源下的自然状态；其工程意义是“冲突被保留”，而不是“冲突被随机裁决”。如果阙疑对外仍保留 `verified / advice / warn / block`，建议内部另外存储 `support_bit`、`refute_bit`、`information_level` 与 `action_level`，不要声称四个标签本身就是标准 FOUR。每次融合都输出一条证明链：输入证据 ID 列表、冲突对、运算顺序、规则版本和最终状态；对相关来源的重复引用应按 `independence_group` 去重，避免一篇复制同一标准文本的网页被算成多条独立证据。

不确定性应分为至少四类：观测不确定性（传感器噪声、文本截断、编译失败）、模型不确定性（规则未覆盖、未知 C++ 版本）、冲突不确定性（支持与反驳同时存在）和分布不确定性（holdout 与外部 corpus 不同）。NIST 的测量不确定度页面把不确定度评估拆成基本定义、分量评估、分量合成、扩展不确定度和覆盖因子，并提供 GUM 相关计算工具。[10] 阙疑可以借用这种“预算表”形式，但不能把四态硬套成连续测量误差：报告应列出每个缺口的来源、影响方向、是否可通过行动减少，以及减少它所需的成本。已有方向 50 的结论也必须保留：ECE 需要概率输出，阙疑的四态不是概率向量，因此不能随意给标签造概率再报 ECE；比例检出率用 Clopper–Pearson，共形集合另行承担覆盖率声明，二者不能混淆。

## 四、注意与反馈：让系统主动寻找最能改变判决的下一条 C++ 证据

仿生注意不是“把重要文本加粗”，而是有限预算下的证据选择策略。对每条 claim，系统应维护 `attention_score`，但这个分数必须由可解释因素组成：当前冲突质量、判决边界距离、证据缺口的可验证性、来源可靠性、预计读取/编译成本、对下游卡片的依赖数和安全代价。一个简单优先级可写为：`priority = conflict_mass * downstream_impact * actionability / (cost + epsilon)`。如果文本声明与标准文档一致但没有代码证据，应优先运行最小编译；如果代码能编译但解释依赖某个模板约束，应优先读取对应标准条款；如果两个版本的 cppreference 或仓库代码冲突，应先固定版本和 `source_revision`，而不是立即更新判决。

主动感知的动作集合应限制在可回放的动作：`read_span` 读取指定文档行段；`resolve_symbol` 解析头文件和命名空间；`compile_probe` 编译一个最小 C++ 程序；`run_test` 执行指定测试；`change_standard` 在 C++17/C++20/C++23 下重跑；`change_compiler` 只在环境白名单内切换；`inspect_log` 读取标准输出、错误输出和 sanitizer 结果；`request_human_review` 在冲突无法自动消解时升级。每个动作都产生新的 `EvidenceEvent`，并写入 `action_parent_id`，这样可以回答“系统为什么去读这一段、这次行动是否降低了不确定性”。“主动”不等于无限尝试；达到预算、重复证据、冲突无法下降或风险超过阈值时，应停止并输出 `inconclusive`/`draft`，而不是伪造确定结论。

反馈分三种。正反馈是新证据强化原有判决，例如标准条款、实现代码和编译实验同向；负反馈是新证据削弱判决，例如最小程序在声明的标准版本下失败；结构反馈是证据链本身异常，例如依赖环、重复来源、时间戳倒序、QoS 不兼容或编译器版本漂移。对阙疑最重要的是结构反馈：它不直接说 C++ 命题真/假，却能指出当前判决不能被信任。反馈更新不能覆盖旧账本记录，只能追加一个新的事件，保留 `previous_verdict_hash`、`new_verdict` 和 `delta_reason`。这样 452 条账本继续是 append-only 证据，而不是被新模型静默重写的缓存。

四态判决的可执行规则可以先采用保守版本：`verified` 需要至少一条高质量、版本匹配且可执行的支持证据，并且没有未解决的高质量反证；`block` 需要一条高质量可复现反证，或多个独立来源共同指出违反标准/测试不通过；`advice` 表示证据支持方向明确但尚缺执行验证；`warn` 表示存在冲突、版本敏感性或高影响缺口；`draft` 表示信息不足。若已有内核只接受四态，则把 `warn` 的 `conflict_mass > 0` 作为必填原因，禁止把冲突压成 `advice`。若未来引入 `Both`，应通过版本化迁移并在账本中保留双向映射，不得让旧记录含义悄然改变。

反馈实验必须测“注意是否真的有用”，而不只是测最后的准确率。对每一条 claim 记录首次判决、动作序列、每步新增证据、冲突质量、信息缺口数、最终判决、总成本、延迟和是否需要人工。指标包括：单位成本带来的不确定性下降、首次动作命中高价值证据的比例、冲突发现率、错误升级率、重复读取率、反事实敏感性和判决稳定性。可以把“随机读取”“固定优先级”“冲突/影响驱动注意”三种策略进行配对比较；在 30 条 holdout 和 40 条 corpus 上分别报告原始计数及 Clopper–Pearson 区间，不把小样本上的偶然改善写成泛化定律。

## 五、对阙疑的落地方案、实验、来源与盲区：先做可复算闭环，再谈更强的仿生模型

建议分三步执行。第一步是建立证据事件格式和独立重放器：实现 `EvidenceEvent` 的 JSONL 序列化，所有事件必须有 `claim_id`、来源引用、版本、位置、模态、原始哈希、支持/反驳/未知位、质量、父动作和融合规则版本；写一个不依赖内核的 `evidence_replay`，输入同一 JSONL 时重新计算每条融合结果、冲突对和四态判决。验收标准是同一账本的事件数、哈希和判决链逐项一致；任何字段缺失只能输出结构错误，不能默认为未知。第二步是实现三类主动动作：文档片段读取、最小 C++ 编译探针、指定测试重放。每次动作固定命令、编译器、标准版本、环境哈希和退出码，并把 `std::variant`、`std::expected`、`cv::KalmanFilter`、ROS 2 QoS/时间同步各做一个最小样例，形成视觉文本、触觉执行、听觉事件三个通道的基准卡。第三步才比较融合策略：基线为安全的支持/反驳计数，实验组为质量加权、冲突保留的双序状态和信息增益注意；任何实验组若不能保留原始证据链，不得进入主结果。

建议至少做四个实验。实验 A 是“单模态到多模态”：从 C++ 官方文档片段、头文件/示例代码、编译探针、运行测试四种来源构造同一批 claim，逐步开放来源，记录 `verified/advice/warn/block/draft` 的转移矩阵、冲突质量、延迟和成本；预期不是每加一个通道准确率都上升，而是识别哪些通道提供互补证据。实验 B 是“冲突注入”：对标准版本、函数签名、异常语义、QoS 可靠性、时间同步窗口和代码实现故意注入一条互斥证据，比较计数平均、优先级覆盖和冲突保留三种融合；验收要求是注入冲突时不能仍输出 `verified`，并能列出冲突来源与最小修复动作。实验 C 是“主动注意”：将随机读取、按静态依赖读取、按冲突×下游影响读取三策略在同一 claim 集上运行，比较每减少一个未决缺口所需的动作数、编译次数、人工升级次数和总延迟；同时做预算截断，证明系统在预算不足时诚实输出 `draft/warn`。实验 D 是“反事实反馈”：把一条支持文档替换为旧版本、删除一条关键测试、改变编译标准或反转一条规则前提，检查判决是否沿证据链改变；方向 brief 中反事实 P=R=F1=0，因此该实验应作为优先修复项，而不是只报告已有变异测试 97.3% 的好成绩。

对阙疑的三条具体行动是：其一，在 2026-12 前完成 `EvidenceEvent`、JSONL 账本和独立 replay，先覆盖 20 张 C++ 断言卡；验收为每张卡能从来源 URL/路径跳到位置、从事件跳到动作、从动作跳到原始输出，且内核与对账器结果一致。其二，在 2027-02 前完成“冲突保留 + 主动注意”最小实现，加入 `conflict_mass`、`missing_evidence`、`attention_score`、`action_cost`、`fusion_rule_version` 五个字段，并对 30 条 holdout 做三策略配对实验；报告原始四元组、每步成本和区间，禁止只报一个总准确率。其三，在 2027-04 前把视觉/听觉/触觉类比落到三个可运行通道：文档读取、编译/测试触觉、日志/时序听觉；用 `std::expected` 明确失败，用 `std::variant` 或状态枚举表达四态，用 OpenCV/ROS 2 文档中的预测-校正、QoS、近似同步概念作为外部对照，但不声称阙疑实现了生物神经系统。

盲区必须诚实写清：第一，现有 37 张实卡、67 条规则和 452 条账本的真实字段、四态确切命名、依赖关系和源码位置没有在本次 brief 中完整展开，因此上文的 `verified/advice/warn/block/draft` 是接口建议，不是对现有枚举的事实断言；落地前必须读仓库真实 schema。第二，视觉—听觉整合研究的样本和任务结论不能直接外推到 C++ 知识验证；主动视觉综述是范式启发，不是阙疑效果证据。第三，Kalman、Dempster-Shafer、Belnap 双格和信息增益的数学假设不同，不能因为都叫“融合”就互换；尤其证据来源常常相关，简单相加会重复计权。第四，C++ 文档页面是外部证据，不等于标准原文；网页版本、实现版本、编译器行为和本地代码可能不一致，必须记录 revision 并做触觉验证。第五，样本量只有 30/40 级别，任何主动注意收益都应作为探索性结果，配合原始计数、精确区间和失败案例，不能据此宣称生物启发模型普遍优于规则系统。
