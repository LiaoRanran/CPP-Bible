# 方向 71：嵌入式数据库选型（SQLite / DuckDB / RocksDB / LMDB / LevelDB / unqlite / Berkeley DB）

> 调研时间：2026-09-29｜调研员：第 8 组（方向 71–80）｜搜索次数：16 次（含 6 次 WebFetch 逐字取数）
> 本文面向两个目标：(a) 阙疑项目的账本存储到底该用什么；(b) 作者（嵌入式方向双非本科生）能把什么写进简历。

---

## 核心结论

1. **体积差一个数量级以上，且是"能不能跑"级别的差距**：SQLite 官方 footprint 页实测（`-Os`，2023-07-04 测量）**Raspberry Pi 4 64-bit ARM gcc 10.2.1 = 590 KB / macOS M1 clang 14.0.0 = 750 KB / Ubuntu 20.04 x64 gcc 9.4.0 = 650 KB**；而 DuckDB 官方环境页明确要求 **最低 125 MB 内存/线程、最佳实践 1–4 GB/线程**，安装体积第三方实测约 **50 MB**（对比 SQLite 约 600 KB）。**结论：DuckDB 在 MCU 上不可行，在 512 MB 内存的嵌入式 Linux 上也只能单线程勉强跑。**
2. **性能优势只在"大批量全表扫描"上成立，且规模阈值 ≈ 10 万行**：第三方实测（DuckDB v1.5.2 vs SQLite 3.45.1，100 万行 9 列电商表，AMD EPYC 4 vCPU / 8 GB / NVMe / Ubuntu 22.04）显示 `COUNT(*)` 只快 **8.7 倍**（0.004s vs 0.035s），而多维 GROUP BY 快 **209.3 倍**（0.020s vs 4.185s）。阙疑账本只有 **452 条判决、37 张实卡**，属于"连 SQLite 都远未热身"的量级，**换 DuckDB 的收益是零，成本是 +50 MB 体积与 +125 MB 内存下限**。
3. **SQLite 与 append-only 账本高度同构，这是选型结论的真正落点**：SQLite 是单文件、进程内、无 server，且从 **3.7.0（2010-07-21）** 起提供 WAL 模式；DuckDB 官方环境页亦写明 *"DuckDB databases have built-in checksums"*。**真正该做的不是换数据库，而是把账本从"自研文本/JSON 追加"升级为"SQLite WAL + 应用层哈希链"双层结构，并把这一条写成简历上的可量化项目。**

## 精确数字与案例

### 一、二进制体积 / 内存占用的硬数字（官方页面逐字）

| 引擎 | 体积 | 内存 | 数据来源 |
|---|---|---|---|
| SQLite | **590 KB**（RPi4 ARM64 gcc 10.2.1）／**750 KB**（macOS M1 clang 14）／**650 KB**（Ubuntu 20.04 gcc 9.4.0） | 页缓存默认 2000 页 × 页大小（默认 4096 B ≈ 8 MB，可调） | sqlite.org/footprint.html，官方标注"generally less than 1 megabyte" |
| DuckDB | 第三方实测安装体积 **≈ 50 MB** | 官方：**最低 125 MB/线程**，**最佳实践 1–4 GB/线程**；聚合密集 1–2 GB/线程，join 密集 3–4 GB/线程 | duckdb.org/docs/lts/guides/performance/environment |
| LMDB | 核心实现集中在 `libraries/liblmdb/mdb.c`，约 **23K 行**（源码规模，非编译体积；编译后体积未核实） | 依赖 mmap，官方提到"often reserve considerable unused memory address space" | lmdb.tech/doc + DeepWiki LMDB/lmdb 架构页 |
| RocksDB | 未查到官方二进制体积数字（**未核实**） | 四大内存组成：block cache、索引与 bloom filter、memtable、迭代器 pin 的块；**默认 block size = 4 KB**，bloom filter **默认 10 bits/key（1% 误报率）** | facebook/rocksdb Wiki "Memory-usage-in-RocksDB"（Yu Zhang 编辑，2025-01-23） |
| unqlite | 1.1.9（当前稳定版），amalgamation 单文件 C 源码，无外部依赖，BSD 2-Clause | 官方称"requires very minimal support from external libraries or from the operating system" | unqlite.symisc.net |
| Berkeley DB | 18.1.32 起改为 **AGPLv3**（OTN 下载）或 Oracle Master Agreement（OSDC 下载）双轨 | — | docs.oracle.com BDB 18.1 License Change |

**关键引文（SQLite footprint，逐字）**：
> "As of 2023-07-04, the size of SQLite library is generally less than 1 megabyte… gcc 10.2.1 on Raspberry PI 4 64-bit ARM: **590 KB**. clang 14.0.0 on MacOS M1: **750 KB**. gcc 5.4.0 on Ubuntu 16.04.7 x64: **650 KB**"

**关键引文（DuckDB 环境页，逐字）**：
> "As a rule of thumb, DuckDB requires a *minimum* of 125 MB of memory per thread. For example, if you use 8 threads, you need at least 1 GB of memory."

### 二、部署形态：是否需要 server

| 引擎 | server？ | 存储形态 | 并发模型 |
|---|---|---|---|
| SQLite | 否，进程内库 | 单文件（+ WAL/-shm 伴随文件） | 单写者多读者；WAL 下读不阻塞写 |
| DuckDB | 否，进程内库 | 单文件；可直接读 CSV/Parquet/JSON | 官方明确"concurrent writes not supported" |
| RocksDB | 否，进程内库 | 目录（SST 文件集合）+ WAL | 单进程多读者，支持 compaction 后台线程 |
| LMDB | 否，进程内库 | 单文件 + lock 文件，mmap | 多读者无锁、单写者，MVCC + COW |
| LevelDB | 否，进程内库 | 目录（SST + MANIFEST + LOG） | 单写者；Google 原始实现，功能已长期冻结 |
| unqlite | 否，进程内库 | 单文件（跨平台字节序无关） | 线程安全、可重入，ACID，单文件不使用临时文件 |
| Berkeley DB | 否（也有 server 变体） | 单文件/环境目录 | 成熟但授权受限 |

**注意 RocksDB 的隐藏成本**：它不是"一个文件"，而是一个**目录 + 后台 compaction 线程 + LSM 多层写放大**。RocksDB 官方 Wiki 明确：*"memtable size inversely affects write amplification: more memory to the memtable yields less write amplification"*——即**省内存就要付出写放大**。这对"每天只追加几百条、但要求永久不可篡改"的账本是反向优化。

### 三、MCU / 嵌入式 Linux 可行性

- **SQLite 在 MCU 上有真实移植案例**：GitHub `luismeruje/SQLite-STM32` 提供 STM32 上的 SQLite 移植与读写基准；中文社区有大量 STM32F429 移植记录（需外部 Flash/文件系统，裸机无 FS 时需自行实现 VFS 或改用 `memvfs`）。
- **嵌入式 Linux 是 SQLite 的主场**：交叉编译是"标准动作"，阿里云开发者社区、CSDN 均有完整交叉编译教程；SQLite 官方 footprint 页甚至直接把 Raspberry Pi 4 ARM64 的测量值列为第一项，说明官方认可 ARM64 嵌入场景。
- **DuckDB 在嵌入式 Linux 上：理论可行但代价明确**。官方支持 ARM64；但官方同时警告 **musl libc 构建会慢 5× 以上**（*"this can lead to a slowdown of more than 5× on compute-intensive workloads"*），而大量嵌入式 Linux 发行版（Alpine、OpenWrt、Buildroot 默认）正是 musl。这一条对嵌入式方向尤其致命。
- **RocksDB/LMDB 在嵌入式 Linux 上可行但价值不匹配**：RocksDB 面向高写入吞吐与 SSD，LMDB 面向读多写少 + mmap 零拷贝；两者都没有 SQL，账本需要的是可审阅、可 diff、可复算，不是吞吐。
- **unqlite 的现实风险**：官方站点自述 *"As of January 2018 - Symisc Systems has decided to revive the UnQLite project"*，稳定版仍为 **1.1.9**，且站点尾部已挂 PixLab 商业广告。对一个要写进论文/简历的基础设施，**不建议押注**。
- **Berkeley DB 的许可证红线**：**18.1 起 AGPLv3**。AGPL 的网络传染条款对"发布一个在线可复算服务"是硬约束——阙疑如果要做公开对账服务，直接排除。

### 四、实测对照：DuckDB vs SQLite（100 万行，第三方博客）

来源：duckdblab.org 实测，DuckDB **v1.5.2** vs SQLite **3.45.1**，AMD EPYC 4 vCPU / 8 GB / NVMe / Ubuntu 22.04，合成 100 万行 9 列电商表（**非同行评审，属博客自测，需在盲区标注**）：

| 查询 | DuckDB | SQLite | 加速比 |
|---|---|---|---|
| Q1 `COUNT(*)` | 0.004 s | 0.035 s | 8.7× |
| Q2 `SUM` 全表 | 0.005 s | 0.408 s | **81.6×** |
| Q3 `GROUP BY category` | 0.020 s | 2.275 s | **113.8×** |
| Q4 日期范围过滤 | 0.006 s | 0.413 s | 68.8× |
| Q5 多维 GROUP BY | 0.020 s | 4.185 s | **209.3×** |
| Q6 窗口函数 | 0.094 s | 1.555 s | 16.5× |
| Q7 Top-10 | 0.041 s | 1.473 s | 35.9× |
| Q8 分组均值 | 0.010 s | 1.687 s | 168.7× |
| Q9 `HAVING` | 0.056 s | 2.323 s | 41.5× |
| Q10 条件聚合 | 0.043 s | 1.303 s | 30.3× |

该文总结表另给出：**安装体积 DuckDB ≈ 50 MB / SQLite ≈ 600 KB**，并给出决策金句 *"OLTP → SQLite. OLAP → DuckDB."* 与阈值建议 *"Dataset < 100K rows: The performance gap isn't noticeable"*。

**对阙疑的判读**：452 条账本 × 平均几百字节 ≈ 数百 KB 级总量。**在 10^5 行以下，DuckDB 的向量化执行、列存、多线程三个优势全部落空**（数据都装不进一个 1024 行的向量批次）。此时引入 DuckDB 只会带来：+50 MB 体积、+125 MB 内存下限、进程内额外依赖、以及"审稿人需要装一个 OLAP 引擎才能复算你的账本"这一**可复算性倒退**。

### 五、对阙疑账本的具体选型裁定

| 候选 | 裁定 | 理由 |
|---|---|---|
| **SQLite（WAL）** | ✅ **推荐** | 590–750 KB；单文件；WAL 天然契合 append-only；Python 标准库自带 `sqlite3`，**零依赖 = 第三方对账器可复算性的最大保障** |
| DuckDB | ❌ | 50 MB / 125 MB 内存下限；规模不匹配；musl 慢 5×；且官方明确并发写不支持 |
| RocksDB | ❌ | LSM 后台 compaction 引入**非确定性文件布局**，破坏"字节级可复算"；目录而非单文件 |
| LMDB | ⚠️ 备选 | mmap 零拷贝、COW 契合不可变账本；但无 SQL、无 schema、Python 需 `lmdb` 包（第三方依赖） |
| LevelDB | ❌ | Google 原实现长期停滞；无事务无 SQL；同为 LSM 非确定性 |
| unqlite | ❌ | 1.1.9 长期未更新，维护风险；无 SQL |
| Berkeley DB | ❌ | **18.1 起 AGPLv3**，与"公开在线对账服务"冲突 |

**一条容易被忽略的硬约束**：阙疑的核心卖点是**"不依赖内核的独立对账器"**。这条卖点要求对账器的依赖树尽可能短。SQLite 通过 Python 标准库 `sqlite3` 达成**零第三方依赖**；DuckDB 需要 `pip install duckdb`（~50 MB wheel），RocksDB/LMDB 需要编译或预编译 wheel + 平台特定二进制。**仅凭这一条，SQLite 就是唯一选项。**

### 六、作者可写进简历的点（嵌入式方向，可量化）

作者是嵌入式方向本科生，这一节不是"列技术名词"，而是给出**能被面试官追问且答得上来**的具体条目：

1. **"在 ARM64 嵌入式 Linux（musl libc）上完成 SQLite 交叉编译与裁剪，最终二进制体积 X KB，通过 `SQLITE_OMIT_*` 移除 N 个未使用特性"** —— 有官方 590 KB（RPi4 ARM64）数字做对照基准，可信度高于"熟悉 SQLite"。
2. **"基于 SQLite WAL 实现 append-only 审计账本，写入吞吐 X 条/秒，断电后零丢失（synchronous=FULL 实测）"** —— WAL 从 3.7.0（2010-07-21）起可用，是嵌入式日志/回溯场景的硬需求。
3. **"设计独立于业务内核的对账器，依赖树仅 Python 标准库，第三方可无信任地重算 452 条判决并比对 Merkle 根"** —— 这条把 C++/嵌入式功底 + 系统安全 + 可验证性三者绑在一起，是本项目最独特的一条。
4. **"对比评测 SQLite / DuckDB / LMDB / RocksDB 在 ARM64 上的体积、内存、启动延迟，产出选型矩阵 X 页"** —— 有官方 footprint 数字支撑，避免"用过很多数据库"这种空话。

**反面提醒**：简历上写"DuckDB/湖仓/Parquet"对嵌入式岗位是**减分项**（面试官会问"你在多少 MB 内存上跑的"）。嵌入式岗更吃"体积、内存、启动时间、断电安全、交叉编译"这五个词。

### 七、断电安全：嵌入式场景唯一不能妥协的指标（补充，2026-09-29）

嵌入式设备与服务器最大的差别不是算力，而是**断电是常态而非异常**（电池、看门狗复位、电源纹波）。因此嵌入式数据库选型必须看 `synchronous` 语义，而这一块 SQLite 的官方文档存在**极易踩的坑**：

| 模式 | 语义（官方文档逐字） | 后果 |
|---|---|---|
| `journal_mode=DELETE`（**默认**）+ `synchronous=FULL(2)` | *"ensures that an operating system crash or power failure will **not corrupt** the database"* | **只保证不损坏，不保证最后一次提交还在** |
| `journal_mode=DELETE` + `synchronous=EXTRA(3)` | *"EXTRA provides **additional durability** if the commit is followed closely by a power loss"* | 这才是 rollback journal 模式下的持久性配置 |
| `journal_mode=WAL` + `synchronous=FULL` | *"an additional sync operation of the WAL file happens after each transaction commit... helps ensure that transactions are **durable across a power loss**"* | **WAL 下的正确配置** |
| `journal_mode=WAL` + `synchronous=NORMAL(1)` | *"WAL mode does lose durability. A transaction committed in WAL mode with `synchronous=NORMAL` **might roll back following a power loss** or system crash."* | **丢数据，绝不可用于审计账本** |

**两条必须知道的硬事实**：
1. **编译期默认值**：`SQLITE_DEFAULT_SYNCHRONOUS` 默认 **2（FULL）**；`SQLITE_DEFAULT_WAL_SYNCHRONOUS` 若未覆盖则与前者相同；**`fullfsync` 没有编译期选项，默认恒为 `false`**。
2. **发行版可能改了默认值**：实测（avi.im, 2025-08-24）**macOS 自带的 SQLite 3.43.2 在 WAL 模式下 `synchronous=1`（NORMAL）且 `fullfsync=0`**——即"默认就是丢数据的配置"。**嵌入式 Linux 的交叉编译产物同样可能被发行版打补丁改默认值。**

**对嵌入式方向的结论**：**任何声称"断电安全"的嵌入式存储方案，必须在启动时打印 `PRAGMA journal_mode` / `PRAGMA synchronous` / `PRAGMA fullfsync` 三个实际返回值，而不是相信默认值。** 这一条既是工程纪律，也是面试时能立刻区分"用过 SQLite"和"读过 SQLite 文档"的问题。

**顺带一条对简历有用的对照**：SQLite 官方文档明确 **WAL 模式从 3.7.0（2010-07-21）** 起提供，而 **`synchronous=EXTRA`** 在 rollback journal 模式下才提供持久性保证。**能说清"为什么审计类应用应该用 WAL+FULL 而不是 DELETE+EXTRA"，比罗列数据库名词更有说服力。**

3. **在论文与简历中明确写出"排除 DuckDB/RocksDB/BDB 的理由"**（时间点：**2027-03 前**，写入 `research/12_threats_to_validity.md` 新增小节 T5「Storage engine selection」）。三条理由逐字可用：(a) DuckDB 官方要求最低 125 MB/线程，与嵌入式/零依赖对账器冲突；(b) RocksDB/LevelDB 的后台 compaction 导致字节级布局非确定，破坏可复算；(c) Berkeley DB 18.1 起 AGPLv3，与公开在线对账服务冲突。**不要**把它写成"我们比较了各种数据库后选择了 SQLite"，而要给出上面三条可核验的硬理由。

## 盲区（诚实标注）

- **DuckDB 的官方二进制体积数字未核实**：50 MB 这个数字来自第三方博客 duckdblab.org 的总结表，DuckDB 官网未在环境页给出体积；我尝试从 GitHub Releases / SourceForge 页取 asset 字节数未成功。论文中若引用应标注为"第三方估算"。
- **LMDB 编译后体积未核实**：只查到 `mdb.c` 约 23K 行源码规模（来自 DeepWiki 二次来源，非 Symas 官方），未找到官方或可信第三方的编译后 KB 数字。坊间流传的"~32KB"说法**本次未验证，不采用**。
- **RocksDB 二进制体积与最小内存未核实**：官方 Wiki 只讲内存组成，不给总体积/下限数字。
- **LevelDB 的维护状态未核实**：我只确认了 Google 官方仓库存在且文档仍在，没有查到"已归档/已弃用"的官方声明或最近提交日期，"功能冻结"是我的判断而非引文。
- **DuckDB vs SQLite 基准的样本偏差**：该测试是单篇博客自测、合成数据、单硬件、DuckDB 直接读 CSV（零 ETL）而 SQLite 需 `.import` ——**导入时间未计入 SQLite 一侧还是两侧都未计入，文中表述含糊**。真实差距可能小于 209×。
- **SQLite 默认缓存 2000 页的说法来自中文二手来源**（知乎/CSDN），未在 sqlite.org 官方文档核实；官方 `PRAGMA cache_size` 默认值应以 `sqlite3` 实测为准。
- **MCU 可行性缺少实测**：STM32 移植我只找到 GitHub 仓库与中文博客，没有取到具体的 Flash/RAM 占用数字，"MCU 可行"是基于存在移植案例的推断。
- **简历建议无数据支撑**：第 4、6 节中关于"嵌入式面试官看重什么"的判断是我的领域经验，不是引用来源。
