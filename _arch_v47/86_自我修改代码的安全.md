# 方向 86：自我修改代码的安全

## 一、核心结论

“自我修改代码”不能被笼统地理解成一个会自己改文件的机器人。至少要分成三种不同问题：第一种是运行时 self-modifying code，包括 JIT、动态链接、解包器和运行时生成机器码；第二种是 automated program repair（APR），即根据失败测试、漏洞报告或静态分析结果提出补丁；第三种是 LLM coding agent，它能读仓库、执行命令、修改文件，再根据测试结果继续循环。三者都涉及“程序产生新程序”或“程序改变自身行为”，但安全边界并不相同。JIT 的核心危险是动态代码页的写—执行权限、控制流完整性和代码指针；APR 的核心危险是补丁过拟合、测试逃逸和语义回归；LLM agent 的核心危险则是提示注入、过度权限、凭据泄露、非预期文件修改和无人批准的发布。

对阙疑而言，最重要的结论是：**不应允许任何自动代理直接改写 `gate_engine.py` 的生产核心，更不应让它修改规则、保护器、判决账本或审计协议后立即自我生效。** `gate_engine.py` 在共享上下文中是 3826 行的判决内核；阙疑的价值不是“代码能跑”，而是判决可复算、证据可追、盲态协议不可回盲。让一个模型根据当前 gate 的输出去改 gate，再用修改后的 gate 证明自己改对了，会形成验证者与被验证者耦合、目标函数自我篡改和审计信任根坍塌。即使补丁让某个测试通过，也不能说明规则语义、四态判决、9 个保护器或 452 条 append-only 判决记录仍保持原协议。

因此，阙疑应采用“**只读生产核心 + 隔离候选补丁 + 独立验证者 + 签名审批 + 原子发布 + 可回滚审计**”的结构。LLM 或自动修复器可以提出候选 patch，但只能写入一次性工作区、临时分支或候选补丁仓库；它不能获得生产目录的写权限，不能访问签名私钥，不能直接写入正式账本，不能修改审批策略，也不能自己决定合并。候选补丁必须固定基线哈希，在独立沙箱中编译、运行回归、运行 holdout、运行保护器压力测试、运行账本重放和独立对账器；所有结果都绑定到候选补丁哈希、规则快照哈希、环境摘要、工具版本、随机种子、输入卡哈希和操作者身份。只有人工或受控的签名审批服务确认后，发布器才可以把候选版本提升为生产版本。

这不是拒绝自动化，而是把自动化放到正确位置：自动系统负责搜索、解释、生成、测试和排序；确定性门禁负责否决越权、不可复现、回放不一致和盲态污染；人负责批准协议意义上的变化。对阙疑，这种保守设计反而能成为研究贡献：它展示一个知识验证系统如何在 LLM 不可信、候选补丁可能错误、代理可能被外部文档注入的情况下，仍保持验证者与被验证者解耦。

## 二、证据、数字与威胁边界

运行时自修改代码的研究说明，安全边界首先应由内存权限和控制流建立，而不是依靠“代码作者是可信的”这一假设。Renew 论文讨论了动态生成代码的 CFI 保护：代码生成阶段允许写但不可执行，执行阶段允许执行但不可写；同一页面不同时拥有写和执行权限，动态代码在首次执行前被分析和重写，间接控制流被导向受保护目标。其原型使用 16-byte aligned chunks 约束间接跳转目标，在 Firefox JIT 测试中通过了 6206 个相关测试；在 LuaJIT 与关闭 JIT 相比约为 3.4 倍，在 SpiderMonkey 中约为 3.9 倍。这些数字不是阙疑可以直接照搬的性能承诺，但它们证明一个原则：动态代码要先经过权限、映射和控制流边界，不能因为“程序自己生成的”就获得生产级信任。对阙疑的对应物不是机器码页，而是规则快照、候选模块和执行权限：候选代码可以在隔离区被写入和运行，却不能同时拥有修改信任根与宣布自身可信的能力。

自动程序修复的数字也提醒我们，编译成功或测试通过只是弱证据。RepairAgent 在 Defects4J 的 835 个 Java 缺陷上报告 186 个 plausible fixes、164 个 correct fixes，约 22.3% 与 19.6%；实验流程最多允许 40 个 cycle。换言之，有 22 个补丁通过现有测试却没有被判为正确。RepairAgent 的 plausible 定义是通过测试，并不等于覆盖所有输入、没有改变未测试语义或没有引入新漏洞。另一个 OSS-Fuzz 安全修复研究在 588 个 C/C++ 漏洞上报告 CodeRover-S 有 309 个可通过漏洞触发输入验证的补丁，即约 52.6%；这里的成功标准是编译成功且原始 exploit input 不再触发漏洞，论文同时强调这不是完整安全证明。阙疑更不能把“holdout 检出率上升”“编译通过”“coverage 上升”当成规则补丁正确性的充分条件，因为 gate 的输出本身可能就是被优化目标利用的代理指标。

LLM coding agent 的工程结果同样不能被误读成“代理已经适合写核心”。SWE-agent 官方页面报告其在完整 SWE-bench 上解决 12.29% 的问题；OpenHands 论文在 SWE-bench Lite 的 300 个实例上报告过 26.0% 的 CodeActAgent 结果，完整 SWE-bench 有 2294 个实例，作者按约每题 3 美元估算完整评测成本约 6.9K 美元。这些结果说明代理能在沙箱中浏览、编辑、执行和调试，不说明它能理解阙疑的信任协议，更不说明它可以担任自己的安全审批人。OpenHands 的设计把 Bash、IPython 和浏览器执行放进独立 Docker 沙箱；Anthropic 对 Claude Code 的说明也明确区分文件系统隔离与网络隔离，并报告其内部使用中沙箱使权限提示减少 84%。这个 84% 是厂商内部使用数字，不是普适安全率，但它揭示一个实际问题：减少审批提示只有在预先定义的文件和网络边界内才安全，否则“少点几次确认”只是把风险藏起来。

程序修复还有 patch overfitting 问题：补丁可能专门迎合可见测试，却没有修复真实规格。于是阙疑的候选评估不能只在当前 30 条 holdout 或 gate 自己产生的测试上循环优化。候选补丁至少要接受四类相互独立的检查：一是语法和构建检查，包括严格锁定的 C++ 编译器、标准版本和依赖；二是行为检查，包括真实缺陷夹具、回归集、未参与候选选择的保留集和故意构造的反例；三是协议检查，包括 67 条规则的版本哈希、9 个保护器、四态状态转移、盲态不回盲和 452 条账本重放；四是独立语义检查，包括与生产版并行运行、差分输出、独立对账器复算和人工审查。任何一项失败都应是拒绝，不允许用另一项更高的 coverage 或更多通过样例抵消。

权限模型应采用 capability，而不是让代理继承开发者账户的 ambient authority。WASI 官方安全说明把 capability-based security 表述为：模块或组件默认没有外部权限，主机只授予明确的文件系统、网络、环境、时钟等能力；没有文件系统 import 就不能读文件，没有 network import 就不能开 socket。阙疑的候选补丁应获得的 capability 可以极小化为：读取固定基线快照、写入临时工作区、调用无密钥的编译器、执行白名单测试命令、读取测试输出。它不应获得生产目录写能力、私钥、远程 push、数据库删除、正式账本追加或审批策略写能力。OWASP AI Agent Security Cheat Sheet 也强调最小工具集、逐工具读写范围、独立授权层、敏感操作显式确认、fail closed、审计和回滚；其中示例把执行代码列为 HIGH，把数据库删除列为 CRITICAL，并给出了 4 级风险分类。这些数字是示例配置，不是统一标准，但“工具权限不能由模型自己授予”是可迁移的原则。

## 三、阙疑的候选补丁隔离架构

建议把阙疑的修改流程划成六个不可跳过的阶段。第一阶段是冻结基线。发布器读取当前生产版本，计算 `gate_engine.py`、规则目录、保护器配置、账本 checkpoint、依赖锁文件和测试清单的摘要；这组摘要成为 `baseline_manifest`。候选代理只能读取该快照，不能边运行边改变基线。每次候选都生成唯一 `candidate_id`，其内容至少包括 `base_commit`、`gate_hash`、`rules_hash`、`protector_hash`、`ledger_checkpoint`、`prompt_hash`、`agent_id`、`model_id`、`tool_policy_version` 和时间戳。外部文档、知识卡和 issue 描述全部视为不可信数据，不能改变工具权限和审批策略。

第二阶段是候选生成。LLM agent 在临时目录、临时容器或临时虚拟机中工作，目录中只挂载候选分支和脱敏测试素材。推荐把输出限制为 unified diff、结构化变更说明和测试计划，而不是把代理直接连接到生产 Python 解释器。代理可以提出三类候选：测试夹具、变异算子、非核心分析脚本；涉及规则语义、保护器、判决状态机、账本写入或 `gate_engine.py` 的 patch 只能进入“高风险候选”队列，默认不自动合并。更安全的第一步是让代理修改 `candidate_gate_engine.py` 的副本或生成外部策略描述，由固定适配器把它转换为候选输入；生产文件名和生产 import 路径不应在沙箱内可写，避免代理通过路径穿越、软链接或动态 import 绕开限制。

第三阶段是沙箱执行与 capability 过滤。容器或 WASM/WASI 运行时应采用默认拒绝：只读挂载基线、可写挂载候选工作区，禁止访问 `.env`、私钥、SSH 目录、云凭证、生产数据库和远程 git 凭证；网络默认关闭，若依赖下载不可避免，则只允许固定镜像仓库或预构建依赖缓存。编译、测试、静态分析和独立对账器应作为四个不同 capability，不把“能运行测试”自动扩展为“能改账本”。命令通过策略服务规范化后再执行，不接受模型提供的任意 shell 字符串。策略、日志或审批查询失败时必须 fail closed。即便候选代码包含恶意逻辑，也只能影响本次沙箱及其临时数据，不能向外发请求、读取生产密钥或修改宿主文件。

第四阶段是独立评估。候选补丁必须与未修改的生产基线并行评测，评估器和候选代理不能共享可写状态。至少保存：编译命令与完整 stdout/stderr、测试用例版本、输入卡哈希、输出证据哈希、决策前后四态、规则命中差异、保护器事件、盲 holdout 结果、账本重放结果、资源使用量和超时原因。评估结果不能由候选代码自己签名；签名主体必须是隔离的验证服务，并且验证服务只接收候选摘要和结果，不接收候选对自身“我已正确”的自然语言声明。独立对账器应从原始输入重新计算关键计数，避免 `gate_engine.py` 同时产生判决和证明判决正确的证据。

第五阶段是人工审查和签名审批。审批对象不是模糊的“接受这个 agent 的建议”，而是精确绑定的候选哈希、基线哈希、变更文件、权限策略、测试报告和有效期。高风险候选至少需要一名人类对 diff、失败样例、回归差异和回滚方案进行审阅；涉及核心判决语义、保护器或审计账本时，默认拒绝自动批准，最好要求第二名独立复核，或把它定义为研究实验而不是生产发布。Cosign 官方文档提供签名、验证和密钥管理入口；in-toto 的目标是让用户知道软件供应链中做过哪些步骤、由谁完成、以什么顺序完成。阙疑可以把“候选生成—构建—测试—独立复算—人工批准—发布”记录为不可变 provenance，而不是只保留一个最终 commit。

第六阶段是原子发布与回滚。发布器不能把候选 diff 直接覆盖到现有运行进程；应生成新的不可变版本目录或容器镜像，完成签名验证后通过版本指针切换。旧版本必须保留其 manifest、签名、依赖和账本 checkpoint，回滚时切回上一个已批准版本，而不是让代理临时“修回去”。发布后继续运行最小回归和审计健康检查；一旦发现 replay mismatch、protector violation、unexpected decision drift、非确定性重放或签名不匹配，立即停止晋级并切回最近的可信版本。回滚本身也要写入 append-only 审计链，包含触发原因、批准人、旧版本、新版本、时间和验证结果。这样，回滚是受审计的版本转换，不是一次无法解释的文件覆盖。

## 四、对阙疑的 3 条具体行动

1. **先把“核心不可自动写”固化成门禁。** 在现有仓库规范中增加一条明确协议：任何 agent、脚本或自动修复器都不能直接写生产 `gate_engine.py`、规则定义、9 个保护器、正式判决账本和审批配置；自动任务只能输出候选 diff 到隔离目录。实现上先做路径白名单、生产文件只读挂载、无凭证沙箱、默认断网和命令白名单，再为每个候选生成 `baseline_manifest` 与 `candidate_manifest`。验收条件不是“代理能改代码”，而是：代理即使提出恶意路径、软链接、任意 shell、动态 import 或修改账本的操作，也只能得到拒绝事件；生产目录哈希、规则哈希、保护器哈希和账本 checkpoint 在整个候选流程中保持不变。若这一门禁没有通过，暂不做任何自动规则修复实验。

2. **把候选评估做成独立、分层、可重放的实验。** 第一轮不要让代理搜索核心规则，而是让它生成测试夹具、变异算子或只读诊断报告；候选补丁在副本中运行，固定编译器、标准版本、依赖锁定、随机种子和容器摘要。评估至少分为构建、回归、盲 holdout、真实缺陷夹具、保护器压力测试、账本重放、独立对账和人工语义审查八类结果；将 `unsupported_claim`、`blind_holdout_contamination`、`ledger_replay_mismatch`、`protector_violation`、`non_deterministic_replay` 和 `signature_missing` 定义为硬失败。特别要保留“通过测试但语义错误”的候选，形成 patch-overfitting 回归集。候选选择不能以 gate 通过率、coverage、ledger 新增条数或模型自评分数作为唯一目标，也不能因为某个指标提高就抵消协议失败。

3. **建立签名审批、原子发布和可逆版本链，再谈有限自动修复。** 用 Cosign 或同等机制给候选构建物、验证报告和最终版本签名；用 in-toto 风格的步骤证明记录是谁生成、谁验证、谁批准以及顺序是否完整。生产发布只接受满足基线哈希匹配、独立评估通过、人工审批有效期未过、签名可验证的候选。每次上线保留上一个已批准版本和对应账本 checkpoint，发布后进行 replay smoke test；发现判决漂移、保护器违规或审计缺口就自动停止晋级并切回旧版本，但回滚动作必须由发布器执行并写入审计链。时间顺序上，先完成隔离与回滚，再做小规模候选实验；在没有连续重放、权限拒绝、签名验证和回滚演练证据前，禁止任何代理直接触碰 `gate_engine.py` 核心。

## 五、盲区与来源

本文的项目锚点来自共享上下文：阙疑有 37 张实卡、67 条规则、9 个保护器、452 条判决账本，`gate_engine.py` 为 3826 行；盲 holdout 为 30 条、真错 17 条、检出率 66.7%，外部 corpus 的 43.8% 已被上下文标注为算术口径不自洽。本文没有重新审计仓库，也没有读取 `gate_engine.py` 的实际函数、导入关系或文件权限，因此不能断言当前实现已经具备本文建议的隔离门禁。关于 OWASP 的 4 级风险、工具调用 30 次/分钟、失败 5 次和会话成本 10 美元等数字，它们是页面中的示例阈值，不是阙疑应直接采用的基线；阙疑必须通过自己的威胁建模、负载测试和误报成本确定参数。Anthropic 的 84% 是内部使用中的权限提示减少量，不是攻击成功率下降 84%。RepairAgent、CodeRover-S、SWE-agent 和 OpenHands 的成功率来自各自特定数据集、模型、版本和评估定义，不能横向比较成“自动修复准确率”。Renew 的 JIT 数字来自 Linux/x86 原型，不能直接证明 Python 文件自动补丁或阙疑规则候选安全。本文也没有实测容器逃逸、WASI 运行时缺陷、签名密钥轮换、灾难恢复时间或双人审批的人因效果；这些都应作为后续实验，而不能靠文献数字替代。
