# 方向89：终身学习与持续学习（continual/lifelong learning）

## 一、问题定义：阙疑要持续学习什么，而不是让系统自动改写自己

终身学习（lifelong learning）和持续学习（continual learning，CL）所要解决的不是一次性把所有训练数据塞进模型，而是在数据、任务和规则按时间到达的情况下，系统能够吸收新知识，同时保留旧知识，并且在未来仍能解释“某个结论是在什么版本、什么证据、什么规则下产生的”。连续学习文献通常把目标拆成两个相互拉扯的性质：**plasticity（可塑性）**，即遇到新任务、新类别或新分布时能学会；**stability（稳定性）**，即学习新内容不能把旧能力覆盖掉。Rolnick 等人在 CLEAR 论文中直接把 catastrophic forgetting 定义为新经验覆盖旧经验导致的稳定性失败；Kirkpatrick 等人的 EWC 论文则把它描述为顺序训练时新任务的权重更新破坏旧任务能力。对阙疑而言，这两个词不能只映射成“模型准确率”：可塑性对应系统能够发现新的 C++ 语义边界、编译器差异、标准条款变化和新反例；稳定性对应已发布的规则、卡片、证据和判决不能因后来一次自动运行而被悄悄重分类。

catastrophic forgetting（灾难性遗忘）在阙疑中至少有三种形式。第一是**规则遗忘**：系统为适应新样例而调整 67 条规则的判据，结果旧的真实缺陷夹具不再被拦截。第二是**语义遗忘**：加入 C++ 新特性后，生成器只会探索新语法，却忘记旧标准中生命周期、值类别、ODR、异常安全和并发规则。第三是**证据遗忘**：新证据被认为“更近”或“更可信”，于是旧判决的适用条件、编译器版本和人审依据被丢掉。后两种尤其危险，因为它们可能在整体通过率上看起来更好，却让历史审计不可复现。阙疑当前的共享锚点是 37 张实卡、67 条规则、9 个保护器、452 条账本事件和 3826 行内核；盲 holdout 为 30 条，其中真错 17 条，现有检出率 66.7%；外部 corpus 40 条、检出率 43.8% 的算术口径仍不自洽，变异测试为 core 97.3%、all 81.5%，反事实 P=R=F1=0。这里的数字是当前状态，不是可以被新一轮学习覆盖的标签。

因此，阙疑的“持续学习对象”应限定为四层：一是候选测试和候选反例，二是候选原子命题与证据关联，三是经人审批准的规则新版本，四是对未来标准/编译器环境的适用范围扩展；规则核心、保护器、holdout、历史账本和信任根不是普通训练参数。换句话说，阙疑不应追求一个“越跑越会改规则”的黑箱，而应建设一个**版本化、证据约束、可回放的知识持续学习循环**。每一轮新数据都要带时间、来源、标准版本、编译器版本、配置、生成器版本、证据哈希和判决策略指纹；缺失边界就落 `unknown`，而不是凭相似度猜测。这样才把“学习”从参数更新改造成受治理的知识增量。

## 二、方法谱系：replay、EWC 与三种增量场景如何映射到 C++ 验证

持续学习的经典方法大致分为 replay/rehearsal（回放）、regularization（正则化/巩固）、architecture-based（结构隔离）和它们的混合。**Replay** 保存一小部分历史样本，在学习新数据时与新样本交错重放。CLEAR 的具体做法是把 replay 与 off-policy learning、behavioral cloning 结合，用回放增强稳定性，同时保留 on-policy 学习带来的可塑性；它的启发是，阙疑每次接收新 C++ 样例时，不能只运行“最新标准特性”样例，还必须从历史真实缺陷、已验证卡、边界卡和负例中抽取受控的 replay 集。这个 replay 集不是把 452 条账本当成可训练文本，更不能把 holdout 复制进来；它应由可公开复核的开发样例、15 条真实缺陷夹具、已退役规则的反例和跨编译器回归夹具组成，并按语义单元、标准版本、规则覆盖、错误类型和时间分层采样。对账本而言，replay 的对象是“重放事件和判决”，不是“重新解释历史事件”。

Replay 也有代价。缓冲区过小会遗忘长尾规则，缓冲区只保存最近样本会把旧标准挤出，按命中率采样又会偏向现有 67 条规则，导致系统对未知类别没有覆盖。可以借鉴 reservoir sampling 的公平保留思路，但必须加上领域分层：至少为 C++ 标准版本、编译器家族、语言类别、判决状态、规则命中位图、unknown 原因和证据等级设配额。每个 replay 样例应保存原始输入哈希和首次出现时间，不能保存“后来修正过的标签”来冒充原始事实。iCaRL 的 exemplar/prototype 思路也可类比为为每个语义区域保留代表性最小代码，而不是只存完整大样本；但 C++ 的“代表性”须由 AST、类型关系、翻译阶段和编译矩阵定义，不能由文本 embedding 单独决定。

**EWC（Elastic Weight Consolidation）**是另一条路线：学习旧任务后估计每个参数的重要性，用 Fisher information 近似其重要程度；学习新任务时对重要参数增加二次惩罚，形式可写成 `L_new(θ) + (λ/2)Σ_i F_i(θ_i-θ_old,i)^2`。它的直觉是重要权重像被弹簧固定，既允许新任务学习，又减少旧任务遗忘。对阙疑，EWC 不宜直接拿来决定某条规则是否正确，但可转译为**冻结等级**：被多条独立证据、历史人审和多个编译器矩阵支持的规则接口应有较高稳定性；刚由单个新样例提出的候选规则可塑性高，但不能进入 block。实际工程实现更接近“规则版本的保护系数”而不是神经参数：`block` 规则需要人签、存量 0 误报和正反例；`warn` 可以观察但必须解释；`advice` 只提供建议。任何规则的保护系数都不能替代新证据，也不能使旧规则免于回归测试。

三种增量场景必须分开。**Task-incremental** 假设测试时知道任务 ID；映射到阙疑就是调用方明确声明“这是 C++20 模板约束迁移任务”或“这是编译器诊断一致性任务”。它较容易，因为系统可以使用任务专属规则子集。**Domain-incremental** 的标签空间不变，但输入域变化；在阙疑中是同一条语义断言换 GCC/Clang/MSVC、换 ABI、换操作系统、换 `-O0/-O2`、换标准库实现。此时不能把实现差异直接视为标准反例，必须把 `compiler_version`、`std_version`、`optimization` 和 `platform` 写进条件。**Class-incremental** 的类别空间扩展；在阙疑中相当于出现新错误类型、新规则前缀或新 C++ 标准特性，测试时不能假定任务标签，系统需要在既有类别和新类别之间共同判定。三者的难度和指标不可混报；至少要分别报告新知识吸收率、旧知识保持率、平均 forgetting、向前迁移和向后迁移。

## 三、数据漂移与规则演化：什么时候应该更新 67 条规则

C++ 知识流中的漂移不是单一概念。数据漂移（data drift）可以表现为样例的输入分布变了，例如新项目大量使用 modules、coroutines、`constexpr`、contracts 或反射相关草案特性；概念漂移（concept drift）则是“同一形式的输入，其正确判决规律变了”，例如某条原本只适用于 C++17 的陈述在 C++23 或新的 working draft 中增加了条件，或者编译器修复了一个实现错误。漂移还可能只改变可观测输出而没有改变标准语义：GCC 版本升级、Clang 诊断措辞改变、优化器输出变化、标准库实现切换都可能让现有 parser 误报。无监督漂移监测综述强调，监测至少要回答是否发生、何时发生、变化多大、影响哪里和具体发生了什么；阙疑不能把“新文件数量增加”直接当作规则失效。

建议把规则更新触发器分成四级。**一级，观察触发**：新样例在现有规则下大量落 `unknown`，或某个标准/编译器/语言特性分层的 unknown rate 连续超过预先登记阈值；这只生成 drift event，不改规则。**二级，复验触发**：同一语义签名的结果在两个以上独立编译器或两个以上标准模式中稳定分歧，且能排除 UB、环境缺件、超时、测试夹具错误和已知编译器 bug；此时登记候选反例和 `conditions[]`。**三级，规则候选触发**：新反例在开发集、时间切分集和至少一个独立 oracle 上复现，并且对历史 replay 集没有引入 block 误报；才可以起草新规则或新版本。**四级，发布触发**：人审确认 basis，更新 `data/_gate_rules.json`、快照、CHANGELOG 和 AI 使用记录，给新规则新的 `rule_version`，再进行一次完整存量回归。只要只是草案提案、单一编译器行为或没有稳定复现，就保留为 `unknown`/候选证据，不应升级 67 条生产规则。

未来 C++ 标准变化使“规则更新”和“规则适用范围扩展”必须分开。`cplusplus/draft` 仓库明确说明它提供生成标准草案的源文件，草案或生成文档不能视为 ISO 正式出版物，除非已被 WG21 正式采纳；`eel.is/c++draft` 也是可追踪的 working draft 在线参考，不等于 C++20、C++23 或所有编译器都必须支持的标准。故阙疑面对 C++26 及其后续变化，至少维护三类证据：`published_standard`（已发布标准）、`adopted_draft`（已采纳但尚未最终出版的草案）和 `implementation_experiment`（某版本编译器的实测）。规则的 `basis` 必须标出类别、条款/提案、草案快照或 commit、访问日期；feature-test macro、编译器版本和实际命令只能证明实现状态，不能单独证明标准语义。未来标准草案改变措辞时，优先新增适用条件或新规则版本，而不是用最新草案回写旧版本的历史结论。

规则更新的核心判据应是“新证据是否改变未来判定”，而不是“新数据是否更多”。每条候选更新至少回答：旧规则在哪个输入域内仍然成立；新规则增加了什么前提；哪些旧样例被重新解释；是否存在反例；是否需要从 `pass` 降为 `pass_with_exception` 或 `unknown`；是否需要人审；是否影响保护器阈值；是否改变了 holdout 的可比性。规则退役也要保留 ID 和版本，不能删除。若规则误报，先由 `block` 降为 `warn`，仍保留历史引用；若规则完全错误，改成只登记不判并写清作废原因。规则演化必须是 append-only 的决策图，而不是一串覆盖式配置。

## 四、历史判决、452 账本与 holdout：持续学习的防污染边界

历史判决的第一原则是“事实不回溯，解释可叠加”。阙疑已有 452 条 `DecisionEvent v2`，每条有 25 个字段，包含 `seq`、`prev_hash`、`self_hash` 和 `supersedes[]`；现有回填实测 452/452 自哈希吻合，prev_hash 链完整。639 回填报告还明确发现：历史 452 条事件中精确归属到某条规则的为 0，全部标记 `undetermined`，因为事件中的 `ATOM-*` 是原子卡 ID，不是规则 ID，历史 basis_refs 到 authority_log 也不含规则引用。这个事实必须保留，不能利用新规则的命中结果“猜回去”填满历史归属。新 schema 可以增加 `rule_id`、`rule_version`、`policy_digest`、`std_version`、`compiler_matrix` 和 `drift_event_id`，但只能作为 overlay 或新事件字段，不能修改旧事件的 `state`、`decision_id`、`event_id`、`result`、`prev_hash`、`entry_hash`。

历史判决如果需要改判，必须产生新的事件并用 `supersedes` 指向旧事件。`pass` 到 `fail` 需要新证据或冲突保护器条件；`fail` 回到 `pass`/`pass_with_exception` 只能由人审完成；边界失效、证据撤回、工具不可用或编译器超时应降为 `unknown`，而不是用新模型强行“修正”为 pass。读取者默认看当前有效投影，但审计者可以沿事件链重放任何历史时刻。这样既能回答“今天按新规则会怎样”，又能回答“2026-09-20 当时为什么判成这样”。历史 verdict 不是错误样本，不能因当前判断不同而删掉；它们是检测规则漂移、测量回归和识别系统性偏差的 replay 语料。

holdout 必须与持续学习流彻底隔离。当前盲 holdout 只有 30 条，真错 17 条，样本量很小，任何一次窥视、按标签调 prompt、按命中失败样本修改规则，都可能产生明显乐观偏差。建议采用四层数据边界：开发集可被工程师和算法反复查看；时间切分验证集只允许在预登记周期内查看聚合指标；真正 holdout 只由固定 runner 读取并输出总计；新时间窗 holdout 用于检验系统是否能面对未来漂移。holdout 的原始文件、标签、样例 ID、顺序、哈希和评估脚本应只读，规则候选生成器、replay buffer、LLM prompt、变异器、人工筛样工具都不能读取其内容。任何一次对 holdout 的访问必须登记 `run_id`、代码哈希、规则快照、数据版本、访问时间和输出摘要；如果发现候选曾接触 holdout，整轮结果标记 contaminated，不得作为论文主结果。

回溯污染还有更隐蔽的路径：把 holdout 的失败样例复制进 replay；把 holdout 的标签模式写进规则 basis；根据 holdout 的单条结果调整 EWC/replay 权重；用外部 corpus 与 holdout 的重复样例计算阈值；或先运行大量候选，再只报告最高分。阙疑应预先锁定主要指标和停止规则，保留全部候选、失败和重复结果，报告 30 条 holdout 的逐项结果只在最终阶段解封。若规则更新来自未来 C++ 标准，更新后的版本应在 holdout 上只做一次冻结评估；旧版本的历史分数仍保留，不能用新版本结果覆盖旧表格。对小样本结果应同时给出整数计数、Clopper-Pearson 区间或其他合适区间，不把 66.7% 写成稳定泛化能力。

## 五、对阙疑的三条具体行动、诚实盲区与来源

第一条行动是实现一个只读的 continual replay harness，而不是立即引入神经网络训练。将 37 张实卡、15 条真实缺陷夹具、可公开的开发样例、历史 `unknown`、规则反例和编译器差异样例整理成分层 replay manifest；每个条目包含 `artifact_hash`、`first_seen_at`、`std_version`、`compiler_version`、`feature_set`、`rule_ids`、`verdict_at_time`、`current_projection`、`evidence_ids` 和 `contamination_status`。每次新规则候选都必须同时跑新样例与 replay，报告旧规则保持率、候选新增检出、unknown 变化、block 误报数、编译矩阵稳定率和运行成本。replay 只能读历史，不能写 452 账本；人审批准后再以新事件追加规则归属。第二条行动是把 67 条规则分成 task/domain/class-incremental 三种评测协议：按知识主题切任务，按编译器/标准版本测域迁移，按新错误类别测类别扩展，并报告平均准确/检出、平均 forgetting、向前迁移、向后迁移和每层 unknown 率；先以简单 replay、EWC 风格规则冻结、无学习基线作对照，不宣称某种方法必胜。第三条行动是建立“规则演化闸门”：任何新规则必须有最小反例、basis URL、正向夹具、存量反向测试、人签和新 `rule_version`；任何标准草案变更先落 `draft`/`unknown`，只有正式证据和多编译器复验后才影响生产判决；holdout 由固定 runner 隔离，污染即废弃整轮结果。

诚实盲区包括：第一，EWC、CLEAR、iCaRL 等论文主要针对神经网络任务学习，不能直接证明“规则账本采用同样机制就会提升 C++ 验证”；这里是工程类比和待验证设计，不是实测结论。第二，阙疑当前 30 条 holdout、17 条真错的样本量不足以稳定估计长序列 forgetting，也没有按标准版本和编译器域建立足够大的真实流；43.8% corpus 的算术不自洽必须先修，不能成为持续学习奖励。第三，未来 C++ working draft 会变化，草案页面不是 ISO 正式标准，编译器实现又可能领先或滞后；规则必须区分标准事实、草案意图和实现观察。第四，现有 452 条历史事件缺少规则级归属，不能把新产生的 rule_id 伪回填成历史真相。第五，当前反事实 P=R=F1=0，说明反事实评测链还不能承担“学习后是否更会泛化”的证据责任。对阙疑而言，最可靠的终身学习不是自动遗忘旧判决，而是让新证据带着版本、条件和来源进入一条可重放的历史链，并允许系统在不确定时明确说 `unknown`。
