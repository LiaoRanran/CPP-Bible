# 方向135：模糊测试最新进展——从随机敲键到 LLM 造夹具，与"把断言变成可执行 oracle"

## 一、起点：一次"随机喂字符串"的实验，暴露了 24%~33% 的崩溃率

模糊测试（fuzzing）的学术起点通常被定在 1990 年。Miller、Fredriksen 与 So 在《An Empirical Study of the Reliability of UNIX Utilities》（CACM 33(12)，1990）中做了一件当时看来很"粗暴"的事：把随机生成的字符流（以及带特殊字节的变体）灌进一组 UNIX 命令行工具的标准输入，然后看哪些程序会崩溃或挂起。结论是**24%~33% 的工具在随机输入下出现崩溃/挂起**[1]。1995 年的复现实验报告仍有约 9% 的工具失败（**此数字凭记忆，未在本次检索中核到原文，标注待核**）[2]。

这个实验的方法论意义大于它的数字：它把"软件是否健壮"从对谈变成了**可执行实验**——不看代码怎么写的，只看喂进去垃圾会不会炸。它同时暴露了模糊测试与生俱来的两个局限，这两条至今没变：

1. **只能证伪不能证明**。跑通了十万次不代表没 bug，只代表"这十万条输入没触发"。这与阙疑的四态判决里 `UNKNOWN` 的地位完全一致：不能把"没测出问题"当 `PASS`。
2. **覆盖率决定下界**。随机输入几乎永远停在输入的浅层解析（"魔数校验"就挡住了），所以"随机"必须被"覆盖引导"替换，才能变成今天的样子。

## 二、覆盖引导与三大引擎：AFL++、libFuzzer、honggfuzz 的工程分界

现代 fuzzing 的技术转折点是**反馈式覆盖引导**。Michał Zalewski 的 AFL（American Fuzzy Lop，2013 年发布）用编译期插桩记录边覆盖，把"新覆盖"作为保留输入的判据，配合 forkserver 把每次执行压到毫秒级；AFL 的经典战绩是在 coreutils/binutils 等成熟软件里挖出成批缺陷[3]。AFL 后来由社区接手为 **AFL++**（2019 起），持续集成社区补丁、QEMU 模式与多种变异调度，当前发布线已到 **++5.03c**[4][5]。AFL++ 不只是"AFL 的新版本"，它同时是**研究平台**：LAF-INTEL（2020）把它变成"输入到状态"的映射，CmpLog 把比较指令的常量回灌给变异器以突破魔数检查。

libFuzzer 走另一条路：它不是一个独立程序，而是**进程内（in-process）库**，用 `-fsanitize=fuzzer` 与 SanitizerCoverage 插桩把"变异—执行—收集覆盖"全放在同一个进程里循环，因此单次执行成本极低、与 ASan/UBSan/MSan 天然同栈[6]。对 C/C++ 而言，这条"编译器原生"路径的意义在于：**fuzzing 从外挂工具变成了构建系统的一部分**。honggfuzz 是第三条路线，以多线程/多进程与硬件计数器（Intel PT）见长，同样被 OSS-Fuzz 支持[7]。

结构感知是绕不过的第二道坎。纯字节变异对"输入必须是合法格式"的程序（协议、字节码、编译器前端）效率极低；libprotobuf-mutator（2017）用 protobuf 描述输入语法树，让变异发生在**结构层**；FuzzTest/Centipede（Google，2023）进一步把"属性测试"与"大规模并行 fuzzing"合流，并在 **2025 年把 Centipede 合并进 FuzzTest** 统一开发[8]。

规模的证据来自 OSS-Fuzz（2016 年上线，与 Core Infrastructure Initiative、OpenSSF 合作）[7]。它的战果数字有两个可核时点：
- **截至 2023 年 8 月：1,000 个项目、36,000+ 缺陷、10,000+ 漏洞**[9]；
- **截至 2025 年 5 月：13,000+ 漏洞、50,000+ 缺陷**[7]。

内核侧的对应物是 syzkaller（Google，无监督覆盖引导的系统调用 fuzzer），支持 Linux、FreeBSD、Windows、gVisor 等多个内核并持续报出缺陷[10]。这两条线共同说明：**模糊测试的产出已经以"万"为单位计数，但它依赖的是"长跑"（24/7、集群），而不是某一次聪明的运行**。

## 三、LLM 进入 fuzzing 的三种姿势，以及它们的真实数字

2023 年起 LLM 大规模进入 fuzzing，按"LLM 负责哪一段"可分三类：

**（1）生成测试程序（不是生成字节）**。TitanFuzz（ISSTA 2023，arXiv:2212.14834）是第一个用 LLM 直接生成测试程序来 fuzz 深度学习库的工作，它把"API 调用序列"当成生成目标，绕开了传统 DL fuzzer 需要人工标注 API 约束的问题，并在 TensorFlow/PyTorch 上报出缺陷[11][12]（**该文的精确缺陷数与覆盖率增益在本次检索中未核到原文数字，标注待核**）。

**（2）生成"输入语言"本身**。Fuzz4All（ICSE 2024，DOI 10.1145/3597503.3639121）针对的是**语言实现**：它把被测对象的文档/示例/规约喂给 LLM，让 LLM 综合出该语言的输入，从而对 9 个被测系统、6 种语言（C、C++、Go、SMT2、Java、Python/Qiskit）生效；论文报告的成果是**在 GCC、Clang、Z3、CVC5、OpenJDK、Qiskit 等系统中识别出 98 个缺陷**[13][14]。这条路线对 C++ 特别关键：**"新语法特性"（如 C++23 的 `std::expected`）正是传统 fuzzer 覆盖最差的区域**。

**（3）生成 harness（fuzz target）**。Google 的 **oss-fuzz-gen** 让 LLM 为已有项目自动写 fuzz target，把"接入 fuzzing"这件事本身自动化：2024 年 11 月的安全博客给出的是**26 个新漏洞**（在原本已有海量 fuzzing 的项目里又挖出来的）[15]；其仓库 README 的累计口径是**30 个新缺陷/漏洞由自动生成的目标发现**[16]（**两个数字口径不同、时点不同，我在本文不做合并**）。

**（4）顺带一类：token 级 fuzzing**。Salls 等在 USENIX Security 2021 提出对 JS 引擎做 token 级变异，在四个主流 JS 引擎上找到 **29 个此前未知缺陷**[17]——它属于"结构化变异"而非 LLM 路线，但说明同一件事：**变异算子在正确抽象层上，比算力更值钱**。

必须写进"局限"的三条（否则会把 LLM fuzzing 讲成银弹）：
- **oracle 没变**。LLM 提高了"喂进去"的质量，但"什么算错"仍要靠 sanitizer/断言/差分。Fuzz4All 的 98 个缺陷之所以成立，是因为编译器有 crash/断言与差分 oracle，而不是因为 LLM 说了它对。
- **易落进"语法有效、语义贫乏"**。LLM 生成的程序容易集中在训练语料的常见模式上，长尾语义组合仍需变异器与种子库补。
- **可复现性**。LLM 采样带随机性，同一 prompt 两次得到不同输入集；因此必须把**种子集**当作可提交工件（seed corpus + 生成脚本 + 版本），否则"跑出来过"不可复现。

## 四、对 C++ 知识验证的应用：oracle 才是主角，fuzzing 只是生产方式

把方向41（编译器优化假 miss）与方向133（静态/动态分工）连起来看，fuzzing 对"知识验证"的价值不在"找 bug"，而在**它给出了一个可执行的真值来源**：

1. **差分测试 = C++ 领域最自然的 oracle**。同一段代码在 `-O0` 与 `-O2` 下行为不同、在 gcc 与 clang 下结论相反，就是"实现定义/UB/优化敏感"的直接证据。阙疑现役口径的检出率（holdout **81.2%**）正是建立在这种"双档观测"上；把 fuzzing 接进来的第一步不是引入新引擎，而是**把 oracle 从"一对档位"扩成"一族档位与编译器"**。
2. **变异测试与 fuzzing 是两条不同的分母**。变异测试（mutation testing）人为注入缺陷，度量"测试/规则能不能杀掉它"——它给的是**检出能力的下界**（阙疑 core 口径 **97.3%**）；fuzzing 面对的是自然缺陷，给的是**未知的未知**。前者可穷举、可插拔（97.3% 这个数字只对"变异算子覆盖的那类缺陷"成立），后者不可穷举、不可保证。**两者不能互相替代，也不能相加**。
3. **C++ 语料的关键约束是"可执行性"**。阙疑语料当前是 **37 张实卡 / 67 条规则 / 9 个保护器 / 452 条账本事件**，卡面资产（夹具 `.c/.cpp`、`.asm`、`.out`、sha256）已经构成 seed corpus 的雏形：每张卡的 `artifact_assert` 就是一个可执行的 harness 钩子。单卡验证成本 **0.59 ms** 意味着"全语料跑一遍"是毫秒级——预算上完全允许把"每卡多档位、多编译器"常态化。

## 五、对阙疑的映射：把 fuzzing 定位成"第三条证据通道"，而不是新门禁

阙疑现在有三层证据结构：**静态规则门禁（67 条规则）→ 可复现工件（夹具/输出/哈希）→ 人签（verified 唯人签）**。fuzzing 应该插在第二层与第三层之间，承担三种具体角色：

- **角色 A：把"断言"编译成 oracle**。卡面 `claim` 目前是自然语言 + `claim_structured` 三元组，其中可判定的部分应当下沉为**可执行断言**（如"屏障落循环体内 ⇒ 该循环不被消除"，对应 `artifact_assert: contains: spin_plain`）。fuzzing 在这种断言上的作用是**主动找反例**，而不是等读卡的人发现。
- **角色 B：跨编译器差分扩大检出面**。现役口径已从单档 `-O1` 改成 `-O0/-O2` 双档（检出率 66.7% → **81.2%**，同时把"某一档不可用"从"吃掉整个样本"改成"只废该档"）。下一步的自然扩展是**加第二个编译器**（gcc/clang 双栈），而不是加测试条数。
- **角色 C：LLM 只当夹具/变异器，不当判决者**。这与项目的既有红线（**verified 唯人签，Agent 不自置**）一致：LLM 可以生成候选输入、候选 harness、候选反例，但判决必须落在机器可复算的 oracle 与人签上。

同时要明确**不该做**的事：不要把 OSS-Fuzz 那种"24/7 集群长跑"当作目标——那是 1,000 个项目、数万缺陷的量级，靠的是分布式算力与专职团队；单人项目引入它只会得到"跑了一周没有新发现"的挫败，以及一堆无法归因的 crash 报告。

## 对阙疑的3条具体行动

1. **把 oracle 从"档位对"升级为"矩阵对"（本批可做）**：对 holdout 里现存的 catch/miss 逐条登记它依赖的 oracle 类型（`-O0/-O2 差分` / `跨编译器差分` / `断言自报值` / `崩溃` 四类），产出一张"检出面 × oracle 类型"表。**验收判据**：每条 catch 都能指到具体 oracle；**任何"靠人眼判断"的条目必须显式登记为 `human_eye`**（它是当前 81.2% 里最可疑的部分）。这也直接回应论文 Threats：检出率的分母必须能被第三方复算。
2. **用"卡面 harness 化率"作为下一阶段唯一的量化目标**：统计 37 张卡里有多少张能由"一条命令 + 一个断言"独立执行（当前 `artifact_assert` 已具备雏形）。先只做**只读统计**，不引入新引擎；目标是把"可执行卡"比例从现状推进到 100%，并为每张卡补一个**负例**（会失败的输入），因为**只有能被反驳的断言才算可验证**。
3. **建立"三天规则"的 fuzzing 试点，且限定在已知危险区**：选 1 张 UB/并发类卡（例如有符号溢出、fence 类），用 libFuzzer 或一个脚本化差分跑 **72 小时上限 / 单次机器 / 固定 seed**，结束后只回答一个问题："它有没有找到**卡面没写**的反例？"——结果无论正负都写进账本。**禁止**把它扩成 CI 常驻任务：常驻任务会带来"绿灯=安全"的错觉，而 fuzzing 的语义只是"这段时间没发现"（`UNKNOWN`，不是 `PASS`）。

## 盲区

- **检索覆盖有限**：本方向的调研**与本批 5 个方向共用 24 次联网检索**（记录见文末来源清单），远未达到"每个方向 10 次以上深查"的理想密度；数字多取自二手转述（论文摘要页、博客、仓库 README），**未逐篇打开原文核对**。
- **明确待核的数字**：① 1995 年 Miller 复现实验的"约 9%"，凭记忆；② TitanFuzz 的精确缺陷数与覆盖率增益，未核到原文；③ oss-fuzz-gen 的"26 个"（2024-11 博客）与"30 个"（README 累计）口径不同，本文只并列、不合并；④ OSS-Fuzz 的"13,000+ 漏洞 / 50,000+ 缺陷"是 2025 年 5 月的 README 口径，随时间是**单调增长量**，引用时必须带时点。
- **未做任何实测**：本方向没有编译任何 fuzzing 引擎，没有在本机复现任何一个数字；所有工程结论（如"0.59 ms 单卡成本允许全语料多档位跑"）都是**基于项目自报口径的推算**，不是实测。
- **LLM fuzzing 的"真实增益"存疑**：现有公开结果多由引擎作者发布（Google 的博客/仓库、Google 参与署名的论文），缺少独立第三方在**同预算同目标**下的对照；把 LLM 生成说成普遍提升 >X% 目前没有可信证据。
- **采样即偏差**：能被我检索到的失败案例（xz、Cube World、faker.js）都是**足够有名才有报道**的项目，因而本节所有"失败模式"结论都存在幸存者/知名度偏差——真正死于无人知晓的项目不可能出现在检索结果里。
