# 方向 66：时序数据库在验证系统判决账本中的角色（time-series database for verdict logging）

## 核心结论

1. **阙疑 452 条判决账本的数据规模，离任何时序数据库的收益拐点都差 4–5 个数量级。** TSBS 基准的收益区间是"千万级设备、每秒数万到数十万行写入"（TSBS IoT 场景实测 InfluxDB V1.8.10 在 1000 万设备下写入 2.4 万行/秒，DolphinDB V3.00.5 达 40.9 万行/秒）；而 SQLite 单机论坛实测可达 295,000 inserts/秒（sqlite.org 官方论坛帖，2022）。452 条判决即使按每天重跑全部规则生成几千条事件计，写入负载也只有这些基准的约十万分之一。为这个量级引入 InfluxDB/ClickHouse，换来的是额外的守护进程、端口、升级路径和第三方复现门槛——直接违背"独立对账器可不信任内核复算判决"的核心卖点：对账器要在干净环境跑起来，依赖越少越好。

2. **时序数据库的引擎级优化针对的是"等间隔、低基数、数值型 metric"，而判决账本是"不等间隔、高基数、结构化事实+哈希"的事件流，两者的压缩与索引前提互斥。** TimescaleDB 官方文档给出的旗舰压缩手段是 delta-of-delta 编码（等间隔时间戳可从 8 字节压到 1 bit，官方原文 "64x compression"）与 Gorilla XOR；而 InfluxDB 官方文档明确把"把日志消息写进 tag"列为高基数首因（"Writing log messages to tags"），并承认 "High series cardinality is a primary driver of high memory usage"。判决账本里每条记录携带唯一断言 ID、哈希、时间戳——这恰恰是 TSDB 文档警告不要存进 tag/索引维度的东西。

3. **真正值得抄进论文的不是"时序库"，而是"数据库层防篡改账本"的工业化先例：SQL Server 2022 Ledger 与 Google Trillian。** SQL Server 2022 Ledger 的机制与阙疑哈希链账本同构——官方原文："Any rows modified by a transaction in a ledger table are cryptographically SHA-256 hashed using a Merkle tree data structure... The block is then SHA-256 hashed through the root hash of the block, along with the root hash of the previous block"；其 append-only ledger table "block updates and deletions at the API level"。Trillian（Certificate Transparency 的基础设施）则把 inclusion proof / consistency proof 定义成标准概念（RFC 6962）。这两条是论文 related work 与威胁模型小节的现成弹药，比"要不要上 InfluxDB"重要一个量级。

## 精确数字与案例

### 一、四款时序数据库的定位与判决账本适配度

| 数据库 | 最新架构/版本要点 | 核心优化对象 | 对 452 条判决账本的适配度 |
|---|---|---|---|
| InfluxDB | InfluxDB 3 用 Rust 重写，基于 Apache Arrow + DataFusion + Parquet（官方称 FDAP 栈），开源版单进程 | 等间隔 metric 流，低基数 tag | 差。官方文档警告日志型数据写 tag 导致高基数，v2 时代高基数直接拖垮内存 |
| TimescaleDB | PostgreSQL 扩展（非 fork），hypercore 行列混合引擎，Tiger Data（原 Timescale）维护 | 时间分区 + 列存压缩 | 中。好处是"仍是 PostgreSQL"，SQL 兼容；但对几百 KB 数据纯属杀鸡用牛刀 |
| Prometheus | 本地 TSDB，样本按 2 小时分 block，段文件默认上限 512 MB，默认保留 15d，"平均每样本仅 1–2 字节" | 数值 metric 抓取 + 告警 | 极差。官方 storage 文档自述本地存储 "not clustered or replicated"，不是事件日志存储；GitHub issue #8794（2021）请求审计日志功能，至今无原生支持 |
| ClickHouse | 列存 OLAP，ClickBench 的目标负载是 "clickstream and traffic analysis, web analytics, machine learning" | 亿级以上行的聚合分析 | 差。ClickBench 场景与"单写者、逐条 append、按序号验证哈希链"不匹配 |

**关键判断依据（逐字引文）**：Prometheus 官方 storage 文档：*"Note that a limitation of local storage is that it is not clustered or replicated. Thus, it is not arbitrarily scalable or durable in the face of drive or node outages and should be managed like any other single node database."*——注意：官方文档承认它本身就是"单节点数据库"，并未提供账本级的任何完整性保证。Trillian 文档则明确透明日志"通常扮演观察站而非警察"（*"a transparent Log normally acts as an observatory, not as a police officer"*）——账本的可信度来自密码学证明，不来自存储引擎。

### 二、TSBS 实测数字（注意利益相关）

2026-05-27 DolphinDB 官方渠道发布的 TSBS（Time Series Benchmark Suite，github.com/timescale/tsbs）IoT 场景测试，测试环境：Intel Xeon Silver 4216（64 核）、512 GB 内存、3.2 TB SSD，单节点模式；版本为 DolphinDB V3.00.5 / InfluxDB V1.8.10 / TimescaleDB V2.10.1。

| 指标（1000 万设备场景） | DolphinDB | TimescaleDB | InfluxDB |
|---|---|---|---|
| 写入速度 | 40.9 万行/秒 | 19.2 万行/秒 | 2.4 万行/秒 |
| 相对差距 | 1x | 2.1x | 17x |
| 峰值写入（全场景最高） | 69.5 万行/秒 | — | — |

文章原话：*"在 1000 万台设备的场景中，DolphinDB 的写入速度维持在 40.9万行/秒，InfluxDB 则下降至 2.4万行/秒，TimescaleDB 下降至 19.2万行/秒，差距扩大至 2.1倍～17倍"*；查询端标题级数字为"查询差 514 倍"。

**必须标注的偏差**：这是 DolphinDB 自家赞助的市场稿（作者公众号即 DolphinDB，完整报告需加微信索取），InfluxDB 用的是早已停止主推的 V1.8.10，TimescaleDB V2.10.1 也非最新；"17 倍""514 倍"不可作为独立结论引用，只能作为"TSDB 之间的差距在亿级数据上才拉开"的佐证——而这个佐证反而支持"阙疑规模根本不需要 TSDB"。

### 三、高基数问题：判决账本天生是 TSDB 的反模式

InfluxDB 官方文档《Resolve high series cardinality》（OSS v2，2026-09 仍在线）的机制描述与警告逐字如下：

- 机制：*"Each unique set of indexed data elements forms a series key. Tags containing highly variable information like unique IDs, hashes, and random strings lead to a large number of series, also known as high series cardinality."*
- 后果：*"High series cardinality is a primary driver of high memory usage for many database workloads."*（reads/writes 变慢、内存问题；InfluxDB Cloud 中基数超配额直接写入失败）
- 首因黑名单（官方列举的三类常见错误之一）：*"Writing log messages to tags. If a log message includes a unique timestamp, pointer value, or unique string, many unique tag values are created."*

对照阙疑账本：每条判决记录包含唯一的 assertion_id、规则触发组合、SHA-256 哈希片段——如果建模成 InfluxDB 的 measurement+tag，等于把官方文档点名的三类反模式全踩一遍；如果把它们塞进 field，则 TSDB 的核心索引优势（按维度快速过滤时间线）又完全用不上，退化成一个更慢的 KV 存储。**结论：判决账本的数据形态（唯一 ID 密集、逐条哈希、不可聚合）与 TSDB 的性能前提（维度可复用、数值可聚合）结构性冲突，这不是调参能解决的。**

### 四、SQL Server 2022 Ledger 与 Trillian：账本功能的工业化先例

这两个系统证明"append-only + 哈希链 + Merkle checkpoint"已经是主流数据库的**内置功能**，为阙疑的账本设计提供了标准化对照物。

**SQL Server 2022 Ledger**（Microsoft Learn《Ledger overview》逐字引文）：

- 定位：*"The ledger feature provides tamper-evidence capabilities in your database. You can cryptographically attest to other parties, such as auditors or other business parties, that your data hasn't been tampered with."*
- 哈希链生成：*"Any rows modified by a transaction in a ledger table are cryptographically SHA-256 hashed using a Merkle tree data structure that creates a root hash representing all rows in the transaction. ... The block is then SHA-256 hashed through the root hash of the block, along with the root hash of the previous block as input to the hash function. That hashing forms a blockchain."*
- append-only 表：*"Append-only ledger tables block updates and deletions at the API level."* 且 *"don't have a corresponding history table because there's no history to capture"*——SIEM 是其官方列举的目标场景。
- 边界（与阙疑"不依赖内核的独立对账器"直接对应）：*"Ledger can't prevent such attacks but guarantees that any tampering will be detected when the ledger data is verified."* 验证方式：digest（最新 block 根哈希）保存在库外 WORM 存储，验证时重算哈希并与 digest 比对。

**Google Trillian / Certificate Transparency**（官方《Transparent Logging: A Guide》逐字引文）：

- *"The Trillian project generalizes the ideas behind Certificate Transparency, to allow transparent, append-only logging of arbitrary data."*
- 叶子哈希定义：*"The default Merkle hash for a Trillian Log leaf is SHA-256(0x00 | leaf.LeafValue)"*（前缀 0x00 防二次原像攻击）。
- 两种证明：*"An inclusion proof gives cryptographic proof that a particular Merkle tree head includes a given entry"*；consistency proof 证明日志只增不改。对应 RFC 6962。
- 工程边界：*"Trillian can accommodate fairly large leaves, but would struggle with storing multi-gigabyte leaf contents"*（Cloud Spanner 单叶上限约 10 MB）——阙疑单条判决远小于此。

### 五、SQLite/JSONL 的能力边界与"迁移触发条件"

SQLite 的写入能力远超阙疑需求：SQLite 官方论坛帖（2022-02，sqlite.org/forum/info/8455e73e...）作者报告 *"I was able to speed up one to 295,000 inserts per second"*，并评论 *"SQLite is impressively fast"*。452 条判决 + 全量规则重跑也就数千行，事务化写入在毫秒级完成。JSONL 的优势则是零依赖、可直接 `git diff`/`cat` 审阅、对账器可逐行流式读取重建哈希链——这些"可审计的朴素性"对 NeurIPS E&D 的复现审稿人是加分项而非减分项。

时序/列存数据库在这个问题里唯一有意义的用法：**如果未来要做"判决速率随时间的漂移分析"或"规则触发频率热图"**，可以让 Grafana 直连 SQLite（有官方/社区 SQLite 数据源插件），或者干脆导出 CSV 用 pandas 画——不需要部署 Prometheus+InfluxDB 全栈。TSDB 优化的"按时间范围聚合"恰恰是对账器最不需要的操作：对账器要的是全量顺序扫描 + 逐条重算哈希，任何索引都帮不上忙。

### 六、"时间序列 vs 关系型/文档型"的取舍框架，及其在判决账本上的逐项打分

综合本次核实到的官方文档与基准，TSDB 相对通用数据库的收益点可归纳为五项，逐项对照阙疑账本：

| 收益点 | TSDB 的实现机制 | 阙疑账本是否受益 | 理由 |
|---|---|---|---|
| 高吞吐写入 | LSM-Tree / 批量刷盘（TSBS 实测十万行/秒级） | 否 | 452 条判决，写入总量 < 1 MB，写入延迟从不构成瓶颈 |
| 存储压缩 | delta-of-delta、Gorilla XOR、字典压缩（官方称块压缩 90% 以上） | 否 | 判决记录是唯一 ID + 哈希 + 结构化事实，高熵内容压不动；TSDB 字典压缩对"几乎唯一"的值官方自述不奏效 |
| 按维度过滤的时间线索引 | measurement/tag/series key | 反受益 | 官方文档：唯一 ID、哈希、随机字符串写进 tag 会造成高基数，直接拖垮内存——判决记录恰恰全是这类值 |
| 按时间范围聚合查询 | 连续聚合、下采样 | 不需要 | 论文与对账器都不需要"每 5 分钟平均判决数"这类 metric 语义 |
| 保留策略/自动过期 | retention policy | 有害 | 判决账本必须永久保留（append-only 语义），任何自动删除机制都与账本定义冲突 |

结论：五项收益点里两项无关、一项反受益、一项不需要、一项直接有害。这个表本身就是给"要不要上 TSDB"的一劳永逸的回答，可以直接进 research 文档。

反过来，关系型（SQLite/PostgreSQL）与文档型（JSONL/JSON 文件）各自给出 TSDB 给不了的东西：SQLite 给事务、索引和单文件可拷贝的完整性（账本连同 WAL 一起 `cp` 走即可在别处验证）；JSONL 给逐行哈希链的天然载体——第 n 行的哈希进入第 n+1 行，`cat ledger.jsonl | verifier` 就是完整的对账流程，不需要任何数据库驱动。NeurIPS E&D 审稿人复现时，"pip 装零依赖、python 直读 JSONL"与"先装并启动一个 TSDB 服务"之间的差距，就是复现成功率之间的差距。

## 盲区（诚实标注）

- **TSBS "写入差 17 倍、查询差 514 倍"未独立复现且利益相关**：数字来自 DolphinDB 官方公众号市场稿（掘金/搜狐/CSDN 同稿分发），测试用的是 InfluxDB V1.8.10（旧版）与 TimescaleDB V2.10.1，完整报告需私下索取，独立第三方复核缺失。本文只将其用作"TSDB 差距在千万级设备才显著"的佐证。
- **TimescaleDB "压缩 90% 以上"未在官方英文文档逐字核实**：中文镜像文档（docs.timescaledb.cn）写有"压缩时序数据可将数据块大小减少 90% 以上"，dev.to 案例（Logtide 生产数据，150GB→15GB）与 oneuptime 博客称 90–95%；本次抓到的官方英文页（tigerdata.com hypercore 压缩算法页）只给了算法细节与时间戳 delta-of-delta 的 "64x compression"，未给出总压缩率百分比。引用时需标注"厂商口径，非独立测量"。
- **Prometheus "not intended to be durable long-term storage" 一句在 latest 版 storage 文档中不存在**：本次核实到的最近似原句是 "not arbitrarily scalable or durable in the face of drive or node outages"；旧版本文档可能有过更强表述，未核实到具体版本与原文，写论文引用时必须用本次核实到的句子。
- **SQLite "295,000 inserts/秒" 来自论坛个人帖**（2022），非官方基准，硬件、事务批量大小、数据行宽均未知；只用于量级论证，不可进论文正文。
- **未找到任何"审计日志/账本超过多少行值得迁移 TSDB"的直接文献**：行动 1 中的 1,000 万行阈值与第五节迁移触发条件均为本文推断，不是查证的行业标准，需要在 research 文档里如实标注为工程判断。
- **ClickBench 只核实到 workload 描述**（"clickstream and traffic analysis, web analytics..."），未核实 ClickHouse 与 SQLite 在 append-only 小数据集上的直接对比数字；该对比可能根本不存在公开基准。
- **中英文来源的偏差**：四款 TSDB 的选型结论在中文技术社区（CSDN、腾讯云开发者社区、掘金）高度同质化，多篇互为改写、无独立测试数据，本方向刻意只采信官方文档与可溯源基准；英文侧 InfluxData 与 Tiger Data 的"官方对比页"均为厂商自售内容，同样存在立场偏差，本方向未采用其对比页中的性能数字。
- **Trillian 的生产规模数字未核实**：Certificate Transparency 日志的真实体量（数十亿条证书）来自常识背景，本次未打开 CT 官方统计页核实具体条目数，论文引用时需补查 crt.sh 或 Chrome CT policy 页面。
