> 核心命题：**未验证的备份等于没有备份**。本文要用真实事故和真实统计数字证明这句话，并给出阙疑在"单人 + 无预算 + 零运维"约束下可执行的方案。

## 核心结论

1. **GitLab 2017-01-31 事故是"5 种备份机制同时失效"的教科书案例，其根因不是技术，而是"没人负责测试恢复"。** 官方复盘逐字：*"Because there was no ownership, as a result nobody was responsible for testing this procedure."* 具体失效链条：`pg_dump` 备份用了 **9.2** 而生产库是 **PostgreSQL 9.6**（大版本不匹配 → 报错退出）→ S3 bucket 是空的；Azure 磁盘快照**根本没给数据库服务器启用**（*"these snapshots were not enabled for any of the database servers as we assumed that our other backup procedures were sufficient enough"*）；LVM 快照 *"are not really meant to be used for disaster recovery"*；最后只能从 **6 小时前**的手动 LVM 快照恢复，而 staging 环境被限速到 **约 60 Mbps**，拷贝耗时 **约 18 小时**。**删除量约 300 GB，宕机约 18 小时，丢失约 6 小时数据，影响约 5,000 个项目 / 5,000 条评论 / 700 个新用户账号。** 更致命的是失败通知被静默：*"DMARC was not enabled for the cronjob emails, resulting in them being rejected by the receiver. This means we were never aware of the backups failing, until it was too late."*
2. **"有备份"和"能恢复"之间有一条巨大的、被行业数据反复证实的鸿沟。** Veeam 2024 Ransomware Trends Report（**1,200** 份有效问卷，全部来自过去 12 个月至少遭受一次成功网络攻击的组织，2024 年初调研、2024-06-04 发布）：被攻击数据中 **41% 被破坏，只有 57% 被成功恢复**——即 **43% 永久丢失**（新闻稿标题即 *"Unable to Recover 43% of Affected Data"*）；**81% 的组织支付了赎金**，其中 **1/3 即使付了赎金仍无法恢复**；且连续第三年"付了钱但恢复不了"的组织数量**多于**"没付钱就恢复了"的组织。Sophos *State of Ransomware 2025* 补充：全球 **50%** 的勒索攻击导致数据加密（2024 年为 **70%**），而**通过备份恢复的比例只有 54%——是六年来最低**。
3. **对 append-only 哈希链账本，"恢复成功"有一个比校验和强得多的判据：恢复后的账本能通过独立对账器复算出同一个 Merkle root。** 这一条是阙疑相对通用备份实践的**真实差异化优势**，应当写进论文。通用系统的"备份验证"只能做到"文件能打开、行数对得上"；而阙疑的对账器**定义了什么叫"恢复正确"**：不仅字节要一致，**从字节推出的判决必须逐位一致**。这把"备份验证"从"运维动作"升级为"可被第三方复核的科学主张"。**建议把它写成论文的一个小节，标题可以是"Recovery verification as a recomputability claim"。**

## 精确数字与案例

### 一、3-2-1 与 3-2-1-1-0：规则的来源与含义

| 要素 | 含义 | 来源 |
|---|---|---|
| **3** | 3 份数据副本 | Peter Krogh（**摄影师**，非 IT 从业者）于 **2006 年**提出（BackupSec 知识库、HYCU 博客均如此记载） |
| **2** | 2 种不同介质 | 同上 |
| **1** | 1 份异地（offsite） | 同上 |
| **1（新增）** | 1 份**离线 / 不可变**（air-gapped 或 immutable）副本 | 为应对勒索软件新增（BackupSec 知识库逐字：*"专门针对勒索软件新增了两位数字"*） |
| **0（新增）** | 恢复过程**零错误**（zero errors），即**已验证** | Veeam 中文博客逐字：*"Veeam 的 3-2-1-1-0 规则新增一份不可变副本，并校验恢复过程中零错误，增强了对勒索软件的弹性。"* |

**对阙疑的启示（必须诚实）**：3-2-1-1-0 是**面向企业多系统、有专职运维**的规则。阙疑是单人项目，**严格执行 3-2-1-1-0 在成本和复杂度上都不现实**。**应当采纳的是它的"0"**——**零错误 = 已验证**，这一条单人完全做得到，而且因为账本小（452 条判决），**全量恢复验证的成本极低**。

### 二、RPO / RTO：定义与阙疑的合理取值

- **RPO（Recovery Point Objective，恢复点目标）**：可容忍的**最大数据丢失量**。Veeam 官方定义其"最常以秒、分钟、小时或天计量"。
- **RTO（Recovery Time Objective，恢复时间目标）**：故障后系统可宕机的**最长时间**。

**对阙疑的具体建议取值**：

| 对象 | 建议 RPO | 建议 RTO | 理由 |
|---|---|---|---|
| **判决账本（append-only 哈希链）** | **0**（不允许任何一条判决丢失） | ≤ 5 分钟 | 账本是论文核心证据；一条丢失会导致哈希链断裂，**且断链不可修复**（只能标记为"链在此处有缺口"） |
| **知识卡源文件（37 实卡 + 10 草稿）** | 0（git 已提供） | ≤ 1 分钟（本地 git 即可） | 文本文件，git 天然满足 |
| **`gate_engine.py`（3826 行）+ 595 个 .py 工具** | 0 | ≤ 1 分钟 | 同上 |
| **判决的完整可复算环境（Python 版本 + 依赖锁）** | 每日 | ≤ 30 分钟 | 需要 `requirements.lock` + `python --version` 记录；环境漂移是本项目**已存在的硬伤**（227 项工作树漂移） |

**关键洞察**：**RPO = 0 和"每天备份一次"是不兼容的**。如果账本一天只备份一次，那么 RPO 实际上是"最多 24 小时"。**要做到 RPO ≈ 0，必须让"追加账本"和"备份"在同一步完成**——最简单的做法是：**账本每次追加后立刻 `git commit && git push` 到一个异地裸仓库**。这不是"备份系统"，而是**把版本控制当作持续备份**。

### 三、GitLab 2017 事故：5 种备份机制逐条失效

来源：GitLab 官方复盘 *Postmortem of database outage of January 31*（发布于 2017-02-10）。

**时间线（逐字）**：

| 时刻（UTC, 2017-01-31） | 事件 |
|---|---|
| ~17:20 | 工程师对生产库做 LVM 快照并载入 staging |
| ~19:00 | 数据库负载上升（疑似 spam） |
| ~23:00 | secondary 复制开始滞后并失败 |
| **~23:30** | **工程师误在 primary 上执行清空数据目录的操作** |
| 2017-02-01 17:00 | 恢复出无 webhooks 的 GitLab.com 数据库 |
| ~18:00 | 完成最终恢复流程 |

**删除量逐字**：*"The engineer terminated the process a second or two after noticing their mistake, but at this point around **300 GB of data** had already been removed."*

**五种备份机制逐条失效**：

| # | 机制 | 失效原因（逐字要点） |
|---|---|---|
| 1 | `pg_dump` 上传 S3 | 备份脚本用 **pg_dump 9.2**，生产库是 **PostgreSQL 9.6**；*"A difference in major versions results in pg_dump producing an error, terminating the backup procedure."* 且失败邮件因 **DMARC 未启用被接收方拒收**，**两年无人知晓** |
| 2 | S3 快照 | *"When we went to look for the pg_dump backups we found out they were not there. **The S3 bucket was empty**"* |
| 3 | Azure 磁盘快照 | *"these snapshots were **not enabled for any of the database servers** as we assumed that our other backup procedures were sufficient enough."* 另注：*"in one such case it took over a week to restore a snapshot"* |
| 4 | LVM 快照 | *"the produced snapshots are **not really meant to be used for disaster recovery**."* 只有 24 小时前（staging 自动）与 6 小时前（手动）两份可用 |
| 5 | staging 备份 | staging 跑在慢速 Azure classic VM 上，*"throttled to a really low number (**around 60Mbps**)"*，数据拷回生产 **约 18 小时** |

**损失与影响逐字**：
- 丢失时间窗：*"between 17:20 and 00:00 UTC on January 31"*（约 **6–7 小时**）
- 影响规模：*"Our best estimate is that it affected roughly **5,000 projects, 5,000 comments and 700 new user accounts**."*
- 宕机：*"**GitLab.com was down for about 18 hours.**"*
- 未受影响：*"Code repositories or wikis hosted on GitLab.com were unavailable during the outage, but were **not affected by the data loss**."*

**整改措施（与本文最相关的四条，逐字）**：
- *"our main focus is to improve disaster recovery, and making it more obvious as to what host you're using; instead of preventing production engineers from running certain commands."*（**不靠"禁止危险命令"，而靠"让环境可辨识"**）
- *"**LVM snapshots are now taken every hour instead of once per 24 hours.** Enabling Azure disk snapshots is something we're still looking into."*
- 官方 issue **#1102：PostgreSQL 备份恢复的自动化测试**（这是"0 = 已验证"的工程化落地）
- 官方 issue **#1163：指派数据持久性的负责人**（对应根因 *"there was no ownership"*）
- 其他：`max_connections` 从 **8000** 降到 **2000**；`max_wal_senders` 从 3 临时升到 **32**；建立公开备份监控面板

### 五、对象存储版本控制与对象锁（WORM）：官方语义

来源：AWS 官方 *Locking objects with Object Lock* 与 S3 定价页。

| 机制 | 官方逐字语义 |
|---|---|
| **Compliance mode（合规模式）** | *"a protected object version **can't be overwritten or deleted by any user, including the root user** in your AWS account. When an object is locked in compliance mode, its retention mode can't be changed, and its retention period can't be shortened."* |
| **Compliance 下提前删除的唯一办法** | *"The only way to delete an object under the compliance mode before its retention date expires is to **delete the associated AWS account**."* |
| **Governance mode（治理模式）** | *"users can't overwrite or delete an object version or alter its lock settings **unless they have special permissions**"*；绕过需要 `s3:BypassGovernanceRetention` 权限 + 请求头 `x-amz-bypass-governance-retention:true` |
| **Legal hold（法律保留）** | *"a legal hold **doesn't have an associated fixed amount of time** and remains in effect until removed... Legal holds are **independent from retention periods**."* 需要 `s3:PutObjectLegalHold` 权限 |
| **版本控制前提** | *"Object Lock **works only in buckets that have S3 Versioning enabled**."* 且（据第三方 AWS 术语站 awsglossary.org）**Object Lock 只能在创建桶时启用，无法在已有桶上启用**，一旦启用**不能关闭** |
| **保护粒度** | *"retention periods apply to individual object versions. **Different versions of a single object can have different retention modes and periods.**"* |
| **Object Lock 自身是否额外收费** | 据 awsglossary.org：*"There are **no additional charges** for using S3 Object Lock itself"*（**第三方来源，未在 AWS 定价页核实**） |

**S3 最低存储期与最小计费对象（官方定价页逐字）**：

| 存储类 | 最低存储期 | 最小计费对象 |
|---|---|---|
| S3 Standard-IA / One Zone-IA | **30 天** | — |
| S3 Glacier Instant Retrieval | **90 天** | **128 KB** |
| S3 Glacier Flexible Retrieval | **90 天** | — |
| S3 Glacier Deep Archive | **180 天** | — |
| Glacier FR / Deep Archive 每对象额外元数据 | — | **40 KB**（8 KB 按 Standard 费率、32 KB 按 Glacier 费率） |

**提前删除的代价（逐字）**：*"Objects deleted prior to the minimum storage duration incur a pro-rated charge equal to the storage charge for the remaining days."*

**MFA Delete（防"连备份一起删"）**：官方 S3 FAQ 逐字——启用 Versioning + MFA Delete 后，*"two forms of authentication are required to permanently delete a version of an object: your AWS account credentials and a valid **six-digit code** and serial number from an authentication device in your physical possession."* **这是把"删除权"从"知道密码"提升到"物理持有设备"，对单人项目是极低成本、极高收益的一道锁。**

**成本提醒（对阙疑的实际意义）**：阙疑账本体积极小（452 条判决，估计几十 KB 到几 MB），**因此 S3 的存储成本几乎为零**。但要注意 **Glacier 的 90/180 天最低存储期**：如果因为"想省钱"把账本转进 Glacier 然后发现需要频繁读取，会产生**提前删除的按比例收费**和**取回费用**（官方 re:Post 算例：从 Glacier Flexible Retrieval 取回 15,000,000 个对象、共 100 TB，**Standard 取回总成本 $1,774，Expedited 取回 $153,072**——**差 86 倍**）。**结论：阙疑的账本应留在 S3 Standard，不要下沉到 Glacier。**

### 六、SHA-1 与 Git 作为备份介质的一个真实隐患

**SHAttered 事件**：2017-02-23，CWI Amsterdam 的 Cryptology Group 与 Google Research 联合宣布*"the first practical technique"*实现完整 SHA-1 碰撞（`shattered.io`，论文 *The first collision for full SHA-1*）。原始报告称 *"Despite its deprecation, SHA-1 remains widely used in 2017 for document and TLS certificate signatures"*。

**为什么这对阙疑重要**：**Git 的对象寻址（默认）基于 SHA-1**。如果阙疑用 git 作为账本备份介质（见上文 RPO=0 的建议），那么"账本未被篡改"的论证**不能只依赖 git 的对象哈希**。**两条应对**：
1. 使用 Git 的 **SHA-256 仓库格式**（`git init --object-format=sha256`，Git 2.29+ 提供；**版本号我未核实**，见盲区）；
2. 更重要的是：**阙疑自己的哈希链与 Merkle checkpoint 就是独立于 git 的第二套完整性证据**。**这两套证据互相独立，正是"不依赖内核的独立对账器"这一卖点的具体体现**——git 说"字节没变"，对账器说"判决可复算"，两者不可互相替代。

## 对阙疑的 3 条具体行动

1. **【2026-10 前，优先级最高】实现"追加即备份"：每次账本追加后自动 `git commit && git push` 到异地裸仓库。** 具体做法：
   - 在 `gate_engine.py` 的账本追加函数末尾，调用 `tools/ledger_sync.sh`，脚本内容：`git -C <ledger_dir> add -A && git -C <ledger_dir> commit -m "ledger: +1 entry $(date -u +%FT%TZ)" && git -C <ledger_dir> push origin main`；
   - 异地端用 `git init --bare`，可放在**另一个物理磁盘 + 一个云上私有仓库**（两处异地，满足 3-2-1 的"1"并留冗余）；
   - **失败必须显式报错**：脚本退出码非 0 时，`gate_engine.py` 必须打印醒目警告并**把退出码写进本次判决的元数据**。**理由引用**：GitLab 事故的致命点就是 *"DMARC was not enabled for the cronjob emails... we were never aware of the backups failing, until it was too late."*——**静默失败比没有备份更危险**；
   - **时间点**：2026-10 完成脚本；2026-11 起每次运行都自动执行。
   - **这条同时解决 RPO = 0**：账本追加与备份在同一控制流内完成。

2. **【2026-12 前】建立 `tools/verify_restore.py`，把"备份验证"实现为"复算一致性检查"，并接入 CI。** 具体验收步骤（写成可执行的 5 步，输出一份 `recovery_drill_report.json`）：
   - **Step 1**：从异地裸仓库 `git clone` 到临时目录（**不读本地任何文件**）；
   - **Step 2**：校验哈希链自洽：逐条重算 `hash_n = SHA256(hash_{n-1} || entry_n)`，必须与账本记录的链头一致；
   - **Step 3**：用**独立对账器**（不是内核）重算全部 452 条判决，逐条比对四态判决结果，输出"一致 / 不一致"计数；
   - **Step 4**：重算 Merkle root，与最后一次 checkpoint 记录的值比对；
   - **Step 5**：把 Step 2–4 的三个结果（链自洽布尔、判决一致数、Merkle root 匹配布尔）连同 `git rev-parse HEAD` 一起写入 `recovery_drill_report.json`，并**在 README 里贴最近一次的运行日期与结果**。
   - **在 CI 里每周自动跑一次**（GitHub Actions `schedule:` cron）。**理由引用**：GitLab 官方整改 issue #1102 就是"PostgreSQL 备份恢复的自动化测试"；Veeam 数据表明 63% 的组织在恢复时有"重新引入感染"风险——**根源都是恢复路径从未被跑过**。
   - **这一条是本方向最重要的行动**，因为它是"未验证的备份等于没有备份"在阙疑语境下的**可执行版本**，且**直接强化了论文的"可复算"卖点**。

## 盲区（诚实标注）

- **Veeam 2024 报告的关键数字（41% / 57% / 43% / 81% / 1/3）来自新闻稿而非报告 PDF 本身。** 新闻稿明确给出了样本量（1,200）、样本筛选条件（2023 年至少一次成功攻击）与调研时间（2024 年初），可信度较高，但**我未打开报告 PDF 核对分项口径**（例如"41% of data is compromised"的分母究竟是什么）。
- **Sophos 2025 的所有数字（50% / 70% / 54% / 97% / $2.73M→$1.53M / 7%→16% / 35%→53%）全部来自第三方汇总页 brightdefense.com，我没有打开 Sophos 原始报告。** 该汇总页明确在"哥伦比亚"章节被截断，且自称"500+ 统计"，**我无法确认这些数字是否被正确归属到 Sophos**。**论文引用前必须回溯 `sophos.com/en-us/content/state-of-ransomware` 原文。**
- **Fortinet（60% / 4%）、Halcyon（84%）、Varonis（64.8%）三个数字均为二手转引，未核实原始报告。**
- **"Peter Krogh 于 2006 年提出 3-2-1 规则"这一归属来自多个二手来源（BackupSec 知识库、HYCU 博客、techreviewadvisor），我没有找到 Krogh 本人的原始出版物。** 该归属在业内广泛流传，但**严格说属于"未核实"**。论文中若要提，建议写"commonly attributed to photographer Peter Krogh"。
- **CISA `#StopRansomware Guide` 的具体条目我没有打开逐字核对。** 搜索结果显示该指南存在（cisa.gov 与 DoD 镜像，2023-10-19 版本），但**我没有核实它是否明确推荐"3-2-1"或"离线不可变副本"**。论文中引用 CISA 必须逐字核对。
- **S3 Object Lock 的两条结论来自第三方术语站 awsglossary.org，而非 AWS 官方文档**：(a) "Object Lock 只能在创建桶时启用，无法在已有桶上启用"；(b) "Object Lock 本身不额外收费"。**AWS 官方 Object Lock 文档（我实际打开的那份）只说 *"Object Lock works only in buckets that have S3 Versioning enabled"*，没有明确说"不能事后启用"。** 这两条必须回溯 AWS 官方文档核实。
- **Git SHA-256 仓库格式的可用版本号我未核实。** 我只知道 Git 提供了 `--object-format=sha256`，**具体从哪个版本开始稳定可用、是否有已知限制（如与 SHA-1 仓库互操作的约束），我没有查证**。论文中若提及必须先查 `git-scm.com` 官方文档。
- **SHAttered 论文的"full SHA-1 碰撞计算成本"（业界常引用的 6,500 CPU-years / 100 GPU-years 量级）我没有在本次调研中核实**，因此正文中未给出该数字。
- **样本偏差（最重要的盲区）**：本文所有"恢复失败率"统计**都来自企业级、且大多来自"已被成功攻击过"的组织**。**没有任何数据覆盖"单人科研项目"这一规模**。因此本文对阙疑的建议**是从企业实践"缩放到单人"的类比推理，不是实测**。论文中必须写明这一点，不能把 Veeam 的 43% 说成"也适用于像我们这样的项目"。
- **阙疑账本的实际体积我没有测量。** 452 条判决 + 37 张卡，估计在几十 KB 到几 MB 之间（取决于是否内联证据文本）。**"S3 成本几乎为零"这个结论依赖该估计，属未核实。**
