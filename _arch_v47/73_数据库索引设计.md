# 方向 73：数据库索引设计——B+ 树 / LSM / 哈希，最左前缀、选择性、覆盖索引、EXPLAIN，以及"索引会不会破坏可复算性"

> 调研时间：2026-09-29｜调研员：第 8 组（方向 71–80）｜搜索次数：14 次（含 4 次 WebFetch 逐字取数）

## 核心结论

1. **三种结构的代价可以用一张公式表钉死**（TiKV 官方 Deep Dive）：B+ 树写放大 **Θ(B)**（B = 块大小字节数，最坏情况每次插入都要写整个叶子块）、读放大 **O(log_B N/B)**；Level-based LSM 树写放大 **Θ(k·log_k N/B)**（k = 层间增长因子）、读放大 **O((log² N/B)/log k)**。TiKV 原话：*"a data structure can optimize for at most two from read, write, and space amplification"*。**对阙疑的 append-only 账本：写放大 Θ(B) 是常数级，452 条 × 每次一个 4KB 页 = 约 1.8 MB 实际写盘，完全可接受——B+ 树是正确选择。**
2. **"LSM 写放大一定更小"这个共识正在被推翻**：FAST 2022 论文 *Closing the B-tree vs. LSM-tree Write Amplification Gap on Modern Storage Hardware with Built-in Transparent Compression*（Yifan Qiao, Xubin Chen, Ning Zheng, Jiangpeng Li, Yang Liu, Tong Zhang，arXiv:2107.13987，2021-07-27 投稿）摘要逐字：*"the proposed design techniques can **reduce the B-tree write amplification by over 10x**. Compared with RocksDB…, the implemented B-tree can achieve **similar or even smaller write amplification and physical storage space usage**."* **这条对本项目的意义：不要被引擎选型话术带偏，B+ 树（SQLite）不是"过时选择"。**
3. **索引不会破坏可复算性，但"用索引做复算"会**。索引是**派生数据**：只要哈希链的计算输入是**逻辑条目序列**（按 seq 全序），索引的有无不影响结果。真正的三个风险是：(a) 对账器若走索引扫描，索引损坏/被篡改会导致**漏检**；(b) 数据库文件字节布局受索引与 VACUUM 影响，**不能拿 .db 文件哈希当账本哈希**；(c) 索引可被用来构造"看起来正常"的查询结果。**结论：账本的哈希必须基于逻辑语义（canonical JSON 序列化后逐条哈希），对账器强制全序扫描（SQLite 用 `NOT INDEXED` 或按 `seq` 排序读取）。**

## 精确数字与案例

### 一、三种索引结构的代价公式（TiKV 官方，逐字）

| 数据结构 | 写放大 | 读放大（范围查询） |
|---|---|---|
| **B+ 树** | **Θ(B)** | **O(log_B N/B)** |
| **Level-Based LSM 树** | **Θ(k·log_k N/B)** | **O((log² N/B)/log k)** |

三个放大的官方定义（逐字）：
> "*Write amplification* is the ratio of the amount of data written to the storage device versus the amount of data written to the database. For example, if you are writing 10 MB to the database and you observe 30 MB disk write rate, your write amplification is 3."

> "*Read amplification* is the number of disk reads per query. For example, if you need to read 5 pages to answer a query, read amplification is 5."

> "*Space amplification* is the ratio of the amount of data on the storage device versus the amount of data in the database."

TiKV 的关键判断（逐字）：
> "Generally speaking, **a data structure can optimize for at most two from read, write, and space amplification**… a B-tree has less read amplification than an LSM-tree while an LSM-tree has less write amplification than a B-tree."

> "The main purpose for TiKV to use LSM-tree instead of B-tree as its underlying storage engine is because **using cache technology to promote read performance is much easier than promote write performance**."

**哈希索引**：点查 O(1)（内存中），但**不支持范围查询与排序**，且需要能放进内存。对账本上"按 seq 范围拉取第 N–M 条"这种操作直接不可用。

### 二、LSM 写放大的真实量级与"共识被推翻"

- RocksDB 官方 Wiki（2025-01-23 编辑）：*"memtable size inversely affects write amplification: more memory to the memtable yields less write amplification"* —— 即 LSM 的写优势是**用内存换来的**，在内存受限的嵌入式环境会迅速退化。默认 block size **4 KB**，bloom filter 默认 **10 bits/key（1% 误报率）**。
- FAST 2022（arXiv:2107.13987）摘要逐字：
> "The current consensus is that, compared with B-tree, LSM-tree has distinct advantages in terms of storage space efficiency and write amplification. **This paper argues that one should revisit this belief** upon the arrival of storage hardware with built-in transparent compression."
> "…three simple design techniques (i.e., **deterministic page shadowing, localized page modification logging, and sparse redo logging**)… The results show that the proposed design techniques can **reduce the B-tree write amplification by over 10x**. Compared with RocksDB…, the implemented B-tree can achieve **similar or even smaller write amplification and physical storage space usage**."

论文信息：作者 Yifan Qiao, Xubin Chen, Ning Zheng, Jiangpeng Li, Yang Liu, Tong Zhang；12 页；2021-07-27 提交 arXiv；DOI 10.48550/arXiv.2107.13987；USENIX FAST'22 收录（PDF 见 usenix.org/system/files/fast22-qiao.pdf）。

**这组数字对嵌入式方向作者的价值**：它说明"B+ 树 vs LSM"不是简单的新旧之争，而是**硬件假设之争**。在带透明压缩的存储上 B+ 树可以打赢 RocksDB。这是一个能写进简历/面试的、有文献支撑的技术判断。

### 三、复合索引最左前缀、选择性与覆盖索引（SQLite 官方文档，逐字数字）

**覆盖索引定义**（SQLite Query Planner 文档 §1.7）：
> "这个新索引包含原始 FruitsForSale 表中查询使用的所有列 - 搜索词和输出。我们称之为 '覆盖索引'。因为所有必要的信息都在覆盖索引中，所以 SQLite 不需要再查询原始表来查找价格。"
> `CREATE INDEX Idx4 ON FruitsForSale(fruit, state, price);`

**覆盖索引的收益上限（这个数字非常关键，容易被夸大）**：
> "通过在索引的末尾添加额外的 '输出' 列，可以避免引用原始表，从而将查询的二进制搜索次数减少一半。这是一种性能上的**常数因子**改进（速度大约提高一倍）。"
> "但另一方面，这也只是一项改进；两倍的性能提升并不像第一次索引表格时看到的百万倍提升那样戏剧性。而且对于大多数查询来说，**1 微秒和 2 微秒之间的差异可能不会被注意到**。"

**其他官方给出的量级数字**：
- 首次建索引相对全表扫描：*"大约快 100 万倍"*（N/logN 量级，示例表 1000 万行 / 700 万行）
- 普通索引排序：`NlogN`；覆盖索引排序：**与 N 成正比**，且无需大缓冲区
- 一般查询成本：**(K+1)·logN**（K 为输出行数）
- 部分排序示例：**7 个元素**改为 *"5 次对单个元素的排序"* + *"1 次对 2 个元素的排序"*

**最左前缀**：复合索引 `(a, b, c)` 只能被 `a`、`(a,b)`、`(a,b,c)` 的前缀命中；`WHERE b=?` 无法使用。SQLite 文档明确：*"满足 WHERE 子句的行保证是相邻的，因为 WHERE 子句是对索引最左侧列的等值约束"*，且 *"输出保证按状态排序，因为状态列位于水果列的右侧"*。

**选择性（Selectivity）**：定义为 `cardinality / row_count`（不同值个数 ÷ 总行数）。选择性接近 1 说明该列区分度高、适合做索引前导列；选择性极低（如布尔列、状态枚举）的列放在复合索引前导位置会浪费。官方 SQLite 文档未给出"选择性低于 X% 就不用索引"的阈值，**坊间流传的"30% 规则"本次未在任何官方页面核实，不应写进论文**。

**部分索引（Partial Index）**：自 **SQLite 3.8.0（2013-08-26）** 起支持。官方给出使用条件的形式化规则：令 X 为索引 WHERE 子句、W 为查询 WHERE 子句，则**当 W ⇒ X（W 蕴含 X）时可用**。SQLite 用两条简单规则判定（逐字）：
> "1. 如果 W 是 AND 连接的项，X 是 OR 连接的项，并且 W 的任何项都出现在 X 中，则部分索引可用。"
> "2. 如果 X 中的项为 'z IS NOT NULL' 形式，并且 W 中的项为 'z' 上的比较运算符（非 'IS'），则这些项匹配。"
> "SQLite 没有复杂的定理证明器来确定 W⇒X… 并假设所有其他情况都为假。"

**注意**：部分索引的 WHERE 子句**不能包含子查询、对其他表的引用、非确定性函数或绑定参数**——这条限制对账本很友好（非确定性函数会破坏可复算）。

### 四、EXPLAIN 解读（SQLite 官方，逐字输出格式）

| 输出关键字 | 含义 |
|---|---|
| `--SCAN t1` | **全表扫描**（包括按索引顺序迭代全表） |
| `--SEARCH t1 USING INDEX i1 (a=?)` | 只访问子集行，走索引 |
| `--SEARCH t1 USING COVERING INDEX i2 (a=?)` | 走覆盖索引，**不回表** |
| `--USE TEMP B-TREE FOR ORDER BY / GROUP BY / DISTINCT` | 需要临时 B 树排序，**通常意味着缺索引** |
| `--MULTI-INDEX OR` | WHERE 含 OR，走"OR by union"，每个分支一条子记录 |
| `--CO-ROUTINE xxx` / `--MATERIALIZE xxx` | 子查询以协程或物化临时表执行 |
| `--COMPOUND QUERY` / `--MERGE (EXCEPT)` | 复合查询 |

官方警告（逐字）：*"EXPLAIN QUERY PLAN 命令返回的数据仅用于交互式调试。输出格式可能会在 SQLite 版本之间发生变化。应用程序不应依赖 EXPLAIN QUERY PLAN 命令的输出格式。"* 且输出格式在 **3.24.0（2018-06-04）** 有重大变化、**3.36.0（2021-06-18）** 有小变化。

**这条警告对项目的直接含义**：**不要**把 EXPLAIN 输出作为自动化断言写进 CI。要做断言就改用 `sqlite3_stmt_status` / `PRAGMA` 之类的稳定接口，或者只断言"查询能返回正确结果"。

### 五、核心问题：索引会不会破坏可复算性？

**结论：不会——前提是三条纪律。**

**论证**：索引是**派生数据（derived data）**。给定同一组逻辑条目，无论有无索引，查询结果集合相同。可复算性的对象是**哈希链**，其输入是"按 seq 全序排列的、canonical 序列化后的条目"，与物理存储结构无关。因此索引的存在、类型、数量都不改变哈希值。

**但有三个真实风险必须处理**：

| 风险 | 机制 | 对策 |
|---|---|---|
| R1 **索引扫描导致漏检** | 对账器若用 `WHERE card_id=?` 走索引，则索引损坏或被删除时，可能漏掉本应检查的条目而**不报错** | 对账器强制**全序扫描**：`SELECT ... FROM verdicts NOT INDEXED ORDER BY seq`；或按 `seq` 顺序逐条拉取并计数，最后比对总数 |
| R2 **文件哈希 ≠ 账本哈希** | SQLite 数据库文件字节布局受索引、页分配、VACUUM、freelist 影响；同一组逻辑条目可产生**不同字节**的文件 | **账本哈希必须由应用层计算**（canonical JSON → SHA-256 → 链式），**绝不能**用 `.db` 文件哈希或 `PRAGMA` 校验和充当 |
| R3 **索引成为构造性攻击面** | 攻击者可删索引/加索引让"查询看起来正常"，而底层行已被改 | 用 **`UNIQUE(seq)`** 约束保证 seq 单调无缺；用 **触发器** 禁止 `UPDATE`/`DELETE`；用 `PRAGMA integrity_check` 作为辅助（不替代哈希链） |

**一个可引用的工业先例**：Microsoft SQL Server Ledger（SQL Server 2022 起）提供 append-only ledger tables，官方定义逐字：*"Append-only ledger tables, which only allow insertions to your tables"*、*"Append-only ledger tables block updates and deletions at the API level. This blocking provides more tampering protection from privileged users such as system administrators and DBAs."* 其完整性机制为：*"Any rows modified by a transaction in a ledger table are cryptographically SHA-256 hashed using a **Merkle tree** data structure that creates a root hash representing all rows in the transaction. The transactions… are then also SHA-256 hashed together through a Merkle tree… That hashing forms a **blockchain**."* Database digests 需外置到 *"tamper-proof storage, such as Azure Blob Storage configured with immutability policies, Azure Confidential Ledger or on-premises WORM storage"*。

**注意一个诚实的发现**：SQL Server Ledger 文档**完全没有提到索引与账本完整性的关系**（我在该页面检索 `index` 关键词无结果）。这说明"索引 vs 可复算性"是一个**没有被工业界显式讨论过的问题**——这对论文反而是机会：可以把它作为一个明确的贡献点写进 threats to validity / design rationale。

### 六、在 append-only 账本上的索引取舍（具体建议）

| 索引 | 建议 | 理由 |
|---|---|---|
| `UNIQUE(seq)`（或 `INTEGER PRIMARY KEY`） | ✅ **必须** | 保证追加序号唯一无缺，是哈希链完整性的第一道防线 |
| `idx_card_id (card_id)` | ✅ 建议 | 按卡片追历史判决是最常见的查询；card_id 在 37 张卡规模下选择性高 |
| `idx_state (state)` | ⚠️ **谨慎** | state 只有四态（选择性 ≈ 1/4 或更低），走索引收益有限；**建议改为部分索引**：`CREATE INDEX idx_block ON verdicts(card_id) WHERE state='block'`——block 规则 44 条是最高频查询 |
| `idx_ts (ts)` | ⚠️ 视需求 | ts 若精确到毫秒则选择性高；若只到天则低 |
| 覆盖索引 `(card_id, seq, payload_hash)` | ✅ 建议 | 让"拉某张卡的全部哈希"不回表；SQLite 官方称最多快 **2×**（常数因子） |
| 全文索引 / R*Tree | ❌ | 只会增大体积，与账本无关 |

**写放大的实际估算**：SQLite 默认页 4096 B。452 条账本，每条插入最坏写 1 个叶子页 + 每索引 1 个页。若建 3 个索引，写入总量约 452 × 4 × 4096 B ≈ **7.4 MB**（最坏上界）。这对任何设备都不是问题，**但它是 VACUUM/文件布局不确定性的来源**——再次印证 R2。

## 对阙疑的 3 条具体行动

1. **给对账器加一条"强制全序、禁用索引"的硬约束**（时间点：**2026-12 前**）。具体：在 `_arch_v47/tools/reconcile_ledger.py`（或在现有 595 个 .py 工具中新建，命名 `reconcile_strict.py`）中，所有账本读取语句显式写成 `SELECT seq, card_id, state, payload, prev_hash FROM verdicts NOT INDEXED ORDER BY seq ASC`，并在函数开头断言 `SELECT COUNT(*) FROM verdicts` 等于账本声明的条目数。**同时在文件头注释写明 R1 风险**（索引损坏 → 静默漏检 → 判决覆盖率虚高）。
2. **把"账本哈希必须由应用层计算、不得使用文件哈希"写进论文的设计约束小节**（时间点：**2027-03 前**，写入 `research/design.md` 新增小节 D4「Why the ledger digest is computed at the application layer」）。可用的逐字论据：SQLite/LSM 的文件字节布局受索引与 compaction 影响（RocksDB 官方明确 *"memtable size inversely affects write amplification"*，Delta Lake 官方要求 compaction 到 *"at least 128MB"* 文件），因此**字节级可复算只能在应用层语义上定义**。
3. **做一次"索引存在性 vs 哈希链不变性"的实测并出表**（时间点：**2027-01 前**，产物 `_arch_v47/73_index_invariance_test.md`）。实验设计：对同一组 452 条判决，分别在 (a) 无索引、(b) 1 个索引、(c) 3 个索引、(d) `VACUUM` 之后 四种状态下计算 Merkle 根，断言**四者完全相等**；同时记录四种状态下 `.db` 文件的字节数与 SHA-256，展示**文件哈希四次都不同**。这张表能一次性证明"索引不破坏可复算性，但文件哈希不可用"，是可直接放进论文附录的实证。

## 盲区（诚实标注）

- **"选择性低于 30% 就不用索引"未核实**：我在多个来源（mironsoft、Couchbase、CSDN）看到选择性定义 = cardinality/row_count，但**没有任何官方页面给出 30%（或任何其他数值）的阈值**。本文件未采用该数字，论文中也不要引用。
- **FAST 2022 论文正文未细读**：我只取了 arXiv 摘要页（含作者、机构、10× 数字）。正文中的实验配置（具体商用存储盘型号、对比的 RocksDB 版本、具体写放大从多少降到多少）**未核实**。
- **TiKV 的公式是理论渐近分析**，不是实测：Θ(B) 写放大是"最坏情况插入"的上界，实际 SQLite 因 WAL 与页缓存会显著低于此。文中"452 条 × 4 页 ≈ 7.4 MB"是**我的推算，非实测**。
- **SQLite 默认页大小 4096 B 未核实**：方向 71 中"默认缓存 2000 页 × 1024 B"来自中文二手来源，本次仍未在 sqlite.org 官方页确认。本文件的写放大估算依赖此值，需实测修正。
- **SQL Server Ledger 页面未提及索引**：这是"检索无结果"，不等于"官方从未讨论"。可能在其他文档页（如 `ledger-append-only-ledger-tables` 或性能调优页）有相关说明，本次未覆盖。
- **哈希索引部分无官方引文**：我只写了教科书级结论（点查 O(1)、不支持范围查询），没有找到可引用的权威页面；属于常识性内容，标注为无引文。
- **最左前缀规则无官方逐字引文**：我引用的是 SQLite 文档中"最左侧列等值约束"的段落，但标准的"最左前缀原则"表述（MySQL 文档）本次未取到官方原文，引用的 besthub / geekcoder 均为二次来源。
- **EXPLAIN 输出格式的版本变动风险**：官方明确警告输出格式会在版本间变化（3.24.0 / 3.36.0 已变过两次），任何基于其字符串的自动化断言都是脆弱的。
