# 方向105：零信任架构

## 一、先把零信任还原成阙疑要解决的具体问题

零信任不是给系统贴一个“安全架构”标签，也不是把所有服务都搬进一个网格、再加一层登录页。NIST SP 800-207 于 2020 年 8 月发布，它把 zero trust architecture（ZTA）定义为从静态的、基于网络边界的防御，转向保护用户、资产和资源；它明确假设：不能仅因为用户或设备位于内网、属于组织、处于某个地址段，就对其授予隐式信任。身份认证和授权是两个离散动作，应在建立资源会话之前完成。CISA 在 2023 年 4 月 11 日修订的 Zero Trust Maturity Model 2.0，则把目标说得更工程化：在假设网络已经被攻破的前提下，尽量减少不确定性，做出准确、按请求、最小权限的访问决定，并把控制粒度推进到用户、系统、数据和资产之间。对阙疑而言，这个定义不能泛化成“每个接口都鉴权”这么一句空话；它必须回答：谁能提交 C++ 知识卡，谁能看到匿名投稿的原文，谁能运行 gate_engine，谁能修改规则，谁能写入 452 条账本，谁能发布镜像，谁能独立复算，以及某个组件被攻破后能不能继续横向得到其他权限。

阙疑当前的工程锚点是 37 张实卡、67 条规则、9 个保护器、452 条账本记录；brief 还记录了 holdout 30 中真错 17、检出率 66.7%，以及 corpus 40 的 43.8% 口径，但后一个数字存在算术不自洽，不能把它直接写成有效能力指标。零信任首先要保护的不是“网络”，而是这些判决证据及其生成路径：知识卡的 claim、标准版本、编译器上下文、证据 URL、expected verdict、规则版本、运行参数、输出判决、账本 hash 和 Merkle checkpoint。阙疑的核心承诺是“任何判决都要能自述用哪版内核、哪版规则、什么证据跑出来”，因此最危险的不是某个端口没有加 TLS，而是一个看似正常的 CI job、规则文件、容器镜像或投稿处理器以过宽权限改变了判决，再让内部组件互相引用同一份被污染的结果。

这里应使用 “never trust, always verify”，但要准确理解它的含义：不是永远拒绝所有请求，而是不把过去成功、网络位置、容器名称、作者身份、Git 分支或上一次通过当作本次请求的充分条件。每次访问都要基于当前主体、当前设备或工作负载、目标资源、动作、数据敏感度和运行环境作决定；授权之后还要把请求和结果记入可审计记录。least privilege 也不是“给管理员账号少加几个菜单”，而是把权限收窄到资源、动作和时间窗：匿名投稿器可以创建一个待审投稿对象，但不能读取其他投稿、不能调用判决内核、不能写 verified 账本；规则维护任务可以提交候选规则，但不能直接把规则切换为 enforce；CI 的测试 job 可以读代码和 fixtures，但不能获得发布 token；独立对账器可以读已发布的输入、规则快照和账本副本，但不能读写生产账本，更不能调用内核的内部状态。

零信任也不等于把匿名性与身份性混为一谈。匿名投稿的对外语义是“评审者看不到投稿者现实身份”，不是“系统内部没有可审计的主体”。最小实现可以给投稿人生成随机 submission_id 和一次性 bearer token；原文、联系人映射和公开内容分成不同存储，评审接口只接触去标识化后的 claim 与证据。提交动作仍须绑定一个不可逆的 actor_ref、时间戳、内容 hash 和策略版本，actor_ref 不必暴露真实姓名，但必须让系统能判断同一令牌是否重复提交、是否尝试越权读取、是否在审核后继续修改内容。这样既不破坏匿名投稿，又避免“匿名”成为绕过速率限制、审计和撤销机制的万能借口。NIST 的重点是保护资源而非网络段，阙疑的资源边界就是“单条证据、单个判决、单个版本和单个账本事件”，而不是笼统地说“内网里的服务可信”。

## 二、把身份、设备、工作负载和数据策略映射到阙疑

CISA ZTMM 2.0 的五个支柱是 Identity、Devices、Networks、Applications and Workloads、Data，并配套 Visibility and Analytics、Automation and Orchestration、Governance 三项横向能力；它还用 traditional、initial、advanced、optimal 四个阶段描述成熟度。阙疑不应照搬企业清单，而应把五个支柱压缩成能在本地 Python/C++ 验证系统中落地的四类策略对象。第一类是主体身份：区分 submitter、reviewer、rule-author、ci-runner、release-bot、auditor 六种主体，不用一个万能管理员账号。第二类是设备或运行环境身份：记录本机开发、CI runner、Docker 容器和独立复算环境的环境指纹与已验证版本；指纹不是信任本身，只是策略输入。第三类是工作负载身份：每个容器或 job 用自己的短期身份和明确的允许动作，不能因为它叫 `verifier` 就默认读写全部数据。第四类是数据策略：把匿名原文、公开 claim、证据快照、gold verdict、规则快照、运行回执和 append-only 账本分级，并为每类数据写出 read、append、update、delete、export 五种动作的白名单。

在 NIST SP 800-207 的逻辑模型中，Policy Decision Point（PDP）由 Policy Engine（PE）和 Policy Administrator（PA）构成，Policy Enforcement Point（PEP）位于资源访问路径上。阙疑可以做一个极小的对应关系：PE 是纯函数式的策略决定器，输入主体、资源、动作、上下文，输出 allow、deny 或需要人工复核；PA 只发布带版本号和 hash 的策略快照，不直接执行用户请求；PEP 放在投稿 API、规则加载器、账本写入器、CI 发布步骤和独立对账器入口处。不要让每个脚本各自实现一套“差不多的 if”；所有入口都调用同一个、依赖最少的 policy decision 模块，并把 decision_id、policy_hash、subject_ref、resource_ref、action、decision、reason_code 写入审计事件。策略引擎本身也应只返回决定，不持有匿名原文、长期密钥或账本写权限，以免“做决定的代码”同时成为“改结果的代码”。

身份策略的最小版本可以写成如下矩阵，而不是建设一套昂贵的企业 IAM：

| 主体 | 允许读取 | 允许写入 | 明确禁止 |
|---|---|---|---|
| 匿名投稿器 | 自己的提交状态、公开收据 | 新建待审投稿、追加证据引用 | 其他投稿、gold verdict、规则、账本历史 |
| 规则维护者 | 开发集、规则草案、失败样本 | 规则草案和评审请求 | 直接修改 enforce 规则、写生产判决 |
| CI 测试工作负载 | 固定 commit、锁文件、公开 fixtures | 测试回执和构建产物 | 读取私有 holdout、写仓库、读取长期 secrets |
| 判决工作负载 | 已批准规则、指定输入、证据快照 | 新的判决事件 | 删除或原地更新历史事件 |
| 独立对账器 | 发布的输入、规则快照、账本只读副本 | 对账回执到独立输出区 | 调用内核内部 API、改原账本、读取投稿身份映射 |
| 发布工作负载 | 已审计 commit、镜像构建上下文 | 发布不可变镜像和 provenance | 修改源分支、改规则、读取匿名原文 |

设备策略不要误解为“只允许某台电脑”。单人项目可能在 Windows 开发机、Linux CI、Docker 容器和审稿人复现机之间切换；零信任做法是每种环境都重新验证：Python/C++ 版本、锁文件 hash、Docker 基础镜像 digest、工具完整性基线、输入账本 hash 和网络模式。开发机可以运行测试，但不能获得生产发布凭据；CI runner 可以构建，但构建出的产物必须重新由独立验证步骤检查；复现机即使使用同一个 Docker tag，也要按 digest 验证，因为 Docker 官方说明 tag 可以被复用或改变，而 digest 是表示镜像内容的 SHA-256 标识，按 digest 拉取才能保证拿到同一份内容。设备“合格”只代表它满足一组当前条件，不代表该设备之后永远可信。

工作负载策略是阙疑最值得优先落地的部分。把四个职责拆成四个运行面：投稿面只做 schema 校验、大小限制、去标识化和内容 hash；判决面只接收经过批准的输入快照，输出四态判决和理由；账本面只接受经过签名或 MAC 校验的 append 事件，拒绝带有既有 entry_id 的 update/delete；对账面在完全独立的进程或容器中运行，只读取导出快照，重新计算 entry_hash、prev_hash、规则 hash 和最终 Merkle root。它们可以先在一台机器上用不同用户、不同目录和 Docker network namespace 隔离，不必先引入 Kubernetes 或 service mesh。网络隔离只是 PEP 的一层，真正的授权仍由主体、资源和动作矩阵决定。

数据策略必须把“匿名原文”和“可验证证据”分开。投稿原文可能包含个人信息、未公开漏洞或尚未发布的材料，应只在 intake 层短暂可见；进入验证流程后生成 canonical claim、evidence_ref、source_url、fetch_timestamp_utc、content_sha256 和 provenance_ref，判决器尽量只消费规范化后的数据。gold verdict 与 holdout 题面不能出现在公开 Docker 上下文、CI 日志、规则提示和对账器输入中。匿名投稿通过后，公开的应是脱敏 claim、证据 hash、规则版本和聚合结果，而不是原文和身份映射。append-only 不代表任何人都能读；它只要求已写入事件不能被无痕覆盖。读取权限和追加权限必须分开，审计者可以获得只读镜像和 proof，不能因为能查账本就能重新写账本。

## 三、把“永不默认信任”落实到 CI/CD、Docker 和供应链

CI/CD 是阙疑最容易出现“隐式信任”的地方：工作流从一个 pull request 获取输入，调用第三方 action，安装依赖，构建 Docker 镜像，运行测试，然后可能把产物推到 registry。如果整条链只靠“main 分支是可信的”来保护，攻击者只需让一个 PR 分支名、脚本参数、依赖包或 action 改变执行路径。GitHub 官方建议把 GITHUB_TOKEN 默认设为 repository contents 的 read 权限，只在具体 job 中提升权限；官方还指出第三方 action 一旦被攻破，可能接触 workflow secrets、token、共享目录和 Docker socket。因此阙疑的 CI 顶层应是 `permissions: contents: read`，测试 job 不拥有写权限；第三方 action 固定到官方仓库的完整 commit SHA，而不是只写可移动的 tag；能不用 secret 就不用 secret。若未来必须访问云服务，使用 GitHub OIDC 换取短期、范围受限的 token，而不是在仓库中保存长期云密钥。

最小 CI 流程可以只有四个互相隔离的 job。`lint` 读取 Dockerfile、lock 文件和 workflow，检查 `FROM` 是否有 digest、依赖是否带 hash、权限是否过宽、是否出现 `.env` 或金钥；它不接触 holdout。`unit` 在固定 Python/C++ 版本上运行单元测试和独立对账器测试，不上传题面，只上传脱敏后的 JUnit 摘要。`replay` 读取冻结的 452 条公开或已授权快照，验证账本链、规则 hash 和预期 Merkle root，不允许把运行时产生的任意文件回写源目录。`publish` 只在受保护分支、人工批准和前面三个 job 全部通过后运行，生成 SBOM、构建 provenance 和带 digest 的镜像；它不拥有修改源代码的权限。每个 job 设置 timeout，重复 push 时用 concurrency 取消旧任务，避免一个挂死的 job 长时间保留不必要的访问上下文。CI 的绿灯只证明这次运行在当前输入和当前 runner 上通过，不证明外部依赖永远无毒，也不证明结果数学上正确，因此必须同时保存版本 hash 和对账回执。

Docker 侧只做阙疑确实需要的隔离。基础镜像使用 `image:tag@sha256:digest`，不能使用 `latest` 或无 digest 的浮动 tag；构建阶段和运行阶段分开，多阶段构建只把必要的运行文件复制到最终镜像；最终进程使用非 root UID，工作目录只读，运行时不安装包、不下载模型、不访问宿主 Docker socket。构建可以在有网络的受控阶段解析已经锁定的依赖，运行验证则使用 `docker run --network=none`，证明判决与对账不依赖临时网络。Docker 官方文档给出的 digest 逻辑是，内容任何微小变化都会产生不同 SHA-256；这正好可以成为 PEP 的输入：启动对账器前先检查镜像 digest、entrypoint、UID、只读挂载和网络模式，任一条件不符就拒绝运行。不要把 secret 放入 `ARG`、`ENV`、镜像层或构建日志；阙疑当前如果只跑本地和公开 CI，最小方案是“零 secrets”，而不是先搭建一套 secrets manager。

软件供应链不能只检查 Python 包名。NIST SP 800-218 是 2022 年 2 月发布的 SSDF 1.1，它提供了可嵌入现有开发流程的安全软件开发实践；NTIA 的 SBOM 最小要素报告于 2021 年 7 月 12 日发布，要求把组件名称、版本、唯一标识、依赖关系、SBOM 作者和时间等作为供应链记录的基础。阙疑应为内核、独立对账器、Docker 镜像和 CI action 分别生成 SBOM，而不是只提交一个 `pip freeze`。每个依赖记录 package name、resolved version、下载来源、文件 hash、许可证和直接/传递依赖关系；每个镜像记录基础镜像 digest、构建 commit、编译器版本和生成时间；每个 action 记录完整 SHA。SLSA 1.2 已把 provenance 作为推荐的证明格式之一，并将构建轨迹、来源可追溯和产物验证分成逐步增强的安全保证；阙疑不需要声称达到了某个 SLSA level，但可以先保留最小 provenance：source_commit、builder_id、input_digest、dependency_lock_hash、artifact_digest、timestamp 和 verifier_result。

发布不应只把一个 tag 推到镜像仓库。构建器生成镜像后，独立验证器读取镜像 digest、SBOM 和 provenance，检查 source commit 是否来自受保护分支、依赖锁文件是否与提交一致、最终镜像是否含 secret、运行用户是否为非 root、对账命令能否在 `network=none` 下通过。验证成功后，将发布事件追加到账本，字段至少包含 artifact_digest、source_commit、sbom_digest、provenance_digest、policy_hash 和 verifier_ref。Sigstore Rekor 的透明日志提供了记录、检索、完整性验证和 inclusion proof 的思路；阙疑不必一开始依赖远程 Rekor，但可以仿照其“签名事件进入透明、可校验日志”的形态，在本地 append-only 账本上先实现相同的验证接口。供应链零信任的要点是：发布产物也不能因为“来自自己的 CI”而自动可信，消费者仍需按 digest、provenance 和策略重新验证。

## 四、把独立对账器和 append-only 账本做成零信任的证据边界

独立对账器是阙疑区别于普通“跑测试”的关键，但只有在依赖、输入和写权限真正分离时才独立。它不能 import 生产 gate_engine 的内部函数，也不能共享一个会自动更新的规则目录；最小实现是一个纯标准库或极少依赖的只读程序，输入为版本化的 claim/evidence 快照、规则快照、判决输出和账本导出，输出为逐项 diff、输入 hash、规则 hash、对账结果和 verifier_version。内核可以给出一次判决，独立对账器必须以不同实现路径重新计算必要的完整性约束；若二者共享同一份 gold verdict 或同一段“正确答案”代码，得到的一致只是共因污染，不是独立验证。对账器自身也要有身份，但它只有 read-only scope 和 append-receipt scope；它能写一份新的对账回执，不能修改被对账的源账本。

append-only 账本的安全语义要说准确：它是 tamper-evident，不是 tamper-proof。每条事件包含 `entry_id`、`event_type`、`actor_ref`、`utc_timestamp`、`resource_hash`、`policy_hash`、`prev_hash` 和 `entry_hash`；`entry_hash` 由 canonical event 与前一条 hash 计算得到，禁止按 entry_id 原地更新。更正不是删除旧事件，而是追加 `supersedes`、`quarantined` 或 `reverted` 事件，并保留旧事件的 hash 和原因。账本写入器只接受格式合法、prev_hash 正确、actor 具有 append 权限的事件；如果调用者提交一个看似更“新”的完整文件，PEP 应拒绝替换整个账本。读取者拿到的是某个 checkpoint 的只读快照，不能凭读取权限获得写句柄。

RFC 6962 对透明日志的准确表述是“publicly auditable, append-only, untrusted logs”：日志公开可审计、仅追加，而且不能被盲目信任。它还区分两种 Merkle 证明：Merkle audit path 证明某个叶子包含在指定树中；Merkle consistency proof 证明新树保留旧树的前缀，因而没有悄悄改写历史。阙疑有 452 条账本记录时，`ceil(log2(452))` 为 9，RFC 给出的 consistency proof 节点数上界为 `ceil(log2(n)) + 1`，因此审计接口可以把“某条记录在 checkpoint 452 中”“checkpoint 300 是 checkpoint 452 的前缀”变成小型、可独立验证的证明，而不是让审稿人相信一份手工导出的 JSON。这里的数字是证明结构的上界，不是声称当前仓库已经实现了 RFC 全部协议；是否已有完整 inclusion/consistency proof，必须以代码和测试为准。

阙疑的 PEP 应在四个关键位置拒绝隐式信任。第一，规则加载时检查规则包的 commit/hash、签名或批准记录；没有对应策略快照就只进入 shadow，不得 enforce。第二，判决写账本时检查输入快照、规则 hash、运行器身份和前一条 hash；缺一个就 deny。第三，独立对账时拒绝接收内核给出的“最终可信”标签，只读取原始输入和公开规则，自己生成 `recomputed_verdict`。第四，发布时拒绝仅凭 tag、分支名或 CI 成功标记，必须重新核对 source commit、SBOM、provenance、镜像 digest 和审计回执。任何一项核验失败都不应静默降级为 allow；可以返回 `unknown` 或 `needs_review`，并追加拒绝事件。

匿名投稿在这条证据链中也要有明确边界。intake 服务接收原文后计算内容 hash，写入“收到”事件；去标识化处理器生成公开 claim，写入“规范化”事件；评审者只能看到公开 claim 和证据，不可通过 submission_id 反查身份映射；判决器看到的是 claim、证据快照和策略版本，不看到联系人信息；最终对账器只看到已经发布的输入和账本导出。若投稿者在审核后修改原文，系统不能把原事件直接覆盖，而应新建 revision，并让规则明确“哪个 revision 进入了哪个判决”。这使匿名性、可追责性和内容完整性互相配合，而不是把匿名通道变成系统内部的超级入口。

## 五、对阙疑的最小化落地、三条行动与盲区

最小化落地不需要先采购完整零信任平台，也不需要把 3826 行内核改造成微服务。第一步是建立一个本地策略表和一个不可绕过的 PEP：六类主体、七类资源、五种动作，先覆盖投稿入口、规则加载、判决写入、账本读取、独立对账和镜像发布；所有决策输出 `decision_id + policy_hash + reason_code`。第二步是拆分四个工作负载目录或容器：intake、verifier、ledger-writer、reconciler，各自使用独立 Unix 用户或容器 UID；`reconciler` 只读输入并写独立回执，`ledger-writer` 只追加，intake 永远不能写 verified 账本。第三步是把 CI 顶层权限降为 `contents: read`，第三方 action 固定完整 SHA，测试工作流不接触 holdout 和长期 secret，发布工作流只在保护分支和人工批准后运行。第四步是把 Docker 基础镜像钉到 digest、最终镜像用非 root、运行时 `--network=none`，并把镜像 digest、SBOM、provenance 和 source commit 写入发布回执。第五步是给 452 条账本补齐 `prev_hash`、`entry_hash`、actor_ref、UTC 时间戳和 checkpoint 验证脚本；先提供 `--replay`、`--inclusion`、`--consistency` 三个只读命令，再考虑接入 Sigstore 或其他外部透明日志。做到这五步，阙疑已经拥有一个范围很小但语义完整的零信任闭环，而不是泛泛声称“采用了零信任架构”。

对阙疑的 3 条具体行动如下。**第一，先做主体—资源—动作矩阵，并在一个 PEP 中集中执行。** 在 `queyi-core` 或 CPP-Bible 的现有工具边界内新增最小策略模块，禁止匿名投稿器、规则作者、CI runner、判决器、独立对账器和发布器复用同一高权限身份；每次 allow/deny 都追加审计事件。验收标准不是“有配置文件”，而是三个负测试必须失败：匿名 token 读取其他投稿失败，CI job 写生产账本失败，独立对账器修改输入账本失败。**第二，建立供应链与发布零信任链。** 为 Python/C++ 依赖、Docker 镜像和 CI action 生成 SBOM，锁定依赖 hash，基础镜像使用 digest，action 使用完整 SHA，CI 使用 `contents: read`；发布回执绑定 source commit、policy hash、SBOM digest、provenance digest 和 artifact digest。验收标准是换一个 tag 但不换 digest、修改一个依赖 hash、把运行网络打开或把容器改成 root 时，独立验证器均拒绝。**第三，把独立对账和 append-only 账本变成论文可复核证据。** 对 452 条既有事件先做只读迁移检查，报告缺失字段和 hash 链断点；对每个新 checkpoint 生成 inclusion/consistency proof，CI 中运行内核与独立对账器的差分回放，并把失败作为硬门禁。验收标准是第三方在不导入 gate_engine 内部模块、不读取匿名身份映射、不获得账本写权限的情况下，能够用 Docker 在 `network=none` 下复算同一输入并验证同一 checkpoint。

这些行动有明确边界。NIST SP 800-207 的正式发布日期是 2020 年 8 月；CISA ZTMM 2.0 页面确认五个支柱、三项横向能力和四个成熟度阶段，但它是路线图，不等于阙疑必须实现企业级 IAM。NIST SP 1800-35 的 2025 年实践指南展示了 19 个 ZTA 示例实现，并由 24 个协作者参与；这些规模只能说明企业实施复杂，不能推导出阙疑需要 19 套产品。NIST SP 800-218、NTIA SBOM 和 SLSA 能提供供应链术语及证明方向，但不能证明某个依赖没有后门。Docker digest 能保证引用的内容地址不变，不能保证该内容本身没有恶意代码；GitHub OIDC 能减少长期密钥，不能让不可信 workflow 自动安全。RFC 6962 的 Merkle proof 能证明包含和追加一致性，不能阻止第一次写入错误判决；“append-only”也不能替代独立对账。brief 中的 66.7% 来自 17/30，样本很小；corpus 40 的 43.8% 算术口径尚未修复，不能用零信任语言包装成性能结论。
