## 1. 回路组成（读码 + 实测）

日常回路 = **两段 pytest + gate + poison**（来自 `pyproject.toml` 注释与 `quality_gates` 清单）：

1. `pytest -m "not slow" -n auto` —— 纯逻辑并行（fast）
2. `pytest -m slow -n0` —— 共享真实仓库状态，串行（slow）
3. `tools/gate_engine.py --check` —— 原子内核门禁（63 规则）
4. `tools/poison_drill.py` —— 毒样例对抗回归

> 读取：`tools/gate_engine.py`、`tools/mutation_fuzz.py`、`tools/atom_evidence_replay.py`、`pyproject.toml` 的 `[tool.pytest.ini_options]`、`tests/conftest.py`。

`conftest.py` 用**模块级** `SLOW_MODULES` + `SERIAL_EXTRA` 给测试打 `slow/fast` 标记（508 任务1）。分类语义是"是否调编译器 / 跑 replay / 跑 poison"，**不是按墙钟**。

## 3. 攻击既有结论（纪律②：先找错、先找反例）

- **`pyproject.toml` 注释"fast ~10s / slow ~140s"** → 实测 **70s / 203s**，两处都错。注释是过期假设，不是事实。
- **`conftest.py` 大段论证"`-n auto` 对 not slow 安全（~10s）"** → 实测 70s，且 fast 阶段里混着**重 replay/fuzz** 测试（`test_mutation_parallel_580`、`test_mutation_isolation_579`），它们本应属 slow 却漏分进 fast，既撑大 fast 又触发锁竞争。
- **`_worklog_580.md` 验收声称 "poison 118/118 ✓ / replay confirm=56 refute=0"** → 实测 `poison_drill.py` **直接崩溃**（`_REPLAY_LOCK` 不存在）。声明与当前工作树**矛盾**：要么依赖文件没改、要么改了又被冲掉。这是既有结论"已完成"被实测推翻的硬反例。
- **隐含假设"回路已绿"** → 实测 fast 7 失败、slow 1 失败、poison 崩溃，回路非绿。

## 4. 为什么 fast 不是 10s 而是 70s

`test_mutation_parallel_580.py`、`test_mutation_isolation_579.py` 是**重 replay/fuzz** 测试（单个 18–25s），但**不在** `conftest.py` 的 `SLOW_MODULES` / `SERIAL_EXTRA` 里 → 被划进 fast 并行阶段。后果：

1. fast 墙钟从"纯逻辑应有"被撑到 70s；
2. 这些测试在 `-n auto` 下与共享 `build/.replay_lock` 的其他模块抢锁，正是 fast 阶段失败的来源之一（另因 `_REPLAY_LOCK` 陈旧引用，见 §5）。

## 6. B3 / B4 当年为什么没落地（读码结论，非附和 worklog）

- **B4（gate 索引化 / frontmatter 缓存键改内容 sha）**：本仓 frontmatter 解析在 `atom_evidence_replay.parse_frontmatter`（gate_engine 复用）。cProfile 显示冷启重解析仅 ~1.3s，且属"每次进程冷启"问题——**ROI 上限 ~1.3s / 回路（gate 每回路只跑一次）≈ 全程 0.5%**。加上缓存必带失效处理（见 02 ESLint 先例），收益小、风险在。故当年没做是合理工程取舍，不是疏漏。
- **B3（受影响测试选择）**：本仓**没有任何 change→test 依赖图**。测试读的是 atoms/evidence/tools，不是 C++ 源文件；一次原子 frontmatter 改动可能影响多条 gate 规则 + replay 判决，无法靠"改了哪个 .py 就跑哪些测试"判定。B3 落地前提（依赖图 + 漏捕率证明）在 560 轮时都不具备，故没动。
