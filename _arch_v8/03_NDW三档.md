# 03 NDW 三档 · 现在做(N) / 攒数据(D) / 等条件(W)

检索日期：2026-09-18 ｜ 纪律③：算不出/没实测的明说"缺数据"，不填数。
纪律红线：**凡是会动到真编译判决、会让"没查成"冒充"查过"的，一律放 W，不许放 N。**

> 前提（见 00/01）：回路当前 RED，最大单测 79.4s，fast 70s/slow 203s/gate 3.8s/poison 崩溃。
> 残酷事实：**N 档里没有任何一项能"砍掉"测试时间**——那需要 W 档的 B3。N 档只做"重新分区 / 编排内联 / 固化基线"，不跳过、不伪造。

---

## N 档（现在就能做、弱模型可施工、零 Oracle 风险、有机器验收）

### N1 · 把漏分的重测试移回 slow
- **改文件**：`tests/conftest.py` 的 `SLOW_MODULES` frozenset，加入
  `test_mutation_parallel_580.py`、`test_mutation_isolation_579.py`、`test_replay_lock_serial.py`。
- **为什么零风险**：只是把测试从 fast 阶段挪到 slow 阶段，**同测试同跑、同判决**，总节点数不变。不改任何判决逻辑。
- **验收（机器可判）**：
  - `pytest -m "not slow" -n auto --durations=15` 总墙钟**下降**（70s → 真·快子集）；
  - `pytest --co -q | tail` 节点总数**不变**；
  - `pytest -m slow -n0` 墙钟**等量增加**；
  - gate / poison 判决文件（如 `build/gate_report.json`）**逐字不变**。
- **回退**：`git revert` / 删一行 frozenset 即可。
- **注意**：不解决 RED（`_REPLAY_LOCK` 失败仍在）；只让 fast 变回"可用快速反馈"并停止把锁竞争测试塞进并行阶段。

### N2 · gate 外层循环 in-process 复用（中等改动）
- **改文件**：`tools/cppbible.py` 的 `cmd_check` 外层循环。对 `gate_engine` 这类"内部已带进程内缓存"的门禁，改走 import-in-process 而非子进程；warm 路径实测已存在（<0.5s，见 01 cProfile）。
- **为什么低风险**：gate 仍只跑一次，退出码 / 报告 JSON 与子进程版等价；省的是一次 Python 冷启（~3s）。
- **验收**：`cppbible check` 退出码 0、生成的 `build/gate_report.json` 与子进程版**逐字一致**；整条 check 墙钟下降 ~3s。
- **回退**：revert `cppbible.py`。
- **风险标注**：改动编排层，属"中等"而非"一行"；需先确认所有被内联的门禁都无进程级副作用。

### N3 · 固化本次实测基线（零风险、纯记录）
- **改文件**：新建 `_arch_v8/bench_baseline.json`（本调研已附数字；可落盘）。
- **内容**：fast 70.2s / slow 203.4s / gate 3.8s / poison 崩溃 / 最大单测 79.4s + 检索日期 + 环境（32 核、`.venv` 3.13.13）。
- **为什么有价值**：以后任何"压缩"提案都必须用这组数据做**可量化验收门槛**（快了多少、判决逐字不变怎么证）。
- **验收**：文件存在、数字可复现（`pytest -m ... --durations` 重跑对比）。
- **回退**：删文件。

> 以上 N 档**都不触碰真判决、都不让"没查成冒充查过"**，符合红线。但坦白：它们省的时间有限（N1 重新分区不省总时；N2 省 ~3s；N3 不省时）。真正的"大头"在 W 档。

## D 档（攒数据，为未来升 N 做准备）

### D1 · 建 change→test 依赖图 + 漏捕率
- **干什么**：扫描哪些测试读哪些 atom/evidence/tool（静态 + 覆盖率插桩），构建依赖图；用历史回归做回放，量化"按变更只跑子集"能跳过多少、又会不会漏掉曾捕获的回归。
- **为什么必要**：B3 是否安全完全取决于此。testmon 已证明动态语言下漏选真实存在（02-A）。
- **验收**：依赖图覆盖率报告 + "全量周兜底能兜住的历史回归清单"。
- **产出**：决定 B3 能否升 N 的数据。

### D2 · 剖析 79.4s `test_task_queue_stateful`
- **干什么**：测 `--hypothesis-max-examples` 与 trap 捕获率曲线，找"捕获率不降"的最小样例预算。
- **为什么必要**：这是 slow 的 39%。若能证明某 budget 下捕获率不变，未来可升 N（证明等价而非偷减）。
- **验收**：捕获率随 examples 的曲线；选定 budget 下 trap 捕获 == 全量。
- **当前状态**：**缺数据**，未测。

### D3 · B4 内容哈希索引原型 + 失效证明
- **干什么**：给 gate 做 `内容 sha` 索引（frontmatter 键改内容哈希），测 (a) 冷启省时；(b) **规则集/工具版本变更时索引是否自动失效**。
- **为什么必要**：ESLint 已证明缓存不自动失效会静默削弱判决（02-B）。(b) 不证明前 B4 留 W。
- **验收**：(a) 省时数字；(b) 注入规则变更后索引必重算、旧结果不被复用。
- **当前状态**：ROI 上限实测 ~1.3s（01 cProfile），性价比低。

## W 档（等模型或条件；凡能动真判决 / 让"没查成冒充查过"的一律 W）

### W1 · B3 受影响测试选择（跳过判决测试）
- **归 W 理由**：跳过 verdict-bearing 测试 = 削弱可信度，正中红线。在 **D1 证明完备性 + 全量周兜底**前禁止。
- **条件**：依赖图完备、漏捕率可证、周兜底已上 → 才可能升 N。

### W2 · B4 网关缓存 / 索引化
- **归 W 理由**：缓存失效会静默让"没查成冒充查过"；且 ROI 仅 ~1.3s（01 实测）。
- **条件**：D3 证明"内容哈希 + 规则集版本"键能正确失效 → 才考虑，且收益仍小。

### W3 · "每次编辑只跑 fast / 跳过 slow" 的回路策略
- **归 W 理由**：跳过 slow 里的 replay / mutation 判决 = 直接削弱可信度。
- **条件**：无（本质是偷减，除非 D1/D2 证明子集等价）。

### W4 · 砍 79.4s stateful 测试的样例数
- **归 W 理由**：在 D2 证明"捕获率不降"前，减 examples = 可能放过真回归。
- **条件**：D2 证明等价预算 → 升 N。

## 总结（给决策者的三句话）
1. **回路先修绿**（580 未完工的 `_REPLAY_LOCK` 连带改），否则"压到绿"是空话。
2. **安全可做的 N 档只做重新分区/编排内联/固化基线**，省时有限但不伤判决。
3. **真能砍时间的是 B3，但它必须等 D1 数据证明不漏捕**；B4 性价比低且带失效风险，建议长期 W。
