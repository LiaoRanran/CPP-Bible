# 562-03 · 没有终极可信底座时怎么收敛：架构含义与现在就要留的口子

> 检索日期 2026-09-17。本文回答：既然底座不存在（三个方向的 2025-26 形式化结果），为什么系统必须开放/可推翻/单调收敛；哪些设计现在就要留口子。

## 1. 先论证"不存在终极底座"（把话说死）

**【事实】三条独立的形式化路线，2025–2026 各拿到新结果**：
1. **计算层**：内对齐验证不可判定——归约到停机问题与 Rice 定理（Alfonseca et al., *Nature Scientific Reports* 2025）；完整版进一步：开放域动态不可判定（Rice）、静态框架撕裂"真/可证"（Gödel）、"逃进有限世界"撞 Trakhtenbrot 墙（有限有效性 co-RE-完全）（[arXiv:2606.28639v1, 2026-06](https://arxiv.org/html/2606.28639v1)）。
2. **物理层**：Gödel + Tarski + Chaitin 信息论不完备 ⇒ 全算法化的"万物理论"不可能（[arXiv:2507.22950v1, 2025-07](https://arxiv.org/html/2507.22950v1)）。【类比】某一天连物理定律的完备算法表述都不可得——依赖"某天会有终极验证器"的架构假设本身就是反数学的。
3. **实践层**：Refutability Gap——AI 科研的当前验证即使不做形式化也大面积失效（训练数据不可查、模型漂移、反事实缺失）（[arXiv:2601.02380v3](https://arxiv.org/html/2601.02380v3)）。

**结论**：【推断】任何"用 A 验 B"的链条都不可能找到一个"自身不需要被验"的终点。这不是工程债，是数学事实。因此元系统的正确目标不是"建一个可信底座"，而是**建一个在底座不存在时仍能单调收敛的装置**。

## 2. 为什么"开放 + 可被推翻 + 单调收敛"是唯一自洽的形态

**推导（三段，每段可检验）**：
- P1（由 §1）：任何验证者 V 都可能被下一个 V' 推翻（V' 更强或 V 有盲区）。
- P2（由 P1）：若系统把 V 的判决当永久真理（不可替换），则系统误差不会小于 V 的误差，"更强者到来"时只能整体废止——知识生产史的历史形态（地心说、以太）。
- P3：若系统把"V 的判决"记为"当前最强证伪者下的暂定状态"（可替换、可回退、错误率单调收敛于 V 的可达最优），则 V→V' 迁移只损失"放权"而不是损失"知识"（因为知识本就是暂定态）。
- 结论：**系统必须把"被推翻"设计为正常操作**（不是事故）。阙疑的"状态可回退、放权门 exit 立即生效、suspect 级联"就是 P3 的实例化。

**"单调收敛"的正确含义（容易说错，说清楚）**：【推断】不是"错误率必然降到 0"（不可能，§1），而是三条可操作性质：
(a) **错误率随验证者强度单调不增**：更强的 Oracle 只允许减少已接收的假命题（需要"可替换 Oracle"接口）；
(b) **错误不可藏**：每次逃逸必须留下案例（毒样案例库/逃逸库/失败报告），使同一类错误不会第二次以新形态通过（需要错误暴露机制）；
(c) **回退成本不随规模爆炸**：放权门 exit 立即生效、suspect 级联列出（不需要人工重审全部知识），使"推翻"是局部操作（需要依赖闭包与级联标记）。

## 3. 由此"现在就要留的口子"（按 562 纪律：小而确定）

### 3.1 可替换 Oracle（接口级，不是实现级）
- 现状【事实】：replay 的 Oracle 抽象到"编译器+命令"程度（`command` 字段+`_pin_compiler`），但没有"同一条命题的第二个 Oracle"概念。
- 口子：命题验证记录里增 `verified_by_oracle: {toolchain_id, method, policy_version}`——**现在只写不读**；当出现第二个可用 Oracle（例如 Clang 矩阵或 z3/SMT 通道，561 正在调研）时，不必改 schema 就能挂第二验证者。
- 机器验收：56 卡全量 replay 后，每卡 verdict 记录都带 oracle 身份（哪怕只有一种）；schema 不破坏旧卡。

### 3.2 可换更强验证者（放权门的物理分离）
- 现状【事实】：放权门（G-iso 等）在蓝图里，判据写在文档；进入/退出条件已可计算但未绑定"验证者版本"。
- 口子：每个门的 enter/exit 判据必须引用**验证者版本**（"G-iso ON 前置 = 对当前 Oracle 版本的 56 卡 0 误伤"），使"换 Oracle"自动作废全部开启的门（fail-closed）。这与 532 §四"矩阵由开关触发，不允许提示词改"一致。
- 机器验收：人为改 `toolchain_id`（模拟换 Oracle）→ 所有 ON 的门自动回 OFF（pytest 钉）。

### 3.3 单调收敛的可观测（把"收敛"变成数字）
- 现状【事实】：metrics.jsonl 有 gate/poison/replay 计数，有断流（560 已发现，E-3 待修）；**没有**"逃逸率/误伤率的时间序列"。
- 口子：三张曲线进 metrics：①每批 mutation 逃逸率（暴露率）=逃逸数/生成变体数；②每次 Oracle 升级后"旧判决被推翻数"；③毒样例库规模 vs 逃逸中位生存时间。三条都不需要新基础设施。
- 机器验收：连续 3 批数据存在且可画趋势；出现"逃逸生存时间上升"自动告警（说明验尸流程失效）。

### 3.4 "被推翻"的一等公民化（管理流程，非代码）
- 现状【事实】：有 refute 三分类、有 status_history、有 golden 四桶；但"某命题被更强验证者推翻"这条**事件类型**没有专属通道（现在混在 refute/suspect 里）。
- 口子：任务队列增事件 `overturned_by_stronger_verifier`（task_state/events 已有 append-only 表，534 已建）；每次发生必须留：旧判决者、新判决者、推翻证据锚点、影响面（suspect 列表）。以后统计"平均被推翻滞后"（发现旧错误用了多久）——这是系统健康度的核心指标。
- 机器验收：一次人工模拟推翻走完全链路：事件落库 + suspect 级联列出 + metrics 计数 +1。

## 4. 反例检验（这套论述会被什么推翻）

- 若未来出现"数学上被证明完备的验证方法"（比如某 NP 完全问题的 P 解法,或某形式化体系被证明同时完备自洽）——那么 §1 的 P1 反例成立，本架构的"必须开放"不再是必然，只是保险。**目前所有证据反向**（§1 三条）。
- 若"单调收敛"在实践中无法维持（例如模型每次换代都让旧判决大面积失效、成本爆炸）——那说明 P3 的成本假设错了。这正是 534 的 reverify_model type 和模型 canary 批次要测的东西：**"被推翻滞后"分布若是重尾，收敛性存疑**。
- 诚实边界：【推断】"错误率单调收敛"目前是**架构目标而非实测事实**——阙疑当前 56 卡/27 原子规模太小，统计上还看不到"率"的收敛；三条曲线（§3.3）是把它变成可验证主张的最小工具。

## 5. 一页总结（可贴墙）

1. 底座不存在（三条形式化结果，2025–26）——不是遗憾，是设计前提。
2. 正确目标：不是找底座，是让"被推翻"成为正常运行、让误差只在"暂定态知识"的边界上流动。
3. 收敛的三条操作含义：更强验证者单向减少假命题；错误不可藏；推翻是局部操作。
4. 现在就留的四个口子：Oracle 身份进判决记录（只写不读）、放权门绑验证者版本、三条收敛曲线进 metrics、`overturned_by_stronger_verifier` 事件通道。
5. 防呆：一切"等某个终极验证技术出现再收敛"的路线（形式化万物/单点数学归约/终极编译器）与 §1 冲突，不在任何路线图上立项。
