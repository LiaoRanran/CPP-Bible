## 二、模型上限态（真实判断）

1. **阙疑文档结构——模型能设计全套，且应与书文档显式分离**。最小必要集：
   - README-元系统（一页：阙疑是什么/四部件 gate·mutation·poison·trust/当前数字表/
     复现入口）；
   - ARCHITECTURE（数据流图：卡→frontmatter 解析→规则判决/真编译→报告；信任根链）；
   - REPRODUCE（命令清单 + 期望输出 + commit/工具链 id）；
   - KNOWN-LIMITS（machine-untriggerable 3、活雷 29+1、manifest 口子、统计口径）；
   - API/CLI（各工具 argparse 参数，部分 docstring 已含）。
   卡点纯工程；内容素材全部已在 worklog/_arch，模型做的是归并不是新研究。
2. **一键复现 `make repro`——模型能写规格，但编排链有顺序约束**：
   全量 v7 mutation（198s 级）→ gate+poison+replay 验收 → 逃逸率/命中数 →
   selfcheck 确定性闸；每步比对应机器化。两个真实卡点：① 全量 mutation 耗时
   使"一键"在日常不现实，应分 `repro-fast`（增量+小卡集 selfcheck）/
   `repro-full`；② Windows .bat 与跨平台（投喂词多处 Linux CI 语义）需两条脚本
   或 Python 单入口（更合理）。
3. **活文档——格式与校验模型都能设计**：
   数字块形如 `blocked=1378 [repro: cmd | commit d36d5c8]`；每条强主张带
   "可证伪条件"（如"若 v7 与 commit 自报数不符则本文档失效"）。校验法：
   文档内嵌命令由检查器抽出来跑、比对捕获值——技术=doc_lint 思路扩展
   （doc_lint 已能对 docs/kernel 做数字核对，改成通用抽取即可）。
4. **文档-代码一致性——已有半个机制**：gen_metrics --check 守护 README 书数字
   （README 声明，本轮未实测）、doc_lint 守规则名/工具名；缺口是这些机制各自
   为政且覆盖面不含 worklog/_arch。统一化纯工程。
5. **对外演示——我给判断**：非技术受众理解"阙疑"的最佳形态是**一条变异的
   可视化时间线**（原卡→注入弱化→门禁变红/静默；对比无防护系统）——交互式
   HTML 单页即可，素材=现有 v6 escaped/blocked 实例。技术上模型可产出大纲与
   数据 JSON；真实"视频/在线 playground"成本高且单用户无托管，静态 HTML 是
   诚实的上限。

## 四、卡点与解冻信号

1. **文档归并——纯工程，但应在 v7 冻结后做**（否则文档抄的数字立刻过期，
   重蹈本轮发现的 v6 时效问题）。信号：v7 落地 + 数字带 commit 写入。
2. **一键复现——工程+耗时权衡**。信号：fast 档 <60s 跑完全部闸并产出数字表；
   full 档人工/nightly 触发。
3. **对外托管——单用户结构性**。信号：无（静态文件可直接分发/挂 GitHub Pages，
   远端本身也是带外信任源）。
4. **旧文档误导风险**：AGENT.md 已自标历史，但 GOVERNANCE/README 无显式时效头，
   新 agent 可能读错——本轮证据：AGENT.md 的自标注是好惯例，应推广（纯文档纪律）。

## 五、本维度自由探索

1. **"文档即代码"与维度11 A1 发现是一体两面**：文档能驱动 agent 行为 ⇒ 文档
   需要完整性；文档需要防过期 ⇒ 数字需要可复跑。当前两个机制都只建了一半。
2. **worklog+_arch 事实上承担了架构文档职能**（43+多轮目录），但检索靠文件名
   记忆——log_query.py（tools/log_query.py 存在）类工具可扩展为跨调研检索，
   纯工程。
3. **演示性最差的环节是"信任根为什么是自己"无法靠演示消除**——演示能展示
   机制强度，不能把结构性限制讲成优势；诚实的演示必须把缺口页与能力页并列。
