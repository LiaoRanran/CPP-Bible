## 二、模型上限态（真实判断）

1. **B3 受影响测试选择——模型能建图与度量，"零漏捕"宣称理论上可达但当前数据
   完全不支持**：
   - 模型可做：① change→test 依赖图（静态：测试文件读取的工具/数据路径反查，
     纯 AST/文本分析，不执行跳过）；② 漏捕率度量——历史上"跳过测试后仍发生
     失败"的事件回放。589 任务4a 只建图不跳过是正确顺序【一方称】。
   - 宣称"零漏捕"的条件：依赖图必须对每条测试的**全部**读取/依赖面完备
     （含动态 import、配置驱动路径、共享 fixture）——Python 动态性使静态图
     原理上可能不完备，只能用统计上界兜底，不能证明零漏。
   - 外部实证：T-TS（arXiv:2509.10279，2025-09-12，【检索 2026-09-19】）
     在工业线上只选 15% 测试、提速 5.9×、检出 >95% 失败——**不是 100%**，
     且刻意不用覆盖率图（用变更文件 BoW）。这是行业给出的真实边界：5% 漏检
     量级，且需大量历史数据训练。单用户无此数据量，模型内最多做到"静态图 +
     小规模回放估漏"，漏捕率上界算不出精确值（缺历史跳过事件）。
2. **replay/golden --jobs（B2）——强规格模型可写，确定性风险可构造性控制**：
   mutation 侧 --jobs 已证明"worker 独占根 + 串行顺序重排 ⇒ 判决逐条相等"
   （投喂词；v6 root_fingerprint_ok=True 本轮【已查证】）。replay 侧同范式
   可行：每 worker 独立工件根（沙箱已支持 Examples 复制）+ 卡级锁
   （_replay_lock_path 已备）+ 结果按序重排。卡点是纯工程规格量，不是模型
   能力；风险在"共享 manifest 写入"，需分片锁，投喂词已点出。
3. **stateful 79.4s 样例最小化——模型能设计 delta-debugging 流程**：
   先静态读 test_task_queue_stateful.py（370 行）确认其判决面（8 场景见
   投喂词：taskkill/F 断点续跑、并发 claim、touch 冲突、yield 切换、验证失败
   恢复…）。样例最小化方法（DD/min CFS）模型可跑（需写盘执行——属工程批），
   但该测试验的是**状态机+真实进程**，样例数减少到判决力以下就失去意义；
   最小预算 = 每状态迁移/每竞态至少 1 个样例，预计可压缩 30-50%（判断，
   未实算），79.4s → 约 40-55s（判断）。
4. **真编译物理下限的模型内空间**：
   - ccache：已在系统内（_resolve_ccache/_wrap_ccache，
     atom_evidence_replay.py:395-430）——但 ccache 命中替代编译时，Oracle
     实际是 ccache 而非 gcc；系统用工具链指纹+preprocessed hash 兜住错误命中，
     可信但"--no-reuse 真编译对账"必须定期跑（投喂词 PoC#3 边界）。
   - 增量编译：只重编变化 TU——replay 增量机制已是此形态（card_fingerprint
     粒度），到 11.2s 已接近工程上限。
   - 分布式编译：单用户单机无意义。
5. **性能/可信度交易边界（我的分级）**：
   - 零 Oracle 风险：卡间并行（隔离根+重排）、索引化（若保持失效联动）、
     纯算法缓存——判决等价性可机器对账。
   - 必须统计上界兜底：测试选择（漏捕率）、任何"跳过"。
   - 绝对不能做：用 manifest 命中替代真编译作为最终判决（只可作增量）、
     为提速降低断言计数（已有 baseline 闸 gate_engine.py:2775）。

## 四、卡点与解冻信号

1. **nightly <60s——测试结构卡点（纯工程大改）**。信号：slow 测试拆分/最小化后
   总墙钟实测 <60s，且每判决面有等价性对账。
2. **B3 安全跳过——数据+理论卡点**。信号：依赖图完备性有独立核验 + 漏捕回放
   事件积累到可给 C-P 上界；当前 0 回放事件。
3. **B2 replay 并行——纯工程规格卡点**。信号：强规格包 + 串行对账 0 差异。
4. **墙钟数字不稳（198 vs 269）——测量方法问题**。信号：性能测量统一报告
   多次中位数+机器负载（当前无此规范）。

## 五、本维度自由探索

1. **性能数字的诚实化本身是缺口**：所有性能数散在 worklog，单次墙钟受负载影响
   大（同 jobs4 差 36%）。应固定测量协议（冷/热、重复次数、取中位数）并把
   原始数据落 probes/（560 有 perf_data 先例）。
2. **stateful 测试是"慢但必要"的代表**：它是唯一验证 task_queue 故障恢复的
   判决，压缩空间有限；把它移出主回路（nightly only）是零可信度损失的提速
   ——这属于回路组织而非 Oracle 弱化，工程上可立即做（【边界判断】，不是
   建设建议）。
