# 10 · 与本仓现有工具的集成

## 10.1 集成矩阵

| 现有工具 | 集成点 | 最小可行设计 |
|---|---|---|
| `prop_graph.py` | 人审队列/状态视图 | 加 `query --pending-attack-edges` 子视图（复用 566 `--pending-signoff`） |
| `governance_doc_guard.py` | 标注 schema 防护 | annotation schema 变更时入防护（防误改结构） |
| `golden_lock.py` | accept 工作流复用 | 单条确认封装为 golden accept 动作 |
| `tool_integrity.py` | 人审工具哈希 | 若人审做成 CLI 子命令，需 --update 重钉；纯读 jsonl 则不必 |
| `metrics_collector.py` | 进度度量 | 人审进度/确认率/拒绝率写入 metrics |
| `overturned_events.py` | 推翻事件流 | 人审 reject/改判写入（573 设计，592 初始化） |

## 10.2 人审数据存哪？

- **首选 `data/human_annotations.jsonl`**（独立、append-only、可 git 跟踪、可机器解析）。
- 不写卡面（污染命题真伪语义）、不写 propositions.db（派生视图，由 W2 重算生成）。
- 与 `overturned_events.jsonl` 并列于 `data/`，同源治理。

## 10.3 人审工具是否属于 CORE_TOOLS？

- 若做成 `prop_graph.py` 子命令（如 `prop_graph.py review`），属现有工具扩展，**改后需 --update 重钉**（与现有 CLI 同纪律）。
- 若做成独立读 jsonl 的轻脚本，则不必入 CORE_TOOLS 哈希。
- **建议**：作为 `prop_graph.py` 子命令，统一治理。

## 10.4 与 golden_lock 的零误伤联动

- 人审确认一条攻击边 → W2 重算 → 若某 confirmed 命题转 OUT → 触发 golden_lock 复核（与锁定"好状态"冲突时告警）。
- 这是"零误伤"的最后闸门：机器 + 人审双重确认才允许命题翻转。

## 10.5 外部实证【一方称：待核验】

- 工具链集成最佳实践：标注系统与主数据管道解耦（独立存储 + 事件流），本仓 jsonl + overturned_events 设计契合。

## 10.6 本仓落地评估

- 最小可行集成 = `prop_graph.py query --pending-attack-edges` + `data/human_annotations.jsonl` + W2 重算钩子。
- 其余（golden_lock/governance/metrics）为增强，按 596 批次节奏接入。
