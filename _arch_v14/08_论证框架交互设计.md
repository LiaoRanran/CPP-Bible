# 08 · 论证框架交互设计

## 8.1 人审界面形态（本仓 CLI 为主）

| 形态 | 适合 | 本仓可行性 |
|---|---|---|
| CLI 交互 | 批量确认、键盘流、git 友好 | ✅ 现状首选，复用 prop_graph query |
| 静态 HTML 报告 | 人审读图、理解辩护链 | ✅ 本探针已生成 visualization/index.html |
| Web 界面 | 富交互、点选、悬浮 | ⚠️ 需前端框架（W 段） |

## 8.2 入口与任务列表

- **入口**：`prop_graph.py query --pending-attack-edges`（扩展 566 的 `--pending-signoff` 模式）。
- **任务列表**：42 个 MIS 组，按歧义度降序，分页/筛选/进度条（已审/未审/确认率/拒绝率）。
- **详情页**：每组展示 误解 trigger_patterns + refutations 文本 + 关联卡主张 + 候选目标命题 + W2 预测 + 人审表单（确认/拒绝/修改 + 理由 + 置信度）。
- **批量操作**：批量确认高 cred 组；跳过/稍后。

## 8.3 提交动作：写哪？

- **独立文件 `data/human_annotations.jsonl`**（维度 6 提案）：与卡面解耦，append-only，可 git 跟踪、可机器解析。
- **不写卡面 verified_by**：attack 边是人审独立产物，混进卡面会污染"命题真伪"语义。
- **不写 propositions.db**：db 是派生视图，人审原始过程存 jsonl，db 由 W2 重算生成。

## 8.4 与现有 CLI 复用

- 566 `prop_graph.py query --pending-signoff` 已是"人审交接视图"——加 `--pending-attack-edges` 子视图成本极低。
- golden_lock 的 accept 动作、governance_doc_guard 的防护可封装为单条确认的底层调用。

## 8.5 外部实证【一方称：待核验】

- LabelStudio / Prodigy / Brat 的交互范式：队列 + 详情 + 批量 + 理由，本仓 CLI 可 1:1 映射。
- CLI 人审工具（如 `todo-cli` 式）在单人项目里效率常高于 Web（省上下文切换）。

## 8.6 本仓落地评估

- **MVP = CLI + 静态 HTML**：594/595 已证明 W2 + 可视化纯标准库可生成，596 建设批次只需把 `human_annotations.jsonl` 的读写 + `--pending-attack-edges` 视图落地。
- Web 界面是增强（悬停/拖拽/实时重算），非必需；留 W 段。
- **给 596 的接口建议**：人审接口 = `list_pending()` → `show_group(mis)` → `submit(decision, reason, confidence)` → `append_annotation()` → `recompute_w2()`。
