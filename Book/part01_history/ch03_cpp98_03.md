## ⓪ 历史动机：C++98 / C++03 奠基时代的来龙去脉

> 第一份国际标准落地的那一刻，C++ 才真正"成年"——它不再属于某家公司，而属于一份公开文档。

### 0.1 起源（谁·何时·为何）

C++ 在 1980 年代野蛮生长：各厂商方言林立，库互不相通。Stroustrup 早在 1990 年与 Margaret Ellis 合著《The Annotated C++ Reference Manual》(ARM)，想给语言一个"权威描述"。<span class="badge badge-history">史</span> 但 ARM 只是事实参考，真正需要的是**一份由 ISO 背书、可被编译器实现检验的国际标准**。这就是 C++98 的由来：把十年实践（class、模板、异常、RTTI…）冻结成规范。另一条线索是 STL——Stepanov 在 HP/SGI 打磨泛型容器与算法多年，认定"算法与数据结构应当用模板解耦、且零开销"。<span class="badge badge-history">史</span>

### 0.2 关键转折（编年）

- **1998**：ISO/IEC 14882:1998（C++98）发布，确立类、继承、虚函数、模板、异常、RTTI、名字空间、bool 等现代骨架，并把 Stepanov 的 STL 收编为标准库。<span class="badge badge-history">史</span>
- **2003**：C++03 作为技术勘误版，修正 C++98 的缺陷（如 value-initialization 修正、去除了争议中的 `export` 模板用法），不引入新特性。<span class="badge badge-history">史</span>
- **1994**：STL 被正式纳入标准化流程（早于 98 定稿），成为标准库核心。<span class="badge badge-history">史</span>

### 0.3 设计哲学之争

C++98 最鲜明的哲学是 **"给程序员尽可能多的武器，哪怕能伤到自己"**——模板的图灵完备、多范式并存（过程式、OO、泛型）都体现这一点。<span class="badge badge-comment">评</span> 对比同期 Java（1995）走"虚拟机 + 垃圾回收 + 删繁就简"的路，C++ 坚持以值语义与零开销掌控硬件。STL 的加入也曾有争议：有人担心泛型库过于"学院派"，但 Stepanov 用"与手写循环等价甚至更快"的性能说服了委员会。<span class="badge badge-history">史</span><span class="badge badge-comment">评</span>

### 0.4 史料补遗与持续编年

- <span class="badge badge-history">史</span> C++98 的 `export` 模板（可分离编译模板）几乎只有 EDG 前端实现过，因复杂度与收益不成正比，最终在 C++11 被废弃、C++17 删除——是标准里"写进又删掉"的罕见失败实验。
- <span class="badge badge-history">史</span> Boost 库在 2000s 成为标准特性的"试验田"：`shared_ptr`、`optional`、`any`、`filesystem` 皆先在 Boost 孵化再标准化，奠定了"先实践、后入库"的演进模式。
- <span class="badge badge-history">史</span> C++03 之后委员会跳过了一次更名，直接冲刺 C++11；此后确立"train model"每三年一版，避免了 98→11 那 13 年的漫长等待重演。
- <span class="badge badge-comment">评</span> `auto_ptr` 从 C++98 到 C++17 才彻底移除，说明标准维护"万亿行代码投资"的兼容性代价——哪怕明知是坑，也得给足迁移窗口。

> 史料来源：Itanium C++ ABI（GCC/Clang 遵循） https://itanium-cxx-abi.github.io/cxx-abi/abi.html ；Boost 官方 https://www.boost.org/

!!! note "类比：C++98 = 江湖秘籍刻成典籍"
    C++98 把十年实践「冻结成标准」可以**类比**为把江湖口口相传的武功秘籍刻成官方典籍——此前各厂商方言林立、库互不相通，一份 ISO 背书文档才让编译器有可验证基准。其「给程序员尽可能多武器，哪怕能伤到自己」的哲学更**好比**瑞士军刀——功能多到能割伤手，但老手用它如鱼得水。
    换个角度：这把「多范式并存」的军刀也**类似于**与 Java「删繁就简的安全剪刀」截然不同的路线——C++ 坚持以值语义与零开销掌控硬件，选择交给你而非替你没收。

    > 失效边界：多范式并存与图灵完备模板是把双刃剑——能力越大越易写出不可维护或 UB 代码；`auto_ptr` 拖到 C++17 才移除，说明兼容万亿行代码的代价：明知是坑也得给足迁移窗口，不能快刀砍。

> **一句话结论**：C++98/03 把十年实践冻结成第一份国际标准，并把 STL 收编为核心；其哲学是「给程序员尽可能多武器，哪怕能伤到自己」，与 Java 的简化路线分道扬镳。

> 历史注脚：C++98 罕见地「整库采纳」了一个外部设计——STL 由 Stepanov 与 Meng Lee 在 HP 实验室做成、1993 年才在委员会会议上演示、1994 年获接纳，距 1998 定稿只剩四年（[hopl:cpp1991] 记录了 1991–2006 这一时段的演进）。这不是委员会自研的产物，而是"语言部分已定、库在最后一刻换心脏"的豪赌。代价写在两处：语言与库磨合不足——`vector<bool>` 这个至今挨骂的特化就是那时塞进去的遗留（见 ch20）；标准化周期被拉到近十年，其"慢"直接逼出了后来 C++11 的「小步快跑」（见 ch04）。

## ① C++98：第一个国际标准

C++98是Bjarne Stroustrup的"C with Classes"(1979)→C++(1983)→ARM(1990, Ellis & Stroustrup)→C++98标准化这一漫长过程的终点。自C++98起，C++有了正式的国际规范，编译器实现有了可验证的基准。

`[标准]` C++98 确立的不是一份语法清单，而是一整套此后 20 多年保持 ABI 级稳定的对象模型契约：类与继承给出类型层次；虚函数 + vtable 给出运行期多态（§⑫ 的 2 条指令真机证据）；模板给出零开销抽象（§⑧ 的二段式查找）；异常给出栈展开式错误通道（§⑨ 的 throw() 及其后来者）；RTTI 给出运行期类型查询（§⑲ 的真机实测）；STL 给出泛型容器与算法（§②）。这份契约的分量在 2003 年看得最清楚——C++03 只敢做勘误，一个字都不敢动它。

## ② STL（Standard Template Library）

STL的进入是C++98最大的标准化事件。Alexander Stepanov在HP实验室开发的STL(1994)被纳入标准，成为C++标准库的核心：

| 组件 | 内容 | 设计者 |
|---|---|---|
| 容器 | vector, list, deque, map, set | Stepanov, HP |
| 算法 | sort, find, transform, accumulate | Stepanov, HP |
| 迭代器 | input/output/forward/bidirectional/random | Stepanov |
| 函数对象 | less, greater, bind1st/bind2nd | Stepanov |
| 分配器 | std::allocator (来自SGI STL) | SGI |

`[经验]`：STL的设计哲学——"正交组件"(orthogonal components)至今仍是C++标准库的核心原则。

### iostream 的性能陷阱

    // 关闭同步: cout ≈ printf (same speed)
    return 0;
}
```

### vector<bool> 的容器陷阱

> **示例 2** <span class="badge badge-exp">难度 ★☆☆☆☆</span> · vector<bool> 的容器陷阱

#include <iostream>

```

## ⑤ C++03：Bug-fix 修订

C++03没有新增特性，只修复了C++98的措辞错误和歧义。最著名的修复是 `std::vector` 的元素连续内存保证——C++98的措辞模糊，C++03明确要求vector的元素是连续存储的。

## ⑥ 性能遗产

| 操作 | C++98 | 现代替代 | 加速比 |
|---|---|---|---|
| 输出(10000 ints) | cout(~500us, 量级) | std::print(~50us, C++23; 来源 cppreference) | 10x(量级) |
| 排序(1M ints) | std::sort(**85ms 本机实测**) | std::sort(**85ms 本机实测**) | 1x(相同算法) |
| std::string 构造 | COW(拷贝共享) | SSO(小字符串优化) | 2-100x(量级, 取决于串长) |
| bind1st 调用 | 函数指针(~5ns) | lambda 内联(~0ns) | ∞(bind1st 已 C++17 弃用/C++20 删除, 本机 -std=c++23 不可编译) |

- `[实测]`：上表"排序"行经本机 `g++ -O2` + `std::sort(1M int)` 实测 **85ms**（旧估 ~450ms 偏高约 5x）；其余行为**量级参考 + 权威来源标注**，非本机单点实测（cout/printf 受 `sync_with_stdio` 状态影响大、std::print 依赖 C++23 实现、bind1st 已被删除）。来源 `Examples/_ch03_perf.out`。

## ⑦ 面试巩固

> 三问三答的速查版；深度展开在 §⑭（移动语义为何缺位）、§⑯（COW/ABI）与附录 J（高频速查表）。

Q: C++98最大的贡献？
A: 将C++标准化为国际标准。STL的标准化使得泛型编程成为C++的核心范式。

Q: auto_ptr 为什么被移除？
A: 拷贝语义=所有权转移（违反直觉）。在STL容器中使用auto_ptr导致UB。

Q: vector<bool> 该怎么办？
A: 用 `std::deque<bool>`（真正的bool容器）或 `boost::dynamic_bitset`（位集）。

> **示例 3** <span class="badge badge-exp">难度 ★☆☆☆☆</span> · 面试巩固

```cpp title="示例 3 · ★☆☆☆☆"
#include <iostream>
#include <deque>
int main() {
    std::deque<bool> v{true, false, true};  // 真正的容器：元素可取址
    bool& b = v[0];                         // works fine!
    b = false;
    std::cout << v[0] << std::endl;
    return 0;
}
```

<span class="badge badge-std">标准</span> C++98/03 已过时——新项目的最低基线是 C++17（ch02/ch10 的共识），98/03 只以「遗产维护模式」存在。
<span class="badge badge-exp">经验</span> 理解技术债的因果链，比记住结论有用：没有移动语义 → `auto_ptr` 只能靠拷贝转移；位压缩容器早于完善的模板约束设计 → `vector<bool>` 特化失控；`throw()` 只有运行期检查 → C++11 才有编译期 `noexcept`。现代 C++ 的每个「新特性」，都是在还 98 时代的哪一笔旧账。

## ㉒ 历史纵深·真实产业坐标·生产踩坑·与标准的互动

> 本节为 P0-15 全库深度升维大波次之一：压实历史出处、真实产业坐标、生产级踩坑与「本特性与 C++ 标准」的互动。引用链接列于 ㉒.5。

### ㉒.1 历史渊源补强：第一个 C++ 国际标准

<span class="badge badge-history">史</span> 1998 年 ISO 发布 **ISO/IEC 14882:1998（C++98）**，把此前十年 AT&T 方言与 CFront 时代的事实实践固化成标准：模板、异常、`dynamic_cast`/RTTI、标准库（IOStream、STL 的 vector/map/algorithm、string）。<span class="badge badge-history">史</span> 2003 年的 **C++03（ISO/IEC 14882:2003）** 只是技术勘误（TC1）+ 修复"值初始化"缺陷（CWG Issue 178），没有引入新语言特性——所以业界常说"98/03 是一代"。<span class="badge badge-anecdote">轶</span> 一个被低估的细节：C++98 的 STL 直接"收编"了 Stepanov 的泛型算法与 HP/SGI 的实现，但**未规定 ABI**——于是 GNU、MS、Borland、IBM 各搞各的名字改编与异常模型（SjLj vs SEH vs DWARF），二进制至今不互操作。<span class="badge badge-comment">评</span> C++98/03 的"技术债"（无移动语义、无 `auto`、无智能指针正统化——`auto_ptr` 是半成品）恰恰是 C++11 大改革的动机清单。

### ㉒.2 真实工程坐标：C++98/03 活在哪

C++98/03 不是「古董」，而是大量关键系统仍在跑的事实标准。下面按领域展开：

| 领域 / 类别 | 代表系统 · 生态 | 它承担的角色 | 规模 · 行业地位 | 备注 / 标准互动 |
|---|---|---|---|---|
| 存量关键系统 | 航空航天 / 汽车 ECU / 金融核心（交易网关）/ 电信交换机 | 因重认证成本不敢升级 | 关键基础设施 | 重测试 / 重认证是拦路虎 |
| 老编译器固化 | 嵌入式 SDK（仅 C++03）/ PS3 Cell 工具链 | 把 C++03 当事实最高标准 | 受限工具链 | 厂商 SDK 锁死版本 |
| 编译器自举 | Clang 早期严格 C++98/03 子集实现 | 便于在旧工具链自举 | 编译器生态起点 | 自举约束语言基线 |
| 金融与航空存量 | 交易网关 / 航电（DO-178C 认证）仍 C++98/03 | 「能跑就不敢动」 | 安全关键长期存活 | [据记载] 重认证成本极高 |
| Bloomberg BDE | BDE（`bdl`/`bsl`）早期 C++03，2010s 才迁 C++11 | 大型金融慢升级代表 | 金融基础设施 | 见 BDE 源码 |

> **表注（㉒.2）**：上表前 3 行是「为什么 C++98/03 还活着」，后 2 行是「金融/航空存量与 Bloomberg BDE 的具体坐标」；安全关键领域（DO-178C 等）的重新认证成本以年计，这是「能跑就不敢动」的工程现实，不是技术保守。

**一条判读**：维护老标准代码时，别急着「升级到现代 C++」——安全关键/金融核心的升级成本是认证而非语法；真正该做的是用特性宏隔离可升级部分，把迁移当成受控项目而非顺手重构。

### ㉒.3 生产踩坑：C++98/03 时代的经典误用

- **`auto_ptr` 的"拷贝即转移"语义**：C++98 没有移动语义，`auto_ptr` 用"拷贝构造偷偷转移所有权"模拟，导致放进容器（如 `vector<auto_ptr>`）会发生诡异的所有权丢失——C++11 用 `unique_ptr` 彻底取代。
- **缺少 `shared_ptr` 标准版**：C++98 时期要么手写引用计数（易漏 `delete`）、要么用 Boost，跨模块传递时引用计数实现不一致就内存泄漏或双重释放。
- **异常与 ABI 模型**：不同编译器默认异常模型（SjLj/DWARF2/SEH）不同，混合链接时栈展开行为不一致，跨 DLL 抛异常可能直接 terminate。

### ㉒.4 与标准的互动：被 C++11 取代的历史

<span class="badge badge-history">史</span> C++03 之后，WG21 意识到"小步快跑"优于"十年一跃"，于是 C++11（N3337 草案，2011）一口气补上移动语义、lambda、`auto`、智能指针、并发库，等于把 13 年的技术债一次性还清。<span class="badge badge-comment">评</span> 今天新项目应以 **C++17 为最低基线**（ch02/ch10 的共识）；C++98/03 仅因"既有系统/受限工具链"才保留——把它当"遗产维护模式"而非"学习起点"。

- <span class="badge badge-history">史</span> C++98 即 **ISO/IEC 14882:1998**，C++03 即 **ISO/IEC 14882:2003**（仅技术勘误 TC1 + 值初始化修复，CWG 178）。委员会的设计理由是**标准有意不规定 ABI**——把二进制接口留给实现者竞争（Itanium/GNU C++ ABI、MSVC 各自演进），换取编译器厂商的自由度，代价是跨编译器二进制至今不互操作。

## 附录 H：C++98编译器与经典项目

C++98 标准有意不规定 ABI，把二进制接口留给实现者竞争。同一行代码的符号名因此分道扬镳：`void f(int)` 在 GCC/Clang（Itanium C++ ABI）下改编为 `_Z1fi`，在 MSVC（MS ABI）下改编为 `?f@@YAXH@Z`——§⑫ 的真机 `nm` 输出就是活证据，附录 O 的 ABI 陷阱表与 ch11 的名字改编详解都根植于此。

```text
void f(int) 的符号名（同一声明，两种 ABI）
  GCC/Clang (Itanium C++ ABI): _Z1fi
  MSVC     (MS ABI):           ?f@@YAXH@Z
```

## ⑪ iostream vs format 性能证据

> **示例 4** <span class="badge badge-exp">难度 ★★★★☆</span> · iostream vs printf 真机微基准

```cpp title="示例 4 · ★★★★☆"
// ④ 真机微基准：同样 1M 个 int，cout（关同步）vs printf 写入 NUL
#include <iostream>
#include <cstdio>
#include <chrono>

int main() {
    std::freopen("NUL", "w", stdout);   // 丢弃输出，只测格式化+写入开销
    std::ios_base::sync_with_stdio(false);

    constexpr int N = 1000000;
    auto t0 = std::chrono::steady_clock::now();
    for (int i = 0; i < N; ++i) std::cout << i;
    auto t1 = std::chrono::steady_clock::now();
    double cout_ns = std::chrono::duration<double, std::nano>(t1 - t0).count() / N;

    std::FILE* f = std::fopen("NUL", "w");
    auto t2 = std::chrono::steady_clock::now();
    for (int i = 0; i < N; ++i) std::fprintf(f, "%d", i);
    auto t3 = std::chrono::steady_clock::now();
    double printf_ns = std::chrono::duration<double, std::nano>(t3 - t2).count() / N;
    std::fclose(f);

    std::fprintf(stderr, "cout(sync off) = %.0f ns/op | printf = %.0f ns/op | ratio = %.2f\n",
                 cout_ns, printf_ns, cout_ns / printf_ns);
    return 0;
}
```

`[实验·本机实测][UNVERIFIED]` GCC 13.1.0 `-O2`，N=1M，写入 NUL（证据 `Examples/_ch03_perf.out` 尾部）：**关同步 cout = 76 ns/op，printf = 296 ns/op——cout 反而快 3.9×**；默认同步态 cout = **5159 ns/op**。真相与讹传相反：「iostream 慢」的坑几乎全部来自默认的 `sync_with_stdio(true)`（每次输出穿透 stdio 缓冲，5159 ns/op 是 printf 的 17 倍）；关掉后 libstdc++ 的 stream 缓冲 + 整数格式化路径反超 printf。旧说「cout 比 printf 慢 3-5 倍」「关同步后差不多」在方向上就错了，以本机数据为准。

## ⑭ 面试：为什么C++98没有移动语义

原因是值语义设计哲学(1980年代): "值=拷贝"。Bjarne在设计C++时受到Simula和C的影响，这两种语言都没有移动语义的概念。直到C++11引入rvalue reference才解决了这个问题——因为移动语义需要"右值引用"这种全新的语言机制来区分"可以窃取资源的临时对象"和"不能窃取的持久对象"。

> **示例 6** <span class="badge badge-exp">难度 ★☆☆☆☆</span> · C++98 所有权手法：侵入式引用计数

```cpp title="示例 6 · ★☆☆☆☆"
// ⑥ C++98 的所有权手法：侵入式引用计数 + 托管指针（LLVM RefCountedBase / Boost intrusive_ptr 的直系祖先）
#include <iostream>

class Widget {
    long refs_;
public:
    Widget() : refs_(1) {}                             // 出生即被一个 RefPtr 持有
    void addRef() { ++refs_; }
    void release() { if (--refs_ == 0) delete this; }  // 自杀式析构：98 年代惯用法
    long use_count() const { return refs_; }
protected:
    ~Widget() { std::cout << "Widget destroyed\n"; }   // protected：外部不许直接 delete
};

class RefPtr {
    Widget* p_;
public:
    explicit RefPtr(Widget* p = 0) : p_(p) {}          // 98 无 nullptr，用 0
    RefPtr(const RefPtr& o) : p_(o.p_) { if (p_) p_->addRef(); }
    RefPtr& operator=(const RefPtr& o) {
        if (this != &o) {
            if (p_) p_->release();
            p_ = o.p_;
            if (p_) p_->addRef();
        }
        return *this;
    }
    ~RefPtr() { if (p_) p_->release(); }
    Widget* operator->() const { return p_; }
};

int main() {
    RefPtr a(new Widget());
    {
        RefPtr b = a;                                  // 拷贝 = 计数 +1（共享，非转移）
    }                                                  // b 析构：计数 -1，对象仍活着
    std::cout << "use_count = " << a->use_count() << " (still alive)\n";
    return 0;
}
```

真机运行（GCC 13.1.0，`-std=c++23` 编译 98 风格代码）：`use_count = 1 (still alive)`，程序退出时 `Widget destroyed`。这套「侵入式引用计数 + `delete this`」是没有 `shared_ptr` 的年代唯一的所有权解法——今天 LLVM 的 `RefCountedBase`、Boost 的 `intrusive_ptr`、Qt 的 `QSharedDataPointer` 都是它的直系后代。

## ⑯ COW string的性能陷阱(GCC 5.1 ABI break)

libstdc++的std::string在C++11前使用COW(Copy-on-Write):
- 优点: 拷贝string不立即分配内存(共享底层buffer)
- 陷阱: operator[]在有其他引用时触发COW→意想不到的堆分配
- GCC 5.1彻底移除COW→SSO(Small String Optimization)
- ABI break: 链接GCC5+程序与GCC4.9-库→SIGSEGV

> **示例 7** <span class="badge badge-exp">难度 ★☆☆☆☆</span> · COW→SSO 的 ABI 编译期探针

```cpp title="示例 7 · ★☆☆☆☆"
// ⑦ 新旧 libstdc++ ABI 编译期探针：COW(旧)与 SSO(新) 的库不能互链，先探再链
#include <iostream>
#include <string>

int main() {
#if defined(_GLIBCXX_USE_CXX11_ABI)
    std::cout << "_GLIBCXX_USE_CXX11_ABI = " << _GLIBCXX_USE_CXX11_ABI << '\n';
#else
    std::cout << "_GLIBCXX_USE_CXX11_ABI undefined\n";
#endif
    std::string s = "short";
    std::cout << "sizeof(std::string) = " << sizeof(std::string) << '\n';  // 旧COW=8, 新SSO=32
    return 0;
}
```

真机运行（GCC 13.1.0）：`_GLIBCXX_USE_CXX11_ABI = 1`、`sizeof(std::string) = 32`。新 ABI（`__cxx11` inline namespace + SSO）下 string 是 32 字节的带缓冲对象；旧 COW ABI 下它只是 8 字节的堆指针。两边的 `std::string` 连符号名都不同——这就是 GCC 5.1 ABI break 的机理，也是「混合链接 → SIGSEGV」的判别法：先用这个编译期探针确认每一段库的 ABI，再谈链接。

### GCC 2.95(1999): 首个完整C++98实现

GCC 2.95（1999）是首个完整 C++98 实现，它奠定的实现骨架至今没变，五点如下：`[实现·GCC]`

1. **虚函数表**：每个多态类一张 vtable，存于 `.rodata` 段（§⑫ 的 2 条指令分发）。
2. **异常**：DWARF2 unwind 表（`.eh_frame` 节），无异常时零开销——「表驱动展开」的由来。
3. **RTTI**：`type_info` 对象挂在 vtable 前一个槽位（约 8 字节偏移）。
4. **模板**：两段式名称查找，C++98 标准要求（§⑧ 的真机历史弧线）。
5. **名字改编**：`_Z1fi` = `void f(int)`（Itanium ABI，附录 H）。

第 3 点可以真机眼见为实——`typeid` 只是一次经 vptr 的查表：

> **示例 11** <span class="badge badge-exp">难度 ★★★☆☆</span> · type_info 与 vtable 相邻关系真机演示

```cpp title="示例 11 · ★★★☆☆"
// ⑪ type_info 与 vtable 的相邻关系：98 的 RTTI 实现就是"vtable 前一个槽位"
#include <iostream>
#include <typeinfo>

struct Base { virtual ~Base() {} };
struct Derived : Base {};

int main() {
    Base* p = new Derived;
    std::cout << typeid(*p).name() << '\n';   // 经 vptr → vtable 前槽位取 type_info
    std::cout << (typeid(*p) == typeid(Derived) ? "same" : "diff") << '\n';
    delete p;
    return 0;
}
```

真机输出（GCC 13.1.0，MinGW）：`7Derived`、`same`。`7Derived` 是 Itanium mangling 的 `type_info::name()` 原始字节（长度前缀 7 + 类名）；比较操作则只比 `type_info` 地址——与 §⑲ 实测的 `typeid ~1.8ns` 完全自洽。

> **示例 13** <span class="badge badge-exp">难度 ★★☆☆☆</span> · Doom 3 式 -fno-rtti 下转：手写类型标签

```cpp title="示例 13 · ★★☆☆☆"
// ⑬ -fno-rtti 时代的下转：手写类型标签替代 dynamic_cast（id Tech 4 惯用法示意）
#include <iostream>

class Entity {
public:
    enum Kind { KIND_PLAYER, KIND_MONSTER };
    virtual ~Entity() {}
    virtual Kind kind() const = 0;
};

class Player : public Entity {
public:
    Kind kind() const { return KIND_PLAYER; }   /* 98 无 override 关键字 */
    void say() const { std::cout << "player\n"; }
};

Player* as_player(Entity* e) {
    return e && e->kind() == Entity::KIND_PLAYER
         ? static_cast<Player*>(e) : 0;         /* 98 无 nullptr */
}

int main() {
    Player p; Entity* e = &p;
    if (Player* pl = as_player(e)) pl->say();
    return 0;
}
```

真机输出：`player`。这就是 `-fno-rtti` 时代的 `dynamic_cast` 替身：手写类型标签 + `static_cast`，把「失败下转」从运行期类型比较变成一次 enum 比较——快（§⑲ 实测 `dynamic_cast` 成功路径本就仅 ~6.2ns），但**类型安全责任转嫁给了程序员**（标签与实际类型漂移即 UB）。现代等价物是 `std::variant` + `std::visit` 的穷尽分发（ch25/ch48）。

1998: C++98发布
1999-2002: "C++0x"讨论开始(期望200x年代发布)
2003: C++03 bugfix发布
2003-2006: 提案积累期(move语义、lambda、auto各自立项，提案号见WG21论文库)

train model 落地后，「你现在到底在哪个标准档位」成了每个工程都要回答的问题——答案是编译器宏，不是口头约定：

> **示例 15** <span class="badge badge-exp">难度 ★☆☆☆☆</span> · __cplusplus 标准档位探测真机演示

```cpp title="示例 15 · ★☆☆☆☆"
// ⑮ train model 时代的日常：用 __cplusplus 探测编译器实际标准档位
#include <iostream>

int main() {
#if __cplusplus >= 202302L
    std::cout << "C++23\n";
#elif __cplusplus >= 202002L
    std::cout << "C++20\n";
#elif __cplusplus >= 201703L
    std::cout << "C++17\n";
#elif __cplusplus >= 201402L
    std::cout << "C++14\n";
#elif __cplusplus >= 201103L
    std::cout << "C++11\n";
#else
    std::cout << "C++98/03\n";
#endif
    return 0;
}
```

`[实验·本机实测][UNVERIFIED]` GCC 13.1.0 以 `-std=c++23` 编译，输出却是 **`C++20`**——该版本 `-std=c++23` 下 `__cplusplus` 仍为 `202002L`。这是探测宏的头号坑：**`__cplusplus` 报告的是「实现自认的档位」，不是命令行开关**；MSVC 更是要开 `/Zc:__cplusplus` 才报告真实值，否则恒为 `199711L`。版本迁移的判据要落在特性检测宏（`__has_include`、`__cpp_*`）上，别信单一数字。

## ⑧ C++98的模板二段式查找

C++98 要求二段式名称查找（two-phase lookup）：第一阶段在模板**定义处**解析非依赖名；第二阶段在**实例化时**才解析依赖名（`typename T::value_type` 一类）。这条规则是类型安全的地基——定义处就该抓出的错误，不该拖到实例化。

真机复现这段历史最有意思：同一行「缺 `typename`」的代码，`-std=c++98` 下 GCC 13.1 在第一阶段即报错，而 `-std=c++23` 下**编译通过**——C++20 的 P0634（"Down with typename!"）在类型语境可唯一确定的场合取消了强制。更妙的是老 MSVC：它当年因一阶段查找「不报这个错」被批不合规，二十年后的标准反而向它的行为靠拢——歪打正着。

```text
// two_phase.cpp — 同一行依赖名，两代标准两种命运
template <class T> struct Bad { T::type value; };

$ g++ -std=c++98 -c two_phase_err.cpp
two_phase_err.cpp:2:33: error: need 'typename' before 'T::type' because 'T' is a dependent scope
    2 | template <class T> struct Bad { T::type value; };
      |                                 ^
      |                                 typename

$ g++ -std=c++23 -c two_phase_err.cpp   # 通过：C++20 P0634 松绑，类型语境可省 typename
```

移植性忠告因此要更新：MSVC 直到 VS2013 才完全实现两段式查找；而标准自己在 C++20 又松了绑——移植性永远要以**目标编译器 + 目标标准档位**实测为准，别背教条。

## ⑨ C++98的异常规范

C++98的throw()异常规范(已废弃):
- void f() throw(std::bad_alloc) → 声明可能抛bad_alloc
- 违反→std::unexpected()→默认std::terminate()
- 问题: 运行时检查, 性能开销, 无法静态验证
- C++11: noexcept替代(编译期, 无运行时检查)
- C++17: throw()完全移除

## ⑩ C++98的STL分配器模型

C++98的allocator设计过于复杂:
- rebind机制: allocator<T>::rebind<U>::other → 类型转换
- 有状态分配器无法传播 → 限制容器使用
- C++17: pmr::memory_resource完全重写(类型擦除+多态)

## ⑱ C++98与现代C++的桥接

extern "C"是C/C++的唯一ABI桥梁:
- C++调用C: extern "C" { #include "c_header.h" }
- C调用C++: extern "C" void cpp_func() { /* C++ code */ }
- 限制: 无异常, 无重载, 无name mangling

## ⑲ C++98的RTTI性能

typeid/dynamic_cast的性能代价（本机实测，GCC 13.1 -O2，TSC 2.395GHz，N=1M，来源 `Examples/_ch03_perf.out`）:
- typeid: **~1.8ns**（经 vtable 前 8 字节取 `type_info` 指针，见 `Examples/_ch03_perf.asm` 的 `get_tname`）
- dynamic_cast: **~6.2ns**（成功下转；本机实测远低於旧估 ~50-200ns——类型匹配时 `__dynamic_cast` 运行时极廉价，仅比较 type_info 指针，旧估把"失败/深继承链遍历"当常态）
- Google/LLVM: -fno-rtti → 禁用, 用手写enum替代（上述实测为开启 RTTI 的代价上限参考）

## 附录 A：工业实战复盘与设计取舍 [I: Practice / H: Design]

### 工业案例（真实可查证）

- **C++98 代码库的现代编译器迁移**：大量存量工业代码（如 2010 年代前的 MFC/Win32、嵌入式固件 SDK）仍以 C++98 标准编译于 MSVC 6.0/GCC 3.x。升级到 C++17 编译器时，因旧代码依赖非标准扩展（如 `for` 循环作用域、模板非类型参数隐式 `int`、缺 `typename`）而大面积编译失败——这是 C++ 版本互操作性的经典痛点。
- **`auto_ptr` 的淘汰**：C++11 以 `unique_ptr` 取代 `auto_ptr`（后者在拷贝时转移所有权，语义反直觉且破坏容器安全）。存量库若头文件公开 `auto_ptr` 成员，C++17 下直接 `=delete`，导致下游 ABI 断链。

### 常见 Bug 与 Debug 方法

- **`std::bind`/`mem_fun` 生命周期陷阱**：C++98 用 `std::bind` 绑定成员函数时误持裸指针，对象析构后回调悬垂。Debug 用 ASan 抓 UAF；现代替代是 `std::bind_front`/`lambda` 显式捕获 `weak_ptr`。
- **模板报错可读性**：C++98 模板错误（如 STL 嵌套实例化）可输出上千行。Debug 用 `-fdiagnostics-show-template-tree`（Clang/GCC）折叠；Code Review 时对深模板加 `static_assert` 早失败。
- **Code Review 关注点**：是否泄漏 `auto_ptr`/`throw()` 动态异常规范（C++20 起仅 `noexcept` 语义保留）；循环变量是否跨作用域逃逸（C++98 允许、C++11 收紧）。

### 设计取舍（Trade-off）与反模式（Anti-Pattern）

| 维度 | C++98 做法 | 现代替代 | 代价 |
|------|-----------|----------|------|
| 所有权 | `auto_ptr`/裸指针 | `unique_ptr`/`shared_ptr` | 需改公开接口（ABI 风险） |
| 遍历 | 手写迭代器/`for` | 基于范围的 `for` | 旧编译器不支持 |
| 回调 | `std::bind` 裸指针 | lambda + `weak_ptr` | 语法迁移成本 |

- **反模式**：用 `#define` 模拟 `nullptr`（旧编译器无 `nullptr`）；为兼容 C++98 把 `constexpr` 退回 `enum` 常量（丢类型安全）。
- **API Design**：存量库对外接口优先保持 `const T&`/值语义而非裸指针；新增 API 直接按 C++17 写，用宏隔离旧编译器（`#if __cplusplus >= 201703L`）。

### 重构建议

把 `auto_ptr<T>` 字段重构为 `unique_ptr<T>` 并显式 `std::move`；把 `std::bind(&C::f, this)` 重构为 lambda 捕获 `std::weak_ptr<C>` 后 `lock()` 判空，消除悬垂。迁移时先用 `-Werror` + 双编译器（MSVC+GCC）跑通再切标准。

## 最佳实践 <span class="badge badge-exp">经验</span>

- **维护遗留 98/03 代码先开 `-Wall -Wextra -Wpedantic`**：老代码常靠隐式转换与宏，先以全量警告暴露隐患，再小步重构，不要一次性「现代化」导致行为漂移。
- **ABI 稳定优先于语言特性**：98/03 时代大量库以二进制兼容为契约；升级编译器或标准时先确认 `libstdc++`/`libc++` 的 ABI 基线（如 `_GLIBCXX_USE_CXX11_ABI`），避免运行时符号错配。
- **警惕 `std::auto_ptr` 的历史坑**：它是 C++11 前唯一智能指针，但拷贝即转移所有权、不能进容器；遇到它优先替换为 `std::unique_ptr`，并在替换处补生命周期注释。
- **头文件守卫＋显式 `inline` 防 ODR 重定义**：98/03 没有 `inline` 变量与 modules，跨 TU 共享常量须 `inline` 或放进匿名命名空间，避免链接期多重定义。

### 练习 1（难度 ★★）

**真实场景：C++98 存量代码的容器遍历。** 你接手一个仍锁定 C++98 的嵌入式/网络服务（编译器不支持 `auto`），需要遍历一个 `std::map` 里的已连接套接字描述符并逐个发送心跳。请写程序用 `std::vector` 配合显式迭代器类型遍历（C++98 时代写法，`auto` 尚不存在），并说明迭代器为何是连接容器与算法的"泛型指针"。

> **示例 16** <span class="badge badge-exp">难度 ★☆☆☆☆</span> · 练习 1（难度 ★★）

```cpp title="示例 16 · ★☆☆☆☆"
#include <iostream>
#include <vector>
#include <numeric>   // std::accumulate

int main() {
    std::vector<int> v;
    v.push_back(3); v.push_back(1); v.push_back(4);

    // C++98 写法：迭代器类型必须写全，无 auto
    for (std::vector<int>::const_iterator it = v.begin(); it != v.end(); ++it)
        std::cout << *it << ' ';
    std::cout << '\n';

    int sum = std::accumulate(v.begin(), v.end(), 0);
    std::cout << "sum = " << sum << '\n';
}
```

<span class="badge badge-std">标准</span> 结论：迭代器把“如何遍历”与“遍历后做什么”解耦——同一套 `<algorithm>`
可作用于任意提供合规迭代器的容器，这是 STL 泛型设计的基石（C++98 起定型）。

<span class="badge badge-ref">引用</span> ISO C++98 §[lib.iterators] / §[sequence.reqmts]；cppreference "std::vector"（https://en.cppreference.com/w/cpp/container/vector）与 "迭代器"（https://en.cppreference.com/w/cpp/iterator）。STL 泛型设计源自 Stepanov 的标准模板库提案，是后续 `<algorithm>` 的基础。

### 练习 2（难度 ★★★）

**真实场景：插件式图形后端。** 一个 C++98 时代的 GUI/游戏引擎把各种图元（圆、方块）统一收进 `Shape*` 容器，主循环只管"画"，具体画法是派生类的事。请写程序演示基类指针通过虚函数调用派生类实现，并说明 vtable 的运行期开销来源（读 vptr→查表→间接跳转）。

> **示例 17** <span class="badge badge-exp">难度 ★★☆☆☆</span> · 练习 2（难度 ★★★）

```cpp title="示例 17 · ★★☆☆☆"
#include <iostream>
#include <memory>

struct Shape {
    virtual double area() const = 0;  // 纯虚：抽象接口
    virtual ~Shape() = default;       // 基类虚析构，避免切片式泄漏
};
struct Circle : Shape {
    double r;
    explicit Circle(double r_) : r(r_) {}
    double area() const override { return 3.14159265 * r * r; }
};
struct Square : Shape {
    double s;
    explicit Square(double s_) : s(s_) {}
    double area() const override { return s * s; }
};

int main() {
    std::unique_ptr<Shape> a = std::make_unique<Circle>(2.0);
    std::unique_ptr<Shape> b = std::make_unique<Square>(3.0);
    std::cout << "circle area = " << a->area() << '\n';
    std::cout << "square area = " << b->area() << '\n';
}
```

<span class="badge badge-std">标准</span> 结论：虚调用需先读对象头部的 vptr → 查 vtable → 间接跳转，比直接调用多两次
内存访问且难以内联；换来的是运行期多态。C++98 起该模型未变（`unique_ptr` 属 C++11，此处仅作管理便利）。

<span class="badge badge-ref">引用</span> ISO C++ §[class.virtual]；cppreference "虚函数"（https://en.cppreference.com/w/cpp/language/virtual）。Itanium C++ ABI（https://itanium-cxx-abi.github.io/cxx-abi/abi.html）规定了 vtable 布局与虚调用机制，GCC/Clang 均遵循。

### 练习 3（难度 ★★★★）

**真实场景：位压缩特性开关的坑。** 一个网络/嵌入式配置用位集合表示功能开关，新手顺手写成 `std::vector<bool>` 想逐个取地址传给底层寄存器接口，结果编译失败——位压缩特化让 `operator[]` 返回的是代理而非 `bool&`。请写程序暴露这一陷阱，并给出工程替代方案。

> **示例 18** <span class="badge badge-exp">难度 ★★★☆☆</span> · 练习 3（难度 ★★★★）

```cpp title="示例 18 · ★★★☆☆"
#include <iostream>
#include <vector>
#include <deque>

int main() {
    std::vector<bool> vb(4, false);
    // auto ref = vb[0]; ref 的类型是代理 std::vector<bool>::reference，不是 bool&
    auto proxy = vb[0];
    proxy = true;                 // 通过代理写回，vb[0] 确实变 true
    std::cout << "vb[0] = " << vb[0] << '\n';

    // 陷阱：不能取 bool* 指向元素（元素不是独立字节）
    // bool* p = &vb[0];          // 编译失败：无法取代理的地址为 bool*

    // 工程替代：需要真正 bool 容器时用 deque<bool> 或 vector<char>
    std::deque<bool> db(4, false);
    db[0] = true;
    std::cout << "db[0] = " << db[0] << " (deque<bool> 无位压缩，行为正常)\n";
}
```

<span class="badge badge-std">标准</span> 结论：`vector<bool>` 违反了“容器元素可取址、`operator[]` 返回 `T&`”的一般契约，
泛型代码对它易失效。工业实践：位图用 `std::bitset`/`vector<char>`，需要动态 `bool` 序列用 `deque<bool>`。

<span class="badge badge-ref">引用</span> ISO C++ §[vector.bool]（`vector<bool>` 特化）；cppreference "std::vector<bool>"（https://en.cppreference.com/w/cpp/container/vector_bool）与 "std::deque"（https://en.cppreference.com/w/cpp/container/deque）。代理引用问题在 C++ 核心指南 SL.con.4 明确建议避免把 `vector<bool>` 当可变位集使用。

### 练习 4（难度 ★★）

**真实场景：维护一份 C++98 老代码，发现 `NULL` 的重载歧义。** 你接手一个 C++98 项目，里面大量用 `NULL`（本质是 `0`）传空指针；新加一个 `void on(int)` 重载后，原本"清空指针"的调用莫名其妙调到了整数重载。请用最小程序复现这一歧义，并说明 C++11 引入 `nullptr` 如何根治它。

<details><summary>答案与解析</summary>

在 C++98 里 `NULL` 通常是 `0` 或 `(void*)0` 的宏，本质是整型/空指针常量。当存在重载 `void f(int)` 与 `void f(char*)` 时，传入 `NULL` 会优先匹配到 `int` 重载——这正是"本想传空指针却调到整数版"的根源。

> **示例 19** <span class="badge badge-exp">难度 ★★★☆☆</span> · 练习 4（难度 ★★）

```cpp title="示例 19 · ★★★☆☆"
#include <cstdio>

void log(int)    { std::printf("log(int)\n"); }
void log(char*)  { std::printf("log(char*)\n"); }

int main() {
    log(0);                      // C++98 下 NULL==0，匹配到 log(int)，并非空指针版
    log(static_cast<char*>(0));  // 显式强制才能命中 log(char*)
    return 0;
}
```

<span class="badge badge-std">标准</span> C++98 中 `NULL` 是实现定义的空指针常量（常为 `0`）；C++11 引入关键字 `nullptr` 与类型 `std::nullptr_t`，它只匹配指针/引用，彻底消解与整数重载的歧义。

<span class="badge badge-exp">经验</span> 老代码里若无法立刻升级标准，可用 `static_cast<T*>(0)` 或显式 `0` 规避歧义；新代码一律用 `nullptr`。这也是为什么现代 C++ 指南第一条就是"别再用 NULL"。

</details>

### 练习 5（难度 ★★★）

**真实场景：写 C++98 的 RAII 资源管理，却没 move 语义。** 你要在 C++98 下实现一个"离开作用域必释放"的句柄（如文件/锁），不能用 C++11 的 `unique_ptr`/移动。请用析构函数 + 禁止拷贝演示一个最小 RAII 类型，并对比说明为什么 C++11 之后这类手写代码大多可被标准库取代。

<details><summary>答案与解析</summary>

C++98 已经具备 RAII 的全部基础：构造获取、析构释放、作用域结束自动调用析构。缺的是"移动语义"，所以只能靠"禁止拷贝 + 显式释放函数"或 `auto_ptr` 的诡异转让来近似独占所有权——这也是 `auto_ptr` 后来被 `unique_ptr` 取代的原因。

> **示例 20** <span class="badge badge-exp">难度 ★★★☆☆</span> · 练习 5（难度 ★★★）

```cpp title="示例 20 · ★★★☆☆"
#include <cstdio>

struct File {
    int id;
    explicit File(int i) : id(i) { std::printf("open %d\n", id); }
    ~File() { std::printf("close %d\n", id); }  // 离开作用域自动释放
private:
    File(const File&);                          // C++98：禁止拷贝，避免双重释放
    File& operator=(const File&);
};

int main() {
    { File f(1); }                              // 析构在此触发，绝不泄漏
    std::printf("done\n");
    return 0;
}
```

<span class="badge badge-std">标准</span> C++98 §[class.dtor] 规定具名对象在作用域末尾按构造逆序析构；`private` 拷贝构造/赋值可阻止值语义拷贝，是 C++98 模拟独占所有权的基本手法。

<span class="badge badge-exp">经验</span> RAII 是 C++98 就成立的铁律；但手写"禁止拷贝 + 析构释放"在 C++11 后被 `unique_ptr` 全面接管——库方案更安全（不会因忘了写 `private` 而失效），这也是为什么现代代码几乎不手写这类类型。

</details>

## 附录：用法演绎（从选型到落地）

### 演绎 1：RAII —— C++98 留给现代 C++ 的最重要遗产

**场景**：函数中途 `return`/抛异常，手动 `delete`/`fclose` 极易漏掉导致泄漏。
**选型**：把资源生命周期绑定到栈对象——构造时获取、析构时释放（RAII）。
**错误**：裸 `new`/`delete` 配 try/catch，路径一多必漏。
**落地**：

> **示例 21** <span class="badge badge-exp">难度 ★★☆☆☆</span> · 演绎 1：RAII —— C++98

```cpp title="示例 21 · ★★☆☆☆"
#include <iostream>
#include <cstdio>

// C++98 惯用法：一个自管理 FILE* 的守卫类
class FileGuard {
    std::FILE* fp_;
public:
    explicit FileGuard(const char* path, const char* mode)
        : fp_(std::fopen(path, mode)) {}
    ~FileGuard() { if (fp_) std::fclose(fp_); }  // 无论如何退出都关闭
    std::FILE* get() const { return fp_; }
    bool ok() const { return fp_ != nullptr; }
    FileGuard(const FileGuard&) = delete;        // 禁拷贝，独占所有权
    FileGuard& operator=(const FileGuard&) = delete;
};

int main() {
    FileGuard f("nonexistent_probe.tmp", "r");
    std::cout << "open " << (f.ok() ? "ok" : "failed (符合预期)") << '\n';
    std::cout << "离开作用域时析构自动 fclose，无需手写清理路径。\n";
}
```

**结论**：RAII 把“释放”从控制流里彻底消除，是异常安全的地基；现代 `unique_ptr`/`lock_guard`
都是它的泛化。

### 演绎 2：函数对象（functor）—— lambda 出现前的可携带状态可调用体

**场景**：给 `std::sort` 传一个“按绝对值排序”的比较逻辑，C++98 无 lambda。
**选型**：定义重载 `operator()` 的结构体（functor），可携带成员状态。
**落地**：

> **示例 22** <span class="badge badge-exp">难度 ★★☆☆☆</span> · 演绎 2：函数对象（functor）

```cpp title="示例 22 · ★★☆☆☆"
#include <iostream>
#include <vector>
#include <algorithm>
#include <cstdlib>                             // std::abs

struct AbsLess {                               // C++98 functor
    bool operator()(int a, int b) const { return std::abs(a) < std::abs(b); }
};

int main() {
    std::vector<int> v; v.push_back(-5); v.push_back(2); v.push_back(-1);
    std::sort(v.begin(), v.end(), AbsLess());  // 传 functor 实例
    for (std::size_t i = 0; i < v.size(); ++i) std::cout << v[i] << ' ';
    std::cout << "\n(现代等价: std::sort(...,[](int a,int b){return std::abs(a)<std::abs(b);}))\n";
}
```

**结论**：functor 比函数指针更强——能内联、能带状态；C++11 lambda 本质就是编译器自动生成的
匿名 functor，理解 functor 才能真正理解 lambda 的闭包捕获。
