## 一、核心资料（S 级，必须进入教材）

### 1. Linux Kernel Memory Barriers（memory-barriers.txt）

- **类型**：官方技术文档
- **来源**：Linux Kernel（kernel.org）
- **链接**：https://www.kernel.org/doc/Documentation/memory-barriers.txt
- **作者**：David Howells、Paul E. McKenney、Will Deacon、Peter Zijlstra（全是 Linux 内存模型核心维护者）
- **核心内容**：Linux 内核内存屏障的完整使用指南——抽象内存访问模型、屏障种类（acquire/release/rmb/wmb/mb）、什么不能假设、地址依赖、控制依赖、SMP 屏障配对、锁与信号量的排序语义、跨 CPU 交互
- **解决的问题**：在弱内存模型架构（ARM/PowerPC）上如何正确使用内存屏障；x86 强模型与弱模型的差异
- **为什么重要**：这是操作系统级内存屏障的权威文档，McKenney 是 RCU 发明者、C++ 内存模型委员会成员。文档明确说"不是规范，是最低功能保证"——这种工程诚实本身就是教学素材
- **技术亮点**：ACQUIRE/RELEASE 的"屏障三明治"模型；屏障配对原则（release 必须配 acquire）；UP 系统上锁不提供排序保证
- **与 C++ 的关系**：Linux 的 smp_load_acquire/smp_store_release 与 C++ memory_order_acquire/release 语义同源；Linux 内核的内存模型是 C++ 内存模型的重要参考
- **与 CPP-Bible 的关系**：ch108 memory_order / ch109 fence 的核心参考资料；可以直接提取屏障配对示例作为实验
- **可以放入哪个章节**：part09_concurrency（ch108/ch109）、part14_perf（内存屏障性能）
- **适合讲什么**：内存屏障为什么需要、acquire/release 语义、屏障配对、弱模型 vs 强模型
- **可以提取什么源码**：smp_mb()/smp_rmb()/smp_wmb() 的架构特定实现（arch/x86/include/asm/barrier.h、arch/arm64/include/asm/barrier.h）
- **可以设计什么实验**：在 x86 上运行 Dekker 算法用 relaxed 序观察是否出错（x86 上通常不出错，ARM 上出错）；对比 acquire/release 修复
- **可以设计什么案例**：Linux 内核中真实的内存屏障使用场景（如 wakeup 路径）
- **历史背景**：文档从 2000 年代维护至今，反映了 Linux 从单 CPU 到多核的演进
- **工程背景**：Linux 必须支持从 x86 到 DEC Alpha 的全谱系架构，内存屏障抽象是可移植性的关键
- **相关论文**：McKenney "Is Parallel Programming Hard"（perfbook）
- **相关项目**：Linux kernel tools/memory-model/（形式化内存模型）
- **相关作者**：Paul E. McKenney（RCU 发明者、C++ 委员会成员）
- **可信度**：S
- **教材价值**：S

### 2. Hans Boehm "Threads cannot be implemented as a library"（PLDI 2005）

- **类型**：学术论文（奠基性）
- **来源**：ACM PLDI 2005 / HP Labs Technical Report HPL-2004-209
- **链接**：https://dl.acm.org/doi/10.1145/1065010.1065042（HPL 原链接已失效）
- **核心内容**：论证了在 C/C++ 中，线程不可能作为纯库实现——因为编译器优化（特别是基于单线程语义的重排）会破坏线程库的同步原语。必须在语言标准中定义内存模型
- **解决的问题**：C++11 之前，pthread 等线程库与编译器优化之间存在根本冲突；为什么需要语言级内存模型
- **为什么重要**：**这是 C++11 内存模型的奠基性论文**。没有这篇论文，C++ 可能不会有 memory_order 这一套。Boehm 是 C++ 内存模型的主要设计者
- **技术亮点**：用具体的编译器优化案例（如寄存器分配、指令重排）证明线程库无法自卫；提出"数据竞争即未定义行为"的核心原则
- **与 C++ 的关系**：直接催生了 C++11 [intro.multithread] 和 [atomics]；Boehm & Adve 的 N2052 "Memory Model for Multithreaded C++" 是其延续
- **与 CPP-Bible 的关系**：讲"为什么 C++ 需要内存模型"的历史脉络时的核心引用；可以解释为什么 data race 是 UB
- **可以放入哪个章节**：part09_concurrency 开篇（为什么需要内存模型）、C++历史章节
- **适合讲什么**：编译器优化如何破坏线程同步、为什么 memory_order 是语言特性不是库特性
- **可以设计什么实验**：展示一个编译器优化破坏 pthread 同步的最小案例（如全局变量的寄存器缓存）
- **历史背景**：2005 年，C++ 标准委员会正在规划 C++0x；Java 已经在 2004 年（JSR-133）修订了内存模型
- **工程背景**：HP 的 Boehm 团队在 IA-64（Itanium，弱内存模型）上的实践直接推动了这篇论文
- **相关论文**：Boehm & Adve "Foundations of the C++ Concurrency Memory Model"（PLDI 2008）、Manson/Pugh "Java Memory Model"（JSR-133）
- **相关项目**：GCC/Clang 的原子操作实现
- **相关作者**：Hans Boehm（C++ 内存模型首席设计师）、Sarita Adve
- **可信度**：S
- **教材价值**：S

### 4. Herlihy & Shavit "The Art of Multiprocessor Programming"

- **类型**：经典教材
- **来源**：Morgan Kaufmann，第 2 版 2020
- **核心内容**：并发编程的理论与实践——互斥、锁、并发对象、原子操作、内存模型、无锁数据结构、事务内存
- **解决的问题**：系统建立并发编程的知识体系
- **为什么重要**：**并发编程领域的圣经**。Herlihy 是无锁计算的奠基人（1991 年 Wait-free synchronization 论文），Shavit 是分布式计算专家
- **技术亮点**：共识数（consensus number）理论——它精确刻画了每种同步原语的计算能力（atomic registers=1、test-and-set=2、compare-and-swap=∞）；这是理解"为什么 CAS 是无锁编程的基础"的理论钥匙
- **与 C++ 的关系**：书中示例主要用 Java，但所有算法可直接翻译为 C++ atomic；C++20 的 std::atomic_ref、std::latch 等都能在书中找到理论基础
- **与 CPP-Bible 的关系**：CONC 域的理论框架来源；共识数理论可以做成一个独立的"为什么需要 CAS"原子
- **可以放入哪个章节**：part09_concurrency 理论部分
- **适合讲什么**：共识数、互斥算法演进、无锁数据结构设计
- **可以设计什么实验**：共识数的最小演示——用 atomic<int> 实现两线程共识，证明 test-and-set 只能解决 2 线程
- **历史背景**：第 1 版 2008，第 2 版 2020（增加了 GPU 并发、事务内存等）
- **相关论文**：Herlihy 1991 "Wait-free synchronization"（PODC，奠基性）
- **相关作者**：Maurice Herlihy、Nir Shavit
- **可信度**：S
- **教材价值**：S

- **历史背景**：Hazard Pointer 2004 年由 Maged Michael 提出；folly 实现从 2010 年代开始
- **相关论文**：Michael 2004 "Hazard Pointers: Safe Memory Reclamation for Lock-Free Objects"
- **相关项目**：libcds、Boost.Lockfree

### 9. Facebook folly MPMCQueue

- **类型**：开源项目源码
- **来源**：GitHub facebook/folly
- **链接**：https://github.com/facebook/folly/blob/master/folly/MPMCQueue.h
- **核心内容**：无锁多生产者多消费者队列，基于 Dmitry Vyukov 的 bounded MPMC queue 设计
- **解决的问题**：高性能消息传递——多线程间无锁传递数据

- **适合讲什么**：无锁队列设计、acquire/release 的实际应用、false sharing 避免
- **可以提取什么源码**：MPMCQueue::write/read 的核心循环（~20 行，极其精炼）
- **可以设计什么实验**：对比 MPMCQueue 与 std::queue+mutex 的吞吐率；在 ARM 上验证 acquire/release 的必要性
- **历史背景**：Vyukov 的设计来自 2010 年代；folly 实现被 Facebook 大规模使用
- **相关项目**：Boost.Lockfree queue、Disruptor（LMAX）
- **相关作者**：Dmitry Vyukov（设计）、Facebook 工程团队（实现）

### 10. Intel x86/64 Architecture Specification Volume 3 §8.2（Memory Ordering）

- **类型**：硬件架构规范
- **来源**：Intel 官方文档
- **链接**：Intel SDM Vol. 3A, Chapter 8.2
- **核心内容**：x86/64 的内存排序保证——TSO（Total Store Order）模型、什么会重排什么不会、locked 指令的语义、clflush 的排序
- **解决的问题**：x86 硬件到底保证什么
- **为什么重要**：x86 是"强内存模型"的代表；理解 x86 的 TSO 是理解弱模型差异的基础
- **技术亮点**：8.2.3.6 节的"loads may be reordered with older stores to different locations"——这是 x86 唯一允许的重排（StoreLoad），也是为什么 mfence 存在
- **与 C++ 的关系**：C++ memory_order 在 x86 上的实现直接受此规范约束；seq_cst 需要 mfence 或 lock 前缀
- **与 CPP-Bible 的关系**：讲"为什么 x86 上 relaxed 看起来没问题"的硬件依据；可以做成 CONC/ARCH 交叉原子
- **可以放入哪个章节**：part09_concurrency、part14_perf、体系结构章节
- **适合讲什么**：TSO 模型、StoreLoad 重排、mfence 的代价
- **可以设计什么实验**：用 mfence vs 不用 mfence 的 StoreLoad 重排演示
- **历史背景**：从 Intel 386 开始的 TSO 保证；x86 是唯一保持强排序的主流架构
- **可信度**：S（官方规范）
- **教材价值**：A

## 九、发现的知识空白

1. **C++ 内存模型的"为什么"叙事缺失**——现有 ch108/ch109 只讲"是什么"，没有讲"为什么 C++ 需要内存模型"（Boehm 论文的核心论点）
2. **编译器重排 vs CPU 重排的区分实验缺失**——preshing 的实验可以直接借鉴，但需要适配 CPP-Bible 的证据卡格式
3. **弱内存模型实验缺失**——本机只有 x86（强模型），需要 ARM 设备或 QEMU 模拟才能展示弱模型重排；CI 只有 x86
4. **共识数理论完全未覆盖**——Herlihy 的共识数是理解无锁编程的理论基础，但全书无此内容
5. **无锁内存回收（Hazard Pointer/RCU/Epoch）完全未覆盖**——这是 lock-free 编程的核心难题
6. **C++26 hazard pointer 标准化（P2530R3）未跟踪**——与 folly Hazptr 的关系值得做一个 HIST 原子
