## 一、为什么读大代码库难

| 障碍 | 本质 |
|---|---|
| 体积 | 百万行，人脑无法线性读完 |
| 历史 | 代码是演化的沉淀，不是一次设计（约束/妥协埋在深处） |
| 依赖 | 组件间隐式耦合（全局状态、回调、宏） |
| 惯例 | 每个项目有自己的"方言"（命名/结构/模式） |
| 缺上下文 | 没有设计文档时，只能从代码反推意图 |

- **正确心态**：读大代码库不是"读"，是"狩猎"——带着具体问题，用工具定位，而非从头到尾
- 目标分层：能用（改 bug）→ 能懂（讲机制）→ 能扩（加功能）——先定目标再选策略

## 二、两种策略：自顶向下 vs 自底向上

### 自顶向下（推荐入门）

1. **架构地图先行**：官方文档/目录结构/组件图（30 分钟建立地图，不急着读码）
2. **入口点追踪**：从 main() 出发，跟随初始化 → 主循环 → 核心调用链
3. 每次沿一条"请求路径"深入（如 Chromium 一次页面加载），**用完即退**
4. 用调试器断点验证理解（70 轮技能直接复用）

### 自底向上（推荐攻坚）

1. 选核心**数据结构**（如 LLVM 的 Instruction/Value、Chromium 的 RenderFrameHost）
2. 读懂数据结构的字段与生命周期
3. 看操作它的算法（pass/遍历）
4. 最后组装成系统理解

- **两者结合**：地图（顶）告诉你去哪，数据结构（底）告诉你到了后看什么——**迭代收敛**，不追求一次读通

## 三、工具：代码导航与动态阅读

### 1. 静态索引

- **X-Refs（Chromium CodeSearch）**：调用图、override、引用、声明/定义一键跳转（Chromium 官方文档：cross-reference searches 给 call graph/overrides/declaration）
- cscope/ctags：经典符号索引；IDE 的 Go to Definition / Find References
- 现代：sourcegraph/LSP（clangd）——**语言服务器把索引能力带进编辑器**

### 2. 动态阅读（被低估的武器）

- **调试器**：断点 + 调用栈 = 运行时调用图（比静态 grep 准——宏/虚函数/模板展开后的真相）
- **性能工具**：perf 火焰图/LLVM XRay（函数级 trace）——"热路径在哪"直接告诉你重点读哪
- **日志/测试**：跑测试打断点，看真实数据流——比读代码快

### 3. 构建系统也是文档

- 模块划分（CMake target 依赖图）≈ 架构图（54 轮构建系统的读法）
- 测试文件命名 = 功能清单（68 轮测试工程）

## 四、三个旗舰项目的架构模式

| 项目 | 架构模式 | 阅读切入口 |
|---|---|---|
| Chromium | **多进程 + 分层**（浏览器/渲染/GPU 进程，content API 分界） | 一次页面加载的进程间消息流 |
| LLVM | **流水线 + 模块化 pass**（Frontend→IR→Opt→Backend） | 一行代码如何变成机器码 |
| MySQL | **插件化存储引擎 + 两层优化器**（server 层/存储引擎层） | 一条 SQL 的执行路径 |

- 共同规律：**旗舰项目都有清晰的分层/流水线主线**——找到主线，其余都是细节
- 每项目一部"宪法文档"：Chromium 的 design docs、LLVM 的 Programmer's Manual、MySQL 的 internals 文档

## 五、给 CPP-Bible 读者的路线

1. **别从 Chromium 开始**：先读小型精品（SQLite/Redis/单文件库）——5000 行能读透的比百万行"看过的"更有价值
2. 按"一个请求的全路径"读：SQLite 一条 INSERT、Redis 一次 GET——**用路径组织阅读，不用目录**
3. 每读完一段，用"我能讲清它怎么工作"自测（费曼检验）
4. 工具优先：clangd + 调试器 + 火焰图三件套
