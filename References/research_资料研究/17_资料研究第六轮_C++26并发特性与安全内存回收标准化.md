## 一、核心资料（S/A+ 级）

### 1. P2530R3：Hazard Pointers for C++26

- **类型**：标准提案（WG21 论文）
- **来源**：WG21（open-std.org）
- **链接**：https://wg21.link/P2530
- **作者**：Maged M. Michael（HP 论文作者）、Facebook Folly 团队
- **状态**：**已投票进入 C++26**（Varna 2023 plenary，LWG Motion 7）
- **核心内容**：将 hazard pointer 安全延迟回收技术纳入 C++26 标准库。接口基于 Concurrency TS 2（N4895）的子集，参考实现是 Facebook Folly（2017 年起生产环境重度使用）。
- **解决的问题**：无锁数据结构中"unlink 的节点什么时候可以安全 delete"——use-after-free 是无锁编程最致命的 bug
- **为什么重要**：**这是 C++ 首次把"安全内存回收"纳入标准库**。之前只能用 folly Hazptr、liburcu 等第三方库。C++26 起 `#include <hazard_pointer>` 即可用。
- **技术亮点**：
  - **核心 API**：`std::hazard_pointer`、`std::hazard_pointer_obj_base<T>`、`std::make_hazard_pointer()`
  - **保护机制**：线程设置 hazard pointer 指向对象 → 告诉所有线程"这个对象我正在用，别回收"
  - **延迟回收**：retire 对象后，扫描所有 hazard pointer，没被保护的才回收
  - **刻意省略的功能**：自定义 domain（folly 经验表明默认 domain 够用）、全局同步回收（cohort-based 更优但措辞复杂，留待未来）
  - **ABI 稳定性预留**：`hazard_pointer_obj_base` 预留计数器和指针空间，为未来扩展（commutative counting、cohort reclamation）留余地
  - **实现量限制**：可保护对象数上限 256（实现定义下限）
- **与 C++ 的关系**：直接对应 C++26 `<hazard_pointer>` 头文件，feature-test macro `__cpp_lib_hazard_pointer`
- **与 CPP-Bible 的关系**：CONC 域"安全内存回收"章节的标准依据；与第三轮 folly Hazptr 源码调研形成"第三方实现→标准化"的闭环
- **可以放入哪个章节**：part09_concurrency（无锁编程）、part03_template（标准库新特性）
- **适合讲什么**：hazard pointer 原理、C++26 标准 API、从 folly 到标准的演化
- **可以设计什么实验**：用 folly Hazptr（当前可用）和 C++26 std::hazard_pointer（未来可用）写同一个无锁栈，对比 API 差异
- **历史背景**：Michael 2004 论文 → folly 2016 实现 → 2017 生产使用 → 2023 投票进 C++26 → 2026 标准发布
- **可信度**：S（WG21 官方提案，一手来源）
- **教材价值**：S

### 2. P2545：Why RCU Should be in C++26

- **类型**：标准提案（WG21 论文）
- **来源**：WG21（open-std.org）
- **链接**：https://wg21.link/P2545
- **作者**：Paul E. McKenney（RCU 之父）、Michael Wong、Maged M. Michael 等
- **状态**：**已进入 C++26**（P2545R4，2026 年 3 月 Croydon 会议最终确定）
- **核心内容**：将 RCU（Read-Copy-Update）纳入 C++26 标准库。API 比 Linux 内核 RCU 小得多，跟踪用户态实现经验。
- **解决的问题**：读多写少场景下的无锁读——读端零开销（非抢占内核编译为空），写端延迟回收
- **为什么重要**：**RCU 从 Linux 内核（2002）走到 C++ 标准（2026），24 年的演化**。这是内核技术进入用户态标准库的里程碑。
- **技术亮点**：
  - **核心 API**：`std::rcu_domain`、`std::rcu_obj_base<T>`、`std::rcu_reader`（RAII）、`rcu_synchronize()`、`rcu_retire()`、`rcu_barrier()`
  - **侵入式设计**：被保护对象继承 `rcu_obj_base<T>`（类似 Linux 的 `struct rcu_head`）
  - **读端零开销**：`rcu_reader` 构造/析构在非抢占内核编译为空操作用户态实现可能是线程局部计数器
  - **可移植性取舍**：允许在 `retire()` 内同步调用回调（不需要后台线程），但因此不能在持有任何 deleter 可能获取的 mutex 时调用 retire——否则死锁
  - **比内核 RCU 小**：刻意只标准化用户态经验验证过的最小接口
- **与 C++ 的关系**：C++26 `<rcu>` 头文件
- **与 CPP-Bible 的关系**：CONC 域"RCU 标准化"章节；与第二轮 RCU 调研形成"内核→用户态→标准"的完整演化链
- **可以放入哪个章节**：part09_concurrency、part16_os
- **适合讲什么**：RCU 原理、C++26 API、从内核到标准的演化
- **可以设计什么实验**：用 liburcu（当前可用）和 C++26 std::rcu（未来可用）写同一个读多写少数据结构
- **历史背景**：Linux 内核 2002 年采用 → liburcu 用户态移植 → P0566 2017 首次提案 → P2545 2022 重提 → 2026 标准化
- **可信度**：S（WG21 官方提案 + McKenney 亲自设计）
- **教材价值**：S

### 3. Paul McKenney：RCU API in C++26（内核 vs 标准对照表）

- **类型**：技术博客（一手作者）
- **来源**：people.kernel.org（Paul McKenney 个人博客）
- **链接**：https://people.kernel.org/paulmck/stupid-rcu-tricks-rcu-api-in-cpp26
- **核心内容**：McKenney 亲自写的 Linux 内核 RCU vs C++26 RCU API 对照表：

| Linux 内核 | C++26 |
|---|---|
| `guard(rcu)()` | `std::scoped_lock l(std::rcu_default_domain())` |
| `rcu_read_lock()` | `std::rcu_default_domain().lock()` |
| `rcu_read_unlock()` | `std::rcu_default_domain().unlock()` |
| `synchronize_rcu()` | `std::rcu_synchronize()` |
| `struct rcu_head` | `std::rcu_obj_base<T>`（继承） |
| `call_rcu()` | `fp->retire(cb)` |
| `kfree_rcu()` | `fp->retire()`（无参） |
| `rcu_barrier()` | `std::rcu_barrier()` |

- **为什么重要**：**RCU 之父亲自解释 C++26 API 设计取舍**——为什么比内核小、为什么允许同步回调、死锁风险在哪
- **技术亮点**：
  - 侵入式 vs 非侵入式：C 用 `struct rcu_head` 嵌入，C++ 用继承 `rcu_obj_base<T>`
  - 同步回调的可移植性：C++ 要能在无后台线程的环境运行，所以允许 retire() 内直接调用 deleter
  - 死锁警告：不能在持有任何 deleter 可能获取的 mutex 时调用 retire()
  - 参考实现：thin C++ wrapper around liburcu
- **可信度**：S（McKenney 本人，一手来源）
- **教材价值**：A+

### 4. C++26 并发特性实现现状（2026 年 7 月）

- **类型**：实现状态追踪
- **来源**：GCC bug tracker + libc++ PR + 韩国工程师博客
- **核心内容**：
  - **GCC libstdc++**：GCC 16.1（2026 年 4 月）未包含 `<hazard_pointer>` 和 `<rcu>`；Jonathan Wakely 2025 年 10 月说"还没人开始实现"
  - **Clang libc++**：2026 年 8 月 PR #218218 实现了 `std::hazard_pointer`（domain、per-thread record cache、sharded retired lists、reclamation pass），RCU 尚未实现
  - **MSVC STL**：还在完成 C++23 功能，C++26 库功能 PR 要等
  - **结论**：三大编译器都还没完整发布这两个头文件，标准确定和实现之间有时间差
- **教学价值**：**"标准确定 ≠ 可以用"**——这是 C++ 开发者必须理解的现实。教材应该教"用 folly/liburcu 过渡，等编译器跟上"。

### 5. P3135R0：Hazard Pointer Extensions

- **类型**：后续扩展提案
- **来源**：open-std.org
- **链接**：https://www.open-std.org/jtc1/sc22/WG21/docs/papers/2024/p3135r0.pdf
- **核心内容**：P2530R3 进入 C++26 后，描述可能的扩展：commutative counting、cohort-based synchronous reclamation、custom domains。基于 folly 生产经验排序优先级。
- **教学价值**：展示标准化的"先最小可用、再逐步扩展"策略。

### 6. P3428R0：Hazard Pointer Batches

- **类型**：性能优化提案
- **来源**：open-std.org
- **核心内容**：批量 retire 优化——一次 retire 多个对象，减少扫描 hazard pointer 的开销。
- **教学价值**：无锁数据结构的性能优化方向。

### 7. C++26 标准时间线

- **类型**：标准化进程
- **来源**：isocpp.org + 多方确认
- **核心内容**：
  - 2026 年 3 月：Croydon 会议，C++26 技术工作完成（feature freeze）
  - 2026 年 6 月：开始 C++29 工作草案
  - C++26 关键特性：reflection（P2996）、contracts（P2900）、hazard_pointer、rcu、std::simd、std::execution、memory safety hardening
- **教学价值**：C++ 标准化进程的真实时间线——从提案到发布通常 5-10 年。

## 四、HP vs RCU 选择指南（教学用）

| 维度 | Hazard Pointer | RCU |
|---|---|---|
| 读端开销 | 低（写 hazard slot + 重确认） | 零（编译为空或线程局部计数） |
| 写端开销 | 中（扫描 hazard slot） | 高（等待 grace period） |
| 适用场景 | 通用无锁数据结构 | 读多写少（99% 读） |
| 内存开销 | 每线程 hazard slot | grace period 内累积对象 |
| 延迟 | 低（异步回收） | 写端延迟高（等 grace period） |
| 可移植性 | 高 | 中（用户态实现复杂） |
| C++26 头文件 | `<hazard_pointer>` | `<rcu>` |
| 参考实现 | folly Hazptr | liburcu |
