## 一、GC 为什么存在：自动内存管理的哲学

- 手动内存（C/C++）：精确、可控，但错误率高（泄漏/悬垂/双重释放）
- GC（Java/Go/Rust 的某些路径/托管运行时）：自动识别"不再可达"的对象并回收，免除 UAF（use-after-free）与大多数泄漏
- 代价：**回收时机不可控、暂停（pause）、额外元数据与屏障开销**——与 C++ RAII 的"确定性析构"形成根本对照
- **RC 与 GC 的本质区别**：引用计数（shared_ptr）是"对象本地记账"（有循环泄漏问题）；追踪式 GC 是"从根出发做图可达性分析"（天然解决循环）

## 二、基础概念

### 1. 可达性（Reachability）

- 从**根集（roots）**出发：栈上的引用、静态/全局变量、寄存器中的引用
- 沿引用图能到达的对象 = 存活；其余 = 垃圾
- 这正是图遍历问题（DFS/BFS）——GC 是算法教科书在工业界的直接应用

### 2. 三大经典算法

| 算法 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| 标记-清除（Mark-Sweep） | 标记可达，扫描清除 | 简单、对象不搬移 | 碎片化、两次遍历、清除后局部性差 |
| 复制（Copying） | 存活对象拷到另一半空间，整半清零 | 无碎片、分配快（bump pointer）、局部性好 | 内存利用率减半（from/to 双空间） |
| 标记-整理（Mark-Compact） | 标记后把存活对象压实到一端 | 无碎片、空间利用率高 | 移动对象需更新所有引用（慢） |

- 现代收集器都是组合：分代（年轻代复制 + 老年代标记整理/并发标记）

### 3. 分代假说（Weak Generational Hypothesis）

- **绝大多数对象朝生夕死**（临时对象迅速变垃圾）
- 少数对象存活久（缓存、单例）
- 推论：把堆分年轻代/老年代，年轻代用快速复制收集（一次 GC 只处理一小块）、老年代低频收集 → 吞吐与暂停的平衡

- **来源**：dev.to + kaksha-dev + 综合
- **可信度**：S

## 三、并发 GC 的正确性：三色标记与屏障

### 1. 问题

GC 标记对象时，**应用线程（mutator）同时在改引用图**——可能把已标记为"黑"的对象指向"白"（未标记）对象，漏标 → 误回收存活对象（灾难）。

### 2. 三色抽象

- 白：未访问（可能是垃圾）
- 灰：已发现但引用未处理完
- 黑：已访问完，引用都已处理
- **不变量**：黑色对象不能指向白色对象（否则漏标）
- 并发标记破坏该不变量 → 需要屏障

### 3. 写屏障（Write Barrier）

- 编译器/JIT 在**每次指针写入**时插入小段检查（赋值 x.f = y）：
  - **增量更新（Dijkstra 型）**：把新写入的引用目标标灰（防止黑→白）
  - **SATB（Snapshot-at-the-Beginning，快照）**：记录被覆盖前的旧引用（Yuasa），保持开始时的快照语义
- 代价：每条指针写都多几条指令——这是托管语言"对象赋值"比 C++ 赋值"贵"的一个隐藏原因

### 4. 读屏障/载荷屏障（Load Barrier，ZGC/Shenandoah 用）

- 读指针时插入检查（对象可能正在被移动）——如果对象被移动，跟随转发表找到新地址
- ZGC 用**着色指针（colored pointer）**：把 GC 状态编码进指针的未用位（64 位架构的地址空间富余），读屏障按指针里的颜色判断是否要转发
- Shenandoah 用 **Brooks 指针**（对象头部放一个"前向指针"字段，任何读都先解引用）
- 两种"移动对象而不用停世界"的技术——并发压实（concurrent compaction）的钥匙

### 5. 安全点（Safepoint）

- 并发收集不是每个指令都能打断：GC 只能在**安全点**（方法调用边界、循环回边、特定指令）暂停线程
- JIT 编译器负责在安全点插入检查——与第三十五轮 JIT 直接衔接
- 大循环不调方法时可能长期不到安全点（GC 等待）——"GC 暂停时间莫名变长"的排查点

- **来源**：martinuke0 三色标记（清晰）+ ACM ZGC + geekworkbench
- **可信度**：S

## 四、G1 / ZGC / Shenandoah：现代三巨头

| | G1 | ZGC | Shenandoah |
|---|---|---|---|
| 目标 | 吞吐与暂停平衡（默认） | 超低延迟（亚毫秒） | 超低延迟 |
| 堆模型 | 固定大小 Region | 变长 ZPage | Region |
| 分代 | 是 | Java 24+ 仅分代 | 可选 |
| 并发压实 | 否（复制阶段 STW） | 是（着色指针+读屏障） | 是（Brooks 指针） |
| 暂停 | 数十毫秒 | 亚毫秒~低个位数毫秒 | 低个位数毫秒 |
| 实现方 | Oracle | Oracle | Red Hat |
| 关键技术 | 区域回收+SATB | 着色指针+读屏障+转发表 | 前向指针+读屏障 |
| 适用 | 大多数服务器 | 大堆+延迟敏感（可达 16TB） | 延迟敏感 |

- **G1**：把堆切成 Region，优先回收垃圾最多的 Region（Garbage-First）→ 暂停可控
- **ZGC**：标记/压实几乎全并发；**暂停不随堆大小增长**（这就是它的卖点）；代价：指针位被占用（限制 64 位、不支持 compressed oops）、读屏障开销（每条引用读取）
- **Shenandoah**：对象头部前向指针方案，无需占用指针位，但对象头开销（早期 1 word，JDK14 优化掉）

- **来源**：G1GC vs ZGC vs Shenandoah 对比 + ACM + CSDN + rgyani
- **可信度**：S

## 五、GC 与 C++ 的哲学对话（对 CPP-Bible 最有价值）

| 维度 | 追踪式 GC | C++ RAII/智能指针 |
|---|---|---|
| 回收时机 | 不可控（堆满/触发） | 确定性（作用域结束/引用归零） |
| 循环引用 | 天然解决（图可达性） | shared_ptr 有循环问题（weak_ptr 破环，第五批 RAII 原子已覆盖） |
| 碎片 | 复制/整理消除 | malloc 可能碎片化（内存池缓解） |
| 开销 | 屏障、暂停、额外内存 | 引用计数原子操作、unique_ptr 零开销 |
| 实时性 | 不适合硬实时 | 适合（析构确定） |
| 悬垂引用 | 不可达即回收（安全） | 裸指针悬垂、use-after-free 风险 |
| 失败模式 | GC pause/内存无界 | 泄漏/悬垂（人为错误） |

- **工程判断**：
  - 事件驱动/低频对象 → GC 的"自动"很划算
  - 高频对象创建/硬实时/嵌入式 → RAII 确定性的价值无可替代
  - 混合：C++ 里用 arena/内存池模拟"区域回收"（scope 型分配器），用 unique_ptr 表达所有权——这是 C++ 的"GC 替代品"
- **互操作**：Java/Kotlin 通过 JNI 持有 C++ 对象、C++ 调用 JVM 时 GC 与 RAII 边界的正确管理（引用注册/卸载）是真实工程难点
