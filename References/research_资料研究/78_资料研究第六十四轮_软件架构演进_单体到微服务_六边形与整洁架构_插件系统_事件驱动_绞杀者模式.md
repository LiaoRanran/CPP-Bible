## 一、核心认知：架构是复杂性斗争的编年史

- 架构没有"最好"，只有"当前复杂度的合适解"——**每个模式是上一个模式缺点的解药**（CSDN 那篇标题就是"与复杂性斗争的编年史"）
- 决策维度（Learnixo 表）：
  | | 单体 | 模块化单体 | 微服务 | Serverless |
  |---|---|---|---|---|
  | 部署单元 | 1 进程 | 1 进程 | N 服务 | 函数 |
  | 数据 | 共享 DB | 分离 schema | 独立 DB | 外部存储 |
  | 通信 | 进程内 | 进程内 | 网络（HTTP/队列） | 事件/HTTP |
  | 事务 | ACID | ACID | Saga（最终一致） | Saga |
- **规律**：粒度越细，部署/扩展/团队自由越高，但分布式复杂度越高（网络/一致性/可观测性）

## 二、内部架构模式

| 模式 | 核心 | 适用 |
|---|---|---|
| 分层（N-Tier） | 表现→应用→领域→基础设施 | 简单 CRUD；易耦合（依赖 DB/API） |
| 六边形/端口-适配器 | **领域在中心，端口（接口）向外，适配器插拔** | 复杂业务、要测试/换基础设施 |
| 整洁/洋葱 | 依赖规则单向指向核心 | DDD 应用 |

- **六边形的本质**：业务逻辑长寿、基础设施易变 → 让业务不依赖基础设施（Ports & Adapters：Ruchit Suthar 明说 "swap Postgres for DynamoDB without touching a business rule"）
- 对 C++ 的映射：接口（纯虚/概念）作为端口、具体实现作为适配器——**依赖倒置是插件系统的基石**
- 工程提醒：分层"严格分层"增加调用链复杂度——ionutbalosin 演讲：松弛分层优于强制分层（无中间层时不要硬塞）

## 三、插件系统：架构的可扩展性终极形态

- **核心 + 插件**：核心定义接口（端口），插件实现并注册——能力以增量模块加入
- 典型：编辑器（VSCode/LSP）、游戏引擎（57 轮）、浏览器扩展
- C++ 实现三件套：接口（抽象基类/概念）+ 注册表（工厂/类型映射）+ 动态加载（dlopen/插件目录）
- 与依赖注入的关系：插件系统 = 依赖倒置 + 运行时发现（延迟绑定）
- **关键取舍**：插件 API 一旦发布就成契约（兼容负债）——接口稳定性是插件系统的生命线

## 四、事件驱动（EDA）

- **服务间不直接调用，而是发事件**：订单服务发 OrderPlaced → 库存服务订阅处理——松耦合、异步、可扩展
- 配套模式：事件溯源（Event Sourcing，状态 = 事件的回放）、CQRS（读写分离模型）
- 代价：**最终一致性**（不再是 ACID 事务）——从"强一致"到"可接受的不一致"是架构范式转移
- 对 C++ 的映射：事件循环 + 回调/协程（72 轮 Asio）是 EDA 的进程内形态

## 五、迁移：绞杀者模式（Strangler Fig）

- **渐进替换而非推倒重来**：新服务逐步绞杀老单体——按路径路由分流，功能迁移完单体"被绞杀至空"
- 方法论：DDD 限界上下文（找到服务边界）、事件风暴（发现领域事件/聚合）、数据库接缝（只被一处访问的表 = 迁移候选）
- 教训：**大爆炸重写是反模式**（Rewrite 的经典失败：复杂与历史一起丢失）——这与本项目的"存量债务不重写、新原子单列"哲学同构

## 六、给 CPP-Bible 项目的架构启示

- 本项目本身就是"核心（工具链/门禁）+ 内容（原子库）+ 适配器（生成器/质检器）"的架构——**领域核心 = 质量标准，工具 = 端口实现**
- 教训迁移：
  - 六边形思想 → 质检规则（gate_engine）与执行器（工具）解耦——**规则是端口，工具是适配器**（与现架构一致）
  - 插件系统 → 规则可注册（29 条规则的注册中心）已是插件式设计
  - 绞杀者模式 → G5 原子化对存量 Book 内容的渐进替换正是"绞杀"
