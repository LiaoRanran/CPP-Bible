## 一、零开销异常模型（Zero-Cost Exception Handling）

### 1. 核心思想

> 正常路径（不抛异常）**零额外指令执行**——try 块的存在不增加任何运行时代码。成本只在异常真正抛出时支付。

- 术语由 **HP** 在实现 C++ 异常时提出
- Itanium C++ ABI 定义了标准实现方法
- **来源**：Itanium C++ ABI 规范 + LLVM 异常处理文档
- **可信度**：S

### 2. 旧方案 vs 现代方案

| 维度 | SjLj（setjmp/longjmp） | 表驱动（Table-Driven，零开销） |
|---|---|---|
| 正常路径 | 有开销（每个 try 入口设置/拆除 jmp_buf） | 零额外指令 |
| 异常路径 | 快（直接 longjmp） | 慢（遍历静态表） |
| 代码大小 | 小 | 大（.eh_frame + .gcc_except_table） |
| 代表 | 旧版 GCC、某些嵌入式 | 现代 GCC/Clang（Linux）、MSVC x64 |

### 3. "零开销"的真实含义

零开销指的是**正常路径无指令开销**，但有隐藏成本：

| 成本维度 | 具体表现 |
|---|---|
| 代码大小 | .eh_frame + .gcc_except_table 增加约 **7-15%** 二进制大小（GCC 官方数据 ~7%） |
| 编译限制 | 异常边界可能抑制编译器内联和死代码消除（try/catch 是优化屏障） |
| 异常路径 | ~1-10 微秒（取决于栈深度）——栈遍历 + RTTI 类型匹配 + 析构调用 |
| 全局锁 | 表驱动展开器用全局互斥锁保护表（P2544R0 指出高核心数下灾难） |
| OOM 问题 | 异常对象本身需要堆分配，OOM 时抛 bad_alloc 可能递归失败 |

- **来源**：GCC libstdc++ 手册 + P2544R0 提案 + Dr-Sergey 分析
- **可信度**：S

## 二、Itanium C++ ABI：两阶段展开

### 1. throw 的完整调用链

```
throw MyException();
  │
  ├─ 1. __cxa_allocate_exception(size)  ← 堆分配异常对象（__cxa_exception 头部 + 用户对象）
  │
  ├─ 2. 拷贝/移动构造用户异常对象到分配的内存
  │
  ├─ 3. __cxa_throw(exc_obj, type_info, destructor)  ← 设置异常头字段
  │     │
  │     └─ 4. _Unwind_RaiseException(&unwindHeader)  ← 语言无关的展开入口
  │           │
  │           ├─ 阶段 1：搜索阶段（Search Phase）
  │           └─ 阶段 2：清理阶段（Cleanup Phase）
  │
  └─ 5. 如果 _Unwind_RaiseException 返回（说明没有捕获者）→ failed_throw() → std::terminate()
```

### 2. 阶段 1：搜索阶段（Search Phase）

- 从当前帧开始，**向上遍历调用栈**
- 对每个帧调用 **personality function**（带 `_UA_SEARCH_PHASE` 标志）
- personality function 查 `.gcc_except_table`（LSDA），问："这个帧能捕获这个异常类型吗？"
- 找到捕获帧后**记录位置**，但**不执行任何析构**
- 如果遍历完整个栈都没找到捕获者 → uncaught exception → std::terminate()

### 3. 阶段 2：清理阶段（Cleanup Phase）

- **重新从当前帧开始遍历**（不是从搜索阶段的断点继续）
- 对每个帧调用 personality function（带 `_UA_CLEANUP_PHASE` 标志）
- 执行该帧的 **cleanup**（局部对象析构）
- 到达捕获帧时：恢复寄存器状态（从 DWARF CFI 恢复），跳转到 **landing pad**（catch 块入口）
- 调用 `__cxa_begin_catch` 获取异常对象，执行 catch 块
- catch 块结束后调用 `__cxa_end_catch`，异常对象引用计数减 1，到 0 则释放

### 4. 为什么要两阶段？

> 如果在搜索阶段就执行析构，而后来发现没有捕获者（uncaught exception），已经析构的对象无法恢复——所以先搜索确认有捕获者，再清理。

这是异常安全的关键设计：**析构只在确认异常会被捕获时才执行**。

- **来源**：Itanium C++ ABI 规范（abi-eh-1.22）+ PVS-Studio 深度分析
- **可信度**：S

## 三、关键组件详解

### 1. Personality Function（人格函数）

- 每个帧的"裁判"，C++ 用 `__gxx_personality_v0`
- 职责：
  - 搜索阶段：判断该帧是否有匹配的 catch（类型匹配用 RTTI）
  - 清理阶段：执行该帧的 cleanup（局部对象析构）
- 输入：当前 PC、异常对象、阶段标志
- 输出：`_URC_CONTINUE_UNWIND`（继续展开）/ `_URC_HANDLER_FOUND`（找到捕获者）/ `_URC_INSTALL_CONTEXT`（安装上下文，跳转到 landing pad）
- **来源**：libcxxabi cxa_personality.cpp 源码
- **可信度**：S

### 2. DWARF CFI（Call Frame Information）

- 存在 `.eh_frame` 段
- 描述**如何恢复每个帧的寄存器状态**（栈指针、返回地址、被调用者保存寄存器）
- 栈展开时需要：知道当前帧的返回地址在哪、上一帧的寄存器怎么恢复
- 格式基于 DWARF2/DWARF3 标准
- **可信度**：S

### 3. LSDA（Language-Specific Data Area）

- 存在 `.gcc_except_table` 段
- 描述每个函数的 **try/catch 块位置**和**类型匹配表**
- personality function 查 LSDA 来判断某个 PC 是否在 try 块内、对应的 catch 类型是什么
- **可信度**：S

### 4. Landing Pad（着陆垫）

- catch 块的入口地址
- 展开器跳转到 landing pad 时，已经恢复了该帧的寄存器状态
- landing pad 开头通常是 `__cxa_begin_catch` 调用（获取异常对象）
- **可信度**：A

### 5. 异常对象的生命周期

- 异常对象在**堆上**分配（`__cxa_allocate_exception`）
- `__cxa_exception` 头部包含：引用计数、异常类型（type_info）、析构函数、unwind header
- 引用计数管理：`__cxa_begin_catch` 增加引用，`__cxa_end_catch` 减少
- `std::current_exception` / `std::rethrow_exception` 也通过引用计数管理
- **可信度**：S

## 四、性能开销的量化

### 1. 正常路径（不抛异常）

- **指令开销**：接近零（无额外分支、无额外存储）
- **间接开销**：
  - 代码大小 +7-15%（.eh_frame 表）
  - try/catch 边界可能抑制内联（编译器不能跨异常边界内联有副作用的函数）
  - 指令缓存可能因代码膨胀而命中率下降

### 2. 异常路径（抛异常）

| 操作 | 成本 |
|---|---|
| 异常对象分配 | 一次 malloc |
| 搜索阶段 | 遍历栈 + 每帧 personality 调用 + RTTI 类型匹配 |
| 清理阶段 | 再次遍历栈 + 每帧析构调用 |
| 上下文恢复 | 从 DWARF CFI 恢复寄存器 |
| 总计 | ~1-10 微秒（取决于栈深度） |

### 3. 高核心数下的问题（P2544R0）

> 异常展开实际上是**单线程的**——表驱动展开器用全局互斥锁保护展开表，高核心数下多个线程同时抛异常会严重争用。

- **来源**：WG21 P2544R0 提案
- **可信度**：A+

### 4. 与 error codes / std::expected 的对比

| 维度 | 异常 | error code | std::expected |
|---|---|---|---|
| 正常路径 | ~0 | 每次调用检查返回值 | 每次调用检查 expected |
| 错误路径 | ~1-10μs | ~0（只是返回值） | ~0 |
| 代码大小 | +7-15% | 基线 | 略增（判别联合） |
| 错误不可忽略 | 是（不 catch 就 terminate） | 否（可忽略返回值） | 是（必须访问 value/error） |
| 类型安全 | 是（RTTI） | 弱（int 错误码） | 强（泛型错误类型） |

## 五、Windows SEH 对比

### 1. x86 32位：基于帧的 SEH

- 异常处理程序注册在栈上的**单链表**（FS:[0] 指向链表头）
- 每个 `__try` 块入口注册处理程序，出口注销
- **正常路径有开销**（注册/注销指令）
- 已被 x64 表驱动方案取代

### 2. x64：表驱动 SEH

- 类似 Itanium ABI 的表驱动方案
- 正常路径**零开销**
- 异常表存在 `.pdata` 和 `.xdata` 段（对应 Linux 的 .eh_frame）
- MSVC 的 C++ try/catch 内部用 SEH 实现

### 3. VEH（Vectored Exception Handling）

- 通过 `AddVectoredExceptionHandler` 注册
- **VEH 优先于 SEH 调用**——硬件异常时内核先调 VEH，再调 SEH
- 不依赖栈帧，适合注入式调试

### 4. Itanium vs SEH 总结

| 维度 | Itanium ABI（Linux/Mac） | Windows SEH x64 |
|---|---|---|
| 正常路径 | 零开销 | 零开销 |
| 展开表 | .eh_frame + .gcc_except_table | .pdata + .xdata |
| Personality | __gxx_personality_v0 | __C_specific_handler / __CxxFrameHandler3 |
| 异常对象 | 堆分配 | 堆分配（EXCEPTION_RECORD） |
| 两阶段 | 是（搜索+清理） | 是（类似） |

- **来源**：Microsoft Learn + Hex-Rays Compiler Internals（Recon 2012）
- **可信度**：A+

## 六、替代方案与未来

### 1. Herb Sutter 确定性异常（P0709）

- 异常作为**值**传递，不做栈展开
- 类似 std::expected 的语言级支持
- 正常路径和错误路径都有确定性开销（无"罕见事件"假设）
- 解决了：非确定延迟、代码大小膨胀、ABI 锁定、全局锁
- 状态：提案中，未进入标准

### 2. -fno-exceptions

- 禁用异常（嵌入式/游戏/浏览器常用）
- throw 编译为 std::terminate 或链接错误
- 标准库在 -fno-exceptions 下有特殊编译版本（无异常抛出）
- 代码大小显著减小

### 3. std::expected（C++23）

- 错误作为值，无栈展开
- 已在第十二轮调研中详细覆盖
- 与异常的对比见上表

## 十二、发现的知识空白

1. **异常底层实现完全空白**——项目有 RAII 原子但没有讲解异常怎么触发析构
2. **两阶段展开空白**——搜索阶段/清理阶段的设计原因是极好的教学内容
3. **异常性能量化空白**——正常路径零开销但异常路径 1-10μs，没有实测
4. **Itanium vs SEH 跨平台对比空白**——ABI 域完全没有异常相关内容
5. **P2544R0 高核心数问题空白**——异常的根本缺陷，工业界重要话题
