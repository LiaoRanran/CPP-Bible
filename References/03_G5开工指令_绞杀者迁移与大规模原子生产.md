## 二、开工前必须先建的两个基础设施

### 2.1 全局误解库 `misconceptions/`

**问题**：当前每个原子的 misconception 字段手写文本，1300 个原子全手写不现实，且同一误解（如"std::move 会移动对象"）会被重复写、表述不一致。

**做法**：
1. 建 `misconceptions/` 目录，每条误解一个文件，命名 `MIS-{域缩写}-{序号}.md`
2. 文件结构：
   ```yaml
   ---
   id: MIS-MEM-001
   name: std::move 会移动对象
   level: deep          # surface | deep
   domain: MEM
   trigger_patterns:    # 学习者常犯的代码/表述模式
     - "std::move(x) 之后 x 被清空了"
     - "move 就是 memcpy"
   refutations:         # deep 类必须 ≥2 条，每条带证据
     - "std::move 只是 static_cast<T&&>(x)，不生成任何指令 [expr.static.cast]"
     - "源对象有效但未指定 [lib.types.movedfrom]，移动构造是否掏空由实现决定"
   related_atoms: [ATOM-MEM-MOVE-002]
   ---
   ```
3. 原子的 misconception 字段改为引用 ID 列表：`misconceptions: [MIS-MEM-001, MIS-MEM-003]`
4. gate_engine 加规则：引用的误解 ID 必须存在；deep 类误解 refutations ≥ 2

**首批建 50 条**，覆盖 P0 五域高频误解（从三个样板已有的 misconception 提取 + 从 Book 章节的"常见错误"节提取）。

### 2.2 原子 `audience` 字段（补"认知适切"维度）

**问题**：当前原子默认读者是"懂 C++ 基础的进阶者"，没有显式声明目标读者和认知负荷预算。G4 三样板都是进阶难度，但 G5 会涉及入门章节。

**做法**：
1. G1_layout.md 原子 frontmatter 加字段：
   ```yaml
   audience: intermediate    # beginner | intermediate | expert
   cognitive_load: medium    # low | medium | high
   prerequisites_readable: true  # 前置原子是否已锻造（机器可查）
   ```
2. gate_engine 加规则：audience 必须三选一；beginner 类原子的正文必须包含"类比/直觉"段（不是只有形式化定义）
3. 学习路径生成时按 audience 排序：beginner → intermediate → expert

## 三、Agent 三权分立分工（G4 经验的升级）

G4 是同一个 Agent 既写又红队，有自我包庇倾向（B 样板的纠错过头就是例证）。G5 起强制分离：

### Writer Agent
- **只写**：从 Book 章节提取知识点候选 → 写原子 frontmatter + 正文 → 写证据卡 + 夹具
- **不评判**自己写的质量，不打 rubric 分
- 输出：`goldens/{域}/{原子ID}_draft.md` + 配套证据卡

### RedTeamer Agent
- **只攻击**：拿到 Writer 的输出，按 S1-S6 + 语义红队清单逐条挑刺
- 语义红队清单（G4 教训固化）：
  1. 标准版本边界：这个论断在 C++11/14/17/20/23 下是否一致？有没有用旧规则套新标准？
  2. 断言-证据同代：改了 .cpp 或卡里计数，工件重生成了吗？sha256 换了吗？
  3. 零观测伪证据：输出符合预期，但汇编里能找到观测通路吗？-O2 有没有把实验消除？
  4. 自身 UB：夹具自己有没有踩 UB？sanitizer 过了吗？
  5. 证伪对照：实验有区分力吗？恒真测试会"证实"一切。
  6. 跨编译器：GCC 成立的，Clang 成立吗？结构断言是不是只锚定了 GCC 特有符号？
  7. 术语精确：unspecified / undefined / implementation-defined 用对了吗？
  8. 过度简化："不该用"三条有没有漏掉重要例外？
- 输出：缺陷报告（严重/一般/建议），不修改原文

### Gatekeeper（机器，已有）
- gate_engine 25 规则 + replay + poison_drill + golden_lock
- 全绿才进人审

### 人审（你）
- 只审 **5 分候选**（Writer 自评 ≥4 且 RedTeamer 无严重缺陷）
- 3-4 分：机器全过 + RedTeamer 通过 → 直接进 verified，你 10% 抽样
- ≤2 分：打回 Writer

**流转**：Writer → RedTeamer →（修改循环）→ Gatekeeper → 人审（5分候选）→ 原子化 → verified 签署

## 七、血泪注意事项（G1-G4 全部踩坑积累）

1. **工件必须与断言同代**：改 .cpp 或卡里计数 → 必须重生成 .asm → 必须换 sha256。旧工件 hash vs 旧记录 hash 一致 ≠ 复现性。
2. **验证不带 PATH 前置**：`_pin_compiler` 已经钉住完整路径，但你手动跑命令时不要前置编译器路径，那会掩盖缺陷。
3. **硬编码期望会被 S3 拦**：期望片段出现在夹具字符串字面量里 = 作弊级伪证据。
4. **查同名必须 rglob**：新建文件前 `Get-ChildItem -Recurse -Filter "*.py"` 查全仓库，不要只查顶层。
5. **中文提交走 -F**：commit message 写进 UTF-8 文件，`git commit -F msg.txt`，不要 `git commit -m "中文"`。git 编码已置 utf-8。
6. **计数/计时类实验双跑**：-O0 与 -O2，计数器 volatile。汇编层找不到调用点却"证实"了论断 = 伪证据。
7. **不要预设汇编里有什么**：先看工件再写断言。-O2 可能内联一切（B 样板的 g/h、C 样板的拷贝构造都被内联了）。
8. **标准版本边界**：C++11/14/17/20/23 的规则可能不同。用旧规则套新标准是 G4 最严重的语义错误。写论断时必须声明适用版本。
9. **relations 先确认目标存在**：指向尚未锻造的原子会背 ATOM-REL-TARGET 债。写之前 `ls atoms/` 查一下。
10. **产物写 build/**：证据卡 command 的 -o 必须指向 build/，不要在仓库根留 a.exe。pre-push hygiene 会抓。
11. **异构环境不污染工件**：WSL 跑 replay 会把 MinGW 的 .asm 换成 Linux 产物。replay 已有快照还原，但手动操作时注意。
12. **sanitizer 覆盖不对称**：Windows MinGW 无 libasan，UB 类证据卡必须在 WSL/Linux 侧过一遍 sanitizer。
13. **gray_zone 术语精确**：unspecified / undefined / implementation-defined 不是措辞差异，是事实性差异。读者会把 unspecified 当成 UB 恐慌。
14. **--accept 留痕**：golden_lock 的 warn 如果是预期债务（如服务的原子尚未锻造），用 `--accept "理由"` 显式留痕，不要静默 sync。
15. **CI Clang 是 continue-on-error**：Clang 编译失败只留注解不阻塞，但 Gray-zone Matrix 的 notice 注解是公开可读的，用来回填 Clang 列实测结果。
