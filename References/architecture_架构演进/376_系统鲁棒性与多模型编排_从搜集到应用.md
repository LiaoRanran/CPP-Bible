# 376 系统鲁棒性与多模型编排：从搜集到应用

> 日期：2026-09-13。监工完成，回应"Agent速度很慢""上下文耗尽""额度榨干"等真实痛点。
> 流程：搜集 → 整理 → 挖掘 → 联系 → 批判 → 结合 → 应用。

## 三、挖掘（每个类别的核心洞察）

**A. Checkpoint-Resume**：每步成功后序列化状态（对话历史、工具结果、当前计划）到持久存储，失败后从最近 checkpoint 恢复。关键不是"保存一切"，是"保存能恢复决策的最小状态"。agent-recall-ai 的洞察：快照格式是为冷恢复设计的，不是压缩——新 Agent 读 briefing 就能从中断处继续，不需要原始上下文。

**B. 优雅降级五级**：Level1 重试 → Level2 降级（简化任务/更轻量模型）→ Level3 丢弃低优先级上下文 → Level4 升级给用户 → Level5 优雅失败+状态保存。关键：Level4 不是失败，是正确的委托——有些问题确实需要人判断。

**C. 上下文管理三层法**：① compaction（总结对话保留架构决策，丢弃细节）② 结构化外部记忆（进度文件/checkpoint/数据库）③ 子Agent委托（卸载有界子任务，只返回紧凑摘要）。三者结合最强，单用任何一种都不够。Anthropic Claude Code 实证：能力足够的模型配合好的上下文管理，长任务质量不下降。

**D. 模型路由**：实证数据——**50-70% 企业请求可以用最便宜层处理而无质量损失**。FrugalGPT 级联（便宜先试，质量不够升级）降 98% 成本；RouteLLM 矩阵分解分类器降 85%。核心不是"用便宜模型"，是"知道哪些任务便宜模型能做好"。

**E. 混合编排**：前沿模型做编排和路由（需要 broad knowledge），微调小模型做任务特定执行（需要 speed+cost）。AWS 实证："token 成本增长快于业务价值"——前沿模型处理所有任务（路由/分类/摘要/生成）导致高 per-token 花费，即使简单任务不需要前沿智能。

**F. 两种运行模式**：① Fast-first accurate-second：小模型快速返回<100ms，大模型后台修正；② Parallel probing：高价值请求并行探测便宜和贵的模型，返回 SLA 内先到的，贵的结果后到用来更新缓存。

## 四、联系（和我们系统的映射）

| 外部发现 | 我们的真实痛点 | 差距 |
|---|---|---|
| A. Checkpoint-Resume | "上下文耗尽，如实汇报进度而非结果"反复出现 | 只有手动记忆文件，无标准化恢复格式 |
| B. 优雅降级 | 额度榨干后只能换模型/停手 | 没有降级策略，额度没了就是硬停 |
| C. 上下文三层法 | 证据卡从60行膨胀到200+行，上下文被撑爆 | 只有被动总结，无主动丢弃+子Agent委托 |
| D. 模型路由 | 所有任务用 ds/hy4p，杂活也烧大模型额度 | 完全手动切换，无任务-模型匹配 |
| E. 混合编排 | 建设者/红队/监工都是大模型，成本高 | 没有小模型做杂活的分工 |
| F. Fast-first 模式 | "Agent速度很慢" | 所有任务都等大模型完整输出 |

**已有的雏形**：2026-09-12.md 记忆文件就是手动版 checkpoint；三权分立（建设者/红队/监工）就是子Agent委托的雏形；ds→hy4p 切换就是手动版模型路由。但都是手动的、非标准化的。

## 五、批判（哪些不适用、哪些有局限）

1. **我们在 IDE（CodeBuddy/TRAE）内运行，不是独立 Agent 框架**——checkpoint/resume 需要 IDE 支持或手动实现（写文件），不能直接用 LangGraph 的 Checkpointer。
2. **模型路由需要统一 API 层**——我们现在手动切换模型（ds 额度没了换 hy4p），没有自动路由基础设施。短期只能做"任务分层+手动分配"。
3. **小模型的能力边界需要实测**——不是所有"简单任务"都真简单，比如"解读门禁错误信息"可能需要理解复杂输出。盲目用小模型会引入新错误。
4. **预测性暂停需要精确的速率限制阈值**——我们的额度是模糊的（"白嫖一点""额度榨干"），难以精确预测何时暂停。只能做"额度低时主动降级"的粗粒度策略。
5. **子Agent委托增加协调成本**——任务太细反而更慢，需要找到合适的粒度。我们的红队已经是独立子Agent，但建设者仍是长任务单体。
6. **Fast-first 模式对我们的场景不完全适用**——我们的任务是知识生产，不是交互式问答，"快速返回一个可能错的答案"没有价值，必须准确。更适用的是"杂活用小模型快做，核心活用大模型慢做"的并行分工。

## 六、结合（和已有架构的结合点）

**和 G6 状态体系结合**：
- checkpoint 可以和 status_history 联动——每个状态转换（draft→machine-verified→human-verified）就是一个自然的 checkpoint 点
- 状态文件本身就是恢复入口：新 Agent 读 status+status_history 就能知道做到哪了

**和三权分立结合**：
- 建设者/红队/监工本身就是子Agent，每个应该返回紧凑摘要（不是全文对话），监工只持有摘要
- 红队已经是独立子Agent，建设者可以进一步拆成"夹具设计→卡写作→门禁"三个子任务

**和记忆文件结合**：
- 2026-09-12.md 是手动版 checkpoint，可以标准化格式：已完成/未完成/关键数据（sha/读数）/下一步/阻塞项
- 标准化后，新 Agent 能直接读取恢复，不需要重新读所有文件

**和额度管理结合**：
- 定义"任务复杂度分级"：S级（架构决策/claim设计/红队）用大模型，A级（卡写作/门禁解读）用中模型，B级（文件移动/状态报告/格式检查/简单编译）用小模型
- 额度低时自动从 S→A→B 降级，而不是直接停手

## 七、最终应用（分阶段落地）

### 立即落地（零成本，流程改进）

**应用 1：标准化记忆文件格式（手动版 checkpoint）**
- 每轮结束写结构化记忆：已完成（带文件路径和commit）/ 未完成（带阻塞原因）/ 关键数据（sha/读数/门禁结果）/ 下一步（具体到第一个动作）
- 新 Agent 启动时先读记忆文件，不重新读所有源文件
- 这直接解决"上下文耗尽后新窗口要重读一切"的问题

**应用 2：任务复杂度分级+模型分配**
- S级（架构决策/claim设计/红队对抗/语义判断）→ 大模型（ds/hy4p）
- A级（证据卡写作/门禁解读/夹具调试）→ 中模型
- B级（文件移动/git操作/状态报告/格式检查/简单编译运行）→ 小模型
- 这直接解决"杂活也烧大模型额度"和"速度慢"——B级任务用小模型快10倍+省额度

**应用 3：额度低时主动降级**
- 额度预警时，B级任务继续做（不烧额度），S级任务暂停或降级为A级
- 不是"额度没了就停"，是"额度低了先做杂活，核心活等额度恢复"

### 中期落地（需要一些工程）

**应用 4：建设者子任务拆分**
- 建设者拆成：夹具设计Agent → 卡写作Agent → 门禁Agent，每个返回紧凑摘要
- 主Agent只协调，不持有所有细节
- 这解决上下文膨胀（证据卡200+行的问题）

**应用 5：主动上下文管理**
- 定期（每N轮）丢弃低优先级上下文（工具输出原文、中间探索过程），只保留架构决策和关键数据
- 不是等满了才总结，是主动保持上下文在安全线内

### 长期落地（需要基础设施）

**应用 6：自动模型路由层**
- 统一API层，按任务类型自动选模型，额度/延迟/质量三目标优化
- 支持级联（小模型先试，质量不够自动升级）和并行（高价值任务多模型并行）

## 八、和 374/375 的关系

- 374（语义自律）和 375（证据智能）解决"生产质量"问题
- 376（鲁棒性+编排）解决"生产效率和可持续性"问题
- 三者是并行的：质量和效率不冲突，效率提升（小模型做杂活）让大模型有更多额度做高质量的核心活
- 落地顺序：376 的立即落地项（应用1/2/3）可以现在就做，不依赖 374/375

## 九、局限与后续

- 本调研聚焦"系统鲁棒性+多模型编排"，未覆盖"并行Agent调度""任务队列""分布式执行"——那些是更大规模的问题，当前单用户场景不需要。
- 任务复杂度分级的边界需要实测校准——首批上线后要用"B级任务用小模型是否出错"做阴阳例测试。
- 标准化记忆文件格式需要和现有的 2026-09-12.md 兼容，不能另起炉灶。
- 模型路由的长期落地依赖可用的模型列表和API，当前只有 ds/hy4p 两个，路由空间有限，但"杂活用小模型"的原则即使只有两个模型也能应用（hy4p 比 ds 快/便宜，适合B级）。
