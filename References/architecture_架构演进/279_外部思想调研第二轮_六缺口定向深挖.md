## 缺口一：I5 横向差分（.asm 工件是编译器行为数据库，目前只做纵向 replay）

### 外部最强实践
- **Souper（Google）**：LLVM IR 超级优化器，从 bitcode 提取 SMT 查询，solver 返回 unsatisfiable = 「错过的优化机会」。**核心是 oracle-free 判定**——不需要 ground truth，SMT 自己证明两段 IR 等价，不等价就是差异点。
- **Alive2（PLDI 2021，Utah）**：LLVM 有界翻译验证，把优化转 SMT 公式，flow-sensitive 跟踪 undef/poison——直接对应我们的 UB 灰区原子。
- **LPO（arXiv 2508.16125，2025）**：**LLM 生成 peephole 候选 + Souper/SMT 验证**。完美印证宪法公理一「模型提议器，系统判定者」——LLM 负责发散找候选，SMT 负责收敛证等价。
- **PrediPrune（2026）**：用 ML 剪枝 Souper 的 SMT 查询，降低验证开销（我们的 90 工具性能问题可参考）。

### 批判
- Souper 不支持内存访问/浮点/向量（我们的 .asm 差分主要是整数控制流，适用面够）；SMT 求解有超时，需要预算上限。
- LPO 的 LLM 候选质量依赖 prompt，且有重复候选——需要去重。

### 吸收动作
- **不引入 SMT solver（过重）**，但迁移其** oracle-free 判定思想**：同一夹具多编译器 .asm 做结构化差分（符号集/控制流图/指令序列），不需要「正确答案」，差异本身就是教学点。
- 写 `tools/asm_diff_matrix.py`：输入 N 个编译器×档位的 .asm，输出「哪些符号只在某编译器出现、哪些优化决策不同」的差分矩阵。B 样板式内容可半自动产出。
- LPO 范式迁移：**LLM 提议「这个 .asm 差异可能说明什么教学点」+ 机器用符号差分证据判定**，不允许 LLM 直接下结论。

### 落点 / 优先级
- P1：`asm_diff_matrix.py`（复用现有 49 卡 .asm，零新采集）。
- 来源：Souper https://github.com/google/souper ；Alive2 https://users.cs.utah.edu/~regehr/alive2-pldi21.pdf ；LPO https://arxiv.org/pdf/2508.16125v2

## 缺口二：I4 毒样例/失败模式自动化（P4–P7 只机械化 4 类，第五批又暴露 4 类新模式）

### 外部最强实践
- **PyRIT（微软）**：红队自动化协议——Phase 0 verbatim ×10 次 → Phases 1–10 各用一种 prompt converter ×10 次 → early stop on jailbreak。**分阶段升级 + 早停**，不是一次性攻击。
- **Failure taxonomy 带频率**（arXiv 2505.04806）：Partial Refusal 34% / Hidden Compliance 22% / No Output 18% / Misleading Response 15%。**有频率的 taxonomy 才能校准毒样例覆盖**。
- **False-premise resistance**：模型应标记「无法验证的前提」而非编造——直接对应公理二「无客观锚不断言」。
- **Process mining 理解红队过程**（arXiv 2606.07833，2026）：不只看 pass/fail，看 LLM 抵抗/失败的过程轨迹——对应我们的「红队要看修复循环过程，不只看最终结果」。

### 批判
- 这些 taxonomy 主要面向安全/jailbreak，我们的失败模式是「知识工程错误」（自证断言/恒真观测/口径反转），需迁移而非照搬。
- PyRIT 的 10×10 攻击预算对我们太贵（每轮红队是独立子 agent），需降配。

### 吸收动作
- **P8–P11 毒样例**（第五批真实案例）：P8 编译期常量冒充活性观测 / P9 一 bit 两计 / P10 口径不统一致方向反转 / P11 消除与失败不可区分。每条配一个最小触发夹具 + 预期 gate 拦截。
- **红队协议加「分阶段升级」**：先查机械化清单（P1–P11），再查语义盲区，最后查创新/品味——早停在第一阶段就不用浪费上下文。
- **失败模式带频率追踪**：每批红队拦截记录类别，累计后看哪类高频，优先机械化。

### 落点 / 优先级
- **P0**：P8–P11 毒样例（证据新鲜，第五批刚实证）。
- P1：红队分阶段升级协议 + 失败模式频率表。
- 来源：PyRIT https://github.com/Azure/PyRIT ；taxonomy https://arxiv.org/html/2505.04806v1 ；process mining https://arxiv.org/html/2606.07833v1

## 缺口三：P0-3 fringe / 知识图谱激活（knowledge_graph.json 0 引用，fringe 视图未建）

### 外部最强实践
- **KST（Doignon & Falmagne 1985）+ ALEKS**：surmise relation（先决拟序）= 掌握 B 必掌握 A；**outer fringe = 当前知识状态的后继中可学的下一项**；ALEKS 用 20–30 题定位（vs IRT 100+ 题），50M 学生验证。
- **Vanderbilt knowledge-spaces（2026）**：**用 QUERY 算法（Koppen & Doignon 1990）+ Claude 当领域专家**构建 surmise relation——LLM 回答「掌握 A 是否必须先掌握 B」，算法聚合一致性。这正是我们构建 atoms prerequisite DAG 的方法！
- **PLRS（2026）**：先决边作为硬约束，候选概念的先决链不满足就不推荐——对应我们的 verified 原子 prereq 悬空 BLOCK。
- **2026 新论文**：用 KST 分析 LLM 自身的知识结构连贯性——可以反过来检测我们的原子 DAG 是否自洽。

### 批判
- QUERY 算法对领域专家的错误敏感，LLM 当专家会有噪声——需要多轮采样+一致性校验，不能一次问答就定边。
- KST 的知识状态是「项的子集」，我们的原子是带证据的知识单元，粒度更粗，需适配。

### 吸收动作
- **fringe.py 实现路径明确**：复用 `learning_path.py` 的 DAG 构建 + `prereq_topo_check.py` 的拓扑校验，加 outer fringe 计算（verified 原子中，prereq 全满足但自身未 verified 的 = 下一步该锻造）。
- **prerequisite 边构建**：用 LLM 当领域专家跑 QUERY 算法（对每对原子问「掌握 B 是否必须先掌握 A」），多轮采样取一致边，人工抽检——不手工编 relations。
- **knowledge_graph.json 激活**：要么作为 atoms DAG 的序列化输出（接 fringe），要么退役。限期一个迭代。

### 落点 / 优先级
- **P0**：fringe.py（复用现有工具，工作量小）+ prerequisite 边 LLM 采样构建。
- P1：knowledge_graph.json 激活/退役裁决。
- 来源：Vanderbilt https://github.com/vanderbilt-data-science/knowledge-spaces/ ；ALEKS https://www.aleks.com/about_aleks/research_behind ；KST+LLM https://arxiv.org/html/2609.05245v1

## 缺口四：I2 工具治理（90 个 py，CI 只调 36 个，~54 个身份不明）

### 外部最强实践
- **Bazel release model**：三态 Active / Maintenance / Deprecated，LTS 3 年支持，rolling 每 2 周。Deprecated = 不再支持，用户必须迁移。
- **monorepo 废弃通知模式**：在包的 CLAUDE.md 头部加 `# 非推奨：已被 packages/auth-v2 替代，禁止加新功能`——工具级同理，加 frontmatter `status: deprecated` + `replaced_by:`。
- **Bazel 9 移除 WORKSPACE 的教训**：大版本移除要分阶段（先 Bzlmod 迁移→验证→再移除），不能一步到位。对应工具退役：先有替代者→标注 deprecated→归档。

### 批判
- Bazel 的 LTS 是面向用户的版本策略，我们的工具是内部脚本，不需要 3 年支持，但三态分类法适用。
- 90 个工具里可能有「一次性脚本」（如 _clean_junk.py），不应与核心工具同标准——需区分「核心工具」与「一次性脚本」。

### 吸收动作
- **工具普查（tool census）**：90 个脚本分四类——CI 核心（Active）/ 本地常用（Maintenance）/ 一次性脚本（Archive 候选）/ 僵尸（Deprecated）。
- 每个工具 docstring 加身份标注 `# status: active|maintenance|deprecated` + `# ci: yes|no`，gate 加规则：deprecated 工具被 CI 调用 = BLOCK。
- 僵尸归 `tools/archive/`，维护面从 90 收敛到 ~40。

### 落点 / 优先级
- P1：工具普查 + 身份标注（纯机械，零风险）。
- 来源：Bazel release https://bazel.build/release ；monorepo 废弃模式 https://thepromptshelf.dev/blog/monorepo-ai-tools-patterns-2026-ja/

## 缺口五：candidates/ 创造力管理（FORGE 候选仓未建，检验闸缺负向判定）

### 外部最强实践
- **Google X（Astro Teller）kill criteria**：「给未来自己的诚实信息」——在乐观时预设什么条件下该杀，review 时**默认 kill 除非 criteria 满足**。Rapid Eval 两阶段：第一阶段几周几千美元查最大风险（杀掉几十上百个），第二阶段 Extended Investigations。
- **Amazon PR/FAQ（Working Backwards）**：写不存在产品的新闻稿+FAQ，写不出来就不推进。narrative meeting 开始时全员静默读文档——**强制把想法推到「能清晰表达客户价值」的程度**。
- **Stage-gate + Definition of Done**：每阶段投资随证据累积增加，每 gate 有明确 DoD，默认 NO-GO。

### 批判
- Google X 的 kill criteria 面向硬件 moonshot，我们的候选原子成本低，不需要「几千美元预算」，但「默认 kill」的负向判定思想核心。
- PR/FAQ 对教材原子可迁移为「学完这颗原子后学生能做什么的 press release」——写不出来说明教学价值不清晰。

### 吸收动作
- **candidates/ 仓建立**：每个候选 frontmatter 含 `kill_criteria:`（预设什么条件下该杀）+ `press_release:`（学完后学生能做什么，写不出来不进仓）。
- **检验闸用负向判定**：review 时默认 kill，除非 kill_criteria 全部不触发 + press_release 成立。防止沉没成本（274 已识别的「黄金 diff 惩罚创新」的反面是「沉没成本保垃圾」）。
- **Rapid Eval 两阶段迁移**：候选进仓=第一阶段（轻量，只写 claim+夹具草图）；过检验闸=第二阶段（Extended，完整五件套）。

### 落点 / 优先级
- **P0**：candidates/ 目录 + frontmatter 约定（FORGE 唯一纯缺口）。
- 来源：Google X https://www.x.company/blog/posts/a-peek-inside-the-moonshot-factory-operating-manual/ ；kill criteria https://www.pmf.show/blog/astro-teller-x-moonshot-factory-kill-criteria-innovation ；Amazon PRFAQ https://ones.com/blog/how-amazon-uses-prfaq-to-innovate-and-ship-products/

## 缺口六：error budget 深度（debt_ledger 已有负债率，缺燃烧速率）

### 外部最强实践
- **SRE burn rate**：`burn_rate = 实际错误率 / 允许错误率`。burn_rate=1 = 30 天预算恰好用完；14.4 = 2% 预算在 1 小时烧完（Page 级）。
- **多窗口多燃烧率（MWMBR）**：Page 告警 = 1h 长窗 + 5m 短窗 AND，阈值 14.4x；Ticket 告警 = 6h + 30m AND，阈值 6x。**AND-Gate 防误报，双窗口防漏慢烧**。
- **slo-burn 工具**：实现 MWMBR，解决「慢烧 14 小时耗尽预算无人注意」的问题。

### 批判
- SRE 的 error budget 面向服务可用性（连续时间序列），我们的 debt 是离散事件（每批新增几条），需适配为「批次数列」。
- 多窗口对我们的批次粒度（每批 3-4 原子）来说，长期窗口=近 10 批，短期=本批。

### 吸收动作
- **debt_ledger 扩展 burn rate**：不只是 `票据数/门禁项 >15%`，加 `debt_burn_rate = 本批新增 debt / 预期每批 debt`。
- **双窗口 AND-Gate**：本批 burn_rate > 阈值（快速燃烧）**且**近 10 批累计 > 阈值（持续恶化）→ 触发「冻结新生产，先还债」。单窗口超阈值只告警不冻结。
- GAUNTLET 逃逸也开 debt 票（owner human、到期、补偿），与现有豁免票据统一台账。

### 落点 / 优先级
- P1：debt_ledger 扩展 burn_rate + 双窗口（复用现有票据结构，加字段）。
- 来源：MWMBR 分析 https://dev.to/npayyappilly/multi-window-burn-rate-alerting-a-formal-analysis-of-the-and-gate-logic-behind-googles-alert-model-37h0 ；slo-burn https://github.com/Ajay150313/slo-burn ；Google Cloud https://cloud.google.com/stackdriver/docs/solutions/slo-monitoring/alerting-on-budget-burn-rate

## 给用户的话

这轮调研最有价值的不是某个具体工具，而是**三个范式级迁移**：
1. **Souper/LPO 的「LLM 提议 + SMT 判定」**——我们的宪法公理一在编译器领域有工业级实现，.asm 差分可以 oracle-free。
2. **Google X 的「默认 kill」**——candidates 检验闸从「通过才进」改为「不满足 kill_criteria 就杀」，负向判定比正向判定更防沉没成本。
3. **SRE 的「燃烧速率」**——debt_ledger 从静态负债率升级为动态燃烧速率，慢烧和快烧区别对待。

这三个加上 278 的六笔内部红利，就是下一轮架构进化（280？）的燃料。你说「调研到没有可以调研的程度」——按追踪表，还剩 6 个方向，其中形式化方法和 Agent self-healing 最值得下一轮深挖。要继续吗？
