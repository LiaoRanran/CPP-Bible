### v0.2 模板全文

```markdown
## claim 契约（v0.2）

### 一句话 claim
<单句可证伪，不超过 50 字>

### precondition（前提条件）
在什么条件下此 claim 成立：
- 条件1：____
- 条件2：____

### postcondition（后置断言）
claim 成立时，什么必须为真（可机械检查）：
- 断言1：____
- 断言2：____

### invariant（不变量）
在整个过程中始终保持真的性质：
- 不变量1：____

### 竞争假设（competing_hypotheses）—— v0.2 新增
如果 claim 不成立，最可能的替代解释是什么？列出至少 2 个：
- H1（首选）：____
- H2（替代）：____
- H3（替代）：____
→ 证据卡的 falsification 字段必须能区分 H1 与 H2/H3（否则 claim 不可证伪）
→ 来源：CIA Tradecraft Primer ACH——不是找支持首选假设的证据，而是找「哪个假设被证据排除」

### 理论根基（theoretical_foundation）—— v0.2 新增
此 claim 在 Curry-Howard 对应下的定位：
- 命题（claim）：____
- 证明（证据卡+夹具）：____
- 证明验证（gate_engine 机械检查）：____
- 证明化简（证据最小化）：actual 中是否有可被其他行推导的冗余行？
→ 来源：Curry-Howard 对应——命题=类型，证明=程序，类型检查=证明验证
→ 这不是隐喻，是精确数学等价：写一个类型正确的程序 = 构造一个证明

### 失效后果分级（failure_severity）—— v0.2 新增
如果 claim 被证伪，后果是什么？（DO-178C DAL 分级思想）
- [ ] A 级（灾难性）：claim 是教材核心结论，证伪会导致整章知识体系崩塌
- [ ] B 级（危险）：claim 是重要推论，证伪会导致多个子结论失效
- [ ] C 级（较大）：claim 是具体案例，证伪只影响该案例
- [ ] D 级（较小）：claim 是边缘观察，证伪影响有限
- [ ] E 级（无影响）：claim 是补充说明，证伪无后果
→ A/B 级 claim 必须有 ≥2 张独立证据卡支撑
→ C/D/E 级 claim 1 张证据卡即可

### 规格独立性检查
此 claim 是否依赖特定编译器/标准库/平台？
- 是/否：____
- 如果是，哪些部分是平台相关的？____
- 独立验证方法：____

### 可证伪性
什么观测结果会证明此 claim 错误？
- 证伪条件1：____
- 证伪条件2：____
```

### 竞争假设字段的使用规则

1. **至少 2 个竞争假设**：H1 是 Writer 主张的解释，H2/H3 是替代解释
2. **falsification 必须能区分**：证据卡的 falsification 字段必须说明「什么观测结果会排除 H2/H3」
3. **红队核查**：红队必须检查竞争假设是否真的互斥——如果 H1 和 H2 可以同时成立，说明 claim 定义不清
4. **反例**：如果 Writer 写不出 ≥2 个竞争假设，说明 claim 可能是恒真的（不可证伪）

### 失效后果分级的使用规则

- A/B 级 claim：≥2 张独立证据卡 + 必须有活性对照
- C 级 claim：1 张证据卡 + 建议有对照
- D/E 级 claim：1 张证据卡即可
- gate_engine 未来可加 ATOM-SEVERITY-EVIDENCE 规则：A/B 级 claim 证据卡数 <2 时 warn

## 二、证据链归约化（refutes 字段）—— 294 P1-5

### 设计原则

来源：密码学归约证明——「如果攻击者能攻破 X，就能构造攻击者攻破已知困难问题 Y」。

对应到我们的系统：**如果证据卡 refute，哪个 claim 被证伪？** 这必须显式声明，不能靠人猜。

### 字段格式

```yaml
refutes:
  - ATOM-MEM-LEAK-002   # 这张卡 refute 时，LEAK-002 的 claim 被证伪
  - ATOM-MEM-LEAK-001   # 可选：如果同时影响多个原子
```

### 与现有 serves 字段的区别

| 字段 | 方向 | 含义 |
|---|---|---|
| `serves: [ATOM-XXX]` | 卡 → 原子 | 这张卡为哪个原子提供证据 |
| `refutes: [ATOM-XXX]` | 卡 → 原子 | 这张卡 refute 时，哪个原子的 claim 被证伪 |

- `serves` 是「支持关系」（卡 confirm 时支持原子）
- `refutes` 是「证伪关系」（卡 refute 时证伪原子）
- 两者通常指向同一个原子，但不一定——一张卡可能支持 A 原子的 claim，但 refute 时证伪的是 B 原子的 claim（如果两原子有依赖关系）

### 并存模式

- `refutes` 是可选字段，现有 42 张卡不加不报错
- atom_evidence_replay.py 不读此字段（不影响 replay）
- golden_lock 未来可加检查：serves 和 refutes 不一致时 warn（支持 A 但证伪 B，需要解释）

### 归约链示例

```
EV-MEM-043（LEAK-002 检测侧卡）
  serves: [ATOM-MEM-LEAK-002]
  refutes: [ATOM-MEM-LEAK-002]
  → 如果这张卡 refute，LEAK-002 的 claim「检测工具报告与否不能等价于泄漏有无」被证伪
  → 归约链：卡 refute → 夹具输出与 actual 不符 → claim 的实证基础失效 → claim 被证伪
```

## 三、Curry-Howard 根基对现有系统的映射

| Curry-Howard | 我们的系统 | 现状 |
|---|---|---|
| 命题（Proposition） | atom claim | ✅ 已有（单句可证伪） |
| 证明（Proof） | 证据卡 + 夹具 + 工件 | ✅ 已有（evidence/mem/ + Examples/） |
| 证明验证（Proof checking） | gate_engine + replay | ✅ 已有（33 规则 + replay confirm/refute） |
| 证明化简（Proof normalization） | 证据最小化（actual 去冗余） | ❌ 未实现（P2-9） |
| 空类型（False） | 反例夹具（构造 claim 的反例） | ⚠️ 部分实现（falsification 字段，但不是独立夹具） |
| 证明不可规范化（Non-termination） | 证据卡无法 replay（编译失败/运行超时） | ✅ 已有（replay refute:compile_error 等） |

### 关键洞察

Curry-Howard 对应给了我们一个**数学根基**：我们的「证据=证明」不是比喻，是精确的结构对应。这意味着：

1. **claim 必须是命题**：有明确的真值（真/假），不能是模糊的「X 很重要」
2. **证据必须是证明**：从公理（编译器行为、标准条文）出发，通过推理步骤（夹具运行、asm 分析）到达 claim
3. **gate 是类型检查器**：机械验证证明是否符合规则，不判断证明是否「有意义」
4. **证明化简是可能的**：证据卡中的冗余行可以被去掉（就像程序中的死代码），不影响证明的有效性
