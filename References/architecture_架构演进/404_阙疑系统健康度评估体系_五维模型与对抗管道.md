# 404 阙疑系统健康度评估体系：从"门禁绿"到"五维健康度"

> 日期：2026-09-13。外部调研：Agent 评估框架（Google Cloud 双支柱、Braintrust eval=TDD、12 指标框架）、对抗自动化管道（Test-Fix-Prove、ASR/FPR 熔断、去重聚类）、知识库冲突检测（四阶矛盾识别、Kontrast 跨模态、嵌入语义比对）。
> 核心问题：**阙疑现在只有"门禁绿不绿"（下限），没有"系统好不好"（上限）。** 27 原子、56 证据卡、42 规则、30 毒样例——规模在涨，但没有一个综合指标回答"这个系统现在健康吗？"

---

## 一、为什么门禁绿不够

当前门禁回答的是"**有没有明显错误**"（block=0），不回答：
- 这 27 颗原子之间有没有矛盾？
- 红队发现的问题，修复后真的不再复发了吗？
- 生产一颗原子的成本是在涨还是降？
- 规则覆盖率是多少？没覆盖的规则是不是等于不存在？
- 证据卡的 claim 真的可证伪吗？还是"看起来可证伪"？

类比：单元测试全过 ≠ 软件质量高。还需要集成测试、性能测试、覆盖率、缺陷密度、MTTR。

## 二、五维健康度模型

借鉴 Google Cloud 的"结果+过程"双支柱，扩展为五维：

### 维度 1：产物质量（Product Quality）——"做出来的东西对不对"

| 指标 | 计算方法 | 当前基线（待实测） | 目标 |
|---|---|---|---|
| 原子 verified 率 | verified 原子数 / 总原子数 | 20/27 = 74% | ≥90% |
| 证据卡 replay confirm 率 | confirm / (confirm+refute) | 56/56 = 100% | 维持 |
| claim 可证伪率 | 有 falsification 字段且非空的卡 / 总卡数 | 待实测 | ≥95% |
| 工件同代率 | artifact_sha256 与重编译产物一致的卡 / 总卡 | 待实测（C1 --verify-artifact 后可算） | 100% |
| DAL 匹配率 | DAL 级别与实际风险匹配的原子 / 总原子 | 待实测 | ≥90% |

### 维度 2：过程质量（Process Quality）——"做的过程规不规范"

| 指标 | 计算方法 | 目标 |
|---|---|---|
| MCC 六步走完率 | 走完预言冻结→夹具→双平台→2卡→红队→门禁的批次 / 总批次 | 100% |
| 红队阻断率 | 红队发现阻断数 / 红队总发现数 | 监控趋势，不设阈值 |
| 预言冻结遵守率 | 有实验前 commit 的批次 / 总批次 | ≥90% |
| 红队裁决率 | 有明确采纳/驳回+理由的红队发现 / 总发现 | 100% |
| EIR（错误引入率） | 红队采纳数 / 修复操作数 | 监控趋势 |

### 维度 3：抗攻击能力（Attack Resistance）——"能不能被绕过"

| 指标 | 计算方法 | 目标 |
|---|---|---|
| 毒样例拦截率 | poison 通过数 / 毒样例总数 | 100% |
| 规则覆盖率 | 有毒样例覆盖的规则数 / 总规则数 | 当前 10/42 = 24%，目标 ≥60% |
| 对抗逃逸数 | 独立对抗实测逃逸数 | 每轮递减 |
| 针对性攻击拦截率 | 拦截数 / (拦截+逃逸) | 373 基线 14%，目标 ≥50% |
| 修复复发率 | 已修复漏洞被再次绕过的次数 | 0 |

### 维度 4：知识健康（Knowledge Health）——"知识库本身有没有病"

| 指标 | 计算方法 | 目标 |
|---|---|---|
| 原子间冲突数 | 同域原子 claim 互相矛盾的对数 | 0 |
| 重复原子数 | 主题+claim 高度重叠的原子对 | 0 |
| 误解-原子对应率 | 被至少 1 颗原子引用的误解 / 总误解 | ≥80% |
| relations 完整性 | 有 prereq/contrasts/serves 的原子 / 总原子 | ≥70% |
| 过期原子数 | 引用的编译器/标准版本已过时的原子 | 监控 |

### 维度 5：效率（Efficiency）——"成本是在涨还是降"

| 指标 | 计算方法 | 目标 |
|---|---|---|
| 每原子窗口数 | 生产一颗原子的对话窗口数 | 监控趋势（第五批 6 窗口是警报） |
| 每原子 token 粗估 | 输入+输出字数 / 原子数 | 监控趋势 |
| 红队每轮发现数 | 红队总发现 / 红队轮次 | 监控（下降可能=体系成熟，也可能=红队变弱） |
| 规则增长速率 | 新增规则数 / 批次 | 监控（爆炸式增长=维护危机） |
| 门禁执行时间 | 全量门禁（replay+gate+poison+pytest）耗时 | 监控（超 10 分钟需优化） |

## 三、对抗→修复→回归自动化管道（Test-Fix-Prove）

当前 373 的收编是手工的（监工逐条核实）。规模变大后需要自动化：

### 管道四步

```
对抗报告 → ①去重聚类 → ②根因分类 → ③毒样例生成 → ④规则修复+回归
```

**① 去重聚类**：
- 同一根因的多个逃逸合并为一个 issue（Secure.com 最佳实践：同一根因不生成十个 ticket）
- 聚类键：攻击手法（frontmatter 注入/借工件/注释伪造/Unicode 绕过）+ 被攻击的规则
- 实现：对抗报告的每个发现提取 `attack_pattern` 标签，按标签+规则聚类

**② 根因分类**：
- 工具漏洞（gate/replay 代码 bug）→ 改代码
- 规则盲区（规则没覆盖这种形态）→ 加规则+毒样例
- 流程漏洞（纪律没被遵守）→ 加门禁检查
- 文档失真（架构声称但代码没实现）→ 补实现或改文档

**③ 毒样例生成（Prove 阶段）**：
- 每个逃逸必须转化为毒样例（阴阳配对）
- 毒样例 = 逃逸的最小复现（不是完整证据卡，是触发规则的最小 frontmatter）
- 修复后重跑毒样例，确认拦截（Test-Fix-Prove 的 Prove）

**④ 回归测试**：
- 修复后全量 poison + 全量 replay + 存量卡 gate
- 新增误伤必须收窄（A2 正例回归制度）

### 熔断阈值（借鉴 ASR/FPR）
- 对抗逃逸数 > 上一轮的 150% → 暂停生产，先修体系
- 规则误伤率 > 10% → 新规则降级为 warn/advice
- 毒样例拦截率 < 100% → block 级阻断

## 四、知识冲突检测的落地方法

27 颗原子之间可能有矛盾（PERF-003"小对象分配器更快" vs PERF-004"要看平台"——实际是互补，但需要机器确认）。

### 三层检测（从轻到重）

**L1 结构冲突（可机器检测，零 LLM）**：
- relations 矛盾：A 是 B 的 prereq，但 B 的 claim 说"不依赖 A"
- ID 冲突：两颗原子同 ID（已有 ATOM-ID-UNIQUE 规则）
- serves 悬空：原子 A serves 原子 B，但 B 不存在（已有 EV-SERVES-EXIST）
- 误解引用悬空：原子引用 MIS-XXX，但 MIS-XXX 不存在

**L2 语义冲突（LLM 辅助，需人确认）**：
- 同域原子 claim 语义比对：用嵌入相似度找同主题原子对，LLM 判断 claim 是否矛盾
- 借鉴 Alhena AI：嵌入+语义搜索（不是关键词匹配），措辞完全不同也能抓矛盾
- 输出：候选冲突对 + 矛盾点 + 建议（合并/修正/标注为 contrast）

**L3 跨模态冲突（长期）**：
- 原子 claim vs 证据卡 actual：claim 说的数字和卡内实测数字是否一致
- 借鉴 Kontrast：文本声明 vs 表格/工件证据的不一致检测
- 这是最有价值的：ALLOC-002 的"pool 32B 最省"就是 claim 与工件不符，被红队抓的——如果 L3 自动化，红队之前就能发现

### 落地优先级
- L1：已有部分规则（ATOM-ID-UNIQUE、EV-SERVES-EXIST），补全 relations 矛盾检查 → P1
- L2：需要嵌入模型，当前环境可能没有 → P2（先用 LLM 批量比对，不做实时）
- L3：需要解析 claim 中的数字断言并和卡内 actual 比对 → P2

## 七、与现有体系的关系

- **不替代门禁**：门禁是"每批必须过的下限"，健康度是"系统整体状态的上限"
- **不替代 golden_lock**：golden_lock 管基线不恶化，健康度管绝对值和趋势
- **是 399 可观测性（L7）的具体落地**：399 说"可观测性是前提"，404 给出"观测什么、怎么算、目标是多少"
- **是 400 问题 1（观测成本）的回应**：默认层只算确定性指标（门禁结果、原子数、窗口数），零 LLM 调用；L2/L3 语义检测按需开启

## 八、元结论

阙疑系统的成熟度不能只用"门禁绿"衡量。五维健康度中，**抗攻击能力是当前最弱的一环**（规则覆盖率 24%、针对性拦截率 14%）——这正是 402 对抗和 373 修复在解决的。**效率是第二弱的**（每原子窗口数从 3 涨到 6）——这是颗粒度失控的信号，需要 B1 提示词压缩和流程优化来逆转。

健康度仪表盘的价值不在于"打分"，而在于**让恶化可见**——如果规则覆盖率从 24% 涨到 30%，说明在进步；如果每原子窗口数从 6 涨到 8，说明在恶化。没有指标，这些趋势都是"感觉"。
