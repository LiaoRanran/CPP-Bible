# 外部思想调研第三轮：无人自纠错闭环的理论栈（形式化 × 程序合成 × Self-Healing）

> 2026-09-12 · 第 280 份。279 覆盖六缺口，本轮按饱和表优先深挖三个最相关方向——**形式化方法、Agent self-healing、程序合成**。三者交叉后恰好构成宪法第八节「无人自纠错闭环」的完整外部理论栈：合成=生成、形式化=验证、self-healing=修复。
>
> 每个方向给：最强点 / 批判 / 吸收动作 / 落点 / 优先级。末尾更新饱和追踪表。

## 方向一：形式化方法/定理证明（原子 claim 从自然语言到机器可检查契约）

### 外部最强实践
- **CompCert**：形式化验证的 C 编译器，旗舰案例——证明每遍优化保持语义等价。对应我们的「.asm 差分可证等价」（与 279 Souper 路线汇合）。
- **VST（Verifiable C，Appel 团队）**：基于分离逻辑的 C 程序验证，pre/post condition + 不变式机器可检查。直接对应内存原子的指针操作正确性。
- **Vellvm**：LLVM IR 在 Rocq（原 Coq）中的形式化语义+可执行解释器，证明精化关系。
- **Cerberus**：C 的可执行形式化语义，含 CHERI 内存模型——C++ 内存模型的形式化参照。
- **Software Foundations（Penn CIS5000）**：Coq 教学经典，从逻辑到程序验证的完整路径。
- **FMAIV（2026 课程）**：形式化方法 + AI 辅助验证，用 transition systems 作为统一行为模型，串起 SAT/SMT→模型检查→定理证明→程序验证。

### 批判
- 全 Coq/Lean 验证对我们的教材原子过重（证明成本 >> 写作成本），不现实。
- C++ 没有完整形式化语义（Cerberus 只覆盖 C 的大子集），C++ 模板/异常/多继承的形式化是开放问题。
- 形式化方法的工业采用率低，主要在安全关键领域（航空/医疗），普通教材不需要全证明。

### 吸收动作（轻量迁移，不全量引入）
- **原子 claim 契约化**：把 claim 从自然语言升级为「precondition / postcondition / invariant」三段式，可被机器解析检查。precondition=夹具前提（如「对象非 const」），postcondition=断言锚（如「dtor_count=1」），invariant=跨状态成立的性质（如「引用计数≥0」）。这是从「人审品味」到「机器可验证」的关键一步，且不引入证明器。
- **契约字段进 frontmatter**：`claim_pre:` / `claim_post:` / `claim_invariant:`，gate 加规则：postcondition 中的每个断言必须在 actual 中有对应行（防止「claim 说的和 actual 测的不是一回事」——第五批 ALLOC-002 的方向反转就是这个病）。
- **FMAIV 的 transition system 思想**：每个原子的夹具本质是一个状态转移系统（初始态→操作→终态），把状态序列写进卡（不只是终态输出），红队可以检查「中间态是否合理」。

### 落点 / 优先级
- **P0**：claim 契约化（pre/post/invariant 三段式 + gate 规则）——直接治第五批暴露的「claim 与证据不一致」病。
- P2：长期探索 VST/分离逻辑对内存原子的轻量验证（不引入 Coq，只借鉴断言模式）。
- 来源：CompCert https://compcert.org/ ；VST https://vst.cs.princeton.edu/ ；Software Foundations https://softwarefoundations.cis.upenn.edu/ ；FMAIV https://github.com/ttj/fmaiv

## 方向二：Agent Self-Healing / 自动修复（无人闭环的修复环）

### 外部最强实践
- **Getafix（Meta 2018）**：从工程师修复历史中挖掘 AST 模式，自动生成修复补丁——第一个部署到生产规模的自动修复工具。为 SapFix 提供修复，Sapienz 找 bug → Getafix 生成修复 → 工程师审批。
- **RepairAgent（2024）**：自主 LLM agent 程序修复，工具链=读失败测试→搜索代码→生成补丁→运行测试→迭代。关键是「搜索代码库找修复原料」（repair ingredients）。
- **多 agent 对抗修复**：hunter（找 bug）/skeptic（质疑）/referee（裁判）/fixer（修复）/recon（侦察）五 agent——比我们的三权分立多了 recon 和独立 fixer。
- **SecureFixAgent**：静态分析器（Bandit）+ LLM 混合，检测→解释→修复→自纠正→验证闭环，本地隐私保护。
- **TDD for Code Generation（2024）**：测试在生成阶段就介入，remediation loop 显著提升正确率（GPT-4 上复杂问题通过率大幅提升）。

### 批判
- Getafix 是模式匹配（AST 级），对我们的「语义级错误」（如口径反转）无能为力——需要 LLM 级理解。
- 自动修复的「plausible but incorrect」问题（补丁通过测试但语义错误）——我们的红队就是防这个，但自动修复时红队可能被绕过。
- 多 agent 五角色对我们的上下文预算太重（每批 3-4 原子，五 agent 跑不起）。

### 吸收动作
- **Getafix 思想迁移：从红队历史中提炼修复模式**——第五批红队抓出的「自证断言」「一 bit 两计」「口径反转」「消除与失败不可区分」都是可泛化的修复模式。建 `tools/repair_patterns/`，每个模式含「识别特征→修复模板→验证方法」，Writer 写完后自动跑修复模式扫描，命中则提示修复。
- **修复循环上限硬编码**：宪法已规定修复循环≤2轮，超限升级人审。Getafix 的教训是「自动修复可能 plausible but incorrect」，所以**修复后必须重跑红队（不是只跑 gate）**——gate 只查格式，红队才查语义。
- **不引入独立 fixer agent**：Writer 兼修复，但修复后必须经过「红队复审」（不是 Writer 自审）。五角色降为三角色+修复后复审。
- **recon 角色吸收**：红队开工前先做「侦察」（读夹具源码+工件，不读草稿）——这正是 P1-1 新纪律「不给草稿全文」的延伸，已在执行。

### 落点 / 优先级
- **P0**：修复模式库 `repair_patterns/`（从第五批真实案例起步，4 个模式）+ 修复后必须红队复审的硬规则。
- P1：TDD 迁移——先写证据卡 actual（测试），再写夹具（实现），当前是反过来的。
- 来源：Getafix https://engineering.fb.com/2018/11/06/developer-tools/getafix-how-facebook-tools-learn-to-fix-bugs-automatically/ ；RepairAgent https://arxiv.org/pdf/2403.17134 ；TDD for Code Gen https://arxiv.org/html/2402.13521v2/

## 方向三：程序合成（原子夹具/证据卡的自动生成）

### 外部最强实践
- **DreamCoder（MIT 2021，PLDI）**：wake-sleep 贝叶斯程序学习——wake 阶段从例子合成程序，sleep 阶段用 E-graph 匹配提取公共子组件、自动构建可复用库。**「库自己写自己」**：从基本操作重新发现函数式编程基础（map/fold/compose）。
- **Example-based synthesis (PBE)**：例子作为规格，Flash Fill 商业化——输入输出对即可合成程序。
- **Test-Driven Development for Code Generation**：先写测试，测试在生成阶段介入，remediation loop。
- **LPO（279 已覆盖）**：LLM 生成 peephole 候选 + SMT 验证，与程序合成汇合。

### 批判
- DreamCoder 主要在函数式/小领域有效，对 C++ 系统编程（指针/内存/并发）的合成能力有限。
- 程序合成的「例子不够充分」问题——几个输入输出对不能唯一确定程序，可能合成出过拟合的解。我们的夹具需要「活性对照」防过拟合，正好对应。
- 自动合成的夹具可能「为了通过断言而写」（恒真观测），需要红队防。

### 吸收动作
- **DreamCoder 的 wake-sleep 迁移为原子生产节奏**：
  - wake 阶段=Writer 批量生产原子+夹具（当前模式）；
  - sleep 阶段=从已 verified 原子中提炼可复用模式（夹具模板、证据卡模板、误解模式），更新 `templates/` 库。
  - 当前我们只有 wake，没有 sleep——每批原子都是从零写，没有复用积累。**sleep 阶段是「越写越快」的关键**。
- **E-graph 匹配提取公共子组件**：对已 verified 的 20 颗原子做结构聚类，提取「夹具骨架」（如「分配计数型」「析构观测型」「地址判定型」），新原子从骨架开始填，减少从零写的错误率。
- **PBE 迁移**：原子的 claim 可以写成「输入→输出」例子对（如「传右值→拷贝 0 次」），夹具从例子对生成，而不是从自然语言 claim 生成。这降低了「claim 与夹具不一致」的概率。

### 落点 / 优先级
- **P1**：sleep 阶段——从 20 颗 verified 原子提炼夹具骨架库（结构聚类，零新内容）。
- P2：PBE 式 claim 例子对（长期，需契约化后才能做）。
- 来源：DreamCoder https://people.csail.mit.edu/asolar/papers/EllisWNSMHCST21.pdf ；Royal Society 综述 https://royalsocietypublishing.org/rsta/article/381/2251/20220050

## 交叉发现：三者合起来 = 无人自纠错闭环的理论栈

这是本轮最重要的发现——三个方向不是孤立的，它们恰好对应宪法第八节的三个环节：

| 宪法环节 | 外部理论 | 具体机制 |
|---|---|---|
| 生成（Writer 提议） | 程序合成 | DreamCoder wake 阶段 + PBE 例子对 + LLM 候选 |
| 验证（Gatekeeper 判定） | 形式化方法 | claim 契约化 pre/post/invariant + replay 运行时验证 + Souper oracle-free 差分 |
| 修复（无人自纠错） | Self-healing | Getafix 修复模式库 + 修复后红队复审 + ≤2 轮上限 |

**之前宪法第八节的「无人自纠错闭环」是工程直觉，现在有了外部理论支撑**：生成用合成、验证用形式化、修复用 self-healing，三者各有工业级先例（CompCert/Getafix/DreamCoder）。

这也解释了为什么我们的三权分立能工作——它不是拍脑袋的组织设计，而是对应了「生成-验证-修复」的计算范式。

## 给用户的话

本轮最有价值的不是某个工具，而是**三个方向交叉后验证了宪法的核心设计**：
- 三权分立（Writer/RedTeamer/Gatekeeper）= 生成-验证-修复的计算范式，不是拍脑袋的组织设计。
- 无人自纠错闭环 = 程序合成（生成）+ 形式化方法（验证）+ self-healing（修复），三者各有 CompCert/Getafix/DreamCoder 工业级先例。

**三个 P0 吸收动作**（可直接进下一轮架构进化）：
1. **claim 契约化**（pre/post/invariant 三段式 + gate 规则）——治「claim 与证据不一致」。
2. **修复模式库**（从第五批真实案例起步）+ 修复后必须红队复审——治「自动修复 plausible but incorrect」。
3. **sleep 阶段**（从 20 颗 verified 原子提炼夹具骨架）——治「每批从零写、越写不快」。

剩余 3 个方向（复杂系统/教育技术/技术债），建议下一轮做「复杂系统/系统思维」——它是架构治理的元理论（反馈回路、杠杆点、系统动力学），能把前面 10 个方向的机制串成一个整体。要继续吗？
