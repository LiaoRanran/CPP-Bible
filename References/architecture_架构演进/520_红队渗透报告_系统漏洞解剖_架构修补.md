## 二、四个真正的漏洞

### 漏洞1：S1门禁的安全根基是"谁都能写的字符串" 🔴

**位置**：`check_s1_human_signoff()`（line 1912）

**实现**：
```python
by = str(meta.get("verified_by") or "")
p_ok, p_why = principal_ok(by, need)
```

**问题**：`verified_by` 是从YAML frontmatter读的字符串。任何人（包括Agent）都可以在frontmatter里写：
```yaml
verified_by: human:liaoranran
```

**这就是之前对抗发现的E12**——"签收字符串自证"。但当时只修了一半：
- ✅ 加了 `principal_ok()` 检查前缀格式（`human:` / `machine:` / `redteam:`）
- ❌ 没验证"这个字符串真的是人写的"——Agent写的和人写的，格式完全一样

**红队攻击路径**：Agent想把自己生产的原子推成verified → 直接在frontmatter写 `verified_by: human:liaoranran` → S1门禁通过 → 原子verified。

**git author binding（S1-GIT-AUTHOR-BINDING）为什么拦不住**：
1. 它是warn级别，不block
2. 它查的是"最后一次commit的作者"，不是"谁写的frontmatter"
3. 宽松匹配（包含即通过）——`liaoranran` 和 `LiaoRanran` 匹配

**修补建议**：
- P0：把 `verified_by` 改为从git commit metadata自动提取，不允许手写
- P1：S1-GIT-AUTHOR-BINDING 升block
- P2：人审需要在单独的文件（如 `signoffs/` 目录）有签名记录，不依赖frontmatter

### 漏洞2：32条warn已被accept成基线，永远不会再修 🟡

**位置**：golden_lock基线管理

**问题**：
- 今天跑 `--accept` 把 warn=32 写进了 golden_state.json
- 这意味着这32个warn永远是"基线"，不会再被认为是"新恶化"
- 但其中很多是存量真债（如EV-MEM-017的_Znwm/_Znwy符号不匹配）

**红队攻击路径**：想加一个新规则？新规则会产生warn → 对比基线发现"多了几个warn" → 又accept一次 → warn基数膨胀到40/50/60...

**这就是402对抗说的"warn信噪比恶化"**——但当时只是建议，没有机制阻止。

**修补建议**：
- P0：warn基线不应该"永久accept"，应该有过期机制（3个月后重新评估）
- P1：新增warn必须分类——真债 vs 误报，误报直接修规则不修卡
- P2：warn超过50条自动触发"技术债清零"警报

### 漏洞3：规则全是静态分析，没有运行时验证 🔴

**位置**：全部50个check函数

**问题**：所有规则都是：
- grep / 正则匹配YAML frontmatter
- 检查文件存在
- 检查字符串格式

**没有任何规则真正验证**：
- 代码逻辑是否正确
- claim和实际行为是否一致
- 工件是不是真的从夹具编译出来的

这就是为什么对抗测试总能找到绕过——**门禁是"格式警察"，不是"逻辑警察"**。

**红队攻击路径**：
1. 写一个格式完全合规的frontmatter
2. 夹具代码做一件完全不同的事
3. .out文件手动写正确的输出（不真的跑程序）
4. 门禁全绿

之前的E05（cat式证据）、F02（编译后覆写）都是这个路径。

**修补建议**：
- P0：replay的"重编译不变量"已经做了一半（独立重编译对比sha）
- P1：加"运行时不变量"——replay不仅检查工件sha，还检查程序实际输出和.out一致
- P2：关键claim加"行为断言"——不只是grep工件，还要跑程序验证输出

### 漏洞4：工具债无管理，100个工具不知道谁在用谁 🟡

**位置**：tools/ 目录

**问题**：
- 100个.py文件，~40个是死代码
- 没有工具调用关系图
- 不知道哪些工具是CI在用，哪些是手动用
- 改一个工具不知道会影响谁

**红队攻击路径**：
1. 改一个"看起来没人用"的工具
2. 实际上它被某个关键路径调用
3. CI红了，但不知道为什么

**修补建议**：
- P0：跑 `tool_integrity.py` 扩展，自动生成调用关系图
- P1：100个工具按功能分组，每组一个入口
- P2：死代码定期清理

## 四、红队元结论

**系统现在的状态**：
- 格式门禁很强（55条规则拦格式问题）
- 逻辑门禁很弱（不验证行为正确性）
- 信任模型有漏洞（谁都能写human签名）

**类比**：这就像一个大楼，门锁很好（格式检查），但保安不验证身份证（逻辑验证），而且访客可以自己写"我是住户"的纸条（字符串自证）。

**下一步**：
1. 先修P0的3个漏洞（安全根基）
2. 再做518的6个性能/功能改进（加新东西之前先补洞）
3. 最后才加知识图谱/RAG/调度器（上层建筑）

**一句话：现在加再多新工具，底下地基是松的。先补洞，再加高。**
