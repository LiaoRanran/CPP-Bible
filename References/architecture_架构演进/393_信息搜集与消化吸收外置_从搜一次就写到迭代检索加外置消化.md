# 393 信息搜集与消化吸收外置：从"搜一次就写"到"迭代检索+外置消化"

> 日期：2026-09-13。监工完成。聚焦**信息搜集能力**和**消化吸收的外置**——Agent 怎么更高效地搜集信息，以及"消化"（从搜集到理解到应用）能不能外置到工具/系统中。
> 核心命题：**我们的信息搜集是"单次查找"，不是 Agentic RAG（迭代检索+信息缺口检测+查询分解）；我们的消化吸收全在 Agent 上下文里做，没有外置的"消化层"。三层记忆架构（工作记忆→会话压缩→长期持久）中，我们的长期记忆是扁平文件，不是向量+图。**

## 一、信息搜集：从单次查找到 Agentic RAG

### 核心发现

**Agentic RAG**（AWS Bedrock/Microsoft Azure，2026）：检索不再是单次 lookup，而是推理 Agent 在循环中——
1. 决定是否检索、检索什么
2. 多次检索以精炼
3. 选择哪个知识库（语义路由）
4. 才组合有引用的答案

**Interact-RAG**：Agent 从"查询发起者"升级为"信息操控者"——精确匹配、实体锚定、上下文整形，6 个基准平均提升 22.5%。

**查询分解**（TREC 2025）：复杂查询分解为子问题，每个独立跑完整 Retrieve→Expand→Refine，RRF 合并。

**SCMRAG**：自纠正多跳 RAG——自主识别信息缺口，从外部源检索缺失信息。

**Contextualization module**：外部 LLM 从检索文档中提取相关信息，维护持久记忆缓存——不是把原始文档全塞进上下文。

### 和我们的映射

| 能力 | 我们的现状 | 差距 |
|---|---|---|
| 单次检索 | ✅ general_search 一次 1-3 个 query | 有 |
| 信息缺口检测 | ❌ 搜一次就开始写，不评估"信息够不够" | 缺 |
| 迭代检索 | ❌ 没有"不够再搜"的循环 | 缺 |
| 查询分解 | ⚠️ 手动并行 2-3 query，非系统化 | 部分 |
| 语义路由 | ❌ 所有搜索都走 general_search，不分源 | 缺 |
| 消化层 | ❌ 搜索结果全文进上下文，无外置提取 | 缺 |

### 挖掘

**1. 我们的调研流程是"手动 Agentic RAG"，但没有系统化**：
- 我每次调研都是：搜 2-3 个 query→读结果→判断是否够→不够再搜→写文档
- 这就是 Agentic RAG 的"检索→评估→迭代"循环，但是我（监工）在上下文里手动做的
- **如果把这个循环写成提示词/工具，Agent 就可以自动做——不需要监工每次手动判断"信息够不够"**

**2. 查询分解是最容易落地的提升**：
- 当前：一个复杂问题（如"多模型路由"）搜 1-2 个 query
- 应该：分解为 3-5 个子查询（FrugalGPT/RouteLLM/oh-my-claudecode/企业级实践），每个独立检索，合并结果
- **零成本——只需要在搜索提示词里加"先分解为 3-5 个子查询再并行搜索"**

**3. 信息缺口检测是质量的关键**：
- 当前 Agent 搜一次就写，可能遗漏重要角度
- 应该：搜索后先评估"是否覆盖了问题的所有方面？有没有矛盾的信息？有没有需要深挖的点？"
- **这和 389 的自纠错是配套的——"信息是否充分"是自纠错的第一步**

## 二、消化吸收外置：从"上下文里消化"到"外置消化层"

### 核心发现

**三层记忆架构**（2025-2026 生产共识）：
1. **In-context working memory**：当前会话原始消息缓冲，临时，会话结束清除
2. **Session-scoped compressed memory**：当前会话的摘要/提取事实，按需读取
3. **Long-term persistent store**：跨会话知识、偏好、工作流，向量+图存储

**ByteRover**（arXiv 2604.01599）：Agent 原生记忆——反转记忆管道，同一个 LLM 既推理又策展/结构化/检索知识。层级 Context Tree（Domain>Topic>Subtopic>Entry），每个条目有：显式关系、来源、Adaptive Knowledge Lifecycle（重要性评分、成熟度层级、近因衰减）。

**"Memory Is the New RAG"**（2026）：扁平向量存储不够，生产 Agent 需要三层——episodic（向量）、semantic（图用于多跳推理）、procedural。Anthropic 发布"Dreaming"（异步记忆重组）、Google 发布 Memory Bank。

**知识图谱作为记忆后端**：显式实体关系、可解释推理路径、冲突检测——Generalized RAG 最强大的结构化记忆后端。

**成本现实**：企业客户每月 $4,200 在用陈旧上下文填充提示词，90% 的 token 从未被模型有意义地读取。

### 和我们的映射

| 记忆层 | 我们的现状 | 差距 |
|---|---|---|
| 工作记忆 | 当前对话上下文 | ✅ |
| 会话压缩记忆 | 每轮结束的固化摘要（383） | ⚠️ 有但不系统 |
| 长期持久存储 | 仓库文件（架构文档+原子+误解） | ✅ 但扁平 |
| 语义检索 | grep/Glob（关键词匹配） | ❌ 无向量检索 |
| 图推理 | 无（380 提了但未落地） | ❌ |
| 成熟度标签 | 无（19 份架构文档无"已验证/调研中/已过时"） | ❌ |
| 近因衰减 | 无 | ❌ |
| 消化层 | 全在上下文里做（搜集→整理→挖掘→...） | ❌ 无外置 |

### 挖掘

**1. 我们的 19 份架构文档是"扁平文件"，没有成熟度标签**：
- 374-392 共 19 份，每份都是"调研文档"，但没有标注：
  - 哪些是"已验证可落地"（如 386 的负面指令改正面）
  - 哪些是"调研中待验证"（如 384 的模型路由，需要基准测试数据）
  - 哪些是"已过时/被后续取代"（如 372 v5 的某些设计被 382-385 修正）
- **ByteRover 的 Adaptive Knowledge Lifecycle（重要性+成熟度+近因衰减）正是我们缺的——没有成熟度标签，Agent 不知道哪些文档可以直接用，哪些需要验证**

**2. "消化吸收外置"的核心是 Contextualization module**：
- 当前：Agent 搜索到网页→全文进上下文→Agent 在上下文里消化（提取关键信息）→写文档
- 问题：消化过程占用大量上下文 token，且消化结果不持久（下次调研类似主题要重新消化）
- **外置消化层：搜索结果→外部 LLM 提取关键信息→存到记忆缓存→Agent 只读取消化后的摘要**
- 映射到我们：调研文档本身就是"消化后的产物"——但创建过程（消化）是在上下文里做的。如果把"消化"外置成工具（输入：搜索结果；输出：结构化摘要），就可以复用和持久化

**3. 知识图谱是"消化吸收"的终极形态**：
- 380 已经提了知识图谱（relations schema+equivalent 关系+缺口检测）
- 如果 19 份架构文档+27 颗原子+80 条误解都进了知识图谱：
  - Agent 可以"图推理"（"哪些架构层和自纠错有关？"→遍历 389→385→382 的关系）
  - 可以检测冲突（"372 说 X，386 说 Y，是否矛盾？"）
  - 可以发现缺口（"19 层架构中，哪层没有对应的落地项？"）
- **这是从"全文检索"到"结构化推理"的跃迁**

**4. 成本问题：90% 的 token 从未被有意义地读取**：
- 我们的 Agent 每次都把大量工具输出（搜索结果、文件内容）塞进上下文
- 383 已经识别了"工具输出是最大污染源"
- **外置消化层可以在工具输出进入上下文之前就压缩——只提取相关信息，丢弃 90% 的噪声**

## 三、应用（分阶段）

### 立即落地（零成本）

**应用 1：搜索提示词加"查询分解+信息缺口检测"**
- 搜索前："先将问题分解为 3-5 个子查询，并行搜索"
- 搜索后："评估信息是否覆盖了所有方面？有没有矛盾？有没有需要深挖的点？如果有，继续搜索"
- 这是 Agentic RAG 的最小实现

**应用 2：架构文档加成熟度标签**
- 每份文档 frontmatter 加 `maturity: validated/exploratory/superseded`
- validated：已落地或已验证
- exploratory：调研中，待验证
- superseded：被后续文档取代
- 19 份文档逐份标注（约 10 分钟）

### 中期落地

**应用 3：外置消化工具**（digest_search_results.py）
- 输入：搜索结果（URL+摘要）
- 输出：结构化摘要（关键发现+来源+可信度+与已有知识的关系）
- Agent 不读原始搜索结果，只读消化后的摘要
- 这是 Contextualization module 的最小实现

**应用 4：架构文档的语义索引**
- 对 19 份架构文档+27 颗原子做 embedding，存到本地向量库
- Agent 可以语义检索（"哪些文档和自纠错有关？"），而不是 grep 关键词
- 需要 embedding 工具（如 sentence-transformers），当前环境可能不具备

### 长期落地

**应用 5：知识图谱**（和 380 配合）
- 19 份架构文档+27 颗原子+80 条误解→知识图谱
- 实体：架构层、原子、误解、规则、工具
- 关系：prereq/contrasts/serves/equivalent/extends
- 支持图推理、冲突检测、缺口发现

## 五、局限

- 完整向量检索需要 embedding 工具和向量数据库，当前环境可能不具备
- 知识图谱需要实体关系抽取工具，成本较高
- 外置消化工具（digest_search_results.py）需要调用 LLM，增加延迟和成本
- 查询分解的质量依赖 Agent 的理解能力——分解得不好反而增加噪声
- 成熟度标签需要人审——不能自动分配"validated/exploratory/superseded"
- 本调研未覆盖"主动信息搜集"（Agent 主动发现需要什么信息，而不是等用户问）——这是更高级的能力
