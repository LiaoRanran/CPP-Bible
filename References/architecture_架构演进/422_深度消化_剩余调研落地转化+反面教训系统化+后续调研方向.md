# 422 深度消化：剩余调研的落地转化 + 反面教训系统化 + 后续调研方向

> 日期：2026-09-13。418-421 消化了核心高价值调研（验证闭环/自检层/成本追踪/矛盾检测）。本文消化剩余的 6 项（405/406/409/415 L2/L5/407），并把两个反面教训（时序约束/错误模式自动转化）系统化，最后给出后续调研方向。

## 一、剩余调研的核心洞察与最小可行闭环

### 1.1 405 教学转化：素材已经全有，缺的是导出格式

**核心洞察**：阙疑的知识是"实测出来的"不是"写出来的"——27 颗原子 + 80 条误解 + 56 张证据卡 = 教学内容已经存在，只需要转换器。

四层模型的最小可行闭环：

| 层 | 内容 | 素材来源 | 最小闭环 |
|---|---|---|---|
| L1 闪卡 | claim + 1 反例 | 原子 claim + 误解反例 | Markdown → Anki CSV 导出 |
| L2 诊断 MCQ | 误解的 3 反例 → 选择题 | misconceptions/*.md | 误解 → 4 选 1 自动生成 |
| L3 学习路径 | prerequisite 关系 → 学习顺序 | atoms/*.md 的 relations | 拓扑排序输出 |
| L4 活代码 | 夹具 + .out → 可交互实验 | Examples/atoms/*.cpp + .out | 只读展示（不做在线编译） |

**关键决策**：先做 L1 闪卡导出（最简单），验证 27 颗能导出、格式正确、学生能用。L2-L4 等 L1 有真实用户反馈再做。

**反面教训**：不要一上来做完整的学习平台（Qt 脚手架那个方向），先做"导出器"——把已有素材转成标准格式（Anki/Markdown），零风险、立即可用。

### 1.2 406 增量知识更新：不是所有原子都需要同等频率更新

**核心洞察**：原子会老，但老化速度不同。三类数据新鲜度：

| 类型 | 例子 | 老化速度 | 更新触发 |
|---|---|---|---|
| deterministic | sizeof、语法规则、ODR | 极慢（年级别） | 标准变更 |
| performance | 倍数、纳秒、缓存行大小 | 中（编译器/硬件升级） | 编译器大版本升级 |
| tool_observation | LSan 报不报、TSan 检测率 | 快（工具版本变） | sanitizer 升级 |

**最小可行闭环**：
1. 给原子加 `data_freshness:` 字段（deterministic/performance/tool_observation）
2. 存量 27 颗批量标注
3. 建立"编译器升级检查清单"：升级后自动重跑所有 performance 类原子的夹具，比对 sha/读数

**关键决策**：不做自动更新（风险太高），只做" freshness 标签 + 更新提醒"。当 performance 类原子的工件 sha 与卡内不一致时，gate 给 warn（不是 block，因为可能只是编译器版本不同）。

### 1.3 409 对抗防御：毒样例的攻击面覆盖率是盲区

**核心洞察**：402 的 F02（A4 时序穿链）漏过去，根本原因是毒样例只覆盖了 A1-A3（声明伪造/工件借品/断言恒真），A4-A10 几乎没有毒样例。

A1-A10 十类攻击面的当前覆盖率（估算）：

| 类 | 说明 | 毒样例数 | 覆盖率 |
|---|---|---|---|
| A1 声明伪造 | frontmatter 字段造假 | ~10 | 高 |
| A2 工件借品 | cp/mv/python 覆写 | ~5 | 中 |
| A3 断言恒真 | 通用符号/注释伪造 | ~8 | 高 |
| A4 时序穿链 | 编译后覆写/顺序依赖 | ~1 | **极低** |
| A5 环境依赖 | nproc/路径/时区进断言 | ~2 | 低 |
| A6 格式混淆 | 中文/全角/YAML 重复键 | ~2 | 低 |
| A7 关系滥用 | 纯标量/自引用/矛盾 | ~3 | 中 |
| A8 间接注入 | 夹具注释/外部文件 | 0 | **零** |
| A9 规则绕过 | 利用 warn 不 block | ~3 | 中 |
| A10 供应链 | 外部依赖/工具版本 | 0 | **零** |

**最小可行闭环**：
1. 给现有 47 条毒样例加 `attack_type:` 标签（A1-A10）
2. 统计每类覆盖率
3. 优先补 A4/A8/A10（覆盖率最低的三类）
4. 把覆盖率写进健康度仪表盘

**关键决策**：不是"更多毒样例"，是"更均衡的毒样例"。47 条集中在 A1-A3，对 A4-A10 的防御几乎为零。

### 1.4 415 L2 影响分析：区分"引用"和"依赖"

**核心洞察**：影响分析不是"谁引用了我"，是"改了我的 claim，谁的结论会变"。

- **引用**：只是提到，改了不影响结论（contrasts、see_also）
- **依赖**：结论建立在上面，改了会连锁失效（prerequisite、specializes、realizes）

γ^k 加权传播的最小可行版本：
```
直接依赖（prerequisite/specializes/realizes）：γ=1.0
间接依赖（依赖的依赖）：γ=0.5
对比关系（contrasts）：γ=0.3
矛盾关系（contradicts）：γ=0.8
```

**最小可行闭环**：先做上游遍历（谁依赖我），只用 prerequisite/specializes/realizes 三类，不做下游、不做加权、不做优先级排序。输出"改这颗原子会影响 X 颗"的列表。

**关键决策**：不做完整的影响传播（太复杂），先做"直接依赖列表"——这已经能解决 80% 的问题（改一颗原子前，先看谁依赖它）。

### 1.5 415 L5 文档腐烂：引用漂移已有，概念陈旧是空白

**核心洞察**：三类腐烂中，引用漂移（ATOM-REL-TARGET）已有，概念陈旧需要矛盾检测（417 在做），结构衰变需要版本比对。

**最小可行闭环**：
1. 引用漂移增强：不只是"目标存在"，还要"目标的 status 不是 deprecated"
2. 概念陈旧：结合 417 的矛盾检测，如果 A 依赖 B 且 B 被 C contradicts → warn（"A 依赖的 B 已被 C 质疑"）
3. 结构衰变：暂不做（需要版本历史，复杂度高）

**关键决策**：L5 不独立做，而是增强现有规则（ATOM-REL-TARGET + 417 ATOM-REL-CONFLICT）。这比新建一个工具更高效。

### 1.6 407 提示词压缩：只做了 312，还有 401/402/403

**核心洞察**：312 压缩 -81% 证明了压缩的价值，但 401（搭建执行）、402（对抗）、403（苦力）这三份高频使用的提示词还没压缩。

**最小可行闭环**：按 312 的压缩方法（删冗余/结构化/约束核对表），依次压缩 401/402/403。每份压缩后验证"关键约束不丢失"。

**关键决策**：优先级低于工具落地——提示词压缩是"省 token"，但当前更缺的是"工具落地"。等 420/421 跑完有了成本数据，再决定压缩哪份最划算。

## 二、反面教训的系统化（两个架构原则）

### 2.1 原则一：不变量约束优于存在性检查

**来源**：402 F02（编译后覆写）

EV-ARTIFACT-PRODUCER 的原始设计是"检查编译行在 command 中"（存在性检查），被"真编译 + python 覆写"绕过。修复应该是"编译行之后没有对 artifact 的写操作"（不变量约束）。

**推广到所有 gate 规则的设计原则**：

| 反模式（存在性检查） | 正模式（不变量约束） |
|---|---|
| command 中含编译行 | 编译行之后无 artifact 写操作 |
| artifact_sha256 字段存在 | sha256 == 重生成工件的 sha |
| actual 中有断言标签 | 断言标签在工件中存在且非注释 |
| relations 中有 prerequisite | prerequisite 目标存在且非 deprecated |
| .out 中有读数 | 读数与 command 同代生成 |

**实现方式**：在 gate_engine.py 中新增 `check_invariant()` 辅助函数，支持"X 之后无 Y"、"X 与 Y 同代"、"X 非注释"等时序/代际检查。

**这是架构级的改进**，不是修一个规则——所有新规则都应该按不变量约束设计，而不是存在性检查。

### 2.2 原则二：错误模式 → 自检规则的自动转化管道

**来源**：416"机械错误消耗语义错误的精力" + 420 自检层

当前流程：红队发现 E1/E2 → 人写进自检层 → 下次拦住。
问题：人工转化慢，且可能遗漏。

**半自动化管道**：

```
红队报告
  → 标记 E1/E2 错误（红队已做）
  → 自动提取错误模式（正则/关键词）
    例："artifact_sha256 与重生成不一致" → WC-01
    例："断言标签不在工件中" → WC-02
  → 生成自检规则的伪代码
  → 人审确认（防止误判）
  → 加入 writer_checks.yaml
  → 下次 Writer 自动拦住
```

**最小可行闭环**：先做"错误模式库"（writer_checks.yaml），每条记录来源（哪次红队/哪颗原子）、检查逻辑、拦截率。人工维护，但格式标准化，为后续自动化铺路。

**关键决策**：不做全自动（误判风险高），先做"半自动化+人审确认"。错误模式库本身就是有价值的资产——它记录了"阙疑历史上犯过哪些机械错误"。

## 三、后续调研方向（基于消化后的空白）

### 方向 1：教学转化的实证研究（P1）

**研究问题**：阙疑的"实测驱动"教学内容 vs 传统"讲解驱动"内容，学习效果差异如何？

**需要调研**：
- 提取练习效应（Karpicke & Roediger 2008）：闪卡对长期记忆的影响
- 错误示例学习（Metcalfe 2017）：看错误示例 vs 看正确示例的学习效果
- 自适应学习路径（VanLehn 2011）：基于 DAG 的学习顺序优化

**落地**：405 L2 诊断 MCQ 的设计依据。

### 方向 2：知识新鲜度的自动化检测（P1）

**研究问题**：如何自动检测 performance 类原子的数据过期？

**需要调研**：
- 编译器版本差异的自动检测（gcc 13 vs 14 vs 15 的代码生成差异）
- 性能基准的统计显著性检验（7 轮中位数的置信区间）
- 数据漂移检测（concept drift in data streams）

**落地**：406 的"编译器升级检查清单"自动化。

### 方向 3：攻击面分类的毒样例自动生成（P1）

**研究问题**：如何为 A4-A10 自动生成毒样例？

**需要调研**：
- 变异测试（mutation testing）：自动生成代码变异体
- 属性测试（property-based testing）：自动生成边界 case
- 模糊测试（fuzzing）：自动生成异常输入

**落地**：409 的毒样例覆盖率提升。

### 方向 4：时序约束的通用框架（P0，架构级）

**研究问题**：如何在 gate 引擎中支持"X 之后没有 Y"的时序检查？

**需要调研**：
- 命令式程序的时序逻辑（LTL/CTL）
- 数据流分析（def-use chain）
- 脚本安全审计（command injection 的时序检测）

**落地**：2.1 原则一的工程实现。

### 方向 5：错误模式的自动提取（P2）

**研究问题**：如何从红队报告中自动提取 E1/E2 错误模式？

**需要调研**：
- 信息抽取（IE）：从非结构化文本提取结构化模式
- 错误分类学（error taxonomy）：E1-E6 的自动分类
- 主动学习（active learning）：人审确认后自动更新分类器

**落地**：2.2 原则二的自动化。

### 方向 6：影响分析的图算法验证（P2）

**研究问题**：γ^k 加权传播的 γ 值如何确定？0.5/0.3/0.8 是拍脑袋还是有依据？

**需要调研**：
- 图神经网络的消息传递（message passing）
- 知识图谱的影响传播算法
- 软件变更影响分析（change impact analysis）

**落地**：415 L2 的 γ 值校准。

## 六、元结论

**消化的本质不是"读完了"，是"改变了决策"。**

本文消化的 6 项调研 + 2 个反面教训，改变了以下决策：
1. 405 → 不做学习平台，先做导出器
2. 406 → 不做自动更新，只做 freshness 标签+提醒
3. 409 → 不是"更多毒样例"，是"更均衡的毒样例"（补 A4/A8/A10）
4. 415 L2 → 不做完整影响传播，先做直接依赖列表
5. 415 L5 → 不独立做，增强现有规则
6. 407 → 等成本数据再决定压缩哪份
7. 时序约束 → 所有新规则按不变量约束设计（架构原则）
8. 错误模式 → 建立 writer_checks.yaml 错误模式库

**最有价值的发现**：409 的毒样例覆盖率分析——47 条毒样例集中在 A1-A3，A4/A8/A10 覆盖率为零。这解释了为什么 402 的 F02（A4 时序穿链）能漏过去。**不是规则不够多，是规则覆盖的攻击面不够均衡。**

**一句话**：从"堆规则数"切换到"补攻击面覆盖率"——这是 409 调研给阙疑的最有价值的方向修正。

累计 49 份（374-422）。
