# 474 代码级深度架构分析报告

> 2026-09-14 · 基于 tools/ 91 个 .py 文件、56 张证据卡、27 颗原子、CI 74 步的实测分析。
> 这不是框架级反思，是代码级审计——每个数字都来自实跑。

## 一、工具层全景（91 个 .py，实测）

### 1.1 代码量分布

| 层级 | 工具 | 行数 | 占比 |
|---|---|---|---|
| 核心三件套 | gate_engine / replay / poison | 1950+1132+1055=4137 | 23% |
| 书籍构建 | gen_mkdocs_nav / rewrite_links / compile_all / chapter_compile_check 等 | ~3000 | 17% |
| 内容审计 | 20+ 个 audit 工具（density/mermaid/table/terminology 等） | ~4000 | 22% |
| 编译验证 | compile_run_sanitize_pipeline / run_cpp_assertions / run_expected 等 | ~1500 | 8% |
| 基础设施 | toolchain / utf8_console / l2_state / snapshot | ~600 | 3% |
| 其他 | 30+ 工具 | ~4500 | 27% |

**关键发现**：
- 91 个工具**全部被引用**（全仓搜索 import/调用，无死代码）
- 但"被引用"≠"被使用"——部分工具只在文档/提示词中被提到，CI 中未实际调用
- 内容审计类工具占 22%，是最大的一类，但很多是一次性审计后未再使用

### 1.2 依赖关系（反向分析）

```
toolchain.py  ← 18 个工具依赖（最核心基础设施：编译器解析/路径/编码）
utf8_console  ← 11 个工具依赖（Windows 控制台编码）
gate_engine   ← 6 个工具依赖（flashcard/writer_selfcheck/impact/cost/poison/golden）
replay        ← 5 个工具依赖（writer_selfcheck/gate/poison/book_atom_sync/golden）
comment_blocks ← 4 个工具依赖（注释块解析）
```

**结论**：toolchain 和 utf8_console 是真正的基础设施层，gate/replay 是核心业务层。修改 toolchain 会影响 18 个工具，必须有回归测试。

### 1.3 replay 内部复杂度（37 函数）

| 函数 | 行数 | 职责 |
|---|---|---|
| replay_card() | 263 | 单卡验证主流程（最大函数，上帝函数风险） |
| check_artifact_assert() | 147 | 断言检查（contains_in/absent_in/contains_any） |
| _parse_block() | 70 | 自定义 YAML 解析器（不用 pyyaml 的原因？） |
| _recompile_invariant() | 43 | P0-A 重编译不变量（470 新增） |
| _acquire_replay_lock() | 32 | N1 僵尸锁所在（mtime 判陈旧，无 pid 检测） |

**问题**：
- replay_card() 263 行是上帝函数，承担了 sha 比对+编译+run_match+artifact_assert+sanitizer+锁 全部职责
- _parse_block() 自定义解析器是 E07 缩进走私的根源——标准 pyyaml 不会有这个问题
- 锁只按 mtime 判陈旧，无 pid 存活检测 = N1 僵尸锁 DoS

## 二、性能瓶颈（实测，非估算）

### 2.1 replay 全量性能

```
总卡数: 56
单卡时间: 0.7s ~ 13.7s（差异 20 倍）
前5卡平均: 5.19s/卡
全量实测: 268s = 4.5min（无 P0-A 重编译）
全量预估: 7.2min（含 P0-A 重编译 +2.5s/卡）
```

### 2.2 最慢 5 卡 vs 最快 5 卡

| 最慢 | 时间 | 特征 | 最快 | 时间 | 特征 |
|---|---|---|---|---|---|
| EV-CONC-001 | 13.7s | assert+run_match | EV-CONC-002 | 0.7s | assert+run_match |
| EV-MEM-045 | 13.6s | assert+run_match | EV-UB-001 | 0.8s | assert |
| EV-CONC-003 | 7.9s | assert+run_match | EV-UB-002 | 0.8s | assert |
| EV-CONC-004 | 7.9s | assert+run_match | EV-MEM-004 | 0.8s | assert |
| EV-CONC-005 | 7.3s | assert+run_match | EV-MEM-005 | 0.9s | assert |

**关键发现**：快慢差异不是"有没有 assert"（所有 56 卡都有 artifact_assert），而是**command 的复杂度**：
- 慢卡：多文件编译、性能基准、sanitizer 运行
- 快卡：单文件编译、纯符号检查

### 2.3 优化方向（按收益排序）

1. **增量 replay**（收益最大）：只重跑 git diff 变更的卡。日常开发只改 1-2 张卡，增量 replay 只需 5-10s，而非 4.5min。
2. **ccache 接入**（已装未用）：replay 编译命令加 ccache 前缀，重复编译从 3-5s 降到 0.3s。
3. **并行 replay**：多卡并行编译，4 核可提速 2-3 倍。
4. **P0-A 按需启用**：不是每卡都需要重编译不变量——只有 artifact_assert 的卡需要，且可以缓存结果。
5. **replay_card() 拆分**：263 行上帝函数拆成 5-6 个小函数，便于并行和缓存。

## 三、数据模型一致性（重大发现）

### 3.1 原子 frontmatter（27 颗）

| 字段 | 覆盖率 | 问题 |
|---|---|---|
| id/title/domain/type/status/dal/status_history | 100% | 通用字段，OK |
| verified_by / verified_at | 96% | 1 颗缺（draft 状态） |
| human_review | 88% | 3 颗缺 |
| depth / pedagogy | 33% | 只有 9 颗有结构化教学法 |
| audience/cognitive_load/prerequisites_readable | 29% | 只有 8 颗有 |
| claim / claim_boundary / relations / evidence | 29% | **只有 8 颗有 claim！** |
| sources / first_hand / superiority | 29% | 只有 8 颗有 |
| misconceptions | 25% | 只有 7 颗有 |
| dal_reviewed_by | 18% | 只有 5 颗有 |
| gray_zone | 3% | 只有 1 颗有 |

**这是系统性问题**：
- 早期原子（MEM 域，~18 颗）和近期原子（CONC/LANG 域，~9 颗）格式完全不同
- 27 颗原子中只有 8 颗有 claim 字段——而 claim 是知识的核心！
- pedagogy 只有 33%——这就是"4 颗折叠 pedagogy 致 PED 规则静默跳过"的根源
- 这直接阻碍证据网构建：没有 claim/relations/evidence 字段，无法构建 claim→证据→夹具的映射图

### 3.2 证据卡 frontmatter（56 张）

| 字段 | 覆盖率 |
|---|---|
| id/serves/kind/hypothesis/controlled_vars/matrix/fixture/command/artifact/artifact_sha256/artifact_compiler/artifact_assert/actual/expected/verdict/falsification | 100%（17 个字段） |
| depth_layer / drill_note | 80% |
| reproduce | 69% |
| status | 25% |
| domain/type/dal/relations/evidence/expected_sanitizer | 10% |

证据卡一致性好很多——17 个字段 100% 通用。这是因为证据卡的格式从一开始就严格定义了。

### 3.3 数据模型修复建议

**原子字段统一是 P0**：
- 所有原子必须有 claim 字段（≤50 字，契约化）
- 所有原子必须有 relations 字段（prerequisite/specializes/evolved_from）
- pedagogy 结构化（不是自由文本）
- 迁移方案：写一个 `atom_field_migration.py`，批量补全缺失字段（从正文提取 claim，从证据卡反推 relations）

## 四、gate 规则命中分布（实测）

```
EV-MATRIX-UNBACKED      16 条（最大类：多平台声明但留痕不足）
EV-OUT-UNDECLARED-KEY    6 条（.out 含未声明键）
EV-FALSIFICATION-QUANT   4 条（证伪缺量化）
EV-ASSERT-SYMBOL-MAPPED  3 条（断言符号映射）
EV-OUT-STALE-MTIME       2 条（.out 比夹具旧）
ATOM-REL-TARGET          2 条
EV-ENV-DEPENDENT-KEY     2 条（环境依赖键如 nproc）
EV-SERVES-EXIST          1 条
ATOM-PREREQ-READABLE     1 条
```

**关键发现**：
- EV-MATRIX-UNBACKED 16 条是最大类——16 张卡声明了多平台但留痕格式不符合规则。这可能是**规则太严**（要求双平台 .out + CI run 号），而非卡真的有问题。
- 32 条 warn 已被 accept 为基线（golden_lock），但其中 17 条是 MATRIX 规则对已真实跨平台卡的误报。
- **规则信噪比问题**：warn 太多导致真正的问题被淹没。建议把 EV-MATRIX-UNBACKED 从 warn 降为 advice，或收窄判据。

## 六、架构层面的核心矛盾（代码级证据）

### 6.1 矛盾一：规则军备竞赛

- 48 条规则，对抗每轮找新逃逸（E01→F02→E01 变体，同一漏洞三次变种）
- 规则越多，维护成本越高，误报率越高
- 代码证据：gate_engine.py 1950 行，其中规则注册和检查逻辑占 60%
- **根因**：规则是枚举的，永远列不全。需要元规则（如"断言必须可证伪"）覆盖一类问题

### 6.2 矛盾二：架构-工程脱节

- claim 契约化设计了，但只有 29% 原子有 claim 字段
- 候选仓 candidates/ 设计了，从未使用
- 科学发现状态机 S1-S6 设计了，红队还是"读代码+推理"
- 数据飞轮 Distill/Improve 设计了，没有实现
- **代码证据**：27 颗原子中只有 8 颗有 claim，说明架构设计没有落地到生产流程

### 6.3 矛盾三：预测性为零

- 架构只能解释过去的错误，不能预测未来的
- 代码证据：没有任何工具做"错误预测"——所有工具都是事后检查
- **Lakatos 判据**：这是退化纲领，不是进步纲领

### 6.4 矛盾四：replay 上帝函数

- replay_card() 263 行，承担 6 种职责
- 自定义 YAML 解析器（_parse_block 70 行）是 E07 缩进走私的根源
- 锁机制无 pid 检测 = N1 僵尸锁
- **代码证据**：replay 是最复杂的工具，也是对抗逃逸最多的工具

### 6.5 矛盾五：公共库缺失导致重复代码

91 个工具中有 30 个跨工具重名函数（排除 main()）：

| 函数 | 重复次数 | 说明 |
|---|---|---|
| find_gpp() | 5 | 编译器查找逻辑，应该在 toolchain 里 |
| cmd_check() | 5 | 命令检查逻辑 |
| scan_file() | 5 | 文件扫描逻辑 |
| extract_blocks() | 5 | 代码块提取逻辑 |
| collect() | 6 | 收集逻辑 |
| scan() / process_file() / report() / audit_file() | 各 4 | 通用审计逻辑 |
| flags_for() / detect_format() / detect_version() | 各 2 | asm_regen 和 asm_repro_spotcheck 几乎重复 |

**根因**：工具层缺乏公共库抽象。toolchain.py 被 18 个工具依赖，但只覆盖了编译器解析/路径/编码，没有覆盖：
- 编译器查找（find_gpp 重复 5 次）
- 代码块提取（extract_blocks 重复 5 次）
- 文件扫描（scan_file 重复 5 次）
- Markdown frontmatter 解析（每个工具自己写）

**后果**：
1. 维护成本高（改一个逻辑要改 5 个地方）
2. 容易出现不一致（5 个 find_gpp() 可能有细微差别）
3. 新工具开发成本高（要复制粘贴通用逻辑）
4. 对抗逃逸面大（5 个 extract_blocks() 可能有 5 种不同的边界处理）

### 6.6 矛盾六：80% 工具零测试（质量盲区）

- 91 个工具中只有 18 个有测试（20%），73 个零测试（80%）
- 零测试工具中很多是 CI 实际调用的核心工具：
  - compile_run_sanitize_pipeline.py: 607 行（零测试！）
  - gen_mkdocs_nav.py: 764 行（零测试！）
  - cppbible.py: 671 行（零测试！）
  - compile_all.py: 552 行（零测试！）
  - rewrite_links.py: 583 行（零测试！）
  - expand_assist.py: 533 行（零测试！）
- 测试集中在 gate（87 个测试）和 replay（28 个测试），其他工具几乎裸奔
- **后果**：这些工具的任何改动都没有回归保护，CI 绿了不代表工具没坏

### 6.7 矛盾七：actual 手写率 88%（证据真实性风险）

- 56 张证据卡只有 7 个 .out 工件（12.5%）
- 其余 49 张卡的 actual 是手写的，不是从真实运行输出提取
- 工件完整性本身很好：0 空文件、0 过期 .asm（N4 事故已修复）
- 但 .out 缺失意味着 actual 的真实性无法通过"重跑 command 比对"来验证
- **这是 E06（虚构 .out 留痕）和 E05（cat 式证据）的温床**——如果 actual 是手写的，攻击者可以写任何数字

### 6.8 矛盾八：误解库利用率 44%（知识资产沉没）

- 79 条误解中 41 条是孤儿（56%），没有被任何原子引用
- 深度字段 94% 缺失（74/79 unknown），0% 有来源引用
- 域分布不均衡：MEM 29 条、UB 14 条、STL/CONC 各 10 条，但 LANG 只有 1 条
- **后果**：误解库维护成本高，但教学转化率低；孤儿误解可能过时/重复，无人复审

### 6.9 矛盾九：golden_lock accept 无过期机制（基线信噪比持续恶化）

- 17 条 accept 记录，第 17 条一次涨 24 条 warn（8→32）
- 13 条是"预期中间态"（EV-SERVES-EXIST），但从未自动清零
- 没有任何 accept 有"复审日期"或"自动过期"机制
- warn 被 accept 后永远在基线里，导致新 warn 被淹没在 32 条基线中
- **后果**：golden_lock 从"质量守门"退化为"历史记录"，新问题的信噪比持续下降

### 6.10 矛盾十：Writer 自检 7 项有盲区（生产期质量门不足）

- WC-01~07 覆盖了工件同代/断言标签/command可执行/.out同代/活性对照/数字一致性/无无限循环
- 但不检查：claim 字段是否存在（29% 原子缺 claim）、relations 是否完整、pedagogy 是否结构化、DAL 定级是否合理、expected_sanitizer 是否声明
- _parse_block 71 行自定义 YAML 解析器是 E07 缩进走私的根源——应该用 yaml.safe_load
- **后果**：Writer 自检拦住了"工件过期"这类机械问题，但拦不住"数据模型不完整"这类结构性问题

### 6.11 矛盾十一：CI 流水线 37 步全串行（性能瓶颈）

- quality job 有 37 步（占总 74 步的 50%），全部串行执行
- Set up Python 重复 5 次（每个 job 都要设置）
- pdf/epub 都要安装 mermaid-filter 和 Chromium libs（重复安装）
- 内容审计工具之间没有依赖关系，可以并行但没有并行
- **后果**：CI 一次 15min+，日常开发反馈慢；quality job 是最大瓶颈

### 6.12 矛盾十二：actual 格式 3 种不统一（43% 手写摘要）

- 7 个 .out 工件有 3 种格式：每行 key=value（4 个）、| 分隔（2 个）、stderr（1 个）
- run_match_keys 格式的 5 张卡 100% 真实（键在 .out 中存在）
- 但 3 张卡的 actual 是手写摘要（用 | 分隔），不是 .out 原文——43% 的卡 actual 非原文
- **后果**：replay 的 run_match 解析逻辑复杂，容易出错；手写摘要存在证据真实性风险

### 6.13 矛盾十三：claim 契约化零落地（0/8 符合）

- 8 颗有 claim 的原子，0 颗符合 ≤50 字契约（平均 200+ 字，最长 514 字）
- 0 颗有 pre/post/invariant 结构化字段——claim 都是散文式长文本
- 只有 1 颗有竞争假设（ATOM-LANG-INLINE-001）
- 288/298 文档设计的 claim 契约化（pre/post/invariant + 竞争假设≥2 + Curry-Howard）完全没落地
- **后果**：claim 无法被机器验证，只能靠人读；"claim 契约化"是纸面设计

### 6.14 矛盾十四：原子数据模型两极分化（教学字段 29%）

- 原子核心字段 100%（id/title/domain/type/status/dal/status_history）
- 但教学/知识字段只有 29-33%：claim(29%)、relations(29%)、evidence(29%)、sources(29%)、pedagogy(33%)、depth(33%)
- 4 个字段类型不一致：verified_at(date+str)、depth(dict+str)、controlled_vars(str+list)、expected(dict+str)
- 证据卡核心字段 100%——证据卡的数据模型比原子更一致
- **后果**：原子无法构建证据网（relations/evidence 缺失），无法做教学路径规划（pedagogy/depth 缺失）

### 6.15 矛盾十五：单人项目无代码审查（996 提交全是一个人）

- 总提交 996 条，最近 3 天 206 条（日均 68 条），全部是 LiaoRanran
- 没有 PR、没有 code review、没有协作
- 红队对抗和机器门禁在替代 code review 的角色
- **后果**：提交粒度细（一条修复一个 commit）但缺乏外部视角；红队是唯一的"外部审查"机制

### 6.16 矛盾十六：基础安全好但核心工具静默失败多

- 基础安全做得好：0 处 shell=True、0 处 eval/exec、0 处 pickle、0 处 bare except、0 处 yaml.load（非 safe）
- 81 处 subprocess 调用全部是 list 形式（无注入风险），参数来自内部变量
- 但 17 处 except + pass/continue 静默失败，分布在 9 个工具中
- 核心工具最严重：atom_evidence_replay.py 有 3 处、compile_all.py 有 4 处、metrics_snapshot.py 有 3 处
- 大部分是 `except Exception`（太宽泛），不是具体异常类型
- **后果**：证据验证失败、编译错误、指标计算错误可能被静默吞没，门禁绿了不代表没问题

### 6.17 矛盾十七：规范文档严重过时（M4 差 30 条规则）

- M4_gate_engine.md 说 21 条规则，实际 51 条——差了 30 条（143% 增长）
- G6_status_levels.md 定义 5 种状态（draft/verified/machine_verified/human_verified/red_team_verified），但代码中只有 draft 和 verified 两种——状态机设计没完全落地
- tool_assumptions.md 只有 7 条假设（之前说 15 条）

### 6.18 矛盾十八：数据模型结构不一致（misconceptions 扁平 vs atoms 子目录）

### 6.19 矛盾十九：replay 性能瓶颈根因在编译（占 99.5%）

- 实测：单卡编译 -O0 平均 1.1s（冷启动 2.28s）、-O2 平均 0.525s

- **后果**：ccache 接入（编译时间降 90%）和增量 replay（只重跑变更卡）是最高优先级优化，YAML/IO 优化完全无用

### 6.20 矛盾二十：知识图谱极度稀疏（44% 孤立节点）

### 6.23 矛盾二十三：规则膨胀但大部分不生效（24% 命中率）
