# 302_证据卡三层分离瘦身架构调研_核心卡留痕外置修订史git化

> 2026-09-12 · 解决"颗粒度失控"：证据卡从 60 行膨胀到 100+ 行，维护成本接近教学价值
> 关联：tools/atom_evidence_replay.py · evidence/mem/EV-MEM-*.md（45 张，平均 66 行，最大 117 行）

---

## 一、问题定义

### 1.1 膨胀趋势

| 批次 | 卡编号 | 典型行数 | 新增内容 |
|---|---|---|---|
| 第一批 | EV-MEM-001..018 | ~50 行 | 基础结构（frontmatter + actual + verdict） |
| 第二批 | EV-MEM-019..031 | ~65 行 | + 双平台对照 + expected_sanitizer |
| 第三批 | EV-MEM-032..037 | ~75 行 | + 跨编译器断言 + limitations 字段 |
| 第四批 | EV-MEM-038..039 | ~110 行 | + 完整原始输出（7 轮逐样本）+ 修订记录 |
| 第五批 | EV-MEM-040..045 | ~90 行 | + 统一口径说明 + 活性对照 + 可复算推导 |

**趋势**：每批新增 10-20 行，且新增内容多为"留痕"而非"教学"。

### 1.2 膨胀的代价

1. **Writer 成本上升**：每张卡要写完整原始输出、双平台对照、修订记录——单卡从 30 分钟涨到 1 小时
2. **红队成本上升**：红队要读 100+ 行才能找到 claim 和证据，注意力被稀释
3. **replay 校验变慢**：actual 字段超长，run_match 逐行比对耗时
4. **教学价值下降**：核心结论被淹没在留痕细节中，读者找不到重点
5. **修改成本上升**：改一个数据要同步 actual/expected/hypothesis/修订记录 4 处

### 1.3 根因分析

证据卡承担了**三种不同性质的内容**，但都塞在一个文件里：

| 内容类型 | 性质 | 应该在哪 |
|---|---|---|
| 断言 + 校验锚（frontmatter） | 机器必需 | 核心卡（保留） |
| 教学结论（hypothesis/falsification） | 人读必需 | 核心卡（保留） |
| 完整原始输出（actual 超长字符串） | 留痕/可复算 | 外置 .out 文件 |
| 双平台对照/跨编译器留痕 | 留痕/可复算 | 外置 .out 文件或单独节 |
| 修订记录（v1→v2 改了什么） | 历史追溯 | git log（不需要卡内） |
| 教训注释（"这是 XX 教训的又一实例"） | 方法论沉淀 | 误解库或质检报告（不需要卡内） |

## 二、三层分离设计

### 2.1 第一层：核心卡（~50 行）

**保留**：机器校验必需 + 人读教学必需

```yaml
---
id: EV-MEM-040
serves: [ATOM-MEM-ALLOC-002]
kind: run
hypothesis: >-
  统一口径下三种分配策略的元数据排序：arena 32B < bitmap 181B ≪ pool 8056B（n=1000）。
controlled_vars: 同一夹具、同一请求大小、同一 workload；唯一变量=策略与规模
matrix:
  compiler: [GCC 15.3.0 (MinGW-w64), GCC 14.2.0 (WSL)]
  std: [c++23]
  opt: [-O2]
fixture: Examples/atoms/_atom_alloc_strategies.cpp
command: |
  g++ -std=c++23 -O2 -S ...
  g++ -std=c++23 -O2 ... && ./build/_replay_...
artifact: Examples/atoms/_atom_alloc_strategies.asm
artifact_sha256: 4f482fdc...
artifact_assert:
  - {kind: contains_any, texts: ["%s_meta_total_bytes="]}
actual:
  run_match_file: Examples/atoms/_atom_alloc_strategies.out  # 外置！
  run_match_keys: [arena_n1_meta_total_bytes, pool_n1_meta_total_bytes, bitmap_n1_meta_total_bytes]
verdict: confirm
falsification: >-
  真对照：若 pool 元数据只有"容器头"，bookkeeping 应接近 0——实测 8000B。
limitations: 统一口径前提；arena 零碎片前提是批量申请+整体释放
---
```

**关键变化**：
- `actual.run_final_O2`（超长字符串）→ `actual.run_match_file`（指向 .out 文件）+ `run_match_keys`（只列需要校验的 key）
- 删除 matrix 中的注释性留痕
- 删除 artifact_assert 中的教训注释
- 删除正文的"修订记录"节（靠 git log）

### 2.2 第二层：原始留痕（外置 .out 文件）

**位置**：`Examples/atoms/_atom_xxx.out`（与夹具同目录，已在 P4 中存在）

**内容**：
- 完整运行输出（stdout）
- 完整 stderr（含 sanitizer 输出）
- 编译命令行
- 双平台对照（Windows + Linux）
- 多轮原始样本（性能卡的 7 轮逐样本数据）

**replay 工具改动**：
- 读取 `actual.run_match_file` 指向的 .out 文件
- 从 .out 中提取 `run_match_keys` 列出的 key
- 与重跑输出比对（而不是与卡内字符串比对）

**好处**：
- 卡内不再有超长 actual 字符串
- .out 文件是纯文本，可直接 diff
- 双平台对照可以放在同一个 .out 里（用注释分隔）
- 性能卡的 7 轮逐样本数据不再占卡内空间

### 2.3 第三层：修订史（git log）

**删除卡内"修订记录"节**，改为依赖 git 历史。

**约定**：
- 每次修改证据卡必须在 commit message 中说明改了什么
- 重大修订（口径变化、方向反转）在 commit message 中用 `[REVISION]` 标记
- 卡内可以有一个 `revision_note` 字段（一句话），指向 commit hash

**示例**：
```yaml
revision_note: "v1→v2: 元数据口径统一（pool 32B→8056B），见 commit 4f482fd"
```

## 三、replay 工具适配

### 3.1 actual 字段的两种形态（向后兼容）

```yaml
# 旧形态（兼容）
actual:
  run_final_O2: "req_bytes=24|..."

# 新形态（推荐）
actual:
  run_match_file: Examples/atoms/_atom_xxx.out
  run_match_keys: [key1, key2, key3]
```

replay 工具：
- 如果 `actual.run_final_O2` 存在 → 旧形态（直接比对字符串）
- 如果 `actual.run_match_file` 存在 → 新形态（读 .out 文件，提取 key 比对）

### 3.2 run_match_keys 的语义

从 .out 文件中提取指定 key 的值，与重跑输出比对。

.out 文件格式（key=value 用 | 分隔，与当前运行输出一致）：
```
req_bytes=24|block_bytes=32|arena_n1_meta_total_bytes=32|...
```

replay 提取 `run_match_keys` 中列出的 key，检查：
1. key 在 .out 中存在
2. key 的值与重跑输出一致

**好处**：只校验关键指标，不校验整行输出（更鲁棒，不受行序/格式变化影响）。

### 3.3 渐进迁移

- 新卡用新形态（run_match_file + run_match_keys）
- 旧卡保持旧形态（run_final_O2），逐步迁移
- replay 工具同时支持两种形态

## 四、预期效果

### 4.1 卡行数变化

| 内容 | 当前 | 三层分离后 |
|---|---|---|
| frontmatter（含 actual 超长字符串） | ~45 行 | ~30 行（actual 缩为 2 行） |
| 正文（hypothesis/falsification/修订记录/教训） | ~40 行 | ~20 行（删修订记录和教训） |
| **合计** | **~85 行** | **~50 行** |

### 4.2 Writer 效率提升

- 不需要把完整运行输出粘贴进卡（直接用 .out 文件）
- 不需要写修订记录（commit message 即可）
- 不需要在卡内写教训注释（归入误解库或质检报告）
- **预计单卡写作时间从 1 小时降到 30 分钟**

### 4.3 红队效率提升

- 卡更短，红队可以更快找到核心 claim 和证据
- .out 文件是纯数据，红队可以直接 grep 验证
- **预计红队时间从 1.5 小时降到 1 小时**

### 4.4 教学价值提升

- 核心卡只保留教学必需内容，结论更突出
- 读者不需要在 100+ 行中找重点
- 原始数据可通过 .out 文件查阅（需要时）

## 五、风险与缓解

### 5.1 风险：.out 文件丢失或不同步

**问题**：如果 .out 文件被误删或与卡不同步，replay 会失败。

**缓解**：
- .out 文件与夹具同目录（Examples/atoms/），已在 git 中
- replay 工具检查 .out 文件存在性，缺失则 infra_error
- golden_lock 检查卡的 run_match_file 指向的文件存在

### 5.2 风险：run_match_keys 遗漏关键指标

**问题**：如果 Writer 只列了部分 key，可能漏掉重要的校验点。

**缓解**：
- gate 规则：run_match_keys 必须包含 hypothesis 中提到的所有数值
- 红队检查：run_match_keys 是否覆盖了 claim 的核心断言
- 可以用 `run_match_keys: all` 表示校验所有 key（向后兼容旧形态）

### 5.3 风险：旧卡迁移成本

**问题**：45 张旧卡需要迁移，工作量大。

**缓解**：
- 渐进迁移：新卡用新形态，旧卡保持旧形态
- replay 同时支持两种形态
- 可以写一个迁移脚本（自动把 actual.run_final_O2 拆成 .out + run_match_keys）
- 迁移不紧急，不阻塞新卡生产

### 5.4 风险：git log 不如卡内修订记录直观

**问题**：读者可能不知道卡有修订历史。

**缓解**：
- 卡内保留 `revision_note` 一句话（指向 commit hash）
- 重大修订在质检报告中记录
- git log --follow <卡文件> 可以查看完整历史

## 七、与其他系统的关系

### 7.1 与 replay 三分类（301）的关系

三层分离和三分类是互补的：
- 三分类解决"基础设施故障与内容证伪不分流"
- 三层分离解决"卡内容膨胀"
- 两者都在 replay 工具上改动，可以一起实现

### 7.2 与 Writer 预防机制的关系

Writer 阶段应该自检：
- .out 文件是否已生成？
- run_match_keys 是否覆盖了 claim 的核心断言？
- 卡是否超过 60 行？（超过则考虑外置）

### 7.3 与 golden_lock 的关系

golden_lock 可以增加统计：
- 卡平均行数（监控膨胀趋势）
- 使用新形态的卡比例（监控迁移进度）
