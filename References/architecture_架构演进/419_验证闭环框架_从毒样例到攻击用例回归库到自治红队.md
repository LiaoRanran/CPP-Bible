# 419 验证闭环框架：从毒样例到攻击用例回归库到自治红队

> 日期：2026-09-13。418 指出"落地缺验证闭环"，本文补齐——设计阙疑的质量保证金字塔，把三次对抗（368/373/402）的 64 个攻击用例固化成回归测试集，让"工具写了"自动升级为"工具真的拦住了"。

---

## 一、问题：当前验证的三层缺口

### 缺口 1：毒样例只验证"规则存在"，不验证"攻击被拦"

当前 47 条毒样例是"构造一个违反规则的卡，确认 gate block"。但这验证的是**规则能拦住它设计的那个违规**，不是**规则能拦住真实攻击**。

402 的 F02（编译后覆写）就是证明：EV-ARTIFACT-PRODUCER 有毒样例，但 F02 用 python 覆写绕过了——毒样例没覆盖这种攻击形态。

### 缺口 2：攻击用例没有固化，对抗完就丢了

368 发现 13 个逃逸、373 发现 13 个逃逸、402 发现 13 个逃逸。这些逃逸修复后，**攻击用例本身没有变成回归测试**。下次工具改动，可能重新引入同样的漏洞。

### 缺口 3：没有"拦截率"度量

402 报告了"针对性语义攻击拦截率 35%"，但这是一次性的人工统计。没有持续的、自动化的拦截率度量。规则数从 29→42 不代表质量提升——可能新规则都是拦低质量攻击的。

## 三、L3 攻击用例回归库设计

### 3.1 数据结构

每个攻击用例一个 YAML 文件，存在 `attacks/` 目录：

```yaml
# attacks/F02_compile_after_overwrite.yaml
id: F02
source: 402                          # 来自哪次对抗
attack_type: timing_chain            # 攻击类型分类（A1-A10）
severity: block                      # 严重度
description: 真编译行满足 producer 规则，随后 python 覆写工件
reproduction:
  fixture: |
    # 最小复现夹具（如果需要）
  command: "g++ -o artifact.asm fixture.cpp && python -c \"import shutil; shutil.copy('other.asm', 'artifact.asm')\""
  card: |
    # 最小复现卡的 frontmatter
    artifact: Examples/_atom_bypass.asm
    artifact_sha256: "<other.asm 的真实 sha>"
    artifact_producer: "g++ -o artifact.asm fixture.cpp"
expected:
  gate_block: true
  gate_rule: EV-ARTIFACT-PRODUCER    # 应该被哪条规则拦
  replay_result: refute              # replay 应该 refute
status: fixed                        # fixed / unfixed / partial
fixed_by: 414 P1-2                   # 哪次修复拦的
regression_priority: P0              # 回归优先级（P0 每次跑，P1 每日，P2 每周）
```

### 3.3 回归测试 runner

`tools/attack_regression.py`：

```python
def run_attack_regression(attack_ids=None, priority="P0"):
    """
    跑攻击用例回归库。
    - 对每个 status=unfixed 的用例：确认仍然被拦（如果没被拦 → 报新逃逸）
    - 对每个 status=fixed 的用例：确认仍然被拦（如果没被拦 → 报回归）
    - 输出拦截率 = 被拦住的用例数 / 总用例数
    """
    results = []
    for attack in load_attacks(priority=priority):
        # 1. 构造最小复现环境（临时目录）
        # 2. 跑 gate_engine.py 对该卡
        # 3. 跑 atom_evidence_replay.py 对该卡
        # 4. 比对 expected
        # 5. 记录结果
        results.append({
            "id": attack.id,
            "status": attack.status,
            "blocked": actual_blocked,
            "expected_block": attack.expected.gate_block,
            "match": actual_blocked == attack.expected.gate_block,
        })
    
    # 输出 JSON（四工具 --json 格式一致）
    return {
        "total": len(results),
        "blocked": sum(r["match"] for r in results),
        "interception_rate": blocked / total,
        "regressions": [r for r in results if r["status"]=="fixed" and not r["match"]],
        "new_escapes": [r for r in results if r["status"]=="unfixed" and not r["match"]],
    }
```

### 3.4 拦截率度量

```
拦截率 = 被拦住的攻击用例数 / 总攻击用例数

按攻击类型分解：
- A1 声明伪造：X%
- A2 工件借品：X%
- A3 断言恒真：X%
- ...（A1-A10 十类）

按严重度分解：
- block 级：X%
- warn 级：X%
```

**目标**：拦截率从 402 的 35% 提升到 ≥80%（P0 级攻击 ≥95%）。

## 四、L0 Writer 自检层（413 的极致形态）

413 设计了 7 项检查，但极致形态是**自检项从历史错误中自动提取**：

### 4.1 错误模式 → 自检规则的转化

每次红队发现 E1/E2 机械错误，自动转化为 Writer 自检项：

```yaml
# writer_checks.yaml（自动维护）
- id: WC-001
  source: 第五批 EV-MEM-040
  error_type: E1 工件不同代
  check: "卡的 artifact_sha256 == 重生成工件的 sha256"
  auto_fixable: false
  status: active

- id: WC-002
  source: 第五批 EV-MEM-040/041
  error_type: E2 断言字面量未实测
  check: "actual 中的每个标签在 Linux .asm 中 grep 得到"
  auto_fixable: false
  status: active
```

### 4.2 自检层的验证闭环

不是"7 项检查都实现了"，是：
```
用历史上真实犯过的 E1/E2 错误回放 → 自检能拦住 ≥80%
```

**验证数据集**：从第五批/第六批的红队报告中提取所有 E1/E2 错误，构造"错误卡"，跑自检，统计拦截率。

## 五、L4 自治红队（远期设计）

### 5.1 自动化红队流程

```
1. 每周自动触发
2. 随机选 3-5 颗原子 + 2-3 张证据卡
3. 两段式盲读（先读夹具/工件，再读卡）
4. 生成攻击用例（按 A1-A10 分类）
5. 实跑验证攻击是否成功
6. 成功的攻击 → 自动加入 attacks/ 库（status=unfixed）
7. 报告：新逃逸数 + 拦截率变化
```

### 5.2 攻击用例的自动修复建议

对每个 unfixed 攻击，自动生成修复候选：
```
攻击 F02（编译后覆写）
→ 根因：EV-ARTIFACT-PRODUCER 只检查编译行，不检查编译后时序
→ 修复候选：在 command 中，编译行之后禁止出现对 artifact 路径的写操作
→ 毒样例：P32（python 覆写）、P33（powershell 覆写）
```

**但修复不自动落地**——自治红队只发现+建议，修复交苦力或人审。

## 八、元结论

418 说"落地缺验证闭环"，419 补齐的方案是：

**不是"每个工具配毒样例"，是"把历史上所有攻击变成回归测试"。**

- 毒样例（L2）验证"规则能拦住设计的违规"
- 攻击用例库（L3）验证"规则能拦住真实攻击"
- 自治红队（L4）持续发现新攻击

三层的区别：
```
L2：我知道这个违规，造个样例验证规则能拦
L3：攻击者真的这么攻过，固化成回归测试
L4：自动发现攻击者还没发现的攻击
```

**最极致的验证闭环**：每次工具改动，自动跑 64+ 个历史攻击用例，输出拦截率。如果拦截率下降 → 阻断提交。这比"规则数增加"有意义得多——规则数可以灌水，拦截率不能。

**一句话**：阙疑的质量保证从"规则数"升级到"拦截率"——规则数是输入，拦截率才是输出。
