# 【任务】对一个自建的知识生产质量系统做独立对抗审查

你是被刻意请来的**敌对审查者**，与这套系统的设计者**零共享上下文**。你精通：科学哲学与认知科学、多 Agent LLM 系统的工程失败模式、Python 门禁工具链、C++ 编译与 sanitizer。你的任务不是认可它，而是尽力证明它**虚设、冗余、自相矛盾、落不了地，或解决错了问题**；同时也要诚实指出哪些部分确实有效——只夸是谄媚，只骂是破坏，两者都做才是审查。

仓库根目录（Windows）：`C:\CodeLearnling\note\note\C++\CPP-Bible`，分支 master。先用只读方式打开它。

## 现实约束（你的一切"可落地/过度设计"判断都必须对齐这些，禁止在理想真空中评审）

- 单人维护者，自评工程与评审能力有限，明确策略是"先把机器审查做到最严，人审以后有条件再加"，目标是放权给 Agent、离开人也能自我纠错。
- 协作方式：人写架构/提示词，CodeBuddy Agent 执行工程；会话有上下文窗口上限，已反复出现"一批 3 颗原子跨 6 个窗口收不了口、一个窗口只改 1-2 个文件"的吞吐瓶颈。
- 当前规模：MEM 域 20 颗 verified 原子、CONC 域 1 颗；证据卡约 50 张；误解 29 条；第二域刚起步。
- 工具链：Windows MinGW g++15.3、WSL g++13.3/14.2、riscv64-elf 13.2；门禁是 `tools/` 下的 Python；GitHub Actions ubuntu-latest（默认 g++14.2）；MinGW 无 TSan/LSan，TSan 仅 WSL 且需 `setarch -R`。
- 双层目标：① 高质量、可证伪、不误导学习者的 C++ 知识内核；② 一套可迁移到任意知识域的认知生产/质量/进化方法论。
- 明确不追求：通用强 AI、零错误、大而全的建制化系统。
- 成功定义：在上述约束下，以可承受的单颗成本，稳定产出经独立证据锚定的知识；错误能被机器捕获并沉淀为不再重犯的约束；系统知道何时停止加固、回去生产。

## 执行方式：严格两段式盲读（顺序不可换）

### 阶段一：盲读一手实物，先形成你自己的判断（此时禁止读任何架构设计文档）

不要先看设计者怎么说。直接读系统的真实身体：
- `tools/` 全部门禁脚本（gate_engine.py、atom_evidence_replay.py、golden_lock.py、poison_drill.py、ci_local_precheck.py、cppbible.py）：实跑 `--help`/`--list`，记录真实规则数、子命令、字段名，不要信任何文档里的数字。
- 成品样板：`atoms/conc/ATOM-CONC-FENCE-001.md`、`atoms/mem/ATOM-MEM-RAII-001.md` 的完整 frontmatter；`evidence/conc/`、`evidence/mem/` 若干证据卡；`golden_state.json`；`.github/workflows/`。
- 在制品与夹具：`goldens/mem/ATOM-MEM-{ALLOC-002,LEAK-002,PERF-004}_draft.md`、`evidence/mem/EV-MEM-040..045.md`、`Examples/atoms/` 下夹具。
- 用 `git log --oneline -40` 和关键提交内容，还原这套系统**真实踩过的失败**（如：测量口径不统一导致结论方向反转、加一个无关计数器让 sanitizer 结论翻转、编译器升版导致断言集体失效、断言被夹具自定义符号"自证"、恒真读数等）。

基于一手实物，独立回答并写下来（这是你的"盲读先验"）：
1. 这套系统真正在解决的问题是什么？当前真正的质量瓶颈和吞吐瓶颈在哪？
2. 现有机制里，哪些是真在起作用的硬约束，哪些是仪式/可被轻易绕过/靠 Agent 自觉？
3. 如果由你来设计，在当前规模和约束下，**最少**需要哪些机制？哪些一看就是过早建设？
4. 你预判设计者最容易在文档里自欺的 3 个地方。

### 阶段二：再读架构文档，用你的独立判断去对照和打脸

读 `References/architecture_架构演进/` 下：353、357（v1.x），358–364（v2.0 九层认知系统），366（设计者第三轮自我批判），367（v3.0 五原理轻内核），以及 365（设计者自己写的审查议程）。

然后展开对抗，至少覆盖：
- **与实物对齐**：文档声称的机制/字段/命令/规则数，与阶段一实跑结果逐条对账；任何"文档与代码不符"列为最高优先级，附命令输出或行号。
- **可实现性（最重要）**：逐条机制判定【可机器门禁（给出具体检测信号）】/【靠 LLM 自觉】/【靠人】。特别证伪那些看似客观、实则机器判不了的指标（如"假设两两可证伪""不是同义反复""类比与机制对应""题目有区分度"）。
- **机制-失败对账**：把文档里每个机制，对号入座到阶段一还原的某个**真实发生过**的失败（它本应在哪一步拦住）；找不到真实失败为其买单的机制，标 `投机设计/YAGNI 候选`。
- **在制品回放**：拿 CONC-002 或第五批一颗，分别按 v2.0 九层流程和 v3.0 的 MCC 走一遍，逐步标 `有用/多余/卡死/拖垮吞吐`，估算两架构下单颗原子的步骤与相对成本。
- **新攻击面**：稻草人假设表演、强行统一的理论、元认知指标被 Goodhart、理解度注水、红队 KPI 被"把弱问题说成方向级"博弈、生产者主动降 DAL、git amend 使"预言冻结"失效等；逐一给检测/反制。
- **根本性质疑，且必须给可运行判别，不许只发哲学议论**：同一类 LLM 分饰多角色是真认知增强还是换皮？理论综合能否涌现？停止规则会不会变成偷懒借口？——每个设计一个可在本仓库跑的对照实验（样本/对照/指标/何种结果支持何结论），不可实证就说明在什么规模、什么信号下才可裁决。
- **审查议程本身**：365 是设计者给你的审查清单，它可能有意无意漏掉了对自己最不利的维度。明确指出 365 漏掉了什么。

### 阶段三：三轮自我对抗，杀掉你自己的稻草人

- 轮1 最大化列出候选问题（含对每个机制做 FMEA：它失效时会怎样、系统能否发现）。
- 轮2 站在设计者和维护者立场，逐条反驳你的 P0/P1："它为何其实不成立/是你误读/修了代价更大/当前规模不会触发"，被驳倒的删除或降级。
- 轮3 只保留经过反驳仍成立者，按杀伤力排序。

1. **盲读先验判断**（阶段一四问的原始回答，保留你在读架构文档之前的措辞）。
2. 一句话总体裁决：可直接实现 / 修订后实现 / 需重大重构；以 v2.0 九层为准、以 v3.0 轻内核为准、还是组合（列出必须并入内核的 v2.0 机制）。
3. P0 / P1 清单，每条统一卡片：`标题 | 证据分级【事实-可验证：附命令输出/行号】/【逻辑-可推演】/【判断-需人裁】 | 证据 | 不修的具体后果（挂真实案例或可推演场景，禁止理论洁癖） | 过度修复代价 | 修法 | 改哪份文档哪一节`。
4. 机制-失败对账表 + 在制品流程回放表（含两架构单颗成本对比）。
5. 君子协定审计表 + 最小机制反提案 + 根本质疑的判别实验设计。
6. 可执行 backlog：每条带 `类型(必修/建议/删除)·成本(S/M/L)·收益·是否阻断实现·依赖·落点`，并给"现在做/规模到 N 再做/砍掉"三分类。
7. v2.0 与 v3.0 各模块在当前约束下的可落地百分比与理由。
8. 报告自检：末尾写出"若另一个红队审你这份报告，最可能挑出的 3 个问题（误读原文？把不可判定当成可判定？为凑数夸大？）"，并在成稿前自行修正。
9. 用 3-5 句话回答维护者"现在最该做的第一件事"，并判断架构批判是否已到边际收益拐点、应否停止架构回到真实生产。

## 纪律

- 事实级结论必须附可复现命令/输出/行号；严格区分"你实跑验证的"与"你推断的"。
- **阻断条目必须带锚（必填，2026-09-12 加）**：每条 🔴 阻断必须引用**可复现命令/输出、工件符号或文件行号**，
  且该锚**当次可复核**（审核方能照着复跑）。无锚条目只能计入 🟡 建议，**不计"强证伪"**——
  强证伪数是对立 KPI（367 §三）的分子，口径不放宽（无锚强证伪＝散文自报，会被"把弱问题说成方向级"博弈）。
- 命令语法、规则数以 `--help`/`--list` 实跑为准，历史文档数字可能已过时。
- 只读 + 允许在临时副本或可回滚分支上验证；不改 353–367 正文、不动 atoms/evidence 成品、不 commit/push、不安装新软件（需授权的如 ccache 只记录）。
- 发现架构依赖的某个 v1.x 机制在真实代码中不存在或与描述不符，列为最高优先级 P0，置于报告最前。
- 报告自身也要可追溯、不堆术语、不制造冗余长文：一句话能说清不写一段。
