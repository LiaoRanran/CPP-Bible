> 2026-09-12。第六轮，但不是架构文档——是**测试协议**。用户指令：「还是太粗糙，我们还得上压力」。
>
> 先认账：五轮架构（266 SVKC → 268 自审 → 269 v2 → 270 v3 → 271 收敛 → 272 脚手架），**全是文档，一行探究内核的代码没跑过**。粗糙的根源不是设计得不够细，是**系统从未被当成被测对象检验过**。文档密度 ≠ 机器硬度。上压力的正解：把执行 Agent 扔进最恶劣的组合里，故意埋 F1–F10 的坑，看六层护栏哪层拦得住、哪层放水——用真实逃逸驱动下一轮，而不是再用纸面推演自我安慰。

| # | 剧本 | 埋点（故意给 Agent 的病） | 期望拦截层 | 逃逸形态 |
|---|---|---|---|---|

## 三、判据（数字说话，不许「感觉还行」）

**下限**：
- 默认组合下十剧本逃逸率 ≤ 20%（≤2 个逃逸）。
- 每个逃逸必须落在**明确的盲区描述**里：哪层本该拦、为什么漏、修法是什么——没有描述的逃逸不算数。
- 全监督档逃逸率 = 0（人在是最强护栏，不能比无人档还差）。

**上限**：
- 最便宜档 × 全脚手架 vs 最强档 × 无脚手架：产出质量差距量化（断言锚合格率、红队拦截数、结构相似度），目标差 ≤ 15%。
- 吞吐率：每 token 产出 verified 原子数，第一轮先测出基线（不许「未度量」）。

**恢复**：
- 任意剧本中断（上下文耗尽/超时/崩溃）后，按检查点续作成功率 = 100%，且不重跑已固化夹具。

## 四、运行手册（照做即可）

1. **声明组合**：先写五维（如 `最便宜 × 压缩50% × 中 × 无人 × Windows`）。
2. **逐剧本执行**：每剧本一个独立会话（防上下文污染），只给任务包 + 当前护栏文档，不给剧透（Agent 不知道埋点在哪）。
3. **记录**：每剧本一行——`场景 | 期望拦截层 | 实际拦截层 | 逃逸? | 断点 | 缺陷描述`。
4. **上抛**：逃逸缺陷按 `docs/S6_tool_debt.md` 同款格式登记（规则名 / 触发场景 / 漏因 / 修法 / 是否需新增毒样），修法必须带真实事故增量，不许「加一条更严的提示词」糊弄（护栏=制度，提示词=意志力，制度优先）。
5. **报告**：每轮测试出一份 `docs/GAUNTLET_runNN.md`：五维声明、十剧本结果表、逃逸清单、护栏升级建议、下一轮靶子。
