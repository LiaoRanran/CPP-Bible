## 一、C++ 移动语义与 RVO：std::move 不移动

### 1.1 外部发现（证据等级：C++ 标准 + 一手教程，事实级）

- **std::move 不移动任何东西**——它只是 `static_cast<T&&>`，把左值转成右值引用（xvalue），让移动构造/赋值被选中。真正的移动发生在移动构造函数里（窃取资源）。
- **RVO（Return Value Optimization）**：返回匿名临时对象（prvalue），**C++17 后强制保证**（mandatory copy elision）——对象直接在调用者的返回槽构造，零拷贝零移动。
- **NRVO（Named Return Value Optimization）**：返回具名局部变量，是**可选优化**，依赖编译器实现，需所有返回路径返回同一变量。
- **return 中用 std::move 是常见反优化**——它把表达式变成 xvalue，禁用 RVO/NRVO。编译器在 NRVO 不适用时会自动隐式移动，不需要显式 std::move。
- **noexcept 移动构造是 STL 优化前提**——vector realloc 时，如果移动构造是 noexcept，用移动（O(1) 窃取）；否则用拷贝（O(n) 深拷贝，异常安全）。
- Rule of Five / Rule of Zero。

### 1.2 对阙疑的意义

阙疑目前没有专门的移动语义原子——MEM/PERF 域的知识空白。

**落地项 MV1（待验证假设，新原子选题）**：ATOM-MEM-MOVE-001「std::move 不移动 + return 中 move 禁用 RVO」——
- 夹具：`return local` vs `return std::move(local)` vs `return T(...)` 三种，对比 .asm 指令数 + 构造/析构/移动计数
- claim：std::move 是 cast 不是移动；return 中显式 move 禁用 RVO 反而降低性能
- 活性对照：构造/析构/移动计数器（和 ALLOC-002 的计数方法一致）

**落地项 MV2（立即可做）**：移动语义类原子的夹具模板——构造/析构/拷贝/移动计数器是标准活性对照，写入夹具方法论 v2.0（443）的"计数器模式"。

**证据**：C++17 [class.copy.elision] + cppcheatsheet/0xghost 一手教程，事实级。

## 二、虚函数与 RTTI：三层代价模型

### 2.1 外部发现（证据等级：Itanium ABI + CppCon benchmark，硬数据）

- **vtable**：每个类一张函数指针表，存在静态数据区（`.rodata`）；**vptr**：每个对象一个隐藏指针（8B），指向类的 vtable。
- **虚函数调用开销**：一次间接调用（vptr 解引用 → vtable 索引 → call），比普通函数慢几个周期；可能 **cache miss**（vtable 在冷数据区）、**branch target mispredict**、**不能内联**。
- **RTTI 布局**：vtable 的固定偏移位置（Itanium ABI：vtable[-1]）存放 `type_info` 指针。`typeid` 就是读这个指针。
- **dynamic_cast 代价**：运行时遍历继承图，**O(n)**（n=基类数）。Arthur O'Dwyer CppCon 2017 benchmark：`dynamic_cast<void*>` 973ns vs native 524ns；深/多继承更慢。
- **多重继承**：vtable 结构更复杂，有 **thunk**（调整 this 指针的跳板函数）。
- **-fno-rtti / -fno-exceptions**：禁用 RTTI/异常，减少代码体积（嵌入式常用）。

### 2.2 对阙疑的意义

阙疑目前没有专门的虚函数/RTTI 原子。

**落地项 VF1（待验证假设，新原子选题）**：ATOM-MEM-VTABLE-001「虚函数的三层代价」——
- 内存代价：vptr 每对象 8B + vtable 每类（对比无虚函数的对象大小）
- 性能代价：间接调用 + 不可内联（对比普通函数调用的 .asm）
- RTTI 代价：dynamic_cast O(n) 遍历（对比虚函数调用的耗时）
- 夹具：简单继承 vs 深继承 vs 多继承，三层代价分别量化

**落地项 VF2（立即可做）**：虚函数类原子的 .asm 分析要点——vtable 符号（`vtable for X`）、vptr 初始化（构造函数中 `mov [rdi], offset vtable`）、间接调用（`call [rax+offset]`）、thunk（`non-virtual thunk to X::f`）。写入夹具方法论的"asm 识别模式"。

**证据**：Itanium C++ ABI + Arthur O'Dwyer CppCon 2017 benchmark（973ns vs 524ns），一手。

## 三、Agent 任务规划 DAG 化：解决"上下文耗尽"的根因

### 3.1 外部发现（证据等级：一手论文 + 工业框架，硬数据）

- **层级任务网络（HTN）已成主流**：高层目标 → 子目标 DAG → 原子任务，而非线性步骤列表。
- **TDP（Task Decoupling Planning）**：Supervisor 角色做全局拆解，生成**带依赖关系的 DAG**，拒绝让单一大模型在超长上下文中做全链路推理。
- **Atomic Task Graph**（arXiv 2607.01942，2026-07）：统一规划执行框架——失败时定位到**失败原子节点**，回溯到其最低公共祖先（LCA），只重做失败子树。
- **局部重规划 vs 全局重规划**：子任务失败时，局部调整（从最后成功子目标继续）vs 全局重规划（从头来）。HTN 的核心价值是**局部重规划**——其余计划保持不变。
- **Microsoft CORPGEN**（arXiv 2602.14229，2026-02）：生产级层级规划实现，模拟企业数字员工。
- **MiRA**（arXiv 2603.19685）：里程碑式密集奖励信号，解决长程任务的稀疏奖励问题。

### 3.2 对阙疑的意义

**这是本轮最有价值的系统级发现**——直接解决阙疑反复出现的"本窗口上下文耗尽，批次中断"问题。

当前阙疑的批次生产是**线性的**（夹具→卡→红队→门禁→原子化），一个窗口耗尽就全停。DAG 化后：

**落地项 PLAN1（立即可做，零成本）**：批次生产任务 DAG 化——
```
claim(冻结) → 夹具 → 工件(.asm/.out) → 证据卡 → 红队 → 门禁 → 原子化
              ↘ 误解卡 ↗
```
每个节点有明确的输入/输出/验收标准。节点之间是文件依赖（夹具产出 .cpp，工件依赖 .cpp，卡依赖 .asm/.out）。

**落地项 PLAN2（立即可做）**：**检查点续作机制**——每个节点完成后写一个 `_checkpoint.json`（节点名、状态、产出文件、sha）。窗口耗尽后，下一窗口读 checkpoint，从最后完成节点继续，**不重做已完成节点**。这和 426 的不变量约束一致——已完成节点的产出文件 sha 不变就是不变量。
- 这直接解决"续作时不需要重跑夹具"的经验做法，把它制度化。

**落地项 PLAN3（立即可做）**：**失败精确定位**——当前"上下文耗尽"是粗粒度失败。DAG 化后，失败精确定位到节点（夹具编译失败？卡 replay refute？红队超时？），每个节点有独立的超时和重试策略。

**落地项 PLAN4（待验证假设）**：**并行化**——两颗独立原子的夹具/卡可以并行写（无依赖），红队可以并行跑。当前是串行的，DAG 化后可以识别独立子图并行执行。

**证据**：Atomic Task Graph / TDP / CORPGEN 一手论文 + HTN 主流框架，硬数据。

## 四、提示词压缩深化：从"五层压缩"到归因分析

### 4.1 外部发现（证据等级：一手论文 + 工业实践，硬数据）

- **ProCut**（arXiv 2508.02053，2025-08）：通过**归因分析**压缩提示词——把 prompt 分成语义单元，量化每个单元对任务性能的影响，剪枝低效用组件。生产环境**减少 78% token**，性能不降。
- **TokenPilot**（arXiv 2606.17016，2026-06）：双粒度上下文管理——全局稳定前缀 + 局部动态内容，解决"文本稀疏性 vs 缓存连续性"的权衡。
- **Acon**（arXiv 2510.00615）：用"全上下文成功但压缩后失败"的配对轨迹来**迭代优化压缩指南**——可蒸馏到小模型。
- **Shopify Gisting**（2026-09）：把长系统提示词压缩成学习到的 "gist" token，Sidekick GraphQL agent 从 ~6000 token 压缩。
- **LLMLingua-2**：用小 LM 做 token 分类，最高 20x 压缩。
- **Prompt caching**：稳定前缀（system prompt/工具定义/项目背景）放前面，变化内容（当前时间/临时路径/工具输出）放后面。
- **输出长度控制**："只输出 JSON""只输出 diff""只输出 5 条结论"——输出控制不是为了短，而是为了减少低信号输出。

### 4.2 对阙疑的意义

阙疑的提示词（312/365B/452）越来越长，407 提了五层压缩但还没深化。

**落地项 PC1（立即可做，高价值）**：对 452 红队提示词做 **ProCut 式归因分析**——
- 必要段（不可删）：门禁规则清单、两阶段盲读协议、逃逸登记格式、can't-miss 清单
- 低效用段（可删/压缩）：背景介绍（"阙疑是什么"）、重复的铁律（铁律在系统提示词里已有）、历史教训的冗长叙述（可以只给编号引用）
- 目标：压缩 30-50%，同时保持红队拦截率不变
- 验证方法：用压缩后的提示词跑一颗已知有阻断的原子（如 ALLOC-002 旧版），看红队是否还能抓到阻断

**落地项 PC2（立即可做）**：**稳定前缀/动态后缀分离**——提示词的固定部分（规则清单、格式要求、铁律）放前面，变化部分（当前批次的原子 ID、夹具路径、已知洞索引）放后面。利用 prompt caching 降低重复调用成本。

**落地项 PC3（立即可做）**：**输出长度控制**——红队报告要求"阻断+高级放正文，建议放附录"；工具调用要求"只输出 JSON"。减少输出 token = 减少成本 + 减少上下文消耗。

**证据**：ProCut 78% 压缩（一手论文）+ Shopify Gisting（工业实践）+ TokenPilot，硬数据。

## 五、STL 容器实现：增长因子与 cache locality

### 5.1 外部发现（证据等级：标准库实现 + 一手分析，事实级）

- **vector 增长因子**：libstdc++/libc++ 用 **2x**，MSVC 用 **1.5x**。
  - 2x 问题：旧内存**永不复用**（新容量 > 所有旧容量总和），平均利用率 ~50%，内存碎片高
  - 1.5x 优势：可以复用旧块（新容量 ≤ 旧容量总和），利用率 ~75%，碎片低
  - 黄金分割 1.618 是理论最优（利用率 61.8%）
- **push_back 摊销 O(1)**：N 次 push 的总 realloc 代价 O(N)，平均每次 O(1)。100 万次 push，2x 增长只需 ~20 次 realloc。
- **deque**：分段连续（map of blocks，通常 512B/块），随机访问 O(1) 但比 vector 慢（块索引计算），前后插入 O(1)。
- **unordered_map**：哈希表（bucket array + 链表），平均 O(1)，最坏 O(n)（哈希碰撞/病态哈希），内存开销大。
- **map/set**：红黑树，O(log n)，有序。
- **reserve()** 预分配可以避免 realloc，是性能优化关键。

### 5.2 对阙疑的意义

阙疑目前没有专门的 STL 容器原子——MEM/PERF 域的大空白。

**落地项 STL1（待验证假设，新原子选题）**：ATOM-MEM-VECTOR-001「vector 增长因子的空间-时间权衡」——
- 夹具：2x 模拟 vs 1.5x 模拟，对比内存峰值、realloc 次数、旧内存可复用性
- claim：2x 增长因子的平均利用率只有 ~50%，且旧内存永不复用；1.5x 利用率 ~75% 且可复用
- 和 ALLOC-002（分配器策略权衡）同族——都是"空间-时间-灵活性"三角

**落地项 STL2（待验证假设）**：ATOM-PERF-LOCALITY-001「vector vs list 的遍历性能」——
- 夹具：100 万元素，vector 连续遍历 vs list 指针遍历，对比耗时 + cache miss（可用 perf stat 或模拟）
- claim：连续内存的 cache locality 让 vector 遍历比 list 快 10x+（和 PERF-004 false sharing 同族，都是内存布局影响性能）

**证据**：libstdc++ 源码（增长因子 2）+ MSVC 实现（1.5）+ 42jerrykim 容器成本模型，事实级。

## 六、本轮元批判（按 453 标准）

### 真增量（改变做法）

1. **任务规划 DAG 化 + 检查点续作（PLAN1/2/3）**：直接解决"上下文耗尽导致批次中断"的根因。把线性流程变成 DAG，每个节点有 checkpoint，续作不重做。零成本（只是流程设计）。
2. **提示词归因分析（PC1）**：从"凭感觉压缩"升级为"量化每个段的效用"。ProCut 的 78% 压缩率是硬数据，阙疑的 452 提示词至少可以压缩 30%。
3. **移动语义/虚函数/STL 三个新原子选题（MV1/VF1/STL1/STL2）**：填补 MEM/PERF 域的知识空白，且都有成熟的夹具模式（计数器/asm 分析/增长模拟）。

### 换术语（已有实践获得学名）

- 检查点续作 → 阙疑已有"续作不重跑夹具"的经验做法，PLAN2 是把它制度化
- 提示词压缩 → 407 五层压缩已有框架，PC1 是加归因分析
- DAG 依赖 → 阙疑的 relations DAG（prerequisite/contrasts）是知识层的 DAG，PLAN1 是生产流程层的 DAG

### 明确不采纳/推迟

- Shopify Gisting（需要模型微调，阙疑无此能力）
- LLMLingua（需要小 LM 做 token 评分，当前环境无）
- CORPGEN 全量实现（过于复杂，当前先做 DAG + checkpoint）

### 证据越界警示

- ProCut 的 78% 压缩率是生产环境的通用 prompt，阙疑的红队提示词是高度特化的，压缩率可能不同——必须用 PC1 的验证方法（已知阻断原子）实测
- dynamic_cast 的 973ns benchmark 是 2017 年的硬件，当前硬件数字不同——但"dynamic_cast 比虚函数慢"的方向成立
- vector 2x vs 1.5x 的利用率是理论值，实际取决于分配器——需要阙疑自己实测
