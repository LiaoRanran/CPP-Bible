## 一、系统工程：V 模型与需求可追溯性

### 1.1 核心理论

**V 模型**：
- 左侧分解（top-down）：系统需求 → 子系统需求 → 组件需求
- 底部实现：build/code/fabricate
- 右侧集成验证（bottom-up）：组件测试 → 子系统测试 → 系统测试
- 每个需求链接到对应的验证活动

**需求可追溯性矩阵（RTM）**：
- 每个需求唯一标识
- Satisfaction links：详细需求 → 抽象需求
- Verification links：测试用例 → 需求
- Mitigation links：需求 → 缓解的风险
- 覆盖率可检测：没有验证用例的需求 = gap

**Verification vs Validation**：
- Verification = "build it right"（符合需求）
- Validation = "build the right thing"（满足用户真实需求）
- 验证方法：Test / Analysis / Inspection / Demonstration（T/A/I/D）

### 1.2 对「阙疑」的映射

**原子体系 = V 模型的微缩版**：

| V 模型阶段 | 「阙疑」对应 |
|---|---|
| 系统需求 | claim（原子的核心断言） |
| 子系统需求 | 夹具设计（如何验证 claim） |
| 组件需求 | 证据卡断言（具体检查点） |
| 实现 | 夹具代码 + 工件 |
| 组件测试 | replay（逐卡验证） |
| 子系统测试 | gate（规则检查） |
| 系统测试 | 红队审查（整体评估） |
| Validation | 人审/教学评估 |

**RTM 工具**：`tools/rtm_check.py`
- 自动检查每个 claim 是否有对应证据卡
- 检查证据卡的断言是否覆盖 claim 的全部范围
- 覆盖率报告：哪些 claim 部分未被证据覆盖

**Verification vs Validation 的失衡**：
- 我们目前偏重 Verification（replay/gate/红队）
- Validation 不足（原子真的教会了学生吗？）
- 需要补：教学效果评估（如学生测试、概念理解度）

## 二、安全工程：FMEA 与 FTA

### 2.1 核心理论

**FMEA（失效模式与影响分析）**：
- 自底向上：每个组件的失效模式 → 影响 → 严重度/发生度/探测度
- RPN（风险优先级数）= 严重度 × 发生度 × 探测度
- 优先处理高 RPN

**FTA（故障树分析）**：
- 自顶向下：从顶事件（不希望发生的事）到基本事件组合
- 逻辑门：AND（多个原因同时发生）、OR（任一原因发生）
- 最小割集：导致顶事件的最小组合

**ISO 26262**：
- 汽车功能安全标准
- ASIL A-D 等级（A 最低，D 最高）
- FMEDA：FMEA + 诊断覆盖率

### 2.2 对「阙疑」的映射

**FMEA 应用于红队**：

| 原子失效模式 | 严重度 | 发生度 | 探测度 | RPN |
|---|---|---|---|---|
| claim 被证伪 | 10 | 3 | 2（replay 能抓） | 60 |
| 证据不足（恒真断言） | 9 | 4 | 4（P4 能抓） | 144 |
| 与已有原子矛盾 | 8 | 2 | 5（先例检查能抓） | 80 |
| 口径不统一 | 7 | 3 | 6（新规则能抓） | 126 |
| 夹具被内联 | 6 | 2 | 3（工件检查能抓） | 36 |

- 高 RPN = 优先补检查项
- 这正是 P4-P7 规则的优先级排序依据

**FTA 应用于系统故障**：
```
顶事件：低质量原子被 verified
├── OR
│   ├── 红队漏拦
│   │   ├── AND：红队只读卡不读工件 + 卡自述掩盖问题
│   │   └── OR：红队上下文耗尽 / 红队被 Writer 误导
│   ├── gate 规则缺失
│   │   └── 新失效模式未被规则覆盖
│   └── replay 断言恒真
│       └── AND：夹具自定义函数 + 断言只做存在性匹配
└── 人审走过场
    └── 人审只看结论不看证据
```
- 最小割集：哪些组合最容易导致顶事件
- 防御：切断每个割集的至少一个环节

**与医学鉴别诊断的互补**（326）：
- 鉴别诊断 = 找问题（FMEA 的失效模式识别）
- FTA = 找根因组合（为什么问题漏过去了）
- 两者结合 = 完整的安全分析

## 三、知识管理：SECI 知识螺旋

### 3.1 核心理论

**SECI 模型**（Nonaka & Takeuchi, 1995）：
- **Socialization（社会化）**：隐性→隐性，通过共享经验（学徒制、观察模仿）
- **Externalization（外化）**：隐性→显性，通过表达（写文档、比喻）
- **Combination（组合）**：显性→显性，通过综合（整理知识库、分类）
- **Internalization（内化）**：显性→隐性，通过实践（做中学、练习）

**知识螺旋**：
- 不是循环，而是螺旋上升
- 从个人级 → 团队级 → 组织级
- 每轮螺旋产生更高层次的知识

**2024 新发展**：从 SECI 到 GRAI（生成式 AI 时代的知识管理）

### 3.2 对「阙疑」的映射

**「阙疑」的知识螺旋**：

| SECI 阶段 | 「阙疑」对应 | 例子 |
|---|---|---|
| Socialization | Agent 间经验共享 | 红队报告、教训库 |
| Externalization | 经验写成文档 | 架构调研 300-328、质检报告 |
| Combination | 整理成体系 | docs/kernel/、提示词模板、规则库 |
| Internalization | 通过实践内化 | 生产原子时自动应用教训 |

**隐性知识的价值**：
- Agent 的"直觉"（如"这个 claim 可能有问题"）是隐性知识
- 需要通过 Externalization 变成显性（写进红队报告）
- 再通过 Internalization 变成新的直觉（下一批自动应用）
- 目前的瓶颈：Externalization 不够系统（教训散落在各批次报告中）

**知识螺旋的层级**：
- 个人级：单个 Agent 的经验（上下文内）
- 团队级：多个 Agent 共享的教训库（docs/kernel/教训库.md）
- 组织级：整个「阙疑」系统的规范文档（G6_status_levels.md 等）
- 目标：让个人级经验快速上升到组织级

**落地**：`tools/knowledge_spiral.py`
- 自动从红队报告中提取教训（Externalization）
- 分类整理到教训库（Combination）
- 在下一批提示词中自动引用（Internalization）

## 四、决策科学：AHP 层次分析法

### 4.1 核心理论

**AHP（Analytic Hierarchy Process）**：
- 将决策问题分解为目标、准则、方案三层
- 成对比较矩阵：两两比较准则的相对重要性（Saaty 1-9 标度）
- 特征向量法：从比较矩阵计算权重
- 一致性比率（CR）：CR < 0.1 可接受

**多准则决策（MCDM）**：
- 在多个冲突准则下选择最优方案
- 准则有权重，方案有评分
- 加权求和 = 综合得分

### 4.2 对「阙疑」的映射

**原子优先级排序用 AHP**：

```
目标：选择下一批原子
├── 准则层
│   ├── 教学价值（权重 0.4）
│   ├── 证据可得性（权重 0.3）
│   ├── 与已有原子互补性（权重 0.2）
│   └── 实现难度（权重 0.1，反向）
└── 方案层
    ├── CONC-002（锁代价）
    ├── CONC-003（数据竞争）
    └── UB-002（未定义行为）
```

- 成对比较：教学价值 vs 证据可得性，哪个更重要？（1-9 标度）
- 计算权重，排序方案

**红队问题优先级用 AHP**：
- 准则：严重度、修复难度、影响范围
- 方案：红队发现的问题列表
- 高优先级先修

**一致性检查**：
- 如果 A > B 且 B > C，但 C > A，说明判断不一致
- 工具：`tools/ahp_check.py`，自动检查决策的一致性
- CR > 0.1 时要求重新判断

**与 DAL 分级的结合**（G6）：
- DAL A/B = 高严重度 → 强制人审
- DAL C/D/E = 低严重度 → 可机器豁免
- AHP 可以量化 DAL 分级的依据

## 五、精益生产：丰田生产系统

### 5.1 核心理论

**三大浪费**：
- **Muda（浪费）**：不增加价值的活动（七大浪费：运输、库存、动作、等待、过量生产、过度加工、缺陷）
- **Mura（不均衡）**：生产负荷波动
- **Muri（过载）**：超出能力的负荷

**两大支柱**：
- **准时化（JIT）**：只在必要时间生产必要数量
- **自働化（Jidoka）**：异常时自动停机，不把不良品流到下一道

**持续改进**：
- **Kaizen（改善）**：持续小改进，PDCA 循环
- **现场（Gemba）**：一切决策回到真实发生的地方
- **5 Whys**：根因分析，连续问 5 个为什么

### 5.2 对「阙疑」的映射

**三大浪费映射**：

| TPS 浪费 | 「阙疑」对应 | 例子 |
|---|---|---|
| Muda（浪费） | 证据卡中不服务于教学的冗余内容 | 颗粒度失控（200+ 行卡） |
| Mura（不均衡） | 批次间质量/数量波动 | 一批 4 颗 vs 一批 1 颗 |
| Muri（过载） | 单窗口上下文耗尽 | 第五批 6 个窗口未收口 |

**自働化（Jidoka）= 门禁系统**：
- "异常时自动停机" = gate block 时停止生产
- "不把不良品流到下一道" = 红队阻断时不进入原子化
- 这正是我们的三权分立体系！

**Kaizen（改善）= 每批教训总结**：
- PDCA 循环：
  - Plan = 提示词设计
  - Do = 原子生产
  - Check = 门禁验证
  - Act = 教训总结
- 每批结束后的教训总结 = Kaizen
- 小改进累积成大变革（P4-P7 规则就是 Kaizen 的产物）

**现场（Gemba）= 红队两段式盲读**：
- "回到真实发生的地方" = 看工件/夹具，不看卡的自述
- 这正是红队两段式盲读的理论基础！
- 第一段盲读 = Gemba  walk（去现场看真实情况）

**5 Whys = 红队根因分析**：
- 例子：ALLOC-002 口径不统一
  - 为什么？→ meta() 函数定义不同
  - 为什么？→ 没有统一口径规范
  - 为什么？→ 没有检查项
  - 为什么？→ P4-P7 没覆盖
  - 为什么？→ 规则设计时没考虑口径问题
- 根因：规则设计时缺乏"口径一致性"维度
- 修法：新增检查项 + 写入提示词

**库存隐喻**：
- TPS："库存像水位，淹没了水下的暗礁；把水位降下来，暗礁就暴露了"
- 「阙疑」："证据卡的冗余内容像水位，淹没了真正的问题；把卡瘦身，问题就暴露了"
- 这正是证据卡瘦身（315）的理论基础！

## 六、科学史：库恩范式转移

### 6.1 核心理论

**库恩的科学发展模型**（《科学革命的结构》, 1962）：
- **前范式期**：没有统一框架，各学派竞争
- **常规科学**：在现有范式内解决谜题（puzzle-solving）
- **异常**：无法用现有范式解释的观察
- **危机**：对范式解决问题的能力失去信心
- **革命**：范式转移，新范式取代旧范式
- **新常规科学**：在新范式内继续

**关键概念**：
- **范式（Paradigm）**：科学共同体共享的理论框架和实践
- **不可通约性（Incommensurability）**：竞争范式无法直接比较
- 科学进步是非线性的：不是知识的线性积累，而是周期性革命

### 6.2 对「阙疑」的映射

**「阙疑」的范式转移**：

| 阶段 | 「阙疑」对应 | 时间 |
|---|---|---|
| 前范式期 | G0-G3：原子 = 知识点 + 示例，无统一规范 | 早期 |
| 常规科学 | G4：原子 = 知识点 + 示例 + 简单验证 | 中期 |
| 异常 | 原子质量不可控、证据不可复现、红队抓出方向性错误 | 第五批 |
| 危机 | 用户对质量不满意，要求"极致自律" | 近期 |
| 革命 | G5-G6：原子 = claim + 证据卡 + 红队 + 门禁 + 四级状态 | 当前 |
| 新常规科学 | 在 G6 范式内生产原子（第六批、第七批...） | 下一步 |

**不可通约性**：
- 旧原子（Book 章节）与新原子（atoms/）无法直接比较
- 需要转换层（Book 与原子同步机制，309）
- 不能简单说"新原子比旧原子好"，而是"新范式解决了旧范式无法解决的问题"

**异常的价值**：
- 红队发现的"异常"（claim 与证据矛盾）是范式进步的动力
- 不要掩盖异常，要暴露它（这正是"如实报告"纪律）
- 每个异常都是潜在的规则改进机会（P4-P7 就是从异常中提炼的）

**下一次范式转移（G7？）**：
- 触发条件：G6 范式出现无法解决的异常
- 可能的异常：
  - 证据卡维护成本超过教学价值（颗粒度失控）
  - 红队与 Writer 的对抗导致创新不足（损失厌恶）
  - 机器审查达到极限，需要新的验证范式
- 不要急于 G7，先在 G6 内做好常规科学（生产更多原子）

## 九、一句话总结

328 把「阙疑」的理论支撑从三十学科扩展到**三十六学科**。最关键的三个新洞察：

1. **精益生产的自働化（Jidoka）= 我们的门禁系统**——"异常时自动停机，不把不良品流到下一道"正是 gate block + 红队阻断的理论基础。而"现场（Gemba）"正是红队两段式盲读（不看卡自述，去看工件/夹具）的理论基础。5 Whys 根因分析可以标准化为红队标配。

2. **安全工程的 FMEA/FTA 互补**——FMEA（自底向上找失效模式）= 红队找问题；FTA（自顶向下找根因组合）= 分析为什么问题漏过去了。两者结合 = 完整的安全分析。RPN（严重度×发生度×探测度）可以量化红队问题的优先级，指导检查项的补充顺序。

3. **知识管理的 SECI 螺旋**——「阙疑」的知识创造应该遵循 Socialization（Agent 间经验共享）→ Externalization（写成文档）→ Combination（整理成体系）→ Internalization（实践内化）的螺旋上升。目前的瓶颈是 Externalization 不够系统（教训散落在各批次报告中），需要工具自动提取和分类。
