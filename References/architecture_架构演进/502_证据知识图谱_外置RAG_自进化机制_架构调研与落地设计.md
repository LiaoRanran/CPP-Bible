## 一、证据知识图谱（Evidence Knowledge Graph）

### 1.1 业内先进实践

| 系统 | 核心机制 | 可借鉴点 |
|---|---|---|
| **GitNexus**（2026） | Tree-sitter AST 解析 + KuzuDB 图数据库，预计算依赖/调用链/执行流，MCP 接口暴露 | 预计算而非按需、零服务器、图数据库存储 |
| **Graphify**（2026） | 确定性知识图谱，Tree-sitter 解析 40 语言，边分类为 EXTRACTED（源码显式）/ INFERRED（逻辑推导） | 边的来源分类（显式 vs 推导） |
| **RANGER**（arXiv 2509.25257, 2025） | 仓库级 Agent，图增强检索，CONTAINS/HAS_METHOD/HAS_FIELD 边 | 层级关系建模 |
| **SemanticForge**（arXiv 2511.07584, 2025） | 静态-动态双知识图谱，自动调和，可证明收敛到真实程序依赖图 | 静态+动态双源 |
| **GitHub Copilot Chat**（2026.3） | repo-wide 知识图谱上下文，walk call graph 替代纯文件 embedding | 向量搜索 miss 的 bug，图谱能抓到 |

**关键洞察**：纯向量相似度搜索会 miss 3 类 bug（跨文件依赖、隐式调用、层级关系），知识图谱的结构化多跳推理能补上。这正是我们系统的痛点——`impact_analysis.py`（425 已建）只能做单层上游依赖遍历，没有多跳推理。

### 1.2 当前系统的差距

当前 28 颗原子 + 56 张证据卡 + 80 条误解的关系全部存在 YAML frontmatter 里：

```yaml
# atoms/mem/ATOM-MEM-RAII-001.md
relations:
  prerequisite: [ATOM-MEM-ALLOC-001]
  specializes: [ATOM-MEM-OWNERSHIP-001]
misconception: MIS-MEM-001
```

**问题**：
- 关系是扁平的字符串列表，无法做多跳查询（"A 依赖 B，B 依赖 C，那 A 间接依赖什么？"）
- 无法发现隐式矛盾（A 说 X，B 的 evidence 反驳 X，但 A 和 B 之间没有显式 contradicts 边）
- `impact_analysis.py` 只能做单层上游遍历，改一个夹具不知道影响多少层下游
- 没有"证据链"概念——一个原子的 claim 由哪些证据卡支撑、每张卡用了什么夹具/工件，无法一键追溯

### 1.3 知识图谱架构设计

```
┌──────────────────────────────────────────────────────┐
│              tools/knowledge_graph.py                  │
│                                                        │
│  ┌─────────────┐  ┌──────────────┐  ┌───────────────┐ │
│  │ 图构建器     │→│ SQLite 图存储 │→│ 查询引擎       │ │
│  │ (解析YAML)   │  │ (nodes+edges)│  │ (多跳遍历)    │ │
│  └─────────────┘  └──────────────┘  └───────────────┘ │
│                                            │           │
│  ┌─────────────────────────────────────────▼───────┐  │
│  │  CLI 接口                                       │  │
│  │  kg query "ATOM-MEM-RAII-001" --hops 3          │  │
│  │  kg impact "Examples/atoms/_atom_raii.cpp"      │  │
│  │  kg contradictions                               │  │
│  │  kg evidence-chain "ATOM-CONC-FENCE-001"         │  │
│  └─────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────┘
```

**节点类型**（6 类）：

| 类型 | 来源 | 属性 |
|---|---|---|
| ATOM | atoms/**/*.md | id, domain, type, status, dal, claim |
| EVIDENCE | evidence/**/*.md | id, verdict, fixture, artifact, serves |
| MISCONCEPTION | misconceptions/**/*.md | id, depth, refuted_by |
| FIXTURE | Examples/atoms/*.cpp | path, sha256, compiler |
| ARTIFACT | Examples/atoms/*.asm, *.out | path, sha256, version |
| RULE | gate_engine.py 规则注册表 | id, severity, domain, description |

**边类型**（10 类）：

| 边 | 源→目标 | 来源 |
|---|---|---|
| PREREQUISITE | ATOM→ATOM | relations.prerequisite |
| SPECIALIZES | ATOM→ATOM | relations.specializes |
| REALIZES | ATOM→ATOM | relations.realizes |
| EVOLVED_FROM | ATOM→ATOM | relations.evolved_from |
| CONTRADICTS | ATOM→ATOM | relations.contradicts（415 已加） |
| VERIFIES | EVIDENCE→ATOM | serves 字段 |
| USES_FIXTURE | EVIDENCE→FIXTURE | fixture 字段 |
| USES_ARTIFACT | EVIDENCE→ARTIFACT | artifact 字段 |
| REFUTED_BY | MISCONCEPTION→ATOM/EVIDENCE | refuted_by 字段 |
| BLOCKS | RULE→ATOM/EVIDENCE | gate --check 运行时命中 |

**存储**：SQLite（`data/knowledge_graph.db`），零外部依赖。两张表：
- `nodes(id, type, properties_json)`
- `edges(src, dst, type, source)` — source 标注 EXTRACTED（YAML 显式）或 INFERRED（逻辑推导，如改夹具的影响传播）

**核心查询**：

1. **依赖链**：`kg deps ATOM-MEM-RAII-001 --hops 3` → 返回所有前置依赖（多跳）
2. **影响面**：`kg impact Examples/atoms/_atom_raii.cpp` → 反向遍历 USES_FIXTURE→VERIFIES，返回所有受影响的证据卡和原子
3. **矛盾检测**：`kg contradictions` → 遍历 CONTRADICTS 边，找出自相矛盾或互相矛盾的原子对（415 的 ATOM-REL-CONFLICT 规则可以消费这个查询）
4. **证据链**：`kg evidence-chain ATOM-CONC-FENCE-001` → 从原子→证据卡→夹具→工件的完整追溯链
5. **孤立节点**：`kg orphans` → 找没有任何关系边的原子/证据卡（可能是遗漏）

### 1.4 落地路径

| 阶段 | 内容 | 工作量 |
|---|---|---|
| L1 | 图构建器（解析 YAML→SQLite）+ 5 个核心查询 CLI | 1 个苦力批次 |
| L2 | impact_analysis 迁移到图谱（替代单层遍历）+ 矛盾检测自动化 | 1 个苦力批次 |
| L3 | 隐式关系推导（INFERRED 边）+ 图谱可视化（HTML 交互图） | 好模型批次 |

## 二、外置 RAG 检索（Knowledge Retrieval）

### 2.1 业内先进实践

| 组件 | 方案 | 适用性 |
|---|---|---|
| **向量库** | Chroma（2025 Rust 重写，本地优先，零服务器）/ pgvector（PostgreSQL 扩展）/ Weaviate | Chroma 适合本地中小规模，零依赖 |
| **Embedding** | all-MiniLM-L6-v2（本地，384 维，快）/ text-embedding-3-large（API，1536 维，质量高） | 本地模型零成本，API 质量高但有费用 |
| **分块** | 按文档章节分块（# / ## 标题），chunk_size 512-1024，overlap 50-100 | 架构文档有清晰标题结构，按章节分块最准 |
| **检索** | top-k=5 + 元数据过滤（按类型/编号/日期） | 我们的文档有编号和类型，过滤很有效 |
| **RAG 模式** | LangChain DeepAgents：chunk-analyst 子 agent 并行分析每个分块 | 复杂查询可用，简单查询直接 top-k |

### 2.2 当前系统的差距

- 230+ 份架构文档（300-502）+ 56 张证据卡 + 28 颗原子，Agent 每次都要 `Read` 或 `Grep`，token 消耗巨大
- 没有全局检索：Agent 想知道"之前有没有研究过诊断引擎"，只能靠记忆或 Grep 关键词
- 文档之间的引用关系没有索引（501 引用了 499/500，但 Agent 不知道）

### 2.3 RAG 架构设计

```
┌──────────────────────────────────────────────────────┐
│              tools/knowledge_search.py                 │
│                                                        │
│  ┌──────────┐  ┌───────────┐  ┌────────────────────┐ │
│  │ 索引构建器 │→ │ Chroma DB │→ │ 检索引擎           │ │
│  │ (分块+embed)│  │ (本地)    │  │ (top-k + 元数据过滤)│ │
│  └──────────┘  └───────────┘  └─────────┬──────────┘ │
│                                          │            │
│  ┌───────────────────────────────────────▼──────────┐ │
│  │  CLI: python tools/knowledge_search.py "查询"     │ │
│  │  --type architecture|evidence|atom|all            │ │
│  │  --top-k 5                                        │ │
│  │  输出: [{title, path, snippet, score}]            │ │
│  └──────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────┘
```

**索引范围**（4 个 collection）：
1. `architecture`：References/architecture_架构演进/*.md（230+ 份）
2. `evidence`：evidence/**/*.md（56 张）
3. `atom`：atoms/**/*.md（28 颗）
4. `kernel`：docs/kernel/*.md（规范文档）

**分块策略**：
- 按 Markdown 标题（# / ##）分块，每块保留完整章节
- 元数据：doc_id（编号）、title、type、path、section（章节标题）
- 不按固定字符数硬切，避免把一个完整的设计切散

**检索策略**：
- 默认 top-5，按相似度排序
- 支持 `--type` 过滤（只搜架构文档 / 只搜证据卡）
- 支持 `--doc-id` 精确查找（如 `--doc-id 501`）
- 输出包含文件路径，Agent 可以直接 Read 原文验证（**RAG 结果不当事实用，必须标注来源**）

**Embedding 选择**：
- 首选本地 `all-MiniLM-L6-v2`（sentence-transformers，384 维，CPU 可跑，零 API 成本）
- 备选：如果本地模型质量不够，换 API embedding（但需要 key）
- 索引构建一次约 5-10 分钟（230 份文档），增量更新只处理修改过的文件

**与现有工具的集成**：
- Agent 提示词中加一条："不确定之前有没有研究过某方向时，先跑 `python tools/knowledge_search.py '关键词'`"
- `cppbible.py quality` 可调用 knowledge_search 检查新文档是否与已有文档重复

### 2.4 落地路径

| 阶段 | 内容 | 工作量 |
|---|---|---|
| L1 | 索引构建器 + Chroma + 检索 CLI（architecture collection） | 1 个苦力批次 |
| L2 | 4 个 collection 全量索引 + 增量更新 + Agent 提示词集成 | 1 个苦力批次 |
| L3 | 检索结果质量评估 + 查询重写（query expansion）+ 多轮对话检索 | 好模型批次 |

## 三、自进化机制（Self-Evolution）

### 3.1 业内先进实践

| 系统 | 核心机制 | 可借鉴点 |
|---|---|---|
| **Self-Harness**（上海 AI 实验室, 2026.6） | 三阶段循环：①弱点挖掘（运行任务→失败 trace→分类失败模式）②规则提案（proposer 角色生成最小化规则修改）③规则编辑（应用修改）。性能提升 60% | 三阶段循环、最小化修改、不需要重训练模型 |
| **Trace2Policy**（arXiv 2606.10457, 2026） | 从专家行为 trace 到自进化决策 Agent，EISR 错误驱动迭代技能精炼 | 错误驱动的迭代精炼 |
| **Google Reasoning Memory**（2026.9） | 从经验和错误中积累知识，泛化到新任务 | 经验积累+泛化 |
| **AutoRule** | 把推理 trace 和偏好反馈转成显式规则化训练奖励 | 反馈→规则的转换 |

**Self-Harness 的核心洞察**（最相关）：
- 不重训练模型，只改操作规则（harness）——这正是我们系统的形态（gate 规则就是 harness）
- "最小化修改"原则：每个规则修改只针对一个具体失败机制，避免过度泛化
- 失败 trace 是最有价值的训练数据——我们的变异测试/对抗测试就是在生成失败 trace

### 3.2 当前系统的差距

当前的规则进化是**纯手动**的：
1. 对抗/变异测试发现逃逸 → 2. 人分析逃逸根因 → 3. 人写新规则 → 4. 人写毒样例 → 5. 人跑门禁验证 → 6. 人合入

每一步都靠人，从发现逃逸到规则合入通常跨 2-3 个批次。

### 3.3 自进化架构设计

```
┌──────────────────────────────────────────────────────────┐
│              tools/rule_evolver.py（半自动化）              │
│                                                            │
│  阶段1: 逃逸收集                                           │
│  ┌─────────────┐  ┌──────────────┐  ┌─────────────────┐  │
│  │ 变异测试报告 │  │ 对抗测试报告 │  │ 门禁失败日志     │  │
│  └──────┬──────┘  └──────┬───────┘  └────────┬────────┘  │
│         └────────────────┼───────────────────┘            │
│                          ▼                                │
│  阶段2: 自动分类（零 LLM，机械）                            │
│  ┌──────────────────────────────────────────────────┐    │
│  │ 按逃逸模式分类:                                    │    │
│  │  - 断言问题(恒真/判别力不足/符号不可映射)          │    │
│  │  - 留痕问题(未声明键/陈旧/不存在)                  │    │
│  │  - 工件问题(版本不匹配/被篡改/不存在)              │    │
│  │  - 解析问题(YAML走私/重复键/编码)                  │    │
│  │  - 元数据问题(缺字段/ID冲突/状态非法)              │    │
│  └──────────────────────┬───────────────────────────┘    │
│                         ▼                                 │
│  阶段3: 规则候选生成（LLM，好模型）                         │
│  ┌──────────────────────────────────────────────────┐    │
│  │ 输入: 逃逸案例(含探针代码+gate输出+根因分类)       │    │
│  │ 输出: 规则候选(规则名/severity/判据伪代码/毒样例)  │    │
│  │ 约束: 参考现有规则结构、最小化修改、存量零误伤     │    │
│  └──────────────────────┬───────────────────────────┘    │
│                         ▼                                 │
│  阶段4: 自动验证（机械）                                   │
│  ┌──────────────────────────────────────────────────┐    │
│  │  - 存量56卡跑gate: 0新增block?                    │    │
│  │  - 毒样例正反例: 阳性block/阴性放行?               │    │
│  │  - pytest: 全绿?                                  │    │
│  │  → 全部通过: 标记"候选就绪，等人审合入"            │    │
│  │  → 任一失败: 标记"需修订"，附失败原因              │    │
│  └──────────────────────────────────────────────────┘    │
│                                                            │
│  阶段5: 人审合入（最终决策权在人）                           │
│  - 人审规则候选 → 合入或驳回 → 记录决策                    │
└──────────────────────────────────────────────────────────┘
```

**关键设计决策**：

1. **半自动化，不是全自动**：阶段 1/2/4 全机械，阶段 3 用 LLM 生成候选，阶段 5 必须人审。原因：规则是系统的免疫系统，自动合入有风险（可能误伤存量、可能被对抗利用）。
2. **逃逸案例是输入**：变异测试/对抗测试的报告（含探针代码、gate 输出、根因分类）是规则候选生成的唯一输入。不凭空生成规则。
3. **最小化修改**：每个规则候选只针对一个具体逃逸模式，参考 Self-Harness 的"diverse yet minimal modifications"原则。
4. **存量零误伤是硬门槛**：阶段 4 的自动验证不通过，候选直接淘汰，不进入人审。
5. **决策留痕**：每个人审决策（合入/驳回/修订）记录到 `data/rule_evolution.jsonl`，形成进化历史。

**与现有系统的集成**：
- 变异测试报告（499/500 的 mutation_test_*.md）→ 阶段 1 输入
- 对抗测试报告（_adv_v*/REPORT.md）→ 阶段 1 输入
- gate_engine.py 规则注册表 → 阶段 3 参考结构
- poison_drill.py → 阶段 4 毒样例验证
- 415 的 CONFLICT_REL 就是一次手动自进化的实例（从 F07 逃逸→分析→新规则→毒样例→验证）

### 3.4 落地路径

| 阶段 | 内容 | 工作量 |
|---|---|---|
| L1 | 逃逸收集器（解析变异/对抗报告→结构化 JSON）+ 自动分类器（机械） | 1 个苦力批次 |
| L2 | 规则候选生成器（LLM prompt 模板 + 输出格式约束）+ 自动验证器 | 1 个好模型批次 |
| L3 | 进化历史追踪 + 规则候选仪表盘 + 人审工作流 | 好模型批次 |

## 四、三者的协同关系

```
                    ┌─────────────────┐
                    │  变异/对抗测试   │
                    │  (生成逃逸案例)  │
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │   自进化机制     │
                    │ (逃逸→规则候选)  │
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │   知识图谱       │
                    │ (规则→命中→原子) │
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │   外置 RAG       │
                    │ (历史修复检索)   │
                    └─────────────────┘
```

- **变异/对抗测试**是输入源：持续生成逃逸案例
- **自进化机制**是引擎：把逃逸案例转成规则候选
- **知识图谱**是骨架：记录规则与原子/证据的关系，支持影响面分析
- **外置 RAG**是记忆：检索历史修复案例，辅助规则候选生成（RAG 历史修复）

四者形成闭环：测试→进化→图谱→检索→更好的测试。

## 五、优先级与依赖关系

| 优先级 | 项目 | 依赖 | 理由 |
|---|---|---|---|
