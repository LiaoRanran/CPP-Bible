# 310_CI加速架构调研_从串行1.5小时到并行20分钟

> 2026-09-12 · 当前 CI 6 job 串行依赖（quality→compile→site/pdf/epub→deploy），quality 正常 <5min 但全流程约 1.5 小时。
> 本文调研 CI 加速方案。
> 关联：.github/workflows/ci.yml（751 行）· ci_local_precheck.py（WSL 预检 31 步）

---

## 一、现状诊断

### 1.1 CI 结构

```
push/PR
  ↓
quality (ubuntu-latest, timeout 30min, 正常 <5min)
  ├─ Ruff
  ├─ Mypy
  ├─ Metrics
  ├─ Star/H2 Audit
  ├─ Gate Engine
  ├─ Evidence Replay (48 卡)
  ├─ Poison Drill
  ├─ Pytest
  ├─ Golden Lock
  ├─ Consistency
  ├─ Whitespace
  └─ ... (约 15 步)
  ↓
compile (needs quality)
  ├─ GCC-15 编译 Book 示例
  ├─ Clang-19 编译 Book 示例
  └─ ...
  ↓
site (needs [compile, publish-check])
pdf (needs [compile, publish-check])
epub (needs [compile, publish-check])
  ↓
deploy (needs [site, pdf, epub])
```

### 1.2 耗时瓶颈

| 阶段 | 估计耗时 | 瓶颈 |
|---|---|---|
| quality | ~5 min | Evidence Replay（48 卡编译+运行） |
| compile | ~20-30 min | GCC-15 + Clang-19 编译 Book 所有示例 |
| site/pdf/epub | ~15-20 min | 文档构建（mdbook/LaTeX） |
| deploy | ~2 min | 部署 |
| **总计** | **~45-60 min** | 串行依赖 |

### 1.3 已有优化

- ✅ concurrency 取消旧 run（同一 ref 多次 push 时）
- ✅ quality timeout 30min（防止挂死）
- ✅ fetch-depth: 0（增量门禁需要）

### 1.4 缺失的优化

- ❌ 无缓存（pip 包、编译器、构建产物每次重新下载/编译）
- ❌ 全串行（compile 等 quality，site/pdf/epub 等 compile）
- ❌ 无条件执行（每次 push 都跑全部 6 个 job）
- ❌ quality 内部串行（15 步顺序执行，可并行）
- ❌ 无路径过滤（改 README 也跑全量编译）

## 二、加速方案

### 2.1 方案一：quality 内部并行化（P0，预计省 3-5 min）

当前 quality 的 15 步是顺序执行。可以拆成并行子 job：

```
quality:
  strategy:
    matrix:
      group: [lint, metrics, gate, replay, tests]
  steps:
    - if matrix.group == lint: ruff + mypy
    - if matrix.group == metrics: gen_metrics + star/h2 + consistency + whitespace
    - if matrix.group == gate: gate_engine + golden_lock
    - if matrix.group == replay: evidence_replay + poison_drill
    - if matrix.group == tests: pytest
```

**效果**：quality 从 5 min → 2-3 min（最慢的一组决定总时间）。

**注意**：replay 和 gate 都需要完整的 atoms/evidence/，不能拆分数据。

### 2.2 方案二：compile 与 quality 并行（P0，预计省 5 min）

当前 compile `needs: quality`，但 compile 只需要 Book/ 示例代码，不需要 quality 的结果。

**修改**：compile 不依赖 quality，两者并行启动。

```yaml
compile:
  needs: []  # 不依赖 quality
  runs-on: ubuntu-latest
```

**风险**：如果 quality 失败，compile 已经在跑了——浪费 runner 时间。但 concurrency 取消旧 run 已经缓解了这个问题。

**缓解**：compile 可以 `needs: quality` 改为 `if: always()`，但 quality 失败时 compile 继续跑（不阻断）。或者用 `needs: quality` 但 quality 内部并行化后已经很快。

### 2.3 方案三：缓存（P1，预计省 3-5 min）

#### pip 缓存
```yaml
- uses: actions/cache@v4
  with:
    path: ~/.cache/pip
    key: pip-${{ runner.os }}-${{ hashFiles('**/requirements*.txt') }}
```

#### 编译器缓存
```yaml
- uses: actions/cache@v4
  with:
    path: ~/.ccache
    key: ccache-${{ runner.os }}-${{ github.sha }}
    restore-keys: ccache-${{ runner.os }}-
```

#### 构建产物缓存
site/pdf/epub 的构建产物可以缓存，只在 Book/ 变更时重新构建。

### 2.4 方案四：路径过滤（P1，预计省大量时间）

只在相关文件变更时运行特定 job：

```yaml
quality:
  if: |
    contains(github.event.head_commit.modified, 'tools/') ||
    contains(github.event.head_commit.modified, 'atoms/') ||
    contains(github.event.head_commit.modified, 'evidence/')

compile:
  if: |
    contains(github.event.head_commit.modified, 'Book/') ||
    contains(github.event.head_commit.modified, 'Examples/')

site:
  if: contains(github.event.head_commit.modified, 'Book/')
```

**效果**：只改 atoms/ 时，compile/site/pdf/epub 全部跳过，CI 从 1 小时 → 5 分钟。

**实现**：用 dorny/paths-filter 或 tj-actions/changed-files 检测变更路径。

### 2.5 方案五：拆分 quality 为独立 job（P2）

把 quality 的 15 步拆成 5 个独立 job，并行执行：

```
quality-lint: ruff + mypy
quality-metrics: gen_metrics + star/h2 + consistency
quality-gate: gate_engine + golden_lock
quality-replay: evidence_replay + poison_drill
quality-tests: pytest
```

**好处**：
- 真正并行（不是 matrix 内的 if）
- 每个 job 可以独立缓存
- 失败时只重跑失败的 job

**代价**：每个 job 都要 checkout + setup python，有固定开销（~30s/job × 5 = 2.5min）。

### 2.6 方案六：按需构建 site/pdf/epub（P2）

site/pdf/epub 只在 main 分支且 Book/ 变更时运行：

```yaml
site:
  if: github.ref == 'refs/heads/main' && needs.changes.outputs.book == 'true'
```

PR 阶段只跑 quality + compile，不构建文档。

## 三、推荐方案组合

### 3.1 第一阶段（P0，立即实施）

1. **quality 内部并行化**（matrix 5 组）：5 min → 2-3 min
2. **compile 与 quality 并行**：省 5 min（quality 跑的时候 compile 同时跑）
3. **pip 缓存**：省 1-2 min

**预计总耗时**：45-60 min → 30-40 min

### 3.2 第二阶段（P1，下周实施）

1. **路径过滤**：只改 atoms/ 时 CI 5 分钟，只改 Book/ 时跳过 quality-gate
2. **ccache 缓存**：compile 从 20-30 min → 10-15 min（增量编译）
3. **构建产物缓存**：site/pdf/epub 从 15-20 min → 5-10 min

**预计总耗时**：30-40 min → 15-25 min

### 3.3 第三阶段（P2，后续优化）

1. **拆分 quality 为独立 job**：更细粒度的并行
2. **按需构建 site/pdf/epub**：PR 阶段不构建文档
3. **Evidence Replay 增量**：只 replay 变更的证据卡（当前全量 48 张）

**预计总耗时**：15-25 min → 10-15 min

## 四、风险与缓解

| 风险 | 缓解 |
|---|---|
| 并行化后 quality 失败时 compile 已在跑 | 浪费有限，但 concurrency 取消旧 run 已缓解 |
| 缓存污染（旧缓存导致错误） | 缓存 key 包含 hashFiles，变更时自动失效 |
| 路径过滤漏检（改了工具但没触发 quality） | 路径规则要覆盖所有相关目录，保守起见 tools/ 变更触发全量 |
| matrix 并行的固定开销 | 5 组 × 30s = 2.5min，远小于并行节省的时间 |
| ccache 在 CI 上的效果不确定 | 先试点，测量实际加速比 |

## 五、与本地预检的关系

当前有 `ci_local_precheck.py`（WSL 31 步），是 CI quality 的本地复刻。CI 加速后：
- 本地预检仍然需要（push 前快速验证）
- 但本地预检可以也做增量（只检查变更的原子/卡）
- CI 加速后，本地预检的"提前暴露问题"价值降低，但仍有价值（不需要等 CI）

---

*核心结论：CI 当前 45-60 min 的主要瓶颈是串行依赖和无缓存。最有效的加速是"quality 内部并行化 + compile 与 quality 并行 + 路径过滤"——这三项可以把 CI 从 1 小时降到 15-20 分钟。路径过滤的价值最大：只改 atoms/ 时，compile/site/pdf/epub 全部跳过，CI 只需 5 分钟。实施顺序：先 P0（并行化+缓存），再 P1（路径过滤+ccache），最后 P2（细粒度拆分+按需构建）。*
