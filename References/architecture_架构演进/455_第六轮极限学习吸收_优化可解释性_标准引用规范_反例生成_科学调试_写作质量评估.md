## 一、编译器优化可解释性：从"展示优化"到"解释优化"

### 1.1 外部发现（证据等级：官方文档 + 一手教程，事实级）

- **Optimization Remarks**（GCC/Clang 官方支持）：`-Rpass=<name>`（优化被应用）、`-Rpass-missed=<name>`（优化没被应用及原因）、`-Rpass-analysis=<name>`（优化分析过程）。这是编译器内置的"优化日志"，直接告诉开发者每个 pass 做了什么、为什么没做。
- 典型优化 pass：DCE（死代码消除）、CSE（公共子表达式消除）、LICM（循环不变代码外提）、内联（inline）、循环展开（loop unroll）、自动向量化（vectorize）、GVN（全局值编号）。
- LTO（链接时优化）/PGO（剖面引导优化）是更高级的跨函数/运行时反馈优化。
- GCC 的 `-fopt-info-vec-missed` 等选项也提供类似信息。

### 1.2 对阙疑的意义

阙疑目前的优化类原子（PERF-003/004、CONC-001 等）只通过 .asm 对比展示"优化发生了"——学生看到的是"内联后少了 call 指令"，但不知道"编译器为什么决定内联"或"为什么这个函数没被内联"。

**落地项 O1（立即可做，零成本）**：优化类原子的夹具编译时加 optimization remarks，写入 .out：
```bash
g++ -O2 -Rpass=inline -Rpass-missed=inline -Rpass-analysis=inline ...
```
输出示例：
```
remark: _Z3foov inlined into main (cost=0, threshold=325)
remark: _Z4barv not inlined into main because cost 500 exceeds threshold 325
```
这直接回答"为什么内联/为什么不内联"，是 .asm 对比给不出的教学信息。

**落地项 O2（立即可做）**：证据卡 actual 增加 `optimization_remarks` 字段（可选，仅优化类原子），记录关键 pass 的应用/未应用及原因。这是"活性观测"的新形态——remarks 是编译器的运行时输出，不是编译期常量。

**证据**：GCC/Clang 官方文档，事实级。PERF-004 的"为什么 padding 影响性能"可以用 remarks 补充编译器视角。

## 二、C++ 标准引用规范：用 tag 而非节号

### 2.1 外部发现（证据等级：ISO 标准 + WG21 论文，一手）

- **N5032** 是 C++26 工作草案（2025），**ISO/IEC 14882:2024** 是 C++23 正式标准。
- 标准结构：1 Scope [intro.scope]、2 Normative references、3 Terms、4 General principles、5 Lexical conventions [lex]、... 每节有稳定的 **[section.tag]** 标签。
- 关键概念：C++ 定义的是 **"parameterized nondeterministic abstract machine"**（参数化非确定性抽象机）——标准不规定具体实现，只规定抽象机的可观测行为。
- **cppreference 是标准的通俗解释，不是标准本身**——前者是 informative（参考性），后者是 normative（规范性）。
- C++26 新特性：Reflection (P2996R11)、Expansion Statements (P1306R5)；Contracts 仍有争议（P3829 认为不该进语言）。

### 2.2 对阙疑的意义

INLINE-001 红队误判 IFNDR 条款号的根因：用了"16.2 子条"这种节号引用，但节号在标准版本间会变。

**落地项 C1（立即可做，零成本）**：原子卡引用标准时，**必须用 [section.tag] 格式**，如 [basic.indet]（未初始化值）、[expr.prim.lambda]（lambda）、[temp.inst]（模板实例化），而非"标准第 6.2.3 节"。tag 在版本间稳定，节号会变。

**落地项 C2（立即可做）**：标准引用必须区分 **normative（标准原文）** 和 **informative（cppreference/教程解释）**。卡内引用标准原文时标 [std:tag]，引用 cppreference 时标 [cppref:title]。两者证据等级不同——normative 是可证伪的（标准文本可查），informative 是解释性的（可能有误）。

**落地项 C3（待验证假设）**：新建 `tools/std_ref_check.py`，扫描所有原子卡的标准引用，检查：①是否用了 tag 格式 ②tag 是否在当前标准草案中存在 ③是否混淆了 normative/informative。这是铁律 10（无锚不入）在标准引用侧的具体化。

**证据**：ISO/IEC 14882:2024 结构 + WG21 N5032，一手。

## 三、程序合成与反例生成：从 claim 自动生成对照夹具

### 3.1 外部发现（证据等级：一手论文 + 工具）

- **PBT-Bench**（Jing et al. 2026-05）：基准测试 Agent 能否自己从代码中发现不变量（invariant discovery）——这是 PBT 的核心难点。
- **HARDTESTGEN**（CMU，2026）：LLM 生成高质量测试用例，47k 问题，专门针对"伪装的错误解法只能被精心设计的边界用例检测"。
- **CodeSpecBench**（arXiv 2604.12268）：可执行行为规格生成基准——从自然语言生成可执行的规格（assertions），而非仅测试用例。
- **rotalabs-verity**（PyPI 2026-09）：LLM + 形式化验证合成代码，返回 VERIFIED 或 COUNTEREXAMPLE（含具体反例输入）。
- **UnitTenX**（arXiv 2510.05441）：LLM + ESBMC 形式化验证生成遗留代码的单元测试，崩溃的测试自动注释 `// CRASH` 留痕。
- **"Use PBT to Bridge LLM Code Generation and Validation"**（arXiv 2506.18315）：Generator 生成插桩版本 C'，属性违反表现为运行时 AssertionError，用 PBT 输入找反例。

### 3.2 对阙疑的意义

阙疑的夹具生产目前是手工的——Writer 读 claim，手写实验组+对照组夹具。程序合成提供了自动化路径。

**落地项 P1（待验证假设，v8.0）**：从 claim 自动生成反例/对照夹具。claim 说"X 导致 Y"，自动生成：①不做 X 的对照夹具（验证 Y 不发生）②做 X 的实验夹具（验证 Y 发生）。这是 443 的 `single_variable_verification` 的自动化。
- 风险：自动生成的夹具可能不够教学友好（变量名无意义、结构不清晰），需要人审。
- 验证方法：选 1 颗已有原子，用 LLM 自动生成对照夹具，对比人工夹具的教学质量和判别力。

**落地项 P2（待验证假设，v8.0）**：PBT 生成随机输入测试夹具属性。比如 ALLOC-002 的活性对照"arena 元数据不随 n 变"——手工只测了 n=1000/8000 两点，PBT 可以测 n=1..10000 随机点，更有说服力。
- 风险：C++ 没有 Hypothesis 级别的 PBT 库（RapidCheck 存在但不成熟），需要手写随机测试框架。
- 先试点 1 颗原子。

**不采纳**：rotalabs-verity 式的全形式化验证——C++ 的形式化验证（ESBMC 等）对模板/异常/多态支持有限，阙疑的教学夹具用不到全形式化。反例生成（P1/P2）足够。

## 四、科学调试：红队流程的标准化

### 4.1 外部发现（证据等级：一手论文 + 社区 skill，硬数据）

- **Scientific Debugging**（科学调试六步）：Observe（收集证据）→ Hypothesis（一个清晰假设）→ Prediction（如果假设对，还应该有什么现象）→ Experiment（最小变更，一次一个变量）→ Verify（结果是否符合预测）→ Iterate or Conclude。
- **CogniGent**（arXiv 2601.12522，一手）：多 Agent 因果推理 + 调用图根因分析 + 假设测试，591 个 bug 报告上验证。
- **ADI**（arXiv 2604.24212，一手）：Agent-centric Debugging Interface，函数级交互 + Frame Lifetime Trace（封装函数执行轨迹的完整数据结构），SWE-bench 上验证效率提升。
- **"Mutation Testing via Iterative LLM-Driven Scientific Debugging"**（arXiv 2503.08182，一手）：突变体杀灭 + 科学调试循环，假设必须具体且可预测（"对输入 x，基线期望结果 a，突变体期望结果 b"）。
- **系统化调试四阶段**（社区 skill）：Evidence Collection → Pattern Analysis（找正常示例对照）→ Hypothesis & Testing（单一假设、最小变更）→ Implementation。
- 关键纪律：**先复现再修复**、**一次只改变一个变量**、**不在失败修复上叠加新修复**。

### 4.2 对阙疑的意义

阙疑的红队目前是"读代码→找问题→报告"，但没有标准化的调试流程。ALLOC-002 红队能抓出"口径不统一"是因为它做了对照实验（读三个 meta() 函数的实现），但这是自发的，不是流程要求。

**落地项 D1（立即可做，零成本）**：红队报告的每个发现必须包含**科学调试四元组**：
```
假设：[清晰、可证伪的陈述，如"Pool::meta() 漏算了 free-list 堆数组"]
预测：[如果假设对，还应该观察到什么，如"pool 实际元数据应 ≈ 8000+B 而非 32B"]
实验：[具体命令/代码变更，如"在 Pool 构造函数打印 free_list.size()*8"]
结论：[假设成立/不成立/部分成立，附实际输出]
```
没有四元组的发现标【推断级】，不直接采信（铁律 9 反 POR）。

**落地项 D2（立即可做）**：红队纪律新增三条——①先复现再下结论（不能只靠读代码推断）②一次只验证一个假设（不在验证 A 时顺手改 B）③实验必须是最小变更（改一行能验证的不改十行）。
- 这和 454 的突变体杀灭测试（D1）互补：突变测试是"改夹具看断言杀不杀"，科学调试是"改假设看实验证不证"。

**证据**：arXiv 2503.08182/2601.12522/2604.24212 一手论文 + 社区 systematic-debugging skill。

## 五、技术写作质量评估：从字段检查到内容质量

### 5.1 外部发现（证据等级：一手论文 + 行业标准）

- **可读性表面指标**：Flesch Reading Ease（50-70）、Flesch-Kincaid Grade（9-10）、Gunning Fog、SMOG、Coleman-Liau。但这些对技术文档不适用（术语多、句子长是正常的）。
- **DocAgent**（arXiv 2504.08725，一手）：多 Agent 自动生成代码文档，评估四维：Clarity/Conciseness、Descriptive Depth（解释 why）、Parameter Utility（不只是回显参数名）、Guidance（指导何时/如何用）。
- **LLM-Based Code Documentation Multi-Judge**（arXiv 2606.09852，一手）：九维评估——Completeness, Clarity, Coherence, Faithfulness, Hallucination Detection, Code Quality, Mermaid Quality, Relevance, Accuracy。
- **复合质量指标**（Stabilarity 2026）：surface readability + conceptual density + argumentative coherence + expert-judgment calibration，四维加权。
- **RAGAS faithfulness**：答案的每个 claim 必须能在检索上下文中找到出处——这和阙疑的铁律 10（无锚不入）同构。

### 5.2 对阙疑的意义

阙疑目前的质量检查全是**机器字段检查**（gate 37 条规则：frontmatter 字段、ID 格式、relations 存在性等），没有**内容质量评估**——一张卡可以字段全对但写得晦涩、冗余、或 claim 与证据不匹配。

**落地项 W1（立即可做，零新工具）**：证据卡的 **faithfulness 机器检查**——卡内 actual 段的每个断言标签（如 `arena_n1_meta_total_bytes=32`）必须能在 .out 中 grep 到。这是铁律 10 在证据卡侧的机器化，不是 LLM 评估，是确定性 grep。
- 注意：run_match 已经在做这件事（逐 key 比对），但只比对 actual 里声明的 key。W1 是反向检查：.out 里有的关键输出是否都进了 actual（防止"选择性报告"——只报好的不报坏的）。
- 实现：扫描 .out 的所有 `key=value` 行，检查 actual 是否覆盖了 ≥80%（排除环境量如 nproc）。

**落地项 W2（待验证假设，v8.0）**：LLM-as-judge 内容质量评估——用九维（Completeness/Clarity/Coherence/Faithfulness/Hallucination/CodeQuality/Relevance/Accuracy/TeachingValue）对每颗原子卡打分，作为人审的辅助。但这需要稳定的评估 prompt 和校准数据，当前 27 颗原子不够训练/校准。
- 风险：LLM-as-judge 本身有偏差（偏好长文本、偏好特定风格），需要多 judge 取中位数（Multi-Judge，arXiv 2606.09852 的方法）。
- 先试点：选 5 颗已 verified 原子，用 LLM 九维打分，看是否和人审评价一致。

**不采纳**：Flesch/Gunning Fog 等表面可读性指标——对 C++ 技术文档不适用，术语密度高是正常的，强行降可读性会损失精确性。

## 六、本轮元批判（按 453 标准）

### 真增量（改变做法）

1. **Optimization Remarks（O1/O2）**：从"展示优化"到"解释优化"，是教学质量的实质提升，零成本（加编译 flag）。PERF 类原子直接受益。
2. **标准引用 tag 化（C1/C2）**：直接解决 INLINE-001 红队误判的根因，零成本。
3. **科学调试四元组（D1/D2）**：红队从"我觉得有问题"升级为"假设-预测-实验-结论"，和 claim 契约化同构，零成本。
4. **Faithfulness 反向检查（W1）**：防止"选择性报告"，是 run_match 的补集，零新工具。

### 换术语（已有实践获得学名）

- 科学调试 → 阙疑红队已在自发做对照实验（ALLOC-002），只是没标准化
- Faithfulness → 铁律 10（无锚不入）的另一种表述
- PBT → 443 的 metamorphic_relation + 454 的 T2

### 明确不采纳/推迟

- 全形式化验证（rotalabs-verity/ESBMC）——C++ 形式化支持有限，教学夹具用不到
- 表面可读性指标（Flesch 等）——对技术文档不适用
- LLM-as-judge 九维评估（W2）——需要校准数据，v8.0 试点
- 自动反例生成（P1/P2）——需要验证教学质量，v8.0 试点

### 证据越界警示

- "HARDTESTGEN 47k 问题"是竞赛编程场景，不能直接平移到 C++ 教学夹具场景
- DocAgent/Multi-Judge 的评估维度是通用代码文档，阙疑需要加 TeachingValue 维度（教学价值是阙疑的核心目标，通用评估不覆盖）
