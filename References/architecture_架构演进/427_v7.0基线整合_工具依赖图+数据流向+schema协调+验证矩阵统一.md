# 427 v7.0 基线整合：工具依赖图 + 数据流向 + schema 协调 + 验证矩阵统一

### 1.3 投喂顺序（关键）

**不能并行投喂有依赖的工具**——417 依赖 414，425 依赖 417，424 的 P32/P33 验证依赖 414。

正确顺序：
```
第一批（并行，无依赖）：414 + 420 + 421 + 423
第二批（414 完成后）：417 + 424
第三批（417 完成后）：425
```

**426 时序约束框架是晚上好模型的活**，不占白天苦力配额。但 420/424 可以先用"手写检查"实现，等 426 落地后再重构为 InvariantChecker 调用。

## 三、schema 变更协调（避免冲突）

### 3.1 所有 schema 变更清单

| 变更 | 位置 | 类型 | 影响范围 |
|---|---|---|---|
| 417 | atoms/*.md frontmatter | relations 加 contradicts 类型 | 27 颗存量（加性，不强制） |
| 406 | atoms/*.md frontmatter | 新增 data_freshness 字段 | 27 颗存量（需批量补） |
| 424 | tests/poison/*.yaml | 新增 attack_type 字段 | 47→53 条毒样例（加性） |
| 420 | writer_checks.yaml | 新建文件 | 无存量影响 |
| 421 | data/cost/*.json | 新建目录 | 无存量影响 |
| 423 | data/flashcards/ | 新建目录 | 无存量影响 |

### 3.2 协调原则

1. **加性优先**：所有 schema 变更都是加性的（新增字段/类型），不修改现有字段语义
2. **存量迁移脚本化**：406 的 data_freshness 需要批量补 27 颗，必须写脚本，不能手改
3. **版本号同步**：schema 变更后，原子的 schema_version 字段（如果有）要递增
4. **gate 向后兼容**：新字段缺失时给 warn 不 block（存量过渡期）

### 3.3 406 freshness 字段的具体设计（待 428 细化）

```yaml
# atoms/*.md frontmatter 新增
data_freshness: deterministic | performance | tool_observation
# deterministic：sizeof、语法规则（极慢老化）
# performance：倍数、纳秒（编译器/硬件升级时重跑）
# tool_observation：LSan 报不报（sanitizer 升级时重跑）
```

存量 27 颗的标注规则：
- 含性能数据的卡 → performance
- 含 sanitizer 观测的卡 → tool_observation
- 其他 → deterministic

## 六、风险与缓解

### 风险 1：苦力并行投喂导致 schema 冲突

**场景**：417 在改 relations 解析，420 在写 writer_checks.yaml，两者都可能改 gate_engine.py 的 frontmatter 解析。

**缓解**：
- 417 只改 relations 相关代码（_relations_norm、DAG_REL）
- 420 不改 gate_engine.py（自检是独立工具）
- 424 只改 tests/poison/ 和 poison_drill.py
- 每个工具独立 commit，合并时如果冲突，先 Read 再改

### 风险 2：426 时序约束框架与 414 修复重复

**场景**：414 修 F02 时手写了时序检查，426 又做了通用框架，代码重复。

**缓解**：
- 414 先手写修 F02（快速止血）
- 426 晚上落地后，把 414 的手写检查重构为 InvariantChecker 调用
- 重构是纯代码整理，不改变行为，用毒样例验证不回归

### 风险 3：成本追踪数据不准

**场景**：字符数/3 的 token 估算误差大，CPVA 数据不可信。

**缓解**：
- 421 明确标注"估算值"，不精确
- 相对值有意义（阶段间比较、原子间比较）
- 后续如果能接 API，再换精确统计

### 风险 4：闪卡导出的"问题化表述"质量差

**场景**：自动把 claim 改成问题，可能不通顺。

**缓解**：
- 423 第一版用简单模板（"是否/为什么/多少"）
- 不追求完美，先导出，后续人工优化
- 闪卡是"辅助学习"不是"教材"，质量门槛低

## 七、元结论

**50 份调研的最终收敛 = 一个协调的系统，不是一堆独立工具。**

7 个工具 + 2 个架构原则的关系：
- 426 是基础设施（所有新规则的设计范式）
- 414 是紧急修复（CI 硬门禁失效）
- 417/424 是规则扩展（矛盾检测 + 毒样例覆盖）
- 420 是前置拦截（E1/E2 不进红队）
- 421/423 是输出（成本可观测 + 知识被消费）
- 425 是知识推理（relations 变基础设施）

**最关键的协调点**：relations 字段被 4 个工具消费（417/425/gate/闪卡），所以 417 的 schema 扩展必须加性、向后兼容——这是整个系统的"关节"，不能断。

**一句话**：v7.0 基线不是"7 个工具都写完"，是"7 个工具协调运行、数据流通畅、验证矩阵统一"。

累计 51 份（374-427）。
