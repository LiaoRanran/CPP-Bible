# 378 平台化与专用脚手架：从搜集到应用

> 日期：2026-09-13。监工完成，记录用户提出的"Qt等应用搭建究极高效脚手架"的发散想法，作为长期方向。
> 当前决策：先优化系统+加强调研内卷，引擎成熟稳定后再启动平台化，且底层依旧能独立优化。
> 流程：搜集 → 整理 → 挖掘 → 联系 → 批判 → 结合 → 应用。

## 一、想法来源与本质

用户发散："后期有无可能我们自己用Qt等应用搭建究极高效的脚手架给Agent用，不仅优化交互，节约token，还能外置自动化减少多余步骤？"

**本质**：把现在散落在文件系统+命令行+自然语言对话里的Agent工作流，固化成**结构化接口+可视化外壳+内置自动化**的专用工作台。Agent 不再"写命令然后解析文本输出"，而是调用结构化 API 直接拿到结果。

当前 Agent 的工作方式：自然语言 → 写命令行 → 解析文本输出 → 再写命令行。每一步烧 token、每一步可能解析错、每一步重复劳动。

## 二、价值挖掘（能榨干什么）

### A. Token 节约（最直接，估 40-60%）

| 现在 | 脚手架后 |
|---|---|
| 写 `python tools/gate_engine.py --check` 然后读 200 行文本 | 调用 `gate.check()` 返回 20 行结构化 JSON |
| 手动写记忆文件（2026-09-12.md） | 应用层自动 checkpoint，Agent 只填关键字段 |
| 读整个证据卡（200+行）找 sha | UI 侧栏直接显示 sha/verdict/门禁状态 |
| 解析 replay 的 confirm/refute 文本 | 结构化返回，直接知道哪张卡哪个断言失败 |

### B. 外置自动化（376 的设计直接变成应用层功能）

- Checkpoint/Resume：应用层自动保存状态，Agent 崩了新会话直接恢复
- 模型路由：应用层按任务类型自动选模型（S/A/B级），Agent 不关心额度
- 上下文管理：应用层主动压缩低优先级内容
- 门禁联动：文件保存后自动跑 gate/replay，结果实时显示

### C. 交互优化（人也受益）

- 原子/证据卡的 relations DAG 可视化，跨原子矛盾直接高亮
- 门禁结果结构化展示（哪些规则命中、哪些卡 refute、哪个断言失败）
- 批次进度看板（每颗原子到哪一步，阻塞项红色高亮）
- 额度/上下文实时监控

### D. 减少多余步骤

- 现在：写卡 → 手动跑 replay → 看文本 → 改卡 → 再跑 → 循环
- 脚手架：写卡 → 保存即自动跑 → 失败断言直接高亮 → 改那一行 → 自动重跑
- 红队两段式盲读：应用层自动"只给夹具+工件，不给卡"，不需要手动管理文件可见性

## 三、和现有系统的关系（关键：不是替代，是加一层）

现有的 `tools/`（gate_engine.py、replay.py、poison_drill.py 等）是**核心引擎**，Qt/Web/TUI 应用是**外壳+编排层+API层**。

```
┌─────────────────────────────────┐
│   Qt/Web/TUI 外壳（可视化+自动化）  │  ← Phase 1-3，未来
├─────────────────────────────────┤
│   结构化 API 层（函数封装）         │  ← Phase 0，现在就能做
├─────────────────────────────────┤
│   核心引擎 tools/（gate/replay/…） │  ← 已完成，持续迭代
└─────────────────────────────────┘
```

**引擎继续独立迭代，外壳只做结构化和自动化。** 这是"底层依旧能优化"的架构保证。

## 四、批判（约束与风险）

### 1. 时机约束（最重要）
现在工具层每周都在加规则、改接口（374 语义自律要加新规则、375 要加证据缺口扫描、接口频繁变）。**过早固化 UI 会成为负担**——每次改引擎都要同步改 UI，拖慢迭代。
- 启动条件：语义自律（374）落地、规则数稳定在 40+、核心接口（gate/replay/poison）不再频繁变更。
- 当前判断：至少还需要 2-3 批原子生产+工具迭代，引擎才相对稳定。

### 2. Agent-应用通信协议
需要设计：本地 HTTP API？socket？文件监控？而且要兼容 CodeBuddy/TRAE/不同 IDE 内的 Agent。
- 最稳妥：本地 HTTP API（`localhost:PORT`），任何 Agent 都能调用，不依赖特定 IDE。
- 备选：文件监控（Agent 写请求文件，应用读后写响应文件），零依赖但慢。

### 3. 维护成本
UI 层+工具层双层维护。UI 不能拖慢工具迭代——**引擎接口必须稳定，UI 只依赖稳定接口，不依赖内部实现**。

### 4. Qt 的选择
Qt 强在跨平台桌面体验，但开发成本高（C++/Python+Qt）。如果主要在 Windows+WSL，**Web 应用可能更灵活**（FastAPI+前端，Agent 通过 HTTP API 交互，人通过浏览器看），而且天然支持远程访问。
- Qt 是终局（深度集成、原生体验），不是起点。

### 5. 过度工程化风险
如果工具层的问题还没解决（比如语义自律还没落地），做 UI 只是把问题包装得更好看，没有解决本质。**先把引擎做对，再把外壳做好看。**

## 五、分阶段落地路径

### Phase 0（现在就能做，零成本，不依赖引擎稳定）
**函数封装层**：把常用命令封装成 Python 函数，提供结构化返回值。
- `gate.check() -> {block, warn, advice, details: [...]}`
- `replay.run(card_id=None) -> {confirm, refute, infra_error, details}`
- `poison.run() -> {passed, failed, details}`
- `golden.status() -> {atoms, evidence, replay_confirm, ...}`
- Agent 直接 import 调用，不写命令行，不解析文本。
- 这一步已经能省 ~30% token，而且为后续 UI 层打下接口基础。

### Phase 1（引擎相对稳定后，1-2周）
**TUI（终端UI）**：用 Python 的 `textual` 或 `rich`。
- 左侧：任务面板（当前批次、待办、阻塞项）
- 中间：文件编辑器+预览
- 右侧：实时门禁结果（结构化展示）
- 底部：模型选择+额度监控+上下文用量
- 不需要 Qt，跨平台，开发快。验证"结构化接口+可视化"的价值。

### Phase 2（中期，1-2月，引擎稳定后）
**Web 应用**：FastAPI+前端，Agent 通过 HTTP API 交互。
- 内置 checkpoint/模型路由/上下文管理（376 的设计变成应用层功能）
- relations DAG 可视化、跨原子矛盾高亮
- 批次进度看板、额度/上下文实时监控
- 人通过浏览器监督，Agent 通过 API 操作

### Phase 3（长期，究极形态）
**Qt 桌面应用**：深度集成，本地 socket 与 Agent 通信，原生体验。
- 内置自动化（门禁联动、红队盲读管理、模型路由）
- 高性能渲染（大规模原子关系图、实时日志）
- 离线可用，不依赖浏览器

## 六、"底层依旧能优化"的设计原则

这是用户明确要求的，必须作为架构铁律：

1. **引擎和外壳严格分离**：外壳只通过稳定 API 调用引擎，不依赖引擎内部实现。引擎可以随时重构，只要 API 不变。
2. **API 版本化**：`/api/v1/gate/check`，引擎迭代时可以加 v2，旧版保留，外壳逐步迁移。
3. **引擎可独立运行**：没有外壳，`tools/` 仍然能完整工作（命令行调用）。外壳是增强，不是依赖。
4. **外壳可替换**：TUI → Web → Qt，每个阶段的外壳都可以替换，引擎不受影响。
5. **自动化在外壳，规则在引擎**：checkpoint/模型路由/上下文管理在外壳层，gate/replay/poison 的规则在引擎层。两层职责清晰。

## 八、当前决策与后续

**当前优先级**：
1. 继续系统优化（374 语义自律落地、375 证据智能、376 立即项）
2. 继续调研内卷（认知智能、元认知、更多方向）
3. 引擎稳定后（语义自律落地+规则数稳定），启动 Phase 0（函数封装）
4. Phase 0 验证价值后，再考虑 Phase 1（TUI）

**不做的事**：
- 现在不做 Qt/Web/TUI 任何 UI 层开发
- 现在不重构 tools/ 为 API 优先（保持命令行可用，Phase 0 只是加封装层）
- 不因为"将来要做平台化"而限制引擎层的快速迭代

**启动信号**（满足全部才启动 Phase 0）：
- [ ] 374 语义自律三条规则落地并经过对抗测试
- [ ] gate 规则数稳定（连续 2 批没有新增规则）
- [ ] gate/replay/poison 的核心接口连续 1 个月没有破坏性变更
- [ ] 376 的标准化记忆文件格式已经跑通 2 批以上

## 九、局限与后续

- 本文是方向记录，不是详细设计。Phase 0 启动时需要写详细的 API 设计文档。
- Agent-应用通信协议（HTTP vs socket vs 文件监控）需要在 Phase 0 前做技术选型。
- 跨平台（Windows+WSL）的文件系统访问问题需要解决（WSL 侧的文件如何被 Windows 侧 UI 监控）。
- 多 Agent 并发（建设者+红队+监工同时操作）的状态同步问题，需要在 Phase 2 解决。
- 本方向长期跟踪，每次引擎层有重大变更时更新本文的"启动信号"检查清单。
