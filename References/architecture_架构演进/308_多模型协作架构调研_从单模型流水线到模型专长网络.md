# 308_多模型协作架构调研_从单模型流水线到模型专长网络

> 2026-09-12 · 用户目标："极致强悍睿智有创造力系统驱使各种大模型成为超强智能级别"。
> 当前系统是单模型 + 工具链，本文调研如何让不同模型各司其职，形成协作网络。
> 关联：G5 流水线（Writer/RedTeamer/Gatekeeper）· G6 四级状态体系 · 阙疑架构

---

## 一、为什么需要多模型协作

### 1.1 单模型的局限

当前系统（豆包/CodeBuddy）是单模型流水线：
- Writer、RedTeamer、Gatekeeper 都是同一个模型
- 模型的特长是固定的（创意强则逻辑弱，逻辑强则创意弱）
- 所有任务都用同一个"大脑"，没有分工

**单模型的瓶颈**：
1. **创意与严谨不可兼得**：同一个模型写 claim 时创意不足，做红队时严谨不够
2. **上下文窗口限制**：长任务（第五批 6+ 窗口）导致上下文耗尽，需要压缩摘要
3. **错误模式固定**：同一个模型会反复犯同类错误（如"断言未在 Linux 工件实测"出现了两次）
4. **无法交叉验证**：Writer 和 RedTeamer 是同一个模型，红队的"独立视角"不够独立

### 1.2 不同模型的特长差异

| 模型类型 | 特长 | 适合的角色 | 弱点 |
|---|---|---|---|
| 创意型（GPT-4o/Claude Opus） | 发散思维、写作、类比 | Writer（选题/claim 写作） | 事实错误、过度概括 |
| 推理型（O1/DeepSeek-R1） | 逻辑推理、数学、证明 | RedTeamer（形式验证/反例构造） | 慢、贵、创意不足 |
| 代码型（Claude Sonnet/GPT-4o） | 代码生成、调试 | 夹具编写/工具开发 | 架构设计弱 |
| 搜索型（Perplexity/Gemini） | 事实检索、最新信息 | 调研（资料收集） | 深度分析弱 |
| 严谨型（O1/GPT-4o） | 审查、校验、合规 | Gatekeeper（门禁执行） | 创意不足 |
| 小模型（Haiku/Llama） | 快速、便宜 | 机械任务（格式检查/批量处理） | 复杂任务能力弱 |

**核心洞察**：没有一个模型在所有维度都最强。多模型协作的目标是"让每个模型做它最擅长的事"。

## 二、多模型协作架构设计

### 2.1 角色-模型映射

| 流水线角色 | 首选模型类型 | 备选 | 理由 |
|---|---|---|---|
| Writer（选题/claim） | 创意型 | 推理型 | 需要发散思维和教学直觉 |
| Writer（夹具/代码） | 代码型 | 创意型 | 需要可编译的 C++ 代码 |
| RedTeamer | 推理型 | 严谨型 | 需要逻辑推理和反例构造 |
| Gatekeeper | 严谨型 | 小模型 | 机械执行规则，不需要创意 |
| 调研 Agent | 搜索型 | 创意型 | 需要广泛检索和资料整理 |
| 架构师 | 推理型 + 创意型 | — | 需要全局视野和系统设计 |
| 工具开发 | 代码型 | 严谨型 | 需要 Python 工具开发 |

### 2.2 调度层（Model Router）

**核心组件**：一个"模型调度器"，根据任务类型和当前状态选择最合适的模型。

**调度策略**：
1. **规则调度**：根据任务类型硬编码模型选择（如 RedTeamer → 推理型）
2. **质量反馈调度**：根据历史表现调整（如某模型做红队的阻断证实率高 → 优先用它）
3. **成本调度**：在质量达标的前提下，优先用便宜/快的模型
4. **降级调度**：首选模型不可用时，自动降级到备选模型

**调度接口**：
```python
class ModelRouter:
    def route(self, task_type: str, context: dict) -> Model:
        """根据任务类型和上下文选择模型"""
        # 1. 查规则表（task_type -> preferred_model）
        # 2. 查质量反馈（该模型在同类任务的历史表现）
        # 3. 查成本预算（当前批次的 token 预算）
        # 4. 返回模型实例
```

### 2.3 交叉验证机制

**多模型交叉验证**：对高 DAL（A/B）原子，用两个不同模型做红队，对比结果。

```
Writer（创意型）→ 草稿
    ↓
RedTeamer A（推理型）→ 阻断列表 A
RedTeamer B（严谨型）→ 阻断列表 B
    ↓
合并：A∩B = 高置信度阻断（必须修）
      A△B = 单红队发现（需额外验证）
```

**好处**：
- 两个模型都发现的问题 = 高置信度
- 只有一个模型发现的问题 = 可能是误报，需要验证
- 模型 A 的盲区可能被模型 B 覆盖

### 2.4 模型专长档案

为每个模型建立"专长档案"，记录它在各类任务上的历史表现：

```yaml
models:
  gpt-4o:
    roles: [writer, researcher]
    strengths: [创意, 写作, 类比]
    weaknesses: [事实错误, 过度概括]
    metrics:
      writer_claim_quality: 4.2/5
      redteam_block_confirm_rate: 0.75
      avg_tokens_per_task: 8000
  o1:
    roles: [redteamer, architect]
    strengths: [逻辑, 推理, 反例]
    weaknesses: [慢, 贵, 创意不足]
    metrics:
      redteam_block_confirm_rate: 0.92
      avg_tokens_per_task: 25000
  claude-sonnet:
    roles: [coder, tool_dev]
    strengths: [代码, 调试, 工具开发]
    weaknesses: [架构设计弱]
    metrics:
      code_compile_rate: 0.95
      avg_tokens_per_task: 6000
```

**用途**：
- 调度器根据专长档案选择模型
- 定期更新档案（根据实际表现）
- 发现模型的退化（如某模型更新后表现下降）

## 三、实现路径

### 3.1 第一阶段（双模型试点）

1. 保持当前模型作为 Writer/Gatekeeper
2. 引入第二个模型作为 RedTeamer（推理型）
3. 对比单红队 vs 双红队的阻断质量
4. 建立模型专长档案的基础版

**预期效果**：红队的阻断证实率提升（推理型模型更适合红队）。

### 3.2 第二阶段（角色-模型映射）

1. 为每个流水线角色指定首选模型和备选模型
2. 实现简单的规则调度器
3. Writer 用创意型，RedTeamer 用推理型，Gatekeeper 用严谨型
4. 高 DAL 原子用双红队交叉验证

### 3.3 第三阶段（质量反馈调度）

1. 建立模型表现追踪（阻断证实率、编译成功率、token 消耗）
2. 调度器根据历史表现动态调整
3. 模型退化检测（某模型表现下降时自动降级）
4. 成本优化（在质量达标的前提下用便宜模型）

### 3.4 第四阶段（模型专长网络）

1. 更多模型加入（搜索型、小模型、代码型）
2. 复杂任务自动分解为子任务，分配给不同模型
3. 模型间协作协议（标准化的输入输出格式）
4. 模型市场（可插拔的模型适配器）

## 四、风险与缓解

| 风险 | 缓解 |
|---|---|
| 模型 API 不可用 | 降级调度：首选不可用时自动用备选 |
| 模型输出格式不一致 | 标准化输出 schema（所有模型输出同一格式） |
| 多模型成本高 | 成本调度：机械任务用小模型，只有高价值任务用大模型 |
| 模型间通信延迟 | 异步调度：非关键路径的任务并行执行 |
| 质量不一致 | 交叉验证 + 质量反馈 + 专长档案 |
| 上下文碎片化 | 共享记忆层（所有模型访问同一 golden_lock/知识库） |
| 模型偏见 | 多模型交叉验证，避免单一模型的偏见 |

## 五、与现有系统的集成

### 5.1 与 G5 流水线的关系

当前 G5 流水线（Writer→RedTeamer→Gatekeeper）不变，只是每个角色可以用不同模型：
- Writer Agent → 创意型模型
- RedTeamer Agent → 推理型模型
- Gatekeeper → 严谨型模型（或纯工具）

### 5.2 与 G6 四级状态的关系

- multi-model-verified 可以作为新的状态级（比 red-team-verified 更强）
- 双红队交叉验证的原子可以标记为 `multi-redteam-verified`
- 模型专长档案可以作为状态的元数据

### 5.3 与工具链的关系

- 工具（gate/replay/poison/golden_lock）是模型无关的，任何模型都可以调用
- 调度器是新增的工具层，负责选择模型
- 模型适配器是新增的接口层，统一不同模型的 API

## 六、开放问题

1. **当前环境是否支持多模型？**
   - 豆包客户端可能只支持一个模型
   - 需要通过 API 调用其他模型（OpenAI/Anthropic/DeepSeek）
   - 或者通过"多 Agent"方式（每个 Agent 用不同模型）

2. **成本如何控制？**
   - 推理型模型（O1）比创意型贵 5-10 倍
   - 建议：只有 RedTeamer 和高 DAL 原子用推理型，Writer 用创意型
   - 机械任务（Gatekeeper）用小模型或纯工具

3. **如何衡量多模型协作的收益？**
   - 指标：阻断证实率、编译成功率、单原子时间、单原子成本
   - A/B 测试：单模型 vs 多模型，对比同一批原子的质量

4. **模型专长档案的冷启动问题？**
   - 初始档案基于模型的公开评测（MMLU/HumanEval 等）
   - 实际运行后用真实数据更新

---

## 七、近期可做的事（不依赖多模型 API）

即使当前环境只有一个模型，也可以为多模型协作做准备：

1. **标准化输出 schema**：Writer/RedTeamer/Gatekeeper 的输出格式标准化，未来换模型不需要改流程
2. **角色分离**：即使是同一个模型，也用不同的 system prompt 模拟不同角色（当前已经在做）
3. **质量追踪**：记录每个角色的表现（阻断证实率、编译成功率），为未来的模型选择提供数据
4. **交叉验证模拟**：用同一个模型的不同"温度"或"system prompt"做双红队，模拟多模型交叉验证

---

*核心结论：多模型协作不是"换一个更强的模型"，而是"让每个模型做它最擅长的事"。当前系统的单模型流水线已经有角色分离（Writer/RedTeamer/Gatekeeper），但角色和模型是绑定的。多模型协作的第一步是"解耦角色和模型"——让 RedTeamer 可以用推理型模型，Writer 可以用创意型模型。即使当前环境只有一个模型，也可以通过标准化输出、质量追踪、角色分离来为未来的多模型协作做准备。*
