# 491 人的因素与认知偏差防护方案
## 决策日志 + 预注册 + 回溯审计 + 异议机制 + 外部审计

> 生成时间：2026-09-14
> 核心问题：单人项目，所有决策都是一个人做的。"认可权唯人"是对的，但人也会犯错。系统的最终瓶颈是人。
> 认知偏差：确认偏误、锚定效应、沉没成本、后见之明、过度自信

---

## 一、问题：系统的最终瓶颈是人

### 现状

- 单人项目，没有 code review
- 所有决策（原子签署、规则变更、架构选择）都是用户+Agent 做的
- 红队是独立 Agent，但红队的结果还是要人来裁决
- "认可权唯人"（G6 铁律）是对的，但人也会犯错

### 认知偏差风险

| 偏差 | 在本项目中的表现 | 风险 |
|---|---|---|
| 确认偏误 | 只看支持自己观点的证据，忽略反面证据 | 错误的 claim 被签署 |
| 锚定效应 | 第一个数字/结论影响后续判断 | ALLOC-002 的"pool 32B"锚定了方向 |
| 沉没成本 | 已经花了很多时间，不愿意推翻重来 | 卡膨胀了还继续加，不重构 |
| 后见之明 | "我早就知道会这样" | 红队发现的问题被低估 |
| 过度自信 | 觉得自己的架构设计很完善 | 483 才发现六个盲区 |
| 权威偏误 | Agent 说的就信，不验证 | 红队的【推断】级发现被照单全收（371 红队误判 IFNDR 条款） |

### 已有的防护

- 红队独立 Agent（两段式盲读）
- 门禁机器验证
- 对抗测试（外部模型攻击）
- 铁律"不 golden sync"、"不 push"

### 缺失

- 决策没有书面理由（签了就签了，为什么签？）
- 实验没有预注册（预期结果没先写下来）
- 决策没有回溯（当时的决策对不对？）
- 异议没有记录（红队发现被驳回了，为什么驳回？）
- 没有外部审计（自己审自己）

## 二、决策日志

### 2.1 问题

人审签署时只写 `verified_by: human:liaoranran`，不写理由。3 个月后回看，不知道当时为什么通过、有没有考虑过反面证据。

### 2.2 改法

人审签署必须写理由，不能只签名。

```yaml
verified_by: human:liaoranran
verified_at: 2026-09-11
verified_reason: >-
  红队两段式盲读 0 阻断；双平台 replay confirm；
  claim 已收窄为"屏障在循环体内阻止消除"，本地三平台可复现；
  PG commit 降为移植性论据，不作主 claim。
verified_considerations:
  - "考虑过 claim 写成'编译器重排'，但本机 .asm 会反证，故放弃"
  - "考虑过锚定重排方向，但 x86/RISC-V 方向不同，故锚'有没有屏障构造'"
```

### 2.3 规则

- `ATOM-VERIFY-REASON`：verified 原子必须有 `verified_reason`（非空）
- `ATOM-VERIFY-CONSIDERATIONS`：建议有 `verified_considerations`（考虑过的替代方案）
- 理由必须具体（不能写"看起来没问题"），必须引用证据（红队结果/replay 结果）

### 2.4 工具：decision_log.py（约 60 行）

- 记录所有人审决策（原子签署、规则变更、架构选择）
- 每个决策有：时间、决策人、决策内容、理由、考虑过的替代方案、当时的证据
- 可查询、可回溯

## 三、预注册（防止后见之明）

### 3.1 问题

红队对抗、性能实验、新工具上线——这些实验的结果出来后，人会说"我早就知道会这样"（后见之明偏差）。

371 的红队 H2 假设被实测坐实，但如果没有预注册，后人会觉得"这不是显然的吗"。

### 3.2 改法：实验预注册

重要实验开始前，先写预期结果：

```markdown
## 实验预注册

**实验**：LEAK-002 加 volatile 构造计数后 LSan 是否会报 leak

**假设**：
- H1（红队）：加 volatile 计数器后 LSan 会从零报告变为报告（因为之前是分配被消除）
- H0（原结论）：LSan 仍零报告（volatile 不影响泄漏检测）

**预期结果**：
- 如果 H1 成立：stderr >0 字节，LSan 报告 64B/2 allocs
- 如果 H0 成立：stderr =0 字节，零报告

**判据**：stderr 字节数 >0 且 LSan SUMMARY 行存在 → H1 成立

**实验时间**：2026-09-12
**实验人**：Writer Agent
```

实验完成后，对比预期和实际：
```markdown
## 实验结果

**实际**：stderr 1258 字节，LSan 报告 64 byte(s) leaked in 2 allocation(s)
**结论**：H1 成立（红队假设坐实）
**与预期一致**：是
```

### 3.3 规则

- 红队对抗必须预注册（预期哪些洞会被找到）
- 性能实验必须预注册（预期加速比）
- 新工具上线必须预注册（预期效果）
- 预注册文件在实验前 commit（git 时间戳为证）

### 3.4 工具：preregistration.py（约 50 行）

- 创建预注册模板
- 实验后对比预期和实际
- 计算"预测命中率"（482 OPT-2：哪条假设的验证动作产出了新证据）

## 四、决策回溯

### 4.1 问题

当时的决策对不对？3 个月后回看，有没有发现当时漏了什么？

没有回溯机制，同样的错误会反复犯。

### 4.2 改法：季度回溯

每 3 个月自动生成回溯报告：

1. 列出本季度所有人审决策
2. 对每个决策，检查后续是否有证据推翻
3. 评估决策质量：
   - 正确：决策后没有被推翻
   - 部分正确：有小问题但方向对
   - 错误：被后续证据推翻
4. 分析错误原因（是证据不足？还是认知偏差？）

### 4.3 工具：decision_audit.py（约 80 行）

- 从 decision_log 读取决策
- 检查后续 git log 中是否有推翻该决策的提交
- 生成回溯报告
- 标记"需要重新评估"的决策

### 4.4 回溯触发

- 定期（每 3 个月）
- 事件触发（红队发现已签署原子有问题 → 回溯当时的签署决策）
- 人主动触发（"我觉得当时那个决策可能有问题"）

## 五、异议机制

### 5.1 问题

红队的发现如果被人驳回，就消失了。6 个月后发现驳回是错的，但已经找不到当时的驳回理由了。

371 红队有 1 处误判（IFNDR 条款），被正确驳回了——这个驳回是对的。但如果驳回错了呢？没有记录。

### 5.2 改法：异议登记

红队发现被驳回时，必须记录：

```yaml
objections:
  - id: OBJ-001
    date: 2026-09-12
    source: redteam:agent_371
    finding: "IFNDR 不可能是 16.2 子条"
    verdict: rejected
    rejected_by: human:liaoranran
    rejected_reason: "经 eel.is 原文核对，卡内引用无误"
    reevaluate_at: 2027-03-12  # 6 个月后重审
    status: rejected
```

### 5.3 重审机制

- 被驳回的异议 6 个月后自动提醒重审
- 重审时检查：当时的驳回理由是否还成立？有没有新证据？
- 如果驳回是错的 → 标记 `overturned`，修复问题
- 如果驳回是对的 → 标记 `confirmed`，关闭

### 5.4 工具：objection_register.py（约 70 行）

- 登记异议
- 6 个月后自动提醒重审
- 统计驳回正确率（人审的决策质量）

## 六、外部审计

### 6.1 问题

自己审自己，永远有盲区。483 的六个盲区就是自己审了很久才发现的。

### 6.2 改法：定期外部审计

每季度找外部的人/模型审计系统：
- 不依赖内部记忆（新会话、无历史上下文）
- 只读权限（不能改任何东西）
- 按审计清单检查
- 输出审计报告

### 6.3 审计清单

```
## 外部审计清单

### 内容质量
- 随机抽 5 颗原子，claim 是否有证据支撑？
- 随机抽 5 张卡，断言是否可机器验证？
- 有没有 claim 与工件矛盾的？

### 系统健康
- 门禁规则是否有死规则（零命中）？
- 毒样例是否能真正触发对应规则？
- replay 是否真的在验证（还是 sha 路径跳过了断言）？

### 架构合理性
- 工具之间是否有重复代码？
- 数据模型是否一致？
- 有没有过度设计（为了架构而架构）？

### 认知偏差
- 有没有确认偏误（只看支持证据）？
- 有没有沉没成本（该推翻的没推翻）？
- 有没有过度自信（声称"极致"但实际有漏洞）？
```

### 6.4 对抗测试就是外部审计

当前的对抗测试（368/373/402/452/470）就是一种外部审计：
- 独立模型（不同模型族）
- 只读+写探针到沙箱
- 找系统漏洞

但对抗测试只关注"安全逃逸"，不关注"内容质量"和"架构合理性"。外部审计应该更全面。

## 七、认知偏差检查清单

决策前过一遍：

```
## 决策前检查

1. 确认偏误：我有没有只看支持自己观点的证据？反面证据是什么？
2. 锚定效应：第一个数字/结论是不是影响了我的判断？如果换个起点会怎样？
3. 沉没成本：已经花了很多时间，是不是因为不想浪费而继续？如果从零开始会选这个方案吗？
4. 后见之明：这个结果是真的可预测的，还是事后诸葛亮？
5. 过度自信：我有多确定？如果错了代价是什么？
6. 权威偏误：Agent/红队说的就一定对吗？有没有验证原文？
7. 替代方案：除了这个方案，还有至少 2 个替代方案吗？
8. 最坏情况：如果这个决策错了，最坏后果是什么？能恢复吗？
```

## 八、实施计划

### 第一阶段（零/低成本，立即做）

1. **决策日志**：verified 原子必须有 verified_reason，gate 规则强制
2. **预注册模板**：红队对抗和性能实验必须预注册
3. **异议登记**：红队发现被驳回时必须记录
4. **认知偏差清单**：写进 docs/kernel/，决策前过一遍

### 第二阶段（中等成本，下一批做）

5. **decision_log.py**：决策记录和查询工具
6. **decision_audit.py**：季度回溯工具
7. **objection_register.py**：异议登记和重审提醒
8. **外部审计清单**：完整的审计清单文档

### 第三阶段（高成本，需要积累）

9. **决策质量追踪**：人审决策的正确率、驳回正确率
10. **自动外部审计**：每季度自动派外部模型审计
11. **认知偏差检测**：从决策日志中自动检测偏差模式

## 十一、关键认知

**系统的最终瓶颈不是工具、不是规则、不是架构，而是人。**

工具可以自动化，规则可以机器执行，架构可以持续优化——但最终的"认可权"在人手里。人会犯错、会有偏见、会疲劳。

人的因素防护不是"不信任人"，而是"帮人减少犯错"。决策日志、预注册、回溯审计、异议机制——这些都是给人搭的"脚手架"，让人在做决策时更清醒、更可追溯、更能从错误中学习。

**最强的系统不是"机器取代人"，而是"机器让人更聪明"。**
