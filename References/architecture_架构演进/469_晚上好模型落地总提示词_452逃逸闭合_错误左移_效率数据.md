## 二、P0 安全地基：闭合 452 第四轮对抗的确认逃逸

第四轮对抗（`_adv_v70/`，独立模型盲读产出）经 replay 实弹确认的逃逸，按严重度排序。**每条修复必须：配毒样例（poison）+ pytest 正反例 + 存量零误伤（gate block=0 不新增）+ 独立 commit。**

### P0-1【最高，运行时覆写 E01】F02 的 gate 文本检测被 helper 脚本绕过

- **实测（452 v2 复核）**：`EV-ADV70-E01.md` 用无参 `python build_step.py` 编译，脚本**内部硬编码 artifact 路径**做覆写，命令行文本里既无工件名也无写动词 → gate 零命中 → replay **confirm 逃逸**。v1 方案的"gate 静态解析脚本内容"对编译后二进制/网络下载脚本无效。
- **根因**：gate 只做命令文本分析；replay 无"运行时最后写入者"校验。黑名单（cp/mv/python…）永远列不全，426 已论断必须升级到不变量。
- **修复（v2：两项都做，不再只做文本层）**：
  1. **gate 侧（辅助，warn）**：command 中出现脚本解释器调用且脚本在仓库内时，解析脚本内容；脚本内对 artifact 路径的写操作 → warn。脚本不在仓库 → warn"产物经不可审计脚本产出"。
  2. **replay 侧（根本，P0 必做，v1 曾误登记为 P1）**：replay 跑完 command 后，**重编译一次**（用 command 中的编译命令，去掉后置覆写段），对比重编译产物的 sha256 与卡内 artifact_sha256。不一致 → refute:artifact_tampered。这是 426 的"最后写入者"不变量的最小实现：只有编译器能产出匹配 sha 的工件。
- **实现要点**：重编译用临时目录（避免覆盖原工件），只比 sha 不保留产物；编译失败 → infra_error 分流（不判内容 refute）。
- **验收**：E01 探针 replay 重编译后 sha 不一致 → refute；合法卡（无覆写）重编译 sha 一致 → confirm；poison + pytest 绿。

### P0-2【高，假证据 H6】读文件式夹具（cat 式证据）

- **实测**：`EV-ADV70-H6.md` 夹具 open 随库提交的 `expected_data.txt` 并打印，run_match 逐字一致、sha 一致 → **confirm**。但输出只证明"程序打印了文件内容"，不证明任何计算/机制。
- **修复方向**：新增 gate 规则 `EV-FIXTURE-NO-ECHO-DATA`（先 warn 观察 1 批，再升 block）：扫描 fixture 源码，若存在"打开仓库内数据文件（ifstream/fopen/open with r）且其内容经 cout/printf 流向 stdout 的 run 标签"→ warn，提示"读数回显不构成机制证据，活性读数必须由计算产生"。
- **边界**：合法夹具也可能读文件（如演示文件格式），故先 warn；判据聚焦"读入值未经任何运算直接成为 run_match 标签值"。
- **验收**：H6 探针 warn；存量 56 卡若有同类，列出来交人裁决（可能是真问题，如 EV-MEM-017 族）。

### P0-3【高，环境依赖 H7】环境量进 run_match_keys（d8ff94d 只改卡未立规则）

- **实测**：`EV-ADV70-H7.md` 把 nproc/环境量放进 keys，本机 confirm、CI 核数不同必红。历史 commit d8ff94d 修了存量卡但**没立规则**，会复发。
- **修复方向**：gate 规则 `EV-OUT-NO-ENV-KEY`（block 新卡，存量 warn）：run_match_keys / actual run 标签的值若来自 `std::thread::hardware_concurrency`、`std::filesystem::file_size`（非确定性文件）、`__DATE__/__TIME__/__FILE__`、`getenv`、`%USERNAME%/%TIME%/%DATE%`、`nproc`、`uname`、PID、时间戳（chrono now/clock/time）→ block。
- **注意**：`hardware_concurrency` 走 sysconf 不受 taskset 影响（d8ff94d 已实证），不能用"CI 钉核数"绕过，必须禁止进确定性 keys（允许打印但要标记为非确定性、不进 run_match）。
- **验收**：H7 探针 block；CONC-002 的 nproc 兜底（insufficient_cores）是**合法范式**（打印核数用于守卫，不作为逐字 key），不得误伤——用它做反例毒样例。

### P0-4【中高，H2】producer 后写动词黑名单外延不完备

- **实测**：install / ln -sf / xcopy / robocopy / tar 落在黑名单外：xcopy/robocopy/type 完全 BLOCK=0，install/ln/tar 仅 warn。
- **修复方向**：不要再补黑名单。反转判据为 **"producer 段之后，任何触碰 artifact 路径的命令段默认 block；只有读白名单（type/cat/head/tail/grep/od/objdump/nm/file/sha256sum）放行"**（白名单比黑名单安全：读工具数量有限且可枚举，写工具/脚本无限）。读 `_post_compile_writes` 现有 `_POST_READ_PROGS`，把它从"语义不明保守 warn"升级为"不在读白名单即 block"。
- **验收**：H2 全部写动词探针 block；读白名单工具（objdump 验证 .asm 是常见合法后置段）放行；存量卡 command 若有后置触碰 artifact 的非读段，列出来。

### P0-5【中，H16/H16B】零诊断判据字段面太窄 + pragma 消音

- **实测**：规则只扫 `falsification` 字段；零诊断措辞藏进 `expected`/`hypothesis`（H16a）、或用 `#pragma GCC diagnostic ignored` 消音（H16B）都 confirm。
- **修复方向**：①扫描面扩到 expected/hypothesis/actual 全文的"零诊断/无警告/zero warning"声明；②检测夹具是否用 pragma/`-w`/`-isystem` 压制了本应作为证据的警告；③零诊断证据必须配套 `-Werror` 的可复现编译命令（否则"零诊断"不可机器判定，降为 warn）。
- **验收**：H16/H16B 探针 block 或 warn；真用 -Werror 的合法卡（INLINE-001）不误伤。

### P0-6【高，E03 第 21 个恒真符号】denylist 是打地鼠，必须升级判别力证明

- **实测（452 v2 复核）**：20 词 denylist 外，`.seh_endproc/.cfi_startproc/.p2align` + any-of 组成跨双平台恒真断言；`contains_in` 的 `mov` 仅 advice。v1 方案"补 denylist"被证明永远有第 21 个。
- **根因**：黑名单本质是打地鼠。contains/absent 的 text 若在工件**每个函数符号区间都出现**，则它对"该函数有没有某行为"零判别力——这是可以机器计算的，不需要列黑名单。
- **修复（v2：判别力证明为 P0 必做，denylist 只作临时过渡）**：
  1. **根本（P0）**：`contains_in/absent_in` 断言评估时，先统计 text 在工件**所有函数符号区间**的出现次数。若在 ≥N 个函数区间都出现（N=工件函数总数的 80%，或绝对阈值 ≥5），判 `assertion_no_discriminator` → block（新卡）/ warn（存量）。这需要解析 .asm 的函数符号区间（replay 已有符号区间语义 contains_in/absent_in，复用其区间切分逻辑）。
  2. **过渡（同时做）**：补当前实测的恒真符号到 denylist（.cfi_startproc/.cfi_endproc/.seh_endproc/.seh_proc/__main/%rsp/.p2align/.section/.text/$LN），作为判别力证明上线前的兜底。
- **验收**：E03 探针（contains `.cfi_startproc`）block；真实机制符号（lock xchg/fence，只在特定函数出现）放行；poison + pytest。

### P0-7【高，解析器面 E07/H8/H14/H18/H13】自定义解析器是攻击面，切标准库

- **E07 缩进走私（452 新发现，第 7 种同构变换，v1 未覆盖）**：自定义解析器把缩进项提升为顶层键——列 0 写 `verdict: refute` + 缩进写 `verdict: confirm`，F09 修复（只数列 0 重复键）零 block，解析器 after-wins 得 confirm。451 的"6 种同构变换"被证明不完备。

- **风险**：safe_load 对存量卡的兼容性——先全量解析存量 56 卡 + 28 原子，确认 safe_load 结果与自定义解析一致（或差异可解释），再切换。若有存量卡依赖自定义解析的"宽容"行为，列出来交人裁决。
- **验收**：E07 探针 safe_load 报 DuplicateKeyError 或解析后 verdict=refute（而非 confirm）；存量卡解析结果不变；poison + pytest。

## 五、统一工程铁律（每个 commit 都遵守）

1. **重读磁盘**：改任何工具前先 Read 其当前源码，规则注册表/关系归一/三分类/豁免文件的真实结构以代码为准。
2. **一条修复一个 commit**，message 格式 `fix(gate): P0-x <漏洞> 闭合（452 Hn）` / `feat(...)`。
3. **每条新规则配毒样例**（poison_drill 的 P 编号续号，先 `--list` 看最大编号）+ pytest 正反例（正例=攻击卡被拦，反例=合法卡放行）。
4. **存量零误伤**：每改一条规则，全量 `gate_engine.py --check` 的 block 必须仍为 0（新增 warn 要列出具体卡和理由，交人审）；`replay --check` 保持 confirm 数不下降、无新增 refute。
5. **门禁全绿才提交**：gate block=0、poison 全拦截+阴性放行、pytest 全过、replay 不退化。Windows replay 与 WSL 预检**严禁并行**（同写 .asm 出假红）。
6. **不 push、不 golden sync/accept、不删毒样例、不 renormalize Examples/**。
7. **数字以实跑为准**，文档（含本文）与代码冲突时信代码，并在 worklog 记录文档错误。
8. 插入大段代码后立即 `python tools/gate_engine.py --check` 验证文件可加载（历史教训：replace 破坏过缩进/循环）。
