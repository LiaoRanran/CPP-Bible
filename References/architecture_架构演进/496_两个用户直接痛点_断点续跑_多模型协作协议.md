# 484 两个用户直接痛点的落地方案
## 断点续跑/会话恢复 + 多模型协作协议

> 生成时间：2026-09-14
> 来源：483 差距分析中 P0 级的两个盲区
> 用户痛点：每天手动续 3-5 次 Agent（500 请求上限）、多模型协作全靠人工复制粘贴

---

## 一、断点续跑 / 会话恢复

### 1.1 问题

用户明确说："Agent 干活一次只能 500 次请求，到顶了就得人为续上。"

当前状态：
- 任务进度不持久化（Agent 死了就全丢）
- worklog 是自由文本（每个 Agent 自己写，格式不统一）
- 没有"从第 N 步继续"的能力
- 长任务中途失败要从头跑

### 1.2 改法：结构化 worklog + resume 脚本

#### 1.2.1 worklog JSON Schema

所有 Agent 的 worklog 必须用统一的 JSON 格式（存为 `_worklog_<batch>.json`，同时保留人类可读的 `.md` 版本）：

```json
{
  "batch_id": "479",
  "started_at": "2026-09-14T10:00:00",
  "last_updated": "2026-09-14T11:30:00",
  "status": "in_progress",
  "tasks": [
    {
      "id": "1",
      "name": "TDD 顺序反转写入 Writer 提示词",
      "status": "done",
      "started_at": "2026-09-14T10:00:00",
      "completed_at": "2026-09-14T10:15:00",
      "commits": ["abc1234"],
      "artifacts": ["docs/kernel/writer_production_flow.md"],
      "notes": "铁律 P-TDD 已写入"
    },
    {
      "id": "2",
      "name": "doc_lint.py 文档质量门禁",
      "status": "in_progress",
      "started_at": "2026-09-14T10:15:00",
      "completed_at": null,
      "commits": [],
      "artifacts": ["tools/doc_lint.py"],
      "notes": "工具已写好，pytest 还差 1 个测试",
      "next_action": "补 test_doc_lint.py 的第 3 个测试"
    },
    {
      "id": "3",
      "name": "ccache 接入 replay",
      "status": "pending",
      "started_at": null,
      "completed_at": null,
      "commits": [],
      "artifacts": [],
      "notes": "",
      "next_action": null
    }
  ],
  "baseline": {
    "gate_rules": 50,
    "gate_block": 0,
    "gate_warn": 32,
    "poison": 61,
    "pytest": 272,
    "replay_confirm": 56
  },
  "final_check": null
}
```

#### 1.2.2 状态机

每个任务的状态：
- `pending`：未开始
- `in_progress`：进行中（Agent 死了就从这里恢复）
- `done`：完成（有 commit + 验收）
- `failed`：失败（有原因 + 回滚状态）
- `skipped`：跳过（有原因）

#### 1.2.3 resume 脚本

`Scripts/resume.py`（约 80 行）：

```python
#!/usr/bin/env python3
"""断点续跑：读取 worklog JSON，输出从哪里继续"""
import json, sys
from pathlib import Path

def resume(worklog_path):
    with open(worklog_path, encoding='utf-8') as f:
        wl = json.load(f)
    
    # 找到第一个 in_progress 或 pending 的任务
    for task in wl['tasks']:
        if task['status'] == 'in_progress':
            print(f"🔄 从任务 {task['id']} 继续：{task['name']}")
            print(f"   已完成：{task.get('notes', '无')}")
            print(f"   下一步：{task.get('next_action', '继续完成')}")
            print(f"   已提交：{task.get('commits', [])}")
            return task['id']
        elif task['status'] == 'pending':
            print(f"⏭️  下一个任务：{task['id']} {task['name']}")
            return task['id']
    
    print("✅ 所有任务已完成")
    return None

if __name__ == '__main__':
    resume(sys.argv[1] if len(sys.argv) > 1 else '_worklog_latest.json')
```

#### 1.2.4 Agent 续跑提示词模板

当 Agent 达到 500 请求上限后，用户只需要说：

> "续跑 479，先 `python Scripts/resume.py _worklog_479.json` 看从哪继续，然后 Read 对应的 worklog，接着干。"

新 Agent 不需要重新交代上下文，resume.py 会告诉它从哪个任务继续、已经做了什么、下一步是什么。

#### 1.2.5 长任务 checkpoint

对于全量 replay 这类长任务：
- 每跑完 10 张卡，写一次 checkpoint 到 `build/.replay_checkpoint.json`
- 中途失败后，`--resume` 从 checkpoint 继续
- 不需要从头跑

### 1.3 验收

- 所有 Agent 的 worklog 有统一 JSON 格式
- `python Scripts/resume.py` 能正确指出从哪继续
- Agent 死了之后，新 Agent 能在 5 分钟内恢复上下文（不需要重新交代）
- 全量 replay 有 checkpoint，中途失败不需要从头跑

## 二、多模型协作协议

### 2.1 问题

用户已经在人工做多模型协作：
- 苦力（便宜模型）：干杂活、修复、提交
- 好模型（ds v4.1 flash）：落地系统基线、复杂架构
- 对抗模型（Seed-Evolving/Trae/混元）：红队对抗

但没有系统化：
- 没有标准化的 handoff 格式（全靠人工复制粘贴）
- 没有任务路由规则（每次靠人判断）
- 没有结果验收标准
- 没有升级/降级机制

### 2.2 改法：handoff JSON + 路由规则 + 验收清单

#### 2.2.1 handoff JSON Schema

所有模型之间的交接用统一的 JSON：

```json
{
  "handoff_id": "479-to-480",
  "from_model": "cheap-model",
  "to_model": "strong-model",
  "task_type": "mechanical | semantic | creative",
  "status": "completed | needs_upgrade | failed",
  "summary": "479 批次完成 3/5 任务，ccache 接入有问题需要升级",
  "completed_tasks": ["1", "2"],
  "incomplete_tasks": ["3", "4", "5"],
  "blockers": [
    {
      "task": "3",
      "issue": "WSL ccache 路径和预期不符",
      "attempted": "试过 /usr/bin/ccache 和 /usr/local/bin/ccache",
      "needs": "需要好模型判断怎么处理 WSL 侧"
    }
  ],
  "artifacts": {
    "commits": ["abc1234", "def5678"],
    "files": ["tools/doc_lint.py", "docs/kernel/writer_production_flow.md"],
    "worklog": "_worklog_479.json"
  },
  "verification": {
    "gate": "50 rules, block=0, warn=32",
    "poison": "61/61",
    "pytest": "275 passed",
    "replay": "confirm=56"
  },
  "next_actions": [
    "修复 ccache WSL 路径问题",
    "完成 E12 签收绑定",
    "跑全量门禁收尾"
  ]
}
```

#### 2.2.2 任务路由规则

| 任务类型 | 定义 | 路由 | 升级条件 |
|---|---|---|---|
| **机械** | 有明确规则、可机器验证（改字段、补测试、跑门禁、转换格式） | 苦力 | 连续 2 次失败 → 升级 |
| **语义** | 需要理解但有验证器（写卡、改 claim、红队、写工具） | 苦力→验证→不通过升级 | 门禁失败超过 3 次 → 升级 |
| **创造** | 无明确规则、需要架构判断（新工具设计、范式突破、架构规划） | 直接好模型 | N/A |
| **对抗** | 需要独立视角、攻击思维 | 对抗模型 | N/A |

#### 2.2.3 结果验收清单

每个任务完成后，必须附带：
1. 门禁结果（gate/poison/pytest/replay 对比基线）
2. commit hash 列表
3. 改动文件列表
4. 未完成项和原因
5. 需要下一个模型做什么

没有验收清单的交付 = 未完成。

#### 2.2.4 升级/降级机制

- **苦力→好模型升级**：连续 2 次失败、或遇到"需要架构判断"的阻塞、或门禁失败超过 3 次
- **好模型→苦力降级**：好模型做完架构设计后，具体实现交给苦力
- **对抗模型→建设者**：对抗发现问题后，交给建设者（苦力或好模型）修复

#### 2.2.5 工具：Scripts/handoff.py（约 60 行）

```python
#!/usr/bin/env python3
"""多模型协作 handoff 工具"""
import json, sys
from pathlib import Path

def create_handoff(batch_id, from_model, to_model, task_type, status, **kwargs):
    """创建 handoff JSON"""
    handoff = {
        "handoff_id": f"{batch_id}-{from_model}-to-{to_model}",
        "from_model": from_model,
        "to_model": to_model,
        "task_type": task_type,
        "status": status,
        **kwargs
    }
    path = f"_handoff_{batch_id}_{from_model}_to_{to_model}.json"
    with open(path, 'w', encoding='utf-8') as f:
        json.dump(handoff, f, ensure_ascii=False, indent=2)
    print(f"✅ Handoff 已创建：{path}")
    return path

def read_handoff(path):
    """读取 handoff，输出摘要"""
    with open(path, encoding='utf-8') as f:
        h = json.load(f)
    print(f"📦 Handoff: {h['handoff_id']}")
    print(f"   从: {h['from_model']} → 到: {h['to_model']}")
    print(f"   状态: {h['status']}")
    print(f"   已完成: {h.get('completed_tasks', [])}")
    print(f"   未完成: {h.get('incomplete_tasks', [])}")
    print(f"   阻塞: {len(h.get('blockers', []))} 个")
    print(f"   下一步: {h.get('next_actions', [])}")
```

### 2.3 典型工作流

```
用户：给苦力投喂 479 提示词
  ↓
苦力：执行任务 1-3，任务 3 遇到阻塞（WSL ccache 路径）
  ↓
苦力：创建 handoff JSON（status=needs_upgrade, blockers=[...]）
  ↓
用户：把 handoff JSON 喂给好模型（不需要重新交代上下文）
  ↓
好模型：Read handoff，解决阻塞，完成任务 3-5
  ↓
好模型：创建新的 handoff（status=completed, verification=...）
  ↓
用户：投喂对抗模型（handoff 里有完整的改动清单和门禁结果）
  ↓
对抗模型：Read handoff，针对改动做对抗
```

### 2.4 验收

- 所有模型交接有统一的 handoff JSON
- 用户不需要重新交代上下文（handoff 里有完整信息）
- 任务路由有明确规则（不是每次靠人判断）
- 升级/降级有明确条件
- 交付必须附带验收清单

## 三、两项的优先级与依赖

| 项 | 成本 | ROI | 优先级 | 依赖 |
|---|---|---|---|---|
| 断点续跑 | 低（worklog schema + resume 脚本 80 行） | 极高（每天省 3-5 次手动续） | P0 | 无 |
| 多模型协作 | 低（handoff schema + 路由规则 + 脚本 60 行） | 高（省人工复制粘贴） | P0 | 无 |

**建议**：两项都立即做，都是零/低成本但用户直接痛点。可以合并成一个批次（484 批次）。
