# 446 可突破部分的落地消化：现在就能干的 5 项 + 需要准备的 3 项

> 日期：2026-09-13。基于 445 的"四道墙部分可突破"结论，把能突破的部分消化为可落地的架构改进。原则：先干能干的，不追求完美。

---

## 一、现在就能干的 5 项（零新环境、零大改架构）

### 1.1 语义分层：claim 加 formalizable 字段

**目标**：把 claim 的断言分成"可形式化"和"不可形式化"两类，可形式化的用机器 100% 验证，不可形式化的用红队+人审。

**实现**：在 443 的 claim 契约化 v2.0 基础上，加一个字段：

```yaml
claim:
  assertion: "相邻布局比隔离布局慢约一个数量级"
  formalizable: false  # 性能断言不可形式化
  verification:
    - type: empirical  # 经验验证
      method: "双平台实测，7 轮，中位数对比"
    - type: red_team  # 红队验证
      method: "两段式盲读，检查口径一致性"

# 对比：可形式化的断言
claim:
  assertion: "delete 后再访问是 UB"
  formalizable: true
  verification:
    - type: compiler  # 编译器验证
      method: "UBSan 编译运行，检查 runtime error"
    - type: standard  # 标准条文验证
      method: "C++ 标准 [basic.stc.dynamic.deallocation] p2"
```

**gate 规则**：ATOM-CLAIM-VERIFICATION（warn）
- claim 必须有 formalizable 字段
- formalizable=true 的断言必须有 compiler 或 standard 类型的 verification
- formalizable=false 的断言必须有 empirical 或 red_team 类型的 verification

**为什么现在就能干**：只是 frontmatter 加字段 + gate 加规则，不需要新环境。

### 1.2 规则误报率记录

**目标**：每条 gate 规则记录历史误报率，高误报率规则自动降级。

**实现**：在 data/debt_ledger.yaml 中加规则级统计：

```yaml
rule_stats:
  EV-MATRIX-*:
    total_hits: 17  # 历史总命中数
    false_positives: 17  # 人审确认的误报数
    false_positive_rate: 1.0  # 100% 误报
    level: warn  # 当前级别
    auto_downgrade_threshold: 0.8  # 误报率 >80% 自动降级
    last_evaluated: "2026-09-13"

  EV-ARTIFACT-PRODUCER:
    total_hits: 3
    false_positives: 0
    false_positive_rate: 0.0
    level: block
    auto_downgrade_threshold: 0.8
```

**自动降级机制**：
- 误报率 >80% 的 block 规则 → 自动降为 warn
- 误报率 >80% 的 warn 规则 → 自动降为 advice
- 降级记录在 debt_ledger.yaml 中，人审可以撤销

**为什么现在就能干**：debt_ledger.yaml 已经存在（443 扩展），加规则统计字段即可。自动降级需要改 gate_engine.py，但改动不大。

### 1.3 红队→规则转化率指标

**目标**：记录"红队发现的问题→变成规则/毒样例"的转化率，作为成本下降的量化指标。

**实现**：在批次报告模板（403 的 A1）中加一个指标：

```yaml
redteam_to_rule_conversion:
  batch: "第五批 MEM"
  redteam_findings:
    total: 26  # 红队发现总数（阻断+高级+建议）
    blockers: 3
    high: 15
    suggestions: 8
  converted_to_rules:
    - "S3-EXPECTED-HARDCODED（注释里的双引号字面量）"
    - "EV-ASSERT-SYMBOL-MAPPED（通用符号+注释伪造）"
  conversion_rate: 0.08  # 2/26 = 8%
  note: "转化率低是因为大部分发现是内容级（卡的 claim 方向），不是工具级（规则漏洞）"
```

**目标**：转化率从 8% 提升到 30%+（红队发现的工具级问题都应该变成规则）。

**为什么现在就能干**：只是报告模板加字段，不需要改工具。

### 1.4 自治边界文档

**目标**：明确哪些检查可以完全自治，哪些需要人，写进 G6 规范。

**实现**：在 docs/kernel/G6_status_levels.md 中加一节"自治边界"：

```markdown
## 自治边界

### 完全自治（零人工）
- 编译检查（g++ 编译成功/失败）
- sanitizer 检查（ASan/TSan/UBSan 报告）
- replay 比对（actual 与工件逐字匹配）
- gate 规则检查（42 条规则）
- poison 毒样例演练
- DAL C/D/E 原子的 verified 状态迁移

### 半自治（机器初筛 + 人确认）
- DAL A/B 原子的 verified 状态迁移（人审签署）
- warn 分类（real_issue vs false_positive）
- 规则降级（误报率 >80% 自动降级，人审可撤销）
- 红队阻断级发现的修复确认

### 非自治（必须人）
- 教学效果评估（学生能不能学会）
- claim 的"教学价值"判断（这颗原子值不值得做）
- 架构级决策（v7→v8→v9 的路线选择）
- 新域的开辟（如从 MEM 转到 CONC）
```

**为什么现在就能干**：只是写文档，不需要改工具。

### 1.5 规则质量评估（拦截率）

**目标**：每条规则计算拦截率（毒样例能拦住设计的违规的比例），低拦截率规则标记为"弱规则"。

**实现**：poison_drill.py 已经有 RULE-COVERAGE，扩展为拦截率：

```yaml
rule_quality:
  EV-ARTIFACT-PRODUCER:
    poison_samples: 2  # 覆盖该规则的毒样例数
    intercepted: 2  # 毒样例被拦住的数量
    interception_rate: 1.0  # 100% 拦截
    quality: strong  # strong / medium / weak
  EV-MATRIX-*:
    poison_samples: 0
    intercepted: 0
    interception_rate: null  # 无毒样例覆盖，无法评估
    quality: unknown
```

**弱规则处理**：拦截率 <50% 的规则标记为 weak，建议改进或删除。

**为什么现在就能干**：poison_drill.py 已经有 RULE-COVERAGE，扩展输出即可。

## 二、需要准备的 3 项（需要新工具或新环境）

### 2.1 Clang Static Analyzer 集成

**目标**：用 CSA 做更深入的静态检查（除了编译+sanitizer 之外）。

**现状**：Windows/WSL 都没有 Clang（已知边界）。

**准备工作**：
- WSL 安装 clang（`apt-get install clang`）
- 写一个 `clang_static_analyze.py` 包装器，调用 `clang --analyze`
- 把 CSA 报告作为证据卡的 additional_verification

**优先级**：P2（v8.0），因为需要新环境，且 CSA 的误报率较高，需要误报治理先落地。

### 2.2 LLM 误报二次筛选

**目标**：gate 报 warn 后，用 LLM 判断是不是真问题，降低人工分类成本。

**现状**：32 条 warn 需要人逐条分类。

**准备工作**：
- 写一个 `warn_triage.py`，对每条 warn 调用 LLM（用最便宜的模型）判断"真问题/误报/不确定"
- LLM 判断为"真问题"的进入 debt_ledger 的 real_issue 分类
- LLM 判断为"误报"的进入 false_positive 分类，人审抽查
- LLM 判断为"不确定"的交给人审

**优先级**：P2（v8.0），因为需要额外 token 预算，且 LLM 分类本身可能有误报，需要校准。

### 2.3 规则自动进化（counterexample mining）

**目标**：用误报和漏报作为反馈信号，自动调整规则条件。

**现状**：规则是人工写的，误报需要人工修。

**准备工作**：
- 积累足够的误报/漏报数据（至少 50 条）
- 写一个 `rule_evolver.py`，用归纳逻辑编程（ILP）自动生成规则改进建议
- 人审确认后应用

**优先级**：P3（v9.0），因为需要大量数据积累，且 ILP 的实现复杂度高。

## 三、随时间解决的 2 项（需要技术进步或长期数据）

### 3.1 教学效果的自动验证

**现状**：教学效果（学生能不能学会）无法被外部验证器检查，需要学生反馈。

**未来可能的解法**：
- 闪卡/MCQ 的答题数据作为学生学习效果的代理指标
- 学习路径 DAG 的完成率作为教学效果的代理指标
- 长期：A/B 测试不同教学方法的效果

**时间线**：需要教学转化体系（405）落地后，积累学生数据，才能做。

### 3.2 性能的形式化

**现状**：性能本质上是经验的，无法形式化。

**未来可能的解法**：
- 性能模型（如 roofline model）可以做"理论上限"验证
- 但"实际性能"仍然需要实测
- 长期：WCET（最坏执行时间）分析可以做形式化，但只适用于硬实时系统

**时间线**：不是阙疑的重点，随时间自然解决。

## 五、为什么这 5 项"现在就能干"很重要

445 说"可形式化部分 100% 正确做得到"——但如果不做语义分层，就不知道哪些是可形式化的。
445 说"零边际成本做得到"——但如果不记录转化率，就不知道成本有没有下降。
445 说"可验证部分自治做得到"——但如果不写自治边界，就不知道哪些可以自治。
445 说"低误报做得到"——但如果不记录误报率，就不知道哪些规则需要降级。

**这 5 项是"突破极限"的基础设施**——没有它们，445 的结论只是"理论上可以"；有了它们，445 的结论变成"实际上在做"。
