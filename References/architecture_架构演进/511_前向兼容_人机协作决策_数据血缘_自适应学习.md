## 一、模型升级前向兼容（用户最关心的问题）

### 1.1 业内核心发现

| 发现 | 来源 | 含义 |
|---|---|---|
| **状态必须外部化** | Zylos AI (2026) | 上下文内记忆不跨runtime转移。模型升级后，in-context memory 全部丢失 |
| **Persona drift** | Zylos AI | 系统提示词token随context增长被注意力稀释，模型升级后行为漂移 |
| **两个关键技术** | Zylos AI | Context compaction + structured memory serialization——没有这两个，迁移=冷启动 |
| **架构 > 提示词** | MLflow 2026 | 模块化多agent架构+路由层，比单体agent更可靠更可维护 |
| **长上下文不是万能** | Berrydesk | 1M-token窗口让RAG变成调优旋钮而非硬需求，但状态外部化仍是必须 |
| **运行时治理不可协商** | MLflow | 确定性策略执行在模型层之下，在动作到达线路之前阻止 |

### 1.2 我们系统的现状评估

**我们天然前向兼容的地方**（这是最大的优势）：
- 状态全在文件系统：`golden_state.json`、`gate_state.json`、`golden_lock`、`task_queue.jsonl`
- 规则全在代码里：`gate_engine.py`（55条规则）
- 证据全在文件里：证据卡+artifact+.asm+.out
- 结论全在commit history里
- **模型升级后这些全部不变**——因为它们不在模型上下文里

**我们还没显式设计的地方**：
1. **没有"模型能力档案"**：不知道哪个模型能做什么（494建了yaml但success_rate全unknown）
2. **没有行为漂移检测**：模型升级后，同样的提示词产出是否一致？没有自动对比
3. **没有提示词版本管理**：提示词改了但不知道哪版产出了哪个原子
4. **Persona drift未防护**：系统提示词随context增长，关键约束可能被稀释

### 1.3 落地方案

**原则：系统越强，模型越强，系统自动受益——这就是"随模型升级进化"**

```
模型升级前的系统假设（写在 config/capabilities.yaml）：
  cheap:
    max_requests: 500
    can_do: [机械代码修改, 文档整理, 测试编写]
    cannot_do: [架构设计, 红队分析]
  mid:
    max_requests: 500
    can_do: [规则设计, 工具开发, 中等调试]
  strong:
    can_do: [对抗测试, 架构决策, 复杂调试]

模型升级后（自动检测）：
  1. 跑标准测试套件（50个已知原子+夹具）
  2. 对比新旧模型产出是否一致
  3. 如果新模型在 cheap tier 完成了原本需要 mid 的任务 → 自动升级它的能力
  4. 如果新模型在某任务上退化了 → 标记，不降级但告警
```

**Persona drift 防护**：
- 铁律放在提示词最前面和最后面（首尾因效应）
- 关键约束每条≤10字（"不push""不golden sync""先Read磁盘"）
- 每批开始时重复铁律（不靠模型记住）
- 这个我们已经在做了（提示词开头列铁律），但要显式化

**提示词版本管理**：
- 每份提示词 frontmatter 加 `prompt_version: v3.1`
- 每个原子的 production_record 记录用了哪个版本的提示词
- 这样模型升级后可以对比"同提示词不同模型"的产出差异

## 二、人机协作决策

### 2.1 业内模式

| 模式 | 来源 | 核心 |
|---|---|---|
| **状态机** | Daily Bits | draft → propose → review → approve → execute → log |
| **不可变审计日志** | OpenBox/Ertas | 时间戳+审核人+AI输出+置信度+决策+理由，创建后不可改 |
| **置信度路由** | Superkind | AI不确定时自动升级给人审，不需要人盯 |
| **批量审批规则** | OpenHelm | "总是批准这类动作"——减少重复人审 |
| **Event Bus** | arXiv 2602.00751 | AI完成事件→事件总线→验证编排器→路由到人审UI |

### 2.2 我们的现状

**已有的**：
- 状态：draft → verified（人签 `human:liaoranran`）
- DAL分级：A/B需人审，C/D/E可机器审
- 铁律：人审前不commit

**缺的**：
1. **审计日志不完整**：人签了但没记录"AI为什么建议这个、人为什么批"
2. **置信度路由**：所有原子都等人审，没有"AI说高置信度就自动过"
3. **批量审批规则**：没有"这类原子自动过"的机制
4. **决策记录**：人否决了一个原子，但理由没结构化记录

### 2.3 落地方案

**审计日志结构化**（扩展 status_history）：
```yaml
status_history:
  - level: draft
    at: "2026-09-14"
    by: machine:writer
    note: "初稿完成"
  - level: proposed
    at: "2026-09-14"
    by: machine:redteam
    note: "红队通过，2高级3建议已修"
    confidence: 0.85  # 新增：AI置信度
  - level: verified
    at: "2026-09-15"
    by: human:liaoranran
    note: "通过，claim收窄正确"
    decision: approve  # approve/reject/modify
```

**置信度自动路由**：
```
confidence >= 0.90 且 DAL=C/D/E 且 gate block=0 且 poison全过
  → 自动 verified（不需人审，留痕）
confidence 0.70-0.90 或 DAL=B
  → 等人审
confidence < 0.70 或 gate block>0
  → 打回重做
```

**批量审批规则**（白名单）：
```yaml
# config/auto_approve_rules.yaml
rules:
  - match: "domain:lang AND type:fact AND DAL:C"
    action: auto_approve
    reason: "语言事实性知识，机器验证充分"
  - match: "domain:conc AND DAL:A"
    action: require_human
    reason: "并发错误即UB，必须人审"
```

## 三、数据血缘与可追溯

### 3.1 业内模式

| 模式 | 来源 | 核心 |
|---|---|---|
| **W3C PROV标准** | ORNL PROV-AGENT | Entity-Activity-Agent三元组，agent交互端到端血缘 |
| **六字段契约** | The Data Praxis | source hash + agent + activity + entity + derivation + timestamp，缺一个不shipping |
| **版本化是前提** | Uplatz/Atlan | 没有稳定唯一标识符，血缘图没东西可指 |
| **DVC/lakeFS** | PulseGeek | 数据版本化+血缘，每个变换读一个版本化repo写另一个 |

### 3.2 我们的现状

**已有的**：
- artifact_sha256：工件指纹
- command：怎么编译的
- artifact_compiler：哪个编译器
- run_match_keys：输出什么
- git commit：谁什么时候提交的

**缺的**：
1. **决策血缘**：人签了"approved"但没记录为什么
2. **推导链**：一个原子的claim基于哪些证据卡，证据卡基于哪些夹具，夹具基于什么编译选项——这条链没有图
3. **上游依赖**：改了gate_engine.py，影响哪些原子？impact_analysis.py做了但没集成
4. **模型版本**：这个原子是哪个模型、哪个版本、哪个提示词版本生产的

### 3.3 落地方案

**六字段契约**（每个原子必须有）：
```yaml
provenance:
  source_hash: "d8b6b18d..."        # artifact sha256
  agent: "human:liaoranran"         # 谁签署的
  activity: "atom_verified"          # 做了什么
  entity: "ATOM-CONC-FENCE-001"     # 对谁
  derivation: ["EV-CONC-001", "EV-CONC-002"]  # 基于什么
  timestamp: "2026-09-15T10:00:00"
  model: "hunyuan-4p"               # 哪个模型生产的
  prompt_version: "508-v2"          # 哪个提示词版本
```

**推导链图**（502知识图谱的L1）：
- 原子 → 证据卡 → 夹具 → 编译选项 → 编译器版本
- 反向查询：改了g++版本，哪些原子受影响？
- 这个用SQLite一张表就能做（502已设计）

### 4.1 业内模式

| 模式 | 来源 | 核心 |
|---|---|---|

| **BKT贝叶斯知识追踪** | CognitoLearn | HMM推断真实掌握程度，不猜阈值 |
| **Dijkstra最短路径** | CSDN | 从当前知识状态到目标节点的最优学习路径 |
| **日常检索练习** | 1Cademy | 答对推进到高级，答错回溯前置知识 |
| **诊断评估** | Geleza | 追踪响应时间、错误模式、主题置信度、会话一致性 |

### 4.2 我们的现状

**已有的**：
- 知识图谱：relations（prerequisite/specializes/contradicts）
- 闪卡导出：flashcard_export.py 已出106张Anki卡
- 误解库：80条MIS记录常见错误

**缺的**：
1. **学习者模型**：不知道用户/学生掌握了什么
2. **路径规划**：不知道下一步该学什么
3. **间隔重复**：闪卡导出了但没有Spaced Repetition算法
4. **诊断**：不知道用户卡在哪

### 4.3 落地方案

**学习者模型**（最小版）：
```json
// data/learner_model.json
{
  "user": "default",
  "mastered": ["ATOM-MEM-RAII-001", "ATOM-MEM-MOVE-002"],
  "struggling": ["ATOM-CONC-FENCE-001"],
  "not_started": ["ATOM-CONC-LOCK-001"],
  "last_review": {"ATOM-MEM-RAII-001": "2026-09-10"}
}
```

**路径规划**（最小版）：
```
输入：已掌握 {A, B}，目标 {D}，D依赖 C，C依赖 B
输出：学习路径 B→C→D（跳过已掌握的B）
算法：Dijkstra on prerequisite graph，从已掌握节点到目标节点
```

**间隔重复**（最小版）：
- 答对 → 下次复习间隔 ×2（1天→3天→7天→14天→30天）
- 答错 → 重置到1天
- 这个Anki已经做了，我们导出CSV给Anki即可，不用自己实现

## 六、核心洞察：前向兼容是我们最大的架构优势

业内（Zylos/MLflow/Dataiku）反复强调的核心原则——**"状态必须外部化，架构>提示词，运行时治理在模型层之下"**——我们系统**天然做到了**：

| 业内要求 | 我们现状 |
|---|---|
| 状态外部化 | ✅ golden_state/gate_state全在文件 |
| 架构>提示词 | ✅ 规则在代码不在提示词 |
| 运行时治理在模型层下 | ✅ gate_engine在模型输出后执行 |
| 不可变审计日志 | ⚠️ 有commit history但没结构化决策记录 |
| 置信度路由 | ❌ 所有人审 |

这意味着：**模型越强，系统自动受益越多**。因为模型只负责生成内容，所有验证、规则、门禁、血缘都在模型之外。模型升级了，规则不变、证据不变、血缘不变——只是生成质量更高了。

这就是用户说的"系统会随大模型能力进化而进化"的架构基础。
