## 二、我们做对的（方向被2026业界验证，不是自嗨）

### ✅ 1. 锚定客观外部oracle——这是最根本的正确
DSE文章的结论几乎是为阙疑背书：**"自改进只有锚定compiler/benchmark这类客观oracle才不崩塌，self-authored test会silent corruption"**。
我们的 replay 锚定的正是三层客观oracle：
- 编译器退出码（不是LLM判断）
- 工件sha256字节一致（不是文本相似）
- sanitizer报告（外部工具）
- 重编译不变量（独立再编译对比，防自写自证）

**判断：这条路是对的，而且比多数agent框架走得远。大部分agent框架的"verify"是LLM-judge（另一个模型说对），我们是compiler-oracle（编译器说对），后者才是DSE说的"不会崩塌"的那种。**

### ✅ 2. 三分类confirm/refute/infra_error
业界系统普遍混淆"内容错"和"环境坏"。我们显式分流且infra也fail-closed（exit 1但不计内容恶化），堵住"删夹具即放行"。这比多数框架严谨。

### ✅ 3. 多轮对抗+毒样例 ≈ mutation testing雏形
我们的7轮对抗（368→v80）本质就是Test-vs-Mutant：攻击者造逃逸，建设者补规则。方向正确。

## 三、四个真实结构性差距（按价值排序）

### 🔴 差距1：claim是一句话文本，没有结构化分解
**AutoVerifier的关键**：把claim拆成(S,P,O)三元组后，才能做跨claim的图推理——自动发现"两个claim共用一个subject但predicate矛盾"。

**我们的现状**：claim是≤50字自然语言（如"屏障在循环体内阻止消除，但屏障≠原子类型"）。机器无法判断两句claim是否矛盾，只能靠红队读。

**这正是521漏洞5"claim-code语义不匹配机器修不了"的根因**——claim没结构化，机器无从下手。

**吸收方案（可落地，非空想）**：
不追求AutoVerifier的全自动NLP三元组抽取（差模型做不好）。改为**Writer半结构化claim契约**：
```yaml
claim_structured:
  subject: 内存屏障           # 主体（概念节点）
  predicate: 在循环体内        # 关系
  object: 阻止编译器消除循环    # 客体
  claim_type: observation     # observation=直接观测可机验 / inference=推断需人审
  negates: [MIS-CONC-001]     # 显式否定哪个误解
```
- `claim_type: observation` 的卡，必须有artifact断言支撑（机器可闭环）
- `claim_type: inference` 的卡，强制人审（机器不下verified结论）
- subject/object进知识图谱节点 → 矛盾检测从"读文本"变成"图查询"

**这一步直接把521的"语义不可机验"边界往后推了一大截。**

### 🔴 差距2：claim没有"直接观测 vs 推断"分级
**Tool Receipts的关键**：pratyakşa（亲眼所见，绑receipt）和anumāna（推理所得）验证强度不同。观测类核对receipt即可，推断类要核对前提链。

**我们的现状**：所有claim一视同仁。"spin_plain产物只有mov/ret"（直接观测，可机验）和"屏障不建立happens-before"（标准推断，需人审）混在同一套verified流程里。

**吸收方案**：和差距1合并——claim_structured.claim_type 二选一：
- observation：机器闭环（replay confirm即可晋升machine-verified）
- inference：必须有人审或独立标准来源（ISO/cppreference）才能verified
**收益：把宝贵的人审注意力只花在推断类上，观测类全自动。这是"放权"的精确化——不是全放，是按类型放。**

### 🟡 差距3：变异靠手写，没有对抗自动生成
**TTHE/Test-vs-Mutant**：变异agent自动造能逃过当前规则的样本，种群进化。

**我们的现状**：72个毒样例全是人（和对抗agent）手写的。每轮对抗要重新投喂、重新想攻击。

**吸收方案（分两步）**：
- 现在能做：**结构化变异算子库**。归纳7轮对抗的逃逸模式，发现它们就是有限的几类"同构变换"（缩进走私/字段位移/同义词/恒真符号/后置覆写/编码变体...）。把每类做成一个自动变异算子，对任意新卡自动跑一遍全部变换，看哪个能逃过gate。
- 以后做：让对抗模型用算子组合生成新变异（Test-vs-Mutant闭环）。
**关键判断：不需要LLM就能做第一步——同构变换是机械的，写个 mutation_fuzz.py 对每张卡自动套用全部算子，等于把7轮对抗的经验固化成永久自动巡检。这比再投喂10轮对抗性价比高。**

### 🟡 差距4：溯源没用W3C PROV的四类约束
**W3C PROV**：溯源图必须满足四类约束——唯一性、事件顺序、不可能性、类型约束。

**我们的现状**：status_history是时间线，但只校验"跃迁合法"（draft→machine-verified→verified），没有PROV的完整约束。例如：
- 事件序约束：verified_at 不能早于 machine-verified 的 at（我们没查）
- 不可能性：一张卡不能同时被两个不同human在同一级签署（我们没查）

**吸收方案**：把status_history当PROV Activity链，加两条机械约束（纯图检查，零LLM）：
- 时间单调：status_history的at必须非递减
- 单签唯一：同一level不能有两个不同by
低成本、纯机械、堵时序造假。

## 四、明确不学的（陷阱识别）

| 外部做法 | 为什么不学 |
|---|---|
| PROClaim三角色法庭辩论 | 我们已有独立红队盲读，三角辩论token成本×3，白嫖预算下不划算；单红队+异模型复测已覆盖主要偏见 |
| AutoVerifier全自动NLP三元组抽取 | 差模型抽取质量不可控，会引入新错误；改Writer半结构化填写更可靠 |
| LLM-as-judge做最终裁决 | DSE明确警告这是reward hacking温床；最终裁决必须留给compiler-oracle和人 |
| 全自动harness种群进化(TTHE完整版) | 需要稳定的generate-and-judge基础设施，当前调度层L2只有12%，先做机械变异算子，不做LLM进化 |
| HMAC签名receipt | 我们是本地单仓git，没有跨网络信任问题，sha256+git已够；HMAC是分布式场景的解 |

## 五、吸收后的架构升级（精确到数据结构）

### 5.1 claim契约 v0.3（在现有frontmatter上加，不破坏存量）

```yaml
claim_structured:
  subject: <概念节点，进知识图谱>
  predicate: <关系>
  object: <概念节点或观测结果>
  claim_type: observation | inference   # 观测类机验 / 推断类人审
  negates: [<误解ID>]                    # 显式否定
  receipt:                               # observation类必填，对应Tool Receipts
    source: replay                       # 客观oracle来源
    evidence: [EV-CONC-001, EV-CONC-002]
    machine_checkable: true
```

**晋升规则随claim_type分叉**：
- observation + replay confirm + 无阻断红队 → 可machine-verified（放权自动）
- inference → 必须 human签 或 独立标准源，机器只到red-team-verified

### 5.2 变异算子库（机械、零LLM、永久巡检）

把7轮对抗逃逸归纳为算子，每个输入一张卡输出N个变异体：
1. 缩进/空格/tab变换（E07）
2. 字段顺序位移（E10a）
3. 关系同义词（refutes/cancels/conflicts_with）
4. 恒真符号注入（.file/.section/.p2align）
5. 重复YAML键（F09）
6. 全角/Unicode键（F04）
7. 后置写入命令（F02，需沙箱）
8. 注释里藏符号（2c）

`python tools/mutation_fuzz.py evidence/EV-CONC-001.md` → 对每个变异体跑gate，报告哪个逃逸。**这是把红队从"每次重新雇佣"变成"永久在岗的自动巡检"。**

### 5.3 PROV时序约束（纯机械，加2条gate规则）
- ATOM-HISTORY-TIME-MONOTONIC：status_history时间非递减
- ATOM-HISTORY-SINGLE-SIGNER：同level唯一签署人

## 七、元判断（这轮调研最有价值的结论）

1. **阙疑的核心路线被2026业界验证为正确**：客观oracle锚定的约束式验证，正是"自改进不崩塌"的唯一已知形态。我们不是在重复造轮子，是在一条被证明对的路上，且比多数agent框架走得深（它们用LLM-judge，我们用compiler-oracle）。

2. **真正的下一个突破口不是加工具，是claim结构化**。521说"语义机器验证不了是纯规则系统的边界"——这个边界可以被claim_type分级和三元组结构化往后推一大截：观测类全自动、推断类才要人。这才是"放权"的精确形态。

3. **红队经验应该固化成机械变异算子，而不是每轮重新对抗**。7轮对抗的逃逸模式收敛到8类同构变换，说明攻击面是有限的、可枚举的。写成mutation_fuzz.py等于请了一个永不下班的红队。

4. **警惕"用更复杂的智能掩盖grounding缺失"**。PROClaim/TTHE看起来炫，但在我们L2调度层只有12%、claim还是纯文本时上这些，是空中楼阁。先把claim结构化和机械变异做扎实。
