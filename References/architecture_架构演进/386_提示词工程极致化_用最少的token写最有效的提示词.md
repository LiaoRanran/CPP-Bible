# 386 提示词工程极致化：用最少的 token 写最有效的提示词

> 日期：2026-09-13。监工完成。这是 374-385 之后的架构升级轮，聚焦**提示词工程极致化**——我们的提示词越来越长（312 有 28KB），怎么用最少的 token 写最有效的提示词。
> 核心命题：**好提示词是短提示词。我们的提示词有巨大压缩空间——重复纪律、负面指令、冗余示例、散文输出。ProCut 证明生产环境提示词可减 78% 而不损失性能。**
> 流程：搜集 → 整理 → 挖掘 → 联系 → 批判 → 结合 → 应用。

## 一、搜集（搜了什么）

两路并行检索：
1. 提示词优化/token 效率/压缩/指令剪枝
2. 提示词蒸馏/few-shot 选择/系统提示词优化

核心来源（12 份）：
- **Token-Optimized Prompt Engineering（企业级）**：6 种设计模式——结构压缩、语义压缩、缓存、检索范围限定、对话摘要、输出控制
- **LLMLingua**（微软）：小模型计算 token 困惑度，移除低困惑度 token，20× 压缩+98.5% 准确率
- **ProCut**（arXiv 2508.02053）：归因分析压缩——分语义单元→量化影响→剪枝低效用，生产环境 78% token 减少
- **企业级实践数据**：系统提示词压缩 15-30%、精准 few-shot（3 vs 10）40-60%、输出长度限制 20-50%、批处理 30-40%
- **"好提示词是短提示词"**：移除填充词、删除冗余指令、告诉模型做什么而不是不做什么
- **结构化输出**：JSON 200 token 胜过散文 500 token
- **自动提示词压缩趋势**：2026 年生产团队把 4000 token 压缩到 800 token（80% 缩减）
- **DSPy 蒸馏**：教师-学生管道——收集候选演示→评分（正确性/简洁性/多样性）→选最优子集→指令优化，8B 可 beat GPT-4
- **Prompt Distillation（自动优化）**：先扩展（加示例）→再压缩（把示例核心思想浓缩成几句话）→防过拟合
- **FrugalPrompt**：token 归因+top-k 过滤，只保留最有信息量的 token
- **示例剪枝**：基于相似度的实例级剪枝，把示例内化到参数
- **PromptDistill**：训练无关，利用早期层注意力识别最有信息量的 token

| 内容层 | few-shot 精简（10→3）、示例蒸馏 | 40-60% | 中 |
| 语义层 | 归因分析剪枝、LLMLingua 困惑度压缩 | 50-80% | 中高 |

| 阶段 | 做什么 | 产出 |
|---|---|---|

## 三、挖掘（核心洞察）

**1. 我们的提示词有巨大压缩空间，且大部分是零风险的噪声层压缩**：
- 312 有 28KB（约 7000-10000 token）
- 重复纪律："铁律 1""铁律 2"在多处重复出现（选题论证、夹具规范、卡层规范各写一遍）
- 负面指令：大量"不要 X""禁止 Y""不得 Z"——可以改成正面指令"只做 X""必须 Y"
- 冗余示例：can't-miss 清单有 10-13 条，很多是同类（都是"断言相关"）
- 散文输出：Agent 输出大量"本轮完成了...""我发现了..."——可以结构化
- **仅噪声层+结构层压缩，零风险就能减 30-40%**

**2. ProCut 的"归因分析"是压缩的正确方法，不是凭感觉删**：
- 把提示词分成语义单元（选题论证/夹具规范/卡层规范/红队规范/门禁规范）
- 量化每个单元对任务性能的影响（去掉某段后，生产的原子是否还能过门禁？）
- 剪枝低效用组件
- **映射到我们：对 312 做 A/B 测试——去掉"选题论证表"后，生产的原子 claim 质量是否下降？去掉"风险表"后，红队是否还能抓出阻断？** 用数据决定删什么，不是凭感觉。

**3. DSPy 蒸馏的"教师-学生"思路完美适配我们的场景**：
- 教师：强模型+长提示词（312）生产高质量原子（我们已经有 27 颗 verified）
- 选择：从 27 颗中选 3 颗最有代表性的作为"黄金示例"（覆盖 pitfall/mechanism/contrast 三种类型，各一颗）
- 压缩：把 312 的长指令压缩成"核心规范+3 个黄金示例"
- **这比"从头写短提示词"更可靠——因为黄金示例是真实 verified 的原子，不是编造的模板**

**4. "告诉模型做什么，不是不做什么"是最简单的零风险压缩**：
- 负面指令（"不要在注释里写双引号"）比正面指令（"注释里只写 %s 格式串"）多 token 且可能混淆模型
- 我们的提示词里有大量负面指令，可以系统性地改成正面
- 这是"噪声层"压缩的一部分，零风险，立即见效

**5. 结构化输出同时减少输入和输出 token**：
- 要求 Agent 用表格/JSON 输出，比散文少 20-50% 输出 token
- 结构化输出也更容易被下游工具解析（门禁、质检报告）
- **映射到我们：红队报告要求"阻断/高级/建议"三级表格，而不是散文叙述；质检报告要求"门禁结果表+案例表"，而不是流水账**

**6. 提示词压缩的"验证-压缩-验证"循环**：
- LobeHub 的 optimize-prompt-token-efficiency skill：分析→压缩→重新验证，最多 5 轮迭代，原子替换
- **映射到我们：每次压缩提示词后，必须跑历史 3 颗原子的 replay+gate，确认没有回归。这和 385 的"提示词回归测试"是配套的。**

## 四、联系（和我们系统的映射）

| 外部发现 | 我们的现状 | 差距 |
|---|---|---|
| 噪声层压缩（删冗余） | 312 有大量重复纪律和负面指令 | 未压缩 |
| ProCut 归因分析 | 凭感觉写提示词，没量化每段效用 | 缺 A/B 测试 |
| DSPy 教师-学生蒸馏 | 有 27 颗 verified 原子但没选黄金示例 | 缺示例选择 |

| 结构化输出 | Agent 输出大量散文 | 缺输出格式约束 |
| 压缩后回归验证 | 改提示词后不跑回归 | 缺验证循环 |

## 五、批判（哪些不适用/有局限）

1. **LLMLingua 等自动压缩工具对我们不适用**：这些工具用小模型计算困惑度来删 token，可能删掉"铁律""DAL"等关键术语。我们的提示词是高度结构化的规范文档，**必须人工压缩+回归验证，不能用自动工具**。

2. **过度压缩可能损失"威慑力"**：我们的提示词里有大量"铁律""禁止""阻断"等强约束词，这些词虽然 token 多，但对 Agent 的行为有威慑作用（"铁律 7：未原子化不得 commit"）。压缩成"提交前必须原子化"可能减弱约束力。**压缩时必须保留强约束词的语义强度。**

3. **few-shot 精简到 3 个可能不够**：我们的任务类型多样（pitfall/mechanism/contrast/perf/leak），3 个示例可能覆盖不全。DSPy 的"最优子集"是在验证集上选出来的，我们需要先定义验证集（哪几颗原子代表哪种类型），再选示例。**不是随便选 3 颗，是按类型覆盖选。**

4. **提示词压缩的 ROI 递减**：第一次压缩（删噪声）减 30%，零风险；第二次压缩（精简示例）减 20%，低风险；第三次压缩（语义层）减 20%，中高风险。**做到 50-60% 缩减就够了，不要追求 80%。**

5. **提示词缓存是平台层面的**：我们控制不了 prefix caching，这部分节省不算我们的优化。

## 六、结合（和已有架构的结合点）

**和 383 上下文工程**：提示词压缩是上下文管理的一部分——系统提示词每次都重复传入，压缩系统提示词=每轮都省 token。383 讲的是"工具输出清理"，386 讲的是"提示词本身精简"，两者配合。

**和 384 多模型路由**：便宜模型的上下文窗口更小，更需要精简提示词。路由到 LOW/MEDIUM 模型时，用压缩版提示词；HIGH 模型时，可以用完整版。

**和 385 数据飞轮**：提示词压缩的 A/B 测试结果（哪段有用、哪段没用）是数据飞轮的输入——自动收集"去掉某段后通过率变化"，聚类成"提示词改进建议"。

**和 382 对抗**：红队提示词的压缩更关键——红队是独立子 Agent，提示词越精简，红队越聚焦（不会被长提示词里的无关内容分散注意力）。

**和 gate 规则**：提示词压缩后，Agent 可能忘记某些规范——gate 规则是"提示词之外的安全网"，确保即使提示词里没写，规则也能拦住。**提示词压缩和 gate 规则是互补的：提示词精简到"核心规范"，gate 兜底"所有规范"。**

## 七、最终应用（分阶段落地）

### 立即落地（零成本，手动压缩）

**应用 1：负面指令改正面（系统性扫描）**
- 扫描所有提示词（312/320/373 等），把"不要 X""禁止 Y""不得 Z"改成"只做 X""必须 Y""规范是 Z"
- 保留强约束词（"铁律""阻断"），只改表述方式
- 预计减 10-15% token，零风险

**应用 2：删除重复纪律**
- "铁律 1-10"在多处重复出现的，只在开头列一次，后面引用"见铁律 N"
- can't-miss 清单里同类的合并（如"断言相关"的 3 条合并成 1 条+子项）
- 预计减 10-15% token，零风险

**应用 3：输出格式约束**
- 红队报告：要求"阻断/高级/建议"三级表格，每条含"位置/问题/修法"
- 质检报告：要求"门禁结果表+案例表+待办表"
- 进度汇报：要求"已完成/未完成/下一步"三段
- 预计减 20-30% 输出 token

### 中期落地（需 A/B 测试）

**应用 4：ProCut 归因分析（量化每段效用）**
- 把 312 分成 5-6 个语义单元（选题/夹具/卡层/红队/门禁/交付）
- 对每个单元做 A/B 测试：去掉该单元后，生产 1 颗原子，看门禁结果
- 记录：去掉某段后，block 数变化、红队阻断数变化
- 低效用单元（去掉后无变化）→ 删除或精简
- 这是"用数据决定删什么"，不是凭感觉

**应用 5：黄金示例选择（DSPy 蒸馏）**
- 从 27 颗 verified 原子中，按类型选 3-5 颗最有代表性的：
  - pitfall 类：PERF-004（有红队阻断+修复记录）
  - mechanism 类：ALLOC-002（有方向反转+修订记录）
  - contrast 类：LEAK-002（有观测反转+前后对照）
- 把这 3 颗的"claim+证据卡摘要+红队处置"作为黄金示例，替换提示词里的抽象描述
- 黄金示例是真实 verified 的，比编造模板更有指导意义

### 长期落地

**应用 6：提示词版本管理+回归测试（和 385 配合）**
- 每次压缩提示词，版本号+1，changelog 记录改了什么
- 压缩后自动跑"受影响的毒样例子集"+最近 3 颗原子的 replay
- 确认无回归后才生效
- 这是"提示词作为代码"的完整实现

## 十、局限与后续

- 本调研聚焦提示词压缩，未覆盖"提示词自动优化"（用 LLM 自动改写提示词）——这需要 A/B 测试基础设施，当前不具备。
- 黄金示例选择（应用 5）需要先定义"代表性"的标准——是按类型覆盖，还是按"红队阻断最多"（最有教学价值）？需要人审决定。
- 提示词压缩的"威慑力"问题（强约束词不能删）意味着压缩有下限——不能无限压缩，核心规范必须保留。
- ProCut 归因分析（应用 4）的 A/B 测试成本高（每段要生产 1 颗原子），建议只对最长的提示词（312）做，短提示词不做。
- 本调研未覆盖"多语言提示词"（中文 vs 英文的 token 效率差异）——中文提示词通常比英文多 1.5-2× token，但我们的提示词是中文的，这个差异无法避免。
- 提示词压缩和 383 上下文工程有重叠（都是减 token），但侧重点不同：383 是"运行时的上下文管理"（工具输出、历史消息），386 是"静态的提示词本身"（系统提示词、任务提示词）。两者配合才能最大化 token 效率。
