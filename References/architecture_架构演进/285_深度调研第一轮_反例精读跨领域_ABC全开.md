## 二、A 反例搜索：6 个直接挑战我们架构的失败案例

### 反例 1：AI 审 AI = AI inception（同模型自审是最高成本低价值模式）
- **来源**：cc-orchestrator code review guide 明确写「Same-model self-review as a security check is the highest-cost low-value review pattern. Fix: Use cross-family review or skip the review stage entirely.」
- **挑战我们的什么**：宪法公理 3「验证必须独立于生成」。如果红队和 Writer 用同一个模型（如都是 DeepSeek V4.1 flash），即使「独立上下文」也不够——同模型有相同的盲区（correlated error）。
- **我们的场景是否成立**：成立。我们多平台轮班用不同模型（DeepSeek/CodeBuddy/豆包），但同一批次内 Writer 和红队可能用同模型。
- **修正动作**：红队必须**跨模型/跨家族**（Writer 用 DS，红队用豆包/CodeBuddy），写入宪法公理 3 的实施细则。**最小可用版**：在执行 Agent 提示词中加「红队必须使用与 Writer 不同的模型，若无法切换则标注「同模型红队，盲区风险高」」。

### 反例 2：CrowdStrike 事件——code review 的结构性盲区
- **来源**：2024 年 7 月，CrowdStrike 内容更新含验证逻辑 bug，部署到 850 万 Windows 机器，code review 没拦住。codegood.co 分析：code review 漏的是「并发问题、特定数据组合的边界、跨系统集成失败、架构不匹配、需领域知识的安全漏洞」。
- **挑战我们的什么**：我们的「机器门禁+红队」是否也有结构性盲区？gate 查格式/复算，红队查语义，但「跨原子集成失败」（如 A 原子的 prereq 指向 B 原子，但 B 的 claim 已改）目前只有 ATOM-REL-TARGET 规则查存在性，不查语义一致性。
- **修正动作**：加「跨原子集成检查」——prereq 边不仅查目标存在，还查目标的 claim 是否与本原子的假设一致。**最小可用版**：在红队清单中加「prereq 目标的 claim 是否与本原子假设一致」检查项。

### 反例 3：形式化验证的 False Axioms——规格错了，证明再完美也没用
- **来源**：Axiom 项目总结形式化验证三成本：① False Axioms（手动加的"自明"公理可能是错的，误导证明器）；② Intellectual Cost（智力成本高）；③ Ripple Cost（涟漪成本）。Vericoding 也指出「机器检查证明能展示代码满足 discount≤20%，但不知道业务把上限改成了 25%」。
- **挑战我们的什么**：修正案 1「claim 契约化」。如果 claim 本身错了（如 ALLOC-002 初版「pool 元数据 32B 最省」），契约化的 pre/post 只是把错误规格写得更正式——gate 检查 postcondition 与 actual 一致，但 actual 也是按错误规格生成的（夹具自己算 32B），所以 gate 不会拦。**这正是 ALLOC-002 发生的事**：claim 方向反了，但格式对了，gate 放行了。
- **修正动作**：claim 契约化必须加「**规格独立性检查**」——postcondition 的断言不能只由 Writer 的夹具生成，必须有一个**独立的最小验证**（如用不同的实现方式重算一次，或用标准条文交叉验证）。**最小可用版**：红队清单加「claim 的关键数字是否有独立于 Writer 夹具的验证？」

### 反例 4：Verification Debt——人审成为瓶颈
- **来源**：mohammadkhan.dev——AI PR 等待审查时间是人类的 4.6 倍，接受率 32.7% vs 84.4%。瓶颈不是复杂度，是信任。
- **挑战我们的什么**：宪法公理 5「verified 唯人签」。20 颗原子还可以，200 颗时人审会不会成为瓶颈？
- **修正动作**：人审规模化方案——「人审只审边界」（宪法已有）+ 「批量人审」（一次审一批，不是逐颗）+ 「人审抽样」（机器门禁+红队全过的原子，人审按 20% 抽样，发现问题则全审）。**最小可用版**：在执行 Agent 提示词中加「人审提交包按批次组织，每批 ≤5 颗，人审可批量签署」。

### 反例 5：Code Review is Dead → Spec Review
- **来源**：estebansancho.com——近一半 AI 生成代码过了 QA/staging 仍需手动调试。「看起来正确」的代码（语法干净、格式好、处理了明显边界）在生产条件下失败。结论：More careful review won't fix this，需要 Spec Review（先审规格再审代码）。
- **挑战我们的什么**：这实际上**支持**我们的 claim 契约化方向——spec-first 是正解。但反例提醒我们：只审代码（gate 查格式）不够，必须审规格（claim 是否正确）。
- **修正动作**：红队的第一检查项应该是「claim 规格是否正确」，而不是「代码是否符合 claim」。当前红队清单可能把重点放在后者。**最小可用版**：红队清单第一项改为「claim 规格审查：这个 claim 本身对吗？有没有反例？有没有过度概括？」

### 反例 6：MemGPT 分层记忆的静默失败
- **来源**：arXiv 2603.07670《Memory for Autonomous LLM Agents》——「The Achilles' heel of hierarchical memory is orchestration. Page the wrong things in and you waste context; archive too aggressively and you create 'memory blindness'—the agent simply does not know that the critical fact exists somewhere in cold storage. orchestration failures are silent（静默的）.」
- **挑战我们的什么**：283 的 T4 分层记忆提案。如果让 Agent 自己管理记忆（MemGPT 式），弱模型可能做次优换页决策，而且失败是静默的（不报错，只是「忘了」）。
- **修正动作**：T4 不应该是「Agent 自主管理记忆」（MemGPT 式），而应该是「**规则驱动的自动归档 + Agent 可检索**」——core 记忆由系统自动维护（当前批次状态），recall 由系统按时间自动归档，Agent 只能检索不能随意删改。**最小可用版**：T4 的 core/recall 由系统脚本维护，Agent 只有读权限和「追加写」权限，没有「替换/删除」权限。

## 三、B MemGPT 精读（arXiv 2310.08560）

### 核心机制
- **虚拟上下文管理**：类比 OS 虚拟内存，把 prompt 当 RAM，外部存储当 disk，通过函数调用换页。
- **三层记忆**：
  - Main context（RAM）：system instructions + working context + FIFO queue
  - Recall storage（对话历史，可搜索）
  - Archival storage（文档/事实，向量索引）
- **LLM 自己管理换页**：通过函数调用（paging in/out）决定什么留在上下文、什么归档。

### 6 个局限（反例级，直接修正我们的 T4）
1. **编排失败是静默的**——换页错了不报错，只是「记忆失明」。→ 我们的 T4 必须有「记忆完整性检查」（定期验证 core 包含必要状态）。
2. **LLM 做次优换页决策**——复杂场景下信息相关性不明显时，过早归档或检索失败。→ 弱模型不适合自主管理，改用规则驱动。
3. **没有显式修正语义**——update 是 replace text，丢历史，难审计。→ 我们的记忆必须是 append-only（追加写），不替换。
4. **安全边界**——函数调用记忆可能让 prompt injection 持久化。→ 不可信内容（如用户输入）不能直接写入 core 记忆。
5. **检索质量依赖 embedding**——向量化质量决定一切。→ 我们的归档检索先用关键词+frontmatter 过滤（精确），语义检索是可选增强。
6. **归档检索慢**——数据量大时延迟明显。→ recall（最近 N 批）保持在轻量文本，archive（更老）才进检索系统。

### 对 T4 的修正（283 提案 → 修正版）
| 283 原版 | 修正版 |
|---|---|
| Agent 自己管理记忆（写/归档/检索） | 规则驱动自动归档 + Agent 只读+追加 |
| 三层：core/recall/archive | 三层不变，但 core 由系统维护，Agent 不可删改 |
| 无完整性检查 | 每批开始时检查 core 记忆完整性（缺什么报什么） |
| update 可替换 | append-only，修正用「修订记录」追加，不覆盖 |

**最小可用版**：`tools/memory_manager.py` 只做两件事——① 每批结束时自动把当前批次状态追加到 `Memory/recall.md`；② 提供 `memory recall <keyword>` 搜索 recall + archive。core 记忆仍由系统提示注入，Agent 不管理。

## 四、C 跨领域借鉴：三个同构映射

### C1：医学鉴别诊断（Differential Diagnosis）→ 红队结构化升级

**医学流程**：
1. 收集信息（病史+体检）
2. 生成 3–5 个可能诊断，按「概率+严重性」排序
3. 特别标注「can't-miss」（即使概率低也必须排除，因为漏掉是灾难性的）
4. 选择测试区分 top contenders（考虑灵敏度/特异度）
5. 逐步排除，迭代更新
6. 最大错误：premature closure（过早下结论）

**与我们的红队同构**：
- 当前红队是「自由探索」——读到什么查什么，没有结构化清单。
- **升级为「鉴别诊断式红队」**：
  1. 红队入场先列「3–5 个最可能的错误假设」（按概率+严重性排序）
  2. 标注「can't-miss 错误」（自证断言/恒真观测/口径不统一/消除与失败不可区分——这些是第五批证明的灾难性错误，必须每批排除）
  3. 设计「测试」（夹具检查/工件检查/对照实验）逐个排除
  4. 防止 premature closure——红队报告必须含「我排除了什么、我没排除什么、为什么」

**最小可用版**：红队提示词加「鉴别诊断清单」模板——先列假设再验证，不先下结论。

### C2：法律证据链（Chain of Custody）→ 证据卡升级

**法律五问**（NIJ 标准）：
1. Who seized the evidence?（谁提取的）
2. When was it seized?（何时）
3. Where has it been since?（存在哪）
4. How was it preserved?（怎么保存的）
5. What records confirm preservation?（什么记录确认）

证据链断裂 = 合理怀疑 = 证据不可采。间接证据定案必须「证据属实、链条闭环、推理严谨、结论排他」。

**与我们的证据卡同构**：
- 当前证据卡有 sha256（回答「怎么确认完整性」），但没有回答「谁/何时/在哪/怎么保存」。
- **升级证据卡 frontmatter**：加 `compiled_by`（编译器版本）、`compiled_at`（时间）、`environment`（OS/平台）、`artifact_path`（工件路径）。
- 这让证据链可审计——任何人都能复现「谁在什么环境什么时候编译的，工件在哪，sha 是多少」。

**最小可用版**：证据卡模板加 4 个字段，`atom_evidence_replay.py` 自动填充 compiled_by/environment（从夹具编译命令提取），compiled_at 用 git commit 时间。

### C3：科学哲学（Lakatos 研究纲领）→ 架构自省

**Lakatos 修正 Popper**：
- 不是单个理论被证伪就放弃，而是「研究纲领」有：
  - **Hard core（硬核）**：不可反驳的基础假设，放弃=放弃整个纲领（如牛顿三定律）
  - **Protective belt（保护带）**：辅助假设，可调整、可退役
  - **Negative heuristic（反面启发法）**：不许把反驳指向硬核
  - **Positive heuristic（正面启发法）**：指导如何扩展保护带
- **进步的纲领**：能预测新事实（progressive）
- **退化的纲领**：只能事后解释（degenerating）

**与我们的架构同构**：
- 五公理 = hard core（不可反驳）
- 护栏/杠杆/工具/规则 = protective belt（可调整）
- 修宪程序 = 纲领变更机制

**最深刻的批判**：**我们的毒样例全是「事后加的」**——第五批出了自证断言的错，才加 P4；出了恒真观测，才加 P6；出了口径反转，才加 P10。这是 Lakatos 说的**退化的研究纲领**特征（只能事后解释，不能预测）。

**进步的纲领应该能预测新错误类型**——比如：
- 「对照被值类别污染」（SHARED-002 红队发现）→ 能不能预测「对照被优化档位污染」？
- 「LSan 可达性假阴性」（LEAK-001 发现）→ 能不能预测「其他 sanitizer 也有类似假阴性」？
- 「夹具注释里的双引号触发 S3」（第五批发现）→ 能不能预测「其他 lint 规则也会扫注释」？

**修正动作**：每批红队结束后，必须做「**错误预测**」——基于本批发现的错误模式，预测下一批可能出现的同类错误，写入 `docs/failure_mode_predictions.md`。下一批红队入场时先核对预测是否命中。**预测命中率 = 纲领进步性的量化指标。**

**最小可用版**：红队报告最后加一节「下一批错误预测」（≥3 条），下一批红队入场时先核对。

## 六、给用户的话

这轮深度调研（ABC 全开）的价值远超之前的摘要级调研。三个最有冲击力的发现：

1. **我们的毒样例全是事后加的 = 退化的研究纲领**（Lakatos）。进步的纲领能预测新错误，我们只能反应。修正：每批红队加「错误预测」，预测命中率=纲领进步性的量化指标。
2. **claim 契约化治不了 ALLOC-002 式的错误**（False Axioms）——如果 claim 本身错了，契约化只是把错误规格写得更正式。必须加「规格独立性检查」（独立于 Writer 夹具的验证）。
3. **MemGPT 式的 Agent 自主记忆对弱模型是危险的**——编排失败是静默的（不报错，只是忘了）。我们的 T4 必须改为规则驱动+append-only，不能让弱模型自己管记忆。

**三关标准执行情况**：
- 原文精读关：MemGPT 过（基于多篇深度分析+原文摘要）；Meadows/CompCert 基于已有调研+本轮补充，标注「待全文精读」。
- 反例关：6 个反例全部找到，每个都有具体来源和对架构的修正。
- 落地关：9 个修正全部含最小可用版（1 天可做完的版本）。
