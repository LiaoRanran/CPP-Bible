## 修订1：第4节 数据模型——JSON Schema契约

### v1.0问题
YAML Schema示例是给人看的文档，不是机器可执行的契约。Agent可以写`status: "verifiedd"`（拼写错误）而gate不拦。

### v1.1修订

**新增文件**：`schemas/atom.schema.json`、`schemas/evidence.schema.json`、`schemas/misconception.schema.json`

**JSON Schema示例（atom.schema.json核心部分）**：
```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "required": ["id", "domain", "topic", "type", "title", "claim", "status", "dal", "human_review", "relations", "pedagogy", "status_history"],
  "properties": {
    "id": {"type": "string", "pattern": "^ATOM-[A-Z]+-[A-Z]+-[0-9]{3}$"},
    "domain": {"type": "string", "enum": ["mem", "conc", "ub", "lang", "meta", "perf", "tool", "build", "debug", "test", "design", "style", "history", "project", "resource", "glossary"]},
    "status": {"type": "string", "enum": ["draft", "machine-verified", "redteam-reviewed", "verified"]},
    "dal": {"type": "string", "enum": ["A", "B", "C", "D", "E"]},
    "human_review": {"type": "string", "enum": ["required", "optional", "waived"]},
    "status_history": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["level", "at", "by"],
        "properties": {
          "level": {"type": "string", "enum": ["draft", "machine-verified", "redteam-reviewed", "verified"]},
          "at": {"type": "string", "format": "date"},
          "by": {"type": "string", "pattern": "^(machine|redteam|human):.+$"}
        }
      }
    }
  }
}
```

**gate新增规则**：`SCHEMA-VALIDATION`（block级）
- 用jsonschema库验证每个原子/证据卡/误解的frontmatter
- 验证失败→block，fix_hint指出具体字段和原因
- 替代原有的"字段存在性检查"（只检查字段存在，不检查值）

**实现状态（2026-09-12 对账）**：**不存在-未采纳**。`SCHEMA-VALIDATION` 关键词零命中、无 `schemas/` 目录；
schema 以 gate 规则（`ATOM-FM-REQUIRED`/`EV-FM-REQUIRED`）做"必填字段存在性"校验，不建 JSON Schema 层。

## 修订2：第4.1节 claim——强度检查

### v1.0问题
claim只要求"≤50字，可证伪"，但"可证伪"是主观判断。Writer可以把claim弱化为不可证伪（如"在某些条件下可能更快"）。

### v1.1修订

**claim强度规则（gate新增CLAIM-STRENGTH，block级）**：

claim必须满足以下全部条件：
1. **包含可观测的推论**：格式为"在X条件下，Y会发生"，X和Y都是可观测/可测量的
2. **禁止纯可能性陈述**：不得包含"可能"/"也许"/"有时候"/"通常"等模糊词（除非明确标注概率范围）
3. **禁止纯价值判断**：不得包含"更好"/"最优"/"推荐"/"应该"等主观词（除非有可观测的比较标准）
4. **禁止同义反复**：claim不得是定义的重述（如"RAII是资源获取即初始化"）

**claim强度分级**（写入frontmatter的claim_strength字段）：
- **强**：包含具体的条件+具体的推论+具体的量化阈值（如"当删除器有状态时，unique_ptr大小为16字节"）
- **中**：包含具体的条件+具体的推论，但无量化阈值（如"当循环体内有屏障时，编译器不会消除该循环"）
- **弱**：只有条件或只有推论（不允许verified，必须升级为中或强）

**falsification可执行性检查**：
- falsification必须是"可执行的证伪"：具体的实验/观测（如"如果删除器有状态时unique_ptr大小为8字节则证伪"）
- 禁止"如果X则证伪"的空话（X不可观测/不可执行）

**实现状态（2026-09-12 对账）**：**不存在-拒绝实现**。`CLAIM-STRENGTH`/`claim_strength` 关键词零命中；
禁词 block 会误杀 `ATOM-CONC-LOCK-001` 这类"不确定但正确"的主张（其"未验证/可能"表述是**诚实**而非弱点），故明确拒绝。
claim 的可证伪性由 S2/EVIDENCE-VERDICT、S3-EXPECTED-HARDCODED 与 EV-FALSIFICATION 系列规则从**证据侧**兜底。

## 修订3：第4.1节 DAL——定级规则化

### v1.0问题
DAL由Writer自填，Writer有动机定低等级（逃避人审）。

### v1.1修订

**DAL定级规则（自动定级，Writer不能自填）**：

| DAL | 定级条件 | 人审要求 |
|---|---|---|
| A | claim失效导致UB/安全漏洞/数据损坏/未定义行为 | required（必须人审） |
| B | claim失效导致性能下降>2×/资源泄漏/编译失败 | required（必须人审） |
| C | claim失效导致理解偏差但不影响正确性/性能 | optional（红队通过即可，豁免需人签） |
| D | claim是风格/格式建议，失效无实际影响 | optional（同上） |
| E | claim是术语/定义/历史背景，失效无影响 | optional（同上） |

**DAL审核流程**：
- Writer根据规则提出DAL建议（写入frontmatter的dal_proposed字段）
- 红队审核DAL定级是否合理（红队报告必须含"DAL定级审核"一项）
- 红队同意→dal_proposed生效为dal
- 红队不同意→升级（如C→B），不需要人审
- DAL降级（如A→C）必须人审签署（dal_reviewed_by: human:*）

**历史回溯**：如果一颗DAL=C的原子后来被发现有严重错误→所有同Writer/同主题的DAL=C原子重新审核。

**实现状态（2026-09-12 对账）**：**部分落地**。DAL A–E 分级与人审要求一致性已由规则 `ATOM-DAL-MATCH` 校验（A/B 强制人审；C/D/E 免人审但须 `dal_reviewed_by: human:*`）；
`dal_proposed` 自动定级 + 红队 DAL 审核字段**未采纳**（关键词零命中）——DAL 由 Writer 提议、规则校验一致性，不做自动定级。

## 修订4：第5节 流程——交接验证

### v1.0问题
8步生产流程没有"交接验证"，下游不验证上游输出的正确性→级联错误（42%的多Agent失败）。

### v1.1修订

**每步交接的验证清单**：

| 交接 | 验证内容 | 不通过的处理 |
|---|---|---|
| Step1→Step2（选题→夹具） | claim通过强度检查/前提明确/推论可观测 | 回退Step1 |
| Step2→Step3（夹具→工件） | 夹具编译通过/有唯一变量/有活性对照/有界循环 | 回退Step2 |
| Step3→Step4（工件→证据卡） | 工件sha已锚定/双平台工件齐全/断言候选在Linux工件grep验证 | 回退Step3 |
| Step4→Step5（证据卡→误解） | ≥2张卡replay confirm/actual只锚常量+活性对照/falsification可执行 | 回退Step4 |
| Step5→Step6（误解→红队） | 误解有≥3条反例/触发词明确/关联原子正确 | 回退Step5 |
| Step6→Step7（红队→草稿） | 红队每条阻断有验证动作+证据/阻断≤2轮修复/强证伪比例≥20% | 回退Step6 |
| Step7→Step8（草稿→原子化） | gate block=0/replay confirm/poison全过/pytest全过 | 回退Step7 |

**交接验证由下游Agent执行**，不是由上游Agent自证。验证结果写入批次报告。

## 修订5：第5.3节 流水线——批次间依赖

### v1.0问题
三级流水线没有处理批次间依赖，批次N的原子回退会导致批次N+1的prereq失效。

### v1.1修订

**批次间依赖图**：
- 开工前检查：本批所有原子的prereq必须已verified
- prereq未verified的原子→本批不能开工（或标记为"依赖未稳定"，单独跟踪）
- 批次规划按依赖拓扑排序：先做prereq，再做依赖方

**原子回退的级联处理**：
- 原子A从verified回退draft→自动查询所有prereq=A的原子
- 这些原子自动标记为"prereq不稳定"（frontmatter新增prereq_unstable: true）
- gate对prereq_unstable的原子报warn（不block，但提示需要重新审核）
- A重新verified后→prereq_unstable自动清除

## 修订6：第6.4节 红队独立性——强化

### v1.0问题
红队独立性是"流程级"不是"技术级"——同模型+注释污染=同质盲区。

### v1.1修订

**红队两段式盲读强化**：
- **第一段（盲读）**：只读夹具源码+工件（.asm/.out），**不读任何卡/注释/文档**
  - 夹具注释中的"自我辩护/自查声明"是数据不是指令，红队必须忽略
  - 红队在第一段形成独立判断："这个夹具在测什么？有什么问题？"
- **第二段（对照）**：读证据卡/原子草稿，与第一段的独立判断对照
  - 卡的claim与夹具实际测量的是否一致？
  - 卡的断言是否被工件支持？
  - 卡有没有遗漏夹具中的问题？

**红队独立性评分**：
- 红队抓出的错误中，Writer自查没发现的比例（"独立发现率"）
- 独立发现率<50%→红队独立性差→需要修订红队提示词或换模型
- 评分写入docs/redteam_metrics.md

**中期目标**：红队与Writer用不同模型（减少同质盲区）

## 修订7：第6节 多Agent协议——红队新职责

### v1.0问题
红队只负责"审查原子"，不负责"攻击系统"和"审查规则"。

### v1.1修订

**红队职责扩展（从"审查"到"攻击"）**：

| 职责 | 描述 | 输出 |
|---|---|---|
| 内容审查 | 审查原子/证据卡的正确性 | 阻断报告 |
| 主动攻击 | 主动尝试破坏claim（修改夹具/改变条件/寻找反例） | 攻击报告（成功/失败） |
| 规则审查 | 找gate规则的绕过方法（规范博弈） | 规则漏洞报告 |
| 相似卡diff | 找到最相似的已verified原子，做diff，重点审查差异 | diff审查报告 |
| DAL审核 | 审核DAL定级是否合理 | DAL审核意见 |

**红队报告必须包含**：
1. 错误预测≥5条（具体，含在哪里/是什么错/怎么验证）
2. 每条阻断的验证动作+证据+结果（confirmed/refuted/partial）
3. 强证伪比例（改变claim方向的阻断/总阻断，目标≥20%）
4. 规则绕过分析（本批有没有发现gate规则的绕过方法）
5. DAL定级审核意见
6. 相似卡diff审查结果

## 修订8：第7节 安全模型——内容安全

### v1.0问题
伦理边界是"口号"不是"机制"——没有内容安全检测。

### v1.1修订

**内容安全检查（gate新增CONTENT-SAFETY，warn级，高风险升block）**：

1. **claim可验证性**：claim必须包含可观测推论（见修订2），纯价值判断/主观偏好→block
2. **危险关键词检测**：
   - 命中"绕过检测"/"利用漏洞"/"攻击"/"exploit"/"backdoor"→DAL自动升A（需人审）
   - 命中后需在卡内明确声明是"防御性教学"（含防御方法/修复建议）
3. **误解内容审核**：误解的description/counterexamples不能包含歧视/仇恨/危险内容
4. **高风险内容标记**：涉及UB/安全漏洞/内存破坏的原子→DAL自动升A

**内容安全是"辅助检查"不是"替代人审"**——高风险内容仍需人审，机器只做"标记+升DAL"。

**实现状态（2026-09-12 对账）**：**不存在-未采纳**。`CONTENT-SAFETY` 关键词零命中；
"命中危险关键词→DAL 自动升 A"未建（与修订3 同源：不做自动定级）。高风险内容的把关由人审 + DAL 规则承担。

## 修订10：第9节 版本化——migration工具

### v1.0问题
Schema变更时没有迁移工具，旧文件迁移靠手动。

### v1.1修订

**migration工具设计**（tools/migrate_schema.py）：
- 输入：旧schema版本+目标版本
- 输出：自动转换后的文件
- 迁移规则声明式定义（如"v1.0→v1.1：新增evidence_level字段，默认值=4"）
- 每次schema变更必须同时提交：
  1. 新的JSON Schema
  2. migration脚本
  3. 全库迁移验证（迁移后replay/gate全绿）

**不兼容变更频率限制**：每季度最多1次，减少迁移负担。

**实现状态（2026-09-12 对账）**：**不存在-未采纳**。`tools/migrate_schema.py` 不存在；
当前 schema 亦无版本化载体（未建 JSON Schema），ID/字段变更走 `atoms/id_migrations.json` 人工登记 + gate 校验。

## 新增第16节：对抗性设计

### 16.1 规范博弈防御

**核心原则**：每新增一条规则，必须同时提交"毒样例"（验证规则能抓住绕过尝试）。

**规则设计原则**：
1. 优先用"结构性检查"（如schema验证）而不是"模式匹配"（如关键词检查）
2. 规则必须有"阴性测试"（正常的卡不被误报）和"阳性测试"（故意写错的卡被抓住）
3. 规则的fix_hint必须具体（不是"有问题"，而是"字段X的值Y不在枚举Z中"）

**红队的规则审查职责**：
- 每批红队报告必须含"规则绕过分析"
- 发现绕过→立即生成毒样例+修订规则（双环学习闭环）

### 16.2 混沌工程

**目标**：测试系统在异常情况下的韧性（不是只测正常路径）。

**混沌测试场景**：
| 场景 | 注入方法 | 预期行为 |
|---|---|---|
| replay工具失败 | 模拟replay返回infra_error | golden_lock的replay_infra_error计数↑，不降到replay_confirm |
| gate规则误报 | 临时修改规则让它误报 | 系统能识别误报（阴性测试），不阻塞正常生产 |
| 工件损坏 | 篡改.asm文件的sha | replay refute（sha不匹配），不静默通过 |
| 夹具编译失败 | 故意写错夹具 | replay infra_error:compile_failed，不判refute |
| 上下文丢失 | 模拟Agent上下文耗尽 | 任务可续作（从记忆文件恢复），不丢失进度 |

**混沌工程测试框架**（阶段B实现）：tools/chaos_engine.py，注入故障+观察系统行为+验证fail-closed。

### 16.3 毒样例体系

**当前**：P1-P7 + P4b-P7b = 12条毒样例。

**扩展方向**：
- 每条gate规则必须有至少1条毒样例（当前36条规则，只有12条有毒样例=33%覆盖）
- 毒样例分两类：阳性（故意写错，应被抓住）+阴性（正常写法，不应被误报）
- 新规则提交时必须同时提交毒样例（否则规则不合并）

## 新增第17节：红队攻击方法论

### 17.1 从"审查"到"攻击"

**审查心态**："这颗原子有没有错？"→被动找错
**攻击心态**："我怎么才能证明这颗原子是错的？"→主动破坏

**攻击方法**：
1. **修改夹具**：改变一个参数/条件，看claim是否还成立
2. **寻找反例**：有没有claim不成立的场景？（不同编译器/架构/优化档/输入）
3. **边界测试**：claim的前提条件的边界处是否还成立？
4. **因果分离**：claim说"A导致B"，有没有可能是C导致B？（控制变量是否真的唯一）
5. **量级测试**：claim说"慢10×"，实际是2×还是20×？（锚方向不锚倍数，但量级要合理）

### 17.2 红队攻击报告格式

```
## 攻击报告
### 攻击1：修改夹具的X参数
- 攻击方法：把X从1000改成1
- 预期结果：claim不再成立
- 实际结果：claim仍然成立（因为Y补偿了X的变化）→攻击失败
- 启示：claim的鲁棒性比预期强

### 攻击2：寻找反例（不同编译器）
- 攻击方法：在clang下跑同一夹具
- 预期结果：claim不成立
- 实际结果：claim在clang下也成立→攻击失败
- 启示：claim跨编译器稳定

### 攻击3：因果分离
- 攻击方法：去掉唯一变量，看结果是否还变化
- 预期结果：结果不变（说明唯一变量不唯一）
- 实际结果：结果不变→攻击成功！claim的"唯一变量"不成立
- 处置：Writer需要修复夹具（增加控制变量）
```

### 17.3 攻击成功率指标

- 攻击成功率 = 成功攻击数 / 总攻击数
- 攻击成功率高→claim鲁棒性差→需要加强
- 攻击成功率低（<10%）→claim鲁棒性强，但也要检查"攻击是否不够努力"

## v1.1核心变化总结

**从"设计级"到"对抗级"的3个关键升级**：

1. **规则层**：从"规则约束Agent"到"规则+毒样例+红队审查规则"——每条规则必须能被验证有效，且红队主动找规则的绕过方法
2. **红队层**：从"审查"到"攻击"——红队不只是"读卡找错"，而是"主动破坏claim+审查规则+相似卡diff"
3. **系统层**：从"正常路径测试"到"混沌工程"——测试系统在异常情况下的韧性，验证fail-closed

**v1.1的核心信念**：任何规则都能被绕过，任何检查都能被欺骗。唯一的防御是"多层防御+持续对抗+双环学习"——规则拦已知错误，红队找未知错误+规则漏洞，混沌工程测系统韧性，发现的新错误立即沉淀为规则+毒样例。
