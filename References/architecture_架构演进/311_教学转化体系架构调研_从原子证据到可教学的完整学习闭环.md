# 311_教学转化体系架构调研_从原子证据到可教学的完整学习闭环

> 2026-09-12 · 当前 23 颗原子是"证据库"，但没有转化为教学内容（章节/实验/习题/面试题）。
> 本文调研如何建立从原子到教学的完整转化体系。
> 关联：atoms/（23 颗）· Book/（151 文件）· M1_ontology · 309 Book 同步

---

## 一、现状诊断

### 1.1 原子的教学转化缺口

| 原子内容 | 已转化 | 未转化 |
|---|---|---|
| claim（核心论断） | ✅ 原子卡内 | ❌ 教材章节 |
| hypothesis（为什么） | ✅ 原子卡内 | ❌ 教学讲解 |
| 证据卡 actual（实验数据） | ✅ 证据卡 | ❌ 教材中的实验结果展示 |
| 夹具（示例代码） | ✅ Examples/atoms/ | ❌ 教材中的可运行示例 |
| 误解（常见误区） | ✅ misconceptions/ | ❌ 教材中的"误区"框 |
| 红队阻断（易错点） | ✅ 质检报告 | ❌ 教材中的"注意"框 |
| 实验设计 | ❌ | ❌ 实验手册/作业 |
| 习题 | ❌ | ❌ 练习题 |
| 面试题 | ❌ | ❌ 面试指南 |
| 可视化 | ❌ | ❌ 图解/动画 |

**问题**：原子是"为验证存在"的，不是"为教学存在"的。每颗原子有完整的证据，但没有转化为学习者可以直接使用的教学内容。

### 1.2 CPP-Bible 的教学目标

用户的目标是"理论 + 源码 + 历史 + 工程 + 实战 + 思维"的完整知识体系。这意味着每颗原子应该能转化为：

1. **教材章节**（理论）
2. **源码阅读任务**（源码）
3. **历史故事**（历史）
4. **工程案例**（工程）
5. **实验/作业**（实战）
6. **思考题/面试题**（思维）

当前原子只覆盖了"理论"和"证据"，其余 4 项都是空白。

## 二、教学转化体系设计

### 2.1 原子的六维转化

每颗原子可以转化为六个维度的教学内容：

| 维度 | 产出物 | 来源 | 格式 |
|---|---|---|---|
| 理论 | 教材章节 | claim + hypothesis + pedagogy | Book/partXX/chYY.md |
| 源码 | 源码阅读任务 | 夹具 + 工件 | docs/source_reading/ATOM-XXX.md |
| 历史 | 历史故事 | sources + first_hand | Book/part01_history/ 或原子内"历史背景"节 |
| 工程 | 工程案例 | 红队阻断 + 修订记录 | docs/case_studies/ATOM-XXX.md |
| 实战 | 实验/作业 | 夹具 + 证据卡 | docs/labs/ATOM-XXX.md |
| 思维 | 思考题/面试题 | claim_boundary + 误解 | docs/interview/ATOM-XXX.md |

### 2.2 转化模板

#### 2.2.1 实验手册（docs/labs/）

```markdown
# 实验：<原子标题>

## 实验目标
- 验证 <claim>
- 掌握 <核心技能>

## 前置知识
- <prerequisites 中的原子>

## 实验步骤
1. 编译夹具：`g++ -std=c++23 -O2 -o atom_xxx Examples/atoms/_atom_xxx.cpp`
2. 运行并观察输出
3. 修改参数（如优化级别、线程数），观察变化
4. 回答思考题

## 预期结果
<来自证据卡的 actual 数据>

## 思考题
1. <来自误解的反例>
2. <来自 claim_boundary 的边界问题>
3. <延伸问题>

## 拓展
- <related 原子>
- <外部资料>
```

#### 2.2.2 源码阅读任务（docs/source_reading/）

```markdown
# 源码阅读：<原子标题>

## 阅读目标
- 理解 <核心数据结构/算法>
- 识别 <关键设计模式>

## 阅读清单
| 文件 | 行数 | 重点 |
|---|---|---|
| Examples/atoms/_atom_xxx.cpp | L1-50 | 核心数据结构 |
| Examples/atoms/_atom_xxx.asm | L100-150 | 编译器生成的关键指令 |

## 引导问题
1. 为什么这里用 <某个设计>？
2. 如果改成 <另一种设计>，会怎样？
3. <关键函数> 的时间/空间复杂度是多少？

## 延伸阅读
- <相关开源项目的源码>
```

#### 2.2.3 面试题（docs/interview/）

```markdown
# 面试题：<原子主题>

## 基础题
Q: <来自误解的常见错误>
A: <原子 claim 的简明回答>

## 进阶题
Q: <来自 claim_boundary 的边界问题>
A: <详细分析，引用证据卡数据>

## 系统设计题
Q: <工程场景，如"如何设计一个高并发计数器">
A: <结合多颗原子的综合回答>

## 代码题
Q: <写一段代码验证某个结论>
A: <夹具的核心部分>
```

#### 2.2.4 工程案例（docs/case_studies/）

```markdown
# 工程案例：<原子标题>

## 问题
<真实工程问题，来自红队阻断或修订记录>

## 错误做法
<初版的错误，含代码和错误原因>

## 正确做法
<修复后的代码，含为什么这样做>

## 教训
<可复用的工程原则>

## 相关原子
- <related 原子>
```

### 2.3 转化优先级

不是每颗原子都需要六维全转化。按 DAL 和教学价值分级：

| DAL | 转化维度 | 理由 |
|---|---|---|
| A（高风险） | 六维全转化 | 读者最容易出错，需要最多教学支撑 |
| B（教学结论方向） | 理论 + 实验 + 面试题 | 核心概念，需要深入理解 |
| C（定量结论） | 理论 + 实验 | 数据驱动，实验最重要 |
| D（补充） | 理论 | 了解即可 |
| E（参考） | 仅原子卡 | 备查 |

### 2.4 自动生成工具

写 `tools/atom_to_teaching.py`，从原子自动生成教学内容的初稿：

```bash
# 生成实验手册初稿
python tools/atom_to_teaching.py --atom PERF-004 --type lab

# 生成面试题初稿
python tools/atom_to_teaching.py --atom PERF-004 --type interview

# 生成全部六维
python tools/atom_to_teaching.py --atom PERF-004 --all
```

**生成逻辑**：
- 从原子 frontmatter 提取 claim/hypothesis/pedagogy
- 从证据卡提取 actual 数据
- 从误解提取反例
- 从夹具提取代码
- 按模板填充，生成初稿
- Writer/红队审核后定稿

## 三、学习路径设计

### 3.1 基于原子图谱的学习路径

利用 306 的知识图谱，为学习者生成个性化学习路径：

```
初学者路径：
  VALUE-001（值类别）→ MOVE-002（移动语义）→ RAII-001（RAII）
  → UNIQUE-001（unique_ptr）→ SHARED-001（shared_ptr）→ WEAK-001（weak_ptr）
  → NEW-001（new/delete）→ ALIGN-001（对齐）

进阶路径：
  PERF-001（移动性能）→ PERF-003（小对象分配器）→ PERF-004（false sharing）
  → ALLOC-001（allocator）→ ALLOC-002（分配器策略）

专家路径：
  LEAK-001（泄漏检测边界）→ LEAK-002（检测工具边界）
  → UB-GRAY-001（UB 灰区）→ CONC-001（内存序）→ CONC-003（数据竞争 UB）
```

### 3.2 学习进度追踪

为学习者建立"原子掌握度"记录：
- 未读 → 已读 → 已做实验 → 已做习题 → 已讲解（费曼学习法）
- 每颗原子的掌握度影响后续推荐

## 四、与其他系统的关系

### 4.1 与 Book 同步（309）的关系

- 教学转化的"理论"维度 = Book 章节
- 309 建立的 `<atom>` 标注是教学转化的入口
- 教学转化的其他维度（实验/源码/面试题）是 Book 的补充材料

### 4.2 与知识图谱（306）的关系

- 学习路径基于原子图谱的关系（prerequisites/builds_on）
- 知识空白发现 = 学习路径的缺口
- 图谱可视化 = 学习地图

### 4.3 与 G6 四级状态的关系

- 只有 red-team-verified 以上的原子才能转化为教学内容
- draft/machine-verified 的原子不能出现在教材/实验中（防止未验证的结论）
- 教学内容的质量 = 原子的验证等级 × 转化质量

## 六、开放问题

1. **教学内容的维护成本**：每颗原子六维转化，23 颗就是 138 份文档。是否需要全量转化？
   - 建议：按 DAL 分级，A/B 全转化，C/D 只转化实验，E 不转化
2. **自动生成的质量**：atom_to_teaching.py 生成的初稿可能质量不高，需要多少人工审核？
   - 建议：初稿生成后必须经 Writer 审核，红队抽查
3. **与 Book 的重复**：教学内容和 Book 章节可能重复，如何避免？
   - 建议：Book 是"叙事"，教学内容是"练习"，两者互补不重复
4. **学习者反馈闭环**：如何收集学习者的反馈，持续优化教学内容？
   - 建议：初期不做，等有实际学习者后再考虑

---

*核心结论：原子是"证据库"，但 CPP-Bible 的目标是"教材"——需要把原子转化为六维教学内容（理论/源码/历史/工程/实战/思维）。转化不需要全量，按 DAL 分级：A/B 全转化，C/D 只转化实验。关键工具是 atom_to_teaching.py（自动生成初稿）+ 六维模板。先选 3 颗高 DAL 原子试点，验证模板后再批量推广。教学转化是原子从"为验证存在"到"为教学存在"的关键一步。*
