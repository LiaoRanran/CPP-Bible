# 398 P0 落地实施方案与自我内卷：从 7 项精简到 3 项核心

> 日期：2026-09-13。397 修正后 P0 有 7 项。本份做两件事：①给出每项的具体落地方法、依赖、完成标准；②自我内卷批判，精简到"真正必须先做的 3 项"。

## 一、7 项 P0 的落地拆解

### P0-1：负面指令改正面

**方法**：
1. 扫描 312（28KB）中所有负面表述："不要/禁止/不得/严禁/避免/切勿/不可"
2. 逐条改写为正面表述
   - 例："不要在断言中使用时序数据" → "断言只锚常量和活性对照"
   - 例："不得编造未实测的数字" → "所有数字必须来自实测或标准条文"
3. 保留必要的负面指令（如"禁止地图渲染"——正面表述反而不清晰）

**工具**：`grep -n "不要\|禁止\|不得\|严禁\|避免\|切勿" 312*.md` 列出所有候选，人工逐条判断

**完成标准**：312 中负面指令数量减少 ≥50%，且改写后跑 1 批产出质量不降级（红队阻断数不增加）

**依赖**：无

### P0-2：搜索提示词加查询分解

**方法**：
1. 在搜索/调研提示词开头加："先将问题分解为 2-3 个子查询，分别搜索，再综合。每个子查询必须覆盖不同维度。"
2. 加"信息缺口检测"：搜索后问"还有什么关键信息没找到？"

**完成标准**：调研提示词已更新；下一次调研使用分解法，记录子查询数量和结果覆盖率

**依赖**：无

### P0-3：正例回归制度化

**方法**：
1. 流程纪律：每次加新规则后，必须跑 `gate_engine.py --check`，记录存量 56 卡的命中数
2. 命中>0 时逐条确认：是"真债"（存量卡确实有问题）还是"误伤"（规则太宽）
3. 误伤必须收窄规则或降为 warn，不能带着误伤上线

**工具**：不需要改工具，`gate_engine.py --check` 已经输出全库命中

**完成标准**：新规则上线时的提交信息必须包含"存量命中数：X（真债 Y / 误伤 Z）"

**依赖**：无

### P0-4：EIR 追踪加"红队裁决"列

**方法**：
1. 质检报告模板加表格：红队发现 | 级别 | 裁决（采纳/驳回）| 理由
2. EIR = 采纳数 / 总修复操作数（只算阻断级和高级，建议级不计）
3. 区分"红队误判"（驳回且经原文/工件核实）和"红队正确但不采纳"（驳回但有理由）

**完成标准**：下一批质检报告使用新模板，EIR 有明确数值

**依赖**：无

### P0-5：手动可观测性

**方法**：
1. 质检报告模板加头部：
   - 本批对话轮次（估算）
   - 本批耗时（从开始到结束）
   - 产出：原子数 / 证据卡数 / 规则数 / 毒样例数
   - 门禁：replay/gate/poison/pytest 结果
2. token 估算：用"提示词字数 + 产出字数 × 1.3（中文 token 系数）"粗估
3. 连续记录 3 批后，看趋势

**完成标准**：连续 3 批质检报告包含可观测性头部

**依赖**：无（但 P0-6 的 A/B 测试依赖它）

### P0-6：312 压缩实验

**方法**：
1. 先做 P0-1（负面改正面）——这本身就是压缩
2. 再删重复内容（312 里纪律说明可能重复出现）
3. 把"参考资料/背景知识"移到附录或外部链接
4. A/B 测试：压缩版 vs 原版各跑 1 批，对比产出质量（红队阻断数）和 token 数

**完成标准**：312 体积减少 ≥30%，且 A/B 测试产出质量不降级

**依赖**：P0-1（负面改正面）、P0-5（可观测性，用于 A/B 测试的 token 对比）

### P0-7：claim 反事实字段

**方法**：
1. 原子卡 frontmatter 加 `counterfactual:` 字段
2. 写"什么观测会推翻这个 claim"
   - 例 PERF-004："如果 alignas 隔离后 tight 不再更慢，则 claim 不成立"
   - 例 LEAK-002："如果加 volatile 后 LSan 仍零报告，则'代码形态敏感'不成立"
3. 存量 27 颗不回填（新卡用新格式，存量逐步迁移）

**完成标准**：下一批新原子全部包含 counterfactual 字段

**依赖**：无

## 二、自我内卷批判（5 处）

### 批判 1：P0-1 和 P0-6 是同一件事

负面改正面是压缩的一种手段。先做 P0-1，看压缩了多少。如果已经 ≥30%，P0-6 的"其他压缩手段"就不需要了。

**修正**：合并为一项"312 优化（负面改正面+去重+压缩）"，目标是体积减 ≥30% 且质量不降级。

### 批判 2：7 项还是太多，真正"立刻有回报"的只有 3 项

| 项 | 做了立刻有回报？ |
|---|---|
| 负面改正面+压缩 | ✅ 立刻减 token |
| 正例回归制度化 | ✅ 立刻防误伤（373 已经踩过误伤的坑） |
| 手动可观测性 | ✅ 立刻有数据（后续所有优化的前提） |
| 查询分解 | ⚠️ 调研质量提升，但不直接影响生产 |
| EIR 追踪 | ⚠️ 放权前提，但当前还没放权 |
| claim 反事实 | ⚠️ claim 质量提升，但下一批才见效 |
| 312 压缩（已合并） | ✅ 见上 |

**真正的 P0 只有 3 项**：可观测性、312 优化、正例回归。其余 4 项是 P1。

### 批判 3：可观测性的 token 数据来源有限

豆包客户端不暴露 API token 统计。只能用"字数 × 系数"粗估，误差可能 ±30%。

**修正**：可观测性先记录"确定性数据"（耗时、原子数、卡数、门禁结果），token 只做粗估并标注"估算值"。等有精确数据来源后再升级。

### 批判 4：正例回归的"流程纪律"是最脆弱的

人会忘。最好加个工具标志：`gate_engine.py --regression` 输出"存量命中数 + 逐条分类"，新规则上线前必须跑。

但这需要改工具，不是"零成本"。**折中**：先做流程纪律（提交信息必须包含存量命中数），跑 3 批后如果发现经常忘，再加工具标志。

### 批判 5：缺少"回滚机制"

如果 P0-1（负面改正面）导致产出质量下降，怎么回滚？
- git 可以回滚提示词文件
- 但如果已经用压缩版提示词生产了原子，这些原子的质量可能受影响
- **修正**：P0-1 先在分支上做，A/B 测试通过后再合并到 master

## 三、精简后的 P0（3 项核心 + 完成标准）

### 核心 1：手动可观测性（零成本，立即做）

**做什么**：质检报告模板加头部（耗时/产出数/门禁结果/token 粗估）

**完成标准**：连续 3 批报告包含头部，形成趋势数据

**为什么先做**：后续所有优化（压缩、路由、放权）都需要数据支撑

### 核心 2：312 优化（负面改正面+去重+压缩，半天）

**做什么**：
1. 负面指令改正面（目标减 ≥50% 负面表述）
2. 删除重复内容
3. 背景知识移附录
4. A/B 测试（压缩版跑 1 批，对比红队阻断数）

**完成标准**：312 体积减 ≥30%，A/B 测试红队阻断数不增加

**为什么先做**：直接对应用户"不浪费 token"的核心诉求，且 312 是生产提示词，每天都在用

### 核心 3：正例回归制度化（零成本，立即做）

**做什么**：新规则上线时，提交信息必须包含"存量命中数：X（真债 Y / 误伤 Z）"，误伤必须收窄

**完成标准**：下一次加规则时的提交信息包含此字段

**为什么先做**：373 修复批已经实测误伤 6 张，这是真实发生过的问题，零成本可防

## 四、P1（原 P0 的其余 4 项，延后）

| 项 | 延后原因 |
|---|---|
| 查询分解 | 调研质量提升，不直接影响生产；等核心 3 项稳定后再加 |
| EIR 追踪 | 放权前提，但当前还没放权；等放权前再做 |
| claim 反事实 | 下一批原子才用；等核心 3 项稳定后加进提示词 |
| （压缩已合并到核心 2） | — |

## 五、执行顺序（有依赖）

```
第 1 天：核心 1（可观测性模板）+ 核心 3（正例回归流程）——零成本，1 小时
第 2-3 天：核心 2（312 优化）——需要 A/B 测试，半天改+1 批验证
第 4 天起：用新模板+新提示词生产，连续 3 批记录可观测性数据
```

**关键**：核心 1 和核心 3 是"改流程/模板"，不影响正在进行的生产。核心 2 需要 A/B 测试，应该在"下一批生产开始前"完成。

## 六、元结论

397 的 7 项 P0 经过自我内卷，精简到 **3 项核心**：
1. **可观测性**（数据基础）
2. **312 优化**（直接省 token）
3. **正例回归**（防误伤）

其余 4 项延后到 P1，不是因为不重要，而是因为"先做最有杠杆的 3 项，用数据验证后再扩展"。

**内卷的价值不是"做更多"，而是"做更少但更准"。** 3 项核心做好了，系统就有了数据基础、成本降低、质量保障——这是后续所有优化的地基。
