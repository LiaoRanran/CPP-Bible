## 三、v8.0 里程碑（按依赖排序）

### M1：断言契约化（S1 基础）

**当前**：claim 是自由文本，红队靠人读判断方向对不对。

**v8.0**：claim 结构化为 `precondition / assertion / invariant / falsification` 四段，每段可机器验证。

```yaml
claim:
  precondition: "4 线程，各累加 1e7 次，相邻布局"
  assertion: "相邻布局比隔离布局慢 ≥10×"
  invariant: "唯一变量 = 布局"
  falsification: "如果隔离布局也慢，则 claim 不成立"
```

**机器可验证的点**：
- precondition 是否在夹具中实现（活性对照）
- assertion 的数值是否在 .out 中出现
- invariant 是否真的是唯一变量（单变量检查）
- falsification 是否有反例对照

**落地**：新原子必须用契约化 claim；存量逐步迁移。

### M2：活性对照自动化（S1 核心）

**当前**：活性对照靠人写（"arena 32→32 不变"），经常漏。

**v8.0**：夹具自动生成活性对照——对每个断言，自动生成"如果这个量是写死的常量，应该不随规模变"的对照。

```
夹具输出：
  arena_meta_total_n1=32
  arena_meta_total_n2=32    ← 活性对照：不随规模变
  pool_meta_total_n1=8056
  pool_meta_total_n2=64056  ← 活性对照：随规模变
```

**机器检查**：如果 claim 说"X 随规模变"，但 X 的 n1==n2 → warn（活性对照失败）。

### M3：relations 推理引擎（S2）

**当前**：relations 只有 L1 结构检查（矛盾/目标存在/DAG 无环）。

**v8.0**：relations 支持 L2-L4 推理：
- L2 影响分析：改 A 之前，列出所有依赖 A 的原子（425 已做 L1）
- L3 传递闭包：A 依赖 B，B 依赖 C → A 间接依赖 C
- L4 跨域迁移：MEM 域的 RAII 模式 → CONC 域的锁管理模式（结构相似）

**落地**：`tools/knowledge_graph.py`，支持 `impact <id> --depth 3`、`transitive <id>`、`migrate <from_domain> <to_domain>`。

### M4：错误模式自动转化（S3）

**当前**：429 设计了半自动化管道（提取→草稿→人审→验证→active），仍需人审。

**v8.0**：人审只做"确认"，不做"设计"——错误模式的检查逻辑由 LLM 生成，拦截率由机器验证，≥70% 自动 active。

```
红队报告 → 自动提取 E1/E2 → LLM 生成检查逻辑 → 历史错误回放
  → 拦截率 ≥70% → 自动 active（人审只做最终确认）
  → 拦截率 <70% → 标记为"需改进"，不进 active
```

**关键**：拦截率是机器算的，不是人评的——这是自治的基础。

### M5：诊断 MCQ + 学习路径（S4）

**当前**：423 只做了闪卡导出（L1）。

**v8.0**：
- L2 诊断 MCQ：每颗原子配 3-5 道选择题，测学生是否理解 claim
- L3 学习路径 DAG：根据 relations 生成"先学什么后学什么"的路径
- L4 错误示例库：把 misconceptions 变成"错误代码+为什么错+怎么改"的活示例

**落地**：`tools/quiz_generator.py`（MCQ 生成）、`tools/learning_path.py`（DAG 路径）。

## 四、v9.0 愿景：自治层

### 4.1 核心命题

**v9.0 = "系统能自己发现问题、自己修复、自己验证"**

- 自治红队：定期自动跑红队，不需要人触发
- 自治修复：红队发现的 E1/E2 错误，自动转化为规则并修复
- 自治更新：编译器升级后，自动重测 performance/tool_observation 类原子
- 自治教学：根据学习者反馈，自动调整闪卡/MCQ 的难度和顺序

### 4.2 v9.0 的前提

v8.0 的 S3（自治进化）必须成熟——错误模式→规则的转化不能有人审瓶颈。否则自治就是"自动产生未经验证的规则"，更危险。

## 六、v7.0→v8.0 的关键风险

### 风险 1：语义校验的"可验证性"边界

不是所有语义都可机器验证。claim 的"方向对不对"可能需要理解 C++ 语义，这超出了纯文件解析的能力。

**缓解**：v8.0 只做"可机器验证的语义"——precondition 是否实现、assertion 数值是否在 .out 中、invariant 是否真的唯一变量。不做"claim 的 C++ 语义对不对"（那仍需红队/人审）。

### 风险 2：LLM 生成检查逻辑的可靠性

M4 用 LLM 生成检查逻辑，但 LLM 可能生成有 bug 的代码。

**缓解**：拦截率验证是硬门槛——生成的检查逻辑必须在历史错误回放中拦截率 ≥70%，否则不 active。buggy 的检查逻辑拦截率会低，自然被过滤。

### 风险 3：知识推理的复杂度膨胀

relations 推理从 L1 到 L4，复杂度指数增长。

**缓解**：按层推进，L2 先做（425 已完成 L1），L3 等 L2 稳定，L4 等 L3 稳定。不跳跃。

## 七、元结论

**v7.0 是"把形式错误拦住"，v8.0 是"把语义错误拦住"，v9.0 是"自己拦住自己"。**

每一代的核心能力：
- v6.0：有架构（知道要做什么）
- v7.0：有工具（能做形式检查）
- v8.0：有理解（能做语义检查）
- v9.0：有自治（能自己进化）

**最关键的洞察**：v8.0 的 M4（错误模式自动转化）是 v9.0 的前提——如果错误模式→规则的转化还需要人审，自治就不可能。所以 v8.0 的核心不是"更多工具"，是"把人审从转化管道中移除"。

**这与用户的目标一致**："放更多权力让它们自动化"——v8.0 就是自动化的关键一跃。
