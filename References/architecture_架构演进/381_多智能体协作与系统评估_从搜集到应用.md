## 二、整理（分类）

### 协作部分

| 模式 | 特征 | 生产占比/代表 |
|---|---|---|
| Supervisor/Hierarchical | 协调者分发+双向汇报 | 我们的监工→建设者/红队 |

| 轴 | 度量 | 我们的现状 |

## 三、挖掘（核心洞察）

### 协作部分

**1. 我们已是最优拓扑**：Orchestrator-Worker（占 70% 生产部署）+ Supervisor 混合，正是我们的监工→建设者/红队结构。Swarm（对等水平通信）不适合我们——三权分立需要集中裁决。**不需要改拓扑，需要的是把现有拓扑做到极致**。

**2. Anthropic 的验证**：2026 年 Anthropic 转向"brain/hands 解耦"（角色限定子代理，减少上下文串扰）——这正是 376 的模型路由 + 379 的角色分层。我们三权分立的方向和业界最前沿一致。

**3. Debate 的价值**：辩论（支持方 vs 挑战方）比单方批判更收敛——不是"你找错"，是"你论证支持、他论证反对，一起收敛"。374 的正反论证强制（建设者必须给支持+反对各≥2条）就是辩论的最小形式。**目前我们只有红队单方批判（挑战方），没有支持方**——缺失的一半。

**4. 竞争驱动探索**：竞争不是坏事，是解空间探索机制。异模型对抗（373）就是竞争——它抓出的逃逸比同模型红队多。**竞争的价值在"视角差异"，不在"谁赢"**。

### 评估部分

**5. 黄金数据集是防退化核心工具**：一个固定的、版本控制的、人签过的测试集，每次改动后跑回归，防止退化。"known-correct = 领域专家签过，不是 GPT-4 同意"——我们的毒样例就是黄金数据集，而且是**对抗产出**（比生产日志挖掘更硬）。

**6. 规模门槛**：POC 50 / 生产 100-200 / 关键任务 300-500+。我们 30 毒样例（含豁免台账）在 POC 和生产的边界。**至少扩到 50+ 才到生产级**。

**7. 四轴缺 efficiency**：AWS 强调"每任务 token、p95 延迟、成本"随时间追踪。我们从不追踪 token 成本——而 376 说 50-70% 任务可用小模型。**没有 efficiency 数据，就无法验证"任务分级+模型路由"是否真的省了**。

**8. KPI 趋势化**：我们有门禁快照（每批 block=0 等），但没有跨批趋势线。**"系统变强没有"需要的是趋势，不是单点**——比如"红队发现的问题严重度分布随时间变化"（从机械可查→方向性错误→语义级），这才是"智能性进步"的度量。

## 四、联系（和我们的映射）

| 外部发现 | 我们的现状 | 差距 |
|---|---|---|
| 协作拓扑 | 已是 Orchestrator-Worker+Supervisor 混合 | 无需改，做到极致 |
| Debate 支持方 | 只有红队（挑战方） | **缺"支持方"——建设者自述是弱支持** |
| Brain/Hands 解耦 | 376 模型路由设计 | 未落地 |
| 黄金数据集 | 毒样例 30（对抗产出） | 规模未达生产门槛 50+ |
| 四轴评估 | correctness+safety+robustness | **缺 efficiency 轴（token/延迟追踪）** |
| KPI 趋势 | 门禁快照 | 无跨批趋势线 |

## 五、批判（哪些不适用）

1. **Swarm/去中心化**：不适用。知识生产需要集中裁决（监工），去中心化会失去一致性。
2. **复杂辩论协议**（三维分类的完整实现）：对我们的粒度过度。我们需要的是"建设者自述支持理由 + 红队挑战"，不是多轮自由辩论（烧 token 且收敛慢）。
3. **Agent-Bench 等通用评估框架**：我们不需要通用 Agent 评估（任务完成率等），我们评估的是**知识生产质量**——毒样例+replay+红队更直接。
4. **端态 DB diff（tau-bench 风格）**：不适用。我们的产物是文档/夹具，不是系统状态。
5. **大黄金数据集（300-500）**：当前原子 27 颗，毒样例 30，扩到 300 需要更多规则和更多原子——**规模要跟着系统增长走，不能提前堆**。

## 六、结合（和已有架构的结合点）

**和 374 正反论证强制**：374 要求建设者给支持+反对各≥2条，381 给出理由——这是"辩论"的最小形式，补上"支持方"缺失的一半。**落地顺序：374 先做，381 验证它有效（红队命中率是否变化）**。

**和 379 自我进化**：黄金数据集（毒样例）是自我进化的地基——每次红队发现新逃逸 → 必须成为毒样例（379 应用2）。381 确认这是业界标准做法（防退化核心工具）。

**和 376 效率**：efficiency 轴追踪（每批 token 成本）是验证 376 模型路由是否有效的必要条件。**没有数据，优化就是玄学**。

**和 poison_drill**：毒样例 14→30 了，381 给出下一个门槛（50+）。但扩毒样例的正确方式不是"为凑数而造"，是"每次真实逃逸都回填"——这强化了 379 的回归强化提示。

## 七、最终应用（分阶段落地）

### 立即落地（零成本）

**应用 1：支持方缺失的补位**
- 建设者提交前自检三问（379 应用3）+ 374 正反论证强制，就是"支持方"
- 红队报告模板加一栏："你认为 claim 最可能成立的理由是什么"——强迫挑战方先理解支持方，避免为批判而批判
- 这是流程改进，零工具成本

**应用 2：KPI 快照制度化**
- 每批验收报告统一记录：gate 规则数 / 毒样例数 / pytest / replay / warn 数 / 红队发现严重度分布 / 原子数 / 证据卡数
- 每批追加一行到 docs/kernel/KPI_trend.md，形成趋势线
- 判断"系统变强"用趋势不用感觉

### 中期落地（需少量工程）

**应用 3：efficiency 轴追踪**
- 每批记录：本次消耗的模型会话数、大致 token 量级、任务数
- 不追求精确（我们无法拿到 token 数），用"会话数×任务复杂度"粗粒度代理
- 目的：验证 376 任务分级是否真省——分级前后对比

**应用 4：毒样例规模增长机制**
- 规则数 × 每规则 ≥1 毒样例 = 最低规模（现在 42 规则、30 毒样例，覆盖率 71%）
- 目标：每个规则 1 阴阳例 + 已知逃逸全回填
- 到 50+ 后宣告"生产级黄金数据集"

### 长期落地

**应用 5：辩论式评审（增强版红队）**
- 红队从"单方盲读批判"升级为"支持方+挑战方两段式"：先让一个 agent 论证 claim 成立的最强理由，再让另一个挑战
- 需要两个独立会话（或一个会话两阶段），token 成本×2，所以先验证单方红队的边际价值再升级
- 这是 373 异模型对抗的扩展——从"攻击"到"全视角评审"

## 九、局限与后续

- 本调研聚焦协作拓扑与评估框架，未覆盖"多 Agent 间知识共享/教学"（一个 Agent 学到的如何教给另一个）——那是分布式记忆问题，当前单机多会话通过记忆文件共享已够用。
- 辩论式评审（应用5）必须先做 A/B：单方红队 vs 双方辩论，哪个性价比高。不能凭"辩论更高级"就升级。
- efficiency 追踪是粗粒度的（拿不到精确 token 数），只能做趋势验证，不能做精确优化依据。
- 黄金数据集规模增长要跟系统增长同步，不能为了达标而堆——凑数的毒样例是浪费。
- KPI 趋势线的初始基线从本批（373 修复批）开始记录，历史批次不补（数据口径不一致，补了反而误导）。
