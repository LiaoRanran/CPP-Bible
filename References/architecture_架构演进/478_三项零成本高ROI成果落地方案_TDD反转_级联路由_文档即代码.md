# 478 三项零成本高 ROI 成果的落地方案设计

> 生成时间：2026-09-14
> 来源：477 中最被低估的 3 项调研成果，全部零成本/低成本但 ROI 极高
> 目标：给出可直接交给苦力执行的详细方案

## 一、TDD 顺序反转（零成本，直击根因）

### 1.1 问题根因

ALLOC-002（口径反转）、LEAK-002（LSan 零报告被推翻）、EV-MEM-017（`_Znwm` vs `_Znwy`）——三个方向性错误的共同根因：

**先写夹具再补断言 → 断言被夹具输出锚定成自证。**

Writer 看到夹具输出 `pool_meta=32`，就写断言 `pool_meta=32`。但如果夹具本身有 bug（口径不统一），断言就把 bug 固化了。红队要花大量时间才能发现"断言和夹具同错"。

### 1.2 改法：先写断言，再写夹具

和 TDD"红→绿→重构"同构：

**旧流程**（当前）：
1. 写夹具 → 编译运行 → 看到输出
2. 根据输出写断言 → 断言必然通过（自证）
3. 写 claim → claim 被输出锚定

**新流程**（TDD 反转）：
1. **基于理论预期写断言**（不看夹具输出，甚至不写夹具）
   - 例如："arena 元数据不随规模变" → 断言 `arena_n1_meta == arena_n2_meta`
   - 例如："pool 元数据随块数增长" → 断言 `pool_n2_meta > pool_n1_meta`
2. 写夹具验证断言
   - 如果断言失败 → 要么理论预期错了，要么夹具有 bug
   - 如果断言通过 → 断言是独立验证，不是自证
3. 最后写 claim（基于断言结果，不是基于夹具输出）

### 1.3 落地方式（零成本，只改提示词）

在 Writer 提示词的生产流程中，把"写断言"提到"写夹具"之前，并增加一条铁律：

> **铁律 P-TDD：断言必须在看到夹具输出之前写好。断言基于理论预期，不基于夹具输出。写完断言后再写夹具，夹具运行结果如果和断言矛盾，必须解释是理论错了还是夹具有 bug，不能改断言去匹配输出。**

具体操作：
1. Writer 先写 `expected:` 段（基于理论）
2. 再写夹具
3. 运行夹具，对比 `expected:` 和实际输出
4. 如果一致 → 写 `actual:`
5. 如果不一致 → 停下来分析，不能静默改 `expected:`

### 1.4 预期效果

- 减少 30-50% 的"断言写死常量/与工件不符"类问题（红队抓得最多的类型）
- claim 不再被夹具输出锚定，方向反转类错误会在生产期就暴露
- 零成本，只改生产顺序

## 二、级联路由（成本降 50-70%）

### 2.1 现状

用户已经在人工做路由：
- 苦力（便宜模型）：干杂活、修复、提交
- 好模型（ds v4.1 flash）：落地系统基线、复杂架构
- 对抗模型（Seed-Evolving/Trae/混元）：红队对抗

但没有系统化的级联机制——每次都靠人判断"这个任务该给谁"。

### 2.2 级联路由原理

**先便宜模型 → 验证 → 不通过升级**。

因为阙疑有确定性验证器（gate/replay/poison/pytest），所以可以：
1. 先用苦力（成本 1×）做任务
2. 用门禁验证结果
3. 如果通过 → 完成，成本 1×
4. 如果不通过 → 升级到好模型（成本 10-100×），成本 1× + 10×

对比"直接用好模型"（成本 10×），级联路由在 50-70% 的任务上能省成本。

FrugalGPT/RouteNLP 实测：40-98% 成本降低，匹配 GPT-4 质量。

### 2.3 任务难度分类

| 难度 | 定义 | 路由 | 预期通过率 |
|---|---|---|---|
| 机械 | 有明确规则、可机器验证（改字段、补测试、跑门禁） | 苦力 | 80%+ |
| 语义 | 需要理解但有验证器（写卡、改 claim、红队） | 苦力→验证→不通过升级 | 60% |
| 创造 | 无明确规则、需要架构判断（新工具、新范式） | 直接好模型 | N/A |

### 2.4 落地方式（低开发成本）

不需要写复杂的路由系统，只需要在任务提示词中加一个"路由标签"：

```
## 任务难度：机械 / 语义 / 创造
## 路由策略：
- 机械：直接执行，完成后跑门禁验证
- 语义：先执行，完成后跑门禁验证，如果失败超过 2 次，标记"需要升级"并停止
- 创造：需要好模型，本 Agent 不执行
```

苦力 Agent 遇到"需要升级"的任务就停下来，等人交给好模型。

### 2.5 预期效果

- 成本降 50-70%（同样额度能跑更多红队/对抗）
- 好模型的精力集中在真正需要创造力的任务上
- 零/低开发成本，只改提示词约定

## 三、文档即代码（doc_lint.py，解决系统性失真）

### 3.1 问题

100+ 份架构文档，反复出现"文档与代码不符"：
- M4 说 21 条规则，实际 51 条（差 30 条）
- G6 定义 5 种状态，代码只有 2 种
- 300 说 36 条规则，实际 48 条
- 414 说 42 规则/47 毒/107 卡，全部与源码不符

这些失真导致：
- 新 Agent 按照过时文档写代码，必然出错
- 架构调研的结论建立在错误数字上
- "文档说 X 但实际 Y"成为反复出现的系统性问题

### 3.2 改法：doc_lint.py

写一个文档质量门禁工具，扫描 docs/kernel/ 和 References/architecture_架构演进/ 中的：

1. **规则名引用**：文档中提到的规则名（如 `EV-FALSIFICATION-QUANT`）必须在 gate_engine.py 的 RULES 中存在
2. **数字引用**：文档中提到的"X 条规则""Y 个毒样例""Z 张卡"必须和实际一致
3. **工具名引用**：文档中提到的工具名必须在 tools/ 目录存在
4. **状态码引用**：文档中提到的状态码必须在 G6 定义中存在

### 3.3 具体实现（约 150 行 Python）

```python
# doc_lint.py 伪代码
import re, yaml
from pathlib import Path

# 1. 收集实际数据
actual_rules = set(re.findall(r"'([A-Z][A-Z-]+)'", gate_engine_source))
actual_tools = {f.stem for f in Path('tools').glob('*.py')}
actual_counts = {
    'rules': len(RULES),
    'poison': count_poison_samples(),
    'atoms': count_atoms(),
    'evidence': count_evidence(),
}

# 2. 扫描文档
for doc in docs:
    content = doc.read_text()
    
    # 检查规则名引用
    for rule_name in re.findall(r'\b([A-Z]{2,}-[A-Z-]+)\b', content):
        if rule_name not in actual_rules and not is_known_false_positive(rule_name):
            warn(f"{doc}: 引用了不存在的规则 {rule_name}")
    
    # 检查数字引用（"X 条规则"模式）
    for m in re.finditer(r'(\d+)\s*条规则', content):
        if int(m.group(1)) != actual_counts['rules']:
            warn(f"{doc}: 说 {m.group(1)} 条规则，实际 {actual_counts['rules']}")
    
    # 检查工具名引用
    for tool_name in re.findall(r'\b(\w+)\.py\b', content):
        if tool_name not in actual_tools:
            warn(f"{doc}: 引用了不存在的工具 {tool_name}.py")
```

### 3.4 接入 CI

在 ci.yml 的 quality job 中加一步：
```yaml
- name: Doc Lint
  run: python tools/doc_lint.py
```

### 3.5 预期效果

- "文档说 21 条规则实际 51 条"这类问题在 CI 阶段就被拦住
- 新 Agent 读到的文档永远和代码一致
- 零成本（已有规则列表和工具列表），开发量约 150 行

## 四、三项的优先级与依赖

| 项 | 成本 | ROI | 优先级 | 依赖 |
|---|---|---|---|---|
| TDD 顺序反转 | 零（改提示词） | 极高（减少 30-50% 断言自证） | P0 | 无 |
| 文档即代码 | 低（150 行 Python） | 高（解决系统性失真） | P0 | 无 |
| 级联路由 | 零（改约定） | 高（成本降 50-70%） | P1 | 需要任务难度分类共识 |

**建议**：TDD 顺序反转和文档即代码立即做（P0），级联路由在任务难度分类达成共识后做（P1）。
