# 303_Writer阶段预防机制架构调研_把红队拦截前置到自检

> 2026-09-12 · 解决"吞吐下降"：红队抓出的问题本应在 Writer 阶段避免，而不是事后修复
> 关联：第五批三个方向性案例（ALLOC-002 口径不统一 / LEAK-002 无关改动翻转 / 040-041 断言未实测）

---

## 一、问题定义

### 1.1 吞吐下降的事实

| 批次 | 窗口数 | 原子数 | 单原子窗口数 | 红队阻断数 |
|---|---|---|---|---|
| 第一批 | 2 | 8 | 0.25 | ~6（一般级） |
| 第二批 | 2 | 4 | 0.5 | ~6（一般级） |
| 第三批 | 3 | 3 | 1.0 | 3 阻断 + 11 高 |
| 第四批 | 3 | 1 | 3.0 | 2 阻断 + 10 高 |
| 第五批 | 6+ | 3 | 2.0 | 6 阻断 + 28 高 |

**趋势**：单原子窗口数从 0.25 涨到 2.0，红队阻断从"一般级"升级到"方向性"。

### 1.2 根因：Writer 阶段缺预防

第五批红队抓出的三个方向性错误，全部是 Writer 阶段可以自检的：

| 红队阻断 | 本质 | Writer 阶段是否可自检 |
|---|---|---|
| ALLOC-002 元数据口径不统一（pool 32B→8056B） | 同一实验用不同口径测量 | ✅ 可自检：写卡前检查"三个策略的元数据定义是否一致" |
| LEAK-002 一 bit 两计（cycle_is_leak ≡ dtor_count==0） | 派生读数冒充独立证据 | ✅ 可自检：写卡前检查"每个读数是否有独立计算路径" |
| EV-MEM-040/041 断言字面量未在 Linux 工件实测 | Windows sha 路径覆盖不到 artifact_assert | ✅ 可自检：写断言前在 Linux .asm 中 grep 验证 |
| PERF-004 padded_shares_line 恒真 0 | 夹具自己写死对照结果 | ✅ 可自检：写夹具后检查"对照变量是否真的在运行时计算" |
| LEAK-002 消除与失败不可区分 | 没有证明分配真发生 | ✅ 可自检：写夹具后检查"是否有活性对照证明分配/构造真发生" |

**结论**：5 个阻断全部可在 Writer 阶段自检。如果 Writer 有预防机制，这些问题不会流到红队，吞吐可以提升 2-3 倍。

### 1.3 为什么 Writer 没有预防

当前 Writer 提示词的结构：
1. 写 claim
2. 写夹具
3. 跑夹具拿数据
4. 写证据卡
5. 自评

**缺少**：在每一步之后的**强制自检**。Writer 写完就往下走，不回头检查。

红队的价值是"独立视角"，但如果 Writer 自己就能检查出 80% 的问题，红队可以专注于更深层的 20%。

## 二、Writer 自检清单设计

### 2.1 五层自检（在每个阶段后强制执行）

#### 第一层：夹具写完后（编译前）

**检查项**：
1. **对照变量是否真的在运行时计算？**
   - 反面：`padded_shares_line = (sizeof(Padded) > kLine) ? 0 : 0`（两支都是字面量 0）
   - 正面：`padded_shares_line = (&padded[1] / kLine == &padded[0] / kLine)`（真地址比较）
2. **是否有活性对照？**
   - 反面：所有读数都是编译期常量
   - 正面：至少一个读数随输入变化（如 arena 32→32 不变、pool 8056→64056 变）
3. **是否重载了 operator new/delete？**
   - 反面：重载后断言只做存在性匹配（自证断言，P4 规则）
   - 正面：不重载，或重载后有调用点计数
4. **同一实验中的多个对象是否用同一口径测量？**
   - 反面：arena 的 meta() 只算 sizeof，pool 的 meta() 算 sizeof+堆数组
   - 正面：三个策略的 meta() 用同一函数、同一拆分（struct_bytes + bookkeeping_bytes）
5. **是否有消除与失败不可区分的风险？**
   - 反面：dtor_count=0 可能是"泄漏"也可能是"构造被优化消除"
   - 正面：有 volatile 构造计数证明分配真发生

#### 第二层：数据拿到后（写卡前）

**检查项**：
1. **每个读数是否有独立计算路径？**
   - 反面：cycle_is_leak = (dtor_count == 0)（1:1 派生）
   - 正面：cycle_allocated（构造计数）、cycle_destroyed（析构计数）、cycle_live_objects（差值）三条不同源
2. **数据是否与 claim 一致？**
   - 反面：claim 说"pool 最省"，数据说"pool 8056B 最大"
   - 正面：claim 按真实数据写，不预设结论
3. **是否有基数不一致？**
   - 反面：比值用排序后中位数，打印用原始序第 4 样本
   - 正面：所有比值用同一基数（同一轮、同一排序方式）
4. **时序数据是否入了断言锚？**
   - 反面：actual 里写"tight=562500600ns"（跨运行会变）
   - 正面：actual 只锚方向（sharing_is_slower=1），时序数据放 .out

#### 第三层：断言写完后（replay 前）

**检查项**：
1. **断言里的每个字面量是否在 Linux 工件中 grep 得到？**
   - 反面：写 `arena_n1_meta_total_bytes=`，但工件里只有 `%s_meta_total_bytes=`（格式串模板）
   - 正面：在 Linux .asm 中 grep 验证，写 `%s_meta_total_bytes=`
2. **断言是否是自证断言？**
   - 反面：夹具自定义 operator delete[]，断言 contains "_ZdaPvy"（定义处即满足，零调用点）
   - 正面：断言检查调用点（call_count）或不重载
3. **断言是否有判别力？**
   - 反面：use_count after join=1（对"原子/非原子"零判别力）
   - 正面：lock 指令计数（unique_ptr 0 条 vs shared_ptr 3+ 条）

#### 第四层：证据卡写完后（红队前）

**检查项**：
1. **claim 是否可证伪？**
   - 反面："三实现各有特点"（无法证伪）
   - 正面："libstdc++ 32B/15 字符，libc++ 24B/22 字符，MSVC 32B/15 字符"（具体数字可证伪）
2. **claim 是否 ≤50 字？**（296 claim 契约 v0.2）
3. **是否有竞争假设？**（至少 2 个替代解释）
4. **limitations 是否写了前提条件？**
   - 反面：arena"零碎片"不写前提
   - 正面：arena"零碎片"前提是"批量申请+整体释放，中途释放单块会产生空洞"

#### 第五层：自评前（提交前）

**检查项**：
1. **夹具名是否与已有夹具重名？**
2. **误解编号是否存在？**（MIS-MEM-026 不存在会在 git mv 时 block）
3. **frontmatter 字段是否完整？**（status/type/dal/verified_by/status_history）
4. **rubric_self 是否 ≤4？**（未自封 verified）
5. **是否有未处置的红队阻断？**（如果是红队后修改）

## 三、实现方式

### 3.1 提示词嵌入（最轻量）

在 Writer 提示词中嵌入自检清单，每完成一个阶段后强制过一遍。

**优点**：零工具改动，立即生效
**缺点**：依赖 Writer 自觉，可能跳过

### 3.2 gate 规则固化（机器强制）

把自检清单中可机器检查的项固化为 gate 规则：

| 自检项 | 机器可查？ | gate 规则 |
|---|---|---|
| 断言字面量在 Linux 工件中存在 | ✅ | EV-ASSERT-LINUX-VERIFIED（新增） |
| 自证断言（重载 + contains） | ✅ | EV-SELF-SATISFIED-ASSERT（已有 P4） |
| 误解编号存在 | ✅ | MIS-ID-EXISTS（已有） |
| frontmatter 字段完整 | ✅ | ATOM-FRONTMATTER（已有） |
| claim ≤50 字 | ✅ | CLAIM-LENGTH（新增） |
| 对照变量是否运行时计算 | ❌ | 需红队/人工 |
| 同一口径测量 | ❌ | 需红队/人工 |
| 活性对照 | ❌ | 需红队/人工 |
| 独立计算路径 | ❌ | 需红队/人工 |

**结论**：约 40% 的自检项可机器固化，60% 需 Writer 自觉 + 红队复核。

### 3.3 Writer 自检脚本（半自动）

写一个 `tools/writer_selfcheck.py`，在 Writer 完成后自动运行：
- 检查断言字面量在 Linux 工件中存在
- 检查 claim 长度
- 检查误解编号存在
- 检查 frontmatter 完整
- 检查夹具名不重名
- 输出"通过/警告/失败"

**优点**：比纯提示词更可靠，比 gate 更前置（Writer 阶段就能发现）
**缺点**：需要写脚本，且只能覆盖可机器检查的项

## 四、预期效果

### 4.1 红队阻断减少

| 阻断类型 | 当前（无预防） | 有预防后 | 减少 |
|---|---|---|---|
| 口径不统一 | 1/批 | 0/批 | -100% |
| 一 bit 两计 | 1/批 | 0/批 | -100% |
| 断言未实测 | 1/批 | 0/批 | -100% |
| 恒真对照 | 1/批 | 0/批 | -100% |
| 消除与失败不可区分 | 1/批 | 0/批 | -100% |
| 深层架构问题（红队核心价值） | ~1/批 | ~1/批 | 0% |

**预期**：红队阻断从 5-6 个/批降到 1-2 个/批，且剩下的都是深层问题（红队的真正价值）。

### 4.2 吞吐提升

- Writer 阶段增加 10 分钟自检
- 红队阶段减少 30-60 分钟（阻断少了）
- 修复阶段减少 30-60 分钟（不需要改夹具重跑）
- **净节省 50-110 分钟/批，吞吐提升 30-50%**

### 4.3 质量提升

- Writer 自检 = 第一道防线
- gate 规则 = 第二道防线
- 红队 = 第三道防线（专注深层问题）
- 人审 = 第四道防线（方向判断）

四道防线各司其职，不是重复劳动。

## 五、与其他系统的关系

### 5.1 与红队的关系

Writer 自检不是替代红队，而是让红队专注于真正需要独立视角的问题：
- Writer 自检：形式问题、机械问题、可检查问题
- 红队：架构问题、逻辑问题、深层假设问题

### 5.2 与 gate 规则的关系

Writer 自检和 gate 规则是互补的：
- Writer 自检：在 Writer 阶段发现问题（早）
- gate 规则：在提交前发现问题（晚，但机器强制）
- 可机器检查的项应该同时在两处（Writer 自检提醒 + gate 强制拦截）

### 5.3 与证据卡三层分离（302）的关系

三层分离减少了卡的行数，Writer 自检减少了卡的修改次数。两者结合可以显著提升吞吐。

## 七、开放问题

1. **自检清单会不会变成形式主义？**
   - 风险：Writer 可能"走过场"式自检，不真检查
   - 缓解：红队检查 Writer 的自检记录（如果 Writer 说"自检通过"但红队发现了可自检的问题，记为"自检失效"）

2. **自检清单会不会限制创造力？**
   - 风险：Writer 为了通过自检而回避复杂实验
   - 缓解：自检清单是"最低要求"，不是"上限"；复杂实验可以有更多检查项

3. **如何衡量自检的有效性？**
   - 指标：红队阻断中"可自检问题"的比例
   - 目标：从 80% 降到 20% 以下

---

*核心结论：吞吐下降的根因不是红队太严，而是 Writer 阶段缺预防。五层自检清单（夹具→数据→断言→卡→提交）可以把 80% 的红队阻断前置到 Writer 阶段，让红队专注于深层架构问题。这不是"降低标准"，而是"把标准前移"——同样的检查，早做比晚做便宜 10 倍。*
