## 一、增量构建系统：Bazel的缓存键设计直接强化阙疑

### 1.1 外部发现（证据等级：Bazel官方文档+工业实践，硬数据）

- **Bazel**：内容哈希而非时间戳判断文件变化。每个action显式声明inputs/output names/command line/environment variables。
- **缓存查找顺序**：本地缓存→远程缓存→执行action。缓存键 = 所有输入文件哈希 + command + 环境变量。
- **远程缓存**：跨机器复用构建结果，输出=文件名列表+内容哈希。
- **缓存投毒防御**：HMAC签名(action_hash:content_hash)，存储在对象元数据，读取时验证。
- **Ninja**：最小构建系统，基于依赖图的增量构建，不做内容哈希只做时间戳。

### 1.2 对阙疑的意义（关键洞察）

阙疑已经在做内容哈希（artifact_sha256），但**缺少输入哈希**——如果夹具.cpp变了，工件.asm.out必须重生成。Bazel的做法是把所有输入文件的哈希也纳入缓存键。

**落地项 BUILD1（立即可做，零代码）**：阙疑工件缓存键 = sha256(夹具.cpp) + command + compiler版本。如果这三者没变，跳过重编译。这比461的DAG2（只检查夹具.cpp）更精确——command变了（如加了-O2）或编译器升级了，也必须重跑。

**落地项 BUILD2（立即可做）**：工件存于隔离目录（Examples/atoms/已经是），make clean不删证据工件（402 F06的教训——make clean会删光.asm.out）。在Makefile中把Examples/atoms/*.asm.out标记为PRECIOUS。

**证据**：Bazel官方文档+阙疑现有artifact_sha256实践，硬数据。

## 二、属性测试：远期，和突变测试共用基础设施

### 2.1 外部发现（证据等级：QuickCheck论文+Hypothesis工业实践，事实级）

- **QuickCheck**（Haskell，2000，ICFP）：把属性规格转化为测试生成器，跑数千随机输入，找到反例后shrink到最小失败案例。
- **Shrinking是核心价值**：找到失败输入只是一半，shrink到最小才是可调试的。Ericsson案例：50个网络操作→2个操作。
- **Hypothesis**（Python）：黄金标准，pytest集成，strategy-based生成。
- 高级PBT用覆盖率指标引导生成（类似fuzzing）。

### 2.2 对阙疑的意义

阙疑的夹具是C++，Hypothesis是Python的。需要用Python生成C++夹具的参数，然后批量编译运行。

**落地项 PBT1（待验证假设）**：对参数化夹具（如ALLOC-002的n=1000/8000），用Python生成不同n值，验证"元数据随规模变化"属性在所有n下成立。这和461的MUT2（突变测试自动化）可以共用基础设施（Python批量生成→编译→运行→对比）。

**落地项 PBT2（待验证假设）**：shrink应用到红队——红队找到逃逸用例后，自动去掉不必要的步骤，得到最小逃逸用例。

**证据**：QuickCheck/Hypothesis工业实践，事实级。但阙疑场景适用性待验证。

## 三、差分测试：阙疑的多编译器对照升级为显式差分

### 3.1 外部发现（证据等级：McKeeman 1998+多篇arXiv，硬数据）

- **差分测试**（McKeeman 1998）：同一输入多个实现对比输出，任何不一致自动可疑。不需要oracle（正确答案）。
- **编译器差分测试三策略**：(1)不同编译器同优化档 (2)同编译器不同优化档 (3)等价程序同编译器同优化档。
- **LLM4FP**（arXiv 2509.00256）：LLM生成程序+差分测试发现浮点不一致。
- **关键**：-O0和-O2输出不一致→可能是UB（未初始化变量、有符号溢出）。

### 3.2 对阙疑的意义（关键洞察）

阙疑已经在做多编译器对照（MinGW 15.3 / WSL g++13.3 / WSL g++14.2 / riscv64 13.2），但这是**人工差分测试**——目前只检查"replay是否confirm"，没有显式对比多编译器的输出差异。

**落地项 DIFF1（立即可做）**：把多编译器对照形式化为差分测试——同一夹具，四编译器，对比.out的确定性输出。任何不一致自动标记（可能是UB，也可能是编译器bug）。这是UB检测的新方法！

**落地项 DIFF2（立即可做）**：同编译器不同优化档（-O0 vs -O2）差分——如果输出不一致，可能是UB。阙疑的CONC-001已经实测了-O0 vs -O2的差异（inline顺序依赖），但没有形式化为规则。

**落地项 DIFF3（待验证假设）**：差分测试结果写入证据卡的`differential:`字段——哪些编译器一致、哪些不一致、不一致的具体行。

**证据**：McKeeman 1998+阙疑现有多编译器实践，硬数据。

## 四、LLM输出结构化验证：把解析失败率从15-30%降到<0.1%

### 4.1 外部发现（证据等级：JSON Schema Bench arXiv+工业实践，硬数据）

- **约束解码**：每步生成时用FSM限制token选择，数学上保证输出符合schema。
- **JSON mode vs structured outputs**：JSON mode保证有效JSON但不保证schema符合（2-5% mismatch），structured outputs保证schema符合（<0.1%）。
- **解析失败率**：自由文本15-30%、JSON mode 2-8%、structured outputs <0.1%。
- **最佳实践**：`additionalProperties: false`、所有属性`required`、无外部`$ref`、内联`$defs`。
- **JSON Schema Bench**（arXiv 2501.10868）：约束解码的系统评估。

### 4.2 对阙疑的意义

阙疑的提示词目前靠"请输出JSON格式"这种脆弱方式。苦力Agent的红队报告、原子卡草稿都是自由文本，需要人工解析。

**落地项 SCHEMA1（立即可做）**：为苦力Agent的核心产出定义JSON Schema：
- 红队报告schema：`{findings: [{level, title, evidence, fix, status}], summary, verdict}`
- 原子卡frontmatter schema：已有YAML，但可以加JSON Schema验证
- 证据卡actual schema：`{run_match_keys, artifact_assert, expected_sanitizer}`

**落地项 SCHEMA2（立即可做）**：在提示词中提供schema并要求结构化输出。豆包/OpenAI都支持structured outputs。这把"请输出JSON"从提示词工程升级为工程化保证。

**落地项 SCHEMA3（待验证假设）**：阙疑的工具已经输出--json（403 C2），但Agent产出还没有schema。可以为原子卡、证据卡、红队报告分别定义schema，用`jsonschema`库在入库前验证。

**证据**：JSON Schema Bench+工业实践，硬数据。

## 五、技术债量化管理：从"一次性accept"到SQALE式量化

### 5.1 外部发现（证据等级：SonarQube官方+Gartner 2026，硬数据）

- **SQALE模型**：技术债=修复所需时间估计，Technical Debt Ratio，维护性评级A-E（A≤5%, B 5-10%, C 10-20%, D 20-50%, E>50%）。
- **SonarQube Remediation Agent**（2026年9月）：后台agent自动修复历史问题，验证后提PR。
- **技术债消耗21%开发时间**（Sonar 2026）。
- **七指标**：圈复杂度、重复率、内聚性、耦合、bug密度、漏洞累积、人员流动。
- **关键**：技术债是可量化的组合，优先级=技术+业务洞察。

### 5.2 对阙疑的意义（关键洞察）

阙疑的warn债务目前是"一次性accept成基线"（373修复批warn 8→32），没有量化和优先级。golden_lock的accept把所有warn一锅端，无法区分"真实问题"和"误报"。

**落地项 DEBT1（立即可做）**：为阙疑的warn定义量化指标——每条warn的修复时间估计（简单=5min, 中等=30min, 复杂=2h），总技术债=Σ修复时间，技术债比率=总债/总产出时间。

**落地项 DEBT2（立即可做）**：warn四级分类——
- `block`：必须修（已存在）
- `warn_real`：有真实问题，应修
- `advice`：建议，可选
- `noise`：误报，应改规则而非修卡
目前阙疑的warn混在一起，32条warn中17条是MATRIX规则对已真实跨平台卡的误报（402报告已指出）。

**落地项 DEBT3（待验证假设）**：SonarQube Remediation Agent式的自动修复——苦力Agent批量修复简单warn（行尾、格式、字段缺失），复杂warn留人工。

**证据**：SonarQube官方+阙疑现有warn债务实践，硬数据。

## 六、本轮元批判（按453标准）

### 真增量（改变做法）

1. **BUILD1 工件缓存键（输入哈希+命令+编译器）**：阙疑已有artifact_sha256但缺输入哈希，Bazel验证了这个设计。直接解决"改了夹具忘了重生成工件"的问题（G2缺陷1的根因）。
2. **DIFF1/2 差分测试形式化**：阙疑的多编译器对照从"人工检查"升级为"显式差分规则"。-O0 vs -O2不一致=UB嫌疑，这是新的UB检测方法。
3. **SCHEMA1/2 LLM输出结构化**：把苦力Agent的产出从自由文本升级为schema验证，解析失败率15-30%→<0.1%。
4. **DEBT1/2 warn量化分级**：从"一次性accept"升级为SQALE式量化+四级分类，17条误报warn可以被识别为noise而非real。

### 换术语（已有实践获得学名）

- 多编译器对照 → 差分测试（DIFF1/2）
- 工件sha → 内容哈希缓存（BUILD1）
- 红队最小化 → shrinking（PBT2）
- warn债务 → 技术债（DEBT1/2/3）

### 明确不采纳/推迟

- Bazel/Ninja全量接入——过于重型，阙疑的"构建系统"就是g+++文件sha
- Hypothesis直接使用——Python生成C++参数的适用性待验证，和突变测试共用基础设施后再做
- SonarQube全量接入——阙疑的debt_ledger.py已存在，升级为量化模型即可，不需要SonarQube
- Outlines约束解码——阙疑用API模型，用平台的structured outputs即可

### 证据越界警示

- Bazel的远程缓存是大型monorepo场景，阙疑是单仓——本地缓存足够
- 差分测试的"不一致=编译器bug"在阙疑场景更可能是UB而非编译器bug——不要过度归因
- SonarQube的21%技术债消耗是工业团队数据，阙疑是个人项目——比例可能不同
