# 394 脚手架提升与外置数据库：从 Bash 脚本到 MCP 标准，从扁平文件到向量+图混合

> 日期：2026-09-13。聚焦**脚手架提升**（Agent CLI/工具链/MCP）和**外置数据库**（向量+图混合替代扁平文件）。
> 核心命题：**我们的工具是 Python 脚本+Bash 调用（最原始形态），2026 标准是 MCP Server+Agent Skills+并行调用+沙箱；我们的知识存储是扁平文件+grep，2026 生产共识是向量+图混合存储。**

## 一、脚手架提升：从 Bash 脚本到 MCP 标准

### 核心发现

**MCP（Model Context Protocol）**：Anthropic 主导的行业标准，让 AI 模型通过标准接口调用外部工具——数据库连接器、文件系统读取器、Shell 执行器，任何 MCP 兼容客户端都可以运行时发现和调用。

**三大工具收敛**（2026）：
- **Claude Code**：最强推理+规划，多文件编辑，Code Review 系统
- **Codex CLI**：开源，沙箱执行，并行云 Agent（300 万周活）
- **Cursor**：IDE 人体工学，Agents Window（管理 Agent 舰队的控制平面）
- 顶级工程师同时用三个工具作为一个栈，Claude Code 作为编排器

**Agent Skills**（npx skills add）：可复用的技能包，三大工具都支持。

**并行工具调用**（supports_parallel_tool_calls）：MCP Server 可以声明支持并行，减少等待。

### 和我们的映射

| 能力 | 我们的现状 | 2026 标准 |
|---|---|---|
| 工具调用 | Bash 执行 Python 脚本 | MCP Server（标准接口） |
| 工具发现 | 靠提示词列举 | MCP 运行时发现 |
| 并行调用 | 手动并行（我一次发 2-3 个搜索） | 原生并行工具调用 |
| 沙箱 | 无（完全访问模式） | 沙箱执行（默认安全） |
| 技能复用 | 无（提示词复制粘贴） | Agent Skills（npx skills add） |
| 编排 | 监工（对话里） | 控制平面（Cursor Agents Window） |

### 挖掘

**1. MCP 是我们缺失的关键基础设施**：
- 当前工具（gate_engine.py, atom_evidence_replay.py, poison_drill.py）通过 Bash 调用
- 如果包装成 MCP Server：
  - 任何 MCP 兼容 Agent（Claude Code/Codex/Cursor）都可以直接调用
  - 工具参数有类型定义，减少调用错误
  - 工具输出结构化，不需要解析文本
- **这是"脚手架提升"最直接的一步——把 5 个核心工具包装成 MCP Server**

**2. 我们的"监工"角色可以类比 Cursor Agents Window**：
- Cursor 3 的 Agents Window 是"管理 Agent 舰队的控制平面"——查看所有活跃 Agent、Agent Tabs 并排、Design Mode 标注 UI
- 我们的监工是"对话里的编排器"——没有可视化界面，但功能类似（分配任务、检查结果、决策）
- **378 平台化的 Phase 2（Web 界面）就是做这个——但当前优先级低**

**3. Agent Skills 是"提示词复用"的标准化**：
- 当前我们的提示词（312, 373 等）是 Markdown 文件，手动复制粘贴
- Agent Skills 是可安装的技能包（npx skills add），包含提示词+工具+工作流
- **如果我们的"原子生产提示词"变成 Agent Skill，就可以一键安装到任何 MCP 兼容环境**

## 二、外置数据库：从扁平文件到向量+图混合

### 核心发现

**向量库 vs 图数据库**（2026 共识）：
- **向量库**：内容存为 embedding，语义相似检索（ANN）——快、零冷启动、适合非结构化内容
- **图数据库**：类型化实体关系，确定性多跳遍历——适合关系推理、冲突检测
- **生产级 Agent 两者都需要**：Mem0/Letta/LangGraph 都在收敛到混合模式

**选型指南**：
| 数据库 | 最佳场景 | 我们的规模 |
|---|---|---|
| FAISS | 内存研究 | 太小，不需要 |
| **pgvector** | <5000 万向量，简单场景 | ✅ 适合（~200 文档） |
| **Chroma** | 本地开发，免费 | ✅ 适合（零安装） |
| MongoDB | 文档原生 | 不适合 |
| Milvus | 十亿级 | 太大 |
| Pinecone | 零运维托管 | 太贵 |
| Neo4j | 关系推理/多跳 | ✅ 适合（知识图谱） |

**延迟预算**（四层记忆）：
- 工作记忆：<10ms
- 会话压缩：10-50ms
- 长期语义（向量+图）：100-500ms 读 / 50-200ms 写

**Samyama**（统一图-向量数据库）：255K nodes/s（CPU）/412K（GPU），115K Cypher queries/s。

### 和我们的映射

| 能力 | 我们的现状 | 外置数据库 |
|---|---|---|
| 存储 | 扁平 Markdown 文件 | 向量+图混合 |
| 检索 | grep/Glob（关键词） | 语义检索（embedding） |
| 关系推理 | 无（380 提了未落地） | 图遍历（多跳） |
| 冲突检测 | 无 | 图一致性校验 |
| 缺口发现 | 无 | 图拓扑分析 |
| 检索速度 | 几秒（遍历文件） | 100-500ms（向量） |
| 规模上限 | ~1000 文件（grep 还能应付） | 百万+ |

### 挖掘

**1. 我们当前规模（~200 文档）grep 还能应付，但增长后会成为瓶颈**：
- 27 原子+56 卡+80 误解+20 架构文档≈183 个 Markdown 文件
- grep 遍历 183 个文件需要 1-3 秒
- 如果到 500+ 原子、1000+ 卡，grep 需要 10+ 秒，且无法语义检索
- **提前迁移到向量+图混合，可以避免未来的性能瓶颈**

**2. 语义检索是"信息搜集"的升级**（和 393 配合）：
- 当前：grep "false sharing" → 找到包含这个关键词的文件
- 语义检索："哪些原子和多线程性能有关？" → 找到 PERF-004（false sharing）、PERF-003（小对象分配）、CONC-LOCK-001（锁代价）
- **语义检索可以发现关键词匹配不到的相关知识——这是"信息搜集能力"的质变**

**3. 图数据库是"知识网络"的落地**（和 380 配合）：
- 380 提了 relations schema（prereq/contrasts/serves/equivalent）
- 图数据库可以：
  - 多跳推理（"A 的前置是 B，B 的对比是 C，A 和 C 是什么关系？"）
  - 冲突检测（"A 说 X，B 说 Y，是否矛盾？"）
  - 缺口发现（"哪些原子没有前置关系？哪些域没有覆盖？"）
- **这是从"文件集合"到"可计算知识网络"的跃迁**

**4. 轻量级选型：Chroma（向量）+ NetworkX（图，Python 库）**：
- 不需要安装数据库服务器
- Chroma：本地文件存储，Python API，零配置
- NetworkX：Python 图库，内存计算，适合~1000 节点
- **这两个都是 Python 库，可以直接集成到现有工具链中，不需要额外基础设施**

## 三、应用（分阶段）

### 立即落地（零成本/低成本）

**应用 1：工具输出结构化**——当前 gate/replay 输出是文本，改为 JSON 输出（--json 标志），为 MCP 包装做准备
**应用 2：Chroma 本地向量索引**——对 183 个 Markdown 文件做 embedding，建本地向量库，支持语义检索（需要 sentence-transformers）

### 中期落地

**应用 3：核心工具 MCP 化**——把 gate_engine.py, atom_evidence_replay.py, poison_drill.py 包装成 MCP Server
**应用 4：NetworkX 知识图谱**——从原子的 relations 字段构建图，支持多跳推理和缺口检测

### 长期落地

**应用 5：混合存储架构**——Chroma（向量）+ NetworkX（图）+ Markdown（原文）三层，检索时先向量召回，再图重排，最后返回原文

## 五、局限

- MCP 包装需要学习 MCP SDK，有一定开发成本
- 向量检索需要 embedding 模型（sentence-transformers），当前环境可能不具备
- 图数据库（Neo4j）需要安装服务器，轻量级替代（NetworkX）是内存计算，不持久化
- 混合存储架构（向量+图+原文）需要设计数据同步机制（Markdown 改了，向量和图要更新）
- 我们的规模（~200 文档）还没到"必须用数据库"的程度——grep 还能应付，迁移是"提前布局"而非"紧急需求"
- 本调研未覆盖"实时索引"（文档改了自动更新向量/图）——这是生产级需求，但当前规模可以手动重建
