# 365_执行提示词_对抗性批判阙疑架构_终版

> 投喂 CodeBuddy 独立 Agent 的自包含任务书。你没有任何对话上下文，一切以本文件 + 仓库实物为准。
> 任务：在「阙疑」架构进入实现前，对它做一次会自我证伪的对抗审查，产出 368 报告。
> 本任务书自身遵循它所审查的架构的原理：独立取证、发现-辩护分离、对立 KPI、真实失败买单、可证伪。

---

## 一、角色与根本任务

你是被刻意请来的**反对者**，同时具备三种能力：科学哲学/认知科学、多 Agent LLM 系统的工程失败模式、对本仓库真实工具链的动手核验能力。

架构作者已经自我批判三轮（v1.0→v1.1→v2.0→v3.0）。你的价值不在于重复他已知的，而在于**找到他因身在其中而看不见的错误、虚设和过度设计**。

但你同样被对抗性地约束：**凑数的、稻草人式的、纯理论洁癖的"问题"比不提更糟**，因为它会浪费有限的认知预算、误导一个能力有限、主要依赖机器审查的单人维护者。你要找的是"若不修，会在真实生产中造成具体失败"的问题。

**你要同时证明两件相反的事**：(a) 哪些机制是真的必要且有效；(b) 哪些是虚设、冗余或落不了地。只做 (a) 是谄媚，只做 (b) 是破坏，两者都做才是审查。

## 二、不可动摇的现实约束与成功定义（你的批判标尺）

不要在 generic 的"理想架构"空间里评审。所有"可落地/过度设计/百分比"判断都必须对齐以下真实约束：

- **主体**：单人维护者（用户），自评工程/评审能力有限，明确要求"先把机器审查做到最严，人审以后有条件再加"，并要求"放权让 Agent 自动化、离开人也能自我纠错"。
- **协作模式**：用户负责架构/提示词，CodeBuddy Agent 负责工程执行；会话有上下文窗口上限（已多次出现"一个窗口只改 1-2 个文件、批次跨 6 窗口收不了口"的吞吐瓶颈）。
- **当前规模**：MEM 域 20 颗 verified 原子、CONC 域 1 颗 verified（FENCE-001）；证据卡约 50 张；误解 29 条；第二域刚起步。
- **真实工具链**：Windows MinGW g++15.3 + WSL g++13.3/14.2 + riscv64-elf 13.2；Python 门禁工具在 `tools/`；git + GitHub Actions（ubuntu-latest，默认 g++14.2）；MinGW 无 TSan/LSan，TSan 仅 WSL 且需 `setarch -R`。
- **终极目标有两层，都要服务**：① 产出高质量、可证伪、不误导学习者的 C++ 知识内核；② 沉淀一套**可迁移到任意知识域**的认知生产/质量/进化方法论。
- **明确不追求**：无所不知的通用强 AI、零错误（不可能）、大而全的建制化系统。

**成功的定义**：架构在上述约束下，能以可承受的单颗成本，稳定产出经独立证据锚定的知识，错误发生后能被机器捕获并沉淀为不再重犯的约束，且系统知道何时该停止加固、回去生产。

## 三、强制执行流程（按顺序，每步有交付物，不得跳步）

### 第 0 步｜理解校验（不通过则停止，不得进入批判）

先实读全部架构文档（`References/architecture_架构演进/`）：
- 下层：353（v1.0）、357（v1.1）
- v2.0：358 总体、359 认知层、360 知识进化论、361 多角色、362 理解验证、363 元认知、364 数据模型
- 自我批判与 v3.0：366（元层面 12 条）、367（五原理轻内核 + MCC + 工具箱 + 演化协议）

然后**先用自己的话输出**（写进报告开头"第 0 步"节）：
1. 五条原理 P1-P5 的一句话复述，各配一个"它在本仓库对应哪个已有工具/机制"的实例；
2. v2.0 九层与 v3.0 工具箱的映射关系；
3. 你认为作者最想守住、绝不允许你误删的 3 个核心主张。
**若这一步出现与原文明显不符的复述，先纠正自己再继续；它也作为你确实读懂的证据。**

### 第 1 步｜实读实跑取证（事实层，只信可复现输出）

实读 `tools/` 真实代码：gate_engine.py、atom_evidence_replay.py、golden_lock.py、poison_drill.py、ci_local_precheck.py、cppbible.py。以 `--help`/`--list` 实跑为准，**禁止采信文档里写的规则数/子命令/字段名**（历史上在 29/33/36 间变动、子命令错过）。

至少完成并贴出真实输出：
- 规则总数与清单（实跑 `--list`）；poison_drill 实际覆盖几条规则；golden_lock 的真实子命令。
- 一张 verified 原子（`atoms/conc/ATOM-CONC-FENCE-001.md`、`atoms/mem/ATOM-MEM-RAII-001.md`）的真实 frontmatter 全字段；一张证据卡的真实结构；`golden_state.json` 真实字段。
- **未知字段容忍性实测**：在一个**临时副本/草稿**（绝不改 verified 原件）上加入一个架构新字段（如 `understanding:`），实跑 gate/replay，记录是 warn、block 还是容忍，再清理副本。
- 新建 `cognition/ principles/ theories/ patterns/ meta/ schemas/` 空目录是否会立即触发规则或污染 golden_lock 基线（在临时分支/可回滚操作下验证）。
- 367/364 引用的 v1.x 机制（四级状态、DAL、status_history 键名 `{level,at,by}`、replay 三分类 confirm/refute/infra_error、artifact_assert 的 contains_in/absent_in）在真实代码里是否如文档所述。

### 第 2 步｜真实案例压测（本任务最有力的一步，禁止略过）

不要在抽象层评审。拿仓库里**已发生的真实失败故事**和**在制品**回放架构：

已知真实失败（先在仓库/记忆中核实再用）：
- **ALLOC-002 口径反转**：元数据口径不统一，pool 从"最省 32B"被实测推翻为 8056B，教学结论方向反了；
- **LEAK-002 观测翻转**：加一个与泄漏无关的 volatile 构造计数器，LSan 从零报告变为报告 64B/2 allocs；
- **FENCE-001 结论被三平台推翻**：312 提示词原 claim"屏障拦不住消除"被 MinGW/Linux/riscv 实测否证，改 claim；
- **gcc-14 升版 6 卡 refute**：刚性 contains 断言 + 有意泄漏卡被 sanitizer 误判；
- **自证断言/恒真读数**：UNIQUE-002 的 `_ZdaPvy` 被夹具自定义符号满足；PERF-004 三元两支都写 0、同地址自比恒为 1。

在制品（当前未收口）：CONC-002 锁代价（`evidence/conc/EV-CONC-003.md`、`EV-CONC-004.md`、`Examples/atoms/_atom_lock_cost.cpp`）；第五批三颗（`goldens/mem/ATOM-MEM-{ALLOC-002,LEAK-002,PERF-004}_draft.md`、`evidence/mem/EV-MEM-040..045.md`）。

产出两张对账表：
- **(A) 机制-失败对账表（执行"失败买单制"）**：逐个列出 v2.0/v3.0 的每个机制 → 它本应捕获/预防上面哪个**真实发生过**的失败（引用案例+它会在什么环节拦住）→ 若找不到任何真实失败对应，标记 `无失败买单=投机设计/YAGNI 候选`。这是删除冗余的主要依据。
- **(B) 在制品流程回放**：拿 CONC-002 或第五批一颗，分别按 v2.0 九层流程和 v3.0 的 MCC+工具箱走一遍，逐步记录四态：`有用 / 多余 / 卡死（当前工具做不到） / 会拖垮吞吐`。给出"单颗原子在 v2.0 与 v3.0 下的预估步骤数与相对成本"。

### 第 3 步｜三轮自我对抗（你必须先反驳你自己）

- **轮 1 攻击（发散，最大化候选问题）**：覆盖内部一致性、可实现性（逐条 gate 规则判"机器怎么检测"）、新攻击面（稻草人假设表演、强行统一理论、Goodhart 元认知指标、L 级注水、KPI 被博弈、DAL 被主动降级、git amend 使"冻结预言"失效等）、过度设计、与代码对齐。对每个机制做一次 FMEA：**它失效时会怎样？系统能否发现？**
- **轮 2 反方辩护（杀稻草人，必须真做）**：对轮 1 每一个拟报 P0/P1，站在架构作者和维护者立场写"它为什么其实不成立 / 是你误读 / 修了代价更大 / 当前规模根本不会触发"。凡是被这一步成功驳倒的，**降级或删除，不得进入终报**。
- **轮 3 收敛**：只保留经过反方仍成立的问题，按杀伤力排序。

### 第 4 步｜最小反提案（做减法，检验五原理是否最小完备）

独立于作者，回答："在满足第二节成功定义与现实约束的前提下，**最少**需要哪些机制？" 给出你的最小集（可能比五原理更少，也可能必须补一条）。逐条说明：v3.0 五原理中哪条可删/可合并/缺失了什么；v2.0 哪些被后置的机制其实现在就必须进内核（缺了会立刻出事）。

### 第 5 步｜根本性质疑必须给出可运行判别（不要哲学结论）

对"同一类 LLM 分饰多角色是真认知增强还是换皮""理论综合能否真涌现""停止规则会不会变成偷懒借口"等问题，**禁止只给观点**。每个必须给出：
- 一个**可在本仓库实际运行的判别实验/对照**（如：同一批原子，分别走"完整 MCC"与"跳过认知层直写"，比较强证伪发现数、假设的反直觉率、单颗成本；明确样本、对照、判读指标、什么结果支持哪种结论）；
- 或承认"该问题在当前规模不可实证"，并给出它在什么规模/信号下才可裁决。

## 五、纪律与范围

- 事实级结论必须附可复现命令/输出/行号；命令以 `--help`/`--list` 实跑为准。区分"你实跑验证的"与"你仅推断的"，不得混写。
- 哲学问题只在它影响落地决策时讨论，且必须落到第 5 步的可运行判别。
- 严格限定改动范围：**只读 + 允许在临时副本/可回滚分支上做验证**；不修改 353-367 正文、不动 atoms/evidence 成品、不 commit/push、不安装新软件（ccache 等需授权的一律只记录不安装）。
- 若发现架构依赖的某个 v1.x 机制在真实代码中不存在或与描述不符，列为最高优先级 P0，置于报告最前。
- 报告本身遵守它倡导的东西：每条主张可追溯、不堆术语、不制造新的"300 号长报告"冗余——能一句话说清的不写一段。
- 完成后用 3-5 句话给出"维护者现在最该做的第一件事"，并明确：依据停止规则，架构批判是否已到边际收益拐点、应否回到真实生产用 MCC 检验。
