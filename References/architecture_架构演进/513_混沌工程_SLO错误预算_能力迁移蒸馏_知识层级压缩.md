## 一、混沌工程（主动注入故障测试韧性）

### 1.1 业内模式

| 模式 | 来源 | 核心 |
|---|---|---|
| **AgentChaos** | arXiv 2608.06790 | LLM API层注入crash/omission/value故障，不改源码 |
| **Flakestorm** | baeseokjae.github.io | 工具调用级故障注入，95%失败率因无恢复机制 |
| **关键原则** | Nefe Tech | "hardening the harness, not grading the model"——加固框架，不评分模型 |
| **故障类型清单** | DEV Community | timeout/rate limit/malformed response/partial success/duplicate/permission denied/empty/stale |

### 1.2 我们的现状

**我们已经在做的"混沌工程"**：
- 7轮对抗（368→v80）就是注入"假卡/逃逸"，测框架韧性
- 毒样例72条就是故障注入（恶意构造的卡片）
- 变异测试（499/500）就是在工具输出层注入变异

**和业内的差距**：
- 我们注入的是"内容故障"（假卡），不是"工具故障"（编译超时/磁盘满/git挂）
- 没有系统性测试"replay挂了会怎样""gate_engine崩了会怎样"
- 没有稳态假设（steady state hypothesis）——不知道正常态长什么样

### 1.3 落地方案

**工具故障注入清单**（扩展毒样例）：
```
在 tools/chaos_probes/ 下：
├── compile_timeout.py     # 模拟g++超时（sleep 600）
├── compile_crash.py       # 模拟g++段错误
├── malformed_asm.py       # 模拟.asm损坏（空文件/乱码）
├── disk_full.py           # 模拟磁盘写满
├── git_conflict.py        # 模拟merge conflict
├── lock_stuck.py          # 模拟僵尸锁（N1已发现）
└── yaml_parse_error.py    # 模拟frontmatter损坏
```

**稳态假设**（每次混沌实验前定义）：
```
正常态：gate block=0, replay confirm≥55, poison exit=0
注入故障后：应该——
  1. infra_error正确识别（不是refute:compile_error）
  2. fail-closed（exit非零）
  3. 不污染其他卡片
  4. 故障移除后自动恢复
```

**关键区别**：
- 对抗测试测的是"人/模型能不能骗过规则"
- 混沌工程测的是"环境/工具挂了系统能不能优雅降级"
- 两者互补：对抗测内容安全，混沌测运行时韧性

## 二、SLO 与错误预算

### 2.1 业内现状

业界坦诚："currently there is no formalism for SLA for AI agents"——AI agent的SLO还没有标准。但可以借鉴传统SRE：

| SLO | 目标 | 窗口 | 错误预算 |
|---|---|---|---|
| 任务完成率 | 95% | 7天 | 5%任务可失败 |
| p95延迟 | 30s | — | 5%任务超过30s |
| 幻觉率 | <3% | — | — |

**关键原则**：
- burn rate告警 > total burn告警（1小时内burn rate从1x跳到10x就是出事了）
- 分层SLO：按DAL分级——DAL A（错即UB）99.9%、DAL C（事实性）95%
- 错误预算花在哪：有风险的部署/实验/新规则

### 2.2 我们的现状

**我们已有隐含SLO但没显式定义**：
```
隐含SLO：
- gate block = 0（100%）
- replay confirm = 100%（双平台）
- poison = 100%（72/72）
- pytest = 100%（366/366）
```

**缺的**：
1. 没有显式错误预算——"允许多少个refute才算正常"
2. 没有burn rate监控——一周内refute从0跳到5就是出事
3. 没有分层SLO——所有原子同等严格，但DAL A应该比DAL C严

### 2.3 落地方案

**显式SLO定义**（`config/slo.yaml`）：
```yaml
slo:
  gate_block_rate:
    target: 0.0    # 零容忍
    window: 1w
  replay_confirm_rate:
    target: 0.98   # 允许2% refute（环境问题）
    window: 1w
  poison_pass_rate:
    target: 1.0    # 100%
    window: 1w
  pytest_pass_rate:
    target: 1.0
    window: 1w
  atom_verify_rate:  # 原子从draft到verified的比例
    target: 0.80
    window: 1m
```

**错误预算**：
- replay允许2% infra_error（不是refute）
- 花预算：新规则实验时允许暂时warn增加
- burn rate：连续3天refute>0 → 告警

**分层SLO**：
- DAL A（并发/UB）：replay confirm必须100%，infra_error也block
- DAL C（事实性）：允许1-2张卡infra_error后补

## 三、能力迁移（强模型在线教弱模型）

### 3.1 业内模式

| 模式 | 来源 | 核心 |
|---|---|---|
| **Inter-Cascade** | arXiv 2509.22984 | 强模型解决deferred query时生成通用策略，存入库，弱模型检索增强 |
| **AgentDistill** | arXiv 2506.14728 | training-free：teacher生成MCP-boxes（可复用模块），student直接复用 |
| **AI4AI Scaffolding** | arXiv 2608.12307 | 强模型建harness帮弱模型，不改弱模型参数 |
| **Self-Consistency Cascade** | 博客园 | student多次投票一致就信，不一致才升级teacher |

### 3.2 我们的现状

**509设计了FrugalGPT级联**：便宜模型→中档→强模型。但缺了关键一环——**强模型不只做最后兜底，还要把它的判断教给弱模型**。

现在的流程：
```
便宜模型做 → 验证失败 → 升级中档 → 验证失败 → 升级强模型
强模型做完 → 就完了（弱模型下次还是不会）
```

**改进后**：
```
便宜模型做 → 验证失败 → 升级中档 → 验证失败 → 升级强模型
强模型做完 → 生成"为什么这个做法对/那个做法错"的通用策略
           → 存入 data/strategies/
           → 下次便宜模型先检索相似策略
```

### 3.3 落地方案

**策略库**（`data/strategies/`）：
```yaml
# data/strategies/S001.yaml
id: S001
trigger: "replay sha_mismatch"
strategy: "改了.cpp但没重生成.asm。改源码后必须重编译换sha。"
example: "EV-MEM-027: 改malloc计数2→3但没重跑g++ -S"
created_by: strong-model
confidence: 0.95
```

**检索增强**（弱模型提示词注入）：
```
你之前的经验：
{检索到的strategies}
如果遇到类似情况，参考这些经验。
```

**Self-Consistency**：
- 弱模型对同一任务跑2次
- 两次产出一致 → 接受
- 不一致 → 升级强模型
- 这比"一次失败就升级"更省token

## 四、知识层级压缩（230+文档）

### 4.1 业内模式

**层级摘要**（DEV Community）：
```
500文档 → 500个单文档摘要 → 20个类别摘要 → 5个阶段摘要 → 1个综合
```
每层压缩80%，重要信号存活。

**关键**：信息密度逐层递增——从原始文本→token依赖→"观点"→"原则"（Socratic RL）。

### 4.2 我们的现状

230+架构文档，编号到512。问题：
- 太多了，不知道哪份讲了什么
- 早期文档的结论可能已被后续推翻
- 没有"精华版"

### 4.3 落地方案

**四层压缩**：
```
L1: 单文档摘要（每份文档3行：做了什么/核心结论/状态）
    ↓ 230份 → 230个3行摘要

L2: 主题聚类（按方向聚类）
    ↓ 230份 → ~10个主题（基础设施/性能/智能/治理/安全...）
    每个主题一份"综述文档"（~2页）

L3: 架构总览（一份）
    ↓ 10个主题 → 1份"阙疑架构v1.0"（~10页）
    这就是给其他AI看的系统全貌

L4: 核心原则（5-10条）
    ↓ 10页 → 5-10条铁律
    这就是系统的"宪法"
```

**L1实现**（`tools/doc_summarize.py`）：
- 每份文档读前2000字+后500字
- 提取标题/结论/状态
- 输出到 `data/doc_index.jsonl`

**L2实现**（502 RAG L1后可做）：
- embedding聚类
- 每簇选一份"代表性文档"

**L3已经有了**：505就是架构总览，但需要更新到512

**L4已经有了**：铁律4条+G6规范

## 六、核心洞察

**混沌工程**：我们的对抗测试已经很成熟，但测的是"内容"（假卡骗过规则）。混沌工程补的是"运行时"（工具挂了系统怎么办）。两个互补。

**SLO**：我们隐含SLO已经很严（block=0/confirm=100%），但没显式写出来。显式写出来后，burn rate告警才能自动化——"连续3天refute>0"比"总共refute=5"更早发现问题。

**能力迁移**：这是对509级联路由的关键增强。强模型不只做"最后兜底"，还要把它的判断沉淀为策略库，让弱模型下次不用升级就能做。Inter-Cascade的在线蒸馏模式。

**知识压缩**：230+文档必须层级压缩。L1（单文档3行摘要）是基础——有了它，新Agent不用读230份文档，只读230个3行摘要就能找到需要的。
