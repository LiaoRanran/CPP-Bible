## 二、4 个缺口的补全设计

### 缺口 1：安全与数据保护（P1）

**问题**：golden_state.json、metrics.jsonl、knowledge_graph.db、artifact_versions.json 都是关键数据，没有备份。

**设计**：

```
tools/backup.py
├── snapshot()          # 备份关键数据到 data/backups/YYYY-MM-DD-HHMM/
├── restore(path)       # 从备份恢复
├── list()              # 列出备份
└── auto()              # 每次批次结束自动调用（cppbible quality 钩子）

备份内容（白名单）：
- data/golden_state.json
- data/metrics.jsonl
- data/knowledge_graph.db
- Examples/atoms/artifact_versions.json
- config/*.yaml

保留策略：最近 10 份 + 每周一份（永久）
```

**工作量**：~2h，1 个苦力批次。**优先级 P1**（数据丢失不可逆）。

### 缺口 2：配置管理（P2）

**问题**：配置散落在各工具中（gate_engine 硬编码规则数、阈值写死、模型路由还没建）。

**设计**：

```
config/config.yaml
├── gate:
│   ├── max_warn: 32
│   └── rules_dir: tools/gate_rules/
├── replay:
│   ├── timeout_seconds: 600
│   └── incremental_default: true
├── ci:
│   ├── parallel_jobs: 4
│   └── pytest_xdist: 16
├── models:
│   ├── cheap: hunyuan-4p
│   ├── strong: ds-v4.1-flash
│   └── adversarial: seed-evolving
├── observability:
│   ├── log_dir: data/logs
│   └── retention_days: 30
└── backup:
    ├── dir: data/backups
    └── keep: 10
```

所有工具读 `config/config.yaml`，支持环境变量覆盖（`QUEYI_GATE_MAX_WARN`）。

**工作量**：~3h，1 个苦力批次。**优先级 P2**。

### 缺口 3：规则/工具版本化与回滚（P2）

**问题**：规则在 gate_engine.py 里，改了就改了，没有版本号，回滚靠 git。

**设计**：

- 每条规则加 `version: "1.0"` 字段
- 规则变更记录到 `data/rule_changelog.jsonl`：`{rule_id, old_version, new_version, changed_at, changed_by, reason}`
- `tools/rule_rollback.py <rule_id> <version>`：单规则回滚（从 changelog 恢复）
- 工具版本：每个插件的 manifest.json 有 version（504 插件架构）

**工作量**：~2h，1 个苦力批次。**优先级 P2**。

### 缺口 4：API 层（P3）

**问题**：全是 CLI，Web 仪表盘要实时数据得每次 fork 进程。

**设计**：

```
tools/api_server.py (FastAPI)
├── GET /api/metrics          # 当前指标
├── GET /api/metrics/history  # 历史趋势
├── GET /api/tasks            # 任务队列
├── POST /api/tasks           # 提交任务
├── GET /api/logs?trace_id=xx # 日志查询
├── GET /api/kg/query?q=...   # 知识图谱查询
├── GET /api/health           # 健康检查
└── WS /ws/realtime           # WebSocket 实时推送
```

**工作量**：~6h，1 个好模型批次。**优先级 P3**（Web 仪表盘 L1 可以先读静态文件，不需要 API）。

## 三、技术选型审查

| 选型 | 决定 | 替代方案 | 风险 | 审查结论 |
|---|---|---|---|---|
| SQLite（知识图谱） | 采用 | NetworkX（纯内存）、Neo4j（服务器） | SQLite 并发写入可能锁 | ✅ 零依赖、够用、读多写少 |
| Chroma（RAG） | 采用 | pgvector（需 PG）、FAISS（纯索引无元数据） | 本地 embedding 质量 | ✅ 本地优先、零服务器、Rust 重写性能够 |
| all-MiniLM-L6-v2（embedding） | 首选 | text-embedding-3-large（API，有成本） | 中文语义可能不够 | ⚠️ 先试本地，质量不够换 API |
| pytest-xdist（并行） | 采用 | 手动分片 | 测试间共享状态 | ⚠️ 需排查测试隔离 |
| JSON Lines（日志） | 采用 | SQLite（结构化查询）、Parquet（分析） | 大文件查询慢 | ✅ 简单、可 grep、log_query 可索引 |
| FastAPI（API 层） | 采用 | Flask（更轻）、直接 CLI fork | 增加依赖 | ✅ 异步+WebSocket 支持好 |
| PySide6（Qt 桌面） | L3 才考虑 | Electron（更重）、Tauri（Rust） | 打包体积大 | ✅ L1/L2 用 Web，L3 再评估 |

**关键风险点**：
1. pytest-xdist 可能因测试间共享文件锁而失败——需要先跑一轮排查
2. 本地 embedding 对中文架构文档的语义检索质量未知——先做小样本评估
3. 知识图谱的 YAML 解析要兼容现有 28 原子 + 56 证据卡的各种格式变体
