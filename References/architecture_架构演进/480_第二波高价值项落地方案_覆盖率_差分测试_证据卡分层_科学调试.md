## 一、覆盖率量化（gcov，零新工具）

### 1.1 问题

阙疑的夹具没有覆盖率数据，不知道断言覆盖了多少路径。402 F03（断言判别力不足）的根因可能就是"断言只覆盖了部分路径"。

硬证据：AI 生成测试 93.1% 行覆盖率，但只有 58.6% 突变杀灭率——超过 1/3 的真实 bug 在 CI 全绿时溜过。

### 1.2 改法

gcov 是 GCC 内置，零新工具。每颗新原子的夹具跑 gcov，<80% 行覆盖率标 weak。

### 1.3 具体实现

#### 工具：tools/coverage_check.py（约 100 行）

```python
# 伪代码
import subprocess, re
from pathlib import Path

def check_coverage(fixture_cpp, threshold=80):
    """编译夹具带 --coverage，运行，gcov 分析，返回行覆盖率"""
    # 1. g++ -O0 --coverage -o build/cov_test fixture_cpp
    # 2. 运行 build/cov_test
    # 3. gcov -b fixture_cpp（生成 .gcov 文件）
    # 4. 解析 .gcov 文件，计算行覆盖率
    # 5. 返回 (line_coverage, branch_coverage, uncovered_lines)
```

#### 接入方式

- 不接入 replay（会显著拖慢 replay）
- 作为独立工具，CI 中单独一步（只对新增/修改的夹具跑）
- 结果写入证据卡的 `coverage:` 字段（可选，不强制）

#### 验收标准

- 新原子夹具行覆盖率 <80% → 在证据卡中标注 `coverage: weak (<80%)`
- 覆盖率数据写入 worklog，不阻断门禁（先观察一个批次）

### 1.4 和突变测试的关系

覆盖率（执行了没有）+ 突变测试（执行了能不能检测错误）= 双维度闭环。
先做覆盖率（零新工具），突变测试等覆盖率数据积累后再做。

## 二、差分测试形式化（五编译器对比，零成本升级）

### 2.1 问题

阙疑已有五编译器（MinGW 15.3 / WSL g++13.3 / 14.2 / riscv64 13.2 / clang++ 22.1.8），但只用来做 replay 的跨编译器验证，没有显式对比输出差异。

CONC-001 的 inline 顺序依赖（-O0 顺序敏感 / -O2 顺序无关）就是差分测试的天然案例，但目前没有形式化为规则。

### 2.2 改法

同一夹具，多编译器，对比 `.out` 的确定性输出。任何不一致自动标记——**-O0 vs -O2 不一致 = UB 嫌疑**。

### 2.3 具体实现

#### 工具：tools/diff_test.py（约 150 行）

```python
# 伪代码
COMPILERS = [
    ('mingw', 'g++', '-O0'),
    ('mingw', 'g++', '-O2'),
    ('wsl', 'g++-13', '-O0'),
    ('wsl', 'g++-13', '-O2'),
    ('clang', 'clang++', '-O0'),
    ('clang', 'clang++', '-O2'),
]

def diff_test(fixture_cpp):
    """用多编译器多优化档编译运行同一夹具，对比 .out 输出"""
    results = {}
    for name, compiler, opt in COMPILERS:
        # 编译运行，捕获 stdout
        output = compile_and_run(compiler, opt, fixture_cpp)
        results[f"{name}_{opt}"] = output
    
    # 对比所有组合
    differences = []
    for (k1, v1), (k2, v2) in itertools.combinations(results.items(), 2):
        if v1 != v2:
            differences.append((k1, k2, v1, v2))
    
    return results, differences
```

#### 判定规则

- 同一编译器不同优化档输出不一致 → **UB 嫌疑**（高优先级）
- 不同编译器同一优化档输出不一致 → **实现定义行为**（中优先级）
- 全部一致 → 确定性行为（低优先级）

#### 接入方式

- 不接入 replay（会非常慢）
- 作为独立工具，新原子生产时可选运行
- 结果写入证据卡的 `diff_test:` 字段

### 2.4 和反事实扰动验证的关系

差分测试就是反事实扰动验证（391）的一种形式——同一夹具，多编译器/多优化档，claim 的适用范围自动显式化。

## 三、证据卡分层（核心层 <50 行 + 附录层）

### 3.1 问题

证据卡从 60 行膨胀到 200+ 行（平均 5.6KB），维护成本接近教学价值。一张卡承载了太多东西：断言 + 留痕 + 双平台 + 修订史 + 处置登记。

吞吐下降的直接原因：第四批一批 4 颗，第五批 3 颗跨 6 个窗口。

### 3.2 改法

证据卡分层：
- **核心层**（<50 行）：frontmatter + claim + 关键断言 + verdict。这是 replay 和 gate 只看的部分。
- **附录层**（单独文件或同文件 `## 附录` 之后）：完整原始输出、双平台对照、修订记录、处置登记、红队发现。这是人读的部分，机器不解析。

### 3.3 具体实现

#### 格式约定

```markdown
---
# 核心层 frontmatter（replay/gate 只解析这里）
id: EV-MEM-040
verdict: confirm
artifact: ...
artifact_sha256: ...
actual:
  run_match_keys: [...]
  artifact_assert: [...]
expected: ...
---

# claim（≤50 字）
...

## 关键断言（3-5 条最重要的）
...

---

## 附录（机器不解析，人读）

### 完整原始输出
...

### 双平台对照
...

### 修订记录
...

### 红队发现与处置
...
```

#### 工具改动

- replay/gate 只解析 `---` 之间的 frontmatter 和 `## 附录` 之前的内容
- `## 附录` 之后的内容完全忽略
- 存量卡不需要立即迁移，新卡按分层格式写

#### 迁移策略

- 新卡必须分层
- 存量卡逐步迁移（每批迁移 3-5 张）
- 迁移不改变断言，只移动内容位置

### 3.4 预期效果

- 核心层 <50 行，replay/gate 解析更快
- 附录层可以无限膨胀，不影响机器
- 红队盲读时只读核心层（减少上下文消耗）
- 吞吐提升：一张卡的生产时间从 200+ 行降到 50 行核心 + 附录

## 四、科学调试四元组（红队提示词升级，零成本）

### 4.1 问题

红队发现经常是"我觉得有问题"，没有可验证的结构。ALLOC-002 红队的"口径不统一"是好的发现，但很多红队发现是"可能有问题"，没有假设、预测、实验。

### 4.2 改法

红队每个发现必须含四元组：
1. **假设**（Hypothesis）：我认为 X 有问题，因为 Y
2. **预测**（Prediction）：如果假设成立，那么 Z 会发生
3. **实验**（Experiment）：我做了什么来验证（命令/输出/行号）
4. **结论**（Conclusion）：假设成立/不成立/部分成立

### 4.3 具体实现

修改 365B 红队提示词，在交付物格式中增加四元组要求：

```markdown
## 发现 1：[标题]

### 假设
[我认为 X 有问题，因为 Y]

### 预测
[如果假设成立，那么 Z 会发生]

### 实验
[我做了什么来验证]
- 命令：`...`
- 输出：`...`
- 行号：file:line

### 结论
[假设成立/不成立/部分成立]
[严重度：阻断/高级/建议]
```

### 4.4 预期效果

- 红队从"我觉得有问题"升级为"可验证的科学发现"
- 减少"可能有问题"类的无效发现
- 红队校准率（EVAL2）可量化：有多少假设被实验证实
- 零成本，只改提示词
