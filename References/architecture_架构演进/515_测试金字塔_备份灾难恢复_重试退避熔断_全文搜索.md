## 二、备份与灾难恢复

### 2.1 业内要求

**备份三原则**：
1. 三副本：本地+远端+异地
2. 不可变备份：WORM/Object Lock
3. **恢复测试**：备份了不算，能restore才算

**备份清单**：
- [ ] 备份存在独立账号/提供商
- [ ] 至少一份不可变
- [ ] 保留策略≥90天
- [ ] 最近30天内做过restore测试
- [ ] 备份成功/失败有监控

### 2.2 我们的现状（最大风险）

**⚠️ ahead 173+ 提交未 push**：
- 本地有173个commit没推到GitHub
- 如果磁盘挂了/系统崩了，这173个commit全丢
- SSH 22/443 exit 141网络阻断
- **这是整个系统最大的单点故障**

**已有的**：
- git本地历史（.git目录）
- GitHub远端（但落后173个commit）

**缺的**：
- 本地bare clone备份
- 未push commit的紧急备份
- 恢复测试（从没试过git clone --mirror后能不能restore）

### 2.3 落地方案

**紧急**：用户在能连通SSH时手动git push（已多次提醒）。

**自动备份脚本**（`tools/backup.sh`）：
```bash
# 每天创建bare mirror clone
git clone --mirror . /backups/cpp-bible-$(date +%Y%m%d).git
# 保留最近30天
find /backups/ -name "cpp-bible-*.git" -mtime +30 -delete
```

**恢复测试**（每季度）：
```bash
# 从备份clone
git clone /backups/cpp-bible-latest.git /tmp/restore-test
cd /tmp/restore-test
git fsck  # 验证完整性
cppbible check  # 门禁能跑通吗
```

## 三、重试退避与熔断

### 3.1 业内模式

**指数退避+抖动**：
```
重试间隔：100ms → 200ms → 400ms → 800ms → cap 3s
抖动：delay *= 0.5 + random.random()
防止thundering herd（雪崩）
```

**错误分类重试**：
| 错误类型 | 重试策略 |
|---|---|
| timeout/连接拒绝 | 快速重试（100ms×2^n） |
| rate limit | 中等重试（1s×2^n） |
| 4xx参数错误 | 不重试 |
| 5xx服务错误 | 慢速重试（5s×2^n） |

**熔断**：
- 连续失败N次 → 开（停止调用）
- 冷却M秒 → 半开（探测一次）
- 成功 → 关；失败 → 再开

### 3.2 我们的现状

**已有的**：
- 编译器熔断（circuit_breaker.py）：连续失败5次→60s冷却

**缺的**：
1. **编译器失败没有重试**：g++偶发失败直接infra_error，不重试
2. **没有退避**：重试就立即重试，不给编译器恢复时间
3. **没有错误分类**：compile_error/timeout/crash不区分
4. **git操作没有重试**：git push网络失败直接放弃

### 3.3 落地方案

**重试包装器**（`tools/retry.py`）：
```python
def retry_with_backoff(func, max_retries=3, base=0.5, cap=5.0):
    for attempt in range(max_retries):
        try:
            return func()
        except (TimeoutError, ConnectionError) as e:
            delay = min(base * (2 ** attempt), cap)
            delay *= 0.5 + random.random()  # jitter
            time.sleep(delay)
    raise
```

**应用到**：
- 编译器调用：timeout重试3次
- git操作：push失败退避重试
- 文件锁等待：僵尸锁检测后等30s

## 四、全文搜索（230+文档）

### 4.1 业内方案

| 方案 | 速度 | 中文支持 | 依赖 |
|---|---|---|---|
| ripgrep (rg) | 100x grep | ✅ | 二进制 |
| SQLite FTS5 | 毫秒级 | trigram ✅ | 内置 |
| grep -r | 慢 | ✅ | 内置 |

**FTS5优势**：
- 倒排索引，不是全表扫描
- BM25排序
- trigram tokenizer支持中文
- 增量索引按mtime更新
- 无外部依赖（SQLite内置）

### 4.2 我们的现状

**现在搜230+文档**：
- 用grep/Glob按关键词找
- 没有全文索引
- 不知道哪份文档讲了什么
- 找"混沌工程"要grep --include="*.md" -l "混沌"

**问题**：
1. 每次搜索全目录扫描
2. 没有排序（相关度）
3. 没有高亮
4. 没有增量索引

### 4.3 落地方案

**FTS5索引**（`tools/doc_search.py`）：
```python
import sqlite3
conn = sqlite3.connect('data/docs_index.db')
conn.execute('''CREATE VIRTUAL TABLE IF NOT EXISTS docs 
    USING fts5(title, path, content, tokenize="trigram")''')

# 索引：遍历References/architecture_架构演进/*.md
# 增量：按mtime判断哪些要更新

# 搜索
results = conn.execute(
    "SELECT title, path, snippet(docs, 2, '<b>', '</b>', '...', 10) "
    "FROM docs WHERE docs MATCH ? ORDER BY rank", ('混沌',)
).fetchall()
```

**收益**：
- 搜索"缓存"从全目录扫描→毫秒级
- BM25排序：最相关的排前面
- 中文trigram："缓存"能匹配"cache"
