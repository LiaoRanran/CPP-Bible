# 305_红队制衡体系进化架构调研_从v1.1到v2.0_错误预测命中率与效能度量

> 2026-09-12 · 红队是系统质量的核心制衡层。v1.1 已建立两段式盲读 + 替代解释 + can't-miss 10 条，
> 但缺少"红队自身的质量度量"和"红队发现的知识沉淀"。本文调研 v2.0 升级方向。
> 关联：References/architecture_架构演进/295（红队 v1.1 全文）· 第五批红队统计（6 阻断 + 28 高）

## 一、红队 v1.1 的成就与局限

### 1.1 成就（第五批实证）

| 批次 | 红队阻断 | 阻断性质 | 价值 |
|---|---|---|---|
| 第三批 | 3 阻断 | 形式问题（自证断言、值类别污染） | 机械可查 |
| 第四批 | 2 阻断 | 数据问题（基数不一致、断言不存在） | 可机器固化 |
| 第五批 | 6 阻断 | 方向性问题（口径不统一、一 bit 两计、消除与失败不可区分、恒真对照、与既有证据重复、观测反转） | 深层架构 |

**趋势**：红队抓的问题级别在上升——从"形式"到"数据"到"方向"。这说明浅层问题已被 gate 规则拦住，红队被迫往更深处挖。

### 1.2 局限

1. **红队效能不可度量**：只知道"抓了几个阻断"，不知道"红队的预测准确率"——哪些阻断被证实是真问题？哪些是误报？哪些阻断的修复产生了新证据？
2. **红队知识不沉淀**：每批红队独立工作，上一批的教训靠 can't-miss 清单传递，但清单是静态的，不会自动更新
3. **红队与 Writer 的博弈不可见**：Writer 改了什么、红队抓了什么、哪些问题反复出现——没有数据支撑
4. **红队提示词是静态的**：v1.1 是人工编写的，不会根据红队的实际表现自动优化
5. **单红队模式**：每批只有一个红队，没有"红队的红队"（meta-redteam）来检查红队是否遗漏

## 二、红队 v2.0 设计

### 2.1 错误预测命中率追踪（核心新增）

**概念**：红队在审查时，不仅要"找问题"，还要"预测问题"——在看到证据之前，先预测"这张卡最可能在哪里出错"。然后对比预测与实际发现，计算命中率。

**为什么重要**：
- 命中率高 = 红队对 Writer 的弱点有精准理解，可以针对性预防
- 命中率低 = 红队的假设与实际问题不符，需要更新 can't-miss 清单
- 追踪"哪条预测的验证动作产出了新证据"（LEAK-002 教训：红队 H2 的"先证分配真发生"本身产出了观测反转）

**实现方式**：
- 红队提示词增加"预测阶段"：在盲读夹具后、读证据卡前，写下"我预测这张卡最可能的 3 个问题"
- 红队报告增加"预测命中"字段：每个阻断标注"是否在预测中"
- 质检报告统计：预测命中率 = 被证实的预测数 / 总预测数

**数据结构**：
```yaml
redteam_predictions:
  - prediction: "元数据口径可能不统一（ALLOC-002 教训）"
    hit: true
    evidence: "pool 实际 8056B，卡写 32B"
  - prediction: "可能有派生重复读数"
    hit: true
    evidence: "cycle_is_leak ≡ dtor_count==0"
  - prediction: "断言可能未在 Linux 工件实测"
    hit: false
    evidence: "本卡断言已在 Linux 侧验证"
```

### 2.2 红队效能度量（新增指标）

| 指标 | 定义 | 目标 |
|---|---|---|
| 阻断证实率 | 被 Writer 承认并修复的阻断 / 总阻断 | >80% |
| 预测命中率 | 被证实的预测 / 总预测 | >50% |
| 深层阻断率 | 方向性阻断 / 总阻断 | >30% |
| 修复循环数 | 平均每个阻断需要几轮修复 | <1.5 |
| 误报率 | 被 Writer 反驳且红队承认错误的阻断 / 总阻断 | <10% |
| 知识产出率 | 红队发现中被写入 can't-miss 清单或 gate 规则的比例 | >20% |

**当前基线**（第五批）：
- 阻断证实率：6/6 = 100%（全部被修复）
- 预测命中率：未追踪（v2.0 新增）
- 深层阻断率：6/6 = 100%（全部是方向性问题）
- 修复循环数：~1.2（大部分 1 轮修复，少数 2 轮）
- 误报率：0%（第五批红队没有误报）
- 知识产出率：3/6 = 50%（口径不统一、一 bit 两计、断言未实测被写入纪律）

### 2.3 红队知识自动沉淀

**机制**：每批红队结束后，自动生成"红队教训卡"，写入 `docs/redteam_lessons/`：

```
docs/redteam_lessons/
  L001_口径不统一.md（ALLOC-002 教训）
  L002_一bit两计.md（LEAK-002 教训）
  L003_断言未在Linux工件实测.md（EV-MEM-040/041 教训）
  L004_恒真对照.md（PERF-004 教训）
  ...
```

每张教训卡包含：
- 问题描述
- 红队如何发现的（盲读观察）
- 修复方式
- 预防措施（Writer 自检项 / gate 规则）
- 复发记录（如果后续批次又出现同类问题）

**can't-miss 清单自动更新**：当某类问题在 2 个以上批次出现时，自动加入 can't-miss 清单。

### 2.4 多红队协作（可选，高级功能）

**模式**：对高 DAL（A/B）原子，同时派 2 个红队独立审查，然后对比结果。

**好处**：
- 红队 A 遗漏的问题可能被红队 B 发现
- 两个红队都发现的问题 = 高置信度
- 只有一个红队发现的问题 = 需要进一步验证

**成本**：红队时间翻倍。只用于 DAL A/B 原子或争议性大的原子。

**实现**：
- 红队 A 和红队 B 使用相同的提示词，但独立上下文
- 审查结束后，合并两份报告，去重并标注"双红队共识" vs "单红队发现"
- 单红队发现的问题需要额外验证

### 2.5 红队的红队（Meta-Redteam，可选）

**概念**：定期（如每 10 批）对红队本身进行审查——红队是否遗漏了明显问题？红队的误报率是否在上升？红队的 can't-miss 清单是否过时？

**实现**：
- 选取 3-5 张已验证的卡，让新红队重新审查
- 对比新红队的发现与原红队的发现
- 如果新红队发现了原红队遗漏的问题，说明原红队有盲区
- 结果用于更新红队提示词和 can't-miss 清单

## 三、红队提示词 v2.0 增量（相对 v1.1）

### 3.1 新增：预测阶段

```
## 预测阶段（盲读后、读卡前）
在读完夹具和工件后、读证据卡前，写下你预测这张卡最可能的 3 个问题：
1. ...
2. ...
3. ...
每个预测必须配"验证动作"（如何确认这个预测是否成立）。
```

### 3.2 新增：阻断分级

```
阻断分级：
- B1（方向性）：claim 的方向错了，需要重写（如 ALLOC-002 口径反转）
- B2（证据性）：证据不支撑 claim，需要补实验或改断言
- B3（形式性）：格式/引用/编号问题，可机械修复
```

### 3.3 新增：知识产出

```
审查结束后，回答：
1. 本次发现中，哪些应该写入 can't-miss 清单？
2. 哪些应该固化为 gate 规则？
3. 哪些是 Writer 自检可以预防的？
```

### 3.4 新增：自我评估

```
自我评估：
- 我的预测命中率是多少？（X/3）
- 我有没有遗漏明显问题？（如果有，为什么？）
- 我的阻断中，哪些是高置信度，哪些需要进一步验证？
```

## 四、与其他系统的关系

### 4.1 与 Writer 预防机制（303）的关系

- Writer 自检 = 第一道防线（预防）
- 红队 = 第二道防线（检测）
- 红队的预测命中率可以反馈给 Writer：如果红队反复预测同一类问题，说明 Writer 自检没有覆盖到

### 4.2 与 gate 规则的关系

- gate 规则 = 机器可查的红队发现（固化）
- 红队知识产出率 = 红队发现转化为 gate 规则的比例
- 目标：红队发现的问题中，>20% 能固化为 gate 规则

### 4.3 与 G6 四级状态的关系

- red-team-verified 状态的前提是红队通过
- 红队效能度量可以作为 red-team-verified 状态的质量指标
- 如果某批红队的阻断证实率 <80%，该批原子的 red-team-verified 状态需要额外审查

## 五、实施路径

### 5.1 第一阶段（第六批，轻量升级）

1. 红队提示词增加"预测阶段"（3 个预测 + 验证动作）
2. 质检报告增加"预测命中率"统计
3. 红队报告增加"阻断分级"（B1/B2/B3）

### 5.2 第二阶段（第七批，知识沉淀）

1. 建立 docs/redteam_lessons/ 目录
2. 每批红队结束后自动生成教训卡
3. can't-miss 清单根据复发情况自动更新

### 5.3 第三阶段（高级，可选）

1. 多红队协作（DAL A/B 原子）
2. Meta-Redteam（每 10 批一次）
3. 红队效能仪表盘（趋势图）

## 六、开放问题

1. **预测阶段会不会增加红队时间？**
   - 预计增加 10-15 分钟（写 3 个预测）
   - 但预测可以帮助红队聚焦，后续审查可能更快
   - 净影响：可能持平或略增

2. **红队教训卡会不会变成另一个维护负担？**
   - 风险：教训卡写了但没人看
   - 缓解：教训卡直接关联 can't-miss 清单和 gate 规则，不是孤立文档
   - 教训卡可以自动生成（从红队报告中提取），不需要人工写

3. **多红队协作的成本是否值得？**
   - 只用于 DAL A/B 原子（目前 0 颗），成本可控
   - 当 DAL A/B 原子出现时，值得投入

---

*核心结论：红队 v1.1 解决了"独立审查"的问题，v2.0 要解决"红队自身的质量和进化"问题。错误预测命中率是核心指标——它不仅度量红队的准确度，还能反馈给 Writer 预防机制和 gate 规则。红队不应该是"一次性审查"，而应该是"持续学习的制衡层"。*
