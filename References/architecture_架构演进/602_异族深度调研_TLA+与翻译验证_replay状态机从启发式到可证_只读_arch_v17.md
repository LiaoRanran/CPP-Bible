阙疑（CPP-Bible）是一个**机器可核验、错误率有上界、可换验证者**的 C++ 知识生产系统。

### replay 机制现状（开工先量，先读 atom_evidence_replay.py）

- `atom_evidence_replay.py`（106KB，CORE 工具之一）：复算验证工具
- 当前 confirm=56 / refute=0 / infra_error=0（596 后基线）
- replay 的核心流程（先核实，按实际代码调整）：
  1. 读取证据卡的 artifact_assert（断言：编译应该通过/失败、应该输出什么符号、应该有什么行为）
  2. 在沙箱中用 g++ 编译夹具文件（Examples/ 下的 .cpp）
  3. 检查编译结果（exit code、stderr、输出二进制）
  4. 检查符号（nm/objdump 验证符号存在/不存在）
  5. 比对断言与实际结果 → confirm（一致）/ refute（不一致）/ infra_error（编译环境问题）
  6. 还原沙箱（删除临时文件，恢复真实仓库）
- replay 的"还原真实仓库"逻辑：会 git checkout 被跟踪但未提交的文件（2026-09-18 已实锤损失过未提交编辑）
- replay 有并发锁（_REPLAY_LOCK，580 已改为跟随跑批根分片）
- replay 有 manifest（build/replay_manifest.json，跨进程增量复用缓存，579 已隔离）

### replay 的"启发式"体现在哪里（调研的核心问题）

replay 当前是"编译+sha 比对+符号检查"的**启发式验证**，不是**形式化证明**：
- 它验证"这次编译的结果与断言一致"，但不证明"断言本身是正确的"
- 它验证"这个夹具文件编译出这个二进制"，但不证明"编译过程是确定性的"（不同编译器版本/优化级别可能产生不同结果）
- 它验证"符号存在/不存在"，但不证明"符号的语义是断言期望的"
- 它有"还原真实仓库"的副作用，但不证明"还原后仓库状态与跑批前完全一致"
- 它有并发锁和 manifest 隔离，但不证明"并发跑批不会互相干扰"

**翻译验证（Translation Validation）**的核心思想：不证明编译器本身正确（那是 CompCert 的做法，需要 10 年+），而是证明**每次编译的具体输入输出对是正确的**（检查编译前后的语义等价性）。这对本项目的 replay 有直接借鉴价值。

### 方向 2：翻译验证（Translation Validation）深度调研与本项目落地设计

**调研问题**：
- 翻译验证的核心概念：不证明编译器正确，只证明**每次编译的输入输出对**语义等价（source program ≈ target program）
- 翻译验证 vs 编译器验证（CompCert）：翻译验证是"每次编译都检查"，编译器验证是"一次性证明编译器正确"；翻译验证成本低但只覆盖具体编译，编译器验证成本高但覆盖所有编译
- 翻译验证的经典方法：
  - **Pnueli et al. (1999)**：最早的翻译验证框架，用模拟关系（simulation relation）证明源和目标的语义等价
  - **Necula (2000)**：携带证明的代码（Proof-Carrying Code），编译器生成证明，消费者验证证明
  - **Rinard & Marinov (1999)**：用符号执行和约束求解验证编译前后的等价性
  - **CompCert 的翻译验证**：CompCert 本身是"验证编译器"（编译器用 Coq 证明正确），但它的每个编译 pass 也有翻译验证
  - **Alive/Alive2**：LLVM 优化的翻译验证，用 SMT 求解器验证优化前后的语义等价
  - **Souper**：LLVM 超优化器，用 SMT 求解器验证超优化的正确性
- **本项目 replay 的翻译验证设计**：
  - replay 当前验证什么？（"夹具文件编译出的二进制与断言一致"）
  - 翻译验证能增强什么？（证明"编译前后的语义等价"，而不只是"编译结果与断言一致"）
  - 本项目的"源"和"目标"是什么？（源 = 夹具 .cpp 文件 + 编译命令；目标 = 编译出的二进制 + 符号表）
  - 语义等价的定义是什么？（对于 C++ 编译，"语义等价"很难形式化——但可以定义为"可观察行为等价"：相同输入产生相同输出、相同的未定义行为触发、相同的符号存在性）
  - 纯标准库能做什么？（比对编译前后的 AST？比对符号表？比对控制流图？——这些需要解析 C++ AST，纯标准库做不到）
  - 需要什么外部工具？（g++ -fdump-tree-all 导出 GIMPLE/RTL、clang -Xclang -ast-dump 导出 AST、nm/objdump 导出符号表、readelf 导出 ELF 信息）
  - **轻量级翻译验证方案**：不做完整的语义等价证明，只做"编译可复现性验证"——同一夹具用同一编译命令编译两次，产出的二进制 sha 一致（确定性编译）+ 符号表一致 + 关键段（.text/.data）一致。这是翻译验证的"弱化版"，但纯标准库+g++ 可做
  - **中量级翻译验证方案**：用 g++ -fdump-tree-all 导出 GIMPLE IR，比对编译前后的 GIMPLE（同一夹具不同优化级别的 GIMPLE 差异），验证"优化没有改变可观察行为"
  - **重量级翻译验证方案**：用 Alive2/Souper 验证具体的编译优化（如 -O2 中的某个 pass），需要 SMT 求解器（Z3），学习成本高
- **与现有 replay 的集成**：
  - replay 的 confirm/refute 判定增加"翻译验证"维度？（当前只有"断言与实际一致"，增加"编译可复现"）
  - 翻译验证作为 replay 的一个 inspection 点？（在 601 的 in-toto layout 中，replay_verify step 的 inspection 包含翻译验证）
  - 翻译验证的结果写入 metrics？（"编译可复现率"作为新指标）

**本项目现状**：没有翻译验证，replay 只验证"断言与实际一致"，不验证"编译本身的正确性/可复现性"。

**产出要求**：
- 翻译验证核心概念的准确解释（附经典论文链接和检索日期）
- 翻译验证 vs 编译器验证的对比
- 经典方法的概述（Pnueli/Necula/Rinard/CompCert/Alive2/Souper）
- 本项目 replay 的翻译验证设计（轻量/中量/重量三档方案，每档的具体做法、需要的工具、能验证什么、不能验证什么）
- 纯标准库能做的部分（编译可复现性验证：同一命令编译两次，sha/符号表/关键段一致）
- 需要外部工具的部分（GIMPLE IR 比对、AST 比对、SMT 求解）

### 方向 4：replay 不变量与活性属性的形式化规格

**调研问题**：

基于方向 1 的状态机建模，深入分析 replay 的**不变量**（必须始终成立的属性）和**活性属性**（最终会发生的属性），并给出形式化规格。

**replay 的不变量候选**（先核实，按实际代码调整）：
1. **仓库一致性不变量**：replay 完成后，真实仓库的状态与跑批前完全一致（所有临时文件被删除、所有被修改的文件被还原、git status 与跑批前相同）
2. **判定一致性不变量**：replay 的 confirm/refute 判定与证据卡的 artifact_assert 一致（断言"编译通过"且实际编译通过 → confirm；断言"编译通过"但实际编译失败 → refute）
3. **符号一致性不变量**：replay 检查的符号与 artifact_assert 中声明的符号一致（不多查、不漏查）
4. **并发隔离不变量**：并发跑批时，每个 worker 的沙箱互不干扰（一个 worker 的编译/删除/还原不影响另一个 worker 的判定）
5. **锁正确性不变量**：replay 锁（_REPLAY_LOCK）不会死锁（最终会被释放）、不会漏锁（需要互斥的操作都在锁内）
6. **manifest 一致性不变量**：replay manifest（build/replay_manifest.json）的条目与实际编译结果一致（manifest 中记录的 sha 与实际二进制 sha 一致）
7. **错误处理不变量**：replay 遇到 infra_error（编译环境问题）时，不会误判为 refute（infra_error 与 refute 严格区分）
8. **还原幂等不变量**：replay 的"还原真实仓库"操作是幂等的（连续还原两次，仓库状态相同）

**replay 的活性属性候选**：
1. **终止性**：replay 最终会完成（不会死锁、不会无限循环）
2. **公平性**：并发跑批时，每个证据卡最终都会被处理（不会有卡被饿死）
3. **进度性**：replay 处理 N 张卡的时间是 O(N)（不会因为卡数增加而超线性增长）
4. **错误恢复性**：replay 遇到 infra_error 后，能继续处理下一张卡（不会因为一张卡的错误而中断整个批次）

**形式化规格**：

- 每个活性属性用 TLA+ 公式表达（[]<> 表示"最终总是"，<> 表示"最终"）

### 方向 5：编译可复现性（Deterministic Builds）深度调研与本项目落地

**调研问题**：
- 编译可复现性的核心概念：同一源代码 + 同一编译命令 + 同一编译器版本 → 产出的二进制逐字节一致（bit-for-bit identical）
- 编译不可复现的常见原因：
  - 时间戳（__DATE__ / __TIME__ 宏、__TIMESTAMP__）
  - 随机数（编译器内部的随机化，如 ASLR 相关的随机布局）
  - 环境变量（PATH、LC_ALL、TZ 等影响编译行为）
  - 文件系统顺序（readdir 的顺序不确定，影响链接顺序）
  - 并行编译（make -j 的顺序不确定）
  - 绝对路径（调试信息中包含绝对路径）
  - 用户名/主机名（__FILE__ 宏、调试信息）
- 可复现构建的标准与工具：
  - **reproducible-builds.org**：可复现构建的标准定义和最佳实践
  - **diffoscope**：比较两个二进制文件的差异（深入到 ELF 段、调试信息、指令级别）
  - **strip + objcopy**：去除不可复现的部分（调试信息、符号表）
  - **SOURCE_DATE_EPOCH**：环境变量，用于替代 __DATE__/__TIME__ 的时间戳
  - **GCC -frandom-seed**：固定编译器内部随机种子
  - **GCC -ffile-prefix-map**：将绝对路径映射为相对路径
- **本项目的编译可复现性现状**（先核实，实跑验证）：
  - 同一夹具用同一编译命令编译两次，二进制 sha 是否一致？
  - 如果不一致，差异在哪里？（用 diffoscope 或 cmp 比较）
  - 本项目的夹具是否使用了 __DATE__/__TIME__/__FILE__ 等宏？
  - 编译命令是否包含绝对路径？
  - g++ 版本是否固定？（15.3.0，MinGW-w64）
- **本项目的编译可复现性提升方案**：
  - 轻量级：固定 SOURCE_DATE_EPOCH + -frandom-seed + -ffile-prefix-map，验证编译可复现
  - 中量级：用 diffoscope 比较两次编译的差异，定位不可复现的根源，逐一修复
  - 重量级：将编译可复现性作为 replay 的一个 inspection 点（每次 replay 都验证编译可复现，不可复现则 infra_error）
- **与翻译验证的关系**：
  - 编译可复现性是翻译验证的"弱化版"（不证明语义等价，只证明"同一输入产生同一输出"）
  - 编译可复现是翻译验证的必要条件（如果编译不可复现，翻译验证无法做——每次编译结果不同，无法验证"输入输出对"）
  - 本项目应该先做编译可复现性（轻量、纯标准库可做），再做翻译验证（中量/重量）
- **与 metrics 的集成**：
  - "编译可复现率"作为新指标（N 张卡中，M 张可复现 → M/N）
  - 不可复现的卡列入待修复清单

**产出要求**：
- 编译可复现性核心概念的准确解释（附 reproducible-builds.org 链接和检索日期）
- 编译不可复现的常见原因清单
- 可复现构建的工具清单（diffoscope/SOURCE_DATE_EPOCH/-frandom-seed 等）
- 本项目编译可复现性现状的实跑验证结果（同一夹具编译两次，sha 是否一致；如果不一致，差异在哪里）
- 本项目编译可复现性提升方案（轻量/中量/重量三档）
- 与翻译验证的关系（编译可复现是翻译验证的必要条件）
- 与 replay/metrics 的集成方案
- 成本-收益分析
- 反例：哪些因素导致编译不可复现且无法修复（如 g++ 本身的 bug）
- 外部一手来源（reproducible-builds.org/diffoscope 文档/GCC 文档），标注【已查证】或【一方称】
