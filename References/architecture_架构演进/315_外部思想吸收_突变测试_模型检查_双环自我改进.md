## 一、突变测试：从人工毒样例到自动变异评分

### 1.1 业界现状

**SWE-Mutation 基准**（arXiv 2605.22175，2026-08）：
- 用 agentic 变异框架生成"真实语义错误"的变异体，测试 LLM 生成的测试套件能否抓住
- DeepSeek-V3.1：Verified Reproduction Rate 仅 **10.20%**，Relative Detection Rate **36.15%**
- 结论：LLM 生成的测试/断言鉴别力很差，覆盖率高 ≠ 能抓 bug

**Meta 的实践**（InfoQ 2026-01）：
- 用 LLM 生成上下文感知的变异体，替代传统静态规则变异（算术替换/条件取反）
- 减少等价变异体噪声，聚焦高价值代码路径

**突变分数门槛**（业界共识）：
| 代码类型 | 最低突变分数 | 理由 |
|---|---|---|
| 安全/认证 | 70% | 安全关键 |
| 支付/金融 | 70% | 财务完整性 |
| 数据完整性 | 60% | 状态错误最难自检出 |
| 普通业务 | 50% | 成本/收益平衡 |

### 1.2 对「阙疑」的启发

我们的 poison_drill（P1-P7）是**人工写的毒样例**，覆盖 7/30 条规则（23%）。问题：
1. 人工写毒样例慢，且只能覆盖写样例的人能想到的错误模式
2. 没有"突变分数"概念——不知道门禁到底能抓住多少种错误
3. 新规则上线时，不一定有对应的毒样例

**升级方案：突变测试驱动的门禁质量度量**

```
对每张证据卡，自动生成变异体：
  M1: 删掉一个 artifact_assert 条目（断言弱化）
  M2: 把 contains_any 改成 contains（断言强化，应 refute）
  M3: 修改 actual 中的一个值（证据篡改）
  M4: 删掉 controlled_vars（变量控制缺失）
  M5: 把 claim 改成与 actual 矛盾的方向（claim 与证据不符）
  M6: 删掉 falsification（可证伪性缺失）

对每个变异体跑 replay + gate：
  被抓住（refute/block）→ killed ✓
  没抓住（confirm/pass）→ survived ✗

突变分数 = killed / total
```

**落地路径**：
1. 先写 `tools/mutation_drill.py`，支持 M1-M3（机械变异，不需要 LLM）
2. 对全库 48 张卡跑一轮，得到基线突变分数
3. 分数 < 60% 的卡 → 红队重点审查（断言太弱）
4. 新卡必须达到 ≥60% 才能入库（DAL 级门槛）

### 1.3 与现有 poison_drill 的关系

- poison_drill：**规则级**验证（每条规则有对应毒样例，确认规则能拦住）
- mutation_drill：**卡级**验证（每张卡的断言强度，确认卡能被变异抓住）
- 两者互补：poison_drill 保证规则不退化，mutation_drill 保证内容不注水

## 二、并发内存模型：litmus test + 模型检查

### 2.1 业界工具

| 工具 | 能力 | 对我们的价值 |
|---|---|---|
| **CDSChecker** | C11/C++11 原子的模型检查器，穷举所有线程交错 | CONC 原子的"确定性行为"验证，不依赖运行时调度 |
| **DIVINE** | 显式状态模型检查器，检查死锁/数据竞争/断言违反 | 可选，需要 LLVM 编译链 |
| **cppmem** | Cambridge，从 Isabelle/HOL 生成代码探索内存模型语义 | 理论参考 |
| **litmus test** | 并发编译器测试的标准格式 | 夹具设计范式 |

### 2.2 对 CONC 域的启发

当前 CONC-001 的做法是"写夹具 → 编译看 .asm → 运行看输出"。问题：
- 运行时输出依赖调度，不确定
- .asm 只能看编译器做了什么，不能看"允许的行为集合"

**litmus test 范式**：
```c
// 标准 litmus 格式：两个线程，初始状态，观测最终状态
int main() {
    atomic_int x = 0, y = 0;
    int r1, r2;
    // 线程 A
    { atomic_store(&x, 1, memory_order_release); }
    // 线程 B
    { r1 = atomic_load(&y, memory_order_acquire);
      r2 = atomic_load(&x, memory_order_acquire); }
    // 观测：r1=1 && r2=0 是否可能？
}
```

**模型检查的价值**：
- CDSChecker 穷举所有线程交错，告诉你"哪些最终状态是允许的"
- 不依赖运行时调度，结果确定
- 对"内存序六档的可观测差异"这类主题，模型检查比运行时测试可靠 100 倍

**落地路径**：
1. CONC-001/002/003 的夹具用 litmus 格式写（标准、可移植）
2. 证据卡的 claim 锚定"模型检查允许的行为集合"，而非"某次运行的输出"
3. CDSChecker 如能在 WSL 安装，作为 CI 可选步骤（不强制，工具链重）
4. 不能安装时，用"编译器工件 + 标准条文"双锚定（当前做法的强化）

### 2.3 关键约束

- litmus test 是**小而精**的测试，不适合复杂场景
- 模型检查有状态空间爆炸问题，只适合 <10 行的并发片段
- 我们的夹具（如 false sharing 性能测试）不适合 litmus 格式，仍用传统方法
- **结论**：CONC 域的"内存序/数据竞争"类原子用 litmus，"性能/工程"类原子用传统夹具

## 三、双环自我改进：从三权分立到持续进化

### 3.1 业界最新架构

**ASG-SI**（arXiv 2512.23760，Audited Skill-Graph Self-Improvement）：
- 把自我改进当作"迭代编译"——agent 被编译成一个不断增长的有向技能图
- 提升由**验证器背书的证据**门控，不是 LLM 自说自话
- 组合：可验证的分解奖励 + 经验合成（压力测试+课程覆盖）+ 持续记忆控制

**ReVeal**（arXiv 2506.11442）：
- 多轮 RL，生成-验证交错
- 每轮密集奖励（不是只看最终结果）
- 生成能力与验证能力共同进化

**Armature**（GitHub，2026-08）：
- **双环设计**：
  - 内环：post_run refiner（DAG 完成后看完整轨迹，精炼）
  - 外环：SelfImproveRunner（load traces → diagnose → propose YAML revision → auto-apply）
- 强调"复现失败签名"——从历史失败中诊断系统性问题

**Self-Harness pattern**（GitHub，2026-09）：
- 提案（创造性、便宜）与验证（确定性、昂贵）分离
- 人拥有晋升门（human-owned promotion gate）
- 可重放的回归套件（replayable regression suites）

### 3.2 对「阙疑」的启发

我们当前的三权分立（Writer → 红队 → Gatekeeper → 人审）是**单环**——每颗原子独立闭环，但批次之间的经验没有系统化回流。

**双环升级**：

```
内环（每颗原子）：
  Writer 生产 → 红队制衡 → Gatekeeper 门禁 → 人审签署
  ↓
  产出：verified 原子 + 证据卡 + 红队报告

外环（每批/每周）：
  收集内环的红队报告 + 门禁 warn + CI 失败
  ↓
  诊断：哪些错误模式反复出现？哪些规则没拦住？哪些提示词误导了 Writer？
  ↓
  Propose：新规则 / 新毒样例 / 提示词修订 / 工具改进
  ↓
  验证：回归测试（全库 replay + poison + mutation）
  ↓
  晋升：人审签署后合入，成为下一批的内环约束
```

**外环的具体产出物**：
1. **错误模式台账**：每批红队抓到的阻断级问题，按"错误类型"分类，统计频率
2. **规则覆盖率**：poison_drill 的 RULE-COVERAGE（当前 7/30 = 23%），目标 >60%
3. **突变分数趋势**：全库卡的平均突变分数，目标 >60%
4. **提示词修订记录**：312→314 的修订就是外环产出（CONC-001 实测推翻了 312 的方向）

**与 G6 四级状态的关系**：
- 内环用 G6 状态机（draft → redteam → gate → verified）
- 外环用"提案-验证-晋升"流程，产出物是规则/提示词/工具的改进
- 外环的改进必须经过回归验证，不能直接改内环约束

## 四、3C 原则：证据的质量度量

### 4.1 SmartSnap 的 3C 原则

- **Completeness（完整性）**：证据是否覆盖了 claim 的所有方面？
- **Conciseness（简洁性）**：证据是否没有冗余？（对应我们的三层分离瘦身）
- **Creativity（创造性）**：证据是否揭示了新东西，而不只是重复已知？

### 4.2 对证据卡的应用

当前证据卡的质量检查是"门禁规则"（机械的），缺少"质量评分"。

**3C 评分（红队执行，每卡 1-5 分）**：
| 维度 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| Completeness | 只覆盖 claim 的一个方面 | 覆盖主要方面，缺边界 | 全覆盖 + 边界 + 反例 |
| Conciseness | 200+ 行，大量重复 | ~100 行，有少量冗余 | <80 行，无冗余（三层分离） |
| Creativity | 重复已知结论，无新发现 | 有一个新观测 | 有反直觉的新发现（如 LEAK-002 的观测反转） |

**门槛**：3C 总分 <9 的卡不能入库（红队签署）。
