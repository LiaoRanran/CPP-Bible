# 407 阙疑提示词压缩与 Token 成本优化：五层压缩 + 缓存联合优化

> 日期：2026-09-13。外部调研：LLMLingua（20× 压缩、LongLLMLingua 4× 压缩反升 21.4%）、Selective Context（自信息剪枝）、Shopify Gisting（主旨词元）、即时加载（JIT Section Loading）、前缀缓存（90% 折扣、命中率 7%→74%）、Cache-Aware Prompt Compression（压缩与缓存的冲突）。
> 核心问题：**阙疑的提示词越来越长（312 要压缩 30%），每次生产原子都加载完整规则+模板，多轮对话历史无限累积。token 就是钱，压缩就是直接省钱。**

---

## 一、阙疑的 Token 成本结构（钱花在哪了）

| 成本源 | 特征 | 占比估计 |
|---|---|---|
| 系统提示词（规则+模板+纪律） | 每次调用都加载，稳定不变 | ~30% |
| 任务提示词（312/401/402/403 等） | 每批生产加载一次，长 | ~25% |
| 上下文（对话历史+已读文件） | 多轮累积，越来越长 | ~30% |
| 工具描述（MCP/函数调用 schema） | 每次调用都加载，很多用不到 | ~10% |
| 输出（模型生成） | 通常比输入短 | ~5% |

**关键洞察**：输入 token 占 90%+，输出只占 5%。优化输入的 ROI 远大于优化输出。

---

## 二、五层压缩技术（从易到难，ROI 从高到低）

### L1：结构化压缩（立即可做，零风险，省 20-40%）

**原理**：同样的信息，结构化表达比散文省 token，且模型理解更快。

| 手法 |  before | after | 省 token |
|---|---|---|---|
| 散文→列表 | "你必须先检查 A，然后检查 B，最后检查 C" | "检查顺序：A→B→C" | ~50% |
| 冗余引导语删除 | "请你务必注意，在任何情况下都不要" | "禁止：" | ~70% |
| 重复表述合并 | 三处各写一遍"工件必须与断言同代" | 一处定义+三处引用 | ~60% |
| 表格代替段落 | 段落描述规则名+级别+触发条件 | 三列表格 | ~40% |

**对 B1（312 压缩）的具体建议**：
- 312 的"选题论证表"已经是表格，好
- 但 §4.1/§4.2/§4.3 的正文有大量散文式约束，可以压缩为"条件→动作"列表
- 13 项 can't-miss 清单每条可以压缩为"触发词→检查动作→反例"三列
- 目标：体积减 ≥30%，约束条目数不变（用 grep 核对）

### L2：即时加载（JIT Section Loading，省 40-60% 系统提示词）

**原理**：用 20-30 行目录代替完整指令文件，只在触发条件满足时加载详情段。

**阙疑应用**：
- 当前系统提示词包含 Writer/红队/Gatekeeper/人审四个角色的全部规则，但一次只扮演一个角色
- 改为：
  ```
  【角色目录】
  - Writer 规则（触发：生产原子时加载）
  - 红队规则（触发：红队阶段加载）
  - Gatekeeper 规则（触发：门禁阶段加载）
  - 人审规则（触发：人审阶段加载）
  ```
- 每次只加载当前角色的规则，其他角色的规则不进上下文
- 预计系统提示词从 ~3000 token 降到 ~800 token（省 70%）

**实现方式**：不需要工具支持，提示词本身写成"目录+按需引用文件路径"，模型在需要时主动 Read 对应文件。

### L3：动态工具呈现（省 10-20% 工具描述）

**原理**：AWS 最佳实践——每次调用只呈现相关工具，工具描述压缩为"名称+一句话+精简参数"。

**阙疑应用**：
- 当前 MCP 工具列表很长，但生产原子时只用 Read/Write/Bash/gate/replay
- 红队时只用 Read/Bash/grep
- 可以按角色预定义工具子集，减少每次加载的工具 schema
- 工具描述从"完整功能说明"压缩为"一句话+必需参数"

### L4：递归摘要（Agent Loop 压缩，省 30-50% 上下文）

**原理**：多轮生产中，每几步用小模型/便宜模型总结之前的步骤，代替完整历史。

**阙疑应用**：
- 当前"上下文总结"已经在做，但可以更系统化：
  - 每 5 轮自动触发一次摘要（用便宜模型，如 Seed-Code 0.06x）
  - 摘要只保留：当前状态、已完成项、待办项、关键决策、文件路径
  - 不保留：完整对话、工具输出细节（需要时重新 Read）
- 这是"不可压缩事实清单"（401 A3）的自动化实现

### L5：LLMLingua 级动态压缩（长期，省 60-80% 检索内容）

**原理**：用小模型的困惑度信号检测不重要的 token，黑盒压缩。LongLLMLingua 在 NaturalQuestions 上 4× 压缩反而提升 21.4%（去掉噪音后关键信息密度更高）。

**阙疑应用**：
- 证据卡内容（动态检索的）适合动态压缩
- 系统提示词（稳定的）不适合——query-aware 压缩每次结果不同，会破坏前缀缓存
- 当前不具备小模型部署条件，列为长期方向

## 三、前缀缓存优化（与压缩互补，省 45-90% 重复输入）

### 核心规则：稳定内容放前面，易变内容放后面

```
正确顺序（从最稳定到最易变）：
1. system prompt（固定）
2. 规则/模板（固定，版本升级才变）
3. 任务提示词（一批生产不变）
4. 已读文件内容（当前任务不变）
5. 历史对话（追加式，前缀稳定）
6. 当前指令（每轮变化）
```

### 阙疑的缓存优化点

1. **系统提示词已经是稳定前缀**——确保它在最前面，不要在中间插入易变内容
2. **规则文件按版本号引用**——`gate_engine v42` 而不是每次把规则全文贴进提示词，版本不变则前缀不变
3. **多轮对话追加式**——不要每轮重新组织历史，保持追加，前缀缓存命中率高
4. **缓存不是免费的**——只使用一次的前缀比不缓存更贵（写入费 1.25× > 读取费 0.1×），所以短任务不要刻意缓存

### 数据
- Anthropic 缓存读取 0.1× 费率（90% 折扣）
- 命中率从 7% 优化到 74% 的工程实践存在
- 4 个模型测试：缓存节省 45%-80% 成本，延迟改善 13%-31%
- 31% 的 LLM 请求有语义相似性——没有缓存就是巨大浪费

## 四、关键陷阱：压缩与缓存的冲突

**Cache-Aware Prompt Compression 的核心发现**：
- query-aware 压缩（LLMLingua）会让每次压缩结果不同
- 这机械地使前缀缓存失效——每次都是新前缀，无法命中缓存
- 压缩省的钱可能被缓存失效吃掉

**阙疑的应对策略**：
| 内容类型 | 压缩方式 | 缓存友好？ |
|---|---|---|
| 系统提示词（稳定） | L1 静态压缩（人工） | ✅ 压缩结果不变，前缀稳定 |
| 规则/模板（稳定） | L1 静态压缩 | ✅ |
| 任务提示词（半稳定） | L1 静态压缩 + L2 即时加载 | ✅ 目录部分稳定 |
| 证据卡/检索内容（动态） | L5 动态压缩（长期） | ❌ 每次不同，不缓存 |
| 对话历史（累积） | L4 递归摘要 | ⚠️ 摘要后前缀变化，需策略 |

**原则**：稳定内容用静态压缩+缓存，动态内容用动态压缩不缓存。两者不要混。

## 五、对 B1（312 压缩）的升级建议

苦力Agent正在做 312 压缩，407 的调研可以补充：

1. **压缩目标从"减 30%"升级为"减 30% + 前缀缓存友好"**：
   - 确保压缩后的 312 结构稳定（目录在前、详情在后）
   - 易变内容（具体选题、夹具名）放在最后

2. **加 L2 即时加载**：
   - 312 的"附录 A/B/C"可以改为"触发时加载"
   - 主提示词只保留目录+核心约束，附录作为独立文件

3. **压缩后验证**：
   - 不仅 grep 核对约束条目数
   - 还要测"压缩后的提示词能否产出同样质量的原子"（用一颗已知原子做 A/B 对比）

4. **token 计数**：
   - 压缩前后用 tokenizer 实算（不是估算字数）
   - 记录"压缩前 X token → 压缩后 Y token，省 Z%"

## 七、元结论

提示词压缩不是"把字写少"——是**信息密度工程**。LongLLMLingua 证明了 4× 压缩反而提升 21.4% 性能，因为去掉了噪音，关键信息密度更高。

阙疑的提示词有三个独特的压缩机会：
1. **四角色分离**——一次只扮演一个角色，其他角色的规则不需要加载（L2）
2. **规则稳定**——系统提示词+规则是稳定前缀，极度适合前缀缓存
3. **生产流程标准化**——每批生产的提示词结构相同，压缩模板可以复用

**先做 P0**：L1 结构化压缩（B1 正在做）+ 前缀缓存优化（确保稳定内容前置）。这两个零风险、立刻见效。
