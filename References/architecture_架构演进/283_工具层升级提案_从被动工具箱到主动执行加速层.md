# 工具层升级提案：从「被动工具箱」到「主动执行加速层」

> 2026-09-12 · 第 283 份。回答用户问题「工具层还有无升级调研必要」——结论：**非常有必要，且是当前性能轴的最大瓶颈**。本文是工具层升级提案，与 282 宪法 v1.1 修正案互补（架构管「怎么干才对」，工具层管「怎么干才快」）。

### 关键缺口
1. **Agent 找东西靠 rglob/grep/Read**——82 份 References + 20 原子 + 42 证据卡 + 79 误解 + 1528 Examples，没有语义检索，没有快速定位。
2. **Writer 从零写 Markdown**——没有模板引擎、没有 frontmatter 生成器、没有夹具骨架复用。每批原子都从零搭结构。
3. **记忆是单层文本**——MEMORY.md（之前 334 行被压缩）+ daily memory，没有分层、没有检索、Agent 不能自己管理记忆。
4. **按行号编辑脆弱**——Read/Edit 按行号，行号漂移就 Edit 失败；没有按符号/字段寻址的能力。
5. **54 个工具未普查**——CI 只调 36 个，~54 个状态未知（僵尸/本地用/废弃），是技术债。

## 二、四方向外部调研成果

### 方向 1：高效撰写
- **RepoAgent**（arXiv 2402.16667）：三阶段——全局结构分析→文档生成→**文档更新**（增量更新，不是全量重写）。
- **Docs-from-Diff**：代码变更时自动触发文档更新（PostToolUse hook）。
- **arc42 Toolkit**：12 章节各有 dedicated skill，先问对问题再生成结构化草稿。
- **AI Project Template v3**：MEMORY.md + HANDOFF.md + AGENTS.md + CONVENTIONS.md 预加载模式。
- **吸收**：原子生产用「Docs-from-Diff」思想——夹具变更时自动触发证据卡更新；用结构化模板减少 Writer 从零搭结构的负担。

### 方向 2：多文件驾驭
- **tree-sitter**：增量解析、多语言、容错（语法错误也能给出有用结果）。
- **agent-file-tools (AFT)**：「给 Agent 一个 IDE」——按语义寻址（函数/类/符号）而不是按行号，编辑后验证语法。
- **Code HUD**：symbol-aware editing，编辑后 tree-sitter 重解析验证，无效语法拒绝。
- **吸收**：我们的主要文件是 Markdown（tree-sitter 支持有限），但对 .cpp 夹具、.py 工具、.yml CI 配置很有用。先做 Markdown 的 frontmatter 字段级寻址（YAML 解析），代码文件后续加 tree-sitter。

### 方向 3：内容高效检索（最有争议的方向）
- **Claude Code 放弃了 RAG**——Anthropic 工程师在 Latent Space 播客说：代码场景向量检索不如精确搜索（grep/glob/find），让模型自己调用工具更准。
- **但我们的项目是文档为主**——20 原子 + 42 证据 + 79 误解 + 82 References，找「讲移动语义的原子」用语义搜索比 grep "move" 更准。
- **tRPC code_rag**：混合检索（语义向量 + 元数据/字面量过滤）+ 图遍历（call graph）。
- **吸收**：**混合检索**——文档层用语义（原子/证据/误解/References 向量化），代码层用精确（grep/glob），图遍历用 knowledge_graph（prerequisite/serves 边）。一个入口 `kb_search "移动语义"` 返回相关原子+证据+夹具。

### 方向 4：外置高效记忆
- **Letta (MemGPT)**：三层记忆——核心记忆（in-context，RAM）/ 回忆记忆（对话历史）/ 归档记忆（外部存储，disk）。Agent 自己管理换页（paging）。
- **「Is a Filesystem All You Need?」**——Letta 基准测试发现文件系统对很多场景够用，但分层记忆在长任务中显著更好。
- **记忆是 git 仓库**——Agent 拥有并编辑，跟随 Agent 到处走。
- **吸收**：当前 MEMORY.md 单层升级为三层：核心（宪法+铁律，in-context）/ 回忆（最近批次状态，l2_state）/ 归档（历史详情，可检索）。Agent 自己管理（写/归档/检索），记忆是 git 仓库的一部分。

## 三、工具层升级提案（4 工具 + 1 治理）

### T1：原子脚手架工具 `tools/atom_scaffold.py`（高效撰写，P0）

**机制**：给定原子 ID（如 `ATOM-MEM-ALLOC-002`），自动生成：
- 原子 frontmatter 模板（含 claim_pre/post/invariant，依赖修正案 1）
- 2 张证据卡模板（含 actual/sha/command 占位）
- 1 条误解模板（含触发词/反例占位）
- 夹具骨架（从 `templates/` 库选最接近的模式：分配计数型/析构观测型/地址判定型/性能基准型）

**机械判据**：脚手架生成的文件必须通过 gate 的 schema 检查（L1）；夹具骨架必须编译通过（空 main）。

**与宪法关系**：依赖修正案 1（claim 契约化）；是修正案 4 sleep 阶段的消费者（templates/ 库由 sleep 阶段维护）。

**预期收益**：Writer 从零写结构 → 只填内容，单颗原子生产时间预计降 30–40%。

### T2：统一文件工具 `tools/file_ops.py`（多文件驾驭，P2）

**机制**：封装 Read/Edit/Write，支持：
- **按 frontmatter 字段寻址**：`file_ops set atoms/mem/ATOM-MEM-001.md claim_post "dtor_count=1"`——不按行号，按 YAML 字段。
- **编辑后自动验证**：YAML 格式、Markdown 结构、frontmatter 必填字段。
- **批量操作**：`file_ops batch --domain mem --field status --to draft`（批量改字段，受 gate 拦截防误操作）。
- 代码文件（.cpp/.py）后续加 tree-sitter 符号级编辑（先做 Markdown，代码文件是第二阶段）。

**机械判据**：任何字段级编辑后必须通过 YAML 解析；批量操作必须有 dry-run 模式。

**与宪法关系**：横切工具，不依赖修正案。

**预期收益**：消除行号漂移导致的 Edit 失败；批量操作（如全库 [xvalue.cast]→[expr.static.cast]）从手动逐个改 → 一条命令。

### T3：混合检索工具 `tools/knowledge_search.py`（内容高效检索，P0）

**机制**：一个入口 `kb_search <query>`，三路并行：
1. **文档语义检索**：原子/证据/误解/References 的 frontmatter + 正文向量化（用本地 embedding 模型，如 sentence-transformers，离线无 API 依赖），返回 top-k 相关文档。
2. **代码精确检索**：夹具/工具/CI 配置用 ripgrep（精确，不用语义）。
3. **图遍历**：knowledge_graph.json 激活，按 prerequisite/serves 边遍历（如「找 MOVE-002 的所有下游原子」）。

**机械判据**：每次检索返回结果必须带文件路径 + 匹配片段 + 置信度；语义检索结果必须可被精确检索交叉验证（防幻觉）。

**与宪法关系**：依赖修正案 4（prerequisite 边构建）；是 knowledge_graph.json 从僵尸到激活的路径。

**预期收益**：Agent 找「讲 XX 的原子」从 rglob+grep+Read 多轮 → 一次调用；红队独立上下文的「相关原子检索」更精准。

**关键设计决策**：不用外部向量 API（隐私+成本），用本地 sentence-transformers（~100MB 模型，CPU 可跑）。如果本地 embedding 质量不够，退化为「关键词 + frontmatter 字段过滤」的混合精确检索。

### T4：分层记忆工具 `tools/memory_manager.py`（外置高效记忆，P1）

**机制**：三层记忆，Agent 自己管理：
- **核心记忆（core）**：宪法 + 铁律 + 当前批次状态——in-context，每次对话注入（已在做，系统提示）。
- **回忆记忆（recall）**：最近 N 批的决策/教训/失败模式——`Memory/recall.md`，Agent 可读可写，上下文耗尽时作为恢复入口。
- **归档记忆（archive）**：历史批次详情、调研文档、红队报告——References/ + docs/，通过 T3 检索工具访问，不直接进上下文。

Agent 操作：`memory write "第五批教训：ALLOC-002 口径反转"` → 自动进 recall；`memory archive --batch 5` → recall 中第五批内容移到归档；`memory recall "口径反转"` → 搜 recall + archive。

**机械判据**：core 记忆不可由 Agent 自行修改（只能人修宪）；recall 每次写入必须带时间戳和来源批次；archive 必须可检索。

**与宪法关系**：横切，是「无人自纠错闭环」的记忆基础设施——上下文耗尽后 Agent 能从 recall 恢复，不需要人重新喂上下文。

**预期收益**：长任务（多批次）上下文耗尽后的恢复时间从「人重新喂摘要」→「Agent 自己读 recall 恢复」；MEMORY.md 不再膨胀（334 行的问题根治）。

### T5：工具治理（元层，P1）

**机制**：90 工具普查四分类（Bazel 四态迁移）：
- **LTS（长期支持）**：CI 调用 + 有测试 + 有文档——核心工具。
- **Active（活跃）**：本地调用 + 有维护者——常用工具。
- **Maintenance（维护）**：偶用 + 无活跃开发——保留但不新增功能。
- **Deprecated（废弃）**：僵尸/重复/被替代——归档到 `tools/_archive/`，从 CI 移除。

每个工具加 `OWNER`（human:liaoranran 或 system）和 `LIFECYCLE` 字段（在工具 docstring 或 `tools/TOOL_REGISTRY.md`）。

**机械判据**：CI 只调 LTS/Active；Deprecated 工具 90 天后删除；新工具必须先登记到 TOOL_REGISTRY。

**与宪法关系**：与修正案 5（概念审计）同精神——工具层也防膨胀。

```

修正案 5（概念审计）────────→ T5（工具治理，同精神）
T2/T4 ────────────────────── 横切，不依赖修正案
```

**实施顺序建议**：
1. **T3 混合检索先做**（P0，当前最大瓶颈，不依赖修正案——可以先用关键词+frontmatter 过滤，语义检索后续加）
2. **T1 原子脚手架**（P0，依赖修正案 1，与修正案 1 同步实施）

4. **T5 工具治理**（P1，还债，90 工具普查）
5. **T2 统一文件工具**（P2，nice-to-have，当前 Read/Edit 够用）

## 五、给用户的话

回答你的问题：**工具层非常有升级必要，而且是当前性能轴的最大瓶颈。**

架构层（宪法 v1.1）管「怎么干才对」，工具层管「怎么干才快」。当前 90 个工具全是门禁/审计/编译/清理，**零检索、零撰写辅助、零结构化记忆**——Agent 每批原子都在「找东西 + 从零搭结构 + 手动维护记忆」上浪费大量上下文。

四个工具的预期收益：
- **T3 混合检索**：找东西从多轮 rglob/grep → 一次调用，红队独立上下文的检索更精准。
- **T1 原子脚手架**：Writer 从零写结构 → 只填内容，单颗生产时间降 30–40%。
- **T4 分层记忆**：上下文耗尽后 Agent 自己恢复，不需要人重新喂摘要。
- **T2 统一文件工具**：消除行号漂移，批量操作一条命令。

**与 282 宪法 v1.1 的关系**：T1 依赖修正案 1，T3 依赖修正案 4。建议**架构和工具同步推进**——修正案 1 落地时 T1 同步上线，修正案 4 落地时 T3 的图遍历上线。

**下一步**：T3 混合检索不依赖任何修正案，可以**立刻开工**（先用关键词+frontmatter 过滤的轻量版，语义检索后续加）。你说「开干」我就先做 T3 的最小可用版。或者你想先把 282 宪法 v1.1 的红队批判走完，再统一实施架构+工具？
