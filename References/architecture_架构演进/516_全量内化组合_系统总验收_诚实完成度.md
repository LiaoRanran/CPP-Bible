## 二、501-515 之间的矛盾和重叠

### 2.1 重复设计（三份文档讲同一件事）

| 主题 | 出现在 | 问题 |
|---|---|---|
| 多模型级联路由 | 503、509、513 | 三份各说各的，503说FrugalGPT、509说级联、513说Inter-Cascade，没统一 |

| 错误处理 | 512（容错降级）、515（重试退避） | 512说熔断，515说retry，没合并 |
| 文档治理 | 510、513（知识压缩） | 510说去重，513说四层压缩 |
| 自进化 | 502、510、512 | 三份都说"系统自己进化"，机制不同 |

### 2.2 矛盾（互相打架的设计）

1. **"严格block"vs"WARN过渡"**：
   - 369/373追求block=0零容忍
   - 514说新规则应该WARN跑两周再BLOCK
   - 这两个不矛盾，但需要显式流程：新规则默认WARN→观察→BLOCK

2. **"全量replay"vs"增量replay"**：
   - 498做了增量replay（0.3s）
   - 470 P0-A重编译不变量要求全量重编译（300-400s）
   - 矛盾点：增量模式下重编译不变量怎么保证？498没解决这个

3. **"56张卡串行"vs"16核并行"**：
   - 514建议ProcessPoolExecutor并行
   - 470的build/.replay_lock是独占锁
   - 并行需要改锁机制，514没提这个冲突

4. **"人工push"vs"自动化"**：
   - 铁律7：Agent不push
   - 515说备份是P0紧急
   - 矛盾：SSH被阻断，Agent不能push，用户不push就丢数据

## 三、批判：系统现在的真实问题

### 3.1 最大的问题：调研膨胀 vs 工程落地

**247份架构文档，落地16项（6.5%）。**

这不是"系统很强"，是"设计很多、落地很少"。501-515这15份文档里：
- 501-507是"愿景设计"
- 508是"派给苦力的提示词"
- 509-515是"继续想"

真正在磁盘上跑的，是508提示词里的工程任务+494/498几轮迭代。设计文档比代码多20倍。

### 3.2 工具碎片化

100个tools/*.py，但功能重叠：
- `compile_all.py` / `compile_gate.py` / `compile_run_sanitize_pipeline.py` / `d5_compile_gate.py` / `d5_runtime_gate.py`——5个编译相关
- `verify_asm_evidence.py` / `verify_compiler_features.py` / `asm_repro_spotcheck.py`——3个asm验证
- `chapter_compile_check.py` / `chapter_lint.py`——章节检查

**问题**：谁调用谁？100个工具之间的依赖图没人画过。

### 3.3 知识没有压缩

247份文档，每份5-14KB，总共~2MB的Markdown。
- 没有一份"系统全貌"（505是7KB的简版）
- 新Agent进来要读247份才能理解系统
- 513设计了四层压缩，但没执行

### 3.4 备份是单点故障

**ahead 176个commit未push**。这是最严重的。
- 不是"设计不够好"的问题
- 是"数据可能全丢"的问题
- 其他100个工具、55条规则、72毒样例——如果磁盘挂了，全没了

## 六、核心诚实结论

**这个系统不是"很强"，是"很详细"。**

- 详细：247份设计文档、55条规则、72毒样例、7轮对抗、100个工具
- 但：落地率6.5%、备份是单点故障、工具碎片化、知识没压缩

**和用户理想的差距**：
- 用户想要"烧多少token不浪费、性能质量压满、所有情况游刃有余"
- 现状：性能replay串行298s、质量block=0但有逃逸、token成本没追踪清楚

**真正的下一步**：不是再设计，是收债。把已有的100个工具理顺、176个commit推上去、247份文档压缩成1份全貌。做完这些，系统才从"骨架"变成"能跑的身体"。
