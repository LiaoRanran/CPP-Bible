# 387 可观测性与 Agent 调试：知道 Agent 在干什么、哪里慢、哪里错

> 日期：2026-09-13。监工完成。374-386 之后的架构升级轮，聚焦**可观测性**——我们只有门禁结果，没有 Agent 内部的可观测性（每步 token、耗时、错误、决策路径）。
> 核心命题：**Agent 是非确定性的——同样的输入可能触发不同的工具序列。没有可观测性，失败就是"神秘的"，不是"可诊断的"。四支柱：Traces+Metrics+Logs+Evaluations。**
> 流程：搜集 → 整理 → 挖掘 → 联系 → 批判 → 结合 → 应用。

## 一、核心发现

**四支柱模型**（Portkey/agentic-ai）：
1. **Traces**：完整执行路径——每个 LLM 调用、工具调用、检索步骤、中间决策，携带输入/输出/token/延迟/成本
2. **Metrics**：聚合时间序列——token 消耗趋势、延迟分布、错误率、成本 per request/session
3. **Logs**：结构化事件记录——调试和审计
4. **Evaluations**：自动质量评分——LLM-as-judge、幻觉检测、回归测试

**Trace = span 树**：root span = 用户请求，child spans = 检索/提示词组装/每个 LLM 调用/每个工具调用。每个 span 携带：时间戳、token 数（input/output/cached）、模型 ID、工具参数/结果、完成原因、错误状态。

**四层监控**（Luong Hong Thuan）：
- L1 基础设施：token/请求、TTFT、总完成时间、LLM API 错误率、成本
- L2 推理轨迹：发了什么 prompt、返回了什么、调用了哪些工具
- L3 决策质量：评估分数、幻觉率、回归测试通过率
- L4 用户体验：任务完成率、用户满意度

## 二、和我们系统的映射

| 外部概念 | 我们的现状 | 差距 |
|---|---|---|
| Traces | 只有最终报告（"红队 3 阻断"），无中间步骤 | 缺结构化 trace |
| Metrics | 有门禁数字（replay 56/56、gate block=0），无趋势 | 缺时间序列 |
| Logs | 2026-09-12.md 流水账（非结构化） | 缺结构化日志 |
| Evaluations | 红队+门禁=评估，但无自动评分 | 部分有 |
| Token 归因 | 从未追踪每步 token | 完全缺失 |
| 延迟归因 | 从未追踪哪步是瓶颈 | 完全缺失 |

## 三、挖掘（核心洞察）

**1. 我们的"吞吐下降"问题，没有可观测性就无法诊断根因**：
- 我们知道"从一批 4 颗降到一个窗口改 1-2 个文件"，但不知道是哪步慢了
- 是红队子 Agent 慢？是 replay 编译慢？是上下文压缩慢？还是 Agent 在重复读文件？
- **没有 per-step token 和延迟数据，"吞吐下降"只是感觉，不是事实**

**2. Token 归因是成本优化的基础**：
- 384 说"50-70% 任务可用最便宜层"，但我们不知道每类任务实际花多少 token
- 生产一颗原子花多少 token？红队花多少？门禁花多少？
- **没有 token 归因，路由决策就是拍脑袋**

**3. Trace 是数据飞轮（385）的输入**：
- 385 说"结构化 trace 是 triplet (task, trajectory, outcome) 的基础"
- 没有 trace，就无法做失败聚类和根因分析
- **可观测性是数据飞轮的前提——没有 trace，Distill 阶段就是空中楼阁**

**4. 我们的门禁是"黑盒评估"，不是"白盒可观测"**：
- gate 告诉我们"block=0 warn=8"，但不告诉我们"Agent 为什么写出了触发 warn 的卡"
- replay 告诉我们"confirm=56"，但不告诉我们"每张卡的断言是怎么设计的、花了多少轮修改"
- **可观测性 = 知道"为什么"，不只是"是什么"**

## 四、应用（分阶段）

### 立即落地（零成本）

**应用 1：每颗原子的 trace 文件**（和 385 应用 4 合并）
- `docs/kernel/traces/ATOM-XXX_trace.md`：记录关键决策点（claim 设计、夹具选择、红队阻断、人审裁决）+ 每步 token 估算 + 耗时
- 不记录完整工具输出（383 工具输出清理），只记录决策点

**应用 2：KPI 趋势线**（和 381 合并）
- 每批结束记录：原子数、证据卡数、replay 数、gate 规则数、毒样例数、token 估算、耗时
- 存到 `docs/kernel/kpi_trends.md`，判断"系统变强"用趋势不用感觉

### 中期落地

**应用 3：门禁输出结构化**
- gate/replay/poison 的输出从散文改成 JSON/表格
- 包含：规则名、命中原子、严重度、修复建议
- 这是 386 结构化输出的一部分

## 五、局限

- 完整可观测性需要 SDK 集成（LangSmith/Langfuse），我们当前环境不具备
- 手动 trace 增加了每批的文件数量，需要和 383 上下文工程配合
- Token 估算（length/4）不精确，但比"完全没有"好
- 本调研未覆盖"实时监控/告警"——我们是离线批处理，不需要实时告警
