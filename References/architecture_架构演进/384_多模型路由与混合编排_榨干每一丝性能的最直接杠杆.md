# 384 多模型路由与混合编排：榨干每一丝性能的最直接杠杆

> 日期：2026-09-13。监工完成。这是 374-383 之后的架构升级轮，聚焦**多模型路由**——直接关系到"榨干每一丝性能"和 token 成本。
> 核心命题：**50-70% 的任务不需要最强模型。我们当前所有任务都用同一个模型，是巨大的浪费。级联路由（先便宜→验证→不通过再升级）因为有确定性验证器，比预测路由更可靠。**
> 流程：搜集 → 整理 → 挖掘 → 联系 → 批判 → 结合 → 应用。

## 一、搜集（搜了什么）

两路并行检索：
1. FrugalGPT/RouteLLM/级联路由/成本优化
2. 难度感知 Agent 编排/任务复杂度分类/多模型混合

核心来源（12 份）：
- **FrugalGPT**（Stanford）：级联路由，先便宜模型→评分→不通过升级，50-98% 成本降低，匹配 GPT-4 质量
- **RouteNLP**（arXiv 2604.23577）：闭环路由+共形级联+蒸馏协同，40-85% 成本降低，96-100% 质量，比 RouteLLM 更优
- **Cascade vs Router**：级联能看到便宜模型的实际回答再决定，预测路由只看输入——级联结构性更优
- **AutoMix**：回答后再决定是否升级
- **Brick**：空间能力路由，Mixture-of-Models，中性 profile 74% 准确率但成本低 4.71×
- **NVIDIA NeMo Switchyard**：免调优路由器，LangChain 基准 74% 成本降低
- **DAAO**（arXiv 2509.11079）：VAE 难度估计+模块化操作分配+成本性能感知路由器
- **oh-my-claudecode 三层路由**：LOW（Haiku）→ MEDIUM（Sonnet，分数4-7）→ HIGH（Opus，≥8），按任务类型分
- **Microsoft Foundry Model Router**：简单交互（50-60% 流量）路由到便宜模型
- **Agent-as-a-Router**（arXiv 2606.22902）：Agent 自己做路由，编码任务中等层级 $10-13 vs Always-Opus $34
- **50-70% 企业请求可用最便宜层无质量损失**（Zylos AI）
- **10-100× 定价差**：前沿 $5-25/MTok vs 效率 $0.10-1/MTok

## 二、整理（分类）

### 路由策略

| 策略 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| 预测路由 | 看输入就决定模型 | 不浪费便宜模型调用 | 预测不准时浪费或降级 |
| 级联路由 | 先便宜→验证→不通过升级 | 能看到实际回答再决定 | 简单任务多一次验证开销 |
| 语义路由 | 按任务类型/领域路由 | 可解释、易调优 | 需要人工定义分类 |
| Agent 自路由 | Agent 自己决定用哪个模型 | 灵活 | 不可控、可能偷懒 |

### 难度分层（oh-my-claudecode 实践）

| 层级 | 模型 | 典型任务 | 响应深度 |
|---|---|---|---|
| LOW | 最便宜 | 查询、grep、单文件编辑、格式检查 | 简明直接 |
| MEDIUM | 均衡 | 多步骤编辑、模块变更、标准分析 | 详尽结构化 |
| HIGH | 最强 | 架构决策、根因分析、安全审查 | 全面细致 |

## 三、挖掘（核心洞察）

**1. 级联路由比预测路由更适合我们，因为我们有确定性验证器**：
- FrugalGPT 的级联用 LLM 评分函数判断"便宜模型的回答够不够好"——评分本身可能不准
- 我们的验证器是确定性的（gate block=0？replay confirm？poison 全过？）——不需要 LLM 评分
- **流程：便宜模型生产 → 门禁自动验证 → 不通过 → 升级到强模型重做**
- 这比 FrugalGPT 更可靠，因为验证器是"不智能但正确"的（AxiomGuard 哲学）

**2. 我们的任务天然有三层难度，当前全部用同一模型是浪费**：
- **LOW（约 40-50%）**：门禁全跑、git status、文件移动、格式检查、提交信息撰写、索引更新
- **MEDIUM（约 30-40%）**：写证据卡、跑夹具、改已知 bug、按模板生成文件、红队执行（有检查清单）
- **HIGH（约 15-20%）**：架构决策、claim 设计、方向反转判断、红队发现新攻击手法、人审裁决
- 当前全部用 ds v4.1 flash——LOW 任务完全可以用更便宜/更快的模型

**3. 难度不只是"任务类型"，还和"原子属性"相关**：
- DAL A/B 原子（高风险）→ HIGH
- DAL C/D/E 原子（低风险）→ MEDIUM
- pitfall 类型（有明确反例）→ MEDIUM
- mechanism 类型（需要量化数据）→ HIGH
- 新域首颗（无先例）→ HIGH
- 同域第 N 颗（有模板）→ MEDIUM
- DAAO 的"难度感知"证明：动态调整比固定分层更优

**4. 级联的"升级"不是重做，是"定向修复"**：
- 便宜模型生产后，门禁报具体哪条规则 block
- 强模型不需要从头做，只需要修 block 的那几处
- 这比"便宜模型全丢→强模型重做"更高效
- **映射到我们：红队发现阻断后，不是让强模型重写整张卡，是让强模型只修阻断项**

**5. 成本差是 10-100×，路由的 ROI 极高**：
- 假设 60% LOW + 30% MEDIUM + 10% HIGH
- 全部用 HIGH：100 × 1.0 = 100 单位成本
- 路由后：60 × 0.05 + 30 × 0.2 + 10 × 1.0 = 3 + 6 + 10 = 19 单位
- **成本降低 81%**，且 HIGH 任务质量不变
- 这还没算"级联升级"的额外开销（LOW 失败后升级到 MEDIUM，约 10-15% 的 LOW 会升级）

## 四、联系（和我们系统的映射）

| 外部发现 | 我们的现状 | 差距 |
|---|---|---|
| 级联路由 | 所有任务同一模型 | 无路由 |
| 三层难度分层 | 隐式有（监工/苦力/红队）但未按模型分 | 缺显式分层 |
| 确定性验证器 | gate/replay/poison 已有 | ✅ 已有，是级联的基础 |
| 难度感知（DAAO） | 按批次固定模型 | 缺动态调整 |
| 定向修复而非重做 | 红队后修阻断项 | ✅ 已在做 |
| Agent 自路由 | 监工决定谁干什么 | 部分（人决定，非自动） |

## 五、批判（哪些不适用/有局限）

1. **我们不是在开发 API 路由层，是在使用多个 Agent 工具**：FrugalGPT/RouteLLM 是 API 层面的自动路由，我们的场景是"用户/监工决定哪个任务交给哪个 Agent（CodeBuddy/Trae/hy4p）"。**路由是人工的（提示词里写"这个任务用 X 模型"），不是自动的。** 但这不影响分层思路——我们可以在提示词里明确"本任务属于 LOW/MEDIUM/HIGH，建议用 X 模型"。

2. **模型可用性受限于用户的订阅/额度**：用户当前可用 ds v4.1 flash（CodeBuddy/Trae）、hy4p（腾讯）、Qwen3.8 flash。没有 GPT-4o/Claude Opus 这种"最强层"。**三层路由在我们的场景下是"ds flash vs hy4p vs Qwen flash"的选择，不是"Haiku vs Sonnet vs Opus"。** 需要先做一轮各模型在我们任务上的基准测试，才能确定哪个模型适合哪层。

3. **级联升级的开销在我们的场景下是"换窗口"**：API 路由的升级是同一会话内的第二次调用，我们的升级是"开新 Agent 窗口"——有上下文传递成本。**所以 LOW 任务的失败率必须足够低（<15%），否则升级开销抵消路由收益。**

4. **红队任务不适合级联**：红队需要"独立盲读"，如果先用便宜模型红队→不通过→强模型再红队，强模型会被便宜模型的发现污染（失去独立性）。**红队必须一次到位用足够强的模型，不能级联。**

5. **架构决策任务不适合级联**：架构决策的"验证器"是人审，不是确定性门禁。便宜模型做架构决策→人审不通过→强模型重做，人审的成本比模型成本高。**架构决策直接用最强模型。**

## 六、结合（和已有架构的结合点）

**和 381 评估体系**：模型路由的 KPI（各层任务占比、升级率、成本降低比）加入 KPI 趋势线。

**和 382 对抗**：红队必须用最强模型（不能级联），但红队报告的"毒样例候选生成"可以用便宜模型（有模板）。

**和 383 上下文工程**：LOW 任务的上下文可以更精简（只给必要信息），HIGH 任务的上下文可以更充分。路由和上下文管理是联动的——便宜模型+精简上下文 vs 强模型+充分上下文。

**和 376 鲁棒性**：模型路由本身是一种降级策略——最强模型不可用时自动降级到中等模型（376 的优雅降级五级）。

**和 gate 验证器**：gate 是级联路由的"评分函数"——gate block=0 就是"便宜模型的回答够好"。这是我们比 FrugalGPT 更强的地方（确定性评分 vs LLM 评分）。

## 七、最终应用（分阶段落地）

### 立即落地（零成本，提示词/流程改进）

**应用 1：任务难度标签**
- 每个给 Agent 的提示词开头加"难度：LOW/MEDIUM/HIGH"
- LOW：门禁、git、格式、索引、提交信息
- MEDIUM：写卡、跑夹具、改已知 bug、按模板生成
- HIGH：架构、claim 设计、方向反转、红队新攻击、人审裁决
- 用户根据标签选择用哪个 Agent/模型

**应用 2：级联修复流程（已有验证器的天然优势）**
- MEDIUM 模型生产 → 门禁验证 → block 项列出 → HIGH 模型只修 block 项
- 不是"HIGH 从头重做"，是"HIGH 定向修复"
- 这在红队后修复已经在做，推广到所有生产任务

**应用 3：红队和架构决策直接用最强模型**
- 明确写在提示词里："本任务为 HIGH，不适用级联，必须一次到位"
- 避免为了省 token 用弱模型做红队（结果漏报更多，得不偿失）

### 中期落地（需基准测试）

**应用 4：各模型在我们任务上的基准测试**
- 选 5 个典型任务（LOW/MEDIUM/HIGH 各若干），分别用 ds flash、hy4p、Qwen flash 跑
- 记录：成功率、token 用量、时间、门禁结果
- 输出"模型-任务匹配表"：哪个模型适合哪层
- 这是路由的前提——没有基准数据，分层是拍脑袋

**应用 5：动态难度调整**
- 同一类任务（如"写证据卡"），根据原子属性动态调整：
  - DAL A/B + 新域首颗 → HIGH
  - DAL C + 同域第 N 颗 → MEDIUM
  - 简单判据卡（有模板）→ LOW-MEDIUM
- 这是 DAAO"难度感知"的人工版

### 长期落地

**应用 6：自动路由（平台化阶段）**
- 378 平台化时，在脚手架里内置路由器
- 任务提交时自动判断难度→选择模型→执行→门禁验证→不通过自动升级
- 这是 FrugalGPT 的完整实现，但需要平台化基础设施

## 十、局限与后续

- 本调研聚焦模型路由，未覆盖"同一模型的不同参数配置"（temperature/top_p 对不同任务的优化）——那是提示词工程的事。
- 模型基准测试（应用 4）是路由的前提，没有数据就没有可信的分层。建议下一批先做 5 个任务的基准测试。
- 级联升级的"换窗口"开销在我们的场景下不可忽略——LOW 任务失败率必须<15% 才划算。需要先统计当前 LOW 任务的失败率。
- 红队和架构决策不能级联（独立性/人审成本），这两类任务直接用最强模型——这限制了路由的适用范围（约 80% 任务可路由，20% 必须 HIGH）。
- 自动路由（应用 6）依赖平台化（378），当前阶段只能做"人工标签+用户选择模型"。
- 本调研未覆盖"模型集成"（多个模型投票/辩论）——382 的辩论式红队是一种集成，但通用任务的模型集成（如 Self-Consistency）未覆盖，未来可做一轮。
