# 442 深度内卷：65 份调研的全量消化、批判与终极整合

> 日期：2026-09-13。停止外部调研，向内卷。对 374-441 共 68 份文档（374-441，含 396/397 元调研）做全量消化、批判、整合。目标：找出内部矛盾、遗漏、重复，形成"改无可改"的最终架构形态。

## 一、元模式提炼：65 份调研在说同一件事

把 16 个方向的调研摊开，核心元模式只有 **7 条**：

### 元模式 1：不变量约束优于存在性检查（最核心）

- 426 时序约束框架：编译后无覆写（时序不变量）、sha==重生成（代际不变量）、符号在工件非注释（空间不变量）
- 436 形式化验证：invariant 是契约编程的核心
- 438 差分测试："两个平台输出一致"是不变量
- 440 混沌工程："稳态不被破坏"是不变量
- 402 对抗的元结论："修复按字符串/单点生效，攻击按数据流/时序穿链"——因为修复做的是存在性检查（"有没有这个字段"），攻击破坏的是不变量（"编译后工件没变"）

**架构原则**：所有 gate 规则最终应该表达为不变量，不是存在性检查。存在性检查可以被"每点都合规"的组合绕过，不变量不能。

### 元模式 2：零 LLM 确定性检查是成本优势

- 416 全量消化：门禁零 token，这是阙疑的成本优势
- 413 错误分类：E1/E2/E5/E6 可机械修，不需要 LLM
- 420 Writer 自检层：7 项确定性检查，零 token
- 412 成本经济学：CPVA 指标，门禁是零成本的

**架构原则**：能机器查的绝不交给 LLM。LLM 只做"需要判断"的事（claim 方向、红队替代解释），其余全部机械化。

### 元模式 3：对抗驱动进化，且问题级别在上升

- 第三批红队抓"断言自证"（形式问题）
- 第五批红队抓"口径不统一导致方向反转"（语义问题）
- 402 对抗抓"cl 免检链"（架构级漏洞）
- 浅层问题被门禁固化成规则拦住后，红队被迫往更深的地方挖

**架构原则**：对抗不是"一次性审计"，是"持续进化的驱动力"。每次对抗发现的问题必须转化为规则/毒样例/工具改进，否则白打。

### 元模式 4：校准是自治的前提

- 440 元认知：校准=信心与实际表现的匹配
- 441 校准训练：Writer 自评 vs 红队评分
- 404 健康度评估：五维模型就是系统的"自我监控"
- 397 批判的批判：对自己的架构设计做自我批判

**架构原则**：系统要自治，先得能准确评估自己。自评不可信的系统，做的决策也不可信。

### 元模式 5：因果推断是所有"实测"的理论基础

- 436 因果推断：单变量对照=处理效应估计（ATE）
- 434 变形测试：变形关系=因果关系的另一种表达
- 434 属性测试：性质=不变量，与活性对照同源
- PERF-004 的 18.86×→8.78× 波动：因为没有遵循因果推断的原则（没有随机化、没有报告 ATE+CI）

**架构原则**：所有性能/机制卡的夹具设计必须遵循因果推断。不遵循的，数据不可信。

### 元模式 6：知识是网络，不是层级

- 440 知识管理：Zettelkasten 的原子性+连接性+有机生长
- 415 知识图谱推理：relations 从装饰变基础设施
- 434 知识图谱质量：四维评估（一致性/完整性/时效性/正确性）
- 阙疑的 16 域不是预先设计的，是从 ch 章节自然生长的

**架构原则**：原子库的价值不在"有多少颗"，在"连接有多密"。孤岛原子没有教学价值。

### 元模式 7：成本是隐形约束，且与质量不矛盾

- 412 成本经济学：CPVA 指标，五杠杆优化
- 407 提示词压缩：五层压缩，前缀缓存
- 432 多模型协作：苦力 60-70%/好模型 20-30%/对抗 5-10%
- 红队是成本热点但不能砍——因为红队发现的问题，修复后变成零成本的规则

**架构原则**：成本优化不是"砍质量"，是"把 LLM 用在刀刃上"。机械化的部分零成本，LLM 只做判断。

## 二、批判：已有架构设计中的 6 个内部矛盾

### 矛盾 1：v6-v9 的分层与 L1-L7 不对齐

- v6.0（399）定义了 L1-L7 七层架构（数据层→自治层）
- v7.0（427）定义为"工具层基座"
- v8.0（431）定义为"语义层纵深"
- v9.0（431）定义为"自治层"

**问题**：v7/v8/v9 是"时间维度"的版本，L1-L7 是"空间维度"的分层。两者的对应关系没有定义清楚。v7.0 对应 L1-L3？v8.0 对应 L4-L5？v9.0 对应 L6-L7？

**修法**：明确定义版本与分层的对应关系：
- v7.0 = L1（数据）+ L2（工具）+ L3（门禁）的基座
- v8.0 = L4（语义）+ L5（推理）的纵深
- v9.0 = L6（进化）+ L7（自治）的闭环

### 矛盾 2：P0/P1 清单有依赖关系没排序

7 项 P0/P1：
1. 性能卡 v2.0（P0）
2. warn 分类（P1）
3. 差分测试（P1）
4. 夹具方法论（P1）
5. claim 契约化（P1）
6. 混沌对抗（P1）
7. 决策质量（P1）

**问题**：
- 性能卡 v2.0 依赖夹具方法论（夹具设计要先有因果设计框架）
- 差分测试依赖性能卡 v2.0（要先有"方向量"的定义，才能做跨平台比较）
- 混沌对抗依赖 warn 分类（稳态快照需要知道哪些 warn 是真问题）
- 决策质量依赖 claim 契约化（六要素检查需要 claim 有 pre/post/invariant）

**修法**：按依赖排序，分三批：
- 第一批（无依赖）：夹具方法论 v2.0、claim 契约化 v2.0
- 第二批（依赖第一批）：性能卡 v2.0、warn 分类
- 第三批（依赖第二批）：差分测试、混沌对抗、决策质量

### 矛盾 3：工具层 7 个提示词与新 P1 不匹配

427 设计的 v7.0 工具层 7 个提示词：
- 414（对抗修复）、420（Writer 自检）、421（成本追踪）、423（闪卡导出）、424（毒样例分类）、417（relations 矛盾）、425（上游依赖）

但 435-441 新增了 7 项 P1，其中需要新工具的：
- 性能卡 v2.0 → 需要新的性能夹具模板 + gate 规则 EV-PERF-RIGOR
- warn 分类 → 需要 debt_ledger.py 扩展
- 差分测试 → 需要新的 gate 规则 EV-CROSS-PLATFORM-CONSISTENCY
- 混沌对抗 → 需要对抗报告模板 + 稳态快照工具
- 决策质量 → 需要 human_review 字段扩展 + gate 规则

**问题**：工具层提示词过时了，没有覆盖新 P1。

**修法**：更新 v7.0 工具层清单，新增 5 个提示词（性能卡规范、债务治理、差分测试、混沌对抗、决策质量），总共 12 个工具任务。

### 矛盾 4：多模型协作没有考虑"模型校准"

432 设计了苦力/好模型/对抗模型的分工，但假设"模型的自评是可信的"。

**问题**：不同模型的校准能力不同。Seed-Code 可能自评偏低，Seed-Evolving 可能自评偏高。如果不做模型级校准，"Writer 自评 4/5"这个数据就不可比。

**修法**：每个模型有一个"校准系数"，根据历史表现调整。例如：
- 苦力模型（Seed-Code）：自评普遍偏低，校准系数 ×1.2
- 好模型（ds v4.1 flash）：自评较准，校准系数 ×1.0
- 对抗模型（Seed-Evolving）：自评偏高，校准系数 ×0.8

这是元认知的"模型级校准"。

### 矛盾 5：教学转化与生产流程的优先级冲突

- 生产流程：原子→证据卡→误解→红队→门禁→人审
- 教学转化：闪卡→MCQ→学习路径→错误示例

**问题**：教学转化是"额外的工作"，会拖慢生产。但教学转化是阙疑的最终目的（做 CPP 学习库）。

**修法**：教学转化应该是"生产的副产品"，不是额外工作：
- 闪卡：从原子卡自动生成（423 已经在做）
- MCQ：从误解库自动生成（每个误解=一道 MCQ 的错误选项）
- 学习路径：从 relations 自动生成（DAG 遍历）
- 错误示例：从毒样例自动生成（每个毒样例=一个错误示例）

**核心洞察**：教学转化不应该是"生产完再做"，而是"生产过程中自动产生"。

### 矛盾 6：缺少"失败恢复"机制

所有架构设计都在说"怎么防止失败"，但没有说"失败了怎么恢复"。

**问题**：
- 如果门禁全红了（gate block>0、replay refute>0），怎么回滚？
- 如果一次提交引入了坏规则，怎么快速定位和回退？
- 如果工件被意外删除，怎么恢复？

**修法**：
- 门禁全红时，自动回滚到上一个 golden 基线（golden_lock 有基线）
- 每次提交自动记录"门禁快照"，可以 diff 两次提交的门禁变化
- 工件有 sha256，可以从 .out 重生成（如果 command 还在）

## 三、遗漏：65 份调研没有覆盖的 5 个环节

### 遗漏 1：门禁本身的性能

跑一次全部门禁要多久？
- gate_engine.py --check：<1s
- poison_drill：<5s
- atom_evidence_replay --check：5-10 分钟（要编译 56 个夹具）
- pytest：<10s
- WSL 预检：31 步，<5 分钟

**问题**：replay 是瓶颈（5-10 分钟）。随着原子数增加，会越来越慢。56 张卡 5 分钟，560 张卡就是 50 分钟。

**修法**：
- 增量 replay：只重跑改动过的卡（414 的 F01 修复后，cl 卡跳过，已经是增量的雏形）
- 并行 replay：多进程并行编译（但 Windows/WSL 不能并行写 .asm）
- ccache：编译缓存（线 C 卡在授权，待安装）

### 遗漏 2：schema 演化的迁移机制

frontmatter schema 已经变了多次（G6 四级状态、DAL、status_history、pedagogy 结构化）。

**问题**：旧卡怎么迁移？当前是"新卡用新 schema，旧卡保持旧 schema"，但 gate 规则对新旧卡的检查不一致。

**修法**：
- schema 版本号：每张卡有 schema_version 字段
- 迁移脚本：自动把旧 schema 迁移到新 schema（如补 status_history、补 dal）
- 迁移测试：迁移后门禁结果不变

### 遗漏 3：多人协作的冲突避免

当前只有一个人（用户）在生产，但未来可能多人协作。

**问题**：
- 两个人同时改同一个原子卡，怎么合并？
- 两个人同时生产同域的原子，ID 冲突怎么办？
- 一个人的红队发现另一个人的卡有问题，怎么处理？

**修法**：
- ID 分配机制：生产前先注册 ID（如 ATOM-MEM-PERF-005），避免冲突
- 分支策略：每人一个分支，合并前跑门禁
- CODEOWNERS：每域有负责人，合并需要负责人审批（第二批任务，已登记）

### 遗漏 4：安全——恶意提交的防护

如果有人恶意提交有毒的卡/夹具：
- 卡的 command 里写 `rm -rf /` 怎么办？
- 夹具里写恶意代码怎么办？
- 工件是借品怎么办？（402 的 F02 已经发现了这个漏洞）

**修法**：
- command 白名单：只允许 g++/clang++/python 等安全命令
- 夹具编译沙箱：编译和运行在沙箱中，不能访问网络和敏感文件
- 工件溯源：426 时序约束框架已经在做（编译后无覆写）

### 遗漏 5：可观测性——系统运行时的仪表盘

当前有 gen_metrics.py，但只是"数字自洽"，没有可视化。

**问题**：
- 每次提交的门禁结果变化趋势？
- 红队发现的问题级别分布？
- 修复时间（MTTR）？
- 原子数/证据卡数/毒样例数的增长曲线？

**修法**：
- 健康度仪表盘（410 已经设计了 v0.1，待落地）
- 每次提交自动记录门禁快照，生成趋势图
- 红队报告自动提取"阻断/高级/建议"分布

## 四、终极整合："改无可改"的架构形态

把 65 份调研、7 条元模式、6 个矛盾、5 个遗漏整合，最终架构是：

### 核心原则（3 条，不可动摇）

1. **不变量约束优于存在性检查**——所有规则最终表达为不变量
2. **零 LLM 确定性检查是成本优势**——能机器查的绝不交给 LLM
3. **校准是自治的前提**——系统要先能准确评估自己

### 三层架构（时间维度）

| 版本 | 对应分层 | 核心目标 | 验收标准 |
|---|---|---|---|
| v7.0 | L1-L3（数据+工具+门禁） | 机器能拦住形式错误 | 规则≥50，毒样例≥60，拦截率≥60% |
| v8.0 | L4-L5（语义+推理） | 机器能理解语义 | claim 契约化 100%，活性对照自动化，relations 推理引擎 |
| v9.0 | L6-L7（进化+自治） | 系统能自己发现问题、自己修复、自己验证 | 自动毒样例生成，持续对抗，校准分数≥0.8 |

### 12 个工具任务（v7.0 全量）

按依赖排序：
1. 夹具方法论 v2.0（无依赖）
2. claim 契约化 v2.0（无依赖）
3. 性能卡 v2.0（依赖 1）
4. warn 分类+债务台账（无依赖）
5. Writer 自检层（无依赖，420 已就绪）
6. 成本追踪（无依赖，421 已就绪）
7. 差分测试自动化（依赖 3）
8. 混沌对抗形式化（依赖 4）
9. 决策质量检查（依赖 2）
10. relations 矛盾检测（已完成，417）
11. 上游依赖遍历（依赖 10，425 已就绪）
12. 闪卡导出（无依赖，423 已就绪）

### 5 个遗漏修复（v7.5）

1. 门禁性能优化（增量 replay + ccache）
2. schema 演化迁移机制
3. 多人协作冲突避免
4. 安全沙箱（command 白名单 + 编译沙箱）
5. 可观测性仪表盘

### 持续进化循环（v9.0 的核心）

```
监控（健康度评估）→ 校准（自评 vs 实际）→ 决策（改进计划）→ 执行（工具修复）→ 验证（门禁+对抗）→ 监控（...）
```

这就是元认知的"监控-控制循环"，也是 v9.0 自治的核心。

## 五、结论：现在能送去对抗了吗？

**架构设计层面：能。**

理由：
- 65 份调研覆盖 16 个方向，没有明显盲区
- 7 条元模式提炼完成，核心原则明确
- 6 个内部矛盾已识别并有修法
- 5 个遗漏已识别并有修复计划
- v7-v9 路线清晰，12 个工具任务排序完成
- 持续进化循环定义完成

**但建议先落地第一批 P0/P1（4 项），再送对抗：**
1. 夹具方法论 v2.0
2. claim 契约化 v2.0
3. 性能卡 v2.0
4. warn 分类+债务台账

这 4 项是"最明显的攻击点"，落地后对抗模型才能往更深的地方挖。
