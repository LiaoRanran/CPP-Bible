# 395 Fuzzing自动化、任务分解规划、性能剖析：三个垂直领域的深度提升

> 日期：2026-09-13。聚焦三个垂直方向：**Fuzzing/突变测试**（毒样例自动化）、**任务分解规划**（批次生产自动化）、**性能剖析**（PERF 类证据升级）。
> 核心命题：**这三个方向都是"把人工做的事自动化/深化"——毒样例从手工写到自动生成，任务分解从监工手动到 Planner 自动，性能证据从时钟计时到缓存/分支/内存带宽剖析。**

## 一、Fuzzing 与突变测试：毒样例的自动化

### 核心发现

**libFuzzer**：LLVM 的进程内、覆盖率引导的进化式 fuzzing——插桩代码追踪路径，变异输入以最大化覆盖率，和 ASan/UBSan 紧密集成。

**Mut4All**（arXiv 2507.19275）：用 LLM 从 bug 报告中学习变异算子——多 Agent 框架（变异发明 Agent 识别目标+生成算子，从编译器 bug 报告提取知识）。

**关键机制**：覆盖率引导的反馈循环——种子输入→变异（翻转位/插入字节/拼接）→触发新路径则保存→继续变异。

### 和我们的映射

| 概念 | 我们的现状 | 升级方向 |
|---|---|---|
| 毒样例 | 手工写 30 个，覆盖 10/37 规则 | 自动生成变异测试用例 |
| 变异算子 | 无（手工设计每个毒样例） | 从红队逃逸中学习攻击模式 |
| 覆盖率 | 无（不知道规则覆盖了多少代码路径） | 规则覆盖率引导 |
| 反馈循环 | 无（毒样例写了就放着） | 新逃逸→新毒样例→新规则 |

### 挖掘

**1. 毒样例的自动化生成是 385 数据飞轮的"Distill"阶段**：
- 当前：红队发现逃逸→人写毒样例→加规则
- 自动化：红队发现逃逸→自动聚类攻击模式→自动生成变异毒样例→加规则
- **Mut4All 的思路（从 bug 报告学习变异算子）可以直接映射——从我们的 14 个逃逸+13 个绕过中学习"攻击模式"，自动生成新毒样例**

**2. 覆盖率引导可以发现"规则盲区"**：
- 当前 RULE-COVERAGE 只统计"多少规则有毒样例"（10/37）
- 覆盖率引导可以统计"毒样例触发了规则代码的多少分支"
- **有些规则可能有"毒样例通过但没触发关键分支"的假覆盖——覆盖率引导可以发现**

**3. 但 Fuzzing 需要 Clang，我们的环境是 GCC**：
- libFuzzer 是 LLVM 工具链的一部分，需要 Clang
- Windows 无 Clang，WSL 可能有
- **和 392 的工具链边界一致——Fuzzing 是"锦上添花"，不是"雪中送炭"**

## 二、任务分解与规划：批次生产的自动化

### 核心发现

**WORKFORCE**（arXiv 2505.23885）：分层多 Agent——领域无关 Planner（生成抽象任务分解）+ Coordinator（分配子任务）+ 领域特定 Worker。

**HALO**（arXiv 2505.13516）：三层推理——高层规划 Agent（任务分解）+ 中层角色设计 Agent（子任务特定 Agent 实例化）+ 低层推理 Agent（执行），子任务执行重构为 MCTS 工作流搜索。

**四种编排模式**（从轻到重）：ReAct → Plan-and-Execute → Supervisor → Hierarchical Multi-Agent。

**Agent-as-Tool**（arXiv 2604.17009）：把 Agent 和工具都抽象为标准化动作空间，轻量编排器做并行子任务分解。

### 和我们的映射

| 概念 | 我们的现状 | 升级方向 |
|---|---|---|
| 任务分解 | 监工手动（"先做 PERF-004，再做 LEAK-002"） | Planner Agent 自动分解 |
| 依赖管理 | 手动（红队必须在卡层之后） | DAG 自动管理依赖 |
| 并行执行 | 无（串行生产） | 独立子任务并行（如三颗原子的夹具可以并行写） |
| 工作流搜索 | 无（固定流程） | MCTS 探索最优生产顺序 |
| 编排模式 | Supervisor（监工+Writer+红队） | 已在最优模式 |

### 挖掘

**1. 我们的编排已经是最优模式（Supervisor），但任务分解是手动的**：
- 381 确认：Orchestrator-Worker+Supervisor 占 70% 生产部署
- 我们的监工=Orchestrator+Supervisor，Writer=Worker，红队=独立 Worker
- **缺的是 Planner——监工手动分解"生产一批原子"为子任务，应该自动化**

**2. DAG 依赖管理可以防止"顺序错误"**：
- 当前：红队必须在卡层之后，门禁必须在红队之后——靠提示词和纪律保证
- DAG：自动检测依赖（红队 depends_on 卡层，门禁 depends_on 红队），违反则阻断
- **这是"自律性"的又一层——从"靠纪律"到"靠 DAG 强制"**

**3. 并行执行可以提升吞吐**：
- 当前：三颗原子串行生产（PERF-004→LEAK-002→ALLOC-002）
- 可以并行：三颗原子的夹具可以同时写（无依赖），卡层也可以并行（独立）
- **但并行需要上下文隔离——当前单会话做不到，需要多 Agent 并行（381 已确认是最优拓扑）**

## 三、性能剖析：PERF 类原子的证据升级

### 核心发现

**工具全景**：
- **perf**：Linux 采样剖析，调用图，低开销
- **Callgrind**：精确调用计数+周期归因，~50x 减速
- **Cachegrind**：缓存剖析，模拟 CPU 缓存层次（L1/L2/L3 未命中）
- **VTune**：完整 PMU+内存流量，~5% 开销，缓存未命中/分支预测错误/内存带宽
- **Tracy**：实时逐帧延迟监控
- **PGO**（Profile-Guided Optimization）：用运行时采样驱动编译器优化

**关键洞察**：访问主存比 L1 缓存慢 100 倍——缓存未命中是性能问题的主要来源。

### 和我们的映射

| PERF 类原子 | 当前证据 | 升级方向 |
|---|---|---|
| PERF-003（小对象分配） | 时钟计时（std::chrono） | Cachegrind 看分配器的缓存未命中 |
| PERF-004（false sharing） | 时钟计时（18.86×） | Cachegrind 直接看缓存行竞争的未命中数 |
| CONC-LOCK-001（锁代价） | 时钟计时+方向量 | perf 看锁竞争的等待时间 |

### 挖掘

**1. 时钟计时是"结果级"证据，性能剖析是"机制级"证据**：
- 当前：PERF-004 说"相邻布局慢 18.86×"——但不知道为什么慢
- 升级：Cachegrind 可以显示"相邻布局的 L1 缓存未命中数是隔离布局的 N 倍"——直接证明 false sharing 的机制
- **机制级证据比结果级证据更有说服力，也更难被"跨运行波动"推翻**

**2. 但性能剖析工具有环境边界**：
- perf/VTune：Linux only，Windows 无
- Cachegrind：Valgrind，WSL 可跑，但 ~50x 减速
- **和 392 一致——性能剖析是"可选增强"，不是"必须"**

**3. PGO 的思路和我们的"实测驱动"同构**：
- PGO：用运行时采样驱动编译器优化（内联热调用点、冷热分离）
- 我们：用实测数据驱动 claim（不锚绝对纳秒，锚方向和因果链）
- **都是"数据驱动"而非"先验推理"——这是我们系统的核心哲学**

## 四、应用

### 立即落地（零成本）
**应用 1**：从 14 个逃逸+13 个绕过中提取"攻击模式分类"，为自动毒样例生成做准备
**应用 2**：批次生产流程显式 DAG 化（写在提示词里：步骤+依赖）

### 中期落地
**应用 3**：PERF-004 用 Cachegrind 验证（WSL），补充缓存未命中数作为机制级证据
**应用 4**：Planner 提示词——输入"生产 N 颗原子"，输出 DAG（子任务+依赖+并行度）

## 五、局限
- Fuzzing 需要 Clang，当前环境无
- 性能剖析需要 Linux（perf/Cachegrind），Windows 无
- 任务分解自动化需要多 Agent 并行，当前单会话做不到
- 这三个方向都是"增强"而非"必需"——当前系统没有它们也能工作
- 本调研未覆盖"property-based testing"（基于属性的测试）——这是另一个有价值的方向
