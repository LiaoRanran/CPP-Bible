# 488 安全性与信任模型详细方案
## 身份信任 + 签名验证 + 供应链安全 + 对抗防御体系

> 生成时间：2026-09-14
> 前置实测：18 个 audit 工具全是内容审计，零身份信任工具；E12 签收自证（human:liaoranran 谁都能写）0 block 0 warn；对抗 5 轮发现 30+ 逃逸
> 核心问题：系统有"内容安全"（51 规则检查内容），但没有"身份安全"（谁写的、能不能信）

---

## 一、问题：内容安全 ≠ 身份安全

### 现状

- **内容安全**：51 条规则检查原子/证据卡的内容质量（断言、口径、格式...）
- **身份安全**：零。任何人/Agent 都可以写 `verified_by: human:liaoranran`，系统不验证

### 对抗暴露的身份问题

| 轮次 | 逃逸 | 根因 |
|---|---|---|
| 368 | 签收字符串自证 | `human:liaoranran` 谁都能写，无 git 身份绑定 |
| 373 | 声明-实现脱钩 | artifact_producer 声明漂亮，command 实际 cp 借品 |
| 402 | 编译后覆写 | 真编译行满足 producer，随后 python 覆写工件 |
| 452 | helper 脚本覆写 | 无参脚本内部硬编码目标路径，时序检查漏 |
| 470 | 僵尸锁 DoS | 锁只按 mtime 判陈旧，无 pid 存活检测 |

**共同根因**：系统验证"内容对不对"，但不验证"内容是谁写的、有没有被篡改、来源可不可信"。

## 二、信任模型设计

### 2.1 信任层级

```
Level 0: 不可信（默认）
  └─ 任何未签名的内容

Level 1: 机器可信
  └─ 工具生成的内容（replay 结果、门禁结果）
  └─ 验证：工具版本 + 输入哈希 + 输出哈希

Level 2: Agent 可信
  └─ Agent 生成的内容（Writer 写的卡、红队报告）
  └─ 验证：Agent ID + 模型版本 + 提示词版本 + 输入输出哈希

Level 3: 人可信
  └─ 人审签署的内容（verified 原子）
  └─ 验证：git author 匹配 + GPG 签名 + 签署时间
```

### 2.2 身份绑定

#### Git Author 绑定（E12 修复）

当前：`verified_by: human:liaoranran` 只是字符串，谁都能写。

改法：
```yaml
verified_by: human:liaoranran
verified_at: 2026-09-11
verified_commit: abc1234        # 新增：签署时的 git commit
verified_git_author: liaoranran <xxx@xxx.com>  # 新增：git author
```

验证规则：
- `verified_git_author` 必须等于该 commit 的 git author
- `verified_commit` 必须存在于 git 历史中
- 原子文件的最后修改 commit 必须等于或早于 `verified_commit`（签署后没被改过）

#### GPG 签名（远期，可选）

- 人审签署时用 GPG 签名
- `verified_signature: <gpg signature>`
- 验证：公钥在仓库 `docs/kernel/trusted_keys/` 中

### 2.3 工具链信任

每个工具的输出附带"生产证明"：
```json
{
  "producer": "atom_evidence_replay.py",
  "producer_version": "v7.0",
  "producer_sha256": "<工具文件的sha256>",
  "input_hash": "<输入文件的sha256>",
  "output_hash": "<输出的sha256>",
  "timestamp": "2026-09-14T10:30:00Z"
}
```

验证：工具文件的 sha256 必须匹配（防止工具被篡改）。

## 三、供应链安全

### 3.1 问题

- 夹具（.cpp）是 Agent 写的，可能包含恶意代码（虽然只是编译运行，但有风险）
- 工件（.asm/.out）可能被篡改（402/452 的覆写攻击）
- 工具脚本（.py）可能被篡改
- 外部依赖（pip 包、编译器）可能有供应链风险

### 3.2 工件完整性

当前：artifact_sha256 锚定工件哈希。

增强：
- **工件来源证明**：工件必须由卡内 command 生成，不能手动放一个 .asm
- **重编译不变量**（470 已做）：replay 时独立重编译，对比 sha，不一致 → refute:artifact_tampered
- **工件签名**：人审时对工件哈希签名，后续篡改可检测

### 3.3 夹具沙箱

夹具编译运行时的安全：
- 编译在临时目录，不访问网络
- 运行有超时限制（600s）
- 不允许夹具修改 atoms/evidence/tools/ 下的文件
- 夹具输出只在 stdout/stderr，不写文件

### 3.4 工具脚本完整性

- 核心工具（gate_engine/replay/poison）的 sha256 记录在 `tools/checksums.txt`
- CI 中验证工具脚本 sha256 未被篡改
- 工具改动需要人审（核心工具的 PR 必须人 review）

### 3.5 依赖锁定

- `requirements.txt` 固定版本（已有）
- 编译器版本固定（卡内 artifact_compiler 字段）
- pip 包 hash 校验（`pip install --require-hashes`）

## 四、对抗防御体系

### 4.1 当前防御层级

```
L1: 格式检查（YAML 合法、必填字段）
L2: 内容检查（51 规则）
L3: 复算验证（replay 双平台 confirm）
L4: 红队盲读（独立 Agent 两段式）
L5: 人审签署
```

### 4.2 缺失的防御层

| 层级 | 现状 | 缺失 |
|---|---|---|
| L0 身份验证 | 无 | 谁写的？能不能信？ |
| L1.5 来源验证 | 无 | 内容从哪来？有没有被篡改？ |
| L3.5 时序验证 | 部分（470） | 编译后覆写、helper 脚本 |
| L4.5 对抗回归 | 无 | 历史逃逸是否重测？ |
| L5.5 签署验证 | 无（E12） | 人签是不是真的？ |

### 4.3 对抗回归测试

把每轮对抗发现的逃逸做成回归测试：

```
tests/adversarial_regression/
  368_signature_self_proof/     # 368 轮发现的签收自证
    probe.md                     # 逃逸探针
    expected_result: block       # 修复后应该被拦
  373_declaration_decoupling/    # 373 轮发现的声明-实现脱钩
  402_post_compile_overwrite/    # 402 轮发现的编译后覆写
  452_helper_script_overwrite/   # 452 轮发现的 helper 脚本覆写
  470_zombie_lock_dos/           # 470 轮发现的僵尸锁
```

`tools/adversarial_regression.py`（约 80 行）：
- 跑所有历史逃逸探针
- 验证每个探针都被正确拦截（block 或 refute）
- 如果某个探针又逃逸了 → 立即报警（修复退化）

### 4.4 攻击面分类（424 已做）

424 批次做了攻击面分类 A1-A10，持续维护：
- A1: 断言伪造
- A2: 工件篡改
- A3: 恒真断言
- A4: 时序穿链
- A5: 环境依赖
- A6: 解析走私
- A7: 关系隐形
- A8: 签收自证
- A9: 门禁假阳性
- A10: 供应链

每个攻击面有对应的毒样例和防御规则。

## 五、权限模型

### 5.1 角色与权限

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| Writer Agent | 写草稿、写夹具、写卡 | 不能置 verified、不能改规则、不能改核心工具 |
| Redteam Agent | 写红队报告、写毒样例候选 | 不能改卡、不能置 verified |
| Gatekeeper | 跑门禁、跑 replay | 不能改内容、不能置 verified |
| 人（监工） | 置 verified、改规则、改核心工具、push | — |
| 对抗 Agent | 只读+写探针到 _adv/ | 不能改正式目录 |

### 5.2 执行

- Writer 自检层检查：Writer 不能写 `status: verified`
- gate 规则：`status: verified` 必须有 `verified_by: human:*` + git author 匹配
- 目录权限：_adv/ 是对抗 Agent 的沙箱，正式目录只读
- git hook：核心工具（gate_engine/replay/poison）的改动需要人审（CODEOWNERS）

```json
  "actor": "writer:cheap_agent",

  "target": "evidence/mem/EV-MEM-040.md",

```

### 6.2 审计工具

`tools/audit_log.py`（约 60 行）：
- 记录操作
- 查询操作历史
- 检测异常操作（如 Agent 尝试改 verified 原子）

## 七、实施计划

### 第一阶段（零/低成本，立即做）

1. **E12 git author 绑定**：verified 原子加 `verified_commit` + `verified_git_author`，gate 验证匹配（约 50 行）
2. **对抗回归测试**：把 5 轮对抗的逃逸探针做成回归测试（约 80 行工具 + 5 个探针）
3. **CODEOWNERS**：核心工具目录需要人审（.github/CODEOWNERS）
4. **工具 checksums**：核心工具 sha256 记录，CI 验证

### 第二阶段（中等成本，下一批做）

5. **工件来源证明**：replay 输出附带生产证明（工具版本+输入哈希+输出哈希）
6. **夹具沙箱**：编译运行在临时目录，超时限制，禁止写正式目录
7. **权限模型**：Writer 不能写 verified，gate 强制检查
8. **审计日志**：关键操作记录到 audit.jsonl

### 第三阶段（高成本，远期）

9. **GPG 签名**：人审签署用 GPG 签名
10. **依赖 hash 校验**：pip install --require-hashes
11. **完整信任链**：从工具→夹具→工件→卡→原子，每一环都有来源证明

## 十、风险与缓解

| 风险 | 缓解 |
|---|---|
| git author 可以伪造 | git author 只是第一层，远期加 GPG 签名；单人项目风险可控 |
| 对抗回归测试探针过时 | 每轮对抗后更新探针，探针本身也有版本管理 |
| 工具 sha256 每次改工具都要更新 | 只锁核心工具（gate/replay/poison），其他工具不锁 |
| 权限模型增加 Agent 负担 | 只在关键操作检查，日常操作不检查 |
| GPG 签名增加人审负担 | 可选，先 git author 绑定，GPG 远期再做 |
