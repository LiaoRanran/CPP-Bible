# 317_「阙疑」性能优化架构_从单窗口1文件到流水线并行

> 2026-09-12 · 针对"单窗口产出从 4 颗降到 1-2 文件、红队 53 次工具调用、上下文反复耗尽"的性能瓶颈
> 关联：315 双环改进 · 316 角色分化 · G5 流水线

---

## 一、性能瓶颈诊断（用数据说话）

| 瓶颈 | 现状 | 根因 | 业界对标 |
|---|---|---|---|
| 单窗口产出 | 1-2 个文件/窗口（第五批） | 上下文耗尽，每颗原子的细节污染父 agent | Subagents 模式：子 agent 只返回 400 token 摘要 |
| 红队成本 | 53 次工具调用/颗 | 单 agent 串行做所有检查 | 并行工具调用 + 检查项分片 |
| 提示词体积 | 312 提示词 32KB | 铁律/历史教训/格式规范全塞提示词 | PromptPack：系统指令占 94% 输入 token，应外置 |
| 门禁串行 | gate→replay→poison→pytest 顺序跑 | 无依赖的步骤串行 | 并行工具调用，3-5x 延迟降低 |
| 上下文压缩 | 手动对话摘要，丢失信息 | 无结构化 compaction | NVIDIA：156K→20K，context rot 控制 |
| 流水线串行 | Writer 全写完→红队全审完→门禁 | 无重叠 | 投机执行：红队审卡1时 Writer 写卡2 |
| 工具输出 | replay 输出 48 卡详细日志 | 未过滤 | 工具结果只返汇总，详情写文件 |

## 二、七大优化方向（按落地优先级）

### P0-1：子代理模式（Subagents）— 解决上下文耗尽

**业界实践**（Ranjan Kumar, 2026-04）：
- 父 agent 把聚焦工作委托给子 agent
- 子 agent 在**全新上下文窗口**中工作，只返回 ~400 token 摘要
- 子 agent 的所有中间步骤（读的文件、失败尝试）被丢弃
- 父 agent 保持清晰，不会被每颗原子的细节污染

**我们的落地**：

当前已经在用"独立子 agent 红队"，但可以系统化：

```
父 agent（监工/调度器）：
  - 维护批次状态（哪些原子完成、哪些待审）
  - 每颗原子启动一个 Writer 子 agent
  - 每颗原子启动一个 RedTeamer 子 agent
  - 子 agent 返回结构化摘要（claim/证据/门禁结果/待办）
  - 父 agent 只做：调度 + 汇总 + 门禁总控

子 agent（每颗原子一个）：
  - 全新上下文，只加载当前原子需要的文件
  - 完成后返回 < 500 token 的结构化报告
  - 中间过程全部丢弃
```

**预期效果**：
- 父 agent 上下文从"每颗原子 2000+ token"降到"每颗 500 token 摘要"
- 单窗口可以处理 3-4 颗原子（当前 1 颗就耗尽）
- 子 agent 之间可以并行（见 P0-2）

### P0-2：流水线并行 — 解决串行等待

**当前流水线**（串行）：
```
Writer 写卡1 → Writer 写卡2 → Writer 写卡3
→ 红队审卡1 → 红队审卡2 → 红队审卡3
→ 门禁卡1 → 门禁卡2 → 门禁卡3
```

**优化后**（流水线重叠）：
```
时间 →
Writer:  [卡1] [卡2] [卡3]
红队:        [审卡1] [审卡2] [审卡3]
门禁:            [门卡1] [门卡2] [门卡3]
```

**实现方式**：
- Writer 写完卡1 立即启动红队子 agent（不等卡2/3）
- 红队审完卡1 立即启动门禁（不等卡2/3）
- 三颗原子的三个阶段在时间上重叠

**预期效果**：批次总时间从 `3×(Writer+红队+门禁)` 降到 `Writer + 红队 + 门禁 + 2×max(单步)`，约省 40%。

### P0-3：门禁并行 — 解决串行工具调用

**当前**：gate → replay → poison → pytest 顺序跑，每个 1-3 分钟。

**优化**：这四个工具**无依赖**，可以并行：
```python
# 伪代码
async with asyncio.TaskGroup() as g:
    t1 = g.create_task(run_gate())
    t2 = g.create_task(run_replay())
    t3 = g.create_task(run_poison())
    t4 = g.create_task(run_pytest())
# 4 个并行，总时间 = 最慢的一个（replay ~3min），不是 4 个之和（~8min）
```

**注意**：Windows replay 与 WSL ci_local_precheck **不能并行**（同写 Examples/*.asm），但 gate/poison/pytest 与 replay 可以并行。

**预期效果**：门禁总时间从 ~8min 降到 ~3min。

### P1-1：提示词瘦身 — 解决 token 浪费

**现状**：312 提示词 32KB，其中：
- 铁律 12 条（~2KB）→ 已在 gate_engine 中实现，提示词里不需要重复
- 历史教训（~5KB）→ 应该移到知识库，需要时检索
- 格式规范（~3KB）→ 应该移到模板文件，引用即可
- 当前批次特定指令（~5KB）→ 这才是提示词该有的

**优化后提示词结构**（目标 <10KB）：
```
1. 角色定义（500 token）
2. 本轮任务（1000 token）— 特定于当前批次
3. 关键约束（500 token）— 只列本批特有的约束
4. 交付物清单（500 token）
5. 引用：[铁律见 docs/kernel/iron_laws.md] [教训见 docs/kernel/lessons.md] [模板见 templates/]
```

**蚂蚁灵犀的实践**：上下文动态裁剪 + JSON 语义化压缩 + 巡检结果外置仅留摘要，砍掉 98% 无效 token。

**预期效果**：每轮 LLM 调用的输入 token 减少 60-70%，速度提升，成本降低。

### P1-2：结构化上下文压缩 — 解决摘要丢失

**当前**：上下文耗尽时手动写"对话摘要"，自由文本，容易丢关键事实。

**优化**：每批结束时自动生成**结构化批次摘要**：
```yaml
batch_id: G5_MEM_batch5
atoms_completed: [ALLOC-002, LEAK-002, PERF-004]
atoms_pending: []
evidence_cards: {EV-MEM-040..045: confirm}
gate_result: {block: 0, warn: 10}
key_findings:
  - "ALLOC-002 元数据口径统一后方向反转（pool 8056B 非 32B）"
  - "LEAK-002 加 volatile 后 LSan 从零报告变报告 64B"
pending_decisions: []
next_batch: CONC-001/002/003
```

**关键**：摘要只保留**可验证的事实**（claim/sha/门禁结果），不保留中间推理。下一批从摘要恢复，不读原始对话。

**NVIDIA 实践**：上下文从 156K 压缩到 20K，管理 context rot，控制缓存输入 token 花费。

### P1-3：工具结果过滤 — 解决输出污染

**当前**：replay 输出 48 张卡的详细日志（每张 5-10 行），全进上下文。

**优化**：工具只返回**汇总**，详情写文件：
```
[replay] confirm=48 refute=0 infra_error=0 共 48 张卡
  详情见 build/replay_detail.log
```

红队/Writer 只需要知道"全绿"还是"哪张卡红了"，不需要每张卡的逐行日志。

**预期效果**：工具输出从 ~500 行降到 ~5 行，上下文污染减少 99%。

### P2：投机执行（流程层模拟）

**业界**（PASTE, arXiv 2603.18897）：预测下一个工具调用，在 LLM 还在生成时就执行。

**我们的流程层模拟**：
- Writer 写完 claim 后，**预启动**夹具编译（不等 Writer 写完证据卡）
- 红队审完卡1 的形式问题后，**预启动**卡1 的门禁（不等红队写完语义审查）
- 这是"乐观执行"——如果后续步骤发现问题，预执行的结果作废，但不浪费时间

**风险**：预执行可能浪费资源（如果后续步骤推翻了前提）。只对**确定性高**的步骤预执行（如夹具编译、门禁跑规则）。

## 三、性能指标体系

建立性能基线，每批测量：

| 指标 | 当前基线 | 目标 |
|---|---|---|
| 单窗口原子产出 | 1 颗 | 3 颗 |
| 单颗原子总耗时 | ~3 窗口 | ~1 窗口 |
| 红队工具调用数 | 53 次/颗 | <30 次/颗 |
| 门禁总时间 | ~8min（串行） | ~3min（并行） |
| 提示词体积 | 32KB | <10KB |
| 上下文压缩比 | 手动，信息丢失 | 结构化，零丢失 |
| 批次总时间 | 6+ 窗口 | 2-3 窗口 |

每批结束时在质检报告中记录这些指标，外环（315 §三）监控趋势。

## 四、落地顺序

1. **第一波**（立即）：P0-3 门禁并行 + P1-3 工具结果过滤 — 纯工具改动，零风险
2. **第二波**：P0-1 子代理模式 + P0-2 流水线并行 — 需要调整执行提示词
3. **第三波**：P1-1 提示词瘦身 + P1-2 结构化压缩 — 需要重构提示词体系
4. **第四波**：P2 投机执行 — 高风险，前三波稳定后再做

## 五、与已有架构的关系

- **315 双环**：性能指标是外环的输入（"单窗口产出下降"本身就是外环该诊断的问题）
- **316 角色分化**：子代理模式是角色分化的执行载体
- **310 CI 加速**：门禁并行是 CI 加速的本地版（CI 也需要并行化）
- **G6 四级状态**：状态机不变，性能优化是让状态流转更快

**核心洞察**：「阙疑」的质量体系（三权分立+33规则+48卡replay）已经足够强，当前的瓶颈不是质量而是**吞吐量**。性能优化的目标是"在不降低质量的前提下，把单窗口产出从 1 颗提到 3 颗"——这需要的不是更聪明的模型，而是更高效的架构。
