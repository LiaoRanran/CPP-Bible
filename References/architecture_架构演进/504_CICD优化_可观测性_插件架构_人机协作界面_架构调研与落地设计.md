## 一、CI/CD 流水线优化

### 1.1 业内先进实践

| 技术 | 效果 | 可借鉴点 |
|---|---|---|
| **增量测试选择**（Bazel/Nx affected） | 单 commit 只改 1-2 包时测试范围减少 90%，20min→3min | 基于依赖图确定受影响测试 |
| **Test sharding**（pytest-xdist） | 30min→5-10min，近线性加速 | 测试分片并行执行 |
| **Job 级并行** | 独立阶段并行，总时间=最长阶段而非总和 | CI 矩阵拆分 |
| **依赖/构建缓存** | 每次节省 1-5min，cache key 基于文件 hash | GitHub Actions cache |
| **分层测试** | 快测试每次跑，全量回归定时跑 | prepush 只跑快测试 |

**关键原则**：Wall-Clock Time 是唯一重要的指标（不是 CPU time）。并行不减少总计算量，但大幅减少开发者等待时间。

### 1.2 当前系统的瓶颈（实测数据）

| 阶段 | 耗时 | 瓶颈 |
|---|---|---|
| pytest | ~642s | 3 个 contains_in 测试烧 174.7s（整仓 rglob 28588 文件，499 已发现） |
| replay 全量 | 245-300s | 每卡独立编译，P0-A 重编译禁用 ccache |
| gate + poison + consistency + metrics | ~30s | 串行执行，实际可并行 |
| **总计** | **~15min** | **串行+全量+无缓存** |

CI quality job 34 步全部串行，没有并行、没有增量、没有缓存。

### 1.3 优化架构设计

```
┌──────────────────────────────────────────────────────┐
│                   CI 流水线（优化后）                   │
│                                                        │
│  ┌──────────────────────────────────────────────────┐  │
│  │  Step 0: 变更分析（git diff → 受影响范围）         │  │
│  │  - 改了 tools/gate_engine.py → 全量 gate+poison   │  │
│  │  - 改了 atoms/ 某卡 → 只 replay 该卡+依赖卡       │  │
│  │  - 改了 Examples/ 某夹具 → 知识图谱 impact 查询    │  │
│  └──────────────────────┬───────────────────────────┘  │
│                         │                              │
│  ┌──────────────────────▼───────────────────────────┐  │
│  │  Step 1: 并行矩阵（4 个 job 同时跑）              │  │
│  │  ┌──────────┐ ┌──────────┐ ┌────────┐ ┌────────┐ │  │
│  │  │ pytest   │ │ replay   │ │ gate   │ │ poison │ │  │
│  │  │ (xdist  │ │ (增量)   │ │ (全量) │ │ (全量) │ │  │
│  │  │  16路)   │ │          │ │        │ │        │ │  │
│  │  └──────────┘ └──────────┘ └────────┘ └────────┘ │  │
│  └──────────────────────┬───────────────────────────┘  │
│                         │                              │
│  ┌──────────────────────▼───────────────────────────┐  │
│  │  Step 2: 汇总（consistency + metrics + 报告）     │  │
│  └──────────────────────────────────────────────────┘  │
│                                                        │
│  缓存: ccache(编译) + pytest-cache(测试) + pip-cache   │
└──────────────────────────────────────────────────────┘
```

**四项具体优化**：

1. **增量 replay**（已有基础，498 落地了 `--incremental`，0.3s 无改动/2.3s 改 1 卡）
   - CI 中默认 `--incremental`，只在改了工具/全量验证时用 `--rebuild-manifest`
   - 变更分析用知识图谱的 `kg impact` 查询（502 L1）

2. **pytest 并行**（pytest-xdist）
   - 32 核机器用 `-n 16`，预计 642s→80s
   - 先修 499 发现的 contains_in 整仓 rglob bug（预计再省 174s）

3. **CI Job 并行**（GitHub Actions matrix）
   - pytest / replay / gate / poison 四个独立 job 同时跑
   - 总时间 = max(各阶段) 而非 sum，预计 15min→5min

4. **缓存**
   - ccache：replay 编译缓存（P0-A 重编译仍禁用，但普通编译可用）
   - pytest-cache：测试结果缓存，未改的测试跳过
   - pip-cache：依赖安装缓存

**预期效果**：CI 总时间 15min→3-5min。

### 1.4 落地路径

| 阶段 | 内容 | 工作量 |
|---|---|---|
| L1 | 修 contains_in rglob bug + pytest-xdist 并行 | 1 个苦力批次 |
| L2 | CI matrix 并行 + 增量 replay 默认启用 + 缓存配置 | 1 个苦力批次 |
| L3 | 变更分析（知识图谱 impact）+ 分层测试（prepush 快/CI 全量） | 好模型批次 |

## 二、可观测性日志体系

### 2.1 业内先进实践

| 系统 | 核心机制 | 可借鉴点 |
|---|---|---|
| **OpenTelemetry（OTel）** | 成为 AI 可观测性标准，语义约定描述 LLM 操作，零供应商锁定 | 标准格式、可切换后端 |
| **LangSmith** | 完整执行树：每个 LLM 调用、工具调用、检索步骤；监控质量不只是正常运行 | Trace 树、质量监控 |
| **AgentTrace**（arXiv 2602.10133） | 三面分类法：认知面（推理）、操作面（执行）、上下文面（环境） | 多层面内省 |
| **AgentOps** | 本地优先、隐私清理、预算控制、trace 回放 | 本地存储、回放 |

**关键洞察**：AI 系统的可观测性不只是"有没有报错"，而是 token 使用、延迟、执行时长、幻觉检测、成本异常——质量监控比正常运行监控更重要。

### 2.2 当前系统的差距

- trace_logger 已有（498 落地），但只有工具调用的简单 trace
- 没有统一日志格式：每个工具输出格式不同
- 没有 Trace ID：无法关联同一批次的所有日志
- 没有日志查询工具：出问题要手动 grep worklog
- 没有 Agent 决策面的日志（认知面缺失）

### 2.3 可观测性架构设计

```
┌──────────────────────────────────────────────────────┐
│              tools/observability.py                    │
│                                                        │
│  ┌─────────────┐  ┌──────────────┐  ┌───────────────┐ │
│  │ Trace 生成器 │→ │ 结构化日志   │→ │ data/logs/    │ │
│  │ (三面分类)   │  │ (JSON Lines)│  │ (按日期轮转)   │ │
│  └─────────────┘  └──────────────┘  └───────┬───────┘ │
│                                              │         │
│  ┌───────────────────────────────────────────▼───────┐ │
│  │  日志查询工具 tools/log_query.py                   │ │
│  │  log_query --trace-id xxx --tool replay --level error│ │
│  │  log_query --since "1h" --grep "refute"            │ │
│  │  log_query --batch 500 --summary                   │ │
│  └───────────────────────────────────────────────────┘ │
│                                                        │
│  ┌───────────────────────────────────────────────────┐ │
│  │  实时监控（Web仪表盘，504 第四节）                  │ │
│  │  - 当前运行任务的实时 trace                         │ │
│  │  - token/耗时/错误率实时曲线                        │ │
│  └───────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────┘
```

**三面分类日志**（参考 AgentTrace）：

| 面 | 内容 | 示例 |
|---|---|---|
| **认知面**（cognitive） | Agent 的决策、推理、选择 | "选择差模型执行任务 X""判断逃逸根因为 Y" |
| **操作面**（operational） | 工具调用、命令执行、文件读写 | "replay --check 耗时 245s，confirm=56" |
| **上下文面**（contextual） | 环境状态、输入输出、配置 | "git HEAD=abc123，编译器=g++15.3，工作树干净" |

**统一日志格式**（JSON Lines）：

```json
{"trace_id": "batch-500-abc123", "ts": "2026-09-14T20:00:00", "surface": "operational", "tool": "replay", "action": "check", "duration_ms": 245000, "result": {"confirm": 56, "refute": 0}, "level": "info"}
{"trace_id": "batch-500-abc123", "ts": "2026-09-14T20:01:00", "surface": "cognitive", "tool": "agent", "action": "decision", "detail": "M5逃逸根因为EV-OUT-UNDECLARED-KEY缺反向检查", "level": "info"}
```

**Trace ID 规则**：
- 每个批次/任务分配唯一 trace_id（如 `batch-500-<hash>`）
- 所有工具调用携带 trace_id（环境变量 `TRACE_ID`）
- 日志按 trace_id 可完整回溯

### 2.4 落地路径

| 阶段 | 内容 | 工作量 |
|---|---|---|
| L1 | 统一日志格式（JSON Lines）+ Trace ID + 三面分类 + log_query | 1 个苦力批次 |
| L2 | 所有工具接入日志（trace_logger 扩展）+ 日志轮转+清理 | 1 个苦力批次 |
| L3 | 实时监控（WebSocket 推送仪表盘）+ 异常检测（token/耗时突变告警） | 好模型批次 |

## 三、插件扩展机制

### 3.1 业内先进实践

| 系统 | 核心机制 | 可借鉴点 |
|---|---|---|
| **DeepSeek Harness**（2026） | Everything-is-Plugin：模型适配器/工具注册/技能库/会话/沙箱/存储/主循环/调度器/UI 全是插件，基于 Cordis 元框架 | 极致插件化、核心最小化 |
| **OpenClaw** | 微内核架构：插件管理器+工具注册中心+能力路由，运行时注册/卸载/热重载 | 微内核、热重载 |
| **Pi Agent** | 契约式接口：第三方插件不碰核心代码，框架控制能力边界和生命周期 | 安全边界、契约设计 |
| **标准化插件**（2026 趋势） | VS Code 和 Claude Code 之间可互操作的插件，技能/Agent/hook 打包成可安装单元 | 跨平台互操作 |

**关键洞察**：插件=可运行工作流，Skill=Agent 设计品味（SKILL.md），两者是不同层次。我们的系统目前 13 个工具都是硬编码脚本，没有统一接口。

### 3.2 当前系统的差距

- 13 个工具（gate_engine/replay/poison/pytest/golden_lock/...）都是独立 Python 脚本
- cppbible.py 硬编码注册每个工具
- 新工具要改 cppbible.py（违反开闭原则）
- 没有统一的工具接口（每个工具的 CLI 参数、输出格式不同）
- 没有热重载（改了工具要重启）

### 3.3 插件架构设计

```
┌──────────────────────────────────────────────────────┐
│              微内核 (tools/kernel.py)                  │
│                                                        │
│  ┌──────────────┐  ┌───────────────┐  ┌────────────┐ │
│  │ 插件管理器    │→ │ 工具注册中心  │→ │ 能力路由    │ │
│  │ (扫描/加载)   │  │ (manifest)    │  │ (按任务选工具)│ │
│  └──────────────┘  └───────────────┘  └────────────┘ │
│                                                        │
│  插件目录 tools/plugins/                               │
│  ├── gate_engine/          (核心规则引擎)              │
│  ├── replay/               (证据复算)                  │
│  ├── poison/               (毒样例)                    │
│  ├── knowledge_graph/      (知识图谱, 502)             │
│  ├── knowledge_search/     (RAG 检索, 502)            │
│  ├── diagnostics/          (诊断引擎, 501)             │
│  ├── task_queue/           (编排队列, 501)             │
│  ├── metrics/              (质量度量, 503)             │
│  ├── model_router/         (多模型路由, 503)           │
│  ├── observability/        (可观测性, 504)             │
│  └── ...                  (新工具即插即用)             │
│                                                        │
│  每个插件目录:                                           │
│  ├── plugin.py            (实现统一接口)                │
│  ├── manifest.json        (元数据: name/version/inputs)│
│  └── tests/               (插件自带测试)                │
└──────────────────────────────────────────────────────┘
```

**统一工具契约**（每个插件必须实现）：

```python
class ToolPlugin:
    name: str           # "gate_engine"
    version: str        # "1.0.0"
    description: str    # 一句话描述
    
    def run(self, args: dict) -> dict: ...   # 执行，返回结构化结果
    def validate(self, args: dict) -> list[str]: ...  # 参数校验，返回错误列表
    def health_check(self) -> bool: ...      # 健康检查
```

**manifest.json**：

```json
{
  "name": "gate_engine",
  "version": "1.0.0",
  "description": "规则引擎，检查原子/证据卡合规性",
  "inputs": {"mode": "check|list|advice", "target": "path"},
  "outputs": {"block": "int", "warn": "int", "advice": "int"},
  "tags": ["quality", "gate"],
  "parallel_safe": true
}
```

**自动发现**：
- 启动时扫描 `tools/plugins/*/manifest.json`
- 自动注册，不需要改 cppbible.py
- 新工具 = 新建目录 + 写 plugin.py + manifest.json + tests/

**能力路由**（和 503 多模型路由配合）：
- 根据任务标签（quality/performance/diagnosis/...）自动选择工具
- `cppbible run --task "检查卡合规"` → 自动选 gate_engine

### 3.4 落地路径

| 阶段 | 内容 | 工作量 |
|---|---|---|
| L1 | 定义工具契约 + manifest 格式 + 插件管理器（扫描/加载） | 1 个苦力批次 |
| L2 | 迁移 3 个核心工具（gate/replay/poison）到插件架构 | 1 个苦力批次 |
| L3 | 全量迁移 + 能力路由 + 热重载（开发模式） | 好模型批次 |

## 五、四者的协同关系

```
CI/CD 优化 ──→ 更快的反馈循环 → 更频繁的迭代
     │
     ▼
可观测性 ──→ 出问题秒定位 → 更少的调试时间
     │
     ▼
插件架构 ──→ 新工具即插即用 → 系统可扩展性
     │
     ▼
人机界面 ──→ 可视化操作 → 更低的使用门槛
```

- CI/CD 是"速度"：让每次验证更快
