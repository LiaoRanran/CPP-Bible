# 432 架构设计：多模型协作架构（苦力/好模型/对抗模型的分工与协作协议）

> 日期：2026-09-13。用户确立的工作流：白天苦力干杂活 + 架构师调研 → 大版本送对抗 → 晚上好模型落地系统基线。本文设计三类模型的分工边界、协作协议、质量保证和任务路由。

---

## 一、三类模型的定位

### 1.1 苦力模型（差模型，白天）

**特征**：便宜、速度快、上下文小、推理能力弱。

**适合的任务**：
- 确定性高、风险低的工具落地（按提示词改代码、配毒样例、写 pytest）
- 只读工具（闪卡导出、成本追踪、影响分析）
- 机械性分类（毒样例 A1-A10 标签、freshness 批量标注）
- 格式转换（Markdown→Anki CSV、JSON 输出）

**不适合的任务**：
- 架构级改动（gate_engine.py 核心重构）
- 新规则设计（需要理解攻击原理）
- 红队/对抗（需要创造性攻击思维）
- 人审级判断（claim 方向对不对）

**质量保证**：
- 每个任务必须有明确的验收标准（可机器验证）
- 完成后必须跑全量门禁（gate/replay/poison/pytest）
- 存量零误伤是硬约束
- 遇到阻塞立即停，不硬凑

### 1.2 好模型（强模型，晚上）

**特征**：贵、速度慢、上下文大、推理能力强。

**适合的任务**：
- 架构级改动（426 时序约束框架的 InvariantChecker 类）
- 复杂工具实现（419 攻击用例回归库，需交叉提取三个目录）
- 系统基线整合（所有工具注册到 cppbible.py、健康度仪表盘）
- 对抗暴露问题的修复（可能需要理解攻击原理）
- 新规则设计（需要理解攻击面）

**不适合的任务**：
- 确定性高的杂活（浪费 token）
- 批量机械操作（闪卡导出 107 张，差模型也能做）

**质量保证**：
- 任务必须有架构设计文档（不是"你看着办"）
- 完成后必须跑全量门禁 + 对抗复跑
- 改动必须有设计说明（为什么这么改）
- 与苦力的改动分离 commit

### 1.3 对抗模型（独立模型，不定期）

**特征**：与建设者不同实例、不同模型族更佳；目标是攻击，不是建设。

**适合的任务**：
- 独立红队（两段式盲读，只喂夹具/工件/卡 actual）
- 架构对抗（攻击 15 个靶子 + 10 条修复裁决）
- 代码实现层攻击（实弹逃逸，构造可复现的攻击用例）

**不适合的任务**：
- 建设（身份冲突，自己审自己）
- 修复（攻击者的修复建议可能有偏差，需建设者核实）

**质量保证**：
- 两阶段协议：先盲攻（只读代码不读架构结论），再对照
- 每个攻击必须可复现（命令/输出/行号）
- 攻击用例必须固化为回归测试（419）
- 拦截率是硬指标（不是"找了多少问题"，是"多少问题能被拦住"）

## 二、协作协议

### 2.1 任务路由规则

```
任务分类 → 模型选择
  ├─ 确定性高 + 风险低 + 有提示词 → 苦力
  ├─ 架构级 + 复杂 + 需要推理 → 好模型
  └─ 攻击 + 独立 + 需要创造性 → 对抗模型
```

**路由判断的关键问题**：
1. 这个任务有明确的验收标准吗？（有 → 苦力可能能做）
2. 这个任务需要改核心架构吗？（需要 → 好模型）
3. 这个任务需要"攻击思维"吗？（需要 → 对抗模型）
4. 这个任务的失败成本高吗？（高 → 好模型，不能让苦力试错）

### 2.2 交接协议

#### 苦力 → 好模型

苦力完成工具落地后，交接给好模型做架构整合：
```
苦力交付：
  - 工具代码 + 毒样例 + pytest
  - 门禁结果（gate/replay/poison/pytest 全绿）
  - 已知限制（如"手写时序检查，未用 InvariantChecker"）

好模型接手：
  - 重构为通用框架（如 426 的 InvariantChecker）
  - 系统基线整合（注册到 cppbible.py）
  - 对抗复跑（验证重构后不回归）
```

#### 好模型 → 对抗模型

好模型完成系统基线后，交接给对抗模型压力测试：
```
好模型交付：
  - 系统基线（所有工具注册、门禁全绿）
  - 已知弱点（诚实披露，不掩盖）
  - 攻击面清单（A1-A10）

对抗模型接手：
  - 两段式盲攻（先不读架构结论）
  - 实弹逃逸（构造可复现攻击）
  - 拦截率统计
```

#### 对抗模型 → 好模型

对抗完成后，交接给好模型修复：
```
对抗交付：
  - 攻击报告（阻断/高级/建议，分级）
  - 可复现攻击用例（命令/输出/行号）
  - 拦截率统计

好模型接手：
  - 修复阻断/高级
  - 攻击用例固化为回归测试（419）
  - 复跑对抗（验证修复后拦截率提升）
```

### 2.3 质量门禁（跨模型）

| 门禁 | 执行者 | 频率 | 说明 |
|---|---|---|---|
| 单元测试 | 苦力/好模型 | 每次提交 | pytest 全绿 |
| 全量门禁 | 苦力/好模型 | 每个子任务 | gate/replay/poison 全绿 |
| 存量零误伤 | 苦力/好模型 | 每个子任务 | gate block=0, replay confirm=56 |
| 对抗复跑 | 好模型 | 每次架构改动 | 攻击用例库拦截率不下降 |
| 人审 | 用户 | 大版本 | 最终签署 |

## 三、白天-晚上工作流的具体设计

### 3.1 白天（苦力 + 架构师）

```
09:00 架构师：确认昨日成果，写今日大任务包（如 430）
09:30 苦力：开始执行大任务包（8 子任务串行）
10:00 架构师：继续调研/架构设计（不干扰苦力）
12:00 苦力：阶段性汇报（完成了几个子任务，门禁结果）
14:00 架构师：消化调研，写新的架构设计
17:00 苦力：完成或阻塞，汇报最终状态
18:00 架构师：整理今日成果，写晚上好模型的任务包
```

**关键**：白天架构师和苦力并行——苦力干确定性活，架构师做高价值思考。不互相等待。

### 3.2 晚上（好模型）

```
20:00 好模型：读取晚上任务包（架构师白天写的）
20:30 好模型：开始架构级改动（426/419/系统整合）
22:00 好模型：阶段性验证（门禁全绿？）
23:00 好模型：完成或阻塞，汇报
23:30 架构师（或用户）：检查成果，决定是否送对抗
```

**关键**：晚上好模型干的是"苦力干不了的活"——架构重构、复杂工具、系统整合。不是重复白天的工作。

### 3.3 对抗（不定期）

```
触发条件：v7.0 工具层全量落地 + 门禁全绿
执行：独立对抗模型（TRAE/Evolving）
时长：2-4 小时
产出：攻击报告 + 可复现攻击用例 + 拦截率
后续：好模型修复 + 攻击用例固化
```

## 四、Token 经济学（多模型协作的成本优化）

### 4.1 成本分配原则

| 模型 | 单次成本 | 任务类型 | 成本占比目标 |
|---|---|---|---|
| 苦力（差模型） | 低 | 确定性杂活 | 60-70% |
| 好模型（强模型） | 高 | 架构级改动 | 20-30% |
| 对抗模型（独立） | 中 | 压力测试 | 5-10% |

**关键洞察**：苦力虽然单次成本低，但任务量大（8 子任务），总成本占比最高。好模型虽然单次成本高，但任务少（2-3 个架构级任务），总成本占比可控。

### 4.2 成本优化点

1. **苦力任务尽量打包**：一个大任务包（430）比 8 个小提示词省 token（上下文复用）
2. **好模型任务必须有架构设计**：不让好模型"边想边做"，架构师白天已经想好了
3. **对抗模型只在大版本后跑**：不是每次提交都跑，拦截率统计是周期性的
4. **前缀缓存**：所有模型共享系统提示词前缀，利用前缀缓存

### 4.3 CPVA 的多模型分解

```
CPVA = (苦力 token × 苦力单价 + 好模型 token × 好模型单价 + 对抗 token × 对抗单价) / verified 原子数
```

421 成本追踪应该按模型分解，这样才能看出"哪类模型在烧钱"。

## 五、风险与缓解

### 风险 1：苦力任务超出能力范围

苦力可能遇到"提示词写了但实际做不了"的情况（如 414 F02 需要理解时序约束）。

**缓解**：
- 提示词必须有"停止条件"——遇到阻塞立即停，不硬凑
- 苦力的任务必须有明确的验收标准（可机器验证）
- 如果苦力连续 2 轮修不好，升级为好模型任务

### 风险 2：好模型与苦力的改动冲突

苦力改了 gate_engine.py，好模型也改 gate_engine.py，合并冲突。

**缓解**：
- 苦力改的是"规则实现"（EV-ARTIFACT-PRODUCER 的时序检查）
- 好模型改的是"基础设施"（InvariantChecker 类）
- 两者在不同的代码区域，冲突概率低
- 如果冲突，好模型优先（基础设施比规则实现更基础）

### 风险 3：对抗模型的攻击不可复现

对抗模型可能报告"发现了漏洞"但没有可复现的命令/输出。

**缓解**：
- 对抗提示词必须要求"每个攻击必须可复现（命令/输出/行号）"
- 不可复现的攻击降级为"观察"，不阻断
- 419 攻击用例库只收可复现的攻击

### 风险 4：好模型"过度工程"

好模型可能把简单问题复杂化（如把 F02 的手写检查重构为通用框架，但通用框架有 bug）。

**缓解**：
- 好模型的任务必须有架构设计文档（426），不是"你看着办"
- 重构后必须用毒样例+攻击用例复跑验证
- "够用就行"原则：不追求完美，追求可验证

## 六、元结论

**多模型协作的核心不是"用更多模型"，是"让每个模型干它最擅长的活"。**

- 苦力干确定性活（便宜、可验证、零风险）
- 好模型干架构活（贵、复杂、需要推理）
- 对抗模型干攻击活（独立、创造性、压力测试）

**最关键的设计**：交接协议——苦力→好模型→对抗模型→好模型，每个交接都有明确的交付物和验收标准。没有交接协议，多模型就是"各干各的"，不是协作。

**与用户目标的对应**：
- "烧多少 token 一点不浪费" → 成本分配原则 + 任务打包
- "性能和质量都压满" → 苦力干杂活释放好模型 token，好模型专注架构
- "所有情况都能游刃有余" → 三类模型覆盖三类任务，没有能力盲区
