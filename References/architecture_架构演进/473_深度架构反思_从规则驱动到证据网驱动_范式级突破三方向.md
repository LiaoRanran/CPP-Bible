# 473 深度架构反思：从规则驱动到证据网驱动——范式级突破的三个方向

> 2026-09-14 · 第六轮调研收尾后的深度反思。
> 基于 271（概念过剩判据稀缺）、284（元批判三关）、286（极致五标准）、294（Meadows 杠杆点）、五轮对抗结果的综合诊断。

---

## 一、核心诊断：当前系统的本质与瓶颈

### 1.1 当前系统的本质

当前「阙疑」是一个**规则驱动的验证系统**，核心循环：

```
Writer 生产原子 → gate/replay/poison 验证 → 红队找逃逸 → 加规则堵逃逸 → 回到生产
```

这个循环在过去三天产生了显著进步：
- 规则 29→48 条，毒样例 4→52 个，pytest 27→153 个
- replay 40/42→56/56，双平台 confirm
- 红队拦截率 14%→21%→29%

但这个循环有三个结构性瓶颈：

### 1.2 瓶颈一：规则军备竞赛（Meadows 杠杆点 5）

每发现一个逃逸就加一条规则。48 条规则的维护成本随规则数线性增长：
- 规则之间可能冲突（EV-OUT-UNDECLARED-KEY 和 EV-SERVES-EXIST 的 warn 重叠）
- 误报率随规则数上升（32 条 warn 中 17 条是 MATRIX 规则对已真实跨平台卡的误报）
- 新规则需要新毒样例+新 pytest，每条规则的边际成本在递增
- 对抗每轮都能找到新逃逸——规则永远列不全（E01→F02→E01 变体，同一漏洞三次变种）

**286 批判**："逐条加规则而非提炼元规则。'断言必须可证伪'一条元规则可能覆盖 P4/P5/P6/P7。"

### 1.3 瓶颈二：架构-工程脱节（286 最严重问题）

架构层面设计了大量机制，但工程层面还在用旧流程：
- claim 契约化（pre/post/invariant）——设计了，原子生产中使用率 <10%
- 候选仓 candidates/——设计了，从未使用
- 科学发现状态机（S1-S6）——设计了，红队还是"读代码+推理"
- 数据飞轮 Distill/Improve——设计了，没有实现
- 知识进化论（范式健康度监控）——设计了，没有实现

**286 批判**："架构文档越来越厚，工程实践没变。285 的 9 个修正如果不进入工程，就是下一份 282（提案级不执行）。"

### 1.4 瓶颈三：预测性为零（Lakatos 退化纲领）

当前架构只能解释过去的错误，不能预测未来的错误：
- ALLOC-002 的"口径不统一"——架构没有预测到
- LEAK-002 的"无关改动翻转结论"——架构没有预测到
- 470 的"warn 不阻断"——架构没有预测到
- 第五轮对抗的 N1 僵尸锁、N2 恒真盲区——架构没有预测到

**286 批判**："266→285，每一轮都是'发现问题→加规则'，全是事后反应。我们的架构只能解释过去，不能预测未来。这是 Lakatos 意义上的退化纲领。"

## 二、范式级突破的三个方向

基于 Meadows 杠杆点诊断（80% 精力在杠杆点 5 规则层，真正突破在 2 范式层和 6 信息层），提出三个范式级突破方向：

### 方向一：从"规则驱动"到"证据网驱动"（范式层突破）

#### 核心思想

每个 claim 不是被"规则检查"，而是被"证据网支撑"。证据网是一个图：

```
claim → 证据卡 → 夹具 → 工件 → sha256 → 编译器版本+优化档
  ↑                                    ↓
  └── refutes/contradicts ←───────────┘
```

claim 的可信度由证据网的**拓扑结构**决定，而非逐条规则检查：

| 证据网状态 | 可信度 | 自动动作 |
|---|---|---|
| 证据链完整（claim→卡→夹具→工件→sha 都存在且匹配） | 高 | verified 候选 |
| 证据链断裂（工件丢了/sha 不匹配/夹具被删） | 低 | 自动降级为 draft |
| 证据链被证伪（红队找到反例，探针可复现） | 零 | 自动标记 contending |
| 证据网矛盾（A 依赖 B，B 被证伪） | 连锁降级 | A 自动降级 |
| 证据独立（多编译器/多平台一致） | 更高 | cross-checked |

#### 为什么这是范式级突破

1. **新类型的错误不需要新规则**——只需要新的证据类型。比如"恒真断言"不需要一条 EV-ASSERT-DISCRIMINATOR 规则，只需要在证据网中标记"这个断言的证据是恒真的（在所有函数区间都出现）"。
2. **系统可以自动发现矛盾**——A 的 claim 说"pool 元数据最省"，B 的 claim 说"pool 元数据 8056B"，证据网中两者矛盾→自动标记。这是 ALLOC-002 方向反转的自动检测。
3. **证据链断裂自动传播**——工件被清空（N4 事故），所有依赖它的证据卡自动降级，而不是只有一张卡出问题。
4. **符合 277 宪法**——"探究网络为唯一内核"，证据网就是探究网络的工程化。
5. **符合 360 知识进化论**——范式健康度可以由证据网的"退化率"（补丁数/预言成功数）自动计算。

#### 渐进路径（6 步，每步可独立验证）

1. **已完成**：证据卡 refutes/limitations/artifact_sha256 字段
2. **472 在做**：工件还原幂等、签收绑定、恒真断言检测
3. **下一批 P0**：构建证据网索引工具 `evidence_graph.py`——扫描所有原子/证据卡/夹具/工件，构建 claim→卡→夹具→工件的映射图
4. **下一批 P1**：证据网一致性检查——工件变更自动触发依赖它的所有卡标记为"需重验"
5. **P2**：证据网可信度计算——基于证据链完整性和独立性（多编译器/多平台）计算 claim 的可信度分数
6. **P3**：从证据网自动发现矛盾——两个 claim 的证据链完整但结论矛盾→自动标记 contending

#### 与现有系统的关系

证据网不是替代 gate/replay，而是**升维**：
- gate/replay 继续做"单卡验证"（证据网的边是否有效）
- 证据网做"全局一致性"（证据网的拓扑是否自洽）
- 现有 48 条规则中，约 15 条可以转化为证据网的拓扑检查（如 EV-SERVES-EXIST、ATOM-REL-CONFLICT、EV-ARTIFACT-PRODUCER）

### 方向二：诊断引擎（信息流层突破）

#### 核心思想

当前系统的问题是"门禁红了，但不知道为什么、该怎么修"。诊断引擎的目标：

```
输入：门禁输出（refute:run_mismatch, block:ATOM-STATUS-TRANSITION）
输出：根因假设 + 修复建议 + 验证步骤
方法：359 科学发现状态机（异常→溯因→假设竞争→判别实验）
```

#### 为什么这是信息流层突破

Meadows 杠杆点 6："信息流的改变可能比规则改变更有效。"当前门禁只输出"红/绿"，不输出"为什么红/怎么修"——信息在"门禁红了"这一步就断了，后续的根因分析全靠人。

诊断引擎让信息继续流动：

```
门禁红了 → 诊断引擎分析 → 根因假设 → 修复建议 → 自动修复（简单问题）/ 人工修复（复杂问题）
```

#### 具体能力

1. **refute 根因分析**：
   - `refute:run_mismatch` → 自动 diff actual 和 stdout → 推断是"断言写错了"还是"夹具变了"还是"编译器版本变了"
   - `refute:artifact_assert_failed` → 自动检查断言符号是否在工件中存在 → 推断是"符号名错了"还是"工件过期了"
   - `refute:artifact_tampered` → 自动检查 sha 不匹配的原因 → 推断是"工件被改了"还是"重编译环境不同"

2. **block 修复建议**：
   - `block:ATOM-STATUS-TRANSITION` → 自动检查 status_history 格式 → 给出精确的修复 YAML
   - `block:ATOM-DAL-MATCH` → 自动检查 DAL 和 human_review 字段 → 给出修复建议
   - `block:EV-FM-DUP-KEY` → 自动定位重复键 → 给出删除建议

3. **批量问题识别**：
   - 多个卡同时 refute → 自动识别共性（都是同一个编译器版本问题/都是同一个夹具被改了）→ 批量修复建议
   - 同一类 block 反复出现 → 自动建议"这是系统性问题，需要改工具而非改卡"

4. **诊断知识库**：
   - 记录历史上每个错误类型的根因和修复方法
   - 新错误出现时，匹配历史模式→给出"这和 XX 事故类似，当时的修法是 YY"

#### 实现路径

1. **第一步**：在 `atom_evidence_replay.py` 的 refute 输出中增加"根因提示"字段（基于规则的简单匹配）
2. **第二步**：构建 `diagnosis_engine.py`，输入门禁输出，输出根因假设+修复建议
3. **第三步**：接入 Writer 自检层——Writer 写完卡后，诊断引擎预跑一遍，给出"这张卡可能会被 refute，因为 XX"
4. **第四步**：诊断知识库——记录每次修复的根因和方法，用于模式匹配

### 方向三：预测性（从退化纲领到进步纲领）

#### 核心思想

286 的核心批判："架构只能解释过去，不能预测未来。"预测性的目标是在生产原子之前，预测可能的错误类型。

#### 具体能力

1. **原子类型→错误模式预测**：
   - 多 TU 原子→预测"单 artifact 字段问题"（371 已实证）
   - 性能原子→预测"时序数据入断言"（PERF-003/004 已实证）
   - 并发原子→预测"TSan 不可用/非确定终值"（CONC-003 已实证）
   - UB 原子→预测"sanitizer 判定与编译器版本相关"

2. **夹具复杂度→逃逸风险预测**：
   - 夹具含 volatile/asm 屏障→预测"编译器优化可能消除观测"（CONC-001 已实证）
   - 夹具含多文件构建→预测"command 解析问题"
   - 夹具含 sanitizer→预测"MinGW 不可用/TSan 需 setarch -R"

3. **预测命中率追踪**：
   - 每批生产前，系统输出"本批预测的 3 个错误类型"
   - 生产后，对比预测和实际→计算命中率
   - 286 标准：连续 2 批命中率 ≥50% = 进步纲领

#### 实现路径

1. **第一步**：构建"错误模式库"——基于历史数据，记录每种原子类型/知识点的常见错误类型
2. **第二步**：Writer 提示词中增加"本批预测错误类型"——Writer 在生产前必须声明预测
3. **第三步**：批次报告中增加"预测命中率"章节——自动对比预测和实际
4. **第四步**：预测命中率低于 50% 时，自动触发架构修正——"预测不准说明架构有盲区"

## 三、三个方向的优先级和依赖关系

```
方向一（证据网驱动）─── 基础 ───→ 方向二（诊断引擎）─── 基础 ───→ 方向三（预测性）
     │                        │                        │
     └── 需要 evidence_graph.py     └── 需要诊断知识库        └── 需要错误模式库
     └── 可以独立启动               └── 依赖证据网的索引       └── 依赖诊断引擎的历史数据
```

**推荐顺序**：
1. **先做方向一的第 3 步**（evidence_graph.py 索引工具）——这是基础，工作量小（1-2 轮），价值大
2. **同时做方向二的第 1 步**（refute 根因提示）——增量改造，不影响现有系统
3. **方向三在方向一、二有数据后启动**——预测性需要历史数据支撑

**不推荐**：三个方向同时启动——会重蹈"架构-工程脱节"的覆辙（设计太多，落地太少）。

## 四、对 472 修复批的影响

472 的 6 个 P0 都是**规则层修复**（杠杆点 5），是必要的但不是范式级的。在执行 472 的同时，应该为方向一做准备：

1. **472 P0-5（TDD 顺序反转）中的 WC-9（工件同代检查）**——这是证据网一致性检查的雏形，可以扩展为"工件变更→依赖卡自动标记"
2. **472 P0-3（签收绑定）**——签收信息是证据网的一个节点，可以纳入证据网索引
3. **472 P0-2（恒真断言盲区）**——恒真标记是证据网中"证据质量"的一个维度，可以纳入可信度计算

**建议**：472 执行完后，下一批（474）启动 evidence_graph.py，作为方向一的第一步。

## 五、对"极致"的重新定义（286 五标准的当前评估）

| 标准 | 目标 | 当前（2026-09-14） | 差距 |
|---|---|---|---|
| 1. 预测性 | 连续 2 批命中率 ≥50% | 0%（从未做） | 需方向三 |
| 2. 概念收敛 | ≤20 核心概念 | 膨胀中（5原理+5公理+6态+8环节+48规则+...） | 需概念审计 |
| 3. 架构-工程闭环 | 新机制使用率 ≥50% | 脱节（大部分机制未在工程验证） | 需方向一/二落地 |
| 4. 方法独立 | 红队 ≥50% 发现来自对照实验 | 主要靠推理（第五轮对抗的探针是对照实验，但红队报告本身是推理） | 需红队模板升级 |
| 5. 停止条件 | ≥4/5 满足 | 0/5 | 依赖以上 |

**结论**：当前距离"极致"还很远，但方向已经明确。三个范式级突破方向（证据网/诊断引擎/预测性）对应了 286 五标准中的 1/3/4，概念收敛（标准 2）需要一次专门的概念审计，停止条件（标准 5）是前四条的结果。

## 六、一句话总结

> 当前系统在规则层（Meadows 杠杆点 5）已经做到了 80 分，但规则层的天花板就是"逐条堵逃逸"。真正的突破在范式层（杠杆点 2）：从"规则驱动的验证系统"升级为"证据网驱动的知识系统"——让 claim 的可信度由证据网的拓扑结构决定，让门禁的信息流动到根因和修复，让系统能预测下一批的错误而非只解释上一批的错误。
