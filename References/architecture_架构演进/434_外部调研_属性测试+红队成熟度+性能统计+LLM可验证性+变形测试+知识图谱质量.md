## 一、属性测试（Property-Based Testing）

### 核心思想

不写具体输入输出对，而是写"对所有有效输入都成立的性质"。框架自动生成数百/数千个随机输入，发现反例后自动缩小（shrinking）为最小失败案例。

**与阙疑的关系**：阙疑的夹具是"一个例子验证一个 claim"，属性测试是"一个性质验证所有例子"。PERF-004 的"4 线程各累加 1e7 次"就是一个例子——如果线程数、迭代数、布局变化，结论还成立吗？

### 关键模式

| 性质模式 | 说明 | 阙疑对应 |
|---|---|---|
| Invariants | 不管输入怎么变，某个量不变 | arena 元数据不随规模变（活性对照） |
| Round-trip | encode→decode 返回原值 | 构造→析构计数归零 |
| Commutativity | 操作顺序不影响结果 | 多线程累加的最终值 |
| Associativity | 操作分组不影响结果 | 内存分配器的块顺序 |
| Identity | 单位元操作无效果 | 空 arena 的元数据 = 0 |
| Idempotence | 重复操作无额外效果 | release_all 调用两次 |

### 对阙疑的启示

1. **夹具应该声明"验证什么性质"**，而不是只给一个例子
2. **活性对照就是 invariant 性质**——应该形式化，而不是靠人写
3. **反例自动缩小**——红队发现问题后，应该自动缩小到最小复现

### 参考

- QuickCheck（Claessen & Hughes, ICFP 2000，ACM SIGPLAN Most Influential Paper）
- Hypothesis（Python，gold standard）
- PBT-Bench（2026，benchmark AI agent 的属性测试能力）

## 二、红队成熟度模型

### 五级模型

| 级别 | 名称 | 特征 | 阙疑当前 |
|---|---|---|---|
| L1 | Reactive | 事件驱动的临时测试，无系统性 | — |
| L2 | Operational | 定期模拟，有文档流程，MTTD 小时级 | ✅ 当前（定期对抗，有两段式协议） |
| L3 | Adversary-ready | 分钟级检测，验证过的检测覆盖，可测量 | ⏳ 部分（攻击用例库 419 在建） |
| L4 | Advanced | 全紫队集成，威胁行为者 TTP 对齐，持续自动化 | ❌ |
| L5 | Adaptive | AI 增强攻防，实时反馈循环，自定义工具 | ❌ 愿景 |

### 关键指标

- **MTTD**（Mean Time to Detect）：从攻击发生到检测到的平均时间
- **检测覆盖率**：攻击面 A1-A10 的覆盖比例
- **修复率**：发现的漏洞被修复的比例
- **拦截率**：历史攻击用例被门禁拦住的比例

### 对阙疑的启示

1. 阙疑红队当前在 L2，目标是 L3（攻击用例库 + 可测量拦截率）
2. **红队本身的质量需要度量**——不能只看"找了多少问题"，要看"检测覆盖率"和"拦截率提升"
3. L4 的"持续自动化红队"是 v9.0 自治的目标

## 三、性能基准统计方法

### 当前阙疑的问题

PERF-004 报告"7 轮中位数 18.86×"，但：
- 没有置信区间
- 没有统计显著性检验
- 同机跨运行波动 18.86×→8.78×（2×+），说明测量噪声很大
- 7 轮样本量远不够

### 统计严谨性要求

| 指标 | 要求 | 阙疑当前 |
|---|---|---|
| 样本量 | ≥30（中心极限定理） | 7（不够） |
| 置信区间 | mean ± t_critical × SE | 无 |
| 统计检验 | t-test / Mann-Whitney U | 无 |
| 效应量 | Cohen's d | 无 |
| 顺序效应 | 随机顺序执行 | 无（固定顺序） |
| 环境控制 | 记录 CPU/内存/负载 | 部分 |

### 对阙疑的启示

1. **性能卡必须报告置信区间**，不能只报中位数
2. **样本量 ≥30**，不是 7
3. **统计显著性检验**——"A 比 B 慢"必须有 p-value
4. **随机顺序执行**消除顺序效应
5. **锚方向不锚倍数**的纪律是对的，但应该升级为"锚方向 + 置信区间"

## 四、LLM 输出可验证性

### 四层验证模型

| 层 | 验证内容 | 方法 | 阙疑对应 |
|---|---|---|---|
| L1 结构 | 格式是否正确 | JSON schema、YAML 解析 | gate frontmatter 检查 |
| L2 内容 | 是否违反策略 | PII、越界、空值 | gate 规则（42 条） |
| L3 逻辑 | 是否匹配约束 | 价格>0、产品在目录中 | replay 断言验证 |
| L4 语义 | 是否真正回答问题 | 事实核查、证据支撑 | 红队/人审 |

### PRISM 架构（Proof-Carrying Artifact Generation）

- **L1 在线强制**：生成时就强制结构约束（表达力弱但保证强）
- **L2 事后验证**：生成后验证语义/逻辑约束（表达力强但是事后）
- 两者结合 = 安全关键系统的保证

### AutoVerifier：断言三元组

把技术断言分解为 (Subject, Predicate, Object) 三元组，构建知识图谱，逐层验证：
1. 文档内验证
2. 跨源验证
3. 外部信号佐证
4. 假设矩阵生成

### 对阙疑的启示

1. **claim 契约化就是 L3 验证**——precondition/assertion/invariant/falsification 四段可机器验证
2. **阙疑缺少 L4 语义验证**——claim 的 C++ 语义对不对，目前靠红队/人审
3. **断言三元组**可以应用于 claim 的结构化——(主体, 谓词, 客体) 使得 claim 可检索、可验证

## 五、变形测试（Metamorphic Testing）

### 核心思想

解决"oracle problem"——没有单一正确答案时，检查输入变换和输出变化的关系。

**变形关系（MR）**：输入变换 → 预期输出变化。

例：
- 搜索引擎：增加搜索词 → 结果数不增加（或不变）
- 排序算法：输入顺序打乱 → 输出不变
- 编译器：优化档变化 → 可观测行为不变（除非 UB）

### 与阙疑的关系

**阙疑的"单变量对照"夹具本质上就是变形测试**：
- 输入变换：tight 布局 → padded 布局
- 预期输出变化：性能变慢 ≥10×
- 这就是一个变形关系（MR）

### 对阙疑的启示

1. **夹具设计应该形式化变形关系**——明确声明"改变什么变量、预期什么变化"
2. **变形关系可以机器验证**——输入变换后，输出是否按 MR 变化
3. **oracle problem 在阙疑中存在**——"这个 C++ 程序的行为对不对"没有单一答案，但变形关系可以验证

## 六、知识图谱质量评估

### 四维质量模型

| 维度 | 说明 | 阙疑当前 |
|---|---|---|
| Consistency（一致性） | 无矛盾、基数约束、不相交类 | ✅ 417 矛盾检测（L1） |
| Completeness（完整性） | 关系覆盖率、属性填充率 | ❌ 只有存在性检查 |
| Currency（时效性） | 数据是否过时 | ❌ 428 freshness 设计中 |
| Correctness（正确性） | 事实是否准确 | ⚠️ 靠 replay/红队 |

### 关键指标

- **关系覆盖率**：知识图谱中包含的关系类型占领域全部重要关系的比例
- **关系密度**：实际关系数量 / 理论可能关系数量
- **实体属性填充率**：非空属性数量 / 应有属性总数
- **ICR/IPR**：实例化类比例 / 实例化属性比例

### 对阙疑的启示

1. **relations 不只是"有没有矛盾"**——还要评估"完不完整"
2. **关系覆盖率**：阙疑的 DAG_REL 只有 4 种（prerequisite/specializes/realizes/evolved_from）+ 新增 contradicts，是否覆盖了所有重要关系？
3. **属性填充率**：27 颗原子的 frontmatter 字段填充率是多少？有没有必填字段为空？

## 七、六大方向对阙疑的综合影响

| 方向 | 对阙疑的核心贡献 | 落地优先级 |
|---|---|---|
| 属性测试 | 夹具按"性质"设计，活性对照形式化 | P1（v8.0 M2） |
| 红队成熟度 | 红队质量度量，L2→L3 | P1（419 攻击用例库） |
| 性能统计 | 性能卡必须报告置信区间+统计检验 | P0（当前性能卡不严谨） |
| LLM 可验证性 | claim 契约化四段，断言三元组 | P1（v8.0 M1） |
| 变形测试 | 单变量对照的理论基础，MR 形式化 | P1（夹具设计方法论） |
| 知识图谱质量 | relations 完整性+时效性评估 | P2（428 freshness） |

### 最紧急的发现

**性能卡的统计严谨性是 P0**——PERF-004 的 18.86× 同机波动到 8.78×，说明当前性能数据的可信度存疑。在送去对抗之前，必须先把性能卡的统计方法升级（置信区间+样本量+统计检验），否则对抗模型一击必杀。

### 最有价值的框架

**变形测试 = 阙疑夹具设计的理论基础**。阙疑一直在做"单变量对照"，但没有形式化。把变形关系（MR）写进夹具设计方法论，可以让夹具设计从"经验"变成"科学"。
