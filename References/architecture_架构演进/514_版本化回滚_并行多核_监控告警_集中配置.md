## 一、版本化与回滚

### 1.1 业内 Expand-Contract 模式

```
Phase 1: Expand（扩展）
  加新字段/新规则，不删旧的
  旧代码继续工作（向后兼容）

Phase 2: Migrate（迁移）
  代码逐步切到新字段
  双写/双读验证

Phase 3: Contract（收缩）
  确认零依赖后，删旧字段
```

**核心原则**：
- Forward-only：不做down migration，出错写新的forward修
- 幂等：migration可安全重跑
- 回滚预算：能在10分钟内rollback

### 1.2 我们的现状

**已有的**：
- git版本控制（所有变更有commit）
- golden_lock基线管理
- 毒样例版本化

**缺的**：
1. **frontmatter schema变更没有Expand-Contract**：加新字段时旧卡不更新就warn/block
2. **规则变更没有双写期**：新规则一上线就block存量，没有warn→block过渡期
3. **没有回滚演练**：知道git revert能回，但没测过"规则回滚后基线对不对"

### 1.3 落地方案

**规则变更三阶段**：
```
新规则入库时：
  Phase 1: WARN（只记录，不block）—— 跑2周看存量命中
  Phase 2: ADVICE→WARN（调整严格度）—— 确认存量无误伤
  Phase 3: BLOCK（正式上线）—— 此时存量已无命中
```
我们403已经部分这样做了（EV-OUT-UNDECLARED-KEY先warn），但没有显式流程。

**frontmatter schema扩展**：
- 新字段 → 旧卡缺字段 → WARN（不block）
- 跑一批 → 补旧卡
- 补完 → 新字段改REQUIRED
- 这就是Expand-Contract

**版本号**：`config/schema_version: "2.0"`，旧卡标"legacy"。

## 二、并行多核（32核用满）

### 2.1 业内要点

| 任务类型 | 并行方式 | 原因 |
|---|---|---|
| CPU-bound（编译/解析） | ProcessPoolExecutor | GIL阻止threading真并行 |
| IO-bound（文件读/网络） | ThreadPoolExecutor | GIL在IO时释放 |
| Python 3.13+ free-thread | threading无GIL | 我们3.14.7可试 |

**关键**：我们32核，但replay 56张卡是串行跑298s。

### 2.2 我们的现状

**串行的地方**：
- replay 56张卡：每张依次编译→比对→记录
- pytest 366点：串行227s
- gate 55规则：串行扫描所有卡

**并行的机会**：
- replay卡与卡之间完全独立 → 可并行
- pytest不同测试函数独立 → 可并行
- gate不同规则之间独立 → 可并行

### 2.3 落地方案

**replay并行**（最大收益）：
```python
from concurrent.futures import ProcessPoolExecutor

def replay_one(card):
    # 编译→比对→记录
    return result

with ProcessPoolExecutor(max_workers=16) as pool:
    results = list(pool.map(replay_one, all_cards))
```

**预期**：56张卡 / 16进程 ≈ 3.5批 × 5s/卡 ≈ 18s（vs 当前298s）= **16x加速**

**注意**：
- 编译是CPU-bound，必须用ProcessPool（不是ThreadPool）
- 共享锁（build/.replay_lock）需要per-process或无锁
- 临时目录每进程独立

**pytest并行**：
```bash
pip install pytest-xdist
pytest -n 16  # 16并行
```
预期：227s → ~15s

**gate并行**：规则间独立，ProcessPoolExecutor。

## 三、监控告警与异常检测

### 3.1 业内模式

| 方法 | 核心 | 误报率 |
|---|---|---|
| 静态阈值 | refute>0就告警 | 20-40% |
| 动态阈值 | 滑动窗口均值±2σ | 5-15% |
| 马氏距离 | 多变量联合异常 | 最低 |
| 自治可观测 | AI agent自己消费telemetry自动诊断 | 自动根因 |

**AI特有指标**（Pratik Pathak实战总结）：
- 语义漂移：输出偏离预期模式多远
- 置信度分布变化
- token效率：每token的输出质量
- prompt注入尝试次数

### 3.2 我们的现状

**已有的**：
- trace_logger（498）
- cost_tracker（421）
- metrics_collector
- golden_lock基线

**缺的**：
1. **静态阈值**：refute>0就红，没有"正常波动"概念
2. **没有趋势告警**：单看一次不知道是恶化还是正常
3. **没有多变量联合**：refute涨+warn涨+token涨可能是同一个根因
4. **没有自动根因**：告警了要人去查

### 3.3 落地方案

**动态阈值**（滑动窗口）：
```python
# data/metrics_history.jsonl 记录每次门禁结果
# 新结果 vs 过去10次均值±2σ
# 超出 → WARN（不是直接BLOCK）
```

**AI特有指标**：
```yaml
track:
  - replay_confirm_rate: 当前vs7天均值
  - warn_count: 趋势
  - avg_replay_time: 趋势（变慢=可能磁盘问题）
  - token_per_atom: 趋势（涨=效率降）
  - gate_rules_count: 规则数趋势
```

**联合异常**：refute涨+replay_time涨 → 可能是编译器问题（不是卡的问题）。

## 四、集中配置与 Feature Flags

### 4.1 业内原则

- **一个config文件**管理所有magic number
- 每个flag有owner+expiry date
- 100% on一个月后删除flag
- 不要散在代码里改

### 4.2 我们的现状

**散在代码里的magic number**：
```python
# gate_engine.py
threshold = 5          # 连续失败5次
cooldown = 60          # 60s冷却
max_requests = 500     # Agent请求上限
stale = 3600           # 锁陈旧时间
p95_target = 30        # p95延迟30s
```
这些散在不同文件，改一个要grep全仓库。

### 4.3 落地方案

**集中config**（`config/system_config.yaml`）：
```yaml
# 编译器熔断
circuit_breaker:
  failure_threshold: 5
  cooldown_seconds: 60

# Agent请求
agent:
  requests_per_session: 500
  checkpoint_at: 450

# 锁
lock:
  stale_seconds: 3600

# SLO
slo:
  replay_confirm_target: 0.98
  task_latency_p95_seconds: 30

# 并行
parallel:
  max_workers: 16
```

**Feature flags**：
```yaml
features:
  use_incremental_replay: true    # 增量replay
  use_parallel_replay: false      # P1上线
  use_dynamic_threshold: false    # P2上线
  experimental_cat_scan: true     # 实验性
```

每个flag：
- owner：谁负责
- expiry：什么时候删（100% on一个月后删）
- 当前状态

## 六、核心洞察

**版本化**：我们改规则太快（29→55条），没有WARN→BLOCK过渡期。新规则一上线就可能误伤存量。Expand-Contract模式解决这个。

**并行**：32核机器跑56张卡串行298s，是最大的性能浪费。ProcessPoolExecutor改10行代码，16x加速。

**监控**：我们只看"这次过没过"，不看趋势。refute从0跳到3可能是恶化，也可能是正常波动。动态阈值区分两者。

**配置**：magic number散在代码里，改一个grep全仓库。集中一个yaml，改一处生效。
