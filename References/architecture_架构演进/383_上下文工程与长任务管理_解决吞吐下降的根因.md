# 383 上下文工程与长任务管理：解决"吞吐下降"的根因

> 日期：2026-09-13。监工完成。这是 374-382 之后的架构升级轮，聚焦**上下文工程**——直接解决我们的实际痛点：第五批跨 6 个窗口、单窗口产出缩水、上下文耗尽导致半成品。
> 核心命题：**不是模型不够强，是上下文管理不够好。"更少但更精准的上下文"比"塞满整个窗口"更有效。**
> 流程：搜集 → 整理 → 挖掘 → 联系 → 批判 → 结合 → 应用。

## 一、搜集（搜了什么）

两路并行检索：
1. 上下文管理/长会话/分层记忆/checkpoint-resume/上下文压缩
2. token 效率/prompt 压缩/长任务规划/上下文窗口优化

核心来源（12 份）：
- **Adaptive Context Management**：pre-flight token 预算检查 + 分层压缩（近期原文/旧的摘要）+ 结构化思考+置信度 + 子 Agent 隔离上下文
- **Self-GC**（arXiv 2607.00692）：像垃圾回收一样管理上下文对象——fold/mask/prune，44% 裁剪率下 85% 无影响
- **Focus / Active Context Compression**（arXiv 2601.07190）：Agent 自主决定何时固化关键学习到持久 Knowledge 块，主动修剪原始历史（受黏菌启发）
- **Context Engineering 五层**：Budget → Supply（按需检索）→ Compress → Persist（文件系统记忆）→ Share（上下文总线）→ Debug（版本化）
- **70% 阈值共识**：上下文利用率超 70% 时触发压缩，在性能下降之前
- **Anthropic compaction**：上下文蒸馏成高保真摘要，保留最近 5 个访问的文件
- **Tool-result clearing**：清理可重新获取的旧工具结果，保留"调用发生过"的记录
- **ACON**：主动压缩算法，峰值 token 降 26-54%，无需参数更新
- **PAACE**（arXiv 2512.16970）：计划感知的上下文工程，next-k-task 相关性建模
- **Less Context, Better Agents**（arXiv 2606.10209）：驱逐策略——保留最近 N 条，驱逐的 W 条总结成一条
- **PRISM**（arXiv 2605.12260）：**13× 上下文缩减（26K→2K）+ 35pp 评判增益**——结构化候选+内容重排序
- **动态上下文组装**：声明预算从开始就工作，20-200 行函数索引比 2000 行文件好

## 二、整理（分类）

### 上下文管理五层

| 层 | 模式 | 目的 | 我们的现状 |
|---|---|---|---|
| Budget | 上下文窗口预算分配 | 有限 token 跨区域分配 | ❌ 无预算，用到耗尽 |
| Supply | 按需检索（JIT） | 需要时加载，不预先塞满 | ⚠️ 部分（红队盲读） |
| Compress | 压缩流水线 | 超预算区域收缩 | ❌ 无（耗尽才发现） |
| Persist | 文件系统记忆 | 无限状态外置到磁盘 | ⚠️ 2026-09-12.md 流水账 |
| Share | 上下文总线 | 跨 Agent 协调信息 | ❌ 靠提示词传递 |

### 压缩策略

| 策略 | 机制 | 适用场景 |
|---|---|---|
| 分层压缩 | 近期原文+旧的摘要 | 长对话 |
| 驱逐+摘要 | 保留最近 N 条，旧的 W 条合成摘要 | 工具输出密集 |
| 工具结果清理 | 删可重获取的结果，保留调用记录 | 多轮工具调用 |
| 主动固化 | Agent 自主决定何时把学习写入持久块 | 长任务 |
| 计划感知压缩 | 按 next-k-task 相关性决定保留什么 | 有明确计划的任务 |

## 三、挖掘（核心洞察）

**1. "更少上下文=更好 Agent"是实证结论，不是直觉**：PRISM 证明 13× 缩减（26K→2K tokens）同时带来 35pp 评判增益（0.48→0.83）。原因：长上下文里的噪声稀释了注意力，精准检索的少量相关信息比塞满整个窗口更有效。**映射到我们：Agent 会话里堆积的 git status、门禁输出、历史对话，大部分是噪声——清理后反而更聚焦。**

**2. 70% 阈值是行业共识**：不是"耗尽了才压缩"，是"利用率超 70% 就主动压缩"。我们现在是"上下文耗尽→报错→换窗口"，应该在 70% 时主动固化+压缩。

**3. 工具结果是最大的上下文污染源**：Claude 的 tool-result clearing 专门处理这个——工具输出（git status、编译日志、门禁结果）堆积如山，但大部分可重新获取。应该保留"调用发生过+关键结论"，删除原始输出。**映射到我们：每次门禁全跑的输出（replay 56/56、gate block=0 等）只需要结论行，不需要完整输出。**

**4. 分层记忆是长任务的基础**：工作记忆（当前窗口）→ 短期记忆（会话摘要，结构化）→ 长期记忆（知识库）。我们的 2026-09-12.md 是短期记忆，但**是流水账不是结构化摘要**——新 Agent 启动时读它要花大量 token 还找不到重点。

**5. 子 Agent 隔离上下文是最有效的策略**：每个子 Agent 在干净窗口里工作，不被主 Agent 的历史污染。我们的红队已经用独立子 Agent（正确），但**建设者本身的上下文没有管理**——建设者在一个窗口里从夹具写到卡层写到门禁，上下文越来越脏。

**6. Self-GC 的"无影响率"是核心 KPI**：裁剪后任务完成率不受影响的比例。Self-GC 做到 44% 裁剪率下 85% 无影响。这告诉我们：**上下文管理不是"尽量保留"，是"大胆裁剪+验证无影响"**。

**7. 计划感知压缩比通用压缩强**：PAACE 证明，知道"接下来要做什么"的压缩（保留和 next-k-task 相关的）比通用摘要好。**映射到我们：每批开始时有明确计划（夹具→卡→红队→门禁），压缩时应该保留和下一步相关的，删除已完成步骤的细节。**

## 四、联系（和我们系统的映射）

| 外部发现 | 我们的痛点 | 差距 |
|---|---|---|
| 70% 阈值压缩 | 上下文耗尽才换窗口 | 缺主动压缩 |
| 工具结果清理 | 门禁输出堆积 | 缺清理机制 |
| 分层记忆 | 2026-09-12.md 是流水账 | 缺结构化摘要 |
| 子 Agent 隔离 | 红队已隔离，建设者未隔离 | 建设者上下文脏 |
| 计划感知压缩 | 每批有明确计划但未用于压缩 | 缺计划-上下文联动 |
| PRISM 精准检索 | 全量塞入 | 缺按需检索 |

## 五、批判（哪些不适用/有局限）

1. **完整上下文工程框架对我们过度**：我们不是在开发 Agent runtime，是在使用现成的 Agent（CodeBuddy/Trae）。很多机制（pre-flight 检查、自动压缩）是 runtime 层面的，我们控制不了。**我们能做的是"提示词层面的上下文纪律"和"文件层面的记忆结构化"。**

2. **向量数据库长期记忆对我们过度**：我们的知识已经在 git 仓库里（原子/证据卡/误解），不需要额外的向量库。需要的是**更好的索引和检索**（380 知识图谱+按需读取），不是新的存储。

3. **自动压缩的质量风险**：LLM 生成的摘要可能丢失关键细节（比如"这个 sha 是改夹具后的新 sha"）。Self-GC 的 85% 无影响率意味着 15% 有影响——在我们的高严谨场景，15% 不可接受。**压缩必须保留"关键决策+未解决事项+具体数字"，不能只做通用摘要。**

4. **子 Agent 隔离增加协调成本**：每个子 Agent 干净窗口，但需要传递上下文。如果传递的上下文不够，子 Agent 会做错；如果传递太多，就失去了隔离的意义。**我们的红队提示词已经在做这个（P1-1 不给草稿全文），但建设者的子任务拆分还没有。**

## 六、结合（和已有架构的结合点）

**和 376 鲁棒性**：376 提了 checkpoint-resume，383 给出具体实现——checkpoint 不是"保存整个上下文"，是"保存结构化摘要+关键决策+未完成项"。

**和 379 自我进化**：379 的错误记忆分层（patterns/decisions/errors）就是 383 的"结构化短期记忆"的具体内容。

**和 380 知识图谱**：380 的图谱是"按需检索"的基础设施——Agent 不需要把所有原子读进上下文，需要时查图谱。

**和 381 评估**：上下文管理的 KPI（无影响率、token 缩减比、单窗口产出）加入 KPI 趋势线。

**和红队 P1-1**：P1-1（不给草稿全文，只给夹具/工件/actual）就是"子 Agent 上下文隔离+精准供给"的实例——已经在做，应该推广到建设者的子任务。

## 七、最终应用（分阶段落地）

### 立即落地（零成本，提示词/流程改进）

**应用 1：每批提示词加"上下文预算"段**
- 提示词开头声明：本批预计 X 轮，每轮上下文预算 Y token
- 每轮结束时输出"本轮关键结论+未完成项"（不超过 200 字）
- 这是"声明预算从开始就工作"的最小实现

**应用 2：2026-09-12.md 从流水账升级为结构化摘要**
- 分三段：①已完成（原子/卡/门禁结论）②未完成（具体缺口+下一步）③关键决策（人审裁决+方向反转）
- 每段不超过 500 字，具体数字（sha/读数）放引用链接不展开
- 新 Agent 启动时只读这个摘要，需要细节再查原文

**应用 3：工具输出清理规则**
- 门禁全跑输出：只保留结论行（replay confirm=56、gate block=0 等），删除完整逐卡输出
- git status：只保留"有什么未跟踪/已修改"，不保留完整文件列表
- 编译输出：只保留"成功/失败+错误行"，不保留完整警告

### 中期落地（需少量工程/提示词设计）

**应用 4：建设者子任务拆分（上下文隔离）**
- 一批 3 颗原子，不是一个 Agent 从头做到尾
- 拆成：夹具 Agent（只做夹具+实测）→ 卡层 Agent（只写卡，读夹具数据）→ 红队 Agent（独立盲读）→ 门禁 Agent（只跑门禁）
- 每个 Agent 干净窗口，靠结构化文件传递数据（夹具输出→卡→红队报告→门禁结果）
- 这是"子 Agent 隔离"的推广，直接解决"建设者上下文脏"

**应用 5：70% 阈值主动固化**
- 提示词里加："当你感觉上下文接近上限时，主动输出'固化摘要'（关键决策+未完成项+具体数字），然后请求新窗口"
- 不是等系统报错，是主动判断
- 固化摘要格式和应用 2 一致

### 长期落地

**应用 6：计划感知的上下文供给**
- 每批开始时生成计划（步骤1-6），每步只供给该步需要的文件
- 步骤 1（夹具）：只读 Examples/ 模板，不读证据卡
- 步骤 2（卡层）：只读夹具输出+证据卡模板，不读其他原子
- 步骤 3（红队）：只读夹具+工件+卡 actual（P1-1）
- 这是 PRISM"精准检索"的人工版

## 十、局限与后续

- 本调研聚焦上下文工程，未覆盖"多 Agent 间的上下文共享协议"（Context Bus）——当前靠文件传递，未来平台化（378）时需要正式的上下文总线。
- 自动压缩的质量风险（15% 有影响率）在高严谨场景不可接受，所以我们的压缩必须是"结构化摘要+人审关键项"，不能全自动。
- 子 Agent 拆分增加了协调成本和文件 I/O，需要先做 1 颗原子的 A/B 测试（单 Agent 从头做 vs 多 Agent 拆分），确认吞吐提升后再推广。
- 70% 阈值是经验值，不同模型（ds v4.1 flash vs hy4p）的上下文大小不同，需要按模型调整。
- 本调研未覆盖"prompt 本身的压缩"（怎么用更少的 token 写同样有效的提示词）——那是提示词工程的事，当前提示词已经比较精简，未来可以做一轮专门的 prompt 压缩。
