# 428 架构设计：406 数据新鲜度字段（原子会老，数据会过期）

> 日期：2026-09-13。来源：406 增量知识更新调研 + 422 消化。阙疑 27 颗原子的数据会随编译器/硬件/工具版本变化而过期，但目前没有任何机制标记"这颗原子的数据有多新鲜"。本文设计 data_freshness 字段 + 存量迁移 + 过期检测。

---

## 一、问题：原子会老，但没有标记

### 1.1 真实案例

- PERF-004 的 18.86× 是在 MinGW 15.3.0 上测的，换编译器/硬件可能变
- LEAK-002 的"LSan 零报告"是在 g++-14 -O1 上测的，加 volatile 计数器后变成报告
- ALLOC-002 的元数据读数是特定实现的，换 allocator 实现可能变

这些原子的 claim 方向是对的，但**具体数值可能过期**。目前卡内只有 artifact_compiler 字段，没有"这个数据多久需要重测"的标记。

### 1.2 不是所有原子都需要同等频率更新

| 数据类型 | 例子 | 老化速度 | 更新触发 |
|---|---|---|---|
| deterministic | sizeof、语法规则、ODR | 极慢（年级别） | 标准变更 |
| performance | 倍数、纳秒、缓存行大小 | 中（编译器/硬件升级） | 编译器大版本升级 |
| tool_observation | LSan 报不报、TSan 检测率 | 快（工具版本变） | sanitizer 升级 |

## 二、schema 设计

### 2.1 frontmatter 新增字段

```yaml
# atoms/*.md 新增
data_freshness: deterministic | performance | tool_observation
# 说明：
#   deterministic：数据由标准/语言定义，几乎不变（sizeof、语法、ODR）
#   performance：数据依赖编译器/硬件，需要定期重测（倍数、纳秒）
#   tool_observation：数据依赖工具版本，工具升级后可能变（LSan/TSan 观测）
```

### 2.2 证据卡新增字段

```yaml
# evidence/*/EV-*.md 新增
data_freshness: deterministic | performance | tool_observation
last_verified: "2026-09-12"  # 最后一次实测验证日期
compiler_versions: ["gcc-14.2", "gcc-13.3", "MinGW 15.3.0"]  # 实测过的编译器
```

### 2.3 加性原则

- 存量原子缺失 data_freshness 时，gate 给 warn（不 block）
- 新原子必须填 data_freshness（gate block）
- 过渡期：存量批量补标签后，warn 清零

## 三、存量 27 颗批量标注规则

### 3.1 自动标注规则

```python
def auto_label_freshness(atom):
    """
    根据原子的 claim 和 evidence 自动标注 data_freshness。
    规则：
    1. claim 含"倍数/×/ns/纳秒/周期/缓存行" → performance
    2. claim 含"LSan/TSan/ASan/检测/报告/零报告" → tool_observation
    3. evidence 含性能夹具（_perf.cpp） → performance
    4. evidence 含 sanitizer 观测 → tool_observation
    5. 其他 → deterministic
    """
```

### 3.2 预期标注结果（估算）

| 类型 | 数量 | 例子 |
|---|---|---|
| deterministic | ~12 | RAII、move、inline、ODR、UB |
| performance | ~8 | PERF-003/004、lock cost、false sharing |
| tool_observation | ~7 | LEAK-001/002、data race、sanitizer 边界 |

### 3.3 人工复核

自动标注后，人审抽查 5 颗确认无误。标注错误的修正后写入 `data/freshness_override.json`（覆盖自动标注）。

## 四、过期检测机制

### 4.1 gate 规则：ATOM-DATA-FRESHNESS（warn）

```python
def check_data_freshness(atom):
    """
    如果 data_freshness = performance 或 tool_observation，
    且 last_verified 超过阈值 → warn。
    
    阈值：
    - performance：last_verified > 180 天 → warn
    - tool_observation：last_verified > 90 天 → warn
    - deterministic：不检查（极慢老化）
    """
```

### 4.2 编译器升级检查清单

当编译器大版本升级时（如 gcc-14 → gcc-15），自动生成待重测列表：

```bash
python tools/freshness_check.py --compiler-upgrade gcc-14 gcc-15
# 输出所有 data_freshness=performance 的原子，建议重测
```

### 4.3 重测流程

```
1. freshness_check 列出待重测原子
2. 重跑夹具，生成新工件
3. 比对新旧 sha/读数
4. 如果读数变化 → 更新卡 + 原子版本号递增
5. 如果读数不变 → 更新 last_verified
```

## 五、与版本管理（406）的衔接

### 5.1 原子版本号

```yaml
version: 1.0.0  # SemVer
# major：claim 方向改变（如 pool 从"最省"变"最费"）
# minor：数据更新（如 18.86× → 8.78×）
# patch：文字修正（不改变结论）
```

### 5.2 freshness 触发版本递增

- performance 类重测后读数变化 → minor 版本递增
- tool_observation 类重测后结论变化 → minor 版本递增
- deterministic 类标准变更 → major 版本递增

## 八、元结论

**data_freshness 不是"更多元数据"，是"知识的保质期管理"。**

阙疑的知识是实测出来的，实测数据会过期。没有 freshness 标签，就不知道哪些原子需要重测、哪些可以信任。这与食品的保质期同理——不是所有食品都同时过期，需要分类管理。

**最反直觉的发现**：deterministic 类原子（sizeof、语法）占比最高（~45%），这些几乎不需要更新。真正需要频繁重测的是 performance（~30%）和 tool_observation（~25%）。这意味着"原子会老"是真的，但**只有一半需要定期维护**，不是全部。
