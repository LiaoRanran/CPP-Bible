# 385 数据飞轮与主动学习：让系统越用越强的核心机制

> 日期：2026-09-13。监工完成。这是 374-384 之后的架构升级轮，聚焦**数据飞轮**——379 提了经验→启发式但没深挖，这是"系统越用越强"的核心机制。
> 核心命题：**我们已经有数据飞轮的雏形（红队→毒样例、对抗→规则），但没有系统化。缺的是 Distill（从失败中自动提炼可复用知识）和 Improve（提示词版本管理+回归测试）。**
> 流程：搜集 → 整理 → 挖掘 → 联系 → 批判 → 结合 → 应用。

## 一、搜集（搜了什么）

两路并行检索：
1. 数据飞轮/主动学习/生产数据反馈闭环/错误挖掘
2. RLHF/Agent 自进化/生产轨迹/失败驱动训练

核心来源（12 份）：
- **Agent-in-the-Loop (AITL)**（arXiv 2510.06674）：Agent 自身纳入飞轮，四种标注集成到 live 操作：pairwise 偏好、采纳决策+理由、知识相关性、缺失知识
- **NVIDIA Data Flywheel Blueprint**：端到端自动化飞轮，集成 Curator/Customizer/Evaluator/Guardrails
- **AgentLoop（阿里云）**：两条路径——①数据驱动调优（BadCase→聚类→修复→回归）②轨迹驱动自进化（完整调用轨迹）
- **AgenticQwen**（arXiv 2604.21590）：双数据飞轮，第 k 轮任务作为第 k+1 轮更难任务的种子，闭环课程
- **Agent Learning Flywheel（Augment Code）**：Execute→Coach→Distill→Improve 四阶段，原子单元 triplet (task, trajectory, outcome)
- **Continuously Improving Agents**：量化"好"行为→可观测性→遥测转数据→失败聚类+根因→改进阶梯
- **Airbnb Data Flywheel**：捕获每次生产交互→评分→反馈训练，重训练周期数月→数周
- **Prompt versioning + eval**：提示词作为版本化制品，改前跑历史 traces 回归
- **SENTINEL**（arXiv 2606.12908）：失败驱动 RL——Controller 分析失败→总结 recurring patterns→Proposer 生成针对性任务→Solver 训练
- **RetroAgent**（arXiv 2603.08561）：回顾性双内在反馈，比较失败/成功轨迹的 token 级置信度
- **Hermes Agent（腾讯）**：两条进化路径——Skill 生成（"记笔记"）+ RL 训练（"练内功"）
- **LangChain trace loop**：trace 是改进起点——丰富 trace→识别失败模式→定向修改→验证发布

## 二、整理（分类）

### 数据飞轮四阶段（Agent Learning Flywheel）

| 阶段 | 做什么 | 产出 | 我们的现状 |
|---|---|---|---|
| Execute | 执行任务并记录轨迹 | triplet (task, trajectory, outcome) | ⚠️ 有最终报告，无结构化 trace |
| Coach | 评估+反馈 | 评分、失败标注、人审裁决 | ✅ 红队+门禁+人审 |
| Distill | 从轨迹中提炼可复用知识 | 规则、模板、毒样例、最佳实践 | ❌ 人工回填，无自动化 |
| Improve | 更新系统并验证 | 新版本提示词/规则/模板 | ⚠️ 规则在加，提示词无版本管理 |

### 失败驱动的两种模式

| 模式 | 机制 | 代表 |
|---|---|---|
| 被动收集 | 生产中自然产生的失败→聚类→修复 | Airbnb、AgentLoop Path 1 |
| 主动生成 | 分析失败模式→生成针对性任务→训练 | SENTINEL、AgenticQwen |

## 三、挖掘（核心洞察）

**1. 我们已经有飞轮的雏形，但卡在 Distill 阶段**：
- Execute：每批生产原子（有 task 和 outcome）
- Coach：红队+门禁+人审（有反馈）
- Distill：**缺**——红队报告里的"阻断模式"没有自动变成"下一批的重点检查项"；门禁的 warn 没有自动聚类成"规则改进建议"
- Improve：部分——gate 规则在加（33→42），但提示词（312 等）改了就改了，没有版本管理和回归测试

**2. SENTINEL 的"失败驱动"是红队的升级方向**：
- 当前红队是"通用检查清单"（can't-miss 10 条），每批都一样
- SENTINEL 是"分析上次失败→生成针对这些弱点的新任务"
- **映射：每批红队发现的阻断模式，应该自动变成下一批红队的"重点检查项"**——比如第五批红队抓了"口径不统一"，第六批红队就应该把"口径一致性"作为重点检查项，而不是每次都用同一个清单
- 这就是"主动学习"——不是被动等失败发生，是主动针对已知弱点施压

**3. Prompt versioning + eval 是我们缺的关键基础设施**：
- 我们的提示词（312、320、373 等）改了就改了，没有版本管理
- 改提示词后没有跑"历史生产 traces 的回归测试"——不知道新提示词会不会让之前能过的卡现在过不了
- **映射：每次改提示词，应该自动跑一遍历史 56 张卡的 replay，确认没有回归**。369 加了"数字止漂移"，但没有完整的提示词版本+eval 体系
- 这是"提示词作为代码"的理念——版本管理、回归测试、CI 门禁

**4. 原子单元 triplet (task, trajectory, outcome) 是数据飞轮的基础**：
- 我们的每颗原子生产都有 task（生产什么原子）、trajectory（夹具→卡→红队→门禁的完整过程）、outcome（verified/rejected）
- 但 trajectory 没有结构化记录——只有最终报告（"红队 3 阻断/15 高"），没有中间步骤的 trace（"红队第 2 轮发现了什么、第 3 轮修了什么"）
- **没有结构化 trace，就无法做失败聚类和根因分析**——只能靠人读报告总结

**5. 主动学习比被动收集更高效**：
- 被动收集：等生产中自然产生失败，可能等很久才遇到某个弱点
- 主动学习（SENTINEL）：分析已知弱点→生成针对性任务→立即验证
- **映射：我们的毒样例就是主动学习——不是等生产中出现逃逸，是主动构造逃逸样例来验证规则**。但毒样例目前是人工构造的，可以升级为"红队发现→自动生成毒样例候选"（382 应用2）

**6. Airbnb 的"重训练周期数月→数周"对应我们的"迭代周期"**：
- 我们不训练模型，但"提示词/规则/模板的迭代周期"可以从"每批人工总结"降到"自动收集+聚类+建议"
- 当前：每批结束后人读报告→总结教训→下一批提示词里加一条纪律（人工，跨窗口）
- 目标：每批结束后自动聚类失败模式→生成规则改进建议→人审后入库（半自动，当批完成）

## 四、联系（和我们系统的映射）

| 外部发现 | 我们的现状 | 差距 |
|---|---|---|
| Execute→Coach→Distill→Improve | Execute+Coach 有，Distill+Improve 缺 | 缺自动化提炼和版本管理 |
| SENTINEL 失败驱动 | 红队通用清单 | 缺"针对上次弱点的重点检查" |
| Prompt versioning+eval | 提示词改了就改了 | 缺版本管理和回归测试 |
| triplet (task,trajectory,outcome) | 有 task+outcome，trajectory 是流水账 | 缺结构化 trace |
| 主动学习（毒样例） | 人工构造毒样例 30 个 | 缺自动生成候选 |
| 失败聚类+根因 | 人工读报告总结 | 缺自动聚类 |

## 五、批判（哪些不适用/有局限）

1. **完整 RL 训练对我们不适用**：我们不训练模型权重（没有 GPU/数据/基础设施），Hermes 的"练内功"路径走不通。我们的"自进化"是**提示词/规则/模板层面的进化**，不是模型层面的。这是"记笔记"路径，不是"练内功"路径。

2. **生产 trace 的隐私/成本问题**：完整记录 Agent 的每步工具调用和输入输出，token 成本很高。我们不需要记录所有 trace，只需要记录**关键决策点**（claim 设计、红队阻断、人审裁决、方向反转）。

3. **自动聚类的质量风险**：失败模式聚类需要 LLM 理解"这两个失败是不是同一类"，可能聚类错误。**聚类结果必须人审，不能自动变成规则。** 我们的 gate 规则是"不智能但正确"的，自动聚类的结果如果直接入库可能引入错误规则。

4. **提示词回归测试的成本**：每次改提示词跑 56 张卡的 replay，时间成本高（双平台 replay 约 10-20 分钟）。**不是每次改提示词都跑全量，是跑"受影响的子集"**——比如改了红队提示词，只跑红队相关的毒样例，不跑全量 replay。

5. **主动学习可能"过拟合已知弱点"**：SENTINEL 针对已知弱点生成任务，可能忽略未知弱点。**主动学习和通用红队必须并行**——主动学习压已知弱点，通用红队找未知弱点。

## 六、结合（和已有架构的结合点）

**和 379 自我进化**：379 提了经验→启发式，385 给出具体实现——Distill 阶段就是"经验→启发式"的自动化。

**和 382 对抗**：382 应用2（红队报告自动生成毒样例候选）就是数据飞轮的一个实例。385 把它推广到所有失败类型（不只是红队逃逸，还有门禁 warn、人审驳回、方向反转）。

**和 381 评估**：数据飞轮的 KPI（失败模式聚类数、规则改进建议数、提示词版本数、回归测试通过率）加入 KPI 趋势线。

**和 383 上下文工程**：结构化 trace 是上下文管理的副产品——每轮结束的"固化摘要"就是 trace 的关键节点。

**和 gate 规则**：gate 规则是 Distill 的产出之一。数据飞轮让规则从"人工加"变成"自动建议+人审入库"。

## 七、最终应用（分阶段落地）

### 立即落地（零成本，流程改进）

**应用 1：每批结束的"失败模式聚类"段**
- 质检报告里加一段：本批所有阻断/高级/驳回，按模式聚类（如"口径不统一""断言恒真""工件不同代"）
- 每个聚类标注：出现次数、涉及原子、根因、建议改进方向
- 这是 Distill 的最小实现——人工聚类，但格式结构化

**应用 2：下一批红队的"重点检查项"来自上一批聚类**
- 红队提示词里加："本批重点检查项（来自上批失败聚类）：XXX"
- 通用 can't-miss 清单保留，重点检查项追加
- 这是 SENTINEL"失败驱动"的人工版

**应用 3：提示词版本管理**
- 提示词文件头部加 `version: vX.Y` 和 `changelog:` 段
- 每次改提示词，changelog 记录改了什么、为什么
- 这是"提示词作为代码"的最小实现

### 中期落地（需少量工程）

**应用 4：结构化 trace 记录**
- 每颗原子生产时，在 `docs/kernel/traces/` 下建一个文件：ATOM-XXX_trace.md
- 记录：task（生产什么）、关键决策点（claim 设计、夹具选择、红队阻断、人审裁决）、outcome（verified/rejected）
- 不记录完整工具输出（383 工具输出清理），只记录决策点
- 这是 triplet (task, trajectory, outcome) 的结构化实现

**应用 5：门禁 warn 自动聚类**
- gate 输出的 warn 按规则名+原子名聚类
- 同一规则命中多张卡 → 建议"这条规则可能需要收紧/豁免"
- 输出到 `docs/kernel/warn_clusters.md`，人审后决定是否改规则

### 长期落地

**应用 6：提示词回归测试**
- 每次改提示词，自动跑"受影响的毒样例子集"
- 改红队提示词→跑红队相关毒样例（P1-P10）
- 改生产提示词→跑最近 3 批原子的 replay
- 这是"提示词作为代码"的完整实现——版本管理+回归测试+CI 门禁

**应用 7：自动毒样例候选生成**
- 红队报告的每个"绕过成功"用例，自动生成毒样例模板（阴阳配对）
- 人审后入库（382 应用2）
- 这是主动学习的自动化——不是人工构造毒样例，是从对抗中自动生成

## 十、局限与后续

- 本调研聚焦数据飞轮，未覆盖"模型训练层面的自进化"（RL/RLHF）——我们不训练模型，只做提示词/规则/模板层面的进化。
- 自动聚类的质量风险（LLM 可能聚类错误）意味着 Distill 阶段必须人审，不能全自动——人从"做"变成"审"，但不能完全去掉。
- 结构化 trace（应用 4）增加了每批的文件数量，需要和 383 上下文工程配合——trace 只记录决策点，不记录完整输出。
- 提示词回归测试（应用 6）的成本较高，需要先做"受影响子集"的智能选择，不能每次跑全量。
- 数据飞轮的效果需要时间积累——前几批可能聚类不出有价值的模式（数据量不够），需要至少 5-10 批的数据才能看出趋势。
- 本调研未覆盖"成功案例的提炼"——当前聚焦失败案例（BadCase），但成功案例（"这颗原子为什么一次过门禁"）也有价值，可以提炼成"最佳实践模板"。未来可做一轮。
