## 1. 系统概述与目标

### 1.1 定义
「阙疑」是一个基于Curry-Howard同构的、法治的、有反馈回路的、自组织的知识证明助手系统。

### 1.2 核心抽象
- **原子（Atom）**：知识的最小可验证单元，含claim（命题）+证据（证明）+误解（反例）+教学（直觉/层级）
- **证据卡（Evidence Card）**：claim的可复现验证记录，含夹具（程序）+工件（运行输出/汇编）+断言（验证逻辑）
- **误解（Misconception）**：常见错误认知，含触发词+反例+关联原子
- **规则（Rule）**：机器可执行的质量检查，分block/warn/advice三级
- **铁律（Iron Law）**：人定的宪法级约束，不可被Agent修改

### 1.3 设计目标（按优先级）
1. **正确性**：每颗verified原子的claim在声明的适用范围内可复现（最高优先级）
2. **可追溯性**：每个结论都有可核对的证据链（夹具→工件→断言→replay结果）
3. **可扩展性**：原子数从20到1000时，系统性能/质量不退化
4. **自治性**：低风险知识（DAL C/D/E）可机器自治，人只监督高风险知识
5. **教学性**：原子不仅是"正确的知识"，还是"可学习的知识"（有直觉/误解/层级）

### 1.4 非目标
- 不做形式化证明（经验验证级，不追求数学级确定性）
- 不做通用知识库（专注C++编程知识）
- 不做实时问答系统（批处理生产，不是在线服务）
- 不替代人类专家（高风险知识仍需人审）

## 2. 核心原则（7条）

| # | 原则 | 一句话 | 违反后果 |
|---|---|---|---|
| 1 | Curry-Howard同构 | 命题=claim，证明=证据卡，程序=夹具 | claim不可证伪/证据与claim无关 |
| 2 | 系统科学 | 负反馈稳定质量，正反馈加速改进 | 反馈延迟过长/规则膨胀/循环不收敛 |
| 3 | 法治 | 规则约束Agent，铁律=宪法，gate=司法 | 规则只覆盖可形式化部分/规则追溯/规则规避 |
| 4 | 激励设计 | 提示词/门禁/铁律是激励，三权分立是博弈 | Goodhart定律/红队Writer合谋/激励错位 |
| 5 | 信息科学 | 本体/知识图谱/RAG/信息检索是技术基础 | 关系标注不全/检索与生产脱节/本体僵化 |
| 6 | 证伪主义 | claim可证伪，红队=证伪者，证据=证伪尝试 | 伪证伪/证伪不足/证伪过度/证伪不可复现 |
| 7 | 双环学习 | 单环=纠错，双环=改规则 | 只单环不双环/双环过度/学习遗忘/学习滞后 |

每条原则的实现路径/失败模式/验证方法见348。

## 3. 系统架构（六层）

```
┌─────────────────────────────────────────────────────────┐
│ 教学层：教材同步 / 学习路径 / 间隔重复 / 评估测试        │
├─────────────────────────────────────────────────────────┤
│ 性能层：流水线并行 / 增量验证 / 缓存层次 / 任务调度      │
├─────────────────────────────────────────────────────────┤
│ 数据层：原子 / 证据卡 / 误解 / 知识图谱 / 本体           │
├─────────────────────────────────────────────────────────┤
│ 工具层：replay / gate / golden_lock / poison / CI        │
├─────────────────────────────────────────────────────────┤
│ 机制层：三权分立 / 四级状态 / 反馈回路 / 红队制衡        │

│ 思想层：7原则 / 铁律 / 提示词宪法 / 术语本体             │
└─────────────────────────────────────────────────────────┘
```

### 3.1 层间依赖
- 上层依赖下层（教学层依赖数据层，数据层依赖工具层）
- 下层不依赖上层（工具层不需要知道教学层的存在）
- 跨层通信通过"数据契约"（见第4节），不通过函数调用

### 3.2 层内组件
- **思想层**：M1_ontology（术语本体）、铁律文档、提示词模板、can't-miss清单
- **机制层**：Writer/红队/Gatekeeper三角色、G6四级状态机、反馈回路（红队→修复→规则沉淀）
- **工具层**：atom_evidence_replay.py、gate_engine.py、golden_lock.py、poison_drill.py、ci_local_precheck.py
- **数据层**：atoms/、evidence/、misconceptions/、Examples/、golden_state.json
- **性能层**：ccache、WSL /tmp构建、增量replay、三级流水线
- **教学层**：Book/、学习路径生成、间隔重复卡片（待建）

## 4. 数据模型（形式化定义）

### 4.1 原子（Atom）Schema

```yaml
# 必填字段（ATOM_REQUIRED，缺一即gate block）
id: string                    # 格式：ATOM-{DOMAIN}-{TOPIC}-{NNN}，如ATOM-MEM-RAII-001
domain: string                # 16域之一（mem/conc/ub/...），须在M1_ontology中注册
topic: string                 # 主题词，如raii/lock/fence
type: string                  # 10类之一（mechanism/pitfall/contrast/...），须在M1_ontology中注册
title: string                 # 中文标题
claim: string                 # ≤50字，可证伪，单句
status: enum                  # draft / machine-verified / redteam-reviewed / verified
dal: enum                     # A/B/C/D/E（决策影响等级）
human_review: enum            # required / optional / waived（waived须有dal_reviewed_by）
relations:                    # 关系
  prereq: [string]            # 前置原子ID列表
  contrasts: [string]         # 对比原子ID列表
  serves: [string]            # 被哪些证据卡服务
pedagogy:
  misconception: [string]     # 关联误解ID列表
  level: enum                 # beginner / intermediate / advanced
status_history:               # 状态变更历史（G6规范）
  - {level: string, at: date, by: string}  # by必须带前缀machine:/redteam:/human:

# 条件必填
verified_by: string           # status=verified时必填，格式human:<name>
verified_at: date             # status=verified时必填
dal_reviewed_by: string       # human_review=waived时必填，格式human:<name>
rubric: integer               # 1-5分，status=verified时必填（人审授予）

# 选填
evidence_level: enum          # 1=确定性/2=统计性/3=外部引用/4=品格（阶段A1新增）
limitations: [string]         # 适用范围/边界条件
refutes: [string]             # 证伪了哪些常见误解
revision_history: [string]    # 修订记录
```

### 4.2 证据卡（Evidence Card）Schema

```yaml
# 必填字段（EV_REQUIRED，缺一即gate block）
id: string                    # 格式：EV-{DOMAIN}-{NNN}，如EV-MEM-001
serves: [string]              # 服务哪些原子ID
kind: enum                    # 判据卡/性能卡/对照卡/检测卡
verdict: enum                 # confirmed / refuted / infra_error
fixture: string               # 夹具路径（Examples/atoms/_atom_xxx.cpp）
command: string               # 复现命令（可直接复制执行）
artifact: string              # 工件路径（.asm或.out）
artifact_sha256: string       # 工件sha256（身份锚定）
artifact_compiler: string     # 编译器+版本+架构+优化档
actual:                       # 运行输出断言
  run_match: [string]         # 逐字匹配的行
  run_match_file: string      # （可选）从.out文件读取匹配
  run_match_keys: [string]    # （可选）匹配的key列表
  artifact_assert:            # 汇编断言
    - type: enum              # contains / contains_any / absent / contains_in / absent_in
      value: [string]         # 断言值
expected: string              # 预期结果描述
falsification: string         # 怎么证伪这张卡（含可复算数字）
matrix:                       # 多编译器矩阵
  compiler:                   # 编译器→结果映射
    "mingw-15.3": {verdict: confirmed, sha: "..."}
    "gcc-14.2": {verdict: confirmed, sha: "..."}
controlled_vars: [string]     # 控制变量列表（唯一变量是什么）

# 条件必填
expected_sanitizer: [enum]    # 夹具含真泄漏/真数据竞争时必填（[leak]/[thread]）
evidence_level: enum          # 阶段A1新增：1=确定性/2=统计性/3=外部引用

# 选填
limitations: [string]
refutes: [string]
revision_history: [string]
```

### 4.3 误解（Misconception）Schema

```yaml
id: string                    # 格式：MIS-{DOMAIN}-{NNN}，如MIS-MEM-001（扁平命名，不建子目录）
domain: string
title: string
trigger_words: [string]       # 触发词列表
description: string           # 误解描述
counterexamples:              # 反例列表（≥3条）
  - {claim: string, evidence: string, ref_atom: string}
related_atoms: [string]       # 关联原子ID
severity: enum                # shallow / deep（deep级须有≥3条反例）
```

### 4.4 关系（Relation）语义

| 关系类型 | 语义 | 传递性 | 对称性 |
|---|---|---|---|
| prereq | A是B的前置知识（学B前先学A） | 是 | 否 |
| contrasts | A与B形成对比（相似但有关键差异） | 否 | 是 |
| serves | 证据卡E服务原子A | 否 | 否 |
| related | 泛化关联（无明确语义） | 否 | 是 |

## 5. 状态机与生产流程

### 5.1 原子四级状态机（G6）

```
draft ──(Writer完成+门禁预检)──> machine-verified
  │                                  │
  │                                  ├──(红队阻断)──> draft（回退，附阻断报告）
  │                                  │
  │                                  └──(红队通过)──> redteam-reviewed
  │                                                       │
  │                                                       ├──(人审拒绝)──> draft（回退，附人审意见）
  │                                                       │
  │                                                       └──(人审签署)──> verified
  │
  └──(任何状态发现严重错误)──> draft（强制回退）
```

**状态转换规则**：
- 每次转换必须记录status_history（{level, at, by}）
- by必须带前缀：machine:<工具名> / redteam:<agent名> / human:<人名>
- verified状态只能由human签署进入
- verified状态发现错误→强制回退draft（须有人审或gate block触发）

### 5.2 单颗原子生产流程（8步）

```
Step 1: 选题与claim设计（≤50字，可证伪，前提/推论明确）
Step 2: 夹具设计（唯一变量/活性对照/反例对照/有界循环）
Step 3: 双平台工件（Windows .asm + WSL .asm/.out，sha锚定）
Step 4: 证据卡撰写（≥2张，actual只锚常量+活性对照，断言候选在Linux工件grep验证）
Step 5: 误解撰写（≥1条，3反例）
Step 6: 红队审查（独立子agent，两段式盲读，错误预测≥3，阻断≤2轮修复）
Step 7: 原子草稿+门禁预检（gate block=0/replay confirm/poison/pytest）
Step 8: 原子化（move+签署+golden_lock sync+全量复算+WSL预检+分离提交）
```

### 5.3 批次生产流程（三级流水线）

```
批次N:   Writer生产 ──> 红队审查 ──> 门禁验证 ──> 提交
批次N+1:            Writer生产 ──> 红队审查 ──> 门禁验证 ──> 提交
批次N+2:                       Writer生产 ──> 红队审查 ──> 门禁验证 ──> 提交
```
（阶段B5实现，当前是串行）

## 6. 多Agent协调协议

### 6.1 角色定义

| 角色 | 职责 | 工具 | 激励 |
|---|---|---|---|
| Writer | 生产原子/证据卡/误解/夹具 | 编辑器/编译器/replay | 产出质量（返工率低） |
| 红队 | 独立审查，找错误 | 编辑器/grep/工件分析 | 错误预测命中率高 |
| Gatekeeper | 执行机器规则，block/warn | gate_engine/replay/poison | 规则执行准确（误报率低） |
| 人审 | 高风险知识签署+规则进化监督 | 编辑器/git | 决策质量（漏审率低） |

### 6.2 通信协议

- **Writer→红队**：交付物清单（原子草稿路径+证据卡路径+夹具路径+工件sha），**不含卡的自述**（红队两段式盲读，先读夹具/工件）
- **红队→Writer**：阻断报告（每条含prediction/verification_action/verification_result/impact/evidence），按severity分级
- **Writer→Gatekeeper**：变更文件列表+预期门禁结果
- **Gatekeeper→Writer**：gate报告（block/warn/advice，每条含规则ID+fix_hint）
- **任何人→人审**：人审请求（含claim/红队处置/门禁结果/人审问题清单）
- **人审→任何人**：签署/拒绝+意见

### 6.3 冲突解决

- Writer与红队冲突（红队说有错，Writer说没错）→ 以工件/实测为准（不是以谁说得为准），仍无法解决→人审裁决
- Gate规则与实际冲突（规则报block但实际没问题）→ 标记为"规则误报"，记录到规则修订史，临时加豁免（不删规则）
- 人审与机器冲突（人审说通过但gate报block）→ gate block优先（法治原则），人审可以要求修订规则但不能绕过规则

### 6.4 红队独立性保证

- 红队是独立子agent（与Writer不同的会话/上下文）
- 红队两段式盲读：先只读夹具源码+工件（不读卡），形成独立判断，再对照卡
- 红队提示词与Writer提示词分离（红队用"对抗性提示词"，Writer用"建设性提示词"）
- 长期目标：红队与Writer用不同模型（减少同质盲区，阶段C2）

## 7. 安全模型与边界

### 7.1 Agent权限边界

| 操作 | Writer | 红队 | Gatekeeper | 人审 |
|---|---|---|---|---|
| 创建/修改原子草稿 | ✅ | ❌ | ❌ | ❌ |
| 创建/修改证据卡 | ✅ | ❌ | ❌ | ❌ |
| 创建/修改夹具 | ✅ | ❌ | ❌ | ❌ |
| 移动原子到atoms/（原子化） | ❌ | ❌ | ❌ | ✅（或授权Agent） |
| 修改frontmatter的verified字段 | ❌ | ❌ | ❌ | ✅ |
| 修改gate_engine.py规则 | ❌ | ❌ | ❌ | ✅ |
| 修改铁律 | ❌ | ❌ | ❌ | ✅ |
| 执行git push | ❌ | ❌ | ❌ | ✅（用户明确授权） |
| 读取任何文件 | ✅ | ✅ | ✅ | ✅ |
| 执行编译器/replay/gate | ✅ | ✅ | ✅ | ✅ |

### 7.2 数据完整性

- 所有verified原子的frontmatter有verified_by+verified_at（不可被Agent修改）
- 证据卡的artifact_sha256锚定工件身份（改工件→sha不匹配→replay refute）
- git历史记录所有变更（可回溯）
- golden_lock sync检查关系一致性（原子引用的证据卡必须存在）

### 7.3 恶意输入防御

- 夹具代码在沙箱内编译运行（不访问网络/不修改系统文件）
- replay的command字段只执行白名单内的命令（g++/python3，不执行任意shell）
- 证据卡的actual字段不执行代码（只做字符串匹配）
- 红队报告不直接写入原子（必须经Writer修改+Gate验证）

### 7.4 灾难恢复

- git仓库是唯一真相源（任何本地文件损坏都可以从git恢复）
- 每周自动备份到远端（GitHub origin）
- golden_state.json每次sync前自动备份（.bak）
- 原子化前必须有git commit（可回退）

## 8. 可观测性体系

### 8.1 指标分类

| 类别 | 指标 | 采集方式 | 目标 |
|---|---|---|---|
| 质量 | gate block数 | gate_engine | =0 |
| 质量 | replay confirm率 | replay | 100% |
| 质量 | 红队错误预测命中率 | redteam_metrics | ≥70% |
| 质量 | 强证伪比例 | redteam_metrics | ≥20% |
| 效率 | 单原子生产轮数 | 批次报告 | 持续下降 |
| 效率 | Writer返工率 | redteam_metrics | 持续下降 |
| 效率 | replay单次耗时 | 计时 | ≤30s（ccache后） |
| 规模 | 原子数 | golden_lock | 持续增长 |
| 规模 | 证据卡数 | golden_lock | 持续增长 |
| 规模 | 规则数 | gate_engine --list | 持续增长 |
| 规则健康 | 规则命中率 | gate扫描统计 | ≥5次/规则 |
| 规则健康 | 规则误报率 | 人工标注 | <10% |
| 自治 | 人审干预率 | 批次报告 | 持续下降 |
| 自治 | DAL C/D/E机器自治率 | golden_lock | 持续上升 |

### 8.2 日志规范

- 每个工具执行输出结构化日志（JSON Lines），含timestamp/tool/input/output/duration
- 红队报告含完整的阻断列表+验证动作+结果
- 批次报告含所有指标的"本批值/累计值/趋势"
- 日志保留在docs/目录，不写入原子/证据卡

### 8.3 告警规则

- gate block>0 → 立即告警（阻断级）
- replay refute>0 → 立即告警（阻断级）
- 红队命中率连续2批<70% → warn（提示修订红队提示词）
- 规则命中率<5次 → warn（提示规则可能过窄/过时）
- 单原子生产轮数>5 → warn（提示流程可能有瓶颈）
- WSL预检失败>0 → 立即告警

## 9. 版本化与兼容性策略

### 9.1 Schema版本化

- 原子/证据卡/误解的frontmatter schema有版本号（schema_version字段）
- 不兼容变更（如新增必填字段）→ schema_version+1，提供迁移脚本
- 兼容变更（如新增选填字段）→ schema_version不变，旧文件自动兼容
- golden_state.json有schema_version

### 9.2 工具接口版本化

- 工具的命令行接口（CLI）稳定，不兼容变更须先deprecate（两个版本周期后删除）
- 工具的输出格式（JSON/Markdown）有版本号
- 新增工具必须同步到tools/cppbible.py的cmd_check元组（META-MANIFEST规则）

### 9.3 原子版本化

- 原子的重大修订（claim方向改变）→ 新增revision_history条目，不覆盖旧claim
- 原子的minor修订（错别字/格式）→ 直接修改，git历史记录
- 原子的废弃（claim被证伪）→ 不删除，标记为deprecated，新增superseded_by字段指向替代原子

### 9.4 向后兼容承诺

- verified原子的claim不被静默修改（任何修改必须经过人审+修订记录）
- 证据卡的artifact_sha256不被覆盖（改工件→新sha→更新卡，旧sha保留在修订记录中）
- 旧版本的提示词保留在References/中（不删除，供回溯）

## 10. 成本模型与性能预算

### 10.1 单原子成本（当前）

| 成本项 | 估算 | 说明 |
|---|---|---|
| Writer生产 | 2-3轮Agent工作 | 夹具+证据卡+误解+草稿 |
| 红队审查 | 1轮独立子agent | 两段式盲读+报告 |
| 修复循环 | 0-2轮 | 红队阻断后的修复 |
| 门禁验证 | 5-10分钟 | replay+gate+poison+pytest+WSL预检 |
| 人审 | 5-15分钟 | 人审签署 |
| **总计** | **4-6轮Agent+15-30分钟人审** | |

### 10.2 性能预算（阶段A目标）

| 操作 | 当前 | 目标 | 手段 |
|---|---|---|---|
| replay单次（全量50卡） | ~2分钟 | ≤30秒 | ccache+增量replay |
| gate全库扫描 | ~10秒 | ≤10秒（已达标） | — |
| poison演练 | ~5秒 | ≤5秒（已达标） | — |
| WSL预检（31步） | ~5分钟 | ≤2分钟 | 并行化+缓存 |
| 单原子生产轮数 | 4-6轮 | ≤3轮 | Writer自检前置+证据卡瘦身 |

### 10.3 成本优化优先级

1. ccache（编译加速，小工作量，等授权）
2. 增量replay（只重跑变更的卡，中工作量）
3. Writer自检前置（减少返工，中工作量）
4. 证据卡三层分离（减少卡的维护成本，中工作量）
5. 三级流水线（吞吐提升，大工作量）

## 11. 扩展性设计

### 11.1 规模扩展路径

| 原子数 | 瓶颈 | 应对 |
|---|---|---|
| 20-50 | 无明显瓶颈 | 当前架构可支撑 |
| 50-100 | 全量replay变慢 | 增量replay+ccache |
| 100-200 | 关键词检索不够用 | 知识图谱+GraphRAG |
| 200-500 | 人审成为瓶颈 | DAL降级+机器自治 |
| 500-1000 | 单仓库文件数过大 | 按域分目录+子模块 |
| 1000+ | 单Agent生产太慢 | 多Agent并行+自动生产 |

### 11.2 域扩展

- 新域（如CONC）只需：①在M1_ontology注册域 ②新建atoms/{domain}/evidence/{domain}/目录 ③误解用扁平命名MIS-{DOMAIN}-{NNN}
- 不需要修改gate_engine（DOMAINS列表已预注册16域）
- 新域的首批原子需要"前置勘察"（如307的CONC域前置勘察）

### 11.3 水平扩展（多Agent）

- Writer可以多实例并行（不同原子/不同域）
- 红队可以多实例并行（不同原子的审查独立）
- Gatekeeper是单实例（规则执行是确定性的，不需要并行）
- 冲突解决：多Writer同时修改同一文件→git merge冲突→人审裁决

## 12. 人机交互设计

### 12.1 人审流程

1. **人审请求**：Agent提交人审包，含：
   - 原子claim（单句）
   - 红队处置摘要（阻断数/高级数/建议数/关键阻断）
   - 门禁结果（replay/gate/poison/pytest）
   - 人审问题清单（2-3个关键决策点）
   - 自评分数（rubric_self，人审可调整）

2. **人审决策**：
   - 通过→签署（verified_by+verified_at+rubric）
   - 拒绝→附意见，回退draft
   - 有条件通过→签署但附"待办"（如"Linux侧锚待CI回填"）

3. **人审效率优化**：
   - 人审包控制在1页内（关键信息前置，细节放链接）
   - DAL C/D/E可以"批量签署"（一次签多颗）
   - 人审历史可检索（之前签过的类似原子）

### 12.2 监工交互

- 监工（用户）通过自然语言指令驱动系统（"继续调研"/"写提示词"/"推进第五批"）
- 系统主动报告：进度/阻断/待决策项/风险预警
- 监工可以随时打断/改方向/加约束
- 所有决策记录在记忆文件（.codebuddy/memory/）和批次报告中

## 13. 伦理与知识边界

### 13.1 知识局限性声明

- 每颗原子的limitations字段必须声明：
  - 适用范围（编译器/架构/优化档/标准版本）
  - 不适用的场景
  - 已知的反例/例外
- 经验验证级的知识不冒充"形式化证明级"
- 平台相关的结论（如性能倍数）必须标注"本平台实测，其他平台可能不同"

### 13.2 误导性知识处理

- 发现verified原子的claim有误→立即回退draft（不保留verified状态）
- 标记为deprecated的原子不删除（保留历史，供学习"曾经错在哪里"）
- 常见误解（MIS-*）是"教学素材"，不是"正确知识"——必须明确标注为误解

### 13.3 引用与归属

- 外部引用（论文/commit/标准条文）必须标注来源（URL/DOI/commit hash）
- 借鉴其他项目的设计（如证明助手/知识图谱）必须在架构文档中注明
- 不抄袭他人的代码/文本（夹具/证据卡/原子正文必须原创）

### 13.4 不做的事

- 不生产无法验证的知识（如"最佳实践"类价值判断，除非有可观测推论）
- 不生产危险知识（如漏洞利用代码，除非是防御性教学且有明确限制）
- 不替代官方文档（标准条文以ISO/IEC为准，「阙疑」只做教学性解释）
- 不对用户的代码做安全审计（「阙疑」是知识生产系统，不是代码审计工具）

## 14. 失败模式与恢复策略

### 14.1 系统级失败模式

| 失败模式 | 触发条件 | 影响 | 恢复策略 |
|---|---|---|---|
| 级联错误 | 一颗原子的错误导致多个依赖原子错误 | 高 | prereq链回溯，从源头修复 |
| 规则膨胀 | 规则数量过多，维护成本上升 | 中 | 规则分层+命中率监控+低命中规则降级 |
| 红队失职 | 红队抓不到真实错误（同质盲区/提示词退化） | 高 | 错误预测命中率监控+多模型红队+毒样例 |
| Writer偷懒 | Writer生产低质量原子（格式合规但内容空洞） | 高 | 红队两段式盲读+证据等级检查+Writer评分 |
| 门禁误报 | gate规则误报block，阻塞正常生产 | 中 | 规则误报率监控+豁免机制+规则修订 |
| 工件损坏 | .asm/.out文件损坏/丢失 | 中 | sha锚定+从夹具重新生成+git备份 |
| 环境漂移 | 编译器升级导致断言失效（如gcc-14事件） | 中 | contains_any跨编译器断言+双平台验证+CI矩阵 |
| 上下文耗尽 | Agent单轮上下文不够，任务中断 | 中 | 分层记忆+任务拆分+续作机制 |
| git冲突 | 多Agent并行导致merge冲突 | 低 | 按域/按文件分工+人审裁决 |
| 数据丢失 | 本地文件损坏/误删 | 低 | git仓库+远端备份+golden_lock备份 |

### 14.2 已知的环境边界（永久限制）

- MinGW无TSan（cannot find -ltsan）→ TSan只作WSL/CI列
- riscv64-unknown-elf-g++无<atomic>头→用__atomic_*内建
- Windows replay与WSL预检不能并行（同写Examples/*.asm）
- ccache两环境皆无（等授权安装）
- pytest两环境无模块（仅CI可跑）

### 14.3 恢复优先级

1. 数据完整性（git仓库/golden_state）——最高优先级
2. 门禁正确性（gate/replay不被绕过）——高
3. 生产连续性（未完成的批次可续作）——中
4. 性能（replay/CI速度）——低

## 附录B：术语表

- **原子（Atom）**：知识的最小可验证单元
- **证据卡（Evidence Card）**：claim的可复现验证记录
- **夹具（Fixture）**：产生证据的C++程序
- **工件（Artifact）**：夹具的编译/运行产物（.asm/.out）
- **红队（Red Team）**：独立审查Agent，主动找错误
- **门禁（Gate）**：gate_engine.py，机器规则执行
- **毒样例（Poison）**：故意写错的卡，用于验证规则能抓住错误
- **DAL（Decision Impact Level）**：决策影响等级，A/B/C/D/E
- **replay**：atom_evidence_replay.py，证据卡复现验证
- **golden_lock**：黄金锁，关系台账与状态基线
