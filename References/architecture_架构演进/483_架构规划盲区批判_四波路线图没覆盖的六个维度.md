# 483 架构规划盲区批判：四波路线图没覆盖的六个维度

> 生成时间：2026-09-14
> 批判对象：474-482 的全部架构规划
> 结论：四波路线图覆盖了"做什么"，但有六个维度完全没碰或只碰了皮毛

---

## 盲区一：成本/Token 经济学（用户最关心但系统最忽视）

### 现状

用户反复说"烧多少 token 一点不浪费"，但：
- cost_tracker.py 存在（430 批次做的），但没有被整合进任何决策流程
- 没有每颗原子的 token 消耗基线（430 做了 27 颗基线 5765 tok/颗，但没有持续追踪）
- 没有每轮红队/对抗的 token 消耗统计
- 没有"这颗原子花了多少 token、值不值"的 ROI 评估
- 级联路由（478）提了，但只是初步想法，没有具体的成本阈值和路由规则

### 问题

系统在"质量"维度有大量门禁（51 规则/61 毒样例/56 卡双平台 confirm），但在"成本"维度是零门禁。Agent 可以无限烧 token，系统不会报警。

### 改法：成本门禁

1. **每颗原子的成本上限**：根据域/类型/复杂度设定 token 预算（如 beginner 机制原子 ≤8000 tok，advanced 性能原子 ≤20000 tok）
2. **超预算报警**：Writer 生产过程中 token 消耗超过预算的 80% → warn，超过 100% → block（需要人审批追加预算）
3. **ROI 评估**：每颗原子完成后，自动计算"token 消耗 / 教学价值"（教学价值 = 误解数 × 证据卡数 × 断言数）
4. **成本趋势追踪**：每批次的平均 token 消耗，趋势上升 → 分析原因（是卡膨胀了？还是红队更严了？）
5. **级联路由正式化**：任务难度分类 → 机械任务用苦力 → 验证不通过才升级。成本差 10-100×，必须系统化。

### 具体工具

- `tools/cost_gate.py`：成本门禁，检查每颗原子的 token 消耗是否超预算
- `tools/cost_roi.py`：ROI 评估，生成每批次的成本报告
- 接入 Writer 自检层和 CI

## 盲区二：多模型协作（用户已经在人工做，但系统没正式化）

### 现状

用户已经在人工做多模型协作：
- 苦力（便宜模型）：干杂活、修复、提交
- 好模型（ds v4.1 flash）：落地系统基线、复杂架构
- 对抗模型（Seed-Evolving/Trae/混元）：红队对抗

但系统里没有正式的多模型协作机制：
- 没有任务难度分类标准
- 没有"什么任务该给谁"的路由规则
- 没有模型能力评估（哪个模型擅长什么）
- 没有多模型结果对比和融合
- 没有"便宜模型做不好自动升级"的机制

### 问题

全靠人判断"这个任务该给谁"，人的判断不一定准，而且不可复用。

### 改法：模型市场（Model Marketplace）

1. **模型能力档案**：每个模型有能力档案（擅长什么、不擅长什么、成本、速度）
2. **任务难度分类**：机械/语义/创造三级，每级有明确的判定标准
3. **路由规则**：
   - 机械任务（改字段、补测试、跑门禁）→ 苦力
   - 语义任务（写卡、改 claim、红队）→ 苦力→验证→不通过升级
   - 创造任务（新工具、新范式、架构设计）→ 直接好模型
4. **结果融合**：多个模型对同一任务的结果，可以对比和融合
5. **模型能力回溯**：记录每个模型的任务成功率，动态调整路由

### 具体工具

- `docs/kernel/model_marketplace.md`：模型能力档案和路由规则
- `tools/model_router.py`：任务难度分类和路由建议（不自动路由，只给建议）

## 盲区三：系统自进化（从错误中自动学习）

### 现状

482 的预测性模块和数据飞轮提了自进化，但只是初步想法。实际情况：
- 每次红队发现的问题都靠人记下来、写成规则
- 没有"红队发现→规则候选→毒样例"的自动化管道
- 没有提示词版本管理和回归测试（改了提示词后，用历史案例验证没退化）
- 没有错误模式库（历史错误的结构化记录）

### 问题

系统的进化完全依赖人的记忆和手动操作。人忘了记，教训就丢了；人记错了，规则就写错了。

### 改法：数据飞轮四阶段自动化

**Produce（生产）**：已有（Writer 生成原子）

**Coach（评估+反馈）**：已有（红队+门禁+人审）

**Distill（提炼）**：缺，需要自动化
- 红队报告自动解析 → 提取错误类型、根因、修复方式
- 错误类型匹配现有规则 → 如果没有对应规则，生成规则候选
- 规则候选自动生成毒样例草稿
- 人审核后入库

**Improve（改进）**：缺，需要自动化
- 提示词版本管理（每次改提示词都记录 diff）
- 提示词回归测试（用历史案例验证改了之后没退化）
- 规则效果追踪（新规则上线后，命中了多少次、误报了多少次）

### 具体工具

- `tools/error_pattern_miner.py`：从红队报告和门禁失败中自动挖掘错误模式
- `tools/rule_candidate_generator.py`：从错误模式自动生成规则候选和毒样例草稿
- `tools/prompt_regression.py`：提示词版本管理和回归测试

## 盲区四：可观测性（系统运行时的黑盒）

### 现状

- 只有 metrics_snapshot.py（快照指标）和 gen_metrics.py（生成指标）
- 没有结构化的 trace 日志（每次 Agent 操作的详细记录）
- 没有实时监控（系统当前在做什么、进度如何）
- 没有告警（什么东西坏了、什么时候坏的）
- worklog 是人工写的 markdown，不是结构化数据

### 问题

系统运行时是黑盒。出了问题只能靠人翻 worklog 和 git log 找原因。没有"系统现在健康吗"的实时视图。

### 改法：结构化 trace + 健康看板

1. **结构化 trace 日志**（JSONL 格式）：
   - 每次 Agent 操作记录：时间、操作类型、输入、输出、耗时、token 消耗
   - 每次门禁运行记录：规则命中、失败项、耗时
   - 每次 replay 运行记录：卡名、结果、耗时、编译耗时
2. **健康看板**（`tools/health_dashboard.py`）：
   - 系统当前状态：门禁绿/红、replay confirm 数、待处理问题数
   - 趋势图：规则数、毒样例数、原子数、replay 耗时、token 消耗
   - 告警：门禁红了、replay confirm 下降了、token 消耗异常
3. **告警规则**：
   - 门禁红 → 立即告警
   - replay confirm 下降 → 告警
   - 单卡 replay 耗时 >30s → 告警（性能退化）
   - token 消耗超预算 → 告警

### 具体工具

- `tools/trace_logger.py`：结构化 trace 日志（JSONL）
- `tools/health_dashboard.py`：健康看板（生成 HTML 或 markdown 报告）
- `tools/alert_check.py`：告警检查（接入 CI）

## 盲区五：知识冲突与版本管理（知识会变，但系统不会处理）

### 现状

- 415 加了 contradicts/conflicts_with 关系类型，但没有冲突解决机制
- 原子的 claim 可以被新证据推翻，但没有"retracted"状态（只有 draft/verified）
- 证据卡有修订记录，但没有版本管理（哪版断言对应哪版工件）
- 夹具改了，工件重生成了，但旧的证据卡可能还引用旧工件
- 100+ 份架构文档，哪些是最新的？哪些过时了？没有文档生命周期管理

### 问题

知识是会变的（新编译器版本、新标准、新证据），但系统没有处理知识变更的机制。一颗 verified 原子的 claim 被新证据推翻了，系统不会自动标记。

### 改法：知识版本管理

1. **原子状态扩展**：draft → machine-verified → human-verified → verified → **superseded**（被取代）/ **retracted**（被推翻）
2. **claim 版本管理**：claim 每次修改都记录 diff，旧版本不删除
3. **证据-工件版本绑定**：证据卡的断言绑定到具体的工件 sha，工件变了 → 卡标记 stale
4. **冲突检测**：两颗原子的 claim 矛盾 → 自动标记，人审解决
5. **文档生命周期**：架构文档有版本号、最后更新时间、状态（active/deprecated/archived）

### 具体工具

- `tools/knowledge_version.py`：知识版本管理（claim diff、工件绑定、stale 检测）
- `tools/conflict_detector.py`：知识冲突检测（claim 矛盾自动标记）
- `tools/doc_lifecycle.py`：文档生命周期管理（479 的 doc_lint 扩展）

## 盲区六：人的因素与认知偏差（单人项目的最大风险）

### 现状

- 单人项目，没有 code review
- 所有决策都是一个人做的（用户+Agent）
- 人的认知偏差（确认偏误、锚定效应、沉没成本）没有机制性防护
- "认可权唯人"是对的，但人也会犯错
- 红队是独立 Agent，但红队的结果还是要人来裁决

### 问题

系统的最终瓶颈是人。人会犯错、会疲劳、会有偏见。如果人的判断错了，系统不会纠正。

### 改法：决策质量保障

1. **重要决策必须有书面理由**：人审签署时必须写理由（为什么通过、为什么拒绝），不能只签个名
2. **决策回溯**：3 个月后回溯之前的决策，评估决策质量（当时的理由是否成立、结果是否符合预期）
3. **异议机制**：红队的发现如果被人驳回，必须记录驳回理由，6 个月后重新评估
4. **预注册**：重要实验（如红队对抗）的预期结果先写下来，实验后对比，防止"我早就知道"的后见之明偏差
5. **外部审计**：定期（每季度）找外部的人/模型审计系统，不依赖内部判断

### 具体工具

- `docs/kernel/decision_log.md`：决策日志（重要决策的理由和回溯）
- `tools/decision_audit.py`：决策回溯（定期评估决策质量）
- 红队提示词中增加"预注册"要求

## 六、六个盲区的优先级

| 盲区 | 严重度 | 成本 | 优先级 | 理由 |
|---|---|---|---|---|
| 成本/Token 经济学 | 极高 | 低 | P0 | 用户最关心，零成本高 ROI |
| 系统自进化 | 高 | 中 | P0 | 从"人监工"到"系统自学习"的关键 |
| 可观测性 | 高 | 中 | P1 | 出问题能快速定位 |
| 多模型协作 | 中 | 低 | P1 | 用户已经在人工做，正式化即可 |
| 知识冲突与版本管理 | 中 | 中 | P2 | 原子数多了之后才会凸显 |
| 人的因素 | 高 | 零 | P2 | 机制性防护，但需要人配合 |

## 七、和四波路线图的关系

这六个盲区不是第四波之后的"第五波"，而是**贯穿所有波次的横向维度**：

- 成本门禁应该在第一波就接入（否则后面的波次都在烧钱）
- 可观测性应该在第二波接入（工具多了之后需要监控）
- 系统自进化应该在第三波接入（规则多了之后需要自动修剪）
- 多模型协作应该在第一波就正式化（否则路由靠人）
- 知识版本管理应该在第二波接入（数据模型统一时一起做）
- 人的因素应该贯穿始终（零成本，只改流程）

四波路线图是"纵向"的（按时间顺序），这六个维度是"横向"的（每一波都要考虑）。完整的架构规划 = 四波 × 六维度。

## 八、结论

四波路线图（478/480/481/482）回答了"做什么"，但没回答：
- 花多少钱做？（成本）
- 谁来做？（多模型）
- 做完怎么知道变好没？（可观测性）
- 下次怎么不犯同样的错？（自进化）
- 知识变了怎么办？（版本管理）
- 人判断错了怎么办？（认知偏差）

这六个维度不补，四波路线图执行到一半就会遇到瓶颈：成本失控、黑盒排障、重复犯错、知识混乱。

**建议**：把这六个维度作为横向约束，补入 476 架构计划，每一波的每项任务都要考虑这六个维度。
