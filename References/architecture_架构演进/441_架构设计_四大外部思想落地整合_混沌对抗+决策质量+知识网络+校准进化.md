# 441 架构设计：四大外部思想的落地整合（混沌对抗 + 决策质量 + 知识网络 + 校准进化）

> 日期：2026-09-13。基于 440 的四个方向外部调研，设计阙疑的架构改进。核心：用混沌工程形式化对抗，用决策科学提升人审质量，用知识管理强化原子库连接，用元认知训练系统校准能力。

---

## 一、P1：混沌工程形式化对抗（稳态假设 + 故障分级 + 持续自动化）

### 1.1 对抗前的稳态定义

每次对抗前，必须先定义"稳态"：

```yaml
# 对抗前的稳态快照（自动生成）
steady_state:
  gate:
    rules: 42
    block: 0
    warn: 32
  replay:
    confirm: 56
    refute: 0
    infra_error: 0
  poison: 39/39
  pytest: 135 passed
  atoms: 27
  evidence: 56
  golden_lock: clean
```

**假设**："在注入攻击用例后，稳态指标不会恶化超过阈值。"

### 1.2 故障注入分级

| 级别 | 攻击范围 | 对应阙疑 |
|---|---|---|
| L1 单条规则逃逸 | 只攻击一条 gate 规则 | 毒样例 P1-P33 |
| L2 组合攻击 | 多条规则的组合绕过 | 402 的 F02（声明-实现+编译后覆写） |
| L3 全系统渗透 | 从卡到工具到 CI 的完整攻击链 | 402 的 F01（cl 免检链，从卡到 replay 到 gate） |
| L4 架构级攻击 | 攻击架构设计本身的逻辑漏洞 | 373 的"建设者自执行"身份冲突 |

**对抗应该从 L1 开始，验证 L1 全绿后再升级到 L2，以此类推。** 这就是混沌工程的"最小爆炸半径"。

### 1.3 自动停止条件

对抗中如果出现以下情况，自动停止并回滚：
- gate block > 0（不是 warn，是 block）
- replay confirm 下降 >5
- 任何工具崩溃（exit code 非预期）
- 工作树被污染（未授权文件被修改）

### 1.4 持续对抗（CI 集成）

不是"送一次对抗就完事"，而是：
- 每次提交自动跑 L1（毒样例）——已经在做（poison_drill）
- 每周自动跑 L2（组合攻击用例库）——419 攻击用例库
- 每月自动跑 L3（全系统渗透）——v8.0
- 每季度人工跑 L4（架构级攻击）——v9.0

### 1.5 gate 规则：ADVERSARY-STEADY-STATE（advice）

对抗报告必须包含：
- 对抗前的稳态快照
- 对抗后的稳态对比
- 哪些指标恶化了，哪些没有
- 否则 advice（对抗报告不完整）

## 二、P1：决策质量检查（人审签署的六要素 + 认知偏差对策）

### 2.1 人审签署前的检查清单

每个人审签署前，必须检查六要素：

```yaml
# 人审签署记录（human_review 字段扩展）
human_review:
  required: true  # DAL A/B
  reviewed_by: human:liaoranran
  reviewed_at: "2026-09-13"
  decision_quality:
    frame: "问题定义正确：这颗原子要证明什么？"  # 1. 合适的框架
    alternatives: "考虑了 2 个备选 claim 方向"  # 2. 创造性的备选方案
    information: "证据来自 2 张证据卡 + 双平台实测"  # 3. 相关可靠的信息
    values: "DAL A，错误后果=学生学到错误知识"  # 4. 清晰的价值观和权衡
    reasoning: "claim 逻辑自洽，falsification 可证伪"  # 5. 合理的推理
    commitment: "签署后进入 verified 状态"  # 6. 承诺行动
  cognitive_bias_check:
    confirmation_bias: "红队独立盲读，未读 Writer 卡"  # 确认偏误
    overconfidence: "自评 4/5，红队发现 2 高级，已修"  # 过度自信
    premature_closure: "红队要求替代解释 ≥1，已提供"  # 过早关闭
```

### 2.2 决策记录

每个人审签署必须记录"为什么签"，不只是签名：
- 这颗原子的核心 claim 是什么？
- 证据是否充分？
- 有没有未解决的疑问？
- 签署后预期会发生什么？

### 2.3 "魔鬼代言人"制度化

红队就是"魔鬼代言人"，但应该更正式：
- 红队有"否决权"吗？当前没有（红队只给建议，Writer 可以不采纳）
- 建议：红队的"阻断"级发现必须修复或明确驳回（附理由），不能忽略
- 这已经在做（铁律 2：宁可只交付到卡层，不压缩红队走过场），但应该写进规范

### 2.4 gate 规则：HUMAN-REVIEW-QUALITY（warn）

DAL A/B 的原子，human_review 字段必须包含 decision_quality 和 cognitive_bias_check，否则 warn。

## 三、P2：知识网络健康度（原子性 + 连接性 + 孤岛检测）

### 3.1 原子性检查

每张原子卡应该只讲一个概念。gate 规则：ATOM-ATOMICITY（warn）
- claim 中如果有"且"连接的两个独立断言，warn
- 例如："false sharing 会导致性能下降，且 padding 可以解决" = 两个断言，应该拆成两颗或用 contrasts

### 3.2 连接性检查

每张原子卡至少有 1 个 relation。gate 规则：ATOM-MIN-RELATIONS（warn）
- relations 为空 = 孤岛，warn
- 建议：每张卡至少有 1 个 prerequisite 或 1 个 contrasts

### 3.3 知识网络健康度指标

```yaml
# 知识网络健康度（gen_metrics.py 扩展）
knowledge_graph:
  total_atoms: 27
  total_relations: 45
  avg_relations_per_atom: 1.67  # 连接密度
  isolated_atoms: 2  # 孤岛数（0 relation）
  max_relations: 5  # 中心节点的连接数
  hub_atoms: ["ATOM-MEM-RAII-001"]  # 枢纽节点（≥3 relation）
  longest_path: 4  # 最长依赖链
  domain_coverage:  # 各域的原子数
    mem: 18
    conc: 3
    lang: 1
    ub: 3
    hist: 2
```

### 3.4 枢纽笔记（Hub Notes）

每个域有一个"枢纽卡"，汇总该域的所有原子：
- `atoms/mem/_HUB.md`：MEM 域的索引，列出所有 MEM 原子 + 关系图
- 学生可以从枢纽卡进入，沿 relations 遍历
- 这是 Zettelkasten 的"枢纽笔记"实践

### 3.5 反向链接

relations 是单向的（A prerequisite B），但应该能从 B 看到"谁依赖我"：
- 425 上游依赖遍历已经在做这个
- 建议：每张卡的底部自动生成"被以下卡引用"列表（静态生成，不进 frontmatter）

## 四、P2：校准训练（自评 vs 红队 + 过度自信检测 + 元认知日志）

### 4.1 校准指标

每次红队后，计算 Writer 自评 vs 红队评分的差异：

```yaml
# 校准记录（每批次自动生成）
calibration:
  batch: "第五批 MEM"
  atoms: 3
  writer_self_eval:
    avg: 4.0  # Writer 自评平均分
    distribution: [4, 4, 4]
  redteam_eval:
    blockers: 3  # 红队发现的阻断数
    high: 28  # 高级数
    suggestions: 18  # 建议数
  calibration_score: 0.6  # 0-1，1=完全校准
  # 计算方法：自评 5/5 但有阻断 = 0；自评 3/5 且无阻断 = 0.8
  overconfident_atoms: 2  # 自评 ≥4 但红队发现阻断
  underconfident_atoms: 0  # 自评 ≤3 但红队零阻断
```

### 4.2 过度自信检测

如果 Writer 持续自评过高（calibration_score < 0.5 连续 2 批）：
- 给 Writer 反馈："你的自评持续高于红队评分，请降低自评或增加自检"
- 自动增加红队的严格度（更多 can't-miss 检查项）
- 这是元认知的"监控-控制循环"

### 4.3 元认知日志

每次批次结束后，记录"我们以为会怎样 vs 实际怎样"：

```yaml
# 元认知日志（docs/kernel/metacognition_log.md）
- batch: "第五批 MEM"
  expected: "3 颗原子，2 轮完成，红队 0 阻断"
  actual: "3 颗原子，6 轮完成，红队 3 阻断（全部方向反转级）"
  gap_analysis: "低估了元数据口径不统一的影响；夹具设计缺乏因果推断框架"
  lesson: "性能/机制卡必须先做口径统一检查，再写 claim"
  action: "写入 437 夹具方法论 v2.0"
```

### 4.4 "不知道"的价值

系统应该能说"我不知道"：
- MSVC 永久边界："MSVC 不可用，不尝试"
- 性能数据波动："同机跨运行波动 2×，不锚倍数"
- 工具行为不确定："此规则在跨编译器路径下未验证"

gate 规则：HONEST-UNCERTAINTY（advice）
- 卡中如果有"不确定"的声明，必须明确标注，不能写成确定结论
- 例如："LSan 零报告"应该写成"LSan 在本夹具本档位下零报告，不代表没有泄漏"
