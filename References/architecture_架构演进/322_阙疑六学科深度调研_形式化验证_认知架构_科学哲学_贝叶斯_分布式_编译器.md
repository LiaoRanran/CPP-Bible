## 一、形式化验证：从经验证据到机器检查证明

### 1.1 领域现状（2026）

**Lean 4 成为主流**：
- 2026-09-04，Anthropic 发布费马大定理的完整 Lean 4 证明——**1300 万行**，史上最大 Lean 证明
- OpenProver：开源 LLM 驱动定理证明，Planner-Worker-Verifier 架构
- Mathlib：>210,000 条定理，数学深度领先（流形、李群、表示论）

**C++ 形式化语义**：
- 剑桥 Peter Sewell 团队：CHERI C Memory Model（CPP 2025），已形式化 C 的内存模型
- 无锁队列验证策略：Model Checking（TLA+/Spin，穷举有限状态）+ Theorem Proving（Coq/Isabelle，处理无限状态）+ Static Analysis+SMT（CBMC/KLEE，规模化）

**Vericoding 工作流**：
- 开发者写函数签名 + 规格（pre/post 条件）→ 写实现 → 调用验证器 → LLM 辅助消除验证条件
- Dafny：前置/后置条件和循环不变量直接集成到代码语法

### 1.2 对「阙疑」的映射

**分层验证体系**（318 的 L1→L2→L3 具体化）：

| 层级 | 方法 | 适用原子 | 成本 |
|---|---|---|---|
| L1 经验证据 | 夹具 + replay（当前） | 全部 | 低 |
| L2 标准条文 | ISO C++ 标准引用 | 全部 | 低 |
| L3 形式化证明 | TLA+ 模型检查 / Lean 证明 | DAL A/B 级 | 高 |

**CONC 域特别适合形式化**：
- 内存序、无锁数据结构的 claim 可以用 TLA+ 做模型检查（穷举线程交错）
- 比"运行时观察"更强：运行时只能看到一次执行，模型检查能看到所有可能的执行
- 落地：CONC-001（屏障与消除）可以加一个 TLA+ 规格作为 L3 证据

**Vericoding 映射**：
- Writer 写 claim（=规格）→ 写夹具（=实现）→ replay 验证（=验证器）→ 红队辅助消除问题（=LLM 辅助）
- 我们的流程已经是 vericoding 的雏形，只是验证器是 replay 而非定理证明器

### 1.3 落地优先级

- P2：为 CONC 域高 DAL 原子加 TLA+ 模型检查（1-2 颗试点）
- P3：探索 Lean 4 对关键 claim 的形式化证明（长期）

## 二、认知架构：从工具到通用智能

### 2.1 核心理论

**SOAR**（State, Operator, And Result）：
- **问题空间假说**：所有任务表示为问题空间，算子变换状态
- **僵局→子目标→chunking**：遇到无法解决的僵局时，创建子目标解决；解决后将成功路径编译为新的产生式规则（学习）
- 最新版本 9.6.5，支持 Python/Java/C# 绑定

**ACT-R**（Adaptive Control of Thought — Rational）：
- **程序性记忆**：产生式规则（"如果-那么"），存在中央执行器
- **陈述性记忆**：知识块，带**激活值**（使用频率越高、越近，激活值越高）
- 中央模块用**效用计算**仲裁竞争规则
- 四大模块：Goal / Memory / Perception / Motor

**Standard Model of the Mind**：跨 SOAR/ACT-R/Sigma 的共识框架

**NL2GenSym**（2025）：用 LLM 自动为 SOAR 生成符号规则——解决手工编码规则的瓶颈

### 2.2 对「阙疑」的映射

**SOAR 的 chunking = 我们的规则沉淀**：
- 僵局（红队阻断）→ 子目标（修复任务）→ 沉淀为规则/毒样例（chunking）
- 我们已经在做这个，但可以更系统化：每批结束时自动生成"本批新产生式规则"（不只是 warn 数）

**ACT-R 的激活值 = 原子健康度**（321 的间隔重复升级）：
- 原子的"激活值" = f(使用频率, 最近使用时间, 证据强度)
- 激活值低于阈值的原子 → 自动触发复习（replay 复跑）
- 高激活值原子 → 可以作为"核心原子"（hub），在知识图谱中优先引用

**缺失的"程序性记忆"**：
- 目前我们只有**陈述性知识**（原子=事实），没有**程序性知识**（"如何做"的产生式规则）
- 可以建立 `playbooks/` 目录：常见任务的标准执行流程
  - `playbooks/produce_atom.md`：如何生产一颗原子（8 步）
  - `playbooks/redteam_review.md`：如何做红队审查
  - `playbooks/ci_failure_diagnosis.md`：如何诊断 CI 失败
- 这些 playbook 就是 Agent 的"产生式规则"，比提示词更结构化、可复用

**LLM 作为规则生成器**：
- NL2GenSym 的思路：LLM 可以自动从自然语言生成符号规则
- 我们的提示词本质上是在为 Agent 生成"产生式规则"——可以更系统化地管理这些规则

## 三、科学哲学：「阙疑」是进步还是退化的研究纲领？

### 3.1 核心理论

**波普尔**：证伪主义
- 科学 = 可证伪，验证是神话
- 一个反例就能证伪（但实际上有辅助假设）
- 越容易被证伪的理论越好（信息量大）

**库恩**：范式革命
- 科学不是渐进积累，而是革命性断裂
- 范式不可通约（不同范式的"事实"不同）

**拉卡托斯**：科学研究纲领（综合波普尔和库恩）
- **硬核**（hard core）：基本假设，方法论决策保护其不受证伪
- **保护带**（protective belt）：辅助假设，吸收经验压力，可以修改
- **正面启发法**（positive heuristic）：指导研究方向
- **进步的纲领**：不断预测新事实且被证实
- **退化的纲领**：只解释已有事实，不预测新事实

**费耶阿本德**：怎么都行（anything goes）
- 每个方法论规则都曾被有效违反
- 不要让方法论变成教条

### 3.2 对「阙疑」的映射

**「阙疑」的硬核**（不可放弃）：
1. 三权分立（Writer/红队/Gatekeeper 分离）
2. 证据可复现（replay 机制）
3. claim 可证伪（冒险预测标准）
4. 人审是最终权威（DAL A/B 必须人签）

**「阙疑」的保护带**（可以修改）：
- 具体的 gate 规则（33→36 条）
- 提示词结构（312 v1→v3.1）
- 工具实现（replay 二值→三分类）
- 证据卡格式（actual → run_match_file）

**判断进步/退化的标准**：
- **进步信号**：每批产出新原子（新事实）、红队抓出的问题被升级为规则（预测新问题）、工具能力扩展（contains_in/absent_in）
- **退化信号**：只修旧问题不产出新原子、规则只增不减且 warn 持续上升、同一类问题反复出现
- **当前状态**：进步——每批都有新原子 + 新规则 + 新工具能力

**费耶阿本德的提醒**：
- 不要让"铁律"变成教条——每条规则都应该有"被有效违反"的记录
- 例如："红队必须两段式盲读"——如果某颗原子的夹具极其简单（10 行），盲读的价值很低，可以跳过
- 建立"规则例外登记"：什么时候违反了哪条规则、为什么、结果如何

## 四、贝叶斯决策论：从二值判决到置信度

### 4.1 核心理论

**"Agentic AI orchestration should be Bayes-consistent"**（arXiv 2605.00742）：
- **可靠性加权更新**：不同来源的证据有不同可靠性参数，弱证据不导致过度自信的后验
- **依赖感知的证据池化**：同一模型的多次提示不是独立证据，需要保守池化
- **先验选择**影响后验

**UniCR**（arXiv 2509.01455）：
- 将异质不确定性证据（序列似然、自一致性分散度、检索兼容性、工具反馈）转化为校准的正确概率
- 用 conformal risk control 提供无分布保证

**贝叶斯自升级**（arXiv 2608.24087）：
- Agent 知道何时该求助：置信度低于阈值时自动升级到人审
- 有有限样本保证：regret = O(L·sqrt(log K/(nT)))

**LLM 信念更新的贝叶斯一致性**（arXiv 2507.17951）：
- BCC（Bayesian Consistency Coefficient）随模型规模增大而提高
- 大模型的信念更新更符合贝叶斯定理

### 4.2 对「阙疑」的映射

**证据卡从二值到置信度**：
- 当前：confirm / refute（二值）
- 升级：每条证据有**可靠性权重**（基于历史表现）
  - 双平台 confirm 的证据 > 单平台 confirm
  - 有活性对照的证据 > 纯存在性断言
  - 新夹具的证据 > 复用夹具的证据
- claim 的置信度 = 所有支持证据的加权后验
- 新证据出现时，贝叶斯更新置信度

**红队/Writer 可靠性动态更新**：
- 红队抓出真问题（被修复验证）的频率 → 红队可靠性
- Writer 产出一次过红队的频率 → Writer 可靠性
- 可靠性高的角色的意见权重高

**依赖感知**：
- 同一夹具的两张证据卡不是独立的（共享工件），不能简单叠加
- 同一模型的两次红队审查不是独立的（共享上下文），需要保守池化
- 落地：证据卡增加 `independence` 字段（independent / shared_fixture / shared_model）

**贝叶斯自升级 = DAL 分级的理论基础**：
- DAL A/B：置信度要求高（>95%），必须人审
- DAL C/D/E：置信度要求较低（>80%），机器审查可豁免
- 当 claim 置信度低于阈值时，自动升级到人审

## 五、分布式系统：多 Agent 协作的一致性保证

### 5.1 核心理论

**CAP/PACELC**：
- CAP：分区时选一致性或可用性
- PACELC：正常时选延迟或一致性
- 现代系统：按实体粒度做 C/A 权衡

**CRDT**（无冲突复制数据类型）：
- 去中心化、分区容忍、无锁、自动冲突解决
- 操作可交换（commutative），最终收敛

**Hashgraph 多模型共识**（arXiv 2505.03553）：
- 每个模型作为 peer，gossip-about-gossip + 虚拟投票
- 用于多模型推理结果的收敛

### 5.2 对「阙疑」的映射

**当前是强一致性模型**：
- Writer→红队→Gatekeeper→人审，全部达成一致才能推进
- 保证质量但牺牲速度（吞吐下降的根因之一）

**引入最终一致性**：
- Writer 可以先产出草稿（AP，高可用）
- 红队异步审查，发现问题后回滚/修复
- 只有原子化（verified）时才需要强一致性（CP）

**golden_lock 作为共识机制**：
- 当前：所有原子/证据卡的状态必须达成一致
- 可以用 CRDT 思路：status 变迁是单调的（draft→redteam→verified），不会冲突
- frontmatter 字段设计为可交换操作（如 `verified_at` 只设一次）

**多 Agent 并行的冲突解决**：
- 当两个 Agent 同时修改同一文件时，用 git merge（当前方案）
- 可以升级为 CRDT：frontmatter 的每个字段是独立的 LWW-Register（Last-Writer-Wins）
- 但这需要工具支持，优先级低

## 六、编译器 IR 与静态分析：replay 的升级方向

### 6.1 核心理论

**LLVM IR 生态**：
- SVF：指针分析（Andersen、流敏感、上下文敏感）
- SAF：Rust 框架 + Python SDK，将 LLVM IR 转为可分析图
- SeaHorn：基于 LLVM 的软件验证器

**抽象解释**（Abstract Interpretation, Cousot 1977）：
- 基于 Galois 连接，在抽象域上计算，保证**可靠性**（无误报/无假阴性）
- 三级精度：语法分析（快/粗）→ 语义分析（中）→ 形式化分析（慢/精）

**翻译验证**（Translation Validation）：
- 每次优化后验证优化后的程序与原始等价
- Peggy 工具：LLVM 编译器的翻译验证

**ML 引导的编译器优化**：
- Google 已在生产环境使用（Chrome Android、Fuchsia、云基础设施）
- 用于内联决策和寄存器分配

### 6.2 对「阙疑」的映射

**replay 的三层验证升级**：

| 层 | 当前 | 升级 |
|---|---|---|
| L1 运行时 | 编译+运行+比对输出 | ✅ 已有 |
| L2 静态分析 | 无 | 加 LLVM IR 指针分析/数据流分析 |
| L3 形式化 | 无 | 加抽象解释/翻译验证 |

**CONC 域特别需要静态分析**：
- 数据竞争检测：用 ThreadSanitizer（运行时）+ 静态数据竞争检测（LLVM ThreadSafetyAnalysis）
- 内存序验证：用 cppmem（C/C++11 内存模型的探索工具）
- 无锁算法验证：用 TLA+ 模型检查

**抽象解释的应用**：
- 验证 claim 的不变量是否在**所有**执行路径上成立（不只是一次运行）
- 例如："unique_ptr 转移后源为空"——抽象解释可以验证所有路径上源都为空，而不只是测试路径

**翻译验证的应用**：
- 确认 -O0 和 -O2 的工件在语义上等价（如果 claim 说"优化不改变行为"）
- 当前我们只看 .asm 差异，翻译验证可以给出"等价/不等价"的机器检查结论

## 九、一句话总结

321 为「阙疑」提供了**四学科理论基础**（机制设计/信息论/控制论/学习科学），322 扩展到**六学科深度调研**（形式化验证/认知架构/科学哲学/贝叶斯/分布式/编译器）——现在「阙疑」的架构有了**十一个学科的理论支撑**，从"工程实践"升级为"跨学科认知系统"。

**最关键的三个洞察**：
1. **SOAR 的 chunking** 完美解释了我们的"红队→规则"沉淀机制，可以更系统化
2. **拉卡托斯的研究纲领** 提供了判断「阙疑」是进步还是退化的标准——不只是看产出量，要看"新事实预测率"
3. **贝叶斯置信度** 可以将二值的 confirm/refute 升级为量化的不确定性，为 DAL 分级提供理论基础
