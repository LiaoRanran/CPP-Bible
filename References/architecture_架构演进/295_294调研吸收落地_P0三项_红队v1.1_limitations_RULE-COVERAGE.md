## P0-1：红队提示词 v1.1（军事红队 ACH + 两段式盲读）

### 变更点（相对 v1.0）

1. **每条阻断必须配「替代解释」**（军事红队 ACH 核心原则）
   - 红队不能只说「这里有问题」，必须给出「如果不是 Writer 说的那样，还可能是什么解释」
   - 格式：`阻断描述 → 替代解释（至少 1 个）→ 验证动作（如何区分）`
   - 来源：CIA Tradecraft Primer 的 ACH（Analysis of Competing Hypotheses）——不是找支持首选假设的证据，而是找「哪个假设被证据排除」

2. **两段式盲读强化**（P1-1 升级）
   - **第一段（盲读）**：只读夹具源码 + 工件（.asm/.out），不读证据卡、不读原子草稿、不读 Writer 的任何自述
   - 输出：你从夹具和工件中独立观察到了什么？claim 可能是什么？有什么可疑之处？
   - **第二段（对照）**：才读证据卡 actual 和原子 claim，对比第一段的独立观察
   - 输出：卡的自述与你的独立观察是否一致？哪里有 gap？
   - 来源：294 军事红队「制度性独立」+ ALLOC-002 实证（盲读夹具才发现口径不统一）

3. **can't-miss 清单补三条**（来自本批实测）
   - **派生重复读数**：两个指标是同一个 bit 的不同表述（如 cycle_is_leak ≡ dtor_count==0）——一 bit 两计
   - **编译期折叠常量冒充活性观测**：actual 中大量行是编译期常量（asm 里 mov 立即数），对运行时变量零响应
   - **载体口径不同变**：对照组的变量在栈、实验组在堆（或反之），「唯一变量」不成立

### 红队提示词 v1.1 全文（可投喂）

```
你是 G5 原子生产流水线的红队（RedTeamer）。你的任务不是「找错」，而是「测试共识能否存活挑战」——军事红队原则：红队不是为了对，而是为了测试 Writer 的 claim 能否经受住独立验证。

## 铁律
1. 两段式盲读：第一段只读夹具源码 + 工件（.asm/.out），不读证据卡、不读原子草稿、不读 Writer 自述。输出你的独立观察。第二段才读卡和 claim，做对照。
2. 每条阻断必须配「替代解释」：格式为「阻断描述 → 替代解释（至少1个）→ 验证动作」。只攻击不提出替代假设=半工作。
3. 修复循环≤2轮，超限升级人审。
4. 不给草稿全文（P1-1）：你只拿到夹具路径、工件路径、证据卡路径，自己去读。

## can't-miss 清单（每条必查）
- [ ] 口径不统一：不同策略的「元数据」「大小」是否用同一口径计算？（ALLOC-002 教训）
- [ ] 消除与失败不可区分：dtor=0 是「泄漏」还是「分配被编译器消除」？加 volatile 构造计数验证（LEAK-001/002 教训）
- [ ] 自证断言：夹具自定义 operator new/delete + 断言只做存在性匹配 → 命中定义处即通过（UNIQUE-002 教训）
- [ ] 派生重复读数：两个指标是否同一 bit 的不同表述？（LEAK-002 教训）
- [ ] 编译期折叠常量冒充活性观测：actual 中的行是否是编译期常量（asm 里 mov 立即数）？（ALLOC-002 教训）
- [ ] 载体口径不同变：对照组和实验组的变量是否在不同存储位置（栈/堆）？（PERF-004 教训）
- [ ] 对照被值类别污染：「传右值0拷贝 vs 传左值1拷贝」只反映实参类别，与目标变量无关
- [ ] 恒真观测：actual 只有存在性判断（!= nullptr 等），对关键变量零响应
- [ ] 基数不一致：比值的分子分母是否来自同一轮同一排序？（PERF-003 教训）
- [ ] 与既有证据实质重复：去 rglob 查同主题的已有原子/证据卡，是否已覆盖？
```

## P0-2：证据卡 limitations 字段规范（密码学 ROM「已知为假但实用」）

### 设计原则

- **并存模式**：limitations 是可选附加字段，不影响 atom_evidence_replay.py 的解析（replay 不读此字段）
- **人类可读**：limitations 是给人审和后续维护者看的，声明「这张卡的断言锚有什么局限」
- **来源**：密码学随机预言机模型（ROM）——「已知为假但实用」，显式声明模型局限比假装完美诚实

### 字段格式

```yaml
limitations: |
  1. 断言锚只锚方向（sharing_is_slower=1），不锚倍数（18.86×）——同机跨运行可波动 2×+
  2. 性能数据来自 MinGW 15.3.0 / WSL g++-14，libc++/MSVC 未实测
  3. 4 线程 × 1e7 次 fetch_add，线程数不同时倍数可能变化
```

### 何时必须写 limitations

- 性能/基准类证据卡（PERF-*）——倍数、纳秒数必然平台相关
- 多编译器声明但只有单平台工件的卡——显式声明哪些编译器未实测
- 断言锚经过「收窄」的卡（如 PERF-003 从锚倍数收窄到锚方向）——说明为什么收窄
- sanitizer 相关卡——声明 LSan/ASan 的可达性局限

### 何时可以不写

- 纯判据类卡（输出是确定性的 0/1、计数、地址比较）——无平台依赖
- 编译期断言（static_assert）——编译器无关

### 与现有 42 张卡的兼容

- 现有卡不加 limitations 不报错（字段可选）
- 新卡（从第五批起）建议加，但非强制
- gate_engine 暂不加检查规则（避免一次性 churn 42 张卡），后续可加 EV-LIMITATIONS-DECLARED 规则（warn 级）
