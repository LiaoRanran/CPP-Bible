# 413 阙疑错误分类与自动修复：哪些能机器修、哪些必须人审

> 日期：2026-09-13。外部调研：SelfHeal 统一错误分类（F1-F4 + 23 种修复模式）、SWE-bench 自动修复（AutoCodeRover 38.4%→v2.1 51.6%，$0.65/issue）、修复验证（复现测试红变绿+原有测试无新失败）、反思循环（生成→批判→重试，批判比生成容易）、重试契约（瞬时错误分类+指数退避+熔断器+幂等性）。
> 研究问题（411 SOP）：阙疑的红队发现和门禁告警如何自动分类？哪些错误可以自动修复？修复质量如何保证？

---

## 一、阙疑的错误分类（E1-E6，适配版）

行业分类是 runtime bug，阙疑是知识生产的质量问题。重新映射：

| 类别 | 子类 | 阙疑实例 | 出现频率 | 可自动修复 |
|---|---|---|---|---|
| **E1 形式错误** | frontmatter 缺字段、ID 格式错、断言语法错 | ATOM-ID-FORMAT block、EV-REQUIRED 缺字段 | 高 | ✅ 高 |
| **E2 工件错误** | 工件与断言不同代、sha 不匹配、.out 缺失 | 第五批 G2 缺陷1（工件旧 sha） | 中 | ✅ 中 |
| **E3 断言错误** | 断言恒真、字面量不在工件中、跨编译器未实测 | PERF-004 红队阻断1/2、EV-MEM-017 _Znwm/_Znwy | 中 | ⚠️ 低 |
| **E4 内容错误** | claim 方向反、口径不统一、与证据矛盾 | ALLOC-002 "pool 32B 最省"、LEAK-002 "零报告" | 低但严重 | ❌ 需红队/人审 |
| **E5 流程错误** | 跳过红队、未原子化就提交、push 未授权 | 铁律拦截 | 低 | ✅ 高（已拦） |
| **E6 环境错误** | 编译器缺失、网络阻断、WSL 不可用 | cl 崩溃、push 网络阻断 | 中 | ✅ 中（已分流） |

### 关键洞察
- **E1/E2/E5/E6 是机械错误**——可以自动检测+自动修复
- **E3/E4 是语义错误**——需要判断和推理，不能自动修复
- 第五批跨 6 个窗口的根因：E4 内容错误（ALLOC-002 方向反转、LEAK-002 观测反转）占了大部分时间，这是不能加速的部分
- 但 E1/E2 类错误也消耗了不少时间（工件不同代、断言字面量没实测），这些可以自动化

## 二、可自动修复 vs 不可自动修复的边界

### 可自动修复（机械类，零判断）

| 错误 | 修复方法 | 验证方法 |
|---|---|---|
| E1 frontmatter 缺字段 | 按模板补字段（值留空或默认） | gate 重新跑，block=0 |
| E1 ID 格式错 | 按 ATOM-{DOMAIN}-{TOPIC}-{NNN} 重命名 | gate 重新跑，ID 规则通过 |
| E2 工件 sha 不匹配 | 重编译+更新 sha（如果 command 能跑通） | replay 重新跑，confirm |
| E2 .out 缺失 | 重跑 command 生成 .out | replay 重新跑，confirm |
| E5 流程违规 | 铁律拦截，不修复（阻止提交） | 铁律检查通过 |
| E6 编译器缺失 | infra_error 分流，不修复内容 | replay 标记 infra_error |

### 不可自动修复（语义类，需判断）

| 错误 | 为什么不能自动修 | 处理方式 |
|---|---|---|
| E3 断言恒真 | 需要判断断言是否真的有判别力 | 红队发现→Writer 修订→红队复核 |
| E3 跨编译器未实测 | 需要在 Linux 侧实跑，判断断言是否成立 | 实跑+更新断言 |
| E4 claim 方向反 | 需要重新推理，可能改夹具+重算 | 红队发现→Writer 重新生产→红队复核 |
| E4 口径不统一 | 需要判断什么是"统一口径" | 红队发现→Writer 修订→红队复核 |

### 边界原则
- **自动修复只做"改了不会错"的事**——补字段、重命名、重编译、更新 sha
- **自动修复不做"改了可能更错"的事**——改 claim、改断言、改夹具逻辑
- 如果自动修复需要判断"哪个值是对的"，就不是自动修复，是升级

## 三、自动修复管道设计

```
检测（gate/replay 报警）
  ↓
分类（E1-E6，规则匹配）
  ↓
可自动修复？
  ├─ 是 → 生成修复补丁（git diff，可审查）
  │         ↓
  │       验证（门禁全跑 + 存量 0 误伤）
  │         ├─ 通过 → 提交修复 + 留痕
  │         └─ 不通过 → 升级到人工（报告失败原因）
  └─ 否 → 升级到红队/人审（附错误分类和建议）
```

### 修复上限（关键，防止无限循环）
- 同一错误最多自动修复 **2 轮**
- 超过 2 轮仍失败 → 升级，不重试
- 重试必须用**不同方法**（不是盲目重试同一个操作）

### 修复留痕（每次自动修复记录）
```json
{
  "error_id": "E2-sha-mismatch-EV-MEM-040",
  "error_type": "E2",
  "fix_method": "recompile+update_sha",
  "fix_attempt": 1,
  "verification": {"gate": "pass", "replay": "confirm", "regression": "0_warn_increase"},
  "git_commit": "abc1234",
  "timestamp": "2026-09-13T11:00:00"
}
```

## 四、修复验证方法（SWE-bench 的教训）

SWE-bench 的验证标准是：**复现测试从红变绿 + 原有测试不能出现新失败**。阙疑映射：

| SWE-bench | 阙疑 |
|---|---|
| 复现测试从红变绿 | 触发 block/warn 的规则现在通过 |
| 原有测试无新失败 | 存量 56 张卡 0 误伤（warn 数不增加） |
| 补丁可审查 | git diff 可读 |
| 安全分析 | 修复不引入新的攻击面（A1-A10） |

### 验证清单（修复后必须全过）
1. `gate_engine.py --check`：block=0，warn 数不增加
2. `atom_evidence_replay.py --check`：confirm 数不减少
3. `poison_drill.py`：全拦截
4. `pytest`：全过
5. `git diff --stat`：只改了应该改的文件
6. （如果是 E2 修复）`replay` 对应卡：confirm

## 五、反思循环的阙疑落地：Writer 自检层

行业洞察：**批判比生成容易**。当前阙疑的流程是 Writer 生产→红队批判，中间缺了 Writer 自检。

### 新增：Writer 自检层（零 token，机器做）

Writer 生产完卡后、交红队前，机器自动跑：

```
自检清单（确定性检查，零 LLM 调用）：
1. frontmatter 完整？（EV_REQUIRED / ATOM_REQUIRED 全字段）
2. ID 格式正确？（ATOM-{DOMAIN}-{TOPIC}-{NNN}）
3. artifact_sha256 与实际工件匹配？（实算 sha 对比）
4. 断言中的每个标签在 .asm 中 grep 得到？（跨编译器路径）
5. .out 与 command 同代？（.out 的 mtime > .cpp 的 mtime）
6. 断言不是恒真？（字面量不是注释、不是三元两支相同）
7. 夹具名无重名？（rglob 检查）
```

### 价值
- 拦住 E1/E2 类错误，不浪费红队的 token
- 红队专注 E3/E4 类语义错误（更有价值）
- 零 token 成本（纯脚本）
- 这是 409 防御纵深的 L1.5 层（在 L1 gate 和 L2 红队之间）

## 六、多 agent 修复（SelfHeal 的启示）

SelfHeal 用两个独立 ReAct agent：fix agent（提出修复）+ critic agent（验证修复）。这与阙疑的 Writer+红队 架构一致。

### 阙疑的多 agent 修复映射
- **fix agent = Writer**：提出修复方案
- **critic agent = 红队**：验证修复是否真的解决了问题
- **工具 = 门禁**：确定性验证（gate/replay/poison）

### 关键差异
- SelfHeal 的 critic 是 LLM（需要 token）
- 阙疑的 critic 是**机器门禁**（零 token）+ 红队（只在语义错误时调用）
- 这是阙疑的成本优势：形式验证不花 token

## 七、落地优先级

| 优先级 | 项 | 对应错误 | 风险 |
|---|---|---|---|
| **P0** | Writer 自检层（7 项确定性检查） | E1/E2/E3 | 零（只读检查） |
| **P1** | E1 自动修复（缺字段补全+ID 重命名） | E1 | 低（加性变更） |
| **P1** | E2 自动修复（重编译+更新 sha） | E2 | 中（需确认 command 能跑通） |
| **P2** | 修复留痕（自动修复日志） | 全部 | 零（只记录） |
| **P2** | 修复上限（2 轮后升级） | 全部 | 零（策略） |
| **P3** | E3 自动修复建议（只给建议，不自动改） | E3 | 中（需人工确认） |

### P0 落地：tools/writer_selfcheck.py

零风险，纯检查，不修改任何文件：
- 输入：原子/证据卡文件路径
- 输出：自检报告（通过/失败+失败项）
- Writer 在交红队前必须跑自检，自检通过才能提交红队
- 这可以直接写进 312 提示词的 MCC 流程

## 八、元结论

第五批跨 6 个窗口的根因不是"红队太严"，是**E1/E2 类机械错误消耗了红队的注意力**——红队应该专注 E3/E4 语义错误，而不是查"sha 有没有更新"。

自动修复的核心不是"让机器改内容"，是**让机器拦住机械错误，把人的/红队的精力留给语义错误**。

**最有价值的立即行动**：Writer 自检层（P0）——7 项确定性检查，零 token，零风险，直接减少红队的无效工作量。这比任何自动修复都更有价值，因为它在错误进入红队之前就拦住了。

**红线**：E4 内容错误（claim 方向反、口径不统一）永远不能自动修复——这是系统的核心价值，必须人审/红队。
