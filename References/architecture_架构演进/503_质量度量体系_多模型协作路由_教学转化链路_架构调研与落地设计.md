## 一、质量度量体系（Quality Metrics）

### 1.1 业内先进实践

| 框架 | 核心指标 | 可借鉴点 |
|---|---|---|
| **DORA Four Keys** | 部署频率、变更前置时间、变更失败率、故障恢复时间 | 吞吐+稳定性平衡，客观自动化 |
| **DORA AI 时代**（2026） | 按代码来源（AI生成/人工）分段统计变更失败率；AI 提升吞吐但可能降低稳定性 | 按生产者分类统计 |
| **SPACE**（GitHub/Microsoft, 2021） | 满意度、绩效、活动、沟通协作、效率流动 | 五维，但含主观调查（我们系统无人，不适用） |
| **DevEx** | 反馈循环时间、认知负荷、流动状态 | 开发者体验，我们映射为 Agent 体验 |

**关键洞察**（DORA AI 时代解读）：AI 提升吞吐的同时可能降低稳定性，"变更失败率"是最被 AI 扰乱的指标——必须按代码来源分段统计。这直接对应我们的系统：差模型生成的代码 vs 好模型生成的代码，故障率应该分开追踪。

### 1.2 当前系统的差距

每次批次结束都有门禁数字（gate 规则数、replay confirm、poison 数、pytest 数），但：
- **没有历史趋势**：数字只存在于当批 worklog，无法对比"一个月前规则数是多少、逃逸率是升是降"
- **没有统一采集**：每个工具输出格式不同，Agent 要手动汇总
- **没有阈值告警**：replay confirm 从 56 降到 54 不会自动告警，要等人发现
- **七维雷达图是手动的**：精密性评估靠我手动打分，没有自动化
- **成本数据分散**：cost_tracker 有 token 数据，但没有和产出关联（token/原子、token/规则）

### 1.3 度量体系架构设计

```
┌──────────────────────────────────────────────────────┐
│              tools/metrics_collector.py                │
│                                                        │
│  ┌──────────┐  ┌───────────┐  ┌──────────────────┐   │
│  │ 采集器    │→ │ 指标计算  │→ │ data/metrics.jsonl│   │
│  │ (5工具)   │  │ (派生指标) │  │ (每次批次一条)    │   │
│  └──────────┘  └───────────┘  └────────┬─────────┘   │
│                                         │             │
│  ┌──────────────────────────────────────▼─────────┐   │
│  │  趋势仪表盘 (HTML, ECharts)                     │   │
│  │  - 产出量趋势(原子/证据/规则/毒样例)             │   │
│  │  - 质量趋势(confirm率/拦截率/逃逸数)             │   │
│  │  - 性能趋势(pytest/replay/gate耗时)             │   │
│  │  - 成本趋势(token/原子/窗口数/批次)             │   │
│  │  - 进化趋势(规则增长率/逃逸闭合率/修复周期)      │   │
│  └─────────────────────────────────────────────────┘   │
│                                         │             │
│  ┌──────────────────────────────────────▼─────────┐   │
│  │  阈值告警                                       │   │
│  │  replay_confirm < 95% → 告警                    │   │
│  │  gate_block > 0 → 告警                          │   │
│  │  pytest耗时增长 > 50% → 告警                    │   │
│  │  token/原子 > 基线2倍 → 告警                    │   │
│  └─────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────┘
```

**五类指标**（25 个具体指标）：

| 类别 | 指标 | 采集方式 | 方向 |
|---|---|---|---|
| **产出量** | 原子总数 | `ls atoms/**/*.md` | ↑ |
| | 证据卡总数 | `ls evidence/**/*.md` | ↑ |
| | 规则总数 | gate --list | ↑ |
| | 毒样例总数 | poison_drill | ↑ |
| | 误解总数 | `ls misconceptions/**/*.md` | ↑ |
| **质量** | replay confirm 率 | replay --check | ↑ |
| | 变异拦截率 | 变异测试报告 | ↑ |
| | 对抗逃逸数 | 对抗报告 | ↓ |
| | gate block 数 | gate --check | =0 |
| | 存量 warn 数 | gate --check | ↓ |
| | pytest 通过率 | pytest | =100% |
| **性能** | pytest 总耗时 | pytest --durations | ↓ |
| | replay 全量耗时 | replay --check | ↓ |
| | gate 耗时 | gate --check | ↓ |
| | 增量 replay 耗时 | replay --incremental | ↓ |
| **成本** | token/原子 | cost_tracker / 原子数 | ↓ |
| | token/批次 | cost_tracker | ↓ |
| | 窗口数/批次 | task_state | ↓ |
| | 差模型 token 占比 | cost_tracker 按模型分类 | ↑(尽量用差模型) |
| **进化** | 规则增长率 | (本期规则-上期)/上期 | 稳定 |
| | 逃逸闭合率 | 本期闭合逃逸/上期逃逸 | ↑ |
| | 修复周期 | 逃逸发现→规则合入的批次 | ↓ |
| | 新规则误伤率 | 新规则导致的存量 block | =0 |
| | 工具数 | `ls tools/*.py` | ↑ |

**采集方式**：
- 每次批次结束后跑 `python tools/metrics_collector.py snapshot --batch 500`，自动采集所有指标，追加到 `data/metrics.jsonl`
- 零 LLM，纯机械（调用各工具的 --json 模式，403 已落地）
- 派生指标（token/原子、拦截率）在采集器中计算

**阈值告警**：
- 硬阈值（必须为 0）：gate_block、pytest_fail、replay_refute
- 软阈值（趋势恶化告警）：replay_confirm 下降 >2、pytest 耗时增长 >50%、token/原子增长 >2 倍
- 告警输出到 metrics 报告，不自动阻断（人决定是否回滚）

**仪表盘**：
- `docs/kernel/metrics_dashboard.html`（ECharts 交互图，5 个子图）
- 每次 snapshot 后自动更新
- 可按批次范围筛选

## 二、多模型协作路由（Multi-Model Routing）

### 2.1 业内先进实践

| 系统 | 核心机制 | 可借鉴点 |
|---|---|---|
| **FrugalGPT**（Stanford, TMLR 2024） | LLM cascade：先用小模型，不够再升级大模型。80% 成本降低 +1.5% 准确率提升 | 级联升级、成本优化 |
| **MasRouter**（ACL 2025） | 多智能体路由：决定协作模式→角色分配→LLM 路由，成本降低 52% | 角色-模型联合优化 |
| **NVIDIA NeMo Switchyard**（2026） | Escalation router：LLM judge 监控进度，持续困难时升级模型 | 运行时动态升级 |
| **路由 vs 级联**（arXiv 2603.04445） | 路由=单次决策选模型；级联=顺序尝试从小到大一 | 生产系统常组合使用 |
| **任务-模型映射**（2026 实践） | 分类/分流→小模型；复杂推理→大模型；多步 agent→可靠性高的模型 | 按任务类型选模型 |

**关键洞察**：模型路由不是"均匀降价"，而是"转移支付"——复杂任务多花一点（planner 仍需好模型），简单任务省很多（长尾巴的机械任务）。如果工作流大部分是简单任务，节省巨大。这正是我们系统的形态（苦力干 80% 的机械杂活）。

### 2.2 当前系统的差距

- **纯手动切换**：用户手动决定"这个任务给差模型""那个给好模型"，没有自动化
- **无级联**：差模型失败了不会自动升级好模型，要用户发现后重新投喂
- **无成本感知**：不知道每个任务花了多少 token、哪个模型性价比最高
- **无任务分类**：提示词里没有标注"这个任务需要什么级别的模型"

### 2.3 路由架构设计

```
┌──────────────────────────────────────────────────────┐
│              tools/model_router.py                     │
│                                                        │
│  ┌──────────────┐  ┌───────────────┐  ┌────────────┐ │
│  │ 任务分类器    │→ │ 模型映射表    │→ │ 调度器      │ │
│  │ (读提示词元数据)│  │ (可配置)      │  │ (选模型)    │ │
│  └──────────────┘  └───────┬───────┘  └─────┬──────┘ │
│                            │                  │        │
│                     ┌──────▼──────┐   ┌──────▼──────┐ │
│                     │ 级联升级器  │   │ 成本追踪器  │ │
│                     │ (失败→升级) │   │ (按模型统计)│ │
│                     └──────┬──────┘   └─────────────┘ │
│                            │                           │
│                     ┌──────▼──────┐                    │
│                     │ LLM Judge   │                    │
│                     │ (监控进度)   │                    │
│                     └─────────────┘                    │
└──────────────────────────────────────────────────────┘
```

**任务分类**（在提示词 frontmatter 中标注）：

```yaml
# 提示词文件头部
model_route:
  primary: cheap        # cheap / strong / adversarial
  max_escalations: 1    # 允许升级几次
  timeout_minutes: 60   # 超时后升级
  failure_threshold: 3  # 连续失败N次后升级
```

**模型映射表**（`config/model_routes.yaml`，可配置）：

| 任务类型 | primary | escalation | 理由 |
|---|---|---|---|
| 机械清理/索引/统计 | 差模型（混元/hy4p） | 不升级 | 纯机械，差模型足够 |
| 变异测试/对抗探针 | 差模型 | 不升级 | 机械执行，结果可验证 |
| 缺陷修复（有明确根因） | 差模型 | 好模型（ds v4.1） | 差模型先试，失败升级 |
| 新规则设计/架构 | 好模型（ds v4.1） | 不降级 | 需要深度推理 |
| 对抗测试/红队 | 异模型族（Seed-Evolving/Trae） | 不升级 | 独立性要求 |
| 文档写作/报告 | 差模型 | 好模型 | 差模型起草，好模型润色 |

**级联升级机制**：
1. 任务先用 primary 模型执行
2. LLM Judge（或机械检查）监控：
   - 连续失败 N 次（failure_threshold）→ 升级
   - 超时（timeout_minutes）→ 升级
   - 输出不通过门禁（gate block >0）→ 升级
3. 升级到 escalation 模型重新执行
4. max_escalations 限制升级次数（默认 1，避免无限升级烧 token）

**成本追踪**：
- cost_tracker 按模型分类统计 token
- 每批次结束输出：差模型 token X / 好模型 token Y / 对抗模型 token Z
- 计算"差模型处理率"= 差模型完成的任务数 / 总任务数（目标 >70%）

### 2.4 落地路径

| 阶段 | 内容 | 工作量 |
|---|---|---|
| L1 | 提示词 frontmatter 加 model_route 字段 + 模型映射表 + 成本按模型分类 | 1 个苦力批次 |
| L2 | 级联升级机制（失败/超时/门禁不通过→升级）+ LLM Judge | 1 个好模型批次 |
| L3 | 路由效果评估（升级率、成本节省、质量对比）+ 自动调优映射表 | 好模型批次 |

## 三、教学转化链路（Learning Content Pipeline）

### 3.1 业内先进实践

| 方向 | 实践 | 可借鉴点 |
|---|---|---|
| **闪卡算法** | Anki FSRS（2023 起默认）：比旧 SM-2 少 20-30% 复习量，相同保持率 | FSRS 调度算法 |
| **AI 闪卡生成** | 每张卡测一个概念；优先 why/how/区别题；cloze deletion；背面含超答案的解释 | 闪卡质量规则 |
| **Memdora**（2027） | 内容类型分类路由：词汇→语言卡、引用→背诵卡、事实/过程→考试卡（含语义干扰项） | 按内容类型选卡型 |
| **间隔重复** | 主动回忆 + 间隔重复 = 记忆效率最优；答错的卡出现更频繁 | 自适应调度 |

### 3.2 当前系统的差距

- **原子→Book**：book_atom_sync.py 已有但不完善（499 发现已注册但缺测试），Book 章节和原子的同步不完整
- **原子→闪卡**：flashcard_export.py 已有（106 张 Anki CSV），但闪卡质量未按 Memdora 的内容类型分类
- **原子→练习题**：完全缺失。80 条误解是天然的选择题干扰项来源，但没有生成练习题
- **原子→代码实验**：Examples/atoms/ 有 51 个夹具，但没有"实验指导"（学生该观察什么、改什么、预期什么）
- **学习路径**：没有基于依赖关系的学习顺序规划

### 3.3 教学转化链路设计

```
原子 (atoms/)
  │
  ├──→ Book 章节 (Book/)          [讲解]
  │     book_atom_sync.py（已有，需完善）
  │
  ├──→ 闪卡 (flashcards/)         [记忆]
  │     flashcard_export.py（已有，需升级）
  │     按内容类型分类：概念卡/过程卡/对比卡/陷阱卡
  │
  ├──→ 练习题 (exercises/)        [应用]
  │     从误解生成选择题（干扰项=误解内容）
  │     从夹具生成代码填空题
  │
  ├──→ 代码实验 (labs/)           [实操]
  │     基于 Examples/atoms/ 夹具
  │     实验指导：观察什么→改什么→预期什么
  │
  └──→ 学习路径 (learning_path/)  [导航]
        基于知识图谱依赖关系生成学习顺序
```

**闪卡升级**（参考 Memdora 内容类型分类）：

| 卡型 | 适用内容 | 格式 | 示例 |
|---|---|---|---|
| 概念卡 | 定义/术语 | Q: 什么是X？A: 定义+关键特征 | "什么是 RAII？" |
| 过程卡 | 步骤/流程 | Q: X的步骤是什么？A: 分步+每步目的 | "new/delete 的执行顺序？" |
| 对比卡 | 易混概念 | Q: X和Y的区别？A: 表格对比 | "move vs copy？" |
| 陷阱卡 | 误解/UB | Q: 以下代码有什么问题？A: 问题+后果+正确写法 | "循环里加 volatile 能阻止消除吗？" |

每张卡：测一个概念、优先 why/how/区别题、背面含超答案的解释、标注来源原子 ID。

**练习题生成**（从误解库自动生成）：
- 80 条误解（misconceptions/）每条有 3 个反例 → 天然的选择题素材
- 题型：选择题（题干=误解描述，正确选项=正确理解，干扰项=其他误解）、判断题、代码改错题
- 工具：`tools/exercise_generator.py`，输入误解 ID，输出练习题
- 验证：练习题的答案必须能在对应原子的 claim 中找到依据

**代码实验**（基于夹具）：
- 51 个夹具（Examples/atoms/）每个都有确定的编译/运行结果
- 实验指导模板：
  1. 目标：这个实验要验证什么（对应原子的 claim）
  2. 步骤：编译命令、运行命令、观察什么输出
  3. 探索：改哪个参数/代码，预期什么变化
  4. 思考题：联系哪个误解
- 工具：`tools/lab_generator.py`，输入夹具路径，输出实验指导 Markdown

**学习路径**（基于知识图谱）：
- 遍历知识图谱的 PREREQUISITE 边，生成拓扑排序
- 输出：从基础到进阶的学习顺序，每个节点标注前置依赖
- 工具：知识图谱的 `kg learning-path --start ATOM-MEM-ALLOC-001` 查询

### 3.4 落地路径

## 四、三者的协同关系

```
质量度量体系 ──→ 追踪教学转化的产出量/质量
     │
     ▼
多模型路由 ──→ 教学内容生成用差模型（机械），质量审核用好模型
     │
     ▼
教学转化链路 ──→ 闪卡/练习题/实验的质量数据回流到度量体系
```

- 质量度量是"仪表盘"：追踪所有维度的健康度
- 多模型路由是"变速箱"：根据任务类型自动选模型，优化成本
- 教学转化是"出口"：把系统的知识资产转化为学习者可用的内容
