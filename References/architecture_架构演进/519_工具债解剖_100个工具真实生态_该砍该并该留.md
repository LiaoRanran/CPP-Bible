## 二、真正的问题

### 2.1 审计工具碎片化

28个audit/check/lint工具，但：
- 没有统一入口——用户不知道该跑哪个
- 大量重叠——4个引用检查工具各说各的
- cppbible.py只包装了部分（check/build/clean），其余散着

**这就像家里有28个螺丝刀，但每个只能拧一种螺丝，且没人告诉你该用哪个。**

### 2.2 历史批次残留

D5系列5个、example_*系列5个、d5_*系列——这些都是历史批次的产物，当时为了一个具体问题写的脚本，问题解决了但脚本留着。

**100个工具里，估计30-40个是"历史批次一次性脚本"，现在没人调用。**

### 2.3 没有工具健康检查

不知道哪些工具：
- 还在被调用
- 已经死了
- 和新代码不兼容

tool_integrity只检查5个核心工具。

## 三、该砍该并该留

### 立即砍（死代码候选）

需要grep确认没人调用：
- d5_appendix_audit / d5_gap_scanner / d5_source_integrity
- caption_truncation_audit / star_h2_audit
- prose_density / density_audit（合并留一个）
- 其他历史批次一次性脚本

### 合并（同功能多个合成一个）

| 合并后 | 吸收 |
|---|---|
| tools/compile.py | compile_all/gate/sanitize/classify/triage + chapter_compile + d5_compile |
| tools/audit.py | check_citations/crossref/dangling_ref/xref_check |
| tools/style.py | codeblock_style/markdown_style/table_style |

### 保留不动

9个核心引擎 + 9个新基建 = 18个

### 净效果

100个 → ~30个（核心+合并后）。
- 减少70%工具数
- 统一入口
- 新人（或Agent）不用在100个文件里找

## 四、和516/517的关系

516说"100个工具是问题"，517说"L0=71%"。
519更进一步：**不是工具少，是工具多且碎**。

L0=71%的另一面是：**L0的29%没完成，但同时有70%的工具是冗余的**。

正确的方向不是"再加更多工具"（518的6个任务），而是：
1. 先砍死代码（减少认知负担）
2. 再合并重复（统一入口）
3. 最后才加新工具（FTS5/retry/backup）

**518的执行顺序应该调：先做工具债清理，再加新功能。**
