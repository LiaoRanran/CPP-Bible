## 一、C++ 编译层优化（replay 核心耗时）

### 1.1 业内实践

| 技术 | 效果 | 适用场景 |
|---|---|---|
| **ccache** | 重复编译 35-50x 加速（SFML 案例） | 相同源码+相同 flags 重复编译 |
| **sccache** | 支持分布式+云后端，但本地比 ccache 慢 | 多机共享缓存 |
| **Ninja** | 增量构建 5-15% 提升（零成本切换） | Make 替代 |
| **预编译头(PCH)** | 20-50% 更快编译 | 稳定头文件 |
| **并行编译 -j** | 近线性加速（受核数限制） | 多 TU 项目 |

### 1.2 当前系统的编译特征

- 56 张卡，每张卡的夹具是单文件 .cpp，编译命令固定
- replay 每次全量跑 = 56 次编译（Windows）+ 56 次（WSL）= 112 次
- P0-A 重编译（防工件篡改）刻意 `CCACHE_DISABLE=1`，每卡多一次编译
- 夹具变化频率低（大部分批次不改夹具），但每次 replay 都全量重编

### 1.3 优化方案

**优化 A：ccache 分层启用**（预期省 60-80% 编译时间）

```
replay 编译分两类：
1. 普通编译（验证夹具可编译+生成.out）→ 启用 ccache
   - 相同夹具+相同 flags → 缓存命中，<1s
   - 首次编译 → 正常编译，写入缓存
2. P0-A 重编译（防篡改验证）→ CCACHE_DISABLE=1（保持安全）
   - 这是安全锚点，不能省
   - 但只在 artifact_assert 路径触发，不是每卡都跑
```

**关键**：499 实测 ccache 热缓存 244.5s（1.22×），收益不大是因为 P0-A 禁用了 56 次。如果普通编译启用 ccache + P0-A 只在跨编译器路径触发，预期全量 245s→80-100s。

**优化 B：并行编译**（预期省 50% 编译时间）

```python
# replay 内部用 ProcessPoolExecutor 并行编译
with ProcessPoolExecutor(max_workers=os.cpu_count()) as pool:
    results = pool.map(compile_one, cards)
```

32 核机器，56 次编译并行 → 理论上 56/16 ≈ 4 批（留 50% 核给系统），编译时间 /4。

**优化 C：增量编译**（已有基础，498 落地 `--incremental`）

- 夹具 mtime 没变 → 跳过编译，直接用缓存的 .out
- 无改动 0.3s，改 1 卡 2.3s
- CI 默认 `--incremental`，全量只在改工具时触发

**优化 D：夹具编译缓存持久化**

- `data/compile_cache/` 存编译产物，key = sha256(夹具内容+编译flags)
- 跨批次复用，不依赖 ccache 的配置
- 比 ccache 更可控（ccache 可能被清理/配置变化）

### 1.4 预期收益

| 优化 | 单独效果 | 组合效果 |
|---|---|---|
| ccache 普通编译 | 245s→150s | — |
| 并行编译 | 245s→120s | — |
| 增量(默认) | 245s→5s(无改动) | — |
| **组合(有改动)** | — | **245s→60-80s** |
| **组合(无改动)** | — | **245s→5s** |

## 二、Python 工具启动层优化

### 2.1 业内实践

| 技术 | 效果 | 说明 |
|---|---|---|
| **延迟 import** | 启动快 30-50% | 只在用到时 import 重模块 |
| **-X importtime 分析** | 定位慢导入 | importguardpy 工具 |
| **工具常驻/daemon** | 消除启动开销 | API server 模式，一次启动多次调用 |
| **去掉重模块** | click/rich/requests 是重模块 | 用标准库替代（argparse/print/urllib） |

### 2.2 当前问题

- 13 个工具，每个都是独立 Python 脚本，每次调用 fork 进程 + import
- gate_engine.py 2137 行，import pyyaml/re/json/subprocess 等，启动 ~0.5-1s
- cppbible check 调用 5 个工具 = 5 次进程启动 = ~3-5s 纯启动开销
- CI 中工具调用更频繁，启动开销累积

### 2.3 优化方案

**优化 A：延迟 import**

```python
# 优化前（启动时全 import）
import yaml
import json
import subprocess
import re
from pathlib import Path

# 优化后（只 import 轻量的，重的延迟）
import json
import re
from pathlib import Path

def run_check():
    import yaml  # 只在需要时 import
    import subprocess
    ...
```

**优化 B：工具常驻模式**（API 层，506 缺口 4）

```
tools/api_server.py (FastAPI)
启动一次，常驻内存
所有工具调用走 HTTP API，不再 fork 进程
- gate --check → POST /api/gate/check
- replay --check → POST /api/replay/check
- 启动开销从 ~1s/次 → ~5ms/次（网络开销）
```

这是最彻底的优化，但需要 API 层先落地（506 缺口 4，P3）。

**优化 C：合并轻量工具**

- consistency.py + gen_metrics.py + tool_integrity.py 都是轻量检查，可以合并为一个 `tools/quick_checks.py`
- 一次进程启动完成 3 项检查，省 2 次启动

### 2.4 预期收益

| 优化 | 效果 |
|---|---|
| 延迟 import | 单工具启动 1s→0.3s |
| 合并轻量工具 | cppbible check 省 ~2s |
| API 常驻模式 | 工具调用 1s→5ms（200x） |

## 三、pytest 层优化（第二大耗时）

### 3.1 业内实践

| 技术 | 效果 | 说明 |
|---|---|---|
| **pytest-xdist** | 近线性加速 | 32 核用 -n 16 |
| **pytest-rs** | coverage 2-3x 加速 | 用 sys.monitoring 替代 tracing hooks |
| **pytest-fastcollect** | 冷启动 28ms→热启动 0.9ms | 缓存测试元数据 |
| **--durations** | 定位慢测试 | `pytest --durations=10` |
| **测试分片** | CI 多 runner 并行 | 按测试文件分片 |

### 3.2 当前问题（499 实测）

- 354 测试，~642s
- **最大瓶颈**：3 个 test_contains_in_* 测试烧 174.7s——根因是 `_assert_haystack()` 中 `ROOT / str(rel or "")` = 仓库根目录，触发整仓 rglob 读 28588 个文件
- 测试串行执行，32 核只用了 1 核
- 没有测试缓存，每次全量跑

### 3.3 优化方案

**优化 A：修 contains_in rglob bug**（499 已定位，504 阶段 0）

```python
# gate_engine.py:1431
def _add(self, rel):
    if not rel:  # 加这行：空 rel 直接返回，不扫整仓
        return
    f = ROOT / str(rel)
    ...
```

**预期省 174.7s**（642s→467s）。

**优化 B：pytest-xdist 并行**

```ini
# pytest.ini
[pytest]
addopts = -n auto  # 自动用所有核
```

32 核机器，354 测试并行 → 理论 642s/16 ≈ 40s（有测试间依赖会打折，预期 ~80-100s）。

**风险**：测试间可能共享文件锁/临时目录。需先跑一轮排查，给有共享状态的测试加 `@pytest.mark.serial`。

**优化 C：慢测试隔离**

```python
# 标记慢测试
@pytest.mark.slow
def test_replay_full():
    ...

# 快速模式跳过慢测试
pytest -m "not slow"  # pre-push 用
pytest              # CI 全量
```

**优化 D：测试结果缓存**

- pytest-cache 或 pytest-fastcollect：未改的测试跳过
- 基于文件 mtime 判断，只跑受影响的测试

### 3.4 预期收益

| 优化 | 单独效果 | 组合效果 |
|---|---|---|
| 修 rglob bug | 642s→467s | — |
| xdist 并行 | 642s→80-100s | — |
| 慢测试隔离 | pre-push 快 50% | — |
| **组合(CI全量)** | — | **642s→60-80s** |
| **组合(pre-push)** | — | **642s→20-30s** |

## 四、数据层优化

### 4.1 业内实践（SQLite）

| PRAGMA | 作用 | 推荐值 |
|---|---|---|
| `journal_mode=WAL` | 读写不互斥 | 必须 |
| `synchronous=NORMAL` | 写不刷盘到事务结束 | NORMAL（非FULL） |
| `cache_size=-64000` | 64MB 内存缓存 | 64MB |
| `mmap_size=268435456` | 256MB mmap 读 | 256MB |
| `busy_timeout=5000` | 锁等待 5s | 5000ms |
| `wal_autocheckpoint=1000` | WAL 自动合并 | 1000 页 |

### 4.2 当前问题

- 所有数据存在 JSON 文件：golden_state.json、metrics.jsonl、artifact_versions.json
- 每次读取全量解析，写入全量重写
- 没有索引，查询靠遍历
- 知识图谱（502）计划用 SQLite，但还没落地

### 4.3 优化方案

**优化 A：知识图谱 SQLite 性能配置**（502 L1 落地时直接用）

```python
conn = sqlite3.connect("data/knowledge_graph.db")
conn.execute("PRAGMA journal_mode=WAL")
conn.execute("PRAGMA synchronous=NORMAL")
conn.execute("PRAGMA cache_size=-64000")  # 64MB
conn.execute("PRAGMA mmap_size=268435456")  # 256MB
conn.execute("PRAGMA busy_timeout=5000")

# 索引
conn.execute("CREATE INDEX idx_edges_src ON edges(src)")
conn.execute("CREATE INDEX idx_edges_dst ON edges(dst)")
conn.execute("CREATE INDEX idx_edges_type ON edges(type)")
conn.execute("CREATE INDEX idx_nodes_type ON nodes(type)")
```

**优化 B：metrics.jsonl 索引化**

- 当前：查询历史趋势要全量扫描 jsonl
- 优化：metrics_collector 同时写 SQLite（`data/metrics.db`），jsonl 只做追加日志
- 查询走 SQLite，秒级响应

**优化 C：JSON 文件缓存**

- `tools/cache.py`：内存缓存 JSON 解析结果，mtime 变了才重读
- 避免同一批次内反复解析同一个文件

### 4.4 预期收益

| 优化 | 效果 |
|---|---|
| SQLite WAL+mmap | 知识图谱查询 <1ms（vs JSON 遍历 10-50ms） |
| metrics 索引化 | 趋势查询 5s→<1s |
| JSON 缓存 | 同批次内重复读省 80% IO |

## 五、系统架构层优化

### 5.1 并行执行模型

```
当前：串行
cppbible check → gate → poison → consistency → metrics → replay → pytest
总时间 = sum(各阶段)

优化：DAG 并行
┌─────────────────────────────────────────┐
│           变更分析 (git diff)            │
└──────────────┬──────────────────────────┘
               │
    ┌──────────┼──────────┬──────────┐
    ▼          ▼          ▼          ▼
  gate      poison    consistency  metrics
  (并行)     (并行)     (并行)      (并行)
    └──────────┴──────────┴──────────┘
               │
         ┌─────┴─────┐
         ▼           ▼
      replay      pytest
      (并行编译)   (xdist)
         └─────┬─────┘
               ▼
            汇总报告
```

**关键**：gate/poison/consistency/metrics 之间没有依赖，可以完全并行。replay 和 pytest 也可以并行（不共享资源）。

### 5.2 增量计算模型

| 当前 | 优化后 |
|---|---|
| 每次全量 replay 56 卡 | 只 replay 变化的卡+依赖（知识图谱 impact） |
| 每次全量 pytest 354 测试 | 只跑受影响的测试（pytest-cache） |
| 每次全量 gate 53 规则 | 只检查变化的文件+依赖 |
| 每次重新计算 metrics | 增量更新，只算变化的指标 |

### 5.3 结果缓存模型

```
data/result_cache/
├── gate/          # gate --check 结果缓存，key = git HEAD + 规则版本
├── replay/        # replay 结果缓存，key = 夹具 sha + 编译器版本
├── poison/        # poison 结果缓存
└── compile/       # 编译产物缓存（1.3 优化 D）
```

- 相同输入 → 直接返回缓存结果，不重算
- 缓存 key 包含所有影响结果的因素（git HEAD、工具版本、编译器版本）
- 缓存失效自动检测（key 不匹配 → 重算）

### 5.4 预期收益

| 优化 | 效果 |
|---|---|
| DAG 并行 | gate+poison+consistency+metrics 30s→8s（4 并行） |
| 增量计算 | 小改动批次 CI 15min→2min |
| 结果缓存 | 重复验证 5min→10s |

## 八、性能监控与防退化

优化做完后要防止退化：

1. **pytest-benchmark**：给关键工具加基准测试，CI 中跑，性能退化 >20% 告警
2. **metrics 采集**：每次 CI 记录各阶段耗时，趋势图监控（503 质量度量）
3. **慢测试标记**：新增测试 >5s 必须标记 `@pytest.mark.slow`，否则 CI 告警
4. **编译缓存命中率**：replay 输出 ccache 命中率，<50% 告警

---

## 九、一句话总结

全栈性能优化的核心是**三句话**：
1. **不重复算**——ccache + 结果缓存 + 增量计算（最大收益）
2. **不串行等**——xdist + DAG 并行 + 并行编译（32 核别闲着）
3. **不全量扫**——修 rglob bug + SQLite 索引 + 增量测试（别扫 28588 个文件）

P0 三项 2.5h 做完，CI 15min→3-5min；P1 做完增量 CI 30-60s。这是投入产出比最高的优化。
