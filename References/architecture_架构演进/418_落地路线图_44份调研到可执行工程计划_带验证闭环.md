## 二、落地的核心问题：没有验证闭环

44 份调研的通病：**落地=工具写了**，但不验证工具是否真的拦住了问题。

正确的落地定义：
```
工具写了 ≠ 落地
工具写了 + 毒样例证明能拦住 + 存量 0 误伤 + 回归测试 = 落地
```

### 每个落地项的验证闭环模板

| 项 | 验证方法 | 通过标准 |
|---|---|---|
| 414 F08（poison exit） | 注入未覆盖规则 → exit 非零 | exit=1 |
| 414 F01（cl 免检） | 造含 cl 且 verdict:confirm 的卡 → gate block | block=1 |
| 414 F02（编译后覆写） | command 含 python 覆写 → gate block | block=1 |
| 417 矛盾检测 | P29/P30 毒样例 → block | block=2 |
| 413 自检层 | 用第五批 E1/E2 错误回放 → 自检拦住 | 拦住 ≥80% |
| 412 成本追踪 | 跑一颗真实原子 → CPVA 有数值 | 数值非空 |
| warn 治理 | 17 条 MATRIX 误报逐条裁决 → warn 32→15 | warn 减半 |

**关键**：413 自检层的验证不是"7 项检查都实现了"，是"用历史上真实犯过的 E1/E2 错误回放，自检能拦住多少"。这才是有意义的验证。

## 七、元结论

44 份调研的落地瓶颈不是"没有方向"，是**三个缺口**：

1. **验证闭环缺口**：工具写了不验证是否真拦住问题 → 用"攻击用例复跑"补齐
2. **提示词缺口**：413/412 有设计但没写成可投喂的苦力提示词 → 立即补写
3. **状态确认缺口**：408/410 的执行结果未知 → 先确认再决定是否重做

**最反直觉的发现**：44 份调研中，真正的"完全空白"只有 3-4 项（矛盾检测、影响分析、文档腐烂、跨域迁移），其他要么已落地、要么有提示词待执行、要么是已有规则的增强。这说明调研已经足够多了，**下一步不是继续调研，是把已有设计落地+验证**。

**一句话**：从"调研驱动"切换到"落地验证驱动"——每写一个工具，必须用攻击用例证明它真的拦住了问题，否则就是装饰。
