## 一、为什么要做这个变更

### 1.1 现实约束

- 用户人审能力有限（时间、精力、专业深度）
- 第五批 3 颗原子停在"卡层阻断清零、待质检报告"，两天无新增 verified 原子
- 瓶颈不在生产，在人审签署

### 1.2 机器与人的能力边界（实证）

| 机器擅长 | 机器不擅长（必须人） |
|---|---|
| 断言与工件逐字一致 | claim 的教学方向对不对 |
| 跨编译器复现 | 与已有原子是否重复 |
| 格式/frontmatter 合规 | 类比/直觉是否恰当 |
| 毒样例拦截 | 失效后果的真实严重度 |
| 引用完整性 | "这个值不值得教" |

**关键实证**：ALLOC-002 的口径反转——机器验证了断言与工件一致，但不可能判断"pool 元数据最省"这个教学结论是错的。这是人审的不可替代性。

### 1.3 设计原则

不是降低人审要求，是**让人审只做只有人能做的事**。机器和红队承担形式审查和断言审查，人审只做方向判断。

## 二、四级状态体系

### 2.1 状态定义

```
draft → machine-verified → red-team-verified → human-verified
```

| 状态 | 含义 | 晋升条件 | 谁决定 |
|---|---|---|---|
| `draft` | Writer 初版，未过任何审查 | — | Writer |
| `machine-verified` | 门禁全绿（replay+gate+poison+pytest） | 自动晋升 | 机器 |
| `red-team-verified` | 独立红队通过，阻断全清 | 自动晋升 | 红队 agent |
| `human-verified` | 人审签署，方向确认 | 人审签署 | 人 |

### 2.2 状态跃迁规则

- **draft → machine-verified**：门禁全绿自动晋升，不需要人
- **machine-verified → red-team-verified**：红队通过（阻断=0）自动晋升，不需要人
- **red-team-verified → human-verified**：人审签署，仅 DAL A/B 必须
- **禁止跳级**：不能从 draft 直接到 human-verified（gate 规则拦截）
- **回退**：任何级别发现问题，回退到 draft，重新走流程

### 2.3 frontmatter 字段

```yaml
status: red-team-verified        # draft / machine-verified / red-team-verified / human-verified
verified_by: redteam:agent-xxx   # 机器/红队晋升时记录执行者
verified_at: 2026-09-12
dal: C                            # 失效后果分级 A-E（claim 契约化 v0.2 已定义）
human_review: required            # required（DAL A/B）/ optional（DAL C/D/E）/ waived
```

## 三、DAL 分级与人审要求

### 3.1 DAL 定义（继承自 296 claim 契约化 v0.2）

| 级别 | 含义 | 示例 | 人审要求 |
|---|---|---|---|
| **A** | 致命：错误会导致读者写出有安全/并发 bug 的代码 | 内存序、UB、数据竞争 | **必须 human-verified** |
| **B** | 严重：教学结论方向错误，误导理解 | ALLOC-002 口径反转、RAII 机制错误 | **必须 human-verified** |
| **C** | 中等：性能量化/平台相关，错误影响有限但不致命 | PERF-003/004、SSO 阈值 | red-team-verified 即可，抽查 20% |
| **D** | 轻微：格式/表述/类比不够精准 | 措辞优化、补充说明 | red-team-verified 即可 |
| **E** | 可忽略：纯事实陈述，几乎不可能错 | 语法规则、标准条文引用 | machine-verified 即可 |

### 3.2 人审轻量化

人审只问**一个问题**：
> "claim 的方向和教学价值对不对？"

其余（断言复现、格式合规、引用完整、跨编译器）机器已保证，人审不需要重复检查。

### 3.3 抽查机制（DAL C/D/E）

- red-team-verified 的 DAL C/D/E 原子自动入库
- 每批随机抽查 20% 做人审
- 抽查发现问题 → 该原子回退 draft + 同批所有 red-team-verified 原子加审
- 抽查通过率 < 80% → 触发红队质量审计

## 四、工具改动清单

### 4.1 gate_engine.py

**修改 `ATOM-NO-UNVERIFIED` 规则**：
- 当前：只认 `status: verified`
- 改为：认 `red-team-verified`（DAL C/D/E）和 `human-verified`（DAL A/B）
- DAL A/B 级原子如果 status 不是 `human-verified` → block

**新增 `ATOM-STATUS-TRANSITION` 规则**：
- 检查状态跃迁是否合法
- 禁止 draft → human-verified 跳级
- 禁止回退状态没有修订记录

**新增 `ATOM-DAL-MATCH` 规则**：
- DAL 字段必须存在且为 A-E
- DAL A/B 必须有 `human_review: required`
- DAL A/B 且 status != human-verified → block

### 4.2 golden_lock.py

**统计口径扩展**：
```python
{
  "total_atoms": 23,
  "human_verified": 5,      # DAL A/B + 抽查通过的
  "red_team_verified": 15,  # DAL C/D/E
  "machine_verified": 3,    # DAL E
  "draft": 0,
  "evidence": 54,
  "replay_confirm": 54
}
```

**恶化检测**：
- human_verified 下降 → 恶化
- red_team_verified 下降 → 恶化
- DAL A/B 未 human-verified → 恶化

### 4.3 红队自动化（阶段 2）

- Writer 完成后自动触发红队（CI job 或脚本）
- 红队结果机器可解析（JSON 格式：阻断数/高级数/建议数）
- 阻断=0 → 自动晋升 red-team-verified
- 阻断>0 → 回退 draft，附红队报告

### 4.4 人审签署工具（可选）

- 简单脚本：`python tools/human_review.py ATOM-XXX --approve` 或 `--reject --reason "..."`
- 自动更新 frontmatter + golden_lock sync
