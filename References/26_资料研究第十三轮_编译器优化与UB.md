## 一、核心原理：编译器把 UB 当"永远不会发生"的许可证

### 1. 核心定理

> 现代优化编译器把 UB 当作"永远不会发生"的许可证。这不是恶意——而是标准契约的数学必然结果：如果合法程序中 UB 不可能发生，优化器可以从这个假设推导事实并传播到整个程序。

- **来源**：LLVM 官方博客 "What Every C Programmer Should Know About Undefined Behavior"（Chris Lattner，2011，三篇系列）
- **类型**：官方设计文档
- **可信度**：S
- **教材价值**：S

### 2. "Time-Travel" 优化（时间旅行优化）

编译器可以删除 **UB 之前**的代码——因为如果某条代码路径会导致 UB，那么这条路径就不可能被执行（合法程序中），所以路径上的所有代码都可以删除。

```cpp
// 经典示例
void foo(int *p) {
    int x = *p;       // 如果 p 是 nullptr，这里是 UB
    if (p == nullptr) // 编译器推理：如果 p 是 nullptr，上面已经 UB 了
        return;       // 所以 p 不可能是 nullptr → 整个 if 分支被删除
    bar(x);
}
```

- **来源**：MIT APSYS 2012 论文 "Undefined Behavior: What Happened to My Code?"（Wang et al.）
- **与 CPP-Bible 的关系**：UB 域核心原子；"为什么 -O2 会改变程序行为"专题
- **可以设计什么实验**：上面的代码 -O0 vs -O2 行为对比（-O0 检查 nullptr，-O2 不检查）

## 二、五类 UB 优化技术（与具体 UB 对应）

| 优化技术 | 利用的 UB | 效果 | 真实案例 |
|---|---|---|---|
| **死代码消除（DCE）** | 空指针解引用 | 删除 null 检查分支 | Linux kernel 曾因此出 CVE |
| **循环优化** | 有符号整数溢出 | 假设循环终止、消除边界检查 | `for (int i = 0; i < n; i++)` 假设 i 不溢出 |
| **分支消除** | 不可达 UB 路径 | 删除整个分支 | `if (x / 0)` 后的代码 |
| **返回值传播** | 函数必须返回值 | 用垃圾/任意值 | 函数末尾无 return，调用者拿到任意值 |
| **严格别名重排** | 类型双关 | 重排读写、load elimination | `int*` 和 `float*` 不可能别名 |

- **来源**：GitHub Dr-Sergey/learn_cpp 整理 + LLVM 官方博客
- **与 CPP-Bible 的关系**：UB 域"编译器优化与 UB"专题原子；PERF 域"为什么 -O2 更快"

## 三、LLVM IR 的 poison / undef / freeze 机制

### 1. poison 值（毒值）

- **nsw**（no signed wrap）：`add nsw` 有符号溢出 → 结果是 poison
- **nuw**（no unsigned wrap）：无符号溢出 → poison
- **exact**：`sdiv exact` 有余数 → poison
- **poison 传播**：poison 经过算术指令继续传播；到达有副作用的指令（store/branch/call）→ UB
- **设计目的**：支持投机执行——可以先执行可能溢出的操作，结果是 poison 而不是立即 UB，后续如果不用就没事

### 2. undef 值（已弃用）

- undef 表示"任意值"，每次使用可以观察到不同的值
- 正在被 poison 替代，仅用于表示未初始化内存的加载

### 3. freeze 指令（PLDI 2017）

- `freeze(x)`：如果 x 是 poison/undef，返回一个非确定值（但同一次 freeze 的所有使用返回相同值）
- 解决了 poison 传播到分支的问题——可以用 freeze 把 poison "解毒"
- **来源**：PLDI 2017 "Taming Undefined Behavior in LLVM"（Lee et al.）
- **可信度**：S（学术论文 + LLVM 官方文档）

### 4. 与 CPP-Bible 的关系

- UB 域"LLVM IR poison 机制"原子——这是理解编译器优化的底层钥匙
- 可以设计实验：`clang -S -emit-llvm` 查看 nsw/nuw 标记，对比 -O0 和 -O2 的 IR

## 四、Strict Aliasing（严格别名规则）

### 1. 规则内容

> 对象只能通过以下类型的指针/引用访问：
> 1. 同类型 T（含 cv 限定）
> 2. T 的有符号/无符号变体
> 3. char / signed char / unsigned char（字节访问例外）
> 4. 聚合/联合类型（包含上述类型的成员）

### 2. 优化效果

```cpp
void update(float *f, int *i) {
    *f = 3.14f;
    *i = 42;
    float x = *f;  // 编译器：int* 和 float* 不可能别名
                   // → *f 还是 3.14f，不需要重新 load
                   // → x = 3.14f（常量传播）
}
```

- TBAA（Type-Based Alias Analysis）pass 基于类型推断不别名
- -O2/-O3/-Os 默认开启 `-fstrict-aliasing`
- 可以重排读写、消除冗余 load

### 3. 类型双关（Type Punning）

```cpp
// ❌ UB：int* 和 float* 类型双关
float f = 1.0f;
int i = *(int*)&f;  // strict aliasing 违规

// ✅ 正确：memcpy（标准保证）
float f = 1.0f;
int i;
memcpy(&i, &f, sizeof(i));

// ✅ C++20：std::bit_cast（编译期优化为零开销）
int i = std::bit_cast<int>(f);
```

### 4. 经典案例：Fast Inverse Square Root（Quake III）

```cpp
float FastInvSqrt(float x) {
    float xhalf = 0.5f * x;
    int i = *(int*)&x;       // ← 类型双关，strict aliasing 下是 UB
    i = 0x5f3759df - (i >> 1);
    x = *(float*)&i;         // ← 又一次
    x = x * (1.5f - (xhalf * x * x));
    return x;
}
```

- 这段传奇代码在严格别名下是 UB——但因为历史原因，GCC/Clang 实际"宽容"了这种写法
- 现代正确写法：`memcpy` 或 `std::bit_cast`

### 5. C vs C++ 的 union 类型双关差异

- **C（C11 6.5.2.3）**：通过 union 不同成员读写是合法的（footnote 82 明确允许）
- **C++**：通过 union 非当前成员读取是 UB（但 GCC/Clang 作为扩展支持）
- **来源**：GCC 官方文档 + C/C++ 标准 + GitHub Gist（shafik 详细整理）
- **可信度**：S
- **教材价值**：S

## 五、常量折叠与"计数实验被 -O2 吃掉"的原理

### 1. 常量折叠（Constant Folding）

- 编译期计算全常量表达式：`7 * 24 * 60 * 60` → `604800`（直接 mov eax, 604800）
- 常量传播（Constant Propagation）：把已知常量值替换到使用处

### 2. 为什么计数实验会被吃掉（你项目的真实踩坑）

```cpp
// 你的实验：统计移动构造的分配次数
int alloc_count = 0;
void* operator new(size_t s) { alloc_count++; return malloc(s); }

int main() {
    Buf a;        // 构造：分配 1 次
    Buf b = a;    // 拷贝：分配 1 次
    Buf c = std::move(a);  // 移动：分配 0 次
    printf("%d", alloc_count);  // 期望输出 2
}
```

**-O2 吃掉的过程**：
1. 编译器发现 `alloc_count` 的值与输入无关（纯常量推导）
2. 常量传播：构造分配 1 + 拷贝分配 1 + 移动分配 0 = 2
3. 常量折叠：`printf("%d", 2)`——整个计数器和 operator new 都被消除
4. 汇编里没有 `call malloc`，但输出照样是 2——**完美的"伪证据"**

### 3. 为什么 volatile 能阻断

- `volatile` 变量的读写是**可观测副作用**，编译器不能消除
- `volatile int alloc_count = 0;` → 每次 ++ 都必须真实执行
- 汇编里出现 `call malloc`，与运行时互证

### 4. 你的项目已经固化的铁律（M2 §5）

> 计数/计时类实验必须 -O0 与 -O2 双跑，计数器必须 volatile；汇编层找不到调用点却"证实"了论断 → 判伪证据。

- **来源**：Stanford CS107 编译优化讲义 + Cornell CS4120 编译原理 + 你的项目 M2 实证方法
- **与 CPP-Bible 的关系**：这是你项目最有价值的"元教学"内容——教学生怎么验证自己的验证
- **可信度**：S
- **教材价值**：S

## 七、真实项目的 UB 优化 workaround

| 项目 | Flag | 禁用的 UB 优化 |
|---|---|---|
| Linux kernel | `-fno-strict-aliasing` | 严格别名（内核大量类型双关） |
| Linux kernel | `-fno-delete-null-pointer-checks` | 空指针检查删除 |
| Linux kernel | `-fwrapv` | 有符号溢出（部分架构） |
| PostgreSQL | `-fno-strict-aliasing` | 严格别名 |
| Python | `-fwrapv` | 有符号溢出 |
| 很多项目 | `-fno-strict-overflow` | 有符号溢出 |
