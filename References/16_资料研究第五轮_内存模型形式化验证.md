## 一、核心资料（S/A+ 级）

### 1. Linux Kernel Memory Model (LKMM)

- **类型**：形式化内存模型 + 工具链
- **来源**：Linux Kernel（tools/memory-model/）
- **链接**：https://docs.kernel.org/dev-tools/lkmm/docs/readme.html
- **核心内容**：Linux 内核有自己的内存一致性模型，用 "cat" 语言编写，由 herd7 模拟器执行——**穷举小 litmus test 的所有可能状态空间**，判断某个执行是否被允许。
- **解决的问题**：内存序对不对，不再靠人想，机器算
- **为什么重要**：**这是把"内存序正确性"从"人工推理"变成"机器验证"的里程碑**。Linux 内核用它验证 RCU、锁、原子操作的内存序正确性。之前四轮讲的"内存序会不会出问题"，这里给了确定性答案。
- **技术亮点**：
  - **cat 语言**：用关系代数描述内存模型（`po` = program order、`rf` = reads-from、`co` = coherence order、`fr` = from-read），模型是一组关系约束
  - **herd7 穷举**：给定 litmus test，输出所有可能的最终状态，标注哪些被允许、哪些被禁止
  - **LKMM 比 C11 更宽松**：内核大量使用控制依赖/地址依赖，这些在 C11 里不保证，但 LKMM 明确允许
  - **12 个分层文档**：simple.txt（新手）→ ordering.txt → recipes.txt → explanation.txt（专家），按读者水平递进
- **与 C++ 的关系**：C++11 内存模型也有 cat 形式化（herdtools7 自带 c11popl15.cat），可以用 herd7 验证 C++ 原子操作的内存序
- **与 CPP-Bible 的关系**：CONC 域"内存序可机器验证"的实验基础；证据卡可以新增"litmus test 验证"维度
- **可以放入哪个章节**：part09_concurrency（内存序）、part16_os（内核同步）
- **适合讲什么**：内存模型的形式化、litmus test、cat 语言基础、控制依赖
- **可以设计什么实验**：用 herd7 验证"MP（Message Passing）在 x86 上不可能 (1,0)、在 ARM 上可能"——直接对比两个架构的 cat 模型
- **历史背景**：2017 年合入 Linux 4.12，由 Alan Stern、Paul McKenney、Andrea Parri 等开发；持续维护至今
- **可信度**：S（Linux 内核官方，一手来源）
- **教材价值**：S

### 2. herdtools7 工具套件

- **类型**：开源工具（OCaml 编写）
- **来源**：Inria（法国国家信息与自动化研究所）/ herd/herdtools7
- **链接**：https://github.com/herd/herdtools7
- **核心内容**：四个工具：
  - **herd7**：通用弱内存模型模拟器——给定 cat 模型 + litmus test，穷举所有可能执行
  - **litmus7**：在真实硬件上跑 litmus test（汇编级），统计各结果出现次数
  - **diy7**：从简洁规格自动生成 litmus test 族
  - **mcompare7**：对比 herd7 模拟结果和 litmus7 硬件结果
- **解决的问题**：形式化模型 vs 真实硬件的对照验证
- **为什么重要**：**herd7 告诉你"理论上什么可能"，litmus7 告诉你"实际上发生了什么"**。两者对照可以发现 CPU 实现是否符合架构规范。
- **技术亮点**：
  - 支持架构：x86、x86_64、Power、ARM、AArch64、MIPS、RISC-V
  - 支持模型：C11、Linux LKMM、ARM、Power、x86-TSO、RISC-V
  - **klitmus7**：把 litmus test 编译成内核模块，在内核态跑（测试内核原语）
  - **在线模拟器**：http://diy.inria.fr/herd/ 可以直接在浏览器跑
- **与 C++ 的关系**：herd7 支持 C11 内存模型（`-model c11`），可以直接验证 C++ `std::atomic` 的内存序
- **与 CPP-Bible 的关系**：可以作为 CONC 域实验工具——学生写一段原子操作代码，用 herd7 验证内存序是否正确
- **可以放入哪个章节**：part09_concurrency、part15_toolchain
- **适合讲什么**：内存模型验证工具链、形式化方法
- **可以设计什么实验**：写一个错误的 acquire-release 配对，用 herd7 证明它允许某个不该允许的执行
- **历史背景**：源于 Peter Sewell（Cambridge）团队的 work，Inria Gallium 项目组维护；POPL/PLDI 多篇论文
- **可信度**：S（Inria 官方开源，学术+工业双重验证）
- **教材价值**：A+

### 3. ARM 官方学习路径：Herd7 and Litmus7 Test Primer

- **类型**：官方教程（含完整可运行示例）
- **来源**：Arm Developer（learn.arm.com）
- **链接**：https://learn.arm.com/learning-paths/servers-and-cloud-computing/memory_consistency/litmus_syntax/
- **核心内容**：用 MP（Message Passing）litmus test 完整演示：
  1. 写 litmus 文件（AArch64 汇编，P0 写 x 再写 flag，P1 读 flag 再读 x）
  2. 假设顺序一致：(1,0) 不可能
  3. herd7 模拟 ARM 模型：**(1,0) 是允许的**（Positive: 1）
  4. litmus7 在真实 ARM 硬件跑 100 万次：**(1,0) 出现 53040 次**
  5. 结论：ARM 违反顺序一致性，(1,0) 是真实可观测的
- **解决的问题**：形式化模型和真实硬件的对照——理论说可能，实际真的发生了
- **为什么重要**：**这是"弱内存模型不是理论玩具"的最直观证明**。53040/1000000 = 5.3% 的概率看到 (1,0)，这不是边角案例。
- **技术亮点**：
  - litmus test 格式：架构标签 + 初始状态 + 线程汇编 + exists 条件
  - herd7 输出：States 4（所有可能结果）、Positive: 1（条件成立的执行数）
  - litmus7 输出：Histogram（各结果出现次数），`*>` 标记条件成立的结果
  - **(1,0) 的成因**：P1 的两个 LDR 被重排——先读 x（得 0），再读 flag（得 1）
- **与 C++ 的关系**：MP 是 C++ 内存模型中最经典的 litmus test——`std::atomic<int> x, flag;` P0: x=1; flag=1; P1: if(flag==1) assert(x==1); 在 relaxed 下 assert 可能失败
- **与 CPP-Bible 的关系**：CONC 域"MP 测试"实验的完整教程；可以直接做成"x86 vs ARM 内存序差异"的可复现实验
- **可以放入哪个章节**：part09_concurrency
- **适合讲什么**：弱内存模型的实证、litmus test 写法、形式化验证流程
- **可以设计什么实验**：在 x86 上跑同一个 MP test（herd7 模拟 x86-TSO 应该显示 (1,0) 不允许），对比 ARM 结果
- **可信度**：S（ARM 官方教程，一手来源）
- **教材价值**：S

## 三、核心概念：litmus test 是什么

```
litmus test = 一小段并行程序 + 一个"exists"条件
            ↓
    herd7：穷举所有可能执行，回答"条件是否可能成立"
    litmus7：在真实硬件上跑百万次，统计条件出现的频率
```

**MP（Message Passing）测试**（最经典）：
```
P0: x = 1; flag = 1;
P1: if (flag == 1) { assert(x == 1); }
问：assert 可能失败吗？（即 flag=1 但 x=0）
```
- x86-TSO：不可能（store 不重排）
- ARM 弱模型：可能（P1 的两个 load 可以重排），herd7 证实 + litmus7 实测 5.3% 概率

**这就是"内存序可以机器验证"的含义**——不再靠人推理"会不会重排"，直接让 herd7 算。

## 九、发现的知识空白

1. **内存序的机器验证完全未覆盖**——全书只讲"应该用什么内存序"，不讲"怎么验证用对了"
2. **litmus test 概念缺失**——这是并发领域的标准验证方法，教材应该引入
3. **形式化方法无内容**——cat 语言、关系代数、状态空间穷举，这些是高级主题但有教学价值
4. **跨架构内存序差异无实验**——没有"x86 vs ARM"的可复现对比实验
5. **C++ 内存模型的形式化定义未引用**——c11popl15.cat 是 C++ 内存模型的"源代码"
