### 2.1 校验范围

| 类别 | 文件 | 说明 |

| 测试配置（2） | conftest.py | pytest 配置（SERIAL_EXTRA/SLOW_MODULES） |
| | pyproject.toml | 项目配置（pytest markers/addopts） |

### 2.2 校验机制

- **checksum 校验**：每个 CORE_TOOLS 和测试配置文件都有 SHA-256 checksum，存储在 tools/.tool_checksums
- **--check**：验证当前文件 checksum 与基准一致（exit 0 = 一致，exit 1 = 不一致）
- **--update**：更新基准 checksum（苦力唯一允许跑的 integrity 命令，且只能用 --update）
- **--check-test-config**：验证测试配置 checksum（conftest.py/pyproject.toml）
- **--check-merkle**：验证 Merkle 根（L3 供应链溯源）

### 2.3 修改规则

- 修改 CORE_TOOLS 后，必须同 commit 运行 `python tools/tool_integrity.py --update` 并重钉 .tool_checksums
- 修改 conftest.py 后，必须运行 `python tools/tool_integrity.py --update --no-update-merkle` 重钉 test_config
- metrics_collector.py **不在** CORE_TOOLS 内，修改后无需 --update

## 六、设计意图分析

### 1. 四层信任根是"纵深防御"的设计（609 后全落地）
L1 工具完整性（checksum）→ L2 治理文档防护（manifest+弱化扫描）→ L3 供应链溯源（Merkle+chain+in-toto+merkle_proof）→ L4 外部时间锚（OpenTimestamps，609 D1 已实现）。四层纵深防御全落地，任何一层被攻破，下一层仍能检测。这是"生成者不能兼任判断者"第一原则在信任根层的体现——信任根本身也需要被验证。

### 2. Merkle 跟踪 5 类目录是"受控目录零污染"的硬保证
atoms(29)/evidence(57)/Examples(1541)/Book(183)/mutation_baselines(7) 五类目录被 Merkle 跟踪，任何修改都会被检测。这是"受控目录零污染"的硬保证——不满足于"git diff 为空"，而是证明"Merkle 根一致"。

### 3. 585 三攻击封堵是"红队驱动的信任根加固"
585 异族红队实锤了 3 个 meta 攻击（规则定义不在覆盖内/豁免台账篡改/人签自证），601 批次做了三攻击封堵回归（12 passed）。这是"红队驱动"的设计——不是"假设安全"，而是"被攻破后加固"。残余风险显式登记（进程内运行时篡改/身份认证/manifest 自身），不掩盖。

### 4. governance 弱化扫描是"治理文档也需要被审计"的设计
governance_doc_guard.py 不仅校验 manifest，还扫描治理文档中的"降级为 warn""跳过门禁""豁免毒样例"等弱化指令。这是"治理文档也需要被审计"的设计——治理文档本身可能被弱化，需要被检测。high=55 需人审确认是"描述"还是"真实攻击指令"，不自行判定语义。

### 5. 单用户结构性上限是"诚实声明"的纪律
OpenTimestamps 只证"存在时间"不证"身份"、git 作者可自设、L2+ 不可达——这些单用户结构性上限在三处明说。这是"度量诚实化"的体现——不掩盖结构性上限，而是明说"在当前架构下不存在"。
