# 09 · 方向 9：数据完整性与时态数据管理

> 来源：【已查证】W3C PROV=w3.org/TR/prov-overview/(2013 推荐标准)；SQL:2011 双时态；CRDT/OT【一方称：领域常识】；Merkle【已查证】1979(本探针实测 root=27c2…)。

## 9.1 技术适用性

| 技术 | 核心 | 对本项目价值 | 可用性 |
|---|---|---|---|
| 时态 DB(双时态) | 有效/事务时间 | prop_asof 四轴 | 需 DB(基础设施) |
| W3C PROV | 溯源实体-活动-者 | **overturned/人审溯源** | 是(模型) |
| Merkle 树/DAG | 不可篡改完整性 | **数据完整性(已探针)** | 是(纯库) |
| CRDT/OT | 无冲突复制 | 未来多人协作 | W |
| ACID/MVCC | 快照隔离 | 跑批根隔离(579/580) | 是(概念) |
| DVC/LakeFS | 数据版本 | data/mutation 基线 | 部分(需工具) |

## 9.2 手搓实现 vs 标准技术
- **prop_asof(四轴快照)**：手搓，时间从 git 卡提交派生。标准做法=双时态 DB(SQL:2011)。**对比**：DB 更标准但需基础设施；手搓足够本项目规模，且 git 本身已是时态后端。**结论**：不必引入 DB，保留 git 作为时态后端 + 显式 PROV 元数据。
- **overturned 事件通道(jsonl)**：手搓。标准=W3C PROV 的 agent-activity-entity 三元组。**对比**：PROV 提供更丰富的溯源语义(谁/何时/为何改)。**可借鉴**：把 jsonl schema 对齐 PROV(加 agent/activity)，纯模型不改存储。
- **full_baseline_v*.json**：手搓版本。标准=DVC。**对比**：DVC 重，本项目用 git + 版本号足矣。

## 9.3 Merkle（已探针实测）
- 108 文件 Merkle root=27c2…，树高 7，篡改检测通过。可作为 data/ 完整性层：定期算根、签名/时间戳，任何人可重算验证。
- 价值：把"逐文件校验"升级为"单一可签名根"，与方向 6 的 in-toto 溯源天然衔接（Merkle 根是 attestation 的输入）。

## 9.4 现在能用 vs 需基础设施
- 纯库可：Merkle 完整性、PROV 对齐元数据、快照隔离概念落地。
- 需基础设施：时态 DB、DVC、CRDT(多人)。

## 9.5 看似相关但不适用（反例）
1. **完整时态数据库(SQL:2011 双时态)**：需部署 DB 引擎，本项目数据量(79 命题)与 git 时态后端已够；引入 DB 是过度工程。
2. **CRDT/OT 无冲突复制**：为分布式多写设计，本项目单用户、未来多人也属低频协作，CRDT 的复杂性无收益。

## 9.6 本项目现状
prop_asof=手搓四轴(从 git 派生)；overturned=手搓 jsonl；数据版本=手搓 full_baseline_v*。缺口：无 Merkle 完整性根、overturned 未对齐 PROV、无签名时间戳。
