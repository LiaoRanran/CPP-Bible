## 核心结论

1. **"规则数"不是能力指标，"工具间重叠率"才是**：Lenarduzzi 等人 2023 年 JSS 的大规模对比（**47 个项目 / 74,486 个类**）实测出**六款主流静态分析工具的总重叠率低于 0.4%**，且**没有任何一条警告被三个及以上工具同时报出**。这意味着"再加一个分析器"的边际检出几乎必然为正——对阙疑来说，**多工具串联是划算的**，而"选一个最好的工具"是伪命题。
2. **误报是静态分析的第一成本项，且必须量化后才敢接进 CI**：同一篇论文实测精度区间 **18%（SonarQube）—86%（Checkstyle）**，而 Checkstyle 的高精度是因为它主要报格式/文档问题（对功能缺陷无价值）；**Coverity Scan 实测精度仅 37%（误报率 63%）**。因此阙疑若把 clang-tidy/cppcheck 结果纳入判决证据，**必须显式声明"每条工具规则的实测精度"**，否则等于把 63% 的噪声包装成证据。
3. **免费额度上，阙疑（双非本科生 / 个人开源项目）完全用得起全套商业级工具**：PVS-Studio 对**个人非商业开源项目**提供**一年期、可年度续期**的免费许可（条件是 README 加署名 + 修复提交里提及工具）；Coverity Scan 对开源项目长期免费；SonarCloud 对**公开仓库不限代码行数免费**。这是一个被严重低估的资源位。

## 精确数字与案例

### 1. clang-tidy：检查数、命名方案与配置面

**来源**：https://clang.llvm.org/extra/clang-tidy/ （本次抓取全文）+ https://clang.llvm.org/extra/clang-tidy/checks/list.html

- **检查总数：官方未公布整数**。按 `checks/list.html` 的条目统计，主要前缀及数量约为：`bugprone-` **105**、`clang-analyzer-` **约 120**、`readability-` **约 100**、`modernize-` **约 55**、`cppcoreguidelines-` **约 45**、`cert-` **43**、`misc-` **约 35**、`google-` **约 30**、`performance-` **约 27**、`llvm-` **约 20**、`fuchsia-` 9、`objc-` 9、`portability-` 7、`llvmlibc-` 4、`concurrency-` 2、`darwin-` 2、`mpi-` 2、`openmp-` 2、`linuxkernel-` 1，合计**约 650+**。**权威数字请用 `clang-tidy -list-checks -checks='*'` 现取**（本文的 650+ 是条目估算，见盲区）。
- **命名方案**：`<类别前缀>-<检查名>`，如 `bugprone-use-after-move`、`readability-function-size`。编译诊断类以 `clang-diagnostic-` 开头，其中 **`clang-diagnostic-error` 不可禁用**（官方原文）。
- **选择语法**：`-checks=` 接逗号分隔的 glob 列表，**按出现顺序处理**，`-` 前缀表示从启用集移除。官方示例：
  ```
  clang-tidy test.cpp -checks=-*,clang-analyzer-*,-clang-analyzer-cplusplus*
  ```
- **配置**：`.clang-tidy`（YAML），从**最近的父目录**逐级查找；命令行选项优先于配置文件；`InheritParentConfig: true` 可继承父配置。可配置字段包括 `Checks`、`CheckOptions`、`HeaderFilterRegex`、`WarningsAsErrors`、`HeaderFileExtensions`（默认 `['', 'h','hh','hpp','hxx']`）、`ImplementationFileExtensions`（默认 `['c','cc','cpp','cxx']`）、`CustomChecks`（**基于 Clang-Query 语法的用户自定义检查**）、`SystemHeaders`、`User`。
- **`--dump-config`** 打印当前有效配置；`--verify-config` 校验配置；`--export-fixes=<file>` 导出修复；`--fix` / `--fix-errors` / `--fix-notes` 应用修复。
- **抑制**：`NOLINT`（同行）、`NOLINTNEXTLINE`（下一行）、`NOLINTBEGIN`…`NOLINTEND`（区间），可带检查名列表与 glob，如 `// NOLINT(google-explicit-constructor, google-runtime-int)`。**负向 glob 被忽略**。

**对阙疑的价值**：`CustomChecks` + Clang-Query 意味着阙疑可以把**自己的部分判决规则直接写成 clang-tidy 自定义检查**，从而复用 clang 的 AST 与编译数据库（`compile_commands.json`），不必自己解析 C++。这是"复用而非重造"的最低成本路径。

### 2. cppcheck：6 个严重级、4 种抑制、以及"基线"CI 工作流

**来源**：https://github.com/cppcheck-opensource/cppcheck/blob/main/man/manual.md （本次抓取全文）

- **严重级（6 个，原文）**：`error`（执行时存在 UB 或错误，如内存/资源泄漏）、`warning`（执行时**可能**存在 UB）、`style`（风格/冗余/const/运算符优先级/可能错误）、`performance`（常识性性能建议，**不保证有可测量收益**）、`portability`（实现定义行为、64 位可移植性、某些"可能按你期望工作"的 UB）、`information`（配置问题）。
- **检查级别**：原文"The 'normal' check level is chosen by default"；**默认 C 标准 `c23`、C++ 标准 `c++26`**（原文）。
- **`--enable`**：手册只出现 `--enable=style` 与 `--enable=all` 两个值；`unmatchedSuppression` 检查属于 `--enable=all`。**从 remark 示例可推断 `style` 默认关闭**（需显式 `--enable=style` 才见 `unreadVariable`）。
- **未给出的数字**：手册**未提供检查项总数**，也**未给出完整 `--enable` 选项列表**（见盲区）。
- **MISRA 覆盖**：原文明确"开源版 Cppcheck 的 MISRA 检查器**仅部分覆盖** MISRA 规则，**完整覆盖需 Cppcheck Premium**"——这是一条重要的免费/商业边界。
- **4 类抑制**：① 纯文本（`--suppress=memleak:src/file1.cpp`、`--suppressions-list=file`）；② XML（`--suppress-xml=`，含 `<id>/<fileName>/<lineNumber>/<symbolName>/<hash>`）；③ 内联（`--inline-suppr` 激活，`// cppcheck-suppress aaaa`、`[aaaa, bbbb]`、`-begin/-end`、`-file`、`-macro`、`symbolName=`）；④ **基线抑制**。
- **`<hash>` 是关键设计**：cppcheck 为每个错误基于**相关代码内容**（而非行号）计算 hash，因此**行号漂移不影响抑制有效性**；`<hash>` 可单独用或与 `id/fileName/lineNumber/symbolName` 组合（组合时须全部匹配）。
- **基线 CI 工作流（官方推荐，四步）**：
  ```sh
  # 1. 生成基线
  cppcheck --enable=style --xml src 2> baseline-results.xml
  # 2. 转成抑制文件
  python3 generate-baseline-suppressions.py baseline-results.xml suppressions.xml
  # 3. 后续运行（CI / pre-commit 核心命令）
  cppcheck --enable=style --xml --suppress-xml=suppressions.xml src
  # 4. 想接受当前状态为新基线时，重跑 1-2（会覆盖 suppressions.xml）
  ```
  原文强调："**`suppressions.xml` 必须由所有在此代码库上运行 Cppcheck 的人共享，包括 CI**"。基线**无需保持同步**：被抑制的代码修好后条目变"死条目"但**不必手动清**，且 `unmatchedSuppression` 检查**不会**对带 `<hash>` 的条目报警。
- **官方自陈的局限（原文）**："The checks in Cppcheck are **not perfect**. There are bugs that should be found, that Cppcheck fails to detect."；设计目标是"**detect only real errors... and generate as few false positives as possible**"；静态分析**不能替代** careful design / testing / dynamic analysis / fuzzing。模板递归上限 **100**（超过则放弃分析）；头文件过滤**不能用 `-i`**，必须用 suppressions。
- **升级风险（原文）**：**升级 cppcheck 会直接影响 hash**——若新版改了消息措辞，hash 变化会导致已基线的警告"复活"，即使代码未变。**这条必须写进阙疑的可重复性章节**（固定工具版本）。

### 3. 六工具大规模对比（本文最重要的量化来源）

**论文**：Valentina Lenarduzzi, Savanna Lujan, Nyyti Saarimäki, Fabio Palomba, *"A critical comparison on six static analysis tools: Detection, agreement, and precision"*，**Journal of Systems and Software (JSS) 2023**，DOI **10.1016/j.jss.2022.111575**（arXiv:**2101.08832**，ar5iv HTML 版已抓全文）。

**规模**：数据来自 **Qualitas Corpus**（Release 20130901，**112 个 Java 系统 / 754 个版本 / 1800 万+ LOC / 16,000 包 / 200,000 类**）；因两个工具无法分析全集，最终纳入 **47 个项目**，共 **74,486 个类 / 169,763 个方法**。

**六工具与检出**（47 个项目上）：

| 工具 | 版本 | 规则数（检测能力） | 检出规则数 | 检出警告次数 |
|---|---|---|---|---|
| Better Code Hub | — | 10 | 8 | 27,888 |
| CheckStyle | 8.30 | 173 | 88 | 9,686,813 |
| Coverity Scan | 2017.07 | 130（文档受限） | — | **7,431** |
| FindBugs | 3.0.1 | 424 | 255 | 33,704 |
| PMD | 6.23.0 | 305 | 275 | 3,380,493 |
| SonarQube | LTS 6.7.7 | 413 | 180 | 418,433 |
| **合计** | | | **936 条被违反的规则** | **13,554,762 次违反** |

**单条警告榜首**：Checkstyle `IndentationCheck` **3,997,581 次**；PMD `LawOfDemeter` 505,947；SonarQube `S1213` 30,888；FindBugs `BC_UNCONFIRMED_CAST` 2,840；**Coverity Scan `Dereference null return value` 1,360**。

**重叠度（RQ2）——本文最硬的数字**：
- 类级总重叠 **18,598 次 / 0.417%**；行级总重叠率约 **0.4%**。
- 最高对：**FindBugs–PMD 9.378%**；最低对：**Checkstyle–PMD 0.144%**。
- 其他：BCH–PMD 3.646%、FindBugs–Checkstyle 3.753%、SonarQube–FindBugs 2.518%、SonarQube–PMD 0.98%、SonarQube–Checkstyle 0.357%；Coverity 各类配对 117–128 次（约 1.5%–1.7%）。
- **原文结论**："**未发现任何涉及三个及以上工具的重叠**"。

**精度（RQ3）——分层抽样 + 双人标注**：
- 抽样规模：95% 置信区间、5% 误差，BCH 375 / Coverity 367 / SonarQube 384 / Checkstyle 384 / FindBugs 379 / PMD 380 条。
- **标注者一致性 Krippendorff's α = 0.84**（高于 0.80 阈值）。

| 工具 | 抽验数 | 真阳性 | **精度** | 误报率 |
|---|---|---|---|---|
| Checkstyle | 384 | 330 | **86%** | 14% |
| FindBugs | 379 | 217 | **57%** | 43% |
| PMD | 384 | 199 | **52%** | 48% |
| **Coverity Scan** | 367 | 136 | **37%** | **63%** |
| Better Code Hub | 375 | 109 | 29% | 71% |
| SonarQube | 384 | 69 | **18%** | **82%** |

- **原文对 Checkstyle 高精度的解释**：其警告"多为文档/格式类问题，**不影响功能**，宜与其他工具配合使用"。
- **SonarQube 的负载**：平均**每个类输出 47.4 条违规**。
- **召回率未评估**——原文明确因缺乏完整 ground truth 而列为未来工作。**这是引用该论文时必须声明的边界**。

### 5. 反方证据：SAST 的失败模式可能不是"误报"而是"漏报"

**论文**：*"An Extensive Comparison of Static Application Security Testing Tools"*，**EASE 2024**（arXiv:**2403.09219**，本次已提取全文 10 页）。结论原文：

> "our study shows that SASTTs **excel in Precision while falling short in Recall**; i.e., **false negatives are more than false positives**."

**这与"误报是主要问题"的流行叙事相反**，也与上表（精度 18%–86%）形成张力。两篇论文的口径差异在于：JSS 2023 用的是**工具默认配置 + 全量规则**（含大量 style 规则），EASE 2024 用的是**安全专用基准（Juliet Test Suite, JTS）**。**写稿时必须区分这两个口径**——否则会得出相反结论。

**行业基准数字（二手，需谨慎）**：getautonoma.com 的对比文给出——**未调优 SAST 误报率 60–90%，调优后 10–20%**；**SonarQube 默认配置在典型 Java/TS 代码库上 40–60% 被标为非问题**；Veracode **厂商自述 <1.1%**（非独立验证）；建议在 **30 天节点审计误报率，若 >40% 被抑制/驳回则需先调优**。该文还给出一个成本模型：10 人团队、每人每周 4 个 PR、每周 40 次扫描、每次 12 个发现、60% 误报 → **每周 288 个误报需人工审查，按每个 5 分钟计约 24 开发者小时/周**。

## 对阙疑的 3 条具体行动

1. **建"双工具串联 + 逐规则精度标注"的最小配置，并先做一次自测精度实验**。
   具体：只接 **clang-tidy + cppcheck** 两个（理由：完全免费、可离线、可固定版本；Coverity/PVS-Studio/SonarCloud 作为"补充轮"）。产出 `_arch_v46/34_静态分析接入设计.md`，含：
   - `.clang-tidy` 片段（**只开 `bugprone-*`、`clang-analyzer-*`、`performance-*`、`portability-*`，明确不开 `readability-*`/`modernize-*`**——理由：JSS 2023 证明风格类规则虽精度高但"不影响功能"，混进判决证据会稀释信号）；
   - `suppressions.xml` **基线工作流**（照抄 cppcheck 官方四步，并**固定 cppcheck 版本号**，因为升级会改 hash 使基线复活）；
   - **精度自测实验**：从 `data/defect_fixtures/defects.json` 的 **15 条真实缺陷夹具**里，人工标注每条是否被 clang-tidy/cppcheck 报出，算出**两个工具在本仓库上的实测精度与召回**。**预期**：由于只有 15 条夹具，召回率的分母极小，**必须用 Clopper-Pearson 区间**（见方向 24）而非点估计。这一步产出的"本仓库精度"数字，比引用任何论文都更有说服力。

2. **把"多工具串联"写进方法节，并用 0.4% 重叠率论证其必要性**。
   具体：在论文 Method 节加一句可直接引用的表述——"依据 Lenarduzzi et al.（JSS 2023, DOI 10.1016/j.jss.2022.111575）在 47 个项目上的实测，主流静态分析工具间的警告重叠率**低于 0.4%**，且**不存在三工具共报**；因此本工作采用多工具串联而非单一工具"。**同时必须补上该论文的两条边界**：(a) 其主体是 **Java** 项目，**不能直接外推到 C++**（原文的 threats to validity 自己承认"仅限开源 Java 项目"）；(b) **未评估召回率**。**加上这两条边界，引用才不会被审稿人抓住**。

3. **申请 PVS-Studio 免费许可，并把它当作"第三方独立验证者"用在缺陷夹具上**。
   具体：① 确认资格——**双非本科生的个人开源项目**完全符合 PVS-Studio 的"personal creative projects"条款（**且允许接受捐赠**）；② 履行两条义务——README 加指定 Markdown 片段、在修复提交里注明"Fixed issues found by PVS-Studio"；③ **用途设计**：只把 PVS-Studio 跑在 `data/defect_fixtures/` 的 **15 条真实缺陷**上，报告"PVS-Studio 能报出其中几条"，作为**独立于阙疑内核的第三方证据**。**这一步的战略价值**：阙疑的核心主张是"可被独立验收"，那么**用第三方商业分析器对同一批缺陷做交叉验证**，正是"独立验收"的现成实现——而且免费、合规、可写进论文的 Threats to Validity 章节（"我们使用了一个商业闭源分析器作为补充，其结果不由本项目控制"）。**注意**：PVS-Studio 的免费许可**禁止镜像与 fork**，因此**不可**在他人 fork 上使用。

## 盲区（诚实标注）

1. **clang-tidy 的检查总数（约 650+）是我对 `checks/list.html` 条目的估算，官方未给整数**。权威数字必须用 `clang-tidy -list-checks -checks='*'` 在**固定版本**上现取。各前缀的计数（bugprone 105 / cert 43 等）同样为估算。
2. **cppcheck 的检查项总数、完整 `--enable` 选项列表均未查到**：官方手册未给出，需要读源码或官网 FAQ。
3. **六工具对比论文的"Coverity Scan 规则数 130"标注为"文档受限"**，实际规则数可能更高；Coverity 是**闭源商业工具**，其内部规则集不可公开核查。
4. **该论文的精度数字来自"工具默认配置"**，与"调优后"的精度不可比；且**主体是 Java 项目**，**C++ 外推需谨慎**。**召回率完全未评估**。
5. **EASE 2024（arXiv:2403.09219）与 JSS 2023 的结论方向相反**（前者称 SAST 漏报多于误报），我**未逐字核对两者的实验设置差异**（基准、配置、阈值），只确认了各自的结论句原文。**两篇的张力需要进一步核实后才能写进论文**。
6. **getautonoma.com 的"60–90% / 10–20% / 40–60%"是商业博客的二手数字**，未给出可复现方法学；**Veracode <1.1% 是厂商自述**，**未经独立验证**。这些数字**不宜作为论文证据**，只能作为"业界共识"的背景描述。
