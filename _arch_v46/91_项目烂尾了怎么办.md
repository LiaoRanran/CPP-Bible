## 核心结论

1. **"烂尾"是开源/科研单人项目的默认结局而非例外**：实证数据给出的量级是——GitHub 新建项目约 **95%** 在一年内停止维护（Kula 等，EMSE 2022 引言引用）；流行项目里约 **12%**（618/5000）在抽样时点已停止维护（Coelho & Valente, ESEC/FSE 2017）；发生核心开发者流失（TFDD）的项目中 **59%** 永久死亡（Avelino 等, 2019）。所以阙疑一旦烂尾，**不是你不行的证据，而是基准率**；真正稀缺的能力是"知道什么时候该收尾，并把它收得体面"。
2. **止损与续命之间有一条可量化的判定线**：不是"我还能不能坚持"，而是"**外部信号是否还在增长**"。Avelino 等的存活分析给出了硬指标：TFDD 之后仍存活的项目，其后提交数中位数 **505 commits**，死亡项目仅 **126**（p=5.02×10⁻²²，Cliff's δ=0.64）；且**存活项目在流失时刻更年轻**（中位 1,095 天 vs 死亡项目 1,460 天，p=3.4×10⁻⁷）。对阙疑而言，这意味"再撑 6 个月看看"必须绑定可观测的增长指标，否则只是延长死亡。
3. **对阙疑这个具体项目，"烂尾"的最大损失不是论文，而是"可被独立验收"这套工程资产**：`gate_engine.py` 3826 行 + 67 条规则 + 452 条判决账本 + 30 seed 盲 holdout 的复现包，本身就是一个**可迁移的工程能力证明**。归档 ≠ 抹除，只要按 CHAOSS 的四步流程收尾（识别趋势 → 诊断 → 补数据 → 执行变更），这个仓库在求职/申研里仍然是资产。

## 精确数字与案例

### 一、基准率：烂尾有多普遍（把"失败"还原成常态）

**1）95% 的一年死亡率。** 这个数字的原始出处常被误引。可查到的直接表述来自 *Empirical Software Engineering*（EMSE）2022 年第 27 卷第 1 期论文《Studying donations and their expenses in open source projects: a systematic literature review》（DOI: 10.1007/s10664-021-10060-y），其摘要/引言原文写："**Almost 95% of open source projects are no longer maintained after a year.**"（ACM DL 条目：https://dl.acm.org/doi/10.1007/s10664-021-10060-y ）。**注意口径**：这是"一年内不再维护"的**粗略经验值**，样本口径与"维护"的定义在原文中未必严格，属于**广泛引用但需谨慎**的数字。OpenPledge 2024-02-18 的博客把它转述为"95% of newly created open source projects meet abandonment within a year"（https://www.openpledge.io/abandoned-open-source-projects.html ）。

**2）流行项目也会死：12%。** Coelho & Valente 在 ESEC/FSE 2017 的论文《Why Modern Open Source Projects Fail》里，从 GitHub **top-5,000** 星标项目（2016 年 9 月快照）中筛出疑似停止维护者：**628 个（13%）**过去一年无提交，**207 个（4%）** README 含 "deprecated" 等弃用词（人工核查后 **76 个**为真阳性，即 37%）。清洗后最终 **618 个**（占 top-5,000 的 **12%**）。问卷发给 **414 名**维护者，回收 **118 份**（响应率 **29%**），最终锁定 **104 个**"已失败"项目。DOI: 10.1145/3106237.3106246。

**3）核心开发者流失后的存活率：41%。** Avelino、Constantinou、Valente、Serebrenik 的《On the abandonment and survival of open source projects: An empirical investigation》（arXiv:1906.08058，IEEE，2019）分析了 **1,932 个** GitHub 流行项目（Ruby 398 / JS 342 / C-C++ 335 / PHP 334 / Python 297 / Java 226）。其中 **315 个（16%）**发生过 TFDD（Truck Factor Drop，核心开发者流失）；这 315 个里只有 **128 个存活（41%）**。也就是说，**核心开发者一走，项目立刻进入"六成会死"的赌局**。

**4）"一个人维护"是常态而非异常。** 同一论文报告：**57% 的项目 Truck Factor = 1**（一个人挂了项目就停），25% 为 TF=2，TF>5 的不足 6%。阙疑目前是**单人项目**（TF 严格等于 1），属于风险最高的一档——这是结构性事实，不是道德问题。

**5）科研软件稍微好一点，但没好太多。** 2025 年 FSE 论文《Scientific Open-Source Software Is Less Likely to Become Abandoned Than One Might Think: Lessons from Curating a Catalog of Maintained Scientific Software》（arXiv:2504.18971，ACM DL: 10.1145/3729369）用 LLM 对 World of Code 中的公开仓库做科学软件分类，并用生存模型估计废弃风险。结论是"科学开源软件被废弃的概率**低于直觉**"，但论文强调这是**经过筛选的目录**（本身偏向仍被维护的项目）的结论，存在选择偏差。**未核实**：该论文给出的具体生存曲线数值（hazard ratio）本次未逐字核对原文。

### 二、真实烂尾案例（2025–2026 最鲜活的三个）

**案例 A：pgBackRest（PostgreSQL 备份工具，13 年）。** 2026-04-27/28，作者 **David Steele** 在 LinkedIn 与 GitHub 公告停止维护，稳定版停在 **v2.58.0**，仓库被归档为只读。Percona 社区博客《pgBackRest is archived, what now?》（2026-04-28，https://percona.community/blog/2026/04/28/pgbackrest-is-archived-what-now/ ）记录了此事。**关键后续**：社区在 2026-04-28 立刻发起延续项目 **pgBunker**（"Community-maintained continuation of pgBackRest"，https://github.com/pgbunker/pgbunker ）——这正是 Avelino 论文说的"由 newcomer 恢复"路径（该论文中 48% 的存活项目由新人救活）。维护者自述理由是"和所有人一样，我也需要谋生"（腾讯新闻 2026-04-28 转载）。

**案例 B：MinIO（近 60k stars，对象存储）。** 2025-12-03 官方宣布开源版进入"维护模式"：不再接受新功能、改进或 PR；2026-02 进一步动作，2026-09-14 前后连 Docker 镜像也被删除（Appinn 报道 https://www.appinn.com/minio-remove-docker-images/ ）。时间线整理见 CSDN《MinIO官宣停摆，开源用户何去何从？》（2026-09-21，https://blog.csdn.net/rustfs_contrib/article/details/156312889 ）。**教训**：**"维护模式"是一种比"归档"更暧昧、更伤用户的中间态**——代码冻结、安全支持有限、社区支援停止，但没有一个清晰的"我死了"信号。阙疑如果走到这一步，**应当直接归档，而不是宣称"维护模式"**。

**案例 C：Apache Attic（制度化的"项目墓地"）。** ASF 有正式的退役流程与墓地组织 Apache Attic（https://attic.apache.org/projects.html ，退役跟踪页 https://attic.apache.org/tracking.html ）。它证明：**"体面地把项目送进墓地"是被顶级基金会制度化的标准动作**，不是耻辱。VMware 也有 `vmware-archive` 组织做同样的事。

### 三、方法论：怎么判断该止损还是续命

**1）CHAOSS 从业者指南的四步流程**（https://www.chaoss.community/practitioner-guide-sunset/ ，2026-09-20 更新）：
- **Step 1 识别趋势**：看三组指标——Change Requests（同时看打开与关闭；长期未决的 open PR 是废弃信号）、New Issues（长期几乎无新 issue 可能是被放弃）、Technical Forks（不只数 fork 数，还要看 fork 是否**仍在更新**——更新的 fork 是"活用户"信号）。
- **Step 2 诊断**：区分"真废弃"与"已稳定"（例：某些复杂数学函数的小库**不需要**频繁更新，看似废弃实则被广泛使用）。工具：OpenSSF **Criticality Score**（计算依赖该项目的下游数量）+ 社区 `sunset.py` 脚本。
- **Step 3 补数据**：Clones、Code Changes Commits、Release Frequency、Project Popularity、包管理器使用指标。**特别提醒**：不要忽略空仓库/仅含 README 的仓库，应归档（保留记录成本极低）。工具：GitHub OSPO 的 `empty-repos` Action。
- **Step 4 执行变更**：①沟通（README 顶部声明废弃 + 推荐替代品；Slack/邮件列表/论坛/社媒；wiki/看板/官网；npm/PyPI/RubyGems 加弃用警告；通知已知用户）；②代码与安全审查（**至少检查密钥、密钥文件、PII 并删除或脱敏**，处理 Dependabot/CodeQL 告警）；③关闭/标注 issues（`won't fix`）；④处理变更请求；⑤更新仓库元数据（`code.json`/`publiccode.yml`/`codemeta`）；⑥清理（**审计并移除不再需要的 committer 权限**、删陈旧分支）；⑦归档；⑧可选加入 **Software Heritage** 长期保存。

**2）GitHub 官方的 do / don't（2025-05-06，https://github.blog/open-source/maintainers/dos-and-donts-when-sunsetting-open-source-projects/ ）**：
- **Don't 拖太久**：计算生物学家 **Olga Botvinnik** 说她最想告诉年轻的自己的一句话是"应该**更早**下线 prettyplotlib"；她的导师告诉她"**知道何时结束一个项目，和完成它一样好**"（"knowing when to end a project is just as good as finishing it"）。
- **Do 给别人留门**：Brett Terpstra 维护 **100+** 个仓库，退役前总是先找人接手。
- **Do 保留代码在线**：**归档（archive）而非删除**。Botvinnik 特别指出："任何考虑把自己软件下线的人，都应该考虑是否会给科学界和学术界的人**造成可复现性问题**"。
- **Don't 无预告拔插头**：Terpstra 至少提前 **一个月**通知；他自己即使立刻不干了，也留 **30 天窗口**处理 issue、帮用户迁移。
- **反例：不交接也可以**。BoltDB 作者 **Ben Johnson** 选择直接退役 BoltDB，把人导向 fork **BBolt**（etcd-io/bbolt），而不是让别人接手原仓库——理由是"我的名字和声誉和这个项目绑得太紧……我不想把自己的声誉交到别人手里"。**这对阙疑有直接启示**：如果阙疑被某个下游/学术团队"接手"，作者需要提前想清楚是"交给他们"还是"指引他们 fork"。

**3）"活过你这份工作"的十条建议。** Littauer、Wilson 等 21 位作者的《10 quick tips for making your software outlive your job》（arXiv:2505.06484，v1 2025-05-10，v2 2025-10-28，14 页 1 图）明确针对"关键人员因生病/倦怠/家庭/经费中断/职业转向而离开，导致研究软件被废弃"的场景。**一个极具教育意义的细节**：该文 v2 的更新说明写着"移除了 Rule 7 中不准确、**极可能是幻觉（hallucinated）**的参考文献"——**连 21 位资深作者合写的建议文都栽在编造引用上**。这对阙疑的"防幻觉"叙事是**双向证据**：既是需求证明，也是警告（你的验证器如果自己引用了不存在的文献，会立刻失去可信度）。

**4）规模小反而更容易活。** Avelino 等发现：存活项目在 TFDD 时刻的规模**更小**（开发者中位 32 vs 47，p=2.2×10⁻⁴，δ=0.26；提交中位 384 vs 694，p=2.6×10⁻⁴，δ=0.25；文件中位 54 vs 85）。**这对阙疑是好消息**：3826 行内核 + 37 实卡是"小项目"，按实证规律，它的可接手性优于大型项目。同时论文指出"项目小或简单"本身就是新人愿意接手的原因之一（2/58 条回答，7%）。

**5）最有效的"续命"手段：写贡献指南。** Coelho & Valente 对比 104 个失败项目 vs 104 个 top 项目：**贡献指南（Contributing）采用率 16% vs 72%（large 效应量）**、CI 27% vs 68%（medium）、License 61% vs 88%、Home Page 58% vs 87%。**这是全论文效应量最大的单项**。阙疑如果要"续命"，最高性价比动作不是再写规则，而是把 `CONTRIBUTING.md` 从零补上。

### 四、失败原因：阙疑会怎么死（对照表）

Coelho & Valente 的 104 个失败项目，失败原因分三大组、共 9 类（票数合计 110，因 6 个项目多原因）：

| 组 | 原因 | 项目数 |
|---|---|---|
| 环境 | 被竞争者取代 | **27** |
| 项目 | 项目过时/功能废弃 | **20** |
| 团队 | 主要维护者**缺时间** | **18** |
| 团队 | 主要维护者**失去兴趣** | **18** |
| 项目 | 基于过时技术 | **14** |

**映射到阙疑**：
- **"缺时间"（18/104，17%）**：考研初试约 **2027-12**，2027 年下半年必然挤压。这是**第一号死因**。
- **"失去兴趣"（18/104，17%）**：单人项目、0 反馈、论文被拒三次后——这是**第二号死因**。
- **"被竞争者取代"（27/104，26%，最高）**：如果 2027 年主流 LLM 自带高可信代码验证，阙疑的"外部验证器"叙事会被稀释。

### 五、烂尾后的资产盘点（阙疑具体能留下什么）

即使阙疑明天停摆，以下都是**不可撤回的已达成事实**，且都可独立展示：
1. **一个 3826 行的可运行判决引擎**（`tools/gate_engine.py`）+ 67 条规则（44 block）。
2. **一个 30 seed 的盲 holdout 及其 irreversible reveal 记录**（`data/holdout/holdout.json`，`blind=false / revealed=true / reveal_irreversible=true`）——**"不可回盲"这个协议本身**就是方法论资产。
3. **三层外部 corpus 40 条**（A/B/C，检出率 54.2%/12.5%/0%）——**分层报告检出率**这个做法，比"总体 43.8%"更有学术诚实度。
4. **15 条真实缺陷夹具 + 重注入 6/6**。
5. **一次公开的"自我否定"**：论文 v0.3 主动**放弃**把内部变异率 97.3% 当缺陷检测率、放弃把扩样样本当盲态证据、并把反事实算子 P=R=F1=0 如实写进论文。**这在求职面试里比"我做出了 97.3% 的检测率"值钱得多**。
6. **一个"元状态不可信"的现成案例**：`_auto/status.json` 的 `active_batch=660` 落后于实际 665——可直接作为 Threats to Validity 的实证。

**归档清单（可直接执行，成本 < 1 小时）**：
- README 顶部加 `> **[ARCHIVED 2027-XX-XX]** 本项目已停止维护。已达成：67 规则 / 30-seed 盲 holdout（检出 66.7%）/ 40 条外部 corpus（43.8%）。未完成：<逐条列>。替代/延续：<如有>。`
- 仓库 Settings → Archive（只读）。
- 关闭所有 issue，未解决项打 `won't fix` 并补一句背景。
- 密钥扫描：`git log -p | grep -iE 'api[_-]?key|token|password|BEGIN.*PRIVATE KEY'`（**CHAOSS Step 4 明确要求**）。
- 发一条 Zenodo release 拿 DOI，自动同步 Software Heritage（2024-11-13 起 Zenodo↔Software Heritage 已打通，https://www.softwareheritage.org/2024/11/13/software-heritage-zenodo-integration/ ）。
- 移除多余的 collaborator 权限、删除陈旧分支。

**反面清单（绝对不要做）**：
- ❌ 删仓库（抹掉工作痕迹，且制造可复现性灾难）。
- ❌ 宣称"维护模式"但实际已死（MinIO 式暧昧，最伤用户信任）。
- ❌ 假装还活跃（发一个空 commit 装样子）。
- ❌ 在 README 里写"因为没人关心所以我不做了"（把失败归因给他人，招聘方会读出来）。

## 对阙疑的 3 条具体行动

1. **现在就写 `_arch_v46/90_续命判定表.md` 里的"止损线"，把续命变成可证伪的条件**。具体做法：在仓库新建 `HANDOVER.md`，写死三条**可观测**的续命条件（示例，需作者按实际填）：①到 2027-03-31 前，holdout 检出率从 66.7% 提到 **≥75%**；②外部 corpus 从 40 条扩到 **≥80 条**且 A 层检出率 ≥54.2%；③获得 **≥1 个**非本人的外部使用者（fork 后仍更新，或 GitHub issue 来自陌生账号）。**三条中达成 <2 条 → 触发归档流程**。工具：把这三条写进 `_auto/status.json` 的 `survival_criteria` 字段，用一个 `tools/survival_check_<batch>.py` 在每次批次收尾时打印达成情况。
2. **补 `CONTRIBUTING.md`，因为它是全论文效应量最大的存活因子（16% vs 72%，large）**。内容只需 4 节：①如何跑起来（`python tools/gate_engine.py --check` 一行命令）；②如何新增一条规则（模板 + `data/_gate_rules.json` 的字段说明）；③如何提交盲样本（**明确禁止**把 holdout 样本泄露给内核作者——这是阙疑的方法论红线）；④`won't fix` 与归档政策。时间点：**2027-01 之前**完成，早于考研冲刺期。
3. **把"归档包"当成一个交付物提前做好**（不是等烂尾才做）：新建 `_arch_v46/archive_kit/`，内含 ①`README_ARCHIVED_TEMPLATE.md`（带 `[ARCHIVED]` 顶部块）；②`ZENODO_DEPOSIT.md`（写好 release 步骤 + 要填的 metadata）；③`SECRET_SCAN.sh`（一行 grep 命令，见上文）；④`POSTMORTEM_TEMPLATE.md`（含时间线 / 做成了什么 / 没做成什么 / 为什么停 / 资产在哪）。这样即使 2027-12 考研前三天决定停，**半小时就能体面收尾**。

## 盲区（诚实标注）
