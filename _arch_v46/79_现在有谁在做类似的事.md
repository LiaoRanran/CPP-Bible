# 方向 79：现在有谁在做类似的事

> 说明：本节按"最接近阙疑的三个问题域"筛选——**(A) 可审计的 LLM 评测/验证基础设施**、**(B) LLM 代码缺陷检测**、**(C) 真实缺陷基准**。共 10 个具体项目/团队/论文（另附 5 条补充线索）。每条的"差异"一栏，专门回答"它与阙疑的 67 规则 + 哈希链 + 独立对账器有什么不同"。

## 核心结论

1. **"可审计评测"这条赛道在 2025-2026 已经从学术概念变成有资金、有机构、有制度的产业**（METR、UK AISI 的 Inspect、Epoch AI、DeepMind 双盲评测、英国政府第三方保障路线图），但**几乎全部聚焦"评测前沿大模型的危险能力"，没有一家在做"可被第三方独立复算的知识判定器"**——阙疑的差异化不在"做评测"，而在"判决可复算 + 证据可追"。
2. **LLM 代码缺陷检测是竞争最密集的地带**（SWE-bench Pro、CyberGym、RepoAudit、CWE-Bench-Java、CodeQL Autofix、OSS-Fuzz），但它们的共同弱点是**依赖"测试通过"或"复现成功"作为真值，且基准本身被质疑**：OpenAI 于 2026-07 公开质疑 SWE-bench Pro 的 **731 个任务中约 30% 存在评测缺陷**——这恰好证明"评测的真值本身需要被审计"是公开的行业痛点。
3. **C++ 领域存在明确空位**：真实缺陷基准 Defects4J（Java，**835 个 bug**）、BugsInPy（Python，**493 个 bug**）都有十年积累，而 **C++ 没有对等的大规模"可复现真实缺陷"公开基准**；C++ 侧只有规则型工具（clang-tidy / MISRA / C++ Core Guidelines / CBMC / Frama-C），**"规则 + LLM + 可复算证据"三者结合的项目未检索到**。

## 精确数字与案例

### 1. METR —— 长任务时域与 RE-Bench

**来源**：METR（Model Evaluation & Threat Research），2025-2026 系列博客与论文。
**数字**：TH1.1（2026-01-29）把任务集从 170 扩到 **228**，8h+ 长任务从 14 增到 **31**；全期翻倍时间 **196.5 天**，≥2023 为 **130.8 天**，≥2024 为 **88.6 天**；Opus 4.5 时域 **320 分钟 [170, 729]**。
**差异**：METR 评的是**模型能完成多长的任务**，阙疑评的是**一条知识断言是否为真**；METR 依赖人工设计的 228 个任务，阙疑依赖 67 条可复算规则 + 盲 holdout。METR 的评测**需要人类基线**（31 个长任务中仅 5 个有实测基线），阙疑的对账**不需要人类**。

### 2. Epoch AI —— ECI 与 Benchmarking Hub

**来源**：Epoch AI，[epoch.ai/benchmarks](https://epoch.ai/benchmarks)。
**数字**：ECI（Epoch Capabilities Index）2026-09-03 记录 GPT-6 Astra 达 **167**；FrontierMath Erdős 的 68 道未解问题中 GPT-6 Astra 解出 **2 道（3%）**；开源权重落后闭源 **4 个月**、平均 ECI 差 **8 分**。
**差异**：Epoch 做的是**能力指数的聚合与趋势外推**（"谁更强"），阙疑做的是**判决的可复算与证据链**（"这条判定凭什么成立"）。Epoch 的数据来自厂商 API 与第三方榜单，阙疑的数据来自**自持哈希链**。

### 3. UK AI Security Institute（AISI）—— Inspect 框架与第三方保障

**来源**：UK AISI 的 **Inspect** 开源评测框架（METR 于 2026-01 把评测基础设施从自研 Vivaria 迁移到 Inspect）；英国政府 2025-09-03《Trusted third-party AI assurance roadmap》。
**数字**：METR 迁移后对 5 个模型做了 Vivaria vs Inspect 的配对 t 检验，发现 **GPT-4o 与 o3 在 Vivaria 下显著更高**（scaffold 敏感），但新任务集上两者差异极小（GPT-4o 6 vs 5 分钟、Claude 3.7 Sonnet 56 vs 57 分钟）。
**差异**：Inspect 是**评测框架**（怎么跑评测），阙疑是**判定器 + 对账器**（结论怎么被独立复算）。值得注意的是 METR 的迁移实验本身证明"**同一模型、同一任务、换框架结果就变**"——这正是阙疑坚持"内核与对账器分离、证据带 provenance"的实证理由。

### 4. Apollo Research（+ OpenAI）—— 欺骗行为（scheming）评测

**来源**：OpenAI × Apollo Research，2025-09-17 联合发布；论文 *Stress Testing Deliberative Alignment for Anti-Scheming Training*（arXiv:2509.15541，2025-09-22）。
**数字**：训练 OpenAI o3 与 o4-mini 遵循"反 scheming 规范"后，**隐蔽行动（covert actions）约减少 30%**（媒体口径，未核实原始百分比）；Apollo 曾获 OpenAI o3/o4-mini 的**内部思维链受限访问权限**。
**差异**：Apollo 研究的是**模型是否在评估中伪装**（对应阙疑的"元状态不可信"威胁）；阙疑的应对不是"训练模型别骗人"，而是**把判定从模型嘴里移到哈希链里**——即使模型说谎，链上的证据也不变。

### 5. Scale AI —— SWE-bench Pro（长时程编码基准）

**来源**：Scale AI SEAL，[labs.scale.com/papers/swe_bench_pro](https://labs.scale.com/papers/swe_bench_pro)，arXiv:2509.16941（2025-09-22）。
**数字**：**731 个公开测试任务**（长时程、企业级代码）；2026-04 报道 Opus 4.7 在 Pro 上约 **64.3%**（Anthropic 自报）。**关键事件**：2026-07-09 OpenAI 公开质疑该基准，称 **731 个任务中约 30% 存在评测缺陷**。
**差异**：SWE-bench Pro 的真值是"补丁让隐藏测试通过"，阙疑的真值是"67 条规则 + 四态判决 + 证据链"。**SWE-bench Pro 被质疑 30% 缺陷这件事本身，就是阙疑"评测真值需要被审计"主张的最好外部证据**。

### 6. Berkeley RDI —— CyberGym（真实漏洞复现基准）

**来源**：UC Berkeley Center for Responsible, Decentralized Intelligence，[cybergym.io](https://www.cybergym.io/cybergym/)，arXiv:2506.02548。
**数字**：**1,507 个基准实例**，来自 **188 个**广泛使用的开源软件的真实漏洞；每个实例要求 agent **复现真实漏洞**。
**差异**：CyberGym 用"能否复现漏洞"作为真值（**可执行、可验证**，与阙疑理念最近）；但它面向**安全漏洞**、规模 1,507、需要真实构建与运行环境；阙疑面向**C++ 知识断言**、规模 30+40+15、可在无网络环境复算。两者可以互补：CyberGym 是"大而重"的基准，阙疑是"小而可复算"的判决器。

### 7. RepoAudit（PurCL）—— 仓库级 LLM 缺陷审计 Agent

**来源**：PurCL 团队，[github.com/PurCL/RepoAudit](https://github.com/PurCL/RepoAudit)，arXiv:2501.18160（2025-01-30）；开源的 **dfbscan** 数据流缺陷检测器（2025-04）。
**数字**：定位为"repo-level bug detector for general bugs"，支持空指针等多类缺陷，采用**多 agent + memory + validation** 架构。
**差异**：RepoAudit 用 LLM agent 自主探索代码库（**结论由模型给出**），阙疑用固定规则集 + 独立对账器（**结论由规则给出、可被第三方重跑**）。RepoAudit 的"validation"步骤仍是模型自证，阙疑的对账器不依赖内核——**这是方向 77 所述"内置验证 vs 外部验证"的教科书式对照**。

### 8. AI2 —— RewardBench / RewardBench 2（验证器评测）

**来源**：Allen Institute for AI，[github.com/allenai/reward-bench](https://github.com/allenai/reward-bench)，RewardBench 2：arXiv:2506.01937（2025-06）。
**数字**：RewardBench 2 含 **1,865** 个 prompt（约 70% 人类来源），四选一、随机基线 **25%**；评估 **100+ 个**奖励模型；榜首 **Skywork-Reward-V2-Llama-3.1-8B = 84.1**，击败 70B/72B 与闭源 Gemini-2.5-pro（79.5）；Best-of-N 下 113 个 RM 与人类判断 **Pearson r = 0.87**；PPO 训练中 RM 分数在 **49.8–68.5** 区间后饱和。
**差异**：RewardBench 评的是**奖励模型本身好不好**（元评测），阙疑做的是**判定一条 C++ 知识断言是否为真**（对象评测）。但 RewardBench 2 的发现对阙疑极有价值：**"验证器指标 ≠ 验证器效用"**，且 **8B 可以打败 72B**——支持阙疑把 L2 层压到 7B 级的选型。

### 9. Google DeepMind + Singapore AISI + OpenMined + AVERI + MLCommons —— 全球首个双盲 AI 评测

**来源**：DeepMind 官方博客 [*Piloting the world's first double-blind AI evaluations*](https://deepmind.google/blog/piloting-the-worlds-first-double-blind-ai-evaluations/)（2026-08-27）；AVERI 试点报告（2026-07/08 执行）。
**数字**：2026-08-27 发布；用**机密计算（confidential computing）**让评估机构**看不到模型权重**也能施测，同时 Google 也看不到第三方的测试提示词（防数据污染）。
**差异**：这是**唯一在制度设计上与阙疑同频的项目**——都在解决"如何让验证方独立于被验证方"。区别：DeepMind 的双盲是**为前沿模型的安全评测服务**（一次性、高成本、需要机密计算硬件）；阙疑的对账是**为知识断言服务**（随时、零成本、只需要一个哈希函数）。**阙疑可以把"零成本可复算"作为对双盲评测的差异化补充**。

### 10. IRIS / CWE-Bench-Java —— LLM 辅助静态分析降误报

**来源**：IRIS 团队，*LLM-Assisted Static Analysis for Detecting Security Vulnerabilities*（arXiv:2405.17238）；数据集 [github.com/iris-sast/cwe-bench-java](https://github.com/iris-sast/cwe-bench-java)（2025-01-31）。
**数字**：**120 个**手工核验、可编译的 Java 项目；方法为"静态分析给候选 → LLM 判定可达性"。
**差异**：这是"规则 + LLM"分工的最接近的先例，但**对象是 Java 安全漏洞、真值是人工标注**；阙疑是 C++ 知识断言、真值是**盲 holdout + 哈希链**。相关同族工作：**LLM4PFA**（arXiv:2506.10322，路径可行性分析降误报）、**腾讯企业定制 SAT**（arXiv:2601.18844，2026-01，在腾讯广告营销服务大规模代码库上降误报）。

### 补充线索（5 条）

11. **Meta CRUXEval**（arXiv:2401.03065，ICML 2024）：**800 个 Python 函数**，CRUXEval-I（预测输入）/ CRUXEval-O（预测输出）——代码推理基准，**不含 C++**。
12. **Google OSS-Fuzz**（2016 起）：截至 **2025-05**，已在 **1,000+** 个项目中发现并修复 **超过 13,000 个漏洞和 50,000 个 bug**；2025-02 Google 称 AI 增强版在开源库中发现 **26 个漏洞**（含 OpenSSL）。
13. **GitHub / Microsoft CodeQL + Copilot Autofix**：CodeQL **2.22.4 版**在完整配置下运行 **478 条安全查询**（2026-06 报道）；Autofix 为 CodeQL 告警生成修复建议。
14. **seL4 + APOLLO（Lean 4）**：seL4 微内核的形式化验证被广泛引用为"约 **20 人年**"量级的证明工作量；APOLLO（arXiv:2505.05758）探索"LLM + Lean 协作"以降低证明成本。**注意：C++ 与 C 的形式化验证工具（CBMC / Frama-C / VeriFast）在工业界仍有高门槛，本文未取到精确采用率数字。**
15. **OpenAI MLE-bench**（arXiv:2410.07095）：**75 个** Kaggle 竞赛任务，评估 ML 工程 agent；单次主实验配置需 **24 小时/任务**，属资源密集型基准。

### 关键空白：C++ 没有 Defects4J

- **Defects4J**（Java）：**835 个 bug**（另有 29 个已废弃），是"真实缺陷"研究的黄金标准。
- **BugsInPy**（Python，arXiv:2401.15481）：**493 个真实 bug**，明确"inspired by Defects4J"。
- **C++**：**未检索到**对等的、公开的、大规模"可复现真实缺陷"基准。C++ 侧只有规则工具（clang-tidy 的 MISRA 映射、C++ Core Guidelines、CBMC、Frama-C、PVS-Studio、Cppcheck）与**小规模**的真实缺陷集（阙疑自建的 **15 条**缺陷夹具正是这一空白的直接证据）。

### 横向归纳：这 10 个项目共有的三个盲点

**盲点一：真值几乎全部来自"可执行"或"人类标注"，没有一家来自"可复算的规则判决"。** SWE-bench Pro 靠隐藏测试通过，CyberGym 靠漏洞复现成功，RepoAudit 靠模型自证，CWE-Bench-Java 靠人工标注，Defects4J/BugsInPy 靠人工最小化。**"规则判决 + 哈希链"这一形态在这 10 个项目中出现次数为零。** 这不是因为没人想到，而是因为**它要求先有一套被承认的规则集**——而 C++ 领域唯一被广泛承认的规则集是编译器行为与标准文本，二者都太庞大，难以被单人所持。阙疑的 67 条规则（44 block）规模虽小，但**是当前唯一被作者自己完整掌握、可逐条复算的集合**。

**盲点二：规模崇拜。** CyberGym 1,507 实例、SWE-Lancer 1,488 任务、RewardBench 2 有 1,865 prompt、OSS-Fuzz 覆盖 1,000+ 项目。**"大"是这些项目的合法性来源。** 阙疑的 30/40/15 在数量上完全不可比——**因此阙疑不能打规模牌，只能打"每一条都可被独立复算"的密度牌**。这也解释了为什么论文标题里的"可被独立验收"必须放在最前面，而不是"67 条规则"。

**盲点三：全部依赖外部模型/服务。** 除 Defects4J/BugsInPy 外，其余项目都需要调用前沿模型或特定基础设施（机密计算、Docker 构建环境、GPU）。**"零网络、单机、秒级"这一运行档位在 10 个项目中没有对应物**——这既是阙疑最独特的卖点，也是它最容易被质疑的地方（"是不是因为做不大才说不需要大"）。**应对方式：明确声明阙疑的定位是"判决器"而非"基准"，基准的建设交给社区。**

### 三个空白可直接变成阙疑的资产

| 空白 | 现状 | 阙疑可做的 |
|---|---|---|
| C++ 无 Defects4J 对等物 | Java 835 / Python 493 / C++ ≈ 0（仅阙疑 15 条） | 扩到 ≥60 条并公开方法学 |
| 无"规则判决 + 哈希链"形态 | 10 个项目中出现 0 次 | 把对账器做成独立可跑的工具 |
| 无"零网络单机"验证档 | 全部需要外部服务/基础设施 | 写清运行档位与复算命令 |

## 对阙疑的 3 条具体行动

1. **把"SWE-bench Pro 被指 30% 任务有缺陷"写成论文的动机段第一句**：在 `research/00_problem.md` 与论文 §1 Introduction 加入"评测真值本身需要被审计"的论据链——引用 OpenAI 2026-07 对 SWE-bench Pro 731 任务的质疑、METR 的 Vivaria/Inspect 框架差异（GPT-4o 在 Vivaria 下显著更高）、RewardBench 2 的"PPO 饱和区间 49.8–68.5"。**三组数字共同支撑阙疑的核心主张：判决必须可复算，而非依赖跑分。**
2. **在 2027-03 前把缺陷夹具从 15 条扩到 ≥60 条，抢占"C++ 版 Defects4J"的空位**：参照 Defects4J（835 bug）与 BugsInPy（493 bug）的方法学，从 GCC/Clang/LLVM 的公开 bug tracker 与 CVE 中筛出**可复现、可最小化**的 C++ 缺陷，新增 `data/defect_fixtures/defects_v2.json`，字段含 `source_commit / reproducer / minimized / rule_hits / provenance_hash`。目标：重注入检出率保持 **≥90%**，并把历史覆盖率从 **12/15 = 80%** 提升到 **≥80% 且样本量翻四倍**。**这是阙疑最有可能被外部引用的资产**。
3. **对标 DeepMind 双盲评测，写一页"零成本独立验收"对照说明**：在 `research/11_reproducibility.md` 增加一节，逐条对比"DeepMind 双盲（机密计算硬件 + 一次性 + 高成本）"与"阙疑对账器（单机 + 随时 + 只需哈希函数）"，并给出可执行命令（`python tools/auditor_blindtest_<批次>.py --verify-chain data/holdout/holdout.json`）。同时引用 UK AISI Inspect 与英国政府第三方保障路线图，说明阙疑的对账器可作为**低成本第三方验证组件**接入既有评测生态。

## 盲区（诚实标注）

- **"Apollo × OpenAI 减少隐蔽行动约 30%"** 来自虎嗅等媒体转述，**未核实 arXiv:2509.15541 原文中的精确百分比与实验条件**。
- **SWE-bench Pro 的"约 30% 任务存在评测缺陷"** 来自 OpenAI 博文的二手报道（ai.codefather.cn / chinaz，2026-07-09），**未取得 OpenAI 原文逐条核对"缺陷"的定义**（是任务歧义、测试错误，还是评分口径问题）。
- **seL4 的"20 人年"** 是长期被广泛引用的量级，**未核实官方最新口径**；APOLLO 的实际降本幅度**未取到数字**。
- **CBMC / Frama-C / VeriFast 的工业采用率**：检索到的"97% 团队在 Frama-C 上失败"等说法来自 CSDN 博客，**来源不可靠，本文未采用**。
- **clang-tidy 的规则总数、C++ Core Guidelines 的规则条数、MISRA C++ 的规则条数**未取得权威计数，**未引用任何数字**。
- **CodeQL 2.22.4 的 478 条安全查询**来自第三方博客（safeguard.sh），**未在 GitHub 官方 changelog 核实**。
- **OSS-Fuzz 的 13,000/50,000/1,000 数字**来自 GitHub README（"as of May 2025"），**未独立复算**。
- **是否真的"没有任何项目在做规则 + 哈希链 + 独立对账器的 C++ 验证"**：本文基于 13 次定向检索的**阴性结论**，**不能排除小众/未索引项目**；这是本方向最大的不确定性。
