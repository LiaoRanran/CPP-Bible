# 方向 39：错误处理最佳实践（fail-closed vs fail-open）

> 调研时间：2026-09-29（GMT+8）｜联网搜索 10 次 + 2 次 WebFetch 读一手规范/官方文档
> 锚点项目：阙疑 / queyi（67 条规则 / 44 block / 四态判决 / append-only 哈希链 + 独立对账器）
> 关联：方向 36（`--no-verify` 绕过钩子 = fail-open 的实例）、方向 37（CI 门禁必须 fail-closed）、方向 38（审计账本完整性）

---

## 核心结论

1. **阙疑是"安全/正确性场景"，必须 fail-closed：任何一条检查失败、任何一次依赖不可用、任何一处解析异常，都必须判 `block`（或至少 `unknown` 并阻断），绝不能"跳过检查继续放行"**。这是 NIST SP 800-53 的 **SC-7(18) Fail Secure** 与 **SA-8(23) Secure Defaults** 两条控制项要求的姿态，不是风格偏好。
2. **`--no-verify` 是阙疑身上已经发生的 fail-open 事故**：`00_仓库扫描.md` §1 记录提交 `a18fb201 660：验收报告登记 push 走 --no-verify`。这等于"检查器故障时不阻断，而是继续放行"——**正是 fail-open 的定义**。论文里若声称"可被独立验收"却存在可绕过的门禁，审稿人一旦发现就是致命的。
3. **`fail-closed` 与 `error budget` 在阙疑身上是冲突的**（见方向 38 §6）：error budget 的哲学是"允许偶尔坏一点"，fail-closed 的哲学是"一次都不许坏"。**对外的可验收性必须用 100% 不变量，对内的开发过程才可以用 error budget**。这个取舍必须在论文里明写，否则会被认为"口径不一致"。

## 精确数字与案例

### 1. fail-closed 的准确定义与生产事故案例

一手来源 `https://devsecopsschool.com/blog/fail-closed/`（2026-02-20，DevSecOps School）给出的两个定义版本，原文引用：

> **快速定义**："Fail Closed: a safety posture where a system **denies action when a dependent component or check fails**, prioritizing safety/security over availability. Analogy: an airport security gate that stays locked if badge verification fails. Formal: an operational policy that **defaults-deny on component failure**, enforcing deny-by-default semantics in runtime flows."

> **一句话定义**："Fail Closed is the **deny-by-default** operational behavior where systems **block actions when required checks or dependencies fail or become unavailable**."

文章强调三点边界条件：

- Fail Closed **不等同于 fail-stop**（fail-stop 只是停止运行，不指定"拒绝"语义）。
- Fail Closed **不总是面向用户、可用性关键流程的正确选择**。
- 需要为降级服务提供**明确的异常处理路径**。

**文章列出的 5 个真实生产失败案例**（原文"what breaks in production"）：

1. **授权策略服务中断** → 结账请求被拒绝，购买停止。
2. **模型验证失败** → AI 推荐器被禁用，个性化减少，但避免了有偏见的建议。
3. **证书签名服务不可达** → 内部服务间 TLS 握手失败，连接被阻断。
4. **支付网关健康检查失败** → 系统阻止交易，避免重复扣款或结算失败。
5. **WAF 配置错误** → 触发误报并丢弃合法流量，直至人工修复。

案例 5 是关键：**fail-closed 的代价是可用性**。WAF 配错就把合法流量全丢。所以 fail-closed 不是免费的，必须量化它的代价。

**文章给出的 10 个量化目标（M1–M10，原文表格）**：

| ID | 指标 | 起始目标 |
|---|---|---|
| M1 | 拒绝率（Deny Rate） | **< 5%**（安全类流程除外） |
| M2 | 意外拒绝率 | 关键流程 **< 0.1%** |
| M3 | PDP（策略决策点）可用性 | 关键 PDP **99.9%** |
| M4 | 拒绝延迟影响 | API **< 50 ms** |
| M5 | 策略服务恢复时间 | 关键场景 **< 15 分钟** |
| M6 | 回退激活率 | 尽可能低 |
| M7 | 安全违规计数 | **零或接近零** |
| M8 | 安全错误预算消耗 | **零容忍** |
| M9 | 策略部署失败率 | **< 0.1%** |
| M10 | 可观测性覆盖率 | 关键点 **100%** |

以及 SLO 示例（原文）：**安全 SLO = 100% 无安全违规；可用性 SLO = 允许请求 99.9% 成功**。告警燃烧率指导：**若安全错误预算消耗在不到 6 小时内超过日预算的 50%，触发 Pager 告警；否则开 Ticket**。政策审计频率：关键策略**至少每月**一次，更广泛政策集**每季度**一次；混沌工程演练**每季度**一次。

**⚠️ 诚实标注**：这篇文章**没有引用任何正式标准**（无 NIST、无 IEC 61508、无 ISO 26262）。上面的 M1–M10 是博客作者的建议值，**不是标准值**，阙疑不能把它当作"合规要求"引用。

### 2. NIST 的两条正式控制项

要引用正式标准，应引 NIST SP 800-53 Rev. 5（`https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final`，2020-12-10）：

- **SC-7(18) Fail Secure**（`https://csf.tools/reference/nist-sp-800-53/r5/sc/sc-7/sc-7-18/`）：原文描述为"Fail secure is a condition achieved by employing mechanisms to ensure that in the event of **operational failures of boundary protection devices**…"（在边界保护设备运行故障时仍保持安全状态）。
- **SA-8(23) Secure Defaults**（`https://csf.tools/reference/nist-sp-800-53/r5/sa/sa-8/sa-8-23/`）：原则是"系统初始（默认）配置"与"安全工程"都应按最安全默认值设定。

**对阙疑的映射**：阙疑的"边界保护设备"就是那 67 条规则 + 44 条 block。当某条规则**无法执行**（解析失败、依赖缺失、超时、异常）时，SC-7(18) 要求的姿态是**保持安全状态 = 判 block 或判 unknown 并阻断**，而不是"这条跳过，其余继续"。

### 3. C++ 异常安全三级保证：一手定义

一手来源 `https://learn.microsoft.com/en-us/cpp/cpp/how-to-design-for-exception-safety?view=msvc-170`（Microsoft Learn，2025-06-18 更新）。三级保证的**原文定义**：

- **No-fail guarantee（no-throw）**："the strongest guarantee that a function can provide. It states that the function **will not throw an exception or allow one to propagate**." 但"you cannot reliably provide such a guarantee unless (a) you know that all the functions that this function calls are also no-fail, or (b) …any exceptions that are thrown are caught before they reach this function, or (c) …you know how to catch and correctly handle all exceptions that might reach this function."
- **Strong guarantee**："if a function goes out of scope because of an exception, it **will not leak memory and program state will not be modified**. A function that provides a strong guarantee is essentially **a transaction that has commit or rollback semantics: either it completely succeeds or it has no effect**."
- **Basic guarantee**："if an exception occurs, **no memory is leaked and the object is still in a usable state** even though the data might have been modified."（原文注明：当 strong 保证在内存或性能上太贵时，basic 可能是最好选择。）

**两条硬规则（原文）**：

- "**All containers and types in the Standard Library guarantee that their destructors do not throw.**" 并且"the Standard Library requires that user-defined types that are given to it—for example, as template arguments—**must have non-throwing destructors**."
- "**Do not allow any exceptions to escape from a destructor.** …If a destructor must perform a potentially exception-throwing operation, it must do so in a try catch block and swallow the exception."

**对阙疑的映射**：阙疑的"判决"是一个事务。**一次 gate run 应当提供 strong guarantee**——要么整批判决全部产出并写入哈希链，要么**完全不写入**（回滚）。绝不允许"写了 300 条判决、第 301 条崩了、账本停在 300 条但链头已更新"这种**半完成状态**——那会让哈希链的语义崩掉。

C++ Core Guidelines 的对应条目：**E.6**（`https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines`，E.6 标题为 "Use RAII to prevent leaks"）与 **E.12**（"Use `noexcept` when exiting a function because of a `throw` is impossible or unacceptable"）。E.6 的说明里有一句对阙疑直接适用：**"When exceptions cannot be used, simulate RAII. That is, systematically check that objects are valid after construction and release all resources in the destructor."**

### 4. 错误码 vs 异常：C++ 侧的取舍

一手来源 `https://learn.microsoft.com/en-us/cpp/cpp/errors-and-exception-handling-modern-cpp?view=msvc-170` 把程序错误分成两类：

- **逻辑错误（logic errors）**：由编程失误导致，如"数组下标越界"。
- **运行时错误（runtime errors）**：超出程序员控制，如"网络服务不可达"。

`https://pkglog.com/en/blog/cpp-exception-performance/`（2026-06-03）的结论：**在成功路径上，用不用 try 的优化后代码性能相近；在错误路径上，异常通常更贵**（因为要栈展开）。这就是"C++ 异常是零成本"这句话的准确边界：**零成本指的是"不抛就不付费"，不是"抛了也免费"**。

`https://kindatechnical.com/c-plus-plus/error-codes-vs-exceptions-expected-cpp23.html`（2026-03-05）与 `https://www.cppstories.com/2024/expected-cpp23-monadic/`（2024-05-06）介绍了 **C++23 `std::expected<T, E>`**：把"正常值或错误"直接写进返回类型，让失败成为**类型系统的一部分**而不是靠自觉。它提供 monadic 接口（`and_then` / `or_else` / `transform`）用于链式组合，避免层层 `if` 嵌套。

**对阙疑的映射**：阙疑的 C++ 夹具检测器如果要在"检测失败"时明确表达"我没能检测（而不是没检测到缺陷）"，`std::expected<DetectionResult, DetectionError>` 比 `bool` 或裸错误码更能防止**静默的 fail-open**——因为调用者**必须**显式处理 `unexpected` 分支，编译器不会放过。

### 5. 幂等与重试：RFC 9110 的正式定义

一手来源 `https://www.rfc-editor.org/rfc/rfc9110.html`（HTTP Semantics）第 9.2 节定义了两个正交属性：

- **Safe（安全）**：方法不改变服务器状态。`GET`、`HEAD`、`OPTIONS`、`TRACE` 是 safe。
- **Idempotent（幂等）**：**对同一请求执行一次与执行多次，服务器上产生的状态效果相同**。`PUT`、`DELETE` 以及所有 safe 方法都是幂等的；**`POST` 不是幂等的**。

`https://runebook.dev/zh/docs/http/rfc9110/section-9.2.2`（2025-12-07 中文解读）补充了关键实践含义：非幂等操作需要**幂等键（idempotency key）**来防止重复提交。

**对阙疑的映射**：阙疑的 gate run 必须**幂等**——同一批输入跑两次，哈希链上要么只增加一条（去重），要么两条内容完全相同（可证明确定性）。**如果同一输入跑两次得到不同哈希，那"可被独立验收"就不成立**。这条应作为 CI 断言（见方向 37/40）。

### 6. 重试：指数退避 + 抖动，以及"重试风暴"的具体数字

一手来源 `https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/`（AWS Architecture Blog，作者 **Marc Brooker**，2015-03-04；2023-05 有更新说明）。要点：

- 场景是乐观并发控制（OCC）下 N 个客户端争抢同一行。原文指出**总工作量随 N 增长为 N²**（"the total amount of work done by the system increases with N²"）。
- 模拟参数：**网络延迟均值 10 ms、方差 4 ms**。
- 三种抖动策略：
  - **Full Jitter**：`sleep = random_between(0, min(cap, base * 2^attempt))`
  - **Equal Jitter**：保留一半退避，只对另一半抖动
  - **Decorrelated Jitter**：在 Full Jitter 基础上，用上一次随机值提升抖动上界
- 结论（原文）："**The no-jitter exponential backoff approach is the clear loser.** It not only takes more work, but also takes more time…it takes so much more time we have to leave it off the graph."；"Of the jittered approaches, **'Equal Jitter' is the loser**. It does slightly more work than 'Full Jitter', and takes much longer."；**"In the case with 100 contending clients, we've reduced our call count by more than half."**
- 更新的 2023 说明：**AWS 各 SDK 现在内建支持指数退避 + 抖动**（standard / adaptive 模式）。

**⚠️ 诚实标注**：博客给出的**具体调用次数与睡眠总时长的表格数字我没有取到**（页面正文中的公式与图表数值以图片/公式形式呈现，WebFetch 未完整返回）。上面引用的"减少一半以上""N² 增长"是**原文文字表述**，不是我编的数字。

**重试风暴（retry storm）**：一手来源 `https://learn.microsoft.com/en-us/azure/architecture/antipatterns/retry-storm/`（Azure Architecture Center）。原文定义的恶性循环："Excessive connection attempts during recovery can overwhelm the service and intensify the original problem. This situation is sometimes called a **thundering herd**."

**官方给出的具体数字案例**：

- **客户端侧**：Application Insights 显示"**over 21,000 failed connection attempts to a dependency within a short time**"，图表具体值为 **21.34k**。
- **服务端侧**：Azure Front Door 日志中，**一个 IP 在 1 小时内产生 81,608 个事件**，而另一个 IP 只有 **5** 个——相差约 **1.6 万倍**。官方给出的 Kusto 查询：

```kusto
AzureDiagnostics
| where ResourceType == "FRONTDOORS" and Category == "FrontdoorAccessLog"
| where TimeGenerated > ago(1d)
| summarize count() by bin(TimeGenerated, 1h), clientIp_s
| order by count_ desc
```

官方推荐的 8 条客户端缓解措施：**限制重试次数与总时长**、**退避并递增等待**、**优雅处理服务故障**、**用 Circuit Breaker 模式**、**遵守 `retry-after` 响应头**、**用官方 SDK**、**用抽象层（service mesh / Dapr）**、**批量与连接池**。服务端侧：**加网关层阻断连接（Bulkhead 模式）**、**在网关限流**、**回 `retry-after` 信号**。

同时原文强调一条对阙疑很关键的**错误分类**："Some error types don't indicate a service failure, but instead indicate an invalid request from the client. For example, if a client application receives a `400 Bad Request` error response, **retrying the same request likely won't help**."

**对阙疑的映射**：阙疑的重试策略必须**按错误类型分类**：

- **可重试**（transient）：编译器临时不可用、文件锁、网络拉取失败 → 指数退避 + Full Jitter，**最多 3 次**，总时长上限 **30 秒**。
- **不可重试**（permanent）：规则本身写错、输入格式非法、哈希不匹配 → **立即 fail-closed 判 block，不重试**。重试一个确定性错误只会浪费时间并掩盖根因。

## 对阙疑的 3 条具体行动

**行动 1：把"检查器自身失败"从"跳过"改为"判 block"，并写一条可测的断言。**
具体：审计 `tools/gate_engine.py`（3826 行）里所有 67 条规则的执行路径，把每一处 `except Exception: pass` / `continue` / `return None` 改为**显式产出 `verdict=block, reason=checker_unavailable`**（或 `unknown` 并阻断）。规则：**任何一条规则的执行异常都必须记入账本，且不得静默降级为"通过"**。新增夹具 `fixtures/checker_failure/`：故意让某条规则抛异常，断言 gate 输出**不是** `pass`。验收标准：`python tools/gate_engine.py --check --inject-checker-fault` 必须返回非零退出码。**这一条是 NIST SC-7(18) Fail Secure 的直接落地**。

**行动 2：把 gate run 改成"事务化"（strong guarantee），并写一条半完成状态断言。**
具体：账本写入采用 Microsoft 定义的 **strong guarantee** 语义——先在内存/临时文件里生成整批判决，**全部成功后一次性 append 到账本并更新链头**；任何中途失败则**完全不写入**（临时文件丢弃）。断言：`reconcile.py` 增加一条检查——**账本条数必须等于 `status.json` 里登记的已写入条数**，若不等则报错（防止"写了 300 条但链头已更新到 301"）。验收标准：在写入过程中 `kill -9` 进程，重启后 `reconcile --verify-ledger` 仍必须通过（链未断、无半条记录）。这一条同时解决方向 38 的审计完整性问题。

**行动 3：把 `--no-verify` 彻底废掉，并把重试策略写进配置。**
具体：(a) 在 `.githooks/pre-push` 与 CI（方向 37）都跑同一个 `make check`，并在 CI 里加一条 job：`git log --format=%B -n 50 | grep -q 'no-verify' && exit 1` 之类**无法可靠实现**的方案应放弃——改为**在 CI 里跑与本地完全相同的检查**，让 `--no-verify` 在收益上归零（本地跳过 = CI 一定红）。(b) 新增 `config/retry.json`，显式分类：`{"retryable": ["compiler_unavailable", "file_locked", "network_fetch_failed"], "max_attempts": 3, "total_timeout_s": 30, "backoff": "full_jitter", "non_retryable": ["rule_syntax_error", "input_malformed", "hash_mismatch"]}`。验收标准：`grep -rn "no-verify" .githooks/ tools/ Makefile` 无结果；`retry.json` 被 `gate_engine.py` 实际读取（加一条日志证明）。
