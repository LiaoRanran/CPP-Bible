# 方向 95：下一个项目做什么

> 锚点项目：**阙疑 / queyi**（论文内名「祈易 / queyi」）—— C++ 知识验证系统
> 实测锚点：实卡 **37**（verified 23 / red-team-verified 3 / draft 11）+ 草稿 **10**；规则 **67**（block 44 / warn 16 / advice 7）；`tools/gate_engine.py` **3826 行**；盲 holdout **30 seeds**（真错 17），检出率 **66.7%**；外部 corpus **40 条**（A 54.2% / B 12.5% / C 0%），总体 **43.8%**；真实缺陷夹具 **15 条**；反事实算子 **P=R=F1=0**；工具 `.py` **595** 个；批次 **665**。
> 作者约束：双非本科生、合肥、嵌入式、0 影响力；2026-09 起大三；考研初试约 **2027-12**。
> 本文件为 v46 第 95 号方向，只写 `_arch_v46/`，未改动仓库任何其它文件。

---

## 核心结论

1. **选下一个项目的第一原则不是"哪个方向热"，而是"哪个方向能复用阙疑已建成的资产"**。阙疑的真实资产清单是：**67 条规则 + 3826 行引擎 + 30 样本不可回盲 holdout 协议 + 三层外部 corpus + 15 条真实缺陷夹具 + 一套"独立对账器"**。任何需要从零重建数据集的候选，都会把 2027-12 考研前的可用时间吃光——**这是硬约束，不是偏好**。
2. **在 8 个候选里，有两个是"高杠杆低风险"的：①"AI 代码可信度基准"（把阙疑从"系统"变成"评测协议"，直接命中 NeurIPS E&D 的口味）；②"编译档 × sanitizer 交叉矩阵工具"（把阙疑已有的"`-O1`→`-O0` 使 3/5 miss 被抓"这一发现产品化，且完全对口合肥-嵌入式就业市场）**。这两个都不需要重做数据集，且都能独立发表或独立找工。
3. **有一个候选应当明确排除：从零做一个"Rust 借用检查可视化工具"**——因为 **Aquascope（Brown University Cognitive Engineering Lab）已经做了这件事**，且它自己都因依赖 nightly rustc 内部 API 而**维护困难**（3.0k stars、**最后一次提交是 1 年前**、35 个未关闭 issue）。**在已经有人做过、且证明"技术耦合度太高导致维护失败"的方向上重开一局，是最差的资源分配。**

## 精确数字与案例

### 一、外部环境的三个硬事实（决定了什么值得做）

**事实 1：内存安全缺陷占比极高，且是被政策推动的市场。** Interpretica《Static Analysis Tools for Embedded C and C++ (2026)》（2026-07-24 最后审阅，https://interpretica.io/research/static-analysis-tools-embedded-cpp-2026/ ）汇总的七个数字中，最关键的四个：
- **约 70%**：Microsoft 十多年来每年分配的约 **70% CVE** 由**内存安全缺陷**引起，且大部分被分析的代码是 C 和 C++（Microsoft MSRC, 2019）；
- **约 70% of 912**：自 2015 年以来 Chrome 记录的 **912 个**高/严重安全 bug 中约 **70%** 是 C/C++ 指针处理中的内存安全 bug，**其中约一半是 use-after-free**（Chromium Projects）；
- **76% → 24%**：Android 内存安全漏洞占比从 2019 年 **76%** 降至 2024 年 **24%**（新开发转向内存安全语言，遗留 C/C++ 代码量基本不变）（Google Online Security Blog, 2024）；
- **7 of 25**：**2025 CWE Top 25** 中 **7 项**是内存与指针缺陷——越界写(#5)、use after free(#7)、越界读(#8)、经典缓冲区溢出(#11)、NULL 指针解引用(#13)、栈缓冲区溢出(#14)、堆缓冲区溢出(#16)（MITRE, 2025 CWE Top 25）；
- 另：**2023 年 12 月，CISA、NSA、FBI 及澳、加、新、英网络安全机构联合要求软件制造商发布内存安全路线图**（CISA）。

**事实 2：MISRA C:2012 是一个有确定规模的标准，且有商业市场。** 同一报告：**MISRA C:2012 定义 143 条规则和 16 条指令**（来源标注 Perforce）；报告对比了 **11 款**工具（Visao、Coverity、Polyspace、Klocwork、CodeSonar、Parasoft C/C++test、Perforce QAC、Astrée、PVS-Studio、Cppcheck、Clang Static Analyzer），并明确指出"**工具不可互换**"、"**没有放之四海皆准的最佳工具**"。**关键限定**：该报告**明确排除定价信息**（"多数企业厂商使用项目特定报价"），**也不打分**（准确率、误报率、速度均不评分），且**作者自述开发了 Visao（对比工具之一）**——存在利益关联，已披露但需打折。

**事实 3：C++ 的安全路线在 2025 年被官方否决了。** 据 The Register 报道（中文转载：搜狐 2025-09-17，https://www.sohu.com/a/935826356_114765 ）：
- C++ 标准委员会**放弃**了 Sean Baxter 的 **Safe C++** 提案；
- **EWG（C++ 演进工作组）联合主席 Erich Keane 给出的投票数字：45 人中约 20 人支持 Safe C++ 论文，30 人支持 Profiles 工作（6 人中立）**；
- Baxter 原话："**Rust 安全模型在委员会中不受欢迎。我这边的进一步工作也不会改变这种情况。Profiles 方案赢得了这场争论。**"；
- **Bjarne Stroustrup 支持 Profiles**，其理念是"我希望获得这套保证，然后它将被强制执行"；但他也说"**令人遗憾的是，标准委员会感到困惑，没有保证这将包含在 C++26 中**"；
- Profiles 方案本身**也备受争议**（被批"不像任何已建立的可行解决方案、没有实现、今年早些时候也未能进入 C++26 标准"）；
- Baxter："**整个标准库都是不安全的。我提议了一个严格安全的 std2，但被拒绝了。**"
- 替代路线：**Carbon**（Google 实验性 C++ 继任者）路线图显示可能在"**2028 年之后**"发布 1.0。

**对阙疑的含义**：**"C++ 安全"这个战场在 2025–2026 年处于"官方路线未定 + 多方争议"的窗口期**。这对单人是**机会**（没有大一统方案），也是**风险**（可能押错路线）。

### 二、8 个候选项目（含取舍分析）

#### 候选 1：**queyi-eval —— AI 代码可信度基准（Benchmark）** ⭐ 最推荐

**一句话**：把阙疑从"一个验证系统"改造成"一套评测协议 + 公开基准"，让**任何人**可以用它评测 LLM/静态分析工具对 C++ 语义的判定可信度。

**为什么值得做**：
- **直接命中 NeurIPS E&D 的口味**：E&D track 要的就是"可信的评估设计"，而阙疑**已经有**：30 样本不可回盲 holdout（`reveal_irreversible=true`）、三层外部 corpus（A/B/C 分层报告，拒绝用总体平均掩盖 C 层 0%）、15 条真实缺陷夹具、以及**一次公开的"主动放弃口径"**（放弃内部变异率 97.3%）。
- **零数据集重建成本**：全部资产已在仓库里（`data/holdout/`、`data/external_corpus/`、`data/defect_fixtures/`）。
- **需求侧有硬证据**：Stack Overflow 2025 调查（33,244 人）显示 **46%** 的开发者主动不信任 AI 输出准确性、信任的只有 **33%**、"高度信任"仅 **3%**；**66%** 的最大挫败是"AI 给的方案几乎对但不完全对"（https://survey.stackoverflow.co/2025/ai ）。

**要补什么（工作量估计）**：①把 holdout 从 **30** 扩到 **100+**（新样本必须用新协议，不能碰已 reveal 的）；②把 corpus 从 **40** 扩到 **200+**；③写一个**不依赖内核的独立评测脚本**（阙疑已有"独立对账器"，复用即可）；④写协议文档（`EVAL_PROTOCOL.md`）。

**风险**：扩样本身就是"最贵的动作"，且**必须重新 blind**（旧 holdout 已 reveal，永久失效）。**但这是唯一能让阙疑"以最小增量变成 E&D 论文"的路径。**

#### 候选 2：**queyi-matrix —— 编译档 × sanitizer 交叉矩阵工具** ⭐ 最推荐（就业向）

**一句话**：把"**`-O1`→`-O0` 使 3/5 的漏检被同一个 sanitizer 抓住**"这个发现，做成一个**可直接用于嵌入式 CI 的交叉矩阵扫描器**。

**为什么值得做**：
- **完全复用阙疑已发现的实证**：论文 v0.3 已经把"编译档"列为三大测量陷阱之一，这是**独有发现**，别人没系统量化过。
- **对口合肥-嵌入式就业市场**：方向 93 的数据显示，2026 年 1–5 月应届生招聘需求增速领先行业中，**电子/半导体/集成电路**位列需求绝对量 TOP，**汽车零部件 28.4%**、**机器人 83.8%**；而**大疆"嵌入式软件工程师-RTOS"、华为"嵌入式软件工程师"（含 DSP/多线程调度）**都在招。
- **技术上是"小工具"**：核心是一个驱动脚本，跑 `-O0/-O1/-O2/-O3/-Os` × `ASan/TSan/MSan/UBSan/Valgrind` 的矩阵，输出"哪些缺陷在哪个档位被哪个工具抓住"的表格。
- **有现成的行业参照**：Interpretica 报告明确指出"**不同分析器很少返回相同的发现**"（引 NIST SATE 十年数据），且"**稳健的嵌入式工作流通常组合多层工具**"——**这句话就是 queyi-matrix 的产品定义**。

**要补什么**：①一个统一的 C/C++ 测试用例集（可用阙疑的 15 条缺陷夹具起步）；②CI 集成（GitHub Actions matrix）；③报告生成器（Markdown 表格）。

**风险**：**学术新意弱于候选 1**——它更像工程工具而非研究贡献。**但它的求职价值最高。**

#### 候选 3：**queyi-edu —— 面向教学的可视化验证器**

**一句话**：把阙疑的判决结果变成"教学可视化"，让学生看到"编译器/分析器到底看到了什么"。

**为什么值得做**：
- **有现成的、成功且失败都很清楚的先例**：**Aquascope** 是 Brown University **Cognitive Engineering Lab** 做的 Rust 借用检查可视化工具，把 rustc 内部 MIR/HIR 分析和 Miri 执行轨迹渲染成可交互的权限图与时间线。它的数据（Starlog 分析，2026-05-10，https://starlog.is/articles/developer-tools/cognitive-engineering-lab-aquascope ）：
  - **3.0k stars、72 forks、MIT 许可、4 位贡献者、35 个未关闭 issue**；
  - **最后一次提交：1 年前**；
  - **必须安装 `rustc-dev` 组件（数 GB）、锁定到特定 nightly（当前 2024-12-15）**；
  - 作者自述"**是明确的研究软件**"，"包含 bug、接口不稳定、文档稀疏"，"**不能跑在 CI 里**"；
  - 维护者的"坑"是："**每次编译器大重构，就得重写整个集成层。**"
- **这给出了两条明确教训**：①**教学可视化确有需求**（3.0k stars 说明有人要）；②**直接耦合编译器内部 API 是死路**——而**阙疑的架构恰好相反**：它是**独立于编译器的 Python 引擎 + 外部规则表**，耦合度天然低。

**要补什么**：①一个"学生视角"的 web 前端（阙疑已有 `web/verify.html`、`web/card.html`、`web/starmap.html`，可复用）；②10–20 个典型教学案例（C++ UB、悬垂指针、迭代器失效等）；③与一门具体课程绑定（本校的 C/C++ 课程）。

**风险**：**教育类工具"叫好不叫座"**，且**教育研究的发表周期长**（需要 IRB/伦理审查、前后测设计）。**不建议作为主项目。**

#### 候选 4：**queyi-multilang —— 多语言版（Rust/Go/Python）**

**一句话**：把阙疑的 67 条规则从 C++ 扩到多语言。

**为什么值得做**：**有顶级会议的工业界先例**——蚂蚁集团 + 华中科技大学的 **YASA**（Yet Another Static Analyzer）被 **FSE 2026 Industry Papers** 接收（2026-07-08 报告，DOI 10.1145/3808159，https://conf.researchr.org/details/fse-2026/fse-2026-industry-papers/24/YASA-Scalable-Multi-Language-Taint-Analysis-on-the-Unified-AST-at-Ant-Group ）。其摘要给出的具体数字：
- 核心方案是 **UAST（Unified Abstract Syntax Tree）**——为多语言提供统一抽象；
- 在**行业标准基准**上，与 **6 款单语言 + 2 款多语言**静态分析器对比，**在 Java、JavaScript、Python、Go 上一致优于所有 baseline**；
- **真实部署：分析超过 1 亿行代码、覆盖 7.3K 个内部应用**；
- **发现 314 条此前未知的污点路径，其中 92 条被确认为 0-day 漏洞**；
- **所有漏洞均已负责任披露，76 条已被内部开发团队修复**。
- 论文也点名了既有方案的局限："多语言工具如 **CodeQL、Joern、WALA**"在"中间表示设计、分析精度、可扩展性"上有局限。

**为什么不该现在做**：**这是一个 10 人团队 + 1 亿行代码部署的规模**。单人 + 考研时间表下，**从 C++ 扩到第二种语言就意味着规则表、语料、holdout 全部重做**——与"复用资产"原则直接冲突。

**结论**：**排除**（除非作为长期 3–5 年路线）。

#### 候选 5：**queyi-formal —— 形式化增强（"证明"而非"警告"）**

**一句话**：从"发现缺陷"升级到"证明某类运行时错误不存在"。

**外部参照**：
- **Rust 生态已有成熟工具矩阵**：*Surveying the Rust Verification Landscape*（arXiv:2410.01981，2024-10，发表于 **HATRA 2024** workshop，https://arxiv.org/abs/2410.01981 ）覆盖 **Prusti / Creusot / Aeneas / Verus / Kani / SMACK** 等工具；**Kani** 的论文 *Kani: A Model Checker for Rust* 已于 **2026-07-03** 发布（arXiv:2607.01504，https://arxiv.org/pdf/2607.01504 ）；**Creusot** 通过把 Rust 翻译成 Why3 平台的 **Coma** 中间验证语言工作（https://github.com/creusot-rs/creusot ）；**Prusti 与 Creusot** 都需要用户写函数契约（contracts）（ACM DL 10.1145/3744916.3773122）。
- **C++ 侧有 Polyspace Code Prover 与 Astrée**——Interpretica 报告明确定位它们为"**面向形式化、证明导向的分析**"，其中 **Astrée 基于抽象解释**，"核心目的是**证明 C/C++ 软件中运行时错误不存在**"，并明确警告"**编码标准合规非 Astrée 的主要角色**"、"**不要仅按警告数量或扫描速度将其与 MISRA 检查器比较**"。

**为什么不该现在做**：形式化验证的入门成本极高（需要掌握抽象解释、SMT、分离逻辑），且**已有大量成熟工具**。**单人新做形式化工具，学术上很难超越 Kani/Prusti/Verus，工程上也很难超越 Polyspace/Astrée。**

**结论**：**排除作为"新做工具"，但可作为"接入"**——见候选 6。

#### 候选 6：**queyi-bridge —— 把阙疑规则桥接到既有验证器**

**一句话**：不做新工具，做**翻译层**：把阙疑的 67 条规则自动转成 Kani/Prusti 的 harness，或转成 Hypothesis/QuickCheck 的属性。

**为什么值得做**：
- **有直接的研究空白可填**：**HarnessLLM: Rust Verification Harness Generation with Large Language Models**（ACM DL 10.1145/3744916.3773122，2026-09-11）正在做"**用 LLM 生成验证 harness**"——这说明"**harness 生成**"是一个被认可的研究问题。
- **属性测试（PBT）在 2026 年被认为进入主流**：多篇 2026 年的文章把 PBT 描述为"从 Haskell 小众工具走向主流工程"（例：talkingtech.io 2026-06-09；pistack.xyz 2026-05-04 对比 **Hypothesis / fast-check / proptest**）；且普遍共识是"**PBT 是互补而非替代**基于样例的测试"。
- **工作量可控**：核心是"规则 → 属性"的映射表 + 一个生成器。阙疑已有 `data/_gate_rules.json`（67 条规则的结构化表示），**这是天然的输入**。

**风险**：**依赖外部工具的稳定性**（Kani/Prusti 都是活跃研究项目，接口会变）。

#### 候选 7：**queyi-compliance —— MISRA C:2012 合规检查器**

**一句话**：把阙疑的规则集映射到 **MISRA C:2012 的 143 条规则 + 16 条指令**，做嵌入式合规工具。

**为什么有吸引力**：市场明确（Interpretica 报告列出 7 款支持 MISRA 的商业工具：Coverity、Polyspace Bug Finder、Klocwork、CodeSonar、Parasoft C/C++test、Perforce QAC、PVS-Studio，以及 Cppcheck Premium）；标准规模明确（**143 规则 + 16 指令**）。

**为什么不该做**：
- **合规工具的核心壁垒不是技术，是"资格认证包"（qualification package）和审计证据链**——这是**一家公司**的活，不是一个人的活。
- Interpretica 报告明确："**MISRA 支持 = 功能安全认证吗？否**——MISRA 是编码指南框架。"
- 且报告强调"**检查 MISRA 规则的工具不等于形式化验证器**"——**阙疑的定位（可被独立验收）与 MISRA 合规是两回事**。

**结论**：**排除。**

---

#### 候选 8：**queyi-embedded —— 嵌入式专用子集（安全关键 C 子集）**

**一句话**：把阙疑从"C++ 通用"收窄到"**嵌入式安全关键 C 子集**"（MISRA 风格 + 静态存储 + 无动态分配 + 中断/并发）。

**为什么有吸引力**：
- **完全对口作者的"合肥-嵌入式"身份**：方向 93 已列出长鑫存储（合肥，2026 秋招覆盖本科）、大疆、华为等真实岗位。
- **可以复用阙疑的并发域资产**（`atoms/conc/` 3 卡）与内存域资产（`atoms/mem/` 23 卡，最大头）。
- **收窄反而提升精度**：C 子集比完整 C++ 语义简单得多，**67 条规则的误报率会显著下降**。

**风险**：**收窄会削弱"可被独立验收"的通用叙事**（NeurIPS E&D 更认通用协议）。**但与候选 2 可以合并**（queyi-matrix 就是嵌入式的）。

### 三、取舍矩阵（8 个候选的打分）

评分维度：**①资产复用度**（能否直接用阙疑的 67 规则/holdout/corpus）；**②学术可发表性**；**③求职价值**；**④单人可完成度**（在 2027-12 考研前）；**⑤维护成本**（越低越好）。每项 1–5 分。

| 候选 | 资产复用 | 学术 | 求职 | 单人可完成 | 低维护 | **合计** | 结论 |
|---|:--:|:--:|:--:|:--:|:--:|:--:|---|

**最优组合（推荐）**：**queyi-eval（学术主线） + queyi-matrix（就业主线）**，两者共享同一套规则与语料，**边际成本最低**。具体做法：**queyi-matrix 的矩阵输出，直接成为 queyi-eval 的一个评测维度**（"同一缺陷在不同编译档下是否被检出"），**一份工作量，两个产出**。

### 四、必须避免的三种"下一个项目"

1. **从零做已被验证失败的技术路线**：如 Rust 借用检查可视化（Aquascope 已做且已 1 年未更新）。
2. **从零做需要大规模数据集的方向**：如多语言污点分析（YASA 是 10 人团队、1 亿行代码部署）。
3. **从零做需要资质认证的方向**：如 MISRA 合规工具（壁垒是资格认证包与审计链，不是技术）。

### 五、"不做新项目"也是一个正当选项

按方向 91 的数据，**2026 年 1–5 月应届生招聘需求增速**中，**机器人 83.8%**、**新材料 60.1%**、**电子/半导体/集成电路位列需求绝对量 TOP**（智联招聘）。**如果作者决定把 2026-10 到 2027-06 的全部时间用于"补嵌入式硬技能（RTOS、驱动、DSP）+ 考研"，而把阙疑冻结在现有状态，这也是完全理性的选择**——因为阙疑的**67 条规则 + 3826 行引擎 + 30 样本不可回盲协议**已经是完整的求职素材，**不需要新项目来证明它**。

## 对阙疑的 3 条具体行动

1. **启动 queyi-matrix（就业向，成本最低），2026-12 前出第一版**。具体交付物：①`tools/matrix_scan_<batch>.py`——输入一个 C/C++ 文件，自动跑 `-O0/-O1/-O2/-O3/-Os` × `ASan/TSan/MSan/UBSan/Valgrind` 的矩阵；②`data/matrix_<batch>.json`——结构化结果；③`_arch_v46/95_matrix_report.md`——一份"哪些缺陷在哪个编译档被哪个工具抓住"的表格。**起点直接用阙疑的 15 条真实缺陷夹具**（`data/defect_fixtures/defects.json`），**第一版只跑 15 条，不求多**。**验证标准**：能复现论文 v0.3 已记录的"**`-O1`→`-O0` 使 3/5 miss 被同一 sanitizer 抓住**"这一发现。
2. **为 queyi-eval 做"扩样可行性评估"，2027-01 前给出数字**。具体三步：①**算清成本**——把 holdout 从 **30** 扩到 **100** 需要多少人工小时（按现有 30 样本的实际耗时外推）；②**确认协议约束**——旧 holdout 已 `revealed=true`、`reveal_irreversible=true`，**新样本必须是一套全新的、从未 reveal 的 blind set**，并在 `data/holdout/` 下新建 `holdout_v2_blind.json`（`blind=true`、`revealed=false`）；③**写一页决策备忘 `_arch_v46/95_eval_go_nogo.md`**：若扩到 100 的预估成本 **> 120 小时**，则**放弃 queyi-eval，全力做 queyi-matrix**（因为考研时间不可再挤压）。**这是一个明确的"止损点"，不要含糊。**
3. **写一份《阙疑资产复用清单》（`_arch_v46/95_资产复用清单.md`），2026-11 前完成**。内容：把仓库里**所有可被下一个项目直接复用的东西**列成表——①`data/_gate_rules.json`（67 条规则，可直接作为任何新工具的知识源）；②`data/holdout/holdout.json`（30 样本 + 不可回盲协议，**只能作为"协议范本"，不能作为新项目的盲测集**）；③`data/external_corpus/external_corpus_665.json`（40 条，三层）；④`data/defect_fixtures/defects.json`（15 条真实缺陷）；⑤`tools/gate_engine.py`（3826 行，可作为"独立对账器"的对照组）；⑥`web/verify.html`（现场验哈希，可作为任何新项目的可信度演示前端）。**每一行标注"可否直接复用 / 需改造 / 不可复用"**。**理由**：这份清单能让"下一个项目"的启动成本从"重新开始"降到"改配置"，而这正是单人项目在考研挤压下唯一可行的做法。
