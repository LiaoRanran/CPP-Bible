# 方向 50：形式化验证性价比（seL4 / CompCert / Frama-C / Kani / Prusti）

> 调研时间：2026-09-29。联网检索 16 次（WebSearch 10 + WebFetch 6）。
> 锚点：阙疑的"可被独立验收"若走到极致就是形式化验证。本方向回答：**证明一行代码要花多少钱、什么时候值、什么时候纯属自杀。**

## 核心结论

1. **形式化验证的性价比在"验证单元越小、规格越清晰"时越好，且差距是数量级的**：HACMS 项目的对照表（PMC5597724）给出 8 个已验证系统的硬数据——**seL4：10K 行 C + 480K 行证明 + 13 人年（48:1）**；而 **Quark 浏览器：5.5K 行 + 0.5 人年**、**Nucleus 垃圾回收器：6K 行 + 0.75 人年**。**同一份"形式化"标签下，单位成本可以差 50 倍以上**。决定因素不是技术，而是**规格好不好写**。
2. **对阙疑最关键的判断是：阙疑"值得"的形式化验证不是 seL4 式的全证明，而是 Kani/Frama-C 式的"契约 + 有界模型检查"**。Kani 的实测数据显示：**零注解就能自动检查"无 UB + 无 panic"**，且在生产代码里找到 **11 个测试与模糊测试都漏掉的 bug**（其中 s2n-quic 的 `try_fit`：模糊测试跑了 **16,777,216 次执行、超 10 分钟未发现，Kani 20 秒找到**）。
3. **"证明完成"之后收益是长期且可量化的，这是形式化验证唯一真正的卖点**：seL4 官方页给出硬数字——**自 2009 年功能正确性证明完成以来，超过 15 年、10,000 行已验证代码中"零功能正确性缺陷"**；同期未验证配置（多核 SMP、x64 VT-x）**持续被发现缺陷**。**对阙疑的映射：把 67 条规则中最核心的 44 条 block 规则做成"可独立验收 + 永不复现旧缺陷"的资产，比"再做 100 条规则"更有价值。**

## 精确数字与案例

### 一、HACMS 的 8 系统对照表（本方向最重要的一张表）

- 来源：`The HACMS program: using formal methods to eliminate exploitable bugs`，Fisher 等，Phil. Trans. R. Soc. A，PMC5597724（2017）。
- 表 1 原文数据（LoC = 代码行；LoP = 证明行；PY = 人年）：

| 验证对象 | 规模 | 开发时间 | 性能代价 |
|---|---|---|---|
| **seL4** | 10K LoC，**480K LoP** | **13 PY** | 206 vs 227 cycles |
| **CompCert** | 42K LoC+P | **3 PY** | 比 gcc -O0 快 2 倍；比 -O1 慢 7%；比 -O2 慢 12% |
| FSCQ 文件系统 | 24K LoC+P | <5 PY | xv6 文件系统的 80% |
| certiKOS Hypervisor | 2K LoC，18.5K LoP | **1 PY** | 多数 lmbench 基准 <2 倍减速 |
| **SHA-256/HMAC** | **407 LoC，14.4K LoP** | n.a. | 与 OpenSSL 0.9.1c 相当 |
| **Rocksalt 沙箱** | **100 LoC，10K LoP** | <2 PY | 比 Google 的 checker 快 1M 指令/秒 |
| **Nucleus GC** | 6K LoC+P | **0.75 PY** | "有竞争力" |
| **Quark Web 浏览器** | 5.5K LoC+P | **0.5 PY** | 相对 WebKit 基线 24% 开销 |

- **关键读数**：
  - **seL4 的证明/代码比 = 480K / 10K = 48:1**；若只算功能正确性证明（SOSP09 口径 200K 行）则为 **20:1**；
  - **Quark（5.5K 行 / 0.5 PY）与 seL4（10K 行 / 13 PY）对比：单位人年成本差约 14 倍**（按 5.5K/0.5=11K 行/人年 vs 10K/13=0.77K 行/人年）；
  - 论文自承的关键阻碍（原文 7(a)）：**2006 年估计全世界形式化方法专家不足 5,000 人**；7(b)：**证明规模必然反映为开发时间增加**；
  - 论文对 seL4 的评价：**"seL4 是个离群点（outlier），其它系统的验证开销率更低"**——原因是"**形式化写清楚"微内核正确意味着什么"本身就无法简洁完成**"。

### 二、seL4：最贵、也最成功的那个

- 论文：`seL4: Formal Verification of an OS Kernel`，Klein 等，**SOSP 2009**，pp. 207–220，DOI `10.1145/1629575.1629596`；获 **ACM SIGOPS Hall of Fame Award (2019)** 与 **ACM Software System Award (2022)**。
- 规模（SOSP09）：**8,700 行 C + 600 行汇编**。
- 证明：**约 200,000 行 Isabelle/HOL**（功能正确性证明）。
- 人力：**约 11 人年**（seL4 专属部分，不含可复用基础设施投入）；另一官方表述为"初始功能正确性证明 11 人年"。
- 分解（据二手论文笔记，**未逐字核对 SOSP09 原文表格**）：抽象规格 4 人月、Haskell 原型 2 人年、C 实现 2.2 人年、验证约 11 人年；**80% 的 refinement 工作量花在不变式保持上**；不变式约 **150+ 条**，分四类（内存、类型、数据结构、算法）。
- 性能：**单向 IPC 约 224 cycles**；论文强调"**无显著性能退化**"，推翻了"已验证内核必然慢"的说法。
- **官方 15 年战绩（seL4 官方 proofs 页，2026-09 更新）**：
  - "**自 2009 年功能正确性证明完成以来，已验证代码中零功能正确性缺陷**"（more than 15 years）；
  - 完整性证明完成后**从未出现完整性缺陷**；
  - 对照：**未验证配置（多核 SMP、x64 VT-x 虚拟化）中持续发现缺陷**；**即便在已验证配置里，每一类未验证代码（硬件假设、编译器假设、未验证的启动代码）都发现过小缺陷**；
  - 原文表述："在全部 **10,000 行已验证代码**中，那么长时间里**什么都没有出错**。"
- **证明不覆盖什么（官方 assumptions 页）**：**GCC 编译器、汇编桩、硬件（ARMv6）、TLB/cache 行为、启动代码**。原文："C 层以下的错误不被覆盖。"
- **阙疑可借鉴的两条设计原则（原文 Lessons Learned）**：① **"为验证而设计"**（event-based 内核、最小抢占、显式内存管理、受控中断点、capability 化内存控制）；② **验证约束反过来提升了设计质量**。**这两条对阙疑的 `gate_engine.py` 重构直接可用。**

### 三、CompCert：证明/代码比最低的"划算案例"

- 论文：`Formal verification of a realistic compiler`，Xavier Leroy，**CACM 52(7):107–115，2009-07**（POPL 2006 首发），DOI `10.1145/1538788.1538814`。
- 规模：**Coq 证明基约 100,000 行**（含形式语义与各 pass 的正确性证明），**编译器本体约 20,000 行** → **证明/代码比约 5:1**（**这是所有大型案例里最低的**）。
- HACMS 口径：**42K LoC+P，3 人年**。
- 性能：**比 gcc -O0 快 2 倍；比 gcc -O1 慢 7%；比 gcc -O2 慢 12%**。
- 覆盖：**ISO C 2011 的绝大部分**；目标 **x86-64 / ARM / RISC-V / PowerPC**；约 **12 道 IR、约 20 个 pass** 逐一证明语义保持（据二手汇总，**未逐字核对**）。
- **CSmith 的实证（PLDI 2011，Yang 等，被 seL4 官方页引用）**：原文——"关于 CompCert 的结果中最引人注目的是，我们在其它所有编译器中找到的 middle-end bug 在这里**不存在**。**截至 2011 年初，处于开发中的 CompCert 是我们测试过的唯一一个 Csmith 找不到 wrong-code 错误的编译器。这不是因为没试：我们为此投入了大约六个 CPU 年。**"
- **TCB（可信基）清单**：Coq 内核（约 10K 行）、源语言形式语义（约 4K 行）、目标汇编形式语义（约 3K 行）、OCaml 提取出的可执行编译器（提取过程 + OCaml 编译器均属 TCB）。**所有 IR 与 pass 的实现都不在 TCB 内**（因为它们被证明语义保持）。
- **明确不覆盖**：**源程序的未定义行为**（越界访问、use-after-free、有符号整数溢出）——"这些仍是程序员的责任"。
- 认证与荣誉：**2026-03 首次为 ATR 42/72 航电软件（AbsInt 在 Airbus 指导下）依据 DO-178C / DO-333 / DO-330 主张认证积分**；**2022 ACM SIGPLAN Programming Languages Software Award**；**2021 ACM Software System Award**。
- **对阙疑的含义**：**CompCert 是"证明/代码比 5:1"的存在性证明**——说明**只要规格好写，形式化验证不必是 48:1**。阙疑的规则如果写成"输入域 → 判决"的纯函数契约，就落在 CompCert 这一档，而不是 seL4 那一档。

### 四、Frama-C：C 语言的工业级"半自动"路线（最贴近阙疑的现有工具）

- 论文：`Post-Hoc Formal Verification of Automotive Software with Informal Requirements: An Experience Report`，Ung、Amilon、Gurov、Lidström、Nyberg、Palmskog（**Scania + KTH**），**RE 2024**，pp. 287–298。
- 案例：一家**重型车辆行业**公司提供的**工业软件模块**；起点是 **32 条非形式化需求**。
- 做法：按需求性质分别形式化为 **ACSL 契约 / LTL / MITL**，用 **Frama-C 演绎验证框架**验证源码。
- **结果：32 条需求中，21 条成功验证、6 条未通过、5 条因"描述模块之外的行为"而无法在模块内验证。**
- 论文结论：**"形式化验证驱动的模块开发 + 已验证的系统需求分解，很可能能补救我们遇到的问题"**。
- 相关工具链进展：**AutoDeduct**（arXiv:2501.10889，2025-01）在 Frama-C 之上做演绎验证自动化；**2026 年已有工作评估 LLM 生成的 ACSL 注解**（arXiv:2602.13851，CASP 基准 + Frama-C WP 插件）——**这条对阙疑特别有价值：LLM 写契约、Frama-C 判契约，正好分工。**
- **阙疑可借鉴的数字口径**：**21/32 = 65.6% 的需求可被成功验证**，且**失败与"模块外行为"占了 11/32 = 34.4%**——**这提示阙疑：先划清"哪些断言在本模块内可判定"，比"能不能证明"更重要。**

### 五、Kani：Rust 的"零注解即可用"路线（阙疑最该学的性价比模型）

- 论文：`Kani: A Model Checker for Rust`，arXiv:2607.01504（2026-08）；仓库 `github.com/model-checking/kani`（AWS 主导）。
- **默认自动检查（无需任何用户注解）**：**无未定义行为**（无效/悬垂指针解引用、未对齐转换、无效枚举判别值）、**无运行时 panic**（算术溢出、除零、未定义移位、越界索引、`unwrap()` on None）、**资源属性**（浮点转整数有限性）。
- **可选深度检查**：`valid-value pass`、`uninit-memory pass`（影子内存）。
- **需加契约才能验证**：无界功能正确性、递归函数无界验证、终止性证明（`loop_decreases`）。
- **真实生产项目的 harness 数与耗时**：

| 项目 | 领域 | Harnesses | 运行时间 | 用契约 |
|---|---|---|---|---|
| **Firecracker** | 云基础设施 | 34 | 21 分钟 | ✓ |
| **s2n-quic** | 网络协议 | 102 | 23 分钟 | – |
| **Hifitime** | 航空航天 | 153 | 42 分钟 | ✓ |
| **verify-rust-std** | 标准库 | **16,748** | 69 分钟 | ✓ |
| zerocopy | 序列化 | 10 | 3 分钟 | ✓ |
| rust-sel4 | 微内核 | 1 | 4 分钟 | – |

- **verify-rust-std 每次代码变更验证 16,000+ harnesses**，通过并行化 + 增量缓存实现 **3.97× 加速**，CI 约 **69 分钟**。**大多数项目 CI 在 25 分钟内**，可进 PR 工作流。
- **在 4 个生产 Rust 代码库中发现 11 个测试与模糊测试都漏掉的 bug**（原文 Table 2）：
  - **s2n-quic `try_fit` 断言**：**模糊测试跑了 16,777,216 次执行（>10 分钟）未发现失败，Kani 20 秒找到**——bug 位于 1 字节与 2 字节整数编码的边界，**模糊测试无梯度可循的稀疏区域**；
  - **s2n-quic `decode_packet_number`**：Kani **2.8 秒**找到；
  - **Firecracker 限流器舍入**：允许 guest 在对抗性定时下**超出 I/O 预算最多 0.01%**；
  - **Firecracker VirtIO panic**：guest 可把队列组件起始地址放入 MMIO 间隙导致启动 panic；
  - **Cedar `contains_at_least_two`**：多字节字符跨越非字符边界切片 `&str` 导致 panic——**即使在针对形式化参考模型的差分测试下仍存活到生产代码**；
  - **Hifitime 6 个 bug**（`normalize()` 符号溢出、`i64::MIN.abs()` panic、浮点乘法 NaN 循环、Epoch/Duration 的 Eq/Ord 不一致、`is_gregorian_valid` 溢出）——**其中 2 个违反 Rust 标准库自身要求**。
- **契约带来的性能提升（决定性数字）**：

| 场景 | 无契约 | 有契约 |
|---|---|---|
| GCD 全 u64 范围有界验证 | **1 小时超时未终止** | **202 个检查 0.54 秒通过** |
| Hifitime `Mul<f64>` 循环隔离验证 | 展开 19 次迭代需 **91.8 秒** | **0.2 秒** |
| TokenBucket::new（Firecracker） | 需展开全部 64 位 GCD 迭代，数小时 | **数秒**（对所有 64 位输入无界保证） |

- **Kani 的 soundness 局限（原文明确列出）**：**不支持 Stacked Borrows / Tree Borrows 指针别名建模**；**无 FFI**（除非 stub）；**顺序执行**（无线程/async）；**递归函数不验证终止性**；**不支持互递归**；**不支持泛型、动态 trait 分派、并发执行**。
- **Hifitime 的注解成本（可作阙疑的预算参照）**：**9.5K 行库 + 125 个契约注解 + 153 个 harnesses**；**84 个函数带 ensures、41 个带 requires**。
- **对阙疑的含义（最重要）**：Kani 的模式是**"零注解先拿到 UB/panic 检查，再按需加契约换无界保证"**——这正是阙疑可以照搬的**渐进式验证策略**。**且契约带来的加速是 100 倍量级（1 小时超时 → 0.54 秒），说明"写规格"不是成本，而是投资。**

### 六、Prusti：Rust 演绎验证的另一条路（数据不足）

- 项目：`Prusti`，ETH Zurich Programming Methodology Group，基于 **Viper** 验证基础设施；通过注解指定函数行为，**编译时**保证程序正确性（`github.com/prusti/prusti`；dev guide `viperproject.github.io/prusti-dev/`）。
- 相关资源：ETH 硕士论文 `Annotating the Rust Standard Library with Specifications for Prusti`（Julian Dunskus，2023-05）——说明**为 Rust 标准库写规格本身就是一项研究级工作量**。

### 七、成本的外部参照：DO-178C（把形式化放回航空认证语境）

- **⚠️ 以下数字全部来自厂商/博客二手来源，未经同行评审，本报告只登记不采信：**
  - Black Duck/Coverity 的 DO-178C 白皮书：**认证成本通常为每行代码 $25–$100**（即 10 万行代码约 $2.5M 起）；
  - `koddex.io` 引"2025 RTCA benchmark"：**DO-178C Level A 软件认证平均 €18–25M / 项目**；
  - `speytech.com`：**认证工作量随代码规模增长**。
- **可采信的一手事实**：**CompCert 已于 2026-03 首次为 ATR 42/72 航电（AbsInt + Airbus）依据 DO-178C/DO-333/DO-330 主张认证积分**（来源：compcert.org 官方新闻页）。
- **对阙疑的含义**：DO-178C 的"每行 $25–$100"给出了**形式化验证的商业天花板参照**——**任何"比这更贵"的验证方案在工业界都卖不出去**。

### 八、什么时候值得、什么时候不值（把上面的证据压成判据）

| 判据 | 值得做形式化验证 | 不值得 |
|---|---|---|
| **规格是否好写** | 规格能用一页写清（SHA-256：407 行代码 14.4K 行证明，但**语义明确**） | 规格写不清楚（**seL4：官方承认"写清微内核正确意味着什么"无法简洁完成**） |
| **验证单元大小** | 小而关键（**Rocksalt 100 行 / Nucleus 6K 行 / Quark 5.5K 行**） | 大而模糊（seL4 10K 行 13 PY） |
| **是否需要"无界保证"** | 需要（**Kani 契约：1 小时超时 → 0.54 秒**） | 只需抽样（有界模型检查 + 模糊测试更便宜） |
| **缺陷是否会长期复现** | 会（**seL4：15 年零功能正确性缺陷**） | 一次性原型 |
| **团队是否有形式化专家** | 有（**2006 年全球不足 5,000 人**） | 没有（**HACMS 明确列为第一阻碍**） |
| **是否有认证需求** | 有（CompCert 拿 DO-178C 积分） | 无 |

- **一句话判据**：**"规格能一页写清 + 单元小 + 缺陷会复现" 三者同时成立才值得；缺一个就该退回到"契约 + 有界检查"或"规则 + 测试"。**

## 对阙疑的 3 条具体行动

1. **对 44 条 block 规则做一次"可形式化性"三档分类（零成本，写作层）**：把 44 条规则按"规格能否一页写清"分成三档——**A 档（可形式化，如整数溢出、越界、空指针）**、**B 档（可写成 ACSL 式契约，如前置条件/后置条件）**、**C 档（语义模糊，如"命名风格""可读性"）**。依据：HACMS 证明"**规格好不好写"是成本的第一决定因素**（seL4 48:1 vs Quark 11K 行/人年）；Frama-C 的 Scania 案例显示 **32 条需求中 11 条（34.4%）要么失败要么在本模块外**。**落地**：在本目录（`_arch_v46/`）起草分类表，作为论文 Method 的"哪些断言可被独立验收"的依据。
2. **对 A 档规则照搬 Kani 的"零注解优先 + 契约加速"策略（技术落地）**：① 先给阙疑的 C++ 缺陷夹具跑 **clang 静态分析 + UBSan/ASan**（等价于 Kani 的"零注解 UB/panic 检查"）；② 再对**边界敏感的规则**（如整数溢出、移位、有符号比较）写**前置/后置条件**，预期获得 Kani 量级的加速（**1 小时超时 → 0.54 秒**）。**依据**：Kani 在生产代码找到 **11 个测试与模糊测试都漏掉的 bug**，其中 **s2n-quic 的 bug 模糊测试 16,777,216 次执行未发现、Kani 20 秒找到**。**注意：本方向只写 `_arch_v46/`，代码落地由后续批次执行。**
3. **把"15 年零缺陷"改造成阙疑的"回归不变式"叙事（写作层，最有论文价值）**：seL4 官方页的核心论据是"**自证明完成以来 15 年、10,000 行已验证代码零功能正确性缺陷，而同期未验证配置持续出缺陷**"。阙疑可对应建立：**一旦某条 block 规则被"独立验收"通过，就在 append-only 哈希链上标记为 `frozen`，此后任何新批次若使该规则的历史判决发生变化即触发告警**。**这是把"形式化验证的长期收益"用哈希链账本实现的低成本版本**，且完全落在阙疑现有架构内（Merkle checkpoint + 独立对账器）。

## 盲区（诚实标注）

- **seL4 的人年数字有多个口径**：SOSP09 写 **约 11 人年**（seL4 专属）；HACMS 表 1 写 **13 PY**；另有二手来源写 **约 20 人年 / 约 25 人年**（含全部基础设施）。**本报告同时列出 11 与 13 并标注来源，不合并成一个数。**
- **seL4 的证明行数有多个口径**：SOSP09 写 **约 200,000 行 Isabelle**（功能正确性）；HACMS 写 **480K LoP**；`andygauge.github.io` 写"**每 10,000 行代码约 200,000 行证明**"。**差异来源（是否含安全证明、二进制正确性证明、是否含可复用库）未逐字核对**。
- **seL4 的"80% 工作量在不变式"与"150+ 不变式"来自二手论文笔记**（justinlinkk.github.io），**未从 SOSP09 原文逐字核对**。
- **CompCert 的"100,000 行 Coq"来自二手来源**（`sota.io` 博客、`magicliang` 博客），**未从 CACM 2009 原文核实**；HACMS 只给"42K LoC+P，3 PY"。**"5:1 证明/代码比"是基于"100K 证明 / 20K 代码"的自行计算**，可能因口径不同而偏差。
- **CompCert 的"12 道 IR、约 20 个 pass"来自中文二手博客**（magicliang），**未核实**；compcert.org 主页只零散提到 Clight、if-conversion pass、寄存器分配器等。
- **CompCert 的 TCB 明细（Coq 内核 10K 行、源语义 4K 行、目标语义 3K 行）来自中文二手博客，未核实。**
- **Kani 论文（arXiv:2607.01504）是 2026-08 的 arXiv 预印本**，未见同行评审；其 Hifitime 案例（Blue Ghost Mission 1 登月任务）的表述来自该论文。
- **Prusti 的量化数据（每行代码需多少行规格）本轮未查到**；只知 ETH 有专门硕士论文研究"给 Rust 标准库写规格"。
- **DO-178C 的"$25–$100/行""€18–25M/项目"全部来自厂商/博客二手来源，未经同行评审，本报告明确标注为不采信**；唯一一手事实是 CompCert 的 2026-03 DO-178C 认证积分。
- **Frama-C 的 Scania 案例只有"21/32 需求验证成功"这一层数字**；**该模块的代码行数、ACSL 注解条数、证明义务（PO）数量与自动 discharge 比例本轮未查到**——这是本方向最大的数据缺口。
- **未查到**：C++ 领域的完整形式化验证案例（如给 C++ 子集做 seL4 式验证的公开项目）。**阙疑若做 C++ 子集的形式化，属空白区，但没有可对标 baseline。**
- **未查到**：形式化验证的"每小时人力成本"公开数字（人年 → 货币的换算本轮无来源）。
- 所有数字需在 **2027 投稿时点刷新**。
