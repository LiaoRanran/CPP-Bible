# 方向 42：数据版本管理（DVC / git-lfs / lakeFS / 数据集哈希清单）

> 调研时点：2026-09-29。搜索次数：14（WebSearch 11 + WebFetch 3）。
> 服务对象：阙疑（queyi）的 `data/holdout/holdout.json`（30 seeds）、`data/external_corpus/external_corpus_665.json`（40 条）、`data/defect_fixtures/defects.json`（15 条）与 452 条判决账本。

## 核心结论

1. **数据集版本化是"可复现性"的瓶颈而非补充**：Gundersen 等（AAAI 2025，arXiv:2412.17859）对 30 篇高被引 AI 论文做系统复现，发现**同时共享代码与数据的论文有 86% 能完全或部分复现，而只共享数据的是 33%，只共享论文的不足 10%**；更关键的是**"数据文档质量与复现成功率相关，而代码文档质量不相关"**——这直接说明"数据怎么版本化、怎么记哈希清单"比"代码写得多漂亮"更决定别人能否验收你。
2. **DVC 与 git-lfs 解决的是两类不同问题，不能互相替代**：git-lfs 只是把大文件换成指针（**GitHub Free 账户仅 10 GiB 存储 + 10 GiB 带宽**），**不提供数据血缘、不提供管道复现**；DVC 用 `.dvc`/`dvc.yaml`/`dvc.lock` 把**数据哈希 + 管道 DAG + 参数**一起版本化，`dvc repro` 能"改一个参数，只重算受影响的 stage"。lakeFS 则是另一层：在对象存储上做**零拷贝分支**，面向 PB 级数据湖。
3. **对阙疑这种"小数据 + 强可复现声明"的项目，最划算的不是上 DVC 全家桶，而是"哈希清单（manifest）+ 单一数据冻结版本 + 一条 `dvc repro` 等价命令"**：因为 30/40/15 这三份 JSON 总共可能只有几百 KB，真正的风险不是"数据太大"，而是**"别人拿到仓库后无法证明跑的是同一份数据"**。

## 精确数字与案例

### 1. 复现危机的实测数字（这是本方向最重要的一手证据）

**Gundersen, Odd Erik; Cappelen, Odd; Mølnå, Martin; Nilsen, Nicklas Grimstad（2024），"The Unreasonable Effectiveness of Open Science in AI: A Replication Study"，arXiv:2412.17859，被 AAAI 2025 接收。** 原文摘要关键句（逐条）：

- 系统复现了 **30 篇高被引 AI 研究**；
- **8 篇被直接排除**，原因是"需要实际不可能获取的数据或硬件"（required access to data or hardware that was practically impossible to acquire）；
- **6 篇完全复现，5 篇部分复现**，合计 **50%（15/30）**在某种程度上被复现；
- **共享了代码与数据的论文：86% 完全或部分复现；只共享数据的论文：33%**；
- **"数据文档的质量与成功复现相关（correlates with successful replication）"**；
- **"令人意外的是，代码文档质量与成功复现不相关"**——原文："Surprisingly, the quality of the code documentation does not correlate with successful replication. Whether the code is poorly documented, partially missing, or not versioned is not important for successful replication, as long as the code is shared."

这条结论对阙疑的启示是**反直觉但极其重要**：阙疑花了大量精力在"67 条规则、3826 行内核、452 条账本"的代码侧文档，但按这项研究，**真正决定别人能否验收的是数据侧的文档与版本**。阙疑的 holdout/external_corpus/defects 三份 JSON 必须带**数据卡片（datasheet）级别的说明**（来源、采集时间、标签口径、标注者、盲化状态、版本哈希），否则复现失败的概率远高于代码写得差。

**补充数字**（来自 HDSR 的 Barba 综述与多方交叉）：
- **ICML 2019**：**36%** 的 3,000+ 投稿包含代码；**774 篇录用论文中有 67%** 包含代码（有代码的论文录用率略高）；
- **NeurIPS 2019**：**6,743 篇投稿中 40%** 包含代码；**录用论文中 74.4%** 包含代码（Pineau et al., 2021）；
- 另有综述（TechRxiv, 2025, doi:10.36227/techrxiv.177155769.94899097）指出：ML 复现的三大障碍是**技术性（不确定性 + 环境不稳定）、方法性（报告差 + 评估陷阱）、文化性（激励结构）**，并给出五步模型：**协议定义 → 环境规格 → 实验追踪 → 验证协议 → artifact 准备**。

### 2. DVC 的精确机制（一手文档核实）

DVC 官方文档（doc.dvc.org）明确的核心文件与语义：

| 文件 | 作用（文档原文语义） |
|---|---|
| `dvc.yaml` | 定义 ML 项目的**流水线 stage**（YAML 1.2），"设计得足够小，便于你用 Git 与代码一起版本控制" |
| `dvc.lock` | 记录流水线状态与输出，**含内容哈希字段（`md5` / `etag` / `checksum`）**，"请勿手动编辑" |
| `.dvc` 文件 | 与 `dvc add` 配套的单文件/目录追踪文件，存放输出哈希与大小 |

`dvc.lock` 的真实样例（官方文档原文，可直接对比阙疑的 JSON 哈希）：

```yaml
schema: '2.0'
stages:
  features:
    cmd: jupyter nbconvert --execute featurize.ipynb
    deps:
      - path: data/clean
        md5: d8b874c5fa18c32b2d67f73606a1be60
    params:
      params.yaml:
        levels.no: 5
    outs:
      - path: features
        md5: 2119f7661d49546288b73b5730d76485
        size: 154683
```

**stage 的必需字段只有 `cmd`**，其余 `deps` / `outs` / `params` / `frozen` / `always_changed` / `meta` / `desc` 均为可选；输出的子字段包括 `cache`（是否缓存）、`remote`（用哪个远端）、`persist`（repro 时是否保留）、`push`（是否随 `dvc push` 上传）。

**关键命令族**（文档中出现并被本调研交叉确认）：
- 数据侧：`dvc add`（把文件/目录纳入 DVC 追踪，生成 `.dvc`）、`dvc push` / `dvc pull` / `dvc fetch` / `dvc checkout`；
- 管道侧：`dvc stage add`、`dvc repro`（只重跑受影响的 stage）、`dvc status`、`dvc dag`（打印依赖图）；
- 实验侧：`dvc exp run`（配合 DVCLive 做实验追踪）、`dvc params diff`、`dvc metrics`、`dvc plots`。

**DVC 的一个硬性要求（官方原文）**：`cmd` 应该"只从指定的 dependencies 和 outputs 读写、完全重写输出（不要追加或编辑）、退出时停止读写文件"，且"代码应具备确定性（避免随机数、时间函数、硬件依赖等）"——**这一条与阙疑的"可复现"目标直接冲突：如果 gate_engine 用了时间戳、随机种子、绝对路径，`dvc repro` 就会每次都被判为"已变更"**。

### 3. git-lfs 的真实计费（GitHub 官方文档，2026 抓取）

这是被大量中文博客写错的地方（流传"1GB 免费"），官方文档的**准确数字**是：

| 计划 | 带宽（Bandwidth） | 存储（Storage） |
|---|---|---|
| GitHub Free | **10 GiB** | **10 GiB** |
| GitHub Pro | 10 GiB | 10 GiB |
| GitHub Free for organizations | 10 GiB | 10 GiB |
| GitHub Team | **250 GiB** | **250 GiB** |
| GitHub Enterprise Cloud | 250 GiB | 250 GiB |

- 计费规则：**push 一个 500 MB 文件 = 消耗 500 MB 存储、0 带宽；再 push 一个 1 字节改动 = 再消耗 500 MB 存储**（因为 LFS 存整份新版本）；**下载 500 MB = 消耗 500 MB 带宽**；**GitHub Actions 下载 LFS 文件同样计入仓库所有者的带宽**。
- 存储按月按小时累计：官方示例"1 GiB 用 15 天 + 2 GiB 用 15 天 = 1,080 GiB-hours ÷ 720 小时 = **1.5 GiB-month**"。
- 超额且未绑卡：**只能拿到指针文件、无法 push 新文件**；带宽超额则 **LFS 支持被禁用直到下月**。
- 预警：用量到 **90% 和 100%** 时发邮件。

**结论**：对阙疑，git-lfs 的 10 GiB 免费额度**绰绰有余**（三份 JSON + 账本总量应在 MB 级），但 git-lfs **不提供哈希清单、不提供管道复现**——它只是"把大文件搬出 git 对象库"。**如果要的只是"数据不膨胀仓库"，git-lfs 够用；如果要的是"能证明数据没变"，必须自己维护哈希清单或用 DVC。**

### 4. lakeFS：面向数据湖的"零拷贝分支"

lakeFS 的实现路径是**在 S3/GCS 等对象存储之上实现原子的 Git 式操作**（分支、提交、合并、回滚），核心卖点是**零拷贝分支**——`branch` 不复制数据，只写元数据，因此可以在 PB 级数据上秒级建分支做实验，实验失败直接 `revert`。与 DVC 的定位差异（多份对比文章一致）：

| 维度 | DVC | lakeFS |
|---|---|---|
| 面向对象 | ML 工程师 / 单机或小集群的**数据集与模型** | 数据平台 / 数据湖，**PB 级、多团队** |
| 版本粒度 | 文件级哈希 + 管道 DAG | **对象存储之上的分支/提交/合并** |
| 存储依赖 | S3/GCS/Azure/SSH 等 remote | **必须挂在对象存储上**，作为访问网关 |
| 对阙疑的适用性 | **高**（小数据、单人、本地） | **低**（典型的过度工程） |

### 5. 哈希清单的两种"标准格式"

**（a）Frictionless Data Package**：一个 `datapackage.json` 描述符（descriptor）作为容器，内含 `resources`（每个数据文件的 path、schema、**hash/checksum**、encoding 等），是"轻量、可校验"的数据定义语言。阙疑可以直接用一个 `data/manifest.json` 达到同样效果，无需引入依赖。

**（b）Croissant（MLCommons，2024-03 发布）**：构建在 schema.org 的 `Dataset` 词汇之上，为 ML 数据集提供**标准化元数据词汇表**，包含资源文件描述、字段类型、切分信息等，目标是"让数据集可被机器搜索与加载"（docs.mlcommons.org/croissant）。对阙疑的意义：如果 2027 年要投稿，**给 holdout/external_corpus 各写一份 Croissant 风格的元数据**，会比裸 JSON 更容易被审稿人接受为"规范的数据发布"。

**（c）Hugging Face Hub 的版本化**：每个数据集仓库就是一个 git 仓库，`revision` 可以是 **commit hash / tag / branch**，`load_dataset(..., revision="<sha>")` 可锁定到精确版本；配套的 **Dataset Card（README.md 的 YAML 头部）** 记录 license、task_categories、语言、来源等。阙疑如果要把三份 JSON 公开，**上传到 HF Hub 并记录 commit hash** 是最省事、最可验证的做法。

### 6. 数据血缘与文档：datasheet / model card 的标准

"版本化"解决的是"哪一份数据"，"血缘与文档"解决的是"这份数据是什么、怎么来的、有什么坑"。两类标准值得借用：

**（a）Datasheet for Datasets（Gebru et al., 2018/2021, CACM）**：把数据集文档拆成**动机（Motivation）、构成（Composition）、采集过程（Collection Process）、预处理（Preprocessing）、用途（Uses）、分发（Distribution）、维护（Maintenance）**七个板块。**对阙疑最直接的三项**：① "Composition" 要求写清样本量与标签分布——对应 holdout 的 30 seeds（真错 17 / 对照 9 / unknown 4）；② "Collection Process" 要求写清"标注者是谁、如何复核"——对应 662 A1 的人工复核与 665 扩样；③ "Uses" 要求写清"不该用来做什么"——对应论文已主动放弃的"把内部变异率 97.3% 当缺陷检测率"。

**（b）Model Card（Mitchell et al., 2019）**：为模型提供"预期用途、性能指标、局限、伦理考量"的结构化说明。**阙疑如果微调小模型验证器（见方向 44），必须配一份 model card**，至少写明：训练数据来源、底座模型版本、量化位宽（q4_k_m 还是 q3_k，见方向 44 §4 的伤害数据）、以及"不用于开放式判断"的边界。

**（c）Hugging Face Dataset Card 的 YAML 头**：如果阙疑把三份 JSON 上传 HF Hub，README.md 顶部的 YAML 块可声明 `license`、`task_categories`、`language`、`size_categories`、`source_datasets` 等字段，Hub 会自动渲染成可筛选的卡片。**成本极低（一个 README 的头部），但让"数据文档质量"这一项直接可被审稿人验证**——而按 Gundersen 等的结论，**这一项正是决定复现成功率的因素**。

### 7. 一份可直接照抄的 manifest 格式

综合 Frictionless Data Package 的 `descriptor` 思路与 DVC 的哈希字段，阙疑可以写一个零依赖的 `data/manifest.json`：

```json
{
  "schema": "queyi-data-manifest/v1",
  "generated_at": "2026-09-29T00:00:00Z",
  "source_commit": "<git rev-parse HEAD>",
  "entries": [
    {"path": "data/holdout/holdout.json", "sha256": "<64 hex>", "bytes": 0,
     "records": 30, "labels": {"planted_true": 17, "false": 9, "unknown": 4},
     "blind": false, "revealed": true, "reveal_irreversible": true},
    {"path": "data/external_corpus/external_corpus_665.json", "sha256": "<64 hex>",
     "bytes": 0, "records": 40, "layers": {"A": 0, "B": 0, "C": 0}},
    {"path": "data/defect_fixtures/defects.json", "sha256": "<64 hex>",
     "bytes": 0, "records": 15, "source_commits": 7},
    {"path": "data/_gate_rules.json", "sha256": "<64 hex>", "bytes": 0,
     "records": 67, "severity": {"block": 44, "warn": 16, "advice": 7}}
  ]
}
```

**为什么这个格式比"只算哈希"更好**：它把**记录数、标签分布、层级分布、严重度分布**一起冻结。任何一项对不上，校验就会失败——这相当于把"数据没变"的证明从"哈希相同"升级为"**结构与分布都没变**"。**这与阙疑的 append-only 哈希链是同一种设计哲学：不只记录结果，还记录结果的形状。**

### 8. 与 CI 集成（DVC + GitHub Actions）

DVC 官方与社区模板的典型 CI 形态：
- 关键前置：**`fetch-depth: 0`**（完整历史，否则 DVC 无法比对哈希）；
- 认证：DVC remote 的凭据走 **CI secret**（`DVC_REMOTE_*` 环境变量或 service account JSON），**绝不入库**（呼应方向 41）；
- 典型步骤：`pip install dvc` → `dvc pull`（拉数据）→ `dvc repro`（只重跑变更 stage）→ `dvc push`（回传新产物）→ 上传 `dvc.lock` diff 作为 artifact；
- 断言：CI 结束时检查 **`dvc.lock` 是否被改动但未提交**，若是则失败——这条"锁文件漂移检测"是防止"数据变了但没记录"的最有效手段，**与阙疑的"append-only 哈希链"哲学完全同构**。

## 对阙疑的 3 条具体行动

1. **今天就能做：生成 `data/manifest.json` 哈希清单并写进验收流程**。对 `holdout.json` / `external_corpus_665.json` / `defects.json` / `_gate_rules.json` 各算 **SHA-256**，写成一个清单文件（字段：`path`、`sha256`、`bytes`、`generated_at`、`source_commit`），并加一个工具 `tools/verify_manifest_<batch>.py --check`，**把"清单校验通过"作为验收报告的必填项**。这一步零依赖、10 分钟完成，且直接对上 Gundersen 那条"数据文档质量决定复现成功率"。
   - 命令参考：`python -c "import hashlib,pathlib;[print(hashlib.sha256(p.read_bytes()).hexdigest(), p) for p in pathlib.Path('data').rglob('*.json')]"`

2. **本月内：给三份数据集各写一份"数据卡片"（datasheet）**，放进 `data/` 或 `research/06_datasets.md` 的配套文件，必含 7 项：① 来源与采集时间（holdout 是自造 planted seed 还是真实缺陷？）；② 标签口径（`planted=true` 的判定规则）；③ 标注者与复核批次（662 A1 人工复核、665 扩样）；④ 盲化与 reveal 记录（`blind=false`、`revealed=true` 的时点）；⑤ 已知偏差（A/B/C 三层的检测器可用性差异，C 层检出率 0% 的原因）；⑥ 版本哈希（接第 1 条的 manifest）；⑦ 使用限制。**理由：论文 v0.3 已经诚实登记了"标签效度/检测器可用性/编译档"三大陷阱，把这三点从论文正文搬进数据卡片，是"可独立验收"最直接的兑现方式。**

3. **投稿前（2027 年）：在"上 DVC"和"不上 DVC"之间做显式取舍并写进论文 §Reproducibility**。建议**不上 DVC 全家桶**（对几百 KB 的 JSON 是过度工程），而是：① 用 git tag 冻结数据版本（如 `data-freeze-v1.0`）；② 提供**一条等价的复现命令**（`python tools/run_665_gate.py --holdout data/holdout/holdout.json --out results/`），并在 CI 里跑通；③ 若审稿人要求大文件托管，再用 **git-lfs（10 GiB 免费额度足够）** 或上传 HF Hub 并记录 commit hash。**同时明确在论文里写清"数据版本通过 SHA-256 manifest 锁定，manifest 随论文提交"，这句话本身就是审稿人想看的 reproducibility 证据。**
