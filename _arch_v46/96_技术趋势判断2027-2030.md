## 核心结论

1. **你赌的那个赛道，在 2026 年 3 月被官方"改名字"了——而且是朝着对你有利的方向改**。NeurIPS 2026 把 "Datasets & Benchmarks Track" 正式更名为 **Evaluations & Datasets (E&D) Track**（2026-03-23 官方博客），并明确写下一句改变游戏规则的定义：**"evaluation itself becomes an object of scientific study"（评估本身成为科学研究的对象）**。CFP 明确列出欢迎 **benchmark saturation（基准饱和）研究、复现/审计/压力测试、negative results（阴性结果）、批判性分析**。→ **阙疑的"三大测量陷阱"（标签效度 / 检测器可用性 / 编译档）恰好落在这个新 scope 的正中心，而不是边缘。**

2. **但同一份 CFP 也把门槛抬高了，而且抬在你最弱的地方**：E&D track 2026 年起**默认双盲（double-blind）**，并且明确规定——**当论文的主要贡献是"可复用的可执行工件"（benchmark suite / evaluation environment / data generator / software tool）时，代码必须在投稿时就可执行地开放**；数据集必须挂 **Croissant 元数据（含 RAI 字段）**；**不合规直接 desk reject**。→ **阙疑是"工具型贡献"，因此"代码可执行 + 文档完整 + 匿名化"不是加分项，是入场券。**（对应你仓库 227 项工作树漂移、README 口径滞后——这在匿名评审里是硬伤。）

3. **2027–2030 的三条主趋势里，有两条帮你、一条杀你**：① **LLM 编码能力在饱和（SWE-bench Verified 已被 OpenAI 于 2026 年 2 月宣布弃用，前沿模型解决率突破 80%）**——"模型会写代码"不再是新闻，"模型写的代码对不对、谁来独立验收"才是新闻 → **帮你**；② **形式化验证与 LLM 结合（vericoding）正在起飞但远未解决**（Lean 27% / Verus 44% / Dafny 82%，12,504 条规格的公开 benchmark）——**证明"验证"是 2027–2030 的开放问题，帮你**；③ **但"验证"这个赛道的入场券正在从"想法"变成"规模 + 独立可复现 + 审计链"**——你的 37 实卡、40 条 corpus、0 影响力的体量，在这条趋势下**是风险**，不是资产。

## 精确数字与案例

### 一、赛道本身：E&D track 在 2026 年发生了什么（一手来源）

**（1）改名与 scope 扩张（官方）**

NeurIPS 官方博客 2026-03-23《Introducing the Evaluations & Datasets Track at NeurIPS 2026》原文：

> "the Datasets & Benchmarks Track at NeurIPS 2026 has been officially renamed the **Evaluations & Datasets (ED) Track**... we introduce an important refinement; an expanded scope that explicitly positions **evaluation as a scientific object of study**."

官方给出的 evaluation 定义（**这是你可以直接引用进 Related Work 的句子**）：

> "Processes, practices, tools, and resources for making evaluative claims about AI/ML systems, including – but not limited to – datasets, benchmarks, user studies, simulators, **auditing**, **red-teaming methods**, interaction protocols, **metrics**, and experimental or qualitative study designs."

**（2）明确的 in-scope 清单（节选，逐条对应阙疑）**

| 官方 in-scope 条目 | 阙疑对应资产 | 是否已具备 |
|---|---|---|
| "Study benchmark saturation or overfitting and their impact on scientific conclusions" | 三大测量陷阱（标签效度/检测器可用性/编译档）量化 | ✅ 已有可复算数字 |
| "Compare evaluation designs and demonstrate how different assumptions lead to different results" | `-O1`→`-O0` 使 3/5 miss 被同一 sanitizer 抓住 | ✅ 有具体实验 |
| "Provide rigorous reproduction, auditing, and stress-testing of prior evaluations" | 独立对账器（不依赖内核） | ✅ 架构上具备 |
| "Present **negative results**, critical analyses" | **主动放弃变异率 97.3% 当检测率** | ✅ 已写进 v0.3 |
| "Contribute tools... that improve how evaluative claims are constructed" | gate_engine.py 3826 行 + 67 规则 | ✅ 但需可执行+文档 |
| "Develop documentation methodologies (Data Cards, Model Cards, evaluation cards)" | append-only 哈希链 + Merkle checkpoint | ⚠️ 未按 Croissant 规范 |

**（3）硬性门槛（2026 CFP 原文，直接决定你能否过 desk）**

- **关键日期**：Abstract **2026-05-04 (AoE)**；Full paper（含全部补充材料）**2026-05-06 (AoE)**；Notification **2026-09-24 (AoE)**；投稿系统 **2026-04-15** 开放。→ **按同一节奏外推，NeurIPS 2027 E&D 的 deadline 大概率在 2027 年 5 月上旬**（⚠️ 2027 CFP 未发布，属外推，列入盲区）。
- **双盲**：原文 "the default review mode for the E&D Track is now **double-blind**"。仅当数据集因科学/伦理原因无法匿名时可申请 single-blind。
- **代码政策**：原文 "code release is ***required*** at submission when the primary contribution is a **reusable executable artifact**, such as a benchmark suite, evaluation environment, data generator, or **software tool**, whose functionality must be inspected in order to evaluate the scientific claims."
- **数据托管**：必须托管在 **Dataverse / Kaggle / Hugging Face / OpenML**（或专用站点）；**>4GB 需附小样本**。
- **元数据**：必须用 **Croissant** 机器可读格式，**2026 年起额外要求 Responsible AI (RAI) 字段**；Croissant 文件需随投稿上传到 OpenReview。
- **desk reject 条款**：原文 "Non-compliance justifies the **desk rejection** of the paper."

### 二、趋势 A：LLM 编码能力——饱和、弃用、以及"验收"上位的窗口

**（1）SWE-bench Verified 的饱和与弃用（这是 2026 年最重要的一条趋势信号）**

- 2026 年 2 月，**OpenAI 宣布逐步停用 SWE-bench Verified**，理由是该基准已不能区分前沿模型（多家中文技术媒体与英文站点报道，2026-02 ~ 2026-04）。
- 中文分析（知乎，2026-02-24）原文：**"随着 Claude 4.5, GPT 5.2, Gemini 3.1 等最先进模型的发布，SWE-Bench Verified 的解决率已经突破了 80%"**。
- 模型对比（devtk.ai，2026-02-24）：**Claude Opus 4.5 在 SWE-bench 上 72%，GPT-5 为 69%**（⚠️ 与"突破 80%"口径冲突，可能是不同子集/不同 scaffold，列入盲区）。

→ **关键推论：当"能不能写对"被解决后，产业与学术的注意力必然转向"怎么证明它写对了"。** 这正是阙疑的问题定义。

**（2）替代基准 SWE-bench Pro 的出现（Scale AI，2025-10-30）**

Scale AI 发布 SWE-bench Pro，官方说明在**统一 scaffold** 下评测主流编码模型，"their performance on ... (is far lower)"。→ **含义：把 scaffold 统一后，真实能力远低于宣传值。** 这是"评估设计决定结论"的教科书级案例，**与阙疑的"编译档陷阱"是同一类发现**。

**（3）METR 的时间跨度（time horizon）数据（趋势量化）**

METR 官方 dashboard（2026-05-08 更新）：

- **GPT-4（2023-03）：预测 50% 时间跨度 = 17 小时**；
- **GPT-5：时间跨度约 2 小时 17 分钟**，在"人类专家需 90 分钟到 3 小时"的任务上 **100% 成功**；
- **官方警告："Measurements above 16 hrs are unreliable with our current task suite"（超过 16 小时的测量不可靠）**；
- 趋势拟合：原文 "an **exponential trend** is a much better fit to the data than both the linear and hyperbolic trends"，且 "we haven't seen any evidence of the exponential growth in time horizon slowing down"。
- ⚠️ **注意：dashboard 上同时存在 GPT-4 = 17hr 与 GPT-5 = 2h17m 两个数字，这看起来矛盾**。合理解释是**口径不同**（17hr 是"预测/外推值"，2h17m 是"实测 100% 成功率下的保守值"）——**但 METR 页面未逐字解释，故此项列为盲区，引用时必须标注口径**。

**（4）AI 写代码的占比（产业侧量化）**

- GitHub Copilot **2025 年 7 月突破 2,000 万累计用户**；
- 多家统计站口径：**Copilot 平均贡献其用户所写代码的约 46%**（⚠️ 第三方聚合，非 GitHub 官方，列入盲区）。

→ **含义：到 2027–2030，"人写一半、AI 写一半"是默认状态。"AI 写的这一半谁来验"会成为组织级刚需。**

### 三、趋势 B：形式化方法与"验证"——起飞但远未解决

**（1）vericoding benchmark（arXiv:2509.22908，2025-09-26，Max Tegmark 等）——这是你能引用的最硬的一条**

原文精确数字：

> "Our benchmark contains **12,504 formal specifications**, with **3,029 in Dafny**, **2,334 in Verus/Rust** and **7,141 in Lean**. Of these, **6,174 are new unseen problems**. We find vericoding success rates of **27% in Lean**, **44% in Verus/Rust** and **82% in Dafny** using off-the-shelf LLMs."

- **另一条极关键的趋势数字**：原文 "LLM progress has improved progress on pure Dafny verification **from 68% to 96% over the past year**"。→ **一年内从 68% 涨到 96%**，这是"验证能力正在被 LLM 快速吃掉"的直接证据。
- 附带发现：**"Adding natural-language descriptions does not significantly improve performance"**（加自然语言描述几乎没用）——**这条对"用 LLM 做知识验证"的人是冷水**。

**（2）seL4 的成本基线（形式化验证的"重力"）**

seL4 微内核形式化验证（Klein et al., 2009 起）：**约 10,000 行 C 代码，约 200,000 行 Isabelle 证明脚本，约 20–25 人年**，比例约 **200:1**（证明行数 : 代码行数）。

→ **这是"验证很贵"的量级锚点。阙疑的成本结构完全不同（Python 规则引擎，3826 行），所以不要和 seL4 比，要比"验证的边际成本"。**

**（3）LLM 做漏洞检测的真实成绩（arXiv:2601.19239，2026-01-27，v2 2026-09-25）——这是最"打脸"的一篇，必须读**

原文精确数字：

> "evaluating **five specialized methods, two general-purpose agents, and four traditional static analyzers** on **265 known C/C++ and Java vulnerabilities** and **24 active open-source projects/modules**. Using Codex-assisted labeling with stratified manual validation, we analyze **6,442 sampled warnings** and classify **5,896 false positives**... LLM-based methods incur substantial costs: **hundreds of thousands to hundreds of millions of tokens, API charges exceeding $1,000 per project/module, and runtimes ranging from hours to days.**"

→ **对阙疑的三重含义**：① **"漏报/误报"在项目规模上是普遍现象**（5,896/6,442 ≈ **91.5%** 的采样告警被判为误报）——你的 **0 误报**（holdout fp=0）在这个背景下是**卖点**，但也要警惕"样本太小导致 0 误报"；② **成本是真实门槛**（>$1,000/项目）——**你的规则引擎几乎零成本，这是结构性优势**；③ **失败原因被分类了**（截断的过程间上下文、程序点分类错误、推理失败、prompt 不合规）——**这份 taxonomy 可以直接用来定位阙疑的 rule 覆盖盲区**。

### 四、趋势 C：监管——把"可独立验收"从学术品味变成合规刚需

**（2）中国监管：从"原则立法"到"三轨制 + 硬截止"**

- 《生成式人工智能服务管理暂行办法》确立**安全评估 + 算法备案**义务（第十四、十七条）。
- **GB/T 45654—2025《网络安全技术 生成式人工智能服务安全基本要求》**（国家推荐性标准）：明确要求**训练阶段的"虚假有害信息测试题库建设 + 定期代码审计"**、输出阶段的**拒答机制 + 显式/隐式标识**、运行阶段的**实时监测 + 应急管理**。（来源：最高人民检察院官网，2026-07-09）
- **2026-03-17** 国家网信办发布配套执行细则，**"三轨制"（算法备案 / 大模型备案 / AI 应用登记）** 全面落地；**2026-06-30** 前未完成备案的大模型服务**停止访问**；**2026-09-30** 前完成 AI 应用登记。

→ **关键推论：中国监管把"安全评估"写成法定义务，但没有规定"用什么工具做"。这正是"独立可验收的验证器"的市场缝隙——它不要求你有牌照，只要求你能出具可复算的证据。**

### 五、趋势 D：C++ 与内存安全——你的"技术底座"在 2026 年同时被加固和被质疑

- **C++26 技术工作完成**（Herb Sutter 行程报告，2026-03-29，伦敦 Croydon 会议）：核心内容包括 **reflection（反射）、contracts（契约）、memory safety 强化**，被多篇报道称为"C++11 以来最重要的一次更新"。
- **GCC 16.1 发布（2026-04-30）**：支持 **C++26 reflection / contracts / safety hardening**，且 **C++20 成为默认标准**。
- **CISA/FBI 设定 2026-01-01 为内存安全路线图截止日**；**Microsoft 宣布 2030 年"eliminate C++"**（⚠️ 二手来源 byteiota 2026-03-04，**未从 Microsoft 官方核实**，列入盲区）。NSA/CISA **2025-06-23** 联合发布《Memory Safe Languages: Reducing Vulnerabilities in Modern Software Development》。

→ **双重含义**：① **C++ 在自我加固（contracts / safety hardening）→ 阙疑的"规则库"有官方标准的对标物，可以做"规则 vs 标准"的映射表**；② **"淘汰 C++"的叙事会持续 → 但恰恰因为 C++ 存量巨大（Linux、浏览器、嵌入式），"验证 C++ 是否正确"的需求会长期存在**。**你的嵌入式 + C++ 组合，在这条趋势里是"遗产系统的验证者"，不是"被淘汰的人"。**
