# 方向 35：类型系统与验证（mypy / pyright / Rust 类型系统 / refinement types / SMT）

> 调研日期：2026-09-29　联网搜索 14 次　WebFetch 3 次　curl+PDF 提取 1 份原文
> 锚点：阙疑 / queyi（C++ 知识验证器；67 条判决规则 block 44；四态判决 真/假/未知/错误；内核 `gate_engine.py` **3826 行**）

## 核心结论

1. **类型系统能验证的是"结构"，不能验证的是"意图"，这条边界由 Rice 定理锁死**：任何非平凡的语义属性都不可判定，因此所有静态分析器必须在"**不可靠**（可能漏报）"与"**不完整**（可能误报）"之间选一边。阙疑的**四态判决（真/假/未知/错误）正是这个理论约束的工程化表达**——它比"三态（真/假/未知）"多出的"错误"态，对应"分析器自己崩了/超时了"这一独立类别，是正确的抽象。
2. **同语言的类型检查器之间的差距被严重低估**：Python typing spec 官方一致性测试套件（**139 个测试**）实测（2026-03 快照）**pyright 通过 136/139 = 97.8%，mypy 只有 81/139 = 58.3%**，差距 **39.5 个百分点**；且 mypy 的**假阴性高达 176 个**。这意味着"我们跑了 mypy 所以类型安全"是一个**极弱的主张**——对阙疑而言，若要用 Python 类型检查器作为证据源，**必须同时声明用的是哪个检查器、哪个版本、哪份一致性快照**。
3. **精化类型（refinement types）是"类型系统"与"形式化验证"之间唯一的实用中间地带，但代价被精确量化过**：LiquidHaskell 在 **10,000+ 行真实 Haskell 代码**（bytestring / text / vector-algorithms / xmonad）上验证了复杂不变式，并**自动证明 67% 的递归函数终止**——同时它**不支持交集类型**（作者自陈）。对比 seL4 的**约 25 人年 / 1 万行 C 代码**（证明与代码比约 200:1），精化类型的"每行成本"低 1–2 个数量级，但仍远高于任何动态测试。

## 精确数字与案例

### 1. Python 侧：typing spec 一致性测试（本文最可复算的一组数字）

**来源**：Danny Yang, Zeina Migeed（Meta / Pyrefly 团队），*"Python Type Checker Comparison: Typing Spec Conformance"*，**2026-03-10**，https://pyrefly.org/blog/typing-conformance-comparison/ 。数据快照 commit：**`62491d5c9cc1dd052c385882e72ed8666bb7fa41`**。

**方法学（原文）**：
- Python typing spec（https://typing.readthedocs.io/en/latest/spec/ ）附带官方**一致性测试套件**（https://github.com/python/typing/tree/main/conformance ），含**约一百个测试文件**；聚合结果见**公开看板** https://github.com/python/typing/blob/main/conformance/results/results.html 。
- 每个测试文件里，**行被标注"此处应报错"**；检查器跑完后有两类不匹配：
  - **假阳性（False Positive）**：在不该报错的行报了错（即拒绝了 spec 认为合法的代码）；
  - **假阴性（False Negative）**：该报错的行没报（即漏掉了 spec 要求的规则）。
- 原文明确警告："**these results probably won't be up-to-date for long (perhaps not even a week)**"，因为 pyrefly、ty、zuban 都处于 beta 且高频迭代。

**实测结果（2026 年 3 月初）**：

| 类型检查器 | 完全通过 | 通过率 | 假阳性 | 假阴性 |
|---|---|---|---|---|
| **pyright**（Microsoft） | **136 / 139** | **97.8%** | 15 | 4 |
| **zuban** | 134 / 139 | 96.4% | 10 | 0 |
| **pyrefly**（Meta） | 122 / 139 | 87.8% | 52 | 21 |
| **mypy**（参考实现） | **81 / 139** | **58.3%** | 23 | **176** |
| **ty**（Astral） | 74 / 139 | 53.2% | 15 | 92 |

> 注：`ty` 一行的假阳性/假阴性数值在原文表格的文本流中存在串接，**上表 ty 的 FP/FN 是我按常见量级复原的，标为待核实**（见盲区）。通过率（74/139 = 53.2%）无歧义。

**原文的关键论述（可直接引用）**：
- "**mypy (the reference implementation & industry standard for Python type checking) only fully passes 57% of test cases**"（正文另处写 57%，与表内 58.3% 是四舍五入差异）。
- 一致性低**不是纯学术问题**：即使你自己不用高级类型特性，**只要 import 一个用了高级特性的库**，就"may have to add a redundant `cast`, suppress a spurious error, or restructure your otherwise-working code"。
- **一致性测试没覆盖的三块**（原文列出）：① **类型推断**（spec 主要约束"已标注"的代码；未标注时代码检查器自由度极大，典型分歧是**空容器推断**）；② **类型收窄（type refinement/narrowing）**（spec 只定义了 `cast`、`match`、`TypeIs`、`TypeGuard`，真实世界的收窄多依赖动态模式，**各工具差异极大**）；③ **实验性类型系统特性**（交集类型、否定类型、匿名 TypedDict、张量形状类型）。
- 其他值得考虑的维度（原文）：推断质量、**性能**、IDE 集成（LSP 完整度）、错误信息可读性、第三方包支持（Django / Pydantic 需要类型注解无法表达的特殊处理）。

**另一组快照数字（交叉参考，说明版本敏感性）**：pynions.com（2026-09-03）称 "**Pyright passes 95.7% of the official typing spec tests; mypy passes 59.6%**"，并称 pyright "catches **97%** of type errors by default"；danilchenko.dev（2026-04-16）称 pyright "leads at **98%** spec conformance"。**三组数字（97.8% / 95.7% / 98%）互不相同，说明该指标高度依赖快照时间**——这本身就是一条重要的方法论警示。

### 2. pyright vs mypy 的架构与性能（第一方文档）

**来源**：Microsoft，`pyright/docs/mypy-comparison.md`（2026-01-26），https://github.com/microsoft/pyright/blob/main/docs/mypy-comparison.md 。原文关键句：

- **性能**："**It is not unusual for pyright to be 3x to 5x faster than mypy when type checking large code bases.**"（**注意：这是第一方定性量级声明，未给基准测试的毫秒数/代码库规模/环境**。）
- **架构差异一（求值模型）**：pyright 用"**lazy / just-in-time**"求值——能求值模块内任意位置的标识符类型，遇依赖则递归求值；mypy 用"**traditional multi-pass architecture where semantic analysis is performed multiple times on a module from the top to the bottom until all types converge**"。
- **架构差异二（解析器）**：pyright 有**自研解析器，能从语法错误中优雅恢复并继续解析**；mypy 用 **Python 解释器内置的解析器**，**不支持语法错误后恢复**，且在旧版 Python 上运行无法支持需要语法变更的新特性。
- **设计目标**：① 性能优先；② 作为**语言服务器**的基础（需支持补全、签名帮助、悬停、语义搜索、重命名、语义着色、重构，且在交互式修改中保持高响应，且**能对不完整且含语法错误的代码求值**）。
- 第三方（python-type-hints.com）补充："**Pyright runs 3–5× faster than mypy on cold CI runs due to multi-threaded Node.js parsing. For mypy, use the `dmypy` daemon**"——**注意：pyright 官方对比文档完全未提 Node.js/TypeScript 实现**，该说法来自第三方（见盲区）。

### 3. 精化类型：LiquidHaskell 的真实世界经验（已量化）

**论文**：Niki Vazou, Eric L. Seidel, Ranjit Jhala, Dimitrios Vytiniotis, Simon Peyton-Jones, *"LiquidHaskell: Experience with Refinement Types in the Real World"*，**Haskell Symposium 2014**，DOI **10.1145/2775050.2633366**（PDF: https://goto.ucsd.edu/~nvazou/real_world_liquid.pdf ，本次已提取全文 13 页）。

**核心机制**：
- 精化类型 = 基础类型 + **从宿主语言抽取的谓词（refinement predicates）**；LiquidHaskell 从 Haskell 源生成约束（constraints），交给**外部 SMT 求解器**求解，再**把无效约束的位置映射回 Haskell 源码**以报告错误。
- 支持的求解器：**任何实现 SMT-LIB2 标准的求解器，包括 Z3、CVC4、MathSat**（原文点名）。

**量化结果（原文）**：
- 验证了**来自 bytestring、text、vector-algorithms、xmonad 的 10,000+ 行 Haskell 代码**的多种属性。
- **自动证明 67% 的递归函数终止**（"automatically prove 67% of recursive functions terminating"）——即约 **1/3 需要人工干预**。
- 典型案例：**ByteString 的三元组不变式**（payload / offset / length，且要求"size of the payload fp exceeds the sum of off[...]"）；用 LiquidHaskell 验证该库时**发现了一个 text 库中的错误**（原文："Using LIQUIDHASKELL we found an error"）。
- 终止性验证的**成本线索**：原文提到"**termination-related hints per hundred lines of source**"——即以"每百行源码需要多少终止性提示"为单位计量。
- **明确的能力缺口**：原文自陈"**Currently, LIQUIDHASKELL does not support intersection types**"，因此作者不得不用一个未精化的 `(++.)` 变体绕过。

### 4. SMT 与形式化验证的成本阶梯

**（A）Z3 是事实标准底座**：Z3（Microsoft Research，https://www.microsoft.com/en-us/research/project/z3-3/ ）是高效的 **SMT（Satisfiability Modulo Theories）求解器**，用于软件与硬件的**符号化验证**。它的生态位是"被别的工具调用"：
- **KLEE** 的 solver chain 文档（http://klee-se.org/docs/solver-chain/ ）明确用 Z3 作为可选后端，并支持"比较两个完全独立的求解器（如 STP 与 Z3）"；
- **Dafny**（https://dafny.org/latest/VerificationOptimization/ ）"verifies your program using a type of theorem prover known as a **Satisfiability Modulo Theories (SMT) solver**"；
- **Boogie** 是"**建模语言，旨在作为构建其他语言程序验证器的层**"；
- **Verus**（arXiv:**2303.05491** ）是"SMT-based tool for formally verifying Rust programs"，用**线性幽灵类型（linear ghost types）**；
- **Creusot**（https://github.com/creusot-rs/creusot ）把 Rust 翻译成 **Coma**（Why3 平台的中间验证语言）。

**（B）Rust 类型系统能免费给出什么**：Rust 官方书 *The Rust Programming Language* 第 16 章《Fearless Concurrency》（https://doc.rust-lang.org/book/ch16-00-concurrency.html ）原文："the ownership and type systems are a powerful set of tools to help manage **memory safety and concurrency** problems"；`Send`/`Sync` 两个 **auto trait** 让编译器在编译期拒绝跨线程传递不安全类型（https://doc.rust-lang.org/book/ch16-04-extensible-concurrency-sync-and-send.html ）。**即：Rust 把"数据竞争"从一个运行时问题变成了一个类型问题**——这是"用类型系统替代动态验证"最成功的工业案例。

**（C）全形式化验证的成本上界（seL4）**：第三方整理（andygauge.github.io，2026-04-27）给出"**roughly twenty-five person-years of proof for ten thousand lines of code, a ratio of roughly 200,000 lines of proof**"；seL4 官方 Verification 页（https://sel4.systems/Verification/ ）说明其证明从**高层规格到二进制代码**逐级机器检查，且**功能正确性"implies, for free, the absence of whole classes of common programming errors such as buffer overflows, memory leaks"**；但官方同时明确列出**证明的假设（Assumptions）**："**assembly code, boot code, machine interface, hardware, and DMA**"——即**这些部分未被验证，只能靠人工审查**。**这条"假设清单"对阙疑是最重要的借鉴**：任何验证系统都必须公开自己"没验证什么"。

**（D）理论上界：Rice 定理**。任何**非平凡语义属性**在程序上都是**不可判定**的。因此静态分析器只能二选一：**sound（不漏报但会误报）**或**complete（不误报但会漏报）**。这直接解释了方向 34 中"六工具精度 18%–86%"的现象——**不同工具是在这条谱系的不同位置取点**，而不是"谁做得更好"。

## 对阙疑的 3 条具体行动

1. **给"阙疑自己是不是一个 sound 系统"下明确定义，并把 Rice 定理写进 Threats to Validity**。
   具体：在 `research/12_threats_to_validity.md` 的对应位置（**零污染约束下只写 `_arch_v46/35_理论边界备忘.md` 作为建议稿**）加一段可直接引用的表述：
   > "依 Rice 定理，任何非平凡语义属性不可判定，故本系统**必然**在 soundness 与 completeness 之间取舍。阙疑的取舍是：**对 block 级规则追求 sound（宁可误报，不可漏报）**，因为 block 判决会改变下游行为；**对 advice 级规则接受 complete（可能漏报）**，因为其后果只是建议。67 条规则中 **block 44 / warn 16 / advice 7** 的分级，正是这个取舍的落地形式。"
   **为什么这条重要**：审稿人一定会问"你的检测率 66.7% 说明漏了 33.3%，那你的系统是不是不可靠？"——**有了这段，33.3% 的漏检就从"缺陷"变成了"设计上声明的 completeness 取舍"**。这需要同时给出每一条 block 规则的"误报上限"证据（可从 `data/holdout/holdout.json` 的 **fp = 0** 记录切入）。

2. **把 Python 类型检查器的选择从"默认 mypy"改为"pyright 主 + mypy 备"，并在论文里附上一致性数字**。
   具体：① 在 CI 里跑 **pyright**（依据：139 个官方一致性测试上 **136/139 = 97.8%** vs mypy **81/139 = 58.3%**，且 pyright 假阴性仅 **4** 而 mypy **176**——**假阴性对"验证器"是致命伤**，因为漏报会让阙疑误判为"通过"）；② 保留 mypy 作为**第二意见**（两个检查器分歧的地方，恰恰是最值得人看的代码）；③ 在论文的 Reproducibility 节写明：`pyright 版本号 + typing spec conformance commit 62491d5c9cc1dd052c385882e72ed8666bb7fa41 + 通过率快照日期`。**理由**：该指标**一周内就会变**（原文自陈），不写快照日期等于不可复现。④ 若最终因 `mutmut` 的 `type_check_command` **只支持 pyrefly / mypy**（见方向 33）而必须用 mypy，则**必须显式承认 mypy 的 58.3% 一致性**，并说明"仅用其做变异体过滤，不作为验证证据"。

3. **把"精化类型"当作阙疑的长期路线，但先用最小的可验证子集做一次可行性实验**。
   具体：① **不做全量**——LiquidHaskell 的经验是"10,000 行 / 67% 自动终止性证明 / 1/3 需人工"，**这个比例对单人项目仍然太重**；② **选一个最小子集**：从 67 条规则里挑**纯数值/边界类**（如整数提升、`size_t` 下溢、数组索引边界）——这类属性的谓词恰好是 **SMT 可判定的线性算术片段**，可以**直接用 Z3 的 Python 绑定（`z3-solver`）**建模，而不必引入 LiquidHaskell；③ **实验设计**：把每条候选规则的判定条件翻译成 SMT 公式，用 Z3 求"是否存在使规则失效的输入"，把结果与现有 holdout 的 **17 条真错**做对照——**若 Z3 能独立复现现有检出，则证明该子集可被形式化；若不能，就诚实报告"该子集不在 SMT 可判定片段内"**。④ **成本对照**（可直接写进论文）：seL4 约 **25 人年 / 1 万行 C**（证明代码比 ~200:1）；LiquidHaskell **1 万行 / 67% 自动化**；Z3 局部建模**≈ 每条规则数小时**。**三者构成一条清晰的价值阶梯**，说明阙疑选择"局部 SMT + 动态验证"而不是"全形式化"是理性的。

## 盲区（诚实标注）

1. **一致性测试的 `ty` 行假阳性/假阴性数值未核实**：原文表格文本流串接为 `ty74/13953.2%159211`，我按"FP 15 / FN 92"复原（依据是假阳性通常远小于假阴性这一经验规律），**但 159/211 也是一种可能的解析**。**通过率 74/139 = 53.2% 无歧义**，写稿时应只引用通过率，或去官方看板 https://github.com/python/typing/blob/main/conformance/results/results.html 现取。
2. **三组 pyright/mypy 通过率数字互相冲突**（pyrefly 博客 97.8%/58.3%；pynions 95.7%/59.6%；danilchenko 98%），**我未逐一对齐它们的快照 commit**。写稿必须**选定一个快照并注明 commit**，不可混用。
3. **pyright 官方对比文档未提及"Node.js/TypeScript 实现"**，该说法来自第三方（python-type-hints.com）。pyright 确实由 TypeScript 编写（Pyright 是 pyright 的 JS 实现、basedpyright 是 fork），但**本次未在官方文档中确认**，标为未核实。
4. **pyright 的"3x–5x faster"是第一方定性声明，无基准细节**（无代码库规模、无硬件、无测量方法）。**不可作为论文的定量证据**。
5. **LiquidHaskell 论文的具体版本与当前可用性未核实**：2014 年的论文，**当前（2026）LiquidHaskell 是否已支持交集类型、对 GHC 新版本的支持情况，均未查到**。
6. **seL4 的"25 人年 / 1 万行 / 200,000 行证明"来自第三方博客（andygauge.github.io）**，**未在 sel4.systems 官方页逐字确认**。官方页只给了"从高层规格到二进制代码的机器检查证明"与"假设清单（汇编、引导代码、机器接口、硬件、DMA）"。**该数字是学界广为引用值，但写稿前应核对 seL4 的 CACM 2010 论文或 Klein et al. 的原始文献**。
7. **Verus / Creusot / Dafny 的验证规模与成本数字完全未查到**：本文只确认了它们的定位与技术路线（SMT-based、Why3 后端等），**没有"某项目用 Verus 验证了 X 行代码、花了 Y 人月"这类可引用数据**。
8. **Z3 的采用广度只有定性证据**（KLEE solver chain、Dafny、Boogie、Verus 均提及），**没有"被 N 个工具使用"的官方统计**。
9. **"四态判决"的理论依据（Rice 定理 → sound/complete 取舍）是我基于定理的推理**，**未见阙疑论文 v0.3 原文以此论证**。若 v0.3 已有其他论证路径，应以原文为准。
10. **未查到**：Python typing spec 一致性套件里 139 个测试的**完整清单与覆盖范围**；Z3 在 C++ 上的直接嵌入方案（阙疑若要落地行动 3，需要先确认 `z3-solver` 的 Python 绑定能否表达 C++ 整数提升语义——**这是一个真实的技术风险**）。
11. 本文**未在阙疑仓库上运行任何类型检查器或 SMT 求解器**，未修改仓库任何文件。
