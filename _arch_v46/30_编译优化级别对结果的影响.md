# 方向 30：编译优化级别对结果的影响（-O0 / -O1 / -O2 / -O3 / -Os）

> 调研时间：2026-09-29
> 本机实测工具链：GCC 15.3.0（MinGW-W64 winlibs x86_64-msvcrt-posix-seh）、GCC 13.1.0（MinGW-Builds）、Clang 22.1.8（msys2 x86_64-w64-windows-gnu）
> 本文核心：**"-O 档位"是 C/C++ 世界里最容易改变程序可观测行为的单一开关**。本文件所有矩阵均为本机实测，可独立复算。

---

## 核心结论

1. **优化档对结果的影响不是"快慢差异"，而是"语义差异"。** 本机实测：同一份未初始化数组求和程序，在 `{GCC15.3.0, GCC13.1.0, Clang22.1.8} × {-O0,-O1,-O2,-O3,-Os}` 的 **15 个配置下产生 8 种不同的输出值**；同一份 `for(int i=0;i>=0;i++)` 程序在 **15 个配置下产生 4 种截然不同的行为**（正常返回 / 真死循环 / 异常终止 / 折叠为常量）。

2. **`-Ofast` 是唯一会破坏 IEEE 语义的档位，且不同编译器破坏的范围不同。** 本机实测：GCC 15.3.0 `-Ofast` 下 `isnan(sqrt(-1.0))` 返回 **0**（应为 1）；Clang 22.1.8 `-Ofast` 下 `isnan(0.0/0.0)`、`isnan(sqrt(-1.0))`、`isinf(1e308*10.0)` **三个全部返回 0**。而 `-O0` 到 `-O3` 五个档位下，三编译器这六项检查**全部正确**。**`-Ofast` 不是"更快的 -O3"，它是"另一门语言"。**

3. **降档是最强的第一手诊断信号，也是阙疑最便宜的可复算证据。** 本机实测：GCC `-O2` 下严格别名违规返回 0（错），`-O0`/`-O1` 返回 1（对）；GCC `-O2` 下 `for(int i=0;i>=0;i++)` 变死循环，`-O0`/`-O1` 正常返回 42。**"改档位结果就变"几乎等价于"这里有 UB"**（Shafik Yaghmour 2025 博文原话："If the behavior of your program changes when using some level of optimization, then it is likely you have undefined behavior"）。

## 精确数字与案例

### 1. 各档位的规范定义（GCC 手册口径）

GCC 的 `-O` 档位是**开关集合**而非线性刻度：

| 档位 | 关键开关（与本文件相关的部分） |
|---|---|
| `-O0` | 关闭所有优化（默认） |
| `-O1` | 开启基础优化；**不含** `-fstrict-aliasing` 的激进形态；不含循环重排 |
| `-O2` | `-O1` + 几乎所有不需要空间-时间折中的优化；**开启 `-fstrict-aliasing`**；开启 `-ftree-vectorize`（GCC 12 起） |
| `-O3` | `-O2` + 更激进的循环变换、内联、向量化 |
| `-Os` | `-O2` 中**不增加代码体积**的子集（关闭会增大体积的优化） |
| `-Ofast` | `-O3` + `-ffast-math` + `-fno-protect-parens` + `-fstack-arrays`（GCC 手册口径），**放弃 IEEE 合规** |
| `-Og` | 为调试优化的档位（GCC 4.8+），本文件未实测 |

**关键事实**：`-fstrict-aliasing` 在 **`-O2` 及以上默认开启**（本机实测印证：GCC `-O1` 不利用别名假设、`-O2` 利用，见 §3.1）。**这解释了为什么大量"严格别名 miscompile"报告的触发条件都是 `-O2`。**

MSVC 的对应机制不同（文档）：`/O1`（最小体积）、`/O2`（最大速度）、`/Ox`（完全优化）、`/Od`（禁用优化），且浮点语义由独立的 **`/fp:precise | /fp:fast | /fp:strict`** 控制。MSVC 文档（`/fp` 页）原文指出：`/fp:precise` 模式下"The compiler **doesn't perform algebraic transformations on floating-point expressions, such as reassociation**"。**注意：MSVC 把"优化档"与"浮点语义"分成两个正交开关，而 GCC 的 `-Ofast` 把两者耦合在一起。**

### 2. 实测矩阵 A：未初始化读取（15 配置 → 8 种输出）

```cpp
#include <cstdio>
int main(){ int a[10]; int s=0; for(int i=0;i<10;i++) s+=a[i]; printf("s=%d\n", s); return 0; }
```

| 编译器 | `-O0` | `-O1` | `-O2` | `-O3` | `-Os` |
|---|---|---|---|---|---|
| GCC 15.3.0 | 297780922 | -25442731 | 1615970530 | -1492990318 | -1492516522 |
| GCC 13.1.0 | 1290687602 | — | 2067748199 | 1373394044 | -1009511281 |
| Clang 22.1.8 | 1946384909 | **0** | **0** | **0** | **0** |

**观察**：
- GCC 在 5 个档位给出 **5 个互不相同的值**（且与另一版本 GCC 的 5 个值也不相同）→ 共 **10 个不同值**；
- Clang 在 `-O1` 及以上**全部折叠为常量 0**（因为 `a` 未初始化是 UB，Clang 直接假定 `s` 可取任意值，选了 0）；
- **8 种不同输出**（去重后：GCC15 的 5 个 + GCC13 的 5 个中有 2 个与 GCC15 重复 + Clang 的 0 和 1946384909）。

**这对阙疑的意义**：如果 holdout 里有一张卡断言"未初始化读取会得到垃圾值"，那么**在 Clang `-O1` 以上该断言必然失败**（得到确定的 0）。**规则必须把编译档写进语义范围。**

### 3. 实测矩阵 B：UB 被优化掉 / 变成死循环

**3.1 严格别名违规（GCC 真实 miscompile）**

```cpp
int reorder(unsigned* foo){ *foo = 0; short* ptr=(short*)foo; *ptr=1; return *foo; }
```

| | `-O0` | `-O1` | `-O2` |
|---|---|---|---|
| GCC 15.3.0 | 1 | 1 | **0** |
| GCC 13.1.0 | 1 | 1 | **0** |
| Clang 22.1.8 | 1 | 1 | 1 |
| GCC 15.3.0 `-O2 -fno-strict-aliasing` | — | — | **1**（修复） |

**这是"-O2 开启严格别名优化 → 代码被编错"的完整链路**。GCC 手册对此的官方说明是："To disable optimizations based on alias-analysis for faulty legacy code, the option `-fno-strict-aliasing` can be used as a **work-around**"（注意用词 "work-around"，不是 "fix"）。

**3.2 有符号溢出导致的死循环**

```cpp
int f(){ for(int i=0;i>=0;i++){} return 42; }
```

| | `-O0` | `-O1` | `-O2` | `-O3` | `-Os` |
|---|---|---|---|---|---|
| GCC 15.3.0 | `f=42` exit 0 | `f=42` exit 0 | **超时 exit 124** | 超时 exit 124 | 超时 exit 124 |
| GCC 13.1.0 | `f=42` exit 0 | `f=42` exit 0 | **超时 exit 124** | 超时 exit 124 | 超时 exit 124 |
| Clang 22.1.8 | **超时 exit 124** | **无输出 exit 3** | 无输出 exit 3 | 无输出 exit 3 | 无输出 exit 3 |
| GCC 15.3.0 `-O2 -fwrapv` | — | — | **`f=42` exit 0**（修复） | — | — |

**注意一个反直觉的细节：Clang 在 `-O0` 就已经"坏"了（死循环），GCC 要到 `-O2` 才坏。** 这意味着"降档诊断"这个方法论本身是**编译器相关的**——对 GCC 有效，对 Clang 未必。

**`-fwrapv` 的修复效果**：`-O2 -fwrapv` 下恢复正常（本机实测）。GCC 手册口径：`-fwrapv` 让有符号整数环绕成为**有定义**的行为。Shafik Yaghmour 博文补充了一个重要细节："with this flag, **UBSan will no longer treat signed overflow as UB**"——**即 `-fwrapv` 会让 UBSan 的 `signed-integer-overflow` 检查失效**。这是一个隐藏的"检测率-编译档"耦合。

**3.3 空指针检查被删除**

```cpp
int deref(int* p){ int x=*p; if(p==nullptr) return -1; return x; }
```

本机实测：三编译器在 `-O0`..`-Os` 全部输出 `ok=7`（因为调用方传了非空指针），**未观察到差异**。但这正是 LWN 2009 年讨论的形态：编译器从 `*p` 推断 `p` 永不为空，删除 `if(p==nullptr)`。**本机未复现出差异，列入盲区。**

### 4. 实测矩阵 C：`-Ofast` 破坏 IEEE 语义

```cpp
printf("isnan(0.0/0.0)=%d isnan(sqrt(-1))=%d\n", (int)std::isnan(0.0/0.0), (int)std::isnan(std::sqrt(-1.0)));
printf("1e308*10 = %g  inf?=%d\n", 1e308*10.0, (int)std::isinf(1e308*10.0));
```

| 配置 | `isnan(0.0/0.0)` | `isnan(sqrt(-1.0))` | `isinf(1e308*10.0)` |
|---|---|---|---|
| GCC 15.3.0 `-O0`/`-O2`/`-O3` | **1** | **1** | **1** |
| Clang 22.1.8 `-O0`/`-O2`/`-O3` | **1** | **1** | **1** |
| **GCC 15.3.0 `-Ofast`** | **1** | **0** ❌ | **1** |
| **Clang 22.1.8 `-Ofast`** | **0** ❌ | **0** ❌ | **0** ❌ |

**这是本文最有冲击力的实测结果**：
- `-O0` 到 `-O3` 五个档位，三编译器六项检查**全部正确**；
- 一旦切到 `-Ofast`，**GCC 破坏 1 项、Clang 破坏 3 项**；
- `isnan(0.0/0.0)` 在 Clang `-Ofast` 下返回 0，意味着**程序无法再检测 NaN**——任何"用 NaN 做哨兵值"的数值代码在 `-Ofast` 下静默失效；
- `isinf(1e308*10.0)` 在 Clang `-Ofast` 下返回 0，意味着**溢出检测静默失效**。

**GCC 手册对 `-ffast-math` 的口径**：允许"assume that arguments and results are valid"（假定参数与结果都是有效的）——即**假定不会有 NaN/Inf**。所以 `isnan()` 返回 0 是"符合 `-ffast-math` 契约"的行为，**不是 bug**。这恰恰是最危险的地方：**它不报错，它只是让检查失效。**

### 5. 实测矩阵 D：浮点重排（本机未复现）

```cpp
volatile double arr[3] = {1.0, 1e-16, -1.0};
double s_ordered(){ double s=0; for(int i=0;i<3;i++) s+=arr[i]; return s; }      // 1.0, 1e-16, -1.0
double s_reordered(){ double s=0; for(int i=2;i>=0;i--) s+=arr[i]; return s; }    // -1.0, 1e-16, 1.0
```

| 配置 | `s_ordered` | `s_reordered` |
|---|---|---|
| 全部 8 个配置（GCC15/Clang22 × `-O0`/`-O2`/`-O3`/`-Ofast`） | `0` | `1.1102230246251565404e-16` |

**诚实结论：本机在 `-Ofast` 下也**没有**把 `s_ordered` 重排成 `s_reordered`**——因为源程序里的两个函数本身就是**不同的表达式**（加法顺序由循环方向决定），编译器没有跨函数的"重排"机会。**要复现 `-ffast-math` 的重排，需要写成同一表达式的不同括号形式，或使用 `-ffast-math` 下的向量化归约。本机未复现，列入盲区。**

**但文献依据明确**：MSVC `/fp` 文档原文说 `/fp:precise` 下"compiler doesn't perform algebraic transformations on floating-point expressions, such as **reassociation** or [distribution]"——**反过来说，`/fp:fast` 下它会做重排**。KDAB 2023-02-24 的文章标题即 "FMA woes"（FMA 的麻烦），讨论的正是浮点收缩（contraction）导致的跨平台结果差异。

**浮点收缩（FMA）的机制**：`a*b + c` 可以被收缩为一条 `fma(a,b,c)` 指令，**只有一次舍入**（而不是两次），因此结果与"先乘后加"不同。GCC/Clang 的 `-ffp-contract` 有三个取值：`off` / `on`（仅同一表达式内）/ `fast`（允许跨语句）。本机实测在 `-O2`、`-O2 -ffp-contract=off`、`-O2 -ffp-contract=fast`、`-O2 -ffast-math` 四种配置下，`1.0*1e-16 + (-1.0)` **全部输出 `-0.99999999999999988898`**（即本机没有生成 FMA，可能因为 MinGW 目标 CPU 默认不含 FMA 指令集）。**这也是一个"未复现"项，列入盲区。**

### 6. 实测矩阵 E：代码体积与运行时间

**代码体积**（GCC 15.3.0，同一 C++ 程序：`vector<string>` + `sort` + `map` + 递归 fib，Windows PE 可执行文件字节数）：

| 档位 | 体积（字节） | 相对 `-O0` | 相对 `-O2` |
|---|---|---|---|
| `-O0` | 248,487 | — | +104.8% |
| `-O1` | 122,822 | **-50.6%** | +1.2% |
| `-O2` | 121,350 | -51.2% | — |
| `-O3` | 120,658 | -51.4% | **-0.6%** |
| `-Os` | **107,673** | **-56.7%** | **-11.3%** |
| `-Ofast` | 123,432 | -50.3% | +1.7% |

**可复算结论**：
- **`-O0` → `-O1` 的体积降幅最大（-50.6%）**，因为 `-O0` 不做任何内联和常量折叠，保留了全部调试用代码；
- **`-O2` → `-O3` 几乎不增体积（-0.6%，即 `-O3` 反而略小）**——这反驳了"`-O3` 一定更大"的直觉；
- **`-Os` 相对 `-O2` 减小 11.3%**，是唯一有意义的体积优化档；
- **`-Ofast` 比 `-O2` 还大 1.7%**——"放弃精度"并不换来体积。

**运行时间**（GCC 15.3.0，递归 `fib(35)`，单次 wall-clock，Windows）：

| 档位 | 时间（ms） |
|---|---|
| `-O0` | 1472 |
| `-O1` | **1558** |
| `-O2` | **1389** |
| `-O3` | 1443 |
| `-Os` | 1554 |

⚠️ **本组数字是单次 wall-clock 测量，Windows 下抖动约 ±5%，且 `-O1`（1558ms）比 `-O0`（1472ms）慢这一反常现象很可能是噪声。本文不把它当作结论，只作为"实测原始记录"列出。** 要做严肃的性能对比需要多次重复 + 取中位数 + 关闭后台进程。

### 7. 优化档对"检测工具"的影响（跨方向交叉点）

这一节与方向 29 深度耦合，此处只列与本方向直接相关的结论：

| 现象 | 机制 | 来源 |
|---|---|---|
| 高优化档 → ASan 检测率下降 | ASan 插桩放在"LLVM 优化流程的最末端"，**只检测在优化中幸存下来的内存访问**；"对由 LLVM 优化掉的本地堆栈对象的内存访问将不会被检测" | ASan 论文（ATC 2012） |
| `-O2` → Valgrind 开始误报 | Valgrind 官方原文："**Use of `-O2` and above is not recommended as Memcheck occasionally reports uninitialised-value errors which don't really exist.**" | Valgrind Quick Start |
| `-O1` → Valgrind 行号不准 | Valgrind 官方原文："With `-O1` line numbers in error messages can be **inaccurate**" | 同上 |
| 高优化档 → UBSan `object-size` 检测率**上升** | 该检查基于 `__builtin_object_size`，"may be able to detect **more** problems at **higher optimization levels**" | Clang UBSan 文档 |
| `-fwrapv` → UBSan 有符号溢出检查**失效** | "with this flag, UBSan will no longer treat signed overflow as UB" | Shafik Yaghmour, 2025-02-11 |
| `-fno-strict-overflow` / `-fwrapv` → UB 优化被抑制 | UBSan 文档：`add-signed-overflow-test` 模式"仅抑制未定义行为的检查，**激进的 UB 优化仍可能发生**"，可用 `-fwrapv` 或 `-fno-strict-overflow` 缓解 | Clang UBSan 文档 |

**综合机制**：优化档对检测率的影响是**非单调的**——降档让更多访问"幸存"（ASan 检测率↑），但降档也让 `__builtin_object_size` 变弱（UBSan `object-size` 检测率↓），而 `-O2` 让 Valgrind 开始误报。**因此"检测率"必须报告为一个以配置为自变量的矩阵，而不是一个标量。**

## 对阙疑的 3 条具体行动

**行动 1（立即可做，本机可完成）：把"编译档"从元数据升级为**判决的第一等输入**，并产出 `data/opt_matrix.json`。**
- 设计：对每一个判决样本，记录 `(compiler, version, opt_level)` 三元组，并**强制要求同一断言的证据至少来自 2 个不同档位**。
- 本机可复算的起步矩阵（3 编译器 × 5 档 × 6 个 UB 程序 = 90 次编译运行）：
  - `t_uninit.cpp`（未初始化读取）→ 15 配置 / 8 种输出
  - `t_ovf.cpp`（有符号溢出死循环）→ 15 配置 / 4 种行为
  - `t_sa.cpp`（严格别名 miscompile）→ 15 配置 / 2 种输出（`-O2` 分界）
  - `t_null.cpp`、`t_seq.cpp`、`t_arg.cpp` → 对照组
- 产出：`data/opt_matrix.json`，字段 `{source, compiler, version, opt, stdout, exit_code, stderr_warnings}`。
- 论文写法：§Evaluation 用这张表支撑一句主张——"**同源异构**：6 个程序 × 15 个配置 = 90 个运行，其中 N 个在配置间输出不一致"。**这是最便宜、最难被质疑的实证。**

**行动 2（1 天内）：在规则库里新增 4 条"编译档敏感"标记，并修掉受影响的既有规则。**
- 新增元数据字段 `opt_sensitivity`，取值 `{none, o2_boundary, ofast_breaking, all_levels}`：
  - `o2_boundary`：GCC `-O2` 起行为变化（严格别名、`for` 溢出死循环）→ 对应实测矩阵 B；
  - `ofast_breaking`：仅 `-Ofast` 行为变化（`isnan`/`isinf` 失效）→ 对应实测矩阵 C；
  - `all_levels`：所有档位行为都不可预测（未初始化读取）→ 对应实测矩阵 A；
  - `none`：档位无关。
- **必须修掉的既有风险**：任何以"未初始化读取会得到随机值"为断言的卡片，在 Clang `-O1` 以上会得到确定的 0（实测），必须把 `input_domain` 里的编译档写清，或把断言改为"值未定义"而非"值为垃圾"。
- 验收：写 `tools/opt_sensitivity_audit_<batch>.py`，扫描 `data/_gate_rules.json` 与 `atoms/**/ATOM-*.md`（37 实卡），报出"含编译档敏感断言但未标注 `opt_sensitivity`"的条目数；目标为 0。

**行动 3（3 天内）：新增一条 block 规则 `OPT-FASTMATH-001`，把 `-Ofast` / `-ffast-math` 列为"检测能力破坏"事件。**
- 理由（本机实测 + 官方口径）：`-ffast-math` 的契约是"假定参数与结果都是有效的"，因此 `isnan()` 返回 0 **不是 bug 而是契约**——**它让所有基于 NaN/Inf 的错误检测静默失效**。
- 规则行为：若编译命令含 `-Ofast` 或 `-ffast-math`，且被检测代码含 `std::isnan` / `std::isinf` / `std::isfinite` / NaN 哨兵比较，输出 block 并给出本文件的实测矩阵作为证据。
- 论文写法：在 §Threats to Validity 的"编译档"一节引用本矩阵，明确指出：**"我们的检测能力边界依赖于编译命令；`-Ofast` 下 NaN 检测失效是我们主动放弃的覆盖范围，已在规则库中显式声明。"** —— 主动声明覆盖边界，是"外部效度优先"叙事的关键姿态。
- 诚实边界：本机无 MSVC，`/fp:fast` 下的同类行为**未实测**（文档口径见 §1）。

## 盲区（诚实标注）

1. **浮点重排（reassociation）未在本机复现**。`-Ofast` 下 `s_ordered`（1.0+1e-16-1.0）仍输出 0，未被重排。本文**不引用任何"`-ffast-math` 会改变结果"的自测数字**，只引用 MSVC `/fp` 文档与 KDAB 文章的定性说明。
2. **FMA 收缩未在本机复现**。`-O2`、`-O2 -ffp-contract=off`、`-O2 -ffp-contract=fast`、`-O2 -ffast-math` 四种配置下 `1.0*1e-16 + (-1.0)` 输出完全相同。推测原因是 MinGW 默认目标 CPU 不含 FMA 指令（**未验证**）。要复现需显式加 `-mfma` 或 `-march=native`（**未实测**）。
3. **空指针检查删除未在本机复现**（三编译器 `-O0`..`-Os` 全部输出 `ok=7`）。本文只引用 LWN 2009 的历史案例。
4. **运行时间矩阵（§6）是单次 wall-clock 测量，噪声约 ±5%**，且出现 `-O1`（1558ms）比 `-O0`（1472ms）慢的反常现象。**本文不把该组数字作为结论**，只作为原始记录。要严肃对比需要多轮重复 + 中位数 + 空闲机器。
5. **`-Os` 的体积数字（-11.3%）来自单一程序（`vector<string>` + `sort` + `map` + 递归 fib）**，不同程序的 `-Os` 收益差异极大，**不可外推**。
6. **`-Og` 档位未实测**。
7. **MSVC 的 `/O1`/`/O2`/`/Ox`/`/Od` 与 `/fp:*` 的交叉矩阵完全未实测**（本机无 MSVC），仅引用文档定性描述。
8. **"Clang `-O1` 起 `exit=3`"的机制未反汇编确认**（同方向 26/27 的盲区）。
9. **`-O2` 与 `-O3` 的开关集合差异未逐条核对 GCC 手册**。本文只保证 `-fstrict-aliasing` 在 `-O2` 及以上开启这一条（有本机实测印证），其余开关归属为手册口径的概述。
10. **"15 配置 → 8 种输出"这一去重数字是本文基于实测原始值人工去重的结果**。原始 15 个值全部列在 §2 表中，可独立复核去重口径。
