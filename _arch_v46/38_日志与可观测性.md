# 方向 38：日志与可观测性

> 调研时间：2026-09-29（GMT+8）｜联网搜索 11 次 + 2 次 WebFetch 读一手规范/官方文档
> 锚点项目：阙疑 / queyi（append-only 哈希链 + Merkle checkpoint + 452 条判决账本 + 独立对账器）
> 关联：方向 36（原子提交/可回滚）、方向 39（fail-closed）、方向 40（性能门禁）

---

## 核心结论

1. **阙疑已经拥有"可观测性三支柱"里最难的一根：审计账本**。OpenTelemetry 把可观测性拆成 traces / metrics / logs 三类 signal；绝大多数项目的 logs 是"随手 print"，而阙疑的 452 条判决账本是**append-only + 哈希链 + Merkle checkpoint**，天然满足"可验证完整性"——这比普通应用日志高一个量级，论文里应当把它明确定位为 **tamper-evident audit log（防篡改审计日志）**，而不是"日志"。
2. **普通日志与审计日志必须物理分离、格式分离、保留策略分离**：审计日志需要 append-only、不可篡改、可验证；应用日志需要可轮转、可丢弃、可采样。把两者混在同一个文件里，等于让"可轮转"这个特性去破坏"不可篡改"这个特性。
3. **SLI/SLO 对阙疑要做"批处理改造"**：Google SRE 的 SLO 公式（`error budget = 1 − SLO`，99.9% → 0.1%）是**面向请求型服务**的；阙疑是批处理验证器（一次跑一批），直接套 "99.9% 请求成功率" 会算错。正确做法是把"每次 gate 运行"当作一个请求、把"判决可复算"当作 SLI。

## 精确数字与案例

### 1. 结构化日志：为什么必须是 JSON（键值对），而不是拼接字符串

一手实践指南 `https://uptrace.dev/glossary/structured-logging` 与 `https://logmonitor.io/blog/structured-logging-best-practices` 给出的核心论点是：**纯文本日志只能被人读、无法被机器可靠解析**（正则解析脆弱、字段一改就崩）；结构化日志把每个字段变成显式键值对，使"按 `rule_id=44` 过滤""按 `verdict=block` 聚合"成为一次查询而不是一次正则。

关键工程约束（多篇一致）：

- **字段名必须稳定且可枚举**，例如 `ts` / `level` / `event` / `trace_id` / `span_id` / `rule_id` / `verdict` / `atom_id`。字段名漂移是结构化日志最常见的失效方式。
- **一行一条 JSON（JSON Lines / NDJSON）**，不要用多行 pretty-print——多行日志会破坏基于行的采集器（Fluent Bit / Vector / Loki）。
- **时间戳用 UTC + ISO 8601 带时区**，不要用本地时间。阙疑在 GMT+8，若不写时区，独立验收者（可能在其他时区）会算错时间线。
- **日志级别要有明确语义**（见 §3），并且**级别不是"重要性"而是"可操作性"**：只有"需要人立刻行动"的才配 ERROR。

`https://sudonull.com/zh/structured-json-logs-a-guide-for-developers`（2026-04-08）特别强调 **MDC（Mapped Diagnostic Context）**：把 `batch_id`、`run_id`、`trace_id` 放进一个上下文对象，之后每一条日志自动带上它，而不是每条都手写一遍。Python 侧的对应实现是 `structlog` 的 `contextvars` 绑定（`https://jishuzhan.net/article/2055105598878486530` 与 `https://devpress.csdn.net/v1/article/detail/94588028` 都提到 structlog 用 `threadlocal` 和 `contextvars` 管理上下文，在异步/多线程下正确传播）。

### 2. trace / span / traceparent：32 位与 16 位十六进制

一手来源 `https://opentelemetry.io/docs/concepts/context-propagation/`（WebFetch 读原文）：

- **context** = 一个对象，携带"发送方与接收方"之间用于关联 signal 的信息。服务 A 调用服务 B 时，A 把 **trace ID 和 span ID** 放进 context；B 用这些值创建一个新 span，把 A 的 span 设为 parent。
- **propagation** = 把 context 在服务/进程之间搬运的机制（序列化/反序列化）。
- **默认传播器 = W3C TraceContext**，HTTP header 名为 `traceparent`，格式原文：

```
<version>-<trace-id>-<parent-id>-<trace-flags>
```

官方示例：

```
00-a0892f3577b34da6a3ce929d0e0e4736-f03067aa0ba902b7-01
```

字段长度（从示例可数出，且与 W3C 规范一致）：`version` = **2 位十六进制**（`00`），`trace-id` = **32 位十六进制**（16 字节），`parent-id`（即 span-id）= **16 位十六进制**（8 字节），`trace-flags` = **2 位十六进制**（`01` = sampled）。

**安全警告（原文）**："**Be cautious when accepting context from external sources.** Malicious actors could send forged trace headers to manipulate your tracing data or potentially exploit vulnerabilities in context parsing." 以及 baggage："**avoid putting sensitive information (like user credentials, API keys, or PII) in baggage**"。

**对阙疑的映射**：阙疑没有分布式服务，但有"多次运行的批次链"（`_auto/status.json` 的 `active_batch`）。可以把 **批次号当 trace-id、单条判决当 span**：一次 gate run = 一个 trace，67 条规则各判一次 = 67 个 span。这样"某条规则为什么在这一批判定为 block"就有了可下钻的因果结构，而不是一堆平铺日志。这正是 OTel 文档里 `POST /cart/add > GET /product` 那种"带因果的聚合指标"的对应物。

### 3. 日志级别：RFC 5424 的 8 档与 Python 的 5 档

`https://www.rfc-editor.org/info/rfc5424/`（Syslog 协议）定义了 **8 个严重性级别，取值 0–7**：

| 值 | 关键字 | 语义 |
|---|---|---|
| 0 | `emerg` | 系统不可用 |
| 1 | `alert` | 必须立即行动 |
| 2 | `crit` | 严重状态 |
| 3 | `err` | 错误 |
| 4 | `warning` | 警告 |
| 5 | `notice` | 正常但重要 |
| 6 | `info` | 信息性 |
| 7 | `debug` | 调试 |

Python 标准库 `logging` 是 5 档（DEBUG=10 / INFO=20 / WARNING=30 / ERROR=40 / CRITICAL=50），**与 RFC 5424 不是一一对应**：Python 的 `CRITICAL` 只覆盖了 RFC 的 emerg/alert/crit 三档。跨语言/跨工具对接时（例如把日志送进 syslog 或 Loki），必须显式做映射，**不能假设同名同义**。

**阙疑的具体建议**：67 条规则里 `block 44` 触发时应记 **`err`**（因为它是"判决为错误"，需要人看）；`warn 16` 记 **`warning`**；`advice 7` 记 **`info`**。**不要用 `error` 记录"预期内的判决结果"**——判决结果是正常产出，不是异常。

### 4. 指标（metrics）：四种类型与"基数爆炸"

一手来源 `https://prometheus.io/docs/tutorials/understanding_metric_types/`：Prometheus 有四种核心指标类型——

- **Counter**：单调递增，只能加不能减（如"累计判决数"）。查询用 `rate()` / `increase()`。
- **Gauge**：可增可减的瞬时值（如"当前活动批次号"）。
- **Histogram**：把观测值放进预设桶（bucket），同时给出各桶计数与总和，可算分位数（`histogram_quantile`）。
- **Summary**：客户端预计算分位数。

**高基数（high cardinality）是"杀死 Prometheus 的头号方式"**。一手案例 `https://www.baodev.studio/blog/prometheus-high-cardinality-label-problem/`（2026-09-16）给出了具体数字：**一个 `user_id` 标签把 216 条时间序列变成 140 万条，并在 64 GiB 内存下 OOM-killed Prometheus**。另一篇 `https://www.michal-drozd.com/en/blog/prometheus-cardinality-explosion/`（2025-07-23）原文："Cardinality explosion is the number one way to kill Prometheus."

**对阙疑的直接约束**：**绝不要把 `atom_id`、`run_id`、`file_path` 做成 Prometheus 标签**。阙疑有 47 个 atom 文件、640 个 tools 条目，如果把它们当标签，序列数会瞬间膨胀。正确做法：标签只放**低基数**维度（`verdict` 四态 = 4 个值、`rule_class` = 3 个值 block/warn/advice、`layer` = A/B/C），高基数的 `atom_id` 放进**日志**或 **span attribute**，不进指标。

### 5. 审计日志 vs 应用日志：两类东西，两套设计

一手对比 `https://auditkit.dev/blog/audit-logs-vs-application-logs`（2026-03-10）与 `https://blog.csdn.net/leeyisoft/article/details/161624780`（2026-08-18，标题即"审计日志：append-only 的合规链路"）给出的一致结论：

| 维度 | 应用日志 | 审计日志 |
|---|---|---|
| 目的 | 调试、排障 | 问责、合规、证明"谁做了什么" |
| 可变性 | 可轮转、可删除、可采样 | **只增不改不删（append-only）** |
| 完整性 | 无保证 | **必须有完整性证明（哈希链/Merkle）** |
| 保留 | 通常 7–30 天 | 合规场景常 1–7 年 |
| 失败模式 | 丢日志可接受 | **丢一条即破坏链，不可接受** |

`https://blog.csdn.net/weixin_46044356/article/details/163628320`（2026-08-10，"考试操作日志怎么证明没有被改过"）进一步指出**普通 Audit Log 的可信边界**：单纯把日志写进数据库并不能证明"没被改过"，因为数据库管理员可以改。要证明，必须有 **append-only 写入 + 哈希链**，即每条记录的哈希包含上一条的哈希。

**这正是阙疑已经做的事**。阙疑的账本是 append-only + 哈希链 + Merkle checkpoint，在工程上等价于 **RFC 6962（Certificate Transparency）** 的 Merkle 树审计证明结构。`https://gm.okpki.com/wiki/certificate-transparency`（2026-06-02）描述了 CT 的核心：每张证书作为一个叶子进入 Merkle 树，任何第三方可以取 **audit proof（审计证明）** 与 **consistency proof（一致性证明）** 来验证"这条记录确实在树里"且"新树是旧树的扩展"。RFC 6962 定义了 `get-proof-by-hash`（输入 base64 的 v1 叶哈希 + `tree_size`，返回审计路径）等接口（`https://rfcinfo.com/zh-Hans/rfc-6962/4-5-retrieve-merkle-audit-proof-by-leaf-hash/`）。

`https://zatona.dev/blog/tamper-evident-audit-logs`（2026-09-06）给出实现视角：哈希链 + Merkle 树 + 证明。`https://lyceum.technology/magazine/tamper-evident-ai-audit-trails-hash-chains-and/`（2026-09 发布，4 天前）特别提到 **RFC 8785（JSON Canonicalization Scheme, JCS）**——因为要对 JSON 算哈希，必须先把它**规范化**（键排序、数字格式统一、无多余空白），否则同一个逻辑对象在不同序列化下哈希不同，链就断了。`https://www.rfc-editor.org/rfc/rfc8785.pdf` 是规范原文。

**这是阙疑最容易被审稿人抓住的技术点**：如果账本条目是 JSON，而哈希是对 `json.dumps(obj)` 的直接输出算的，那么**键顺序、空格、浮点表示**的差异会导致"同样的内容算出不同哈希"。必须在论文的 reproducibility 章节明确写"哈希前做了 RFC 8785 JCS 规范化"（或明确写"使用 canonical JSON，键按字典序、分隔符固定"），否则独立验收者复算会失败。

### 6. SLI / SLO / error budget：精确公式与批处理改造

一手来源 `https://sre.google/workbook/error-budget-policy/`（Google SRE Workbook，作者 Steven Thurgood，2018-02-19）原文：

- **"An error budget is 1 minus the SLO of the service. A 99.9% SLO service has a 0.1% error budget."**
- **"If our service receives 1,000,000 requests in four weeks, a 99.9% availability SLO gives us a budget of 1,000 errors over that period."**
- **"Changes are a major source of instability, representing roughly 70% of our outages."**
- **Outage policy（原文）**："If a single incident consumes more than **20%** of error budget over four weeks, then the team must conduct a postmortem. The postmortem must contain at least one **P0** action item to address the root cause."
- 若单类故障在一个季度内消耗超过 **20%** 预算，必须在季度规划文档里放一个 P0 项。

**对阙疑的批处理改造**：阙疑不是请求型服务，没有 "requests/second"。可行的 SLI 定义（建议写进论文的 evaluation 章节）：

- **SLI-1（判决可复算率）** = 独立对账器能成功复算哈希链的账本条目数 / 总条目数。目标 SLO = **100%**（这是硬不变量，不是 99.9%——哈希链断一条就是 0，不存在"部分可用"）。
- **SLI-2（gate 运行成功率）** = 成功完成（非崩溃、非超时）的 gate run 数 / 总 run 数。这个可以设 99% 之类的软目标。
- **SLI-3（判决确定性）** = 同一输入两次运行给出相同判决的次数 / 总次数。目标 SLO = 100%。

**关键点**：SLI-1 和 SLI-3 应当是 **100% 硬门禁**（fail-closed，见方向 39），而不是"有 error budget 可以烧"的软目标。error budget 的哲学是"允许偶尔坏一点"，而"可被独立验收"的哲学是"一次都不许坏"。这两者在阙疑身上是**冲突的**，必须明确取舍——建议：**对内（开发过程）用 error budget，对外（论文声称的可验收性）用 100% 不变量**。

### 7. 采样与敏感信息：两个必须显式决策的点

- **采样（sampling）**：trace 采样（如 head-based 1%）对高流量服务是必需；阙疑的 gate run 频率低（每批次几次），**应 100% 采样**，不要引入采样——采样会让"某次判决没有 span"变成不可复现的借口。
- **脱敏**：`https://jsonic.io/guides/json-structured-logging` 提到 JSON 日志的 **redaction**（脱敏）字段列表。阙疑当前无用户 PII，但**有密钥风险**（方向 41 主题）：`gh` token、任何 API key 都不能进日志。OTel 原文同样警告 baggage 不要放凭据。

## 对阙疑的 3 条具体行动

**行动 1：把账本条目哈希的"规范化"步骤显式化，并写成可复算的断言。**
具体：在 `tools/` 下新增（或核实已有）`canonical_json.py`，实现 RFC 8785 JCS 子集（键按 UTF-16 码元序排序、无多余空白、数字用 ECMAScript `Number.prototype.toString` 等价格式），把账本哈希函数改为 `sha256(jcs(entry_without_hash))`。在 `reconcile.py --verify-ledger` 里加一条断言：**对每一条历史条目重算 JCS 哈希并与链上值比对**。验收标准：`python tools/reconcile.py --verify-ledger` 对 452 条全部通过，且对任意一条人为改一个字节后必须失败。**这一条是论文 reproducibility 的命门**——若现在没有规范化，独立验收者复算会 100% 失败。

**行动 2：把 gate run 改成"trace 化"，并在日志里注入 `trace_id` / `span_id` / `batch_id`。**
具体：用 `structlog`（`pip install structlog`）替换现有 `print`/`logging`，用 `structlog.contextvars.bind_contextvars(batch_id=..., run_id=...)` 在 run 开始时绑定上下文；每条判决日志输出一行 NDJSON，字段固定为 `{ts, level, event, trace_id, span_id, batch_id, rule_id, rule_class, verdict, atom_id}`。**`atom_id` 只进日志不进指标**（避免基数爆炸）。验收标准：`grep '"verdict":"block"' logs/run-*.ndjson | jq -r .rule_id | sort | uniq -c` 能一条命令给出"本批 block 规则的分布"。

**行动 3：建立"审计日志 / 应用日志"物理分离，并给审计日志写一条不可变断言。**
具体：审计账本（452 条）继续放在只增不删的路径（如 `data/ledger/`），**禁止任何代码对它做 `rotate` / `truncate` / `unlink`**；应用日志放在 `logs/` 并配 `logging.handlers.RotatingFileHandler(maxBytes=..., backupCount=...)`。在 CI（方向 37）里加一个 job：`git diff --name-status HEAD~1 HEAD | grep '^D.*data/ledger/' && exit 1`（审计账本不允许删除文件），再对每个账本条目跑一次 `reconcile --verify-ledger`。验收标准：故意删除一条账本条目后 CI 变红。**同时**在论文 §Evaluation 里把 SLO 写成：SLI-1 判决可复算率 = **100%（硬门禁，非 error budget）**，SLI-2 gate 运行成功率 = 软目标，并说明为什么前者不能用 error budget。

## 盲区（诚实标注）

1. **阙疑账本的哈希规范化方式我未读源码核实**。`00_仓库扫描.md` 只登记"452 条（采信 README，未独立复算）"，**没有说明哈希输入是否做过 JCS/canonical 化**。上面行动 1 是**基于风险的假设**，不是发现的问题。需要实读 `tools/` 里的账本/对账器实现确认。
2. **W3C TraceContext 的字段长度是我从 OTel 文档的示例字符串数出来的**（trace-id 32 hex、span-id 16 hex、version 2 hex、flags 2 hex）。我**未逐字读 W3C TR 规范原文**核对边界条件（如 version=`ff` 时按非法处理）。
3. **RFC 5424 的 8 个级别名称与取值**来自 `rfc-editor.org` 条目与第三方中文解读的一致性，**未逐字读 RFC 5424 正文**；Python `logging` 五档的映射关系是我的推断，非规范文本。
4. **"变更占 Google 约 70% 的故障"是 Google SRE Workbook 的原文数字**，但它描述的是 Google 自身的服务，**不能直接外推到阙疑**。
5. **140 万序列 / 64 GiB OOM 的案例来自第三方博客**（`baodev.studio`），非 Prometheus 官方文档；数字真实性未独立验证。
6. **structlog 在 2026 年的最新版本号、以及它与 Python 3.12/3.13 `contextvars` 的兼容细节未核实**。搜索到的 structlog 官方文档链接指向 `https://www.structlog.org/en/17.2.0/`（一个较老版本），**最新稳定版未确认**。
7. **"阙疑无用户 PII"是我的判断**，未逐一检查 `web/` 前端与数据管道是否收集任何个人信息。
8. **批处理 SLO 的改造方案是我提出的设计**，未找到"批处理验证器 SLI/SLO"的一手权威范本；Google Cloud 的 SLI 文档（`https://docs.cloud.google.com/stackdriver/docs/solutions/slo-monitoring/sli-metrics/overview`）主要面向请求型服务，我**未逐页读完**。
