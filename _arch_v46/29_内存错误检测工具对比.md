# 方向 29：内存错误检测工具对比（ASan / TSan / MSan / UBSan / Valgrind）

> 调研时间：2026-09-29
> 本机实测工具链：GCC 15.3.0（MinGW-W64 winlibs）、GCC 13.1.0（MinGW-Builds）、Clang 22.1.8（msys2 x86_64-w64-windows-gnu）
> ⚠️ 本文件的一个核心实测结论就是：**本机三套工具链的 sanitizer 运行时全部缺失**（见 §0）。

---

## 核心结论

1. **五个工具不是"强弱之分"，而是"分工之分"，且互相不可替代。** ASan 抓**空间错误**（越界/UAF/双重释放），MSan 抓**未初始化读取**，TSan 抓**数据竞争**，UBSan 抓**约 30 类显式 UB**，Valgrind 抓**无需重编译的内存错误 + 未初始化读取**。任何声称"跑通 ASan 就没有内存错误"的说法在工程上是错的——ASan 论文自己列出**三类 false negative**。

2. **开销差三个数量级，且"优化档会改变工具的行为"。** ASan 官方口径 **2×** 减速、ASan 论文口径 **73% 减速 + 3.4× 内存**；TSan **5–15× 减速、5–10× 内存**；MSan **3× 减速、2× 内存**（开 origin tracking 再加 **1.5–2×** 减速、内存升到 3×）；UBSan "开销很小且不影响地址空间布局或 ABI"；Valgrind **20–30×**。**最要命的一条是 Valgrind 官方明说"`-O2` 及以上不推荐，因为 Memcheck 偶尔会报告实际不存在的未初始化值错误"**——**优化档直接改变工具的报告**。

3. **阙疑当前无法在本机运行任何 sanitizer 报告，这是必须写进论文的硬约束。** 本机实测：GCC 15.3.0 `-fsanitize=undefined` → `cannot find -lubsan`；Clang 22.1.8 `-fsanitize=address` → `cannot find libclang_rt.asan_dynamic_runtime_thunk.a`。这意味着阙疑 v0.3 记录的"`-O1`→`-O0` 使 3/5 miss 被同一 sanitizer 抓住"这一结果，**不可能是在本机产生的**，必须能追溯到具体环境。

## 精确数字与案例

### 0. 本机实测：sanitizer 运行时可用性（2026-09-29）

| 工具链 | 尝试 | 实测结果 |
|---|---|---|
| GCC 15.3.0 (MinGW-W64 winlibs, x86_64-msvcrt-posix-seh) | `g++ -fsanitize=undefined` | **失败**：`ld.exe: cannot find -lubsan` |
| Clang 22.1.8 (msys2 mingw64) | `clang++ -fsanitize=address` | **失败**：`cannot find .../libclang_rt.asan_dynamic_runtime_thunk.a` |
| Clang 22.1.8 | `clang++ -fsanitize=undefined` | **失败**：`undefined reference to '__ubsan_handle_add_overflow'` |
| `/c/msys64/mingw64/lib/clang/` 目录 | 查找运行时 | 只有版本号目录 `22`，**无 `lib/windows/` 下的 sanitizer 运行库** |
| GCC 15.3.0 的 `lib/` 与 `x86_64-w64-mingw32/lib/` | 查找 libasan/libubsan | **无任何匹配** |

**结论**：本机（Windows + MinGW 工具链）**无法链接、无法运行任何 sanitizer**。这与本项目自有 UB 库的环境声明完全一致（该库原文："本机**无法链接并运行 ASan/UBSan 运行时**，故 sanitizer 的栈回溯报告在本库中以 `[DOC-REPORT]` 标记，取自 GCC/Clang 官方文档的预期格式，**非本机捕获**"）。

**这条对阙疑的直接影响**：任何"sanitizer 检出率"数字都必须标注运行环境；本机不能产生 sanitizer 证据，只能产生（a）编译期警告、（b）`-O0`/`-O2` 输出分歧 两类证据。

**关键点**：**严格别名违规没有任何一个工具能直接检测**（UBSan 不覆盖，ASan/MSan/TSan 都不管）。Clang 新的 **TypeSanitizer（TySan）** 是为这个空白设计的（官方文档原文："TypeSanitizer is built to catch when these strict aliasing rules have been violated"），但 Shafik Yaghmour 2025-02-11 博文明确说它"**relatively new and still has some bugs**"。

### 2. UBSan 的完整检查清单（Clang 官方文档逐项，共 30+ 项）

**单项检查**（`-fsanitize=` 可取的值）：
`alignment`、`bool`、`builtin`、`bounds`、`array-bounds`、`local-bounds`、`enum`、`float-cast-overflow`、`float-divide-by-zero`、`function`、`implicit-unsigned-integer-truncation`、`implicit-signed-integer-truncation`、`implicit-integer-sign-change`、`integer-divide-by-zero`、`implicit-bitfield-conversion`、`nonnull-attribute`、`null`、`nullability-arg`、`nullability-assign`、`nullability-return`、`objc-cast`、`object-size`、`pointer-overflow`、`return`、`returns-nonnull-attribute`、`shift`、`shift-base`、`shift-exponent`、`unsigned-shift-base`、`signed-integer-overflow`、`unreachable`、`unsigned-integer-overflow`、`vla-bound`、`vptr`。

**检查组**：`undefined`（默认组，**不含** `float-divide-by-zero` / `unsigned-integer-overflow` / `implicit-conversion` / `local-bounds` / `vptr` / `nullability-*`）、`implicit-integer-truncation`、`implicit-integer-arithmetic-value-change`、`implicit-integer-conversion`、`implicit-conversion`、`integer`、`nullability`、`undefined-trap`（已废弃别名）。

**注意语义边界**（官方原文）：`unsigned-integer-overflow` 与 `float-divide-by-zero` **不是 UB**，但"常为无意"，所以它们被排除在 `undefined` 组之外；`vptr` 也不在 `undefined` 组里。**因此 `-fsanitize=undefined` 并不等于"所有 UB 检查"**——这是最常见的误用。

### 3. 开销的精确数字

**ASan**
- Clang 官方文档："**Typical slowdown introduced by AddressSanitizer is 2x.**"；"AddressSanitizer uses more stack memory. We have seen **up to 3x increase**."；"On 64-bit platforms AddressSanitizer maps (but not reserves) **16+ Terabytes** of virtual address space."
- ASan 论文（Serebryany 等, USENIX ATC 2012）：**"73% slowdown and 3.4x increased memory usage"**；"Its average slowdown is just 73% yet it accurately detects bugs at the point of occurrence. It has found **over 300 previously unknown bugs in the Chromium browser** and many bugs in other software."
- SPEC CPU 2006 官方性能数据（Clang 3.3 trunk r179094，2013-04-09，Intel Xeon W3690 @3.47GHz，`-O2` vs `-O2 -fsanitize=address -fno-omit-frame-pointer`）：**平均减速 1.93×，中位数 1.86×**。逐项极值：
  - 最慢：`400.perlbench` 344.00 → 1304.00 = **3.79×**
  - 最快：`462.libquantum` 480.00 → 539.00 = **1.12×**
  - 其他：`464.h264ref` 2.40×、`453.povray` 2.25×、`483.xalancbmk` 2.17×、`458.sjeng` 2.15×、`445.gobmk` 2.04×、`456.hmmer` 2.03×、`403.gcc` 1.89×、`471.omnetpp` 1.87×、`447.dealII` 1.86×、`429.mcf` 1.84×、`482.sphinx3` 1.76×、`401.bzip2` 1.72×、`473.astar` 1.63×、`433.milc` 1.63×、`444.namd` 1.61×、`450.soplex` 1.58×、`470.lbm` 1.24×
  - 更早的测量（asan r496，`malloc_context_size=1`）：全插桩平均 **1.73×**；**仅插桩写操作时平均 1.26×**（这个 1.26 是"只检查写"的代价，很有参考价值）

**TSan**
- Clang 官方文档："**Typical slowdown introduced by ThreadSanitizer is about 5x-15x. Typical memory overhead introduced by ThreadSanitizer is about 5x-10x.**"（另一处表述："At the default settings the memory overhead is 5x plus 1Mb per each thread. Settings with **3x** (less accurate analysis) and **9x** (more accurate analysis) overhead are also available."）
- 历史：**TSan v1**（基于 Valgrind 的二进制翻译版本，2009 年发布）减速为 **20–300×**（LWN 引用 2012 年演讲），**用它在 Chromium 里找到近 180 个 bug**，但因为太慢无法用于完整浏览器测试，所以重写为编译期插桩的 TSan v2。

**MSan**
- Clang 官方文档："**Typical slowdown introduced by MemorySanitizer is 3x.**"；"MemorySanitizer uses **2x more real memory** than a native run, **3x with origin tracking**"；"MemorySanitizer maps (but not reserves) **64 Terabytes** of virtual address space."
- Origin tracking 代价（官方原文）："It slows down program execution by a factor of **1.5x-2x** on top of the usual MemorySanitizer slowdown and increases memory overhead."
- 平台限制：**只支持 Linux / NetBSD / FreeBSD**。**不支持静态链接**。
- **最硬的使用约束（官方原文）**："MemorySanitizer requires that **all program code is instrumented**. This also includes any libraries that the program depends on, **even libc**. Failing to achieve this may result in **false reports**." 为此 MSan 运行时内置 **70+ 个 libc 拦截器**。

**UBSan**
- Clang 官方文档只给定性表述："The checks have **small runtime cost** and **no impact on address space layout or ABI**."
- ⚠️ 本文**未找到 UBSan 的一手基准数字**。社区资料（如 `kavinchan13.github.io` 的技术笔记）给出 "1.05–1.10×" 区间，但**这不是官方数字，本文不作为结论引用**（列入盲区）。

**Valgrind (Memcheck)**
- 官方 Quick Start 原文："Your program will run **much slower (eg. 20 to 30 times)** than normal, and use a lot more memory."
- Valgrind 手册原文（关于内存）："more than **twice as much** as normal under the Memcheck tool."
- 第三方对照文章给出 20–50× 的区间（**该数字来自该文的经验值，不是 Valgrind 官方**）。
- 另一处社区资料给 "10–30 倍"，根因是"动态二进制插桩（DBI）"：每条机器指令都被翻译为中间表示并插入影子内存检查。

### 4. 误报（false positive）与漏报（false negative）

**ASan 的官方立场**（Clang 文档原文）："**AddressSanitizer is not expected to produce false positives.**"（官方认为看到误报应先复查，很可能是真阳性）。但**明确列出的 false negative 有三类**（ASan 论文）：
1. **越界访问跳得特别远、越过 redzone** —— 落入下一块合法内存，无法检测；
2. **UAF 在 quarantine 队列已满后被复用** —— 无法检测；
3. **未对齐字节的读写** —— 可能检测不到（修复会拖慢 fast path）。

另有 ASan 实现层面的已知漏报（第三方技术笔记，非官方）：**intra-object overflow 不检测**（redzone 只在整个 allocation 前后，struct 内部字段共享合法 shadow）；**自定义 allocator 的 sub-allocation 不被监控**；**mmap / 大块 syscall 缓冲弱覆盖**。

**ASan 明确会误报的场景**（Clang 文档原文）：**container overflow detection 易产生误报**——"栈上对象的部分投毒（如小字符串优化）会导致误报和漏报"、"若二进制仅部分被 ASan 插桩，检查可能引发误报"。可用 `ASAN_OPTIONS=detect_container_overflow=0` 或 `-D__SANITIZER_DISABLE_CONTAINER_OVERFLOW__` 关闭。

**Valgrind 的官方立场**（Quick Start 原文）："Memcheck is not perfect; it occasionally produces **false positives** ... However, it is typically **right 99% of the time**." —— **这是所有工具里唯一给出"准确率 99%"这类量化自评的**。

**Valgrind 的官方能力边界（原文）**："Memcheck cannot detect every memory error your program has. For example, it **can't detect out-of-range reads or writes to arrays that are allocated statically or on the stack**."

**MSan 的误报来源（官方原文）**：未全程序插桩会"result in false reports"。另外 `disable_sanitizer_instrumentation` 属性"may introduce false positives"。

### 5. 优化档对工具的影响（本方向最关键的交叉点）

| 来源 | 原文/数字 | 含义 |
|---|---|---|
| Valgrind 官方 Quick Start | "Using `-O0` is also a good idea... With `-O1` line numbers in error messages can be **inaccurate**... **Use of `-O2` and above is not recommended as Memcheck occasionally reports uninitialised-value errors which don't really exist.**" | **`-O2` 会让 Valgrind 产生"实际不存在"的未初始化错误报告** |
| ASan 官方文档 | "To get a reasonable performance add **`-O1` or higher**."；"To get perfect stack traces you may need to disable inlining (**just use `-O1`**) and tail call elimination (`-fno-optimize-sibling-calls`)" | ASan 推荐 `-O1`，**用 `-O1` 是为了栈回溯质量，不是为了检测率** |
| TSan 官方文档 | "To get a reasonable performance add **`-O1` or higher**." | 同上 |
| MSan 官方文档 | "To get a reasonable performance add **`-O1` or higher**." | 同上 |
| ASan 论文 | ASan 检测被放在 "**LLVM 优化流程的最末端**"，"我们仅检测那些在 LLVM 优化器执行的所有标量和循环优化中**幸存下来的内存访问**。例如，对由 LLVM 优化掉的本地堆栈对象的内存访问将不会被检测。" | **优化掉的访问 → 检测不到** |
| UBSan 官方文档 | `object-size` 检查基于 `__builtin_object_size`，"consequently may be able to detect **more** problems at **higher optimization levels**" | **UBSan 有一项检查反而在高优化档更强** |
| UBSan 官方文档 | `add-signed-overflow-test` 模式"仅抑制未定义行为的检查，**激进的 UB 优化仍可能发生**"，可用 `-fwrapv` 或 `-fno-strict-overflow` 缓解 | **"关掉 UBSan 报告" ≠ "消除 UB"** |

**综合结论**：优化档对工具的影响是**双向的、非单调的**——
- 高优化档 → 更多访问被优化掉 → **ASan 检测率下降**；
- 高优化档 → `__builtin_object_size` 更精确 → **UBSan `object-size` 检测率上升**；
- `-O2` → **Valgrind 开始误报**。

**这正是阙疑 v0.3 记录的"编译档"陷阱的完整机制**：`-O1`→`-O0` 使 3/5 miss 被同一 sanitizer 抓住，因为降档后更多内存访问"幸存"到了插桩点。

### 6. Sanitizer 互斥性与平台差异

**互斥矩阵**（来源：Conan 文档 + 多篇技术笔记 + 华为 HarmonyOS 开发者文档）：

| | ASan | TSan | MSan | HWASan | UBSan | LSan |
|---|---|---|---|---|---|---|
| ASan | — | ❌ | ❌ | ❌ | ✅ | ✅（内置） |
| TSan | ❌ | — | ❌ | ❌ | ✅ | ⚠️ 部分 |
| MSan | ❌ | ❌ | — | ❌ | ✅ | ⚠️ 部分 |
| HWASan | ❌ | ❌ | ❌ | — | ✅ | ✅ |
| UBSan | ✅ | ✅ | ✅ | ✅ | — | ✅ |

**根因**（技术笔记归纳）：shadow memory 布局冲突（每个 sanitizer 独占虚拟地址空间特定段）+ allocator 冲突（都替换 `malloc`/`free`）+ signal handler 冲突（都装 `SIGSEGV`/`SIGBUS` handler）。**UBSan 是唯一例外**——它在指令级 in-place 插检查，不用 shadow、不替换 allocator，因此**可与任何其他 sanitizer 同跑**。这也是官方推荐的组合 `-fsanitize=address,undefined` 与 `-fsanitize=hwaddress,undefined` 的原因。

**平台差异**：
- **MSan 不支持 Windows**（只支持 Linux/NetBSD/FreeBSD）。因此 Windows 上抓未初始化读取只能靠 **Valgrind** 或 **MSVC 的 `/RTCu`**（未核实）。
- **Valgrind 基本不支持 Windows**。
- **ASan 支持 Windows**（MSVC 2019 16.9+），但 **`alloc-dealloc-mismatch` 检查在 Windows 上默认关闭**（Microsoft Learn 原文），需 `set ASAN_OPTIONS=alloc_dealloc_mismatch=1`。
- **LeakSanitizer**：Linux 默认开启；macOS 需 `ASAN_OPTIONS=detect_leaks=1`；**其他平台尚不支持**（Clang 文档原文）。
- **HWASan**：仅 ARM/AArch64，需要 TBI（Top Byte Ignore）或 MTE 硬件支持。

### 7. 泄露检测的分类粒度差异（实测对照）

| 工具 | 输出措辞 | 分类档数 |
|---|---|---|
| ASan（LSan） | `Direct leak of 4 byte(s)` | **2 档**：Direct / Indirect |
| Valgrind Memcheck | `definitely lost: 4 bytes in 1 blocks` | **4 档**：definitely lost / indirectly lost / possibly lost / still reachable |

同一 UAF 案例下两个工具的定位行号完全一致（读 `:20` / free `:19` / malloc `:17`），只是措辞不同：ASan 报 `heap-use-after-free` + `located 0 bytes inside of 4-byte region`；Memcheck 报 `Invalid read of size 4` + `Address ... is 0 bytes inside a block of size 4 free'd`。

### 8. ASan 的实测假阴性案例（一手实测）

同一篇文章给出真实跑测：未初始化读取场景下 ASan **完全静默**，程序正常返回垃圾值：
```
$ ./cases 1
uninit=-1094795586
```
作者结论："ASan 一声不吭，正常返回垃圾值（地址合法，无 V-bit 判断）。这块错 memcheck 能抓、ASan 抓不到。"

### 9. 生态采用率

SoK: Sanitizing for Security（Song 等, IEEE S&P 2019, arXiv:1806.04355）原文："**We found that ASan is used in 24 and 19 of the most popular C and C++ projects on GitHub respectively.**" 该论文认为 ASan 流行源于三点：(i) 检测的 bug 类别最可能被利用（内存安全违规）；(ii) 兼容性极高（不引入额外元数据依赖）；(iii)（原文第三点未在本环境完整提取，列入盲区）。

## 盲区（诚实标注）

1. **UBSan 的运行时开销没有任何一手数字**。Clang 官方文档只写"small runtime cost"，**没有百分比**。社区流传的 "1.05–1.10×" 无官方出处，本文不采信。
2. **HWASan 的开销数字全部来自第三方技术笔记**（如 "1.3–1.5× CPU / 1.5–2× 内存"、MTE "1.05–1.15×"）。本文**未在 Clang 官方 HWASan 文档中逐字核对**，故只作趋势性描述。
3. **ASan 论文的 "3.4x memory" 与官方文档的 "up to 3x stack memory" 是两个不同口径**（论文是整体内存，文档是栈内存），本文并列但未做归一。
4. **"ASan 误报率 1/2^8 = 0.4%"** 这类数字来自第三方技术笔记，**无官方出处**，本文不引用。
5. **Valgrind "20–50×" 的区间来自第三方对照文章**，官方只写 "20 to 30 times"。
6. **SoK 论文（S&P 2019）的完整比较表未提取到**。该论文是 PDF（arXiv:1806.04355 与 oaklandsok.github.io），本环境 WebFetch 拒绝解析 PDF、Read 工具报 "Cannot display content of binary file"。因此本文只引用搜索片段中出现的 "ASan is used in 24 and 19 of the most popular C and C++ projects on GitHub respectively" 这一句，**其余数字（如各 sanitizer 的覆盖率百分比）未引用**。
7. **MSVC 的 sanitizer 能力未实测**（本机无 MSVC）。MSVC 只提供 ASan（无 UBSan/TSan/MSan 的官方支持），此结论**引自社区共识，未在 Microsoft Learn 逐字确认**。
8. **"MSVC `/RTCu` 可替代 MSan 抓未初始化读取"** 这一说法**未核实**，仅为常见工程做法，不建议直接引用。
9. **本机 sanitizer 缺失的根因未追**。可能是 MinGW-w64 发行版未捆绑运行时（如本项目 UB 库所述），也可能是 msys2 打包裁剪。本文只报告"链接失败"这一事实。
10. **Valgrind 在本机不可用**（Windows），因此本文所有 Valgrind 结论均来自官方文档与第三方实测文章，**非本机实测**。
