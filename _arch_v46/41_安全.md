# 方向 41：安全（不要泄漏密钥 / 凭证管理）

> 调研时点：2026-09-29。搜索次数：14（WebSearch 12 + WebFetch 2，另 1 次 PDF 抓取失败）。
> 本方向的服务对象：阙疑（queyi）仓库中的 `data/vsa_secret.key`、`.env`、供应链台账，以及 append-only 哈希链的签名密钥。

## 核心结论

1. **密钥泄漏不是"小概率意外"，而是当前软件供应链最高频、成本最低、后果最重的风险类别**：GitGuardian《State of Secrets Sprawl 2025》实测 **2024 年公共 GitHub 上泄漏 2380 万条密钥（同比 +25%）**，且 **2022 年泄漏的密钥中有 70% 到今天仍然有效**——也就是说，绝大多数泄漏从未被修复，攻击者拿到的是一把仍然能开门的钥匙。
2. **防御必须做成"三层纵深"，任何单层都不成立**：第一层是**提交前本地拦截**（gitleaks / git-secrets / detect-secrets + pre-commit），第二层是**服务端 push protection**（GitHub 官方支持 **522 个 provider pattern**，公开仓库免费自动开启），第三层是**事后全历史扫描 + 活体验证 + 轮换**（trufflehog 的 **700+ 个 detector 支持主动验证**，能区分"字符串长得像"和"真的能登录"）。
3. **最关键的认知（GitHub 官方文档原文）："Once you have pushed a commit... you should consider any sensitive data in the commit compromised. If you have committed a password, you should change it. If you have committed a key, generate a new one."** —— 历史重写（`git filter-repo` / BFG）**只能减少暴露面，不能替代轮换**；正确顺序永远是 **先轮换、再清理历史**，因为 fork、clone、SHA-1 缓存视图、PR 引用都无法收回。

## 精确数字与案例

### 1. 全局规模：GitGuardian《State of Secrets Sprawl 2025》（2025-03-11 发布）

这是目前公开可查、口径最清晰的一份密钥泄漏年度报告。原文关键数字（逐条列出，均来自报告页与官方博客）：

| 数字 | 含义 |
|---|---|
| **23.8 million（2380 万）** | 2024 年在**公共 GitHub 仓库**上泄漏的密钥总数 |
| **+25%** | 相对 2023 年的同比增长率 |
| **1.4 billion（14 亿）** | 2024 年 GitGuardian 扫描分析的 commit 总数 |
| **58%** | "通用密钥"（generic secrets，如私钥、数据库连接串）占全部泄漏凭据的比例 |
| **70%** | 2022 年泄漏的密钥中**至今仍然有效**的比例（"remain active today"） |
| **4.6%** | 公共仓库中包含密钥的比例 |
| **35%** | **私有仓库**中包含明文密钥（plaintext secrets）的比例 |
| **15%** | 泄漏过密钥的 commit 作者占比 |
| **8% / 5×** | 私有仓库出现 AWS IAM 密钥的比例是 **8%**，是公共仓库的 **5 倍** |
| **3×** | 硬编码密码在私有仓库的出现频率是公共仓库的 3 倍 |
| **18.8%** | 公共仓库中最常泄漏的密钥类型：MongoDB 凭据 |
| **98% / 7,000** | DockerHub 中检测到的密钥有 **98% 藏在镜像层**；其中 **7,000 个 AWS 密钥仍然有效** |
| **6.1% / 2.4%** | 企业 Jira 工单中暴露凭据的比例 **6.1%**（最脆弱的协作工具）；Slack 频道 **2.4%** |
| **1.9M** | GitGuardian 免费发送的公益告警（pro-bono alerts）数量 |

报告同时点名两个真实事件：**2024 年美国财政部（U.S. Treasury）泄漏事件**追溯至 BeyondTrust 认证平台的 **API 密钥泄漏**；**2025 年 Sysdig 事件**中，攻击者利用公共存储桶里发现的 **IAM 密钥，在 8 分钟内拿到管理员权限**。8 分钟这个数字是"密钥泄漏 → 全量失守"的最短实测路径，比任何理论风险论述都更有说服力。

> 注：GitGuardian CEO Eric Fourrier 的原话是 "Leaked secrets in private repositories must be treated as compromised."（私有仓库里的泄漏密钥必须按已失陷处理）——这条原则直接适用于阙疑这类"私有 + 单人 + 本地"的仓库。

### 2. 案例 A：DeepSeek / Common Crawl —— 12,000 条活体密钥（与 LLM 训练数据直接相关）

这是对阙疑**最有相关性**的案例，因为阙疑是一个"用 LLM 辅助、且声称可被独立验收"的项目。2025-02-28，Truffle Security 公开了这项研究（原始博客：trufflesecurity.com/blog/research-finds-12-000-live-api-keys-and-passwords-in-deepseek-s-training-data），具体数字：

- 扫描了 **400 TB 的 Common Crawl 2024 年 12 月快照**，包含 **26.7 亿（2.67 billion）个网页**、来自 **4,750 万（47.5 million）个 host**；
- 使用 **TruffleHog 的验证引擎**，识别出 **11,908 条经活体验证（verified live）的密钥**，可真实登录 AWS、Slack、Mailchimp 等服务；
- **276 万（2.76 million）个网页**含有暴露的凭据，其中 **63% 的密钥在多个域名间被复用**；
- 单个 **WalkScore API key 重复出现 57,029 次**，横跨 **1,871 个子域名**；
- **Mailchimp API key 泄漏最多（1,500+ 次）**，常直接写在前端 JavaScript 里；
- 单个网页的聊天功能里硬编码了 **17 个不同的 Slack webhook**；
- 数据以 **90,000 个 WARC 文件**存储；研究团队用了 **20 节点 AWS 集群**，通过 `awk` 切分后逐段扫描，优化后下载时间缩短 **5–6 倍**。

**为什么这条对阙疑致命**：报告明确指出，**LLM 无法区分"有效密钥"和"占位符"**，因此用 Common Crawl 训练的模型会把"硬编码凭据"当成正常模式学习，并在代码生成时**主动建议硬编码**。阙疑的 `.env` 与 `vsa_secret.key` 如果进入任何公开语料（GitHub 公开仓库、博客、issue、数据集），就有被"模型学会"的长期风险，而不只是被爬虫抓一次。

### 3. 案例 B：微软 AI 研究团队 38 TB 泄漏（2023-09）

Wiz Research 于 2023-09-18 公开（原文 wiz.io/blog/38-terabytes-of-private-data-accidentally-exposed-by-microsoft-ai-researchers）：微软 AI 研究团队在发布开源训练数据时，误分享了一个**配置错误的 Azure Blob 存储 SAS token**，导致 **38 TB 私有数据**可被匿名访问，其中包含 **30,000+ 条内部 Microsoft Teams 消息**和备份。微软 MSRC 同日回应（microsoft.com/en-us/msrc/blog/2023/09/...）。**根因不是密码泄漏，而是"过度授权（overly permissive）的 SAS token"**——这提醒阙疑：密钥泄漏不只是"AKIA 开头的字符串"，**签名 URL、预签名 token、只读 token 都是密钥**。

### 4. 案例 C：Uber 2016（私有仓库 + 硬编码 AWS key）

攻击者通过一组被盗的 GitHub 凭据，进入一名 Uber 工程师的**私有仓库**，在其中找到**硬编码的 AWS access key**，进而访问 Uber 的 Amazon S3 数据存储。FTC 的正式文件（ftc.gov/system/files/documents/cases/1523054_uber_technologies_revised_analysis.pdf）记录了 2016-10-13 至 2016-11-15 期间入侵者使用该 S3 Datastore 访问数据。**"私有仓库 = 安全"是错误假设**——GitGuardian 2025 报告也印证：35% 的私有仓库含明文密钥。

### 5. 案例 D：Toyota —— 密钥在 GitHub 上挂了近 5 年

2022 年 10 月，丰田披露其 **T-Connect** 应用的**访问密钥被公开放在 GitHub 上将近五年**，导致客户邮箱与管理编号泄漏；2023 年 5 月又披露 **215 万（2,150,000）名客户**的车载位置信息因云配置错误暴露近十年（CSO Online、TechSpot 均有报道）。**"长期驻留"是密钥泄漏最危险的特征**——GitGuardian 的 70% 未轮换数字与 Toyota 的 5 年驻留互为佐证。

### 6. 工具层：三款扫描器的精确能力边界

**（a）git-secrets（AWS Labs，github.com/awslabs/git-secrets）**
- 定位：**正则 + 原生 AWS pattern** 的轻量钩子；官方 AWS Prescriptive Guidance 收录了"用 git-secrets 扫描 Git 仓库敏感信息"的标准模式。
- 核心命令：`git secrets --install`（装钩子）、`git secrets --register-aws`（注册 AWS pattern）、`git secrets --scan`（扫当前）、`git secrets --scan-history`（扫全历史）。
- 局限：**只覆盖 AWS 系 + 自定义正则**，对新式 token（Anthropic/OpenAI/Stripe 等）需手工加正则；**无活体验证**。

**（b）gitleaks（开源，Go 实现）**
- 定位：**规则可控的 Git / 目录 / stdin 扫描器**，输出 SARIF/JSON，天然适合 CI。
- 典型命令（本次调研从多个实操指南交叉确认）：`gitleaks detect --source . --log-opts="--all --full-history" --report-format sarif --report-path gitleaks-report.sarif`。
- CI 集成：`gitleaks/gitleaks-action@v2`，需 `fetch-depth: 0` 才能扫全历史。
- 局限：**基于规则/熵，误报需要靠 `.gitleaksignore` 与 baseline 抑制**；无活体验证。

**（c）trufflehog（Truffle Security，github.com/trufflesecurity/trufflehog）**
- 定位：**唯一强调"活体验证（active verification）"的主流开源扫描器**。官方 README 原文："We've added over **700 credential detectors** that support active verification against their respective APIs."
- 规模：第三方评测（appsecsanta，2026-06）记录 **26.8k GitHub stars**、**每天 250,000+ 次扫描**。
- 典型命令：`trufflehog git file://. --only-verified --json > trufflehog-report.json`（`--only-verified` 是关键，只报能真实登录的）。
- 局限：**验证会对目标服务发起真实请求**，在受限网络下不可用；对无 API 可验证的通用密钥退化为熵检测。

**（d）detect-secrets（Yelp）**：基线式扫描，用 `.secrets.baseline` 记录已知假阳性，适合"存量已扫、只拦增量"的团队。

### 7. 流程层：pre-commit 与历史清理

**pre-commit 框架**（`.pre-commit-config.yaml`）是本地拦截的事实标准，实测配置形态：

```yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks: [{ id: gitleaks }]
  - repo: https://github.com/Yelp/detect-secrets
    rev: v1.4.0
    hooks: [{ id: detect-secrets, args: ['--baseline', '.secrets.baseline'] }]
  - repo: https://github.com/awslabs/git-secrets
    rev: master
    hooks: [{ id: git-secrets }]
```

安装与全量检查：`pip install pre-commit && pre-commit install && pre-commit run --all-files`。

**历史清理**（GitHub 官方文档 "Removing sensitive data from a repository"）：
- 官方**推荐 `git filter-repo`**（`pip install git-filter-repo`），示例：`git filter-repo --path path/to/secret-file --invert-paths`；替换文本用 `git filter-repo --replace-text expressions.txt`。
- **BFG Repo-Cleaner** 是"更快更简单的替代品"，但**必须在 bare mirror clone 上运行**：`git clone --mirror` → `bfg --replace-text passwords.txt` → `git reflog expire --expire=now --all` → `git gc --prune=now --aggressive` → `git push --force`。
- 官方明确警告：**这些工具会改写 commit SHA**，影响未合并的 PR；**fork 中的提交会继续存在**，必须联系 fork 所有者；**改完历史后仍要轮换密钥**。
- 实操安全建议（多份指南一致）：用 `git push --force-with-lease` 而非 `--force`；保护分支需临时关闭。

### 8. 密钥轮换与管理的权威依据

- **NIST SP 800-57 Part 1 Rev. 5**（2020-05-04 发布，"Recommendation for Key Management: Part 1 – General"）给出了**cryptoperiod（密码周期）**框架，即每类密钥的推荐最长使用期；**Rev. 6 草案（Initial Public Draft）于 2025-12-05 发布**，说明该标准正在更新。**⚠️ 本调研未能逐字读取 PDF 中的 cryptoperiod 表（WebFetch 不支持 PDF），具体年限数字列为盲区。**
- **AWS Secrets Manager** 支持**自动轮换**：由 Lambda 函数执行，官方文档 `rotate-secrets_lambda.html` 描述四步轮换流程（createSecret → setSecret → testSecret → finishSecret），常见配置为每 30 天或 90 天轮换一次。
- **集中式密钥管理工具**（2025-2026 市场横评）：HashiCorp Vault（自托管、功能最全、运维成本最高）、AWS Secrets Manager（与 IAM 深度集成、按密钥数计费）、Doppler（SaaS、开发者体验最好）、1Password Secrets、Infisical（开源替代）。对阙疑这种单人项目，**1Password / Infisical 的免费档即可覆盖**，Vault 属于过度工程。

### 9. 一句话风险公式

从上述案例可以提炼：**实际风险 = 泄漏概率 × 驻留时长 × 权限范围**。Toyota 是"驻留 5 年 × 高权限"；Sysdig 是"驻留短但权限是管理员，8 分钟失守"；微软 38TB 是"SAS token 权限范围过大"。**阙疑的 `vsa_secret.key` 若泄漏，风险取决于它能签什么**——如果它能伪造哈希链/checkpoint 签名，那么整个"可被独立验收"的可信基础就崩了，这比泄漏一个 API key 更严重。

### 10. 泄漏响应时间线：四个真实事件的时间尺度对照

把四个案例按"泄漏 → 被发现 → 被处置"的时间轴排开，可以看清一件事：**密钥泄漏的杀伤力主要由"驻留时长"决定，而不是由"泄漏的密钥种类"决定**。

| 事件 | 泄漏起始 | 被发现 / 披露 | 驻留时长 | 后果 |
|---|---|---|---|---|
| **Uber 2016** | 2016-10-13（攻击者开始使用 S3 数据存储） | 2017 年披露 | 至少 **1 个月**（FTC 文件记录的访问窗口为 2016-10-13 至 2016-11-15） | 私有仓库中的硬编码 AWS key 被利用 |
| **Toyota T-Connect** | 约 2017 年（密钥被放上 GitHub） | **2022-10** | **接近 5 年** | 客户邮箱与管理编号泄漏 |
| **Microsoft AI 38 TB** | SAS token 被写入开源仓库（具体起始未披露） | **2023-09-18**（Wiz 披露，MSRC 同日响应） | 未披露（Wiz 称是"近期"） | **38 TB** 私有数据、**30,000+** 条内部 Teams 消息可匿名访问 |
| **Sysdig 2025** | IAM 密钥出现在公共存储桶 | 同日 | **8 分钟** | 攻击者取得**管理员权限** |

**这张表给出的两个结论**：① Toyota 是"低权限但长期驻留"的典型——密钥本身权限有限，但**5 年不轮换**使其成为持续暴露面；② Sysdig 是"高权限但短驻留"的典型——**8 分钟足够**，说明"发现得快"也救不了"权限太大"。**对阙疑，`data/vsa_secret.key` 的权限是"能签哈希链/checkpoint"——按这个表，它属于"高权限"类，因此即使驻留时间短，后果也可能不可逆（签名一旦被伪造，整个"可被独立验收"的可信基础失效）。**

### 11. 最小可用防护清单（.gitignore + pre-commit + CI 三层）

**第一层：`.gitignore`（仓库根，5 行以内即可覆盖 90% 场景）**

```gitignore
.env
.env.*
*.key
*.pem
*.p12
secrets/
credentials.json
```

**第二层：`.pre-commit-config.yaml`（三钩子，见 §7 的完整配置）**——本地提交前拦截，**成本是一次配置、长期零维护**。

**第三层：CI 里的 gitleaks（防止有人绕过本地钩子，例如 `git commit --no-verify`）**

```yaml
- uses: actions/checkout@v4
  with: { fetch-depth: 0 }          # 必须，否则扫不到历史
- uses: gitleaks/gitleaks-action@v2
  env: { GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }} }
```

**为什么必须有三层**：GitGuardian 2025 报告的 **15% commit 作者**都泄漏过密钥，说明"人"这一层必然出错；而 **4.6% 的公共仓库**含密钥，说明"仓库"这一层也不可靠。**三层不是冗余，而是对"人必然犯错"的工程承认。** 特别注意：阙疑的 git log 中**存在 `push 走 --no-verify` 的历史记录**（见 `00_仓库扫描.md` 第 29 行的提交 `a18fb201`），**这正是"本地钩子会被绕过"的实证**——因此第三层（CI）对阙疑不是可选项。

## 对阙疑的 3 条具体行动

1. **立刻轮换 + 全历史扫描（本周内，1 小时内可完成）**：把 `data/vsa_secret.key` 与 `.env` 视为**已泄漏**（按 GitHub 官方口径），重新生成签名密钥；在仓库根加 `.gitignore` 条目（`.env`、`*.key`、`*.pem`、`*.p12`、`secrets/`）；执行 `gitleaks detect --source . --log-opts="--all --full-history" --report-format sarif --report-path gitleaks-report.sarif`，把 SARIF 报告**保留在 `_arch_v46/` 之外的项目证据目录**（但报告本身不含明文密钥）作为"密钥卫生"的可验收证据。
   - 命令级细节：先 `pip install detect-secrets gitleaks trufflehog`，再 `trufflehog git file://. --only-verified`，**只有 `--only-verified` 命中才需要立刻轮换**，否则先降噪。

2. **装上 pre-commit 三层拦截（本周内）**：在仓库根写 `.pre-commit-config.yaml`（gitleaks + detect-secrets + git-secrets 三钩子，配置见上文 §7），执行 `pre-commit install && pre-commit run --all-files`；同时在 GitHub 侧确认 **Secret scanning + Push protection 已开启**（公开仓库免费；GitHub 支持 **522 个 provider pattern**，Anthropic/AWS/OpenAI 等主流 token 都在列表内）。这样"本地拦截 + 服务端拦截"双保险，避免单点失效。

3. **把"密钥不硬编码"写成可验收的不变量（本月内）**：修改 `tools/gate_engine.py` 的启动逻辑，**只从环境变量或 `~/.queyi/secret` 读取签名密钥**，读不到就 fail-closed（拒绝启动），并在验收报告里加一条自动断言 `assert_no_hardcoded_secret()`；把 `data/vsa_secret.key` 从 git 索引移除（`git rm --cached data/vsa_secret.key`）但保留本地文件，确保"重跑对账器仍可复现、但仓库不含密钥"。

## 盲区（诚实标注）

- **NIST SP 800-57 的 cryptoperiod 具体年限未逐字核实**：WebFetch 无法解析 PDF（返回 "non-text resource"），本方向只确认了 Rev.5（2020-05-04）与 Rev.6 IPD（2025-12-05）的存在与标题，**未读取表格中的具体天数/年数**。需要人工下载 PDF 后核对。
- **"81% 的数据泄露源于硬编码密钥"这个流传数字来自 CSDN 二手引用**（标注"根据 GitGuardian 2024 年报告"），**未在 GitGuardian 一手报告中定位到对应原句**，故未采信。
- **Uber 的具体受影响人数（常见说法 5,700 万乘客 / 60 万司机 / 2018 年 1.48 亿美元和解）本次只确认了 FTC 文件中 2016-10-13 至 2016-11-15 的 S3 访问时间段**，具体人数与金额未逐字核对 FTC 原文，列为未核实。
- **GitHub "522 个 pattern" 是 2026-09-29 抓取时点的数字**，GitHub 每月都在新增（如 2025-12 的 changelog），2027 年投稿时需刷新。
- **trufflehog 的 "700+ detectors" 与 "26.8k stars"** 中，前者来自官方 README（可信），后者来自第三方评测站（appsecsanta，2026-06），**非 GitHub 官方实时数**。
- **AWS Secrets Manager 的"30 天 / 90 天"轮换周期**是社区常见实践与官方示例的默认值，**未在 AWS 官方文档中定位到"强制 90 天"的表述**（AWS 强调的是"可配置"，无强制上限）。
