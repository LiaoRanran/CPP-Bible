# 方向 82：12-18 个月后会被追上吗

> 调研时间：2026-09-29（GMT+8）
> 联网搜索：12 次（WebSearch）+ 2 次原文核对（WebFetch）
> 时间锚点：现在 = 2026-09；12–18 个月后 = **2027-09 至 2028-03**；NeurIPS 2027 E&D 预计投稿期 = 2027-05（社区估计 2027-05-20）

---

## 核心结论

**结论一：从「技术能力」维度看，阙疑会在 6 个月内被追上——LLM-as-a-Verifier（2026-07，Stanford/UC Berkeley/NVIDIA）已经在 SWE-Bench Verified 上做到 78.2%、Terminal-Bench V2 上 86.5%，且完全开源；哈希链 + Merkle 更是 RFC 6962 公开标准，复制成本近乎为零。**

**结论二：从「可审计 + 独立对账 + 盲态数据集」这个组合维度看，12–18 个月内被完整追上概率约 30%——因为大厂有动机做「验证能力」，但没有动机做「可被第三方独立复算的验证」（前者是产品卖点，后者是责任敞口）。**

**结论三：真正的时间敌人不是竞品，而是「benchmark 饱和」——2026 年 ICML 论文《When AI Benchmarks Plateau》实测 60 个 LLM benchmark 中 29 个（48.3%）已饱和，发布 24 个月内的饱和比例就有 42.9%；阙疑的 holdout 30 若在 2028 年前不扩样，会重演 SWE-bench Verified 被 OpenAI 宣布「退役」的命运。**

## 精确数字与案例

### 1. 竞争者速度：三类玩家，三种速度

**（A）学术大厂联合体 —— 速度：最快，6 个月一代**

`LLM-as-a-Verifier`（arXiv:2607.05391v2，2026-07-07，Stanford / UC Berkeley / NVIDIA Research，作者含 Chelsea Finn、Marco Pavone、Ion Stoica、Azalia Mirhoseini）：
- 从「思路」到「SOTA + 开源 + 配套 TurboAgent 产品」的周期极短；
- 数字：Terminal-Bench V2 **86.5%**、SWE-Bench Verified **78.2%**、RoboRewardBench 轨迹偏好准确率 **87.4%**、MedAgentBench **73.3%**；
- 平局率从离散 Judge 的 26.7%（K=1）降到 Verifier 的 **0**；
- 代码仓 `github.com/llm-as-a-verifier/llm-as-a-verifier` 已开源，并作为 Claude Code 的「drop-in LLM API proxy」发布。
- **对阙疑的威胁等级：高（能力维度）/ 低（审计维度）**——它验证的是「LLM 自己的判断」，没有第三方复算层。

**（B）创业公司 —— 速度：中，靠融资驱动**

- **Theorem**：2026-01-27 的 VentureBeat 报道标题为「Theorem wants to stop AI-written bugs before they ship and just raised **USD 6M**」——用 AI 驱动的形式化验证「数学地证明」代码正确性。融资额 600 万美元，属于种子/早期阶段。
- 行业背景：2026 年「vericoding / AI formal verification」已成为显学（多篇 2026 年指南文章，如 baeseokjae.github.io 的《Vericoding AI Formal Verification Code Correctness: How AI…》，2026-06-15）。
- **对阙疑的威胁等级：中**——方向重叠（代码正确性验证），但 Theorem 走「形式化证明」路线，与阙疑的「规则 + 证据链」路线不同。

**（C）基础设施玩家 —— 速度：慢，但一旦进入就是碾压**

- 开源审计层：`maco144/merkle-audit`（2026-06-21）、`MaqAnquor/incident-ledger`、`AuditWeave`（arXiv:2607.09682，2026-06-14）——**这些项目把「防篡改审计层」变成了通用基础设施**。
- 含义：如果未来 OpenAI / Anthropic 在 API 层内置「审计日志 + Merkle checkpoint」，阙疑的 L1 护城河（见方向 81）会**在一夜之间归零**。
- **对阙疑的威胁等级：极高（一旦发生）**，但发生概率在 12–18 个月内我判断 < 25%。

### 2. 开源复制成本：拆解到「人月」

把阙疑的产出物拆成可复制单元：

| 产出物 | 复制工作量估计 | 依据 |
|---|---|---|
| append-only 哈希链 + Merkle checkpoint | **0.5–1 人月** | RFC 6962 标准 + 现成库（merkle-audit 等） |
| 独立对账器（不依赖内核） | **1–2 人月** | 需重写判决逻辑 + 对账逻辑，且需通过一致性测试 |
| 67 条规则（44 block） | **2–3 人月** | 需 C++ UB 领域知识；规则本身明文可读 |
| 30 条盲 holdout + 40 条 corpus + 15 缺陷 | **3–6 人月 + 专家成本** | 需「找懂 C++ UB 的人 + 逐条核标签」 |
| 论文 + 复现包 | **1–2 人月** | 已有大量模板 |
| **合计** | **约 8–14 人月** | — |

**关键洞察**：**8–14 人月对一个 3–5 人的团队来说是 2–4 个月的事**。也就是说，**「能不能复制」的答案是「能」；「会不会复制」的答案取决于动机。**

**动机分析（为什么大厂不做）**：
1. **可审计性 = 责任敞口**：一个「可被第三方独立复算」的验证器，意味着厂商必须接受「外部人说你错了」的法律与 PR 风险。大厂的产品法务通常阻止这种设计。
2. **负结果 = 反营销**：阙疑公开了「反事实算子 P=R=F1=0」「C 层检出率 0%」这类数字。**大厂的 PR 流程不允许发布负面指标**。
3. **市场太小**：AI Audit 市场虽然被估为 92.6 亿–134 亿美元（三家口径，见方向 81），但**细分到「C++ 代码知识验证」可能只有百万美元级**，不值得大厂投入。

### 3. 窗口期判断：benchmark 饱和的硬约束

2026 年 ICML 论文《When AI Benchmarks Plateau: A Systematic Study of Benchmark Saturation》（arXiv:2602.16763v3，2026-06-30）给出了可量化的饱和速度：

- 样本：**60 个基于文本的 LLM benchmark**，来自 **61 份主要模型厂商技术报告（2022-01 至 2025-11）**；
- 结果：**29/60（48.3%）**呈现高或极高饱和（S_index ≥ 0.7），其中 **14 个（23.3%）**属于极高饱和（S_index ≥ 0.9）；
- **按年龄分组**：发布 **24 个月内**的饱和比例 **42.9%**（平均 S_index 0.51）；超过 **60 个月**的饱和比例 **54.5%**（平均 0.60）；
- **关键否证**：私有/隐藏测试集（H1）**无显著保护作用**（public N=52 vs private N=8，分布相似）；开放式输出格式（H4）**未比封闭式更能保持区分度**；
- **唯一有效因素**：**专家策展（expert-curated）**比众包更抗饱和（如 ARC-AGI、BIG-Bench Hard 长期暴露后仍未饱和）；
- 代码开源：`github.com/evaleval/benchmark-saturation`。

**把这条规律套到阙疑**：
- 阙疑 holdout 30 于 2026 年扩样（20→30），若按「24 个月内 42.9% 饱和」的基线速度，**到 2028 年有约 43% 概率饱和**；
- 但阙疑有一个「专家策展」属性——C++ UB 标签需专家核验——**这是论文明确指出的唯一抗饱和因素**；
- **对策**：holdout 必须**持续扩样**（建议每 6 个月 +10 条），且**新样本必须保持盲态**（老样本已 reveal，不可复用）。

### 5. 情景分析

**乐观情景（概率 30%）**：
- 前提：EU AI Act 高风险义务（2027-08-02 全面适用）推动「可审计验证」需求爆发；AI assurance 市场从「161 家英国公司」的量级快速扩张；阙疑论文被 NeurIPS 2027 E&D 接收。
- 结果：**阙疑成为「C++ 知识验证可审计性」的引用基准**；即使技术被追上，**「第一个把审计纪律引入代码验证并诚实报告负结果」的优先权不可剥夺**。
- 阙疑应做：抢时间戳、抢标准定义权（把「独立对账协议」写成公开规范）。

**中性情景（概率 45%，最可能）**：
- 前提：LLM-as-a-Verifier 类工具继续在「能力维度」领跑；1–2 个团队开始做「可审计变体」但未形成标准；阙疑论文被拒或只进 workshop。
- 结果：**阙疑退化为「一个有意思的单一作者项目」**，引用数停在个位数，但在「C++ UB 数据集」上有小众引用。
- 阙疑应做：把项目定位从「验证器」收缩为「**数据集 + 协议**」，放弃与 LLM 比能力。

**悲观情景（概率 25%）**：
- 前提：某大厂（OpenAI/Anthropic/Google）在 API 层内置「可验证输出 + 审计日志」；或 SWE-bench Verified 式的「退役」逻辑蔓延，导致所有 benchmark 类工作被审稿人视为「又一次 benchmark 刷榜」。
- 结果：**阙疑的 L1/L2 护城河同时归零**，只剩数据集。
- 阙疑应做：**提前准备 Plan B**——把 holdout 30 作为「不可回盲的历史证据」永久存档，转向「AI 审计方法论」的批判性研究（E&D track 明确欢迎 negative results）。

### 6. 「被追上」的定义需要精确化

必须区分三种「被追上」：
1. **能力被追上**（某工具在阙疑的任务上做得更好）——**几乎必然发生，6 个月内**；
2. **方法被追上**（有人做出同构的「可审计验证器」）——**12–18 个月内概率约 30%**；
3. **优先权被剥夺**（有人在阙疑之前发表同构工作并获认可）——**概率 < 10%**，因为目前公开检索未见同构项目。

**结论**：阙疑真正的风险是 (1)，而 (1) 对论文发表**不致命**——E&D track 明确写着「Submissions need not introduce a new model or outperform prior work」（见 NeurIPS 2026 E&D CFP）。**这意味着「被追上」在 E&D track 的评审语境里不是拒稿理由。**

### 7. 历史类比：单人 / 小团队项目的窗口期有多长

要判断「12–18 个月够不够」，最好的参照是**历史上同类项目的窗口期实测**。

**（A）正面案例：单人 / 小团队在「评测方法论」上占位成功。**

- **SWE-bench（2023-10 首发）**：由普林斯顿团队（Carlos E. Jimenez 等）提出，用真实 GitHub issue 做代码修复评测。它在 **2024 年成为事实标准**，被 OpenAI、Anthropic、Google 等所有主要厂商写进技术报告。**从发布到成为标准，约 12 个月。**
- 但注意：SWE-bench 的护城河**不是方法本身**（评测代码是开源的，谁都能跑），而是**「所有人都在用同一个数字」这一网络效应**。而网络效应一旦形成，就极难被推翻——这就是为什么 OpenAI 在 **2026-04 宣布 SWE-bench Verified「退役」**时，必须先推出替代品（Scale AI 的 SWE-bench Pro 于 2025-09 发布）。
- **对阙疑的启示**：**12 个月是「成为被引用标准」的典型周期**。阙疑如果不能在 2027-09 前让至少 3 个独立团队引用其 holdout 或对账协议，窗口就基本关闭。

**（B）负面案例：被更大玩家「顺手覆盖」。**

- **可复现性工具（如 DVC、MLflow）**：这些工具在 2019–2021 年被大量讨论，但当云厂商（AWS SageMaker、Azure ML、GCP Vertex AI）把「实验追踪」内置为平台功能后，独立工具的生存空间被大幅压缩。
- **对阙疑的启示**：**如果 OpenAI / Anthropic 在 2027 年把「可验证输出 + 审计日志」做成 API 的默认能力，阙疑的 L1 与部分 L2 会在一个季度内失效。** 这是悲观情景的核心机制。

**（C）「数据集 + 协议」类项目的特殊窗口。**

- 对比 **CASTLE（arXiv:2503.09433，2025-03）**：它用 250 条手工构造的 micro-benchmark 评测 13 个静态分析工具 + 10 个 LLM + 2 个形式化验证工具。CASTLE 的价值**不在工具，而在「所有人都得跑它来比较」**——即**评测基准的护城河 = 被采纳为对照组的程度**。
- **对阙疑的启示**：**阙疑的 30 条 holdout 太小，不足以成为「对照基准」；但它的「独立对账协议」有潜力成为对照流程。** 这是 12–18 个月里唯一值得全力投入的方向。

**（D）时间窗口的量化总结**

| 资产类型 | 从发布到被覆盖的典型时间 | 依据 |
|---|---|---|
| 密码学基础设施（哈希链 / Merkle） | **0 天**（本就是公开标准） | RFC 6962 |
| 验证能力（模型 / 框架） | **3–6 个月** | LLM-as-a-Verifier 迭代速度 |
| 评测方法 / 协议 | **12–18 个月** | SWE-bench 的经验 |
| 已 reveal 的盲数据集 | **不可覆盖**（一次性资产） | reveal 不可逆 |
| 制度性地位（被写入标准 / 法律） | **24–48 个月** | EU AI Act 时间表 |

**结论**：**阙疑在 12–18 个月里唯一「跑得赢」的赛道是「协议」与「数据集」；「能力」与「基础设施」两条赛道必然输。** 因此论文定位必须收缩到前两条。

## 对阙疑的 3 条具体行动

**行动 1：立即做「竞品雷达」并固化为每季度一次的机器检查。**
- 具体做法：新建 `tools/competitor_radar.py`，每季度抓取 GitHub API 上关键词（`verifier`、`audit trail`、`merkle`、`C++ UB`、`undefined behavior benchmark`）的新仓库数与 star 增速，输出 `_arch_v46/competitor_snapshot_YYYYQN.json`。
- 触发阈值：若出现「同时含 merkle + C++ + benchmark」的仓库 star > 500，立即升级应对。
- 时间点：本季度内（2026-12 前）跑第一次。

**行动 2：把 holdout 扩样写成「可执行的季度计划」，对冲 benchmark 饱和。**
- 具体做法：在 `data/holdout/` 下建立 `holdout_expansion_plan.md`，规定每 6 个月 +10 条新盲样本（真错比例维持 ≥ 50%），并记录每次扩样的 `reveal` 时间戳。
- 依据：benchmark saturation 论文（arXiv:2602.16763）实测 24 个月内 42.9% 饱和——**扩样是唯一被验证的抗饱和手段**。
- 时间点：2027-03 前完成第一次扩样（30→40），投稿时 holdout ≥ 40。

**行动 3：把论文定位从「我们做得更好」改写为「我们定义了如何独立验收」。**
- 具体做法：修改 `research/paper_v0.3.md` 的 Abstract 与 Contributions，删掉任何暗示「比 LLM 更准」的表述，改为「提出并验证一套可被第三方独立复算的验收协议」，并引 NeurIPS 2026 E&D CFP 的「evaluation becomes an object of scientific study in its own right」作为定位依据。
- 理由：**能力竞赛阙疑必输，协议定义权是唯一可赢的战场。**
- 时间点：投稿前 2 个月。
