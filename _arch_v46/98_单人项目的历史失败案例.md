# 方向 98：单人项目的历史（失败案例）

> 服务对象：双非本科（合肥、嵌入式、2026-09 起读大三、考研初试约 2027-12、毕业 2028-06）
> 项目锚点：**阙疑 / queyi** —— 「可被独立验收」的 C++ 知识验证器
> 精确锚点：**37 实卡**（verified 23 / red-team 3 / draft 11）+ 10 草稿；**67 规则**（block 44 / warn 16 / advice 7）；`tools/gate_engine.py` = **3826 行**；盲 holdout **30 seeds**（真错 17），检出 **66.7%**（10/15 可测）；外部 corpus **40 条**（43.8%）；缺陷夹具 **15 条**（重注入 6/6 = 100%）；反事实算子 **P=R=F1=0**。

---

## 核心结论

1. **单人项目最常见的死法不是"技术不行"，而是三种非技术死因：① 维护者耗尽（burnout）；② 单点信任被利用（供应链攻击 / 恶意接管）；③ 治理缺失导致"一个人能一键毁掉所有人的构建"**。本方向 12 个案例里，**有 6 个直接属于这三类**（xz、left-pad、colors.js、event-stream、core-js、OpenSSL）。→ **阙疑作为"单人 + 大量下游依赖假设"的项目，这三类风险全部适用，且你现在**没有任何一项**防护措施（无 LICENSE 治理说明、无 CODEOWNERS、无 release 流程、无资助来源）。

2. **"死"有两种：猝死（一次事故）和慢死（十年不发版）**。猝死的案例（left-pad 2016、colors.js 2022、event-stream 2018、TrueCrypt 2014）**共同点是"没有第二个人 + 没有治理规则"**；慢死的案例（GNU Hurd 1990–2026、Mochizuki 2012–2025）**共同点是"作者拒绝外部输入"**。→ **阙疑的两个具体风险：① 猝死风险来自"你一个人握着所有东西"（你的 3826 行内核 + 452 条账本 + 全部规则）；② 慢死风险来自"你的 0 影响力 = 没有外部输入"**——这正是 Mochizuki 的翻版：**一个人写、一个人信、一个人审。**

3. **最刺痛的一条：本方向 12 个案例里，有 3 个"失败"其实是"作者太累而放弃"，而放弃前的共同征兆是"作者公开抱怨没人资助"**（core-js 的 Denis Pushkarev 2023-02、OpenSSL 的 Steve Marquess 2014、以及 Tidelift 2024/2025 调查中 **44% 的维护者把 burnout 列为离开原因**）。→ **对你而言最现实的止损信号不是"论文被拒"，而是"你开始觉得维护阙疑是负担而不是乐趣"。这条信号一旦出现，且持续 ≥2 个月，就应按本方向第 3 条行动执行"降级归档"。**

## 精确数字与案例

### 案例 1：xz utils 后门（CVE-2024-3094，2024）——"维护者 burnout 是攻击面"

- **时间线**：**2021 年起**，一个化名 **"Jia Tan"** 的贡献者开始向 xz utils 提交代码；**2024 年 3 月 29 日**，微软 PostgreSQL 开发者 **Andres Freund** 在 oss-security 邮件列表公开披露后门。
- **受害者结构（关键）**：xz utils **"had long been maintained largely by one volunteer, Lasse Collin"**（长期主要由一个志愿者维护）。Jia Tan 用**约两年时间**逐步获取信任，最终获得提交权限，在 **v5.6.0 / v5.6.1** 中植入恶意代码，目标是**替换 OpenSSH 的部分行为**。
- **官方善后**：Tukaani 项目发布官方说明（`tukaani.org/xz-backdoor/`），明确 **"Jia Tan only had access to things hosted on GitHub"**，并做了权限收缩。
- **教训（三条，逐条对应阙疑）**：① **单人维护 = 信任可以被"慢慢养"出来**——阙疑若未来接受外部 PR，**必须建立"提交者权限分级 + 关键路径双人 review"**；② **约 2 年的社会工程期**意味着**任何"热心长期贡献者"都要做身份核验**；③ **项目的关键路径（构建脚本）被改动时必须有独立复算**——这正是阙疑"独立对账器"要解决的同类问题，**但阙疑自己的构建脚本没有对账**。

### 案例 2：left-pad 下架事件（2016-03-22）——"11 行代码毁掉上千个构建"

- **时间**：**2016 年 3 月 22 日**。
- **起因**：作者 **Azer Koçulu** 发布了一个名为 `kik` 的 npm 包，与同名公司 Kik Interactive 产生名称争议；npm 管理层将 `kik` 包名判给该公司。Azer 愤而**下架了自己在 npm 上的全部包**，**共 273 个包**，其中包括被广泛依赖的 `left-pad`。
- **后果**：**Babel、React Native、Ember 等大量工具的构建失败**；社区报道称"**上千个项目崩溃**"。npm 随后**恢复了 left-pad**，并**修改政策：已发布的版本不可撤销（unpublish 限制）**。
- **教训**：① **"一个人可以一键删除所有人依赖的东西"是系统性风险**；② **修复方式不是道德劝说，而是政策（不可撤销发布）**；③ **阙疑含义**：你的 **append-only 哈希链**在设计上恰好对应"不可撤销"这一原则——**这是一个可以写进论文的、有历史事故背书的强论点**（"为什么验证证据必须 append-only"）。

### 案例 3：colors.js / faker.js 恶意破坏（2022-01）——"作者主动投毒"

- **时间**：**2022 年 1 月**（Bleeping Computer 于 **1 月 9 日**首发报道）。
- **作者**：**Marak Squires**。
- **行为**：主动把自己维护的两个高依赖包 **`colors.js` 与 `faker.js` 改成破坏性代码**——`colors.js` 被改为**无限循环 + 输出乱码**，导致依赖它的程序**卡死或输出垃圾**；`faker.js` 被清空。此类行为后来被命名为 **"protestware"（抗议性软件）**。
- **后果**：**数千个 npm 项目被破坏**；Sonatype 等安全公司当日发布紧急通告。
- **教训**：① **"作者情绪"是供应链的单点故障**，且**无法通过技术手段完全防御**；② 社区应对是**fork + 托管迁移**（`faker.js` 后来由社区以 `@faker-js/faker` 延续）；③ **阙疑含义**：**如果你的项目未来有下游使用者，必须提前声明"治理与继任计划"**（谁在你消失后接管、规则库的许可证、数据的托管地）。**这份声明本身就是 E&D track 认可的"responsible dataset/tool development"的一部分**。

### 案例 4：event-stream / flatmap-stream 后门（2018-11）——"善意交接导致比特币被窃"

- **时间**：**2018 年 11 月**。
- **链条**：`event-stream` 是**周下载量数百万**的 npm 包；原维护者 **Dominic Tarr** 因"不再使用该包"，把发布权限**交给了自称愿意维护的陌生人 "right9ctrl"**。该人随后添加依赖 **`flatmap-stream@0.1.1`**，其中包含**针对 Copay 比特币钱包的窃取代码**。
- **影响规模**：中文安全媒体口径为**影响 2000 万次下载**（⚠️ 口径未核实）；受害产品是 **Dash Copay**（比特币钱包）。
- **修复**：Snyk 等发布 post-mortem；建议**降级到 event-stream@3.3.4 或升级 flatmap-stream@0.1.2**。
- **教训**：① **"维护权交接"是比"写代码"更高危的动作**；② **依赖链上的任何一层都可能被投毒**；③ **阙疑含义**：如果阙疑未来把某个子模块（如"外部 corpus 维护"）交给别人，**必须保留"独立对账"能力**——**这正是阙疑架构里最值钱的一条设计**。

### 案例 5：core-js 维护者 burnout（2023-02）——"扛着半个互联网的人要走了"

- **时间**：**2023 年 2 月 14–16 日**（InfoQ、腾讯新闻等集中报道）。
- **作者**：**Denis Pushkarev**（单人长期维护 **9 年**）。
- **规模（精确数字）**：`core-js` **月均 npm 下载量约 2.5 亿次**；**全球 TOP 1000 网站中超过半数使用**；被描述为"**用于 2.5% 的所有网站**"。
- **作者原话（关键）**：他"**准备放弃开源开发**，因为很少有人为他们所依赖的东西付钱"；并提到"**除了常见的威胁、指责、要求和侮辱，我还经常听到类似'别搁这要饭了，找个班上'之类的话语**"，且这些说这话的人中"**有很多人年收入超过 30 万美元**"。
- **教训**：① **"被依赖"和"被资助"完全不相关**（这直接呼应 Tidelift 数据：只有 **3%** 的维护者从开源基金会获得过收入）；② **burnout 的触发点是"被辱骂"而非"被忽视"**；③ **阙疑含义**：**不要指望阙疑带来收入**（对应方向 87/99），并且**要在开始对外传播前就设好"评论过滤器"**（例如关闭无意义 issue、不在社交媒体上回应挑衅）。

### 案例 6：OpenSSL / Heartbleed（2014-04-07）——"500,000 行关键代码，1 个全职 + 3 个志愿者"

- **时间**：**2014 年 4 月 7 日**公开披露并修复。
- **根本原因（精确）**：一个 **2012 年**的补丁（作者 Robin Seggelmann）**漏掉了对长度变量的校验**；该补丁被一名 OpenSSL 核心开发者 review 过，但 review 目的是"验证功能改进"，**不是安全审计**。
- **资源状况（最触目惊心的数字）**：
  - **只有 1 人（Stephen Henson）全职**工作于 OpenSSL，另有 **3 位核心志愿者**；Henson "**批准了 45 万行以上源码中一半以上的更新**"；
  - OpenSSL 项目**年度捐赠收入约 2,000 美元**（"够付电费"），Henson 年收入**约 2 万美元**；
  - OpenSSL Software Foundation 年收入**不足 100 万美元**，且合同工作**偏向加新功能而非维护旧代码**；
  - 受影响范围：当时**约 17%（约 50 万台）**经可信机构认证的互联网安全 Web 服务器被认为存在漏洞；
  - **Heartbleed 披露后 2–3 天内的捐款总额仅 841 美元**（Dan Kaminsky 评论："**我们正在用令人震惊地资金不足的基础设施，构建全球经济最重要的技术。**"）
- **行业反应**：**2014 年 4 月 24 日** Linux 基金会成立 **Core Infrastructure Initiative（CII）**，**13 家公司**（AWS、Cisco、Dell、Facebook、Fujitsu、Google、IBM、Intel、Microsoft、NetApp、Rackspace、Qualcomm、VMware）**各承诺每年捐 10 万美元、持续 3 年**，初始资金池**近 400 万美元**；CII 资助了 **2 名全职 OpenSSL 核心开发者**。
- **后续治理（可复制的机制）**：Tim Hudson 在 2024 年重组 OpenSSL 治理，**"instituted that no code can go in the code base without two people reviewing it and signing off"（任何代码入库必须两人 review 并签字）**；OpenSSL 拆分为"基金会（面向个人/学术/研究者）+ 公司（面向商业客户）"两个平行组织。
- **教训**：① **"足够多的眼睛"（Linus's Law）在现实中不成立**——Eric Raymond 本人承认 Heartbleed "**there weren't any eyeballs**"；② **单人/极小团队维护关键基础设施是系统性风险，不是个人道德问题**；③ **阙疑含义**：**"两人 review + 签字"是一个可以在 2026 年就落地的、成本极低的治理动作**（见行动 1）。

### 案例 7：GNU Hurd（1990–2026）——"36 年不发版"的慢死

- **起点**：GNU 项目从 **1990 年**起开发 Hurd（基于 GNU Mach 微内核）。
- **状态（2026）**：**依然存在，"在少数贡献者的努力下缓慢前行"**；**从未成为主流**；Linux 在 1991 年出现后彻底占据了这个位置。
- **死因**：**范围无界（"面向对象的多服务器微内核"）+ 无明确交付时间 + 设计不断演进**（"使得它不断发展而不用改变当前的设计"）。
- **教训**：① **"设计得好"不能替代"交付"**；② **没有 deadline 的项目会被有 deadline 的项目杀死**；③ **阙疑含义**：**必须给自己设一个不可协商的"交付日期"**——本方向建议 **2027-05-06（NeurIPS 2027 E&D 外推 deadline）**，**无论完成度如何都要投出去**（对应方向 17/100）。

### 案例 8：Mochizuki ABC 猜想（2012–2025）——"单人 + 拒绝外部输入 = 13 年悬案"

- **起点**：**2012 年 9 月**，京都大学 **望月新一（Shinichi Mochizuki）** 发布 **500 页**的 ABC 猜想证明（Nature 2012-09-10 报道）。
- **争议过程**：**2018 年** Peter Scholze 与 Jakob Stix 指出关键步骤存在"**致命漏洞**"；望月**拒绝修改、拒绝离开自己的期刊体系**；**2020 年他的论文在自己任编辑的期刊 PRIMS 上被接收**；**2024 年 3 月**《New Scientist》报道数学界"**激烈分裂**"；**2025 年 5 月**出现《Final Report on the Mochizuki-Scholze-Stix Controversy》（arXiv:2505.10568）；**2025 年 6 月**仍有媒体讨论"**只在日本才成立的数学证明**"。
- **死因**：**不是证明一定错，而是"无法被共同体独立验收"**。
- **教训（对阙疑最直接的一条）**：**"可被独立验收"不是学术品味，而是"成果能否被承认"的唯一通道**。望月的证明若一开始就配套"可被独立复算的验证脚本"，争议不会持续 13 年。→ **阙疑的"独立对账器 + 哈希链"就是针对这个失败模式的直接对策，应该把 Mochizuki 作为论文 Introduction 的动机案例。**

### 案例 9：Vinay Deolalikar 的 P≠NP 证明（2010-08）——"两周内崩盘"

- **时间**：**2010 年 8 月 6–8 日**，HP Labs 研究员 **Vinay Deolalikar** 向多位数学家发送了一份**百余页**的论文，宣称证明了 **P ≠ NP**。
- **结果**：**在数周内**，多位研究者（含 Neil Immerman、Scott Aaronson 等）指出**致命缺陷**——其论证使用了**有限模型论**中的结果，但这些结果**无法给出所需的"非单调性"**；证明**未能跨过相对化障碍**。
- **教训**：① **"宣称大结果"如果缺少"可被独立复算的中间步骤"，会在数周内崩盘**；② **社区会立刻组织"验证冲刺"**——**这既是风险也是机会**：如果你的结果**真的可复算**，社区的验证冲刺会变成你的放大器；③ **阙疑含义**：**投稿前必须自己先跑一遍"红队式复算"**（你已有 `red-team-verified 3` 卡，应扩到全部规则）。

### 案例 10：TrueCrypt 突然终止（2014-05-28）——"匿名团队 + 无继任计划"

- **时间**：**2014 年 5 月 28 日**。
- **行为**：项目**匿名开发者**突然把 `truecrypt.org` 官网跳转到 SourceForge 项目主页，**宣布终止开发**，并把页面替换为"**TrueCrypt 不再安全**"的警告，建议 Windows 用户改用 BitLocker、Mac 用户**不加密**（**完全没有提到 Linux**）。
- **后果**：后续安全审计**发现了若干问题**；社区被迫 fork（如 VeraCrypt）。
- **教训**：① **"匿名 + 无继任"= 项目随时可被一键终结**；② **官方警告的措辞会直接造成用户恐慌**（"不再安全"这句话的杀伤力远超漏洞本身）；③ **阙疑含义**：**即使你不想公开身份，也必须留下"继任机制"**——至少是 **LICENSE + 数据托管地 + 规则格式的公开规范**，让任何人可以在你消失后接管。

### 案例 11：Diaspora（2010–2012）——"融资成功 ≠ 交付成功"

- **时间**：**2010 年 5 月**发起 Kickstarter 众筹，**6 月 2 日**结束。
- **数字**：**筹得约 20 万美元，来自近 6,500 名支持者**（TechCrunch 2010-06-02）。
- **团队**：**四名纽约大学（Courant 研究所）计算机科学学生**。
- **承诺 vs 现实**：TechCrunch 当时就写道"**While Diaspora has plenty of money, they have yet to make the actual Facebook alternative site**"（钱够了，但产品还没有）。项目**始终未交付可用的"Facebook 替代品"**，2012 年后实质消亡。
- **教训**：① **"钱"不是瓶颈，"把东西做出来"才是**；② **过度承诺（"Facebook killer"）会在交付不足时反噬**；③ **阙疑含义**：**不要在论文/README 里用"取代 X"的表述**（对应方向 19 的 overclaim 问题）。**应写成"针对 Y 场景提供一个可独立验收的评估协议"**。

### 案例 12：moment.js 进入维护模式（2020-09）——"软性死亡"

- **时间**：**2020 年 9 月**，维护者宣布项目进入 **"legacy project in maintenance mode"（遗留项目 / 维护模式）**。
- **状态**：**"It is not dead, but it is indeed..."**（官方文档口径）；**2026 年 8 月**官方再次更新状态（距上次状态更新**已近六年**）。
- **影响**：作为曾经的日期库事实标准，**大量项目仍依赖它但无人推进**。
- **教训**：① **"维护模式"是一种体面的死亡方式**，比猝死好；② **它需要一次明确的官方声明**（否则用户会一直以为在活跃开发）；③ **阙疑含义**：**如果决定止损，请发一份正式的"项目状态声明"**（写明：支持范围、最后验证日期、如何复算、是否接受 PR）——**这本身就是对社区负责的学术行为**。

### 量化背景：维护者群体的整体状况（Tidelift 调查）

- **Tidelift 2024 年开源维护者状况报告**（基于 **400 多名**维护者调查）：
  - **约 45% 的维护者没有报酬**（OSCHINA 2024-09-19 口径）；
  - **只有 3% 的维护者**表示曾从开源基金会获得过收入（BusinessWire 2024-09-17 口径，且"**这一比例一直没变**"）；
  - 付费维护者比未付费维护者**做了明显更多的关键安全与维护工作**。
- **2025 年数据**（byteiota，2025-12-26 口径）：**60% 的维护者无报酬**；**44% 的人把"burnout"列为离开的原因**。
- ⚠️ **以上均为第三方转述 Tidelift 调查，未读原始 PDF 逐页核对**；2025 年数据来自二手技术博客，**可信度更低**。

### 把 12 个案例压成"死因表"

| 死因类别 | 案例 | 阙疑是否已有防护 |
|---|---|---|
| 维护者 burnout / 无报酬 | core-js、OpenSSL、xz（诱因） | ❌ 无 |
| 单点信任被利用（供应链） | xz、event-stream | ❌ 无 |
| 治理缺失（一人可毁全部） | left-pad、colors.js、TrueCrypt | ❌ 无 |
| 范围无界 / 无 deadline | GNU Hurd | ⚠️ 有"100 方向"的扩散倾向 |
| 拒绝外部输入 | Mochizuki | ❌ 0 影响力 = 无外部输入 |
| 中间步骤不可复算 | Deolalikar | ✅ **有独立对账器（唯一已具备的防护）** |
| 融资 ≠ 交付 | Diaspora | ✅ 无外部资金（反而是优势） |
| 过度承诺 | Diaspora | ⚠️ 需检查论文措辞 |

→ **结论：8 类死因里，阙疑只对 1 类有防护。这个数字应该被写进你的风险评估。**

## 对阙疑的 3 条具体行动

1. **本周内落地"两人 review + 签字"机制（照抄 OpenSSL 2014 年后的治理）**：
   - **落地物**：在仓库根目录新建 `GOVERNANCE.md`（**本方向不改仓库，仅给建议**），写明三条：① **任何修改 `tools/gate_engine.py` 或 `data/_gate_rules.json` 的提交，必须有两个独立身份 review 并签字**；② **规则变更必须附"复算脚本 + 变更前后检出率对比"**；③ **指定一名继任者**（哪怕只是"若作者失联 6 个月，则本项目规则格式由社区按 `SCHEMA.md` 接管"）。
   - **最低成本实现**：用 GitHub **CODEOWNERS + 分支保护规则**（要求 1 个 approve 才能 merge）——即使你现在只有自己，**开启分支保护也能防止"手滑直推 master"**（你的工作树已有 **227 项漂移**，这本身就是"无流程"的证据）。
   - **时间点**：2026-10-31 前完成。
   - **验收**：`git log` 中 `master` 不再有直接推送的规则变更提交。

2. **把"三类失败模式"写进论文的 Threats to Validity，并给每一项配一个已实现的机制**：
   - **写法**（建议文本，进 `research/12_threats_to_validity.md`）：
     - **Single-maintainer risk** → 对策：**append-only 哈希链 + 独立对账器**（保证即使作者行为异常，历史证据不可篡改、可被第三方复算）；
     - **Trust concentration** → 对策：**规则与引擎分离**（规则在 `_gate_rules.json`，引擎在 `gate_engine.py`，任何规则变更留下可 diff 的证据）；
     - **Irreproducibility** → 对策：**Merkle checkpoint + 一键复算**（对应方向 43）。
   - **加分点**：引用 **left-pad（2016）** 与 **xz（2024）** 作为"为什么 append-only 是必需的"的历史论据——**这是把工程细节升级为学术动机的最短路径**。
   - **时间点**：2026-11-30 前完成这一节。

3. **设"burnout 止损线"并写下来（本方向最重要的一条）**：
   - **量化信号（任一触发即进入评估）**：① 连续 **2 个月**每周投入阙疑时间 **< 3 小时**且**没有愧疚感**；② 对"打开 `_arch_v46/`"产生**回避情绪**且持续 **≥3 周**；③ 收到外部负面评论后**情绪影响超过 48 小时**。
   - **触发后的动作（不是放弃，是降级）**：发布 `STATUS.md`（照抄 moment.js 的"maintenance mode"声明），内容：**支持范围 / 最后验证日期 / 如何复算 / 是否接受 PR / 继任安排**；然后把项目转为"**只维护不扩展**"（停止新增方向文档，保留 CI 与复算能力）。
   - **为什么这么做**：**44% 的维护者因 burnout 离开**（Tidelift 2025 口径），而**体面降级（moment.js 模式）比猝死（left-pad / TrueCrypt 模式）对你自己和对使用者都好得多**。
