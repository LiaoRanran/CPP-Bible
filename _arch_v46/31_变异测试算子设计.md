# 方向 31：变异测试算子设计（具体算子列表）

> 调研日期：2026-09-29　联网搜索 16 次　WebFetch 6 次（含 3 份 PDF 原文全文提取）
> 锚点：阙疑 / queyi（C++ 知识验证器，67 条判决规则，block 44）；本文所有数字均以 `00_仓库扫描.md` 实测口径为准。

## 核心结论

1. **变异得分（mutation score）只有在"算子集合被显式声明"时才有意义**：同一个被测程序，用 5 个充分算子（ABS/UOI/LCR/AOR/ROR）与用 42 个 Mull `cxx_all` 算子，得到的分数可以相差数十个百分点。阙疑对外报的 **core 97.3% / all 81.5%** 若不附算子清单，在 NeurIPS E&D 审稿人眼里是不可复核数字。
2. **C++ 的变异算子必须显式处理"编译错误"与"等价变异"两类污染**：Google 的工程实践证明，未做 arid node（贫瘠节点）抑制时，约 **72.18%** 的变异体来自 SBR（语句块删除），而其中大量变异体会直接导致编译失败或语义等价；C++ 特有的 `nullptr`/`false` 等价、`for` 循环 `<`→`!=` 等价都必须单独屏蔽。
3. **2024–2025 年的新证据表明"传统算子"与"LLM 生成变异体"是互补而非替代**：LLMorpheus（2024）用 codellama-34b 生成 **6,712** 个变异体，其中 **63.2%** 的存活变异体是非等价的行为差异（StrykerJS 为 **73%**），且能产出传统算子**根本无法生成**的、与真实 issue 对应的变异（如 `fs.constants.R_OK|W_OK` → 只保留 `W_OK`）；而 MOTIF-C++（2025）证明在 C/C++ 上 fuzzing 驱动可平均杀死 **88.7%** 的变异体。

## 精确数字与案例

### 1. 算子分类的三条正统谱系：Mothra → Offutt 充分算子 → 工业工具

**（A）Mothra（FORTRAN，22 个算子）**——最早的系统化算子集，SFU CMPT-473 课程页（2026-01-09 更新）逐条列出：

```
AAR 数组引用替换    ABS 绝对值插入      ACR 数组引用→常量   AOR 算术运算符替换
ASR 数组引用→标量   CAR 常量→数组引用   CNR 同类数组名替换  CRP 常量替换
CSR 常量→标量       DER DO 语句结尾替换 DSA DATA 语句改动   GLR GOTO 标签替换
LCR 逻辑连接符替换  ROR 关系运算符替换  RSR RETURN 语句替换 SAN 语句分析
SAR 标量→数组引用   SCR 标量→常量       SDL 语句删除        SRC 源常量替换
SVR 标量变量替换    UOI 一元运算符插入
```

其中 **AOR/ROR/LCR/SDL/ASR/UOI** 六个缩写即今天所有工业工具仍在用的命名祖源。

**（B）Offutt 等人 1996 的"充分算子"结论**——A. Jefferson Offutt, Ammei Lee, Gregg Rothermel, Roland H. Untch, Christian Zapf，*"An Experimental Determination of Sufficient Mutant Operators"*，**ACM TOSEM 5(2): 99–118, 1996**，DOI **10.1145/227607.227610**。结论：在 Mothra 的算子里，**ABS、UOI、LCR、AOR、ROR** 这 5 个（全部来自"操作数类 + 表达式类"）构成**充分集**，可达约 **99.5%** 的变异得分（该 99.5% 由 dextool 官方设计文档转引，见来源 [3]）。这就是**5-selective mutation**（5 选择变异）的理论依据，也是 Google 生产系统的算子子集基础。

**（C）工业实现的三套现成算子集**（可直接作为阙疑的对标基线）：

| 工具 | 语言 | 算子规模 | 分组机制 |
|---|---|---|---|
| **Mull** | C/C++（LLVM/Clang AST） | **42 个 `cxx_*` 算子**（+`negate_mutator`），归入 **15 个组名** | `cxx_all` / `cxx_default` / 细分 11 组 |
| **PIT (pitest)** | Java/JVM（字节码层） | **29 个 mutator**，含 `AOR_1..AOR_4`、`ROR1..ROR5`、`UOI1..UOI4`、`CRCR1..CRCR6`、`AOD_1..AOD_2`、`OBBN1..OBBN3` 子算子 | `OLD_DEFAULTS` / `DEFAULTS` / `STRONGER` / `ALL` |
| **Stryker** | JS / .NET / Scala | 官网原文"**Control more than 30 supported mutations**"；支持表列 **16 类**（Arithmetic/Array/Assignment/Block/Boolean/Checked/Conditional/Equality/Logical/Method/Object/Optional-chaining/Regex/String/Unary/Update） | 跨语言统一命名方案 |

### 2. Mull 的 42 个 C++ 算子（逐条列出，阙疑可直接抄成对标表）

以下为 `mull-project.com/reference/mutators/` 原文全量（按官方 15 个组归并）：

- **算术（cxx_arithmetic，6）**：`cxx_add_to_sub`（`+`→`-`）、`cxx_sub_to_add`、`cxx_mul_to_div`、`cxx_div_to_mul`、`cxx_rem_to_div`（`%`→`/`）、`cxx_minus_to_noop`（`-x`→`x`）
- **算术赋值（cxx_arithmetic_assignment，5）**：`cxx_add_assign_to_sub_assign`、`cxx_sub_assign_to_add_assign`、`cxx_mul_assign_to_div_assign`、`cxx_div_assign_to_mul_assign`、`cxx_rem_assign_to_div_assign`
- **位运算（cxx_bitwise，6）**：`cxx_bitwise_not_to_noop`（`~x`→`x`）、`cxx_and_to_or`、`cxx_or_to_and`、`cxx_xor_to_or`、`cxx_lshift_to_rshift`、`cxx_rshift_to_lshift`
- **位运算赋值（cxx_bitwise_assignment，5）**：`cxx_and_assign_to_or_assign`、`cxx_or_assign_to_and_assign`、`cxx_xor_assign_to_or_assign`、`cxx_lshift_assign_to_rshift_assign`、`cxx_rshift_assign_to_lshift_assign`
- **比较（cxx_comparison，6）**：`cxx_eq_to_ne`、`cxx_ne_to_eq`、`cxx_le_to_gt`、`cxx_lt_to_ge`、`cxx_ge_to_lt`、`cxx_gt_to_le`
- **边界（cxx_boundary，4）**：`cxx_le_to_lt`、`cxx_lt_to_le`、`cxx_ge_to_gt`、`cxx_gt_to_ge`
- **常量赋值（cxx_const_assignment，2）**：`cxx_assign_const`（`a=b`→`a=42`）、`cxx_init_const`（`T a=b`→`T a=42`）
- **调用（cxx_calls，2）**：`cxx_remove_void_call`（删除返回 void 的调用）、`cxx_replace_scalar_call`（调用→`42`）
- **自增（cxx_increment，2）**：`cxx_pre_inc_to_pre_dec`、`cxx_post_inc_to_post_dec`
- **自减（cxx_decrement，2）**：`cxx_pre_dec_to_pre_inc`、`cxx_post_dec_to_post_inc`
- **逻辑（cxx_logical，1）**：`cxx_remove_negation`（`!a`→`a`）
- **实验（experimental，1）**：`negate_mutator`（`!x`↔`x` 条件取反）

**关键观察**：Mull **没有** Mothra 的 ABS（绝对值插入）、SDL（语句删除）、CR（常量替换的完整版）；它的 `cxx_assign_const` 硬编码成 `42`。因此如果阙疑声称"对标 Mull"，其算子集与 PIT/Stryker 不同构，**不能跨工具比分数**。

### 3. Google 生产系统的实测数据（ICSE-SEIP'18，全文已提取）

**论文**：Goran Petrović, Marko Ivanković（Google Inc.），*"State of Mutation Testing at Google"*，**ICSE-SEIP '18**，DOI **10.1145/3183519.3183521**。核心数字（原文）：

- 数据规模：**1,159,723 个变异体**，覆盖 **7 种语言**（C++/Java/Python/Go/JavaScript/TypeScript/Common Lisp）；分析 **72,425 个 diff**；产生 **150,854 条 actionable findings**；其中 **11,049 条**获得开发者反馈。
- 使用者：**6,000 名工程师**，影响 **13,000+ 名代码作者**；处理 Google 全量"有语句覆盖统计"diff 的约 **30%**；约 **15%** 的语句覆盖计算会失败。
- 用的算子**只有 5 个**：`AOR`、`LCR`、`ROR`、`SBR`（语句块删除）、`UOI`；原文明确"**The ABS (absolute value insertion) mutator was reported predominantly not useful**"，被弃用。
- 变异体分布：**SBR 占 72.18%**（829,999）、UOI 17.19%（197,776）、ROR 4.48%（51,574）、LCR 4.46%（51,360）、AOR 1.69%（19,448）。
- 存活率（= 1 − 变异得分）：整体 **>87% 的测试运行失败（即杀死）**；分语言存活率 **Java 13.2% / C++ 11.7% / Python 14.7% / Go 14.0% / JavaScript 13.1% / TypeScript 8.3% / Lisp 1.0%**。**C++ 存活率 11.7% 是七种语言里第二低**，原文归因于"编译型语言中一整类缺陷会被编译器直接拦下"。
- 分算子存活率：**LCR 最"顽固"（15%）**，SBR 12.9%，AOR 11.8%；极端格：TypeScript AOR **22.727%**（最顽固），Lisp UOI **0.740%**（最易杀）。
- 有用性反馈：**75% 的反馈型 findings 被开发者判为有用**；按算子 **LCR 87.39% > UOI 80.92% > ROR 78.79% > SBR 74.72% > AOR 61.76%**；按语言 Java 83.1% > C++ 78.84% > TS 71.43% > Py 71.23% > Go 65.96% > JS 59.26%。系统通过 arid node 抑制把"非可行动结果"从 **20% 降到 25%（原文：usefulness improved from 20% to 80%）**。
- 每个 diff 的存活变异体中位数 **2 个**，**99 分位 43 个**。
- **C++ 专属 arid 规则（原文附录 A.2.1）**：`if (x != nullptr)` 的 LCR 变异到 `if (x)`/`if (nullptr)`/`if (false)`/`if (true)` 会产生**等价变异**（因 `nullptr` 为假值），被抑制；标签语句、声明、非赋值的二元运算符（SBR 会引发编译错误）被抑制；if 块被删除时替换为**空块**以避免编译错误。

> 这段是**阙疑最应该抄的工程细节**：它给了"C++ 下哪些变异必须屏蔽"的官方清单，且带 Google 内部验证。

### 4. dextool mutate 的算子语义（C++ 逐条替换规则）

`joakim-brannstrom.github.io/dextool/plugin/mutate/doc/design/mutations.html` 给出 11 个算子的**精确替换集合**，并显式引用 Offutt 的三分类（statements / operands / expressions）：

- **ROR**：操作数集合 `<, <=, >, >=, ==, !=, true, false`，采用 **RORG（全局）**；按类型分 `ROR for Booleans / Floating Points / Enumerations / Pointers`。原文注明：枚举变异必须避免生成"枚举范围外的值"，因为在 C/C++ 中是 **UB**。
- **AOR**：`+, -, *, /, %` 互替，**共 5×4 = 20 种**；**AORs** 简化版只做逆运算（`+`↔`-`、`*`↔`/`、`%`→`/`）。
- **LCR**：替换为反运算符，并额外替换为 `true`/`false`/`x`/`y`（后 4 项引自 Google 2018）。
- **LCRb**：只针对按位 `&`/`|`。
- **UOI**：`++x, x++, --x, x--, &x, *x, +x, -x, ~x, !x, sizeof x, sizeof(type)`（显式忽略 cast）；文档坦白"**实际实现只对 `!` 做移除处理，并未完全实现学术定义**"。
- **ABS**：`abs(e)`、`-abs(e)`、`fail_on_zero(e)`；**整数常量不变异**（易生等价变异体）。
- **COR**（条件运算符替换）：**已被移除**，因为产生过多"垃圾"变异体。
- **SDL**：分 `SDL for Function/Method Calls`、`SDL for Void Function Body`。
- **DCR**：把谓词替换为 `true`/`false`，switch 中插入"炸弹"。
- 官方最低要求：**ROR、AOR、LCR、UOI** 四个。

### 5. PIT 的"稳定性"设计哲学（对阙疑最有借鉴价值的一段）

`pitest.org/quickstart/mutators/` 原文的核心设计目标：**"算子尽量保持稳定性（不易被检测）并减少等价变异；不满足要求的算子默认不启用"**。因此 PIT 把算子分成四档：

- `OLD_DEFAULTS`：CONDITIONALS_BOUNDARY、INCREMENTS、INVERT_NEGS、MATH、NEGATE_CONDITIONALS、RETURN_VALS、VOID_METHOD_CALLS
- `DEFAULTS`（现行默认）：以上减 RETURN_VALS，加 EMPTY_RETURNS / FALSE_RETURNS / TRUE_RETURNS / NULL_RETURNS / PRIMITIVE_RETURNS
- `STRONGER`：再加 REMOVE_CONDITIONALS（含 `_EQUAL_IF` / `_EQUAL_ELSE` / `_ORDER_IF` / `_ORDER_ELSE` 四个特化）、EXPERIMENTAL_SWITCH
- `ALL`：再加 INLINE_CONSTS、CONSTRUCTOR_CALLS、NON_VOID_METHOD_CALLS、REMOVE_INCREMENTS，以及全部 `EXPERIMENTAL_*`（ABS/AOR/AOD/CRCR/OBBN/ROR/UOI）

**具体子算子表（可直接抄）**：
- `AOR_1..AOR_4`：对 `+` 分别替换为 `-` / `*` / `/` / `%`
- `CRCR1..CRCR6`：常量 `c` → `1` / `0` / `-1` / `-c` / `c+1` / `c-1`
- `OBBN1..OBBN3`：`a&b` → `a|b` / `a` / `b`
- `ROR1..ROR5`：`<` → `<=` / `>` / `>=` / `==` / `!=`
- `UOI1..UOI4`：`a` → `a++` / `a--` / `++a` / `--a`
- `AOD_1..AOD_2`：`b+c` → `b` / `c`

PIT 明确"**对编译器生成的字节码变异，而非源文件**，因此有时难以映射回源码"——这与阙疑"面向 C++ 源码判决"的定位相反，说明阙疑若要在 Python 侧做变异，**mutmut（AST 层）比 PIT 更贴近**。

### 6. 强/弱变异、等价变异、成本削减（三条必答的审稿问题）

- **强变异 vs 弱变异**（SFU 页面定义）：强变异要求变异体"产生不同输出且测试失败"才算杀死；弱变异只要"变异操作执行后的程序状态可检测地不同"即算杀死。原文："**Weak mutation may be computationally less expensive and also lead to a higher kill ratio**"——阙疑若报高分数，必须说明用的是强变异还是弱变异。
- **等价变异**：有效性定义为 `TS = K/(M−E)`，其中 `E` 为等价变异数；等价性判定**不可判定**，实践中靠人。**LLM 自动判等价的最新工作**：Zhao Tian et al., *"Large Language Models for Equivalent Mutant Detection: How Far Are We?"*，**ISSTA 2024**，DOI **10.1145/3650212.3680395**，在 **3,302 对** method-level Java 变异体上评估。另有 Code Defenders 游戏数据的人工等价变异研究（ICST/Mutation 2024，arXiv:2404.09241）。
- **成本削减三招**（SFU 页面）：① **变异体采样（mutant sampling）**——原文"**even a sample size of 10% can be effective**"；② **选择性变异（selective mutation）**——5-selective 用 ABS/UOI/LCR/AOR/ROR；③ **编译等价检测（trivial compiler equivalence）**——用最高优化档编译，若变异体与原件生成完全相同的目标码则判定等价。
- **LLM 生成变异体（LLMorpheus，2024，arXiv:2404.09952）**：codellama-34b-instruct 在 13 个 JS 项目上生成 **6,712 个变异体**（killed 3,237 / survived 3,155 / timeout 320），耗时合计 **23,890.63 秒**，消耗 **5,841,112 prompt + 721,984 completion = 6,563,096 tokens**，**总成本约 $3.62**（octo.ai 报价 $0.50/M 输入、$1.00/M 输出）；存活变异体中 **63.2% 非等价**（StrykerJS 对照 73%）、仅 **8.5% 等价**。原文点名它能复现真实 issue：`zip-a-folder` #36（`R_OK|W_OK` → 只留 `W_OK`）、`countries-and-timezones` #60（`Math.abs`→`Math.round`）、`image-downloader` #27（`path.resolve`→`path.join`）。
- **C/C++ 侧的最新 SOTA（MOTIF-C++，2025，arXiv:2503.24100）**：fuzzing 驱动的变异测试，"**kills 88.7% of mutants, on average**"，相对符号执行 SOTA（SEMu，基于 KLEE）**高出 13.18–50.33 个百分点**，能检出开发者测试**未检出的 40%–90%** 的变异体；结论中还给出"复用 mutant-killing 输入"的预算阈值 **≥5000 秒/变异体**。原文一句关键判断：**"state-of-the-art mutation testing tools do not target C++ software"**（除 SEMu 外）。
- **C++ 面向对象/类级算子**：Delamaro, Maldonado 等，*"Class mutation operators for C++ object-oriented systems"*，**Annals of Telecommunications 2014**，DOI **10.1007/s12243-014-0445-4**（Springer 全文 PDF 可下）；另有针对 C++11/14 的 4 个新算子（*"Automation and Evaluation of Mutation Testing for the New C++ Standards"*, 2021）。

### 7. C++ 特有的"类级"变异算子：被主流工具系统性遗漏的一层

上面 Mull / PIT / Stryker 覆盖的全部是**语句级与表达式级**算子。但 C++ 作为多范式语言，还有一层**面向对象/模板级**算子，主流工业工具**基本不支持**，而这恰恰是阙疑的知识卡最密集的领域（`atoms/mem/` 有 **23 张**卡，是六个域里最大头）。

**关键论文**：Delamaro, Maldonado 等，*"Class mutation operators for C++ object-oriented systems"*，**Annals of Telecommunications 2014**，DOI **10.1007/s12243-014-0445-4**（Springer 全文 PDF 可下载）。原文定位："this paper aims to introduce a set of mutation operators for **C++ at the class level (by mutating OO features)**"——即专门变异 C++ 的**类级特性**。

**类级算子的典型形态（按 OO 特性归类）**：
- **封装类**：把 `private` 成员改为 `public`、把 `protected` 改为 `public`（访问控制弱化）；
- **继承类**：删除 `virtual`、把 `public` 继承改为 `private` 继承、把虚基类改为非虚基类、改变 `override` 关系；
- **多态类**：把虚函数调用改为静态绑定（去掉 `virtual`）、删除 `final`；
- **构造/析构类**：删除拷贝构造函数、把析构函数改为非虚（**这是 C++ 最经典的 UB 陷阱之一**）、删除 `= delete` 标记；
- **运算符重载类**：把重载运算符替换为默认版本、交换 `operator==` 与 `operator!=` 的语义；
- **模板类**：把模板参数替换为其它类型、把 `constexpr` 去掉、把 `noexcept` 去掉（**去掉 `noexcept` 会让 `std::vector` 的扩容策略从移动退化为拷贝**）。

**第二篇关键论文**：*"Automation and Evaluation of Mutation Testing for the New C++ Standards"*（2021，ResearchGate），原文摘要称"we propose **four new mutation operators for C++11/14** based on common fault patterns"。**注意：本次只拿到摘要级信息，未核实这 4 个算子的名称与定义**（见盲区）。

**这条对阙疑的战略含义**：如果阙疑的 97.3% 是在**语句级算子**上测的，那么它对 `atoms/mem/` 里的 23 张内存域卡片（移动语义、虚析构、迭代器失效、`noexcept` 与容器策略）**几乎没有覆盖力**。**这是一个可以被主动转化为论文亮点的缺口**：阙疑可以声称"我们补齐了主流变异工具缺失的 **C++ 类级算子层**"，并把每个类级算子对应到具体的知识卡。这比"又做了一次通用变异测试"有辨识度得多。

### 8. 等价变异检测的最新工具化进展

除了 §6 提到的 LLM 方法，工程上还有三条可立即使用的路线：

1. **编译器优化档判等（trivial compiler equivalence）**：用最高优化档编译变异体与原件，若生成**完全相同的目标码**则判定等价。**在 C++ 上这条特别有效**——因为 C++ 编译器会做大量常量折叠与死代码消除。**代价**：需要为每个变异体编译一次，成本与变异体数线性相关。
2. **类型检查器过滤**：mutmut 3 已内建 `type_check_command`（仅支持 pyrefly / mypy），用类型检查器拒绝"类型上就非法"的变异体。**C++ 侧对应方案**：把变异体先过一遍编译器，**编译失败的变异体单独计一类**（不是"killed"也不是"survived"）——这正是 Google 论文反复强调的"编译错误"类别。
3. **人工审查 + 抽样估计**：如果变异体数量太大，可以像 OOPSLA 2025 那样**分层抽样**（95% 置信区间、5% 误差），人工判定抽样中的等价比例，再外推总体等价率。**这样可以在论文里给出"等价变异率 = x% ± y%"的可复算区间**，而不是含糊地写"我们做了人工审查"。

**关键提醒**：Google 论文原文明确指出"**The question of equivalence is unfortunately undecidable**"，因此**任何等价变异处理都只能是近似**。阙疑在论文中应当写"我们采用 X 方法近似识别等价变异，识别率的上界由方法 Y 保证"，而不是宣称"我们消除了等价变异"。

### 9. Stryker 的跨语言命名方案（阙疑若扩到多语言可直接复用）

Stryker 支持表（16 类）与 Mutant operator 命名（如 `LessThanBoundary`、`EqualityNegation`、`StrictEqualityNegation`、`AndNegation`、`RemainderToMultiplication`、`BlockRemoval`、`NotRemoval`、`OptionalMemberToRequired`）。其中**正则变异**用 `weapon-regex` 只生成 **Level 1** 变异（如 `^abc`→`abc`、`\d`→`\D`、`(?=abc)`→`(?!abc)`）；**字符串字面量**变异为 `"foo"`→`""`、`""`→`"Stryker was here!"`。这套命名是**跨 JS/.NET/Scala 统一**的，是"算子可移植性"的最佳工程范例。

## 盲区（诚实标注）

1. **阙疑的 `97.3% / 81.5%` 对应的算子集未核实**：`00_仓库扫描.md` 明确写"变异 97.3%/81.5% …… 采信 README/论文/brief 登记，未独立复算"，本文亦未复算。**"core / all"两个口径的分母究竟是什么，目前无法确认**。
2. **Mull 的算子总数 42 是按官方 mutators 页逐行计数得到，官方未给出整数**；若 Mull 后续版本增删算子，该数字需刷新。
3. **Google 论文的 "87% 测试运行失败" 不等于 mutation score**：原文自己强调"**This is not the mutation score**"，因为其变异是概率性的、大量潜在变异体从未被测试。引用时**不可写成"Google 变异得分 87%"**。
4. **LLMorpheus 的成本 $3.62 是 2024 年 octo.ai 对 codellama-34b 的报价**，2026 年价格必然变化；token 数与耗时是原文实测，可直接引用。
5. **MOTIF-C++ 的 88.7% 是在 CPS/嵌入式基准上的平均**，未见其对"通用 C++ 知识验证"场景的外推证据。
6. **C++11/14 的 4 个新算子（2021 论文）我只拿到摘要级信息**（ResearchGate 页面），**未逐条核实算子名称与定义**，列入未核实项。
7. **未查到**：Mull 官方对"等价变异率"的统计；muCPP 的当前维护状态；PIT 的 `STRONGER`/`ALL` 分组在实际项目中的分数差异量化数据。
8. 本文未做任何仓库改动，未跑 mutmut/mull，**所有分数类数字均为二手引用**。
