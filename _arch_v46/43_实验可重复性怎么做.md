# 方向 43：实验可重复性怎么做

> 调研时点：2026-09-29。搜索次数：14（WebSearch 10 + WebFetch 4）。
> 服务对象：阙疑（queyi）的"可被独立验收"主张——67 条规则 / 四态判决 / append-only 哈希链 / 独立对账器；以及 `-O1`→`-O0` 使 3/5 miss 被同一 sanitizer 抓住这条编译档发现。

## 核心结论

1. **可重复性有一套现成的、被 ACM 官方定义的"三级词汇表"，阙疑必须对号入座**：ACM 的定义是 **Repeatability（自己重复自己）/ Reproducibility（独立方用你的 artifact 得到同样结果）/ Replicability（独立方用完全自研的 artifact 得到同样结果）**。阙疑主张的是 **Reproducibility**（"可被独立验收"），因此验收标准应当是"审稿人拿到我的 artifact 包，在**他们的机器**上跑出同样数字"，而不是"我自己在本机跑出同样数字"。
2. **容器不是可重复性的银弹，实测数据极其惨烈**：《It's Not Just Timestamps: A Study on Docker Reproducibility》（arXiv:2602.17678，2026-02）在 **2,000 个 GitHub 仓库**上实测，**43.9% 的仓库根本构建不起来**；在能构建的 1,123 个里，**默认配置下只有 2.7% 能按位复现**，即便启用 `SOURCE_DATE_EPOCH` 等硬化手段也只提升到约 **21.3%**，**仍有 78.7% 不可复现**。**结论：写个 Dockerfile 不等于可复现，必须显式处理时间戳、文件排序、缓存与日志。**
3. **对阙疑这种 CPU + Python + C++ 的项目，最高性价比的三件事是"锁文件 + 随机源审计 + 单一入口脚本"**：因为阙疑的随机性来源不是 GPU 卷积算法（PyTorch 那套 `cudnn.benchmark` 问题对它是次要的），而是 **Python 的 `PYTHONHASHSEED`、dict/set 遍历顺序、`random`/`time`/`uuid`、以及 C++ 编译档（`-O0/-O1/-O2`）**——`-O1`→`-O0` 改变检测结果这件事本身就是"环境即结果"的铁证。

## 精确数字与案例

### 1. ACM Artifact Review and Badging：官方三级定义与三枚徽章

ACM 官方（reviewers.acm.org/training-course/artifact-review-and-badging，指向 acm.org/publications/policies/artifact-review-and-badging-current）给出的**逐字定义**：

- **Artifact（制品）**：作者创建的、或实验本身生成的数字对象（软件系统、实验脚本、输入数据集、原始数据、分析脚本）。
- **Repeatability（可重复）**：一位研究者能可靠地重复**自己**的计算或结果。
- **Reproducibility（可复现）**：一个**独立团队**能用**作者自己的 artifact** 得到同样结果。
- **Replicability（可复证）**：一个独立团队能用**他们完全独立开发的 artifact** 得到同样结果。

**ACM 推荐三枚独立徽章**（可单独获得，也可全部获得）：

1. **Artifacts Available**（制品可用）——artifact 被永久公开归档（通常要求 DOI / 长期仓库）。
2. **Artifacts Evaluated: Functional / Reusable**（制品已评估：功能性 / 可复用）——功能性指"审稿人能跑通并得到与论文一致的结果"；可复用指"质量高到可被他人作为基础继续开发"。
3. **Results Validated: Reproduced / Replicated**（结果已验证：可复现 / 可复证）——对应上文的 Reproducibility / Replicability。

**关键含义**：这三枚徽章是**"独立审计"的产物**，不是作者自评。ACM 原文第一句："An experimental result is not fully established unless it can be independently reproduced."（一个实验结果只有能被独立复现才算真正成立。）

**NeurIPS 侧（ML 社区）的对应物**：
- **NeurIPS Paper Checklist 第 4 项**（Experimental Result Reproducibility）原文："If the contribution is a dataset or model, what steps did you take to make your results reproducible or verifiable?"，并强调"**While NeurIPS does not require releasing code, we do require all submissions to provide some reasonable avenue for reproducibility**"——即**不强制开源，但强制"给出可复现路径"**。
- **第 5 项**（Open Access to Data and Code）原文："did you include the code, data, and instructions needed to reproduce the main experimental results...? **The instructions should contain the exact command and environment needed to run to reproduce the results.**"——"**确切的命令与环境**"是硬要求。
- **第 7 项**（Experiment Statistical Significance）与第 8 项（Compute Resource）也是可重复性的组成部分：误差棒要"appropriately and correctly defined"，且**要说明"the factors of variability that the error bars are capturing"**；算力要写"type of compute workers, memory, time of execution"。
- **重要**：**未包含检查清单的论文会被直接拒稿（desk reject）**；检查清单不计入页数限制。这条对阙疑是零成本的合规要求。
- 历史沿革（Barba, HDSR）：**NeurIPS 2019 首次设立 "reproducibility chair"**；ICML 2019 首次鼓励提交代码（3,000+ 投稿中 36% 带代码，774 篇录用中 67% 带代码）；NeurIPS 2019 的 6,743 篇投稿中 40% 带代码，**录用论文中 74.4% 带代码**。

### 2. Docker 可复现性实测：43.9% 构建失败，2.7% 按位可复现

《It's Not Just Timestamps: A Study on Docker Reproducibility》（arXiv:2602.17678，2026-02）是目前最直接回答"容器能不能保证可复现"的实证研究。方法与数字：

**样本**：从 2024 年修改过 Dockerfile 且 star ≥ 5 的 **19,262 个 GitHub 仓库**中，按 star 分四档（5–7 / 8–19 / 20–82 / >82）分层随机抽取 **2,000 个**。

| 指标 | 数量 | 占比 |
|---|---|---|
| 可构建（至少一个 Dockerfile 能 build） | 1,123 | **56.1%** |
| **不可构建（构建失败）** | 877 | **43.9%** |
| 其中：**开箱按位可复现** | 30 | **2.7%** |
| 其中：基础设施修复后可复现 | 209 | **18.6%** |
| 其中：**仍然不可复现** | 884 | **78.7%** |

**不可复现的根因分布**（基于 **954 份 diffoscope 报告**）：

| 根因 | 占比 |
|---|---|
| **时间戳与元数据**（timestamps & metadata） | **100.0%**（954/954） |
| 格式 / 文件排序（file ordering） | **78.1%** |
| **系统日志**（`/var/log/`，如 `dpkg.log`、`apt/term.log`） | **43.3%** |
| 缓存与数据库（如 `ldconfig/aux-cache`、`fontconfig/`） | **36.8%** |
| 编译产物（ELF 二进制、字节码） | **20.0%** |
| 应用特定文件 | **13.0%** |
| **随机 / 非确定性数据** | **9.4%** |
| 包管理器状态 | **5.6%** |
| pip/Python 相关（`.pyc`、`site-packages/`） | 7.7% |
| npm/Node.js | 1.7% |
| Maven/Java | 0.8% |

**官方镜像验证案例（附录 A.1）**：对官方 `golang:1.25.5-alpine3.22` 镜像按相同 Dockerfile 与构建上下文重建，**5 个层中有 2 个不匹配**（Layer 2 大小 291,165 vs 291,156 字节；Layer 4 大小 124 vs 126 字节），镜像 config 摘要长度 2,165 vs 2,171 字节。**连官方镜像都无法按位重建**——这是本方向最有冲击力的单个数字。

**论文的核心结论（原文语义）**：即便硬化基础设施，也只有约**五分之一**的可构建 Dockerfile 支持基于哈希的重建比对检查，**限制了"可复现构建"作为常规完整性机制的实用价值，且责任正从基础设施转向开发者**。

**对应的标准**：**reproducible-builds.org 的 `SOURCE_DATE_EPOCH` 规范**（specs/source-date-epoch/，2018-05-15）——一个**发行版无关**的标准，让上游构建过程消费统一的时间戳（通常取源码最后一次修改时间/Git 提交时间），从而消除"构建时间"这个最大的非确定性来源。Docker/BuildKit 支持 `rewrite-timestamp` 与 `SOURCE_DATE_EPOCH` 来改写镜像层时间戳。

### 3. 随机种子：PyTorch 官方文档的完整清单（可迁移到任何 Python 项目）

PyTorch 官方 *Reproducibility* 文档（docs.pytorch.org/docs/main/notes/randomness.html，2026-05-14 更新）开篇即警告：

> "**Completely reproducible results are not guaranteed across PyTorch releases, individual commits, or different platforms. Furthermore, results may not be reproducible between CPU and GPU executions, even when using identical seeds.**"

官方给出的**完整控制清单**（原文代码）：

```python
import torch, random, numpy as np
torch.manual_seed(0)          # 所有设备（CPU + CUDA）
random.seed(0)                # Python 自定义算子
np.random.seed(0)             # NumPy 全局 RNG（注意：Random Generator 对象需单独 seed）

# 关闭 cuDNN 卷积算法自动基准测试（避免"同一台机器不同次运行选不同算法"）
torch.backends.cudnn.benchmark = False

# 强制确定性算法；遇到没有确定性实现的算子直接抛错
torch.use_deterministic_algorithms(True)

# 仅控制卷积确定性（与上面不同）
torch.backends.cudnn.deterministic = True
```

**文档中的关键细节**（很多教程会漏）：
- `torch.use_deterministic_algorithms(True)` 会让**没有确定性实现的算子直接抛 `RuntimeError`**（例：`index_add_cuda_`），并**默认把未初始化内存填充为已知值**（`torch.utils.deterministic.fill_uninitialized_memory = True`），代价是性能下降。
- **SDPA（scaled_dot_product_attention）的四个后端确定性不同**：`MATH` 前后向都确定；`FLASH_ATTENTION` / `EFFICIENT_ATTENTION` / `CUDNN_ATTENTION` **前向确定、反向不确定**（用原子操作）；只有 `torch.use_deterministic_algorithms(True, warn_only=False)` 才真正强制，`warn_only=True` 只警告不生效。
- **低精度下不同后端"不保证按位一致"**：因为浮点加法不满足结合律，累加顺序不同结果就不同。
- **DataLoader 的多进程随机性**必须用 `worker_init_fn` + `generator` 固定：

```python
def seed_worker(worker_id):
    worker_seed = torch.initial_seed() % 2**32
    numpy.random.seed(worker_seed); random.seed(worker_seed)
g = torch.Generator(); g.manual_seed(0)
DataLoader(..., worker_init_fn=seed_worker, generator=g)
```

**对阙疑的映射**：阙疑不用 CUDA，但**同类陷阱在纯 Python/C++ 里同样存在**——`PYTHONHASHSEED`（默认随机化，导致 `set`/`dict` 遍历顺序在跨进程间变化）、`dict` 插入顺序、`os.listdir` 返回顺序、`time.time()`/`datetime.now()` 写入账本、`uuid4()`、`random` 未 seed、`hash()` 结果、C++ 侧 `std::unordered_map` 遍历顺序与 `-O` 级别。**PyTorch 文档的"跨版本/跨平台不保证"这句话，对阙疑的 `gate_engine.py 3826 行` 同样适用。**

### 4. 环境锁定：四种锁文件与一份 SBOM

| 工具 | 锁文件 | 关键特性 |
|---|---|---|
| **uv**（Astral，Rust 实现） | `uv.lock` | 锁定**直接与传递依赖的版本 + 内容哈希**；`uv export` 可导出为 `requirements.txt`、**PEP 751 的 `pylock.toml`**、或 **CycloneDX v1.5 SBOM** |
| **pip-tools** | `requirements.txt`（`pip-compile` 生成，含 `--hash=sha256:...`） | 最经典；`pip install --require-hashes` 可强制校验 |
| **Poetry** | `poetry.lock` | 含每个包的哈希；`poetry install --no-root` |
| **conda-lock** | `conda-lock.yml` | 为每个平台（linux-64/osx-arm64/win-64）生成独立锁定，解决 conda 跨平台解析差异 |

**PEP 751** 是 Python 官方正在标准化的 `pylock.toml` 锁文件格式；**CycloneDX** 是 SBOM（软件物料清单）标准，`uv export --format cyclonedx1.5` 可直出——**对阙疑的"供应链台账"主张，SBOM 是最标准的载体**。

**容器侧**：`Dockerfile` 必须用 **digest 而非 tag** 固定基础镜像（`FROM python:3.12-slim@sha256:...`），因为 tag 是浮动的；`docker pull` 后 `docker inspect --format='{{index .RepoDigests 0}}'` 可取 digest。

**HPC 侧（对"合肥 + 嵌入式"作者可能相关）**：**Apptainer（原 Singularity）** 于 **2024-05-13 迁移至 Linux Foundation 并正式更名**；核心特性是**镜像内外 UID/GID 一致**（无需 root 即可运行）、**SIF（Singularity Image File）只读镜像格式** + 可写 sandbox 目录、**兼容 OCI/Docker 镜像**（可直接从 Docker Hub 拉取运行）。一篇 2024 IEEE BigData 论文（DOI 10.1109/BigData62323.2024.10825376）报告在 Pegasus 超算上用 Singularity + Nextflow 使工作流运行性能提升 **3×**（单篇论文声明，非通用结论）。

### 5. Ten Simple Rules（Sandve et al., 2013）：最经典的清单

**Sandve GK, Nekrutenko A, Taylor J, Hovig E (2013), "Ten Simple Rules for Reproducible Computational Research", PLoS Comput Biol 9(10): e1003285, DOI 10.1371/journal.pcbi.1003285。** 十条规则逐字标题：

1. **For Every Result, Keep Track of How It Was Produced**（每个结果都要能追溯它是怎么产生的）
2. **Avoid Manual Data Manipulation Steps**（避免手工数据操作）
3. **Archive the Exact Versions of All External Programs Used**（归档所用外部程序的**确切版本**）
4. **Version Control All Custom Scripts**（所有自研脚本纳入版本控制）
5. **Record All Intermediate Results, When Possible in Standardized Formats**（尽可能用标准格式记录中间结果）
6. **For Analyses That Include Randomness, Note Underlying Random Seeds**（含随机性的分析必须记录随机种子）
7. **Always Store Raw Data behind Plots**（图背后的原始数据要留存）
8. **Generate Hierarchical Analysis Output**（生成可逐层检查的层级化输出）
9. **Connect Textual Statements to Underlying Results**（论文中的陈述要能连回具体结果）
10. **Provide Public Access to Scripts, Runs, and Results**（公开脚本、运行记录与结果）

**原文中的关键补充**：Rule 3 指出"为确保未来可用性，唯一可行的方案可能是存储**操作系统和程序的完整虚拟机镜像**"，最低要求是"记录所用主要程序的确切名称和版本"；Rule 2 指出"手动操作不仅低效、易错，而且**难以复现**"，最低要求是"记录哪些数据文件被修改或移动、出于什么目的"；Rule 4 强调"对计算机程序即使**最微小的改动**也可能带来重大后果"。

**对阙疑的直接映射**：Rule 1 = 哈希链 + 452 条账本；Rule 2 = 67 条规则全自动判决（无手工判定）；Rule 3 = 需补 gcc/clang/python 版本归档；Rule 4 = git 已有；Rule 5 = 四态判决 + 证据带 provenance；Rule 6 = **需补随机种子记录（当前可能缺失）**；Rule 7 = 需补 holdout reveal 的原始输出；Rule 8 = 需补分层结果（A/B/C 层）；Rule 9 = 需补 claim→结果的映射表；Rule 10 = 需补 artifact 包。

### 6. 复现率的硬数字（与方向 42 交叉）

**Gundersen 等（AAAI 2025，arXiv:2412.17859）**：30 篇高被引 AI 研究中 **8 篇因数据/硬件不可得而排除**，**6 篇完全复现 + 5 篇部分复现 = 50%**；**共享代码+数据的论文 86% 可复现，只共享数据的 33%**。

**TechRxiv 2025 综述**（doi:10.36227/techrxiv.177155769.94899097）把复现障碍分为三类并给出五步模型：
- 技术障碍：**不确定性（nondeterminism）+ 环境不稳定**；
- 方法障碍：**报告差 + 评估陷阱**；
- 文化障碍：**激励结构**；
- 五步模型：**协议定义 → 环境规格 → 实验追踪 → 验证协议 → artifact 准备**。

**NeurIPS 2025 规模参照**：第三方统计（intuitionlabs.ai PDF）称 NeurIPS 2025 于 2025-12-02 至 12-07 在圣地亚哥举办，**接收 5,290 篇论文**（**该数字未在 NeurIPS 官网核实，列为盲区**）。E&D track 的复现要求与主 track 一致（同一份 Checklist）。

## 对阙疑的 3 条具体行动

1. **本周内：随机源审计 + 锁文件（半天工作量）**。
   - 全仓库扫描非确定性来源：`grep -rn "random\|time\.\|datetime\|uuid\|hash(\|os\.listdir\|set(" tools/gate_engine.py`，把每一处归类为"必须固定"或"必须记录"；
   - 在 `gate_engine.py` 入口加 `os.environ["PYTHONHASHSEED"]="0"` 检查（若未设置则打印警告并 fail-closed），所有 `random`/`np.random` 走显式 `--seed` 参数；
   - 生成 `requirements.lock`：`pip install pip-tools && pip-compile --generate-hashes -o requirements.lock requirements.in`，CI 里用 `pip install --require-hashes -r requirements.lock`；若已用 uv，则提交 `uv.lock` 并额外 `uv export --format cyclonedx1.5 -o sbom.json`（**SBOM 直接补上"供应链台账"的标准化缺口**）。

2. **本月内：写一个"单命令可复现入口" + 一份"环境清单"，并做 `-O` 级别矩阵实验**。
   - 入口：`python tools/reproduce_665.py --seed 0 --out results/repro_665/`，它必须能**从零跑完** holdout 30 + corpus 40 + defects 15，并把结果写成 JSON；
   - 环境清单 `ENVIRONMENT.md`：Python 版本、gcc/clang 版本（`gcc --version`）、`-O0/-O1/-O2` 三档、ASan/UBSan 版本、OS 版本、CPU 型号、以及 `sha256` 校验和；
   - **重点做 `-O` 矩阵**：论文 v0.3 已记录"`-O1`→`-O0` 使 3/5 miss 被同一 sanitizer 抓住"——把这条从一个观察升级为一张**完整的三档 × 15 缺陷夹具矩阵表**（`-O0/-O1/-O2` × 15 = 45 格），并把它作为论文 §Reproducibility 的核心图表。**这张表是"环境即结果"的最强证据，也是审稿人最想看的东西。**

3. **投稿前（2027）：按 ACM badge 自评并打包 artifact**。
   - **Artifacts Available**：把仓库打 tag（如 `v1.0-neurips2027`），推 Zenodo 拿 DOI（Zenodo 与 GitHub 集成，一个 release 一个 DOI）；**注意先做方向 41 的密钥轮换与清理**，否则 artifact 包会带上 `data/vsa_secret.key` 与 `.env`；
   - **Artifacts Evaluated: Functional**：写 `README_ARTIFACT.md`，含"**确切命令与环境**"（对应 NeurIPS Checklist 第 5 项原文要求），以及一条"从干净容器到得到论文 Table 1 数字"的完整步骤；用 **digest 固定**的基础镜像（`FROM python:3.12-slim@sha256:...`），并设 `SOURCE_DATE_EPOCH`；
   - **Results Validated: Reproduced**：主动在 artifact 包里附一份**"独立对账器"的复现说明**（这是阙疑相对其他论文的独特优势——它天生就有一个"不依赖内核"的独立验证路径，正好对应 ACM 的 Reproducibility 定义）。**把这句写进论文："我们的 artifact 包含一个独立于 gate_engine 的对账器，审稿人可用它在自己的机器上验证哈希链与判决账本，无需信任我们的内核。"**

## 盲区（诚实标注）
